# 0055. Evidence object format

- Status: accepted
- Date: 2026-11-05
- Ticket: R3.01
- Amends: [0003](0003-sqlite-for-daemon-metadata.md) (evidence envelopes in `reef.sqlite3`), [0029](0029-daemon-api-v1.md) (decision 12's exceptions)

## Context

The [design](../design.md)'s fifth object is evidence: "a signed attestation: the snapshot hash it was computed on, the attestor identity, the kind (test, build, lint, policy), result, and an optional artifact hash" (Data model), "content-addressed objects linked to the snapshot they were computed against" (principle 7). The landing gate checks a chain of five links ("What evidence proves"): a claim bound to an exact tree hash, an attestation that signs the claim in a standard envelope, an attestor policy trusts, policy satisfaction, and coverage. R3.01 builds the first two. Trust is R3.03 (session keys) and R3.07 (policy); satisfaction is R3.07 and R3.13; coverage is R3.18 and R3.19.

Executors are built against this format: R3.05 writes the protocol, R3.06 the reference executor, and anyone may write another. The format is the part that cannot be cheaply changed. The design keys evidence by tree hash ("an identical tree is never tested twice", CI load; "verifies that each evidence object's snapshot hash matches the submitted tree", Landing). The technology table names in-toto attestations in DSSE envelopes. ring is the tree's only crypto provider, and `crate_graph` keeps aws-lc and OpenSSL out. None of the Rust in-toto, DSSE or sigstore crates is both maintained and conformant, and sigstore's needs aws-lc-rs or OpenSSL (the R3.01 brief records what was checked).

## Decision

1. **Evidence is bound to the tree.** The Statement has exactly one subject, `{"name": "tree", "digest": {"gitTree": <lowercase hex tree id>}}`, of the repository's object id length (40 with SHA-1 git, 64 with SHA-256 git). The name must be exactly `tree`, so two producers write the same bytes, and no other digest key is accepted in format 1; the subject's optional `uri`, `mediaType` and `annotations` must have their in-toto types. A commit id changes on every describe and rebase, while the tree, and the evidence about it, stays; two changes with one tree share their evidence. A conflicted tree has no single id, so it has no evidence. The data model's "snapshot hash" is the snapshot's tree hash, and ADR 0011's "a hash qualified by its backend" is met by the DigestSet key; Phase 4's backend will use a documented key of its own in the same position.
2. **An in-toto Statement v1 with Reef's predicate.** `predicateType` is `urn:reef-vcs:evidence:v1`. The predicate's fields are `kind` (required; an open vocabulary, `^[a-z][a-z0-9-]{0,62}$`, in which `test`, `build`, `lint` and `policy` are the design's), `result` (required; `pass`, `fail`, or `error`: no verdict, which is not a failure of the tree), `target` (optional, 1 to 512 bytes without control characters; absent means the whole check of that kind), `startedOn` and `finishedOn` (required; exactly `YYYY-MM-DDTHH:MM:SS[.fraction]Z`, one to nine fraction digits, from 1970 to 9999, with no leap second, and the finish not before the start), `artifacts` (optional, at most 64 ResourceDescriptors, each with a `name` and a `sha256` digest; the bytes need not exist anywhere), and `annotations` (an optional object of the producer's own, which Reef never reads and never defines a field in). Unknown predicate fields are kept and ignored. There is no attestor field and no change or commit id in the claim.
3. **A DSSE v1 envelope with one signature; the payload as signed, the envelope canonical; the id its SHA-256.** `payloadType` is `application/vnd.in-toto+json`, and an envelope has exactly one signature: one attestor per object, as the data model has it, and a sigstore bundle v0.3 accepts only one. The payload is UTF-8 JSON with no duplicate key at any depth, kept byte for byte as signed; Reef's producer writes it compact, keys in a fixed order. The stored envelope is rewritten as compact JSON with exactly `payload`, `payloadType` and `signatures` (`keyid`, `sig`), in that order, with padded standard base64 and no trailing newline; unknown fields are dropped, and the signature, over the pre-authentication encoding, stays valid. The evidence id is the SHA-256 of those canonical bytes, in lowercase hex. An envelope is at most 64 KiB and nests at most 32 levels.
4. **ed25519 through ring; keys as SubjectPublicKeyInfo, key ids as its SHA-256; the attestor is the key.** The caller signs; the daemon verifies and holds no evidence-signing key. A public key travels as DER SubjectPublicKeyInfo, so it names its algorithm, and its id is the SHA-256 of that DER (`openssl pkey -pubin -outform DER | shasum -a 256`, sigstore's recommended hint). The envelope's `keyid` must equal it, a consistency check and never a security decision. The eight small-order points and non-canonical encodings are refused, closing the gap between ring's verification and strict verification. Private keys are PKCS#8 PEM, v1 or v2. R3.03 binds keys to identities; until then a key is an attestor nobody has vouched for.
5. **Storage in `reef.sqlite3`, keyed by repository, linked by tree and by change.** Migration `0007_evidence` adds `evidence` (the canonical envelope and index columns read from its verified payload), `evidence_keys` (machine-wide) and `evidence_links` (the change an add named, and the commit it resolved to). The envelopes are small, authoritative and not rebuildable, so they sit beside their index, and backups ([0020](0020-local-backup-format.md)) carry them unchanged; this amends [0003](0003-sqlite-for-daemon-metadata.md), whose database held the index. The evidence on a revision is the evidence on its tree; a link outlives its commit, and a listing by change marks each object `current` or not. A describe or tree-keeping rebase keeps both; an edit leaves the evidence and the link and makes the link not current; abandon, undo and GC change nothing (`GetEvidence` works after the tree leaves the store); backup and restore copy all three tables; `repo forget` deletes the repository's evidence and links and keeps the keys. Nothing else deletes evidence until R3.02's retention.
6. **No operation in the log.** Evidence is an immutable object, not a change to the view: there is nothing for undo to revert, and an operation per object would fill the log the design wants legible with more evidence than code. `AddEvidenceResponse` has no `operation`; [0029](0029-daemon-api-v1.md) decision 12's exceptions gain `AddEvidence` and `UploadScipDocuments`, which they had missed. Remote writes are traced by the remote listener's audit log, as every remote write is.
7. **"Valid" means integrity and signature only.** A stored object's signature is `SIGNATURE_CHECK_VALID` when its id is the SHA-256 of its canonical bytes, its one signature verifies over the payload with the recorded key, its `keyid` is that key's id, and every index column of its row equals what the verified payload says. The daemon checks this at add, in the order envelope, key, signature, payload (so unsigned junk never reaches the statement parser), and again at every read. A read takes every field from the payload, never from the index columns, and a filtered listing checks each object's payload against the filter again, so a row changed in the database, envelope or columns, reads `SIGNATURE_CHECK_INVALID` with the payload's own values and is never presented as matching a filter its payload does not. Re-adding the genuine envelope repairs such a row. Nothing in the API says "trusted": R3.07 evaluates trust and R3.13 refuses on it.
8. **The stability rules.** Format 1 is fixed: Statement v1, the payload type, one signature, the subject rule, the v1 predicate type and its fields, SHA-256 ids over the canonical envelope, and SPKI key ids. Fields are only added: a later Reef may add optional predicate fields, which never change what an existing field means, and a v1 reader that ignores them reaches the same decision. Producer data goes in `annotations`. A change of meaning is a new predicate type (`…:v2`), accepted beside v1; a daemon never rewrites a stored payload or drops a format it once read. Ids never change: a new canonical form would be a new `format`, with its own id rule and column value. Until 1.0, a breaking change to format 1 still needs an ADR that supersedes this one and a migration of stored rows.

## Consequences

- An executor in any language builds evidence from `docs/evidence.md` and `reef schema evidence`, signs it with its own key, and adds it by tree; R3.06's will use `reef-evidence` and an R3.03 session key.
- Anyone can add evidence that reads `signature: valid`, including an agent attesting its own tests (threat model S-48). Until R3.07, reading `valid` as "trusted" is wrong, and the CLI prints the key id, never a name.
- Evidence grows `reef.sqlite3` and every backup by about 1 to 2 KiB per object, with no bound until R3.02 (S-52).
- The subject is a SHA-1 tree id while the repository is on jj's git backend, ADR 0011's known weakness: a chosen-prefix collision on a tree would let one claim cover two trees. The `gitTree` key states the algorithm, and Phase 4's backend changes the key.
- `reef-evidence` depends on no Reef crate but `reef-error` and links no jj-lib, gRPC, tokio or SQLite, so the executor and the Phase 4 store read the format without the client.

## Alternatives considered

- **The commit as the subject.** It dies with every describe and rebase, and contradicts "keyed by tree hash".
- **Both the tree and the commit as subjects.** A second subject makes the statement a claim about the commit too.
- **in-toto's `test-result` for tests, and other predicates for the rest.** No kind, no target and no `error` result, and three predicate types for policy to read.
- **SLSA provenance.** It describes building artifacts, not checking a source tree.
- **A canonical payload (RFC 8785).** DSSE avoids canonicalization by signing bytes, and a canonicalization rule would refuse ordinary encoders' output.
- **The id as the SHA-256 of the payload.** Two signers' envelopes of one claim would merge into one object.
- **BLAKE3 ids.** These ids leave Reef (federation, sigstore tooling, a transparency log entry), and that ecosystem identifies envelopes by SHA-256; ADR 0011 is about object identities, which evidence ids are not.
- **Envelopes as files under `repos/<id>/evidence/`.** A second store to back up and keep in step with the index.
- **Envelopes as git blobs or refs in the jj repository.** git GC deletes unreferenced blobs, and refs would show up in the user's `git` and be pushed.
- **A jj operation per evidence object.** Log volume, and nothing to undo.
- **The `in-toto`, `dsse` or `sigstore` crates.** `in-toto` 0.4 implements Statement v0.1 only and its DSSE is not conformant; `dsse`'s repository is archived; `sigstore` 0.15 needs aws-lc-rs or OpenSSL, which the ring-only rule keeps out, and cannot sign DSSE.
- **A daemon-held signing key.** The daemon did not run the check; session keys for those who do are R3.03's.
