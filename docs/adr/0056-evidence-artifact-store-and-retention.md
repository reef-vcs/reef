# 0056. Evidence artifact store and retention

- Status: accepted
- Date: 2026-11-06
- Ticket: R3.02
- Amends: [0055](0055-evidence-object-format.md) (decision 5: retention deletes evidence), [0020](0020-local-backup-format.md) (the layout gains `repos/<id>/artifacts/`), [0029](0029-daemon-api-v1.md) (decision 12's exceptions gain `UploadArtifact`)

## Context

[0055](0055-evidence-object-format.md) records what a check produced only as digests: each predicate lists at most 64 artifacts, each a `name` and a `sha256`, and the bytes need not exist anywhere. It stores evidence with no deletion except `repo forget`, and leaves the retention of evidence objects to R3.02 (threat model S-52: nothing bounds how many objects a writer adds).

The [design](../design.md) names both halves. Its data model: "Artifacts live in a separate store with its own retention policy, since evidence volume outgrows code volume at agent scale". Its durability table: artifacts are authoritative "within retention", rebuilt by "re-running the executor". The executor protocol's response is "a set of signed evidence objects plus artifacts" (R3.05), and the proposal view shows a check's log beside its result (R3.31).

Client streaming is ruled out: [0029](0029-daemon-api-v1.md) decision 13 keeps streaming server-side because the web UI reaches the API over gRPC-web, and both SDK generators refuse a client-streaming RPC. The largest unary request tonic decodes by default is 4 MiB. GC ([0040](0040-gc-and-the-users-jj-workspaces.md), [0041](0041-gc-on-a-timer.md)) runs per repository under its create lock, with `keep_newer` (the undo window, widened to the backup retention while the last backup is within it) as the floor every step honours, and already has a mark, sweep and cap step for the symbol index.

## Decision

1. **Bytes are content-addressed files per repository; the index is in `reef.sqlite3`.** A stored artifact is `<state>/repos/<id>/artifacts/sha256/<first 2 hex>/<remaining 62 hex>`, mode `0444`; a partial upload is `artifacts/incoming/<sha256>.<size>`. Files stream, read in ranges at no cost, and clone on APFS; blobs in the database would sit in the WAL, the database lock and every backup's page-by-page copy. The index is migration `0008_artifacts`: `artifacts` (size, `stored_at`, `used_at`, `collected_at`, the adder) and `evidence_artifacts` (which digests each evidence object's payload names, written in `AddEvidence`'s transaction from the verified payload, with no foreign key to `artifacts`, since evidence may name bytes never uploaded). Evidence stored under schema 7 is indexed once at the first start by a Rust step after the migrations, the database's first, which reads the payloads without checking signatures: the index only steers retention. Everything is keyed by repository ([0003](0003-sqlite-for-daemon-metadata.md)): two repositories holding the same bytes hold two copies, `repo forget` deletes the rows and the files with `repos/<id>/`, and a remote token's rule for uploads is `AddEvidence`'s. Only a digest checked as 64 lowercase hex digits builds a path, so no request text reaches the filesystem.
2. **The seam is `ArtifactBytes`, at the bytes, not the index.** A trait with blocking methods (`received`, `append`, `check`, `commit`, `open`, `stat`, `remove`, `stored`, `sweep_incoming`), run on the blocking pool; `LocalArtifacts` implements it over decision 1's layout. A remote implementation (R4.02's blob storage, or a team's own) replaces `LocalArtifacts` and nothing above the trait changes: the service, the index, retention and the CLI only call the trait, and the daemon still decides what evidence names and what retention keeps. A remote implementation may make the methods async in its own ticket, which changes signatures, not the seam. This ticket builds no remote store and no setting to choose one.
3. **Upload is chunked unary calls keyed by digest and size; download is one server stream that re-hashes a whole read.** `UploadArtifact { repo, sha256, size, offset, data }` answers `{ received, artifact, created }`. A stored digest (its row stored and its file present at the row's size) answers at once with `received = size` and `created: false`, whatever `data` holds, and marks the artifact used: that is dedup, and an empty call at offset 0 is the probe. Otherwise `offset` must equal the bytes received (`ARTIFACT_OFFSET_MISMATCH`, metadata `received`), the chunk (at most 1 MiB) is appended, and once the bytes reach `size` the daemon hashes them without the lock, then, holding it, checks that the repository is still registered (`REPOSITORY_NOT_FOUND` once it was forgotten) and stores them (`ARTIFACT_DIGEST_MISMATCH` deletes the partial upload); the row is inserted only while the repository's row exists, and no store method creates a directory above `artifacts/`, so nothing outlives a forget. The digest names the upload, so a lost response is retried from the mismatch's `received`, a client that comes back after a restart resumes from the probe, two clients uploading the same bytes share one partial upload, and no session state exists to expire. `max_object_size` is checked on every call, after the dedup check (so a stored artifact is still found once the limit is lowered) and before anything is written. Each repository has an `ArtifactLock`, held by GC while it collects, by `ForgetRepository`, by an upload's commit (the rename and the row), by an upload's stored-digest answer when a stored row matches, and by a damaged read's quarantine while it deletes, so a client never hears "stored" for bytes GC is deleting; appends, hashing, and a stored-digest check that finds no row do not take it, so a chunk costs no write and no wait for GC. `ReadArtifact` streams messages of at most 1 MiB, the first carrying the record. A read of the whole artifact hashes what it sends: bytes that no longer match end the stream with `ARTIFACT_DAMAGED` after the data, and the daemon hashes the file again and, if it is still wrong, takes the lock and, unless an upload repaired it meanwhile, makes the row a tombstone and deletes the file, so the artifact reads as collected and the next upload of the genuine bytes repairs it. A stored row whose file is gone, or of another length than the row's size, is `ARTIFACT_DAMAGED` (`missing`, `size`) before any data, and does not count as stored for an upload. `ReadArtifact` stays `NO_SIDE_EFFECTS` and `ACCESS_READ`: its one effect is removing bytes that already fail their own digest (threat model S-56). Uploads record no operation: decision 12's exceptions in [0029](0029-daemon-api-v1.md) gain `UploadArtifact`, and remote uploads are traced by the remote listener's audit log. The web listener serves `GetArtifact` and `ReadArtifact` by their `ACCESS_READ` classification; the bytes travel as protobuf `bytes` in gRPC-web, never as an HTTP resource a browser could render.
4. **Live work is `trunk() | bookmarks() | working_copies() | mutable()`, and it pins evidence and artifacts.** That is `reef log`'s default set plus every local bookmark's target, evaluated with Reef's own aliases so it does not depend on the user's jj configuration, once per GC run on the read pool. Evidence is pinned when its tree is a live commit's tree, or when a link ties it to a live change (an open change's evidence on its earlier trees, which R3.15's transfer rules read). An artifact is pinned when pinned evidence names it. Pinned evidence and pinned artifacts are never deleted by age or by the cap. R3.13 adds the landing pin: until then, evidence on old trunk commits that no bookmark keeps expires.
5. **GC's seventh step sweeps, caps and tidies, with every cutoff floored at `keep_newer`.** After history and before the reindex, under the create lock, honouring `dry_run`: evidence that is not pinned and was added before `min(now - [evidence] retention, keep_newer)` is deleted with its links and index rows, 1,000 objects per transaction; `evidence_keys` stay. Then, holding the `ArtifactLock` and touching nothing used at or after `keep_newer`: an artifact no evidence names goes, row and file, once used before `min(keep_newer, now - 1 day)` (`UPLOAD_GRACE`), so an upload waiting for its `AddEvidence` keeps a day even with `[gc] undo_window = "0s"`; one named only by evidence that is not pinned is collected once used before `now - [artifacts] retention`; then, while the stored bytes pass `[artifacts] max_size`, the least recently used of what may be collected and is past the upload grace goes. Last, the tidy deletes tombstones no evidence names, partial uploads last written more than a day ago (not in backups, so the backup floor does not apply), and stored files with no stored row older than an hour, and makes a stored row whose file is missing a tombstone. A row change commits before its file is removed, so the database never names stored bytes GC removed. A failure is logged and the run goes on, as for the cache steps, but `GcReport.evidence_error` reports it and `reef ws gc` exits 8, since these are authoritative data. Defaults: `[evidence] retention` 90 days, `[artifacts] retention` 30 days, `max_size` 10 GiB, `max_object_size` 1 GiB; a retention of `0s` turns that age rule off. `max_size` is GC's target, not a quota: no upload is refused for the store's size.
6. **Collected artifacts keep a tombstone; deleted evidence keeps none.** An artifact whose bytes retention removed while evidence still names it keeps its row with `collected_at`, so a reader sees `ARTIFACT_STATE_COLLECTED` and its date rather than `ARTIFACT_STATE_ABSENT` (never uploaded, or deleted when nothing named it); reading it is `ARTIFACT_COLLECTED`, and uploading the same bytes stores them again. The tombstone goes when no evidence names it. Collected also covers bytes Reef found damaged or missing and dropped (decisions 3 and 5): the reader sees the same state, and the same upload repairs it. Deleted evidence is `EVIDENCE_NOT_FOUND`: an id refers to an object of 1 to 2 KiB, and R3.13's landing pin keeps the evidence anyone will refer to later.
7. **Backups include artifacts.** After the database copy and before its jj state, each repository's `artifacts/sha256/` goes to `<dest>/repos/<id>/artifacts/sha256/`, leaving partial uploads out, with a `BACKUP_STEP_ARTIFACTS` progress message, and the manifest's repository entries gain `artifact_files` and `artifact_bytes` (`MANIFEST_VERSION` stays 1; a manifest without them reads 0). GC, the only thing that deletes genuine artifacts, cannot run while a backup holds the maintenance lock, so every stored row of the database copy has its file in the backup. The other deletions are a damaged read's quarantine, which removes only bytes that already fail their digest (the restored daemon's tidy makes such a row a tombstone), and `ForgetRepository`, which deletes a repository whole; files stored after the database copy are extras the restored daemon's tidy removes. Restore stages the copy beside `<state>/repos/<id>/artifacts` and renames it into place with the repository's other copies, keeping what was there as `.replaced-<nanos>`. A backup from before R3.02 restores no artifacts, and its evidence reads them as absent.

## Consequences

- An executor uploads its artifacts through `ArtifactService` before it adds the evidence naming them (R3.05, R3.06), over the socket or the remote listener; `reef_client::Client::upload_artifact_file` is the hash, probe and chunk loop, and `reef evidence add --artifact` uploads by default.
- Evidence volume is bounded by retention for work that is no longer live (S-52 is partly fixed); a writer can still add unbounded evidence on a live tree until R3.07's limits.
- Disk use is soft-capped: `max_size` never collects pinned or recent bytes, and uploads are never refused for the store's size (S-54). The GC report's `artifact_bytes` shows when the cap is passed.
- Backups grow by the artifact store, up to `max_size` per repository, on every backup; APFS clones within a volume, and other destinations pay the copy.
- Whoever can read a repository's evidence can read its artifacts, including logs holding secrets a check printed (S-55); producers redact.
- This is the first ticket that deletes evidence other than at forget. The floor, the 90-day default, `0s`, the dry run and the upgrade note in the changelog are the mitigations.

## Alternatives considered

- **SQLite blobs.** Large values in the WAL, under the database lock, and in every backup's online copy, which restarts a step whenever a page changes.
- **A second database, `artifacts.sqlite3`.** A second authoritative database to back up, for no gain over files.
- **Machine-wide dedup.** Forget, the remote rules and [0003](0003-sqlite-for-daemon-metadata.md) all key by repository; dedup across repositories can come with R3.18's cross-repository cache, if ever.
- **Client streaming.** [0029](0029-daemon-api-v1.md) decision 13, gRPC-web, and both SDK generators exclude it.
- **An upload session id.** State to expire and look up, where the digest already names the upload.
- **The daemon reading a path the client names.** Useless over the remote listener, and a second path to test.
- **Retention by count per check.** More keys, and age already bounds it.
- **A tombstone per deleted evidence object.** Rows that outlive what they describe; R3.13 pins what must stay.
- **Artifacts outside backups.** The durability table calls them authoritative within retention, and a log from a flaky run cannot be produced again.
