# 0048. Status from the watcher's journal

- Status: accepted
- Date: 2026-10-31
- Ticket: R2.23
- Amends: [0003](0003-sqlite-for-daemon-metadata.md), [0026](0026-narrowed-notify-snapshots.md), [0028](0028-watch-attachment-off-the-create-path.md)

## Context

The [design](../design.md) says status "is answered from an incrementally maintained index fed by filesystem notifications, never from a tree walk", and that the walk is "the fallback, not the path" (Storage). Until R2.23 the walk was the path: every read that snapshots a workspace first took an explicit snapshot, and explicit snapshots scanned every tracked file ([0026](0026-narrowed-notify-snapshots.md), decision 7). On `large` the walk was 165 ms of a 182 ms status; at 200 workspaces under load a full scan took 11.3 s, and on Linux it waits for the inotify turn ([0028](0028-watch-attachment-off-the-create-path.md), decision 9).

Most of an index existed in two pieces nothing joined. jj's working-copy state records each tracked file's type, executable bit, mtime, size and content (through the tree), and a scan rehashes only files whose state differs; the walk's cost is listing and `lstat`ing everything to find them. R1.30's scheduler kept the paths the watcher reported since the last scan. What was missing was a way for a read to trust those paths: they arrived after the 500 ms debouncer, nothing proved a read had seen the events of writes finished before it, and on macOS notify's one `FSEvents` stream over every root restarted with `since_when = now` at each watch and unwatch, so a create or a release silently dropped other workspaces' events.

## Decision

1. **The index is jj's working-copy state plus an in-memory journal, not a SQLite table.** The per-file record is jj's, and only jj's decides what a snapshot records (racy mtimes, ignore rules, conflicts, the new-file size limit), so a copy would have to equal it after every snapshot; seeding one is 100,014 rows inside each `large` create, whose budget is one second, and 20 million at 200 workspaces. The dirty set is worthless after a restart, since writes made while the daemon was down were never reported. Every journal therefore starts stale at daemon start, and nothing is persisted or backed up. This amends [0003](0003-sqlite-for-daemon-metadata.md), whose context named the status index as a reason for the database.
2. **The journal is fed on notify's own thread, before the debouncer.** A tap in `ChangesOnly`'s handler (`watcher/notify.rs`) routes each change event's paths to their workspace and records them; the debounced events still drive the scheduler's timing. Every snapshot of any kind takes the journal once it holds its scan permit: paths and stale reason move out together, and events from then on go to the next. R1.30's path set and its `everything` and `behind` marks become the journal's. On Linux notify adds a new directory's watch only once it has read the rest of its buffer, so a write under a directory just created can go unreported: a directory created or moved in stays dirty across takes until an event from under it shows its watch is up, or for 10 s.
3. **A read syncs with the watcher through a cookie in a directory outside the root.** Each notify workspace has `repos/<id>/sync/<ws>/`, created `0700` when tracked, emptied of a crash's cookies, removed at release. It is watched with the root: non-recursively in the daemon's one inotify instance on Linux, whose one queue orders every event, and on macOS as a second path of the workspace's own stream, which delivers in event-id order across its paths. A read creates `<pid>-<n>` there and waits until the tap has seen it, so every write that finished before the read arrived is in the journal. Reads share cookies: one created after a read arrived serves it, so concurrent reads cost at most two round trips each. Cookie numbers come from one counter for the daemon's life, so a journal tracked again never reuses one a scan's mark still holds, and a waiting read stops as soon as its journal goes stale. The wait is bounded by `[status_index] sync_timeout` (1 s); a read that times out walks. The cookie never enters the agent's tree, so watch-mode tools there never see one.
4. **On macOS each notify workspace is its own `FSEvents` stream.** `ChangesOnly` holds one `FsEventWatcher` per root, started over the root and its sync directory in one go (`paths_mut`), so attaching or releasing one workspace never restarts another's stream. notify drops a stream's start error, so a new stream counts as attached only once one cookie has come through it (10 s at most, else the watch failed). This amends [0028](0028-watch-attachment-off-the-create-path.md), decision 6: a macOS attach is a new stream for that workspace. Each stream costs one run-loop thread.
5. **A journal is stale for a stated reason, and a full scan clears it.** Journal states: `not-watched` (the watch is not up; cleared only by a full scan once it is), `watch-restarted` (a notify workspace tracked again after a time unwatched; never for Watchman, whose clock jj keeps), `events-lost` (an inotify overflow, which is every notify workspace's; an inotify watch-limit error, which notify hits for a whole batch of new directories at once, so also every notify workspace's; an `FSEvents` rescan, which on macOS is the stream's workspace's, by root, excluded directories included; a Watchman fresh instance), `too-broad` (more than `watcher.narrowed_max_paths`, the root, `.reefignore`), `snapshot-failed`. Found by one read: `not-synced`, `stale-working-copy` (ADR [0018](0018-snapshot-staleness-and-divergence.md)'s adopt, divergent and recover arms, which scan everything), `path-not-narrowable`, `covered-by-full-scan`. `GetStatus` reports the reason in `WorkspaceStatus.walk_reason`, a new `StatusWalkReason` (API revision 13), and sets R2.01's `STATUS_SOURCE_INDEX` and `STATUS_SOURCE_WALK`.
6. **A read is answered clean, narrowed, or by a walk.** A notify workspace whose journal is fresh syncs, then takes its scan lock. A scan that took the journal after the read's cookie covers it. A fresh, empty journal, no carry, and a row at the view's working-copy commit take no snapshot at all: nothing is scanned or recorded. Otherwise the read takes an explicit snapshot narrowed to the journal's paths, or a full scan with its reason. A Watchman workspace snapshots as before, narrowed by jj's own synced query, and reports `index` unless its journal was stale. This amends [0026](0026-narrowed-notify-snapshots.md), decision 7: reads' explicit snapshots are no longer full.
7. **Every read that snapshots first uses it; requests for a snapshot do not.** `GetStatus`, `ListChanges`, `GetChange`, `GetDiff`, `ReadFile`, `ListFiles`, `ListSymbols`, and `GetWorkspace` with `snapshot_first`, which moves onto the same path. The `Snapshot` RPC (the escape hatch), releases, moves, shutdown and GC snapshots, and writes' pre-snapshots stay full scans: a write that missed an edit would act on it.
8. **A watched workspace is fully scanned at least every `watched_fallback_interval`, busy or idle; reads never walk on a timer.** Until R2.23 the watched fallback fired only when a workspace had no events, and every snapshot reset its clock, so a busy workspace was never fully scanned until its release. Now the scheduler runs a dirty notify workspace's next scheduled snapshot full once its last successful full scan is older than the interval (10 minutes by default), which bounds how long a change no event names can hide from reads. A walk on the read path instead would cost the agent up to 11.3 s under load, and on Linux the inotify turn. This amends [0026](0026-narrowed-notify-snapshots.md), decision 7's last sentence: the watched fallback was a backstop for idle workspaces only.
9. **Misses are found at full scans.** A full scan of a notify workspace that took a fresh journal compares the paths its commit changed with the paths the journal named, and those reported since, after a sync for events still in flight. Each uncovered path is a miss: logged ("status index missed changes", with up to ten paths) and counted. With decision 8 that is a live alarm during a session, not only at release.
10. **What the index does not see until the next full scan is stated.** A write through a hard link from outside the root (the kernel reports the path used), a direct write into an overlay's upper directory, a write through a shared mapping never closed on Linux, and an APFS deletion through another spelling ([0026](0026-narrowed-notify-snapshots.md), decision 6). `IN_CLOSE_WRITE`, which [0028](0028-watch-attachment-off-the-create-path.md), decision 9, dropped with every read event, is now journaled and forwarded as a modify, so a mapped write is seen at its close on Linux. No agent tool writes tracked files these ways.

## Consequences

- Phase 2's exit criterion: status on the 100,000-file preset takes no snapshot when nothing changed and a snapshot of the changed paths otherwise, checked by `benches/status.rs`, which panics if an `index_*` call walks.
- The index answer equals the walk's for every change an event names; `tests/status_index.rs`'s differential test holds it over seeded random edits.
- A read that walks says why, so "why was this slow" is the API's.
- A write followed at once by a read costs one cookie round trip and a narrowed snapshot instead of a walk; a clean read costs the round trip and the read.
- A busy workspace is fully scanned every 10 minutes: one scan per workspace per interval, the rate R1.23 accepts for idle ones.
- On macOS, 200 notify workspaces are 200 run-loop threads.
- A change no event names stays out of reads until the next full scan; `reef ws snapshot` forces one.

## Alternatives considered

- **A SQLite table of file states per workspace**, in a per-repository cache file like the symbol index. It adds a copy of jj's state to keep equal and serves no read better (decision 1).
- **Narrowing reads to the debounced set with no sync point.** Wrong for the common case: an agent writes a file and asks at once.
- **Marking every macOS workspace stale at each stream restart.** Correct, but the index would answer nothing while workspaces come and go.
- **A cookie in the workspace root**, as Watchman does without a VCS directory. Watch-mode tools in the agent's tree would see a create and a delete per read.
- **`FSEventStreamFlushSync` through Reef's own `FSEvents` binding**, or a daemon-owned watcher without notify-debouncer-full. The flush needs Reef to own the stream; a later ticket may.
- **Writes' pre-snapshots from the index.** Revisit after a release whose load runs report no misses.
- **A periodic walk for reads.** It puts the walk back on the path where it is worst (decision 8).
