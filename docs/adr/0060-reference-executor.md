# 0060. Reference executor

- Status: accepted
- Date: 2026-11-08
- Ticket: R3.06

## Context

[0059](0059-executor-protocol.md) wrote down the protocol between Reef and executors and shipped Reef's side of it: a queue, leases, and evidence bound to the requested tree. Nothing ran a check. The [design](../design.md) keeps execution outside Reef ("Sandboxing, hermetic builds, remote execution, and runner fleets are an established domain, and Reef sits on top of it through the evidence format and the executor protocol"), and it also says evidence weighs only when the executor "runs in an environment the submitting agent cannot tamper with". A solo developer trusts their own machine; a small team trusts a CI identity. Both need an executor they can run today, and every later executor needs a working example of the protocol.

The pieces this executor stands on: the evidence format and `Claim::sign` ([0055](0055-evidence-object-format.md)), artifacts uploaded by digest ([0056](0056-evidence-artifact-store-and-retention.md)), session keys with actor `executor` bound to a person or a `ci` identity ([0057](0057-operator-identities-and-session-keys.md)), `FileService.ListFiles` and `ReadFile` at any revision (R2.02), and the remote listener for CI ([0049](0049-remote-listener.md)).

## Decision

1. **The reference executor is a client in its own crate, `reef-executor`, run as `reef executor`.** It links no jj-lib and no daemon (`crate_graph` holds it to the client rule) and calls only RPCs that exist: no API, schema, protocol, SDK or MCP change. `reef executor run` serves the claim loop; `reef executor check` reports the configuration, runs the sandbox's escape probes, and shows what a revision would run. Both are in `--help-all` only: an operator runs an executor, not an agent.
2. **Checks are declared in two places.** The executor's `executor.toml` (in the client's state directory, or `--config`) and, unless it says `[repository] checks = "deny"`, a `reef-checks.toml` at the job's tree. The executor's own checks of a kind come first; the tree's fill only the pairs the executor's do not match. A repository declares the argv, the targets it accepts, a timeout, literal environment variables, artifacts and exit codes that mean no verdict, and a network level up to `[sandbox] max_repository_network` (none by default). It never declares environment passthrough, host paths, caches or the sandbox: those separate a run from the host and from other trees. The file is separate from `reef.toml`, which every daemon parses strictly at workspace creation ([0021](0021-workspace-spec-file.md)), so a new table there would break earlier daemons.
3. **Targets are data.** A requested target matches a check only through its `targets` globs and the executor's target pattern (`^[A-Za-z0-9._/:@+=-]{1,512}$` by default, no `..` component), is substituted into `run_target` as part of one argv element, and is refused at parse time in a shell's `-c` script. There is never a shell between the executor and the program.
4. **The tree is read through `FileService` at the job's commit and checked three times.** The recursive listing must hash, as git hashes trees, to the job's `tree_id`; each blob read must hash to its listed id (collision-detecting SHA-1, `sha1dc`) before it enters a content-addressed cache; and the laid-out directory must hash to `tree_id` again (`[materialize] verify = "disk"`, the default). Nothing is written through a link. A job submitted by tree alone, with no commit, completes `FAILED`. The same path works over the socket and the remote listener and touches nothing in the repository.
5. **Every check runs in a sandbox, or the executor does not start.** Seatbelt (`sandbox-exec` with a generated profile) on macOS and bubblewrap on Linux hide the home (but `[sandbox] read`), Reef's state and configuration, the socket, the runtime directory, the executor's configuration and token file, other jobs and the blob cache; allow writes only in the job's tree, home and temporary directory; deny the network by default; keep other processes out of reach; and build the environment from nothing. Without a sandbox that applies, the executor refuses to start unless configured `kind = "none"`. The kind is a claim label (`sandbox=<kind>`) and is in every object's annotations, so requesters and policy can require one.
6. **One session per job.** After a claim, the executor issues a session key with actor `executor` (the default identity on the socket, the token's linked identity remotely), renews it within the session when less than ten minutes remain, keeps it in memory only, and drops it with the job. The process sets no core files and, on Linux, is not dumpable. A key it cannot get releases the job and stops the executor. On macOS, where no Seatbelt rule hides another process's arguments and environment, `run` re-executes itself with only the variables it needs and reads the token from a pipe; the docs keep the token out of its parent's environment as well.
7. **Exit statuses become results.** Exit 0 is `pass`; an exit in `error_exit` is `error`; another exit or a signal the executor did not send is `fail`; a check the executor stopped (its timeout, the job's budget, a cancellation, a shutdown), one that did not start, and a pair nothing declares are `error`. Each requested pair gets one summary (fail over error over pass); with more than one check, each also gets a finer object, target `<target>#<check>`. Logs and declared files are uploaded before the object that names them. The annotations name the executor, the sandbox, each check's source and the SHA-256 of its declaration, and how the tree was checked.
8. **The sandbox is a reusable module.** `reef_executor::sandbox::Policy` and `Backend` know nothing about jobs, so `reef ws run --sandbox` (#62) can use them.

## Alternatives

- **Declarations only in the executor's configuration.** Strict, but every repository's checks must be copied into every executor's configuration and kept in step with the tree.
- **Declarations only in the repository.** The environment around a run (passthrough, caches, the sandbox) would be the tree's to choose.
- **A `[[check]]` table in `reef.toml`.** Every daemon before this one would refuse to create workspaces on a commit that has it.
- **Materializing through a Reef workspace.** Fast on large trees (the base cache and a copy-on-write backend), but each job would have a watcher whose snapshots record a check's writes, operations and a provenance session in the repository, and a directory listed to every agent; and it works only on the daemon's machine, so CI would need another path anyway. A follow-up issue adds it as an option for local executors on large trees, behind the same checks.
- **A git checkout of the commit.** The tree is usually a proposal that exists only in the daemon's store.
- **Trusting the daemon's listing.** "Materializes the tree hash and checks it" would be someone else's word.
- **ring's SHA-1.** It has no collision detection.
- **Namespaces written in Rust, or landlock alone, on Linux.** bubblewrap is small, audited and packaged everywhere, and gets the delicate mount and user-namespace sequence right; landlock cannot keep a process from connecting to a Unix socket by path. Landlock and seccomp on top of bubblewrap are a follow-up.
- **Containers per check.** An adapter executor's business; the reference stays dependency-light.
- **Running unsandboxed with a warning by default.** A trusted executor that silently runs a tree's code with the user's privileges is the failure this ticket exists to prevent.
- **One key per check, or one for the executor's lifetime.** Too many issuances, or a key that outlives and spans jobs.
- **Parsing test reports into per-test objects here.** R3.22's behavioral diff is the first consumer; this executor uploads declared reports unparsed.

## Consequences

- Reef has a working executor for a laptop and for CI, and the protocol has a real client: [docs/executor.md](../executor.md) is the operator's guide, and the spec's sections 4 and 8 point at it.
- A `pass` from this executor means the tree's own entry point exited 0 in a sandbox that refused every escape probe on that platform, not that the tests are good: R3.22 and R3.24 address circular evidence, and R3.07's policy decides which executors, identities and sandbox kinds to trust.
- The threat model gains S-82 to S-89. The sandbox's limits are documented: the rest of the filesystem stays readable; on macOS `loopback` is the host's, mach services other than the keychain stay reachable, and another process's arguments and environment stay readable (so the executor keeps no secret there); a kernel or bubblewrap bug escapes. A CI identity whose evidence must be strict should still run on a fresh VM.
- The self-hosted macOS runner already runs everything under Seatbelt, which refuses a second sandbox, so the Seatbelt tests run on a hosted macOS job on `main` and `macos`-labelled PRs; the Linux tests install bubblewrap on the hosted runner.
- Reading a tree file by file is the cost of checking it: cheap after the first job (the blob cache), seconds cold for a tree of a thousand files ([docs/benchmarks.md](../benchmarks.md)).
