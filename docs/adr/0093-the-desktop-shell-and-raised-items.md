# 0093. The desktop shell, and the daemon numbering what needs you

- Status: accepted
- Date: 2026-11-22
- Ticket: R3.39 ([brief](../dev-tickets/phase-3/R3.39-desktop-shell.md))
- Amends: [0091](0091-watching-the-inbox.md) (decision 5: a stream lists each repository, and `synced` no longer marks the starting inbox; Consequences: the shell reads the stream in its own process, not through the web page's store), [0005](0005-tauri-desktop-shell.md) (how the shell supervises the daemon)

## Context

Phase 3 exits when the desktop app notifies on the needs-you-now bucket. A notifier has to turn the inbox stream, which says what the inbox is, into news: this item is new, tell the person once. #389 showed that a stream's order cannot say it. Since #387 each repository's first section goes out as soon as it is read, and `synced` waits for every repository, so an item that arrives in one repository while another is still being read comes before `synced`, and a client that treats everything before `synced` as its starting inbox never announces it. A repository registered later lists after `synced`. A repository whose first read fails sends no items, so its items arrive later as changes. A daemon restart judges every proposal again: until the automatic service's first pass, a proposal reads from its lifecycle (in review under watching, or returned), then by its judgment. The phone's push (R3.40) runs in the daemon and must not push twice across a daemon restart either.

The window cannot be a page the app serves: the web listener accepts only its own origin (ADR 0047), so the window loads the daemon's page. The daemon cannot run inside the app (`run_main` sets process-wide state that is sound only on one thread). WKWebView runs passkey ceremonies only for an app's associated domains, which `localhost` cannot have.

## Decision

1. **The daemon numbers needs-you-now episodes.** An episode is an item's key, its reason and a cause: a proposal's or a conflict's commit, since a sign-off binds the tree; nothing for the other objects. Each gets a raise, a number from a table that never hands one out twice (`inbox_raises`, `AUTOINCREMENT`), one row per key, which another reason or cause replaces, so a new ask on the same commit (no executor, then a sign-off; a sign-off, then a returned landing) is news, and the same ask again on the same commit (a second return) is not. A proposal the automatic service has not judged since the daemon started (no status, or `Pending`) reads its reason from its lifecycle, which can differ from its last judgment; that reading is provisional: it keeps the number its key and commit hold, and with none it numbers nothing (raise 0), so a restart announces nothing and the first judgment announces what is new. `Pending` also means waiting for a job slot, so a real new ask that waits for a slot is announced once its jobs are submitted, and one the service cannot judge at all (its job submits keep failing, or its repository's pass keeps failing after a restart) is announced once it can. A row lives while its key is in either bucket, past the cap included, so a restart's judging again keeps its number, and an answered help request asked again gets a new one. Each good read deletes the rows of keys in neither bucket, using every key it placed before the cap, so an item that leaves and comes back with the same reason and commit (an undone landing) is news however full the buckets are; a failed read deletes nothing. Only the inbox's board task writes it, after a good read and before publishing, and that task runs while a `WatchInbox` stream is open. A write that fails keeps the read's items with raise 0, and the newest raise stays where the last board had it: the task reads the repository again within a second, backing off to a minute, until a read writes, since a board a failed write did not settle takes no numbers from, and a repository's first read that failed this way is no listing, so what waited is not announced once the write lands (#400). `GetInbox` reports the numbers it finds and gives none, so news is told from a stream.
2. **The stream says how far each repository has sent.** `InboxItem.raised` carries the number (0 under watching). `InboxSectionChange.listing` is `PART` and `END` on a stream's first listing of a repository from a good read, and `UNSPECIFIED` otherwise; a failed first read is no listing. `InboxSectionChange.raised_through`, on a change's last part, says every listed needs-you-now item of the repository raised at or below it has been sent; it stays the last known number when a read's write to the ledger fails, and that read's items then carry 0, which is not news; a read that fails re-sends the last good board's items as they are. `raise_epoch` (the database's instance id, and its restore time) names the ledger on every frame.
3. **One rule for news, in `reef_client::inbox::News`.** A client keeps the largest `raised_through` per repository. An item raised above it is news. A repository with no number takes one at its listing's `END` and announces nothing it listed. Another epoch starts over quietly. `reef inbox watch` prints each line's news (`new`), so an agent supervising others blocks on news without a memory of its own.
4. **The shell's core is `crates/reef-shell`, with no UI toolkit.** One task owns the connection, the window's session, the menu's items and the notifier, so nothing is shared. Its rules (`notice`, `link`, `menu`, `login`) are pure and tested on Linux. The Tauri app in `shell/` (its own workspace, outside `crates/*`) implements `Platform`: the window, the tray, `UNUserNotificationCenter`, deep links, open at login, updates. Open at login is on until the person turns it off. The app keeps that choice in its data directory (`open-at-login`) and, while it is on, writes the login item (a launch agent) again at a launch whose path it does not open, except from a mounted volume, an App Translocation copy or a debug build, which will not be at that path at the next login; off removes it from any copy. The menu's checkmark means the launch agent opens this copy of the app, and a copy at a passing path shows no toggle (`reef_shell::login`).
5. **The notifier keeps the cursor on disk** (`notices.json`), saved only after the banners it moved past are posted. A banner's identifier is the item's key, so a crash between posting and saving posts again under the same identifier, which replaces it, and a crash before posting loses nothing. More than three items at once post one summary. A posted item that leaves needs-you-now is taken back after 30 s unless it is back.
6. **The shell starts the daemon only at launch, through a CLI.** When nothing answers, it runs `reef daemon start`, the CLI's own detached start, from an installed `reef` first and its bundled one otherwise, so a newer bundled daemon never migrates the schema under an installed CLI that would start its own daemon later. A daemon that answers is used if it serves API revision 46 or later; an older one is restarted only when asked and idle. A lost connection reconnects and never starts a daemon.
7. **The window is the daemon's page on a session minted over the socket**, given to the webview in process with `&embedded=1` in its fragment. Navigation stays on that origin; other pages open in the browser; the page has no IPC into the app. A new daemon process gets a new session at the page the window was on.
8. **Passkey ceremonies run in the browser.** With `embedded` set, the passkey pages offer "Continue in your browser", a same-origin link that opens a new window, which the shell turns into a launch-file session in the default browser, as `reef ui` does.
9. **Every banner, deep link and push links `/repos/<repo>/items/<key>`**, a web route that finds the item in the live inbox and goes to its page. The item-to-page mapping stays in the web. Deep links are `reef://local/<web path>`, the path in `WebPath`'s grammar (`reef_client::web`), which `CreateWebSession` checks too.

## Alternatives

- **A key set in each client.** No migration, but every client owns a starting-state rule and a pruning rule: once per key forever never announces a revised proposal, and once per entry announces again after every restart's judging. R3.40 would write it again in the daemon.
- **A per-repository baseline flag only.** It fixes #389's order problem but leaves the restart's judging and the phone's dedupe to each client.
- **One stream-wide mark.** It is wrong whenever a busy repository lists after another moved on: #389 again, in the cursor.
- **Notifying from the web page.** It needs a live webview with no window (its memory), IPC into the daemon's page, and a page that knows its host (ADR 0005).
- **`tauri-plugin-notification`.** On macOS it posts through the deprecated `NSUserNotification` and reports permission as always granted.

## Consequences

- R3.40's push sender keeps one number per endpoint and pushes items raised above it, linking `/repos/<repo>/items/<key>`. That is not the one mark per stream rejected above: a stream's frames can lag each other, and the board a sender reads cannot, since each repository's read numbers its raises before the board shows it.
- A proposal rewritten while it waits for a sign-off (a rebase included) is news again.
- The first connection to a repository announces nothing already waiting; the menu bar count shows it.
- macOS pins an ad-hoc signed app's notification permission to its exact code: a rebuild or an update re-signed ad-hoc is refused ("not allowed") without asking. A signature with a team keeps it. Builds signed with a developer's Apple Development identity keep it across rebuilds; release builds need Developer ID (R4.17) before updates can keep it.
- `synced` keeps its meaning (every followed repository has listed) and no longer marks the starting inbox; the web page shows each repository as it lists.
