# 0088. The triage inbox: one definition in the daemon, a person's mark, and presence for state that moves silently

- Status: accepted
- Amended by: [0091](0091-watching-the-inbox.md) (the daemon keeps the inbox as a board while someone watches, and the web page reads `WatchInbox`)
- Date: 2026-11-20
- Ticket: R3.33 ([brief](../dev-tickets/phase-3/R3.33-triage-inbox.md))
- Amends: [0086](0086-reviewing-from-the-web-ui.md) (decision 6: the Proposals tab is replaced by the inbox; decision 7 of [0085](0085-verified-human-presence.md) as 0086 amends it: the allowlist gains `MarkInboxSeen`), [0037](0037-presence-channel.md) (two presence kinds the daemon reports, `AUTOMATIC` and `ATTENTION`), [0081](0081-automatic-landing.md) (a sign-off rule's need is in a status's `missing`), [0029](0029-daemon-api-v1.md) (decision 12's exceptions gain `MarkInboxSeen`)

## Context

The design's human interface makes the triage inbox the home page, with three buckets: needs you now (a sign-off policy requires, a conflict nobody owns, an agent asking for help, a batch that failed bisect), watching (proposals in flight), and landed since you last looked (a digest, not a list). By R3.33 every source had a read, one repository at a time: `ListComments` for help requests and instructions, `ListProposals` with `AutomaticStatus` for sign-offs and returned landings, `ListConflictAssignments` for unowned and blocked conflicts, `ListWorkspaces` for attention, and `ListTransitions` for landings. Three things were missing.

- **One definition of "needs a person".** The web page, `reef inbox`, the desktop shell's notifications (R3.39) and the phone's push from the daemon (R3.40) must agree on it. A definition in the web app would be written again in Rust for push.
- **Events for state that moves with no operation.** A proposal's automatic status (and the sign-offs it waits for) changes when evidence lands, and a workspace's attention changes on a failed watch; neither records an operation (#362, #145). The proposal page polled every 10 s; the fleet panel showed attention as of its last refresh.
- **Who "you" is, and where "since you last looked" lives.** A web session belongs to no identity (ADR 0086), and the UI's origin is `localhost:<port>` with port 0 by default, so browser storage resets at every daemon restart and differs between the browser, the desktop app and the phone.

## Decision

1. **`InboxService.GetInbox` (READ) is the inbox, computed on read.** For every repository named, or every registered one, it reads the sources through their own READ handlers and places each record by the first row of its object's rule table (`crate::inbox::rules`) that admits it, in precedence order, so an item is in one bucket. Items are keyed `<object>:<repository>:<id>` (`proposal`, `help`, `instruction`, `conflict`, `workspace`), stable across reads and the same key whatever the reason, so a client tells a new item from a shown one by the key. Each item carries its reason, the daemon's sentence for it, when it began to need its bucket, the change and commit it concerns, a `reef` command where the web UI cannot act, and its record as its own read returns it. Every source is read page by page, so a bucket's total counts every item; each bucket lists at most 200 per repository. Nothing is kept between reads. A repository that fails to read is a section with an error, and the others return: a section's proposals, comments and assignments, the person's mark, its digest and the digest's base are read with it, so any of those failing is its error, and the workspaces needing attention are listed once for every section (for the one repository when the read covers one, else for all), so a listing that fails, even over one repository's bad row, is every section's error. Only a request the daemon refuses as a whole fails the read: more than 256 repositories or `digest_from` entries, a repository `repos` names that does not resolve, a `digest_from` entry that fails to resolve for any reason but not being found (a forgotten repository's entry is skipped), or a failure to list the registered repositories. Per repository it reads its open proposals, help requests, instructions and assignments, the mark, and the newest ten landed changes' descriptions through `ListProposals` again when something landed; each proposal and assignment read first brings the repository's assignments up to date, which costs a scan only when the head moved (S-265).

   | Reason | Bucket | What admits it |
   | --- | --- | --- |
   | `HELP` | needs you now | an open help request |
   | `SIGNOFF` | needs you now | a proposal whose status is `NEEDS` and whose every missing need is a sign-off |
   | `RETURNED` | needs you now | a proposal a landing returned (cause `LANDING` back to `PROPOSED`, not amended since), or held `RETURNED` and not `retrying` (a busy destination the service queues again by itself, up to three times) |
   | `NO_EXECUTOR` | needs you now | a proposal whose jobs no executor claims |
   | `CONFLICT_UNOWNED`, `CONFLICT_BLOCKED` | needs you now | an assignment `UNOWNED` or `BLOCKED` |
   | `ATTENTION` | needs you now | an active workspace that needs attention |
   | `CONFIRM` | needs you now | a person's instruction waiting for its Confirm |
   | `IN_REVIEW` | watching | any other open proposal, failed checks and rules the agent fixes included |
   | `IN_FLIGHT` | watching | an instruction pending, delivered or running |

   `reef inbox` prints it. Neither RPC is an MCP tool (`tools/list` is at its budget): an agent supervising others runs `reef inbox`.

2. **A sign-off rule's need is in the status's `missing`.** `AutomaticStatus.missing` was documented to hold "the missing evidence and sign-offs", but a sign-off rule names no evidence need, so a proposal waiting only on a person said only "blocked by review". The judge now adds one need per unmet sign-off, a `[[signoff]]` rule's or a built-in one (the owners' on a change to a policy file, a resolution's approval under R3.28): kind `signoff`, target the rule's name, attestors its groups and identities. A rule that blocks with nothing to ask for (`[[forbid]]`, `[limits]`, `[[rule]]`, a built-in such as a policy file that does not load, or any rule that could not be evaluated) adds a need of kind `rule` targeted at it, so a sign-off beside it is not the only thing missing. `AutomaticStatus.retrying` says a returned landing will be queued again by the service, soon; when false it waits for a person to land it again, or for an executor to claim its checks.

3. **The daemon reports two presence kinds.** `PRESENCE_KIND_AUTOMATIC`, one entry per open proposal its destination's policy judges, carrying its status without `missing`, replaced when the status's state or evaluation key moves (new evidence on its trees moves the key), ended when it leaves review or turns `OFF`: published by `Automatic::set`, which is now the one place that compares old and new statuses and also returns those that moved, for the agents' instructions. `PRESENCE_KIND_ATTENTION`, one entry per active workspace that needs attention: a task reconciles the entries with the rows whenever a writer of `workspaces.attention` or of a workspace's state wakes it through `Db`, at start, and every 30 s. No client reports either. Presence, not operations, because the state is in memory or derived and the reads rebuild it: an operation per status change would grow the log with entries no undo or replay needs. A client that resubscribes reads again, as every page already does.

4. **A person's mark, in the daemon.** `inbox_marks(identity_id, repo_id, seq, seen_at, web_session)` (schema 28) holds the newest `lifecycle_transitions.seq` a person has seen in each repository; `seq` is per repository, in commit order and never deleted, so it is a sturdier watermark than a time or an operation id, which GC can rewrite. The digest counts the changes landed after the base and still landed (an undone landing is not counted), by proposing agent, with the newest ten. With no mark the base is the newest transition recorded a day ago or earlier. `MarkInboxSeen` (WRITE) moves a mark forward only, never past the repository's newest committed transition, in one transaction, and records no operation. As every web write does (S-253), a move records the web UI session it came through on the row, beside when (`web_session`, `seen_at`, both moving only with the mark), and is logged with the seq before and after (`reef_daemon::inbox::audit`). The socket and a local web session mark for the default person, as every web write already records it; a remote token for the identity it links, and one that links none is refused (`REMOTE_IDENTITY_REQUIRED`). `GetInbox`'s `digest_from` lets a page keep the base its visit started from, so marking does not empty what the person reads.

5. **The inbox is the home page.** `/` shows the inbox across every repository above the repository list, and a repository's Inbox tab, in place of R3.31's Proposals tab, shows the same page for it; `/repos/:repo/proposals` opens the tab. The page reads `GetInbox` again, paced, on the operation kinds the response names and on any change to entries of the presence kinds it names, never on a snapshot alone. The home page reads on those of any repository, one registered after it opened included; a repository's tab only on its own. Another client's jj operation (`jj describe` at the root, and since [ADR 0089](0089-another-clients-undo-keeps-a-workspaces-files.md) the jj CLI's `jj undo`, both kind `EXTERNAL`) is not among the kinds, so a proposal it moves shows at the next read. Each bucket holds its rows: new items wait behind a count, and an item that left keeps its row, dimmed with what happened, until the person shows the new ones. A help request is answered in place, through R3.31's `comment` row. A digest that stays on screen for 3 s in a visible tab is marked seen through the newest landing it showed, and stays shown for the rest of the visit. The page's title carries the needs-you-now count. `inbox/needs.ts` reports the needs-you-now items new at each read, which R3.39 turns into notifications. The proposal page reads again on its `AUTOMATIC` entry and polls only for a proposal no policy judges.

## Alternatives

- **A web page that assembles the inbox from the per-repository reads.** No new read, but the buckets would be defined in TypeScript, and R3.40's push from the daemon would define them again in Rust.
- **A maintained inbox in the daemon**, recomputed by a task and diffed by key, read from memory and published per repository. It gives "item appeared" events for free, but it is held state with its own restart, missed-event and ordering rules, and SQLite's update hook never fires on the `WITHOUT ROWID` tables the sources live in. R3.40 can keep such a task on top of the same rules when it pushes.
- **Operations for status and attention changes.** They would outlive GC and replay, which neither needs, and grow the log on every judgment.
- **"Since you last looked" in the browser's storage.** It resets at every daemon restart (the port changes) and differs between the browser, the desktop app and the phone.
- **Moving the mark when the inbox is read.** A READ that writes, and a remote read token could move it; opening the page by mistake would empty the digest. An explicit "Mark seen" button was the user's alternative; the user chose the automatic mark once seen.
- **Every `NEEDS` status in needs-you-now.** A failed check or rule is the agent's to fix, and on a destination that lands automatically the daemon already instructs it (ADR 0081); the person's bucket holds what only a person can do.

## Consequences

- One page shows what needs the person across every repository, live, with no poll for it, and the desktop shell and the phone build on its keys.
- `ListProposals`, `reef proposal show` and `reef land` show sign-offs in a status's `missing` (kind `signoff`).
- A subscriber to presence sees proposals' statuses and workspaces' attention: the same facts the reads give, to the same callers (S-264).
- A leaked web session can move the default person's marks forward, hiding the digest until more lands; it cannot hide a needs-you-now item, which comes from state, or a landing, which the activity feed and `reef land` keep (S-261).
- A proposal under `checks = "proposal"` without `automatic` has no status, so a sign-off it waits for shows in watching; evaluating policy in the read is a follow-up if a repository needs it.
- An `OFF` proposal keeps the proposal page's 10 s poll: nothing judges it, so nothing notices its evidence.
