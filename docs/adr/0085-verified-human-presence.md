# 0085. Verified human presence: passkeys, pinned by policy, one touch per sign-off

- Status: accepted
- Date: 2026-11-19
- Ticket: R3.43 ([brief](../dev-tickets/phase-3/R3.43-verified-human-presence.md))
- Amended by: [0094](0094-the-pinned-web-origin.md) (the RP ID is `reef.localhost`, and the listener serves at a name of its run under it; decision 2: a pin names the origin too, so what a look-alike page on another port gets approved counts for nothing)
- Amends: [0047](0047-web-ui-transport-and-local-listener.md) (decisions 2, 4, 5 and 6: the listener is `localhost` on both loopback families and passes an allowlist of writes; the app runs on Preact behind React's API), [0057](0057-operator-identities-and-session-keys.md) (decision 5: the web listener issues `user_verified` keys through approvals; decision 8: `user_verified` exists), [0055](0055-evidence-object-format.md) (the session-key predicate's `presence` gains `user_verified`, with `presenceEvidence` required exactly then), [0061](0061-repository-policy-file.md) (`[passkeys]`; the input's key gains `passkey`; a key's `presence` is its effective presence), [0029](0029-daemon-api-v1.md) (decision 12's exceptions gain the five passkey and approval WRITE RPCs)

## Context

#222 asks how a verifier knows that a person signed, and not an agent holding the person's key. [0057](0057-operator-identities-and-session-keys.md) answered that on one uid Reef cannot tell: anything the user can do on the socket, an agent running as the user can do too, so every key it issued carries `presence: none`. It left `presence` in the certificate as the seam for this ticket. [0061](0061-repository-policy-file.md)'s policy already accepted `presence = "user_verified"` in attestor sets, `[[signoff]]` and `[owners]`, and nothing could meet it.

A passkey (WebAuthn with the user-verified flag) needs the person for every assertion: a touch and a fingerprint, a face or a PIN, on an authenticator an agent cannot drive. On this machine it is the one thing an agent running as the user cannot do alone. A passkey needs a browser, and the only browser surface Reef has is the web UI's loopback listener ([0047](0047-web-ui-transport-and-local-listener.md)), which served READ methods only and printed an IP-literal URL. Chromium and WebKit refuse WebAuthn at an IP-literal origin (`SecurityError`, measured with Chromium 156 and WebKit 27.2) and accept it at `http://localhost:<port>`.

R3.31's proposal view must sign its Accept with a key a person was present for. The user chose to build the web listener's write path once, here, around presence. The user also moved #252 (the bundle budget) into this ticket, since it adds the first new pages.

## Decision

1. **A passkey belongs to one person identity and is added from the web UI.** A passkey has an id (`pk_<16 hex>`), the credential id, its public key as DER `SubjectPublicKeyInfo` with its COSE algorithm (ES256 `-7`, EdDSA `-8` or RS256 `-257`; any other is `PASSKEY_ALGORITHM`), its **fingerprint** (the SHA-256 of the DER, lowercase hex, as Reef's key ids are), the RP ID `localhost`, a label of 1 to 64 bytes, the authenticator's AAGUID, the last sign count, when and through which web UI session it was added, when it was last used, and when and why it was removed. Migration `0028_passkeys` (schema 26) adds the `passkeys` table, machine-wide like `identities`. An identity holds at most 32 live passkeys. Registration asks for user verification and attestation `none`; the browser's `getPublicKey()` gives the DER, so the daemon reads no CBOR.
   - **The first passkey is trusted on first use.** Any web UI session can add an identity's first passkey. The daemon issues the registration challenge: 32 random bytes, single use, valid for 5 minutes, and only for the web UI session that started it.
   - **Every later add, and every removal, needs an existing passkey.** The approval is a user-verified assertion by one of the identity's live passkeys over `SHA-256(PAE("application/vnd.reef-vcs.passkey-change", "add\n<the registration challenge, base64url>\n"))`, or over `"remove\n<pk id>\n"` for a removal, else `PASSKEY_REQUIRED`. A removal leaves the keys the passkey certified as they are.
   - **A reset is the way back.** `ResetPasskeys` (ADMIN, socket only) removes every live passkey of an identity and revokes every unexpired key any of its passkeys certified, removed ones included, from now, and logs it as a warning. It is for a lost passkey, or one the person did not add. The keys of a passkey removed before the reset are revoked too, so removing a passkey the person did not add and then resetting leaves none of its keys.
   - **A credential id and a public key are registered once.** A registration of either, when any passkey had it, removed or not, is `PASSKEY_EXISTS`. Attestation `none` proves no possession of the private key, and the public key is in every certificate the passkey approved, so a registration that reused a removed passkey's key would bring back its pinned fingerprint, and with it the touches it approved before the removal or reset, without the person (review of #356, F1). To use an authenticator again after a reset, register a new credential on it, which has a new key, and pin its line in place of the old one.
   - Registration and removal are refused on the socket (`PASSKEY_NEEDS_WEB`) and through the remote listener (`PASSKEY_OVER_REMOTE`): a ceremony needs a browser at the listener's origin.

2. **A passkey counts only where the destination's policy pins it.** `reef-policy.toml` gains `[passkeys]`, from an identity (by name or by id) to the fingerprints of its passkeys. A key's **effective presence** is `user_verified` only when its certificate says `user_verified` and its passkey's fingerprint is pinned under its identity's id or name; otherwise it is `none`. One function, `Policy::presence`, computes it, and every presence comparison uses it (attestor sets, `[[signoff]]` and `[owners]`), as does CEL, whose `e.key.presence` is the effective presence. The input's key gains `passkey`, the fingerprint. A policy that asks for `user_verified` where no pin could meet it loads with a warning, which every evaluation reports among its diagnostics. Changing `[passkeys]` changes the policy file, which `builtin:owners` holds to the owners' sign-off. Pins are only as strong as what may change them. With `presence = "user_verified"` in `[owners]`, a change to the policy file needs an owner's pinned passkey, so an agent cannot pin a passkey of its own. Without it, any owner's sign-off changes the pins, an agent's `--actor human` included, and the policy loads with a warning that says so. The change that first adds the pins and the owners' presence is judged by the policy before it, so a person checks that one change, as they check the first policy. The Passkeys page's snippet names only passkeys whose touch verifies with the key Reef holds, by that key's own fingerprint, so a person on the daemon's own page does not pin a passkey an agent registered first. `EvaluatePolicy` reports presence and pinning per signer.
   - **Why trust on first use alone was rejected.** An agent running as the user can mint a `reef ui` session, drive a headless browser with a virtual authenticator, as this ticket's own end-to-end test does, and register a software passkey before the person ever does. Every later guard then protects the agent's passkey. Pinning moves the trust from the daemon's database, which any same-uid process can write, to the destination's reviewed policy. Because the certificate carries the assertion and the passkey's public key, a forged `user_verified` certificate, signed with a stolen `authority.pem` (S-58), cannot name a pinned fingerprint without the passkey's private key, which stays on the person's authenticator. For policy, the authority key alone no longer makes a person.

3. **One touch per sign-off, through an approval.** An approval (`apr_<16 hex>`) is a person's verified approval of one sign-off. `RequestApproval`, on the socket or through the web listener, takes a fresh session key the requester generated, its proof of possession (actor `human`, an empty session), the in-toto statement the key will sign, and the revision. The daemon parses the statement as `AddEvidence` would, checks that its subject is the revision's tree, and picks an unused session. The approval waits 2 minutes. An identity has at most 8 pending, and the daemon holds at most 256 (`TOO_MANY_APPROVALS`). Approvals live in memory: a restart drops them, and an ended one stays readable for 2 minutes after its expiry. `ResolveApproval` approves with a passkey assertion through the web listener only (`APPROVAL_NEEDS_WEB` on the socket), or declines on either. An approved approval certifies the key for 2 minutes with presence `user_verified`, records its passkey, the approval and the web UI session on the key's row, and returns the certificate. `GetApproval` with `wait` returns when the approval stops being pending. Reviewing ten changes takes ten touches, and each touch approves exactly what the page showed.

4. **The challenge is derived, and checked in three places.** The WebAuthn challenge of an approval is

   ```text
   SHA-256(PAE("application/vnd.reef-vcs.presence-approval",
               "reef-presence-approval/v1\n{authority key id}\n{key id}\n{identity id}\nhuman\n{session}\n{statement sha256}\n{change id}\n"))
   ```

   so the touch approves this key, this statement (its kind, result, target and tree) and this change, and nothing else. The daemon stores no challenge.
   1. **At approval.** The daemon checks the assertion over the derived challenge, and what a stateless reader cannot check: the passkey is a live one of the approval's identity, the origin is exactly `http://localhost:<the listener's port>`, and the sign count went up (or both counts are 0, as synced passkeys report).
   2. **In the certificate.** `reef_evidence::session::check_certificate` derives the challenge again from the predicate's own fields and checks the assertion: the client data's type is `webauthn.get` with that challenge, the origin's host is the RP ID (`http` only for `localhost`), `authenticatorData` starts with SHA-256 of the RP ID with the user-present and user-verified flags set, the signature verifies with the public key by its algorithm (ring), and `passkey` is the public key's SHA-256. `certify` runs the same check before the authority signs, so an authority never signs a certificate a reader refuses. Any verifier, a store included, checks it with nothing but the certificate.
   3. **At `AddEvidence` and on every read.** A `user_verified` key counts only for the evidence object whose payload's SHA-256 is `approves.statement`, linked to the change `approves.change` (decision 6). A read that finds an object that is not its approved one, which only a database edited behind the daemon can hold, reports that object's presence as `none`.

5. **The certificate carries the evidence beside `presence`.** When `presence` is `user_verified`, the session-key predicate carries `presenceEvidence`: `type` `webauthn`, `passkey` (the fingerprint), `credentialId`, `publicKey`, `algorithm`, `rpId`, `approves` (`statement`, `change`), and the assertion's `authenticatorData`, `clientDataJSON` and `signature`. It is required exactly when `presence` is `user_verified`, refused otherwise, and `user_verified` is certified for actor `human` only. A reader older than this ticket does not know `user_verified` and refuses the certificate as invalid, so the new value fails closed: no older reader accepts a certificate while ignoring its `presenceEvidence`. That is the exception to [0055](0055-evidence-object-format.md) decision 8, under which an older reader that ignores an added field reaches the same decision. A certificate grows by about 1 KB with an EdDSA passkey (the committed fixture: 2,208 bytes against about 1,150 for `none`), and more with an RS256 passkey's longer key and signature.

6. **A presence key signs once.** `AddEvidence` refuses an envelope signed by a `user_verified` key whose payload is not the approved statement, or whose revision is not the approved change (`PRESENCE_STATEMENT_MISMATCH`, `field` `statement` or `change`). The first evidence object spends the key: a compare-and-set in the add's own transaction records the object on the key's row. Adding that object again changes nothing, and any other is `SESSION_KEY_SPENT`. The statement and change rules already refuse any other object a client can send, so the spend rule is the backstop that holds one key to one object in the database itself. The key lives 2 minutes, and the requester generates it for the one sign-off and drops it after.

7. **The web listener's writes are an allowlist.** Step 8 of the gate passes `ACCESS_READ` methods and the rows of one table, `web/rules.rs`; every other WRITE and every ADMIN method is `WEB_ACCESS_DENIED`, as before. Each row's rule is its handler's to check:

   | Method | Rule |
   | --- | --- |
   | `IdentityService.StartPasskeyRegistration` | a person identity; empty is the default person |
   | `IdentityService.RegisterPasskey` | the challenge this web UI session started; an existing passkey's assertion when the identity has one |
   | `IdentityService.RemovePasskey` | an assertion by one of the identity's live passkeys |
   | `IdentityService.RequestApproval` | a person identity; the statement's subject is the revision's tree |
   | `IdentityService.ResolveApproval` | any pending approval, the CLI's or a browser's; approve needs an assertion by a live passkey of the approval's identity |
   | `EvidenceService.AddEvidence` | signed by a `user_verified` key, for its approved statement and change; through the web, evidence signed by any other key is `PRESENCE_STATEMENT_MISMATCH` (`field` `presence`) |

   `IssueSessionKey` is not in the table: a browser gets a key only through an approval, bound to one sign-off. Publishing, fetching, pushing landed history and creating workspaces, which run the user's git credentials or tools, never are. A test walks every v1 method against the table. The remote listener refuses the five passkey and approval WRITEs (`PASSKEY_OVER_REMOTE`; R3.40 brings passkeys there), and the MCP server exposes none of the eight new RPCs.

8. **A web request has its own channel.** The gate inserts the request's caller, `web::Caller { session }`: the first 16 hex digits of the blake3 digest of the session's token, never the token. `channel_of` returns `Channel::Web`, recorded as `sessions.channel` `web`, so a web request no longer looks like the socket to a handler. Keys issue through it only by approval: actor `human`, a person identity, presence `user_verified`, a fresh session, never renewed. The audit the threat model's requirement 5 asks for is the `web_session` column on `session_keys`, `passkeys` and `evidence` rows, typed in the API as `WebCaller`, plus a line in the daemon's log for every passkey change, every approval requested, approved, declined or expired (`reef_daemon::identity::audit`), and every evidence object added.

9. **The listener is `localhost` on both loopback families.** The printed URL, the `Host` check and the gate's origin use `localhost:<port>`, and only it: a `Host` of `127.0.0.1:<port>` or `[::1]:<port>` is now `421`, so the app has one origin and one `localStorage` scope. DNS rebinding is unaffected: a rebound page sends its own name as `Host`, and browsers resolve `localhost` to loopback themselves. The listener binds `127.0.0.1:<port>` and `[::1]:<port>`. With port 0 it takes the port the kernel picks for IPv4 and binds IPv6 on it, trying up to 16 ports while that port is taken on `[::1]`. With a fixed port, either address taken fails the bind (`WEB_UI_UNAVAILABLE`, naming the address). It skips IPv6 only on a host with no IPv6 loopback, where nobody can bind it. Without both, a process holding the other family's address at the port serves a page whose origin is exactly `http://localhost:<port>` to a browser that tries that family first, and collects genuine assertions for Reef's RP ID. `[ui] listen` stays an IP literal and must be `127.0.0.1:<port>` or `[::1]:<port>`, either of which binds both; another loopback address, which `localhost` does not reach, is refused at load. Because the RP ID `localhost` is shared by every local web server, the daemon checks the exact origin at registration and at approval: a dev server on another port can ask for an assertion, never one the daemon accepts. `CreateWebSession` takes a path, so `reef` can open a session at a page such as `/approve/<id>` (`INVALID_WEB_PATH` for a path that is not one of the app's).

10. **The five new WRITE RPCs record no operation.** `StartPasskeyRegistration`, `RegisterPasskey`, `RemovePasskey`, `RequestApproval` and `ResolveApproval` join [0029](0029-daemon-api-v1.md) decision 12's exceptions, which `reef-api`'s test `writes_return_operations` lists. A registration challenge and an approval live in memory, and a passkey row, like a session key's certificate ([0057](0057-operator-identities-and-session-keys.md)), is an identity record that changes no jj view. Undo would have nothing to revert, and an operation per touch would fill the log with records of no change. The audit of decision 8 records them instead. `ResetPasskeys` is ADMIN and records none either.

11. **The app runs on Preact behind React's API** (#252). The source keeps importing `react` and type-checks against React's types; Vite and Vitest alias `react` and `react-dom`, with their subpaths, to `preact/compat`, and the unit tests render through the Preact Testing Library (`web/src/test/testing-library.ts`). Each page imports only the service clients it calls. About 200 KB less JavaScript reaches each page, and the budget returns to 500 KiB per page and 600 KiB in total. (Since R3.40 the app is one script, and the 500 KiB are its: [0095](0095-paired-devices.md).) Preact escapes text as React does, so [0047](0047-web-ui-transport-and-local-listener.md)'s rules on rendering API text hold unchanged.

## Alternatives

- **Trust on first use alone.** An agent registers its own software passkey first (decision 2).
- **Authenticator attestation.** It refuses most people's passkeys, synced ones included, and pinning answers the threat it would.
- **One touch for a 5-minute key.** Offered to the user and declined: a key that signs anything for 5 minutes is a key an agent can use in that window.
- **`IssueSessionKey` through the web after an assertion.** A key that is not bound to a statement and a change approves more than the page showed.
- **A challenge the daemon stores.** Only the daemon could check it; a derived one lets a store check the certificate alone.
- **Approvals in the database.** They live 2 minutes; a restart that drops them costs one retry, and nothing pending outlives the daemon that would resolve it.
- **A WebAuthn library or a CBOR parser.** `getPublicKey()` gives DER, attestation `none` carries nothing else to check, and ring already verifies all three algorithms.
- **The IP literal plus an extra accepted origin.** Two origins are two `localStorage` scopes, and WebAuthn works in only one of them.
- **`localhost` on one family.** It leaves the other family's address at the same port to a squatter (S-251).
- **Passkeys through the remote listener.** It needs a DNS name, a CA-issued certificate and its own RP ID: R3.40.

## Consequences

- A person signs off with one touch, from the change detail panel's **Sign off** or with `reef evidence add --actor human --verified`, and a policy that pins the person's passkey can require it (`presence = "user_verified"`). R3.31's Accept is Sign off plus its landing request, and R3.31 adds its decline, comment and land rows to `web/rules.rs`.
- **The residual risk is the person.** An agent can start an approval when the person expects one and hope for a touch without reading. The approval page names the identity, the change, the tree, the kind, the result and who asked; one touch approves one sign-off on one tree, for 2 minutes. The platform's passkey prompt shows only "localhost", so the page is where the person reads what they approve (S-254).
- **A look-alike page is the remaining gap for policy.** The daemon accepts only an assertion made at its own origin, but a certificate's reader can check only the origin's host, since the port changes at every start. Any same-uid agent can read `authority.pem` (S-58), so it can show the person a look-alike approval page on another `localhost` port, get the pinned passkey's touch over its own challenge, and certify the result itself. With the default port 0 the port changes at every start, so the address bar gives the person no cue. The same look-alike can be a Passkeys page whose snippet names the agent's fingerprint, which a person might paste into the first pin change. Until an origin is pinned in policy beside the passkey, with a fixed `[ui] listen` port (S-255), the defence is to open Reef's pages only with `reef ui` or a command from the person's own terminal.
- A reader with no policy still trusts the authority for `user_verified`. `reef evidence show` says whether the policy at `trunk()` pins the passkey, and names the passkey only where there is no policy (S-255).
- The Vite dev server cannot run a ceremony: its origin has another port, which the browser signs into `clientDataJSON`. The passkey flows are previewed on a scratch daemon serving `just web-build`'s assets.
- Bookmarks of `127.0.0.1` URLs stop working, and the app's `localStorage` (`reef.devMode`) starts empty once at the new origin. With port 0 the port changed at every start anyway.
- A lost passkey, or the last one removed, leaves the identity with none: the next one is trusted on first use, and only a new pin in the policy makes it count. `reef identity passkey reset` is the way back from a passkey the person did not add. A removed or reset passkey's key never comes back, so every pin of it is dead from then on: the person registers a new credential and updates the pin.
