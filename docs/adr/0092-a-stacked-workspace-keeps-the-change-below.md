# 0092. A stacked workspace keeps the change below

- Status: accepted
- Date: 2026-11-21
- Tickets: [#380](https://github.com/reef-vcs/reef/issues/380), [#381](https://github.com/reef-vcs/reef/issues/381) ([brief](../dev-tickets/phase-3/issue-380-381-stacked-import.md))
- Amends: [0089](0089-another-clients-undo-keeps-a-workspaces-files.md) (decision 1, for a rebase of a workspace stacked above another change), [0087](0087-adopting-only-what-came-from-the-last-snapshot.md) (decision 2, for a merge's rebase of such a workspace), [0090](0090-reefs-import-keeps-the-commits-workspaces-use.md) (its Consequences on a branch moved back and on the jj CLI's import)

## Context

[0089](0089-another-clients-undo-keeps-a-workspaces-files.md) decision 1 lets a clean workspace follow another jj client's move, or Reef's import of git refs, when the operation recorded the new commit as a rewrite of the old one. [0090](0090-reefs-import-keeps-the-commits-workspaces-use.md) keeps Reef's import from abandoning a commit a workspace uses. Both left a workspace stacked above another change, W2 above W1, exposed:

- **A branch moved back (#380).** When git moves a branch from W1's last snapshot back to an earlier snapshot of the same change, jj's import records the last snapshot as rewritten into the earlier one, and rebases W2's commit onto it. W1 keeps its files by diverging (0089's amendment). W2 followed the rebase and lost the last snapshot's files, from its disk and its commit, with its row not divergent. A pin stops an abandon, not a rewrite.
- **The jj CLI's import (#381).** Any `jj` command at the root first imports git refs with jj's own rules, as its own operation (`import git refs`). After the branch on W1's commit is deleted or pruned, it abandons the commit and rebases W2's commit off it, and W2 followed and lost W1's files.
- **Another client's abandon or revert of the change below.** The same rebase, the same loss; 0089's Consequences accepted following "a rebase that a revert gives a workspace stacked above".
- **The same, beside the stacked workspace's snapshot.** A `jj` command loads the operation head, Reef snapshots W2, and the command then commits an abandon, a revert or an import of the change below. The next load merges the two operation heads, and the merge rebases W2's snapshot off the change below. [0087](0087-adopting-only-what-came-from-the-last-snapshot.md) decision 2 counts a merge's rebase whenever the merge made it from the snapshot, so W2 followed it and lost W1's files, with its row not divergent.

In each, jj recorded W2's rebased commit as made from W2's commit, as every rebase is, so decision 1, or 0087 decision 2 for a merge, counted it. The record says the commit was moved, not that anyone decided anything about it: jj rebases every descendant of a commit that is rewritten or abandoned.

Keeping real jj tags at Reef workspaces' commits, so the jj CLI's import would not abandon them, does not work. jj's default `immutable_heads()` includes `tags()`, so the jj CLI makes a tagged working-copy commit immutable and starts a new commit on it, and it warns on every command that the tag cannot be exported to git (a name git can hold would be exported). It would not stop #380's rewrite either.

## Decision

1. **A rebase counts only when what moved the commit below counts.** Another jj client's move, or Reef's import's, from `was` to `now` counts toward a workspace's adopt and carry when the operation recorded `now` as made from `was`, and each parent of `was` that `now` no longer has was left by a decision. Either the parent is still visible after the operation, so the operation moved `was` off it (`jj rebase -s`, or `jj rebase -r -d`, of the workspace's own change onto another parent), or the operation rewrote the parent into a parent of `now`, and that move counts by this same rule (a describe, a `jj restore` or a git amend of the change below). `reef_lib::jj::snapshot::rewrote` holds the rule; `came_from` and the carry's reading of an import use it. A reorder of the stack, by either change, meets neither arm and diverges (see Consequences).
2. **For every other client's move.** The rule reads the operation's recorded predecessors and its view, not its description. It covers the jj CLI's import and `jj git fetch`, and a person's `jj abandon`, `jj op revert` or `jj rebase -r` of the change below. The user chose this over limiting it to imports.
3. **Otherwise the stacked workspace diverges.** ADR [0018](0018-snapshot-staleness-and-divergence.md)'s fourth arm, as 0089 decision 4 says: the snapshot rewrites the workspace's last snapshot, the change is marked divergent, and the directory stays as it is.
4. **A merge of operation heads reads the heads it merged.** A merge's rebase is made from the workspace's commit by the merge (0087 decision 2), but the rewrite or abandon below that it follows was recorded by one of the heads it merged, not by the merge. So for a merge the rule reads the commits recorded as made from others by the merge and by each operation in the merge's history since the workspace's last snapshot, and what is visible after the merge. A merge that rebased the workspace over a describe or a git amend below, in one of its heads, counts as before; one that rebased it over an abandon, a revert, or an import of a branch deleted or moved back does not. This changes 0087 decision 2 for a workspace stacked above another change.
5. **Unchanged.** Reef's own moves count as before: `reef abandon`, `reef undo`, `reef move` and a landing are requests made through Reef.

## Consequences

- A workspace stacked above another change keeps that change's files when git moves the branch on it back to an earlier snapshot, when the jj CLI's import abandons it, and when another client abandons, reverts or rebases away the change below. Its change is marked divergent with attention `divergent`, beside the rebased commit jj made for it. The agent resolves it as for a single workspace: abandon the commit to drop.
- Following is unchanged for a rewrite of the change below: another client's describe or `jj restore` of it, and a git amend of it, imported by Reef or by the jj CLI. The stacked workspace checks out the rebase, also when the rewrite dropped files.
- A person's `jj rebase -r` of the change below in one operation, which takes it out from under the stacked workspace, now diverges the stacked workspace where it followed and removed the change below's files. A rebase of the stacked workspace's own change onto another parent, which leaves the change below where it is (`jj rebase -s`, or `jj rebase -r -d`), is still followed, as is a rebase of the change below with it (`-s`, `-b`).
- A reorder of the stack diverges too, whichever change moves: `jj rebase -r <W2> -B <W1>`, which moves the stacked workspace's own change below the change it was on, and `jj rebase -r <W1> -A <W2>`, which moves the change below above it. Both write the same graph and the same records: W2's commit rebased onto W1's parent, W1's commit rebased onto that, each recorded as made from its old commit. W1's old commit is hidden and was rewritten into a child of W2's new commit, not a parent, so the rule finds no decision about W2's commit. The records cannot say which change the person moved, so the rule cannot follow the first without following the second, which takes W1 out from under W2 as `jj rebase -r` of the change below does. The user chose to keep the rule (2026-11-22): W2 keeps every file, W1's included, and diverges, where on main it followed and W1's files left its disk.
- The rule reads the commit below, whoever made it, so it covers a single workspace on a trunk commit too. After `git reset --hard HEAD~1` in the root over the commit an agent's workspace is on a new change on, the next `jj` command's import abandons that commit and rebases the workspace onto its parent. The workspace now keeps the commit's files and diverges, where it followed and lost them.
- Two moves of the change below still lose files when a merge of operation heads makes the stacked workspace's rebase, from a head loaded before the workspace's last snapshot, as on main. jj's merge finds the rewrite below by change id, and the head recorded the commit it finds as made from the change below, so the rule counts the rebase. After a `jj split` of the change below, the merge rebases the workspace onto the first half, and the second half's files leave; a split in one operation rebases it onto the second half, which keeps every file. After a `jj rebase -r` of the change below, the merge rebases the workspace onto the moved change, and the files of the commits it left leave.
- A `jj` command that loaded the repository before a stacked workspace's last snapshot, and abandoned, reverted or imported the change below after it, no longer takes the change below's files either: the workspace diverges instead of following the merge's rebase (decision 4). A merge that rebased it over a rewrite below is still followed.
- For each move made from the workspace's commit, the rule reads that commit's parents and the new commit's, and goes down the stack only as far as the move's record made commits below from others. It loads the operation's view, and evaluates one revset over the parents the move left, only when it left one. No new state, API, schema or threat-model row.

## Alternatives considered

- **Imports only, recognised by the jj CLI's `import git refs` description.** It would match jj's operation texts, which 0089 decision 3 stopped reading for undo, and miss `jj git fetch` and a person's abandon or revert of the change below.
- **Pins the jj CLI respects** (the issue's first option): real local tags at Reef workspaces' commits. See the Context: the jj CLI would make Reef's commits immutable and warn on every command, and pins do not stop #380.
- **Re-pinning after another client's operation** (the issue's second option): the abandon and the rebase are in the view by then, and undoing them would write over another client's operation.
- **A merge keeps 0087's rule, made from the snapshot.** This rule, read from the merge alone, would refuse every merge's rebase, since the rewrite below is in a merged head. Keeping 0087's rule for merges leaves the loss above, through the same rebase, whenever the `jj` command loaded the head before Reef's snapshot.
- **Keeping descendants in place in Reef's import of a branch moved back**, by recording the rewrite as divergent so jj does not rebase them. It covers only Reef's import, and the jj CLI's import still needs this rule.
