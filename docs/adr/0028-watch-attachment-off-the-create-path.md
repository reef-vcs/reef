# 0028. Watch attachment off the create path

- Status: accepted
- Date: 2026-10-24
- Ticket: R1.32

## Context

Phase 1's first exit criterion is twenty workspaces on the 100,000-file `large` preset, each created in under one second, on APFS and on overlayfs. `docs/benchmarks.md` names the CI runners' `large` run as the criterion's measurement for overlayfs. The first one (`bench.yml`, main at `4c966c7`, run 40143472665, `ubuntu-24.04`, kernel overlayfs as root) missed by 6 ms: `create_api/large/overlayfs/20` at 1,006 ms per create, 985 ms of it the `watch` step. The backend and the mount took under a millisecond.

The `watch` step is notify's inotify attach, which ran inside `Create` (R1.29). notify sends one message to its single `inotify` event-loop thread. That thread walks the new root and calls `inotify_add_watch` once per directory, 8,336 times for `large`, and reads no events from any workspace until it is done. The daemon has one inotify instance by decision (`max_user_instances` defaults to 128, against a target of 200 workspaces). So attaches are serial however many threads ask for them, and every other workspace's events wait in the kernel queue while one runs. On the M2 Max's Docker VM the same attach took 405 ms; the runner is about 2.4 times slower at it.

R1.29 had already taken the Watchman watcher's set-up off the create path. A just-created workspace's subscription waits until creates go quiet, and the subscription's first result is a full scan (`everything`, [0026](0026-narrowed-notify-snapshots.md)), so a write made before the subscription is caught. That is R1.29's amendment to [0023](0023-watchman-as-the-large-repository-watcher.md). On macOS a notify attach is one `FSEvents` stream restart, 9 ms.

## Decision

`Create` returns once the workspace's row, lease and jj working copy exist. Its watch is then attached or *pending*. A pending watch is one of two kinds:

- a Watchman subscription waiting for creates to go quiet (R1.29); or
- on Linux, a notify watch queued for a background attach.

Both watchers keep the same promise: **a write made after `Create` returns is in the workspace's first watcher snapshot, whether the watch was up at the time or not.**

1. **On Linux, a created workspace's notify watch attaches in the background, one workspace at a time.** `NotifyWatcher` has an attach queue and one worker thread, `reef-notify-attach`. `watch(.., defer = true)` queues the root and returns `Attach::Pending`. The worker attaches roots in queue order, under the same lock and through the same function as an inline watch: route the root in the demultiplexer first, then call `Debouncer::watch`. The queue has its own small lock, so queueing never waits behind an attach in flight. (With the queue under the debouncer's lock, each create of a burst waited for the previous workspace's attach: 456 ms of a 479 ms create in a Docker VM.) Only `TrackReason::Created` defers. A daemon start (`Loaded`), an aborted release (`Restored`) and a move's rewatch (`Rewatched`) attach inline and return `Attach::Attached`, dropping any queued entry for the workspace first.
2. **A watch coming up is an `everything` event.** After an attach succeeds, the worker reports the workspace up through the health hook. Then it sends `WatchEvent { everything: true, at: <queue time> }`. The scheduler turns that into one full scan after `min_interval`. The event is sent strictly after `Debouncer::watch` returns, because a scan that ran before the watch existed cannot vouch for a write made after it. The event is never dropped while the watcher lives: if the channel is full, the worker waits. `at` is the queue time, so the first snapshot's `latency_ms` includes the wait. Until the watch is up the entry is not `watched`, so the short fallback (60 s) is the backstop, narrowing is off, and any scan is full.
3. **A failed background attach is a failed watch.** The worker logs the same warning as an inline failure, with the inotify limit hint when a limit was hit, and reports the workspace down. That marks `attention = 'watch-failed'`. No event is sent, and the workspace lives on the fallback timer until a rewatch or a restart attaches it.
4. **`Watcher::watch` says which it did** (`Attach::Attached` or `Attach::Pending`), replacing `reports_health()`. `Watcher::pending` says why a watch is not up: `PendingWatch::Waiting` for Watchman's quiet wait, `PendingWatch::Attaching` for a queued or in-flight notify attach. `watch_state` in `Create`, `List`, `Inspect` and `Move` is `""`, `"waiting"` or `"attaching"`, and the CLI prints `notify (attaching)`. A pending watch never sets `attention`.
5. **Release, move and shutdown.** The worker takes a root off the queue only while it holds the debouncer's lock, and keeps it to the end of the attach. A release of a queued workspace takes it off the queue under the queue's lock and returns at once. A release of the workspace being attached takes the debouncer's lock, so it waits for that one attach and then removes its watches. An inline watch or an unwatch that comes after an attach and before its report supersedes the report: the worker drops it, and the event with it, so a late "up" or "down" cannot undo what that call set. A report or event that lands after the scheduler untracked the workspace is ignored, as before. On shutdown the worker finishes the attach in flight and stops; the watcher's drop closes the inotify turn (decision 9), which also ends a wait for it. A workspace that was never attached but was written to is covered on the next start by `Loaded` (`behind`, full scan) and the 60 s fallback.
6. **macOS attaches inline whatever `defer` says.** An `FSEvents` attach is a stream restart, and a post-attach full scan of 100,000 files beside the next workspace's APFS clone would be the contention R1.29 measured with Watchman. The queue and the worker are compiled and unit-tested on both platforms; only the choice to use them is `cfg(target_os = "linux")`.
7. **One kill switch, no tuning knob.** `[watcher] notify_attach_background = true`. `false` attaches inside `Create` as before. It is read only on Linux. It does not turn off decision 9, which fixes a loop that predates this ADR.
8. **A pending watch is `behind`, and the attach scans wait for the queue.** Until its first full scan, a workspace whose watch was pending at create may hold writes no event reported, so it is `behind`: every scan of it is full, and the 60 s fallback applies. The attach thread reports each workspace up as it attaches, but holds the `everything` events until its queue is empty, so the attach scans of a burst run after its attaches, not between them. That includes a queue emptied by an unwatch of the last workspace in it. A write after the attach still gets a full scan that covers the earlier writes, so the promise above holds. If creates keep the queue from ever emptying, the 60 s fallback (the workspace is `behind`) is the backstop.
9. **On Linux, full scans of notify workspaces take turns with attaches, and reads never reach the debouncer.** Measuring a burst found a loop this design made easy to start, though it was already possible before it. inotify reports every open of a watched directory twice (to its own watch and its parent's). A full scan of `large` is about 17,000 events, more than the kernel's queue holds (`fs.inotify.max_queued_events`, 16,384), and notify's one thread reads none while it adds a root's watches. notify-debouncer-full also keeps each read in a map under the lock that thread needs for the next event, and rebuilds the map on every tick, so concurrent scans slowed the reader further. The queue overflowed, which makes every notify workspace `everything` ([0026](0026-narrowed-notify-snapshots.md)). Their full scans overflowed it again, in a loop that did not end while the workspaces lived. On main, a restart followed by one write in each of twenty `large` workspaces started it: 33 overflows in 45 s. Two changes stop it:
   - **The debouncer's watcher is a wrapper** (`ChangesOnly`) whose event handler drops `Access` events on notify's thread. Reef's routing dropped them already. They include `IN_CLOSE_WRITE`, the only event a writer through a memory mapping produces. Such a write was, and is, caught only by a fallback or a later full scan.
   - **One inotify turn** (`AttachGate::turn`, a FIFO semaphore of one) is held by each background attach and by each full scan of a watched Linux notify workspace (watcher, fallback, explicit, or before a move), from just before the walk to its end, not through the commit. A release's final snapshot runs after its workspace is unwatched, and a shutdown snapshot after the scheduler stopped, so neither needs the turn. A scan waiting for the turn gives back its scan permit, so narrowed scans of other workspaces go on. Inline attaches (daemon start, a move's rewatch, creates with the switch off) do not take it: they are rare, and a move would otherwise wait behind every queued full scan.

   In a Docker VM, the burst of twenty went from about 600 full scans and 32 overflows to twenty scans and none. The restart case went from 33 overflows to none. Each change alone left one of the two cases overflowing.

This ADR adds to [0023](0023-watchman-as-the-large-repository-watcher.md)'s R1.29 amendment, and to the list in [0026](0026-narrowed-notify-snapshots.md) of what sets `everything` (a background attach coming up). It does not edit them.

## Consequences

- **A `large` create on Linux no longer pays for inotify.** The `watch` step is the time to queue the root, and the create is the daemon's other steps (`jj` about 4 ms, `seed` 2 ms) plus the RPC. `docs/benchmarks.md` ("Linux workspace creation off the inotify watch path") records the runner's numbers before and after.
- **A burst's first snapshots come later.** Attaches stay serial on the one inotify instance. In a burst of twenty `large` creates on the runner, workspace *k*'s watch comes up about *k* attaches (about a second each, 2.4 s on fuse-overlayfs) after its create, followed by one full scan. Before this change the create itself waited for the attach, so the writer could not start earlier. Nothing is lost either way, and `watch_state` says what is happening. In a burst of more than about sixty `large` workspaces, the 60 s fallback snapshots the tail before its watch is up. That is correct, and costs full scans. The bench reports `attach_drain_ms`, and the load test reports `attach.drain_ms` with each attach's queue and attach times, so the cost is visible per run.
- **Each background attach costs one full scan.** It is a stat walk against the seeded tree state (167 ms idle for `large` on APFS, R1.14). A burst of *n* creates runs them one after another, after its attaches.
- **Full scans of watched notify workspaces on Linux run one at a time.** That covers explicit and fallback snapshots too, and they take turns with background attaches. The turn is FIFO, so a scan waits for every full scan queued before it. Recovering many workspaces after a restart (each `behind`, so each scanned in full) takes the sum of their scans, where it took that sum divided by `watcher.max_concurrent_scans` before. Releases and shutdown are not affected: their snapshots skip the turn. Narrowed scans, the steady state since [0026](0026-narrowed-notify-snapshots.md), are not affected. Phase 2's own inotify watcher, without `IN_OPEN` in its mask, would let full scans run in parallel again.
- **An attach in flight holds the debouncer's lock for its length.** A `Release` of an attached notify workspace, a `Move`'s rewatch, or another inline `watch` can wait for up to one attach, as every `watch` inside `Create` did before. A create queueing its watch and a release of a still-queued workspace do not.
- **Other workspaces' events still wait in the kernel queue while a root is being added**, and a heavy writer during an attach can overflow it, which makes every notify workspace `everything`. Both are unchanged from before. A fix needs the attach on a second inotify instance or `fanotify`; that is Phase 2 work.
- **The load criterion is measured with every watch up.** The load test waits for the attach backlog to drain before its steady state starts, and records how long that took. The gate is unchanged.
- **Two code paths.** `notify_attach_background = false` attaches inside `Create` as before R1.32, with decision 9 still in force. The inline path and the worker call the same `attach` function, so the switch cannot drift from it.

## Alternatives considered

- **A second inotify instance per attach**, so an attach does not stall the shared event loop, and attaches can run in parallel. It runs into `max_user_instances` (128 by default) at the 200-workspace target unless instances are pooled and merged. It also needs a watcher of Reef's own rather than notify's single instance, and it does not by itself make `Create` cheaper unless the create still waits. That is Phase 2 Scale work.
- **Watchman for every workspace.** It has the same inotify cost per directory on Linux, plus a crawl. It is an external dependency Reef does not ship, and its per-query cost dominates small repositories ([0023](0023-watchman-as-the-large-repository-watcher.md), [0026](0026-narrowed-notify-snapshots.md)).
- **fanotify** with `FAN_MARK_FILESYSTEM`. One mark covers a whole filesystem with no per-directory watches, but it needs `CAP_SYS_ADMIN`, so the unprivileged tier cannot use it. Overlay mounts complicate which filesystem to mark, and directory-entry events need kernel 5.1 or later. It stays a candidate for privileged daemons.
- **A quiet-window deferral for notify**, as Watchman has. On Linux the create's remaining steps are milliseconds, so there is nothing to protect from the attach. A quiet window would only delay the first snapshot further.
- **For the overflow loop: a larger kernel queue** (`sysctl fs.inotify.max_queued_events`). It needs root, it is the user's machine, and a large enough burst overflows any size. **Patching notify's mask** to drop `IN_OPEN` would remove the events at the source, but a `[patch]` fork does not reach `cargo install` from crates.io ([0026](0026-narrowed-notify-snapshots.md)). **Reef's own inotify watcher** is the real fix, and Phase 2 work.
- **Doing nothing and rerunning the bench.** The miss was 6 ms. A rerun might pass by as little, and the next scheduled run miss again.
