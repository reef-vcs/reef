# R1.16 Local-only snapshot marking

Phase 1 · Size S · Depends on: R1.13 · Unblocks: R4's publish (clears the flag), R1.17 (GC prunes the index), R1.18 (the index is restored with SQLite and reconciled against the operation log)

## Context

The design (`docs/design.md`, Workspaces and Durability): watcher snapshots "stay on the machine. Only a change that an agent or human explicitly publishes leaves it, so half-written edits never reach a shared store", and "local-only work is the exposed state on a laptop". Nothing in Phase 1 exports or pushes, so this ticket cannot enforce the rule at an export; it makes the rule enforceable by recording, for every snapshot operation Reef writes, which workspace took it, why, and that it is local. SQLite is the index over jj's operation log (ADR 0003: "jj's operation log stays authoritative; SQLite indexes it"), so the index must be rebuildable from the log, which also makes it survive R1.18's restore of an older database.

### What was verified while writing this ticket

- jj operations carry `OperationMetadata { start_time, end_time, description, hostname, username, is_snapshot, workspace_name }` (R0.04, ADR 0008) and nothing else; there is no tag or label field, so "local" cannot live in the operation itself. The description and `workspace_name` are the only places Reef can put a marker, and R1.13 fixed the description prefixes.
- `op_walk::walk_ancestors(&[Operation])` streams operations newest first (used by `Repo::op_log`), which is what the reconciliation walk uses.

## Decisions

- **The marker is the `snapshots` table** (R1.01's README schema, created by this ticket's migration): `op_id PRIMARY KEY, repo_id, workspace_id, commit_id, change_id, kind IN ('watcher','explicit','final','move','shutdown'), local INTEGER NOT NULL DEFAULT 1, taken_at`. Every operation R1.13's pipeline commits inserts a row in the same daemon step that updates `workspaces.last_snapshot_op`, after the operation is committed and before `finish` (so a crash between the two leaves a row for an operation that exists, never the reverse).
- **`local` is only ever cleared by publish** (R4). Phase 1 ships no writer of `local = 0`; a unit test asserts no code path in `reef-daemon` writes it (grep-based, like R0.09's field test).
- **Descriptions are the on-log marker.** `reef_lib::jj::oplog::is_reef_snapshot(&OpEntry) -> Option<SnapshotMark { workspace_id, kind }>` parses the R1.13 descriptions (`reef: snapshot workspace <id>`, `reef: final snapshot of workspace <id> (<reason>)`, `reef: move workspace <id> to <change>`) and `is_snapshot`. The `shutdown` kind uses the description `reef: final snapshot of workspace <id> (shutdown)` and `explicit` the plain snapshot description, so `kind` for those two is recovered from the row, not the log; reconciliation records them as `watcher` and `final` respectively when the row is missing.
- **Reconciliation.** `snapshots::reindex(repo)` walks the operation log from head, inserts a row for every Reef snapshot operation not already in the table (with `local = 1`), and deletes rows whose operation is no longer in the log (after R1.17's GC). It runs at daemon start for each repository and after R1.18's restore. The operation log walk runs on the repository thread (`RepoHandle::call_async`) and returns plain rows; the SQLite diff and writes run off that thread, on the calling task. The walk is bounded by `walk_ancestors(..).take(reindex_limit)` with `[gc] reindex_limit = 100000` (new config key) so a huge log does not stall start; the count of rows added and removed is logged.
- **Exposure.** `InspectResponse` gains `snapshot_count`, `local_snapshot_count`, and `recent_snapshots` (the last 10 rows as `SnapshotEntry { op_id, commit_id, kind, local, taken_at }`); `ListResponse` items gain `local_snapshot_count`. `reef ws inspect` prints them (R1.22 renders whatever the response carries).
- **Per-change view.** `snapshots::for_change(repo, change_id) -> Vec<SnapshotEntry>` exists for R4's publish to find what to flip; no RPC in Phase 1.

## Deliverables

### Migration `0003_snapshots.sql`

The `snapshots` table as in the README plus `CREATE INDEX snapshots_by_workspace ON snapshots(workspace_id, taken_at DESC)` and `snapshots_by_change ON snapshots(repo_id, change_id)`.

### `crates/reef-daemon/src/snapshot/index.rs`

```rust
#[derive(Clone, Debug)] pub struct SnapshotEntry { pub op_id: OperationIdHex, pub workspace_id: WorkspaceId, pub commit_id: CommitIdHex, pub change_id: ChangeIdHex, pub kind: SnapshotKind, pub local: bool, pub taken_at: SystemTime }
pub fn record(db: &Db, repo: RepoId, entry: &SnapshotEntry) -> Result<(), DbError>;
pub fn counts(db: &Db, ws: WorkspaceId) -> Result<(u64, u64), DbError>;           // (total, local)
pub fn recent(db: &Db, ws: WorkspaceId, limit: usize) -> Result<Vec<SnapshotEntry>, DbError>;
pub fn for_change(db: &Db, repo: RepoId, change: &ChangeIdHex) -> Result<Vec<SnapshotEntry>, DbError>;
pub struct ReindexReport { pub added: u64, pub removed: u64, pub walked: u64, pub truncated: bool }
pub async fn reindex(db: &Db, repo: &RepoHandle, repo_id: RepoId, limit: usize) -> Result<ReindexReport, ReindexError>;
```

`reindex` sends one job to the repository thread that walks the log with `reef_lib::jj::oplog` and returns `Vec<SnapshotOpRow { op_id, workspace_name, kind, commit_id, change_id, end_time }>`; it then compares those rows with the table and writes the difference itself, never from inside the job.

`reindex` maps `workspace_name` `reef-<id>` back to `WorkspaceId` and skips operations whose workspace is unknown to the table (a reclaimed and GC'd workspace), counting them in `walked`.

### `crates/reef-lib/src/jj/oplog.rs`

`pub struct SnapshotMark { pub workspace_id: String, pub kind: SnapshotMarkKind }`, `pub enum SnapshotMarkKind { Snapshot, Final, Move }`, `pub fn is_reef_snapshot(entry: &OpEntry) -> Option<SnapshotMark>`; unit tests for each description form and for a jj-cli `snapshot working copy` operation returning `None`.

### `crates/reef-daemon/src/snapshot/mod.rs`

R1.13's post-commit hook calls `index::record`. `SnapshotKind` gains `as_str` / `FromStr` for the `kind` column.

### `crates/reef-daemon/proto/reef/daemon/v0/workspaces.proto`

`SnapshotEntry` message and the three new fields above.

### `crates/reef-daemon/src/daemon.rs`

Start: after each repository thread is up, `reindex` on it; log the report.

### `crates/reef-daemon/tests/snapshot_index.rs`

1. `every_kind_is_recorded`: a watcher snapshot (write + wait), an explicit `Snapshot`, a `Move` (R1.06; skip this step if it has not landed, with a note), and a `Release` (final); the table has one row per operation with the right `kind`, all `local = 1`; `Inspect` counts match.
2. `reindex_rebuilds`: delete all rows from the table through a test hook; stop and start the daemon; the rows are back with the same op ids, `kind` for the watcher and final ones recovered, and the report says `added == n`.
3. `reindex_removes_missing`: insert a row with a fabricated op id; restart; it is gone and `removed == 1`.
4. `no_writer_of_local_zero`: grep `crates/reef-daemon/src` for `local = 0` and `local=0` outside this test and the migration; expect no match.
5. `for_change_lists_all_workspaces`: two workspaces on one change each snapshot; `for_change` returns both rows.

## Implementation notes

- Insert the row on the repository thread's reply path in the scheduler, not on the repository thread itself (keeps SQLite off that thread). `reindex` follows the same rule: the thread reads the log, the caller writes SQLite.
- `taken_at` is the operation's `end_time` from jj, not the daemon's clock, so reindex and record agree.
- Reconciliation at start runs before the scheduler starts snapshotting, so it never races new rows.

## Acceptance criteria

- [ ] `snapshots` table exists after migration; every snapshot operation the daemon writes has a row (test 1).
- [ ] `reindex` rebuilds and prunes the table (tests 2, 3) and its report is logged at start.
- [ ] No code path writes `local = 0` (test 4).
- [ ] `reef ws inspect` shows total and local snapshot counts and the recent list.
- [ ] `just ci` passes.

## Out of scope

- Publishing, exporting, or pushing anything (R4.x); the `local` flag's consumer.
- Marking the user's own `default` workspace snapshots (jj-cli's; not Reef's).
- An RPC to list snapshots per change (R2.02's log service).

## Risks

- The description-based recovery is only as stable as R1.13's strings; a unit test pins them, and changing them is a ticket.
- A restored older database plus a long operation log makes the start-time reindex walk up to `reindex_limit` operations per repository; 100,000 operations walk in about 4 s extrapolating from R0.04's `op_log(100)` at 3.7 ms.
