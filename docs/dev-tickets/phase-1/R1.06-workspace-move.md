# R1.06 Move a workspace between changes

Phase 1 · Size S · Depends on: R1.05, R1.13 · Unblocks: nothing directly; proves the exit criterion "a workspace moves to another change without losing its lease or leaving a directory behind"

## Context

Design, "Workspaces": "a workspace can move between changes without being destroyed and recreated". An agent that finishes one task and starts the next keeps its directory, its lease, and its shared store mounts; only the tree changes. On jj this is `jj edit`/`jj new` on the workspace's working-copy pointer plus updating the files, and on a copy-on-write backend the base the workspace was cloned from changes.

### What was verified while writing this ticket

- `LockedWorkingCopy::check_out(&commit) -> CheckoutStats` (async) applies the diff from the working copy's current tree to `commit`'s tree on disk and records the new file states; `LockedWorkingCopy::reset(&commit)` updates the tree state to `commit`'s tree with placeholder file states without touching disk (`TreeState::reset`). `Workspace::check_out(op_id, old_tree, &commit)` wraps lock, concurrent-change check (`CheckoutError::ConcurrentCheckout` when the on-disk tree id differs from `old_tree`), `check_out`, `finish`.
- `MutableRepo::edit` and `check_out` (R1.01) move the pointer; `edit` abandons the previous working-copy commit when it is empty and no other workspace or bookmark references it.

## Decisions

- **`Move` keeps the row, the id, the path, the lease, and the backend.** It changes `change_id`, `commit_id`, `base_tree_id`, and writes one `snapshots` row with `kind = move` for the final snapshot of the old change (R1.16's table, if landed; otherwise nothing extra).
- **Flow**, in order: (1) `Manager::snapshot(id, Final, "reef: final snapshot of workspace <id> (move)")`; a failed snapshot aborts with `Conflict` and the message "workspace has an unsnapshotted write in flight" (this is what `dev-phases.md` means by refusing). (2) On the repository thread, resolve the target (`change` or `new_on`, as `Create`) and move the pointer: `edit` or `check_out` in a transaction described `reef: move workspace <id> to <change>`. (3) `BaseCache::ensure` for the target tree. (4) `backend.swap_base(paths, &old_base, &new_base)`: `TreeReplaced` (overlay: unmount, swap lower, fresh upper, remount) → on the workspace thread `locked_wc.reset(&target)` then seed `tree_state` from the new base as in create; `NeedsCheckout` (clone, copy) → on the workspace thread `locked_wc.check_out(&target)`, which writes only the files that differ. (5) `finish(new_op_id)`, update the row, return `op_id`, `files_updated`.
- **The lease is untouched**, including its expiry; `Move` is not a heartbeat.
- **Watcher**: R1.13's watcher is paused for the workspace during steps 4 and 5 (`Manager::pause_watch(id)` guard) so the checkout's own writes do not trigger a snapshot mid-move.
- **Conformance test**: R1.11's suite gains a `swap_base` case that every backend must pass. It asserts only what `swap_base` promises: materialize tree A, write a file, swap to tree B; after `TreeReplaced` the root equals B byte for byte and the upper directory is empty; after `NeedsCheckout` the root is unchanged (the written file and A's files are still there) and the backend has not touched it. The daemon's steps 4 and 5 are what make the root equal B in both cases.

### `crates/reef-daemon/tests/workspaces.rs` additions

1. `move_keeps_lease_and_path`: create on change A, write `x.txt`, move to a new change B; same `id`, `path`, `lease.id`, `lease.expires_at`; the directory holds B's tree and not `x.txt`; change A's commit tree holds `x.txt` (the final snapshot); `final_op_id != op_id`.
2. `move_to_existing_change_edits_it`: `change = C` → `commit_id == C's`; a later snapshot rewrites C.
3. `move_with_failing_snapshot_is_conflict`: make the final snapshot fail (chmod the workspace root unreadable on Linux, or inject through a test hook) → `FAILED_PRECONDITION`, row unchanged, directory intact.
4. `move_is_cheap_on_shared_tree`: move between two changes whose trees differ by one file: `files_updated + files_added + files_removed == 1` for checkout backends; `tree_replaced == true` for overlay ones.
5. `move_then_first_snapshot_is_noop`.

### `crates/reef-daemon/tests/backend_conformance.rs`

The `swap_base` case described under Decisions, parameterized like the rest of R1.11's suite.

## Implementation notes

- Step 2 runs before step 4, so a failed swap leaves the pointer on the new change with the old tree on disk. Roll back by moving the pointer back in a second transaction (`edit` to the old commit) and return the error; both operations stay in the log and the row is unchanged.
- `NewOn` creates a new change each call; a client wanting "a fresh change on top of main" every task uses it.
- The checkout path writes through the backend's CoW layer naturally (upper layer or broken clones) and needs no backend involvement.

## Out of scope

- Moving a workspace to a different repository.
- Rebasing the old change onto anything; the old change stays where it was.
- Shared store remounting on move (the stores are per repository and keyed by lockfile; if the lockfile differs between trees, R1.20's mismatch handling sets `attention`).

## Risks

- `check_out` on a clone backend turns every changed file into a private copy, which is the expected cost; a move across very different trees approaches a full copy. The base cache swap for overlay backends has no such cost.
- A watcher event delivered after the pause guard is released but caused by the checkout triggers one redundant no-op snapshot; harmless.
