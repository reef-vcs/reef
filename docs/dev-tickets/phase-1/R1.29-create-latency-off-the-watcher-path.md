# R1.29 Workspace creation off the watcher's path

Phase 1 · Size M · Depends on: R1.12 (the `create_api` benchmark and its `breakdown` line), R1.13 (the scheduler and the notify watcher), R1.14 (the Watchman watcher) · Unblocks: Phase 1's first exit criterion on APFS, RX.06 (a gate needs a passing number to hold)

## Context

Phase 1's first exit criterion is twenty workspaces on the 100k-file synthetic repo, each created in under one second on APFS and overlayfs. R1.12 measured it (`docs/benchmarks.md`, "Workspace creation (R1.12)"). Kernel overlayfs passes through the daemon (0.47 s). APFS does not: `create_api/large/apfs/20` is **1.93 s** per workspace on the M2 Max, although the backend alone makes it (`create/large/apfs/20`, 0.96 s). The time goes to the file watcher, in two different ways depending on which one the workspace gets:

- **notify** (`watcher.backend = "notify"`, no `watchman` on `PATH`, or any repository under 50,000 files): the clone stays at 0.95 s, but attaching the watcher adds **1.1 to 1.3 s inside `Create`**.
- **Watchman** (`auto` on the `large` repo with `watchman` on `PATH`, ADR 0023): attaching costs nothing on the create path, but Watchman's crawl of each new workspace's 100,000 files (and the snapshot its first result triggers) runs while the next workspace is being cloned. In R1.12's second run of twenty, the clone took **1.83 s** of a 1.89 s create, against 0.89 s for one workspace on an idle daemon. (The 1.93 s headline is the first, full run, which predates the `breakdown` line.)

One workspace through the daemon on an idle machine takes 0.95 s with Watchman, so the daemon's own steps besides the clone cost about 60 ms. Removing both watcher costs leaves roughly the clone plus 60 ms per create, which is at the target, not comfortably under it (see Risks).

### What was verified while writing this ticket

- `Manager::create` (`crates/reef-daemon/src/workspace/create.rs:79`) is an `async fn`. Its last step, `load_created` (`:226`), calls `self.scheduler.track(record.id)` (`:252`) synchronously, so whatever `track` does blocks a tokio worker thread before `Create` returns.
- `Scheduler::track` (`crates/reef-daemon/src/snapshot/mod.rs:353`) canonicalizes the root and calls `watcher.watch(ws, &root, skip)` inline.
- `NotifyWatcher::new` (`crates/reef-daemon/src/watcher/notify.rs:39`, the `new_debouncer_opt` call at `:52`) builds the debouncer with `notify_debouncer_full::RecommendedCache`. In `notify-debouncer-full` 0.7.0 (the locked version), `RecommendedCache` is `FileIdMap` on every platform except Linux, Android and wasm, where it is `NoCache` (`src/cache.rs:60-65`). `Debouncer::watch` (`src/lib.rs:600-608`) calls the watcher, then `add_root` (`src/lib.rs:577-590`), which takes the debouncer's data mutex and calls `FileIdMap::add_path`. That walks the whole root with `WalkDir::new(path).follow_links(true)` and stats every entry into a `HashMap<PathBuf, FileId>` (`src/file_id_map.rs:39-54`).
  - The walk follows symlinks, so it also walks every shared store mounted into the workspace (R1.20's mounts are symlinks on macOS). FSEvents itself never descends symlinks; notify's `with_follow_symlinks(false)`, which `NotifyWatcher` sets, is ignored on macOS (`FsEventWatcher::new` discards its config, notify 8.2.0 `src/fsevent.rs:581-583`) and has no effect on the debouncer's walk.
  - The debouncer's data mutex is the one its thread takes every tick and its raw-event callback takes for every event (`src/lib.rs:678`, `:693`), so while the walk runs, no workspace's events are delivered and the FSEvents callback blocks.
  - The same cache walks again under that mutex on every `need_rescan` event (every root, `src/lib.rs:282-283`) and on every directory created in a workspace (that subtree, `src/lib.rs:297-303`), such as `cargo build` making `target/`.
  - `NotifyWatcher::watch` also holds its own `debouncer` mutex for the duration (`notify.rs:81`), so concurrent creates attach one at a time.
  - A Python `os.walk` and `os.stat` of every entry in a fresh APFS clone of `target/synth/large` (110,351 entries) took 0.70 s on the M2 Max (2026-10-21). The rest of the 1.1 to 1.3 s is the Rust walk's own cost and the map of 110k paths (not separately measured).
- Reef uses a notify event's paths only to route it to a workspace (`Demux::group`, `notify.rs:149`) and to count them (`paths_count`, `snapshot/mod.rs:791`). The file ID cache exists to stitch FSEvents rename halves into one event, which Reef never looks at: either half routes to the same workspace by prefix.
- notify 8.2.0's `FsEventWatcher::watch_inner` stops the FSEvents stream, appends the path, and starts a new stream with `kFSEventStreamEventIdSinceNow` (`src/fsevent.rs:299`, `:308-314`). Events for other workspaces that arrive during the restart are lost; the fallback timer covers them. This is cheap per call (no tree walk) but is a pre-existing gap, out of scope here (see Risks).
- `WatchmanWatcher::watch` (`crates/reef-daemon/src/watcher/watchman.rs:226-245`) only spawns a task and returns. The task subscribes with `empty_on_fresh_instance: true` (`:454`), and the first (fresh-instance) result of every subscription asks for one snapshot (`:465-470`, `:507`). So a write made before a subscription exists is snapshotted when the subscription comes up. That first snapshot is a full jj scan whatever the seeded `tree_state` holds: jj-lib 0.46.0 returns no changed-file list on a fresh instance (`fsmonitor.rs:249-254`). jj's own first Watchman query also issues `watch-project`, so any snapshot of the workspace (explicit, or a release's final one) starts the crawl too.
- `create` holds the repository's read lock (`create.rs:88-89`) and the store manager's mount read guard (`:115-117`) until it returns, so today they are held across the 1.1 to 1.3 s notify attach, and repository forget and store GC wait on them.
- `CreateResponse` reports `materialize_ms` (ensuring the base plus the backend's materialization) and `base_was_cached` (`proto/reef/daemon/v0/workspaces.proto:81-83`), and R1.12's `breakdown` line prints the median `materialize_ms` and the watcher (`benches/workspace_create.rs:625`). Nothing reports the other steps, which is why R1.12 could not say where the 2.3 s of its first `create_api/large/apfs/1` went.

## Decisions

- **notify uses `NoCache` on every platform.** `NotifyWatcher` builds `Debouncer<RecommendedWatcher, NoCache>`. Attaching a notify watch becomes one FSEvents stream restart on macOS (unchanged on Linux, where it was already `NoCache`). Rename events arrive as two halves instead of one stitched event, which changes nothing Reef does with them. The symlink walk into store mounts, the stall of every workspace's events during a create, and the re-walks on rescans and new directories all go with it, as does holding the repository and mount locks for a second.
- **`track` runs on the blocking pool, and `Create` still waits for it.** `load_created` becomes `async`: `spawn_blocking` the watch call and await it before returning. A workspace stays watched by the time `Create` returns, as R1.13 promised, so a write right after `Create` is seen without waiting for the fallback timer. With the cache gone this costs milliseconds, but it no longer holds a runtime worker thread for whatever the watcher does.
- **Per-step create timings, in the response and the log.** `CreateResponse` gains `CreateTimings timings = 6`, a message of `uint64` millisecond fields: `resolve_ms` (step 2), `base_ms` (3), `materialize_ms` (4, the backend only), `mount_ms` (4, stores), `jj_ms` (5), `seed_ms` (6), `insert_ms` (7), `watch_ms` (`track`), and `total_ms`. The existing `materialize_ms = 4` field keeps its meaning (base plus backend) for compatibility. The `workspace created` log line gets the same fields. R1.12's `breakdown` line prints the medians of all of them instead of `materialize_ms` alone, and `bench-ws.json` gains a `timings` object per row.
- **Watchman subscriptions wait out a burst of creates, only if measurement says so.** First land the decisions above and rerun `create_api/large/apfs/20` with Watchman (`auto`, `watchman` on `PATH`). If its p50 is still over 1 s and the new `breakdown` puts the excess in `materialize_ms` (the clone slowed by the previous workspace's crawl), add this:
  - The scheduler records when the latest create started (`Manager::create` stamps it at step 1). "Creates in flight" is not the test: the bench issues its creates one after another (`benches/workspace_create.rs:216-228`), so the in-flight count drops to zero for microseconds between each pair, and a subscription started in that gap crawls during the next clone exactly as today.
  - A Watchman task for a workspace that `Create` just tracked waits, before subscribing, until no create has started for `watcher.watchman_attach_quiet` (new `[watcher]` key, default `2s`), or until `watcher.watchman_attach_defer_max` (default `10s`) has passed since `track`. `0s` for either turns the deferral off. Its own create is necessarily over before the quiet window can start.
  - The signal is explicit: `Scheduler::track` gains a `TrackReason { Created, Loaded, Restored }` argument (create, daemon start at `workspace/manager.rs:581`, aborted release at `workspace/reclaim.rs:304`), and `Watcher::watch` gains `defer: bool`, which only the Watchman watcher reads. Only `Created` defers.
  - Nothing is lost while it waits: the subscription's fresh-instance result snapshots whatever was written in the meantime (verified above), and the fallback timer still runs. What waits is how fresh the workspace's snapshots are during a burst, by up to the cap. A snapshot of the workspace during the wait (explicit, or a release) still starts the crawl through jj's own query; that is fine.
  - In the bench, each iteration's twenty creates are followed by twenty releases, and `unwatch` cancels a waiting task (`watchman.rs:247-252`), so most deferred subscriptions never start during the measurement. A passing `create_api` number then measures creates with no Watchman work at all. The PR says so, and also runs twenty creates, waits 15 s, and reports the end-of-burst cost: twenty crawls and twenty full first scans competing for `max_concurrent_scans`.
  - `attention` stays clear while the subscription waits; `reef ws inspect` shows `watcher: watchman (waiting for creates to finish)` from a new `watch_state` field on the workspace.

  If the rerun passes without it, do not add it, and say so in the PR. If it is added and the run still misses, stop there and record the numbers (see Risks): do not tune further in this ticket.
- **ADR 0023 gets an amendment**, written by this ticket, recording that Watchman's crawl competes with APFS clones and either that deferral is the answer (with the measured effect) or that it was not needed.
- **Linux is not a target here.** overlayfs already passes and its notify cache was already `NoCache`. The timings and the blocking-pool move apply there too, and `create_api/large/overlayfs/20` must not regress.

## Deliverables

### `crates/reef-daemon/src/watcher/notify.rs`

`Debouncer<RecommendedWatcher, NoCache>` in the struct and `new_debouncer_opt::<_, RecommendedWatcher, NoCache>(..., NoCache, config)`. The module doc says why there is no file ID cache (Reef routes by path prefix and never reads renames) and that the cache's walk was the R1.12 cost.

### `crates/reef-daemon/src/workspace/create.rs`, `snapshot/mod.rs`

- `load_created` becomes `async` and awaits the watch on `spawn_blocking`. `Scheduler::track`'s other production callers, daemon start (`load_active`, `workspace/manager.rs:581`) and an aborted release (`back_to_active`, `workspace/reclaim.rs:304`), also run on async workers; move their watch calls to the blocking pool the same way. (`rewatch`, `snapshot/mod.rs:624-629`, is test-only.)
- A `CreateTimings` struct filled at each step boundary with `Instant`. `Created` gains it, and the `workspace created` log line logs every field.

### `crates/reef-daemon/proto/reef/daemon/v0/workspaces.proto`

`message CreateTimings { uint64 resolve_ms = 1; uint64 base_ms = 2; uint64 materialize_ms = 3; uint64 mount_ms = 4; uint64 jj_ms = 5; uint64 seed_ms = 6; uint64 insert_ms = 7; uint64 watch_ms = 8; uint64 total_ms = 9; }` and `CreateTimings timings = 6;` in `CreateResponse`. `reef ws create -o json` prints it: the CLI's JSON is a hand-written struct, not the response, so `crates/reef-daemon/src/client/json.rs` (`Created`, around `:282-309`) gains a `timings` object copied field by field.

### `crates/reef-daemon/benches/workspace_create.rs`, `docs/benchmarks.md`

A `REEF_BENCH_WATCHER` variable (`notify` or `watchman`; unset keeps `auto`) sets `watcher.backend` on the bench's daemon through `TestDaemon::start_with` (`testing.rs:48`), so a notify run needs no `PATH` surgery. The `breakdown` line prints the median of each timing. A new row block for `create_api/large/apfs/{1,20}` with `watcher.backend = "notify"` and with Watchman, before and after, on the M2 Max. The R1.12 analysis paragraph that calls this "follow-up work" points here instead.

### Only if the Watchman deferral is added

`crates/reef-daemon/src/config.rs` (`watchman_attach_quiet` and `watchman_attach_defer_max`, documented in `reef config show` and the config reference), the last-create-started stamp on the scheduler, `TrackReason` and `Watcher::watch`'s `defer`, the wait in the Watchman task before `subscribe`, `watch_state = 19` on the `Workspace` message (`types.proto`, after `stores = 18`) and in `ws inspect` and the CLI's JSON (`client/json.rs`), and the ADR 0023 amendment.

## Tests

1. `notify_watch_is_cheap_on_a_large_tree` (`watcher/notify.rs`, `#[ignore]` with the reason, run by hand on macOS and in the PR): `watch` of a fresh APFS clone of the `large` preset returns in under 50 ms, and an event in it is delivered.
2. `write_right_after_create_is_snapshotted` (`tests/`, both watchers where available): create, write one file immediately, and assert a watcher snapshot records it within `min_interval + debounce + 2 s` for notify (`track` starts the `min_interval` clock, `snapshot/mod.rs:369`; pin both in the test config), and within `watchman_attach_defer_max + min_interval + debounce + 2 s` for Watchman, without the fallback timer (set `fallback_interval` to 10 minutes in the test config).
3. `create_reports_timings` (`tests/`): every field of `CreateTimings` is present, `total_ms` is at least the sum of the steps, and `watch_ms` is under 1 s on the `small` preset.
4. `store_mounts_are_not_walked_on_watch` (`watcher/notify.rs`, macOS): a workspace with a symlinked store of 10,000 files attaches in under 50 ms.
5. If the deferral is added: `watchman_waits_for_a_quiet_window` (gated on `watchman` on `PATH`, like R1.14's tests), with `watchman_attach_quiet = 1s` and `watchman_attach_defer_max = 5s`. Create workspace A, then create B 500 ms later: A's subscription has not started until 1 s after B's create started. A file written to A during the wait is in A's first watcher snapshot. A workspace tracked at daemon start subscribes without waiting, and a steady stream of creates every 500 ms still subscribes A by the 5 s cap.

## Implementation notes

- Measure before and after on the same machine with nothing else running: R1.12's two runs of `create_api/large/apfs/1` differed by more than a second. Run `create_api/large` alone with the filter in Verification, not the whole bench (`just bench-ws` takes no filter, and the full `large` run takes 53 minutes). Each `large` iteration is twenty creates and twenty releases, about a minute, so even the filtered run takes over ten minutes.
- `create_api/large/apfs/1` measured 2.3 s in R1.12's full run and 0.95 s in its second; the timings make the next such difference explainable. Record which watcher each row used.
- `NoCache` and `FileIdMap` both implement `FileIdCache`; the change is a type parameter and a constructor argument.

## Out of scope

- The FSEvents stream restart on every `watch` and `unwatch`, which drops other workspaces' events for the length of the restart. A fix needs notify to restart from the last event id instead of "now"; file it as its own ticket with a test that loses an event today.
- Making the APFS clone itself faster (an APFS snapshot or volume per workspace needs `diskutil` and root, ADR 0015).
- Watchman's selection threshold (ADR 0023) and notify's start-up cost on Linux (inotify adds a watch per directory, which is not a tree walk of files).
- A latency gate in CI (RX.06).

## Risks

- **The clone is about 0.9 s of the second.** With both watcher costs gone, a create is roughly the directory clone (0.89 to 0.96 s on the M2 Max) plus about 60 ms of the daemon's own steps, so the target may still miss by tens of milliseconds on this machine and pass on a faster one. If it does, the timings say so precisely, and moving the target or measuring on a named reference machine is a decision for the phase owner, not this ticket.
- **Deferral trades snapshot freshness for create latency.** During a burst of creates, a Watchman workspace's first snapshot waits up to `watchman_attach_defer_max`. Nothing is lost, but a reader of the store sees that workspace's first writes up to ten seconds late. R1.23's five-second criterion is measured at steady state, after the creates.
- **notify without the cache** reports a rename on macOS as two unstitched `Modify(Name(Any))` events, possibly in different batches. Each marks the workspace dirty, and one snapshot follows the debounce either way.
