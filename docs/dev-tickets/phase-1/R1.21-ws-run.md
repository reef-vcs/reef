# R1.21 `reef ws run`

Phase 1 · Size S · Depends on: R1.15 (heartbeat RPC and lease semantics), R1.05 (Create, Release, Snapshot), R1.22 for the CLI skeleton it plugs into · Unblocks: R2.11 (presence reporting rides on the same process), R1.23 (the kill tests drive `ws run`), R1.24

## Context

Every agent runtime today launches a process in a directory. `reef ws run <command>` is the one-line replacement for `git worktree add && cd && <command>`: it creates a leased workspace, runs the command inside it, keeps the lease alive for exactly as long as the process lives, and releases on exit. An agent that knows nothing about Reef gets a copy-on-write workspace, continuous snapshots, and automatic reclaim by being started through it. It is "the primary agent entry point for phase one" (`dev-phases.md`), and the process whose death the exit criterion "killing an agent process mid-edit leaves a snapshot in the store and no directory on disk after the lease expires" is about.

The README fixes the behavior: cwd at the workspace root; `REEF_WORKSPACE`, `REEF_WORKSPACE_PATH`, `REEF_REPO`, `REEF_SOCKET` in the environment; heartbeats every `lease.heartbeat`; SIGINT and SIGTERM forwarded; final snapshot and release on exit unless `--keep`; the child's exit code; and, when the daemon is unreachable, keep the child running, retry with backoff, warn, and accept that the directory may vanish.

### What was verified while writing this ticket

- `std::os::unix::process::CommandExt::process_group(0)` (stable since Rust 1.64) puts the child in a new process group without `pre_exec`. This ticket does **not** use it for the agent's process (see Decisions); R1.20 uses it for store builds.
- `nix` 0.31.3: `nix::sys::signal::kill(pid: Pid, signal: impl Into<Option<Signal>>)` (`sys/signal.rs:1092`) and `killpg` (`:1113`); the `signal` feature implies `process` (`Cargo.toml`: `signal = ["process"]`). `Pid::from_raw(child.id() as i32)`.
- tokio's `signal::unix::{signal, SignalKind}` needs the `signal` feature, which the workspace's tokio entry does not enable (`rt-multi-thread`, `macros`, `sync`, `fs`, `time`); this ticket adds `signal` and `process` (for `tokio::process::Command` and `Child::wait` without blocking a thread).
- `std::io::IsTerminal` (stable since 1.70) answers "is stdin a terminal" for the SIGINT rule below.
- When a terminal delivers Ctrl-C it sends SIGINT to the foreground process group, so a child in the same group receives it directly. A child in its own group would not, and would also be stopped with SIGTTIN on any read from the terminal. This is from the POSIX job-control model, not re-measured here; the tests below cover both the terminal and the non-terminal case.

## Decisions

- **The child stays in `reef ws run`'s process group.** Interactive agents (`claude`, `aider`, a shell) must be able to read the terminal, which a background process group cannot. The consequence is that terminal-delivered SIGINT reaches both processes; so:
- **Signal forwarding rule.** SIGTERM and SIGHUP are always forwarded to the child with `nix::sys::signal::kill`. SIGINT is forwarded only when stdin is not a terminal (an orchestrator signalling `ws run` alone); when stdin is a terminal the group already delivered it and forwarding would double it. `ws run` never exits before the child: it waits, then does its own clean-up. A second SIGINT or SIGTERM within 5 s of the first escalates to SIGKILL on the child.
- **Heartbeat cadence comes from the daemon.** `Create` (in `Workspace.lease.heartbeat_every`) and `Heartbeat` responses carry `heartbeat_every` (a `google.protobuf.Duration`, the daemon's `lease.heartbeat`, clamped to at most a third of the lease length; R1.15 defines both fields). `ws run` heartbeats on that interval, so a daemon configured for short leases is not undercut by a client built with a different default. Each heartbeat has a 5 s deadline.
- **Daemon unreachable**: heartbeats retry with exponential backoff 1, 2, 4, 8, 16, 30 s (capped), one `warn`-level stderr line per state change (lost, regained), the child keeps running. When the lease is known to have expired (`now > expires_at + grace` from the last successful response) a single stderr line says the workspace may be reclaimed. There is no `--on-lost-lease kill` in Phase 1.
- **Exit and release.** After the child exits: if `--keep`, call `Snapshot` (kind `explicit`) and stop heartbeating (the lease runs out on its own; the user asked to keep the directory for a while, and a lease that never expires is what `ws create` without `run` is for); otherwise call `Release` with `snapshot_first = true`, which takes the final snapshot and tears down. The exit code is the child's; if the child died from signal *n*, `128 + n`; if the child ran and exited 0 but release failed, the daemon error's exit code from R1.22's table, with the error on stderr; if the child could not be spawned, 127 (not found) or 126 (not executable), matching shells.
- **Attach instead of create** with `--workspace <id>`: no `Create`; the lease must be active and owned by the same owner string unless `--owner` overrides; on exit the workspace is released unless `--keep`. This is how a supervisor re-enters a workspace after its own restart.
- **Owner** defaults to `<user>@<host>:<pid>` where pid is `ws run`'s own pid, so a dead `ws run` is identifiable in `ws list`.
- **Flags**: `--repo`, `--change <id>` | `--new-on <rev>` (as `Create`), `--purpose <text>` (default: the command line, truncated to 200 characters), `--owner`, `--lease <duration>`, `--workspace <id>`, `--keep`, `--path <dir>` (passed to `Create`), `--skip-missing-stores` (R1.20), `--env KEY=VALUE` (repeatable, added to the child's environment), `--` before the command when it starts with a dash. `-o json` prints a single object on exit (workspace id, path, change, exit code, snapshots taken, release outcome) instead of nothing.
- **stdout and stderr of the child are inherited**, never captured; `ws run`'s own messages go to stderr prefixed `reef:`. In JSON mode nothing of `ws run`'s goes to stdout until the final object.

### `crates/reef-vcs/tests/ws_run.rs`

Each test starts a `TestDaemon` (R1.03's helper, re-exported for `reef-vcs` tests through `reef_daemon::testing` behind a `cfg(any(test, feature = "testing"))` feature R1.03 provides; if it does not, this ticket adds the `testing` feature) with a `small` synthetic repo, and runs the `reef` binary via `assert_cmd` with `REEF_SOCKET` pointed at it.

1. `runs_command_in_workspace`: `reef ws run -- sh -c 'pwd; echo "$REEF_WORKSPACE" > marker'`; stdout's first line is a path under the daemon's `ws/` directory; exit 0; afterwards the workspace is `released` and `marker`'s content appears in the final snapshot's tree (`changed_paths` of the workspace's commit, via `Inspect` before release or by reading the commit through `reef_lib::jj::Repo` on the registered root).
2. `exit_code_is_the_childs`: `sh -c 'exit 7'` → 7; `sh -c 'kill -TERM $$'` → 143.
3. `missing_command`: `reef ws run -- does-not-exist` → 127, stderr contains `reef: cannot run`; the workspace is released.
4. `heartbeats_keep_the_lease`: daemon configured with `lease.default = "2s"`, `grace = "1s"`, `heartbeat = "500ms"`, `tick = "500ms"`; run `sleep 5`; during the run `ws list` shows the lease renewed (expires_at moves); after exit the workspace is released, not reclaimed (`reclaims.reason == 'released'`).
5. `killing_ws_run_reclaims`: same daemon config; spawn `reef ws run -- sh -c 'echo hi > f; sleep 60'`; wait for `f` to appear; SIGKILL the `ws run` process (and then the `sleep`, which is orphaned); within 10 s `ws list` shows the workspace `reclaimed`, the directory is gone, `reclaims.reason == 'expired'`, `snapshot_taken == 1`, and `f` is in the final snapshot's tree. This is the phase exit criterion in miniature; R1.23 repeats it at scale.
6. `sigterm_is_forwarded`: run `sh -c 'trap "echo caught; exit 9" TERM; sleep 60 & wait'` with stdin not a terminal; send SIGTERM to `ws run`; stdout has `caught`, exit 9, workspace released.
7. `sigint_forwarded_without_terminal`: same with SIGINT and `trap ... INT`; exit code from the trap.
8. `escalates_to_sigkill`: `sh -c 'trap "" TERM; sleep 60'`; SIGTERM twice 100 ms apart; `ws run` exits within 7 s with 137.
9. `keep_leaves_workspace_active`: `--keep -- true`; afterwards `ws list` shows `active` with a snapshot op recorded; the lease expires on its own on the short-lease daemon and the workspace is reclaimed.
10. `attach_existing_workspace`: `reef ws create -o json` then `reef ws run --workspace <id> -- true`; released afterwards; attaching to a `released` id fails with exit 5 (`Conflict`).
11. `daemon_down_mid_run`: run `sleep 4`; stop the daemon 1 s in (`TestDaemon::stop`); stderr has `reef: daemon unreachable`; the child finishes and the exit code is 0; stderr then has the release failure with exit code 6 (`Unavailable`) because the child succeeded and release failed.
12. `json_output`: `-o json -- sh -c 'exit 2'` → stdout is one JSON object with `exit_code: 2`, `released: true`; nothing else on stdout.
13. `heartbeater_backoff` (unit, mock client): failures produce delays 1, 2, 4, 8, 16, 30, 30; a success resets to the interval; state changes emit exactly one message each.

## Implementation notes

- Use `tokio::process::Command` so `Child::wait()` is a future and `select!` works; keep `kill_on_drop(false)` (the child must outlive a `ws run` that is SIGKILLed? No: a SIGKILLed `ws run` cannot run drop code either way; the flag is irrelevant there, but it must be `false` so a panic in `ws run` does not kill an agent mid-write).
- The heartbeat interval starts after the first successful `Create`/attach; the first heartbeat fires at `heartbeat_every`, not immediately.
- `Release` after a long run can take seconds (final snapshot of a big tree); print `reef: releasing workspace <id>` to stderr when it takes more than 2 s, so the pause is explained.
- Resolve `--workspace` prefixes server-side (R1.22's rule); `ws run` passes the string through.
- Escalation timer: on the first SIGTERM/SIGINT forward, start a 5 s `tokio::time::sleep`; a second signal before it fires, or its expiry while the child is still alive, sends SIGKILL. The timer expiring on its own does not kill (a child may legitimately take longer to shut down); only a repeated signal does. Make the test for item 8 send two signals.
- `--env` values are not expanded; they are passed as given.

## Out of scope

- Presence reporting from `ws run` (R2.11).
- Running the command in a sandbox or a user namespace (RX.01, R1.09's ADR notes the option).
- Reattaching stdio to a running agent, or running detached (`nohup`-style); use the shell for that.
- Killing the child when the lease is lost; it is documented behavior that the directory may vanish.
- The MCP tool equivalent (R2.13).

## Risks

- Test 5 orphans a `sleep`; the test must kill it by pid (read from `pgrep -P` of the `ws run` pid before the kill, or from a pid the script writes) so CI runners do not accumulate stray processes.
- Terminal versus non-terminal SIGINT behavior is hard to test automatically for the terminal case; it is verified by hand in a terminal before the PR and recorded there.
- A heartbeat that succeeds just as the daemon is shutting down can race with the shutdown snapshot; the daemon's `Heartbeat` during shutdown returns `UNAVAILABLE`, which the backoff handles.
