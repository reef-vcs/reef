# R1.14 Watchman backend (optional)

Phase 1 · Size M · Depends on: R1.13 · Unblocks: nothing directly; R1.23 measures whether the 200-workspace target needs it

## Context

R1.13's notify watcher is a trigger only: every snapshot still scans every tracked file, because jj-lib offers no public way to hand its working copy a changed-path set except through Watchman (`docs/adr/0008-jj-lib-embedding-findings.md`, "Not exposed"). On the `large` preset that scan is 146 ms per snapshot per workspace, and on Linux each workspace costs one inotify watch per directory (8,336 for `large`), so 200 workspaces need 1.7 million watches. The design names Watchman as the backend "for the point where per-workspace watchers stop scaling" (`docs/design.md`, Scale, Technology choices). jj already supports it, which is why building on jj-lib pays off here: enabling one cargo feature gives the narrowed scan, and this ticket adds the trigger side and the selection logic.

### What was verified while writing this ticket

jj-lib 0.46.0 (`Cargo.toml`, `src/fsmonitor.rs`, `src/local_working_copy.rs`, `src/config/misc.toml`) and watchman_client 0.9.0 from crates.io.

- Feature `watchman = ["dep:watchman_client", "dep:tokio"]`. `watchman_client` is at 0.9.0 (MIT). jj-lib's default features do not include it.
- `FsmonitorSettings::from_settings` reads `fsmonitor.backend`: `"watchman"` → `Watchman(WatchmanConfig { register_trigger })` with `register_trigger` from `fsmonitor.watchman.register-snapshot-trigger` (default `false` in `misc.toml`); `"none"` is the default. The settings are read into `TreeStateSettings` when a `LocalWorkingCopy` is initialized or loaded (`TreeStateSettings::try_from_user_settings`), so they are per working copy and fixed at load time.
- `LocalWorkingCopy::snapshot` calls `make_fsmonitor_matcher`: with `Watchman`, it queries `watchman::Fsmonitor::init(working_copy_path, &config)` then `query_changed_files(previous_clock) -> (Clock, Option<Vec<PathBuf>>)`; `None` (a fresh Watchman instance or no previous clock) means a full scan; otherwise the scan is restricted to the returned paths, with parents of changed `.gitignore` files rescanned. A query failure is logged at `warn` and falls back to a full scan, so a Watchman outage degrades rather than breaks. The clock is persisted in the working copy's `tree_state` (`watchman_clock`), one per working copy, and is not advanced when no paths changed.
- `Fsmonitor::init` connects with `watchman_client::Connector::new().connect()`, canonicalizes the root, calls `client.resolve_root`, and with `register_trigger = false` unregisters jj's trigger. Reef sets it `false`: the daemon is the trigger.
- watchman_client 0.9.0: `Client::subscribe::<F>(&self, root: &ResolvedRoot, query: SubscribeRequest) -> Result<(Subscription<F>, SubscribeResponse), Error>`; `Subscription::next(&mut self).await -> Result<SubscriptionData<F>, Error>` with `SubscriptionData::{FilesChanged(QueryResult<F>), StateEnter, StateLeave, Canceled}`; `NameOnly` is the field list that returns just paths; `ResolvedRoot` carries the project root and a `relative` path that `subscribe` passes as `relative_root`, so a workspace root under a parent `.watchmanconfig` root subscribes to its own subtree.
- Not verified: Watchman's behavior across an overlayfs mount boundary (Watchman watches the merged directory like any other; FUSE mounts are known to work with `watchman` ≥ 4.9 when `fs.inotify` events are delivered, which fuse-overlayfs does); the exact `SubscribeRequest` fields for `since`/`expression` in 0.9.0 (check `pdu.rs` when implementing).

## Decisions

- **Watchman is reached only through jj-lib's feature.** `reef-lib` and `reef-daemon` get a cargo feature `watchman` that enables `jj-lib/watchman`; `reef-daemon` enables it by default so released binaries have it, and `reef-lib` leaves it off by default. There is no second Watchman client: the trigger subscription uses the `watchman_client` crate jj-lib already pulls in, re-exported as `reef_lib::jj::watchman_client` under the feature.
- **Two settings variants per repository.** `TreeStateSettings` is fixed at `LocalWorkingCopy` load time, so R1.04's `UserSettings` builder gains `with_fsmonitor(Fsmonitor::{None, Watchman})`, and the daemon keeps both variants per repository. A workspace's variant is chosen at creation (or at daemon start for existing rows) and recorded in `workspaces.watcher` (new column, `'notify' | 'watchman'`, migration in this ticket) so a daemon restart loads it the same way; changing `watcher.backend` affects new workspaces only, and `reef ws inspect` shows which one a workspace uses.
- **Selection.** `watcher.backend = "watchman"` requires the `watchman` binary on `PATH` (`Unavailable` otherwise, naming the binary). `"auto"` picks Watchman when the binary is present and the repository's tracked file count is at least `watcher.watchman_threshold_files` (50,000). The count is taken at registration, on the repository thread, as the number of file entries in the tree of the `default` workspace's working-copy commit, and stored in `repositories.tracked_files` (new column); rows registered before this ticket are counted at daemon start. Counting walks tree entries without touching the disk, so it is available before any base cache entry exists. `"notify"` never uses Watchman. The choice is per repository, logged at `info` at registration and at start.
- **Trigger.** `WatchmanWatcher` implements R1.13's `Watcher` trait: one `watchman_client::Client` per daemon, `resolve_root` per workspace root, one `subscribe::<NameOnly>` per workspace with `relative_root`, `defer_vcs = true` is irrelevant (no `.jj` in the root) and `empty_on_fresh_instance = true` so a fresh instance yields one synthetic "everything changed" trigger rather than a flood. Each `FilesChanged` becomes a `WatchEvent` through the same demux and exclusion rules as notify, debounced by R1.13's scheduler (`watcher.debounce` still applies, implemented with a tokio timer since there is no notify debouncer in this path). Subscription `Canceled` or a client error triggers one reconnect attempt with backoff (1 s, 2 s, 4 s, capped at 30 s); while disconnected the workspace is on R1.13's fallback timer and `attention = 'watch-failed'` until the subscription is back.
- **Scan narrowing is jj's.** Nothing in Reef passes changed paths to the scan; the working copy queries Watchman itself using its persisted clock. The trigger and the narrowing are independent, so a lost trigger costs latency (until the fallback timer), never correctness.
- **No `.watchmanconfig` is written** into workspaces or the state directory. Watchman's default ignores (`.git`, `.hg`) do not matter here; the `[snapshot] exclude` directories are passed as `ignore_dirs` in the subscription expression so build output does not trigger, and jj's scan still applies the ignore rules.
- **Tests skip** with a visible `skipped: watchman not on PATH` message when the binary is absent. CI installs `watchman` from apt in the Linux `check` job only (macOS runs the tests skipped; `brew install watchman` is too slow for every run). The R1.23 `load` job installs it on both.

## Deliverables

### Cargo features

`crates/reef-lib/Cargo.toml`: `[features] watchman = ["jj-lib/watchman"]`. `crates/reef-daemon/Cargo.toml`: `[features] default = ["watchman"]`, `watchman = ["reef-lib/watchman"]`. `crates/reef-vcs/Cargo.toml` forwards `watchman` to `reef-daemon` and keeps it in its defaults. `just lint` already builds `--all-features`; add a CI step `cargo check -p reef-daemon --no-default-features` so the feature-less build keeps compiling.

### `crates/reef-lib/src/jj/settings.rs`

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Fsmonitor { None, Watchman }
pub struct SettingsBuilder { /* identity, max_new_file_size, hostname, username, fsmonitor */ }
impl SettingsBuilder { pub fn fsmonitor(self, f: Fsmonitor) -> Self; pub fn build(&self) -> Result<UserSettings, SettingsError>; }
```

Writes `fsmonitor.backend = "watchman"` and `fsmonitor.watchman.register-snapshot-trigger = false` into the generated layer when `Watchman` is chosen; `"none"` otherwise. Under `#[cfg(not(feature = "watchman"))]`, choosing `Watchman` is `SettingsError::FeatureDisabled("watchman")`. If R1.04 landed a builder with another name, extend it rather than adding a second one.

### `crates/reef-lib/src/jj/mod.rs`

`#[cfg(feature = "watchman")] pub use jj_lib::fsmonitor::watchman;` and `pub use watchman_client;` so the daemon does not add the crate itself (it must match jj-lib's version).

### `crates/reef-daemon/src/watcher/watchman.rs`

```rust
pub struct WatchmanWatcher { /* client: Arc<Client>, subscriptions: Mutex<HashMap<WorkspaceId, JoinHandle<()>>>, demux, sender */ }
impl WatchmanWatcher { pub async fn connect(events: mpsc::Sender<WatchEvent>) -> Result<Self, WatchError>; pub fn binary_on_path() -> bool; }
impl Watcher for WatchmanWatcher { /* kind() == WatcherKind::Watchman */ }
```

`watch` spawns a tokio task per workspace that resolves the root, subscribes with `NameOnly`, and loops on `next()`, converting `FilesChanged` into `WatchEvent`s (paths made absolute from the root), applying the `skip` prefixes, and reconnecting on error as decided above. `unwatch` aborts the task and sends an `unsubscribe` best-effort.

### `crates/reef-daemon/src/watcher/mod.rs`

`new_watcher` gains the selection logic; it returns `Unavailable` when `backend = "watchman"` and the binary is missing. A `WatcherKind` is now also stored per workspace (`workspaces.watcher`), and `Scheduler::track` passes the right watcher: the daemon holds at most one `NotifyWatcher` and one `WatchmanWatcher`, created lazily.

### Migration `0005_watchman.sql`

`ALTER TABLE workspaces ADD COLUMN watcher TEXT NOT NULL DEFAULT 'notify' CHECK (watcher IN ('notify','watchman'))`; `ALTER TABLE repositories ADD COLUMN tracked_files INTEGER` (NULL until counted at registration or daemon start; `auto` treats NULL as below the threshold).

### `crates/reef-daemon/proto/reef/daemon/v0/types.proto`

`Workspace` gains `string watcher = 16;` (`notify` or `watchman`), filled from `workspaces.watcher`; `Inspect` and `List` carry it, which tests 1 and 5 read.

### `crates/reef-daemon/src/config.rs`

`watcher.backend` accepts `watchman`; `watcher.watchman_threshold_files` (declared in R1.13) is read here. `reef config show` prints both.

### `.github/workflows/ci.yml`

In the Linux `check` matrix entry: `sudo apt-get install -y watchman` before tests, and `watchman version` logged. `cargo check -p reef-daemon --no-default-features` as a step on both OSes.

### `docs/adr/0023-watchman-as-the-large-repository-watcher.md`

Status `accepted`. Context: inotify watch and instance limits, O(tracked files) scans, jj's existing Watchman integration with a persisted clock per working copy. Decision: Watchman through jj-lib's feature, Reef's own trigger subscription, per-repository selection with the 50,000-file threshold, notify as the default below it. Consequences: a second daemon dependency that is external and optional; the `fsmonitor` settings are baked into each working copy's state at load time, so the choice is recorded per workspace; Watchman's clock makes the first snapshot after a daemon restart a full scan per workspace. Alternatives: a notify-based narrowing through an upstream jj-lib change (preferred long term, listed in ADR 0008 as upstream contribution 2); FSEvents-only on macOS (does not solve Linux); polling (no).

### `crates/reef-daemon/tests/watchman.rs`

All tests begin with `if !WatchmanWatcher::binary_on_path() { eprintln!("skipped: watchman not on PATH"); return; }`. Test config `watcher.backend = "watchman"`.

1. `watchman_triggers_snapshot`: as R1.13 test 1, asserting `Inspect.watcher == "watchman"` and that the daemon log contains `watchman subscription established` for the workspace.
2. `scan_is_narrowed`: on the `medium` preset, time `Snapshot` after one file change with `watcher = notify` and with `watcher = watchman`; the Watchman scan phase (`SnapshotOutcome.scan_ms`, exposed in the response for tests) is at least 3× smaller. Marked `#[ignore]` with the numbers recorded in the PR and in `docs/benchmarks.md`, because CI runners are noisy.
3. `excluded_dirs_do_not_trigger`: `target/` writes produce no snapshot before the fallback timer.
4. `survives_watchman_restart`: `watchman shutdown-server`; the next write still snapshots within the fallback interval, and a later write snapshots within the debounce once the subscription is re-established (log line `watchman subscription re-established`).
5. `auto_selects_by_threshold`: `backend = "auto"`, `watchman_threshold_files = 100` with the `small` preset (1,000 files) → `watchman`; `threshold = 1_000_000` → `notify`.
6. `missing_binary_is_unavailable`: `backend = "watchman"` with `PATH` emptied for the daemon process → `Create` fails with `UNAVAILABLE` naming `watchman`.

## Implementation notes

- Enable the feature first (`cargo build -p reef-daemon`) and note the build-time cost in the PR; `watchman_client` pulls `tokio` into jj-lib's tree, which the daemon already has.
- jj's `Fsmonitor::init` runs on every snapshot and connects to the Watchman socket each time; that is jj-cli's behavior and is acceptable at Phase 1 scale. If `query_changed_files` latency shows up in R1.23, cache the client upstream rather than in Reef.
- `relative_root` matters: resolve each workspace root separately; Watchman will create one watch per filesystem project root (the state directory's `repos/<id>/ws/` if a `.watchmanconfig` were there; without one, each workspace root becomes its own project). Both are fine; do not add `.watchmanconfig`.
- The `empty_on_fresh_instance` field and the `is_fresh_instance` flag in `QueryResult` are what distinguish "everything may have changed" from a normal batch; on fresh instance send one `WatchEvent` with an empty `paths` vector, which the scheduler treats as "scan now".
- Keep the per-workspace subscription task's state machine small: connected, reconnecting(attempt), stopped.

## Out of scope

- Shipping or installing Watchman; it is an external, optional dependency and the quickstart (R1.24) says so.
- Using Watchman for anything but workspaces (the user's `default` workspace is not watched in Phase 1).
- A notify-based narrowing of jj's scan (upstream work, ADR 0008).
- Windows (RX.05).

## Risks

- Watchman on macOS requires a Homebrew install and occasionally a `watchman watch-del-all` after upgrades; test 4 covers the restart case but not a wedged daemon. Document the recovery commands in R1.24.
- Watchman's own inotify usage is one instance per project root, which solves the instance limit but not the watch limit: 200 workspaces of `large` still need the same number of directory watches inside Watchman. R1.23 records the numbers; the honest fix for that scale is sharing one Watchman project root across workspaces, which needs the `.watchmanconfig` this ticket chose not to write.
- Two settings variants per repository double the `UserSettings` plumbing; if R1.04's builder was not designed for it, this ticket touches R1.04's code.
