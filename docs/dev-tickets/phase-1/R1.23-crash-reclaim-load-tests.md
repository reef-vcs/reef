# R1.23 Crash, reclaim, and load integration tests

Phase 1 · Size M · Depends on: R1.15, R1.20, and in practice every other Phase 1 ticket (R1.06, R1.13, R1.18, R1.21, R1.22) · Unblocks: nothing; this is the phase's acceptance test

## Context

The phase exit criteria are statements about behavior under failure and load, not about code: an agent killed mid-edit loses nothing and leaves no directory; two workspaces on one change do not interfere; two hundred workspaces with active watchers get a write into the store within five seconds; the daemon survives being killed and the disk filling. Every other ticket tests its own piece. This ticket writes the tests that assert the invariants end to end against a daemon process, on both platforms, and the load test the design's Scale section promises: "Each is measured by a load test ticket in its phase and revised from the measurement."

Two of the criteria are measured elsewhere and only cross-checked here: creation time and disk per workspace (R1.12, benchmarks) and backup round-trip (R1.18). This ticket's load run reports creation time and free-space delta as well, because the 200-workspace run is the only place both platforms create that many.

### What was verified while writing this ticket

- GitHub-hosted runners for public repositories (docs, "GitHub-hosted runners reference", fetched 2026-10-16): `ubuntu-24.04` 4 vCPUs, 16 GB RAM, 14 GB SSD; `macos-15` 3 vCPUs (M1), 7 GB RAM, 14 GB SSD. The default job timeout is 360 minutes (GitHub's usage limits page; not re-fetched, well known). `docs/benchmarks.md` measured a 100k-file first snapshot at 2.2 s (`medium`) to 5.2 s on these machines and a `large` no-op scan at 146 ms on an M2 Max; expect 2 to 4 times that on the runners.
- Disk budget on a 14 GB runner: the cargo target directory (3 to 5 GB after a full build), the `large` tree (592 MB on disk), its git objects (compressible text, a few hundred MB), one base cache entry (another 592 MB), and 200 working-copy state directories. jj's `tree_state` holds one entry per tracked file (path plus mtime, size, and type, under 150 bytes each), so about 15 MB for `large` and 1.5 MB for `medium` per workspace: 3 GB versus 300 MB for 200 workspaces. The `large` 200-workspace run therefore fits only barely on the runner and is opt-in; the gated run uses `medium`.
- Linux inotify defaults on a 16 GB machine with kernel 6.8 (Ubuntu 24.04): `fs.inotify.max_user_watches` is computed from memory and clamped to 1,048,576; `max_user_instances` is 128. `medium` has 1,000 directories, so 200 workspaces need 200,000 watches; `large` has 8,336, so 1.67 million, above the default. The `large` run raises the sysctl (runners have passwordless `sudo`). One inotify instance per daemon (R1.13) keeps `max_user_instances` out of the picture; the test checks it.
- `hdiutil create -size 256m -fs APFS -type SPARSE` and `hdiutil attach` work without root on macOS (local check on this machine); a tmpfs mount on Linux needs root, so the Linux disk-full test runs on R1.09's privileged job.
- `jj-lib` divergence: two visible commits sharing a change id are what `Repo::heads()` returns as two `ChangeSummary` rows with equal `change_id` and different `commit_id`; no API call is needed beyond R0.04's.

## Decisions

- **Two suites.** `crates/reef-daemon/tests/integration.rs` runs in the ordinary `check` job on both platforms with the `small` preset and short leases (under three minutes total). `crates/reef-daemon/tests/load.rs` is `#[ignore]` and runs when `REEF_LOAD=1`, from a new `load.yml` workflow and by hand. `crates/reef-daemon/tests/disk_full.rs` runs unprivileged on macOS and under the privileged Linux job.
- **Every test drives the real binaries** (`CARGO_BIN_EXE_reef-daemon`, `CARGO_BIN_EXE_reef`), not the in-process `Daemon::start`, because kill tests need a pid to kill and the exit criteria are about processes. `TestDaemon::spawn()` (added here to R1.03's helper) starts the binary with a temp state dir and a config file the test writes, returns the pid and a `Client`, and SIGKILLs it on drop if still running.
- **The gated load profile** is 200 workspaces on the `medium` preset: create all 200 (recording per-create wall time and free-space delta), then a 5-minute steady state in which each workspace writes one small file every 60 s at a staggered offset (3.3 writes per second across the daemon), then a burst in which all 200 write within one second. Latency is `last_snapshot_at` from `Inspect(snapshot_first = false)` minus the write's timestamp, polled every 250 ms. **Gate: steady-state p95 ≤ 5 s and no write unsnapshotted after 30 s.** The burst's p50, p95, and max are recorded, not gated, since they measure scan throughput over `max_concurrent_scans` cores rather than the design's target.
- **The `large` profile** (`REEF_LOAD_PRESET=large`, 200 workspaces on 100k files) is the same program; it is run by hand on a developer machine before the phase closes and on `workflow_dispatch`, with the Linux sysctl raised to 4,194,304 and a 90-minute job timeout. Its numbers go in `docs/load-tests.md` beside the gated run's. Twenty workspaces on `large` are created in every load run (the creation criterion's repo) and timed.
- **Limits are recorded, not assumed.** The load test reads and writes into its JSON report: `fs.inotify.max_user_watches`, `max_user_instances`, and the daemon's inotify instance count (`/proc/<pid>/fd` entries pointing at `anon_inode:inotify`) on Linux; the daemon's peak thread count (`/proc/<pid>/status` `Threads:` on Linux, `ps -M <pid> | wc -l` on macOS); `max_concurrent_scans`; and the watcher's per-minute summary line that R1.13's daemon logs (`watcher summary: scans=N queued_max=M wait_max_ms=K`), parsed from `logs/daemon.log`. (R1.13 must emit that line; reported.)
- **Report format**: one JSON file per run at `target/load/<os>-<preset>-<timestamp>.json` with the machine description, config, every per-workspace creation time, the latency samples, the percentiles, the limits, and pass/fail; plus a Markdown summary printed to stdout in the shape of the table in `docs/load-tests.md`. CI uploads `target/load/` as an artifact.
- **Kill semantics.** "Kill the agent" is SIGKILL to the `reef ws run` process and then to its orphaned child; "kill the daemon" is SIGKILL to the daemon pid. Nothing in these tests uses SIGTERM, which the graceful paths already cover in R1.03 and R1.21.
- **Disk full** is a real `ENOSPC` on the state directory's filesystem: a 256 MB sparse APFS image on macOS, a 256 MB tmpfs on Linux. The invariants are that the daemon stays up, SQLite is not corrupted (`PRAGMA integrity_check` after), snapshots fail and are logged at `error`, and after space is freed the next snapshot succeeds with no edit lost.

### `crates/reef-daemon/tests/integration.rs`

Config for every test unless stated: `lease.default = "3s"`, `grace = "1s"`, `restart_grace = "2s"`, `heartbeat = "1s"`, `tick = "500ms"`, `watcher.debounce = "200ms"`, `fallback_interval = "5s"`.

1. `agent_killed_mid_edit_leaves_snapshot_and_no_directory`: `ws run -- sh -c 'for i in $(seq 1 1000); do echo $i >> log.txt; sleep 0.01; done; sleep 60'`; wait until `log.txt` has at least 100 lines; SIGKILL `ws run` and its child; assert within 10 s: workspace `reclaimed`, directory absent, `reclaims` row `reason == 'expired'` with `snapshot_taken == 1`, and the workspace's final commit tree contains `log.txt` with at least 100 lines (read through `reef_lib::jj::Repo::open` on the registered root and the commit id from `Inspect` before reclaim or from the `snapshots` table). The exit criterion.
2. `agent_killed_with_unsnapshotted_write`: write a file and SIGKILL within 50 ms (inside the debounce window); the final snapshot at expiry still captures it.
3. `lease_expiry_without_heartbeat`: `ws create` (no `ws run`); after `default + grace + tick` the workspace is reclaimed; `ws create --lease 10s` is still active at that point.
4. `heartbeat_in_grace_revives`: let the lease pass `expires_at`, heartbeat before `expires_at + grace`; not reclaimed; a heartbeat after `+ grace` is `Conflict`.
5. `two_workspaces_on_one_change`: `ws create --change C` twice (C created by a first `ws create` and released); A writes `a.txt`, B writes `b.txt`, both snapshot (explicit `Snapshot` RPC); assert: both `active`, A's commit tree has `a.txt` and not `b.txt`, B's has `b.txt` and not `a.txt`, both `change_id == C`, `Repo::heads()` on the root shows two commits with change id C, at least one workspace has `divergent == 1` and `attention == "divergent"`; then A writes `a2.txt` and B writes `b2.txt`, both snapshot again without error and each sees only its own files; release both without error. The exit criterion.
6. `daemon_killed_mid_snapshot_recovers`: workspace on `small`; `synth::mutate` with `modify: 500` in the workspace; trigger `Snapshot` and SIGKILL the daemon 20 ms later (a loop that varies the delay 5, 20, 50, 100 ms across four iterations to hit different phases); respawn; assert: `Status` ok, the workspace is `active`, `expires_at ≥ restart start + restart_grace` (nothing reclaimed on the first tick: no `reclaims` row for 2 s), `Snapshot` succeeds and its tree matches the disk (compare 500 files' content against the tree via `read_file_at`), and the daemon log has no `error` events after the respawn except at most one `stale working copy recovered`.
7. `daemon_killed_during_create`: SIGKILL during `Create` of a `medium` workspace (after `ws/<id>` appears, before `Create` returns); respawn; the half-made workspace is either `active` and usable or absent from `ws list` with its directory removed; never a directory without a row or a row with a missing directory. (R1.05's create must be transactional or self-healing on start; this test pins it.)
8. `restart_reestablishes_mounts_and_watchers` (Linux overlay tier under the privileged job; symlink tier elsewhere): workspace with a store (R1.20 fixture); SIGKILL and respawn; the mount is present, a write after respawn is snapshotted within `fallback_interval`.
9. `one_inotify_instance` (Linux): with 10 workspaces, exactly one `/proc/<pid>/fd` entry resolves to `anon_inode:inotify`.
10. `store_shared_by_twenty` (R1.20 fixture): 20 workspaces; `store list` shows `in_use_by == 20`; release all; `0`.
11. `move_keeps_lease_and_directory` (R1.06): `ws move` to another change; same lease id, same path, `op_id` recorded, no `reclaims` row.
12. `same_cli_both_platforms`: a scripted session (`register`, `create`, `run`, `list`, `inspect`, `release`, `gc`) produces JSON whose key sets are identical on macOS and Linux (the test writes `target/cli-shape-<os>.json`; the CI workflow diffs the two artifacts in a final job).

### `crates/reef-daemon/tests/disk_full.rs`

1. `enospc_does_not_corrupt_or_crash`: mount the 256 MB volume, start the daemon with `REEF_STATE_DIR` on it, register a `small` repo also on it, create a workspace; fill the volume with `fallocate`/`mkfile` until a 1 MB write fails; write a file in the workspace; wait `fallback_interval`; assert the daemon answers `Status`, the log has an `error` event with `message == "snapshot failed"` and an `ENOSPC` chain, the workspace is `active`; remove the filler; wait; the file is snapshotted; `PRAGMA integrity_check` on the database returns `ok`; `Repo::open` on the root succeeds and `op_log(10)` has no error.
2. `enospc_during_final_snapshot_keeps_directory`: fill, let a lease expire; the reclaim is attempted, fails, `attention == "final-snapshot-failed"`, the directory is kept; free space; the next tick reclaims with `snapshot_taken == 1`.

Skips with a visible `skipped: <reason>` when `hdiutil` fails (macOS) or when not running privileged (Linux).

### `crates/reef-daemon/tests/load.rs`

`#[ignore]`, `REEF_LOAD=1`, `REEF_LOAD_PRESET` (`medium` default, `large` opt-in), `REEF_LOAD_WORKSPACES` (200), `REEF_LOAD_STEADY_SECS` (300), `REEF_LOAD_WRITE_PERIOD_SECS` (60). One test function `load_profile` with phases: generate and register (timed); create 20 workspaces on `large` (always; timed, free-space delta before and after; asserts each under 1 s on the CoW tiers and reports the backend used); release them; create N workspaces on the preset (timed, free-space delta); steady state; burst; limits capture; teardown (release all, assert no directories remain under `ws/`); write the JSON report; print the Markdown table; assert the gate.

The writer is a tokio task per workspace with `tokio::time::interval` at the period and a start offset of `i * period / N`, writing `write-<seq>.txt` containing the write timestamp; the sampler polls `Inspect(snapshot_first = false)` every 250 ms and records `(workspace, seq, write_ts, last_snapshot_at)` once the commit id changes. Percentiles from the sorted samples.

### `.github/workflows/load.yml`

```yaml
name: Load tests
on:
  schedule: [{ cron: "23 5 * * 0" }]        # Sundays 05:23 UTC, medium
  workflow_dispatch:
    inputs: { preset: { type: choice, options: [medium, large], default: medium } }
permissions: { contents: read }
jobs:
  load:
    name: load ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    timeout-minutes: 90
    strategy: { fail-fast: false, matrix: { os: [ubuntu-24.04, macos-15] } }
    env: { REEF_LOAD: "1", REEF_LOAD_PRESET: "${{ inputs.preset || 'medium' }}" }
    steps:
      - uses: actions/checkout@v7
        with: { persist-credentials: false }
      - uses: actions-rust-lang/setup-rust-toolchain@v2
      - uses: taiki-e/install-action@v2
        with: { tool: cargo-nextest@0.9 }
      - name: Raise inotify limits for the large preset
        if: runner.os == 'Linux' && env.REEF_LOAD_PRESET == 'large'
        run: sudo sysctl -w fs.inotify.max_user_watches=4194304
      - name: Record limits
        if: runner.os == 'Linux'
        run: sysctl fs.inotify
      - run: cargo nextest run -p reef-daemon --test load --run-ignored all --no-fail-fast
      - uses: actions/upload-artifact@v7
        if: ${{ !cancelled() }}
        with: { name: "load-${{ matrix.os }}-${{ env.REEF_LOAD_PRESET }}-${{ github.sha }}-${{ github.run_id }}", path: target/load/, retention-days: 90 }
      - name: Drop fixtures before the cache is saved
        if: always()
        run: rm -rf target/synth target/load-fixtures
```

`ci.yml` gains the `integration` tests implicitly (they are ordinary tests in `check`) and a final `cli-shape` job that downloads both `target/cli-shape-*.json` artifacts and diffs their key sets (test 12).

## Implementation notes

- Create the 200 workspaces with bounded concurrency (8 at a time) so the creation timings reflect the daemon, not the test's own backlog; record both the per-create latency and the wall time for all 200.
- Writes must change content (`seq` in the file), or jj's scan sees an unchanged file and no snapshot happens.
- `Inspect(snapshot_first = false)` is essential; the default would make the sampler the trigger.
- The steady-state phase holds 200 open `ws` directories with watchers but only `ws create`d workspaces (no `ws run` processes), so the heartbeat load is the test's own loop calling `Heartbeat` every 20 s per workspace through one client; count those RPCs in the report.
- On macOS, FSEvents coalesces events; notify 8.2.0 configures the stream with latency 0.0 (`fsevent.rs:300`), so `watcher.debounce` (500 ms) is the only deliberate delay in the measured number.
- Time budget for the gated run on the Linux runner: generate `medium` 1 s, first snapshot 3 s, 20 × `large` create plus the `large` fixture 60 to 90 s, 200 × `medium` create 60 to 120 s, steady state 300 s, burst 30 s, teardown 60 s: about 12 minutes. The macOS runner is roughly twice as slow. `large` × 200 by hand: an hour.
- Kill the orphaned `sleep` and `sh` children in test 1 and 2 by pid; `SpawnedDaemon`'s drop does the same for the daemon. Use a `Drop` guard struct, not `defer`-style closures.
- The disk-full tests must put the *state directory* on the small volume; the cargo target dir stays where it is.

## Out of scope

- Regression gates on the load numbers (RX.06 owns thresholds; this ticket gates only the phase criterion).
- Backup round-trip under load (R1.18 has its own test with writers).
- Fault injection inside the daemon (a `fail`-point crate); kills are external only.
- Watchman (R1.14) in the load profile; a `REEF_LOAD_WATCHER=watchman` variant is a follow-up once R1.14 lands and Watchman is installed on the runner.
- Network partitions; there is no network in Phase 1.

## Risks

- The macOS runner has 3 cores and 7 GB; 200 workspaces of `medium` with jj's scan at 20 to 25 ms each should hold the 5 s p95 in steady state, but the burst will queue; if the steady-state gate fails only on macOS, the first lever is `watcher.max_concurrent_scans`, the second is to revise the target with a measured justification, never to drop the test.
- Runner noise: the gate is p95 over roughly 1,000 samples in steady state, which tolerates a few slow scans; a flaky gate is revised to p90 only with the numbers in the PR.
- `hdiutil` images occasionally fail to detach while a daemon still holds files; `SpawnedDaemon` is killed before detaching and `hdiutil detach -force` is the fallback.
- 14 GB of runner disk: the `large` opt-in profile may not fit on CI at all with 200 state directories; the report records the free-space check before the run and the run aborts with a clear message rather than filling the disk.
