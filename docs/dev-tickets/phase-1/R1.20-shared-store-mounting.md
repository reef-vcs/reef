# R1.20 Shared dependency store mounting

Phase 1 · Size M · Depends on: R1.19, R1.08, R1.09 · Unblocks: R1.23 (store checks in the integration suite), RX.01 (security review of the store as a lateral-movement path)

## Context

"Twenty workspaces on the same lockfile share one copy of the dependencies. Shared stores are mounted read-only, verified against the lockfile hash, and written only by the daemon, so an agent running arbitrary code cannot poison another agent's workspace" (`docs/design.md`, Workspaces). The worktree problem the design opens with is that each checkout drags its own `node_modules`, virtualenv, and `target`, ten times the size of the source tree. This ticket is the phase's answer: a store directory per `(store name, lockfile hash)` that the daemon builds once and links into every workspace whose lockfile hashes the same.

The phase exit criterion is "A shared dependency store is mounted read-only into every workspace and verified against a lockfile hash." The spec (`[[store]]` in `reef.toml`, R1.19) says what to build, from which lockfile, where to mount it, and with which command. This ticket builds, seals, mounts, verifies, and reports.

### What was verified while writing this ticket

- `blake3` 1.8.7 (CC0-1.0 OR Apache-2.0, on the allow list): `blake3::hash(&[u8]) -> Hash`, `Hash::to_hex() -> ArrayString<64>` (lowercase), `Hasher::update`, `Hasher::update_reader(impl Read)`. Source at `blake3-1.8.7/src/lib.rs` lines 279, 920, 1204, 1471.
- jj-lib 0.46.0: a lockfile's bytes at a commit come from `Repo::read_file_at` (R1.19, over `MergedTree::path_value` and `Store::read_file`). The hash is computed over the blob's bytes, so two commits with byte-identical lockfiles share a store even if the file's mode differs.
- `notify` 8.2.0 `Config::default()` has `follow_symlinks: true` (`config.rs:122`), and the inotify backend passes it to `WalkDir::follow_links` when adding a recursive watch (`inotify.rs:408`). A symlinked store under a watched workspace would therefore be walked and watched unless R1.13 builds its watcher with `.with_follow_symlinks(false)`. Reported to R1.13; this ticket also filters events by prefix as a second line of defense.
- `nix` 0.31.3 `mount` feature (`mount = ["uio"]` in its `Cargo.toml`) provides `nix::mount::{mount, umount2, MsFlags}`; a read-only bind mount is `mount(src, dst, None, MS_BIND, None)` followed by `mount(None, dst, None, MS_BIND | MS_REMOUNT | MS_RDONLY, None)`. Not exercised on this machine (macOS); the Linux CI job from R1.09 runs it.
- jj-lib treats a symlink in the working copy as a `TreeValue::Symlink` entry unless an ignore rule matches it, so the mount path must be in the ignore chain (R1.19's `effective_excludes` already anchors it) or every snapshot would record the link.

## Decisions

- **Store identity is `(repo, name, blake3(lockfile bytes at the target commit))`**, directory `<state>/stores/<name>/<hash>/`, row in `stores`. The hash is a verification digest; it is not an object identity and ADR 0011 is unaffected. Stores are per daemon, not per repository: two registered repositories with the same lockfile bytes and store name share one directory. The `stores` table's `repo_id` column records the repository that first built it; `stores.name` + `lockfile_hash` is the lookup key and `repo_id` is informational (deviation from "every table carries `repo_id`" in spirit but not in schema).
- **Only the daemon writes a store.** `Stores.Build` runs the spec's `build` argv as the daemon's user inside a scratch workspace on the requested revision (default: the repository's `main` bookmark, else the `default` workspace's commit, the same rule as `Create`), with the store's mount path symlinked to `<state>/stores/<name>/<hash>.building/`, `cwd` at the scratch root, and the environment `PATH`, `HOME`, `LANG`, `TMPDIR` from the daemon plus `[store.env]` plus `REEF_STORE_DIR` and `REEF_STORE_NAME`. On exit 0 the directory is sealed; on any other exit it is renamed to `<hash>.failed-<timestamp>/` and kept for inspection until GC. The scratch workspace is a normal workspace with owner `reef-store-build`, purpose `store build <name>`, backend `copy` (a store build must not depend on a CoW backend being available), released when the build ends.
- **Sealing** is `chmod -R a-w` on every file and directory (`0555`/`0444`, executables keep their bits) and `sealed = 1` in the row. On Linux, when the daemon has `CAP_SYS_ADMIN` (the same probe as R1.09's kernel overlayfs tier), workspaces get a read-only bind mount instead of a symlink; the chmod still happens so the symlink tier is no weaker than it has to be. Sealing is advisory against a same-uid agent (it can `chmod +w`); that is the first item handed to RX.01.
- **Mounting** happens in `Create` after the backend materializes and before the working-copy state is seeded: for each store in the resolved spec, hash the lockfile at the target commit, look up a sealed store, and link: symlink `<ws>/<mount>` → store directory (relative symlink is not used; absolute, because the workspace may be moved by `--path`), or on the privileged Linux tier `mkdir <ws>/<mount>` and bind-mount read-only. If `<mount>` already exists in the materialized tree the request fails with `Conflict` ("mount path exists in the tree; add it to .gitignore and remove it from the change"). `Move` (R1.06) re-resolves the spec at the new commit and remounts.
- **A missing store does not silently pass.** Without a sealed store for the hash, `Create` fails `Unavailable` with the message `store <name> has no build for lockfile hash <hash>; run: reef store build <name> --repo <id> --rev <commit>` unless the request sets `missing_stores = SKIP`, in which case the workspace is created without that mount and `attention = 'store-missing'`. The CLI flag is `--skip-missing-stores`. (`store-missing` is a new `attention` value; reported for the README.)
- **Verification after creation** is by tree lookup, not rehashing: the workspace handle keeps each store's lockfile `FileId` at creation; after every snapshot R1.13 compares the new tree's `FileId` at the lockfile path and, when it differs, sets `attention = 'store-hash-mismatch'` and logs at `warn` with the store name. The mount stays (removing it under a running build would be worse); the agent's `ws inspect` shows the mismatch and the fix (`reef store build`, then `reef ws move` to the same change, which remounts).
- **Excluded everywhere**: the mount path is in the ignore chain (R1.19 `effective_excludes`), the watcher filters events under it, `disk_usage` skips it, and backend tear-down removes the symlink (or unmounts the bind mount) before removing the tree. GC (R1.17) item (4) removes store directories no spec of a registered repository names and every `.failed-*` directory older than the undo window; this ticket adds the `stores` queries R1.17 needs.
- **`Stores` service**: `Build` (server-streaming: `BuildEvent { line: string, stream: STDOUT|STDERR }` then `BuildEvent { done: BuildResult { hash, path, bytes, sealed, exit_code } }`), `List` (per repository: name, hash, path, bytes, built_at, sealed, in_use_by workspace count). Build timeout `request.timeout` (default 30 min); on timeout the process group is killed and the build counts as failed. One build per `(name, hash)` at a time; a concurrent request gets `AlreadyExists` naming the running build.
- **ADR 0022** records the store model, the tiers, the trust boundary, and what RX.01 must review.

### `crates/reef-daemon/src/store/mod.rs`

```rust
pub(crate) struct StoreManager { state_dir: PathBuf, db: Db, privileged: bool }

pub(crate) struct StoreKey { pub name: String, pub lockfile_hash: String }   // hex, 64 chars
pub(crate) enum MountMode { Symlink, Bind }
pub(crate) struct MountedStore { pub key: StoreKey, pub mount: RepoPathBuf, pub mode: MountMode, pub lockfile_id: FileId }

impl StoreManager {
    pub(crate) fn hash_lockfile(bytes: &[u8]) -> String;                      // blake3 hex
    pub(crate) fn dir(&self, key: &StoreKey) -> PathBuf;                       // <state>/stores/<name>/<hash>
    pub(crate) fn sealed(&self, key: &StoreKey) -> Result<Option<StoreRow>, StoreError>;
    pub(crate) fn mount(&self, key: &StoreKey, ws_root: &Path, mount: &RepoPath) -> Result<MountMode, StoreError>;
    pub(crate) fn unmount(&self, ws_root: &Path, mount: &RepoPath, mode: MountMode) -> Result<(), StoreError>;
    pub(crate) fn seal(&self, building: &Path, key: &StoreKey) -> Result<StoreRow, StoreError>;
    pub(crate) fn in_use(&self, key: &StoreKey) -> Result<u32, StoreError>;    // active workspaces mounting it
    pub(crate) fn unreferenced(&self, named: &HashSet<StoreKey>) -> Result<Vec<StoreRow>, StoreError>;  // for R1.17
}

#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub(crate) enum StoreError {
    #[error("store {name} has no build for lockfile hash {hash}; run: reef store build {name}")]
    Missing { name: String, hash: String },
    #[error("mount path {mount} exists in the tree")]
    MountExists { mount: String },
    #[error("store {name} build already running")]
    BuildRunning { name: String },
    #[error("store {name} build exited with {code}")]
    BuildFailed { name: String, code: i32 },
    #[error("store {name} build timed out after {secs}s")]
    BuildTimeout { name: String, secs: u64 },
    #[error("{op} {path}")]
    Io { op: &'static str, path: PathBuf, #[source] source: std::io::Error },
    #[error("database")]
    Db(#[from] DbError),
}
```

`Classify`: `Missing` → `Unavailable`, `MountExists` → `Conflict`, `BuildRunning` → `AlreadyExists`, `BuildFailed`/`BuildTimeout` → `Internal` (the build's own output explains it), `Io` → `classify_by_source`.

### `crates/reef-daemon/src/store/build.rs`

The build job: create the scratch workspace through the same `Create` path R1.05 implements (so a store build exercises the real flow), with `missing_stores = SKIP` (a build must not require the store it is building) and the building directory linked at `mount`; spawn the argv with `std::process::Command` on a blocking task, `process_group(0)` so the whole tree dies on timeout, stdout and stderr piped and forwarded as `BuildEvent`s line by line; wait; seal or mark failed; release the scratch workspace; write `reclaims` with reason `released` and `detail = "store build"`. The `op_id` in the result is the scratch workspace's release operation.

### `crates/reef-daemon/src/store/mount.rs`

`symlink_mount` (`std::os::unix::fs::symlink`, parent directories created, refuse if the path exists), `bind_mount` (`cfg(target_os = "linux")`, the two `nix::mount::mount` calls, `umount2(MNT_DETACH)` on unmount), and `seal_tree` (walk with `walkdir`, `set_permissions` clearing write bits; `0755` → `0555`, `0644` → `0444`). On macOS the bind tier does not exist; `MountMode::Bind` is never chosen.

### `crates/reef-daemon/src/service/stores.rs`

The tonic service over `StoreManager`, with the stream built from a `tokio::sync::mpsc` channel the build task writes to.

### `crates/reef-daemon/src/service/workspaces.rs` (changes)

In `Create`: after materialize, resolve stores (hash lockfile bytes at the target commit via `Repo::read_file_at`, `sealed()`, `mount()` or the missing rule), record `MountedStore`s on the handle and in `WorkspaceInfo`; in `Release` and in the lease manager's reclaim: `unmount()` before `tear_down`. In R1.13's post-snapshot hook: compare lockfile `FileId`s and set `attention`.

### `crates/reef-daemon/tests/stores.rs`

Fixture: `TestDaemon` with a `small` synthetic repo plus `reef.toml` declaring one store `deps` with `lockfile = "deps.lock"`, `mount = "vendor/deps"`, `build = ["sh", "-c", "mkdir -p \"$REEF_STORE_DIR\" && cp deps.lock \"$REEF_STORE_DIR/manifest\" && echo built"]`, snapshotted.

1. `create_without_store_fails_unavailable`: `Create` → `UNAVAILABLE`, message names the hash and the `reef store build` command.
2. `create_with_skip_marks_attention`: `missing_stores = SKIP` → created, no `vendor/deps`, `attention == "store-missing"`.
3. `build_seals_and_lists`: `Build` streams the `built` line, then `done` with `sealed = true`; the store directory contains `manifest`; every file and directory lacks write bits; `List` shows it with `in_use_by == 0`.
4. `create_mounts_sealed_store`: `Create` succeeds; `<ws>/vendor/deps` is a symlink to the store (or a bind mount on the privileged job: `statfs` differs from the workspace root); `WorkspaceInfo.stores[0].mode` matches; `in_use_by == 1`.
5. `store_is_excluded_from_snapshots`: write a file through the mount is impossible (read-only, `EACCES`); write a file next to it; snapshot; `changed_paths_in_wc` does not list anything under `vendor/deps`, and the symlink itself is not in the tree.
6. `two_workspaces_share_one_store`: both `Create`; both `vendor/deps` resolve to the same directory; `in_use_by == 2`; release one → `1`.
7. `lockfile_edit_sets_mismatch`: append to `deps.lock` in the workspace, wait for the watcher snapshot (or call `Snapshot`), `Inspect.attention == "store-hash-mismatch"`, mount still present.
8. `build_failure_keeps_failed_dir`: a spec whose build is `["sh", "-c", "exit 3"]`: `done.exit_code == 3`, `sealed == false`, a `.failed-*` directory exists, `List` does not show it, `Create` still `UNAVAILABLE`.
9. `build_timeout_kills_process_group`: build `["sh", "-c", "sleep 300"]` with `timeout = 2s`: finishes within 10 s, `BuildTimeout`, no `sleep` process left (check `pgrep -f` or `kill -0` on the recorded pid).
10. `concurrent_build_rejected`: two `Build`s for the same key; the second is `ALREADY_EXISTS`.
11. `release_unmounts_before_teardown`: after `Release`, the store directory is intact and sealed; the workspace directory is gone.
12. `bind_mount_is_read_only` (`#[cfg(target_os = "linux")]`, `#[ignore]` unless `REEF_PRIVILEGED_TESTS=1`): on the `overlayfs` CI job, the mount is `MountMode::Bind`, writing through it fails with `EROFS`, and `chmod +w` on the store directory from the workspace side does not make it writable.

### `docs/adr/0022-shared-dependency-stores.md`

Status `accepted`. Context: ten-times-the-tree dependency directories, the design's shared store, verification against the lockfile. Decision: the key, daemon-only builds in a scratch workspace, sealing, symlink and bind tiers, fail-by-default on a missing store, mismatch detection by tree lookup. Consequences: builds are a daemon operation with the daemon's privileges (RX.01); a same-uid agent can defeat `chmod` sealing but not a read-only bind mount; stores outlive repositories until GC; build-cache stores keyed by tree hash (design: "a build cache keyed by tree hash") are not this ticket and would be a second store kind. Alternatives: per-workspace installs (rejected: the problem statement), a content-addressed file store like pnpm's with hard links into each workspace (rejected for Phase 1: ecosystem-specific; a later store kind), running builds inside the agent's workspace (rejected: the agent could poison the store).

Section "For RX.01": arbitrary command execution as the daemon user from a repository file, symlink tier writable by a same-uid agent, `[store.env]` as an injection surface, the build's network access, and the absence of any daemon-user separation in Phase 1.

## Implementation notes

- Hash the lockfile from the tree, never from disk: the on-disk file in the workspace is what an agent may have edited.
- When the backend is overlayfs, the symlink lands in the upper layer; the bind-mount tier needs the mount point directory created in the merged view (which also lands in the upper layer) before mounting. Unmount order on tear-down: store mounts first (the release and reclaim pipelines call `StoreManager::unmount` before `backend.tear_down`), then the overlay; `reef_daemon::backend` never depends on `reef_daemon::store`.
- Build output can be large; forward lines through a bounded channel (1,024) and drop with a counter when the client is slow, reporting `dropped_lines` in `BuildResult` (add the field).
- A build may `cd` into the store through the symlink and write there; that is the intended path. It may also write elsewhere in the scratch workspace (caches); those writes are released with the scratch workspace and never snapshotted because the scratch workspace is released without a final snapshot (`Release.snapshot_first = false`), which this ticket adds as a request option.
- `seal_tree` on macOS: `chflags uchg` is deliberately not used (needs the same uid to clear, and would make GC's removal need an extra step).
- The `stores` row is inserted when the build starts (`sealed = 0`, `built_at NULL`) so `BuildRunning` is a database check, not an in-memory one, and survives a daemon restart as a stale row that `List` hides and GC removes.

## Acceptance criteria

- [ ] `Stores.Build` and `Stores.List` exist in `stores.proto` and are served; `reef store build` and `reef store list` work in text and JSON mode.
- [ ] A workspace created on a commit with a sealed store for its lockfile has the store at `mount`, read-only, excluded from snapshots and from the watcher (tests 4 and 5).
- [ ] Without a sealed store, `Create` fails `UNAVAILABLE` with the build hint, or marks `store-missing` with `--skip-missing-stores` (tests 1 and 2).
- [ ] Twenty workspaces on one lockfile share one store directory; `reef store list` reports `in_use_by = 20` (extend test 6 to 20 in R1.23's suite; here 2).
- [ ] Editing the lockfile in a workspace sets `store-hash-mismatch` after the next snapshot (test 7).
- [ ] Failed and timed-out builds leave nothing sealed and kill their process group (tests 8 and 9).
- [ ] Test 12 passes on the Linux `overlayfs` CI job (bind mount read-only, chmod from the workspace side ineffective).
- [ ] ADR 0022 exists with the "For RX.01" section; the ADR index row is added.
- [ ] `just ci` passes; the Linux `overlayfs` job passes.

## Out of scope

- Build caches keyed by tree hash (a second store kind; Phase 2 or later).
- Ecosystem presets (pnpm, cargo, uv) that generate `[[store]]` entries.
- Daemon-user separation or sandboxing of the build command (RX.01 decides).
- Stores on the remote store (Phase 4).
- Automatic rebuild when a lockfile changes; the mismatch is reported, the rebuild is a human or agent action.

## Risks

- A build that needs network access (every package install) runs with the daemon's network; CI's build test uses `sh` and `cp` only, so a real `pnpm install` is only exercised by hand before the phase closes (record it in the PR).
- `chmod -R a-w` on a store with hundreds of thousands of files (a `node_modules`) takes seconds; it runs once per build, on the blocking pool, and is acceptable.
- The symlink tier changes `node_modules` from a directory to a symlink, which some tools resolve (`realpath`) and then write next to; such writes fail on the sealed store with `EACCES`. The quickstart documents it; the bind tier avoids it.
- If `fuse-overlayfs` is the workspace backend, the symlink lives in the upper layer and resolves normally; the bind tier is not used on that tier because FUSE mounts cannot host bind mounts without privilege.
