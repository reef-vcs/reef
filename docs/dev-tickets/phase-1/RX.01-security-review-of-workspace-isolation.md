# RX.01 Security review of workspace isolation

Cross-cutting · Size M · First needed: Phase 1 release · Depends on: R1.20 (stores, the first item handed to this ticket), R1.15 (leases), R1.25 (implicit registration), R1.09 (the privilege tiers), R1.18 (backup files), R1.28 (the installer and release workflow) · Unblocks: the 0.1.0 release (its known-limitations list and `SECURITY.md`), R2.08 (the requirements its remote listener must meet), RX.02 (the threat model's shape)

The brief lives with the Phase 1 tickets because that is where it first runs; it is numbered as a cross-cutting ticket in `docs/dev-phases.md`.

## Context

Phase 1 ships a daemon that materializes repository trees, runs commands a repository declares, deletes directories, binds a socket, registers any git checkout a command is run in, and installs itself with `curl | sh`. Eight tickets deferred a security question to this one: ADR 0022's "For RX.01" (store builds run arbitrary argv as the daemon user; the symlink tier's sealing is advisory; `[store.env]`; build network access; no daemon-user separation), ADR 0019 and R1.15 (the lease id is the capability, the owner is informational), R1.21 and ADR 0016 (no sandbox for `ws run`), R1.09 (`overlay_nosuid`), ADR 0004 ("filesystem permissions on the socket are the first access control"), and R2.08 ("threat model reviewed under RX.01"). `docs/design.md` also makes one claim this ticket has to either make true or qualify: shared stores are "written only by the daemon, so an agent running arbitrary code cannot poison another agent's workspace" (`docs/design.md:115`).

No threat model exists, so those items have nowhere to be answered against. This ticket writes it, fixes what it finds that must be fixed before anyone installs 0.1.0, and writes down the rest where a user will read it.

### What was verified while writing this ticket

Reef at `main` (57af199), jj-lib and jj-core 0.46.0, notify 8.2.0.

- **Everything runs as one uid, and the daemon has no notion of a client.** The socket is `0600` (`crates/reef-daemon/src/daemon.rs:722`), so only processes with the daemon's uid connect, and nothing reads peer credentials (no `SO_PEERCRED` or `getpeereid` anywhere in `crates/`). A root daemon (the kernel overlay tier, ADR 0016) therefore serves only root clients: the agent is root too. Every RPC is open to every client: `Release` takes no lease (`crates/reef-daemon/proto/reef/daemon/v0/workspaces.proto:191-200`), `List` and `Inspect` return every workspace's lease id (`crates/reef-daemon/src/service/workspaces.rs:158-166, 194`), and `ws run --workspace` attaches by reading that id from `Inspect` and heartbeating it (`crates/reef-vcs/src/cli/ws_run.rs:300-324`; `may_attach` compares the owner string, which any client can match with `--owner`). `Create.path` places a workspace root at any absolute path that does not exist (`workspaces.proto:72`, `crates/reef-daemon/src/workspace/create.rs:293-330`, `reef ws create --path`, `crates/reef-vcs/src/cli/ws.rs:105-107`), and `Backup` writes to any absolute directory outside the state directory that is new or empty (`crates/reef-daemon/src/maintenance/backup.rs:393-430`).
- **Modes.** State directory, log directory, and the socket's parent (`$XDG_RUNTIME_DIR/reef`) are created `0700` (`daemon.rs:772-783`, `crates/reef-daemon/src/logging.rs:280-283`, `daemon.rs:702-703`); the lock file `0600` (`crates/reef-daemon/src/lock.rs:81`); a backup destination that did not exist `0700` (`backup.rs:421-427`); a restored state directory `0700` (`crates/reef-daemon/src/maintenance/restore.rs:299-305`). `create_private_dir` leaves an existing directory as it is (`daemon.rs:771-773`), and nothing checks who owns the state directory. The database is opened with `rusqlite::Connection::open` and no mode (`crates/reef-daemon/src/db/mod.rs:259-269`), so it gets `0644 & ~umask`; the backup's `reef.sqlite3` likewise (`backup.rs:440-455`), and `fs::copy` keeps the source modes for the rest. Both are private only because their directories are.
- **Store builds.** `Stores.Build` takes `repo`, `name`, `rev`, `timeout`, `force` and no argv (`crates/reef-daemon/proto/reef/daemon/v0/stores.proto`); the argv comes from `reef.toml` in the tree. The command runs with `env_clear()`, then `PATH`, `HOME`, `LANG`, `TMPDIR` from the daemon, then `[store.env]` (which can override those four and set anything else), then `REEF_STORE_DIR` and `REEF_STORE_NAME` (`crates/reef-daemon/src/store/build.rs:61, 443-461`). Nothing triggers a build but the RPC; the missing-store error's `next` is `["reef","store","build",<name>,"--repo",<id>,"--rev",<commit>]` (`crates/reef-daemon/src/store/mod.rs:258-273`), which an agent following ADR 0025's contract runs verbatim. The CLI streams the build's output but never shows the argv (`crates/reef-vcs/src/cli/store.rs:88-125`). `name` matches `[a-z0-9][a-z0-9_-]{0,63}` (`crates/reef-lib/src/spec.rs`), so it cannot start a flag. All twelve `Advice::run` sites were read: every `next` is literal words plus ids the daemon generated, `name` above, or a path the client itself supplied (`crates/reef-daemon/src/workspace/mod.rs:589-592`).
- **Registration walks to `/`.** `find_git_root` tries every ancestor of the given path for `.jj` or `.git` (`crates/reef-daemon/src/repo/registry.rs:286-300`) with no ceiling and no ownership check, then writes `/.jj/` into `.git/info/exclude` and creates `.jj` (`registry.rs:240-255`). The CLI does this implicitly for any command whose `--repo` or cwd is in no registered repository (`crates/reef-vcs/src/cli/mod.rs:277-300`, `[repo] auto_register = true`, `crates/reef-daemon/src/config.rs:533-539`). jj-lib opens the git repository through `gix::open::Options::default().strict_config(true)` (jj-lib `src/git_backend.rs:619-635`); whether gix reduces trust for a repository owned by another user was not verified.
- **Repository content and the filesystem.** jj-lib refuses to check out an entry named `.git` or `.jj` (`src/local_working_copy.rs:822`, `reject_reserved_existing_path`) and refuses `.` and `..` as file names (`jj-core src/repo_path.rs:95-104`, `to_fs_name`). `RepoPathComponentBuf::new` rejects only an empty name or one containing `/` (`repo_path.rs:51-57`), and `GitBackend::read_tree` unwraps it (`src/git_backend.rs:1181-1184`): a git tree with such an entry panics the job, which the repository thread catches (`crates/reef-daemon/src/repo/thread.rs:132-134`). Every Reef walk refuses to follow symlinks: copy, disk usage, trash removal, and the trash sweep (`crates/reef-daemon/src/backend/fs_util.rs:6-8, 37-38, 383-384, 644-667, 675`), the abandoned-create sweep (`crates/reef-daemon/src/workspace/abandoned.rs:238`, tested), store mounts, which check every ancestor of the mount path and never unmount through a symlink (`crates/reef-daemon/src/store/mount.rs:30-70, 284-288`), and the notify watcher, built with `with_follow_symlinks(false)` (`crates/reef-daemon/src/watcher/notify.rs:69`, tested at `:490`). Tear-down renames the root to a `.trash-*` sibling and deletes that (`fs_util.rs:526-567`), so a root an agent replaced with a symlink is unlinked, not followed. `reef init` follows a symlinked `AGENTS.md` or `CLAUDE.md` but skips a target outside the repository (`crates/reef-vcs/src/agents/mod.rs:296-304`).
- **Privilege.** The bind tier and kernel overlay tier are chosen by `CapEff` bit 21 (`crates/reef-daemon/src/backend/overlay/mod.rs:619`, `crates/reef-daemon/src/store/mod.rs:730-740`); the bind mount is `MS_RDONLY | MS_NOSUID` (`mount.rs:226-234`); overlays are `MS_NOSUID` only with `workspace.overlay_nosuid` (`crates/reef-daemon/src/backend/overlay/kernel.rs:24-38`, default false, `config.rs:421-441`). Nothing logs that the daemon is root.
- **Installer and release.** `install.sh` fetches over HTTPS only (`--proto '=https,file' --proto-redir '=https' --tlsv1.2`), verifies each tarball against the release's `SHA256SUMS`, installs without `sudo`, and defines everything before `main "$@"` on its last line, so a truncated download runs nothing. The checksum file comes from the same release as the tarball, so it proves the download is what GitHub serves, not who built it. `release.yml` runs with `permissions: contents: read`, `persist-credentials: false`, and `contents: write` on the publish job only; the tap deploy key is scoped to the tap. Binaries are unsigned (R1.28, R4.17) and no provenance is attested.
- **Claims in the documents.** `docs/design.md:115` says an agent "cannot poison another agent's workspace"; the quickstart's limitations already say the opposite for the symlink tier (`docs/quickstart.md:240`). `SECURITY.md` is R0.08's stub and names this ticket.

## Decisions

- **One uid is one trust domain in Phase 1, and the daemon is not a boundary against its own clients.** An agent in a workspace runs as the user, can reach the socket, and can therefore do everything the user can: read and write every workspace, the user's checkout, the sealed stores (symlink tier), the state directory, and call every RPC. Workspace isolation in Phase 1 is isolation of *accidents* (a separate directory, a separate working-copy commit, build outputs out of the tree, a lease that cleans up) and of *repository content* (a tree, a `reef.toml`, a symlink). It is not containment of a hostile agent; that needs a sandbox outside Reef (a harness sandbox, a user namespace, a microVM: the design's "Sandboxed microVM" row and ADR 0016's user-namespace alternative). This is written down as **ADR 0027, "Trust boundaries in Phase 1"**, and every item below follows from it. ADR 0019's and ADR 0022's open questions are answered by it, not by editing them (ADRs are frozen after acceptance).
- **Actors, in and out of scope for 0.1.0:**

  | Actor | In scope | Why |
  | --- | --- | --- |
  | A same-uid agent, in a workspace, running arbitrary code | Only as the subject of claims: no document may promise protection against it that the code does not enforce | Not a boundary (above) |
  | Another local user on the same host | Yes | The one boundary the kernel gives us: modes and ownership |
  | Repository content: a repository the user cloned, or a commit an agent made (`reef.toml`, tree entries, symlinks, `.git/config`) | Yes | Reef acts on it with the user's privileges before the user runs anything from it |
  | A compromised package fetched by a store build | Documented only | Equivalent to running the install yourself; Reef cannot vet it |
  | A network attacker against the installer, and the release pipeline | Yes | 0.1.0 is the first thing anyone installs |
  | A remote client (R2.08) | Requirements only | No listener exists; the model states what one must satisfy |
  | Forged evidence, keys, executors | No | RX.02, Phase 3 |

- **Severity rubric** (used in the findings table, applied by the implementing agent to anything new it finds):

  | Severity | Meaning |
  | --- | --- |
  | Critical | Repository content gets code execution, or a write or delete outside the workspace and state directory, from an operation that does not ask for that repository's code to run (create, snapshot, release, reclaim, gc, backup, registration); or another local user reaches the socket, state, or workspaces |
  | High | Another local user reads Reef state or a workspace, or plants something Reef then acts on; repository content makes one of those same operations act outside the workspace and state directory; a tampered binary installs over HTTPS without a checksum failure |
  | Medium | A documented promise the code does not keep; repository content crashes or wedges the daemon; an operation that does ask for the repository's code to run (`reef store build`) does so without showing the command or without an operator's switch; a same-uid process doing something the documents imply it cannot |
  | Low | Hardening with no concrete actor behind it |

  The line between the first two rows and the third is whether the operation *asks for the repository's code*. `reef store build` runs the repository's declared build command, as `npm ci` runs its `package.json` scripts; a user or agent that runs it has asked, and the one-uid decision above says the daemon running it is not an escalation over the agent running it. What is wrong with it today is that the command is never shown and nothing can turn it off, which the third row names. The same line puts `git gc` reading a user-owned `.git/config` outside the model: that is git.

  **Blocks 0.1.0:** every Critical and High is fixed or unreachable by default; every Medium is fixed or listed in `docs/quickstart.md`'s limitations and in the threat model with its number; Low is filed. A promise stronger than the code is itself a Medium: the fix is the document.
- **Deliverable shape.** Two documents and a set of fixes with tests:
  - `docs/threat-model.md`, a living document in the shape of `docs/load-tests.md`: assets, actors, boundaries, what each component trusts, a **findings table** (`S-nn`, area, actor, severity, status: *fixed in RX.01* with the test's name, *documented* with where, or *follow-up* with the issue), and a section "Requirements for a remote listener" for R2.08. Later tickets add rows; the table is the register `SECURITY.md` points at.
  - **ADR 0027** (the decision, short): one uid is one trust domain; what is and is not a boundary; what that implies for the API (every RPC is authorized by the socket's mode, so a listener that is not the socket needs its own identity before serving any of them); what the kernel overlay tier means (everyone is root); the review's stance on store builds and leases.
  - The fixes below, each with a named test, each a row in the table.
- **Fixed in this ticket** (the known items, decided here):
  - **S-01 State directory ownership and mode (High).** At start, before anything else is created: `stat` the state directory; if it exists and is not owned by the daemon's euid, refuse to start (`PermissionDenied`, hint naming the directory and its owner); if it has any group or other bit, `chmod 0700` and log at `warn`. The same check on `<socket parent>` when it is not the state directory. The database is created `0600` (open the file with `OpenOptions::mode(0o600)` before `Connection::open`; an existing file is `chmod`ed). A backup destination that existed and was empty is `chmod 0700`, and its `reef.sqlite3` `0600`. A restore target that exists gets the same ownership check. **No exception for root.** A root daemon started with `sudo -E` keeps the user's `HOME` and `XDG_STATE_HOME`, so its default state directory is the user's; if that directory exists it is owned by the user and the daemon refuses, with the hint "set `REEF_STATE_DIR` (for example `/var/lib/reef`) or run the daemon as that user". Two uids sharing one state directory never works (a root-owned database, socket, and lock refuse the user's next daemon), so refusing is the only honest answer; a missing default directory is created by root, owned by root, and is root's from then on. The quickstart's kernel-tier sentence says to set `REEF_STATE_DIR` for a root daemon.
  - **S-02 Registration refuses a root owned by someone else (High).** `RepoRegistry::register` (implicit or explicit) `stat`s the `.jj` directory, or the `.git` directory it would initialize beside, and accepts it when its owner is the daemon's euid or, when the euid is 0, the uid in `SUDO_UID` (git's own rule for `safe.directory` under `sudo`); otherwise `PermissionDenied`: "`<root>` is owned by uid N; Reef registers repositories owned by the user running the daemon (or the `sudo` user); run the daemon as that user, or set `[repo] allow_foreign_owner = true` in `<state>/config.toml`". This is git's `safe.directory` rule, for the same reason: implicit registration walks to `/`, so a `.git` another user planted in a shared directory (`/tmp`, a CI scratch volume) would otherwise be registered, written to, and have its trees materialized and its `git gc` run with its `.git/config`. A root daemon in a dedicated VM serving a user's clone without `sudo` (a systemd unit, a container entrypoint) is the operator's configuration, and the operator sets the key. New config key `[repo] allow_foreign_owner = false`, read by the daemon.
  - **S-03 Store builds are visible and can be switched off (Medium, by the rubric's third row).** `reef store build` prints, before the first output line, `reef: building <name> at <rev short>: <argv, shell-quoted>` plus `env: K=V ...` for `[store.env]` on stderr, in text and JSON mode (as the registration line does, `cli/mod.rs:290-297`); the daemon logs the same at `info` with the argv as a field. New config key `[store] allow_builds = true`; with `false`, `Stores.Build` is `PermissionDenied` with the hint "store builds are off on this daemon (`[store] allow_builds`); build the store elsewhere or turn them on". The default stays `true` and the `next` for a missing store stays, because an agent that follows the hint runs the repository's build command, which is what an agent working in that repository does anyway (`npm ci`, `cargo build`), and no consent step the socket could carry tells the user from the agent. The one configuration in which the daemon running it is worse than the agent running it is S-07, and the switch is its answer. `[store.env]` is not restricted: it is weaker than `build` itself. The build's network access is not restricted: documented.
  - **S-04 A root daemon says so (Medium).** At start, when the euid is 0, log at `warn`: "running as root: every client of this socket is root, and store builds run repository commands as root; the kernel overlay tier is meant for a VM or container dedicated to the agents". `docs/quickstart.md:26` gains the same sentence and `REEF_STATE_DIR`. `workspace.overlay_nosuid` keeps its default: in the kernel tier the agent is root, so `nosuid` buys nothing today; the flag stays for a future daemon-user separation, and ADR 0027 says so.
  - **S-05 The documents match the code (Medium).** `docs/design.md:115` becomes: "written only by the daemon and, on Linux when the daemon has `CAP_SYS_ADMIN`, mounted read-only; elsewhere protected by file modes, which a process running as the same user can undo" with a link to `threat-model.md` (written as inline code here so `scripts/doc-links.sh` passes before the file exists). `docs/quickstart.md`'s limitations gain: workspaces are not a sandbox (one sentence, pointing at the threat model), store builds run a repository's command as the daemon's user and `[store] allow_builds` turns them off, and registration refuses repositories you do not own. `SECURITY.md` replaces "Planned reviews" with "Threat model" (a pointer and the one-paragraph statement of the boundary) and keeps the reporting section. The code comment at `crates/reef-daemon/src/lease/mod.rs:11` points at ADR 0027.
  - **S-06 Release provenance (Low, cheap).** `release.yml`'s publish job attests the tarballs and `SHA256SUMS` with `actions/attest-build-provenance` (`id-token: write`, `attestations: write` on that job only), and `docs/quickstart.md`'s install section shows `gh attestation verify reef-<v>-<target>.tar.gz --repo reef-vcs/reef`. The installer does not verify it (`gh` is not a dependency we add). Gated on a `dry_run` release showing the step works; if it does not, the row becomes follow-up and R4.17 owns it.
  - **S-07 The socket is a hole in a harness sandbox (Medium, documented, with S-03's switch).** Harness sandboxes (Claude Code's, Codex's) confine an agent's writes and network; none of them know about Reef's socket. If the sandbox lets the agent connect to it, `Create.path`, `Backup.dest`, and `Stores.Build` act outside the sandbox with the user's full privileges: the build is arbitrary argv, and a workspace created at a path of the agent's choosing writes a tree of the agent's choosing there. This is the one-uid decision seen from inside a sandbox: Reef is not the sandbox's enforcement point and cannot tell the sandboxed agent from the user. The threat model and the quickstart's limitations say it plainly, name the socket paths to deny (`<state>/daemon.sock`, `$XDG_RUNTIME_DIR/reef/daemon.sock`), and name `[store] allow_builds = false` as the switch for an operator who wants a sandboxed agent to use workspaces but never trigger a build. The follow-up that would remove daemon-side execution altogether, running the build in the client's process inside its sandbox with the daemon only sealing the result, is filed from this ticket and not built here: it changes ADR 0022's second decision and is a Phase 2 question with R2.13's MCP server.
- **The repository's own flows under S-01 and S-02.** Checked while writing this: every integration test registers a synthetic repository it generated in its own temp directory (`crates/reef-daemon/src/testing.rs:75-96`), so the privileged CI job's root tests own what they register; the load test does the same; the onboarding benchmark clones as the container user into a fresh `REEF_STATE_DIR` (`crates/reef-testing/src/onboarding/run.rs:440, 480`); `just agent-files` runs `reef init --no-register`; and nothing registers the checkout itself. One flow crosses uids: `bench.yml` builds `target/bench-fixtures/<preset>-42/` as the runner user, then runs `workspace_create` again under `sudo -E env "PATH=$PATH" REEF_BENCH_PRIVILEGED=1` (`bench.yml:61-62`), whose `create_api` registers that runner-owned fixture from a root daemon (`crates/reef-daemon/benches/workspace_create.rs:294-307`). The `SUDO_UID` rule accepts it in CI; in the Docker container (root directly, no `sudo`) after a run as `dev` it would not, so `Api::start` sets `[repo] allow_foreign_owner = true` on its daemon with a comment: a bench fixture is the bench's own, whichever uid built it. The daemon state directories in all of these are temp directories the process creates, so S-01 touches none of them; the one hazard is a developer's `REEF_STATE_DIR` reused across a root run and a user run (the memory note's `/scratch/root-state`), which S-01 now refuses with a hint instead of failing later on a root-owned database.
- **Not fixed, documented** (rows in the table with status *documented*): the lease id as a capability (any client lists it; `Release` needs none; authorization is the socket); `Create.path` and `Backup.dest` anywhere the user can write; `Quiesce` by any client; `[store.env]` and build network access; the symlink tier's `chmod` sealing; `.git/config` of a user-owned repository driving `git gc` (`[gc] git_executable`), which is git's behavior; the unsigned binaries (R4.17); watcher snapshots holding every edit on the machine's disk (the design's durability section already says so).
- **Investigate first, with a gate** (as R1.30 does): crafted repository content against materialization, mount, snapshot, and tear-down. Build the tests under "Tests, hostile content" before changing anything. The gate: a test that shows a write, delete, or mount outside the workspace, the base cache, or the state directory is **Critical** and is fixed in this ticket whatever its size; a crash or a wedged repository thread is **Medium** and is fixed here if the fix is in Reef (restart or re-run the job) and filed upstream with a Reef-side guard if it is in jj-lib; a clean error is a passing test and a row with status *verified*.
- **R2.08 is in scope as requirements, out as a review.** The threat model's "Requirements for a remote listener" section says what R2.08 must satisfy before any RPC is served off the socket: TLS with a pinned or CA-issued certificate; a per-client token with scopes, so a phone that approves proposals is not a client that can `Create` a workspace at an arbitrary path, run a store build, back up to a path, quiesce, or release another client's workspace; the local socket's full API never exposed remotely by default; rate limits on the unauthenticated surface; audit of every remote mutation in the operation log's description. R2.08's brief reviews its implementation against that section and adds its rows to the table; that review is an amendment to `threat-model.md`, not a new RX ticket.
- **No external review for RX.01.** Reasons: the pre-release has no users to protect yet; the same-uid model leaves a reviewer nothing to find that the tests here do not assert; and the budget is better spent on RX.02, where identity and signatures appear and `dev-phases.md` already asks for one. The threat model records the decision and names RX.02 as the first external review.
- **Size stays M.** Two documents, six small fixes with two new config keys, one documented hole, and the tests below. If the hostile-content tests find a Critical, the fix joins this ticket and the PR says what it cost.

## Tests

Names follow the existing files. Tests that need another uid run in the privileged Linux CI job (`--features privileged-tests`, as root: `chown` a directory to uid 1) and skip with a message elsewhere, as `tests/stores.rs:647-660` does.

Modes and ownership (`tests/daemon.rs`, beside `socket_mode_is_0600`):

1. `state_dir_with_group_or_other_bits_is_tightened`: a state directory created `0755` before the daemon starts is `0700` after, with a `warn` line in the log.
2. `state_dir_owned_by_another_user_refuses_start` (privileged): `chown 1` the state directory; the binary exits 7 (`PermissionDenied`; `reef_daemon::exit_code` at `run.rs:117-122` maps only `ConfigError` today and exits 1 for every other start error, so it learns `StartError`'s kinds) naming the directory and uid 1; nothing was created in it.

## Implementation notes

- Ownership is `std::os::unix::fs::MetadataExt::uid()` against `nix::unistd::geteuid()`. Check the `.jj` or `.git` *directory*, not the root: on a shared volume the root may be world-writable while the repository is the user's. `SUDO_UID` is read once at start, only when the euid is 0, and only a decimal uid counts; log the uids registration accepts at `info` so a refused registration is explainable from the log.
- Keep the state-directory check before the lock is taken: `InstanceLock::acquire` creates `daemon.lock`, which must not happen in a directory we then refuse.
- The restore path runs without a daemon; share `ensure_private_dir` through `crate::daemon` as `pub(crate)`.
- `BuildStarted` is additive to `BuildEvent` (`v0` is Phase 1's working schema, R2.01 replaces it); `Client::build_store` yields it like a line.
- For the raw git objects, `git hash-object --literally` takes the tree's bytes on stdin: `b"100644 ..\0" + <20-byte blob id>`; then `git commit-tree <tree> -m x` and `git update-ref refs/heads/hostile <commit>`. `reef_testing::git::commit` cannot write these; add `reef_testing::git::raw_tree(root, entries) -> String` for them.
- Test 14 needs a canary outside every directory Reef touches: use `tempfile::tempdir()` beside the test's state directory, not inside it.
- `gh attestation verify` needs a logged-in `gh`; the quickstart says so in one clause.

## Out of scope

- Sandboxing `reef ws run` or the store build (user namespaces, seccomp, a build container): ADR 0016's alternative and ADR 0022's consequence, filed as a follow-up with the threat model's row numbers, scheduled when a harness asks for it or R3.06's executor sandbox exists to share.
- Daemon-user separation (a `reef` system user owning the daemon and stores, clients identified by peer credentials): the threat model names it as the step that would make the daemon a boundary; it is a Phase 2 or later decision with R2.08.
- Reviewing R2.08's implementation (its brief does, against the requirements section) and anything in RX.02's scope.
- Code signing and notarization (R4.17); verifying provenance in `install.sh`.
- Peer-credential checks on the socket: the mode already limits clients to one uid, and the daemon has no second uid to tell apart.
- Rate limiting, request size limits, or any denial-of-service work on the local socket.

## Risks

- **The hostile-content tests may find a Critical in jj-lib** (a checkout that writes through a symlink, say). The gate says it is fixed here; the fix may be a Reef-side check before `check_out` rather than an upstream patch, and the PR must say which and why. A Reef-side check is a path walk over the target tree's entries, bounded and cheap.
- **S-02 refuses repositories people legitimately share.** A team checkout owned by a service account, a root daemon under systemd serving a user's clone, or a bind-mounted repository in a container whose uid differs (Docker Desktop's file sharing may present the host's uid), stops registering. The hint names the config key, the quickstart's limitations list the rule, `SUDO_UID` covers the `sudo -E` case, and the bench daemon sets the key for its fixture.
- **A root daemon's `.jj` in a user's checkout is root's.** Under `sudo -E`, S-02 lets a root daemon initialize jj beside the user's `.git`; the `.jj` directory and the `info/exclude` line it writes are root-owned, and the user's own `jj` then fails with `EACCES` there. That is the kernel tier used on a shared checkout, which the quickstart's root sentence advises against; recorded in the threat model, not fixed.
- **S-01 refuses a state directory a developer reused across uids.** The hint says what to do (`REEF_STATE_DIR`, or remove it); the memory note's `rm -rf /scratch/root-state` becomes the documented step.
- **S-01's `chmod` surprises a user who widened the directory on purpose.** It logs at `warn` with the old mode; a user who wants a shared state directory has no supported way to get one in Phase 1, and the threat model says so.
- **Attestation needs OIDC permissions the organization may restrict.** S-06 is gated on the dry run and falls back to a follow-up.
- **The findings table drifts.** Every later ticket that touches a trust boundary must add a row; the phase README's ticket format gains one line saying so, and `SECURITY.md` points at the table, so a stale table is visible to a reporter.
