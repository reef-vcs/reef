# R1.13 Watcher-driven snapshots

Phase 1 · Size M · Depends on: R1.05, R0.04 · Unblocks: R1.06 (move takes a snapshot first), R1.14 (same `Watcher` trait), R1.15 (final snapshot on expiry), R1.16 (every snapshot is indexed)

## Context

The design's "Always snapshotted" rule (`docs/design.md`, Workspaces): the daemon snapshots the working copy on every API call and on a short timer, driven by filesystem notifications, so dirty state exists in the store within seconds of being written and deleting a workspace loses nothing. R1.05 delivers explicit snapshots through the `Workspaces.Snapshot` RPC; this ticket makes them automatic and makes them scale to the phase target of 200 workspaces with a write reaching the store within 5 seconds.

ADR 0008 left two things to this ticket: the staleness policy (`Repo::snapshot` currently returns `Stale` whenever the working copy's operation differs from the loaded one, which is stricter than jj-cli in one way and more lenient in another), and the fact that jj-lib's working copy has no notify-based fsmonitor, so a notify watcher can only trigger a scan, not narrow it. The README fixes the scan-then-commit split across the workspace thread and the repository thread, the single notify instance per daemon, and the divergence rule when two workspaces edit one change. This brief implements them and writes ADR 0018.

Numbers to keep in mind (ADR 0008, `docs/benchmarks.md`): a no-op scan of the `large` preset (100,014 tracked files) takes 146 ms and a one-file snapshot 194 ms on an M2 Max; jj's `TreeState::save` is O(tracked files) per snapshot. Two hundred workspaces each scanning once per write is affordable only because scans run in parallel and the repository thread serializes just the transaction.

### What was verified while writing this ticket

jj-lib 0.46.0 and jj-core 0.46.0 sources from crates.io, plus notify 8.2.0, notify-debouncer-full 0.7.0, and notify-types 2.1.0.

- `WorkingCopyFreshness::check_stale(locked_wc: &dyn LockedWorkingCopy, wc_commit: &Commit, repo: &ReadonlyRepo) -> Result<Self, OpStoreError>` (`working_copy.rs`): `Fresh` if the working copy's operation equals the loaded one; otherwise it loads the working copy's operation and takes the closest common ancestor of it and the repo's operation. Ancestor equals the repo's operation → `Updated(Box<Operation>)` (the working copy is newer; reload at its operation). Ancestor equals the working copy's operation → `WorkingCopyStale` unless `locked_wc.old_tree()` has the same `tree_ids_and_labels()` as `wc_commit.tree()`, in which case `Fresh`. Anything else → `SiblingOperation`.
- `MutableRepo::rewrite_commit(&predecessor)` builds through `DetachedCommitBuilder::for_rewrite_from`, which clones the predecessor's store commit (same change id), resets the committer, and on `write` records `predecessor → new` in `parent_mapping`. Nothing checks whether the predecessor is visible, so rewriting a commit that another operation already rewrote (and hid) is allowed and produces a second visible commit with the same change id: a divergent change.
- `MutableRepo::rebase_descendants` ends in `update_wc_commits`, which moves every workspace's working-copy pointer whose commit was rewritten to the first replacement ("We arbitrarily pick a new working-copy commit among the candidates"). This is why a snapshot in workspace A moves workspace B's pointer when both are on the same commit, and why B then sees `WorkingCopyStale`.
- `LockedWorkingCopy::snapshot(&SnapshotOptions) -> (MergedTree, SnapshotStats)`; `SnapshotStats { untracked_paths: BTreeMap<RepoPathBuf, UntrackedReason>, invalid_utf8_paths: BTreeSet<(RepoPathBuf, OsString)> }`. `MergedTree::new(store: Arc<Store>, tree_ids: Merge<TreeId>, labels: ConflictLabels)` rebuilds a tree from `tree_ids_and_labels()`, so only ids need to cross threads.
- `LockedWorkingCopy::check_out(&commit) -> CheckoutStats` applies the diff from the old tree to the commit's tree on disk; `LockedWorkspace::finish(op_id)` saves the state.
- `FsmonitorSettings::Test { changed_files }` exists but `FsmonitorSettings::from_settings` rejects `fsmonitor.backend = "test"` ("Cannot use test fsmonitor in real repository"), and `TreeState`'s fields are private, so there is no public way to hand jj a changed-path set. The notify watcher is a trigger; the scan stays O(tracked files). Watchman (R1.14) is the only narrowing path.
- `GitIgnoreFile::chain_with_file(self: &Arc<Self>, prefix: &RepoPath, file: PathBuf)` and `chain(self: &Arc<Self>, prefix: &RepoPath, ignore_path: &Path, input: &[u8])`. `Repo::base_ignores` in `crates/reef-lib/src/jj/snapshot.rs` already chains git's `core.excludesFile` and `info/exclude`; in-tree `.gitignore` files are read by the working copy itself.
- notify 8.2.0: `Watcher::watch(&mut self, &Path, RecursiveMode)` and `unwatch`; `RecommendedWatcher` is `INotifyWatcher` on Linux and `FsEventWatcher` on macOS. One watcher instance may watch many roots. notify-debouncer-full 0.7.0: `new_debouncer_opt(timeout, tick_rate: Option<Duration>, handler: impl DebounceEventHandler, cache, notify::Config) -> Debouncer<T, C>`, `Debouncer::watch/unwatch`, `DebounceEventHandler::handle_event(DebounceEventResult)` with `DebounceEventResult = Result<Vec<DebouncedEvent>, Vec<notify::Error>>` and `DebouncedEvent { event: notify::Event, time: Instant }` (re-exported from notify-types). 9.0 is a release candidate and is not used.
- notify 8.2.0's `Config::with_follow_symlinks` defaults to `true` (`notify-8.2.0/src/config.rs:122`) and the inotify backend passes it to its `WalkDir`, so the watcher is built with `Config::default().with_follow_symlinks(false)`; store mount symlinks (R1.20) are then not descended. Not verified: whether `Merge<TreeId>` and `ConflictLabels` are `Send` (they are plain data; add a static assertion). Linux inotify limits are at `/proc/sys/fs/inotify/max_user_watches` and `max_user_instances`; defaults vary by distribution and kernel, which is why they are logged rather than assumed.

## Decisions

- **One watcher per daemon.** `reef_daemon::watcher::notify::NotifyWatcher` owns a single `Debouncer<RecommendedWatcher, RecommendedCache>` with `timeout = watcher.debounce` (500 ms) and `tick_rate = None`, watches each active workspace root with `RecursiveMode::Recursive`, and demultiplexes debounced events to workspaces by longest root prefix. Workspace roots are siblings under `repos/<repo-id>/ws/` and never nest (R1.05), so prefix matching is unambiguous. Overlay `.upper` and `.work` siblings are outside every root and are never watched.
- **Events under excluded paths are dropped at the demux**: paths under a `[snapshot] exclude` entry of the repository's `reef.toml` (R1.19) or a `[[store]] mount` (R1.20), and `.reefignore` itself is not consulted here (it is an ignore rule for the scan, not a reason to skip triggering). Build output is the common case: `cargo build` writing ten thousand files into `target/` must not cost ten thousand scans.
- **Per-workspace scheduling, not per-event.** Each active workspace has a scheduler entry `{ dirty_since: Option<Instant>, in_flight: bool, rerun: bool, last_completed: Instant }`. An event marks it dirty; if nothing is in flight a snapshot task starts after `watcher.min_interval` (1 s, new config key) has elapsed since `last_completed`; events during a scan set `rerun`, and one more snapshot follows when it finishes. There is never more than one snapshot in flight per workspace and never a queue deeper than one.
- **Fallback timer.** Every `watcher.fallback_interval` (60 s) the scheduler snapshots every active workspace with no event since its last completion. This covers lost events (notify's queue overflow, FSEvents coalescing, a watcher that failed to attach). A workspace whose `watch` call failed is marked `attention = 'watch-failed'` and lives on the fallback timer alone.
- **Concurrency.** Snapshot tasks run on `spawn_blocking` under a `Semaphore` of `watcher.max_concurrent_scans` permits (default `available_parallelism`). The repository thread does only the transaction. Data crossing threads is ids: `Merge<TreeId>`, `ConflictLabels`, `CommitId`, `WorkspaceNameBuf`, and plain stats.
- **Pipeline in reef-lib.** `Repo::snapshot` is split into `Repo::begin_snapshot` (lock, freshness check, scan; runs on the workspace thread), the free function `commit_snapshot` (transaction; runs on the repository thread), and `PendingSnapshot::finish` (save the working-copy state; workspace thread). The one-process `Repo::snapshot` is reimplemented on top of the three and keeps its tests and benchmarks.
- **Freshness policy** (`begin_snapshot` runs `check_stale` first):
  - `Fresh` → scan, plan a rewrite of the current working-copy commit.
  - `Updated(op)` or `SiblingOperation` → `SnapshotError::RepoBehind`. The daemon reloads the repository at head on the repository thread (which merges divergent operation heads) and retries once; a second `RepoBehind` is an error logged at `warn` and retried on the next trigger. With the repository thread reloading after every transaction it commits, both arms only arise from the `jj` CLI used on the registered root.
  - `WorkingCopyStale` with the scanned tree equal to the working copy's old tree (no unsnapshotted edits) → **adopt**: `locked_wc.check_out(&current_wc_commit)` brings the directory to the rewritten commit, `finish(head op id)`, no operation is written. Nothing of the workspace's own is lost, so following the rewrite is correct.
  - `WorkingCopyStale` with local edits → **diverge**: plan a rewrite of `expected_commit` (the commit the workspace last snapshotted, `workspaces.commit_id`) rather than of the current pointer. The change becomes divergent; the daemon sets `divergent = 1` and `attention = 'divergent'`. The workspace never adopts another agent's tree over its own edits, and nothing blocks.
  - The view has no working-copy commit for this workspace at all (someone ran `jj workspace forget`) → **recover**: a new commit from the scanned tree with `expected_commit`'s parents and a fresh change id (jj forgot the old one, and reusing it would diverge silently), `set_wc_commit`, `attention = 'stale-recovered'`.
- **Post-snapshot hooks**: `Scheduler::on_snapshot(Box<dyn Fn(&SnapshotOutcome) + Send + Sync>)` runs after `finish` and the row update, in registration order, on the tokio runtime. R1.16 registers the `snapshots` index insert and R1.20 the lockfile hash check; this ticket registers nothing.
- **A per-minute summary line** at `info`: `watcher summary: scans=N queued_max=M wait_max_ms=K` (scans completed in the last minute, the longest queue observed, the longest wait for a permit in milliseconds), emitted only while at least one workspace is watched. R1.23 parses it from `logs/daemon.log`.
- **Explicit snapshots** go through the same scheduler (`Snapshot` RPC awaits the task's result), so an explicit call during an in-flight scan waits for it and then runs once more. `Release`, `Move`, and `Inspect` with `snapshot_first` use it. `Heartbeat` never snapshots.
- **Operation descriptions** are the README's: `reef: snapshot workspace <ws-id>` for watcher and explicit, `reef: final snapshot of workspace <ws-id> (<reason>)` for R1.15, `reef: move workspace <ws-id> to <change>` for R1.06. `is_snapshot` is set on all of them.
- **Ignores** per snapshot: `Repo::base_ignores` plus, in order, `<root>/.reefignore` via `chain_with_file(RepoPath::root(), ..)`, the `[snapshot] exclude` entries rendered as gitignore lines via `chain(RepoPath::root(), Path::new("reef.toml"), bytes)`, and store mount points as `/<mount>` lines. The combined `Arc<GitIgnoreFile>` is rebuilt when `reef.toml` or `.reefignore` changes (both are inside the watched root, so their events are observed).
- **Snapshot settings** come from the daemon's `UserSettings` (R1.04): `max_new_file_size` from `[snapshot] max_new_file_size`; `start_tracking_matcher = EverythingMatcher`, `force_tracking_matcher = NothingMatcher` as in R0.04. Files left untracked are reported once per path per workspace at `warn` (not on every snapshot).
- **Linux limits** are read at daemon start from `/proc/sys/fs/inotify/max_user_watches` and `max_user_instances` and logged at `info`; a `watch` failure with `ENOSPC` is logged at `error` with the current values and the sysctl to raise.

## Deliverables

### `crates/reef-lib/src/jj/snapshot.rs`

```rust
/// Why a snapshot could not be planned against the loaded repository.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Behind { WorkingCopyNewer, SiblingOperation }

#[non_exhaustive]
pub enum SnapshotError {
    /// The repository must be reloaded at head and the snapshot retried.
    RepoBehind { kind: Behind, wc_op: OperationIdHex, repo_op: OperationIdHex },
    /// `expected_commit` is not in the store; nothing can be rewritten.
    ExpectedCommitMissing(CommitIdHex),
    /* existing variants */
}

/// What the scan found and how to record it. Plain data; crosses threads.
#[derive(Clone, Debug)]
pub struct SnapshotPlan {
    pub workspace_name: String,
    pub rewrite_of: CommitIdHex,        // the commit to rewrite (current pointer, or expected_commit when diverging)
    pub tree_ids: Merge<TreeId>, pub labels: ConflictLabels,
    pub divergent: bool,                // rewrite_of is no longer the view's pointer
    pub recover: Option<Vec<CommitIdHex>>, // Some(parents): create a new commit instead of rewriting
}

/// The locked working copy after a scan. Lives on the workspace thread.
pub struct PendingSnapshot<'a> { /* LockedWorkspace<'a>, plan, outcome fields */ }

impl Repo {
    /// Locks the working copy, checks freshness, scans. `expected_commit` is
    /// the commit the caller last snapshotted (None: trust the view).
    pub async fn begin_snapshot(&mut self, expected_commit: Option<&CommitIdHex>)
        -> Result<PendingSnapshot<'_>, SnapshotError>;
}

impl PendingSnapshot<'_> {
    pub fn changed(&self) -> bool;                       // scanned tree differs from rewrite_of's tree
    pub fn adopted(&self) -> bool;                       // the adopt branch ran: directory updated, no op needed
    pub fn plan(&self) -> &SnapshotPlan;
    pub fn untracked(&self) -> &[(String, UntrackedReasonKind)];
    pub fn scan_time(&self) -> Duration;
    /// Saves the working-copy state at `op_id`: the new operation after
    /// `commit_snapshot`, or the current head when `changed()` is false.
    pub async fn finish(self, op_id: &OperationIdHex) -> Result<(), WorkingCopyStateError>;
}

pub struct SnapshotCommit { pub repo: Arc<ReadonlyRepo>, pub op_id: OperationIdHex, pub commit_id: CommitIdHex, pub write: Duration, pub commit: Duration }

/// The transaction half. Runs wherever the repository head lives.
pub async fn commit_snapshot(head: &Arc<ReadonlyRepo>, settings: &UserSettings, plan: &SnapshotPlan, description: &str)
    -> Result<SnapshotCommit, SnapshotError>;
```

`commit_snapshot`: `start_transaction`, `set_is_snapshot(true)`, `set_workspace_name`, then either `rewrite_commit(&store.get_commit(rewrite_of)).set_tree(MergedTree::new(store, tree_ids, labels)).write()` or, for `recover`, `new_commit(parents, tree).write()`; `set_wc_commit(name, new id)`; `rebase_descendants`; `commit(description)`. `Repo::snapshot(description)` becomes `begin_snapshot(None)` → if `changed()` `commit_snapshot(&self.repo, ..)` then `self.repo = commit.repo` → `finish`. `snapshot_unlogged` keeps its signature for `undo.rs`. Existing `SnapshotOutcome` and `SnapshotTiming` are unchanged.

`Repo` gains `pub fn head(&self) -> &Arc<ReadonlyRepo>` and `pub fn set_head(&mut self, repo: Arc<ReadonlyRepo>)` so the daemon can point a workspace's `Repo` at the repository thread's current head before `begin_snapshot` (if R1.05 already added equivalents, use those).

Static assertions in `tests/jj_spike.rs`: `SnapshotPlan: Send + 'static`.

### `docs/adr/0018-snapshot-staleness-and-divergence.md`

Status `accepted`. Context: ADR 0008's open question, jj-cli's behavior (`Updated` → reload at the working copy's operation; `WorkingCopyStale` → refuse and require `jj workspace update-stale`, which creates a recovery commit via `create_and_check_out_recovery_commit`), the daemon's single writer per repository, and what two workspaces on one change do to each other through `update_wc_commits`. Decision: the four-arm policy above, verbatim. Consequences: divergent changes are a normal state in Phase 1 and are visible; R2.03 provides the resolution operations; the `jj` CLI shows `??` for them. Alternatives: jj's recovery commit (rejected: it moves the workspace onto another agent's tree and makes its edits a child commit it did not ask for); refusing to snapshot a stale workspace (rejected: an agent's edits would be unprotected until a human intervenes); child-commit semantics for every workspace (rejected for Phase 1: "workspace on change C" would mean "on a child of C", which the CLI and the design do not say; recorded as the fallback if divergence proves unmanageable).

## Implementation notes

- Keep `LockedWorkspace` on the workspace thread for the whole pipeline. It borrows the `Workspace` mutably, so the `WorkspaceHandle` mutex guard is held from `begin_snapshot` to `finish`; the repository thread never sees it. The await on the repository thread's reply happens inside `pollster::block_on` on the blocking thread, which is fine because nothing else needs that thread.
- The adopt branch needs the current working-copy commit from the view; `begin_snapshot` reads it from `self.repo` (set to the head just before). `check_out` returns `CheckoutStats`; log `updated_files` as `files_count`.
- Debounced events can arrive for a workspace being released (`unwatch` races with the debouncer thread); the scheduler ignores events for untracked ids.
- FSEvents on macOS reports directory-level events and can drop under load; the fallback timer is not optional there. notify's `Config::default()` is used; `with_compare_contents` stays off.
- `ConflictLabels` and `Merge<TreeId>` cross the channel inside `SnapshotPlan`; if the static assertion fails, send `Vec<Vec<u8>>` of tree id bytes and rebuild.
- The scheduler's per-workspace entries are a `Mutex<HashMap<WorkspaceId, Entry>>`; tasks hold the lock only to flip flags.
- Do not snapshot a workspace whose row is `releasing`: the release flow owns its final snapshot (R1.05, R1.15).

## Out of scope

- Narrowing the scan to changed paths (R1.14 via Watchman; an upstream jj-lib hook otherwise, ADR 0008).
- Indexing snapshots in SQLite (R1.16; this ticket leaves the hook).
- Final snapshots on lease expiry and shutdown (R1.15, R1.03) beyond the `SnapshotKind` variants they use.
- Resolving divergent changes (R2.03).
- Presence or any event stream to clients (R2.10).

## Risks

- `update_wc_commits` picking "the first replacement" means the divergence rule depends on `rewrite_commit` of a hidden commit staying allowed; a jj-lib bump that rejects it breaks test 7, which is the point of the test.
- FSEvents latency on macOS is typically under a second but is not bounded; the 5 s target is measured in R1.23 and the fallback interval can be lowered there.
- A workspace with hundreds of thousands of directories costs that many inotify watches on Linux; 200 such workspaces exceed common `max_user_watches` defaults. R1.14 exists for this; R1.13 only logs the limits.
- Holding the `WorkspaceHandle` lock across the repository-thread round trip serializes explicit RPCs on that workspace behind its scan; acceptable at 200 ms scans, revisit if `Inspect` latency matters in R2.
