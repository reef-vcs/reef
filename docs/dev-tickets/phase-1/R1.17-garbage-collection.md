# R1.17 Garbage collection

Phase 1 · Size M · Depends on: R1.15 · Unblocks: R1.18 (backup takes the maintenance lock GC introduces), R1.22 (`reef ws gc`)

## Context

The design (`docs/design.md`, Workspaces, "Inventory owned by the daemon"): garbage collection reclaims snapshots unreferenced by any named change and older than the undo window, and reports what it reclaimed. In Phase 1 every watcher snapshot rewrites a working-copy commit, so the previous version becomes a hidden commit reachable only from older operations; at one snapshot per write per workspace, the operation log and the git object store grow without bound until something prunes them. The base cache (R1.02) and the state directories of released workspaces (R1.15) are the other two growing sets. The durability section adds the rule GC must respect from R1.18 onward: never delete anything younger than the backup retention window.

### What was verified while writing this ticket

jj-lib 0.46.0 and jj-core 0.46.0 sources.

- `OpStore::gc(&self, head_ids: &[OperationId], keep_newer: SystemTime) -> OpStoreResult<()>` (jj-core `op_store.rs`, async trait). `SimpleOpStore`'s implementation walks the operations reachable from `head_ids`, then deletes every file in `op_store/operations` and `op_store/views` that is unreachable and whose mtime is not newer than `keep_newer`. Reachability ignores `keep_newer`; the timestamp only protects files another process may have just written.
- `GitBackend::gc(&self, index: &dyn Index, keep_newer: SystemTime) -> BackendResult<()>` (`git_backend.rs`): recreates jj's no-gc refs for every head the index reports (`index.all_heads_for_gc()`, excluding the root commit), prunes the extra-metadata table, then runs the external `git` binary (`git.executable-path`, default `"git"` in `config/misc.toml`) as `git --git-dir=. gc --prune=@<keep_newer unix seconds> +0000` in the git directory, and refreshes the packed-refs cache. Reached through `store.backend_impl::<GitBackend>()`.
- The default index keeps every commit it has ever indexed, hidden ones included, and `all_heads_for_gc` returns heads of that whole graph, so running the backend GC against the current index keeps every old snapshot alive. `DefaultIndexStore::reinit()` removes `index/op_links` (and legacy `index/operations`) so the index is rebuilt from the reachable operations on the next load; `IndexStore` is `Any + Send + Sync`, so the store is reached by downcasting `repo.index_store()`. The order is therefore: operation store GC, reinit, reload at head (rebuilds the index from the surviving operations), backend GC with the rebuilt index. jj-cli's `util gc` ordering was not verified (its source is not fetched); the order above is derived from the semantics.
- `git gc` is the only piece that needs an external binary; without `git` on `PATH`, `GitBackend::gc` fails with `GitGcError::GcCommand`.
- SQLite schema: `base_cache`, `workspaces.state`, `leases`, `reclaims`, `snapshots` (R1.16), `stores` (R1.20) as in the README.

## Decisions

- **GC is explicit.** `Maintenance.Gc` and `reef ws gc`; nothing runs it on a timer in Phase 1. `GcRequest { repo (optional: all), dry_run }`.
- **Undo window.** `keep_newer = now - gc.undo_window` (7 d). Operations newer than that are never pruned even if unreachable, and neither are git objects, so `reef undo` (R2.03) always has a week. `gc.undo_window = "0s"` is allowed for tests and means "prune everything unreachable now".
- **Backup retention floor.** `keep_newer = min(now - undo_window, last_backup_at - 0)`: nothing newer than the most recent backup's timestamp (`meta.last_backup_at`, written by R1.18) is pruned unless `backup.retention` has elapsed since that backup. Concretely `keep_newer = now - max(undo_window, retention if last_backup_at + retention > now else 0)`. Until R1.18 lands `last_backup_at` is absent and only the undo window applies.
- **Maintenance lock.** `reef_daemon::maintenance::Lock`, a `tokio::sync::Mutex<()>` on the daemon; GC, backup (R1.18), and quiesce hold it. `Gc` while held returns `Unavailable` ("maintenance in progress") rather than queueing.
- **Four steps per repository**, in order, each reporting bytes before and after (allocated blocks via `walkdir`, as R1.02's `DiskUsage`):
  1. **jj**: on the repository thread, `load_at_head` (merges heads), `op_store().gc(&[head op id], keep_newer)`, `DefaultIndexStore::reinit()`, `load_at_head` again (rebuilds the index; its cost is O(reachable commits) and is logged), `GitBackend::gc(index, keep_newer)`. Measured over `.jj/repo/op_store` and the git objects directory (`.jj/repo/store/git` or, for colocated repos, `<root>/.git/objects`).
  2. **Base cache**: entries with no workspace in state `active` or `releasing` referencing `base_tree_id`, oldest `last_used_at` first, removed until `COUNT(*) <= base_cache.max_entries`; an entry referenced by nothing and older than `undo_window` is removed regardless of the cap. Removal is `rename` to `<tree-id>.gc` then `remove_dir_all`, so a crash mid-delete leaves nothing the daemon would mistake for an entry (R1.02 ignores `*.gc` and `*.tmp` and removes them at start).
  3. **Workspace rows**: `released` and `reclaimed` workspaces whose latest `reclaims.at` is older than `undo_window`: delete their `wc/<id>` state dir if it still exists, their `leases` rows, and the `workspaces` row; `reclaims` rows are kept (audit), `snapshots` rows are left to R1.16's reindex, which runs after GC on each repository.
  4. **Stores** (R1.20): sealed stores no registered repository's `reef.toml` names by `(name, lockfile hash)`, and unsealed stores older than one day.
- **Report.** `GcReport { repo_id, keep_newer, jj_bytes_before, jj_bytes_after, reindex_ms, base_entries_removed, base_bytes_freed, workspace_rows_removed, wc_bytes_freed, stores_removed, store_bytes_freed, elapsed_ms, dry_run }`; `GcResponse { repeated GcReport reports }`. `reef ws gc` prints one line per repository and a total; `--dry-run` reports what would go.
- **Safety.** GC never touches a workspace directory, a base entry an active workspace references (an overlay lower directory in use), the user's `default` workspace, or anything in a quiesced repository. If `git` is missing, step 1 stops after the operation store GC with `GcReport.jj_error` set and the other steps still run; the CLI exit code is 8 (`Io`) with the report printed.
- **Config**: `[gc] undo_window = "7d"`, `git_executable = "git"` (mapped to jj's `git.executable-path` in R1.04's settings builder), `reindex_limit` (R1.16).

## Implementation notes

- Reinit then `load_at_head` on the repository thread replaces its `Arc<ReadonlyRepo>`; every workspace's `Repo` picks the new head up on its next `set_head` (R1.13). Index rebuild time on a repository with many operations is the dominant cost; log it as `reindex_ms` and record a number for the `medium` fixture after 1,000 snapshots in the PR.
- `git gc` holds its own locks; running it while a snapshot transaction writes objects is safe (jj writes objects before operations and `keep_newer` protects fresh ones), but the maintenance lock plus the repository thread's serialization mean nothing else runs anyway.
- Bytes before and after are measured on the same directories; for colocated repositories the git objects live under `<root>/.git/objects`.
- Step 3's cutoff uses `MAX(reclaims.at)` per workspace, joined on `workspace_id`.
- The `*.gc` rename trick needs the base cache to list entries by directory name; `BaseCache::list` already filters to 40-hex names (R1.02).

## Out of scope

- Scheduled or automatic GC and disk-pressure triggers (RX, after R1.23's numbers).
- Garbage collection of the user's `default` workspace's own hidden commits beyond what jj's GC does for the whole repository (it is the same store; they are included).
- The backup retention floor's `last_backup_at` writer (R1.18) and store cleanup's inputs (R1.20); both steps are implemented here against the schema and exercised when those land.
- Artifact or evidence retention (R3.02).

## Risks

- `DefaultIndexStore::reinit` plus reload rebuilds the index from every reachable operation's view; on a repository with hundreds of thousands of operations this is seconds to minutes with the repository thread paused. The first GC after a long time is the slow one; report the time so R1.23 can decide whether GC needs to run more often.
- Depending on an external `git` for object GC is jj's design; a container image without `git` gets operation-store GC only and a clear error.
- `git gc --prune=<date>` prunes by object mtime; cloning or copying a repository with `cp` resets mtimes and can make old objects look new (never pruned) or new objects look old (pruned if unreachable). R1.18's restore copies with mtimes preserved for this reason.
