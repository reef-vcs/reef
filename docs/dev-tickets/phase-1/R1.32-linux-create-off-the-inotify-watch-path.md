# R1.32 Linux workspace creation off the inotify watch path

Phase 1 · Size M · Depends on: R1.12 (the `create_api` benchmark), R1.23 (`watched`, `behind`, the load test), R1.29 (`TrackReason`, `Watcher::watch(.., defer)`, `watch_state`, `CreateTimings`), R1.30 (`WatchEvent::everything`, narrowed scans) · Unblocks: the overlayfs half of Phase 1's first exit criterion as the runners measure it; the 0.1.0 tag

## Context

Phase 1's first exit criterion is twenty workspaces on the 100k-file synthetic repo, each created in under one second on APFS and overlayfs. `docs/benchmarks.md` names the runners' `large` run as the criterion's own measurement for overlayfs. The first one, `bench.yml` dispatched with `preset=large` on main at `4c966c7` (run 40143472665, job `bench ubuntu-24.04`: a 4-vCPU x64 runner, kernel overlayfs as root through `REEF_BENCH_PRIVILEGED=1`, 2026-10-24), misses:

```text
target (create_api/large/overlayfs/20): 20 workspaces under 1 s each: MISS (1.006 s)
breakdown (create_api/large/overlayfs/1):  p50 per create 965.2 ms:  resolve 0, base 0, materialize 0, mount 0, jj 3, seed 1, insert 0, watch 945 ms; watcher notify
breakdown (create_api/large/overlayfs/20): p50 per create 1005.6 ms: resolve 0, base 0, materialize 0, mount 0, jj 4, seed 2, insert 0, watch 985 ms; watcher notify
```

The backend alone (`create/large/overlayfs/20`) is 0.000 s and the mount under a millisecond. 98% of the create is `watch`: inotify adding one watch for each of the `large` fixture's 8,336 directories, inside `Create`, on the blocking pool, with the create waiting for it (R1.29). The same run's `create_api/large/fuse-overlayfs/20` is 2,408 ms with `watch` 2,375 ms; fuse-overlayfs is not named by the criterion, but the same cost dominates it. On the M2 Max's Docker VM (R1.29, "Linux, unchanged") the same create was 430 ms with `watch` 405 ms, so the runner is about 2.4× slower at this and nothing else moved. R1.29 left inotify's attach out of scope ("one watch per directory is inotify's model"), and APFS passes (notify 962 to 969 ms, Watchman 951 to 960 ms on clean runs), so macOS is out of scope here except where shared code changes.

A rerun might pass by six milliseconds and the next scheduled run miss again. The fix is the one R1.29 applied to macOS: take the watcher's work off the create path. `Create` returns once the workspace's row, lease and jj working copy exist; on Linux the notify watch attaches right after, one workspace at a time, and when it comes up the scheduler takes one full snapshot so nothing written in between is lost.

## Decisions

- **On Linux, a created workspace's notify watch attaches after `Create` returns, in the background, one workspace at a time.** `NotifyWatcher` gains an attach queue and one worker thread (`reef-notify-attach`). `watch(.., defer = true)` on Linux pushes the root onto the queue and returns `Pending`; the worker pops roots in order and attaches each under the watcher's mutex exactly as `watch` does today (Demux first, then `Debouncer::watch`). `watch(.., defer = false)` (daemon start, an aborted release, a move's rewatch) still attaches inline and returns `Attached`, after removing the workspace from the queue if it was there. macOS attaches inline whatever `defer` says: its attach is one `FSEvents` stream restart (9 ms, R1.29), and a post-attach full scan of 100,000 files beside the next workspace's APFS clone is the contention R1.29 measured with Watchman. The queue and worker are compiled on both platforms (so the Mac builds and unit-tests them); only the decision to use them is `cfg(target_os = "linux")`.
- **Nothing is lost: the watch coming up is an `everything` event.** When an attach succeeds the worker reports the workspace up through the `HealthHook`, then sends `WatchEvent { workspace, paths: [], everything: true, at: <when the watch was queued> }` on the events channel with `blocking_send` (its own thread; never dropped). The scheduler already turns that into one full scan after `min_interval`, with events arriving before the scan joining it and events during it going to the next (ADR 0026). The mark is sent strictly after `Debouncer::watch` returns: a scan that ran before the watch existed cannot vouch for a write made after it. `at` is the queue time so the first snapshot's `latency_ms` shows the backlog. This is what a Watchman subscription's first result does today; the two watchers now make the same promise: a write made after `Create` returns is in the watcher's first snapshot, whether the watch was up at the time or not. Until the watch is up the entry is not `watched`, so the short fallback (60 s) still applies as the backstop, narrowing is off, and any scan is full.
- **`Watcher::watch` says which it did.** It returns `Result<Attach, WatchError>` with `enum Attach { Attached, Pending }`; `reports_health()` goes away (Watchman returns `Pending` always, notify `Pending` when it queued, `NoWatcher` an error). `Scheduler::track` sets `watched` and clears `watch-failed` on `Attached` and does nothing on `Pending`, which is today's `reports_health` branch. `Watcher::waiting(ws) -> bool` becomes `pending(ws) -> Option<PendingWatch>` with `enum PendingWatch { Waiting, Attaching }`: Watchman answers `Waiting` during its quiet wait exactly as today, notify `Attaching` while the workspace is queued or in flight. `Scheduler::watch_waiting` becomes `watch_pending`, and `watch_state` is `""`, `"waiting"` or `"attaching"` in `Create`'s response, `List`, `Inspect` and `Move`; the CLI prints `notify (attaching)`. `attention` stays clear.
- **A failed attach is what a failed watch is today.** The worker logs the existing warning (`cannot watch the workspace; it is snapshotted on the fallback timer only`, with the inotify limit hint and counts when `is_limit`) and reports the workspace down through the hook, which marks `attention = 'watch-failed'`; no event is sent. The entry stays `watched = false` and lives on the 60 s fallback until a rewatch or a later start attaches it, as now.
- **Release, reclaim, move and a pending attach.** `unwatch` takes the watcher's mutex, which an attach in flight holds, so it waits for that one attach (at most one root, about a second for `large` on the runner, 2.4 s on fuse-overlayfs) and then removes the OS watches; a workspace still queued is removed from the queue and the Demux under the same mutex and nothing else happens. The worker pops and attaches under that mutex too, so a workspace cannot be dequeued by one side and attached by the other. A release's untrack therefore cancels a queued attach outright and waits for an in-flight one. A move's rewatch attaches inline (`defer = false`), dropping the queued entry first; `Rewatched` already marks the entry `everything` and `behind`, so a full scan follows as before. A health report or `everything` event that lands after an untrack is ignored by the scheduler as today (both check the entry exists and, for marks, that the row is active). On daemon shutdown the worker is stopped and joined after the attach in flight (if any) finishes; a never-attached workspace that was written to is covered on the next start by `Loaded`'s `behind` and the 60 s fallback, the same as a watch that failed.
- **Attaches stay serial, and the backlog is measured rather than hidden.** With the attach gone, a `large` create on the runner is the daemon's other steps (`jj` 4 ms, `seed` 2 ms, the rest 0) plus the RPC: tens of milliseconds, expected. Twenty creates then finish in about a second while their attaches take about 20 s in a row (985 ms each), so workspace k's watch comes up about k seconds after its create, and a write made right after that create is snapshotted at about k s plus one full scan. Nothing waits 60 s in a burst of twenty; in a burst of more than about 60 `large` workspaces the fallback timer snapshots the tail before its watch is up, which is correct and costs full scans. For the load criterion (200 `medium` workspaces, 1,000 directories each) the backlog is about 200 attaches of tens of milliseconds, under 20 s on the runner and shorter than the creates themselves today. The criterion is at steady state with active watchers, so the load test waits for the backlog to drain before the steady state starts and records how long that took; the gate is unchanged. The other serialization cost, other workspaces' events waiting in the kernel queue for the length of one attach, is unchanged from today and out of scope (see Risks).
- **The bench stops flattering it.** After its `n` creates, `create_api` waits until none of them is `attaching` (polling `List` every 100 ms, bounded at 10 minutes) before releasing them, so attaches of earlier workspaces run beside later creates as they would for a client, and the post-attach full scans too. The wait is untimed; the row and `bench-ws.json` gain `attach_drain_ms` (from the last create's return to the last attach, p50 over iterations), printed at the end of the `breakdown` line. On macOS it is 0. Without the wait each iteration's releases would cancel the queue and the number would measure creates with no inotify work at all, R1.29's Watchman caveat again.
- **One kill switch, no tuning knob.** `[watcher] notify_attach_background = true` (new key; `false` attaches inside `Create` as before this ticket; read only on Linux; in `reef config show`, the key list and the README's config schema row). There is no quiet-window deferral for notify: on Linux the create's remaining steps are milliseconds and have nothing to protect from the attach.
- **ADR 0028, "Watch attachment off the create path"**, records that `Create` returns with the workspace's row, lease and working copy made and its watch attached or pending (Watchman since R1.29, notify on Linux now), the invariant that a watch coming up is a full scan so no write between the two is lost, why notify stays inline on macOS, that attaches are serial on one inotify instance and what that costs a burst, the kill switch, and the alternatives (a second inotify instance per attach, Watchman for every workspace, fanotify, a quiet-window deferral, doing nothing and accepting a 6 ms miss). It cross-references ADR 0023's R1.29 amendment and ADR 0026's list of what sets `everything` without editing them (ADRs are frozen after acceptance; RX.01 did the same for 0019 and 0022). The README's ADR table allocates 0028 here.

### `crates/reef-daemon/src/watcher/notify.rs`

- `NotifyWatcher { inner: Mutex<Inner { debouncer, queue: VecDeque<Queued>, in_flight: Option<WorkspaceId> }>, pending: Mutex<HashSet<WorkspaceId>>, demux, cv: Condvar, worker: Option<JoinHandle>, stop: AtomicBool, events: mpsc::Sender<WatchEvent>, health: HealthHook, background: bool, gate: Arc<AttachGate> }`. `Queued { workspace, root, skip, queued_at: Instant }`. `pending` is a separate small lock so `Inspect` never waits behind an attach.
- `watch(.., defer)`: `background && defer` → lock `inner`, replace any queued entry for the workspace, push, insert into `pending`, notify the condvar, return `Ok(Pending)`; otherwise lock `inner`, drop any queued entry, attach inline as today, return `Ok(Attached)`.
- The worker loop: lock `inner`; while the queue is empty (or the gate is held) wait on the condvar; pop, set `in_flight`, insert the Demux root, call `debouncer.watch`, clear `in_flight`, remove from `pending`, unlock. Then, outside the lock: on `Ok`, `tracing::info!(workspace_id, path, queued_ms, attach_ms, queue_len, "workspace watch attached")`, `health(ws, true)`, `events.blocking_send(everything event)` (a closed channel is shutdown; ignore it); on `Err`, remove the Demux root, the existing warning with `log_limit_hit` when `is_limit`, `health(ws, false)`.
- `unwatch`: lock `inner` (waits for an attach in flight); remove from the queue and `pending` if queued and return; else as today.
- `pending(ws)`: `Attaching` if in `pending`.
- `Drop`: set `stop`, notify, join the worker.
- `AttachGate` (`cfg(any(test, feature = "testing"))` methods on an always-present struct in `watcher/mod.rs`): `hold() -> AttachHold` (the worker does not pop while a hold is open) and `queued() -> usize`. ## Implementation notes

- Keep the attach itself exactly today's code path (`Demux::insert`, then `Debouncer::watch`, remove on error) and move it into one private `fn attach(&mut Inner, ..)` that both the worker and the inline path call, so the two cannot drift.
- The worker holds `inner` across `Debouncer::watch` on purpose: that is what makes `unwatch` and a rewatch wait for an attach in flight instead of racing it. Nothing else should take `inner` for long. `pending` and `demux` have their own locks; take `inner` before either, never after.
- `blocking_send` on the events channel must not be called while holding `inner` (the scheduler's event loop never takes `inner`, but a full channel would hold the attach lock for the scheduler's backlog). Send after unlocking.
- `at` on the attach event is the `queued_at` instant, so `latency_ms` on that snapshot's `watcher snapshot taken` line includes the queue wait; the load test's `attach.queued_ms` is from the attach line, not that one.
- Measure on the runner, not the Mac. `gh workflow run bench.yml --ref <branch> -f preset=large` and read `target (create_api/large/overlayfs/20)` and the two `breakdown` lines from the artifact's `bench-results-privileged.txt` output (the job log; the artifact holds `bench-ws.json`). The run takes about three hours; dispatch it once the code is final and once more if the first is noisy. The container gives the shape in minutes (`-- 'create_api/large' --measurement-time 20` as root with `REEF_BENCH_PRIVILEGED=1`).
- The end of a burst, by hand in the container as R1.29 did on the Mac: a release daemon, `large` registered, twenty `reef ws create` in a row, then `reef ws run` in the last one writing a file at once; from the daemon log, the twenty `workspace watch attached` lines (queued and attach times, the drain), the twenty first `watcher snapshot taken` lines (`scan_ms` of a full scan through overlayfs on the runner-like VM), and the write's latency. Record it in `docs/benchmarks.md`.
- `create_api` on the runner's unprivileged pass is fuse-overlayfs; its `watch` was 2,375 ms, so its drain for twenty is about 48 s per iteration (untimed). The bench's 10-minute bound on the wait is for that; do not lower it.
- The Linux-only paths are not compiled on the Mac. Before pushing, in the privileged container: `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets`, clippy with and without `--all-features`, `cargo doc` with `-D warnings`, and the tests above as root and as `dev`. The trait change compiles on both platforms, so `just ci` on the Mac still catches most of it.

## Out of scope

- Other workspaces' inotify events waiting in the kernel queue while a root is being added, and the queue overflowing under a heavy writer (a build in a neighbouring workspace) during an attach, which makes every notify workspace `everything`. Both are today's behaviour; a fix needs the attach on a second inotify instance or `fanotify`, and is a Phase 2 Scale item.
- Daemon start with many `large` workspaces, which attaches them inline one after another (`Loaded`); a background attach there changes when the daemon answers `Status`, which R1.03 defined.
- A quiet-window deferral for notify (Watchman's `watchman_attach_quiet`), the Watchman threshold, and `fuse-overlayfs`'s own cost per lookup.
- The APFS clone and macOS's margin (R1.29's risk stands: 962 ms on the M2 Max).
- A latency gate in CI (RX.06).

## Risks

- **The first snapshot of a workspace created in a burst is later than today.** Workspace k of a burst waits about k attaches (a second each for `large` on the runner, 2.4 s on fuse-overlayfs) before its watch is up, then one full scan; today it waited inside `Create` instead, so the writer could not start earlier. Nothing is lost either way, and `watch_state` says what is happening; but a client that creates, writes, and reads the store at once sees its write later than before. The load test's drain figure and `latency_ms` on the attach-time snapshot make the cost visible per run.
- **Twenty full scans at the end of a burst.** Each attach is followed by a full scan of the new workspace (a stat walk against the seeded `tree_state`: 167 ms idle on APFS for `large`, R1.14; through overlayfs on the runner not yet measured). With `n` creates in a burst the scan pool sees `n` of them over the drain, beside later creates' millisecond steps. On overlayfs this cannot cost a create much; the bench's wait makes sure it is measured.
- **An attach in flight holds the watcher's mutex for its length.** A `Release` or `Move` of any notify workspace, and a non-deferred `watch`, waits for it: up to one attach, as every `watch` did inside `Create` before. If a `Release` RPC's time matters in the fleet, the wait is at most one root.
- **A kill switch is a second code path.** `notify_attach_background = false` is the pre-R1.32 behaviour and is covered by `write_right_after_create_is_snapshotted` with the flag off only if a test sets it; test 8's `watch_ms` assertion runs with the default. Keep the inline path the same function as the worker's so the switch cannot rot.
