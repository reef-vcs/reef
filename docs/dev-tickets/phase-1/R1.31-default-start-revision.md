# R1.31 A default start revision beyond `main`

Phase 1 · Size S · Depends on: R1.05 (create), R1.20 (store builds without `--rev`), R1.25 (git checkouts registered on first use) · Unblocks: the quickstart's "no setup" promise for repositories whose default branch is not `main`

## Context

R1.24's walkthrough ran the quickstart on a fresh clone of `pillarjs/path-to-regexp`, whose default branch is `master`. Every workspace started on top of the root checkout's working-copy change instead of on `master`:

- **The agent inherits the human's uncommitted edits.** After `reef init` wrote `AGENTS.md` and `CLAUDE.md` into the root checkout, the next jj command there snapshotted them into the root's working-copy commit, and every agent workspace built on that commit carried them.
- **The human's jj commands rewrite the agents' changes.** Any `jj` command in the root checkout snapshots its working copy. Because the agents' changes descend from that commit, jj rebases them ("Rebased 5 descendant commits onto updated working copy"). Each workspace then finds its working copy stale on its next snapshot (ADR 0018 handles that, but nothing should have moved).
- **Store builds without `--rev` build the wrong lockfile.** `reef store build <name>` without `--rev` uses the same default, so it builds from whatever the root checkout holds.

A plain git user does not expect any of this. `master`, `trunk` and `develop` are common default branches, and the quickstart (R1.24) has to tell such users to pass `--new-on <branch>` on every create until this ticket lands.

### What was verified while writing this ticket

- `default_start` (`crates/reef-daemon/src/workspace/create.rs:596-607`) resolves `main` and accepts it only as a bookmark; otherwise it takes the `default` workspace's working-copy commit. Its callers are create without a start (`create.rs:541`), store builds without `--rev` (`workspace/stores.rs:464`), and GC's store step, which keeps stores the default start names (`workspace/stores.rs:431`).
- The default is described in the CLI help (`crates/reef-vcs/src/cli/ws.rs:99`, `cli/store.rs:48`), the API (`proto/reef/daemon/v0/workspaces.proto:52`, `:249`; `stores.proto:33`), and ADR 0022 decision 8.
- jj-lib 0.46 has no `trunk()`. jj's CLI defines `trunk()` as a revset alias in its configuration, and `jj git clone` and `jj git init` write the remote's default branch into the repository's config (in Reef's own repository, `revset-aliases."trunk()" = "main@origin"`). Reef reads neither.
- R1.25 imports git refs before resolving a revision in a colocated repository (`create.rs:585-592`), so `master` and `master@origin` are visible as bookmarks by then.

## Decisions

- **`default_start` tries, in order:**
  1. the local bookmark `main`;
  2. the bookmark the colocated git remote `origin` names as its HEAD (`refs/remotes/origin/HEAD`, which `git clone` sets), as a local bookmark or `<name>@origin`. It comes before `master` and `trunk` so a stale local `master` beside a remote whose default is now `main` does not win;
  3. the local bookmark `master`, then `trunk`;
  4. the remote-tracking bookmarks `main@origin`, `master@origin`, `trunk@origin`;
  5. the `default` workspace's working-copy commit, as today, logged at `info` on each create with the bookmarks it looked for (no per-repository state to remember a warning).

  The first match wins. A conflicted bookmark is skipped with a warning, not an error.
- **The answer is reported.** `CreateResponse` and `reef ws create` already name the change; `reef ws create` and `reef ws run` print one stderr line when step 5 was used: `reef: no main, master or trunk bookmark; starting on the root checkout's change (pass --new-on <branch>)`. JSON output gains `"start": "<bookmark or 'root checkout'>"`.
- **No configuration key.** A repository with an unusual default branch has `origin/HEAD` (step 2), or passes `--new-on`. A per-repository setting can come later if that proves insufficient.

## Deliverables

- `crates/reef-daemon/src/workspace/create.rs`: `default_start` with the order above, returning which rule matched; the log line and the reported start.
- `crates/reef-lib/src/jj/`: reading the colocated git's `refs/remotes/origin/HEAD` symbolic ref (through jj-lib's git backend or `gix`, whichever `reef_lib::jj` already uses for git refs).
- `proto/reef/daemon/v0/workspaces.proto`: `string start = <next>` on `CreateResponse`; `client/json.rs` and the CLI's create and run output.
- The help texts, proto comments, ADR 0022 decision 8 (amended), and `docs/quickstart.md` (the `--new-on` advice becomes a note for repositories with none of these).

## Tests

1. `default_start_order` (unit, on a test repository with each combination of bookmarks, including a local `master` beside an `origin` whose HEAD is `main`).
2. `default_start_follows_origin_head`: a colocated repository cloned from a git remote whose HEAD is `develop`; a create without a start is on `develop`.
3. `default_start_falls_back_and_says_so`: no such bookmark; the create starts on the root checkout's change, and `reef ws create` prints the line.
4. `store_build_without_rev_uses_master` (`tests/stores.rs`): with only `master`, `reef store build` without `--rev` builds `master`'s lockfile.

## Acceptance criteria

- [ ] On a fresh `git clone` of a repository whose default branch is `master`, `reef ws run -- true` starts on `master`, and a `jj` command in the root checkout afterwards rebases nothing.
- [ ] The four tests pass; `just ci` passes.
- [ ] The help texts, proto comments, ADR 0022 and the quickstart say the new order.

## Out of scope

- A per-repository `default_start` setting.
- Reading jj's `trunk()` alias from the repository's jj config (it is CLI configuration, and its revset language would need jj's CLI parser).
