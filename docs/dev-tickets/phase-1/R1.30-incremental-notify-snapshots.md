# R1.30 Incremental notify snapshots

Phase 1 · Size L · Depends on: R1.13 (the scheduler and the notify watcher), R1.14 (Watchman narrowing, the comparison), R1.23 (the load test, its findings, `watcher.watched_fallback_interval`) · Unblocks: the `large` half of R1.23's measurement, gating `load.yml` on `macos-15` again, the Phase 2 Scale target

## Context

R1.23 ran 200 workspaces with active watchers on one machine (`docs/load-tests.md`). On the `medium` preset (10,014 files) the steady-state write-to-snapshot p95 is under 0.8 s on a 12-core M2 Max and on the 4-vCPU `ubuntu-24.04` runner. It fails elsewhere:

- **`large` (100,014 files), 200 workspaces, M2 Max:** p95 **174 s**, with 831 of 1,000 writes not snapshotted 30 s after they were made. That is after R1.23 stopped the 60 s fallback full scan of every watched idle workspace, which took the whole run from 4 h 9 min to 62 min but barely moved the steady state (194 s before).
- **`medium`, 200 workspaces, the 3-vCPU `macos-15` runner:** p95 **145 to 149 s** in two runs. A full scan of 10,000 files there took 0.8 s at the median and 3.1 s at p95, against 32 and 111 ms on `ubuntu-24.04`.

Both come from the same cost. Every notify-triggered snapshot scans every tracked file, whatever path the event named. In the `large` run a scan took **11.4 s** at the median and 14.2 s at p95 with the pool busy, so 12 permits completed about 63 scans a minute against the 200 writes a minute the profile makes, and the queue grew to 188. `load.yml` now reports and does not gate on `macos-15` for this reason, and the Phase 1 criterion is stated as measured, naming `large` as unmet.

Watchman workspaces already scan only the reported paths, through jj's own integration (ADR 0023). That covers `auto` on a machine with `watchman` installed and a repository over 50,000 files. It does not cover notify workspaces: no Watchman, `watcher.backend = "notify"`, any repository under the threshold, and the load test, which pins notify (`tests/load.rs:112`).

### What was verified while writing this ticket

jj-lib and jj-core 0.46.0, notify 8.2.0 and notify-debouncer-full 0.7.0, the locked versions. Reef references are to R1.23's branch.

- **The scheduler keeps only a count.** `Inner::on_event` (`crates/reef-daemon/src/snapshot/mod.rs:912-924`) sets `dirty_since` and adds `event.paths.len()` to `paths_count`, and `Trigger` (`:322-329`, `Copy`) hands the snapshot the first event's time and that count. The paths themselves are dropped. `take_trigger` runs in `scheduled_snapshot` (`workspace/snapshot.rs:195`), before `run_snapshot` waits for a scan permit, so under R1.23's load the trigger was taken minutes before the scan began.
- **"Anything may have changed" is an empty path list, and a batch can lose it.** `WatchEvent` (`watcher/mod.rs:40-46`) uses empty `paths` to mean "anything", and so does Watchman (`watcher/watchman.rs:655-660`). In the notify handler (`watcher/notify.rs:149-166`), a `need_rescan()` event sets a batch-wide flag, and then every workspace gets `grouped.entry(workspace).or_default()`. A workspace that also had real paths in the same batch keeps them, so its event is not empty and nothing records that events were lost. The debouncer does deliver a held rescan together with expired path events (notify-debouncer-full `src/lib.rs:220-227`, `:282-284`). Today this is harmless, because every notify snapshot scans everything. A narrowed scan would make it a correctness hole.
- **FSEvents' rescan carries a directory; inotify's does not.** On macOS, `MustScanSubDirs` (coalesced events, with or without `UserDropped`/`KernelDropped`) becomes `Flag::Rescan` (notify `src/fsevent.rs:116-124`), and like every translated FSEvents event it gets the event's path (`:570-573`): the directory whose subtree must be rescanned. Reef ignores that path today and rescans every workspace. On Linux, `IN_Q_OVERFLOW` has no path (`src/inotify.rs:213`).
- **inotify names a new directory, not what is in it.** notify adds a watch for a directory only after the `IN_CREATE | IN_ISDIR` (or `IN_MOVED_TO`) event for it (`src/inotify.rs:61-75`). Files written into it before the watch exists, and everything inside a directory moved in from outside the workspace, are never named. A directory moved out, or deleted after its watch was lost, is named only by its own path.
- **jj fixes the fsmonitor when the working copy loads, and reloads the tree state on every mutation.** `LocalWorkingCopy::load` reads `TreeStateSettings` (which includes `fsmonitor_settings`) from `UserSettings` (`src/local_working_copy.rs:2835-2855`). `start_mutation` (`:2759-2783`) clones those settings into a new `LocalWorkingCopy`, re-reads the whole tree state from disk (jj's TODO at `:2773` calls it expensive), and loads it eagerly through `wc.tree()` (`:2781`). Every snapshot, explicit or scheduled, notify or Watchman, pays that reload before it scans. `finish` hands that same working copy back (`:3059`), and Reef's `LockedWorkspace::finish` keeps it as the workspace's in-memory working copy, which `Repo::working_copy_matches_view` reads later (`crates/reef-lib/src/jj/gc.rs:315-324`).
- **jj's only changed-file input is `FsmonitorSettings::Test`, and it matches files exactly.** `TreeState::make_fsmonitor_matcher` (`:1438-1505`) turns `Test { changed_files }` (or Watchman's answer) into a `FilesMatcher` of exactly those paths, unioned with a `PrefixMatcher` of the parent of each changed `.gitignore`. `FilesMatcher` compares bytes (jj-core `src/matchers.rs:170-181`). `TreeState::snapshot` (`:1295-1325`) intersects it with the sparse matcher and unions it with `force_tracking_matcher`. Deleted files are found only where the matcher matches (`emit_deleted_files`, `:1931`), so a directory reported as one path does not delete the files under it. `FsmonitorSettings::from_settings` refuses `fsmonitor.backend = "test"` (`src/fsmonitor.rs:57-79`), so it cannot come from configuration.
- **`TreeState` has the public pieces for a scan of Reef's own.** `TreeStateSettings`'s fields are public (`:968-980`). `TreeState::load(store, working_copy_path, state_path, &TreeStateSettings)` (`:1107`), `snapshot` (`:1295`), `save` (`:1182`) and `file_states` (`:1042`, with `FileStates::prefixed` for one directory) are public. `LockedLocalWorkingCopy::finish` (`:3035-3058`) asserts that its tree state is dirty or its tree unchanged, saves the tree state only when dirty, and saves the checkout state when the operation id changed. Reef reaches jj only through `reef_lib::jj` (ADR 0008). Its scan is `Repo::begin_snapshot` (`crates/reef-lib/src/jj/snapshot.rs:583-694`): it locks the working copy, decides `stale` (`:618`) and whether the view has a working-copy commit, both before the walk, then walks with `EverythingMatcher` and `NothingMatcher` (`:636`), and only then classifies (adopt with `check_out` at `:665`, divergent at `:672`, recover).
- **An idle full scan is cheap; a loaded one is not.** R1.14's `scan_is_narrowed` (`docs/benchmarks.md`, "Watchman-narrowed scans") measured `large` at **167 ms** for a full scan and **31 ms** narrowed by Watchman, one workspace on an idle M2 Max. R1.23 measured 11.4 s for the same full scan with 200 workspaces and 12 scans in flight, 68 times slower. `scan_ms` (`start.elapsed()` at `:694`) covers the lock and tree-state reload, the freshness check, the walk, and on the adopt path a checkout, so nothing yet says which part grew. Two guesses, neither measured: 200 `large` workspaces are 20 million files, possibly more than the kernel's inode and vnode caches hold, so a full scan may read metadata from disk; and the tree-state reload scales with tracked files, which narrowing does not remove.
- **Nobody has measured Watchman at this scale.** `auto` would pick Watchman for `large` on this Mac (`watchman` is installed), but `load.rs` pins notify.

## Decisions

- **Measure first, and stop if narrowing cannot be the fix.** Before any narrowing code:
  - Split the scan. `PendingSnapshot` and the `watcher snapshot taken` log line gain `load_ms` (`start_working_copy_mutation`: the lock and jj's tree-state reload) and `walk_ms` (`locked_wc().snapshot`), timed in `Repo::begin_snapshot` around those two calls. `scan_ms` keeps its meaning.
  - `load.rs` gains `REEF_LOAD_WATCHER` (`notify`, the default, or `watchman`), recorded in the report's `params`.
  - On the M2 Max, nothing else running: 200 × `large` with notify, 200 × `large` with Watchman, and 50 × `large` with notify. The 50-workspace run separates cache pressure (5 million files) from the per-scan cost. Record all three in `docs/load-tests.md` with the split.

  Watchman is not a clean upper bound for notify narrowing: it also pays a query per snapshot (about 10 ms, ADR 0023), its server's crawl of 200 new roots, and a full scan on every fresh instance. So read it this way:

  - **Narrowing is the fix** if Watchman passes the gate, or if notify's loaded `walk_ms` is most of its `scan_ms`. Build the rest of this ticket.
  - **Narrowing cannot be the fix** if `load_ms` (the reload) is most of a loaded notify scan, or if Watchman fails with a small `walk_ms`. Stop, record the split, and file what it points to (the reload, the commit, memory) instead. Do not build the rest.
  - **Inconclusive** if Watchman fails with a large `walk_ms` or query time. Say so in the PR, and decide with the phase owner whether to build narrowing anyway.

- **"Everything" is explicit.** `WatchEvent` gains `everything: bool` in place of the empty-paths convention, set by notify's overflow handling and by Watchman's fresh-instance and first results. The notify handler sets it for every workspace on an overflow, whether or not the workspace also had paths in the batch. On macOS, a `Rescan` event's path is used instead when it lies under one workspace's root: that workspace gets the path (a prefix, below), and the others nothing. A rescan path at or above a root, or with no path (inotify's overflow), is *everything* for each workspace it covers. This is a correctness fix that stands on its own, so it lands with the measurement even if the rest stops there.
- **The scheduler keeps the reported paths.** `Entry` replaces `paths_count` with a path set:
  - `Entry` keeps the canonical root that `Inner::track` computes (a local today, `snapshot/mod.rs:776`), and the set holds paths relative to it. Events carry canonical paths (`/private/tmp` for `/tmp` on macOS). A path outside the root is dropped. The root itself, as a relative path of `""`, means *everything*.
  - Store mounts and literal exclude prefixes never arrive (`skip_prefixes`, `watcher/mod.rs:285`). Glob excludes do arrive, and jj's ignore handling skips them in the walk.
  - The set becomes *everything* on an `everything` event, when it would grow past `watcher.narrowed_max_paths` (new key, default 1,000), or when `.reefignore` is among the paths. Reef's ignore sources are not `.gitignore` files, so jj's own parent rescan does not cover them (the gap ADR 0023 records for Watchman).
  - The set is taken after the scan permit is acquired, just before the scan, not with `first_event` in `scheduled_snapshot`. The early check that skips a snapshot whose events an explicit snapshot already covered stays where it is. Events that arrive while a snapshot waits for a permit join its set; events during the scan go into the next one. Nothing reported is lost between two snapshots.
  - `Trigger` becomes `Clone` (it carries the set), and its `paths_count` (the set's length, or 0 for *everything*) and the log field stay.
- **Every reported path is a prefix.** A reported path covers itself and, if it is or was a directory, everything under it, on disk and in the tree state. That covers inotify's new and moved-in directories, directories moved out or removed, FSEvents' rescanned directories, and rename pairs (both halves are reported). Store mounts are symlinks and are never followed.
- **What stays a full scan:**
  - explicit snapshots: the `Snapshot` RPC, `Inspect` with `snapshot_first`, a release's final snapshot, a move;
  - fallback-timer snapshots;
  - a workspace that is `behind` (R1.23), or whose watch is not working (`watched` false: a failed watch, or inotify's limit hit on a new subdirectory, R1.23), since its still-watched subtrees keep reporting while the rest does not;
  - a set that became *everything*;
  - a snapshot whose working copy is stale or has no working-copy commit in the view (both known before the walk): the adopt, divergent and recover paths;
  - `watcher.narrowed_max_paths = 0`, which turns narrowing off;
  - Watchman workspaces, which keep jj's own narrowing.

  The 10-minute watched fallback (R1.23) is the backstop for anything a narrowed scan missed. Its documentation changes from "events dropped while the scheduler was behind" to that.
- **How the paths reach jj is the ADR's decision, made with the split above.** First check whether a jj-lib release after 0.46 already has an API for it. Otherwise there are two candidates:
  1. **Through `TreeState`'s public API, inside Reef's lock.** Keep `start_working_copy_mutation` for the lock, the freshness check and `finish`. For a narrowed snapshot (fresh, with a working-copy commit), load a second `TreeState` with `fsmonitor_settings = Test { changed_files }`, snapshot it, and `save` it. The locked working copy is then not dirty and its tree unchanged, so `finish`'s assertion holds and it writes only the checkout state.
     - `Test` matches exact files, so Reef expands each prefix first. A directory on disk is walked, without following symlinks and bounded by `narrowed_max_paths` (files, not prefixes). The tracked paths under the prefix come from `FileStates::prefixed`, for deletions. On a case-insensitive volume, each reported path is resolved to its on-disk spelling (`fcntl(F_GETPATH)` on macOS) before matching; one that cannot be resolved makes the set *everything*.
     - The cost is a second full tree-state reload per snapshot, on top of the one `start_mutation` already forces. That is acceptable only if the split shows `load_ms` small next to `walk_ms` under load.
     - The daemon's in-memory working copy still holds the pre-scan tree after `finish`. Reef reloads it after every narrowed snapshot, and `working_copy_matches_view` is tested after one.
  2. **Through jj-lib.** An upstream change has two parts:
     - Let a caller pass changed path prefixes to one snapshot (for example a field on `SnapshotOptions`), turned into a `PrefixMatcher` together with the `.gitignore` parents that `make_fsmonitor_matcher` adds today.
     - Copy the tree state from the loaded working copy, instead of re-reading it, when it has not changed (jj's TODO at `:2773`). That removes the reload for every snapshot, Watchman's included.

     Until a jj-lib release has it, Reef carries it as a `[patch.crates-io]` fork. A patched dependency blocks `cargo publish` of `reef-lib` and `reef-daemon` (not R1.28's prebuilt binaries), so the ADR says when the patch must be gone.

  Either way it sits behind `reef_lib::jj` (a `begin_snapshot` that takes an optional prefix list), so the daemon does not name jj-lib types.
- **ADR 0026, "Narrowed notify snapshots"**, records:
  - the measurement;
  - the choice between the two options above, including how the `.gitignore` parent rescan is kept;
  - what stays a full scan, and the backstop.

  It also amends ADR 0023's alternative "A notify-based narrowing through an upstream jj-lib change" to point here, and ADR 0008's upstream list if option 2 is taken.

## Tests

Notify on the `small` preset unless stated, with `watched_fallback_interval` and `fallback_interval` at 1 h so that no fallback can stand in for the scan under test.

Always:

1. `scan_split_is_reported` (`tests/snapshots.rs`): a watcher snapshot's outcome has `load_ms` and `walk_ms`, and their sum is at most `scan_ms`.
2. `overflow_with_paths_is_everything` (`watcher/notify.rs` unit test): a batch holding a rescan event and a path event for workspace A yields one `WatchEvent` for A with `everything` set, and `everything` for every other workspace. On macOS, a rescan event whose path is under B's root yields B that path only, and nothing for the others.

Only with narrowing; each asserts `narrowed = true` where it says "narrowed":

3. `narrowed_scan_records_the_write`: write one tracked file; the watcher snapshot is narrowed and has the new content.
4. `directory_moved_in_is_snapshotted`: build a directory of 50 files outside the workspace, `rename` it in; every file is in the next snapshot.
5. `directory_moved_out_is_deleted`: `rename` a tracked directory out of the workspace; none of its files are in the next snapshot.
6. `files_written_into_a_new_directory_at_once`: `mkdir` and write 20 files into it with no pause (the inotify race); all 20 are in the snapshot that follows. In the PR, also run it 20 times in a loop in the privileged Linux container; CI runs it once.
7. `everything_scans_everything`: `pause_watcher`, write a file (no event), `resume_watcher`, `inject_event(ws, [], everything = true)`; the next snapshot has the file and is not narrowed.
8. `too_many_paths_scans_everything`: with `narrowed_max_paths = 10`, write 11 files; the snapshot is not narrowed and has all 11.
9. `reefignore_change_scans_everything`: un-ignore a directory in `.reefignore`; its files are in the next snapshot, which is not narrowed. A `.gitignore` change that un-ignores a file is picked up by a narrowed snapshot (jj's parent rescan, kept under either option).
10. `events_while_waiting_and_scanning_are_kept`: with `hold_scans()` held, write file A, release; then hold again, write B during that scan, release. Both A and B end up snapshotted, and no snapshot is lost.
11. `store_mount_is_not_walked`: with a symlinked store of 10,000 files, a narrowed snapshot whose path set names the mount's parent directory records the symlink, not the store's files, and its `walk_ms` is under a tenth of a full scan's on the same workspace.
12. `case_insensitive_write_is_snapshotted` (macOS, case-insensitive APFS): write a tracked `README.md` through the path `readme.md`; the next snapshot has the new content.
13. `unwatched_workspace_is_not_narrowed`: with `refuse_watches` for one workspace (R1.23's hook) and an injected event for it, its snapshot is not narrowed.
14. `explicit_and_final_snapshots_are_full`: `Snapshot`, `Inspect` with `snapshot_first`, and a release's final snapshot all have `narrowed = false`.
15. Option 1 only, `in_memory_working_copy_follows_a_narrowed_snapshot`: after a narrowed snapshot, `working_copy_matches_view` is true, and a following full snapshot finds nothing to change.

## Out of scope

- Per-workspace memory: each loaded working copy keeps its tree state, about 18 MB per `large` workspace on macOS and 73 MB on Linux (R1.23). Unloading idle working copies is a Phase 2 Scale question.
- inotify's watch count (one per directory per workspace), and one Watchman project root shared by all workspaces (ADR 0023's consequences).
- Watchman's own per-query cost and its crawl of 200 roots: measured here, not tuned.
- Deleting released trees at low priority, the rest of R1.23's teardown finding.
- Events dropped when the scheduler's queue (4,096) is full. The 10-minute fallback still covers them, as before.
- The FSEvents stream restart on every `watch` and `unwatch` (R1.29's out-of-scope note).
- Tuning `watcher.max_concurrent_scans` or the debounce.

## Risks

- **A narrowed scan can miss a change, and nothing says so.** A full scan cannot. The backstops are the 10-minute watched fallback, every explicit and final snapshot being full, and *everything* on any overflow. A change that no event names (a tool writing through a path the watcher does not see, a case-folded name on APFS that cannot be resolved) waits up to 10 minutes, or lands in the release's final snapshot. Tests 4 to 13 are the known cases. `narrowed_max_paths = 0` turns the feature off without a rebuild.
- **The fix may not be the walk.** If a loaded scan's 11 s is mostly the tree-state reload, or the kernel's metadata caches missing at 20 million files, narrowing the walk helps less than R1.14's idle numbers suggest. That is why the measurement comes first and can end the ticket.
- **Option 1 couples Reef to `LockedLocalWorkingCopy`'s behaviour.** It relies on `finish` not saving a tree state it did not dirty, and it leaves the daemon's in-memory working copy stale until Reef reloads it. A jj-lib bump that changes either would overwrite the narrowed scan's state or answer `working_copy_matches_view` from an old tree. Test 15 pins both.
- **Option 2 carries a patched jj-lib** until upstream releases the change. Every jj-lib bump has to rebase the patch, `gix` already has to move in lockstep with jj-lib (ADR 0008), and the `.gitignore` parent rescan has to be kept by hand.
