# R1.28 Prebuilt binaries and a one-line install

Phase 1 · Size M · Depends on: R0.03 (the CI matrix the release workflow extends), R1.22 (autostart from the `reef` binary itself, which is why one binary is enough) · Unblocks: R1.24 (the install section), RX.07 (scenario C installs Reef from nothing), R4.17 (signing, notarization, and the mobile shells build on this workflow)

## Context

R1.24's quickstart installs with `cargo install --git`, which needs a Rust toolchain and ten minutes. An agent asked to "set up Reef and use it" in a container has neither, and the human who wants to try Reef on a laptop will not install Rust first. R4.17 owns signed binaries, a Homebrew tap, and app-store distribution, but is scheduled for Phase 2 onward. The pieces an agent needs are smaller and should ship with Phase 1: a GitHub Release with binaries for the four targets, an installer script that works with `curl | sh`, a Homebrew formula, and `cargo binstall` metadata. Signing and notarization stay in R4.17.

### What was verified while writing this ticket

- `cargo install --git https://github.com/reef-vcs/reef reef-vcs` builds only `reef`; R1.22's autostart locates `reef-daemon` beside the binary or on `PATH` and otherwise runs `reef daemon run` from `reef` itself (`crates/reef-vcs/src/cli/autostart.rs:46`, `DAEMON_BIN` lookup with the `["daemon", "run"]` fallback), and `reef daemon run` calls `reef_daemon::run_main` in-process (`cli/daemon.rs:48`). One binary is a complete install; the `reef-daemon` binary is for service managers. R1.24's brief says both crates must be installed; this ticket corrects that in the same PR series.
- The build needs no `protoc` (`crates/reef-daemon/build.rs` uses `protox`), so a release build is `cargo build --release -p reef-vcs` on a stock toolchain.
- CI runs on `ubuntu-24.04` and `macos-15` (R0.03). GitHub's hosted Arm Linux runners (`ubuntu-24.04-arm`) and Intel macOS runners (`macos-15-intel`) were not re-verified this session; if either is unavailable the matrix cross-compiles that target with `cross` and the PR records which.
- `dist` (formerly `cargo-dist`, github.com/axodotdev/cargo-dist) generates a `release.yml` and uploads to GitHub Releases; whether it still generates the shell installer and a Homebrew formula was not confirmed from its README this session. A hand-written workflow of about 120 lines plus a 150-line `install.sh` is cheaper to own than a generator whose output this repository would have to review anyway, so this ticket writes them by hand and keeps `dist` as the alternative in the risks.
- A binary downloaded with `curl` carries no `com.apple.quarantine` attribute (browsers set it, `curl` does not), so an unsigned, un-notarized macOS binary installed by the script runs from a terminal without Gatekeeper's dialog. Homebrew-installed binaries likewise. This is why signing can wait for R4.17.

## Decisions

- **Targets**: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`. musl so one Linux binary runs in any container regardless of glibc; the daemon's overlayfs path is raw `nix::mount` syscalls and its FUSE path spawns an external `fuse-overlayfs`, neither of which needs glibc. If the musl build of jj-lib's dependency tree fails (gix and rusqlite are the likely places), fall back to `*-unknown-linux-gnu` built on `ubuntu-22.04` for an older glibc floor, and record it in the PR and in `docs/quickstart.md`.
- **Artifacts** per target: `reef-<version>-<target>.tar.gz` containing `reef`, `reef-daemon`, `LICENSE`, `README.md`, and `completions/` for bash, zsh, and fish (generated by `reef completions` during the build). One `SHA256SUMS` file for all artifacts. Versions are the workspace version; the first release is `0.1.0` at Phase 1's close.
- **Release trigger**: pushing a tag `v<version>` that matches `Cargo.toml`'s workspace version (the workflow checks and fails otherwise). `workflow_dispatch` with a `dry_run` input builds everything and uploads to the workflow run, not to a Release, for testing. Release notes come from `CHANGELOG.md`'s section for the version (R1.24 creates the file), extracted by a 20-line script; a missing section fails the release.
- **`install.sh`** at the repository root, served as `https://raw.githubusercontent.com/reef-vcs/reef/main/install.sh` and attached to each Release: POSIX `sh`, no bash-isms, `set -eu`. Detects OS and architecture with `uname`, downloads the matching tarball and `SHA256SUMS` for `REEF_VERSION` (default: latest release via the GitHub API's `releases/latest` redirect, no `jq`), verifies the checksum with `sha256sum` or `shasum -a 256`, extracts into `$REEF_INSTALL_DIR` (default `~/.local/bin`), never uses `sudo`, and ends by printing the installed version and, if the directory is not on `PATH`, the one line to add. Exit codes: 0, or 1 with a one-line reason. `shellcheck` clean. Agents can run it unattended: it prompts for nothing (R1.26's contract applies to the installer too).
- **Homebrew**: a tap repository `reef-vcs/homebrew-tap` with `Formula/reef.rb` pointing at the release tarballs by target with their checksums; the release workflow opens a PR to the tap with the new version and checksums (a `GITHUB_TOKEN` with contents write on the tap, stored as a repository secret). `brew install reef-vcs/tap/reef`. A formula template lives in this repository at `packaging/homebrew/reef.rb.tmpl` so the tap is reproducible.
- **`cargo binstall`**: `[package.metadata.binstall]` in `crates/reef-vcs/Cargo.toml` with the `pkg-url` template matching the artifact names, so `cargo binstall reef-vcs` works for people who already have cargo.
- **`reef --version`** prints `reef <version> (<short commit>, <target>)`, the commit from `git describe` at build time via `build.rs` (falling back to `unknown` in a tarball build), so bug reports and RX.07 results name the exact binary.
- **No signing, no notarization, no Windows** (R4.17, RX.05).

## Deliverables

### `.github/workflows/release.yml`

Jobs: `check-version` (tag matches workspace version), `build` (matrix of four, `cargo build --release --locked -p reef-vcs -p reef-daemon`, smoke test `./reef --version` and `./reef guide | head -1` on native runners, tarball, upload artifact), `checksums`, `release` (create the GitHub Release with the changelog section, attach tarballs, `SHA256SUMS`, and `install.sh`), `homebrew` (PR to the tap). `dry_run` skips `release` and `homebrew`.

### `install.sh`, `.github/workflows/ci.yml`

The script, plus a CI job `installer` that runs `shellcheck install.sh` and, on both OSes, `REEF_INSTALL_URL=file://<dir>` against the tarball built in the same run (the script honors `REEF_INSTALL_URL` as a base URL override for exactly this) and asserts `~/.local/bin/reef --version` matches.

### `packaging/homebrew/reef.rb.tmpl`, `scripts/release-notes.sh`, `scripts/update-tap.sh`

Template and the two scripts the workflow calls, each runnable locally with `--dry-run`.

### `crates/reef-vcs/Cargo.toml`, `crates/reef-vcs/build.rs`

binstall metadata; the version string.

### `docs/quickstart.md` (or R1.24's brief if it has not landed), `README.md`

Install section becomes: installer one-liner first, Homebrew second, `cargo binstall` third, `cargo install` last as "from source". The README's status line names the release.

## Implementation notes

- Build with `--locked` and the checked-in `rust-toolchain.toml`; no nightly.
- Strip binaries (`strip = true` in a `[profile.release]` on the workspace) and set `lto = "thin"`, `codegen-units = 1`; measure the size once and put it in the PR.
- Keep the installer's GitHub API use to one unauthenticated request (the `latest` redirect); unauthenticated rate limits are per IP and CI containers share them, so `REEF_VERSION` pinned is what RX.07 uses.
- The tap PR step must not fail the release if the tap is unreachable; it reports and continues, and the formula can be updated by hand with `scripts/update-tap.sh`.

## Acceptance criteria

- [ ] A `workflow_dispatch` dry run produces four tarballs and a `SHA256SUMS` whose entries verify.
- [ ] `install.sh` installs the dry-run artifacts on macOS and Linux in CI, unattended, and `reef --version` prints the version, commit, and target.
- [ ] `shellcheck install.sh` passes; `sh -n install.sh` under `dash` passes.
- [ ] `cargo binstall --dry-run reef-vcs` resolves the artifact URL (run against a dry-run artifact with `--pkg-url` override if no release exists yet).
- [ ] The formula template renders with the dry-run checksums and `brew install --formula ./reef.rb` succeeds on the macOS runner.
- [ ] `docs/dev-phases.md` R4.17 row narrowed to what remains; R1.24 updated.
- [ ] `just ci` passes.

## Verification

```sh
gh workflow run release.yml -f dry_run=true && gh run watch
curl -fsSL https://raw.githubusercontent.com/reef-vcs/reef/main/install.sh | REEF_VERSION=0.1.0 sh
~/.local/bin/reef --version
```

## Out of scope

- Code signing, notarization, and the app-store work (R4.17).
- Windows binaries (RX.05).
- Linux distribution packages (deb, rpm, nix, AUR); the tarball and installer serve them until someone asks.
- A `reef self-update` command.

## Risks

- musl may not build jj-lib's tree; the gnu fallback is decided above so it costs a day, not a debate.
- Hosted runner availability for Arm Linux and Intel macOS; `cross` is the fallback and the smoke test then runs only on the native targets.
- An unsigned binary and a `curl | sh` line will draw the usual criticism; the checksum verification, the `REEF_VERSION` pin, and the Homebrew path are the answer until R4.17 signs releases.
