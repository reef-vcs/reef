# R1.12 Workspace creation benchmarks

Phase 1 · Size S · Depends on: R1.11 (the fixture and the per-kind probing), R1.05 (`TestDaemon` with `Workspaces.Create` for the `create_api` group), R0.06 (the criterion harness and `bench.yml`) · Unblocks: RX.06 (the regression gate reads these numbers), R1.23 (reuses the free-space measurement)

## Context

The first phase exit criterion is quantitative: "Twenty workspaces on the 100k-file synthetic repo, each created in under one second on APFS and overlayfs, with disk usage per workspace proportional to modified files." R0.06 set up criterion in `reef-lib` for snapshot costs (`docs/benchmarks.md`). This ticket adds the workspace-creation benchmarks per backend, publishes them from CI on both platforms the way R0.06 does, and writes the first measured table into `docs/benchmarks.md`. Nothing fails when a number misses the target; RX.06 turns it into a gate.

### What was verified while writing this ticket

- On the authoring machine (M2 Max, APFS), the `large` preset materializes by directory `clonefile` in 1.0 to 1.2 s and costs about 30 MiB of metadata (R1.08's table); per-file clones take 13 s, plain copy 26 s and 632 MiB; `rm -rf` 4.4 s. Twenty workspaces by directory clone is therefore about 22 s of creation and 90 s of teardown on this machine, which bounds how many iterations a benchmark can afford.
- `crates/reef-lib/benches/common/mod.rs` builds the fixture under `target/bench-fixtures/<preset>-42/` with a `.ready` stamp holding `generator <v>, fixture <v>, spec <json>`; a second crate using the same stamp format and `FIXTURE_VERSION` reuses the directory. `CARGO_TARGET_TMPDIR` locates the target directory from a bench.
- `bench.yml` uploads `bench-results.txt` (`--output-format bencher`) and `target/criterion/` as `bench-<os>-<preset>-<sha>-<run id>`; `just bench` is `cargo bench --workspace --bench '*'`, so a new `[[bench]]` in `reef-daemon` is picked up without workflow changes beyond what this ticket adds.
- `libc::statvfs` is available on both platforms (R1.07's `fs_util::free_bytes`).

## Decisions

- **Benches live in `crates/reef-daemon/benches/`**, not `reef-lib`, because the backends are daemon code and `reef-lib` cannot depend on `reef-daemon`. This amends the R0.06 decision "benches live in `crates/reef-lib/benches/`" to "benches live in the crate that owns the code they measure; fixtures are shared through `target/bench-fixtures/`". The README's Phase 0 table is not edited; this brief and `docs/benchmarks.md` record the amendment.
- **One bench target, `workspace_create`**, with groups `create/<preset>/<kind>/<n>` for `n` in 1, 20, 100 and every kind whose probe reports available, measured through the backend layer: the base cache entry is built once in setup (not timed, printed to stderr like the first snapshot in R0.06), each iteration materializes `n` workspaces (timed) and tears them down (not timed, awaited before the next iteration). Criterion `iter_custom` with `sample_size(10)`; measurement time 30 s for `small`, 60 s for `medium`, 120 s for `large`; `large/100` runs only when `REEF_BENCH_WS_MAX=100` (default 20) because its teardown alone is minutes.
- **A second group, `create_api/<preset>/<n>`** for `n` in 1 and 20 drives the full path through an in-process `TestDaemon` (R1.03) and `Workspaces.Create` (R1.05), which is what the exit criterion actually describes (resolve revision, base ensure, materialize, jj workspace init, tree_state seeding, lease row). Runs for the `auto` backend only. This group is the exit-criterion measurement and this ticket owns it.
- **Disk per workspace is measured, not estimated**: `free_bytes` before and after creating `n` workspaces, divided by `n`, printed as `disk_per_ws_mib`; then each workspace is mutated with `synth::mutate(root, seed, modify 50)` and the delta re-measured as `disk_per_ws_modified_mib`. The second number proves "proportional to modified files": it must be close to 50 files' worth of blocks plus metadata, not the tree. Both numbers go to stderr as a Markdown row and into a JSON line (`target/bench-ws.json`) that CI uploads with the artifact.
- **The phase target is a documented check**: the bench prints `target: 20 workspaces under 1 s each: PASS|MISS (<p50> s)` for `create_api/large/20` and, for comparison, per kind for `create/large/<kind>/20`, and never fails. RX.06 decides the threshold and the gate.
- **Teardown cost is reported too** (`tear_down/<preset>/<kind>` for one workspace) because reclaim at 200 workspaces (R1.23) depends on it.
- **CI**: `bench.yml` gains nothing but the JSON file in the artifact path list and, for the Linux runner, a `sudo` variant of the bench run for the kernel overlay kind (`REEF_BENCH_PRIVILEGED=1` makes the bench probe the kernel tier; the step runs `sudo -E env "PATH=$PATH" cargo bench -p reef-daemon --bench workspace_create ...` and chowns `target/` afterwards, as R1.09's job does). `fuse-overlayfs` is installed in the same step.

## Deliverables

### `crates/reef-daemon/benches/common/mod.rs`

The fixture builder, a copy of `reef-lib`'s with the same `SEED`, `FIXTURE_VERSION`, stamp format, and reuse rules, plus `base_entry(fixture) -> BaseEntry` (a temp state directory under `target/bench-state/` with `BaseCache::ensure` of the fixture's first commit) and `available_kinds(state_dir) -> Vec<BackendKind>` from `probe`. Share code rather than copy where a `pub` helper in `reef_daemon::backend` can serve both; the fixture builder itself stays duplicated (it needs jj and the generator, which `reef-testing` cannot link).

### `crates/reef-daemon/benches/workspace_create.rs`

```rust
fn bench_create(c: &mut Criterion) {
    let fx = common::fixture();                 // synthetic repo, first snapshot
    let base = common::base_entry(fx);          // printed: "bench base: materialized <preset> in <s>"
    for kind in common::available_kinds() {
        for n in [1, 20, 100].into_iter().filter(|n| *n <= max_n()) {
            group.bench_function(BenchmarkId::new(format!("{kind}"), n), |b| {
                b.iter_custom(|iters| { /* for each iter: time materialize × n; tear down × n outside the timer; await deletions */ });
            });
        }
    }
}
fn bench_tear_down(c: &mut Criterion);
fn bench_create_api(c: &mut Criterion);        // TestDaemon + Create, n in [1, 20]
criterion_group!(benches, bench_create, bench_tear_down, bench_create_api);
criterion_main!(benches);
```

After each `create/<kind>/<n>` group the bench prints the disk rows:

```text
| preset | kind | n | p50 create ms/ws | disk MiB/ws | disk MiB/ws after modify 50 | tear_down ms/ws |
```

and appends the same as a JSON object to `target/bench-ws.json`.

## Implementation notes

- `iter_custom` returns the total `Duration` for `iters` iterations; divide by `n` for per-workspace. Do the teardown and the `drain_background_deletions()` wait outside the timed region; both are large on APFS.
- Creating 100 workspaces of the `large` preset is 100 × 30 MiB of metadata and 100 × 4 s of teardown; hence `REEF_BENCH_WS_MAX`. On `small` and `medium`, 100 is cheap and always runs.
- Workspace ids for the bench are sequential (`bench-0001`) under `target/bench-state/<preset>/ws/`; the overlay kinds need the state directory on a filesystem that supports `trusted.*` xattrs (the runner's ext4 does).
- Free-space deltas on a shared machine are noisy; sample `free_bytes` three times and take the median, and say so in `docs/benchmarks.md`.
- The `create_api` group needs a `TestDaemon` per group (not per iteration) and `Release` with the background deletion awaited; it measures what the exit criterion says, so its `large/20` p50 is the headline number in the docs table.

## Acceptance criteria

- [ ] `cargo bench -p reef-daemon --bench workspace_create -- --sample-size 10` runs on macOS (`copy`, `apfs`) and Linux (`copy`, `fuse-overlayfs` when installed; `overlayfs` under `sudo`) and prints the Markdown rows and the `target:` line per kind.
- [ ] `target/bench-ws.json` is written and uploaded by `bench.yml` on both runners.
- [ ] On the authoring machine, `create_api/large/20` p50 (the exit criterion; `auto` resolves to `apfs`) is under 1 s per workspace and `disk MiB/ws` is under 50 MiB, with `create/large/apfs/20` recorded beside it; on a Linux machine or the privileged CI job (`auto` resolves to `overlayfs`), `create_api/large/20` p50 is under 1 s and `create/large/overlayfs/20` p50 under 0.1 s per workspace. All recorded in `docs/benchmarks.md` with machine details. A miss is recorded, not hidden.
- [ ] `disk MiB/ws after modify 50` is within 2× of `disk MiB/ws` plus the 50 files' allocated size for every copy-on-write kind, and roughly the tree size for `copy`.
- [ ] `just build` compiles the bench (`--all-targets`), so it cannot rot; `just ci` passes.
- [ ] `docs/benchmarks.md` has the new section and the bench-location amendment.

## Out of scope

- A regression threshold or a failing gate (RX.06).
- Measuring the watcher or snapshot latency under load (R1.23) and the base cache's first materialization (printed, not benchmarked).
- Benchmarking `reflink` in CI (needs the loop mount from R1.10's job; run by hand on a btrfs machine and recorded in the docs table when available).

## Risks

- GitHub's `macos-15` runners (3 vCPU, 7 GB) may put `apfs/large/20` over one second; the criterion is judged on the authoring class of machine and the runner number is trend data, as `docs/benchmarks.md` already says for R0.06.
- Free-space measurement includes everything else happening on the volume (criterion's own reports, the fixture); the three-sample median and a quiet machine are the mitigation, and the modified-files column is the one that matters.
