# R2.22 Subscription load test and broker

Phase 2 · Size M · Depends on: R2.10 (the presence channel; through it R2.09's `Operations.Subscribe`, the `Broker`, the `operations` index and the op-heads watch), R2.03 (`Changes.Describe`, the generator's second operation source), R1.23 (`load.rs`, `SpawnedDaemon`, `load.yml`, `docs/load-tests.md`) · Unblocks: the subscription exit criterion; R4.02 and R4.19 (the store reuses the broker and the test's shape)

## Context

Phase 2's third exit criterion is a number: a client subscribed to the operation log and the presence channel receives events within 100 ms, and that holds with 500 subscribers on one daemon at 1,000 operations per minute (`docs/design.md`, Scale: "500 subscribers on one daemon receiving 1,000 operations per minute, each delivered within 100 ms"). R2.09 builds the in-process `Broker` that every `Operations.Subscribe` and `Presence.Subscribe` stream reads from; R2.10 puts presence on it. Neither measures it. This ticket is the measurement, in the shape R1.23 gave Phase 1's load test, and the fixes the measurement calls for. The design names the broker as "the same component the store reuses in phase four", so what this ticket learns about fan-out is written down for R4.02 and R4.19.

Phase 1's load test taught two things this ticket inherits. First, measure before blaming: `docs/load-tests.md` records that a `large` snapshot scan went from 167 ms idle to 11.4 s under load, and that the fix (R1.30) was not where the first guess pointed. Second, a gate on a timing holds on `ubuntu-24.04` and is reported on `macos-15`, and a failure is compared against `main` in the same environment before it is attributed to a change (`docs/load-tests.md`, "Findings"; the memory of flaking lease and snapshot tests under load). The gate here is the design's number, not a guess, so the test's job is to make the number honest: same host, same clock, a client that cannot be the bottleneck, and a report that says where the time went when it misses.

### What was verified while writing this ticket

Reef at `d156d1e` (0.1.0), tonic 0.14.6, h2 0.4.20, the locked versions. The Phase 2 schema (`reef.daemon.v1`) does not exist yet; message and RPC names below are the Phase 2 README's.

- **The pacing arithmetic comes from two Phase 1 knobs.** `watcher.debounce` is 500 ms and `watcher.min_interval` 1 s (`crates/reef-daemon/src/config.rs:345-352`); a snapshot starts once `min_interval` has passed since the workspace's last one finished, and events during a snapshot queue exactly one more (`crates/reef-daemon/src/snapshot/mod.rs:9-13`). A workspace that writes one changed file every 1.5 s therefore gets one snapshot per write: the debounced event lands 0.5 s after the write and the previous snapshot finished at least 1 s before. Twenty such workspaces are 800 snapshots a minute. A snapshot operation is one jj operation (`is_snapshot`, `crates/reef-lib/src/jj/oplog.rs:40`), so 800 operations a minute from snapshots; the rest comes from `Changes.Describe` (R2.03), one transaction and one operation per call.
- **Commits are serialized per repository, and cost 7 to 9 times more on APFS.** Every transaction runs on the repository's one thread (ADR 0012; `crates/reef-daemon/src/repo/mod.rs:217-257`). R1.23's burst finding (`docs/load-tests.md`, Findings, "A burst on macOS takes 14 to 19 s to drain"): 200 snapshot transactions took 70 to 95 ms each on APFS against about 10 ms on ext4, with no scan waiting. At 1,000 operations a minute (16.7 a second) one repository thread on APFS is busy 1.2 to 1.6 s per second: it cannot keep up. On ext4 it is busy about 0.17 s per second. This is why the generator below spreads its workspaces over two repositories, and why the gate is on `ubuntu-24.04` only.
- **Each `Client::connect` opens one Unix-socket connection** (`crates/reef-daemon/src/client/mod.rs:110-128`: `Endpoint::connect_with_connector` over `UnixStream::connect`), and `Client` clones share it (`tests/load.rs:607` clones one client for every writer and the sampler). tonic's server leaves `max_concurrent_streams` at `None` (`tonic-0.14.6/src/transport/server/mod.rs:128`), so h2's default applies to streams per connection; the default's value was not confirmed in h2 0.4.20's source (`frame/settings.rs` defines the window and frame sizes at `:44-47` and no stream constant was found). The test sidesteps the question: one connection per subscriber (below), so no per-connection limit binds, and the cost is file descriptors, which the test records.
- **The daemon's runtime is tokio's multi-thread default** (`crates/reef-daemon/src/run.rs:66-70`: `new_multi_thread().enable_all()`, so one worker per CPU) and the scheduler's event queue holds 4,096 events (`snapshot/mod.rs:84`). Nothing in the daemon today limits open connections.
- **`load.rs` is the model.** `Params::from_env` (`crates/reef-daemon/tests/load.rs:65-105`) reads `REEF_LOAD_*`; the single `#[ignore]` test (`:146-170`) exits with `skipped:` unless `REEF_LOAD=1`; the report is a `serde_json::Value` written to `target/load/<os>-<preset>-<stamp>.json` (`write_report`, `:1034`) with `machine()` (`:1000`), `params`, the daemon's `config.toml`, per-phase sections, `limits`, and `pass`; `markdown()` (`:1063`) prints the table column; `percentile` is nearest-rank over sorted samples (`:1192`). `SpawnedDaemon::spawn(configure)` (`tests/common/spawned.rs:66`) starts the binary on a fresh state directory with a `FileConfig` the test edits, `register_synth(preset)` (`:215`) registers a synthetic repository, `log_lines(pattern)` (`:192`) reads the JSON log, and a `Monitor` samples the daemon's threads and RSS (`load.rs:805-853`).
- **`load.yml`** runs one job per OS with `REEF_LOAD=1`, builds the test in release first, runs it as root on Linux, uploads `target/load/` for 90 days, and runs on a pull request that changes the test or the workflow (`.github/workflows/load.yml:7-14`, `:238-260`). Its `timeout-minutes` is 90 for `medium`.
- **The local machine's `ulimit -n` is 1,048,576.** The runners' soft limit was not checked; Ubuntu's default soft limit is commonly 1,024, which 500 subscriber connections plus the daemon's would exceed. The test reads the limit and raises its own (`setrlimit`) before connecting, and records both.
- **Frames add up to `[events] frame_interval`** (50 ms, Phase 2 README, "Events and presence") to every event's delivery by design. Of the 100 ms budget, 50 is spent before the event leaves the daemon on the slowest frame boundary. The measurement counts it; the design's number is end to end.

## Decisions

- **One test, `crates/reef-daemon/tests/subscriptions_load.rs`**, `#[ignore]`, a no-op unless `REEF_LOAD=1`, release build, driving the `reef-daemon` binary through `SpawnedDaemon` as `load.rs` does. Knobs, all environment variables, recorded in the report's `params`: `REEF_SUBS_SUBSCRIBERS` (500), `REEF_SUBS_OPS_PER_MIN` (1,000), `REEF_SUBS_STEADY_SECS` (300), `REEF_SUBS_WORKSPACES` (20), `REEF_SUBS_MODE` (`broker`, the default, or `poll`, below). It shares `tests/common/` with `load.rs` and moves `percentile`, `machine`, `write_report`, `Monitor` and `utc_stamp` from `load.rs` into `tests/common/load.rs` so the two tests report alike.
- **The generator: 20 `medium` workspaces over two repositories, writing every 1.5 s, plus `Describe` to make up the rate.** Two `medium` synthetic repositories are registered (`register_synth` twice, different seeds), ten workspaces created on each. A writer task per workspace writes `write-<seq>.txt` with the write time every 1.5 s at an offset of `i × 1.5 s / 20`, which yields 800 snapshot operations a minute (the arithmetic above), 400 per repository thread. A `Describe` task calls `Changes.Describe` on a rotating workspace's change at 3.5 calls a second (210 a minute), alternating repositories, so the operation rate is about 1,010 a minute. The test measures the rate it achieved from the daemon's `operations` index (`Daemon.Status.seq` at the start and end of the steady state, by repository) and reports it; a steady state under 950 operations a minute fails the run as a generator failure, not a gate failure, with the per-repository figure, since a gate passed at a lower rate proves nothing. Two repositories because one APFS repository thread cannot commit 16.7 operations a second (above); the design's target is per daemon, and two threads on ext4 are each a quarter busy.
- **Subscribers: 500 streams, one connection each, in the test process.** 400 `Operations.Subscribe` and 100 `Presence.Subscribe`, each on its own `Client::connect` so no per-connection stream limit applies and the fan-out is 500 sockets, as 500 clients would be. Filters are mixed to exercise server-side evaluation: of the 400, 100 unfiltered, 100 filtered to one repository, 100 to one workspace each (cycling through the 20), 100 to one owner each (the writers use five owner strings). Each subscriber task reads frames and, for every event, records `(seq, kind, event.at, received_at)` into a shared `Vec` behind a mutex, appending only; nothing else happens on the receive path, so the test process cannot be the bottleneck. The test raises its `RLIMIT_NOFILE` soft limit to at least 2,048 before connecting and records the limit before and after, and the daemon's open descriptor count from `/proc/<pid>/fd` on Linux and `lsof -p` on macOS, under `limits`.
- **Latency is `received_at - event.at` on one clock.** `Event.at` is set by the daemon when the broker accepts the event (for an operation, right after `note_committed` on the repository thread; R2.09); `received_at` is `SystemTime::now()` in the subscriber task when it decodes the event. Both are the host's wall clock. The test also records, per operation event, `at - end_at` (how long after the operation's end the broker saw it) so a slow index write shows separately from slow fan-out, and per frame the frame's `to_seq - from_seq` and event count. **The metrics**: p50, p95, p99 and max of delivery latency over the steady state, for all events and split by stream kind (operations, presence) and by filter class; frames per second; events per frame p50 and max; `lagged` frames; and the achieved operation rate. Warm-up (the first 30 s) is excluded from the percentiles and reported separately.
- **The gate: p99 ≤ 100 ms and zero `lagged` frames on `ubuntu-24.04`**, over the steady state, all 500 subscribers, all events. `macos-15` runs the same profile and reports; its result does not fail the job (the repository-thread arithmetic above makes 1,000 a minute on APFS a different test). A run that misses on Linux is re-run against `main` in the same job before the miss is attributed (the Phase 1 lesson); the PR records both.
- **`poll` mode measures what the broker buys.** With `REEF_SUBS_MODE=poll`, each operation subscriber calls `Operations.Log { repo, after_seq, page_size: 500 }` every 50 ms instead of subscribing (presence subscribers still subscribe; presence has no index to poll) and records the same per-event latencies; the daemon runs unchanged. Run at 50 and at 500 subscribers (`REEF_SUBS_SUBSCRIBERS`) with a 60 s steady state; a run that cannot finish 60 s within a 10-minute budget stops and records the subscriber count it reached. The numbers go into ADR 0031's consequences as "what the broker buys" and into `docs/load-tests.md`. No daemon-side flag: a test-only code path in the daemon would measure the flag.
- **What this ticket changes in the broker.** R2.09 ships the broker that works; this ticket makes it hold the number. The measurement runs first on R2.09's code, and the fixes are chosen from what it shows, in this order of likelihood, each landed only if the measurement calls for it:
  1. **Per-subscriber outbound queues and `lagged`.** Each subscription task has a bounded queue (`[events] buffer` events) between the broadcast receiver and the gRPC stream; a slow stream marks its own frame `lagged` and refills from the index, as R2.09 specifies. The test asserts zero `lagged` at the target; if R2.09's implementation shares one queue across streams, this is the first fix.
  2. **Shared frame encoding.** Subscribers with identical filters (the unfiltered 100, the per-repository 100) receive byte-identical frames; encoding each `Frame` once per filter class per tick and handing the `Bytes` to every stream removes 400 of 500 prost encodes per tick. Done only if profiling (`samply` or `perf` on the daemon during the steady state) puts encoding above 10% of the fan-out CPU.
  3. **Filter evaluation cost.** 500 subscribers × about 30 events a second (800 snapshot operations plus their `WorkspaceEvent::snapshotted` twins, plus `Describe`, plus presence) is 15,000 filter checks a second; a `HashSet` per filter makes each a lookup. Done if profiling shows otherwise.
  4. **Frame tick fan-out.** One timer task per subscriber at 50 ms is 10,000 wakeups a second; a single ticker that walks the subscriber list is the alternative. Done if the daemon's idle CPU with 500 subscribers and no events is above 5% of one core (measured, reported either way).
  The broker stays a trait object behind the streams (R2.09), and this ticket adds nothing to its interface except what a fix needs, so Phase 4's store implementation sees the same shape.
- **`load.yml` gains a second job, `subscriptions`**, same matrix, same triggers (weekly, dispatch, pull requests touching either test or the workflow), release build, `timeout-minutes: 45`, uploading `target/load/` as `subs-<os>-<sha>-<run id>`; the Linux job runs as the runner user (no overlay tier is involved; `medium` on the copy backend fits: 20 workspaces × 592 MB is too much, so the job installs `fuse-overlayfs` as `bench.yml` does and `auto` picks it). The `poll` runs are not in CI; they are run by hand once for the baseline and when the broker changes.
- **`docs/load-tests.md` gains "Phase 2: subscriptions"**: how to run, the profile, the gate, the report's fields, the baseline table (M2 Max, the Linux VM on it, both runners), the `poll` comparison, and findings. `docs/dev-phases.md`'s exit criterion is restated from the measurement if it holds, or revised with the number and the reason if it does not, as Phase 1 did for its creation criterion.

## Tests

The load test is the measurement; these are the test's own tests and the broker changes' unit tests, run in the ordinary matrix:

1. `percentiles_are_nearest_rank` moves with `percentile` to `tests/common/load.rs` and stays.
2. `subscriber_sample_latency_uses_one_clock` (unit, in the test file): a `Sample` built from a frame whose `at` is a known timestamp and a `received_ms` from the same clock source yields the expected latency; a sample whose `at` is after `received_ms` (clock skew would show as negative) is recorded as 0 and counted in `negative_latencies`, which the report carries and the gate treats as a failure if it is above 0.1% of samples.
3. `generator_rate_arithmetic` (unit): `Params { workspaces: 20, ops_per_min: 1000 }` yields a write period of 1.5 s and a `Describe` rate of 3.5 a second; `ops_per_min: 500` yields no `Describe` calls and a 2.4 s period (never under `debounce + min_interval`).
4. `lagged_subscriber_refills_from_index` (`crates/reef-daemon/tests/events.rs`, R2.09's file, added if R2.09 did not): a subscriber whose stream is not polled for 5 s while 10,000 events are generated receives, once polled, a frame with `lagged = true` and then every event from its last `seq` on, in order, with no gap and no duplicate.
5. `five_hundred_streams_on_small` (`tests/events.rs`, ordinary CI, `small` preset, 30 s): 500 subscribers over 500 connections, 20 operations, every subscriber receives all 20 within 2 s; the daemon's descriptor count is at least 500 and returns to within 10 of its starting value after the streams close. Proves the shape without the load; `#[cfg_attr(target_os = "macos", ignore)]` only if `macos-15`'s descriptor limit refuses it, with the limit recorded in the PR.
6. `shared_frame_encoding_is_byte_identical` (unit, only if fix 2 lands): two subscribers with equal filters receive equal frame bytes; one with a different filter does not share the buffer.

## Implementation notes

- Build the test around `tokio::time::Instant` for pacing and `SystemTime` for latency; never mix them. `Event.at` is a `google.protobuf.Timestamp`; convert once, with the helper `load.rs` already has for `last_snapshot_at` (`:684-686`).
- Writers must change content (the write time in the file), as `load.rs` learned: an unchanged file is not a snapshot.
- Connect the 500 subscribers with bounded concurrency (16 at a time): 500 simultaneous `connect`s against a Unix socket's backlog (`listen(2)`'s default on Linux is 4,096 since 5.4, 128 on macOS; not verified for tokio's `UnixListener`) would measure the backlog.
- Run the profile on the M2 Max with nothing else running first, release build (`cargo nextest run --release ... --test subscriptions_load`), read the report, and only then touch the broker. Profile the daemon during the steady state with `samply record -p <pid>` on macOS and `perf record -p <pid>` in the privileged container; attach the flamegraph's top ten to the PR.
- `poll` mode's `Operations.Log` call shape is R2.02's; use `page_size: 500` and `after_seq` so a poll never pages.
- The `describer` must not describe a change whose workspace is mid-snapshot in a way that makes the change divergent (ADR 0018: `Describe` rewrites the working-copy commit; the next snapshot of that workspace sees `WorkingCopyStale` with no edits and adopts). Verify in the first run that no workspace shows `divergent` after the steady state; if one does, the describer targets a change with no workspace on it (create 20 extra empty changes with `Changes.Describe` on `new_on main` commits made by a throwaway workspace that is released first).
- The Linux job needs `fuse-overlayfs` (apt) or the copy backend fills the disk; copy `bench.yml`'s install step. Do not run it as root: nothing here needs kernel overlayfs, and the chown step is avoided.
- Timing tests flake under load (the Phase 1 memory): the gate run compares against `main` before the miss is reported, and the PR carries both run ids.

## Out of scope

- A regression gate on the latency numbers (RX.06); this ticket gates the phase criterion only and leaves a machine-readable `pass` and named fields for RX.06.
- Subscriptions over the web and remote listeners (R2.08): the fan-out is the same broker; TLS and gRPC-web framing are measured when R4.19 drives a store.
- Presence at scale beyond 100 subscribers and the daemon's own reports; agents reporting presence at high rates is R4.19's.
- Operations from outside the daemon (`jj` at the root) in the generator; the op-heads watch's latency is R2.09's own test.
- Memory per workspace under 1,000 operations a minute (R1.23's finding stands; the report records RSS).

## Notes from reconciliation

*2026-10-25: the README's Scale row now records the two-repository generator and the APFS commit cost that motivates it; R2.01's schema carries `Daemon.Status.seqs`, `Operations.Log.after_seq`, `Event.at` and `Frame { from_seq, to_seq, coalesced, lagged }` under those names; R2.09's ADR 0031 reserves the dated "Measured" paragraph.*

## Risks

- **The repository thread is the bottleneck before the broker is.** 16.7 commits a second against 10 ms each on ext4 leaves headroom; on APFS it does not, which is why macOS reports and does not gate. If the Linux runner's ext4 commit is slower than the VM's 10 ms (it was 2.9 to 5 s for a 200-write burst on the runner against 1.1 to 2.4 s in the VM, `docs/load-tests.md`), the generator may not reach 950 a minute even over two threads; the rate floor then fails the run with the per-repository figures, and the fix is a third repository, recorded as a measurement, not a gate change.
- **50 ms of the 100 is the frame interval.** A frame boundary in the worst case delays an event by `frame_interval`; p99 therefore has 50 ms for the index write, the broadcast, the encode and the socket. If the measurement shows p99 between 100 and 150 ms with the frame interval the only large term, the lever is `[events] frame_interval` (a `20ms` default is within the design's "batched into frames"), changed with the number in the PR and the README's row updated; the gate is not loosened.
- **500 connections on `macos-15`.** The runner's descriptor soft limit may be low and `setrlimit` may not raise it past the hard limit; test 5 records the limit and the job reports rather than gates on macOS, so this cannot fail the gate, but it can leave the macOS column empty. The report then says why.
- **`Describe` and snapshots on one change race.** A describe between a scan and its commit makes the snapshot's `rewrite_commit` target a commit that is no longer the working-copy commit, which ADR 0018 handles (adopt when no edits, diverge when edits). The describer avoids live workspaces' changes if the first run shows divergence; the arithmetic does not depend on which changes it describes.
- **The test process competes with the daemon for the runner's 4 vCPUs.** 500 tasks appending samples under one mutex is cheap, but 500 HTTP/2 connections decoding frames is not free; if the daemon's CPU is starved, latency rises for a reason the broker cannot fix. The report's `daemon_idle_cpu_pct` and the test's own CPU (from `/proc/self/stat`) are recorded so the PR can say which process was busy.
