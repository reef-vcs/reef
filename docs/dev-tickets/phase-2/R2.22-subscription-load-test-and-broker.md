# R2.22 Subscription load test and broker

Phase 2 · Size L (the row says M; see "Size") · Depends on: R2.10 (`SubscribePresence`, the hub's broadcast, test 12's measurement), R2.09 (the session, its `Source` seam, `LogSource`, `OpEvents`, `Limits`, test 7's measurement), R1.23 and R1.30 (the load test's report, machine and process sampling, `load.yml`) · Unblocks: R4.19 (the store's load test measures delivery through this broker and reuses this generator), R2.18 and R2.20 (live views that open hundreds of streams on one daemon); the phase's exit criterion "500 subscribers at 1,000 operations a minute" is met or revised here

## Context

Phase 2's exit criterion has two halves: a subscriber receives operation log and presence events within 100 ms, "and that holds with 500 subscribers on one daemon at 1,000 operations per minute" (dev-phases.md, Phase 2; design.md, Scale, phase 2's target). R2.09 and R2.10 delivered the first half for one to ten subscribers and left the second to this ticket. design.md (Scale) names the mechanism for the store: "Thousands of long-lived streams need a broker between the operation log and the connections, not database notifications."

Today every operation subscription reads the log itself. When an operation is recorded, every session wakes, and each one runs a blocking read on the pool: the op heads, `walk_after` from its own position, two SQLite queries for snapshot kinds and owners, an effects lookup, and a conversion to `v1::Operation`. At 500 subscribers that is 500 log reads per operation, 8,000 a second at 1,000 operations a minute, through `max(2, cores)` permits. Presence is different: `PresenceHub` stores each change once and broadcasts an `Arc` of it, so its fan-out reads nothing per subscriber.

This ticket builds the load generator first and measures that path, then puts a broker between the log and the sessions: one read per operation per repository into a bounded in-memory ring, with sessions served from the ring and from the log only when they are behind it. It measures again and publishes both runs. The broker lives in its own crate with no jj-lib, so the phase-four store can reuse it as the row asks. The measurement also needs the daemon to accept 500 client connections, which it cannot do safely today (below).

R2.01's rule binds this brief: it implements what R2.01 declared and only adds. It adds nothing to the schema. The frames a subscriber receives do not change.

## Decisions

### Size

L. The row's M fits a generator and an in-process cache. The work under it is wider:

- a generator that opens 1,000 streams over 500 connections and checks every delivery for loss, duplication and order, with stall, reconnect and burst phases;
- a broker crate with eviction, an index of positions, topics that linger and reset, and a criterion bench;
- the daemon's ingest per repository, which has to handle GC, forget, outside rewrites, priming and shutdown the way R2.09's sessions do;
- a source that falls back to the log without changing a frame;
- the descriptor limit and the accept loop;
- an ADR;
- runs on four machines before and after the broker, and the published results;
- about twenty tests.

That is R2.09's breadth, which was L. It is not more than L: there is no schema change, no CLI or MCP work, and the session is unchanged. So it is not split. Splitting the generator from the broker was considered and rejected: the generator's first run (before the broker) is what justifies the broker's design, and the after run is what closes the exit criterion. Two tickets would each need both halves to finish.

### The broker is built, not decided on

R2.09's brief and ADR 0036 left it conditional ("replaces `Feed::read` with its broker if the per-subscriber read cost is what binds"; "R2.22 decides whether 500 need the broker"). The row is not conditional ("Put a broker between the operation log and the streams"), and R4.19 measures "subscription delivery latency through the broker from R2.22". This brief follows the row. Per-subscriber reads cost O(subscribers × operations) in blocking reads and SQLite queries, and concurrent effects misses are computed once per waiting subscriber. A store with thousands of streams cannot work that way, and design.md says so. The before run still matters: it shows what the broker buys and is published beside the after run.

### What the broker is

- **One ingest per followed repository.** When an operation reaches a followed repository, the daemon reads it from the log once, converts it to `v1::Operation` with its effects, and appends it to that repository's ring with the position after it. Sessions read the ring.
- **The broker never changes what a session sends, only where it reads from.** `BrokerSource::read(repo, after, upto, budget)` returns exactly the `Batch` that `LogSource::read` would return for the same arguments over the same log. On a ring hit it serves from memory. On a miss (a position older than the ring, a position the ring never held, or an unprimed ring) it calls R2.09's `feed::read`. Every R2.09 and R2.10 test passes unchanged with the broker on, and a differential test compares the two sources directly (tests 8 and 9).
- **Positions are the frontiers frames already carry.** Each ring entry stores the frontier after it (`Frontier` is `Hash + Eq`, `reef-lib/src/jj/oplog.rs:718`), and an index maps each frontier to its sequence number. A session's position is a frontier, as before: the cursor, `head_operation_ids` and `Position` do not change. A frontier the index holds is a hit; "after it" is the ring entries with higher sequence numbers.

  This is exact. The ingest walks from its own frontier parents-first, so no later entry is behind an earlier entry's frontier. Two walks that have consumed the same downward-closed set of operations stand at the same frontier, because it is that set's maximal elements. A session that reads from the log past the broker's head therefore lands on a frontier the ring holds once the ingest catches up. On the linear log the daemon keeps (it merges concurrent heads on reload), every operation's frontier is `{op}`.
- **In-process first.** The broker is a library in the daemon's process: a mutex-guarded map of rings and a `watch`. There is no broker process or network hop. Phase four's store embeds the same crate behind its own ingest (below).

### Where it sits

```
repository thread ──moved──▶ OpEvents ──changes──▶ Ingest (one task per followed repo)
                                │                      │ walk_after once, Records once, effects once
                                │                      ▼
                                │               reef_broker::Broker<RepoId, Frontier, Delivered>
                                │                      │ ring + index per repo, watch bumped
                                ▼                      ▼
                        (forwarded bump)        BrokerSource: Source ──read──▶ ring hit
                                                       │                    └─ miss ─▶ feed::read (R2.09)
                                                       ▼
                                                 session (unchanged) ──▶ tonic stream
```

- **`crates/reef-broker/`** (new): the generic broker, which depends only on `std` and `tokio`: no jj-lib, tonic, prost or rusqlite, and no Reef crate. `crate_graph` enforces it.
- **`reef-daemon/src/subscribe/broker.rs`** (new): the daemon's adapter. `Delivered` is the ring's item. `Ingest` is the supervisor and one task per followed repository. `BrokerSource` implements `session::Source`, and `broker_summary` writes the per-minute log line.
- **`AppState::broker: Arc<Broker<RepoId, Frontier, Delivered>>`**, built in `Daemon::start` beside `events` (`daemon.rs:329`). The ingest supervisor starts beside `OpEvents::poll` (`:373`) and stops on `AppState::shutdown`.
- **`service/operations.rs`** builds a `BrokerSource` (or `LogSource` when `ring_operations` is 0) and passes it to `session::spawn` (`:551`). It takes each position's `view` from the source, not from `state.events` (`:497`, see "What was verified").

### `reef-broker`: the interface the store reuses

```rust
/// What a ring holds: anything with a weight for the byte bounds.
pub trait Item: Send + Sync + 'static {
    /// Bytes this item costs while held, roughly.
    fn weight(&self) -> usize;
}

/// Bounds; `Default` as in "Limits" below.
pub struct Limits { pub items: usize, pub bytes: usize, pub total_bytes: usize, pub linger: Duration }

/// One appended item and the position after it.
pub struct Entry<P, I> { pub seq: u64, pub item: Arc<I>, pub after: P }

/// Topics `K` (a repository), positions `P` (a frontier), items `I`.
pub struct Broker<K, P, I> { /* Mutex<HashMap<K, Ring<P, I>>>, watch::Sender<u64>, Limits, Stats */ }

impl<K: Eq + Hash + Clone + Send, P: Eq + Hash + Clone + Send, I: Item> Broker<K, P, I> {
    pub fn new(limits: Limits) -> Arc<Self>;
    /// Bumped after every append, start and remove, and by `notify`.
    pub fn changes(&self) -> watch::Receiver<u64>;
    /// One topic's appends and starts only (the store's per-topic wake).
    pub fn changes_of(&self, topic: &K) -> Option<watch::Receiver<u64>>;
    /// A bump with no data: the producer saw something readers must re-check.
    pub fn notify(&self);
    /// Counts a reader of `topic` until dropped; creates the topic unprimed.
    pub fn follow(self: &Arc<Self>, topic: K) -> Following<K, P, I>;
    /// Topics with readers, or lingering after their last one left.
    pub fn wanted(&self) -> Vec<K>;
    /// (Re)starts `topic` empty at `at`: its first position, after a rewrite,
    /// or when the producer cannot continue from its head.
    pub fn start(&self, topic: &K, at: P);
    /// The newest sequence number and position: where the producer reads from.
    pub fn head(&self, topic: &K) -> Option<(u64, P)>;
    /// A version that changes on every append and start, for readers' views.
    pub fn version(&self, topic: &K) -> Option<u64>;
    /// Appends items, each with the position after it, evicting to the bounds.
    pub fn append(&self, topic: &K, items: Vec<(Arc<I>, P)>);
    pub fn remove(&self, topic: &K);
    /// The entries after `after`, up to `upto` or the head, at most `max`:
    /// copies of `Arc`s taken under the lock and filtered outside it.
    pub fn read(&self, topic: &K, after: &P, upto: Option<&P>, max: usize) -> Lookup<P, I>;
    /// Drops topics with no reader for longer than `linger`.
    pub fn sweep(&self, now: Instant);
    pub fn stats(&self) -> Stats;
}

pub enum Lookup<P, I> {
    /// `entries` follow `after` in order; `more` if `max` or `upto` cut them.
    Hit { entries: Vec<Arc<Entry<P, I>>>, more: bool },
    /// `after` or `upto` is not a position this ring holds: read the source.
    Miss,
    /// No such topic, or not primed yet.
    Unknown,
}
```

- **The ring** is a `VecDeque<Arc<Entry>>` plus `index: HashMap<P, u64>` and a base, the position before the first entry (sequence number `first − 1`), which the index also holds. Evicting the oldest entry makes its `after` the base and removes the old base from the index.
- **Filtering is the reader's**, outside the lock. The broker knows nothing of filters, budgets, frames, cursors or gRPC. It holds items and the positions between them.
- **What the store reuses**: `Broker`, `Item`, `Entry`, `Lookup`, `Limits`, `Stats`, unchanged. The store writes its own producer (rows from Postgres instead of `walk_after`) and its own reader (its subscription service). The daemon's adapter is the worked example of both. `changes_of` exists for the store's per-topic wake-ups (R4.19's 1,000 agents across repositories); the daemon does not use it yet (see "Wake-ups").
- **Not in the crate**: presence (below), persistence, cross-process transport. An out-of-process broker for a sharded store is a producer and a reader over a network, a phase-four decision.

### The daemon's item and ingest

```rust
// reef-daemon/src/subscribe/broker.rs
pub(crate) struct Delivered {
    pub(crate) entry: OpEntry,              // for OpMatcher and Frontier::advance
    pub(crate) class: OpClass,              // oplog::classify(&entry), once
    pub(crate) owner: Option<String>,       // the workspace's owner, read at ingest
    pub(crate) effects: Option<OpEffects>,  // for OpMatcher::touches (past the 1,000-entry cap)
    pub(crate) message: v1::Operation,      // exactly what feed::read sends, effects filled
    pub(crate) encoded: usize,              // message.encoded_len()
}
impl reef_broker::Item for Delivered { fn weight(&self) -> usize { 2 * self.encoded + 256 } }
```

- **The supervisor** owns one ingest task per topic in `broker.wanted()`. It wakes on `OpEvents::changes()`, on the broker's topic set changing (a first `follow`), and every 10 s to `sweep`. It starts and stops tasks as topics come and go, and after handling each `OpEvents` change it calls `broker.notify()` once. Forwarding every `OpEvents` change is how sessions still see forgotten repositories, rewrites and newly registered repositories (`follow_repositories`, `apply_rewrites`). Those read `OpEvents`' fields through `BrokerSource::view`. A forwarded wake with nothing due costs a session a version comparison per followed repository.
- **An ingest task** for repository `R` loops:
  1. If `OpEvents::view(R)` is gone, `remove(R)` and end.
  2. If a rewrite is under way (`rewrite_seq` odd), wait.
  3. If `view.rewrites` moved past what the task has seen, `start(R, Frontier::new([last_rewrite.after]))`. A caught-up session's frontier moves from `{before}` to `{after}` in `apply_rewrites` and is a hit on the new base. A session that is rebasing reads up to `before` from the log (a miss), as R2.09 does.
  4. If the topic is unprimed, read the op heads and `start(R, Frontier::new(heads))`.
  5. If `view.version` is unchanged since the last ingest, wait.
  6. Otherwise read: `op_heads(tip)`, then `walk_after(tip, heads, head_position, limits.ring_operations)`. On `truncated`, `start(R, heads)`. On `unreached` or `NotFound` (an outside `jj op abandon` or `jj util gc`), `start(R, heads)` and log at `warn`. Sessions then miss and their log read returns `OPERATION_LOG_REWRITTEN`, as R2.09 does. Otherwise, `Records::of` once for the range, `Reads::effects` for every operation (no `effects_per_frame` budget: one ingest per operation, and the effects are needed by any unfiltered subscriber), `Records::operation` and `convert::effects` exactly as `read_blocking` does, then `append` with each operation's frontier from `Frontier::advance`.

  A read that a rewrite overlapped (`rewrite_seq` changed during it) is discarded, as the session does at `session.rs:388`.
- **The conversion is shared.** `read_blocking`'s per-operation body (records, effects, message) becomes `feed::deliver(state, repo, tip, &records, &operation) -> Delivered`, which both the log path and the ingest call. The log path then applies the matcher and the budget as it does now, so the two paths cannot drift.
- **The ingest runs on the blocking pool without a permit**, through a `Reads::run_unbounded` beside `run_for_write` (`read/mod.rs`, the same `blocking` body). There is one ingest per followed repository, so it is bounded by repositories. It must not queue behind 500 sessions' fallback reads on `Subscriptions::permits`, or every subscriber of a repository would wait for the slowest catch-up. A panic in it is `blocking`'s: the repository's cached reads are cleared, its thread reopens it, and the ingest restarts the topic from the op heads.
- **Ingest batching.** One wake ingests everything new in one walk (up to `ring_operations`), so a burst of outside operations is one read. Frames are still cut by the session: 1,000 operations, 1 MiB, live frames 50 ms apart.

### `BrokerSource`

```rust
pub(crate) struct BrokerSource {
    state: Arc<AppState>,
    matcher: Arc<OpMatcher>,
    log: LogSource,                // the fallback, same state and matcher
}
impl Source for BrokerSource {
    type Follow = (events::Follow, reef_broker::Following<RepoId, Frontier, Delivered>);
    fn repos(&self) -> Vec<RepoId>;               // OpEvents', as LogSource
    fn view(&self, repo) -> Option<RepoView>;     // OpEvents' view with `version` = broker.version(repo)
    fn changes(&self) -> watch::Receiver<u64>;    // broker.changes()
    fn follow(&self, repo) -> Self::Follow;       // both guards: the outside poll and the ring
    async fn read(&self, repo, after, upto, budget) -> Result<Batch, ReadFailure>;
}
```

- **`read` on a hit**: take `broker.read(repo, after, upto, budget.operations)`, then for each entry in order:
  - If `matcher.keeps(&entry.entry, |_| owner)` fails, or the filter names changes and `matcher.touches(effects)` fails, the entry is examined and not kept.
  - Otherwise, apply `bytes` and `first_free` exactly as `read_blocking` does (`feed.rs:151` to `:158`) and clone `message` into the batch.

  The batch's frontier is the last examined entry's `after`. `more` is true if the bytes bound cut the batch or the ring had more before `upto`. `effects_per_frame` does not apply: nothing is computed. A hit is never behind by more than `ring_operations`, which is at most `max_behind`.
- **On `Miss` or `Unknown`**: `self.log.read(...)`, R2.09's path unchanged, counted as a log read. A session whose fallback read passes the broker's head is a hit on its next read, once the ingest appends those operations. It is woken only after that append, because its `view` version is the broker's.
- **`OpMatcher::keeps` takes the classification once.** It calls `oplog::classify(entry)` on every call (`service/op_filter.rs:67`). That is cheap, but run 500 times per operation, so `Delivered` stores the `OpClass` and `OpMatcher` gains `keeps_classified(entry, class, owner)`, which `keeps` calls. `ListOperations` does not change.
- **The broker is on by default.** `subscribe::Limits::ring_operations: 0` selects `LogSource`, R2.09's path, for tests (test 9) and for diagnosis. It is not a configuration-file key, as no `Limits` field is.

### Resume, flow control and memory

- **Resume up to 10,000 back is unchanged.** A cursor or `after_operation` the ring holds is served from it. An older one, up to `max_behind`, is read from the log in R2.09's frames until it reaches the ring's base, then served from the ring. Past `max_behind` it is still `TOO_FAR_BEHIND` (the handler's check at start and `ReadFailure::Behind` mid-stream are untouched). Replay to `H0` is a hit when `H0` is a ring position. Otherwise it is a miss and reads the log: correct either way.
- **Nothing is dropped, and a slow subscriber holds back no one.** Sessions still pull: one channel of one, the slot reserved before the read, so a slow client costs one built frame, the transport's window, and its position. The ring does not keep entries for the slowest reader. Eviction is by bounds only, so a stalled session cannot pin memory or delay anyone. When it reads again it is served from the ring if its position is still there, from the log if it fell off, and fails `TOO_FAR_BEHIND` past 10,000.
- **Frames do not change**: the session cuts them as before.
- **Memory is bounded** by `Limits`:
  - `ring_operations` (4,096) and `ring_bytes` (8 MiB) per repository;
  - `ring_total_bytes` (64 MiB) per daemon, which evicts from the ring holding the most bytes;
  - `ring_linger` (60 s), after which a ring nobody follows is dropped.

  One item is never refused for its size: an operation over `ring_bytes` stands alone in its ring until the next append. Rings exist only for followed repositories, so an idle daemon holds none. A typical operation encodes to 1 to 2 KiB, so 4,096 operations are about 4 to 8 MiB, four minutes at the target rate. Sessions hold `Arc`s only for the entries of one read. Measured in test 12 and in the load test's report.
- **GC, forget and shutdown.**
  - GC: ingest step 3 above. `Reads::clear` already runs.
  - Forget: `OpEvents::removed`, then the supervisor's `remove`, then the forwarded bump, then sessions drop the repository or end `REPOSITORY_NOT_FOUND`.
  - Shutdown: the supervisor and ingest tasks end with `AppState::shutdown`. Sessions already end on it with no reason.
  - A daemon restart starts with no rings. Resumes after it read the log once each, then join the ring: open question 5.

### Wake-ups

Sessions keep one wake-up for every repository: `BrokerSource::changes` is the broker's daemon-wide `watch`. It is bumped after each append or start and by the supervisor's forward. (Implementation: the supervisor forwards an `OpEvents` change only when a repository came or went or a rewrite moved, what sessions read from `OpEvents` rather than a ring, so an operation wakes each session once.) At 1,000 sessions and 17 operations a second that is about 34,000 version comparisons a second, which is negligible next to the reads it replaces. Per-topic wake-ups (`changes_of`) would also spare sessions of other repositories, but they need the session to wait on a set of receivers that changes as repositories come and go. The store needs that and the daemon does not, so the crate offers it and the session is unchanged. The load report records wake-ups per operation from the summary line.

### Presence stays on its hub

`SubscribePresence` does not go through the broker. `PresenceHub` already does what the broker exists for: it stores each change once and broadcasts one `Arc<Change>` that every session filters in memory. No session reads anything per change. Its contract is a set followed by coalesced changes and a resync from state, with no positions (ADR 0037). A ring of positions would add machinery presence does not use and save nothing.

design.md (Scale) says presence "lives in the same broker" on the store. That is phase four's arrangement, where presence crosses daemons, and the crate leaves room for a second kind of topic then (open question 6). Here presence is measured beside the operation log, 500 subscribers with test 12's measurement, as R2.10 promised. The hub changes only if the measurement shows `Lagged` resyncs (counted in the report) or a latency over the gate, and then by its `backlog`, not by moving.

### The daemon accepts 500 clients

- **The `reef-daemon` binary raises its soft `RLIMIT_NOFILE`** in `run_main` (`src/run.rs`), after logging starts and before the runtime does (implementation: `reef_daemon::limits::raise_open_file_limit`, which the load tests call too), to `min(hard, 10,240)` on macOS (`OPEN_MAX`: a larger soft limit is refused there) and `min(hard, 65,536)` elsewhere. It never lowers the limit, and logs `open file limit` with the old and new values at `info`. If it fails, it logs at `warn` and carries on. It uses `nix::sys::resource` (nix's `resource` feature). In-process daemons (`TestDaemon`) do not change their test process's limits.
- **Accepting backs off at the limit.** `daemon.rs` wraps the listener in `Accepting` (in `src/limits.rs`), a stream that on `EMFILE`, `ENFILE`, `ENOBUFS` or `ENOMEM` sleeps 100 ms before accepting again. It logs `accept failed; backing off` at `warn` at most once every 10 s with a count, and yields `Err` only for other errors, which tonic skips as now. Without it a daemon at its limit spins a core inside tonic's serve loop (see "What was verified").
- Not a schema or behavior change for clients. The `limits` section of the load report records the daemon's limit and its peak open descriptors.

They become `reef_broker::Limits`, with `ring_operations` clamped to `max_behind`. None. `reef_api::API_REVISION` stays 5. No field, reason or comment changes: delivery, frames, errors and limits are what R2.09 and R2.10 documented. The CHANGELOG says subscriptions are served from an in-memory broker and that the daemon raises its open-file limit.

### The load generator

A sibling of the Phase 1 load test, not an extension of it and not a criterion bench:

- `load.rs`'s profile builds two synthetic repositories (one `large`) and 200 workspaces with watchers, takes 17 minutes, and gates on write-to-snapshot latency. None of that bears on subscriptions, and adding a phase would make every subscription run pay for it.
- A criterion bench times a closure in one process. This is a minutes-long, multi-process measurement with percentiles over millions of deliveries and correctness checks, which is what the load-test harness already does.
- The broker's in-memory cost per read is a criterion bench as well (`reef-broker/benches/broker.rs`, below): that part is a closure.

**`crates/reef-daemon/tests/subscription_load.rs`**, `#[ignore]`d and a no-op unless `REEF_LOAD=1`, run in release like `load.rs`. What both tests share moves to `tests/common/load.rs`: `Monitor`, `process_usage`, `machine`, `write_report`, `keep_daemon_log`, `percentile`, `utc_stamp`, `millis` and `now_ms`. `load.rs` uses them with no change in behavior or report. Both tests write to `target/load/`, the directory `load.yml` uploads.

**Knobs** (environment variables; `REEF_LOAD=1` is the switch both tests share):

| Variable | Default | |
| --- | --- | --- |
| `REEF_SUBLOAD_SUBSCRIBERS` | `500` | operation-log subscribers |
| `REEF_SUBLOAD_PRESENCE_SUBSCRIBERS` | `500` | presence subscribers |
| `REEF_SUBLOAD_CONNECTIONS` | `500` | client connections; subscriber `i` of each kind uses connection `i mod C` |
| `REEF_SUBLOAD_OPS_PER_MIN` | `1000` | operations a minute driven through the daemon |
| `REEF_SUBLOAD_WORKSPACES` | `20` | writer workspaces |
| `REEF_SUBLOAD_REPOS` | `1` | repositories; writers and subscribers spread round-robin |
| `REEF_SUBLOAD_REPORTERS` | `20` | presence reporters, one report a second each |
| `REEF_SUBLOAD_STEADY_SECS` | `300` | the steady state's length |
| `REEF_SUBLOAD_PRESET` | `small` | the repositories' preset: writes and reads do not scale with the tree (`docs/benchmarks.md`, "Writes (R2.03)") |

**The profile.** One spawned release daemon with the default configuration. The test raises its own soft `RLIMIT_NOFILE` before spawning, as the daemon does, since it opens one descriptor per connection too.

1. **Set up.** Generate and register the repositories. Create `W` workspaces owned by `load@host`. One task heartbeats each workspace every 20 s (`RenewLease`, which records no operation and publishes a `LEASE` entry).
2. **Subscribe.** Open `C` connections (`Client::connect` each), then the subscriptions, 50 every 100 ms:
   - `N` operation subscriptions with no start, each to one repository:
     - 80% unfiltered: a UI, `reef op watch`;
     - 10% filtered to one writer's workspace: an agent's wait tool;
     - 10% filtered to `kinds: [DESCRIBE]`;
   - `P` presence subscriptions, unfiltered.

   Record each subscription's time to its first frame. No operation is recorded during this phase, so every operation subscriber starts at the same head.
3. **Warm up** for 30 s at the target rate.
4. **Steady state**, `STEADY_SECS` at `M` a minute. Operation `k` is due at `t0 + k × 60 s / M` and goes to writer `k mod W`; each writer runs its operations in order, so it never has two in flight. Writers alternate `DescribeChange` of the workspace's `@` and a file write followed by `SnapshotWorkspace`, which records a snapshot with one file in its effects. A writer that starts an operation late records the slip. Reporters replace their `ACTIVITY` entry once a second with a counter in `activity`, under R2.11's contract. Inside the steady state:
   - **stall**, from +120 s to +180 s: 10 unfiltered operation subscribers stop reading, then read again;
   - **reconnect** at +240 s: 100 unfiltered operation subscribers drop their streams and resubscribe at once with their last frame's cursor.
5. **Burst** (recorded, not gated): for 10 s every writer runs operations back to back, which shows the daemon's write ceiling and frames coalescing.
6. **Check and tear down.** Read `ListOperations` for each repository from the subscribers' first head to the end, release the workspaces, and stop the daemon.

**Latency, and from which timestamp.**

- **Operations**: the time a subscriber task gets the frame (`SystemTime::now()` as soon as `Streaming::message()` returns) minus the operation's `ended_at`, the instant jj committed it on the repository thread. This is R2.09's test 7 measurement, on one host and one clock.
- **Presence**: receipt minus the entry's `updated_at`, R2.10's test 12.

Measuring from the writer's RPC call would add the write's own cost, which is not delivery. The report also has receipt minus the writer's RPC return (negative when delivery beats the reply), and the median `GetDaemonStatus` round trip, sampled once a second as a baseline under the same load.

**Correctness of every delivery.** Each subscriber records `(interned id, latency in µs)` for every operation it receives. Ids are interned in one shared map, so 500 subscribers × 6,000 operations take about 24 MB, not 400. After the run:

- every unfiltered subscriber's sequence must equal `ListOperations`' list over its span, oldest first;
- every filtered one must equal `ListOperations` with the same filter;

with these counted and reported per subscriber: `missing`, `duplicated`, `out_of_order`. This covers stalled and reconnected subscribers across their stall and reconnect. Presence subscribers must converge: at the end each one's live set equals a fresh subscription's synced set. States skipped by coalescing are counted, not failed (R2.10: intermediate states may be skipped).

**The gate**, which fails the test:

- Over every delivery in the steady state, operation p99 ≤ 100 ms and max ≤ 2 s. Excluded: stalled subscribers from the stall until they catch up, and reconnecting ones from the drop to their first live frame. Their catch-up times are reported.
- Presence: the same bounds.
- `missing`, `duplicated` and `out_of_order` are 0 for every subscriber.
- The achieved steady-state rate is at least 95% of `M`. Otherwise the run did not test the target, and the daemon's write ceiling becomes the finding.
- No subscription ended with an error the test did not cause.

p99 rather than max is the claim, because a run of 2.5 million deliveries on a shared machine has outliers. The 2 s max catches a stuck stream, as R2.09's tests do (open question 1). The gate is the same on every machine, as `load.rs`'s is (open question 2).

**The report**, `target/load/subscriptions-<os>-<UTC time>.json`, with the daemon's log copied beside it:

- `machine` and `params`.
- `subscribe`: time to first frame, p50, p95 and max.
- `steady.operations` and `steady.presence`: `count`, p50, p95, p99, max and mean, per subscriber class, plus the worst subscriber's p99.
- `deliveries`: `missing`, `duplicated`, `out_of_order`, and per-subscriber detail for any nonzero.
- `frames_per_operation`: how far frames coalesce.
- `stall` and `reconnect`: catch-up times, and the reconnects' first-frame times.
- `burst`: rate achieved and latency.
- `writes`: achieved rate, start slip p95 and max, and the write RPCs' p50 and p95.
- `baseline_rtt_ms`.
- `daemon`: CPU seconds per minute in the steady state, peak RSS, peak threads, open descriptors and their limit.
- `generator`: its own CPU seconds per minute, to tell when the generator is the bottleneck.
- `broker`: the parsed `subscription broker summary` lines, each with `topics`, `items`, `bytes`, `ingests`, `ingest_p50_ms`, `ingest_max_ms`, `ring_reads`, `log_reads`, `resets` and `wakes`.
- `pass`.

The test prints a Markdown column of the headline figures, as `load.rs` does. The summary line is logged once a minute by the supervisor, like the watcher's (`snapshot/mod.rs:93`).

**Durations.** About 8 minutes in all with the defaults: a minute of setup, 30 s of warm-up, 300 s of steady state, a 10 s burst, and teardown. `REEF_SUBLOAD_STEADY_SECS=60` gives a 3-minute run for local iteration.

**Variants recorded once in the PR and in `docs/load-tests.md`, not in CI:**

- `REEF_SUBLOAD_REPOS=4`: whether the daemon-wide wake-up costs anything across topics.
- The before run: this test on the commit before the broker lands (implementation step 1).

### Documentation

- `docs/adr/0038-subscription-broker.md` (accepted). Its outline:
  - **Context**: R2.09's per-subscriber reads, the exit criterion, design.md's store broker, R4.19.
  - **Decisions**:
    1. one ingest per followed repository into a ring;
    2. the broker changes where a session reads, never what it sends (hit or log read);
    3. positions are the frontiers frames carry, indexed;
    4. eviction by bounds only, so a slow reader pins nothing, with linger;
    5. rewrites, outside rewrites and truncation restart the ring, and sessions fall back;
    6. its own crate, generic over topic, position and item, with no jj-lib or gRPC: what the store reuses;
    7. a daemon-wide wake-up forwarded from `OpEvents`, with per-topic receivers for the store;
    8. presence stays on its hub;
    9. the daemon raises its descriptor limit and backs off accepts;
    10. the generator, its gate (p99 within 100 ms, nothing missed, duplicated or reordered) and where results live.
  - **Consequences**: per-subscriber cost becomes a copy and a filter; a ring per followed repository; results published with before and after; per-topic wake-ups and shared encoded frames are the store's next steps.
  - **Alternatives**:
    - a broadcast channel of operations per repository (rejected in 0036: a queue or drops per slow reader);
    - a cache of ranges inside `feed::read` (still a blocking hop, a filter pass and SQLite per subscriber, and concurrent misses compute the same range many times);
    - retaining the ring back to the slowest reader (one stalled client pins memory and, at a cap, holds back everyone);
    - push fan-out with a queue per subscriber (memory per slow reader);
    - a module in `reef-daemon` (no enforced boundary for the store);
    - an out-of-process broker now (NATS or Redis: a dependency for a local daemon; the row says in-process first);
    - presence in the broker (opposite contracts, nothing saved);
    - sharing encoded frames across subscribers (needs a custom codec; measured as not needed at 500);
    - extending `load.rs` or a criterion bench for the generator.

  `docs/adr/README.md` indexes it. ADR 0036 gains under decision 11: "Since R2.22 (ADR 0038) `BrokerSource` serves sessions from a ring and falls back to `feed::read`." ## Implementation notes

- **Order**:
  1. Move the shared helpers to `tests/common/load.rs` and write the generator (test 16). Run it on the code as it is, at the defaults and with `STEADY_SECS=60`, on the M2 Max. This is the before run; it may already fail on descriptors (the next step) or on latency.
  2. The descriptor limit and `Accepting` (test 15).
  3. `reef-broker` with tests 1 to 6, the bench, and test 18.
  4. `feed::deliver` (R2.09's tests pass untouched).
  5. `Ingest` and `BrokerSource`, the handler's `view`, `keeps_classified`, the summary line.
  6. Tests 7 to 14, then every `subscribe`, `presence` and `gc` test.
  7. The after runs on the M2 Max, the Linux VM container, and both runners through `load.yml` on the PR.
  8. Docs and the ADR.
- **Never await a jj-lib future on a tokio worker.** The ingest's read runs inside `spawn_blocking` under `pollster::block_on`, as `feed::read` does. The supervisor and the ingest tasks only await channels, timers and that blocking task.
- **Never hold the broker's lock while converting or filtering.** `read` copies at most `max` `Arc`s out and returns. `append` takes items already built. The lock is a `std::sync::Mutex`, as `OpEvents`' is; do not await while holding it.
- **Bump after the ring changes, never before**, so a woken session always finds what woke it. The forwarded bump for an `OpEvents` change follows the ingest's handling of that change when the ingest is quick. It does not wait for a slow ingest: the ingest bumps again when it appends.
- **`view` must be the broker's version with `OpEvents`' rewrite fields.** `due()` (`session.rs:247`) compares versions, and `apply_rewrites` reads `rewrites` and `last_rewrite`. Do not mix in `OpEvents`' version, or a session can sleep through an append. The handler takes the starting view from the same source.
- **Effects at ingest go through `Reads::effects`**, so a write's response (`effects_of`) and the ingest share the cache, and `Reads::clear` on GC stays correct.
- **The generator's measurement must not be the bottleneck.** Use a multi-threaded runtime with one worker per core. Do nothing in a receiving task but timestamp, intern and push. Do the checking after the run. Report the generator's CPU. If it uses more than half the machine, say so in the findings before reading latency into it.
- **Linux**: nothing here is `cfg(target_os = "linux")` except the `OPEN_MAX` branch in `main.rs` (a `cfg(target_os = "macos")`). Still run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy with and without `--all-features` in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux") before pushing, since `AppState`, `Config` and `tests/common` change under Linux-only test files. Run the generator in that container for the Linux VM column.
- **The disk.** The generator's `small` repositories need little space, but a release build in a second target directory does not. Check `df` before the Linux container run.

## Performance expectations

These are trend data, not gates; the load test's gate is above. Record them in the PR.

- **Before the broker** (step 1), at the defaults on the M2 Max: 500 log reads per operation. `op_range_1` (0.048 ms) plus two SQLite queries and a blocking hop each comes to about 50 to 100 ms of CPU per operation, roughly one core at 17 operations a second. Expect p99 near or over 100 ms when frames queue on the permits. Whatever it is, it is published.
- **After**: one ingest per operation, under 1 ms, plus 500 ring reads at a few µs each. Expect the daemon's CPU in the steady state to fall by an order of magnitude from the before run, `log_reads` per operation to fall from about 500 to under 1, and p99 under 50 ms on the M2 Max.
- `broker/read_1` under 2 µs; `broker/fanout_500` under 2 ms; `broker/append_1` under 5 µs.
- Ring memory at the defaults: 4 to 8 MiB for one repository, from the summary line's `bytes`.
- `create_api/small` (`REEF_BENCH_PRESET=small cargo bench -p reef-daemon --bench workspace_create -- 'create_api/small' --sample-size 10`) before and after: unchanged, since nothing here is on the create path.

## Risks

- **The generator measures itself.** 1,000 streams decoded in one process share its runtime, so receipt times include its scheduling. The baseline round trip, the generator's CPU in the report, and a run with fewer subscribers bound this. If it binds, the next step is several generator processes (open question 7).
- **Small runners.** `macos-15` has 3 vCPUs for the daemon, the generator and 1,000 streams, and Phase 1's load test first failed there for capacity. A failure there is data, not a waiver: open question 2.
- **Timing tests flake under load.** Run the load test alone. The in-process tests' latency bounds are R2.09's, over a baseline measured in the same run.
- **The cap's headroom is 24.** 500 clients on both channels are 1,000 of 1,024 subscriptions. A UI, an `op watch` and a few MCP wait tools beside the target load reach it (open question 3).
- **The ring freezes what the ingest read.** An operation recorded without `reef-agent` whose workspace row is not written yet keeps an empty agent in the ring, so every subscriber and every ring-served resume sees it that way, where a later log read would see the owner. R2.09's live reads have the same race per subscriber, and `ListOperations` shows the owner afterwards. If it shows in practice, the ingest can re-read owners for entries whose workspace had none.
- **One slow ingest delays a repository's subscribers.** An operation whose effects take long (a huge rewrite) holds that repository's ring until it is converted. It held every subscriber's own read before, too. The summary line's `ingest_max_ms` shows it.
- **Two wake-ups per operation per session.** Negligible at 1,000 sessions. At the store's scale, per-topic wake-ups (`changes_of`) are the remedy, and the crate has them.
- **Clock.** Latency is a difference of wall clocks on one host. A clock step during a run corrupts that run; the report's monotonic-clock steady duration beside the wall-clock one shows it.
- **Descriptors elsewhere.** Raising the soft limit helps only up to the hard limit, and a launchd or systemd unit can set a lower hard limit. The log line says what the daemon got.

## Choices this brief made, and why

- **Build the broker unconditionally**: the row and R4.19 require it, and per-subscriber reads cost O(subscribers × operations).
- **Ring hit or log read, never a different frame**: equivalence is testable and the fallback is R2.09's tested path.
- **Frontiers as ring positions**: the cursor, `head_operation_ids` and resume stay as they are, and the index is exact on a graph.
- **Evict by bounds, not by the slowest reader**: a stalled client then costs nothing and holds back no one, and the durable log covers it.
- **Its own crate**: the boundary the store reuses is enforced by the crate graph, not by review.
- **The ingest runs without a permit**: one per repository, and it must not queue behind catch-ups.
- **Presence stays on its hub**: it already fans out without reads, and its contract has no positions.
- **A sibling load test**: subscriptions need none of Phase 1's profile, and a criterion bench cannot run a multi-process measurement.
- **Latency from `ended_at`**: the earliest instant the operation exists, as R2.09 measured.
- **p99 within 100 ms as the gate**: a statistic that survives a shared machine, with a 2 s max for stuck streams.
- **Fix the descriptor limit here**: 500 clients on one daemon is the criterion, and a daemon that spins at 256 connections cannot meet it.

- **R4.19** measures "subscription delivery latency through the broker from R2.22": `reef-broker` unchanged, a store producer and reader in its place, and this generator's shape. Its findings decide per-topic wake-ups and shared encoded frames.

## Open questions

1. **Gate statistic.** p99 ≤ 100 ms with a 2 s max (proposed), or a stricter p999 or max? The design says "each delivered within 100 ms", which taken literally is a max that no shared machine meets. Proposed: p99, and the published table shows max and p999 too.
2. **Do the runners gate?** Proposed: yes, the same gate on every machine, as `load.rs` does. If `macos-15` fails for capacity (3 vCPUs for the daemon, the generator and 1,000 streams), the PR records it and the job uses the generator's `REEF_SUBLOAD_CONNECTIONS` and subscriber knobs scaled to the runner. That would mean a recorded per-runner profile, not a looser gate.
3. **`max_subscriptions`.** It stays 1,024, which the target fits with 24 to spare. Should it be 2,048 now that a subscription costs a position and at most one frame? Proposed: keep 1,024 unless the after run shows the per-session cost is negligible at 1,000. Then raise it in a follow-up with its hint and R2.09's documentation.
4. **Ring size.** 4,096 operations and 8 MiB per repository, 64 MiB per daemon (proposed), or sized by time (five minutes at the observed rate)? Proposed: fixed counts, revised from the load report's `bytes` per item.
5. **Seed the ring on first follow** with the last few hundred operations, so a reconnect storm after a daemon restart is served from memory? Proposed: no. Each resume reads the log once (R2.09's cost, bounded by permits), and the reconnect phase measures that.
6. **Presence in the store's broker.** design.md puts presence "in the same broker" on the store. Proposed: R4.01 decides between a second kind of topic in `reef-broker` (a set with changes and resync, the hub's shape) and the store keeping a hub of its own. Nothing here prevents either.
7. **One generator process or several?** Proposed: one, with its CPU reported. Split only if a run shows the generator, not the daemon, binding.
