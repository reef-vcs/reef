# R2.24 `reef schema`: the CLI and the API as machine-readable schemas

Phase 2 · Size S · Depends on: R2.01 (`reef_api::DESCRIPTOR_SET`, `SCHEMA_HASH`, the `reef_api::json` types), R2.05 (the finished command tree the CLI half describes) · Unblocks: R2.13 (tool definitions and descriptions from the API half), R2.25 (harness packages ship the schemas), R2.06 and R2.07 (their documentation generators read the same descriptors)

## Context

Harnesses turn commands into tools by writing JSON Schema for each one's arguments, and a human writes it today. `reef guide -o json` already lists every leaf command's words (R1.26: `{"guide", "commands": [["ws","run"], ...]}`), which is enough to know the commands exist and not enough to call one. The API side has the same gap: the proto files are the schema, but a Python or TypeScript harness author wants JSON Schema for a message and a description for an RPC without a protobuf toolchain. This ticket gives one command two outputs: `reef schema cli`, the command tree as JSON Schema per leaf command, and `reef schema api`, the daemon's services and messages as a descriptor set or as JSON Schema with the proto comments, both from data the binary already carries (clap's `Command` and `reef_api::DESCRIPTOR_SET`), so neither can drift from the code.

## Decisions

- **One command, two subjects.** `reef schema cli [--command <words>...]` and `reef schema api [--format json|descriptor] [--message <full name>] [--service <name>]`. `reef schema` alone is `reef schema cli`. Both print exactly one JSON value on stdout whatever the terminal (`-o text` is accepted and ignored, like `guide`'s), except `api --format descriptor`, which writes the raw `DESCRIPTOR_SET` bytes (for `grpcurl -protoset`, `buf`, or an SDK's codegen). Both are offline: no daemon is contacted and none is started, so the schema of a build can be read in a container with nothing else installed.
- **`reef schema cli`** returns:

  ```json
  {
    "reef": "0.2.0", "schema_hash": "<blake3 hex>", "draft": "https://json-schema.org/draft/2020-12/schema",
    "globals": [ { "name": "output", "long": "output", "short": "o", "type": "string", "enum": ["text", "json"], "env": "REEF_OUTPUT", "help": "..." }, ... ],
    "commands": [
      { "path": ["ws", "create"], "aliases": [["ws", "new"], ["workspace", "create"], ["workspace", "new"]],
        "about": "Create a workspace and print its path.", "example": "cd \"$(reef ws create -o text --purpose 'fix the parser')\"",
        "args": [ { "name": "repo", "long": "repo", "positional": false, "required": false, "multiple": false, "type": "string", "value_name": "REPO", "help": "..." }, ... ],
        "input": { "$schema": "...", "type": "object", "properties": { "repo": { "type": "string", "description": "..." }, ... }, "required": [...] },
        "output": { "$schema": "...", "type": "object", ... } | null,
        "exit_codes": { "0": "ok", "2": "invalid_argument", ... } }
    ]
  }
  ```

  `args[].type` is derived from the value parser's `AnyValueId`: `String` → `string`; `PathBuf`/`OsString` → `string` with `"format": "path"`; `bool` (`SetTrue`/`SetFalse` actions) → `boolean`; `u8`/`u16`/`u32`/`u64`/`usize` → `integer` with `minimum: 0`; `i*` → `integer`; `Duration` (`humantime::parse_duration`) → `string` with `"format": "duration"` and the description `a humantime span such as 30m`; a `ValueEnum` → `enum` of its possible values. `input` is the same information as a JSON Schema object, one property per argument (positionals by their value name in lowercase), `required` from `is_required_set`, `multiple` as `type: array`; this is what a harness hands a model as the tool's parameters. `output` is the JSON Schema of the `reef_api::json` type the command prints in JSON mode, from a table `fn output_type(path: &[&str]) -> Option<Schema>` in `cli/schema.rs` that names each leaf's type (`["ws","create"] → json::Created`, `["ws","list"] → Vec<json::Workspace>`, `["here"] → here::Inside | here::Outside` as `oneOf`, ...), `null` for commands whose stdout is not Reef's JSON (`ws run`, `tree cat`, `guide`, `completions`, `schema`). The error object every command may print is `error` at the top level: `{ "$schema", "type": "object", "properties": { "error": { kind, message, hint, next } } }`. Hidden arguments (`is_hide_set`) are omitted; `help` is `get_help` as plain text (`StyledStr::to_string`).
- **`reef schema api --format json`** returns:

  ```json
  {
    "package": "reef.daemon.v1", "schema_hash": "<hex>", "api_version": "v1", "draft": "...",
    "services": [ { "name": "Workspaces", "full_name": "reef.daemon.v1.Workspaces", "description": "<leading comment>",
                    "methods": [ { "name": "Create", "input": "reef.daemon.v1.CreateRequest", "output": "reef.daemon.v1.CreateResponse",
                                   "client_streaming": false, "server_streaming": false, "description": "<leading comment>", "implemented_by": "R1.05" } ] } ],
    "messages": { "reef.daemon.v1.CreateRequest": { "$schema": "...", "title": "CreateRequest", "description": "<leading comment>", "type": "object",
                                                     "properties": { "repo": { "type": "string", "description": "..." }, "lease_ms": { "type": "integer", "minimum": 0 }, ... } } },
    "enums": { "reef.daemon.v1.Lease.State": { "enum": ["ACTIVE", "IN_GRACE", "EXPIRED", "ENDED"], "description": "..." } }
  }
  ```

  Messages follow the proto3 JSON mapping: `int64`/`uint64` as `string` with `pattern: "^-?[0-9]+$"` (proto3 JSON writes them as strings; the SDKs' generated code does too), `bytes` as base64 `string`, `google.protobuf.Timestamp` as RFC 3339 `string` with `format: date-time`, `google.protobuf.Duration` as `string` with `pattern` `^-?[0-9]+(\.[0-9]+)?s$`, `google.protobuf.ListValue` as `array`, enums as the value names, nested messages by `$ref` into `messages`, `repeated` as `array`, `map<K, V>` as `object` with `additionalProperties`, a `oneof` as `oneOf` of one-property objects over the members plus the rest. Field descriptions are the field's `leading_comments` trimmed of the `//` and leading spaces; `implemented_by` comes from the method comment's trailing `(R2.xx)` or `// R2.xx` marker R2.01's protos carry, `null` when the RPC is implemented. `--message <full name>` and `--service <name>` filter to one.
- **Where the code lives.** The API half is a library, `reef_api::schema` behind the Cargo feature `schema` (dependencies `prost-reflect` 0.16 and `schemars` 1 with `derive`; `reef_api::json` types get `#[cfg_attr(feature = "schema", derive(schemars::JsonSchema))]`), with `pub fn api_schema() -> serde_json::Value`, `pub fn message_schema(full_name: &str) -> Option<Value>`, `pub fn method_description(full_name: &str) -> Option<String>`, `pub fn methods() -> Vec<MethodInfo>`: R2.13 builds tool input schemas and descriptions from these, and the SDKs' doc generators may call them through a tiny `reef schema api` invocation. The CLI half is `crates/reef-vcs/src/cli/schema.rs` (it needs clap's tree). `reef-vcs` enables `reef-api/schema`; the daemon does not, so it does not compile schemars or prost-reflect.
- **Stability**: the JSON shapes above are part of the CLI contract from this ticket on (ADR 0025's rule 5 applies to field names in them: added, never renamed). `schema_hash` in both outputs lets a harness cache tool definitions per build.
- **No ADR**: this is a presentation of existing contracts; ADR 0029 (the API) and 0025 (the CLI) are the decisions. `docs/api.md` gains a section "Reading the schema programmatically" pointing at the command.

## Tests

1. `cli_schema_covers_every_leaf_command` (`tests/cli.rs`): `reef schema cli -o json`'s `commands[].path` set equals `reef -o json`'s `commands` (R1.26's list), and every entry has `about`, `args`, `input`, and an `output` that is an object or `null`; every `args[]` has a `type` from the fixed set.
2. `cli_schema_types_follow_the_value_parsers` (`cli/schema.rs` unit test): a `Command` built in the test with one argument of each kind (`String`, `PathBuf`, `usize`, `Duration` via `humantime::parse_duration`, a `ValueEnum`, `SetTrue`, a repeated positional) yields the expected `type`, `format`, `enum`, `minimum`, `multiple`, `required`.
3. `cli_schema_output_types_cover_every_json_printing_command` (`tests/cli.rs`): for every leaf whose `output` is `null`, the leaf is in the fixed allow list (`ws run`, `tree cat`, `guide`, `completions`, `schema`, `daemon run`); for every other leaf `output.type == "object"` or `"array"`.
4. `cli_schema_output_matches_real_output` (`tests/cli.rs`): `reef ws create -o json` and `reef ws list -o json` against a `TestDaemon` validate against `schema cli`'s `output` for those commands (with the `jsonschema` crate if adopted; else every key of the real object is a declared property and every `required` property is present).
5. `api_schema_lists_every_service_and_method` (`reef-api/tests/schema.rs`): `api_schema()["services"]` equals the descriptor set's services and methods (R2.01's test 1 list), each with a non-empty `description`.
6. `message_schemas_follow_proto3_json` (`reef-api/tests/schema.rs`): `CreateRequest` has `lease_ms` as `{type: integer, minimum: 0}` (uint64 is an exception? No: uint64 is `string` per the mapping) — the test pins: `uint32` → integer, `uint64` → string with the digit pattern, `Timestamp` → `date-time` string, `repeated` → array, `oneof start` → `oneOf`, enum `Lease.State` → its four names, a nested message → `$ref`.
7. `method_descriptions_come_from_proto_comments` (`reef-api/tests/schema.rs`): `method_description("reef.daemon.v1.Workspaces.Create")` starts with the first sentence of the comment in `workspaces.proto`, read from the file in the test for comparison; a stub method's `implemented_by` is its ticket.
8. `descriptor_format_is_the_embedded_set` (`tests/cli.rs`): `reef schema api --format descriptor` writes bytes equal to `reef_api::DESCRIPTOR_SET`, and `blake3` of them equals the JSON output's `schema_hash` and `reef daemon status`'s.
9. `schema_needs_no_daemon` (`tests/cli.rs`): both commands succeed with `--no-autostart` and a socket path nothing listens on.
10. `help_fits_sixty_lines`, `every_command_completes_with_stdin_closed` (extended for `schema cli`, `schema api`).

## Implementation notes

- Walk clap's tree the way `leaf_commands` does; carry each command's accumulated path and the global arguments (`is_global_set`) separately, so `input` lists a command's own arguments and `globals` the shared ones once.
- `AnyValueId` matching: `parser.type_id() == AnyValueId::of::<PathBuf>()` and so on; `humantime::parse_duration` is a function parser whose type id is `Duration`. A `ValueEnum` is recognized by `possible_values()` being non-empty. Anything unrecognized is `string`, and test 2 keeps the list honest.
- Comments in the descriptor set: build a `HashMap<Vec<i32>, &Location>` per file from `source_code_info.location` once, then look descriptors up by `path()`. Strip each line's leading space (protobuf keeps the space after `//`).
- `$ref` targets are `#/messages/<full name>` within the one document; `--message` output inlines its dependencies under `$defs` instead so the one schema stands alone (what R2.13 and a harness want).
- `uint64`/`int64` as strings surprises people; say so in `docs/api.md` and in the property's `description`.
- `oneOf` for a protobuf `oneof`: `{ "oneOf": [ { "required": ["change"] }, { "required": ["new_on"] }, { "not": { "anyOf": [ { "required": ["change"] }, { "required": ["new_on"] } ] } } ] }` combined with the properties, so an empty oneof is allowed (proto3 lets it be unset).
- Keep `cli/schema.rs` free of `reef_daemon` (the thin-build test from R2.05 applies).

## Out of scope

- Generating tool definitions in a harness's own format (R2.13 for MCP, R2.25 for plugins); this ticket gives them the inputs.
- Validating requests against the schemas at runtime; the daemon validates as it does today.
- Schemas for `reef.toml` or `config.toml` (a `reef schema config` is a cheap follow-up once someone asks).
- A served `/schema` endpoint on the web listener (R2.08 and R2.18 can add one that returns `api_schema()`).

## Risks

- **JSON Schema from clap is lossy.** `conflicts_with`, `requires`, and `--change`/`--new-on` exclusivity are not in the schema; a model may send both and get clap's usage error, which carries the fix. Adding `oneOf` for `ArgGroup`s is possible later; the shape above leaves room.
- **Comments as descriptions make every proto comment user-facing.** R2.01's documentation test already requires one per field; this ticket makes their wording matter. The review reads them as a model would.
- **The `jsonschema` dev-dependency** may not be on the allow list or may be heavy; the fallback checks are weaker but keep the tests honest about key coverage.
