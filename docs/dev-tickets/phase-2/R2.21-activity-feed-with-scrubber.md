# R2.21 Activity feed with scrubber

Phase 2 · Size M · Depends on: R2.12 (`Operations.Replay`), R2.18 (the shell, data layer, harness), R2.09 (`Operations.Subscribe` frames, `Operations.Log` over the index, `Frame.coalesced`, `seq`), R2.19 and R2.20 (the two views this ticket renders in replay mode) · Unblocks: the web UI exit criterion (with R2.19 and R2.20); R3.33 (the inbox's "landed since you last looked" digest is this feed's coalescing over a window); R3.38 (the file browser's time axis reuses the scrubber)

## Context

The activity feed is the design's fifth live view: "the coalesced log with a scrubber to replay any period; also the digest of what happened since you last looked", under the rule "coalesce, never drop: thousands of events a minute are batched into frames and summarized in the feed, and the counts are always right" (`docs/design.md`, "Live by default"). The operation log is complete, so "any live view can be replayed from any point in time" ("Subscriptions"); R2.12 turns that into `Operations.Replay`, and this ticket gives it a handle: a scrubber over the daemon's `seq` that puts the smartlog (R2.19) and the workspaces view (R2.20) into replay mode at any past operation, with a banner that says so and one button back to live.

This is the view that proves R2.09's framing and R2.12's replay to a human. Its two hard parts are coalescing without lying about counts, and scrubbing without flooding the daemon.

### What was verified while writing this ticket

Reef at `d156d1e`; the Phase 2 README's decisions for events, replay and the operation index.

- **Frames** (README, "Subscriptions"): `Frame { events: repeated Event, from_seq, to_seq, coalesced: uint32, lagged: bool }`, framed every `[events] frame_interval` (50 ms) or `frame_max` (500) events; `Event { seq, repo_id, at, payload: Operation | WorkspaceEvent | LeaseEvent | Presence }`. `coalesced` is the daemon's count of events it folded into the frame beyond those listed, so a frame's true event count is `events.length + coalesced`; the feed must add it or its counts are wrong. Presence events never reach the feed (they are not indexed and are not history); the feed filters them out and shows them only in R2.20.
- **`Operation`** (README, "Operations"): `op_id, parents, description, kind (snapshot | create | release | move | undo | describe | abandon | squash | apply | gc | import | external), workspace_id, username, hostname, is_snapshot, external, start_at, end_at, seq, changes`. `WorkspaceEvent { kind: created | snapshotted | released | reclaimed | moved | attention, workspace, op_id }` and `LeaseEvent { kind: issued | heartbeat | expired }` are indexed too. A snapshot therefore appears twice in a frame (the `Operation` and the `WorkspaceEvent { snapshotted }`); the feed shows the `Operation` and uses the `WorkspaceEvent` only to attribute it.
- **The index is the history** (README, "Operation index"): `operations(seq, repo_id, op_id, …)`; `Operations.Log` pages it newest first with `Page`; `seq` is monotone per daemon and the subscription cursor; GC marks rewritten rows `gc_rewritten` and keeps their `seq`, so a scrub position stays meaningful after GC even when the operation id changed. `Daemon.Status` reports the current `seq`.
- **Replay** (README, "Replay"): `Operations.Replay { repo, at: oneof { seq, op_id, time } } -> ReplayState { op_id, seq, at, changes: repeated Change, workspaces: repeated Workspace }`, read on the blocking pool from `RepoLoader::load_at(operation)`; presence is absent. Its cost is a jj view load plus a log, tens to hundreds of milliseconds on `large`, so the scrubber must debounce (below).
- **R2.19 and R2.20** both take `rows` and `live` props and disable holding, actions, disk and presence in replay mode (their briefs' "Replay prop" decisions); R2.18's store has the 5,000-event ring and `lastSeq`.
- **Browser**: `<input type="range">` with `step="1"` over a `bigint`-sized range is fine up to 2^53 (`seq` is a 64-bit integer in proto; JavaScript numbers hold it exactly below 9×10^15, which no daemon reaches), and `requestAnimationFrame` plus a 150 ms trailing debounce is the standard scrub pattern; `history.replaceState` keeps `?at=<seq>` in the URL without navigation (R2.18 already uses it for the token).

## Decisions

- **The feed is rows of coalesced operations, newest at the top, and it never reorders under the cursor.** `ui/src/views/Activity.tsx` reads the store's event ring and `Operations.Log` for anything older than the ring (paged on scroll, 100 per page), filters out presence, and folds events into rows with `coalesce(events) -> Row[]` (`views/activity/coalesce.ts`, pure). A row is `{ key, kind, workspace_id, owner, change_ids, count, first_seq, last_seq, first_at, last_at, ops: op_id[] (at most 50 kept), external }`. Two events fold into one row when they share `kind` and `workspace_id` (or, for operations with no workspace, `kind` and `username@hostname`), their `seq`s are adjacent in the row list (nothing of another key between them), and they are within a 60-second window of the row's `first_at`. `count` includes `Frame.coalesced`: a frame's folded remainder is attributed to the row of the frame's last event (the daemon folds runs of the same kind; R2.09 documents that its `coalesced` events are of the kinds already in the frame) and the row says `≈` when it holds folded events whose individual `op_id`s the client never saw, so a precise count is never faked. The window and the adjacency rule keep the digest honest: "ws 4f2a snapshotted ×37 over 58 s" is one row; a `describe` in the middle splits it.
- **New rows are held at the top**, like R2.19's and R2.20's lists: live frames update the newest row's count in place when they fold into it (the count is the live element here, and it changes with no motion; the row's background tints for 200 ms only when a new row key appears), and events that start a new row are held behind the `Held` badge (`12 new`) until accepted by a click, `r`, or two seconds at the top with the pointer off the list. Accepting inserts the held rows above and the list below does not move (the scroll position is anchored to the first visible row's key). The feed's digest, "since you last looked", is the badge itself plus a `since` marker: the first row accepted in this session is marked and the badge counts from it.
- **Row content**: time (relative, `title` absolute), the kind as a verb (`snapshotted`, `created workspace`, `released workspace`, `moved`, `undid`, `described`, `abandoned`, `squashed`, `applied edit`, `gc`, `imported refs`, and for `external`: `jj: <description>`), the workspace chip (R2.19's component) and the owner, the change(s) touched as reverse-hex links to `/?change=`, the count (`×37` with `≈` when folded), and the `show all` toggle that expands a coalesced row into its individual operations (fetched by `Operations.Log { changes/workspace filter, seq range }` when the row holds more than the 50 kept ids). Every row links to its cause: the newest operation's id opens the operation panel (below), and the owner links to `/workspaces?ws=<id>`. External operations (`jj` at the root) are visibly different (an `ext` tag) because they are the ones no agent explains.
- **Operation panel**: clicking a row's op id (or arriving by `?op=<id>` from R2.19/R2.20) opens a right-hand panel with `Operations.Get`: id, parents (links), kind, description, workspace and owner, host, start and end, `changes` as links, and two buttons: `replay here` (sets the scrubber to this op's `seq`) and `copy id`. Keyboard: `Escape` closes.
- **The scrubber**: a horizontal `<input type="range">` fixed at the bottom of the page, `min` = the smallest `seq` the index holds for the repository (from the first page of `Operations.Log` in ascending order, fetched once; `0` before anything), `max` = the store's `lastSeq`, growing live. A time axis under it with ticks every hour, day or week depending on range (computed from the `seq → at` pairs the feed has loaded, linearly interpolated between known points; the axis is approximate and says so in its `title`). Dragging moves a tooltip (`seq 4,812 · 14:03:22`); the view enters replay when the pointer releases or, during a drag, 150 ms after the last movement (trailing debounce), so a drag across a thousand positions issues a handful of `Replay` calls. Arrow keys step one `seq`; `Shift`+arrows step 50; `Home` is the first `seq` and `End` is live. While a `Replay` is in flight the banner shows `loading…`; a stale response (one for a position the user has left) is dropped by request id.
- **Replay mode is a store flag, not a route.** `daemon.ts` gains `replayAt: { seq, state: ReplayState } | null` and `setReplay(seq | null)`. When set: the smartlog and workspaces routes render `<Smartlog rows={state.changes} live={false} />` and `<WorkspacesView rows={state.workspaces} live={false} />` (their replay props) with a banner across the top of the shell, `Viewing <absolute time> (seq N) · <relative> ago`, in the queued color with a `Live` button and the `?at=<seq>` in the URL; the connection indicator keeps running (frames still arrive, `lastSeq` still grows, the badge still counts) so a reader can tell the fleet is moving while they look back. The activity feed itself stays live in replay mode but highlights the row at or before the replayed `seq` and dims newer rows, so the scrubber position is visible in the list. `Live` clears the flag, restores the live rows (which were kept in the store all along, so there is no refetch), and drops `?at`. A `lagged` frame or a reconnect does not disturb replay; it affects only the live data behind it.
- **Scrub without flooding.** Besides the debounce: at most one `Replay` in flight; positions requested while one is in flight collapse to the latest; results are cached by `seq` for the session (a `Map` capped at 200 entries, LRU) so dragging back over visited positions is instant; the cache is cleared on `lagged` (the index may have been rewritten by GC) and on repository switch.
- **Time to `seq`**: `?at=` accepts a `seq` or an RFC 3339 time; a time is sent as `Replay { at: time }` and the response's `seq` positions the scrubber, so a URL copied from a chat message ("look at what happened at 14:03") works.
- **Empty states**: an index with only the root operation shows one row (`repository registered`) and a disabled scrubber; a repository whose daemon reindexed after GC shows a `history before seq N was rewritten by gc` note at the bottom of the feed, from the first `gc_rewritten` row the log page reports.

## Implementation notes

- Fold on the client with the rules above, but trust the daemon's `coalesced` count: the feed's `count` is `own events + coalesced`, never less. The `≈` is the honest mark for "I know how many, not which".
- The ring in the store holds 5,000 events; the feed's first page is the ring, and `Operations.Log` is consulted only when the user scrolls below it or expands a row whose ops fell out. Merge by `seq`; the index and the ring agree on `seq` because both come from the daemon.
- The scrubber's `max` grows with `lastSeq`; while scrubbing, do not move the thumb under the pointer when `max` grows (set `max` on release). This is the cursor rule applied to a slider.
- `Replay` for `/workspaces` returns rows "as they were" (R2.12); their `lease` has the daemon-computed state as of then, so R2.20's lease label shows it verbatim and the countdown is off in replay mode (R2.20's replay prop).
- Keep the banner in the shell (R2.18's `App.tsx`), not in the views, so navigating between `/` and `/workspaces` while replaying keeps the same position; the `Activity` route is the only one with the scrubber control, but `?at=` works on every route (a shared `useReplayParam` in `hooks.ts`).
- `seqToTime` interpolation can be wrong across a long idle gap (no operations for a week); the axis `title` says `approximate`, and the tooltip uses the real `at` of the nearest known operation when the dragged `seq` has one in the ring or cache.
- The 60-second coalescing window is a constant in `coalesce.ts` with a comment; it is a product choice (a minute of one agent's snapshots is one thought), not a setting.

## Out of scope

- Undo from the feed (R2.03's `Operations.Undo` exists; a UI for it waits for agent-scoped undo, R3.26, so a human does not undo an agent's work with one click).
- Filtering the feed by owner, workspace or kind beyond the links (R3.33's inbox is the filtered view; `reef watch` has the filters for a terminal).
- Replaying presence (it has no history by design) and replaying diffs (R3.38's file browser).
- Exporting or sharing a replay beyond the URL.
- A server-side digest ("since you last looked" persisted per user); Phase 2 has no user identity.

## Risks

- **Coalescing hides the event that mattered**: a `final snapshot` inside a run of watcher snapshots folds into it. Final snapshots have `kind: snapshot` but a distinct description (`reef: final snapshot of workspace …`); the feed splits on `Operation.description`'s prefix for final and shutdown snapshots so they always start their own row. If R2.09 exposes a finer `kind` for them, use it; otherwise the prefix match on the description, as `is_reef_snapshot` does (`crates/reef-lib/src/jj/oplog.rs:95-136`).
- **`Replay` on a `large` repository is slow** (a view load plus a 200-commit log, R2.12's cost): a scrub feels laggy at hundreds of milliseconds per position. The debounce, the in-flight collapse and the cache bound the calls; if R2.12's measurement shows over 500 ms, the banner's `loading…` is the honest state and the next step is R2.12 caching views, not the UI issuing fewer calls.
- **GC rewrites operation ids**: a cached `ReplayState` keyed by `seq` stays valid (rows keep `seq`), but an `?op=<id>` link from before GC can be `NOT_FOUND`; the panel shows the error with the note that GC rewrote history before `seq N`.
- **The 60-second window and the adjacency rule** are a judgment; dogfooding may want a longer window for idle hours or splitting by change. Both are one constant and one predicate in `coalesce.ts`, covered by tests, so a change is a small PR.
