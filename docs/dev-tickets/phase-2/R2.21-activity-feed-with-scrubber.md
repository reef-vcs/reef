# R2.21 Activity feed with scrubber

Phase 2 · Size M · Depends on: R2.18 (the app, the shared operation stream with `reset`, the frame scheduler, the READ-only listener), R2.12 (`ListOperations` and `GetOperation` at and by an operation, `GetOperation` by time, the reads at an operation the other pages use), R2.09 (a stream that drops nothing, its cursor and resets), R2.19 and R2.20 (`?at=` on their pages, `AtBanner`, `RepoNav`, `live/paced.ts`, the scroll anchor, operation ids left as text for this ticket) · Unblocks: none listed (R3.33's digest and held-count bar, R3.37's raw operation log view and R3.38's time axis reuse its window, coalescing and scrubber)

## Context

The design's activity feed is "the coalesced log with a scrubber to replay any period" (`docs/design.md:358`), and its fifth live rule is "Coalesce, never drop. Thousands of events a minute are batched into frames and summarized in the feed, and the counts are always right" (`:348`). Every earlier ticket that touched the operation stream left the summarizing here. R2.09 sends every operation and summarizes nothing: "summarizing a feed with correct counts is the UI's (R2.21) over a complete stream" (ADR 0036, decision 7). R2.12 made every view replayable through `at_operation` and left the scrubber, the counting and any aggregate RPC to this ticket (ADR 0046, decision 9). R2.19 and R2.20 read their pages at `?at=<operation>` and left "everything that picks the point" here, with their operation ids as text until this ticket gives operations a route.

Everything the feed needs is served. `ListOperations` lists the log newest first, from the heads or from an operation, in pinned pages. `GetOperation` returns one operation with its effects, by id or by time. The shared stream delivers every operation once, in frames, and resumes from a cursor. What is missing is the view, and four definitions:

- what a feed row is, so a busy fleet reads as a story and not as 1,000 snapshots a minute;
- what "the counts are always right" means for a page that joins a list it read to a stream that keeps arriving, across reconnects, resets, handovers between tabs, reloads and garbage collection;
- what the scrubber is, where it lives, and how it moves the other pages;
- how a long log is bounded in the browser.

This brief proposes no API change. Every RPC the feed and the scrubber call exists and is `ACCESS_READ`.

### What was verified while writing this ticket

## Decisions

### Size

M, at the top of M. The ticket is web-only apart from one daemon test and the reef-web budget test, with no schema, daemon source or CLI change. The work:

- `log/window.ts`, the per-repository window of operations: one list read joined to the stream, older pages, resets, a point;
- `log/coalesce.ts` and `log/counts.ts`, both pure;
- the scrubber;
- the activity page and its operation pane;
- a repository header in the shell (the nav and the scrubber), which the smartlog and the workspaces page then use;
- links from four places;
- the app split into one chunk per page, with its loading and failure states and a budget measured per page (decided by the user, 2026-11-01);
- about ten tests, a property test, a daemon test, a smoke-test step and docs.

That is R2.20's shape: one model, one page, one shared component, links, plus the split, which adds about a fifth. The cut line, if it runs long, is "Go to time" (the scrubber's time field), which is a convenience over stepping and dragging. It stays in, because it is R2.12's time lookup's first caller.

### One page per repository, and a scrubber on every repository page

- **`/repos/<repo>/activity`**, titled "Activity". `<repo>` is anything the API accepts, as for the other pages. Its query parameters are `op` (a selected operation's id or prefix) and `at` (the point), both optional.
- **A repository header** in the shell (`ui/RepoHeader.tsx`) heads the three repository pages: the nav "Smartlog · Workspaces · Activity" and the scrubber below it. The pages stop rendering `RepoNav` themselves. Activity is appended, so the existing links keep their places.
- **The scrubber moves the page you are on.** On the smartlog it moves the smartlog to `?at=`, on the workspaces page the workspaces page, on the activity page the feed. A point is one operation, the same on all three, and the nav keeps it across them (R2.20 already carries `at` across the two).
- **The header is keyed by the repository only**, outside the pages' `key`, so the scrubber's window survives moving between the three pages and moving `at`. Leaving the repository pages, or changing repository, stops it.

### The window: what the browser holds

`web/src/log/window.ts` holds, per repository, a **contiguous window of the log from the head down**: every operation of the repository from the newest down to a bottom, each once. The feed, its counts and the scrubber are all derived from it. The window holds compact records, not protobuf messages: `id`, `parentIds`, `endedAt` (milliseconds), `kind`, `snapshotKind`, `workspaceId`, `jjWorkspace`, `agent`, `username`, `hostname` and the description's first 200 characters. It never keeps effects or attributes, so a stream operation and a listed one make the same record. The operation pane reads those by `GetOperation`.

- **The first read** is `GetRepository { repo }` for the full id, since the stream carries full ids and the route may name a prefix or a path.
- **Nothing is listed before the stream is live.** Once it is, the window subscribes to `OperationStore` and then reads `ListOperations { repo, page_size: 1000 }` (no effects). Every batch keeps only operations whose `repo_id` is the repository.
- **The join is by operation id.** Stream operations that arrive while the list is in flight are held and merged when it answers. An operation in both is kept once.
- **Why the join is exact.** The window subscribes before it lists, so every operation recorded after the stream's position at that moment is in a later batch, including operations in a batch the store has received and not yet delivered. Every operation at or before that position was recorded before the list was read, so it is in the list. So nothing falls between the two. A follower tab's position is the leader's at its welcome, and the same argument holds. Duplicates (an operation in both, a frame replayed after a handover or a reconnect) collapse on the id. Test 1 checks the daemon side of this argument, and test 4 checks the window under every interleaving.
- **Order.** The window is ordered as `ListOperations` orders it, newest end first, with ties broken by id descending. A stream operation is inserted at its place, which is almost always the top. Ordering by content rather than by arrival is what makes a reload give the same rows as a live session.
- **Older pages** ("Load 1,000 older") follow the first read's page token, with the heads it pinned, so concurrent op heads are paged correctly. One read is in flight at a time, through `Paced.requestNow`.
- **The cap is 10,000 operations**: R2.09's resume horizon and the store's `PENDING_LIMIT`. "Load older" is offered until the window holds 10,000. While live operations push the window past the cap, the oldest are dropped from the bottom, and the bottom's time moves up. At Reef's own rate that is more than a week of history; at the phase's peak of 1,000 operations a minute it is 10 minutes. The page says how far back it holds ("Loaded back to 14:03:22 · 10,000 operations, the most this page holds"), and gives the CLI command for older history.
- **The root operation** ends the log. When a page reaches it, it is not a record. The window marks "the start of the retained log" instead, and the page shows that marker below the last row ("Start of the retained log: garbage collection keeps the undo window, 7 days by default"). It is never counted, and it has no place on the time axis, since its time is the epoch.

#### Resets, reconnects, reloads and garbage collection

- **A reconnect** resumes the stream from its cursor (R2.09). The replayed operations are new to the window, or collapse on their ids.
- **A reset** (`batch.reset`: `TOO_FAR_BEHIND`, `OPERATION_LOG_REWRITTEN`, a refused cursor, or a hidden tab past `PENDING_LIMIT`) means the stream skipped operations. The window does not try to patch the gap. It discards its records, waits for the stream to be live again, and reloads from the head down to the old bottom's time (pages until a page reaches an operation that ended at or before it, within the cap). The selection is kept when its id is still there. A note says "The operation stream started over; the feed was reloaded at 14:03:22."
- **A reload of the page** builds the window afresh from the list. Because rows are a pure function of the ordered records, it shows the same rows and counts that the live session showed for the same operations (test 4).
- **A GC** moves the stream across its rewrite with no reset and no frame, so the stream's later operations are children of the rewritten head, whose id the window does not hold. Kept as it is, the window would join two copies of the log by nothing: the feed at a point (ancestors by `parentIds`) would stop at the rewrite and miss every pre-GC operation. So **an applied operation naming a parent the window does not hold starts the window over**, as for a reset: a fresh list returns the kept operations under their new ids, and merging the two copies would count them twice. Below a full window's bottom a missing parent is expected only for the bottom record itself, never for a new operation, so the rule fires on the first post-GC operation, not on a later page. A later page token or a point that hits the rewrite (`OPERATION_LOG_REWRITTEN` or `OPERATION_NOT_FOUND`) starts over the same way, for a GC followed by no new operation. The note says "Garbage collection rewrote the operation log; the feed was reloaded." A selection by a pre-GC id is cleared.

### What a row is: coalescing

`web/src/log/coalesce.ts` is a pure function from the window's ordered records to rows. Each operation falls in one of three classes:

- **Work**: `SNAPSHOT` (any snapshot kind) and `EDIT` operations recorded for a Reef workspace (`workspace_id` set). Key: workspace id and agent.
- **Outside jj**: `EXTERNAL` operations, which have no agent (all 464 in Reef's log). Key: the jj workspace name and `username@hostname`.
- **Events**: every other kind (`CREATE_WORKSPACE`, `RELEASE_WORKSPACE`, `MOVE_WORKSPACE`, `DESCRIBE`, `ABANDON`, `UNDO`, `IMPORT_REFS`, `OTHER`, `UNSPECIFIED`), and any operation with more than one parent (a merge of concurrent operations), whatever its kind.

Walking the records oldest first:

1. **An event is a row of its own.** It closes every open run in its place: the workspace id, or the jj workspace for one without a Reef workspace. So a workspace's story reads "created · 12 snapshots · described · 30 snapshots · released".
2. **A work or outside operation joins the open run with its key** when that run's newest operation ended no more than 5 minutes (`RUN_GAP_MS`) before it, and no event in its place came between. Otherwise it starts a new run. Operations of other keys in between do not break a run, so two agents snapshotting at once make two rows, not a row per alternation.
3. **Rows are ordered by their newest operation**, newest first, ties by id, as the window is. A row's key for React is its oldest operation's id, which does not change as the run grows at the top.

A run at the window's bottom may continue below it. Its count is of the operations in the window, which is what the page says it holds. The rule needs nothing but the records, so it is the same in the stream and the list, live and after a reload. Effects are never consulted, so a row never depends on whether an operation came with effects.

Why this unit: an agent's snapshots in its workspace are its work in progress, and the 5-minute gap separates sessions of work (the data above: 619 rows for Reef's 3,215 operations, against 932 with snapshots alone). Every event is something a person asks about ("who released it, when"), so none is folded. A workspace's whole lifecycle as one row was considered and rejected: a long-lived workspace's row would hide its moves and describes, and would rise to the top on every snapshot. Fixed time buckets were rejected too: a run that crosses a boundary splits for no reason the reader can see. The gap was decided with the user ("Decisions taken", 1).

### What each row shows

All text is plain text, never HTML (S-33). Times are absolute: `14:03:22`, with RFC 3339 in `title`, and `2026-10-31 14:03` when the row's date differs from the newest operation's date in the window. No clock is read, so "today" is never used. Ids are 8 characters, with the full id in `title`.

The feed is a `<table>` with caption "Activity":

| Column | Shows |
| --- | --- |
| When | The newest operation's time, or "14:03:22 to 14:10:05" for a run. |
| What | For a run: "37 snapshots", "12 snapshots, 3 edits" or "8 jj operations", with the snapshot kinds in `title` ("35 watcher, 2 explicit"), or the first three descriptions for jj operations. For an event: its `operationLabel`, then the description's first line in secondary text, cut to one line. The cell's text is the link that selects the row (`?op=<its newest operation>`, followed with `replaceState`). |
| Who | The agent, as a link to the workspaces page with it selected (`fleetHref({ repo, agent })`). For outside operations, `username@hostname` as text. `-` when neither is known. |
| Where | The workspace id, as a link to the workspaces page with it selected, kept at the point when the feed is at one. Or the jj workspace's name as text (`default`). |
| Ops | The row's count, right-aligned. |

Above the table, **the summary** counts the period shown: "3,215 operations from 2026-10-24 17:04 to 16:39:36 in 619 rows · 2,489 snapshots · 464 jj · 131 creates · 130 releases · 1 ref import · 4 agents · 133 workspaces". Kinds with zero are left out. "Agents" counts distinct non-empty `agent` values. It is text, not filters.

Beside it, **the command** lists exactly the same operations: `reef op log --repo <id> --at-op <newest id> --limit <n>`, where `n` is the window's operation count (plus one when the root was reached, since the CLI lists it), with a copy button. That is how a person, or an agent, checks the counts with one call (the design's rule that the interface shows nothing the API cannot).

Below the last row: "Loaded back to `<time>`" and "Load 1,000 older", or the root's marker, or the cap's note with `reef op log --repo <id> --at-op <oldest id> --limit 0` for everything older.

### Counts that are always right

"Right" means, at every render:

1. **Each row's count** is the number of operations in the window that the rule put in it.
2. **The summary's counts** are counts over every operation in the period shown: from the bottom of the window up to the point, or up to the newest operation shown when live.
3. **The held count** (below) is the number of this repository's operations the window holds above what the table shows.
4. **Each scrubber bar's count** is the number of the window's operations whose `ended_at` falls in its bucket.
5. **They agree**: the rows' counts sum to the summary's total, and the total plus the held count is the window's size. Each operation is counted once, however it arrived.

Each count is a count over the window, and the window holds each operation of its period exactly once (above). So the counts are right by completeness, as ADR 0046 decision 9 planned. No aggregate RPC is needed while a period fits in 10,000 operations (R2.12 left one to this ticket "if its measurement needs one"). Tests 3 and 4 check the five statements against a fake log. Test 10 checks the total against `reef op log` on a real daemon.

### Nothing reorders under the cursor: new rows wait

A run that gains an operation moves to the top, and new rows push the table down. Both are reorders, so:

- **Following**: while the table's first row is in view and focus is not inside the table, each batch applies at once. New rows take R2.18's `changed` transition once. A count that grows does not move or flash.
- **Reading**: once the first row scrolls out of view, or focus enters the table (a link or the selection), batches are held. A bar above the table reads "`<n>` new operations · Show" (a `<button>`), and the table, the summary and the counts stay as of the last operation applied. That is a consistent point, and the counts are right for it. "Show" applies everything held and scrolls to the top. Scrolling back to the top with nothing focused applies them too.
- **The scroll anchor** (`ui/scroll-anchor.ts`) keeps the selected row, or else the first row in view, in place when held batches apply or older pages arrive at the bottom.

R3.33's inbox takes the same rule ("New items arrive behind a visible count you accept"). Holding only while reading was decided with the user ("Decisions taken", 6).

### The scrubber

`web/src/ui/Scrubber.tsx` is a control over the window's operations, in the repository header of all three pages.

- **Stops.** Each operation in the window is a stop, ordered as the window is, and "Live" is a stop after the newest. A stop is a point: `?at=<operation id>`, which moves the page you are on. Live removes `at`.
- **The track** is a time axis from the window's oldest operation to its newest. It is not "now": no clock is read, so an idle repository's track does not creep. It shows up to 120 bars of operation counts. The bucket width is the smallest on the ladder 1 s, 10 s, 1 min, 5 min, 15 min, 1 h, 6 h, 1 d that keeps the window within 120 buckets. Buckets are aligned to multiples of their width (UTC), so a new operation in the newest bucket grows one bar, and the bars shift only when a new bucket starts. Heights are linear in count, the tallest bar's count is labelled, and each bar has its range and count in `title`. The bars are `<div>`s with `aria-hidden`; the slider carries the text. No chart library.
- **The handle** sits at the point's time, or at the right end with "Live". The label beside the track says "Live", or "`abcd1234` · snapshot (watcher) · `<agent>` · 14:03:22 · 1,203 of 3,215".
- **Keyboard.** The scrubber is one `role="slider"`, with `aria-valuemin` 0, `aria-valuemax` the number of stops minus one, `aria-valuenow` the point's index, and `aria-valuetext` the label. Left and Right step one operation older or newer. PageUp and PageDown step one bucket. Home goes to the oldest operation loaded. End goes to Live. Right from the newest operation is Live, and Left from Live is the newest operation, frozen.
- **Pointer.** Pressing or dragging on the track previews the newest operation that ended at or before the pointer's time, in the label and the handle. Releasing commits it.
- **Committing.** A burst of steps is one navigation: the URL changes 250 ms after the last step (`after`, the one delay this ticket adds), or at once on release, End or Enter. So holding an arrow key does not remount the smartlog thirty times a second. The first move away from Live pushes a history entry, and later moves replace it, so Back returns to live. The rest of the query string (the smartlog's revset, a selection) is kept.
- **Go to time.** A `datetime-local` field (seconds) and "Go". A time inside the window resolves in the browser to the newest operation that ended at or before it. A time outside it reads `GetOperation { repo, ended_at_or_before }` once. The errors are the daemon's, shown with `hint` and `next`: `TOO_FAR_BACK` and `OPERATION_NOT_RETAINED` with its oldest time.
- **A point outside the window** (an old link, an old time) is first looked up with `GetOperation { repo, operation_id }`. The window then loads older pages until it holds the point, within the cap. Past the cap, the point is detached: the handle sits at the left edge, marked "older than the loaded period", Left steps to the point's first parent (from `GetOperation`), Right is disabled, and End returns to Live. The feed at a detached point reads `ListOperations { repo, at_operation, page_size: 1000 }` once and coalesces that page, labelled "1,000 operations ending at this point, not joined to the loaded period".
- **No autoplay** in this ticket (decided with the user), and no second stream. R2.12 planned play as `SubscribeOperations` with `after_operation`. The window already holds every operation from the head down, live, so stepping forward needs no stream, and R2.18's rule of one stream per browser holds.
- **Views re-read at each point.** The smartlog and the workspaces page remount at each committed point and read at it, as they do now. R2.12's stepping by applying effects is not used: their models stay as R2.19 and R2.20 wrote them, a read at an operation costs what a read at head does (`load_at_shared`, 0.017 ms), and the 250 ms commit bounds the rate.

### The feed at a point

- **At X inside the window**, the feed shows X and its ancestors in the window (from `parentIds`), which is what `ListOperations { at_operation: X }` lists (ADR 0046, decision 9). With one op head this is every operation at or below X. With concurrent heads it leaves out the other branch's operations, as the API does (ADR 0046, decision 8). The feed computes it with no read, the counts are of that set, and the command reads `reef op log --repo <id> --at-op <X> --limit <n>`.
- `AtBanner` heads the page, as on the other two. Its operation id becomes a link to the feed with that operation selected (`activityHref({ repo, op: X, at: X })`), on all three pages.
- **Held batches** do not apply at a point. The window keeps growing above it, and the track gains bars at its right end.

### Selecting an operation

A row's link selects its newest operation (`?op=<id>`). A pane beside the table at 900 px and wider, and a bottom sheet when narrower, reuses the smartlog's pane CSS (`aside`, `aria-label="Selection"`, `aria-live="polite"`):

- **For a run**: its operations, newest first, up to 50 then "and `<n>` more", each with time, kind and short id, each a link selecting it.
- **For the selected operation**, from `GetOperation { repo, operation_id }`, with answers cached for the 64 most recent ids:
  - the kind, the full id with a copy button, and started and ended times;
  - the agent and the workspace as links, or the jj workspace; the host and user; the remote caller's token name when set (R2.08);
  - the description, full, `pre-wrap`, as text;
  - its parents, as links selecting them;
  - its effects: changes with their kind in words (created, rewritten, abandoned, hidden) and reverse-hex ids linking to the smartlog with the change selected, at this operation, or at its first parent for an abandoned change; bookmarks (`name@remote`, from and to, conflicted); working copies (workspace links, or "added" or "forgotten"); "and `<n>` more" when `change_count` or `bookmark_count` is more than the list holds; nothing about tags (#138);
  - the attributes as `key = value` text;
  - "Open at this operation": the smartlog, the workspaces page and this feed, each with `at` set to it;
  - `reef op show <id> --repo <repo>` with a copy button.
- **An `op` the window does not hold** is read with `GetOperation` all the same. The pane shows it with "Not in the loaded period" and "Show the feed at this operation". An unknown one shows the daemon's error.

### Links to operations

Row `title`s stay text. The smartlog's rows are listbox options, which cannot hold links (R2.20's finding).

### Accessibility and keyboard

- The feed is a `<table>` with a caption and `<th scope="col">` headers. Rows hold several links, so they are not listbox options, as in R2.20. The selected row has `aria-current="true"` and a 2 px `--focus` outline.
- The scrubber is one slider with a text value. Its bars are hidden from assistive technology, and its "Go to time" field and "Go" button are labelled. The held bar is a `<button>` whose name includes the count. The pane announces its heading.
- Nothing is color alone: kinds are words, and operations have no state color, since they are not objects with a state (ADR 0047, decision 11). Only R2.18's tokens are used, so `tokens.test.ts` covers every color. No token is added.

### The bundle: one chunk per page (decided by the user, 2026-11-01)

Main's JavaScript is one 471,967-byte chunk, so every page loads every page's code. This ticket adds 25 to 32 kB of view code and R3's views add more, so the app is split by route here rather than the budget raised again.

- **What splits.** The entry chunk keeps the shell: `App`, the router, the header and its connection indicator, the live layer, the connection, the session, errors, the overview (`/` is the page `reef ui` opens), `NoSession` and `NotFound`. The smartlog, the workspaces page, the activity page and `/states` each load by `import()` behind `React.lazy`. So does the repository header with the scrubber and `log/`, as one module the shell loads for the three repository routes, so the overview never loads them. Rollup puts code shared by several lazy modules (the pane CSS helpers, `paced.ts`, shared descriptors) in shared chunks on its own; no `manualChunks` unless the PR's measurement calls for them. The generated descriptors go where they are imported.
- **One helper**, `ui/lazy-route.tsx`, wraps each `import()`: a `<Suspense>` inside `main`, so the header and footer stay, with "Loading the page." as the fallback, and an error boundary for a failed load.
- **A chunk that fails to load.** Chunk names are content hashes, served `immutable`. After a daemon upgrade, an open tab's entry names chunks the new daemon does not embed, so the first visit to a page not yet loaded gets a 404 from `import()`. The helper shows an error, never a blank page: "This page's code could not be loaded. If the daemon was updated, reload the page.", with a Reload button (`location.reload()`). A network failure shows the same. Vite's `vite:preloadError` event is not used for an automatic reload, which could loop.
- **No preloading** on hover or idle in this ticket. Chunks come from the loopback listener and are cached after the first visit; the PR measures the first visit's delay, and preloading is a follow-up if it is noticeable.
- **The budget measures what a page loads**, not what is embedded. `build.manifest` writes `.vite/manifest.json` (a few kB of public file names, embedded and served like any file). `bundle_budget` reads it and, for each route, sums the entry chunk and every chunk its lazy import pulls in through static imports: each must be at most 500 KiB, the same number as before. The 600 KiB cap on all assets stays as the guard on what the daemon embeds; with every chunk counted, main plus this ticket is about 515 kB of it. `index.html` still links exactly one script, the entry.
- **The CSP** is unchanged: chunks are files under `assets/`, which `script-src 'self'` allows, and Vite's dynamic imports need no inline script (`modulePreload.polyfill` stays off).

### The API: no change

| RPC | Access | Where | At an operation |
| --- | --- | --- | --- |
| `RepositoryService.GetRepository` | READ | once per window, for the full id | not needed |
| `OperationService.ListOperations` | READ | the first page, older pages, the reload after a reset, a detached point's page; never `include_effects` | `at_operation` for a detached point |
| `OperationService.GetOperation` | READ | the selected operation, a point outside the window, a prefix; by time for "Go to time" | by id or `ended_at_or_before` |
| `SubscribeOperations` | READ | R2.18's shared stream | not used |

All are `ACCESS_READ`, so no gate rule changes. Candidates considered and rejected:

- **An aggregate RPC** (counts per kind, agent or bucket over a period). R2.12 left it to this ticket's measurement. A period of up to 10,000 operations costs one to ten list pages and microseconds of counting in the browser. The PR measures the deepest page. If periods past the cap are wanted (a day at the phase's peak), an `OperationService.CountOperations` with buckets is the follow-up, with API revision 15.
- **A per-repository frontier on the shared stream**, to anchor the list to the stream without the id join. The stream follows every repository and has no frontier then (`head_operation_ids`). The join by id is exact without one.
- **Effects in the list**, for rows that name changes. Every listed operation would cost an effects computation, and rows would differ between stream and list unless both carried them. Rows name the agent and the workspace, and the pane names the changes.
- **A time index** (R2.12's open question 1). The scrubber steps through the window it holds, and only "Go to time" outside the window walks the log. The PR measures that walk; R2.12's recommendation, to revisit with a measurement, stands.

### The threat model

S-33's mitigation gains one sentence: the activity page's URL parameters (`op`, `at`) are input a link can set, and reach only `GetOperation` and `ListOperations`. Operation descriptions, attributes, agent names, jj workspace names and remote token names come from any jj client and any caller's `reef-agent` metadata, and are rendered as text. No new row: the page reads what any session may read (S-34). A READ session could already page the whole log. The page bounds what it asks for: one list read in flight, 10,000 operations, and one `GetOperation` per selection or point.

## Performance expectations

Trend data, not gates, recorded in the PR (M2 Max, Chrome):

- **The first load**: `ListOperations` of 1,000 without effects on `medium`, and its bytes on the wire. Expected: about 16 ms in the daemon and about 0.5 MB.
- **Older pages**: the 10th page (9,000 skipped). Expected: under 200 ms, since tokens re-walk. If the 10th page passes 500 ms, the follow-up is a page token that resumes from its last operation when the log is linear.
- **Coalescing and counting** 10,000 records. Expected: under 8 ms. **React's commit** for 200 rows on a batch: under 16 ms.
- **Memory**: the heap with 10,000 records. Expected: under 15 MB.
- **A scrubbed step on the smartlog**: commit to rendered, on `medium` and `large`. Expected: under 100 ms on `medium`. This is the "real scrubbing" R2.12 left to this ticket (its `scrub_step` bench was not written).
- **"Go to time"** 1 hour and 1 day back on Reef's own repository, and 100,000 operations back on `large`, against R2.12's `TOO_FAR_BACK` bound.
- **The daemon's cost of an open feed** under R2.22's generator: no reads per operation beyond the shared stream. That is zero, unlike the smartlog and the workspaces page, which re-read per batch.
- **The bundle.** This ticket's code: 25 to 32 kB raw (8 to 10 kB gzip), all view code, with no dependency and no new descriptor. The PR records, before and after the split, the entry chunk and each route's total (the number `bundle_budget` checks), all JavaScript, and the first visit's delay to a lazy page on the loopback listener. Expected: the entry somewhat under main's 472 kB, since the smartlog, workspaces and states pages leave it, and every route well under 500 KiB.

## Inherited scope

- **From the design**: the feed is "the coalesced log with a scrubber to replay any period"; "Coalesce, never drop ... the counts are always right"; nothing reorders under the cursor, with new items behind a visible count; every live element links to its cause; never fetch on a timer.
- **From R2.09 and ADR 0036**: "R2.21 summarizes frames into the activity feed and owns 'counts always right' on a stream that drops nothing"; no server-side coalescing or summary frame; resets on `TOO_FAR_BEHIND` and `OPERATION_LOG_REWRITTEN`; GC moves subscriptions without a reset.
- **From R2.12 and ADR 0046**: the track is `ListOperations` pages (with `at_operation` for a point outside the window); jumps by `GetOperation` by time; steps are adjacent operations; "it coalesces and counts over complete pages", with an aggregate RPC only if its measurement needs one; "R2.21 measures real scrubbing" (the unwritten `scrub_step` bench, and open question 1, the time index); clients keep each point's time; concurrent heads shown as they are. This ticket departs on play (no `after_operation` stream) and on stepping by effects (views re-read). See "Choices".
- **From R2.18 and ADR 0047**: routes under the router and views under `views/`; `live/` operations with `reset`; one stream per browser; no timers but `after`; motion only on change; hint and `next` on errors; no HTML from the API; "R2.21's scrubber uses R2.12's reads at an operation over the same transport"; the overview's operation cell becomes a link.

## Risks

- **A period of more than 10,000 operations does not fit.** At the phase's peak that is 10 minutes. The page says how far back it holds and gives the CLI command. An aggregate RPC is the follow-up if that is not enough.
- **Older pages re-walk** what earlier pages took, so the 10th page costs ten times the first. The PR measures it, and a resuming token is the follow-up.
- **Clock skew across hosts** can order a child before its parent in the window, as `ListOperations` itself does. Rows follow the API's order, and a late outside operation can land inside a run below the top while following. Holding while reading keeps that from moving anything under the reader.
- **A GC with no later operation, page or point** leaves the window on pre-GC ids. They still answer reads until the next GC. A selection made after that fails with the daemon's error and hint, and the next operation or "Load older" starts over.
- **A tab older than the daemon** cannot load a page it had not loaded yet. The failed-load error says to reload; nothing breaks silently. Pages it already loaded keep working, as all of the app does today.
- **The split moves less than it seems.** React, the protobuf and Connect runtimes and the shared descriptors stay in the entry, so a route's total falls by the other pages' view code, not by half. The budget then grows by page, not by app: R3's views each start with the entry's weight and their own.
- **The header's window reads on every repository page.** Opening the smartlog or the workspaces page now also costs one `ListOperations` page of 1,000 (about 16 ms in the daemon, 0.5 MB), once per repository visit, not per batch. The PR measures it beside those pages' own first reads.
- **The shared header changes two merged pages.** Moving `RepoNav` out of the smartlog and the workspaces page touches their tests; the change is mechanical, and test 9 limits it to the nav's expectations.

## Choices this brief made, and why

- **A window joined to the stream by id, not re-read per batch**: the stream already carries every operation once. Listing once and joining by id is exact (test 1 for the daemon's half, test 4 for the browser's) and costs the daemon nothing per operation.
- **Rows as a pure function of the ordered records**: a reload, another tab and a live session show the same rows for the same operations. "Counts always right" then needs only "each operation once".
- **Runs per workspace and agent with a gap, events never folded**: the fleet's volume is snapshots, and the news is everything else.
- **Holding new rows while reading**: a growing run moves to the top, which is a reorder; a count of held operations keeps the counts honest while the table holds still.
- **One scrubber on all three repository pages**: a point is one operation for every view, and R2.19 and R2.20 built `?at=` for it. A scrubber on the feed alone would leave the smartlog's past reachable only by URL.
- **No play stream, and views re-read per point**: the window already holds the operations ahead of any point, R2.18 keeps one stream per browser, and a read at an operation costs what a read at head does.
- **One chunk per page, the budget per page**: decided by the user over raising the budget again. A page pays for its own code, and the next views do not push every page past the limit.
- **No API change**: everything the row needs is served, and the two candidates (an aggregate RPC and a time index) wait for this ticket's measurements, as R2.12 planned.
