# R2.13 MCP server

Phase 2 · Size M · Depends on: R2.05 (the CLI's command tree, `reef_api::json` request and response types, the `embedded-daemon` split), R2.09 (`Operations.Subscribe`, which `reef_wait` blocks on), R1.26 (the guide and `hint`/`next`), R1.27 (`reef init`'s renderers) · Unblocks: R2.25 (the plugin's `.mcp.json`), R2.26 (an adapter may call the tools), R2.27 (`reef_store_build` becomes a client-side build), R3.12, R3.32

## Context

Design principle 8: a local daemon speaks a typed protocol, and the CLI and an MCP server are thin clients of the same API. Phase 1 shipped the CLI half; agents reach Reef by running `reef` in a shell. That works (RX.07: four tool calls to a working workspace with no configuration) but it has two costs the design wanted gone. Every result comes back as text the model reads out of a shell, so a `reef ws list -o json` costs the tokens of the JSON plus the shell's framing; and every harness that wants to offer Reef as a first-class tool has to wrap the CLI itself. An MCP server removes both: the harness discovers the tools with their input schemas, the model calls them with typed arguments, and the results are structured content with the daemon's own `hint` and `next` in them.

The server is a client of `reef_api::client::Client` and nothing else. It holds no state the daemon does not, it runs no jj-lib, and it ships inside the `reef` binary as `reef mcp`, so the binary that is on `PATH` after `install.sh` is also the MCP server, with zero arguments: a harness configuration is `reef mcp`, nothing more. The agent-facing RPCs it exposes are the README's `read`, `workspaces` and `presence` scopes; `admin` RPCs (registration, GC, backup, quiesce, daemon-side store builds) are deliberately not tools.

## Decisions

- **`reef mcp` is a stdio MCP server built on rmcp 3** (features `server`, `transport-io`, `macros`, `schemars`), in `crates/reef-vcs/src/mcp/`. Zero arguments: it resolves the daemon as every command does (`REEF_SOCKET`, else the platform socket; autostart unless `--no-autostart`) and connects on the first tool call, not at startup, so `claude mcp list` shows it connected even when the daemon is down, and the first call starts the daemon. The global flags (`--state-dir`, `--socket`, `--config`, `--no-autostart`, `--timeout`) apply. Nothing but the MCP protocol goes to stdout; logging goes to stderr through R0.09's `REEF_LOG` (default `warn`). Stdio only in Phase 2: the harnesses verified above all start stdio servers, and an HTTP transport would need R2.08's authentication. ADR 0034.
- **One tool per agent-facing RPC, named `reef_<noun>_<verb>` after the CLI's words.** The Phase 2 set, with the RPC each calls: `reef_here` (`Workspaces.Inspect` by `REEF_WORKSPACE` or the cwd, no snapshot, as `reef here`), `reef_ws_create` (`Create`; never takes a `path`), `reef_ws_list` (`List`, `--limit` semantics), `reef_ws_inspect` (`Inspect`), `reef_ws_release` (`Release`), `reef_ws_move` (`Move`), `reef_snapshot` (`Snapshot`), `reef_status` (`Workspaces.Status`), `reef_log` (`Changes.Log`), `reef_diff` (`Changes.Diff`, levels `stat|files|lines|symbols`), `reef_describe`, `reef_abandon`, `reef_squash` (`Changes.*`), `reef_undo` (`Operations.Undo`), `reef_ops` (`Operations.Log`), `reef_tree_ls`, `reef_tree_cat`, `reef_tree_apply` (`Trees.*`), `reef_symbols_lookup` (`Symbols.Lookup`), `reef_query` (`Queries.Run`; `reef_query_list` for `Queries.List`), `reef_store_build` (R2.27 defines it as `Stores.Prepare`; until R2.27 lands it is `Stores.Build` with its output lines collected into the result, and the README's `allow_builds` applies), and `reef_wait`. Tools that depend on a ticket that has not landed are registered and return the daemon's `UNIMPLEMENTED` as a structured error naming the ticket, so the tool list is stable from this PR on. Excluded, with the reason in the exclusion list the test below reads: `Workspaces.Heartbeat` (the server heartbeats for the agent, below), `Presence.Report` (the server reports), `Presence.Subscribe`, `Operations.Subscribe` and `Operations.Replay` (streams; `reef_wait` is their tool form), `Daemon.Status` (`reef_here` answers "where am I"), every `admin` RPC (`Repositories.*`, `Maintenance.*`, `Stores.Build|Seal|Abort|List`, `Symbols.Index|Ingest`), and the `Remote` service.
- **`ws run` has no tool.** A tool call cannot host a process. The pattern the descriptions teach: `reef_ws_create` returns `path`; the agent runs its commands there with its own shell tool; `reef_ws_release` when done. While a workspace created through the server is active, the server heartbeats its lease on `heartbeat_every` (one `Heartbeater` task per workspace, the same type `ws run` uses, moved to `reef_api::client`), reports `RUNNING` presence with `agent = <owner>` (R2.11), and on the stdio stream closing releases every workspace it created that is still active, with a final snapshot, unless the tool call that created it passed `keep: true`. That is `ws run`'s lifecycle at the granularity of the harness session: a harness that dies leaves snapshots and reclaimable leases, not directories. The owner string is `mcp:<user>@<host>:<pid>`.
- **Descriptions come from the schema and the guide.** Each tool's `description` is the first paragraph of the proto comment on its RPC, read at build time from `reef_api::DESCRIPTOR_SET` (`prost_reflect` is R2.24's dependency; this ticket reads the `SourceCodeInfo` leading comments through `prost_types::FileDescriptorSet` directly, which protox keeps when asked), prefixed by one sentence from `docs/agent-guide.md` for the three tools an agent reaches for first (`reef_here`, `reef_ws_create`, `reef_ws_release`). A unit test fails when a tool's RPC has no leading comment. `title` is the CLI's `about`. `annotations`: `read_only_hint` for every `read`-scope tool, `destructive_hint` for `reef_ws_release`, `reef_abandon`, `reef_undo`, `idempotent_hint` for `reef_here`, `reef_status`, `reef_ws_list`.
- **Input schemas come from `schemars` on `reef_api::json` request types.** R2.05 gives every RPC a serde request type in `reef_api::json` (the CLI builds them from flags); this ticket derives `schemars::JsonSchema` on them (feature `schema` on `reef-api`, so the daemon does not pay for it), and `Parameters<T>` deserializes the tool arguments into them. Field docs become schema descriptions, so a flag's help and a tool argument's description are one string. Ids accept the CLI's unique prefixes; `repo` is optional and defaults as `--repo` does, with the cwd the harness started the server in as the path.
- **Results are structured content, never thrown errors.** Success: `CallToolResult::structured(json)` with the same `reef_api::json` object `-o json` prints, plus one `text` content block holding the CLI's text rendering (`render.rs`), so a harness that shows only text shows what `reef` would print. Failure: `CallToolResult::structured_error({ "error": { "kind", "message", "hint", "next" } })` with `is_error = true` and the text block `error: <message>` plus `hint:`/`next:` lines exactly as the CLI prints them (ADR 0025 rule 2). `next` stays an argv the agent can run in its shell; when the `next` names a command that has a tool, the error also carries `next_tool: { "name", "arguments" }` so the model can call it directly. The mapping from `ClientError` is one function, `mcp::result::from_client_error`, shared by every tool. A protocol-level error (`McpError`) is used only for a malformed request rmcp itself rejects.
- **`reef_wait` blocks on `Operations.Subscribe`.** Arguments: `filter: { repo?, changes?: [id], workspaces?: [id], owners?: [string], kinds?: [kind] }` (R2.09's `SubscribeRequest.filter`, verbatim), `until: oneof { change_snapshotted: { change }, workspace_released: { workspace }, op_seq_at_least: { seq }, any: {} }`, `timeout_ms` (default 60,000, max 600,000), `since_seq` (default: the daemon's current `seq` from `Daemon.Status`, so only new events match). It opens one subscription with `resume_after_seq = since_seq` and the filter, returns on the first frame holding a matching event (`{ matched: true, event, seq }`) or at the timeout (`{ matched: false, last_seq }`, not an error: a timeout is an answer). `change_snapshotted` matches an `Operation` event with `kind = snapshot` whose `changes` names the change; `workspace_released` a `WorkspaceEvent` with `kind = released|reclaimed`; `op_seq_at_least` any event with `seq >= n`. The description says what the tool is for: wait for another agent's snapshot or a workspace to be released instead of polling, and pass `last_seq` back as `since_seq` to continue. One `reef_wait` per server at a time; a second call while one is pending returns a structured error `Conflict` with hint `one wait at a time`.
- **Presence from the tools (R2.11).** `reef_tree_apply` reports `EDITING` on the change for the duration of the call; a workspace created by the server reports `RUNNING` while it is active; `reef_wait` reports `WAITING` with `detail = <the until>`. One `Presence.Report` stream for the server's lifetime, opened on the first report.
- **`reef init` gains the `.mcp.json` renderer** (`Harness::McpJson`): `{"mcpServers": {"reef": {"type": "stdio", "command": "reef", "args": ["mcp"]}}}`, selected when `claude` is detected or named (`--agents claude` writes `CLAUDE.md`, the skill and `.mcp.json` from this ticket on). An existing `.mcp.json` is merged: the `reef` key under `mcpServers` is written or replaced, every other key and server is kept byte-for-byte where `serde_json`'s round trip allows and otherwise re-serialized with two-space indentation (the file is JSON; there is no marker to splice by, so the rule is "only the `reef` entry is ours"); a file that is not a JSON object is `skipped (not a JSON object)`. `--check` compares the `reef` entry. New `--agents` values `codex` (writes `.codex/config.toml`'s `[mcp_servers.reef]` table, merged with `toml_edit` so comments and other tables survive, and the `AGENTS.md` section) and `opencode` (writes or merges `opencode.json`'s `mcp.reef` entry the same way, and `AGENTS.md`). Detection (`auto`): `codex` when `.codex/` exists, `opencode` when `opencode.json` or `.opencode/` exists. R2.25 packages the same renderers as plugins. Reef's own repository commits its `.mcp.json`, and `just agent-files` checks it.
- **The server is listed on the MCP registry as `io.github.reef-vcs/reef`.** `server.json` at the repository root: `$schema` 2025-12-11, `name`, `title: "Reef"`, `description` (under 100 characters), `repository`, `version` (the Cargo version), and `packages[]` with `registryType: "mcpb"`, one package per release target, `identifier` the release asset `reef-mcp-<version>-<target>.mcpb` and its `fileSha256`. The `.mcpb` is a zip of `manifest.json` (`manifest_version: "0.3"`, `server: { type: "binary", entry_point: "reef", mcp_config: { command: "${__dirname}/reef", args: ["mcp"] } }`, `compatibility.platforms` for the target) and the `reef` binary from that target's tarball, built by `scripts/package.sh` beside the tarball. `cargo` was rejected: `reef-vcs` is not on crates.io (`reef-daemon`'s `testing` feature depends on the unpublished `reef-testing`, Phase 1 README), and the registry's `cargo` path needs the crate there. `npm`/`pypi` would list the SDKs, not the server. The publish step (`mcp-publisher login github-oidc` and `publish` on a tag, with `id-token: write`) is R2.25's, which owns the release workflow changes; this ticket writes `server.json`, keeps its `version` in step with `Cargo.toml` (checked by `scripts/version.sh`), validates it in CI with `mcp-publisher validate`, and adds the `.mcpb` to `package.sh`. Both are additive to R1.28's release; `install.sh` and the tap are untouched.
- **Scenario E, "via MCP", joins the onboarding benchmark.** Claude Code, not bare, in A's checkout after `reef init --agents claude` with the skill removed (so the only Reef knowledge is `.mcp.json` and the tool descriptions), prompt `a.txt`, `--allowedTools Bash,Read,Edit,mcp__reef__*`. Measured like B; `Metrics` gains `mcp_calls` (tool calls whose name starts `mcp__reef__`) and `failed_mcp_calls` (results with `is_error`), and "calls to success" counts a `reef_ws_create` followed by an edit and `reef_ws_release` as success. A trial whose stream shows no `mcp__reef__` tool in the `init` event (if the event lists servers; see "Not verified") or no `mcp__reef__*` call and no `reef` shell call is a setup failure. Target: median at most 4 calls and 0 failed `reef` calls, as B's. Results go in `docs/onboarding-benchmark.md` as a new section.
- **The guide names the server.** R2.05 rewrites `docs/agent-guide.md`; this ticket adds one line to its long form: `reef mcp` is the same surface as tools, for harnesses that prefer tools, within the 1,600 bytes. The short form does not change.

## Tests

1. `tool_list_covers_the_agent_facing_api` (`crates/reef-vcs/tests/mcp.rs`): walks `reef_api::DESCRIPTOR_SET` for every RPC in R2.08's `read`, `workspaces` and `presence` scope tables (exported by `reef_api::scopes` for this), and asserts each is either the RPC of a registered tool or in `mcp::tools::EXCLUDED: &[(&str, &str)]` with a non-empty reason; and that no tool names an RPC outside those scopes. This is the exit criterion's test.
2. `every_tool_has_a_description_and_a_schema`: `list_tools` through an in-process rmcp client (`rmcp` `client` feature as a dev-dependency, or the server's `list_tools` called directly): every tool has a non-empty `description`, an `input_schema` with `type: object`, and every property a `description`.

## Implementation notes

- Keep the server a client: `mcp/` imports `reef_api` and `cli::{render, guide, Global, autostart}` only. If a tool needs something the CLI computes (the cwd's repository, `here`'s resolution), move that function into a module both use rather than duplicating it.
- `Parameters<T>` requires `T: JsonSchema`; derive it on the `reef_api::json` request types rather than on MCP-only structs, so a flag and an argument cannot drift. Where a tool's arguments differ from the CLI's (ids as a list in `reef_wait`), the type lives in `mcp/wait.rs`.
- The `next_tool` mapping is clap's tree read backwards; write it as a table from leaf command words to tool name and keep it beside `EXCLUDED` so test 1 can assert every tool has a CLI command and vice versa.
- Heartbeating from the server reuses `Heartbeater` (R1.21); move it to `reef_api::client::heartbeat` in this PR if R2.05 did not, so `ws run`, the SDKs' wrappers (R2.06, R2.07) and the server share one implementation.
- rmcp's `#[tool]` methods are `async fn` returning `CallToolResult` or `Result<CallToolResult, McpError>`; use the first so an application error can never become a protocol error.
- Run `claude mcp add --scope project reef -- reef mcp` once by hand against the dev build and record in the PR what `claude mcp list` and `/mcp` show, and one tool call's rendering in the Claude Code UI; the structured-plus-text shape should read well in both.
- The `.mcpb` is a zip; `package.sh` has `zip` on both runners (verify on `macos-15`; `python3 -m zipfile` is the fallback). Do not sign it (R4.17).

## Out of scope

- Streamable HTTP or SSE transports (need R2.08's tokens), MCP resources and prompts, sampling, elicitation.
- A `ws run` tool, or any tool that hosts a process.
- Publishing `server.json` to the registry (R2.25's release step) and the Claude Code plugin (R2.25).
- Running store builds in the server (R2.27 changes `reef_store_build` to `Prepare`).
- Help requests and comment-as-instruction tools (R3.12, R3.32).

## Risks

- **rmcp 3's macro surface moves between minors** (3.x shipped `ServerConfig` where its README says `ServerInfo`). Pin the minor (`=3.7`) if a bump breaks the build, and keep the macro use to the one `#[tool_router]` block.
- **A tool list that lags the API.** New agent-facing RPCs in later tickets must add a tool or an exclusion, or test 1 fails their PR; that is the point, and it costs each ticket a few lines.
- **Harness tool timeouts.** Codex's default `tool_timeout_sec` is 60; `reef_wait`'s default of 60 s and `reef_store_build` (until R2.27) can exceed it. The descriptions state the durations, and `reef_wait` returns `matched: false` rather than hanging.
- **A server that dies without closing.** SIGKILL of the harness takes the server with it before `shutdown` runs; the held leases then expire and the daemon reclaims with final snapshots, which is the designed outcome, as for `ws run`.
- **The registry listing depends on a bundle format whose packaging tool was not verified** (`mcpb pack`). The zip-and-manifest form is enough for the registry's validation (it checks only the URL and hash); whether every MCP client installs it is R2.25's publish step to find out, and `install.sh` remains the primary path.
