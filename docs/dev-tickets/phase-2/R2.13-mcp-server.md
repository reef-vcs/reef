# R2.13 MCP server

Phase 2 · Size L (the row says M; see "Size, and the registry") · Depends on: R2.05 (`reef-client`, a `reef` with no jj-lib, `--agent`), R2.27 (`reef_client::json` for v1 messages, the scope rule in `cli/scope.rs`), R1.26 (`hint` and `next`, ADR 0025), R1.27 (`reef init`'s renderers), and through them R2.02 to R2.04 · Unblocks: R2.25 (the plugin's MCP entry, and now the registry listing), R2.26 (a harness reaches the provider contract through these tools), R3.12 (instructions reach a waiting agent through the server), R3.32 (help requests as a tool); R2.17 measures tokens through these tools

## Context

Phase 2's API is done: `reef.api.v1` serves status, the log, changes, diff, the operation log, describe, abandon, undo, files and workspaces (R2.01 to R2.04), and the CLI is a thin client of it with JSON for every v1 message (R2.05, R2.27). An agent with a shell can use all of it through `reef`. An agent whose harness speaks MCP, or one with no directory at all, cannot: there is no MCP server, `EditFiles` has no CLI command by design (ADR 0034), and `reef init` writes no `.mcp.json` (R1.27 left it here).

This ticket adds `reef mcp`: an MCP server over stdio, in the `reef` binary, built with `rmcp` on `reef_client::Client`. Each tool is one or two calls, named after the RPC it calls, and returns the JSON `reef -o json` already prints for that message. The work is in what tools share: which repository and workspace a call means, how a Reef error becomes a tool result, the leases of workspaces the server creates, a wait tool over the operation log while R2.09's subscription is still unimplemented, and the `.mcp.json` renderer. The daemon does not change.

The row also lists the server on the MCP registry. The registry lists only servers with a package in a registry it can check (npm, PyPI, NuGet, crates.io, OCI, or an MCPB bundle on GitHub releases), and Reef publishes none of these. That is release packaging, so it moves to R2.25 (below).

## Decisions

### Size, and the registry

L. Twenty tools over a shared scope and error path, structured results, leases for created workspaces, a wait tool, the `.mcp.json` renderer, an ADR, and about twenty tests over stdio. R2.27 was L at similar breadth. The row says M, which does not hold once each tool's inputs, defaults and errors are specified.

The registry listing leaves this ticket for R2.25. Listing needs a package the registry verifies, and Reef has none: the choices are an MCPB bundle per platform on the GitHub release (built from the release workflow's binaries, with `reef-daemon` inside, named with "mcp"), or publishing the crates to crates.io (which ADR 0025 says needs the guide copied into the crate first). Either is release-workflow packaging, the work R2.25 already does for the Claude Code plugin and the Codex and opencode equivalents, and the listing is the same outward-facing "one install line" step. R2.25 grows from S to M. Keeping both here would make this ticket bigger than L.

The annotations follow rules, so a test can check them against the schema: `readOnlyHint` is true exactly for READ RPCs, as R2.01 decided ("R2.13 maps READ to read-only tool hints"; a read's snapshot records what is already on disk). `idempotentHint` is true for a write exactly when its RPC sets `idempotency_level = IDEMPOTENT`. `destructiveHint` is false only for the two writes that add without replacing or removing anything (a new workspace; a snapshot of files already on disk); every other write replaces a description, a tree, a directory, or what an operation did. They are hints for a client's confirmation policy, not a security boundary; MCP says so too.

Not tools, and why:

- **ADMIN RPCs** (registration, forget, GC, backup, quiesce, resume, store builds): daemon-wide or host-level effects, and `Backup.dest` and `BuildStore` are two of S-07's three ways out of a sandbox. Only the launch checkout is registered implicitly (R1.25; `--no-register` and `[repo] auto_register = false` turn that off). A `repo` path in no registered repository is the daemon's `REPOSITORY_NOT_REGISTERED`: registering a path a sandboxed agent chose would have the daemon write `.jj` there and later run git on its `.git/config` (S-07, S-13). (Changed in review.)
- **`CreateWorkspace.path`, `backend` and `lease_length`; `ReleaseWorkspace.force` and `skip_final_snapshot`**: not inputs. `path` is S-07's third way out; `force` skips the final snapshot that makes a release lose nothing; leases are the server's business (below). A workspace from the tool is always at the daemon's root with its default backend, and a release always snapshots first.
- **`RenewLease`**: the server heartbeats (below).
- **`GetRepository`, `GetDaemonStatus`, `ListStores`**: `get_status` names the repository, and the others are for a person running the CLI.
- **`SubscribeOperations`, presence**: not implemented (R2.09 to R2.11). The wait tool covers what an agent needs from the subscription now.

### Inputs

Each tool's input is a struct in `crates/reef-vcs/src/mcp/args.rs` deriving `serde::Deserialize` (`deny_unknown_fields`) and `schemars::JsonSchema`; the doc comment on each field is its schema `description`, one line. Every field is optional unless the table says required. Scope fields first:

Rules across the table:

- **Pages are the API's.** A list tool returns one page and `next_page_token` (`null` on the last), and takes `page_token` back with the same other inputs. The tool defaults (50, 20, 200) are smaller than the API's 100 so one result stays a few thousand tokens; `page_size` up to 1,000 is passed through. No tool follows every page for the caller: what costs tokens is the caller's choice.
- **`release_workspace` and `move_workspace` require `workspace`.** Defaulting them to the launch workspace would let one call release the directory the harness itself runs in (`reef ws run -- claude`). `snapshot_workspace` and `get_workspace` default to it.
- **`undo_operation` requires `operation_id` and `abandon_change` requires `revision`**, as their commands do (ADR 0034): "the last operation" and "the change I am on" are the wrong defaults with watchers and other agents recording operations.
- **Revisions default to `@`** where the RPC needs one (`get_change`, `read_file`, `list_files`, `describe_change`); without a workspace in scope that is the daemon's `WORKSPACE_REQUIRED`.
- **Paths are repository-relative**, the API's form. An absolute path inside the scope's directory (the workspace's path or the repository's root, canonical) is made relative first, as the CLI does for absolute paths; anything else goes to the daemon as given, which refuses what is not repository-relative (`INVALID_PATH`). Unlike the CLI, there is no relative-to-the-current-directory rule: an MCP caller has no current directory the server can see.
- **`edit_files`' edits** are `{ path, content?, content_base64?, replace?: { old_text, new_text, all? }, delete?: true, copy_from?, executable? }`. At most one of `content`, `content_base64`, `replace`, `delete` and `copy_from`; none is allowed only with `executable`. `content` is UTF-8 text; `content_base64` is bytes (standard alphabet, padded), for binary files. The server checks the shape before the call (below). The description says how to rename: `copy_from` the old path, then `delete` it, in one request (R2.04's inheritance).
- **`read_file` stops at a character.** When `limit` ends inside a UTF-8 sequence of an otherwise valid UTF-8 range, the server returns the range up to the last whole character, so `content` stays text; `next_offset` says where to continue. A range that is not UTF-8 for another reason is returned as `content_base64`, as `json::FileRead` does.
- **`create_workspace`'s owner** is `<user>@<host>:mcp` (`default_owner()` plus `:mcp`), the same for every server of this user on this machine, so a restarted server can pick up the leases its predecessor held (below). The agent name is separate (below), as ADR 0033 keeps owner and agent apart. `purpose` defaults to empty.

### Outputs

Every successful result has `structuredContent`, a JSON object, and one text block holding the same object as compact JSON, as MCP asks of a server that returns structured content. The objects are `reef_client::json`'s, so a tool returns what the matching `reef -o json` command prints:

- `get_workspace` → `Inspected`; `create_workspace` → `Created`; `move_workspace` → `Moved`; `release_workspace` → `Released`; `snapshot_workspace` → `Snapshotted`; `get_status` → `RepoStatus`; `get_operation` → `Operation`; `describe_change` → `Described`; `abandon_change` → `Abandoned`; `undo_operation` → `Undone`.
- `get_change` → `{ change: Change, at_operation }`. `get_diff` → `Diff`'s keys (flattened) plus `next_page_token`.
- Lists are wrapped, since structured content is an object: `{ repositories, next_page_token }`, `{ workspaces, next_page_token }`, `{ entries: [LogEntry], at_operation, next_page_token }`, `{ operations, next_page_token }`, `{ entries: [FileEntry], commit_id, at_operation, next_page_token }`. The wrappers live in `mcp/results.rs`; they are the server's shapes, not the CLI's.
- `read_file` → `FileRead`'s keys plus `offset` and `next_offset` (`null` at the end).
- `edit_files` → a new `json::Edited { change, operation, workspace }`, beside `Described`.
- Writes in a workspace scope return that workspace afterwards (`workspace`), read with one `GetWorkspace` (no snapshot, no disk walk), as R2.27's commands do, so a divergent result (issue #80) is visible in the result; `null` in repository scope. A failure of that read leaves `workspace: null` and logs a warning; the write succeeded. The server writes no divergence note: the tool description of each write says "`workspace.divergent` true means its change has more than one commit; `list_changes` with `revset: change_id(<id>)` lists them and `abandon_change` drops one."

No tool declares an `outputSchema` in this ticket. A declared schema binds every result, error results included in some clients' reading of the spec, and deriving one per `json` type is R2.24's job, which derives the CLI's output schemas from the same types; R2.24 adds `outputSchema` to these tools from that derivation. Until then the description names the shape ("Returns the change, as `reef show -o json` prints it, without its files").

### Errors

A Reef error is a tool result, never a JSON-RPC error, so the model sees it and can act on it:

- `isError: true`, `structuredContent: { "error": ErrorObject }`, and one text block with that object as JSON. `ErrorObject` is the CLI's: `kind`, `reason`, `message`, `hint`, `next`, `metadata`, built from the `CliError` the call produced through one function shared with `Out::error` (`cli/out.rs`'s `error_object` becomes `pub(crate) fn error_object(error: &CliError) -> ErrorObject`).
- **The daemon's advice as it is.** The hint is the daemon's, in the API's words, which line up with tool and field names (above). `next` is the daemon's or the client's, a `reef` argv (`reef ws list --all`, `reef ws create --repo <id>`, `reef daemon stop`); it stays, because an agent with a shell can run it and one without can read it. The CLI's advice table (`cli/advice.rs`) is not applied: its `next`s repeat CLI command lines the MCP caller never ran. A reason the CLI advises and the daemon does not keeps the daemon's hint here. This is what R2.05 and R2.27 left to this ticket.
- **The server's own errors** use the same object with kind `invalid_argument` and a reason:
  - arguments that do not deserialize against the tool's input type: reason empty, message serde's, hint "See the tool's input schema.";
  - `edit_files` edits with two actions, none and no `executable`, an empty `old_text`, both `revision` and `new_on`, or neither: reason `INVALID_EDIT` with metadata `edit_index` where it is one edit's, the daemon's own reason for the same mistakes, checked before any call so nothing is snapshotted;
  - `content_base64` that does not decode: `INVALID_EDIT`, `edit_index`;
  - no `repo`, no `workspace`, and no launch scope (below): reason `REPOSITORY_REQUIRED`, hint "Pass repo: an absolute path inside the repository, or its id; list_repositories lists the registered ones." A constant in `mcp/mod.rs`, documented in ADR 0035: the daemon never sends it;
  - `create_workspace` or `move_workspace` with both `change` and `new_on`, `timeout_seconds` over 300, `limit` over 1 MiB: reason empty, a one-line hint naming the input.
- **JSON-RPC errors** only where MCP requires them: an unknown tool name (`-32602`), a malformed request, and a server bug (`-32603`, logged). Argument validation is a tool error, as MCP 2025-11-25 recommends, so a model can fix its call.
- **A request too large** for the daemon (`ClientError::TooLarge`, over 4 MiB of edits) is a tool error with the client's advice ("Edit large files in a workspace, or split the edits across requests.").

### Which repository and workspace a call means

The server keeps no "current workspace" between calls. A harness may route several agents through one server process (Claude Code's subagents share their session's servers), and per-session state would let one agent's call land in another's workspace. Each call resolves its scope from its own `repo` and `workspace` and the server's launch environment, with R2.27's rule, by calling `cli::scope::resolve(ctx, &ScopeArgs { workspace, repo })`:

1. `workspace`: that workspace (an absolute path that exists is canonicalized, as for the CLI).
2. `repo` alone: the repository, and no workspace.
3. `REEF_WORKSPACE` in the server's environment.
4. The workspace containing the server's current directory, else the repository containing it, registering a git checkout implicitly unless turned off.

Steps 3 and 4 are the launch scope. A harness started inside a workspace (`reef ws run -- claude`) passes `REEF_WORKSPACE` to the servers it starts, so their tools default to that workspace; one started in a checkout defaults to its repository. The server's current directory never changes, so the launch scope is the same on every call; it is looked up each time (one or two RPCs of about a millisecond) rather than cached, so a workspace released meanwhile is seen as released. When step 4 finds no repository (the server was started outside every checkout, as a desktop client starts servers), a call without `repo` or `workspace` is `REPOSITORY_REQUIRED` instead of the scope's error.

### The agent, and the client's name

The agent named on every operation the server causes is `--agent`, else `REEF_AGENT` in the server's environment, checked with `check_agent` before the server starts (an invalid one is a usage error on stderr, exit 2, and no server). With neither, the daemon records the workspace's owner, as for the CLI. The MCP client's `clientInfo.name` (`claude-code`) is not used: it names the harness, not the agent, and is absent from requests under MCP 2026-07-28. A per-call agent argument is not added: the server process is the agent's, and `ws run` and `.mcp.json` already set `REEF_AGENT` per session. R2.26 and R3.12 revisit this if a harness multiplexes agents through one server.

### Leases of workspaces the server creates

- **The server heartbeats** every active workspace it created, and every active workspace with its owner (`<user>@<host>:mcp`) that any tool call named, for as long as it runs. `Heartbeater` moves from `cli/ws_run.rs` to `cli/heartbeat.rs` (`pub(crate)`, unchanged), and the server runs one task per leased workspace with the daemon's `heartbeat_every`. Its notes go to the log at `warn` (stderr), never to the protocol. A heartbeat that finds the lease gone (`lease_gone`) ends that task; `release_workspace` ends it after the release.
- **On exit the server releases nothing.** It stops heartbeating, and each lease runs its course (30 minutes and 5 of grace by default), after which the daemon reclaims the workspace with a final snapshot (ADR 0019), so nothing is lost. A server sees end-of-input both when its session ends and when the harness restarts it (Claude Code's `/mcp` reconnect); releasing on exit would remove a directory an agent is still editing through its shell. A restarted server takes over the leases on the next call that names each workspace, through the shared owner.
- The `create_workspace` description says so: "The server keeps the workspace's lease alive while it runs. Release it with release_workspace when done; one left behind is reclaimed, with a final snapshot, about 35 minutes after the server stops."

### The wait tool

`wait_for_operations` is "subscriptions as a wait tool" over what exists: R2.09 has not implemented `SubscribeOperations`, so the tool polls `ListOperations`. Its contract does not depend on that.

- **Inputs**: the scope's repository (one; required by the rule above); a filter (`workspaces`, `changes`, `agents`, `kinds`, as `list_operations` takes them); `after_operation` (an operation id or prefix; default: the head of the operation log when the call starts); `timeout_seconds` (default 30, 0 to 300; 0 checks once); `include_effects`.
- **Result**: `{ operations, last_operation_id, timed_out }`. `operations` are those matching the filter that ended after `after_operation`, oldest first, as `json::Operation`s; the tool returns as soon as there is at least one. `last_operation_id` is the newest of them, or on a timeout the newest operation in the log when it gave up, matching or not; passing it back as `after_operation` waits for what comes next without seeing anything twice. `timed_out` is true with `operations: []`.
- **Polling**: the baseline is `after_operation`'s operation (`GetOperation`), else the head (`ListOperations { page_size: 1 }`, unfiltered). Every 500 ms: read the head (unfiltered, one operation), then `ListOperations { filter, ended_after: baseline.ended_at minus 1 ms, include_effects, page_size: 1000 }` over every page, dropping the baseline itself and anything returned before in this call. With nothing found, the window follows the head read first, 2 seconds behind it, so it stays a few seconds however long the wait, and an operation stamped before the head but recorded after it is still seen. At most 100 operations are returned per call. The wait is not retried after the daemon goes away. (Changed in review.) With an `after_operation` older than now, the first poll returns what already happened since it (resuming). The millisecond of overlap catches operations that ended in the baseline's millisecond.
- **Cancellation and progress**: a `notifications/cancelled` for the call ends it at once (`RequestContext::ct`). If the request carries a progress token, the server sends `notifications/progress` every 10 seconds (progress: seconds waited, total: the timeout), which keeps clients that reset their timeout on progress from cutting the wait. The tool description says waits over 60 seconds may hit a client's own tool timeout.
- **When R2.09 lands**, it adds `Client::subscribe_operations` and switches this tool to the stream: `SubscribeOperationsRequest { repos: [repo], filter, start: after_operation(baseline id) }`, returning the first frame with operations, or nothing at the timeout (keepalive frames reset nothing). The inputs, the result, the descriptions and the tests stay. R2.09's brief says so in its "What later tickets inherit".

### The server

- **`reef mcp`** is a command with no arguments of its own; the global flags apply (`--agent`, `--state-dir`, `--socket`, `--config`, `--no-autostart`, `--no-register`, `--timeout`, `-v`, `-q`). `about`: "Serve Reef's API to an agent harness over MCP on stdio (put it in the harness's config)". It goes after `init` in `--help`. `-o` is ignored. In `cli/mod.rs`, `Command::Mcp` runs before the per-command output default and calls `crate::mcp::serve(global)`.
- **Transport**: `rmcp::transport::stdio()` and `rmcp::serve_server`. Stdout carries only the protocol: the server never calls `Out::object`, `list`, `done` or `raw`, and its `Out` is used only for stderr notes (`started daemon`, `registered …`), which `-q` silences. Logging is the CLI's (`init_logging`, stderr; `REEF_LOG` and `-v`). Nothing else reads stdin.
- **Server info**: name `reef`, title `Reef`, version `reef_client::VERSION`; capabilities: tools only (no resources, prompts, completions or logging). `instructions` is `crates/reef-vcs/src/mcp/instructions.md`, embedded with `include_str!`, at most 1,000 bytes (a test): what Reef is in one sentence, that tools default to the repository or workspace the server started in, that `@` needs a workspace, that errors carry `hint` and a `reef` `next`, that the server keeps created workspaces' leases alive, and that `wait_for_operations` waits for other agents' work. Not the agent guide: the guide is CLI text, is pasted into `AGENTS.md`, and is at 1,596 of its 1,600 bytes. This departs from the row's "Tool descriptions ... reuse R1.26's guide": what is reused from R1.26 is the `hint`/`next` contract and the in-band self-description.
- **Descriptions** are written per tool in `mcp/tools.rs`, one to three sentences each, in the task's words ("Show what the workspace changes and the repository's state, after snapshotting the workspace."), ending in the result's shape. Not R2.01's proto comments, which are written for API implementers, with "Errors:" paragraphs that would cost every session thousands of tokens; the error reasons reach the model when they happen. A budget test holds the whole `tools/list` result to 20,000 bytes of JSON, the guide's discipline applied to tools.
- **Dispatch by hand.** `ReefServer` implements `rmcp::ServerHandler`'s `get_info`, `list_tools` and `call_tool` over one static table (`TOOLS: &[ToolDef { name, title, description, access, annotations, schema, call }]`), not the `#[tool_router]` macros: the table drives the annotations, the tests iterate it, and arguments are deserialized by the server so a bad argument is a tool error. `schema` is `rmcp::handler::server::tool::schema_for_input::<T>()` (or `schemars::schema_for!`, whichever 3.8 exposes publicly; the PR says which). `rmcp`'s `macros` feature is off, which keeps `rmcp-macros` and `darling` out of `reef`.
- **The daemon connection** is made on the first tool call, not at start, so a harness can start the server before a daemon exists and the server answers `initialize` and `tools/list` without one. `cli::connect` makes it (autostart unless `--no-autostart`); the `Ctx` is kept behind a `tokio::sync::Mutex<Option<Arc<Ctx>>>` and shared by concurrent calls. A call whose error is kind `unavailable` with no reason (the daemon went away) drops the `Ctx`, connects again (starting the daemon if allowed), and retries once if the tool is a READ; a WRITE returns the error, with the hint "The daemon went away during the call; check whether it took effect (get_operation, list_operations) before retrying."
- **Another daemon version** is handled as `main` handles it: an `Incompatible` while `!any_call_answered()` restarts an idle daemon (`cli::daemon::restart`) and retries the call once; after that, or with active workspaces, the call fails with `old_daemon`'s error (kind `unsupported`, `next` `reef daemon stop`). `rerun`'s rule is the same: a retry never repeats a call that succeeded.
- **Deadlines**: each RPC gets `--timeout` or 30 seconds, through `Ctx::call` (registration gets `REGISTER_TIMEOUT`); the wait tool's polls each get the RPC deadline, and the wait its own `timeout_seconds`.
- **Shutdown**: end of input, SIGINT or SIGTERM ends the service; the heartbeat tasks are aborted; the process exits 0 (a transport error that is not end of input exits with `internal`'s code). `main` shuts the runtime down with `shutdown_background()` for this command, since tokio's stdin reader is a blocking thread that would otherwise hold the exit.
- **Platforms**: nothing is `cfg(target_os = "linux")`. `stdio()` rather than 3.6's `stdio_pipes()`, whose Linux path differs from macOS's; per-message thread hand-off is not a cost at an agent's call rate.

### `.mcp.json` in `reef init`

- **A new harness file**, `Harness::McpJson`, at `<root>/.mcp.json`, the project-scope file Claude Code reads (and others read in the same shape). Written when Claude Code is detected or named (`--agents claude`, `all`), and by a new `--agents mcp` that writes only it besides `AGENTS.md`. Other harnesses' MCP files (`.cursor/mcp.json`, Codex's `config.toml`) are R2.25's, from the same renderer function.
- **Reef's entry** is the `reef` key of `mcpServers`: `{"type": "stdio", "command": "reef", "args": ["mcp"]}`. `reef` on `PATH`, as every installer puts it; no absolute path, which would bake one machine's layout into a committed file. No `env`: `REEF_AGENT` is the harness's to set.
- **Reef owns that entry, not the file.** The file is parsed into an order-preserving value (`enum Json` over `indexmap::IndexMap`, `#[serde(untagged)]`; `indexmap` with its `serde` feature becomes a dependency of `reef-vcs`, already in the lockfile). Missing file: written with only Reef's entry. No `mcpServers`: added after the other keys. No `reef` server: added after the others. A `reef` entry equal to Reef's: unchanged. A `reef` entry that differs: skipped, reason `mcpServers.reef is not reef init's`; a person who changed it (an `--agent`, an `env`) keeps it, and `--check` does not call it stale. Not a JSON object, or `mcpServers` not an object: skipped, reason `not a JSON object`. The rewrite is two-space pretty JSON with a final newline, CRLF kept if the file had it; keys and values keep their order and content, and only whitespace is normalized. Not `serde_json`'s `preserve_order` feature: features unify across the workspace build and would reorder the daemon's `config show --json`.
- **No version in the entry**, unlike every other generated file (R1.27): JSON has no comment to carry it, and the entry does not change with the version, so a version bump does not make `.mcp.json` stale. `--check` reports it missing or nothing.
- `reef init`'s JSON lists it in `files` like the others. `--print` is unchanged (the `AGENTS.md` section).
- **This repository** commits the `.mcp.json` `reef init --agents claude` writes, since `just agent-files` checks it.

### Threat model

- The server runs where the harness starts it, outside the sandbox the harness gives the agent's shell, so a socket deny rule does not stop an agent from reaching the daemon through it. What it can do there is the tools: no ADMIN RPC, no `path` on a create, no backup, no build, no forced release. Through the server an agent writes only inside Reef's workspaces (at the daemon's root) and the jj store. `docs/threat-model.md`'s "Harness sandboxes" gains that paragraph, and says that an operator who denies the socket must also leave `reef mcp` out of the harness's MCP configuration.
- **Client-side store builds (#61) stay out.** The server exposes no build, so it adds no path to daemon-side execution, and #61 changes ADR 0022's second decision for `reef store build`, a CLI command. The threat model's "(Phase 2, with R2.13)" becomes "(Phase 2; the MCP server exposes no build)". S-07's row is otherwise unchanged.
- Annotations are hints, and `destructiveHint` is not an authorization; nothing in the server checks who calls it. One uid is one trust domain (ADR 0027).

## Implementation notes

- **Order**: move `Heartbeater` (test 20); `error_object`; the server skeleton with `tools/list`, instructions and annotations (tests 1 to 4); scope and the read tools (5, 9, 11, 13); the writes and leases (6 to 8, 10, 12, 14); the wait tool (15, 16); `.mcp.json` (17); the CLI tests and the old daemon (18, 19); docs.
- **Reuse, do not copy**: `cli::connect`, `Ctx::call`, `Ctx::call_with_repo`, `scope::resolve`, `scope::workspace_arg`, `check_agent`, `default_owner`, every `json` type, `Heartbeater`, `daemon::restart`, `old_daemon`, `init_logging`. A tool body that rebuilds what one of these does is a review finding.
- **Absolute paths to repository-relative**: compare against the scope's `dir` canonical and strip it; the CLI's `scope.rs` has the helper for absolute paths (`relative_to`); make it `pub(crate)` rather than writing another.
- **`read_file`'s character boundary**: when the range is not valid UTF-8, check whether `std::str::from_utf8`'s error is an incomplete sequence at the end (`error_len() == None`) and the range ended before the file did; if so, cut to `valid_up_to()`. A range shorter than one character (a `limit` of 1 inside a 4-byte character) returns `content_base64` instead of looping.
- **The heartbeat set** is a `Mutex<HashMap<String, JoinHandle<()>>>` keyed by workspace id; adoption reads the workspace each call already resolved through its scope (no extra RPC) and checks `state == ACTIVE` and `owner`.
- **Linux**: nothing here is `cfg(target_os = "linux")`, so macOS compiles all of it; still run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy with and without `--all-features` in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux") before pushing, since `rmcp`'s own Linux-only code paths and the musl release build are new.
- **The release build**: `cargo build --profile dist --target x86_64-unknown-linux-musl -p reef-vcs` once in the container, and `reef mcp` answers `initialize` there, so the static binary carries the server.
- **The crate graph**: `crate_graph` passes unchanged (nothing new is on its list); record `cargo tree -p reef-vcs -e normal --prefix none | sort -u | wc -l` before and after in the PR, against ADR 0033's 120.

## Risks

- **`rmcp` moves fast.** Weekly 3.x releases, and MCP 2026-07-28 changed the lifecycle (no `initialize`). The exact pin and the stdio tests catch a break; a client on 2026-07-28 and one on 2025-11-25 must both work, and test 1 runs both if `rmcp`'s client can be told which version to offer (else the PR notes which it tested).
- **A harness's file tools may not reach a workspace.** A workspace's directory is under the daemon's root, outside the project, so a harness may ask permission for each edit there. The agent can use `edit_files` instead; R2.26's provider contract is the fix where a harness creates the directory itself.
- **Leases outlive the session by up to 35 minutes.** Workspaces left behind hold disk until reclaimed. That is ADR 0019's trade, and the final snapshot means nothing is lost.
- **A shared owner lets any server of this user adopt any `:mcp` workspace** named in a call, so two sessions naming one workspace both keep it alive. Harmless: the owner is informational, and the release is explicit.
- **Committing `.mcp.json` here** makes Claude Code in this repository offer `reef mcp`, which needs `reef` on `PATH`; Claude Code asks before it starts a project server. Contributors without Reef installed decline it.
- **The tool list costs tokens in every session** that loads the server, used or not. The 20,000-byte budget bounds it; R2.17 measures what it costs against what it saves.
- **Polling the operation log** costs two RPCs a second per waiting call. Agents waiting in parallel multiply it; R2.09's stream removes it.

## Choices this brief made, and why

- **Tools after RPCs, not commands**: the daemon's hints name RPCs and fields, so they name tools and arguments; and an MCP caller has no current directory for the CLI's path rule.
- **No ADMIN tools and no `path`**: the server runs outside harness sandboxes, so its surface is what a sandboxed agent gets.
- **The daemon's advice, not the CLI's table**: the table's `next`s are command lines the caller never ran.
- **Per-call scope, no session state**: servers can be shared by several agents.
- **Heartbeat while running, release nothing at exit**: a restart of the server must not take a directory from an agent mid-edit, and a reclaim snapshots first.
- **Polling now, the stream later**: the tool's contract is what an agent needs; how it is fed changes in R2.09 without the agent seeing it.
- **Lazy connection**: a harness starts servers at session start; the daemon may not be up yet, and `tools/list` should not wait for it.
- **The registry in R2.25**: it needs a package Reef does not publish, and publishing packages is that ticket's work.
