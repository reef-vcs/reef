# R2.25 Harness packages

Phase 2 · Size L (the row says M; see "Size") · Depends on: R1.27 (`reef init`'s renderers and the agent table, `crates/reef-vcs/src/agents/mod.rs`), R1.28 (`release.yml`, `scripts/package.sh`, the dry run on pull requests), R2.13 (`reef mcp` and `render_mcp_entry`), R2.11 (the presence reporting contract the hooks follow), R2.24 (`reef schema`, whose document and descriptor set this attaches to releases), RX.07 (the onboarding harness that gains a scenario) · Unblocks: none listed (RX.07's scenario E measures it; R2.17's second-harness issue and R2.26 build on the agent table it extends)

## Context

An agent gets Reef today in one of two ways. Either a person runs `reef init`, which writes `AGENTS.md` and, for the agents it recognizes (Claude Code and Cursor), their own files: `CLAUDE.md`, the skill, `.cursor/rules/reef.mdc`, and Reef's entry in `.mcp.json`. Or an agent with a shell reads `reef` and `reef --help`. Both happen one repository at a time. No harness can install Reef the way it installs its other tools, and no MCP client outside a repository can find `reef mcp`: the server is listed nowhere.

The row asks for three things. First, a package per harness, built from R1.27's renderers, so that one install line sets a harness up for Reef: Claude Code, Codex and opencode. Second, publishing through R1.28's release workflow. Third, a listing of `reef mcp` on the MCP registry from the same workflow, with a package the registry can check. Earlier briefs left this ticket six promises:

- **R2.13** (lines 34, 190, 342): put `.mcp.json`'s entry into the Claude Code plugin; write the Codex and opencode MCP entries from `agents::render_mcp_entry`; list the server as `io.github.reef-vcs/reef` with `server.json` (schema 2025-12-11) and an MCPB bundle per platform (with `reef-daemon` inside and "mcp" in its name) or the crates on crates.io; publish with `mcp-publisher login github-oidc`, with the publisher pinned and checked with cosign; add RX.07's MCP scenario.
- **R2.11** (line 262): the hooks report declared intent with `reef presence report --id-file <file> --path <file>` before an edit and `reef presence clear --id-file <file>` after.
- **R2.24** (lines 320, 350): ship `reef schema mcp`'s definitions in a package, and attach the schema document and the descriptor set to releases.
- **R2.18** (open question 1): if crates are published, decide how `reef-web` carries the built assets.
- **R2.17** (line 471): add a benchmark adapter in `agent/harness/` for each further harness packaged.
- **ADR 0025** (consequences): publishing `reef-vcs` to crates.io needs `docs/agent-guide.md` copied into the crate first.

The user's standing direction, the agent-agnostic north star, constrains the design:

- The default surfaces stay harness-neutral: `AGENTS.md`, the CLI with `hint` and `next`, and MCP.
- Each harness's files are thin adapters rendered from the same guide and entries.
- Facts about each harness live in one table.
- A harness is added only with verified facts.
- Text a user copies names a harness only where that harness behaves differently.

## Decisions

### Size

L. The row's M covered a plugin and a listing. The work found here:

1. Two agents added to `reef init`'s table, with home-directory detection for `--user` and two new file formats to merge (a TOML table in Codex's `config.toml`, an object in `opencode.json`), each with skip rules and tests.
2. Two plugin trees and two marketplace files rendered from the same functions, kept current by a test.
3. A hook command that reads a harness's event and reports presence, and must never fail or slow the edit it runs before.
4. MCPB bundles for four targets, a `server.json` built from the checksums, and a publishing job.
5. Release attachments for the schema.
6. A CI job that runs each harness's install path against the release build without credentials.
7. RX.07's scenario E.

No API change, no daemon change, no new crate. To bring it back to M, items 3 and 7 would move to a follow-up row (open question 5).

### What "one install line" means for each harness

The harness-neutral surfaces stay first: `AGENTS.md` (which Codex and opencode read, and which Claude Code reads through `CLAUDE.md`'s import), the CLI, and `reef mcp`. A package adds only what a harness cannot get from those: its skill and its MCP entry, and, where its hooks can name the file being edited, presence. Every install line assumes `reef` is already installed, as `reef init` does. No package downloads or installs binaries: a plugin that ran an installer on its own would be a second, unreviewed install path. A skill or MCP entry that finds no `reef` says so through the harness's own error.

| Harness | Install line | What it gets | Why this route |
| --- | --- | --- | --- |
| Claude Code | `claude plugin install reef --marketplace reef-vcs/reef` | the skill, the MCP entry, the presence hooks | its marketplace reads this repository; one command since 2.1.292 |
| Codex | `codex plugin marketplace add reef-vcs/reef && codex plugin add reef@reef` | the skill, the MCP entry | its marketplace reads this repository; an Agent Plugins tree, no hooks (plugin hooks run only in the desktop app, and its edits name no path) |
| opencode | `reef init --agents opencode --user` | the skill in `~/.agents/skills`, the MCP entry in `~/.config/opencode/opencode.json` | a plugin cannot declare an MCP server (undocumented) and would be an npm package; `reef init` already writes files |
| any MCP client | the registry listing `io.github.reef-vcs/reef`, or a `.mcpb` from the release | `reef mcp`, with `reef-daemon` beside it | the registry needs a package it checks |

`reef init --agents codex --user` also works for Codex, without the plugin. It writes the same two things into `~/.agents/skills` and `~/.codex/config.toml`. Within a repository, `reef init` writes the project-level forms for each detected agent, as it does today.

### The agent table grows two rows

`SIGNS` stays the one place that holds per-harness facts. It gains:

Claude Code's row gains `home: &[Home::Dot(".claude")]`, `user: &[ClaudeSkill { user: true }]` (unchanged), `package: Some(Package::ClaudeCode)` and `hooks: Some(&CLAUDE_CODE_HOOKS)`. Cursor's row gets empty `home` and `user`. `Agent` gains `Codex` and `Opencode`, and `--agents` gains `codex` and `opencode`.

- **`OPENCODE=1`** goes into opencode's `env` only if the implementer finds it in the source of the pinned release (`opencode-ai@1.19.5`, the bash tool's environment) and in a recorded `opencode run` session. Otherwise `env` stays `None`, and the PR says which. Codex has none to check.
- **`Harness::AgentSkill { user }`** is `.agents/skills/reef/SKILL.md`, or `~/.agents/skills/reef/SKILL.md` when `user`. It is the Agent Skills standard's shared directory, which Codex and opencode read; one file serves both, and the name is not a vendor's.
  - It is rendered like `ClaudeSkill`, except that the frontmatter keeps to the standard's keys: `name: reef`, `description`, and `metadata:` with `generated-by: reef init` under it.
  - `generated_by_reef` accepts both forms, so a file written by this version is recognized as Reef's.
- **`Harness::CodexConfig { user }`** is Reef's `[mcp_servers.reef]` table in `.codex/config.toml`, or in `$CODEX_HOME/config.toml` (else `~/.codex/config.toml`) when `user`.
  - It is merged with `toml_edit`, which becomes a direct dependency of `reef-vcs` (`default-features = false, features = ["parse", "display"]`, the version already in the lockfile), so comments, order and formatting outside the table survive.
  - The rules are `.mcp.json`'s:
    - No file: one with only the table.
    - No such table: append it.
    - A table equal to Reef's: unchanged.
    - A different table: skipped, with reason `mcp_servers.reef is not reef init's`.
    - Not TOML: skipped, with reason `not TOML`.
  - The table is `command = "reef"` and `args = ["mcp"]`.
- **`Harness::OpencodeJson { user }`** is Reef's `mcp.reef` in `opencode.json`, or in `$XDG_CONFIG_HOME/opencode/opencode.json` (else `~/.config/opencode/opencode.json`) when `user`.
  - It reuses `.mcp.json`'s order-preserving merge with the key path `mcp.reef`, and the entry `{"type": "local", "command": ["reef", "mcp"], "enabled": true}`.
  - A new file also gets `"$schema": "https://opencode.ai/config.json"` first.
  - If `opencode.jsonc` exists instead, the file is skipped, with reason `opencode.jsonc: comments are not rewritten; add "mcp": {"reef": …} by hand`, the reason quoting the whole entry so the person can paste it. No flag is added for printing it.
- **One function for every MCP entry.** `render_mcp_entry(shape: McpShape)` replaces the zero-argument form. `McpShape` is `McpJson` (`.mcp.json`, and the Claude Code plugin's), `AgentPlugins` (the Agent Plugins `mcp.json`, which adds the transport `type`), `CodexToml`, `Opencode` and `Mcpb` (the bundle manifest's `mcp_config`). Each produces `reef mcp` from `PATH`, except `Mcpb`, which is `${__dirname}/reef`. A test checks that every shape names the same program and arguments.

### `--user` selects by home directory

`--user` now writes the user-level files of each agent `--agents` selects. With `auto`, an agent is selected at user level when its `home` directory exists, its `env` signal is set, or the repository shows it. With an agent named on the command line, it is written regardless. Before this change, `--user` with `auto` always wrote Claude Code's skill. Now it does so only when `~/.claude/` exists or Claude Code is detected. That is the same answer on any machine where Claude Code has run, and it is what stops `--user` from creating `~/.codex/` on a machine without Codex.

- `--user`'s help becomes "Also write each selected agent's user-level files (its skill, its MCP entry) in the home directory."
- Claude Code's user level stays the skill alone. Its user MCP configuration is `~/.claude.json`, a state file Reef does not edit, and its user-level path for Reef is the plugin.
- `--check --user` checks the user-level files too, as it does today.
- `CHANGELOG.md`, Changed: "`reef init --user` writes the user-level files of the agents it selects, recognizing each by its home directory (`~/.claude`, `~/.codex`, `~/.config/opencode`), rather than always writing Claude Code's skill."

### The plugin trees and marketplaces

The plugin trees are rendered into the repository and committed. `agents::packages(&Guide, version) -> Vec<(PathBuf, String)>` produces every file below, and a unit test fails when the files on disk differ from it. Run with `REEF_BLESS=1`, the test writes them instead; `just packages` runs it that way. They are not written by `reef init` and add nothing to the CLI. They are Reef's distribution, not a user's repository.


- **Names.** The marketplace is `reef`, and so is the plugin (Claude Code's install line types `reef`, Codex's `reef@reef`). The trees are named by format: `claude-code` is Claude Code's own format, and `agent-plugins` is the standard's, which another harness that adopts it installs unchanged. That harness then needs a marketplace file and a row, not another tree.
- **`plugin.json`** (Claude Code): `name`, `displayName` "Reef", `version` (the workspace version), `description` (the skill's `DESCRIPTION`), `author.name` "Reef contributors", `homepage`, `repository`, `license` "Apache-2.0", and `keywords` `["version-control", "workspaces", "jj", "mcp"]`. The Agent Plugins `plugin.json` has the same fields under that schema's names, and its `$schema`.
- **The skills** are `ClaudeSkill`'s and `AgentSkill`'s renders, with the preface "Part of the Reef plugin (reef <version>); `reef guide` prints the current guide." in place of "Written by `reef init`". `render` takes the preface as an argument.
- **Pinned to the release.** Each marketplace entry points at its tree at the release tag, not at `main`. A plugin on `main` could call a command (`reef presence hook`) that the released `reef` lacks.
  - Claude Code's entry: `{"name": "reef", "source": {"source": "git-subdir", "url": "reef-vcs/reef", "path": "plugins/claude-code", "ref": "v<version>"}, "description", "category": "development"}`.

The implementer takes the `policy.authentication` and `category` values from Codex's documentation at 0.166.0, and the PR quotes them.

The table and the docs say so.
- **This repository's own files are unchanged.** `just agent-files` still runs `--agents claude`, and the plugin trees are separate files.

### Hooks: declared edits as presence

The Claude Code plugin's hooks report the files an agent is about to edit, as an `EDITING` entry with `by_daemon: false`: R2.11's "declared intent", which R3.36 wants and which the daemon's own `EDITING` entries (after a snapshot) arrive too late for. Nothing else goes in the hooks.

- **No `SessionStart` context.** Text a hook adds is read by every session, which is #122's cost, and the skill and `AGENTS.md` already say what it would say.
- **No Codex hooks.** Plugin hooks run only in Codex's desktop app, and `apply_patch`'s input names no path a pointer can select.
- **No opencode plugin** (above).

**`reef presence hook`**, a new subcommand under the `presence` noun, so `reef --help` does not grow:

```
reef presence hook edit --path-at <POINTER>... [--session-at <POINTER>] [--ttl <DURATION>]
reef presence hook end [--session-at <POINTER>]
```

- **The input.** It reads one JSON object from stdin, at most 1 MiB: the harness's hook event. Each `--path-at` is a JSON Pointer (RFC 6901) to a string or an array of strings, and a pointer that selects nothing is skipped. That keeps the command harness-neutral. The pointers are Claude Code's facts and live in its row (`CLAUDE_CODE_HOOKS`), not in the command.
  - A relative path is taken against the process's current directory.
  - `--session-at` selects the session id, and the parent process id stands in when it selects nothing.
- **`edit`** finds the workspace containing the paths by R2.27's scope rule, applied to the first path's directory. If the paths are in no workspace, or in more than one, it does nothing. Otherwise it reports one `EDITING` entry with every path in that workspace.
  - The entry replaces this session's previous one, through `--id-file <state>/presence/hooks/<first 16 hex of SHA-256(session)>.id`, R2.11's `--id-file` mechanism.
  - Its TTL is `--ttl`, 5 minutes by default (R2.11 caps it at 10). The entry therefore says "this session last declared an edit to these files, at most five minutes ago". This departs from R2.11's "report before, clear after": cleared after the edit, the entry would last as long as one `Edit` call, milliseconds, and nobody would see it.
  - The agent is R2.11's rule 7.
- **`end`** clears that entry and removes the id file.
- **It never fails a tool call.** It always exits 0, prints nothing on stdout or stderr (failures go to the debug log), never starts a daemon (`--no-autostart` is implied), and gives up after 2 seconds overall. Claude Code reads stdout as a decision when it is JSON, and shows stderr on a non-zero exit, so silence is the only safe output.
- **In R2.24's `OUTPUTS`**: `presence hook edit` and `presence hook end`, `json: None`, noted "nothing; reads a harness's hook event on stdin". They are run by test 9 here, and R2.24's test 9 lists them as run elsewhere.

`plugins/claude-code/hooks/hooks.json`:

```json
{"hooks": {
  "PreToolUse": [{"matcher": "Edit|Write|MultiEdit|NotebookEdit", "hooks": [{"type": "command", "timeout": 5,
    "command": "command -v reef >/dev/null 2>&1 && reef presence hook edit --path-at /tool_input/file_path --path-at /tool_input/notebook_path --session-at /session_id || true"}]}],
  "SessionEnd": [{"hooks": [{"type": "command", "timeout": 5,
    "command": "command -v reef >/dev/null 2>&1 && reef presence hook end --session-at /session_id || true"}]}]
}}
```

The guard keeps a missing `reef` from printing an error on every edit. The MCP server's failure to start already says that `reef` is missing.

### The registry listing: MCPB bundles

The listing uses MCPB bundles on the GitHub release, not crates.io. Publishing the crates would mean:

- publishing nine crates in order, each version permanent;
- moving `reef-daemon`'s `testing` helper out, because it depends on the unpublished `reef-testing`;
- copying the guide into `reef-vcs` (ADR 0025);
- putting a generated web bundle into `reef-web`'s package (R2.18's question);
- `cargo install`, a Rust toolchain and a long build for every user the listing reaches.

MCPB reuses the release's binaries and adds no account. R2.18's question 1 stays open for whichever ticket publishes crates.

- **One bundle per target**, `reef-<version>-<target>.mcpb`. Four bundles: the format has no architecture field, so each target gets its own. Each is a zip of `manifest.json`, `reef`, `reef-daemon`, `LICENSE` and `README.md`.
- **The manifest.**

  ```json
  {"manifest_version": "0.3", "name": "reef", "display_name": "Reef",
   "version": "<version>", "description": "<DESCRIPTION>",
   "author": {"name": "Reef contributors", "url": "https://github.com/reef-vcs/reef"},
   "repository": {"type": "git", "url": "https://github.com/reef-vcs/reef"},
   "license": "Apache-2.0", "homepage": "https://github.com/reef-vcs/reef",
   "server": {"type": "binary", "entry_point": "reef",
              "mcp_config": {"command": "${__dirname}/reef", "args": ["mcp"]}},
   "tools": [{"name", "description"}, …],
   "compatibility": {"platforms": ["darwin"]}}
  ```

  - `tools` lists the 21 tools' names and descriptions from `mcp::tools` (what `reef schema mcp` prints), so the bundle's listing cannot drift from the server. That is R2.24's "ship the definitions in a package", at the size a listing shows.
  - `platforms` is `darwin` or `linux` by target.
  - `reef` finds `reef-daemon` beside it.
- **`scripts/package-mcpb.sh <bin-dir> <version> <target> <out-dir>`** stages the bundle, writes the manifest from `packaging/mcpb/manifest.json` with `jq` (version and platform), runs `npx --yes @anthropic-ai/mcpb@2.1.2 validate` and `pack`, and prints the bundle's path. Bundles are not signed (`mcpb sign`); signing is R4.17's, with the binaries'.
- **`scripts/mcp-server-json.sh <version> <SHA256SUMS>`** writes `server.json` from `packaging/mcp/server.json`:
  - `$schema` 2025-12-11, `name` `io.github.reef-vcs/reef`, `title` "Reef", `description` "Version control for fleets of coding agents: isolated workspaces, status, diff and history." (89 characters), `version`, `repository` `{"url": "https://github.com/reef-vcs/reef", "source": "github"}`, `websiteUrl`.
  - Four `packages`, each `{"registryType": "mcpb", "identifier": "https://github.com/reef-vcs/reef/releases/download/v<version>/reef-<version>-<target>.mcpb", "version": "<version>", "fileSha256": "<from SHA256SUMS>", "transport": {"type": "stdio"}}`.
  - It fails unless there are exactly four bundles, each with a checksum.
- **Linux bundles are listed too.** No documented Linux client installs MCPB today, but a client that reads the registry can, and the listing's version and checksums are the same either way.
- **The session's directory.** A client such as Claude Desktop starts the server in a directory that is not a repository, so tools act only when given `repo`. The server's instructions already say to pass it (R2.13). Nothing is added.

### The release workflow

- **Triggers**: `pull_request.paths` gains `plugins/**`, `.claude-plugin/**` and `.agents/plugins/**` (`packaging/**` and `scripts/**` are already there).
- **`check-version`** also checks:
  - every `plugin.json`, `packaging/mcpb/manifest.json` and `packaging/mcp/server.json` names the workspace version;
  - both marketplaces' refs are `v<version>`.

  It checks on dry runs too, so a release PR that forgets `just packages` fails before the builds.
- **`build`**, after `Package`:
  - `actions/setup-node` (the web job's `.node-version`), then `scripts/package-mcpb.sh`, then `scripts/test-mcpb.sh` on the bundle (test 12).
  - On `x86_64-unknown-linux-musl` only: `reef schema` into `reef-<version>-schema.json` and `reef schema --descriptor-set` into `reef-<version>-api.binpb`.
  - The artifact uploads `dist/*.tar.gz`, `dist/*.mcpb` and those two files.
- **`checksums`**: `SHA256SUMS` covers every file in `dist`. The count check becomes four tarballs and four bundles. `install.sh` and `update-tap.sh` look up their tarball's line by name, so the added lines do not affect them (test 15 checks).
- **`harness-packages`** (new, needs `checksums`, `ubuntu-24.04`): tests 13 and 14, against `reef` installed by `install.sh` from this run's tarballs. It needs no secret.
- **`release`**: `attest-build-provenance`'s subjects add `dist/*.mcpb`, `dist/reef-*-schema.json` and `dist/reef-*-api.binpb`, and `gh release create` attaches them.
- **`mcp-registry`** (new, needs `release`, publish runs only, `permissions: id-token: write, contents: read`):
  1. Download `mcp-publisher_linux_amd64.tar.gz` v1.8.7 and its `.sigstore.json`, then verify them with `cosign verify-blob` (pinned `sigstore/cosign-installer`) against the registry's release workflow identity.
  2. Write `server.json` with `scripts/mcp-server-json.sh`.
  3. Check that every package URL answers HEAD with 200.
  4. Run `mcp-publisher login github-oidc` and then `mcp-publisher publish`.

  Like `homebrew`, a failure warns and does not fail the release. The warning gives the manual command: `scripts/mcp-server-json.sh <v> SHA256SUMS > server.json && mcp-publisher login github && mcp-publisher publish`. Note that `login github` cannot publish to an organization's namespace (registry issue #1468), so a manual publish needs a token from an owner of the organization, with `read:org`.
- **`harness-packages-live`** (new, needs `release` and `mcp-registry`, publish runs only, warns rather than fails):
  - Runs Claude Code's and Codex's install lines exactly as documented against `reef-vcs/reef`, now that the tag exists, and checks the result as test 13 does.
  - Fetches `https://registry.modelcontextprotocol.io/v0/servers?search=io.github.reef-vcs/reef` and checks that the new version is listed.
- **Dry runs** do everything up to `release`: build the bundles, validate them and run them, write `server.json`, and run `mcp-publisher validate` (which calls the registry's validate endpoint without a credential and publishes nothing). Nothing is published, attested or listed.

### Threat model

`docs/threat-model.md` gains a "Harness packages" paragraph:

- The plugins run only the `reef` on `PATH`. They download nothing, and are pinned to release tags.
- The hooks run `reef presence hook` before every edit. It reads only its stdin and writes only a presence entry and an id file under the state directory.
- The bundles hold the release's unsigned binaries (S-14). Their provenance is attested like the tarballs', and the registry does not check their hashes; clients do.
- A bundle's `reef` and a separately installed `reef` of another version share one daemon per user. The existing version check restarts an idle daemon of another version, or names the mismatch (R2.13).

No new S-row: these are S-14 and the one-uid decision, seen from a new install path.

## Implementation notes

- **JSON Pointer**: `serde_json::Value::pointer` is RFC 6901. No dependency.
- **The workspace for a path**: reuse `cli::scope`'s "workspace containing a directory" step with the path's parent, not the process's directory. A hook runs in the project's directory, which may be the root checkout while the edit is in a workspace.
- **The id file's directory** is created with mode `0700`. A stale id file (the entry expired) is handled as R2.11's `--id-file` handles it: `PRESENCE_NOT_FOUND` reports a new entry.
- **The 2-second budget** is a deadline on the whole command, connect included, not per RPC, enforced with a `tokio::time::timeout` around `run`. Claude Code's `timeout: 5` is the outer bound.
- **`toml_edit`**: append with `DocumentMut::insert("mcp_servers", …)` only when the key is missing. When `mcp_servers` exists as a table, insert `reef` into it (an implicit table if the file uses dotted `[mcp_servers.x]` headers), so the file's style is kept. Test 3's fixtures cover both styles.
- **Blessing** uses the same renderer as the check, so `just packages` followed by the test always passes. The test's failure message names `just packages`.
- **macOS and Linux** build the same code. The hook test runs on both CI runners.
- **The pinned harness versions** go in `release.yml`'s `env` (`CLAUDE_CODE_VERSION` as in `onboarding.yml`, `CODEX_VERSION`, `OPENCODE_VERSION`, `MCPB_VERSION`, `MCP_PUBLISHER_VERSION`). A bump is a PR that runs the dry run.

## Performance expectations

- `reef presence hook edit` takes under 50 ms with a daemon (one scope call and one `ReportPresence` over the Unix socket), and under 10 ms with none (the connect fails at once). The PR reports both, measured in a release build from test 9's fixture.
- `packages_are_current` takes under 1 s.
- Each bundle is about the tarball's size (the same two binaries). The release grows by four bundles and two small files, and the PR reports their sizes.
- `harness-packages` takes under 10 minutes (three npm installs and the checks).

## Risks

- **Codex's plugin facts are thin.** Its documentation centers on the desktop app, and `git-subdir`'s `ref`, the `policy` values and the CLI's need for a sign-in are unverified. The brief decides both fallbacks in advance (a `local` source with `--ref`, or no Codex plugin at all), and test 14 decides between them.
- **The registry is in preview** and may reset data. A reset loses the listing until the next release republishes it. `mcp-registry` warns, and its message gives the manual command.
- **macOS quarantine.** A client that downloads a `.mcpb` may mark the binaries quarantined, and unsigned binaries may then not start under Gatekeeper. This is unverified, since no client documents it. The PR installs a bundle in Claude Desktop on macOS by hand and records the result. If it fails, the listing ships, the quickstart notes it, and R4.17 fixes it.
- **Two copies of the skill in opencode.** opencode reads both `.claude/skills` and `.agents/skills`, so a repository with Claude Code and opencode has two `reef` skills. Test 14 checks how opencode lists them. If it shows two or errors, opencode's row writes `AgentSkill` only when `ClaudeSkill` is not also selected, and the test is updated.
- **Two Reef servers in one Claude Code session.** A person who installs the plugin and then runs `reef init` in a repository gets the plugin's `reef` server and the project's `.mcp.json` entry, and two `reef` skills. If Claude Code loads both, the tool list's fixed cost (#116) doubles. The implementer checks this in test 13 (install the plugin in the scratch `HOME`, add a project `.mcp.json` and skill, and read the `init` event or `claude mcp list`). If both load, the PR records it and files a follow-up issue. `reef init` does not skip the project's files because one person installed the plugin: `.mcp.json` and the skill are committed for everyone who works in the repository, and what it writes must not depend on the machine. If Claude Code deduplicates them itself, nothing changes and the PR says so.
- **Hooks on every edit** cost one local RPC each. Test 10 and the performance numbers bound it, and a daemon that is down costs a failed connect.
- **The window between the release PR and the tag**, when the marketplaces name a tag that does not exist yet. It lasts minutes and fails with a clear git error. The release checklist in `CONTRIBUTING.md` says to tag right after merging.
- **Harness formats move fast** (Claude Code ships several releases a week). The pins and the dry run on every PR that touches the packages catch a break before a release, not after.

## Choices this brief made, and why

- **The neutral surfaces first, packages as adapters.** A package adds only what a harness cannot read from `AGENTS.md` and MCP. That is the north star, and it keeps the packages small.
- **One table.** Detection, files, home directories, package format and hook pointers are all rows in `SIGNS`, so adding a harness is a row and its verified facts.
- **Rendered and committed, not generated at release.** The marketplaces read git, and the check makes drift a test failure, as `just agent-files` does for `AGENTS.md`.
- **Pinned to tags.** Users get what the released binary supports.
- **Named by format.** `agent-plugins` serves any harness that adopts the standard.
- **`reef init --user` for opencode.** It is honest about what opencode's plugins can carry, and needs no npm account.
- **A generic hook command with pointers.** The CLI learns JSON Pointer, not Claude Code.
- **MCPB over crates.io.** It reuses the release, needs no account, and makes no permanent crate versions.
- **Warn, don't fail, on outward steps.** The release is the binaries; the tap and the listing follow it, as R1.28 decided for the tap.
