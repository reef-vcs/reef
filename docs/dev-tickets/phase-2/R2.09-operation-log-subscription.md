# R2.09 Operation log subscription

Phase 2 · Size M · Depends on: R2.02 (`Operations.Log` and the `Operation` message it fills; `RepoHandle::head()`), R2.01 (`reef-api`, the `v1` schema with `Operations.Subscribe`, `Event` and `Frame` as stubs) · Unblocks: R2.10 (presence rides the same broker and frames), R2.12 (replay resolves `seq` through the index this ticket writes), R2.13 (the `reef_wait` tool blocks on `Subscribe`), R2.18 to R2.21 (every live view), R2.22 (the load test measures this path)

## Context

The design makes the operation log the event stream: "the daemon and the store expose a streaming subscription filtered by repository, change, workspace, or agent, and clients render deltas rather than polling" (`docs/design.md`, API). Phase 1 has the log (jj's, read through `reef_lib::jj::oplog`) and one index over part of it (the `snapshots` table, R1.16), but nothing that tells a client an operation happened: the web UI, the MCP server's wait tool, and the SDKs would all poll `Operations.Log`, and the Phase 2 exit criterion ("a client can subscribe to the operation log and presence channel and receive events within 100 ms") would have nothing to measure.

This ticket gives the daemon one place through which every operation it observes passes, an index that assigns each a daemon-wide sequence number, and a server-streaming RPC that delivers them in frames with a resumable cursor. Operations the daemon writes itself (snapshots, creates, releases, moves, R2.03's describe and undo) are the common case; operations written by the `jj` CLI in the registered root are the other, and they are noticed by a watch on jj's operation heads directory. The broker built here is the one the presence channel (R2.10) shares and the store reuses in Phase 4 (`docs/design.md`, Scale: "a broker between the operation log and the connections").

## Decisions

The README's "Events and presence" rows are binding; this section repeats what this ticket implements and adds the decisions below them.

- **One interception point: the repository thread's loop.** `thread.rs`'s `run` records `head.repo.op_id()` before each job and compares after the job and after any reload it does. A changed id means operations were written or loaded, and the thread computes the delta there, on the thread (jj-lib reads, `pollster::block_on`), as plain `IndexedOp` structs: `walk_ancestors_range(&[new_head.operation()], &[old_op])` with `old_op` loaded by `load_operation(old_id)`. The structs go to the broker's indexer over an unbounded `tokio::sync::mpsc::UnboundedSender<OpDelta>`, so the thread never waits on SQLite (Phase 1's rule: SQLite stays off the repository thread). Two cases are not a range: a GC job (the old head is not an ancestor of the new one) and a reopen after a panic (`RepoHead::reopen`, R2.08's RX.01 fix); both send `OpDelta::Rewritten { repo }` and the indexer runs a reindex instead. `RepoHead` gains `note_rewritten()`, which `Manager::gc_jj`'s job calls, and the loop sends `Rewritten` when it sees the flag or when `reload` reopened. `RepoHead::note_committed` stays as it is (unused by this path; the comparison does not need it).
- **`Event.at` is stamped on the repository thread.** When the loop computes a delta, right after the job that committed or loaded the operations and before anything is sent to the indexer, it stamps `IndexedOp.observed_at = Timestamp::now()`; that value becomes `Event.at`, unchanged by the indexer and the broker. R2.22 measures `received_at − at` as delivery latency (what the exit criterion gates) and `at − end_at` separately as the gap between jj's own end time and the daemon noticing, which is zero for the daemon's writes and the debounce for external ones. Workspace and lease events are stamped `at` where they are published, before `publish`.
- **`changes`: what an operation moved.** For each operation in the delta, the thread loads its view and its first parent's view and records the change ids of (a) every `wc_commit_ids` entry whose commit differs, (b) every commit in `head_ids` that the parent lacks, each resolved to its change id through `store().get_commit_async`. Merge operations (two parents) diff against the first parent. The root operation has none. A commit that cannot be read (RX.01's hostile-tree refusal) is skipped with a `debug` line, never a failed index.
- **`kind`** from the description, which the daemon owns (`snapshot/mod.rs:173-183`, `create.rs:77, 707, 755`, `reclaim.rs:265`, `rematerialize.rs:171`, `manager.rs:772`, `abandoned.rs:93`): `reef: snapshot workspace`, `reef: final snapshot of workspace` → `snapshot`; `reef: create workspace` → `create`; `reef: release workspace` → `release`; `reef: move workspace` → `move`; `reef: rematerialize workspace` → `create`; `reef: import git refs` → `import`; R2.03's `reef: describe`, `reef: abandon`, `reef: squash`, `reef: undo operation` and jj's `undo: restore to operation` → `describe`, `abandon`, `squash`, `undo`; R2.04's `reef: apply edit` → `apply`. Anything else is `external` with `external = 1`: jj's `snapshot working copy` in the user's checkout, `jj describe`, `jj rebase`, whatever a human ran. The daemon never writes a `gc` operation (GC rewrites); the kind exists in the proto for Phase 4. `workspace_id` comes from `metadata.workspace_name` when it is `reef-<id>` (as `is_reef_snapshot` reads it), else from the description's id.
- **The index.** Migration `0006_operations` as the README fixes it (`operations(seq, repo_id, op_id, parents, description, kind, workspace_id, username, hostname, is_snapshot, external, changes, start_at, end_at, indexed_at)`, `UNIQUE (repo_id, op_id)`), plus `gc_rewritten INTEGER NOT NULL DEFAULT 0` (the README's GC rule names the flag) and a second table in the same migration for the workspace and lease events the README says are indexed too: `workspace_events(seq INTEGER PRIMARY KEY, repo_id TEXT NOT NULL, workspace_id TEXT NOT NULL, kind TEXT NOT NULL CHECK (kind IN ('created','snapshotted','released','reclaimed','moved','attention','lease_issued','lease_expired')), op_id TEXT, lease_id TEXT, detail TEXT, at INTEGER NOT NULL)`. **`seq` is one sequence across both tables**: the indexer task, the only writer, assigns it from `meta.event_seq` (`SELECT ... FOR UPDATE` is not SQLite; read-increment-write inside the one `in_transaction`, which the connection mutex serializes), so a cursor orders operations and workspace events together and `operations.seq` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`. See "Proposed departure from the README" for why. Indexes: `operations(repo_id, seq)`, `operations(repo_id, workspace_id)`, `workspace_events(repo_id, seq)`.
- **The broker.** `reef_daemon::events::Broker` (new module `crates/reef-daemon/src/events/`): a `tokio::sync::broadcast::Sender<Arc<Event>>` of capacity `[events] buffer` (default 4,096), the indexer task's input channel, the `Db`, and the current `seq` (`AtomicI64`, loaded from `meta.event_seq` at start). Everything that happens goes through `Broker::publish(Pending)`, which hands the indexer a `Pending::Op(IndexedOp) | Pending::Workspace(WorkspaceEvent) | Pending::Lease(LeaseEvent) | Pending::Presence(..)` (R2.10). The indexer assigns `seq`, writes the row (not for presence or heartbeats), then sends the `Event` on the broadcast channel: a subscriber never sees a `seq` the index lacks, so catch-up and live never disagree. `Broker` is a trait (`trait EventBroker: Send + Sync { fn publish(..); fn subscribe(..) -> Subscription; fn current_seq(..); }`) with `InProcessBroker` the one impl; the gRPC service holds `Arc<dyn EventBroker>` so Phase 4 can put the store's behind it.
- **Workspace and lease events.** Published from the write points verified above, after the row they describe is written: `created` from `Manager::create` after `issue_with_workspace`; `snapshotted` from a `SnapshotHook` the broker registers (`changed` only; an unchanged scan is not an event); `moved` after `record_move`; `released` and `reclaimed` after `finish_workspace`, with the `ReclaimRecord`'s `final_op_id` and `reason` in `detail`; `attention` from one new `Manager::set_attention(id, value)` that the five `set_workspace_attention` call sites route through (same SQL, one publish); `lease_issued` beside `created` and from `LeaseManager::issue` (restore); `lease_expired` from `tick_once` when a reclaim for `Expired` succeeds. Heartbeats are `LeaseEvent { kind: heartbeat }` on the broadcast channel only, not indexed (see the departure): 200 workspaces heartbeating every 60 s would be 288,000 rows a day that no view reads back.
- **`Operations.Subscribe`.** `SubscribeRequest { repo, resume_after_seq, filter: EventFilter { changes, workspaces, owners, kinds } }` → `stream Frame { events: repeated Event, from_seq, to_seq, coalesced: uint32, lagged: bool }`. The handler validates `repo` (empty = every repository), resolves `owners` to workspace ids at subscribe time plus live (an owner's new workspace matches from its `created` event on), and spawns the subscription task: it subscribes to the broadcast channel *first*, then, when `resume_after_seq > 0`, pages the index (`seq > cursor`, `[events] frame_max` rows a page, `operations` and `workspace_events` merged by `seq`) until it reaches the current `seq`, then drains live events, dropping any with `seq <= cursor`. Each frame is cut at `[events] frame_interval` (50 ms) since its first event or `frame_max` events, whichever first; a frame's `from_seq`/`to_seq` is the range it covers and `coalesced` the number of events in that range the filter excluded, so a client that counts sees every event once. `resume_after_seq = 0` is "from now": no catch-up, the first frame's `from_seq` is the current `seq + 1`. A client that wants to resume where a repository stands reads `Daemon.Status.seqs` for that repository. A `resume_after_seq` older than the index holds (after GC's row drops) is `INVALID_ARGUMENT` with the hint naming the oldest `seq` and `next = ["reef","watch","--since","<oldest>"]`.
- **Lag.** On `RecvError::Lagged(n)` the task logs at `warn` with `n` and the client's filter, sets `lagged = true` on its next frame, and re-enters catch-up from its last delivered `seq`; the index has every event, so nothing is lost, only delayed. A client that cannot drain even the index pages (its `mpsc` to tonic stays full for `[events] slow_client_timeout`, default 30 s) is closed with `RESOURCE_EXHAUSTED`; it may reconnect with `resume_after_seq`.
- **The op-heads watch.** The notify watcher gains `watch_op_heads(repo: RepoId, dir: PathBuf)` and `unwatch_op_heads(repo)`, a `RecursiveMode::NonRecursive` watch on `<repo>/.jj/repo/op_heads/heads/` through the same debouncer. `Demux` gains `op_heads: BTreeMap<PathBuf, RepoId>`; `route_batch` sends paths under one of them as `OpHeadsEvent { repo, at }` on a second channel (`mpsc::Sender<OpHeadsEvent>`) the events module owns, one per batch per repository (the debouncer coalesces a burst of `jj` commands into one). A rescan event marks every op-heads repository too. The events module's task runs `handle.call_async(|head| head.refresh())` for each; the thread's loop then sees the new head and indexes the range. The watch is attached at registration and daemon start (after the repository thread is up) and removed on forget; a failed watch is logged at `warn` and the repository is `op_heads_watch = false` in `Daemon.Status`'s per-repository list, with external operations then noticed only by the next transaction or reindex, as today. The watch is notify's for every repository, Watchman ones included: Watchman subscribes per workspace root and would need the user's checkout under its watch for one directory, and inotify costs one watch for it.
- **Reindex.** `events::reindex(db, handle, repo, limit)` runs at start (after R1.16's, per repository), after GC and after restore, and on `OpDelta::Rewritten`: walk up to `gc.reindex_limit` operations from head on the thread; for each operation with no row, look for a row with the same `(view_id, start_at, end_at, description, username, hostname)` whose `op_id` the walk did not reach: a GC rewrite keeps all of them (verified above), so that row's `op_id` is updated in place and its `seq` kept; otherwise insert a new row (seq at the tail, in walk order reversed so older operations get smaller seqs). Rows whose operation the walk did not reach and no rewrite matched are marked `gc_rewritten = 1` (unless the walk was truncated, as R1.16 does). `Replay` (R2.12) answers `NOT_FOUND` for a `gc_rewritten` row. The report (`added`, `remapped`, `marked`, `walked`, `truncated`) is logged at `info` and kept in `AppState.events_reindexed` beside R1.16's.
- **`Daemon.Status`** gains `repeated RepoSeq seqs { repo_id, seq }` (the newest `seq` indexed for each registered repository; the cursor itself is daemon-wide and monotone, so a repository's value is where a subscription to that repository alone stands) and `events_buffer: uint32`; **`Workspace`** is unchanged here (R2.10 adds `presence`). Every mutating response gains `seq` as the README says (R2.03 fills it for its RPCs; this ticket fills it for `Create`, `Release`, `Move`, `Snapshot`, which it already touches).
- **`reef watch`.** `reef watch [--repo] [--change <rev>]... [--workspace <id>]... [--owner <str>]... [--kind <kind>]... [--since <seq>] [--once]`: text mode prints one line per event (`<seq> <time> <kind> <repo-short> <workspace-short> <op-short> <description>`; a `lagged` frame prints `reef: lagged; catching up from <seq>` on stderr); JSON mode prints one `Frame` object per line (`reef_api::json::Frame`), so a consumer parses lines and never a growing array. `--since 0` (the default) is from now; `--since <seq>` resumes; `--once` exits after the first frame (for scripts and the tests). Never interactive; `Ctrl-C` exits 0.
- **ADR 0031, "Operation index and event broker"**: the index as the cursor and the thread's loop as the interception point; why the broker is in-process and a trait; the frame and lag rules (coalesce, never drop; the design's live rules); why workspace and lease events are indexed and heartbeats are not; the op-heads watch and its debounce latency; GC's rewrite mapping and `gc_rewritten`; the alternatives (polling `Operations.Log` per subscriber, a trigger-based `jj` hook, indexing views in full, a second inotify instance for op heads). Its consequences end with a dated paragraph headed **Measured** that holds only "pending R2.22" when the ADR is accepted: ADRs are frozen after acceptance, and this paragraph is the one place R2.22 edits, with the load test's delivery latency (`received_at − at`), the broker-versus-polling difference, and the date.

## Implementation notes

- Compute the delta on the thread but keep it cheap: `ops_since` loads two views per operation (its own and its first parent's); a snapshot burst of 200 ops is 400 small protobuf reads from `op_store/views/`. The 10,000 cap makes a pathological external history a reindex, not a stall.
- Subscribe to the broadcast channel before the catch-up read, and dedupe by `seq`; otherwise an event indexed between the read and the subscribe is lost. The indexer publishes after the write, so "subscribed before reading" is sufficient.
- `broadcast::Receiver::recv` returns `Lagged(n)` once and then resumes from the oldest retained; the task must not trust those retained events to be contiguous with its cursor: go to the index.
- The indexer runs on tokio but its SQLite work goes through `spawn_blocking` as every other `Db` write does; `publish` is a `send` on an unbounded channel from any thread (the repository threads are `std::thread`s).
- Shutdown order matters: the scheduler's shutdown snapshots write operations; the broker stops after them, draining the queue, so a restart's reindex has nothing to add for a clean shutdown (test 9 covers the unclean case).
- The op-heads watch is one `inotify_add_watch` per repository; attach it after `RepoThread::spawn` so the first refresh finds a loaded head.
- `reef watch` with `-o json` must flush after every frame (`Out::json_only` buffers per call; add `Out::json_line`).
- R2.10 adds `Pending::Presence` and the presence service; leave the `Payload::Presence` arm compiled but unused here (`#[allow]` with a comment naming R2.10).

## Out of scope

- Presence (R2.10), replay (R2.12), the web UI's use of frames (R2.18), the load test and the broker's measured benefit (R2.22).
- `Operations.Log` and `Operations.Get` (R2.02), which read the index this ticket builds for `seq` and `changes`.
- Watching the op heads of a repository the daemon has not registered, or of the user's other jj workspaces.
- Persisting presence or heartbeats.
- Filtering by path or by symbol (R2.16's queries).

## Risks

- **External operations arrive after the debounce.** The op-heads watch goes through the same `notify-debouncer-full` as workspace roots, so a `jj` command's operation is noticed up to `watcher.debounce` (500 ms) late plus the refresh. The 100 ms criterion is measured on operations the daemon writes (R2.22); the ADR says so. A dedicated undebounced watch would need a second notify watcher (one more inotify instance) and is the alternative recorded.
- **The repository thread does more per job.** Two view loads per new operation, on the thread that is the write lock. For the snapshot pipeline that is one operation per job; the cost is microseconds against a scan. A 10,000-operation external import triggers a reindex, which runs the walk once.
- **GC remapping relies on `reparent_range` keeping metadata.** Verified for jj-lib 0.46.0; a jj-lib change that touched `time` or `description` on rewrite would turn remaps into `gc_rewritten` marks, which is the fallback, not a loss. Test 8 would catch it on a bump.
- **Owners are strings.** `filter.owners` matches `workspaces.owner`, which R3.03 replaces with a session identity; the filter field keeps its name and the ADR notes the change.
- **`meta.event_seq` and the row writes must be one transaction**, or a crash between them leaves a `seq` the index lacks; `Db::in_transaction` gives that, and the indexer is the only writer of both.

## Proposed departure from the README

*Accepted 2026-10-25: the README's "Operation index" row now has `seq` assigned from `meta.event_seq` across `operations` and `workspace_events`, no `AUTOINCREMENT`, `gc_rewritten`, and heartbeats off the index.*

The README fixes `operations.seq INTEGER PRIMARY KEY AUTOINCREMENT` and says workspace and lease events "are indexed too" with `seq` as the one subscription cursor. Those cannot all hold: SQLite's `AUTOINCREMENT` is per table, so workspace events in their own table would get their own sequence and a cursor could not order the two. This brief assigns `seq` from `meta.event_seq` in the indexer's transaction (one writer, one counter, both tables) and drops `AUTOINCREMENT`; `operations.seq` stays the `INTEGER PRIMARY KEY`. It also keeps lease heartbeats off the index (live `LeaseEvent`s only, and presence in R2.10) because they are the one event kind with a steady write rate and no reader of their history. If the parent prefers the README's text as written, the alternative is a single `events` table holding both kinds with a `payload` column, which keeps `AUTOINCREMENT` but puts operation columns behind a discriminator; this brief did not take it because the `operations` table is also what R2.02's `Operations.Log` and R2.16's queries read by column.
