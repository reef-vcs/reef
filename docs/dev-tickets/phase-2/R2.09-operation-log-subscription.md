# R2.09 Operation log subscription

Phase 2 · Size L (the row says M; see "Size") · Depends on: R2.02 (operation reads, classification, effects and their cache, `OperationFilter` semantics), R2.13 (the wait tool this ticket moves onto the stream), R2.27 (`reef op log`, the CLI's JSON and advice, which `reef op watch` extends) · Unblocks: R2.10 (presence over the same connection, on this ticket's session machinery), R2.12 (replay builds on `after_operation`), R2.18 (the web UI's live views); R2.22 adds the broker behind this ticket's `Feed` and measures 500 subscribers

## Context

The operation log is Reef's event stream (design.md, Subscriptions): every snapshot, create, move, release, describe, abandon, undo, edit and ref import is one jj operation, and R2.02 made each one readable with its kind, workspace, agent and effects. A client that wants to know what changed has to poll for it: R2.13's `wait_for_operations` reads `ListOperations` twice a second per waiting call, and the CLI has no way to follow the log at all.

R2.01 declared `SubscribeOperations` in full and the daemon answers it `NOT_IMPLEMENTED`. This ticket implements it: a server stream of frames, filtered by repository, change, workspace, agent and kind, resumable from an operation or from a frame's cursor, with every operation Reef records delivered within 100 ms. The work is in what the declaration leaves open: how the daemon learns of a new operation (it has no notification today), what an operation written by another `jj` process does, what "resume" means on a log that is a graph, how frames are cut, what a slow client costs, and what happens across GC, a forgotten repository, and a daemon restart. It then moves the MCP wait tool onto the stream, as R2.13 promised, and adds `reef op watch`, R2.27's deferred `op log --follow`.

The phase's exit criterion has two halves: events within 100 ms, and that with 500 subscribers at 1,000 operations a minute. R2.22 owns the second (its broker and load test). This ticket delivers the first for one to ten subscribers, and puts the log reading each subscription does behind one function, `Feed::read`, which R2.22's broker replaces without touching anything else.

R2.01's rule binds this brief: it implements what R2.01 declared and only adds. It adds one field (below); nothing declared changes meaning.

## Decisions

### Size

L. The row's three phrases hide a notification path through every write, a poll for other `jj` writers, a resumable position on a graph, frames with a byte budget, flow-control backpressure, GC and forget and shutdown, a schema field and four reasons, a client method, a CLI command with reconnection, the MCP tool's move, an ADR, and about twenty tests. That is the breadth of R2.13, which was L. It is not bigger than L, so it is not split: the CLI command and the MCP switch are each about a day, and R2.13 promised the switch here.

### What a subscriber receives

- **Frames of `Operation`s exactly as `GetOperation` returns them**: classified by R2.02's rules (`oplog::classify`, the snapshot index for the snapshot kind), with `workspace_id`, `agent` (the `reef.agent` attribute, else the workspace's owner) and `effects` always computed (through `Reads::effects` and its cache). An operation whose effects cannot be computed is sent with `effects` unset and a `warn` log, as R2.02's write path does; a `changes` filter does not match it.
- **Order.** Within a repository, every operation comes after its parents (those not already behind the subscription's start), across frames too, and no operation comes twice. Operations on concurrent op heads interleave newest-end-time-first reversed, which for one clock is oldest first. Repositories interleave in no stated order; one repository's operations in a frame are contiguous.
- **Nothing is dropped and nothing is summarized.** Every operation the filter keeps is sent; design.md's "coalesce, never drop" is met by batching into frames, and summarizing a feed with correct counts is the UI's (R2.21) over a complete stream.
- **The filter** is `OperationFilter` with `ListOperations`' semantics (values ORed within a field, fields ANDed): `kinds`, `agents` exactly, `workspaces` resolved once at the start as `GetWorkspace` resolves a `workspace` with an empty `repo` (any state; unknown is `NOT_FOUND`), and `changes` as hex or reverse-hex prefixes matched against effects (past the 1,000-entry cap too). R2.02's `Filter`, `keeps` and `touches` move to `service/op_filter.rs` as `OpMatcher`, which both RPCs use; `ListOperations`' behavior and tests do not change. The owners map is read once at the start and re-read when an operation names a workspace it does not hold.

### How the daemon learns of a new operation

- **A wake-up from the repository thread, for every operation Reef records.** `repo/thread.rs`'s loop reads the loaded operation's id and the generation before each job and again after the job and its reload; when either changed, it calls `OpEvents::moved(repo, head.readonly())`. That one place covers every write path above, the merge a reload commits, and outside operations a reload happens to load. The job's reply may reach its caller a few microseconds before the wake-up; nothing depends on the order. `RepoHead` gets the `Arc<OpEvents>` from `RepoRegistry`, which takes it through `RepoRegistry::with_owners(owners).with_events(events)` (`RepoRegistry::new()` for tests has none, and the loop then skips the call).
- **A poll of the op heads, for other `jj` processes.** For each repository at least one subscription follows, one task reads the op heads from the store (`oplog::op_heads` on the repository's last tip, on `spawn_blocking`, no read permit) every 200 ms, and calls `OpEvents::poked(repo)` when the set differs from the last one it or a wake-up saw. A `jj describe` in the registered root, or `jj` run inside a Reef workspace, reaches subscribers within about 200 ms plus the read; the daemon's next refresh may load it sooner. The poll costs one `readdir` of `.jj/repo/op_heads/heads` per followed repository per tick and stops when no subscription follows the repository. Watching that directory with notify was not chosen: FSEvents registration costs scale with unrelated directories on macOS (R1.29), and a 200 ms poll of one small directory is cheaper than a watch per repository.
- **`OpEvents`** (`subscribe/events.rs`) is the hub every subscription waits on: per repository a version counter, the last tip (`Arc<ReadonlyRepo>`, so a subscription reads the op store without a job on the repository thread, which may be busy materializing a create), the last op heads seen, the number of subscriptions following it, and the last rewrite (below); and one daemon-wide `tokio::sync::watch<u64>` bumped on every change, which a subscription awaits and then compares the versions of the repositories it follows. `RepoRegistry::open` calls `OpEvents::added(repo, tip)`, `close` calls `removed(repo)`, and GC calls `rewritten` (below). Waking every subscription for every operation is O(subscriptions) cheap work; R2.22's broker narrows it if its measurement says so.

### Positions, cursors, and resuming

- **A position in a repository is a frontier**: the op heads up to which every operation has been sent or filtered out. It starts as the op heads when the subscription starts (`H0`), or as given (`after_operation`: `{X}`; a cursor: the frontier it encodes). Sending an operation `o` replaces the frontier with `frontier − parents(o) + {o}`; a merge operation collapses it back to one id. What comes after a position is every operation that is an ancestor of the current op heads and not of the frontier: `after_operation` replays every operation that is not `X` or an ancestor of `X`, the meaning jj gives "after" on a graph.
- **`oplog::walk_after(repo, heads, frontier, limit) -> Result<OpRange, OpLookupError>`** in reef-lib computes it: jj's `walk_ancestors_range` algorithm (a queue by end time from the heads and the frontier, the frontier's ancestors marked unwanted as they are popped, stopping when only unwanted ones remain), written in reef-lib with a bound on operations read, because jj-lib's computes its first chunk without one. `OpRange { operations (parents first), unreached (frontier members that are not heads and that no operation in the range has as a parent: not in the history; computed only when the walk was not truncated), truncated }`. `Frontier` (sorted full ids, `advance(&OpEntry)`) lives beside it.
- **The cursor** is opaque base64url (no padding) of a versioned binary encoding (`subscribe/cursor.rs`): byte 1, then per followed repository its 8-byte id, a 2-byte count and the frontier's 64-byte operation ids. Every frame's `cursor` covers every repository the subscription follows. It is not bound to the filter: a client may resume with another filter, which applies from the cursor on. A cursor that does not decode is `INVALID_ARGUMENT`, reason `INVALID_CURSOR`. Repositories in the cursor that the request does not follow are ignored; followed repositories the cursor does not name start at their op heads.
- **`head_operation_ids`** (the one schema addition, below): when `repos` names exactly one repository, every frame also carries that repository's frontier in clear, sorted by id, one id unless the log has concurrent heads. It is what a client that filters needs to resume by `after_operation` without decoding the cursor: the MCP wait tool's `last_operation_id` on a timeout, and `reef op watch`'s note.
- **How far back.** A position may be at most 10,000 operations behind the op heads (`Limits::max_behind`) in each repository, the examine budget of a `ListOperations` page. Past that, the subscription fails, at the start or mid-stream for a client that stopped reading, with `FAILED_PRECONDITION`, reason `TOO_FAR_BEHIND`, metadata `repo_id`, hint "More than 10,000 operations were recorded after this point; read them with ListOperations, then subscribe without a start." At 1,000 operations a minute that is ten minutes of history.
- **An unknown start.** `after_operation` resolves as `GetOperation`'s id does: empty or not lowercase hex is `INVALID_OPERATION_ID`, ambiguous `AMBIGUOUS_OPERATION_ID`, unknown `NOT_FOUND`, reason `OPERATION_NOT_FOUND` (metadata `operation_id` each); an operation in the store that is not in the history (in `unreached`) is `FAILED_PRECONDITION`, reason `OPERATION_NOT_IN_HISTORY`. With other than exactly one repository in `repos` it is `INVALID_ARGUMENT` with no reason and the hint "after_operation needs exactly one repository in repos; resume several with cursor." A cursor whose operations are gone from the store, or not in the history, is `FAILED_PRECONDITION`, reason `OPERATION_LOG_REWRITTEN`, metadata `repo_id`, hint "This repository's operation log was rewritten (garbage collection) since the cursor; read the state again and subscribe without a start."
- **Replay and `live`.** A subscription with a start reads up to `H0` first: those frames have `live: false`. When the replay is sent, the next frame goes out at once with `live: true`, holding whatever was recorded since the start, or nothing. A subscription without a start sends that live frame first, empty, at once. So every subscription's first live frame arrives promptly and tells the client it is caught up, and the first frame of any subscription confirms where it starts (its `cursor` and `head_operation_ids`) before the client writes anything it wants to see.

### Frames

- **Bounds**: at most 1,000 operations (`Limits::frame_operations`) and at most 1 MiB encoded (`Limits::frame_bytes`); an operation is never split (effects caps keep one under about 300 KiB). 1 MiB rather than R2.02's 3 MiB page: a frame waits in memory per slow subscriber (below), and it stays far under tonic's 4 MiB decode limit for every client.
- **Timing.** A live frame with operations goes out as soon as they are read, unless the previous frame with operations went out less than 50 ms before (`Limits::frame_interval`): then the session waits out the 50 ms and reads everything new in one frame. An isolated operation is never delayed; a burst of a thousand a minute arrives in at most twenty frames a second. Replay frames, and the frame after one cut by a bound, go out as fast as the transport takes them.
- **Effects budget**: a frame read looks up at most 200 operations' effects (`Limits::effects_per_frame`), cached or not, as `ListOperations` counts them, then sends what it has; a replay of old history therefore comes in frames of a few hundred while effects are computed, and the session stays responsive to a dropped client and to shutdown between frames.
- **Keepalive**: an empty frame with the current `cursor` (and `head_operation_ids`, `live` as it stands) after 15 s without a frame (`Limits::keepalive`), inside the declared 30.
- Filtered-out operations advance the position without a frame; the next frame's or keepalive's cursor carries it.

### Backpressure and stream lifetime

- **Pull, not push.** Each subscription is one task feeding a `tokio::sync::mpsc` channel of capacity 1 that tonic drains through `tokio_stream::wrappers::ReceiverStream`. The task reserves a slot (`Sender::reserve`) before it reads the log for the next frame, so it reads only when the transport has taken the previous frame, and HTTP/2 flow control bounds what the transport holds. A slow client therefore costs one built frame, the transport's window, and its position: never a queue of operations. When it reads again it catches up from the log in full frames. Nothing is dropped; a client that falls more than 10,000 operations behind gets `TOO_FAR_BEHIND` and resumes from history (above).
- **Reads.** A frame's log read runs on the blocking pool under its own semaphore, `max(2, available_parallelism())` permits (`Subscriptions::permits`), not `Reads`' permits, so a slow diff never delays delivery and a burst of wake-ups cannot take every blocking thread. SQLite (owners, snapshot-index kinds) is read on the async side, before and after the blocking read, as R2.02 does.
- **At most 1,024 subscriptions at once** per daemon (`Limits::max_subscriptions`), a guard against a client that subscribes in a loop; one more is `UNAVAILABLE`, reason `TOO_MANY_SUBSCRIPTIONS`, hint "The daemon is serving its limit of 1,024 subscriptions; close one and subscribe again." R2.22's 500 fit.
- **A subscription lives until** the client cancels or disconnects (the task sees the channel closed, through `Sender::closed` while it waits, and ends; its slot is freed at once), the daemon shuts down, or it fails (`TOO_FAR_BEHIND`, `OPERATION_LOG_REWRITTEN`, a named repository forgotten). There is no server-side lifetime limit.
- **Shutdown.** Each task selects on `AppState::shutdown` and ends its stream at once with `UNAVAILABLE`, kind `unavailable`, no reason, hint "The daemon is shutting down; subscribe again with the last frame's cursor when it is back.", so streams never hold shutdown for `SHUTDOWN_GRACE`. No reason is the clients' existing signal for "the daemon went away" (R2.13 reconnects on it). Operations recorded during shutdown (the `shutdown` snapshots) and while the daemon was down reach a client that resumes with its last cursor after the restart.
- **Repositories come and go.** A repository registered after an all-repository subscription started is followed from its op heads at registration (its earlier history is not replayed, and its registration's own `import git head` is before that). A forgotten repository is dropped from all-repository subscriptions; a subscription whose `repos` named it ends with `NOT_FOUND`, reason `REPOSITORY_NOT_FOUND`, metadata `repo`.
- **GC.** In the GC's job, before `gc_with`, the daemon tells `OpEvents` a rewrite begins (`OpEvents::rewrite(repo)`), and in `gc_with`'s `abandoned` callback, which names the head it rewrote and the new one, where the op heads moved (`Rewrite::moved_to(before, after)`); dropping the guard ends the rewrite. Sessions do not read a repository while its rewrite is under way, nor across a rewrite they have not applied, and discard a read a rewrite overlapped. (Review: a position behind `before` reads up to `before` first, whose operations the undo window keeps, then moves to `after`; ending it, as below, made GC with an active workspace end live subscribers routinely.) A subscription whose frontier in that repository is exactly `{before}` (it had everything; GC snapshots and refreshes first, so a live subscriber usually has) moves its frontier to `{after}` and sends nothing: the rewrite records nothing new. Any other subscription following the repository ends with `OPERATION_LOG_REWRITTEN`. `Reads::clear` already drops the repository's cached effects.
- **Other log rewrites.** A `jj op abandon` or `jj util gc` in the registered root rewrites history without telling the daemon. The next read finds frontier members gone from the store or in `unreached`, and the subscription ends with `OPERATION_LOG_REWRITTEN`, never by re-sending rewritten operations as new ones.

### `Feed`: the seam R2.22's broker plugs into

`subscribe/feed.rs`:

```rust
/// What one subscription reads from one repository's log. R2.09 reads the
/// log per subscription; R2.22's broker serves the same call from memory.
pub(crate) async fn read(
    state: &AppState,
    repo: &Followed,          // id, handle, the tip from OpEvents
    after: &Frontier,         // the subscription's position
    upto: Option<&[OperationIdHex]>, // H0 while replaying; None: the current op heads
    matcher: &OpMatcher,
    budget: Budget,           // operations, bytes, uncached effects
) -> Result<Batch, SubscribeError>;

pub(crate) struct Batch {
    pub operations: Vec<v1::Operation>, // kept, parents first, with effects
    pub frontier: Frontier,             // after the last operation examined, kept or not
    pub more: bool,                     // the budget stopped it before `upto`
}
```

Everything else (the hub, the session's phases, frames, cursor, backpressure, keepalive, shutdown, rewrites, the cap) is the session's (`subscribe/session.rs`) and stays when R2.22 replaces `read`'s body. R2.22's broker subscribes to `OpEvents` once per repository, reads each new range once, converts and computes effects once, keeps a ring of recent `Arc<v1::Operation>`s, and answers `read` from the ring, falling back to this ticket's log read for a position older than the ring. That is the work its row names: "fan-out does not read the log per subscriber". This ticket measures latency for one and ten subscribers; R2.22 measures 500.

### Schema addition

`reef_api::API_REVISION` becomes 4 and `API_DIGESTS` gains its fourth entry (`crates/reef-api/src/lib.rs:49` and `:54`). One field, at the next free number:

```proto
// operations.proto
message SubscribeOperationsResponse {
  // …R2.01's fields 1 to 3…
  // When `repos` names exactly one repository: the operation heads this
  // frame's `cursor` stands at in it, full hex, sorted. Every operation that
  // is one of them or their ancestor has been sent or filtered out, so one
  // of them is an `after_operation` to resume from. One id unless the log
  // has concurrent heads. Empty when following several repositories.
  repeated string head_operation_ids = 4;
}
```

Why it is needed: `after_operation` is the declared way to resume by operation, and a client that filters never sees the operations it skipped, so without this it cannot name where it stands except through the opaque cursor. Comment-only changes that do not move the digest: `SubscribeOperations`' leading comment (below) replaces "Declared; R2.09 implements it."; `cursor` gains "Not bound to the filter."; `live` gains "The first live frame is sent at once, empty when nothing is new."

`SubscribeOperations`' comment states the order, the first frame, the bounds (1,000 operations, 1 MiB, live frames 50 ms apart, the keepalive), that nothing is dropped and a slow reader is held back and catches up, the 10,000-operation limit, and this "Errors:" paragraph (ADR 0029 checklist 9):

- `INVALID_ARGUMENT`: reason `INVALID_CURSOR`; `INVALID_OPERATION_ID` or `AMBIGUOUS_OPERATION_ID` (metadata `operation_id`) for `after_operation`; `INVALID_CHANGE_ID` (metadata `change`); an unknown `filter.kinds` value; `after_operation` without exactly one repository (no reason).
- `NOT_FOUND`: `REPOSITORY_NOT_FOUND` (metadata `repo`), also mid-stream when a named repository is forgotten; `REPOSITORY_NOT_REGISTERED` (metadata `path`); an unknown `filter.workspaces` value; `OPERATION_NOT_FOUND` (metadata `operation_id`) for `after_operation`.
- `FAILED_PRECONDITION`: `OPERATION_NOT_IN_HISTORY` (metadata `operation_id`); `TOO_FAR_BEHIND` (metadata `repo_id`), at the start or mid-stream; `OPERATION_LOG_REWRITTEN` (metadata `repo_id`), for a cursor or mid-stream.
- `UNAVAILABLE`: `TOO_MANY_SUBSCRIPTIONS`; no reason, mid-stream, when the daemon shuts down.

### Limits

`subscribe::Limits { max_behind: 10_000, frame_operations: 1_000, frame_bytes: 1 MiB, frame_interval: 50 ms, effects_per_frame: 200, keepalive: 15 s, outside_poll: 200 ms, max_subscriptions: 1_024 }`, `Default` as given. `Config` gains `subscribe: Limits`, set like `paths` and not a configuration-file key (`config show` does not list it), so tests shrink the limits through `TestDaemon::start_with` instead of writing ten thousand operations. No user-facing configuration: every client must be able to rely on the same frames from every daemon.

### Client

`reef_client::Client::subscribe_operations(request) -> Result<tonic::Streaming<SubscribeOperationsResponse>, ClientError>`, sending `reef-agent` like every call and no deadline: a caller bounds the response headers with its own timeout (`Ctx::call`) and each wait for a frame itself. A stream error converts through the client's existing `ClientError::from` for `Status`, so `reason`, `hint`, `next` and `metadata` reach the CLI and the MCP server.

### `reef op watch`

R2.27 left `op log --follow` to "R2.13's wait tool or a later row". It is a new command beside `op log`, not a flag: `op log` prints a newest-first array, and a follower prints oldest-first lines as they come.

- **Usage**: `reef op watch [--workspace WS]... [--change C]... [--by AGENT]... [--kind KIND]... [--effects] [--after OP] [--count N] [--for SECONDS | --follow] [--repo REPO]`. The filter flags are `op log`'s (`LogArgs`' fields, shared through a `FilterArgs` struct that both flatten). Scope as `op log`: a repository, from `--repo` or the scope rule's steps 3 and 4. `about`: "Print operations as they are recorded (JSON lines on a pipe)".
- **It always ends by itself**, after `--for` seconds (default 30, the wait tool's default) or `--count` operations printed, whichever comes first; `--follow` drops the time bound for a person following a repository, and still ends at `--count`. `--for 0` prints what `--after` replays and stops at the first live frame. An agent waiting for one thing runs `reef op watch --kind describe --count 1`. A command that never returns by default would hang an agent's tool call, which ADR 0025's "every command completes" exists to prevent.
- **Output**: each operation as soon as its frame arrives, flushed per line: `-o json` prints JSON Lines, one `json::Operation` per line, the object `op show` prints, with `effects: null` unless `--effects` (as `op log`); text prints `op log`'s line. JSON Lines departs from "one array for lists" (R1.22): a stream has no end at which to close an array, and a consumer must read each operation as it comes; ADR 0036 and the CHANGELOG say so. Nothing else goes to stdout.
- **When the time runs out**, stderr says where it stopped, unless `-q`: `reef: stopped after <S> s at operation <id>; reef op watch --after <id> continues`, `<id>` the last of the last frame's `head_operation_ids` (12 characters). Exit 0, with nothing on stdout if nothing matched: "nothing happened" is an answer, as `here` outside a workspace is (ADR 0025). Stopping at `--count` prints no note; the last line's `id` is where to continue.
- **Ends quietly**: SIGINT and SIGTERM end it with exit 0 after the current line (the normal end of `--follow`); a closed stdout (`| head -1`) exits 0 without an error, noticed by a poll of stdout every 200 ms even when nothing more is written. `--for 0` has no time bound: it ends at the first live frame.
- **Reconnects**: a stream that ends with `unavailable` and no reason, or a transport error, is resubscribed with the last frame's cursor (it does not start a daemon itself), with backoff from 100 ms doubling to 2 s, until the `--for` deadline (with `--follow`, for 60 s of failed attempts), then fails with the unavailable error. Nothing is printed twice or missed across it. A daemon of another version on reconnect fails with `old_daemon`'s error; the idle-restart rerun (`!any_call_answered()`) applies only to the first call. The global `--timeout` bounds connecting and each subscribe call's headers, never the stream.
- **Advice** (`cli/advice.rs`): `TOO_FAR_BEHIND` and `OPERATION_LOG_REWRITTEN` for `op watch`: hint "Too much changed since --after, or the log was rewritten; read history with `reef op log`, then watch without --after.", `next` `reef op log --repo <repo id>` (exit 5); `OPERATION_NOT_IN_HISTORY` for `op watch --after`: the row `undo` has, with the same `next`; `OPERATION_NOT_FOUND` and the id reasons for `--after`: as for `op show`; `TOO_MANY_SUBSCRIPTIONS`: the daemon's hint, no `next` (exit by kind `unavailable`).
- **Not in the agent guide**: it is at 1,596 of 1,600 bytes; `reef op --help` and `reef guide -o json`'s command list carry it.

### The MCP wait tool on the stream

As R2.13 and ADR 0035 promised: `wait_for_operations`' inputs, result, description and tests stay; its feed changes.

- **The call**: `SubscribeOperationsRequest { repos: [scope repo], filter, start: after_operation(after_operation) }`, or no start without one. Frames are read until the first with operations (replay frames count), the timeout, or cancellation. That frame's operations, at most 100, are the result, `last_operation_id` the last returned. `timeout_seconds: 0` returns at the first frame with operations or the first live frame, whichever comes first. On a timeout, `last_operation_id` is the last of the last frame's `head_operation_ids`, the position the stream stood at, matching or not, so passing it back sees nothing twice. `effects` are dropped from the result unless `include_effects` (the stream always carries them). Progress notifications every 10 s and cancellation (dropping the stream) stay; keepalives reset nothing; the wait is still not retried after the daemon goes away.
- **The table**: the tool's `rpc` becomes `/reef.api.v1.OperationService/SubscribeOperations` (READ, so `readOnlyHint` is unchanged), and `NOT_TOOLS` loses its `SubscribeOperations` line, so test 2's every-method rule still holds. `ListOperations` stays `list_operations`'.
- **The budget**: no description, title or input changes, so `tools/list` stays 19,983 bytes; test 1's 20,000-byte assertion is untouched.
- `wait.rs` loses the window, `LAG`, `POLL`, the head reads and the same-millisecond set; its module comment and ADR 0035's decision 10 say it reads the stream (ADR 0035 gains "Since R2.09 (ADR 0036) the tool reads `SubscribeOperations`."; its consequence about polling two RPCs a second is struck through with the same note).

## Implementation notes

- **Order**: the schema field, revision, reasons (`buf lint`, `buf format`, `buf breaking` against main); `Frontier` and `walk_after` with tests 1 to 3; `OpMatcher` (R2.02's `reads.rs` tests must pass untouched); `OpEvents` and the hook; the session over a fake feed (unit tests); the real `read`; the handler and tests 4 to 17; the client; `op watch` (18, 19); the wait tool (20); docs and benches.
- **Never await a jj-lib future on a tokio worker.** `read`'s jj work runs inside `spawn_blocking` under `pollster::block_on`, holding a `Subscriptions` permit; the session task only awaits channels, timers and that blocking task.
- **The hook** compares `(head.readonly().op_id(), head.generation())` before and after, in `run` around the job and its reload, and calls `moved` with `head.readonly()`; `send_replace` on a `watch` is synchronous and cheap on the thread. Do not route it through `note_committed`.
- **The tip** held by `OpEvents` is only an `Arc<ReadonlyRepo>` to reach the op store and the op heads store; operations newer than its index (outside writes found by the poll) get effects through `Reads::effects`' `load_at` path. After a reopen (#63) the hook's generation check replaces the tip, so no read uses a store a panic may have poisoned.
- **Replay bound to `H0`**: pass `upto: Some(H0)` until the frontier covers it in every followed repository, then `None`. Re-walking the range for each frame is O(range); at 10,000 operations that is about a second of op-store reads over a full replay, accepted (a cached id list is the follow-up if measured).
- **Ownership of the slot**: the session holds an `OwnedSemaphorePermit`-like guard for its `Subscriptions` slot, released on any exit path, including a panic in the session task (log it at `error`, end the stream `INTERNAL`).
- **`ReceiverStream` and the channel of 1**: build the frame only after `reserve()` returns the slot; `select!` the reserve with `Sender::closed()` is unnecessary (reserve fails when the receiver is dropped), but the idle wait must also select on `closed()` so a client that leaves while nothing happens frees its slot.
- **The CLI's reconnect** reuses `cli::connect` and `daemon::restart` only on the first call; keep the cursor in memory, never print it.
- **Linux**: nothing here is `cfg(target_os = "linux")`; still run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy with and without `--all-features` in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux") before pushing, since `RepoRegistry`'s constructor and `Config` change under Linux-only test files.

## Risks

- **Wake-ups are O(subscriptions) per operation**, and each subscription reads the log. Fine for ten; R2.22 measures 500 at 1,000 a minute and replaces `Feed::read` with its broker if the per-subscriber read cost (the `op_range_1` bench) is what binds.
- **Concurrent op heads make `after_operation` resumes inexact.** With two heads (another `jj` writer racing the daemon, until the daemon's next reload merges them), `head_operation_ids` has two ids, and resuming from one replays the other branch's operations. The cursor has no such gap; the wait tool and `op watch`'s note use the last id and may show a concurrent operation twice in that window.
- **GC racing a live subscriber.** A subscriber that had not received the last operations before GC's rewrite ends with `OPERATION_LOG_REWRITTEN` instead of carrying on. GC snapshots and reloads before it rewrites, so a reading subscriber is normally caught up; GC is explicit and rare.
- **Clock skew.** `walk_after` orders by end time as jj does; operations from hosts with skewed clocks sharing a repository can come in a surprising order (never before their parents, which the walk enforces by marking, but out of time order across branches).
- **Hyper's per-connection stream limit.** The daemon sets none of its own; R2.22 checks what tonic and hyper apply before putting 500 streams on one connection.
- **Outside writers are seen at the poll's pace**, about 200 ms, not 100 ms; the exit criterion is about operations through the daemon.

## Choices this brief made, and why

- **Wake-up from the repository thread**: every Reef write already commits there, so one comparison per job covers all of them, including merges a reload commits, with no reef-lib change.
- **Poll the op heads for other writers**: one small `readdir` five times a second per followed repository, against a watcher's macOS registration cost and lifecycle.
- **The frontier as position**: the log is a graph; a single id cannot say where a subscriber stands across concurrent heads, a frontier can, and it makes resume exact.
- **Pull with a channel of one**: a slow reader costs a frame, not a queue, and the durable log makes catching up free of drops.
- **10,000 operations back**: the same budget a `ListOperations` page examines, ten minutes at the target rate.
- **GC moves caught-up subscribers on**: a UI should not lose its stream to routine maintenance, and one that had everything loses nothing.
- **`op watch` ends by itself**: an agent's command must return; a person adds `--follow`.
- **One schema field**: the minimum for a filtering client to resume by operation, as the declaration intends.
