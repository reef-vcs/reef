# R2.04 Virtual workspace API

Phase 2 · Size L · Depends on: R2.03 (`Manager::rewrite`, `OpMeta`, the write reasons, `reef-agent`), and through it R2.02 (revision resolution, `at_operation`, page tokens, `Change`, effects) · Unblocks: none listed in `dev-phases.md`; R2.13 exposes it as tools

## Context

The design's case for a virtual API is that "many tasks need no workspace. Review, search, analysis, and small edits run against the store through a virtual API: read a file at a snapshot, apply an edit, receive a new snapshot hash. A directory is materialized only when something must execute" (`docs/design.md`, Workspaces). R2.01 declared that API as `FileService` with three RPCs, `ReadFile`, `ListFiles` and `EditFiles`, and left all three answering `NOT_IMPLEMENTED`. This ticket implements them over jj-lib's store: reads off the repository thread as R2.02's reads are, and edits as jj commits written by R2.03's write path, so an edit to a commit that live workspaces sit on holds them still, snapshots them first, and has them take the result afterwards.

The "snapshot hash" of the row is a commit id. An edit either rewrites a commit (keeping its change id, as a snapshot does) or creates a new change on one, and `EditFilesResponse.change.commit_id` is the new commit. Nothing is materialized: no directory, no working copy, no checkout, unless a live workspace sits on the edited commit, in which case that workspace's directory takes the new tree exactly as it takes a describe or abandon in R2.03.

The CLI gains nothing a user sees; `Client` gains one method per RPC and two that follow pages. MCP tools over these RPCs are R2.13's.

R2.01's rule binds this brief: it implements what R2.01 declared and adds. It adds one field, `FileEdit.copy_from`, and so `API_REVISION` becomes 3. Everything else is reasons and comment rewordings.

## Decisions

### Size

The row is M; this brief makes it L. What R2.02 and R2.03 had to build first is in place: revision resolution, `at_operation`, page tokens, the read pool, `Change`, effects, `OpMeta`, `reef-agent`, the five-step write with its locks and follows, and the reason machinery. But on top of that it implements three RPCs, adds one module in each crate (`reef_lib::jj::files`, `service/files.rs`), a fourth `Write` arm with a dry run before any snapshot, eight reasons, one schema field, an ADR and a bench, and 17 tests: R2.03's breadth, and R2.03 was L.

It does more than the row names, because R2.01 declared more: `ListFiles`, edits that create a new change (`new_on`), text replacement, and the executable bit. It adds `copy_from` (below), which the declared schema cannot do without sending a file's content back. The README's "Departures" section says so, and `dev-phases.md`'s row names them.

### Where the code lives, and which thread runs it

- **jj work stays in `reef_lib::jj`**, in a new module `files.rs`: `read_file`, `list_files`, the path rules, the edit overlay, and `Repo::edit_commit` and `Repo::new_change_on`. `diff::entry_kind` and the materialization in `read_side` become `pub(crate)` helpers there or in `diff.rs`, shared rather than copied.
- **Reads run on the blocking pool** through `state.reads.run`, as `GetChange` and `GetDiff` do (ADR 0030 decision 1), never on the repository thread.
- **Edits run through `Manager::rewrite`** as a fourth `Write` arm, `Write::Edit`. Its plan and its commit run on the repository thread through `RepoHandle::call_async`, as R2.03's do (ADR 0031).
- The handlers live in `service/files.rs`. `FilesHandler` gains `new(Arc<AppState>)` and `server.rs` passes the state, as for every other handler.

### Paths

One rule set, `files::check_path`, for every path in the three RPCs (`ReadFile.path`, `ListFiles.path`, `FileEdit.path`, `FileEdit.copy_from`):

- Repository-relative and `/`-separated: R2.02's `check_paths` rules (no empty, `.` or `..` component, so no leading or trailing `/` and no absolute path), and no NUL. Failing is `INVALID_ARGUMENT`, reason `INVALID_PATH`, metadata `path`.
- **For edits only**, also refused: a component equal to `.git` or `.jj` ignoring ASCII case, or `git~1` ignoring case (NTFS's short name for `.git`). A tree holding them cannot be checked out (jj-lib refuses), and git refuses them on case-insensitive filesystems. Reads may name them, since reading is harmless and an imported tree may hold them. `.gitignore`, `.github` and `a.git` are ordinary names.
- `ReadFile` and `EditFiles` require a non-empty path (`INVALID_PATH`); an empty `ListFiles.path` is the root.
- Paths are compared byte for byte. Two paths that differ only in case are two entries, as in git; checking such a tree out on a case-insensitive filesystem is jj-lib's behavior and not this ticket's.

### `ReadFile`

- **`revision`** is required (`REVISION_REQUIRED`), resolved with `revset::resolve_revision` in the request's workspace's scope, at `at_operation` when given (`reading::repo_at`). A hidden commit named by id can be read, as `GetChange` reads one.
- **Snapshot first** when the revision uses `@`, at head, unless `skip_snapshot` or `at_operation`, through `reading::uses_working_copy` and `snapshot_first`, as every R2.02 read does. The snapshot's operation is not reported; the response has no field for it, as `GetChangeResponse` has none.
- **What it returns** depends on the entry at `path` in the commit's tree:

  | Entry | `entry.type` | `content` and `size` | `entry.file_id` |
  | --- | --- | --- | --- |
  | regular or executable file | `FILE`, `EXECUTABLE` | its bytes, as stored | the file id |
  | symbolic link | `SYMLINK` | its target | the symlink id |
  | conflict | `CONFLICT` | jj's materialization, with markers, exactly as `GetDiff` reads a conflicted side (`ConflictMarkerStyle::Diff`, merge options from the settings); a conflict that is not between files (a file against a directory) is jj's one-line description of its sides | empty |
  | directory, submodule | | `FAILED_PRECONDITION`, reason `NOT_A_FILE`, metadata `path`, `type` (the `EntryType` value name), `commit_id`; the hint says `ListFiles` lists a directory | |
  | absent | | `NOT_FOUND`, reason `PATH_NOT_FOUND`, metadata `path`, `commit_id` | |

  A path under a symlink is read through the tree, never the link: `link/x` where `link` is a symlink is `PATH_NOT_FOUND`.
- **Ranges.** `content` is the bytes from `offset`, at most `limit` (0, or more than 1 MiB, is 1 MiB). `size` is the whole length, so a caller reads on from `offset + len(content)` until it reaches `size`. An `offset` at or past the end returns empty `content` and the `size`; it is not an error. Binary files are returned as they are; nothing is decoded or normalized.
- **Cost.** Each call reads the whole blob (the git backend has no ranged or size-only read), so reading an N-byte file in 1 MiB pages reads it N/1 MiB times. No blob cache is added: files over a few MiB are rare in source trees, the bench measures the case, and a cache keyed by file id is a contained follow-up if it matters.
- **The response** carries `entry` (its `path` as requested), `content`, `size`, `commit_id` (full hex) and `at_operation` (the operation read).

### `ListFiles`

- **`revision`** as for `ReadFile`, with the same snapshot rule.
- **`path`** empty for the root, else a directory. Absent is `PATH_NOT_FOUND`; a path that holds anything but a directory is `FAILED_PRECONDITION`, reason `NOT_A_DIRECTORY`, metadata `path`, `type`, `commit_id`.
- **Not recursive**: the directory's own entries, directories among them as `DIRECTORY`, read from the directory's own tree objects only (one per side of a conflicted tree). A name whose every present side is a directory is `DIRECTORY`; a name whose sides disagree otherwise is `CONFLICT`.
- **Recursive**: every entry below the directory that is not a directory (files, symlinks, conflicts, submodules), as `jj file list` and `git ls-files` list; directories are implied by the paths. Symlinks are listed, never followed.
- **Order** is jj's path order, by component (`a/b` before `a.rs`), the order `GetDiff` pages in.
- **Pages** follow ADR 0029 and 0030: `page_size` 0 is 100, above 1,000 is 1,000, negative is `INVALID_ARGUMENT`; the token is bound to the request's other fields (`INVALID_PAGE_TOKEN` otherwise), pins the operation the first page read, and carries the last path returned. A recursive page walks with a matcher that skips every subtree wholly before the cursor without reading it, so a deep page costs what its own entries cost, not the entries before it. Each page also stops before its response passes 3 MiB.
- `file_id` is the file or symlink id, a submodule's commit id, and empty for a directory or a conflict, as declared.

### `EditFiles`

#### The target

- **`revision`** rewrites that commit, keeping its change id: resolved in the request's workspace's scope, then refused when immutable (`IMMUTABLE_REVISION`) or hidden (`HIDDEN_REVISION`), exactly as `DescribeChange` refuses (`rewrite::writable`). One commit of a divergent change may be edited by commit id; the change stays divergent.
- **`new_on`** creates a new change whose one parent is that commit (`jj new <rev>` without moving any workspace). An immutable parent is the usual case (`new_on: "trunk()"`) and is allowed. A hidden parent is `HIDDEN_REVISION`, since building on it would make it visible again. This is a new helper, `rewrite::buildable`, which is `writable` without the immutability check.
- **Neither set, or the set one empty**, is `INVALID_ARGUMENT`, reason `REVISION_REQUIRED`. Every R2.02 resolution error applies to both, and `@` needs a request workspace (`WORKSPACE_REQUIRED`).
- **`expected_commit_id`** is checked against what the target resolves to, for both forms, exactly as in R2.03: empty skips; otherwise a full lowercase id (`INVALID_COMMIT_ID`), and a different commit at step 4 is `EXPECTED_COMMIT_MISMATCH` with metadata `expected_commit_id` and `commit_id`. A caller that read a file and edits it should pass the `commit_id` it read; that is the only way to know nothing changed in between.
- **`description`**: unset keeps the target's (empty for a new change); set replaces it, normalized as `DescribeChange` does (a trailing newline added; a NUL is `INVALID_DESCRIPTION`).
- **`workspace`** names whose `@` the revision may use and is recorded as the operation's `reef.workspace`. It must be active, as for R2.03's writes. It is never moved: an edit with `new_on: "@"` leaves the workspace where it was, and `MoveWorkspace` is how it would move onto the new change.

#### The edits

The edits apply in order to an overlay over the base tree: the target's tree for `revision`, the parent's for `new_on`. Each edit sees the tree as the earlier ones left it, so `delete a` then `content a` replaces a symlink with a file, `content a` then `replace a` edits what was just written, and `copy_from a` to `b` then `delete a` is a rename. All edits or none: the first that fails fails the request, and nothing is written.

Before an edit's action, every proper ancestor of its path must be absent or a directory in the overlay; otherwise `FAILED_PRECONDITION`, reason `NOT_A_DIRECTORY`, metadata `path` (the ancestor), `type`, `edit_index`. So no edit ever writes through a symlink or turns a file into a directory. Writing `a/b/c` creates `a` and `a/b`; deleting the last entry of a directory removes the directory, since trees hold no empty ones.

| Action | The path holds (in the overlay) | Result |
| --- | --- | --- |
| `content` | nothing, a file, an executable, a conflict | a file with these bytes. The bit: `executable` when set; else kept for a file or executable, false for a new file, and for a conflict the bit its file sides agree on, else false (what jj records when it snapshots a resolved conflict) |
| `content` | a symlink, a submodule, a directory | `FAILED_PRECONDITION`, `NOT_A_FILE`; the hint says to delete it first in the same request (a directory's files one by one) |
| `replace` | a file or executable | `old_text`'s UTF-8 bytes are found in the file's bytes, byte for byte, with no line-ending or encoding normalization. `all` false: exactly one occurrence, counting overlapping ones (`aa` occurs twice in `aaa`); none is `TEXT_NOT_FOUND`, more is `TEXT_NOT_UNIQUE` with metadata `occurrences`. `all` true: every non-overlapping occurrence, left to right, as `str::replace`; none is `TEXT_NOT_FOUND`. The bit is kept unless `executable` is set |
| `replace` | nothing | `NOT_FOUND`, `PATH_NOT_FOUND` |
| `replace` | anything else, a conflict included | `NOT_A_FILE`; a conflict is resolved by writing the whole file with `content` |
| `replace` | a file over 16 MiB | `FAILED_PRECONDITION`, `FILE_TOO_LARGE`, metadata `size`: the cap `GetDiff` reads up to |
| `delete` | a file, an executable, a symlink, a conflict, a submodule | removed |
| `delete` | nothing | `PATH_NOT_FOUND`: deleting what is not there is almost always a wrong path, and all-or-none makes failing safe |
| `delete` | a directory | `NOT_A_FILE`; directories are deleted file by file |
| `copy_from` (new, below) | source: a file, an executable, a symlink | the path takes the source's value as the overlay holds it (the same file or symlink id, or bytes written earlier in the request), with no content sent. `executable` set overrides a file's bit; set on a copied symlink it is `INVALID_EDIT`. The destination follows `content`'s rules. A source that is absent is `PATH_NOT_FOUND`; a directory, conflict or submodule is `NOT_A_FILE`; the same path as the destination is `INVALID_EDIT` |
| no action, `executable` set | a file or executable | only the bit changes; nothing else is `PATH_NOT_FOUND` or `NOT_A_FILE` |
| no action, `executable` unset | | `INVALID_ARGUMENT`, `INVALID_EDIT` |

Also `INVALID_EDIT`: an empty `old_text`, `executable` set with `delete`, and more than 1,000 edits in one request (no `edit_index` then). Every error about one edit carries metadata `edit_index` (from 0) and `path`, and its message names both, so a caller knows which edit to fix.

- **Store mounts are refused.** A path at or under a `[[store]] mount` declared in the base tree's `reef.toml`, or in the `reef.toml` the edits leave when it parses, is `FAILED_PRECONDITION`, reason `STORE_MOUNT_PATH`, metadata `path`, `mount`, `edit_index`. A workspace that took such a tree would either write into a read-only store (the bind tier) or skip the file because its parent is a symlink (the symlink tier), and its next snapshot would record the file deleted. Mounts are already excluded from snapshots and the watcher (ADR 0022 decision 7); this keeps the API from putting files there.
- **Ignore rules are not applied.** `.gitignore`, `.reefignore` and `[snapshot] exclude` decide what a snapshot picks up from disk; an edit names its paths explicitly, and jj keeps tracking a file in the tree whether or not it is ignored. Writing an ignored path is allowed and lands in the tree. Reef has no secret scanning, here or in snapshots.
- **Limits.** The request is under tonic's 4 MiB decode limit, which stays as it is: the API has no client streaming (ADR 0029 decision 13), and larger content belongs in a workspace. `Client::edit_files` checks the encoded length before sending and fails with `ClientError::TooLarge { bytes, max }`, kind `InvalidArgument`, hint "Edit large files in a workspace, or split the edits across requests." Other clients get tonic's `OUT_OF_RANGE`, which the RPC's comment names. At most 1,000 edits.

#### The write

- **`revision`**: the overlay is written as a tree with `MergedTreeBuilder` over the commit's tree (a resolved override applies to every side of a conflicted tree; other conflicted paths stay conflicted), file contents with `Store::write_file`. Then `rewrite_commit(commit).set_tree(tree)`, with `set_description` when given, and `rebase_descendants()`. Descendants are rebased onto it and may become conflicted, as with any jj rewrite; local bookmarks follow; working copies on the commit or its descendants move to their rewritten commits. The author stays; the committer becomes the daemon's identity at the current time, as for describe.
- **Nothing to write**: when the new tree's ids equal the commit's and the description is unset or already equal after normalization, nothing is recorded: `operation` unset, `change` the current commit. The checks above still run.
- **`new_on`**: the overlay over the parent's tree, then `new_commit(vec![parent], tree).set_description(text)`. Author and committer are the daemon's identity; the agent is the operation's `reef.agent`, not a commit field. An empty `edits` creates an empty change, as `jj new` does, and records an operation.
- **One operation** per request, recorded with `OpMeta` kind `edit`, `reef.workspace` the request's workspace when named, and `reef.agent` the request's agent, else that workspace's owner. Its description is `reef: edit commit <commit id>` (the commit before the rewrite) or `reef: new change on <commit id>` (the parent), full hex. `classify`'s fallback learns both prefixes as `EDIT`.
- **The response**: `change`, built by `log::Describer` at the new head in the request's workspace's scope (`change.commit_id` is the new commit, the "snapshot hash"; `change.tree_id` the tree, empty when conflicted; `change.conflict` whether it is); `operation` through `written_operation`, kind `EDIT`, with effects (`REWRITTEN` for a rewrite and each rebased descendant, `CREATED` for a new change).

### Edits and live workspaces

`Write::Edit { target: EditTarget, expected, edits: Arc<[files::Edit]>, description }`, with `EditTarget::Rewrite(revision)` or `EditTarget::NewOn(revision)`, runs R2.03's five steps:

0. **Before step 1** (no repository job): paths, `INVALID_EDIT`, the edit count and the description are checked, as `rewrite_detached` checks a describe's description now. A malformed request touches nothing.
1. **Plan.** `refresh_for_resolve` (so a colocated repository imports git refs first, as describe and abandon do), resolve with `writable` or `buildable`, check the expected id, and then **apply the edits as a dry run** against the target's tree as it is now: the overlay is built and every per-edit check runs, but no blob is written. A request that would fail against the current tree fails here, before anything is snapshotted, unless a Reef workspace sits on the target commit itself: its snapshot at step 3 can change the very tree the edits apply to (an edit of `@` sees the files on disk, as a read of `@` does), so a per-edit failure is decided at step 4 instead. (Implementation note: the first draft made every step 1 failure final, which contradicted test 12, whose `replace` needs text only W's unsnapshotted edit has.) The workspaces to lock: for `Rewrite`, those whose working-copy commit is in `<commit>::`, descendants first, as for abandon; for `NewOn`, those whose working-copy commit is the parent, so the new change sits on what is on disk.
2. **Lock**, as R2.03: the create lock shared, then each active workspace's snapshots paused and scan lock taken, in id order.
3. **Snapshot** each locked workspace, kind `explicit`, descendants first, as for abandon. An edit changes a tree, so a workspace's unsnapshotted edits must be recorded before the write, or they would meet a stale working copy at the follow and diverge. A failure stops the write before anything is written, with R2.03's error.
4. **Write.** Resolve again (`resolve_target`, which follows a commit step 3 rewrote, or with `expected_commit_id` reports the mismatch), apply the edits for real against the tree as it is now, and commit. The edits can still fail here, when a snapshot in step 3 changed a file an edit touches (a `replace` whose text the workspace's own edit removed, say); then step 3's snapshots stand in the log and nothing else is written. A caller that passed `expected_commit_id` gets `EXPECTED_COMMIT_MISMATCH` instead, since the snapshot rewrote the commit.
5. **Follow.** For `Rewrite`, every locked workspace whose working-copy commit moved takes its new commit: the tree differs, so it is R2.03's follow-up snapshot, which finds the working copy stale with no edits since step 3 and checks out the files that differ. That is how an edit reaches a live workspace's directory: through jj's checkout, file by file, never by writing the directory here. For `NewOn` no working copy moves. Then the divergent marks are reconciled, unlocked, unpaused.

Two concurrent `EditFiles` on one commit are ordered by the repository thread at step 4. Without `expected_commit_id` the second applies to the first's result, so edits of different files compose and a `replace` either still finds its text or fails; with it, the second is `EXPECTED_COMMIT_MISMATCH`. Neither can make the change divergent: both rewrite the commit the view holds at step 4.

An edit is an ordinary write for everything else: the registered root's `default` workspace is never written and goes stale for the `jj` CLI when its commit is edited (R2.03's rule), and a workspace created or moved onto the commit between steps 1 and 4 follows at its next snapshot.

### Operations and undo

- The `EDIT` operation is listed, filtered and classified like any other: `ListOperations` with `kinds: [EDIT]` returns it, and its attributes are the four R2.03 writes.
- **Undoable as soon as it exists**, with no change to `UndoOperation`: an edit adds or forgets no workspace, is not a move, and changes no git ref. Undoing a rewrite rewrites the commit back and moves the workspaces that followed it back (they are in its working-copy effects, so they are snapshotted first, and their edits since supersede it); undoing a new change hides the change. Undoing an edit whose commit a later edit or snapshot rewrote again is `OPERATION_SUPERSEDED`, as for every operation.
- The snapshots of step 3 are operations of their own, kind `SNAPSHOT`/`EXPLICIT`, as for abandon. `EditFilesResponse` has no field for them; `ListOperations` shows them.

### Errors and reasons

| Reason | Kind | Metadata | RPCs |
| --- | --- | --- | --- |

R2.02's `INVALID_PATH` gains `edit_index` when the path is an edit's (its constant's doc comment says so). An edit's errors carry no `commit_id`: they are about the overlay, which no commit holds yet. `path` is the path at fault: the ancestor for `NOT_A_DIRECTORY`, the source for a `copy_from` whose source fails, else the edit's own. None has a `next`: there is no CLI command for these RPCs until R2.05.

### Schema additions

`reef_api::API_REVISION` becomes 3 and `API_DIGESTS` gains its third entry, commented "R2.04: `FileEdit.copy_from`". The addition is at the next free number with a leading comment (ADR 0029 checklist):

```proto
// files.proto
message FileEdit {
  // …R2.01's fields 1 to 5…
  oneof action {
    // …content = 2, replace = 3, delete = 4…
    // Take the file or symlink at this path, as the earlier edits of this
    // request left it, without sending its content: its bytes or target,
    // and a file's executable bit unless `executable` is set. With a later
    // delete of that path, a rename. A directory, conflict or submodule is
    // FAILED_PRECONDITION, reason NOT_A_FILE.
    string copy_from = 6;
  }
}
```

Why it is needed: without it, renaming or copying a file means reading it back in 1 MiB pages and sending it whole, which a request under 4 MiB cannot do for a larger file at all, and which costs an agent behind MCP every byte of the file in tokens twice. It is the one edit an agent refactoring a tree needs that the declared actions cannot express. Because it reuses blob ids, a copy followed by a delete is exactly a git rename, and `GetDiff` reports it `RENAMED` through the backend's copy detection. A field added to an existing oneof is not a breaking change under buf's `FILE` rules; no daemon before this one implements `FileService`, so no daemon ignores it.

Not added, and why:

- **A symlink write.** Agents rarely create links, and a link is the one tree entry that can point outside the repository; `copy_from` moves an existing link, which covers renames. A later revision can add a `symlink_target` action if a caller needs one.
- **A mode change without content.** Expressed by an edit with no action and `executable` set, a loosening of the declared "Required" that only the comment states (below). No declared client sends that shape today, since nothing implements the RPC.
- **The step 3 snapshots in the response**, for the reason above. **`size` on `FileEntry`**: the git backend can only learn it by reading the blob, which would make a listing read every file.

The comment rewordings, which `buf breaking` and the digest ignore:

- "Declared; R2.04 implements it." is removed from the three RPCs, and each gains an "Errors:" paragraph naming the reasons above.
- `ReadFile`'s comment: `revision` required, the snapshot rule, the table's content per entry type, directories and submodules refused, an offset at or past the end returning empty content. `ReadFileRequest.path`: required.
- `ListFiles`'s comment: what recursive lists and what it leaves out, jj's path order, directories versus conflicts in a conflicted tree, `NOT_A_DIRECTORY`.
- `EditFiles`'s comment: rewrite versus new change; immutable parents allowed for `new_on`; edits in order, all or none, never through a symlink; the store mount and reserved name refusals; workspaces on the commit or its descendants snapshotted first, in operations of their own, and taking the result afterwards (ADR 0031); nothing recorded when nothing changes; the request's 4 MiB limit (tonic's `OUT_OF_RANGE` beyond it) and 1,000 edits; the author and committer; undoable with `UndoOperation`.
- `EditFilesRequest.workspace`: "The workspace `@` refers to, recorded as the operation's workspace; it is never moved. Empty for none." `EditFilesRequest.description`: the trailing newline is added.
- `FileEdit.path`: the path rules. `FileEdit.action`: "Required, unless `executable` is set: an edit with no action and `executable` set changes only the bit of an existing file." `FileEdit.executable`: what it means with each action.
- `TextReplace`: byte-exact matching, the overlapping count, `TEXT_NOT_FOUND` and `TEXT_NOT_UNIQUE`, and that `all` with no occurrence fails too. `FileDelete`: what it deletes, and `PATH_NOT_FOUND` when nothing is there.

## Implementation notes

- Order: `check_path` and `read_file` with test 1 and 3; `list_files` and the matcher with test 2; the overlay and `apply` with tests 4 and 7; `edit_commit` and `new_change_on` with tests 5, 6 and 8; the handlers for the reads with tests 9 and 10; `Write::Edit` and `EditFiles` with tests 11 to 16; the schema field, the client, the bench, the comments, and the documents.
- Reuse, do not copy: `uses_working_copy`, `snapshot_first`, `repo_at`, `op_id`, `PageRequest` and `MAX_PAGE_BYTES` (as `GetDiff` uses them), `convert::entry_type`, `convert::change`, `write_change`'s shape (it takes a `Write` and a kind; a new caller passes `Write::Edit` and `OperationKind::Edit`).
- The overlay is a `BTreeMap<RepoPathBuf, Pending>` over the base tree, with `Pending` holding absent, bytes to write, an existing `TreeValue`, or a bit change; the ancestor check looks at the overlay first, then the base tree's `path_value`. Blobs are written only when `apply` is called with `write: true`, at step 4, and then all at once before the tree. Blobs written for a request that then fails are unreferenced objects for git's own GC.
- `Write` is cloned into the plan and commit closures; keep the edits in an `Arc<[Edit]>` so a 4 MiB request is not copied twice.
- `replace` reads the file (up to 16 MiB) on the repository thread at steps 1 and 4. That delays that repository's other jobs by the read; it is bounded by the cap and acceptable for M. If it shows in the load test, step 1's dry run can move to the read pool.
- The recursive matcher: `matches(file)` is true for paths under the requested directory and after the cursor in component order; `visit(dir)` returns `Visit::Nothing` for a directory that sorts wholly before the cursor and is not an ancestor of it. `RepoPath`'s `Ord` is component order.
- Never await a jj-lib future on a tokio worker: reads go through `state.reads.run`, writes through `call_async`.
- Linux: nothing here is `cfg(target_os = "linux")`; the unfiltered fuse-overlayfs run covers `files.rs`. Add `| (binary(files) & test(/edit_files_moves_workspaces/))` to the kernel overlay root filter in `ci.yml`, since the follow writes into an overlay's upper layer. Before pushing, in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux"), run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets`, clippy with and without `--all-features`, and the new root filter.

## Out of scope

- CLI commands over these RPCs and their JSON (R2.05); MCP tools (R2.13); SDK wrappers (R2.06, R2.07).
- Creating symlinks or submodules; deleting or copying directories recursively; editing several commits, or a merge's parents, in one request; `new_on` with several parents.
- Streaming uploads or downloads, a ranged blob read, and a blob cache; files whose request would pass 4 MiB.
- Searching file contents (grep over a revision), regular-expression replacement, line-ending or encoding normalization, and patch application (unified diffs as edits).
- Secret scanning of written content; applying ignore rules to edits; case-folding collisions in trees.
- Enforcing access scopes on `EditFiles` for remote callers (R2.08); agent-scoped undo (R3.26).

## Risks

- **A busy workspace on an edited commit can diverge.** Edits that reach W's disk between step 3 and the follow make the follow meet a stale working copy with edits, ADR 0018's fourth arm, exactly as for abandon and undo (ADR 0031's window). Nothing is lost and the row is marked, but an agent that edits its own workspace's `@` through the API while also writing files there will see it. Test 15 measures how often. An agent with a directory should write files there; the API is for agents without one, and for editing commits no busy workspace sits on.
- **Paged reads of large files are quadratic** in the file size, because the git backend reads whole blobs. `read_paged_16mib` bounds it; a blob cache by file id is the follow-up.
- **Step 4 can fail after step 3 snapshotted.** The dry run removes the common case (a request that is wrong against the current tree), but a workspace's own unsnapshotted edit can still invalidate a `replace` between the plan and the write; its snapshot then stands in the log with nothing else written. `expected_commit_id` makes that a clean mismatch.
- **Descendants may become conflicted.** Rewriting a commit rebases its descendants, as every jj rewrite does; an edit to a line a descendant also changes leaves that descendant conflicted, visibly (`Change.conflict`, `GetStatus`), and undo reverts it.
- **The mount rule reads `reef.toml` from the tree**, not from the workspaces' mounts, which were read at their creation. A workspace created from an older `reef.toml` with a mount the current one dropped is not protected. That workspace's mount is still excluded from its snapshots, and the tree rule covers every workspace created from the edited commit.
- **`copy_from` is the one schema addition**, made before any client uses the RPC. If it proves wrong it is deprecated and replaced, never edited (ADR 0029).

## Choices this brief made, and why

- **Delete of an absent path fails** rather than succeeding quietly: a wrong path is the likelier cause, and all-or-none means the caller loses nothing by retrying without it.
- **`ReadFile` refuses directories** rather than returning an empty entry: a reader that gets empty content for a directory may take it for an empty file. `ListFiles` of the parent is the stat.
- **Recursive listings leave directories out**, as `jj file list` and `git ls-files` do, so a page is a list of things that have content.
- **`new_on` snapshots the workspaces on the parent**, so "a new change on `@`" builds on the files on disk, as every read of `@` does.
- **Edits are checked twice**, dry at step 1 and for real at step 4, so a wrong request costs no snapshots (except the snapshot of a workspace on the target commit, whose files on disk the edits must see) and a write still sees the tree it commits against.
- **The committer and new author are the daemon's identity**; the agent is in `reef.agent`. Commit identity per agent is evidence and provenance, R3.01's.
- **Writing through ignore rules is allowed**; writing into store mounts and reserved names is not. The first is a choice an agent makes explicitly; the second two break checkouts.
- **One addition, `copy_from`**, and no symlink action: renames are common in agent refactors and impossible for large files without it; symlink creation is rare and the riskiest entry to let an API write.

## What later tickets inherit

- **R2.05** decides whether the CLI gets file commands, and calls the five `Client` methods if so. **R2.13** maps `ReadFile`, `ListFiles` and `EditFiles` to tools (`ACCESS_READ` ones as read-only), sends the caller's name as `reef-agent`, and describes rename as `copy_from` plus `delete`; the tool descriptions come from the reworded comments. **R2.06** and **R2.07** wrap `read_file_to_end` and the page-following list as the client does.
- **R2.08** scopes `EditFiles` as a write: a remote token that may write can put content into trees that local workspaces check out. **R2.09** streams `EDIT` operations with their effects like any other. **R2.14** keys symbols by commit and must take commits written by `EditFiles`, not only snapshots, since no snapshot ever sees them. **R2.23**'s index learns an edit's files through the follow-up snapshot, which reconciles it.
- **R3.01** links evidence to the commits `EditFiles` reports. **R3.26** scopes undo of `EDIT` operations by `reef.agent` like every other kind.
- A later revision may add a `symlink_target` action, a ranged read, or a blob cache, each additive.
