# R2.04 Virtual workspace API

Phase 2 · Size M · Depends on: R2.03 (`reef_lib::jj::write`, the snapshot-first rule, `follow_pointer_moves`, `recheck_divergence`), R2.02 (`read::with_head`, revision resolution, `Diff` for the agent to inspect its edit), R2.01 (`Trees { List, Read, Apply }` stubs) · Unblocks: R2.13 (`reef_tree_ls|cat|apply` tools), R2.05 (`reef tree ls|cat|apply`), R3.12 (an instruction that edits a file without a workspace), R4.04 (lazy fetch reads blobs the same way)

## Context

The design says most of a fleet never needs a directory: "Review, search, analysis, and small edits run against the store through a virtual API: read a file at a snapshot, apply an edit, receive a new snapshot hash. A directory is materialized only when something must execute." Phase 1 made directories cheap; this ticket makes them optional. An agent reviewing a change reads files at a commit; an agent fixing a typo applies an edit to its change and gets a new commit back, with no clone, no mount, no lease, and no watcher. The store already holds every version; the daemon only needs to read and write trees through jj-lib, which it does for every snapshot.

What makes this more than a thin wrapper is the interaction with real workspaces. A Reef workspace may be sitting on the change an edit targets. Rewriting the commit under it is exactly the situation ADR 0018 handles for the `jj` CLI: the workspace's next snapshot finds its working copy stale and either adopts the rewrite (no edits of its own) or diverges (edits of its own). An API edit must not manufacture divergence by accident, so the daemon snapshots the workspace first and checks the result out into it, as R2.03's writes do; the workspace sees the edit as if the agent had typed it.

## Decisions

- **Three RPCs on the `Trees` service.** `Trees.List { repo, rev, path (empty = root), recursive: bool, page }` → `entries: repeated FileEntry { path, kind: FILE | EXECUTABLE | SYMLINK | DIR | SUBMODULE | CONFLICT, size: optional uint64, blob_id, symlink_target, conflicted }`, `at_commit: ChangeRef`, `at_op`. `Trees.Read { repo, rev, path, offset, limit }` → server stream of `FileChunk { data: bytes (≤ 64 KiB), offset, eof: bool, total_size, kind, blob_id, conflicted }`, the first chunk carrying the metadata; a symlink's target is the content with `kind = SYMLINK`; a conflicted file is refused with `Conflict` unless `materialize_conflicts = true`, which streams jj's conflict markers (the only place markers appear, as `Diff` does for conflicted paths). `Trees.Apply` is client-streaming: `ApplyRequest` messages, the first a `header { repo, change: rev, description, expected_commit: optional commit_id, allow_divergence: bool }`, then any number of `edit { path, oneof { write: { data: bytes (chunked across messages for one path, in order), executable: bool }, delete: {}, symlink: { target }, copy_from: { rev, path } } }`, ending when the client half-closes → `ApplyResponse { change: ChangeRef (new commit), op: Operation, snapshots, workspaces_updated, files_written, bytes_written }`. All three are reads or writes in the R2.02/R2.03 sense: `List` and `Read` run on the blocking pool from `RepoHandle::head()` under the read semaphore; `Apply` is one transaction on the repository thread, after the snapshot-first step, followed by `follow_pointer_moves`.
- **`rev` must name a commit of a change, and `Apply` names a change.** `List` and `Read` take any `rev` (a commit of any age, so an agent reads history). `Apply`'s `change` resolves to a commit through the same resolver and the edit rewrites *that commit* (same change id, new commit id), so an agent holding a change id edits its change wherever the commit now is; `expected_commit`, when set, makes the apply conditional (`Conflict` with the current commit in the detail when it differs), which is how an agent avoids clobbering a concurrent edit without a workspace. A `rev` that resolves to a hidden commit (one `Get` can still read but no visible head reaches) is refused for `Apply` with `Conflict` and a hint to name the change id. Divergent changes: `Apply` to a change with two visible commits is `Conflict` (hint: `reef squash`/`abandon` first) unless `change` named a commit id directly and `allow_divergence` is set.
- **Edits are whole-file.** `write` replaces the file's content; there is no patch or hunk application in this ticket (an agent that wants to patch reads, edits in its own memory, writes; R2.15's symbol diff is how it then checks itself). A `write` over a directory path, or a `write` whose path has a file as an ancestor, is `InvalidArgument` (jj would refuse the tree); `.jj` and `.git` components are refused (RX.01's S-19 rule, applied before jj sees it); `..`, empty components, and `/` in a component are `InvalidArgument` (S-17, S-18). `delete` of a missing path is a no-op reported in `files_written` as 0 for that path; `delete` of a directory removes everything under it. `copy_from` reads `(rev, path)`'s blob id and sets it at `path` (no byte copy; git trees share blobs). Executable bit is set by `executable` (default: keep the existing file's bit, false for a new file).
- **Conflicts are refused, not resolved.** `write` or `delete` on a path whose current value is conflicted (`MergedTreeValue` with more than one side, or a `TreeValue::Conflict`) is `Conflict` with the paths listed and a hint to resolve in a workspace; the change itself may be conflicted at other paths (`has_conflict()`), and `Apply` proceeds for the unconflicted paths it names. Writing a resolution through the API (`resolve: true` on a conflicted path, taking the written bytes as the resolution) is a one-line extension recorded under Out of scope for R3.25.
- **Size limits.** Each `write` is capped at `[api] max_apply_file_size` (default 16 MiB) and one `Apply` at `[api] max_apply_bytes` (default 64 MiB), checked as chunks arrive so a stream over the limit is refused with `InvalidArgument` before anything is written to the store; the daemon spools chunks for one path to a temporary file under `<state>/tmp/` when they exceed 1 MiB, else in memory. `Read`'s chunks are 64 KiB; `offset`/`limit` allow ranges. `List` with `recursive` pages at `page_size` entries (default 1,000, cap 10,000); `size` is filled for files only when `with_sizes` is set and the listing has at most 1,000 entries (reading a blob per entry; git trees carry no sizes), else left unset and `sizes_omitted = true`.
- **Nothing is materialized.** `Apply` writes blobs with `Store::write_file`, builds the tree with `MergedTreeBuilder::new(commit.tree())`, `rewrite_commit(&commit).set_tree(new_tree).set_description(desc or keep)`, `rebase_descendants()`, commits with description `reef: apply edit to <change>` (`OpKind::Apply`), attribute `reef.client`, and `reef.apply.files = <n>`. No workspace directory, lease, or watcher is involved unless a Reef workspace already sits on the change.
- **A Reef workspace on the change follows the edit.** Before the transaction, every active Reef workspace whose working-copy commit is `change`'s commit is snapshotted (R2.03's `snapshot_workspaces_on`); if any has `attention = divergent`, `Apply` is `Conflict` as above. After the transaction, `follow_pointer_moves` checks the new commit out in each (the files the edit wrote appear on disk; the agent's own files are untouched because they are in the commit the edit was based on). A check-out failure marks `checkout-failed` and does not fail the RPC (R2.03's rule). This is why the alternative, refusing `Apply` when a workspace is on the change, was rejected: the workspace is a cache of the change, and the change is what the agent edited; refusing would make the virtual API unusable for exactly the mixed fleets the design describes (one agent testing in a directory, another reviewing and fixing without one). The response's `workspaces_updated` tells the caller which directories changed.
- **ADR 0043 "Virtual workspace API."** Records: edits are whole-file rewrites of a change's commit, never materialized; the conditional `expected_commit`; conflicts refused; workspaces on the change snapshotted first and checked out after, and why; limits and streaming; what waits (patch application, conflict resolution through the API, `copy_from` across repositories). Alternatives: materializing a scratch workspace per edit (rejected: a create per edit is seconds and disk, against milliseconds here); refusing edits when a workspace is on the change (rejected above); a patch/hunk edit format (rejected for Phase 2: an agent has the file; whole-file is one round trip and no ambiguity).
- **CLI.** R2.05 wires `reef tree ls <rev> [PATH] [--recursive]`, `reef tree cat <rev> <PATH>`, `reef tree apply <change> [--set PATH=FILE]... [--delete PATH]... [--symlink PATH=TARGET]... [--copy PATH=REV:SRC]... [-m] [--expect <commit>]`; `cat` writes raw bytes to stdout (text mode and JSON mode alike; `-o json` wraps metadata only with `--json-metadata`). This ticket adds `Client::tree_list|tree_read|tree_apply` (the apply method takes an iterator of edits and streams), `reef_api::json::{FileEntry, Applied}`, and the text renderer for `ls` (`<kind> <size or -> <path>`).

## Implementation notes

- Reuse R2.03's `run_write` orchestrator: `Apply` is a write with a pre-snapshot set computed from `workspaces_on_commit(change's commit)` and a job `tree::apply`. The only Apply-specific step before it is collecting and validating the stream, which happens before any snapshot or transaction so a refused stream costs nothing.
- Spool to `<state>/tmp/apply-<random>` with `0600`, feed `Store::write_file` from the file through `tokio::fs::File` adapted to `AsyncRead` (jj-lib's `AsyncRead` is `futures::io::AsyncRead`; `tokio_util::compat` converts); delete the spool in a `Drop` guard.
- `List` sizes: `Store::read_file` and count, bounded by `list_sizes_limit`; reading is on the blocking pool under the read permit like everything else, and a `large` root listing without `with_sizes` is a tree read only.
- `Read`'s channel is bounded (16 chunks); a slow client back-pressures the reader rather than buffering the file.
- `rev` resolution for `Apply` goes through the change id: resolve `change` → `(commit, change_id)`; then load the *visible* commits of that change from `heads()`/`resolve_change_id` to detect divergence and hidden commits; the commit to rewrite is the resolved one.
- The threat-model rows go in the same PR; `validate_path` is the one gate, called before any jj call, with the hostile test 9 as its proof.

## Out of scope

- Patch or hunk application, search-and-replace, and any edit format smaller than a file.
- Resolving conflicts through the API (`resolve: true`; R3.25 defines conflict objects first).
- Directory renames as a primitive (a rename is `copy_from` plus `delete`; no rename records exist in Phase 1 trees).
- Reading or writing across repositories; `copy_from` names a rev in the same repository.
- A per-edit lease or ownership check (the socket authorizes, ADR 0027; R2.08's `workspaces` scope gates `Apply` remotely).

## Risks

- **An agent with a workspace and an agent without one editing the same change** at the same moment: the pre-snapshot and the check-out make the workspace follow, but an edit the workspace agent makes between the pre-snapshot and the check-out is seen as stale-with-edits and diverges (ADR 0018), exactly as it would if a second workspace had snapshotted. Test 14 asserts the end state is consistent; divergence is possible and resolvable (R2.03), never lossy. `expected_commit` is the tool for the directory-less agent to notice.
- **Whole-file writes cost tokens** for a one-line fix in a large file: the agent sends the whole file. The design accepts this for Phase 2; a hunk format is a later ticket if R2.17 shows it matters.
- **`MergedTreeBuilder` on a conflicted base** pads the override to the number of sides (`:76`); writing a resolved value over an unconflicted path in a conflicted tree is what test 16 pins, and jj's own `jj file` commands do the same, so the shape is known but the brief did not run it.
- **Sizes in `List` require blob reads**: a recursive listing of `large` with `with_sizes` is 100,000 blob reads and is refused by the limit; the UI (R3.38) will want sizes and gets them per directory.
- **The spool directory is a new place the daemon writes**; it is inside the state directory (`0700`, S-01's checks cover it) and swept at start, and the threat model row says so.
