# R2.07 TypeScript SDK

Phase 2 · Size M (the row says S; see "Size") · Depends on: R2.01 (`reef.api.v1`, the error envelope, ADR 0029), R2.05 (`reef-client`, whose surface and socket discovery this mirrors), R2.06 (ADR 0054's shared decisions, the fixtures under `sdk/fixtures/`, the Python code this ports), R2.08 (the remote listener and its client rules, ADR 0049), R2.11 (the presence reporting contract and `reef_client::presence::Reporter`) · Unblocks: none listed (the web UI may later import the SDK's messages; see "What later tickets inherit")

## Context

The only TypeScript client of the daemon today is the web UI (R2.18, ADR 0047). It generates its own messages with `protoc-gen-es` at every build and talks gRPC-web from a browser through Connect-ES. A Node program that wants a workspace has two options: shell out to `reef` and parse its JSON, or generate its own stubs and work out by itself everything R2.06 worked out for Python: the socket path, the `:authority` the daemon accepts, how errors are packed, how to pin a remote daemon's key, and how presence is reported.

The row asks for three things: code generated from the schema, a package on npm, and a thin wrapper. R2.06 settled most of the design for every SDK in [ADR 0054](../../adr/0054-sdks.md); this ticket applies it to TypeScript and decides what ADR 0054 leaves to each language. Earlier briefs left this ticket these promises:

- **R2.05** (line 364): mirror `reef-client`'s surface: one method per RPC, page followers, the agent metadata, and the probe for a mismatched daemon.
- **R2.04** (line 363): wrap `read_file_to_end` and the page-following lists as the client does. R2.06 did not wrap `read_file_to_end` (see "Out of scope"); this ticket does.
- **R2.08** (line 768): document the remote connection (`https://` URL, SPKI pin or CA roots, `authorization: Bearer`, the reasons), and read `REEF_REMOTE`, `REEF_REMOTE_TOKEN` and `REEF_REMOTE_FINGERPRINT` as the CLI does.
- **R2.11** (line 260): a workspace helper that holds a workspace for a block of code reports one `ACTIVITY` entry with the `Refresh` cadence (10 s, TTL 30 s) and clears it when the block exits; the agent is rule 7; `Reporter`'s unit tests 1 to 6 are the behaviors to port.
- **R2.12, R2.14 to R2.16** (lines 437, 389, 466, 621): expose their fields and RPCs through the client. Generation does this by construction.
- **R2.18** (lines 614, 663): the SDK may share `web/buf.gen.yaml`'s generator settings, and `web/` may later depend on it.
- **R2.06** (line 373): reuse ADR 0054, the two fixtures, the error class tree, the workspace block and the publish-after-release pattern, and check what the transport sends as `:authority` over a Unix socket.

The user's standing direction applies: the SDK is agent-agnostic. No harness or vendor is named in its API, JSDoc, README, docs page or examples; an agent is a name the caller passes (`agent`, or `REEF_AGENT`), as for the CLI. Nothing in this design couples Reef to a vendor: the dependencies are Buf's open-source protobuf and Connect libraries (Connect is a CNCF project), which the web UI already uses.

**Run while writing this ticket**, in a scratch npm project (Node 22.16.0, the versions above) against the installed daemon (`405aae8`, API revision 14) and a scratch daemon of the same build with its remote listener on `127.0.0.1`, `names = ["reefvm.test"]`:

1. `buf generate` with `protoc-gen-es` writes the 16 v1 files. **The root module's `excludes` apply even when the input is `crates/reef-api/proto` itself**: no v0 files are generated from inside the repository. The same command over a copy of `proto/` outside the repository writes `reef/daemon/v0/{daemon,error}_pb.ts` too. Every service's methods carry the RPC's leading comment as JSDoc.
2. **`@connectrpc/connect-node` over the socket works** with `new Http2SessionManager("http://localhost", …, { createConnection: () => net.connect(socket) })` and `createGrpcTransport({ baseUrl: "http://localhost", sessionManager })`: `GetDaemonStatus` answers `0.3.0`, revision 14, in 6 ms for the first call (session included) and 1.3 ms after. `:authority` is the base URL's host, so the socket path is never sent.
3. **The `:authority` lesson holds for Node.** A raw `node:http2` request over the socket with the percent-encoded socket path as `:authority` is reset (`NGHTTP2_PROTOCOL_ERROR`, RST code 1), as grpcio's was. `@grpc/grpc-js` 1.14.7 with a `unix:` target and no options gets an answer, so it does not send the path either.
4. **Errors decode with stock tooling**, over the socket and over the remote listener: `GetWorkspace` of an unknown id is `Code.NotFound` with `findDetails(ErrorDetailSchema)` giving kind `NOT_FOUND`, reason `WORKSPACE_NOT_FOUND`, `next` `["reef","ws","list","--all"]`, the hint and `{"workspace": …}`. A `SubscribeOperations` stream of an unknown repository fails with `REPOSITORY_NOT_FOUND` and its detail. So the trailers-only fix R2.06 made to the remote listener holds for connect-node, unary and streaming.
5. **Connect does not report transport failures by gRPC code.** A missing socket fails the call as `Code.Internal` with `cause.code` `ENOENT` (not `Unavailable`). A failed TLS check is `Code.Internal` with the TLS error as `cause`. A misdirected host is `Code.Unknown`, message `HTTP 421`. A request over `writeMaxBytes` (4 MiB) is refused before sending as `Code.ResourceExhausted`, "message size 5242885 is larger than configured writeMaxBytes 4194304". An aborted stream ends as `Code.Canceled`.
6. **Pinning through Node's TLS works, in every handshake of the session.** A handshake with `rejectUnauthorized: false` and ALPN `h2` reads the leaf. **`getPeerCertificate().pubkey` is not the SubjectPublicKeyInfo** (for the daemon's P-256 key it is the bare EC point, and its hash matches nothing); `new X509Certificate(raw).publicKey.export({ type: "spki", format: "der" })` hashes to exactly `GetDaemonStatus.remote.certificate.fingerprint`. A session with `ca: [<that leaf as PEM>]` and `checkServerIdentity` comparing that hash with the pin is accepted by OpenSSL (the generated self-signed, non-CA leaf as the only root) and serves `GetDaemonStatus` with `authorization: Bearer`. With a wrong pin, `checkServerIdentity` fails the handshake before `secureConnect`, so no HTTP/2 byte, and no token, is written.
7. **The daemon's refusals arrive with their detail**: a read token's `CreateWorkspace` is `PermissionDenied`, `REMOTE_ACCESS_DENIED`; an unknown token is `PermissionDenied`, `REMOTE_TOKEN_INVALID`.
8. **The listener's Host check is separate from TLS.** With the key pinned and the name check replaced, `https://localhost:<port>` gets `HTTP 421`, because `localhost` is not in `[remote] names`. A session whose URL is `https://reefvm.test:<port>` and whose `createConnection` dials `127.0.0.1:<port>` (same `ca` and `checkServerIdentity`) is served. `X509Certificate.checkHost` and `checkIP` tell which names a leaf has.
9. **A renewal breaks a pinned session.** A new self-signed certificate for the same key, served by a Node TLS server, fails a handshake whose `ca` is the old leaf with `DEPTH_ZERO_SELF_SIGNED_CERT`, and passes with the new leaf. So the SDK must re-pin, as Python does.
10. **Roots**: on this Mac, `tls.getCACertificates("default")` returns 150 certificates (Node's bundled Mozilla store) and `"system"` returns 4 (the keychain's own additions, not Apple's built-in roots).
11. **Node 22.16** defines `Symbol.asyncDispose` but not `SuppressedError`, and `await using` is a syntax error there. Node 24 and later parse it natively.

## Decisions

### Size

M. The row's S assumed a generator run and a publish step. The work, with R2.06's decisions taken as given:

1. A build that generates the messages (`protoc-gen-es`) and the wrapper's methods (a small `protoc-gen-reef` plugin) from the protos, writes the version and API revision, compiles to ESM with declarations, and packs a tarball whose version is the workspace's.
2. Transport: socket discovery as `paths.rs` settles it, and R2.08's remote connection with the key pinned before the token is sent, re-pinning after a renewal, and the CA path.
3. Errors as classes by kind, with the transport failures above mapped by cause rather than code, and the incompatible-daemon probe.
4. A workspace block (`await using` and a callback form) that heartbeats its lease and reports presence, from two sans-I/O cores ported with their tests.
5. Unit and integration tests (local and remote, against `reef-daemon` built in CI), a CI job, a release job that packs and smoke-tests on every dry run, and npm trusted publishing on tags.
6. A docs page, an amendment to ADR 0054, and moving `PAGE_ITEMS` into a fixture both generators read.

Smaller than R2.06's L: there is one client (no sync and async pair), Node parses X.509 itself (no DER walk), the pin is checked inside Node's handshake (no grpc workarounds), Connect already takes a request as an object of fields or a whole message, and the ADR, fixtures, cores and tests exist to port. No API change, no daemon change and no new crate are expected. It would be L with a browser build, Bun and Deno support, or a CommonJS build, which are out of scope.

### Layout and names

- **`sdk/typescript/`** is the project root: `package.json`, `package-lock.json`, `tsconfig.json`, `tsconfig.build.json`, `eslint.config.js`, `vitest.config.ts`, `buf.gen.yaml`, `buf.gen.v0.yaml`, `README.md` (npm's page), `codegen/`, `scripts/`, `src/`, `tests/`.
- **The package is `reef-vcs`**, unscoped, the PyPI distribution's name: `npm install reef-vcs`, then `import { connect } from "reef-vcs"`. The user chose it (see "Decided by the user").
- **Two entry points.** `reef-vcs` is the client, errors, the workspace block, presence and the constants. `reef-vcs/api/v1` is every generated message schema, enum and service of `reef.api.v1` (an `export *` of the 16 files; buf's lint keeps names unique across the package), plus protobuf-es's `create`, `toJson`, `fromJson`, `timestampFromDate`, `timestampDate`, `durationFromMs` and `durationMs`, so a caller needs no direct `@bufbuild/protobuf` dependency. `reef-vcs/api/v1` imports nothing from Node, so a later ticket can let the web UI use it.
- **ESM only**, `"type": "module"`, with `exports` (`types` and `default` conditions for both entry points, and `./package.json`). From Node 22.12, `require("reef-vcs")` loads it from CommonJS, so a dual build would buy nothing but a second copy of every class, which breaks `instanceof` (the dual-package hazard). No top-level `await` anywhere in the package, since `require()` of an ES module refuses one.
- **Node 22.15 or later** (`engines.node: ">=22.15"`), on macOS and Linux. 22 is the oldest Node still supported (until 2027-04-30), as Python's floor is its oldest supported version; 22.15 brings `tls.getCACertificates` (the CA path below), and connect-node 2.3 needs 22. CI tests 22.15.0 and 26, the floor and the newest LTS. Bun and Deno are not tested or promised (see "Out of scope").

### Codegen: protoc-gen-es at build time, not committed

- **Generator**: `buf generate` with `@bufbuild/buf` 1.74.0 and `@bufbuild/protoc-gen-es` 2.16.0, pinned in `package-lock.json`, the web UI's toolchain (ADR 0047 decision 9), so one generator is bumped for both, and no network or system `protoc` is needed. ADR 0029 decision 18 ("building needs neither `protoc` nor `buf`") is about the Rust build; the npm tarball carries compiled JavaScript, so no consumer runs `buf` either.
- **`sdk/typescript/buf.gen.yaml`**: input `directory: ../..` (the `buf.yaml` module, as `web/` uses), plugins `protoc-gen-es` (`target=ts`, `import_extension=js`, out `src/gen`) and `protoc-gen-reef` (`local: ["node", "codegen/protoc-gen-reef.mjs"]`, out `src/gen`), `clean: true`. `import_extension=js` because `tsc` with `NodeNext` resolution requires explicit extensions in emitted ESM (the web UI uses `none` under Vite).
- **v0, for the probe**: the root module excludes `reef/daemon/v0` even when the input is `crates/reef-api/proto` (verified), so `codegen/generate.mjs` copies `reef/daemon/v0/{daemon,error}.proto` into a temporary directory outside the repository and runs `buf generate <tmp> --template buf.gen.v0.yaml` (`protoc-gen-es` only, out `src/gen`). The v0 messages are not re-exported.
- **Not committed**: `sdk/typescript/.gitignore` lists `/src/gen/`, `/dist/`, `/pack/`, `/LICENSE` and `/node_modules/`.
- **`codegen/generate.mjs`** (`npm run gen`, which `build`, `typecheck`, `lint` and `test` run first, as in `web/`):
  1. runs `buf generate` (v1 with both plugins), then the v0 step;
  2. writes `src/gen/api-v1.ts`, the `reef-vcs/api/v1` entry (`export *` from each v1 file, sorted, and the protobuf-es helpers);
  3. writes `src/gen/build.ts`: `VERSION` (`Cargo.toml`'s `[workspace.package] version`, verbatim, since Cargo's versions are already semver), `API_REVISION` (from `reef-api/src/lib.rs`'s `pub const API_REVISION: u32 = N;`, failing loudly if the line is not found), `COMMIT` (`git rev-parse --short HEAD`, else `jj log -r @ --no-graph -T 'commit_id.short()'`, else empty);
  4. copies `../../LICENSE` to `sdk/typescript/LICENSE`.
- **`codegen/protoc-gen-reef.mjs`** is a protoc plugin written with `@bufbuild/protoplugin` 2.16.0, in plain ESM JavaScript with JSDoc types (`// @ts-check`, checked by `tsc` with `checkJs`), so it runs as is on every Node in the matrix without a TypeScript loader. It writes `src/gen/rpcs.ts` and `src/gen/methods.ts` (below). It reads `(reef.api.v1.access)` from each method's unknown option field 50701, as `clientgen.py` does, and the items of a paged RPC from `sdk/fixtures/page-items.json`.
- **`PAGE_ITEMS` moves to `sdk/fixtures/page-items.json`** (`{"GetDiff": "files", "QueryChanges": null}` with an `about`), read by `clientgen.py` and `protoc-gen-reef.mjs` alike, so the two SDKs cannot disagree on a paged RPC's items. ADR 0029's checklist item 12 names the file.
- **Pins and ranges**: `devDependencies` are exact. Runtime `dependencies` are caret ranges whose floors are what the generated code needs: `@bufbuild/protobuf ^2.16.0` (protobuf-es requires a runtime at least as new as the generator), `@connectrpc/connect ^2.3.0`, `@connectrpc/connect-node ^2.3.0`, `smol-toml ^1.9.1` (for `config.toml` and `remotes.toml`: Node has no TOML parser, and a hand-written subset would accept files the CLI refuses). Nothing else at runtime. Test 12 checks the floors against the generator. Dependabot gains an `npm` entry for `/sdk/typescript`.
- **Staying in sync**: nothing generated is committed and the CI job builds from the same commit's protos, so the SDK matches its commit's schema. Test 16 checks `API_REVISION` against a daemon built from the same commit; test 11 checks that every RPC has a method.

### The wrapper's methods, generated

`protoc-gen-reef` writes:

- **`src/gen/rpcs.ts`**: one entry per RPC, keyed by its name: `{ name, path: "/reef.api.v1.WorkspaceService/CreateWorkspace", method: <the DescMethod from protoc-gen-es>, access: "READ" | "WRITE" | "ADMIN", kind: "unary" | "server_streaming", pageItems: string | null | undefined }` (`undefined` for an RPC that is not paged).
- **`src/gen/methods.ts`**: an abstract class `Methods` that `Client` extends, with one method per RPC, named in lower camel case (`createWorkspace`, `getStatus`, `subscribeOperations`). Services are not separate objects, as in ADR 0054: RPC names are unique across the package.
- **Signature**: `createWorkspace(request?: MessageInitShape<typeof CreateWorkspaceRequestSchema>, options?: CallOptions): Promise<CreateWorkspaceResponse>`. protobuf-es's init shape is the TypeScript form of ADR 0054's "every request field is a keyword (or a field of an options object), and a whole request message can be passed instead": `{ repo, start: { case: "newOn", value: "trunk()" } }` or `create(CreateWorkspaceRequestSchema, …)` are both accepted, typed, and a `oneof` is `{ case, value }` (`CreateWorkspaceRequest.start` and `EditFilesRequest.target` are oneofs; the workspace block's options keep `change` and `newOn` flat). Unknown fields are type errors.
- **Call options are a second argument**, `CallOptions { signal?: AbortSignal; timeoutMs?: number }`, the SDK's own type rather than Connect's (no headers or callbacks leak into the API). A request field can never clash with them (`BuildStoreRequest.timeout` stays a field). Unary calls take `timeoutMs`, else the client's default (none unless `connect({ timeoutMs })` sets one); streams take no deadline, only `signal`.
- **No conversions.** Timestamps and durations are protobuf-es's well-known types, built with the re-exported `timestampFromDate` and `durationFromMs`, as any protobuf-es code builds them. A `Date | Timestamp` union would be easy, but a `number` for a duration invites unit mistakes, and one rule for both is simpler to document. 64-bit integers are `bigint`, protobuf-es's default (`uptimeMs: 12n`); the docs page shows `toJson` for logging, since `JSON.stringify` refuses `bigint`.
- **JSDoc**: the RPC's leading comment, then its access (`ADMIN: local socket only; a remote daemon refuses it.` for ADMIN), and `@see` the request type, whose fields already carry their comments from `protoc-gen-es`.
- **Pages**: every paged RPC gets `<method>Pages(request?, options?): AsyncIterable<Response>`, following `nextPageToken` lazily with the same request otherwise; and `<method>All(request?, options?): AsyncIterable<Item>` where the items are known (the response's single repeated field, or `page-items.json`'s entry). `queryChanges` gets `Pages` only. The generator fails on a paged RPC with several repeated fields and no entry, naming the file. Each page is its own call, with `timeoutMs` per page and one `signal` for all.
- **Streams**: a server-streaming method returns `Stream<T>` synchronously: an `AsyncIterable<T>` that is also `AsyncDisposable` and has `cancel()`. The call starts on the first iteration; leaving `await using`, `cancel()`, or `signal` ends it, after which iteration ends rather than throwing `Canceled`. Errors are mapped as for unary calls, mid-stream included. No automatic resume (see "Out of scope").
- **Collisions**: the generator refuses a method name that equals a hand-written member of `Client` (`close`, `withOptions`, `workspace`, `withWorkspace`, `attach`, `withAttached`, `readFileToEnd`, `daemonStatus`, `requireRevision`, `target`, `agent`); none does today, since every RPC is a verb and a noun.

### Hand-written surface

```ts
import { connect } from "reef-vcs";

const client = await connect();                         // socket discovery, as the CLI
const client = await connect({ socket: "/path/daemon.sock", agent: "planner-3" });
const client = await connect({ remote: "vm" });         // a profile in <state>/remotes.toml
const client = await connect({ remote: "https://vm:7470", token, fingerprint: "sha256:…" });

await using client = await connect();
const status = await client.getStatus({ workspace: wsId });
for await (const op of client.listOperationsAll({ repo: repoId, pageSize: 200 })) { … }

await using ws = await client.workspace({ repo: repoId, newOn: "trunk()", purpose: "fix the parser" });
await writeFile(join(ws.path, "src/parser.ts"), source);
await ws.snapshot();
ws.activity("running the tests");

// The same block where `await using` is not available (plain JavaScript on Node 22):
const result = await client.withWorkspace({ repo: repoId }, async (ws) => { … });

await using stream = client.subscribeOperations({ repos: [repoId] });
for await (const frame of stream) { … }
```

- **`connect(options?): Promise<Client>`** with `socket`, `remote`, `token`, `fingerprint`, `rootCertificates` (PEM strings), `stateDir`, `config`, `agent`, `timeoutMs`, `connectTimeoutMs` (default 5,000). `Client` has `close(): Promise<void>` and `[Symbol.asyncDispose]`.
- **Properties**: `client.target` (the socket path, or the remote's origin), `client.agent`; module constants `VERSION`, `API_REVISION`, `COMMIT`.
- **`client.withOptions({ agent?, timeoutMs? })`** returns a client sharing the connection, as Python's does.
- **`client.readFileToEnd(request?, options?)`** ports `reef_client::Client::read_file_to_end`: the first read at the request's revision, then the rest from the commit it returned (`revision: commitId`, `skipSnapshot: true`) until `size`, so every chunk comes from one commit.
- **`client.workspace(...)`, `client.withWorkspace(...)`, `client.attach(...)`, `client.withAttached(...)`**, below.
- **`Reporter`** (from `reef-vcs`), the contract's reporter for callers that report finer activity (an `EDITING` entry for paths, `PROGRESS`), as `reef presence report` does from a shell.
- **Errors**, below. Everything is exported from `reef-vcs`, typed, with declarations.

### Transport: Connect's gRPC transport over `node:http2`

`@connectrpc/connect-node`'s `createGrpcTransport` (native gRPC, binary, HTTP/2), one `Http2SessionManager` per client (shared by `withOptions`), `readMaxBytes` and `writeMaxBytes` 4 MiB (tonic's defaults, which the daemon keeps), and one interceptor that sets `reef-agent` (and `authorization: Bearer <token>` on a remote) on every call. Chosen over `@grpc/grpc-js` because:

- it uses the messages and service descriptors `protoc-gen-es` already generates for the web UI: one generator and one runtime for both, where grpc-js needs a second generator (or `proto-loader`'s untyped dynamic loading);
- `findDetails(ErrorDetailSchema)` decodes the error detail with stock code, as ADR 0029 decision 14 says of Connect-ES, and as `web/src/api/errors.ts` does;
- it is Node's own `http2` and `tls`, so `createConnection`, `ca` and `checkServerIdentity` are Node's documented options, and the pin is checked inside every handshake (below);
- `AbortSignal`, async iterables and init shapes are its native API.

Both were verified to keep the socket path out of `:authority` (verified 2 and 3). Supporting both would be two transports to test for no caller's benefit.

### Transport: the socket

- **Discovery** ports `ClientConfig::load` exactly, as `sdk/python/src/reef/_paths.py` does: arguments (`socket`, `stateDir`, `config`) over `REEF_SOCKET`, `REEF_STATE_DIR`, `REEF_CONFIG`, over `config.toml`'s `[daemon] socket`, over the platform default, with every rule R2.06 lists (empty is unset, relative made absolute, a named config must exist and an implicit one may not, a relative `[daemon] socket` is under the state directory, `$XDG_RUNTIME_DIR` only for the default state directory, at most 103 bytes by `Buffer.byteLength`). The platform defaults: `~/Library/Application Support/reef` on macOS; `$XDG_STATE_HOME/reef`, else `~/.local/state/reef`, on Linux; the home from `os.homedir()`. A file that is not TOML, or whose `daemon.socket` is not a string, is a `ConfigError`. The cases are `sdk/fixtures/socket-paths.json`'s, through an internal `resolveSocket({ args, env, defaults })` so tests need no global state.
- **The session**: `new Http2SessionManager("http://localhost", {}, { createConnection: () => net.connect(socketPath) })` with `baseUrl: "http://localhost"`. `localhost` is the `:authority` ADR 0054 decision 3 requires.
- **Connect is eager**: `connect()` calls `GetDaemonStatus` with `skipBackends: true` within `connectTimeoutMs`, and caches it for `daemonStatus()` and the probe. A missing socket, a refused connection or no answer is `DaemonNotRunningError` (kind `unavailable`), hint "Start the daemon: `reef daemon start`, or run any `reef` command, which starts it.", `next` `["reef", "daemon", "start"]`. A v0 daemon (0.1) is named by the probe here, at `connect()`.
- **No autostart and no restart**, ADR 0054 decision 4.
- **Process lifetime.** connect-node's `Http2SessionManager` already keeps a session's socket `unref()`ed while no stream is open and `ref()`s it for each stream, and its timers are `unref()`ed, so a script that forgets `close()` ends when its work does and never exits in the middle of an awaited call. The SDK adds no ref counting of its own; test 14 checks both directions. (The draft of this brief said an open session kept Node alive for 15 minutes; the implementation found otherwise.)

### Transport: a remote daemon

- **Choosing a remote** follows the CLI's `remote::target` exactly, as Python's `_remote.py` does: the `remote` option, else `REEF_REMOTE`; an `https://` URL needs a token (`token`, else `REEF_REMOTE_TOKEN`), with the fingerprint from `fingerprint`, else `REEF_REMOTE_FINGERPRINT`; any other value is a profile in `<state>/remotes.toml`, whose token and fingerprint the options or variables override. `socket` with `remote` is a `TypeError`. URLs parse as `sdk/fixtures/remote-urls.json` says.
- **Pinned** (a fingerprint is given), in `src/tls.ts`:
  1. **Read the leaf**: `tls.connect({ host, port, rejectUnauthorized: false, ALPNProtocols: ["h2"], servername })` within `connectTimeoutMs`, take `getPeerCertificate(true).raw` on `secureConnect`, and destroy the socket. Nothing is sent but the handshake. `servername` (SNI) is set only when the host is a name (`net.isIP` is 0); Node warns on an IP address.
  2. **Hash its SubjectPublicKeyInfo**: `sha256(new X509Certificate(raw).publicKey.export({ type: "spki", format: "der" }))`, as `sha256:<lowercase hex>`. Never `getPeerCertificate().pubkey`, which for an EC key is the bare point (verified 6). A mismatch is `RemoteTlsError` (`pin_mismatch`) with `presented` and `expected` and `PinMismatch`'s hint.
  3. **Check its dates** (`validFromDate`, `validToDate`), as `_channel.check_dates` does: OpenSSL checks a trusted root's dates even though the pin does not need them, and the error would otherwise be an opaque handshake failure.
  4. **Open the session** with `ca: [<the leaf as PEM>]` and `checkServerIdentity: (_, cert) => <the same SPKI hash of cert.raw equals the pin, else an error>`. Node calls it inside every TLS handshake of the session, reconnects included, after the chain check and before `secureConnect`; a failure destroys the socket before HTTP/2 starts. So the token reaches only a server holding the pinned key (S-35), on every connection, not only the first. Node's own name check is replaced by it: the pin, not the name, authenticates the daemon.
  5. **Name the host** as ADR 0054 decision 6 says: if the leaf names the URL's host (`checkHost`, or `checkIP` for an address), the session's URL is the remote URL. Otherwise the session's URL uses the leaf's first DNS name, else its first IP address, and `createConnection` returns `tls.connect` to the URL's real host and port with the same `ca` and `checkServerIdentity`. The listener's Host check then sees a name the certificate lists (verified 8).
  6. **Keepalive**: `pingIntervalMs: 30_000` and `pingIdleConnection: true`, as the Rust client keeps idle streams alive through NATs.
- **Re-pinning after a renewal.** When a call on a pinned client fails because the handshake's chain check refused the trusted leaf (`cause.code` `DEPTH_ZERO_SELF_SIGNED_CERT`, or another of OpenSSL's verify codes, verified 9), the client reads the leaf again. If its key still matches the pin and the certificate differs, it builds a new session manager on the new leaf and **retries the call once, whatever its access**: the handshake failed, so nothing of the call was sent. A call that fails after its request was sent (a reset mid-call while the daemon restarts) is never retried; it raises `UnavailableError`, and the next call goes through the handshake path. If the key differs, the call raises `RemoteTlsError` (`pin_mismatch`). This refines ADR 0054 decision 6, whose "retry a READ once, raise a WRITE" exists because grpcio cannot tell a refused handshake from a failed call; the ADR amendment says so.
- **CA-verified** (no fingerprint): the session's own handshake verifies before anything is sent, with `ca` set to `tls.getCACertificates("default")` (Node's bundled Mozilla roots and `NODE_EXTRA_CA_CERTS`) plus `tls.getCACertificates("system")` (the OS's store), deduplicated, or `rootCertificates` when given; Node's own `checkServerIdentity` checks the URL's host. The Rust client trusts the OS's roots, and Python grpcio's bundled ones; this is their union, and the docs page states the difference. On a refusal, the SDK reads the leaf as in step 1 to report `presented`.
- **Errors**: nothing answering (`ECONNREFUSED`, `ETIMEDOUT`, `EHOSTUNREACH`, `ENOTFOUND`, `EAI_AGAIN`, or no answer within `connectTimeoutMs`) is `RemoteConnectError` (kind `unavailable`, `RemoteConnect`'s hint). A certificate refused with roots is `RemoteTlsError` (`untrusted`, with `presented`); any other TLS failure is `RemoteTlsError` (`handshake`). `Code.Unknown` with `HTTP 421` is `RemoteMisdirectedError`. The daemon's refusals (`REMOTE_TOKEN_INVALID`, `REMOTE_ACCESS_DENIED`, ADMIN) are ordinary `PermissionDeniedError`s with its detail.

### Errors

`src/errors.ts`, exported from `reef-vcs`:

- **`ReefError extends Error`**: `kind` (`ErrorKind`, the union `"not_found" | "already_exists" | "invalid_argument" | "conflict" | "unavailable" | "permission_denied" | "io" | "internal" | "unsupported"`, the CLI's kind text), `reason` (empty when none), `message` (the chain joined with `: `), `chain`, `hint`, `next` (a `string[]` argv starting `reef`, empty when none), `metadata` (`Record<string, string>`), `code` (Connect's `Code`, re-exported, or `undefined` for a client-side error), `method` (the RPC's path, or `undefined`), and `cause` (the `ConnectError` or Node error, ES2022's field). `message` is the daemon's message alone; Node's inspector prints `hint`, `next` and the rest as the error's own properties, so an uncaught error still shows its advice.
- **One subclass per kind**: `NotFoundError`, `AlreadyExistsError`, `InvalidArgumentError`, `ConflictError`, `UnavailableError`, `PermissionDeniedError`, `IoError`, `InternalError`, `UnsupportedError`. A status with a Reef detail takes the detail's kind; one without takes the code's (`kind_of_code`'s table, ported); `ERROR_KIND_UNSPECIFIED` is `internal`.
- **Client-side subclasses**, as in Python: `DaemonNotRunningError (UnavailableError)`, `RemoteConnectError (UnavailableError)`, `RemoteTlsError (PermissionDeniedError)` with `failure` (`"pin_mismatch" | "untrusted" | "handshake"`), `presented`, `expected`; `RemoteMisdirectedError (NotFoundError)`; `ConfigError (InvalidArgumentError)` with `PathsError`'s and `ProfileError`'s messages; `IncompatibleError (UnsupportedError)` with `daemonVersion`, `daemonApi` (`"v0" | "v1"`), `activeWorkspaces`, reason `API_VERSION_MISMATCH`, hint "The daemon is reef X (API vN); this SDK is reef Y. Restart the daemon with the matching reef (`reef daemon stop`, then any reef command), or install reef-vcs@X." and `next` `["reef", "daemon", "stop"]`.
- **`isReefError(value): value is ReefError`** checks a `Symbol.for("reef-vcs.error")` brand, so two installed copies of the package still recognize each other's errors where `instanceof` cannot.
- **Mapping order** (`src/calls.ts`), because Connect reports transport failures as `Internal` or `Unknown` (verified 5): a Node system error in `cause` first (connection codes as above: `DaemonNotRunningError` on a socket, `RemoteConnectError` on a remote), then the SDK's pin error or a TLS verify code (the re-pin path, or `RemoteTlsError`), then `HTTP 421`, then `ResourceExhausted` from `writeMaxBytes` (`InvalidArgumentError` with `TooLarge`'s hint, "Edit large files in a workspace, or split the edits across requests."), then the detail, then the code. Test 6 pins each Connect message and cause the mapping reads, so a Connect release that changes one fails a test, not a user.
- **The incompatible-daemon probe** ports `is_unserved` and `incompatible`: a bare `Unimplemented`, `UNKNOWN_METHOD`, or `NOT_IMPLEMENTED` from a daemon whose version differs leads to at most two calls (`GetDaemonStatus`, then `reef.daemon.v0.Daemon/Status` through the generated v0 service) and an `IncompatibleError`; `NOT_IMPLEMENTED` from the same version stays `UnsupportedError`. Versions are compared, not revisions.
- **The API revision**: `client.daemonStatus()` returns the cached status; `client.requireRevision(n)` throws `IncompatibleError` when the daemon's `apiRevision` is lower.
- **Agent names** follow `check_agent` (trimmed, empty means none, visible ASCII of at most 256 bytes, else `InvalidArgumentError` reason `INVALID_AGENT` at `connect()` or `withOptions()`), from `agent`, else `REEF_AGENT`.

### The workspace block and presence

`client.workspace({ repo, change?, newOn?, purpose?, owner?, backend?, leaseLength?, activity?, keep?, reportPresence? })` returns a `Promise<WorkspaceHandle>`; the handle is `AsyncDisposable`. It is `reef ws run` for a block of TypeScript, with ADR 0054 decision 7's contract:

- **Create**: `CreateWorkspace` with `owner` defaulting to `<user>@<host>:<pid>`: the user from `os.userInfo().username`, else `$USER`, else the uid; the host from `os.hostname()`, else `localhost`; `process.pid`.
- **Heartbeats**: renew every `Lease.heartbeatEvery`, with a 5 s deadline per renewal and backoff of 1, 2, 4, 8, 16 then 30 s while the daemon is unreachable, stopping when the daemon says the lease ended. Timers are `unref()`ed. Never thrown into the block; `handle.leaseLost` tells it. Warnings go to `process.emitWarning` (type `ReefWarning`, codes `REEF_LEASE_LINK_LOST` and `REEF_LEASE_LAPSED`, once per change), the Node idiom a caller can route with `process.on("warning")` or silence with `--no-warnings`; attempts go to `util.debuglog("reef")` (`NODE_DEBUG=reef`). The SDK never writes to the console.
- **Presence**, unless `reportPresence: false`: one `ACTIVITY` entry for the workspace with the `Refresh` cadence (10 s, TTL 30 s), reported after the workspace exists. Its text is `activity`, else `purpose`, else `running <process.argv.slice(1) joined by spaces>` cut to 200 characters (the script and its arguments, as Python's `sys.argv`). The agent follows rule 7. `handle.activity(text)` replaces it at most once a second. Failures never reach the block.
- **Dispose** (`await using`'s exit, or the end of `withWorkspace`): clear the entry (within 2 s), stop the heartbeats, then `ReleaseWorkspace` with its default final snapshot, unless `keep: true`.
- **`client.withWorkspace(options, fn)`** runs `fn(handle)` and disposes it, returning `fn`'s result. It keeps Python's rule exactly: a release failure is thrown only when `fn` succeeded; otherwise it goes to `process.emitWarning` and `fn`'s error propagates. Under `await using`, the language decides instead: `[Symbol.asyncDispose]` cannot know whether the block threw, so a release failure after a throwing block arrives as a `SuppressedError` holding both. The docs page says so. Both forms ship because `await using` needs Node 24 or a transpiler, and plain JavaScript on Node 22 has neither (verified 11).
- **`WorkspaceHandle`**: `id`, `path` (the directory on the daemon's machine), `repoId`, `changeId` (current as of the last call through the handle), `workspace` (the last `Workspace` message), `leaseLost`, and the calls an agent makes most (`move` refreshes `workspace`; the other responses carry no `Workspace`): `snapshot()`, `status(fields?)`, `diff(fields?)`, `readFile(path, fields?)` (the whole file through `readFileToEnd`, at `revision: "@"` unless one is given, since the daemon requires a revision), `editFiles(fields)` (targeting `{ case: "revision", value: "@" }` unless `target` is given, as R2.06 found the RPC requires), `move(fields)`, `release()` (early, which also stops the heartbeats and clears the entry), and `activity(text)`.
- **`client.attach(workspace, { release?, owner?, reportPresence?, activity? })`** and **`client.withAttached(workspace, options, fn)`** hold an existing workspace under `ws run --workspace`'s rule (active, a live lease, held by `owner` or this user on this machine, else `ConflictError`), and release it at the end only with `release: true`.
- **Remote**: both work with a `write` token; `path` is on the daemon's machine, and the docs page says to use `readFile` and `editFiles` there.
- **Signals**: the SDK installs no signal handlers. A process killed in a block leaves the lease to lapse and the entry to expire (30 s); every edit is already in the change, since the watcher snapshots it. The docs page shows a `SIGINT` handler for a caller who wants a prompt release.
- **One core, one driver each.** `src/presence-core.ts` and `src/lease-core.ts` port `_presence_core.py` and `_lease_core.py` (themselves ports of `presence.rs`'s `run` and `heartbeat.rs`): sans-I/O state machines whose inputs are `set(state)`, `tick(now)` and outcomes, and whose outputs are the next request and the next wake-up. `src/presence.ts` (`Reporter`) and `src/workspace.ts` drive them with timers. The ported tests run against the cores with a fake clock.

## Implementation notes

- **Unit tests use `createRouterTransport`** from `@connectrpc/connect` for request shapes and mapping, and a real `h2c` server only for the probe and process-lifetime tests, so most unit tests open no socket.
- **`Http2SessionManager`**: one per client, created by `transport.ts` with the options above; `close()` calls its `abort()`. The ref counting wraps the generated methods' calls in `calls.ts`, which every unary call, page and stream goes through.
- **Leaf fetch** reads nothing after the handshake and closes, so the listener's handshake limits (64 at once, 10 s each) see one short connection per `connect()` and per re-pin.
- **The `access` option** is read in `protoc-gen-reef.mjs` from `method.proto.options`'s unknown fields (field 50701, varint), as `clientgen.py` reads it, since the plugin runs before `options_pb.ts` exists to give a typed extension.
- **Generated code** is excluded from ESLint and Prettier, as `web/src/gen/` is, and compiled by `tsc` in strict mode with the rest.
- **The Rust tests that read the fixtures** (`paths_follow_the_shared_table`, `urls_follow_the_shared_table`) are unchanged; this ticket adds cases to the JSON only if the port finds a rule the table does not cover, and then all three implementations run them.
- **macOS and Linux** run the same code; the CI legs differ in the default state directory, which the tests do not use, and in OpenSSL's verify codes, which test 31 checks on both.

## Performance expectations

- `connect()` to a local daemon, including its `GetDaemonStatus`, takes under 20 ms (6 ms measured above), and a `getStatus` call adds under 2 ms to the daemon's own time; the PR reports both from the integration fixture.
- A pinned remote `connect()` costs one extra TLS handshake (under 10 ms on loopback).
- `await import("reef-vcs")` takes under 150 ms; the PR reports it.
- The packed tarball is under 500 KiB; the PR reports its size and `npm pack`'s file count.
- The `typescript` CI job takes under 8 minutes per leg when the Rust cache is warm.

## Out of scope

- **A browser build.** A browser cannot reach the socket or pin a key, the remote listener allows CORS only for configured origins, and the web UI already speaks gRPC-web with its own generated code. `reef-vcs/api/v1` imports nothing from Node, so a later ticket can let `web/` import its messages (see "What later tickets inherit").
- **Bun and Deno.** Both load npm packages and implement `node:http2` and `node:tls` to differing degrees; neither is tested or promised. A follow-up issue if a user asks, with a CI leg if it works.
- **A CommonJS build**: ESM only, loaded by `require()` from Node 22.12.
- **Resuming subscriptions automatically**: the docs page shows the `cursor` loop, as for Python.
- **Reason constants**: callers compare strings, as in Python.
- **Windows**: no daemon runs there.
- **`read_file_to_end` in the Python SDK**, which R2.04 promised both SDKs and R2.06 left out: a follow-up issue, filed with this PR, so the two SDKs read files alike.
- **Publishing to JSR**, or attaching the tarball to the GitHub release: npm holds it, with its provenance.
- **The MCP registry's npm package type**: `reef mcp` is not a Node program, and R2.25's MCPB listing covers it.
- **Staged publishing** (`npm stage publish`): the user chose direct publishing.
- **Reading `config.toml` beyond `daemon.socket`**, and writing `remotes.toml`.

## Risks

- **npm's bootstrap order.** A trusted publisher can be added only to a package that exists, and a new one expires if no publish uses it within 2 days. So the name is unreserved until the user publishes a placeholder, and the publisher must be added close to the tag. The one-time setup below orders the steps; the `npm` job's warning names the expiry.
- **Connect's failure reporting** (`Internal` with a `cause`, `Unknown` with `HTTP 421`, the `writeMaxBytes` message) was verified at 2.3.0 only. Test 6 pins each, so a Dependabot bump that changes one fails CI, not a user.
- **OpenSSL accepting a non-CA leaf as its only root**, and its verify codes after a renewal, were verified with Node 22.16 on macOS. Node 26 bundles a newer OpenSSL; tests 25 to 31 run on both Node versions and both platforms on every PR (macOS with the label).
- **The `pubkey` trap**: a port that hashed `getPeerCertificate().pubkey` would pin nothing a daemon reports. Test 5 keeps it out.
- **Process lifetime**: the ref counting depends on the SDK seeing every call, which it does through `calls.ts`; a timer inside connect-node that is not `unref()`ed would keep a process alive. Test 14 catches both directions.
- **`bigint`** surprises callers who `JSON.stringify` a response; the docs page shows `toJson`.
- **A regular expression over Rust source** (`API_REVISION`), as in Python: the generator fails loudly, and test 16 catches a wrong revision.

## Choices this brief made, and why

- **Connect over `node:http2`, not grpc-js**: the web UI's generator and runtime, stock error details, Node's own TLS options, and verified over the socket and the listener.
- **The wrapper generated by a plugin**: explicit methods with JSDoc, access notes and page helpers by rule, where a mapped type over the services would hide them from an editor; every later RPC reaches TypeScript with no SDK work.
- **One table for paged items**: two generators reading one file cannot disagree.
- **Pin checked in every handshake**: Node offers it, and it covers reconnects, which trusting the leaf alone covers only while the certificate is unchanged.
- **Retry any call after a refused handshake**: the refusal proves nothing was sent; Python's READ-only rule exists because grpcio cannot tell the cases apart.
- **ESM only, Node 22.15**: `require(esm)` makes a dual build unnecessary, and 22.15 is the oldest supported Node with the APIs the CA path needs.
- **Both `await using` and a callback**: the first is the language's own idiom, the second is the only one plain JavaScript on Node 22 can use, and it keeps Python's error rule exactly.
- **No conversions for timestamps and durations**: protobuf-es's helpers are the idiom, and a number of milliseconds is a unit mistake waiting.
- **Version set at pack time**: npm reads the version from `package.json`, so the committed file holds a placeholder and the release bumps nothing.
- **Warn, don't fail, on npm**: the release is the binaries; the channels follow, as R1.28, R2.25 and R2.06 decided.

## What later tickets inherit

- **The web UI** can drop its own generation and import `reef-vcs/api/v1`'s messages, which R2.18 anticipated; not done here, since it would tie the app's build to the SDK's package for no change in behavior.
- **Every API change** reaches TypeScript by generation; ADR 0029's checklist item 12 covers the one decision (paged items), in one file for both SDKs.
- **Every release** publishes `reef-vcs` to npm at the workspace version with nothing to bump; the person tagging checks the `npm` job's warning beside `pypi`'s.
- **R3.39 and R3.40** (the shells) can use `reef-vcs/api/v1` from their web views, and the Node SDK from any Node side process.
- **A third SDK** reuses ADR 0054, the three fixtures, and the TypeScript and Python ports as two references.

## User one-time setup

Nothing is needed before the PR merges: the dry run packs and tests the tarball and publishes nothing. Before the next release tag:

1. **Create the package with a placeholder** (any time after the merge; this also reserves the name). Signed in to npmjs.com as the account that should own it, with two-factor authentication on:

   ```sh
   mkdir reef-vcs-placeholder && cd reef-vcs-placeholder
   npm init -y >/dev/null
   npm pkg set name=reef-vcs version=0.0.0 license=Apache-2.0 \
     description="Reef's TypeScript SDK; the first release follows. https://github.com/reef-vcs/reef" \
     repository.type=git repository.url=git+https://github.com/reef-vcs/reef.git repository.directory=sdk/typescript
   printf '# reef-vcs\n\nA placeholder. The TypeScript SDK ships with the next Reef release.\n' >README.md
   npm login && npm publish --access public
   ```
2. **Add the trusted publisher, at most 2 days before pushing the tag** (a configuration no publish uses within 2 days expires). On npmjs.com: Packages, `reef-vcs`, Settings, Trusted publishing, GitHub Actions:
   - Organization or user: `reef-vcs`
   - Repository: `reef`
   - Workflow filename: `release.yml`
   - Environment name: `npm`
   - Allowed actions: tick **`npm publish`** (a configuration made after 2026-09-03 allows only `npm stage publish` unless it is ticked).

   Or from a terminal with npm 11.15 or later: `npm trust github reef-vcs --repo reef-vcs/reef --file release.yml --env npm --allow-publish`.
3. **Leave GitHub Actions' OIDC tokens allowed** for `reef-vcs/reef`: on by default and already used by `release`, `mcp-registry` and `pypi`, so a check, not a change. The `npm` environment is created by the job's first run; protection rules on it are optional.
4. **After the tag's run**: check the `npm` job for a warning; `npm view reef-vcs@<version>` shows the version and its provenance (npmjs.com shows a "Built and signed on GitHub Actions" badge); then in a scratch directory `npm install reef-vcs@<version>` and run the README's first example against your daemon. If the configuration expired, delete it, add it again, and re-run the `npm` job from that run (it keeps `npm-dist` for 14 days).
5. **Then**: `npm deprecate reef-vcs@0.0.0 "placeholder; install the latest version"`; in the package's Settings, Publishing access, choose "Require two-factor authentication and disallow tokens" (trusted publishing keeps working); optionally add a second maintainer, so the name does not depend on one account.
