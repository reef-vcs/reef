# Phase 2 tickets

Source of truth for scope: [`docs/dev-phases.md`](../../dev-phases.md) (Phase 2 tables) and [`docs/design.md`](../../design.md) (API, Query layer, Storage, Scale, Human interface, Deployment topologies). These files expand each Phase 2 row into an implementation brief. They are written for an implementing agent, not for humans: every decision that could be made in advance has been made here, and the brief says so. If a brief and `dev-phases.md` disagree on scope, the brief wins for the implementation and the disagreement is fixed in `dev-phases.md` in the same PR. Where the briefs already deviate from `dev-phases.md`, the deviation is listed under "Departures from dev-phases.md" below and `dev-phases.md` was updated when the briefs were written.

Phase 1 is complete: R1.01 to R1.32, RX.01 and RX.07 merged, and 0.1.0 was released on 2026-10-25 (`CHANGELOG.md`). What it left behind, and what every Phase 2 brief builds on, is recorded in [the Phase 1 README](../phase-1/README.md) under "Decisions fixed across all Phase 1 tickets"; those decisions stand unless a row below says otherwise. The short list: a daemon with one tokio runtime, one `std::thread` per registered repository owning every jj transaction (ADR 0012), workspace scans on the blocking pool; the `reef.daemon.v0` gRPC API over a Unix socket with `ErrorDetail { kind, chain, hint, next }` (ADR 0017, 0025); `reef_daemon::client::Client` as the one client, used by the CLI, the benchmarks and the onboarding harness; a SQLite database with five migrations and a `snapshots` index over the operation log (R1.16); a snapshot `Scheduler` with a `SnapshotHook`; the `reef` CLI with JSON on a pipe, exit codes by `ErrorKind`, `reef guide`, `reef here`, aliases and `REEF_OUTPUT`; `reef init` rendering `docs/agent-guide.md` into `AGENTS.md`, `CLAUDE.md`, a Claude Code skill and a Cursor rule; a release workflow for four targets with an installer, a Homebrew tap and binstall metadata; benchmarks (`bench.yml`), a load test (`load.yml`) and an onboarding benchmark (`onboarding.yml`); and a threat model (`docs/threat-model.md`, ADR 0027) whose "Requirements for a remote listener" section is R2.08's checklist.

The implementing agent for Phase 2 is Claude Opus; the reviewer is Fable 5.1, as in Phase 1. Ticket work happens in Reef workspaces on the colocated jj repository and ships as a signed-off PR with the review table (see "Process" at the end).

## Phase exit criteria (from dev-phases.md)

- The CLI is a thin client with no direct jj-lib access.
- An MCP server exposes the same operations as the API.
- A client can subscribe to the operation log and presence channel and receive events within 100 ms, and that holds with 500 subscribers on one daemon at 1,000 operations per minute.
- Symbol-level diffs work for Python, TypeScript, Go, and Rust.
- A local web UI shows the smartlog, workspaces, and fleet panel live.
- Token cost to answer "what is the state of this repo" is measured and at least five times lower than parsing git output.
- Status on the 100k-file synthetic repository is answered from the incremental index without a tree walk.
- A daemon in a VM is reachable from another machine over TLS with a token, serving the same API and web UI.

Which ticket proves each criterion: R2.05 (thin client: a CI step asserts `jj-lib` is absent from `reef-vcs`'s dependency graph without the `embedded-daemon` feature, and every command but `daemon run` and `restore` is a client call), R2.13 (MCP: a test walks the API's services and the server's tool list and finds every agent-facing RPC), R2.22 (subscriptions: the gated load run), R2.15 (symbol diffs: a fixture per language), R2.19 to R2.21 (web UI: a Playwright smoke per view against a live daemon), R2.17 (token cost), R2.23 (status: the `status` benchmark on `large` shows no scan), R2.08 (remote: an integration test with a second host simulated by a non-loopback bind in CI's Linux job, and the quickstart's VM walkthrough run once by hand and recorded in the PR).

## Departures from dev-phases.md

These were decided while writing the briefs. `dev-phases.md` was edited to match in the same change.

- **R2.01 grows to L and creates the `reef-api` crate.** "Versioned. Reviewed as an API" needs a home that neither the daemon nor the CLI owns: the protobuf files, the generated code, the client, the JSON output types and the error kinds move into a new crate, `reef-api`, with no jj-lib dependency, which is what the SDKs (R2.06, R2.07), the MCP server (R2.13), `reef schema` (R2.24) and the web UI's codegen (R2.18) read from. `v0` is deleted in the same PR and the client, CLI, benchmarks, tests and the onboarding harness move to `v1`: v0 made no compatibility promise (ADR 0017) and two schemas served at once would be two to keep in step. ADR 0007 (crate layout) is superseded by ADR 0029 for this.
- **R2.05 keeps one binary.** "Remove jj-lib from the binary crate" collides with two Phase 1 decisions: `reef daemon start` runs the daemon from the `reef` binary itself when no `reef-daemon` is beside it (R1.22), and `reef restore` is offline by design (ADR 0020). The embedded daemon and `restore` stay behind a default-on Cargo feature `embedded-daemon`; the exit criterion is tested with the feature off. Every other command is a client call over `reef-api`.
- **R2.03 owns divergence resolution.** The Phase 1 divergence rule (ADR 0018) left "resolution is R2.03's (squash or abandon one side)". R2.03 adds `Changes.Abandon` and `Changes.Squash` beside `Describe` and `Undo`, so the known limitation "two workspaces editing one change make it divergent; resolving it is a jj operation for now" closes in this phase.
- **R2.08 also owns the local web listener, and R2.18 depends on it.** A browser cannot open a Unix socket, so the web UI needs an HTTP listener even on the laptop. A loopback listener is reachable by every local user and by any web page the user visits, so it needs the same token check and Origin rules as the remote one. One listener implementation, bound to loopback by default and to a routable address with TLS when `[remote]` is enabled, is R2.08's; R2.18 serves the UI from it. `dev-phases.md`'s R2.18 row gains R2.08 and R2.07 as dependencies.
- **R2.11 depends on R2.06 and R2.07.** "The SDKs report presence automatically" needs the SDKs.
- **R2.17 depends on R2.05.** The agent in the Reef arm of the benchmark uses the Phase 2 CLI (`reef status`, `reef diff`, `reef log`); without R2.05 there is nothing to measure.
- **R2.27 is new: client-side store builds** ([#61](https://github.com/reef-vcs/reef/issues/61), filed by RX.01 for Phase 2 "with R2.13"). The daemon stops running repository-declared commands by default: `reef store build` and the MCP tool run the build in the client's own process, in a scratch workspace the daemon prepares and seals. ADR 0022's second decision is amended by ADR 0039 and `[store] allow_builds` defaults to `false`.
- **RX.03 is in this set** (first needed: Phase 2) and depends on R2.05 and R2.17: it reports the counters the CLI and the token benchmark define. It ships collection and a local report; the upload endpoint is configuration, empty by default, because no collector exists yet.
- **The reads of the new services run off the repository thread.** ADR 0012 put "every jj transaction" on the repository thread and said nothing about reads, which Phase 1 did not have. `Arc<ReadonlyRepo>` is `Send + Sync` (R1.03's static assertion), so `Status`, `Log`, `Get`, `Diff`, `Trees.*`, `Symbols` and `Queries` take the thread's current head and run on the blocking pool, bounded by a semaphore; only transactions queue behind one another. ADR 0045 records it.

### Threads and reads

| Topic | Decision | Set by |
| --- | --- | --- |
| Reads off the repository thread | `RepoHandle::head() -> Arc<ReadonlyRepo>` returns the thread's current head without queueing a job: the thread publishes it through an `arc_swap::ArcSwap` after every transaction and reload. Read RPCs load the head once per request and run jj-lib on `tokio::task::spawn_blocking` with `pollster::block_on`, under a `tokio::sync::Semaphore` of `[api] max_concurrent_reads` permits (default `available_parallelism`). A read never writes. A read that needs the working copy's files (R2.02's `Status` before R2.23) takes the workspace's `Arc<Mutex<WorkspaceHandle>>` as scans do. ADR 0045. | R2.02 |
| Writes | Every transaction still runs on the repository thread through `RepoHandle::call_async`, which stays the write lock R1.18's quiesce pauses. `Describe`, `Abandon`, `Squash`, `Undo`, `Trees.Apply` are one transaction each, with descriptions `reef: describe <change>`, `reef: abandon <change>`, `reef: squash <change> into <change>`, `reef: undo operation <op>`, `reef: apply edit to <change>`. Each sets the operation attribute `reef.client` (see remote) and the jj workspace name of the Reef workspace the request named, if any. | R2.03, R2.04 |
| Reloads | Operations written outside the daemon (`jj` at the registered root) are noticed by R2.09's op-heads watch, which runs `RepoHead::reload` on the thread; read RPCs that follow see them. Until R2.09 lands, reads see external operations after the next transaction or snapshot, as Phase 1 did. | R2.09 |

## Ticket file format

Each ticket has: Context (with "What was verified while writing this ticket" where it depends on jj-lib, a crate, a vendor's format or a runner), Decisions, Deliverables (file by file), Tests, Implementation notes, Acceptance criteria, Verification, Out of scope, Risks. Acceptance criteria are written so an agent can check each one mechanically before opening the PR. Anything not verified is marked as such. A brief that touches a trust boundary (a new listener, a new RPC, a new file the daemon writes or runs, a new place it reads repository content, anything a browser or a remote client reaches) adds its rows to `docs/threat-model.md`'s findings table and names them.

## Process

Unchanged from Phase 1, with the Phase 2 names:

- Work happens in a Reef workspace on the colocated jj repository (`reef ws create --new-on main --purpose "R2.xx ..."`), one workspace per commit, with `CARGO_TARGET_DIR` set to the checkout's `target/` so builds are warm; `jj` runs from the root, not inside the workspace. After every merge to `main`: `jj git fetch`, `jj new main`, reinstall `reef` and `reef-daemon` from the checkout, restart the daemon. Each PR keeps a "Dogfooding notes" section of Reef friction hit on the way, so it becomes tickets. Phase 2 is the phase in which the dogfooding gets `reef status`, `reef diff` and `reef undo`; note in the PR when a `jj` command at the root was still needed and why.
- Branch (bookmark) `r2.xx-<slug>`, implement, `just ci`, Fable 5.1 review, fix, PR in the template's sections with the review table (finding, severity, resolution), DCO sign-off on every commit, `docs/dev-phases.md` updated if scope or dependencies changed, `CHANGELOG.md`'s `[Unreleased]` section updated for anything user-visible.
- Linux-only code (the remote job's network namespace, the overlay tier) is compiled and tested in the privileged container `docs/benchmarks.md` describes before pushing; the Mac never compiles it.
- The phase closes with a 0.2.0 release: the version bump touches `Cargo.toml`, both SDKs, the UI package, `install.sh`'s pin, the tap formula and `CHANGELOG.md` (R1.28's release runbook lists them).
