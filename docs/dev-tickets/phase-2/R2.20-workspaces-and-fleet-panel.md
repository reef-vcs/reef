# R2.20 Workspaces and fleet panel

Phase 2 · Size M · Depends on: R2.18 (the app, the shared operation and presence streams, `StateBadge`, the tokens, the READ-only listener), R2.10 (`LEASE`, `EDITING` and `PROGRESS` entries, `Presence.lease`, `by_daemon`, `end_reason`), R2.11 (client `ACTIVITY` entries and the rule that names their agent), R2.12 (`at_operation` on `ListWorkspaces` and `GetWorkspace`), R2.19 (the router's parameters, `?at=`, the scroll anchor, the smartlog this view links into) · Unblocks: Phase 2's exit criterion on the web UI, R3.39 (its menu bar shows the same fleet state), R5.06 (tier outcomes in the fleet panel); R3.36 reuses its agent join

## Context

The design's fleet panel shows "each agent with its workspace, current change, lease health, and presence", so a person can see "who is doing what, and what is stuck" (`docs/design.md`, Live by default). The design also says the daemon's workspace listing shows "owner, lease state, change, dirtiness, and measured disk usage from one source" (Workspaces, Inventory). Phase 2's exit criterion "A local web UI shows the smartlog, workspaces, and fleet panel live" waits only on this ticket: R2.19 shipped the smartlog.

Most of what the panel needs is already served. `ListWorkspaces` lists active workspaces with owner, purpose, change, commit, attention, lease (state computed at the response), last snapshot and changed-file count, from the metadata database. `GetWorkspace` adds disk usage, recent snapshots, stores and the other workspaces on the same change. The presence stream carries the daemon's `LEASE` entries (observed heartbeats, each carrying the lease), `EDITING` entries (paths from snapshots) and `PROGRESS` entries, plus clients' `ACTIVITY` entries (R2.11), each with an end reason that separates "finished" from "went silent" (ADR 0037, decision 15). The operation stream names the workspace and agent of every operation. `ListChanges` with `working_copies()` returns each workspace's change.

What is missing is the view. It needs a definition of "agent" that matches how entries are reported. It needs a lease health that stays honest without a ticking clock. Disk usage costs a directory walk per workspace, so it needs a measuring policy that bounds that cost. And it needs the joins that give every workspace its agents and every agent its change.

This brief proposes no API change. Every RPC the view calls exists and is `ACCESS_READ`, so the web listener already serves it (R2.18's gate, step 8; `web_ui::only_read_rpcs` covers every method in `reef_api::methods()`).

### What was verified while writing this ticket

Reef at `6228101` (#144 merged). `API_REVISION` is 14 (`reef-api/src/lib.rs:49`). Paths are under `crates/` unless they start with `docs/` or `web/`.

- **The workspace reads.** `ListWorkspaces` (`reef-api/proto/reef/api/v1/workspaces.proto:34`) reads "from the metadata database only". It takes `repo`, `states`, `owner`, `page_size` (0 means 100, maximum 1,000), `page_token`, `changed_file_counts` (`:431`) and `at_operation` (`:437`), and lists newest first. `changed_file_counts` costs "one tree diff per such workspace on its repository's read thread; no snapshot is taken". It is best effort under a 5 s timeout (`reef-daemon/src/service/workspaces.rs:217`): counts are left unset when the timeout passes. `Workspace` (`:237`) carries `owner`, `purpose`, `change_id`, `commit_id`, `backend`, `path`, `state`, `divergent`, `attention`, `created_at`, `last_snapshot_at`, `last_snapshot_operation_id`, `lease`, `watcher`, `local_snapshot_count`, `stores`, `watch_state`, `changed_file_count` (`:290`) and `remote_token_id`. `Lease` (`:212`) carries `id`, `owner`, `issued_at`, `expires_at`, `last_heartbeat_at`, `length`, `grace`, `state` (`ACTIVE`, `IN_GRACE`, `EXPIRED`, `ENDED`, computed "when the response is built ... and the daemon's clock"), `end_reason` and `heartbeat_every` (`:233`).
- **Disk usage is a walk, and only `GetWorkspace` does it.** `GetWorkspaceResponse.disk_usage` (`DiskUsage { allocated_bytes, files_changed }`, `:312`) is filled unless `skip_disk_usage` is set. The daemon measures it on the blocking pool (`reef-daemon/src/workspace/manager.rs:517`, `:551`). For copy, APFS and reflink backends the measurement walks the whole workspace root and compares every file with the base's tree state (`backend/fs_util.rs:149`, `changed_files_vs_base`). For overlay backends it walks the upper directory (`backend/overlay/mod.rs:396`). It counts ignored files such as build output, which no snapshot records. It is unset when the base is no longer cached, at an operation, and for a workspace that is not active. `ListWorkspaces` has no disk field. `base_bytes_unshared` is a field of `CollectGarbage`'s report (`maintenance.proto:108`), an ADMIN RPC the browser cannot call, and is about bases, not workspaces.
- **Leases on the presence stream.** The daemon publishes one `LEASE` entry per workspace when it issues a lease (`lease/mod.rs:322`, `:341`) and at every renewal (`:357`). Its agent is the lease's owner, it carries the lease as of that heartbeat, and its TTL is twice `heartbeat_every` (`presence/publish.rs:27` to `:53`). `heartbeat_every` is `min(lease.heartbeat, length / 3)`, 60 s by default (`lease/mod.rs:286`, `config.rs:297`). So an entry that ends `EXPIRED` means "two heartbeats missed", long before the lease lapses (ADR 0037, decision 11), and after a daemon restart no entry exists until each holder's next heartbeat. `EDITING` entries last 60 s after the last snapshot (`presence/mod.rs:85`) and name the owner. Lease state changes with time but no event marks the change: the lease enters `IN_GRACE` or `EXPIRED` and nothing is published or recorded until the daemon reclaims the workspace, which records an operation.
- **Agents in presence.** A client entry's agent is the `reef-agent` name, else the workspace's owner (R2.11, rule 7). Daemon entries always name the owner (`presence/publish.rs:1` to `:4`). `ws run`'s owner is `<user>@<host>:<pid>`. So one `ws run` with `REEF_AGENT=reviewer` shows as two names: `reviewer` on its `ACTIVITY` entry, and `alice@laptop:4242` on its `LEASE` and `EDITING` entries.
- **The app counts and labels them as two.** The overview's "Active agents" counts distinct `agent` values over every entry (`web/src/views/Overview.tsx:69` to `:80`). The smartlog's agent labels do the same (`web/src/views/Smartlog.tsx:73`, `:94`). Both count daemon entries' owner as an agent beside the name it runs under.
- **The shared presence store drops end reasons.** `PresenceStore.applyFrame` deletes an entry when its event is `ended`, and keeps neither the reason nor the last state (`web/src/live/presence.ts:44`). ADR 0037 added `end_reason` "since 'finished' and 'went silent' are a fleet panel's most different signals". Every tab still receives the ended events, with their reasons: followers decode the leader's frames verbatim (`live/share.ts`).
- **Operations name workspaces.** `Operation.workspace_id` and `agent` are set for creates, moves, releases, snapshots and writes (`operations.proto:200` to `:210`). Kinds `CREATE_WORKSPACE`, `RELEASE_WORKSPACE` (also a reclaim) and `MOVE_WORKSPACE` exist (`:131`). Streamed operations carry their effects, including the working copies they moved.
- **The app.** `api/connection.ts` builds eight clients and no `WorkspaceService` client. `workspaces.proto`'s descriptor is already in the bundle, since `status.proto` and `presence.proto` import it, so a client for its service adds almost nothing. `ui/router.tsx` has `match`, `href`, `useSearch` and `navigate(…, { replace })`. The smartlog's coalescing (`views/smartlog-model.ts:254`, `MIN_SPACING_MS` 250 ms at `:36`) and its scroll anchor (`Smartlog.tsx:241`) are private to it. Its rows are `role="option"` inside a `role="listbox"` (`Smartlog.tsx:145`, `:491`), where its workspace and agent labels are.
- **The bundle.** The built JavaScript at `6228101` is 433,022 bytes (130,192 gzip) against `reef-web`'s `bundle_budget` of 450 KiB (460,800 bytes, `crates/reef-web/tests/assets.rs:123`), which leaves 27,778 bytes. R2.19 grew it by 50.4 kB, mostly four new service descriptors (#142).
- **The smoke test.** `web/e2e/smoke.spec.ts` drives one scratch daemon with two `ws create` workspaces (`e2e/reef.ts:112` onward). It keeps each workspace's id and change, but not its path. It writes `[ui]` and `[watcher]` configuration (`writeConfig`) and has steps for the overview, the smartlog and a restart. #128's brief leaves R2.20 to add "its views' steps".
- **Issues.** #141 (the writing agent on every smartlog row) needs history per row, not presence: this ticket leaves it. #138 (no tag effects) does not touch workspaces. #126 is the CLI's brief JSON. #135 and #89 are the remote listener's and the transport's: this view opens no stream, so it adds nothing to #89's exposure. This ticket takes none of them.
- **A stale line.** `README.md:64` lists symbol-level diffs, a query layer, remote access, replay, an incremental status index and a token benchmark as "still to come in Phase 2". All of them have merged.

## Decisions

### Size

M. The ticket is web-only apart from one daemon test, with no schema change, no daemon source change and no CLI change. The work:

- a `WorkspaceService` client and a route;
- the agent join, applied to the overview and the smartlog too;
- end reasons kept in the presence store;
- lease health;
- a disk-measurement scheduler;
- the pacing extracted from the smartlog's model;
- a view model with live refreshes, ended rows, causes and a read at an operation;
- the page with two tables and two detail panes;
- links from the overview and the smartlog;
- about twelve tests, a smoke-test step, and docs.

That is R2.19's shape without its graph layout. Dropping the disk scheduler (disk only on selection) would make it smaller, but it would drop "disk" from the row and the design's inventory, so it stays in.

### One page per repository

- **`/repos/<repo>/workspaces`**, titled "Workspaces and agents". `<repo>` is anything the API accepts, as for the smartlog. The query parameters are `workspace` (a selected workspace's id), `agent` (a selected agent's name) and `at` (an operation), all optional. When both `workspace` and `agent` are given, `workspace` wins.
- **A repository nav**, "Smartlog · Workspaces", heads both repository pages (`ui/RepoNav.tsx`). The current page is marked with `aria-current="page"`.
- The page has two sections. **Agents** is the fleet panel: who is present and what they are on. **Workspaces** is the inventory: every active workspace with owner, change, files, disk, lease and presence. Both tables are on one page because each joins to the other. Selecting an agent marks its workspaces, and every workspace names its agents.
- **Per repository, not across repositories** (decision 1 below). The overview already spans repositories with a count per repository, and that count now links here.

### Who an agent is

`web/src/fleet/agents.ts` holds one join, used by this page, the overview's count and the smartlog's labels:

1. Only live entries whose `repo_id` is the repository count. Entries with no repository are left out of every repository's page.
2. A client entry (`by_daemon` false) belongs to its `agent`.
3. A daemon entry belongs to every agent that has a client entry on the same workspace. If no client entry names that workspace, it belongs to its own `agent`, the workspace's owner.
4. The result maps each agent to its entries and to the workspace ids and change ids those entries name.

With R2.11's rule 7, a `ws run` without an agent name already reports under its owner, so it is one agent. With a name, it is one agent with that name, not two. A workspace that nothing reports on beyond the daemon's `LEASE` entry shows its owner as its agent, which is the lease holder ADR 0037 describes.

The overview's "Active agents" becomes the number of agents this join returns for the repository. The smartlog's labels become this join's agents for a change's entries and its workspaces' entries. Both drop the double count found above (decision 3 below).

### What each section shows

All text is plain text. Nothing from the API is rendered as HTML (S-33). Times are absolute, `14:03:22` with RFC 3339 in `title`, or `2026-10-31 14:03` for dates, never relative (R2.18's rule). Ids are 8 characters, with the full id in `title`. Change ids are reverse hex, as everywhere in the app.

**Agents** (one row per agent):

| Column | Shows |
| --- | --- |
| Agent | The name, as a link that selects it (`?agent=`). |
| Workspaces | Each workspace id its entries name, as a link that selects it, or "no workspace" for entries with only a repository. |
| Current change | For each of those workspaces, the workspace's change from the last refresh (not the entry's, which may predate a move), with its `StateBadge` and the description's first line. For an entry without a workspace, the entry's `change_id`. Each change id links to the smartlog with it selected (`smartlogHref({ repo, change })`). |
| Doing | The newest of its entries' content: an `ACTIVITY` entry's text, a `PROGRESS` entry's "`<phase>` `<done>`/`<total>` `<unit>`" ("`<done>` `<unit>`" without a total), or an `EDITING` entry's "editing `<n>` paths" (the first three in `title`). |
| Health | The worst lease health among its workspaces ("Lease health"). |
| Since | The newest `updated_at` among its entries. |

An agent whose entries have all ended keeps its row, in place, until the page reloads or the user presses "Hide `<n>` gone". The row then reads "finished `14:03:22`" (`CLEARED`), "went silent `14:03:22`" (`EXPIRED`), "workspace gone `14:03:22`" (`GONE`) or "ended `14:03:22`" (a reason the store did not get). The reason and time are from the last entry to end. An agent that comes back takes its row again.

**Workspaces** (one row per active or releasing workspace, newest first, as `ListWorkspaces` orders them):

| Column | Shows |
| --- | --- |
| Workspace | The id, as a link that selects it, then the attention word when set ("divergent", "stale recovered", "final snapshot failed", "store mismatch", "store missing", "watch failed", "upper missing", "mount failed"), as a neutral label. `releasing` when it is releasing. |
| Owner | The owner, and the purpose in secondary text, cut to one line, full in `title`. |
| Agents | This workspace's agents under the join, as links, at most three then `+n`. |
| Change | `StateBadge`, the change id as a link to the smartlog, and the description's first line in `title`. |
| Files | `changed_file_count`, the files its change changes as of the last snapshot. `-` when the daemon left it unset. |
| Disk | Allocated bytes beyond the base, in the CLI's units (`18 MiB`, `1.2 GiB`, from `reef-vcs/src/cli/render.rs:344`), with "`<n>` files differ from the base, measured `14:03:22`" in `title`. `-` until measured ("Disk"). |
| Lease | Health and expiry ("Lease health"). |
| Last snapshot | `last_snapshot_at`, or "none". |

A summary line above the table counts what needs a person: "`<n>` active · `<n>` missed heartbeats · `<n>` in grace · `<n>` need attention". Counts that are zero are left out. It is text, not a filter.

**A workspace that ends while the page is open** (released, or reclaimed after its lease expired) keeps its row, in place, until the page reloads or the user presses "Hide `<n>` ended". When a refresh no longer lists it, the model reads `GetWorkspace { workspace, skip_disk_usage: true }` once for its final state. The row then reads "released" or "reclaimed (lease expired)" from its state and lease end reason, plus the time and agent of the `RELEASE_WORKSPACE` operation if the stream carried one. Its Files, Disk and Lease cells empty. Rows that vanish under the cursor would break "nothing reorders under your cursor", and an agent's workspace being reclaimed is exactly what a person watching the panel wants to see.

**The other jj workspaces** (`default`, a user's own) are not Reef workspaces and are not listed. The smartlog shows them.

### Lease health, without a clock

The design bans a ticking clock in the UI (R2.18: "motion without a state change"). Lease state changes with time, though, and no event marks the change. The panel therefore shows what events and reads establish, and shows times rather than predicting them:

- **The lease** is the later of the listed one and the one in the workspace's newest `LEASE` entry, compared by `expires_at`. This is the publisher's own rule (`presence/publish.rs:38` to `:42`). The model keeps the last lease each workspace's `LEASE` entry carried, so the value survives the entry's end. A heartbeat therefore updates the lease with no read.
- **Heartbeats**, while the presence set is synced, in this order:
  - `heartbeating`: the workspace has a live `LEASE` entry. `title` gives "last heartbeat `14:03:22`, every 60 s".
  - `not heartbeating`: no live entry, and the lease has never been renewed (`last_heartbeat_at` equals `issued_at`). Only `reef ws run`, the MCP server and store builds heartbeat; a `reef ws create --lease 24h` workspace that an agent works in never does, and relies on the lease's length. That is a holder's choice, not a stall, so the word is neutral and not bold. `title` gives "issued `14:00:00`, never renewed; expires `14:00:00` tomorrow".
  - `waiting for a heartbeat`: no live entry, the lease has been renewed, within the restart window.
  - `missed heartbeats`: no live entry, the lease has been renewed at least once, outside the restart window. `title` gives "last heartbeat `14:01:10`" from the lease. This is the panel's "stuck" signal (ADR 0037, decision 11; R2.10's "`EXPIRED` while the workspace is active is stuck"): a holder that was heartbeating stopped.
  - `-`, while the presence set is not synced. A resubscription is still sending the set, and an absence then means nothing.

  The renewed test compares two fields of the folded lease, so it needs no clock either. A holder that renews once by hand (`reef ws renew`) and then stops reads `missed heartbeats`, which is right: it showed it heartbeats, then stopped. (Decided 2026-11-01; the brief as first written read every unrenewed lease as `missed heartbeats` two heartbeat intervals after its issue, which would flag every `ws create` workspace as stuck.)
- **The restart window.** After a daemon restart no `LEASE` entry exists until each holder's next heartbeat, and a session opened right after an upgrade would otherwise show every workspace as stuck. The model reads `GetDaemonStatus { skip_backends: true }` when it starts and at every presence resync. While `uptime_ms` is less than twice the largest `heartbeat_every` among the listed leases, an absent entry reads `waiting for a heartbeat`. One `after` re-renders when the window closes. It reads nothing, and the window is measured from the daemon's own uptime, so no clock skew enters.
- **Expiry**: "expires `14:30:00`". When the lease's state as last reported (by the list or the entry) is `IN_GRACE`, the cell reads "in grace until `14:35:00`" (`expires_at` plus `grace`). When it is `EXPIRED`, it reads "expired, to be reclaimed". The panel never turns "expires" into "in grace" by itself. By the time a lease could be in grace without a report, two heartbeats have been missed (since `heartbeat_every` is at most a third of the length), so a renewing holder's row already reads `missed heartbeats`. A never-renewed lease reads `not heartbeating` with its expiry time, which is the whole truth about it. The daemon's reclaim records an operation, which refreshes the row into its ended form.
- **No state color.** R2.18 left this question to this ticket. Lease health is not one of the design's object states. Rendering `missed heartbeats` in `failed` red would make red mean two things, and "green always means landed" (ADR 0047, decision 11). The health words use neutral tokens, and "missed heartbeats" is bold. The change column uses `StateBadge`, since a change is an object with a state.

### Disk: measured on a budget

Each measurement is a `GetWorkspace` call that walks a directory ("Verified"), so the panel measures under a budget rather than on every refresh. `web/src/fleet/disk.ts` holds a `DiskScheduler`:

- **What it reads.** `GetWorkspace { workspace: <id> }`, with `skip_disk_usage` false and never `snapshot_first`. The answer feeds the Disk column and, for the selected workspace, its detail pane.
- **One measurement in flight**, and the next starts no sooner than `max(250 ms, 4 × the last measurement's duration)` after the last one started: the smartlog's pacing, extracted ("Pacing"). So one open panel costs the daemon at most a quarter of one core's time in walks, however many workspaces there are.
- **Order.** The selected workspace first. Then active workspaces never measured, in list order. Then workspaces marked dirty, oldest measurement first. A workspace is marked dirty when the stream carries an operation with its `workspace_id` of kind `SNAPSHOT`, `EDIT` or `MOVE_WORKSPACE`, or one whose effects moved its working copy (`reef-<id>`). Nothing else re-measures a workspace.
- **Frames.** A measurement starts from the frame scheduler, so a hidden tab, which gets no animation frames, measures nothing. It resumes when the tab is visible.
- **"Measure again"** in the detail pane puts its workspace first and is not spaced, since a person asked for it. It is the way to see build output, which grows a workspace without any snapshot or event.
- **Failures.** A measurement that comes back without `disk_usage` (the base is no longer cached) shows "not measurable" and is not retried until the workspace is dirty again. A failed call keeps the last value and shows the error in the pane. `WEB_SESSION_INVALID` ends the session, as everywhere.

On a 100,000-file workspace each walk takes hundreds of milliseconds, so filling the column for 20 such workspaces takes tens of seconds to a minute at this budget. The PR measures it on `large` (see "Performance"). If that is too slow, the fix is on the daemon side: a disk figure the daemon keeps per workspace and serves in `ListWorkspaces` (decision 2 below).

### Live: two reads per refresh, from the shared streams

The view adds no stream. It subscribes to R2.18's `OperationStore` and `PresenceStore`, as the smartlog does.

- **Nothing is read before the operation stream is live**, so an operation recorded after a read arrives on the stream.
- **The first read** is `GetRepository { repo }` for the full id and root, since the route may name a prefix or a path, and the stream and presence carry full ids. Then `GetDaemonStatus { skip_backends: true }` for the restart window.
- **A refresh** makes two reads in parallel:
  - `ListWorkspaces { repo, states: [ACTIVE, RELEASING], changed_file_counts: true, page_size: 1000 }`, following page tokens up to 1,000 workspaces. Past that, the table says "Showing the newest 1,000 active workspaces".
  - `ListChanges { repo, revset: WORKING_COPIES_REVSET, skip_snapshot: true, page_size: 1000 }` in repository scope, where `WORKING_COPIES_REVSET` is `working_copies()` (in `web/src/graph/revset.ts`, beside `SMARTLOG_REVSET`). It reads every working copy's change in one call, with its description, conflict and divergence, and never snapshots ("A read in repository scope never snapshots", R2.19).

  The two are joined by change id. `ListWorkspaces` has no `at_operation` echo at head, so the two cannot be pinned to one operation. A workspace whose change is not in the `ListChanges` answer, because it moved between the two reads, shows its change id with no badge. The next operation, which the move itself is, refreshes both.
- **What triggers one.** A batch with `reset`, or any operation with this repository's id. Unlike the smartlog, nothing is skipped: snapshots, which are most operations, change a row's commit, last snapshot and file count.
- **Pacing.** One refresh in flight. Operations that arrive during a refresh mark it dirty, and one more refresh follows. A refresh starts no sooner than `max(250 ms, 4 × the last refresh's duration)` after the previous one started, through `live/paced.ts`. Hidden tabs get no batches and read nothing.
- **Presence** re-renders the page from `PresenceStore.version` with no read: agents, health, the Doing column, the lease fold.
- **Causes.** The model keeps, per workspace id, the latest streamed operation naming it. A row's `title` says "`<kind>` at `14:03:22` by `<agent>`", and the pane shows the operation id. The id stays text until R2.21 gives operations a route, as the smartlog's causes do. That is how this view meets "every live element links to its cause".
- **Motion only for state change.** A cell gets R2.18's `changed` transition once when its word changes: the change id (a move), the attention word, the health word, the Doing text, or the row's ended form. A new row that arrives in a live refresh is marked too. Times, counts and disk figures change without motion, so a busy agent's snapshots do not flash the table. Rows are keyed by workspace id or agent name.
- **Nothing reorders under the cursor.** Workspaces are ordered by creation, so a row never moves, and new workspaces arrive at the top. Agents are ordered by name on the first load. Later arrivals go on top, and rows never move after that. Ended and gone rows stay in place. The smartlog's scroll anchor, moved to `ui/scroll-anchor.ts`, keeps the selected row, or else the first row in view, at the same place on screen across an update.
- **Errors.** A failed refresh shows the error with `hint` and `next` above the tables and keeps the last good tables. The next triggering batch retries. `REPOSITORY_NOT_FOUND` from the first read replaces the page with the error.

### Pacing, extracted

`web/src/live/paced.ts` (new) holds the smartlog's coalescing as a class:

- `request()` asks for a run: now, after the spacing, or after the run in flight;
- `requestNow()` asks for an unspaced run, for a read the user asked for;
- one run is in flight at a time, with an `again` flag for requests that arrive during it;
- the spacing is `max(250 ms, 4 × the last run's duration)`, through `after`.

`smartlog-model.ts` uses it with its behavior unchanged, and its tests pass as they are. The fleet model's refresh and the disk scheduler each own one `Paced`.

### Presence: endings kept

`PresenceStore` gains `endings`: per entry id, the last state, the `end_reason` and the time the browser received it. Entries that end in a frame are recorded there. Entries that a resync drops (the `seen` sweep) are recorded with reason `UNSPECIFIED`. The map is capped at 1,024 endings, oldest first out. It is per tab: a tab that joins later gets the leader's live set (`snapshotFrame`, unchanged) and only the endings it sees from then on. The welcome message and the broadcast format do not change. The fleet panel reads `endings` for gone agents, for each workspace's "ended since you opened" list, and for the last lease each `LEASE` entry carried.

### Selecting a workspace or an agent

A selection is a link (`?workspace=<id>` or `?agent=<name>`) navigated with `history.replaceState`, so selecting does not flood the back button. The pane is beside the tables at 900 px and wider, and a sheet at the bottom of the viewport when narrower, as the smartlog's is (reusing its CSS).

**A workspace's pane** reads `GetWorkspace` through the disk scheduler, first in its queue, and again whenever the workspace is marked dirty. It shows:

- the full id, the state word and the attention word with its meaning;
- the owner, the purpose (full, `pre-wrap`, as text), `created_at`, the path with a copy button ("on the daemon's machine" when the page's host is not loopback), the backend, the watcher and its watch state, and the remote token id when one created it;
- the change: badge, id (reverse hex and hex), commit, description's first line, "Open in the smartlog", and `other_workspaces_on_change` as links;
- files changed, and disk with "measured `14:03:22`" and "Measure again";
- the lease: id, owner, issued, expires, grace, heartbeat interval, last heartbeat, the reported state, and the health with its reason;
- snapshots: the count, the local count, and the ten most recent (time, kind, commit, operation id as text);
- mounted stores (name, mount, mode, verified);
- presence now: each entry, with agent, kind, activity, up to 20 paths then "and `<n>` more", progress, and updated time;
- ended since you opened: up to 10 endings on this workspace, each with its reason in words;
- its cause, when the stream saw one;
- the command `reef ws inspect <id>` with a copy button.

**An agent's pane** reads nothing. It shows the agent's entries as above, its workspaces as links with their changes, and its endings since the page opened.

A `workspace` or `agent` that is not on the page (released before the page opened, or never present) shows "Not active in this repository" with `reef ws inspect <id>` for a workspace, and reads nothing.

### Reading at an operation

As R2.19 did for the smartlog, with R2.21 doing the scrubbing:

- `?at=<operation id or prefix>`, or an `atOperation` input to the model, reads `GetOperation { repo, operation_id }` once for the banner. The errors are the daemon's (`INVALID_OPERATION_ID`, `OPERATION_NOT_FOUND`, `OPERATION_NOT_RETAINED`, `OPERATION_LOG_REWRITTEN`), with `hint` and `next`.

### The API: no change

The view calls:

| RPC | Access | Where | At an operation |
| --- | --- | --- | --- |
| `RepositoryService.GetRepository` | READ | once, for the full id and root | not needed |
| `DaemonService.GetDaemonStatus` | READ | at start and at each presence resync, `skip_backends` | not used |
| `WorkspaceService.ListWorkspaces` | READ | every refresh, with `changed_file_counts` | yes (R2.12) |
| `ChangeService.ListChanges` | READ | every refresh, `working_copies()`, `skip_snapshot` | yes |
| `WorkspaceService.GetWorkspace` | READ | disk, the pane, an ended row; never `snapshot_first` | yes, without disk |
| `OperationService.GetOperation` | READ | the banner, at an operation only | not needed |
| `SubscribeOperations`, `SubscribePresence` | READ | R2.18's shared streams | not used |

All are `ACCESS_READ`, so no gate rule changes. `GetWorkspace` with `snapshot_first` is READ too, and would record an operation. The view never sends it, and test 6 checks that every `GetWorkspace` request it makes has `snapshot_first` false. `api/connection.ts` gains a `workspaces` client.

Had a field been needed, it would have taken API revision 15, in a change of its own. The candidates considered and rejected:

- **Disk usage in `ListWorkspaces`, kept by the daemon.** It would need a daemon-side cache, refreshed after snapshots and on a timer for ignored files. That is daemon work, an API revision and a staleness contract of its own, for a column the scheduler fills under a stated budget. It is decision 2 below, and a follow-up if the PR's measurement on `large` says so.
- **Events for attention and watch state.** `attention` (a watch that failed to attach, a final snapshot that failed) and `watch_state` change without an operation or a presence entry. The row shows them as of the last refresh, and any operation in the repository refreshes it. The PR files a follow-up issue for a daemon presence entry or an operation on an attention change.
- **The status index's state per workspace** (R2.23 offered it). A person watching the fleet does not act on it, and `reef status` reports `walk_reason`.
- **An `at_operation` echo on `ListWorkspaces` at head**, to pin its read to `ListChanges`'. The join tolerates a straddle, and the next operation repairs it.

### The threat model

S-33's mitigation gains one sentence. This page's URL parameters (`workspace`, `agent`, `at`) are input a link can set. `agent` is never sent to the daemon: it only selects among names the page already holds. The other two reach only READ calls, and all three are rendered as text. No new row: the page reads what any session may read (S-34). A READ session could already make the daemon walk a workspace through `GetWorkspace`, and the page bounds how often it does.

## Risks

- **Disk on large workspaces fills slowly.** At the budget, 20 workspaces of 100,000 files take up to a minute to measure, and a busy fleet keeps re-measuring. The cost is bounded, not the delay; the PR measures both, and decision 2 below is the fix if they matter.
- **Ignored files grow disk without any event.** Build output never causes a snapshot, so the figure goes stale until the workspace's next snapshot or "Measure again". The cell's `title` says when it was measured.
- **The two refresh reads can straddle an operation.** A row may show a change id with no badge for one refresh. The next operation repairs it.
- **Attention changes without an event** show at the next refresh in the repository. On a quiet repository that could take a while: the follow-up issue covers it.
- **Changing the overview's and the smartlog's agent counting** changes what earlier views showed. It is a correction, and the CHANGELOG says so under Changed.
- **`changed_file_counts` on every refresh** puts one tree diff per workspace on the repository's read thread, beside the smartlog's reads. The pacing bounds it, and the PR measures it. If it dominates, counts are asked only on refreshes triggered by a snapshot, edit or move.

## Choices this brief made, and why

- **One join for "agent"**: daemon entries name the owner, client entries name the agent, and the app counted both. One rule, applied everywhere, counts each agent once.
- **Health from events, expiry as a time**: the stream says when heartbeats stop. A clock would only predict what the daemon will report anyway.
- **Disk on a budget, not per refresh**: each figure is a directory walk. One walk in flight, paced by its own duration, bounds the cost whatever the fleet's size.
- **Ended rows and gone agents stay in place**: what just ended is the news, and rows that vanish reorder the table under the cursor.
- **Tables, not a listbox**: rows hold several links each, which options cannot.
- **No API change**: everything the row names is served; the one gap, a cheap disk figure, is a daemon design of its own.

## Departures in the implementation

- **Route helpers in their own modules.** `fleetParams` and `fleetHref` live in `views/fleet-route.ts`, and the smartlog's in `views/smartlog-route.ts` (re-exported from `Smartlog.tsx`), so the nav, the overview and the smartlog's pane link to each page without importing it: `Fleet.tsx` imports the smartlog's links, and the smartlog's pane imports the workspaces page's.
- **`Link` takes `replace` and `current`.** A selection is a link followed without a history entry, and the nav marks its page with `aria-current="page"`.
- **`Paced` runs a user's request right after the run in flight**, not after the spacing, and takes a gate. "Measure again", and the smartlog's revset field and "Show more", no longer wait out up to four times the last read when one is in flight (review finding 8). The disk scheduler starts spaced runs from an animation frame, so a hidden tab starts none (review finding 6).
- **The workspace pane's record is the row's**, from the last listing: `GetWorkspace` leaves `changed_file_count` unset and the scheduler's answer may be older. Its answer supplies only disk, snapshots and the other workspaces on the change, and only when it is for the selected workspace (review finding 1).
- **Links on a frozen page keep `at`**, so selecting a workspace at an operation reads it there (review finding 2).
- **Motion**: a word's transition follows the previous word, not the first, and going to or from `-` is not a change. An ended workspace's first cell and a gone agent's row take the transition as they turn (review finding 4).
- **A disk measurement that failed reads `failed`**, with the error in `title`, rather than "not measured yet".
- **The tables' captions are visually hidden**; the sections' headings show the same names.
- **The bundle grew 39 kB, not 15 kB**: 472.0 kB (141.0 kB gzip) against 433.0 kB on main. The page's own view code is 35 kB of it; the join, the links and the nav the rest. The JavaScript budget is 500 KiB (decision 5).
- **Performance**: only one disk walk was measured, on a 10,816-file workspace (APFS, warm): about 60 ms. The `large` runs, the refresh timings at 20 and 200 workspaces, the daemon's CPU under R2.22's generator and React's commit time were not run; decision 2's follow-up issue carries the `large` measurement.
