# R2.20 Workspaces and fleet panel

Phase 2 · Size M · Depends on: R2.18 (the shell, data layer, harness), R2.10 (`Presence.Subscribe`, `Workspace.presence`), R2.09 (`WorkspaceEvent`, `LeaseEvent` in frames), R2.01 (`Workspaces.List|Inspect|Release|Move` in v1) · Unblocks: the web UI exit criterion (with R2.19 and R2.21); R2.21's replay mode renders this view at a past `seq`; R3.36 (the map view reuses the presence model)

## Context

The design's fleet panel shows "each agent with its workspace, current change, lease health, and presence: who is doing what, and what is stuck", and the "Operate the fleet" job lists workspaces "with owner, lease, and disk" (`docs/design.md`, "Live by default", "What humans do"). Phase 1's `reef ws list` and `reef ws inspect` already answer this in a terminal, once. This ticket makes it live: one page at `/workspaces` with a table of workspaces and, beside it, the fleet panel grouping them by owner with each agent's current activity from the presence channel (R2.10). It is also where a human releases a workspace an agent abandoned or moves one to another change, each as one API call with a two-click confirmation and never a blocking dialog.

### What was verified while writing this ticket

Reef at `d156d1e`; the Phase 2 README; v0's `Workspace` message as the base v1 keeps (`crates/reef-daemon/proto/reef/daemon/v0/types.proto:56-93`).

- **What a row has without a second call.** `Workspace` carries `id, repo_id, owner, purpose, change_id, commit_id, backend, path, state, divergent, attention, created_at, last_snapshot_at, last_snapshot_op, lease (with the computed State ACTIVE | IN_GRACE | EXPIRED | ENDED, expires_at, grace_ms, heartbeat_every), watcher, local_snapshot_count, stores, watch_state` (v0 `types.proto`); the README adds `presence` (the latest `PresenceUpdate` for the workspace, or none) in v1. `Workspaces.List` reads SQLite only (`workspaces.proto:9-10` in v0) and does not measure disk; `Inspect` does (`InspectResponse.disk_usage`, skipped with `skip_disk_usage`) and takes a snapshot first unless `snapshot_first = false` (`:112-121`). So disk is a per-row lazy `Inspect { snapshot_first: false }`.
- **Lease state is computed by the daemon at response time** (`types.proto:35-38`: "Computed when the response is built, from `expires_at`, `grace_ms`, whether the lease has ended, and the daemon's clock"). Between frames the UI must count down from `expires_at` with its own clock, which can differ from the daemon's; the README's `Daemon.Status` has no server time field, so the row shows the countdown with the daemon's `expires_at` and relabels only on a daemon event (`LeaseEvent { heartbeat | expired }`, `WorkspaceEvent { reclaimed }`), never by its own clock crossing the line.
- **Mutations the UI's token allows** (README, "Scopes"): the `ui-*` token has `read,presence,workspaces`, which covers `Workspaces.Release`, `Move`, `Heartbeat`, `Snapshot` and `Inspect`; `Create` with an empty `path` is allowed too but not offered (an agent's workspace is created by the agent). `Move` takes `change` or `new_on` and a `missing_stores` policy (`workspaces.proto:140-158` in v0); a `Release` takes `force` and `skip_final_snapshot`.
- **Presence** (README, "Presence"): `Presence.Subscribe` sends the whole table first, then deltas, framed as events; entries carry `agent, workspace_id, change_id, activity (IDLE | EDITING | RUNNING | TESTING | WAITING | CUSTOM), detail, progress { done, total }` and expire after `[presence] ttl` (30 s). The daemon itself reports heartbeats, snapshots in flight, store builds, backup and GC progress. `Presence.Report` is client-streaming and cannot be called from a browser (R2.18's verification), so the panel is read-only for presence.
- **`attention` values** (Phase 1 README, "SQLite schema"): `divergent`, `stale-recovered`, `final-snapshot-failed`, `store-hash-mismatch`, `store-missing`, `watch-failed`, `upper-missing`; `watch_state` is `""`, `waiting` or `attaching`. `reef here`'s `next` logic (ADR 0025) maps states to the next command; the panel reuses the mapping for its hint text.
- **R2.18's harness** gives each smoke a `reef()` runner; `reef presence report --workspace <id> --activity testing --detail "cargo test"` (R2.11) is how the smoke produces presence, and `reef ws run -- sleep 30` produces a `RUNNING` entry and a heartbeating lease.

## Decisions

- **Two panes, one data set.** `/workspaces` renders a table on the left (every workspace of the selected repository, `active` by default with a `show released` toggle) and the fleet panel on the right (active workspaces grouped by owner, each owner a card). Both read one `useWorkspaces(repoId)` hook: `Workspaces.List` on mount, then kept current from `WorkspaceEvent`s and `LeaseEvent`s in the frames (a created workspace is fetched by `Inspect` once and inserted; snapshotted/moved/attention events patch the row's fields from the event; released and reclaimed set `state`), plus `usePresence(repoId)`: one `Presence.Subscribe` stream per page, its first frame the table, deltas patched, entries dropped client-side at `ttl` after their last update as a fallback if a delta is missed.
- **Table columns**: state dot (R2.18's `StateDot` over a workspace state palette that reuses the change tokens: `active` → draft, `releasing` → queued, `released`/`reclaimed` → muted, with `attention` set → conflicted color plus the attention text as the glyph's title), id (4 characters, full in `title`), owner, purpose (truncated at 40 columns, full on hover), change (reverse-hex short, a link to the smartlog row `/?change=<id>`, which R2.19 scrolls to and highlights), lease (below), presence (activity glyph and `detail`, with a thin progress bar when `progress.total > 0`), last snapshot (relative time, `title` the op id, a link to `/activity?op=`), disk (lazy, below), backend and watcher as muted text, and an actions cell. Sortable by the column headers but **sorting is a user action**: a frame never re-sorts; a row whose sort key changed stays where it is with a small "moved" marker until the user re-sorts or the `Held` badge is accepted (same rule as R2.19). New workspaces are held behind the badge (`2 new workspaces`) and inserted on accept; released ones stay in place with the released style until the next accept, when the `show released` toggle decides whether they stay.
- **Lease health**: `active · 27m left`, `in grace · 3m 10s` (amber), `expired` (red; the next tick reclaims), `ended (released|expired|restored)`. The countdown ticks once a second from `lease.expires_at` with the browser clock; the label (active/in grace/expired) changes only on a daemon event, as verified above, so a skewed clock shows `0s left` rather than lying about the state. A heartbeat event resets the countdown and flashes nothing (a heartbeat is not a state change). `heartbeat_every` is shown in the `title`.
- **Disk is lazy.** The disk cell shows `…` until the row is on screen for 500 ms (an `IntersectionObserver`), then one `Inspect { workspace, snapshot_first: false, skip_disk_usage: false }` fills it with `allocated_bytes` (formatted `12.3 MiB`) and `files_changed`; it refreshes on the row's next `snapshotted` event, debounced to one `Inspect` per row per 10 s, and never for `released` rows (the directory is gone; the cell shows the `freed_bytes` from the release event when known). Off-screen rows never cost an `Inspect`.
- **Fleet panel**: one card per owner string (`user@host:pid` from `ws run`, `user@host` from `ws create`; R3.03 replaces it), ordered by the time of its most recent presence update, newest first, but **held** like every list here: a card changes position only on accept. The card shows the owner, its workspaces (id, change, lease state as a colored bar), and the agent's current activity: the newest presence entry for any of its workspaces (`EDITING src/lib.rs`, `TESTING cargo test 3/12`, `RUNNING claude`, `IDLE 2m`), the detail truncated at 60 columns, and a progress bar when given. A card with no presence entry and no heartbeat for longer than the lease's `heartbeat_every × 3` shows `quiet` in muted text; one whose lease is in grace or expired shows `stuck?` in the conflicted color with the hint text from ADR 0025's `next` logic (`reef ws inspect <id>` for a flagged workspace, `reef ws release <id>` for an expired one; shown, not executed). The daemon's own presence (backup, GC, store build, snapshots in flight) is a separate `daemon` card at the bottom.
- **Actions, never modal.** The actions cell has `release` and `move`. `release` becomes `confirm release` on first click and calls `Workspaces.Release { workspace, skip_final_snapshot: false }` on the second within five seconds (then reverts); the row shows `releasing…` and settles on the `released` event, with `freed_bytes` in the disk cell. `move` expands an inline one-line form under the row: a `rev` text field (change id, bookmark, `@`; placeholder `main`), a `new change on` / `edit` toggle mapping to `new_on` / `change`, and `go`, which calls `Workspaces.Move` with `missing_stores: FAIL`; the response's error (`UNAVAILABLE` with a `hint` naming `reef store build`) shows under the form with `hint` and `next` verbatim. Neither action blocks the page: frames keep applying to every other row while a form is open. `force` and `skip_final_snapshot` are not offered (a human who needs them has the CLI). Both actions require the row to be `active`; a released row has none.
- **Attention is visible, not shouting.** A workspace with `attention` set has the conflicted-colored dot and the attention text in the title and in a muted suffix after the id (`divergent`, `watch failed`); `divergent` also links to R2.19's row for the change where both commits show. No toasts, no banners: the design's inbox is Phase 3's; here the dot is the signal.
- **Replay prop**: `<WorkspacesView rows={workspaces} presence={none} live={false} />` for R2.21; in replay mode the actions cell, disk column and presence column are hidden (presence has no history and disk was never recorded) and the lease column shows the state as it was at that `seq` from the replayed row.
- **URL state**: `?ws=<id>` highlights and scrolls to a row (R2.19's chips link here); `?released=1` for the toggle; `?sort=<column>` for the chosen sort.

## Tests

1. `lease.test.ts`: `ACTIVE` with 27 minutes left → `active · 27m left`; `IN_GRACE` → amber label with the grace remaining; `EXPIRED` → red; `ENDED` with `end_reason` → `ended (released)`; a browser clock past `expires_at` while the daemon still says `ACTIVE` → `active · 0s left`, never `expired`; a heartbeat event (new `expires_at`) resets the countdown.
2. `fleet.test.ts`: three workspaces under two owners → two cards, ordered by newest presence; an owner with no presence and no heartbeat for `3 × heartbeat_every` → `quiet`; a lease in grace → `stuck?` with the `reef ws release <id>` hint; the daemon's own entries → the `daemon` card; the newest entry wins when two workspaces of one owner report.
3. `disk.test.ts`: a row intersecting for 500 ms issues one `Inspect` with `snapshot_first: false`; leaving before 500 ms issues none; two `snapshotted` events within 10 s issue one refresh; a `released` row issues none.
4. `Table.test.tsx`: a `WorkspaceEvent { created }` frame holds the new row behind `1 new workspace` and the existing rows' order is unchanged; `accept()` inserts it; clicking a header sorts; a later frame that changes a sort key does not move the row and shows the `moved` marker; a `released` event restyles the row in place.
5. `Actions.test.tsx`: `release` → `confirm release`; a second click within 5 s calls `Release` once with `skip_final_snapshot: false`; waiting 6 s reverts without a call; `move` opens the inline form; `go` with `new change on` calls `Move { new_on }`; an `UNAVAILABLE` response renders `hint` and `next` text under the form and leaves the page live (a frame applied to another row during the error is visible).
6. Playwright `workspaces.spec.ts`: start `reef ws run --purpose fleet-smoke -- sleep 60` through the fixture; within 5 s `/workspaces` shows the row with `active` and the owner card with `RUNNING sleep`; run `reef presence report --workspace <id> --activity testing --detail "cargo test"`; within 3 s the card shows `TESTING cargo test`; scroll the row into view; within 2 s the disk cell shows a byte count; click `release`, then `confirm release`; within 5 s the row shows `released` and the card is gone or marked `released`; the `sleep` child's `ws run` exits (the directory vanished under it, the designed outcome) and the fixture records its exit code without failing the test.

## Implementation notes

- Presence entries arrive for workspaces the table may not have yet (a `created` event and the agent's first `Report` can land in either order); keep presence keyed by `workspace_id` in its own map and join at render time, never drop an entry for an unknown workspace.
- The daemon's `ttl` is 30 s; the client-side fallback expiry is `ttl + 5 s` after the entry's receipt time so a delta that was in flight is not pre-empted. Expiry is a render-time comparison, not a timer per entry.
- `Inspect` with `snapshot_first: false` and `skip_disk_usage: false` walks the directory with `walkdir` on the daemon (Phase 1 README, "Disk usage"); a `large` workspace costs tens of milliseconds and the lazy rule keeps it to rows on screen. Do not add a bulk disk field to `List`; the README's "List reads SQLite only" stands.
- The two-click confirmation state lives in the row component and resets on unmount, on a frame that changes the row's `state`, and after 5 s; a `release` of a workspace whose lease just expired races the reclaim tick, and `FAILED_PRECONDITION` (already releasing) is shown as a muted `already releasing` and the row settles on the event.
- `Move`'s `rev` field is passed to the daemon as typed; the daemon resolves it (Phase 1's rule: the client never resolves ids) and the error's `hint`/`next` are rendered as text, never as an executed command.
- The `?ws=` highlight uses the same `scrollIntoView({ block: "center" })` and 1.5 s outline as R2.19's `?change=`; share the hook (`useHighlightParam`).
- Owner cards group by the exact owner string; two `ws run`s by one user on one host are two cards (`:pid` differs), which is correct for Phase 2 (one agent process is one card). R3.03's session identity collapses them.

## Out of scope

- Creating workspaces from the UI (agents create their own; `reef ws run` is the entry point).
- `force` release, `skip_final_snapshot`, and `--path` creation; the CLI has them.
- Reporting presence from the browser (`Presence.Report` is client-streaming; the UI is a reader).
- The map view (R3.36), help requests (R3.32) and the triage inbox (R3.33).
- Per-agent cost or token figures (RX.03 collects counters; nothing is per agent in Phase 2).

## Risks

- **Clock skew between browser and daemon** makes a countdown wrong by the skew. The label is driven by daemon events only, so the worst case is a countdown that reads `0s left` for a while or jumps on a heartbeat; documented in `docs/ui.md`. A `Daemon.Status.now` field would fix it and is a one-line additive change for R2.01 if dogfooding shows it matters.
- **Presence volume**: 200 agents reporting every few seconds is 200 deltas per frame interval; each is a map write and the panel re-renders once per animation frame. R2.22's load test measures the daemon side; if the browser side lags, the panel drops to one re-render per 250 ms, not to dropping deltas.
- **Two-click confirmation on a live table**: a frame that re-styles a row between the clicks must not move the button under the pointer. Rows never move without accept (the holding rule), and the button's position inside the row is fixed, so the second click lands on the same control; the Playwright smoke clicks both without waiting.
- **Lazy `Inspect` on a workspace whose directory is mid-reclaim** returns `disk_usage` unset (v0 `InspectResponse.disk_usage` is "unset for a workspace whose directory is gone"); the cell shows `—`, not an error.
