# R2.17 Token-efficiency benchmark

Phase 2 · Size S · Depends on: R2.15 (`reef diff --symbols`), R2.05 (`reef status`, `reef log`, `reef diff` in the CLI and the guide), RX.07 (the harness, the stream parser, the judge, the results page and `onboarding.yml`), R2.16 (optional: `reef query` is one way an agent answers T3) · Unblocks: the token exit criterion; RX.03 reports the same ratio from the field later

## Context

Phase 2's sixth exit criterion: "Token cost to answer 'what is the state of this repo' is measured and at least five times lower than parsing git output." RX.07 built the harness that runs a real Claude Code agent headless, parses its `stream-json`, judges the result from the daemon's records and publishes dated rows (`docs/onboarding-benchmark.md`). It measured the step before this one: the cost of learning Reef. This ticket measures the cost of using it. The agent already knows the tool (it has `reef` on `PATH` and the guide names `status`, `log` and `diff`); the question is how many tokens three standard questions about a repository cost through Reef against the same questions through git porcelain, on the same history.

"On RX.07's harness and results page" (`docs/dev-phases.md`, R2.17) fixes the home: new scenarios in `reef-onboarding`, new sections in `docs/onboarding-benchmark.md`, the same workflow. This brief adds the questions, the fixture history both arms see, the two arms, the judge, the metric and the ratio.

## Decisions

- **Three questions, two arms, six scenarios.** `Scenario` gains `T1Reef`, `T1Git`, `T2Reef`, `T2Git`, `T3Reef`, `T3Git` (clap names `T1-reef`, `T1-git`, ...; `letter()` becomes `code()` returning `T1-reef` etc. for the new ones and the letter for A to D, used in file stems and markers). `ALL` keeps A to D; `TOKENS: [Scenario; 6]` lists the new ones, and `just onboarding tokens` runs them. The questions, from `onboarding/prompts/`:
  - **T1, state** (`t1.txt`): "Summarize the state of this repository as JSON on your last line, exactly `{"lines_of_work": [{"name": ..., "author": ..., "files": [...]}]}`: every line of work that is not `main`, who is working on it, and which files it touches relative to `main`." The exit-criterion question.
  - **T2, what changed** (`t2.txt`): "What did the line of work `agent/beta` change relative to `main`? Answer as JSON on your last line: `{"added": [...], "removed": [...], "changed": [...]}` with the names of the functions or methods in each set."
  - **T3, who touched** (`t3.txt`): "Who changed the function `area` in `pkg/geometry.py` since `main`, and in which line of work? Answer as JSON on your last line: `{"authors": [...], "lines_of_work": [...]}`."

  Each prompt ends with one arm sentence, appended by the harness, not in the file: Reef arm, "Use Reef (the `reef` command) to answer; do not run git."; git arm, "Use git to answer." The arm sentence names the tool as RX.07's A does, and nothing more: a prompt that taught `reef diff --symbols` would measure the prompt. The vocabulary "line of work" is neutral between branch and change, and the judge accepts a branch name, a bookmark name, or a change id for `name`.
- **One fixture history, built with git, seen by both arms.** `setup` for a `T*` scenario clones the default repository (or generates the synthetic one with `--offline`), then runs a fixed script through the `git` CLI, from files checked in under `crates/reef-testing/onboarding/fixtures/token/`: `main` gains one commit adding `pkg/geometry.py` (R2.14's python fixture: `area`, `perimeter`, `Point.distance`, `EPSILON`), `pkg/shapes.py` and `pkg/main.py`; then three branches off `main`, each by its own author (`GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL` `Alpha Agent <alpha@agents.example>` etc., `GIT_AUTHOR_DATE` within the last hour, descending): `agent/alpha` (2 commits: `area`'s body changed in `pkg/geometry.py`; `README.md` appended), `agent/beta` (3 commits: `centroid` added and `perimeter` moved in `pkg/geometry.py`; `Circle.scale` renamed to `Circle.resize` in `pkg/shapes.py`; `pkg/main.py`'s call updated), `agent/gamma` (1 commit: `docs/notes.md` added). HEAD stays on `main`. The expected answers are a function of the script and live beside it as `expected.json` (T1: three entries with authors and file lists; T2: `added: [centroid, resize]`, `removed: [scale]`, `changed: [perimeter?]` where `perimeter` moved unchanged, so the accepted answer treats `perimeter` as optional in `changed` and the judge documents why; `main` as `changed` is required; T3: `authors: ["Alpha Agent"]`, `lines_of_work: ["agent/alpha"]`). In the Reef arm the daemon starts on the agent's first `reef` command and imports the branches as bookmarks (`agent/alpha` etc.), so `reef log` and `reef diff --change agent/beta` see the same history git does; no Reef workspace exists before the agent runs, so nothing Reef-only is in the fixture and neither arm has information the other lacks.
- **The judge is mechanical and the same for both arms.** The last JSON object in the agent's final text (`Transcript::final_text`), parsed leniently (a fenced block or a bare line). T1: the set of `name`s, normalized (`agent/alpha`, `alpha`, a bookmark or branch name, or a change id prefix that `reef log` would resolve to the branch's head, which the harness resolves through `reef log -o json` after the trial), equals the expected set, each entry's `author` contains the expected author's first name, and each `files` set equals the expected set (paths normalized to repository-relative). T2 and T3: set equality with the optional element rule above. A trial whose answer fails the judge is a failure and, as in RX.07, counts as infinitely many for the medians of calls but its tokens are still reported in a separate `failed` column so an arm that gives up cheaply does not look efficient. `escaped_to_git` keeps its meaning and gains the symmetric `used_reef` for the git arm (a `reef` call there is a protocol violation, reported, and the trial still counts).
- **Metrics and the ratio.** The existing `Metrics` apply unchanged; `report::Row` gains `total_tokens = input_tokens + output_tokens` (medians over successful trials). Per question, the harness pairs the two arms' rows of the same date and pins and computes `ratio = median_total_tokens(git) / median_total_tokens(reef)`, printed in the Reef row's `Ratio` column and in the summary. **The exit criterion is `ratio ≥ 5.0` on T1 with every Reef trial successful**, three trials per arm; `report::target` returns it for `T1Reef` and `Row::criterion` prints the pass line. T2 and T3 report their ratios without a gate; their place is the symbol diff's and the query layer's value, measured rather than claimed. Cost in dollars and wall time are reported beside the tokens, because a cheaper arm that takes twice as long is worth seeing.
- **Why total tokens, not input alone.** An agent that reads `git log -p` spends input; one that reasons at length over a terse answer spends output. The criterion says "token cost"; the sum is the honest number, and the two parts are in the row for anyone who wants them. Cached input counts (RX.07's rule), because the model is billed for reading it.
- **Results page.** `docs/onboarding-benchmark.md` gains a section "Token efficiency (R2.17)" after the four scenario sections: what the three questions are, the fixture script in a sentence each, the judge, the ratio, then one table per question with columns `Date | Model | Claude Code | Reef | OS | Arm | Success | Tool calls | Turns | Input tokens | Output tokens | Total tokens | Cost | Wall | Ratio | Notes` and markers `<!-- onboarding-rows:T1 -->` etc. (one marker per question; both arms' rows go above it, Reef row first). `insert_rows` keys the marker by question, not by scenario, for the `T*` rows. `docs/benchmarks.md`'s R2.15 size table is linked from the section as the static estimate the measured ratio is compared with.
- **Workflow.** `onboarding.yml`'s `scenarios` input accepts the new names; a new input `tokens` (boolean, default false) adds `T1-reef,T1-git,T2-reef,T2-git,T3-reef,T3-git` to the matrix so a token run is one click; the default dispatch is unchanged (cost: six scenarios × 3 trials × under $0.10 by RX.07's A numbers, under $2 a run). `just onboarding tokens` expands the same list locally. The pins are RX.07's; a token run writes its pins into every row as before.
- **Dependencies on the Phase 2 CLI, stated.** The Reef arm's numbers mean nothing until R2.05's `reef status`/`reef log`/`reef diff` and R2.15's `--symbols` are in the build under test; the harness refuses to run a `T*` scenario when `reef --help` lacks `diff` (a setup failure, "reef build predates R2.05"), so a run against an old binary cannot post a row.
- **No ADR.** The decisions are measurement choices recorded on the results page; the criterion's definition (total tokens, ratio of medians, T1, three trials) is written there so a later change is a visible new baseline.

## Implementation notes

- Keep every `T*` change additive in the harness: `Scenario`'s existing variants, prompts, `bare()` and the A–D judge are untouched, and the A–D fixture streams still parse. RX.07's rows must not change shape; the new columns are in the new tables only.
- The arm sentence is appended at `prompt()` time so `Pins.prompt` records exactly what the agent saw, and a prompt-file change is a new baseline as before.
- `build_token_history` sets `GIT_COMMITTER_DATE` as well as the author date, so `git log` and jj's import agree on times, and uses `--no-gpg-sign`.
- The git arm's `PATH` without `reef` reuses `agent_path(.., false, ..)`; the Reef arm's is A's.
- Resolving change ids in a T1 answer: `reef log -o json` from the trial's `bin/reef` with the trial's environment, after the agent exits; match a 8+ character prefix against each entry's `change_id` and `commit_id` and map to its bookmark. The daemon is still up (the agent's `reef` calls started it); `reef daemon stop` at the end of the trial as A–D do.
- Report `total_tokens` from `Metrics.input_tokens + output_tokens` in `rows()`; do not add a third token counter to `Metrics`.
- The results page's criterion text should quote the number and the three choices (total tokens, medians, T1) so a reader can see what "five times" means without the brief.

## Out of scope

- Questions beyond the three, other harnesses (Codex is RX.07's second harness and comes to these scenarios when it comes to A–D), and prompt tuning.
- Measuring the MCP server's tool-call tokens (R2.13 adds an MCP scenario to RX.07's page when it lands; the tool definitions' size is its concern).
- A Reef-only fixture (live workspaces, divergent changes) that git cannot represent: it would make the comparison unanswerable for one arm.
- Running on pull requests, or gating merges on the ratio.

## Risks

- **The ratio depends on what the agent chooses to run.** A git-arm agent that runs `git log --oneline --all` and `git diff --stat` is cheap; one that runs `git log -p` is not. Three trials and medians smooth it, the streams are kept, and the Notes column says what the median trial ran. The criterion is a measurement of a real agent, which is what the design asked for; if the ratio hinges on the agent's taste, that is a finding to publish, not to hide.
- **The Reef arm may read the guide first.** `reef` with no arguments costs about 400 tokens (ADR 0025's budget); it is part of using Reef and counts. If it dominates T1's cost the guide is too long, which is RX.07's regression test doing its job.
- **Correctness judged by sets is strict.** An agent that lists `pkg/__init__.py` because it created one, or names `agent/beta`'s author by email, fails. The normalization rules (first name containment, path normalization, name forms) are written down and unit-tested; a borderline failure is read from the stream and the rule widened in a PR that notes it as a new baseline.
- **Model and harness pins move the number.** As in RX.07: a new pin is a new baseline, compared with later rows.
