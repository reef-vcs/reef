# R2.16 Query layer

Phase 2 · Size L (the row said M; see "Size") · Depends on: R2.14 (the symbol index and its store), R2.15 (definition matching across a diff, `DiffOptions.pairs`, `Store::find_rows`), R2.09 and R2.22 (the operation log's `Source`, effects and the broker ring this follows), R2.27 (the CLI's scope rule and JSON conventions), R2.13 (the MCP server and its `tools/list` budget) · Unblocks: R3.37 (audit and explain), R5.06 (fallback telemetry); R2.17 measures "who touched this" through it

## Context

The design says "history is a database. Agents ask structured questions such as which changes touched a given symbol in the last week and what their test outcomes were, and receive structured rows" (`docs/design.md`, Query layer), and that "jj's operation log stays authoritative in the repository; SQLite indexes it. The query layer gets SQL for free" (Technology choices). R2.14 built the symbol index, R2.15 the matching of definitions across a diff, and R2.09 and R2.22 a way to read every operation once as it is recorded. Nothing yet remembers, per change, who wrote it, what became of it, and which files and symbols it touches. `ListOperations` walks the log 10,000 operations per page and cannot filter by path or symbol, and `ListSymbols` answers for one tree, not across history.

This ticket builds that memory and one query over it. A per-repository history index follows the operation log as it is recorded, backfills from it, and keeps a row per change. Each row holds the change's outcome, the agents and workspaces whose operations wrote it and when, and the paths and symbols its net diff touches. A new `HistoryService.QueryChanges` filters those rows by symbol, path, agent, workspace, change, outcome and time window, pages them, and groups counts by agent, outcome or workspace. Every answer says how much history it covers. `reef history` and an MCP tool, `query_changes`, expose it. It also finishes the work R2.14 and R2.15 left on `ListSymbols` by name: the filters and the cursor move into SQL, so a page no longer reads and tree-checks every stored hit.

R2.01's rule binds this brief: it adds and never changes. A new service in a new file, `history.proto`, so `API_REVISION` goes up by one (see "Schema").

### What was verified while writing this ticket

Reef at `b68578b` (#110 and #112 merged; 0.2.0 installed at `74ebfcb`), jj-lib 0.46.0. Paths are under `crates/` unless they start with `docs/`.

- **API revision and ADR numbers.** `API_REVISION` is 8, with eight digests, the last "R2.15: symbol-level diff fields in `diff.proto`" (`reef-api/src/lib.rs:49`, `:54`). This ticket's revision is 9. The last ADR is 0043, so this ticket's is 0044.
- **What an operation records.** Every operation Reef records carries `reef.kind`, `reef.workspace`, `reef.agent` and, for a snapshot, `reef.snapshot-kind` (`reef-lib/src/jj/oplog.rs:280`–`:287`). `Operation.agent` is `reef.agent`, else the workspace's owner, from `Records::owner` over `reef.sqlite3`'s workspace rows (`reef-daemon/src/service/reading.rs:160`). `OperationKind` has eleven values, with `EXTERNAL` for other jj writers and `IMPORT_REFS` for git imports (`operations.proto`). `OperationEffects` lists created, rewritten, abandoned and hidden changes, at most 1,000 (`effects::MAX_EFFECTS`, `reef-lib/src/jj/effects.rs:28`). `operation_effects(head, op, max)` takes the cap as an argument (`:199`). A failed write records no operation, so the log holds no failures. Test results arrive with evidence in Phase 3.
- **Where operations are already indexed.** `reef.sqlite3` holds one row per snapshot operation (`snapshots`, migration `0003`), rebuilt from the log at start, after GC and after restore (`reef-daemon/src/snapshot/index.rs`). `SCHEMA_VERSION` is 5 (`db/mod.rs`). Its `Db` is one connection behind a mutex whose methods must stay short (`db/mod.rs:1`–`:9`).
- **GC rewrites operation ids.** GC abandons operations older than the undo window, a week, by rewriting the kept ones onto the root, so every kept operation gets a new id (ADR 0040). `reparent_mapped` builds the old-to-new map (`reef-lib/src/jj/gc.rs:1015`, `Reparented.rewritten`). `gc_with`'s callback receives only the old and new heads (`gc.rs:268`), and `GcOutcome` has no map (`gc.rs:58`). The snapshot index therefore drops and re-adds rewritten rows (`snapshot/index.rs:19`).
- **Reading the log once.** A `session::Source` reads the operations after a `Frontier` within a `Budget` (`reef-daemon/src/subscribe/session.rs:36`). `BrokerSource` serves them from R2.22's ring (`subscribe/broker.rs:528`), and `LogSource` from the log (`subscribe/feed.rs:197`). `feed::deliver` converts one operation, with its effects from the shared cache and its agent (`feed.rs:167`). A position too far behind is `ReadFailure::Behind`, and one GC rewrote is `Rewritten` (`feed.rs:53`).
- **`trunk()`** is the first of `main`, origin's HEAD, `master` and `trunk`, locally then on `origin`, else `root()` (`reef-lib/src/jj/revset.rs:93`, `changes.proto`'s header).
- **The symbol store.** `repos/<id>/symbols.sqlite3` is a cache: one writer, a few readers, WAL, `meta.format`, recreated when unreadable, outside backup and deleted with the repository (`reef-daemon/src/symbols/store.rs:1`). `find_rows(keys, role, limit)` reads the rows of a name or symbol, newest entry first (`ORDER BY o.file DESC`), with each row's enclosing definition's symbol (`store.rs:480`, `:820`). R2.15's brief called it `find_refs(keys, roles, limit_per_key)`. The code wins.
- **`ListSymbols` by name.** `query::by_lookup` reads every stored row of the name with no limit, drops those outside `dir` or the filters, tree-checks each remaining path with `files::tree_file` (one cached lookup per distinct path, through `Current`), then sorts all survivors by path and truncates to the page (`symbols/query.rs:229`–`:283`). Every page therefore costs every hit, whatever its size. jj-lib's tree cache holds 1,000 trees (`jj-lib-0.46.0/src/store.rs:51`), and rows arrive in entry-id order rather than path order, so on `large` most lookups miss it. `docs/benchmarks.md` records `list_name` on `large` at 402 ms against a 200 ms target, and leaves "pushing the tree filter and the cursor into SQL" to this ticket (`benchmarks.md:461`, `:488`). The page cursor is `seq:path` (`service/symbols.rs:146`).
- **R2.15's matching** is `reef_symbols::diff::match_definitions` over `definitions(path, occurrences)` (`reef-symbols/src/diff.rs:162`, `:358`). The daemon's `symbols::diff::compute` adds entries, coverage per pair, line diffs and call sites (`reef-daemon/src/symbols/diff.rs:758`). `matches_expand(entry, symbol, old_symbol, name)` is the "symbol, descriptor suffix or name" rule (`reef-symbols/src/diff.rs:341`).
- **The MCP budget.** `tools/list` from the installed `reef mcp` is 20,048 bytes across 20 tools, against `handshake_and_tools`' 20,250 (`reef-vcs/tests/mcp.rs:186`). `list_operations` alone is 1,331 bytes and `get_diff` 1,653. The test's comment says raising the budget again "needs the same argument in that ticket's brief".
- **The CLI.** `reef op log` filters with `--workspace`, `--change`, `--by` and `--kind` (`reef-vcs/src/cli/op.rs:100`), resolves a workspace path to an id with `scope::workspace_arg`, and stops at `--limit`, default 100 (`cli/log.rs:13`). Config durations use humantime's form (`"30m"`, root `Cargo.toml:99`), and `humantime` is a workspace dependency. `rusqlite` 0.40 is built with `bundled` and `backup` only, so a custom collation needs its `collation` feature, which adds no crate.
- **ADR 0003** keeps "indexes over the operation log and symbols" in the one metadata database. ADR 0042 already amended it for the symbol index. R2.14's brief said this ticket would `ATTACH` `symbols.sqlite3` beside `reef.sqlite3`. This brief does neither (see "Where the data lives").

## Decisions

### Size

L, not M. The work: a per-repository index file with its schema; a follower of the operation log with backfill, catch-up and GC's rewrite of operation ids (which needs the old-to-new map out of `reef-lib`); outcome tracking, including `trunk()` moving; a throttled background worker that computes each change's paths and symbol touches with R2.15's matching; one RPC with nine filters, paging and grouping; a CLI command, an MCP tool and the client's JSON; the `ListSymbols` push-down; a GC step; an ADR; 24 tests, benches and a load-test run. Each part is moderate. Together they match R2.14, which was L. Nothing here is separable without leaving the row's headline, "changes touching a symbol … by agent, by outcome", undelivered, so it is not split.

### What is answered: changes, with outcome and activity

- **The unit is the change**, by change id, as jj and the API name it. A change's commits come and go with every snapshot, and the question the design asks ("which changes touched a given symbol") is about changes.
- **What a change touches is its net diff:** its latest commit against its parents' merged tree, as `reef show` would show it. It is not the sum of its snapshots. A function added in one snapshot and deleted in the next is not a touch. A rebase does not change it.
- **Activity** is who wrote the change and when: one row per (change, agent, workspace), with the first and last time an operation by that agent in that workspace wrote it directly, the number of such operations, and the last one's id. Per-operation rows would grow with every watcher snapshot, about 1.4 million a day at the phase's 1,000 operations a minute. Activity rows grow with changes. The operations of one change remain `ListOperations` with `filter.changes`.
- **An operation writes a change directly** when the change is what the operation set out to write, not a descendant it rebased:
  - **`CREATED`** effects, always.
  - **`REWRITTEN`** effects whose new commit is a working-copy commit the operation moved (a snapshot, a move).
  - **`REWRITTEN`** effects whose previous commit is the one the operation's description names (`reef: describe commit <id>`, `reef: edit commit <id>`, `reef: abandon commit <id>`; the prefixes at `oplog.rs:474`–`:484`).
  - **For `EXTERNAL` and `OTHER` operations, every effect**, since Reef cannot tell what another jj client intended.
  - The other rewrites are rebases: they update the change's commit but add no activity. Describing a change therefore does not credit its describer with every descendant.
- **By agent** keys on `Operation.agent`, exactly as `OperationFilter.agents` does: `reef.agent`, else the workspace's owner, matched as an exact string. `--agent` and `REEF_AGENT` (R2.05) set it, and `ws run`'s default owner `<user>@<host>:<pid>` is one agent per process (R2.11). An `EXTERNAL` or `IMPORT_REFS` operation has no agent. Its activity is recorded with an empty agent, and the change's commit author's email is kept beside it, so an imported commit still says whose it was.

### What "outcome" means

The log records no failures and no test results, so an outcome is what became of the change, from the repository's state as the follower last saw it:

| Outcome | When |
| --- | --- |
| `OPEN` | The change is visible, and its commit is not an ancestor of `trunk()`. |
| `LANDED` | The change is visible, and its commit is in `::trunk()`. `landed_at` is when the follower first saw `trunk()` reach it. A change that a backfill or catch-up walk finds already landed has no `landed_at`, because the follower never saw it land. |
| `ABANDONED` | The change is no longer visible, and the operation that hid it was not an undo: `reef abandon`, a release's abandon of an empty change, or a `jj abandon` or `jj squash` in the root. |
| `UNDONE` | The change is no longer visible, and an `UNDO` operation hid it: its creation was reverted. |

- **Changes on trunk keep their change id, so a rebase onto `trunk()` before a push still lands the change.** A squash merge on a forge that is then fetched does not: it makes a new change, so the agent's change stays `OPEN` until it is abandoned. ADR 0044 records this. Phase 3's landing pipeline lands through Reef and closes it.
- **`divergent` is a flag, not an outcome.** A divergent change is `OPEN` or `LANDED` with `divergent` set.
- **An undo that brings a change back** makes it visible again, and its outcome goes back to `OPEN` or `LANDED`. Outcomes are recomputed from the view, not accumulated, so replaying effects in any order gives the same answer.
- **Later outcomes extend the enum**: Phase 3's proposal states and check verdicts (the design's "what their test outcomes were"). R5.06's tier outcomes are a property of merges per language, not of changes. They become their own table and a group dimension in that ticket (see "What later tickets inherit").

### Where the data lives

- **A third per-repository file, `repos/<id>/history.sqlite3`**, beside `symbols.sqlite3`, built like it: one writer behind a mutex and a few readers, WAL, `0600` through `db::private_file`, `meta.format` "1", no migrations, recreated with a warning when unreadable or of another format, deleted with its repository (`ForgetRepository` removes `repos/<id>/`). `reef.sqlite3` and its `SCHEMA_VERSION` (5) do not change.
  - **Why not `reef.sqlite3`.** Every row is derived from jj's operation log and commits, which stay authoritative (ADR 0003). Queries join tables of hundreds of thousands of rows and must not hold the metadata mutex that lease heartbeats take. A derived index should not grow every backup. ADR 0044 amends ADR 0003 for it, as ADR 0042 did for the symbol index.
  - **Why not `ATTACH` `symbols.sqlite3`**, as R2.14's brief planned. The symbol store evicts entries by size and age and is recreated whenever its format or extractors change. A history of what changes touched must outlive both. So touches are stored in `history.sqlite3` with their own interned symbol, name and path strings, and nothing joins across the two files. An attached file would also have to be re-attached on every reader whenever the symbol store is recreated.
- **It is not backed up.** A lost file is recreated and backfilled from what the operation log still holds (below). Activity older than the log, which GC trims to the undo window, is lost with it. Durable, signed attribution is R3.04's provenance, in `reef.sqlite3`. Open question 2.
- **Rows outlive the operations GC abandons.** Commits and change ids do not change when GC rewrites operations, so a change's row, activity and touches stay true. Only the operation ids stored with them need mapping (below).

The schema, final names the implementer's:

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- format, frontier, trunk, backfill
CREATE TABLE names (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE symbols (id INTEGER PRIMARY KEY, symbol TEXT NOT NULL UNIQUE, name INTEGER NOT NULL);
CREATE TABLE paths (id INTEGER PRIMARY KEY, path TEXT NOT NULL UNIQUE);
CREATE TABLE agents (id INTEGER PRIMARY KEY, agent TEXT NOT NULL UNIQUE);   -- '' for none
CREATE TABLE changes (id INTEGER PRIMARY KEY, change_id BLOB NOT NULL UNIQUE, commit_id BLOB NOT NULL,
                      outcome INTEGER NOT NULL, divergent INTEGER NOT NULL, empty INTEGER,
                      subject TEXT NOT NULL, author_email TEXT NOT NULL,
                      first_at INTEGER NOT NULL, last_at INTEGER NOT NULL,
                      landed_at INTEGER, ended_at INTEGER,
                      touched_commit BLOB, touched_at INTEGER, symbols_coverage INTEGER,
                      paths_changed INTEGER, paths_truncated INTEGER, symbols_changed INTEGER);
CREATE INDEX changes_by_last ON changes (last_at DESC, id DESC);
CREATE INDEX changes_untouched ON changes (last_at) WHERE touched_commit IS NOT commit_id;
CREATE TABLE activity (change INTEGER NOT NULL, agent INTEGER NOT NULL, workspace_id TEXT NOT NULL,
                       first_at INTEGER NOT NULL, last_at INTEGER NOT NULL, operations INTEGER NOT NULL,
                       last_operation_id TEXT, PRIMARY KEY (change, agent, workspace_id)) WITHOUT ROWID;
CREATE INDEX activity_by_agent ON activity (agent, last_at);
CREATE INDEX activity_by_workspace ON activity (workspace_id, last_at);
CREATE TABLE change_paths (change INTEGER NOT NULL, path INTEGER NOT NULL, kind INTEGER NOT NULL,
                           PRIMARY KEY (change, path)) WITHOUT ROWID;
CREATE INDEX change_paths_by_path ON change_paths (path, change);
CREATE TABLE touches (change INTEGER NOT NULL, seq INTEGER NOT NULL, symbol INTEGER NOT NULL,
                      old_symbol INTEGER, name INTEGER NOT NULL, kind INTEGER NOT NULL,
                      change_kind INTEGER NOT NULL, path INTEGER NOT NULL,
                      PRIMARY KEY (change, seq)) WITHOUT ROWID;
CREATE INDEX touches_by_symbol ON touches (symbol, change);
CREATE INDEX touches_by_old_symbol ON touches (old_symbol, change) WHERE old_symbol IS NOT NULL;
CREATE INDEX touches_by_name ON touches (name, change);
```

Times are milliseconds since the epoch, as in `symbols.sqlite3`. Ids are stored as bytes, and the API spells them in hex (ADR 0029, decision 7).

### How it is filled

- **A follower per open repository**, started when `OpEvents` adds the repository and stopped when it is removed or forgotten. It reads with the same `session::Source` the subscriptions use (`BrokerSource` when the broker is on, else `LogSource`) and a matcher that keeps everything. So with the broker on, each operation is read from the log once for every subscriber and the history together. Its position is a `Frontier`, stored in `meta.frontier` in R2.09's cursor encoding and written in the same transaction as the rows it covers. Effects come from `operation_effects` with a cap of 10,000 change entries, not the API's 1,000. Past that, the remaining rebases go unrecorded, and so do the direct changes of an import that large. ADR 0044 records it.
- **Each batch, in one transaction:**
  - **Changes**: one row per change id seen, and its `commit_id` set to the latest commit an effect gave it.
  - **Activity**: added for direct effects.
  - **The outcome** recomputed for every change the batch touched: its visible commits at the batch's tip (divergent when more than one), `LANDED` by ancestry of `trunk()`, and for an invisible change, the kind of the operation whose effect hid it.
  - **`trunk()` moves**: when `trunk()`'s commit at the tip differs from `meta.trunk`, the change ids in `old..new` (at most 10,000 commits, else every row's ancestry is rechecked in a background sweep) become `LANDED` at the batch's last `ended_at`, and those in `new..old` (trunk rewound) return to `OPEN`.
  - **Nothing heavy**: no tree is diffed here.
- **Two `reef-lib` helpers**, in `reef_lib::jj::history`: `change_states(repo, change_ids, trunk) -> Vec<ChangeState { commits, landed }>` and `change_ids_between(repo, from, to, cap)`.
- **Catch-up and backfill.**
  - **A new or recreated file** has no frontier. The follower sets it to the op heads, then backfills newest first through `oplog::walk_from` (what `ListOperations` walks), in chunks of 1,000 operations, each chunk one transaction, with `meta.backfill` recording where it stopped. A restart resumes there.
  - **Where it stops**: at the root, at `[history] backfill_operations` (default 100,000) or at `[history] retention` (default 90 days) by `ended_at`, whichever comes first.
  - **Order does not matter**: activity takes minima and maxima, and outcomes come from the view.
  - **`ReadFailure::Behind`**, after a long stop with other jj writers, is the same walk, down to the frontier instead of a cap.
  - **Coverage**: while either walk runs, every response's `coverage.backfilling` is set, and `oldest_at` says how far back the history reaches.
- **GC's rewrite of operation ids.** `GcOutcome` gains `rewritten: Vec<(OperationIdHex, OperationIdHex)>`, the map `reparent_mapped` already builds, in a new `reef-lib` field. Right after the jj step, under the repository's follower lock, GC maps `meta.frontier` and every `activity.last_operation_id` through it. Ids of abandoned operations become `NULL`. The follower then continues from the mapped frontier without seeing `Rewritten`. If the follower still meets `Rewritten` (a crash between the steps, another jj client's GC), it resets its frontier to the heads and runs the catch-up walk, which re-applies effects idempotently. Activity counts can then double-count the overlap, and ADR 0044 says so. The snapshot index could use the same map instead of dropping and re-adding rows. That is not done here (see "Out of scope").

### Touches: paths and symbols per change

- **A background worker** computes each change's touches: one at a time per daemon, on the blocking pool, under one read permit. Inline extraction for `ListSymbols` and R2.15's diffs runs the same way (ADR 0043, decision 7).
- **Its queue is the table**: the changes whose `touched_commit` is not their `commit_id` (`changes_untouched`), newest `last_at` first.
- **Throttled.** A change is computed once it has been quiet for 5 s, or when its touches are 60 s older than its commit, whichever comes first. A workspace snapshotting every few seconds is therefore computed about once a minute while active and once when it settles. A change computed for an older commit is `STALE` in answers until then.
- **Paths.** The files that differ between the commit and its parents' merged tree, through `diff::diff_page` with `pairs` (R2.15). At most 10,000 are stored, in path order. Past that, `paths_truncated` is set, and `paths_changed` counts them all. A change with no differing paths is `empty`.
- **Symbols**, when the symbol index is enabled and at most 1,000 files differ (R2.15's limit):
  - **A new `symbols::diff::touches(index, store, tree, pairs) -> Touches`** runs R2.15's `entries`, `pair_state` and `Matched::changes` and returns each change's symbol, old symbol, name, kind, change kind and path, with no line diffs, nesting, expansion or call sites.
  - **Missing entries** are extracted inline, at most 1,000 files per side, as `GetDiff` does. The new side is usually indexed already by the background pass.
  - **At most 10,000 touches** are stored per change.
  - **`symbols_coverage`**: `COVERED` when every differing file was `COVERED` or `UNSUPPORTED` (a file of no supported language and no SCIP has no symbols to miss); `PARTIAL` when some were `SKIPPED`; `TOO_LARGE` past 1,000 files; `DISABLED` when the index is off.
- **Imported history.** An `IMPORT_REFS` operation's created changes get rows only when their commit's committer time is within `[history] retention`, and their activity is dated by that time, not by the import's, so a fetch today of last month's commits does not look like today's work. The worker computes them after every other pending change. That covers a fetch's new trunk commits, up to the effects cap. The registration's own import brings in at most the effects cap of the repository's recent history, newest first, and nothing older than `retention`. "Who touched this" for older history is `git log` (see "Out of scope").
- **Abandoned and undone changes** keep their last touches. A change abandoned before its last commit was computed is computed from that commit, which jj keeps for the undo window.

### Retention and GC

- **A sixth GC step per repository** (`history/gc.rs`), after the symbols step. It deletes changes that are not `OPEN` and whose `last_at`, `landed_at` and `ended_at` are all before `now - [history] retention`. While the file's live bytes pass `[history] max_size` (default 512 MiB), it deletes the oldest such changes in batches, then `OPEN` ones whose activity is older than retention, and never a change with activity in the last day. It prunes unused names, symbols, paths and agents, and steps `PRAGMA incremental_vacuum`.
- **The rewrite of operation ids** happens right after GC's first step, not in this step, so the follower never reads between the two.

### The API: a typed query, not SQL

- **One RPC, `HistoryService.QueryChanges`**, in a new `history.proto`. `ACCESS_READ`, `NO_SIDE_EFFECTS`.
- **No raw SQL from callers.**
  - **The schema is a cache's**, recreated under a new `meta.format` whenever it changes. SQL against it would be a contract nothing versions.
  - **R2.08's remote listener and R2.18's web UI** would turn caller SQL into an injection and denial-of-service surface: `ATTACH`, `PRAGMA`, unbounded joins.
  - **Typed filters** get page tokens, bounds and SDKs generated from the schema (ADR 0029, decisions 10 and 11), and the store (R4) can serve the same RPC from Postgres.
  - **A person who wants SQL** can open the file read-only. Its format is documented in the daemon README as unstable.
- **Its own service and file.** Answers come from an index, not from jj state at an operation, so `QueryChanges` has no `revision` or `at_operation`, and it fits neither `ChangeService` nor `OperationService`. buf's `FILE` rules make the placement final.
- **Filters.** Every field is optional and ORed within itself, and fields are ANDed (ADR 0029, decision 11):
  - **`symbols`**: entries matched by R2.15's rule, `matches_expand`. An entry is a full symbol string (compared with `symbol` and `old_symbol`), a suffix of one from a descriptor boundary (`Parser#parse()`), or a display name (`parse`). The store finds candidates by the entry's display name (its last descriptor's name, or the entry itself when it does not parse) through `touches_by_name`, and keeps those `matches_expand` accepts. Every lookup uses an index.
  - **`paths`**: a file or a directory by whole components, as R2.14's `under`. In SQL: `path = ?d OR (path >= ?d || '/' AND path < ?d || '0')`, a range scan of `paths`.
  - **Both set**: one touch must satisfy both, its path under a `paths` entry.
  - **`symbol_changes`**: `SymbolChangeKind` values. Only with `symbols`.
  - **`agents`, `workspaces`, and `since` and `until`** apply to one activity row together: a change matches when some activity row has a listed agent, a listed workspace, and `last_at >= since` and `first_at < until`. "Changes `bot-1` worked on last week" is therefore one condition, not three.
  - **`workspaces`** are ids or unique prefixes of four or more hex characters, matched against the ids the history recorded. A workspace whose row GC removed still matches, and an entry that matches none returns nothing rather than `NOT_FOUND`.
  - **`changes`**: change id prefixes, hex or reverse hex, as in `OperationFilter.changes` (`INVALID_CHANGE_ID` otherwise).
  - **`outcomes`**: `ChangeOutcome` values.
  - **`include_empty`**: changes with no differing paths are left out unless it is set. Every released workspace leaves an empty change behind. A change whose touches are still `PENDING` is not known to be empty, and is included.
- **Order and paging.** Rows come newest first by `last_at`, the change's latest direct activity, then by row id. The page token's cursor is `(last_at, id)`, bound to the other fields as every page token is (`service/page.rs`). A change that becomes newer between pages moves ahead of the cursor and is not repeated. `page_size` is as everywhere: 0 means 100, at most 1,000. A page also stops before 3 MiB.
- **Each row lists, at most:**
  - **16 activity rows**, the latest first, with `activity_count`.
  - **20 touches** that matched the `symbols` and `paths` filters, when either is given (none otherwise), with `touch_count`.
  - **20 matched paths**, when only `paths` was given.
- **Grouping.** `group_by` takes one or more of `AGENT`, `OUTCOME`, `WORKSPACE` and returns `groups`, each with the grouped fields and a count, sorted by count, then by key, and no `changes`. Grouping by agent or workspace counts a change once per matching activity row, so totals can exceed the number of changes. That is the useful count for "changes per agent". At most 1,000 groups, then `groups_truncated`. A grouped request does not page, and a `page_token` with `group_by` is `INVALID_HISTORY_QUERY`.
- **Coverage, on every response:**
  - **`oldest_at`**: the earliest activity the history holds for the repository.
  - **`backfilling`**: set while a backfill or catch-up walk runs.
  - **`behind`**: operations recorded after the follower's position, counted up to 10,000.
  - **`pending`**: changes whose touches are not current.
  - **`symbols`**: whether symbol touches are computed.
  - **Each row** also says `touches_state` (`PENDING`, `CURRENT`, `STALE`), `symbols_coverage` and `paths_truncated`. An answer never hides that it is partial, as R2.15's coverage does not.
- **Bounds on the request.** `symbols` and `paths` hold at most 100 entries each, and `agents`, `workspaces` and `changes` at most 100 each. Entries must not be empty, `since` must not be after `until`, `symbol_changes` needs `symbols`, and enum values must be known, or the request is `INVALID_HISTORY_QUERY` with metadata `field`.

### Errors and reasons

Two new reasons.

| Reason | Kind | Metadata | When |
| --- | --- | --- | --- |
| `HISTORY_DISABLED` | `FAILED_PRECONDITION` | | `[history] enabled = false`. Hint: set it and restart the daemon. |
| `INVALID_HISTORY_QUERY` | `INVALID_ARGUMENT` | `field` | A bound or value above is broken, or `group_by` comes with a `page_token`. `next`: `reef history --help`. |
| `SYMBOLS_DISABLED` (exists) | `FAILED_PRECONDITION` | | `symbols` or `symbol_changes` with `[symbols] enabled = false`. Path, agent and outcome queries still work. |
| `INVALID_CHANGE_ID`, `INVALID_PAGE_TOKEN`, `REPOSITORY_NOT_FOUND`, `REPOSITORY_NOT_REGISTERED` (exist) | as elsewhere | as elsewhere | as for `ListOperations` |

A history still backfilling, or behind, answers with what it has, and its coverage says so. That is not an error.

### Schema

```proto
service HistoryService {
  // Changes from the repository's history index, newest activity first, filtered. Errors: ...
  rpc QueryChanges(QueryChangesRequest) returns (QueryChangesResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
}
enum ChangeOutcome { CHANGE_OUTCOME_UNSPECIFIED = 0; CHANGE_OUTCOME_OPEN = 1; CHANGE_OUTCOME_LANDED = 2;
  CHANGE_OUTCOME_ABANDONED = 3; CHANGE_OUTCOME_UNDONE = 4; }
enum ChangeDimension { CHANGE_DIMENSION_UNSPECIFIED = 0; CHANGE_DIMENSION_AGENT = 1;
  CHANGE_DIMENSION_OUTCOME = 2; CHANGE_DIMENSION_WORKSPACE = 3; }
enum TouchState { TOUCH_STATE_UNSPECIFIED = 0; TOUCH_STATE_PENDING = 1; TOUCH_STATE_CURRENT = 2;
  TOUCH_STATE_STALE = 3; }
enum HistorySymbolCoverage { HISTORY_SYMBOL_COVERAGE_UNSPECIFIED = 0; /* not computed */
  HISTORY_SYMBOL_COVERAGE_COVERED = 1; HISTORY_SYMBOL_COVERAGE_PARTIAL = 2;
  HISTORY_SYMBOL_COVERAGE_TOO_LARGE = 3; HISTORY_SYMBOL_COVERAGE_DISABLED = 4; }
message QueryChangesRequest {
  string repo = 1;
  repeated string symbols = 2;              // symbol, descriptor suffix or name; at most 100
  repeated string paths = 3;                // file or directory; at most 100
  repeated SymbolChangeKind symbol_changes = 4;
  repeated string agents = 5;
  repeated string workspaces = 6;           // ids or prefixes, as recorded
  repeated string changes = 7;              // change id prefixes, hex or reverse hex
  repeated ChangeOutcome outcomes = 8;
  google.protobuf.Timestamp since = 9;      // activity window, with agents and workspaces
  google.protobuf.Timestamp until = 10;
  bool include_empty = 11;
  repeated ChangeDimension group_by = 12;
  int32 page_size = 13;
  string page_token = 14;
}
message QueryChangesResponse {
  repeated HistoryChange changes = 1;       // empty with group_by
  string next_page_token = 2;
  repeated ChangeGroup groups = 3;
  bool groups_truncated = 4;
  HistoryCoverage coverage = 5;
}
message HistoryChange {
  string change_id = 1;  string commit_id = 2;  ChangeOutcome outcome = 3;  bool divergent = 4;
  bool empty = 5;
  string subject = 6;                       // the description's first line, at most 200 bytes
  string author_email = 7;
  google.protobuf.Timestamp first_at = 8;   google.protobuf.Timestamp last_at = 9;
  google.protobuf.Timestamp landed_at = 10; google.protobuf.Timestamp ended_at = 11;
  repeated ChangeActivity activity = 12;    uint32 activity_count = 13;
  repeated SymbolTouch touches = 14;        uint32 touch_count = 15;
  repeated string matched_paths = 16;
  uint32 paths_changed = 17;  bool paths_truncated = 18;  uint32 symbols_changed = 19;
  TouchState touches_state = 20;  HistorySymbolCoverage symbols_coverage = 21;
}
message ChangeActivity {
  string agent = 1;  string workspace_id = 2;  // empty: none recorded
  google.protobuf.Timestamp first_at = 3;  google.protobuf.Timestamp last_at = 4;
  uint32 operations = 5;
  string last_operation_id = 6;             // empty once GC abandoned it
}
message SymbolTouch {
  string symbol = 1;  string old_symbol = 2;  string name = 3;  SymbolKind kind = 4;
  SymbolChangeKind change = 5;  string path = 6;
}
message ChangeGroup {
  string agent = 1;  string workspace_id = 2;  ChangeOutcome outcome = 3;  // the grouped ones set
  uint32 count = 4;
}
message HistoryCoverage {
  google.protobuf.Timestamp oldest_at = 1;  bool backfilling = 2;  uint32 behind = 3;
  uint32 pending = 4;  bool symbols = 5;
}
```

`ChangeGroup.outcome` is `UNSPECIFIED` unless grouped by outcome, and the string fields are empty unless grouped by them. An agent group's empty `agent` is the changes with no agent. The comment says so.

### `ListSymbols` by name and symbol: filters and cursor in SQL

The tree check cannot move into SQL. SQL holds no tree, and a tree's file list per tree is the copy ADR 0042 rejected (decision 2: "no tree is copied"). Everything around it does move into SQL, and the check runs in path order and stops at the page's end. This is how the target is met:

- **A new store read, `Store::find_ordered(key, dir, roles, kinds, source, after)`**, returns a lazy row iterator, ordered by path in jj's component order, then by `seq`, and starting after the cursor. `query::by_lookup` moves onto it. `find_rows` stays for R2.15's call sites, whose `call_sites_common` already meets its target at 25 ms on `large`.
- **What moves into SQL:**
  - **The name or symbol**, through `occurrences_by_name` and `occurrences_by_symbol`, as now.
  - **`dir`**, as the path range above.
  - **Roles and kinds**, as `IN` lists.
  - **The current extractor**: `f.source = 2 OR f.extractor IN (<the six current extractors>)`. Each extractor string names its language, so one list covers every file.
  - **SCIP before tags, when `source` is unset**: a tags row is dropped when `EXISTS` a SCIP entry for its `(path, file_id)`, through `files`' unique index.
  - **The cursor**: `(f.path COLLATE reef_path, o.seq) > (?, ?)`.
  - **The order**: `ORDER BY f.path COLLATE reef_path, o.seq`.
- **The `reef_path` collation** compares paths component by component, as `query::path_order` does, so `a/b` sorts before `a.rs`. It is registered on every store connection when it opens, which needs rusqlite's `collation` feature and no new crate. `files.path` keeps its binary order and unique index, and the format stays "1".
- **What stays in Rust:** `Current::keeps` checks each row's `(path, file_id)` against the tree, once per distinct path per request, as now. The loop stops after `limit + 1` kept rows. A page then costs one SQL statement, which sorts the name's matching rows in a temporary B-tree (a few milliseconds for 5,000), plus tree lookups for the page's paths and the stale versions met on the way. It no longer costs one lookup per hit. Lookups in path order also share jj's tree cache.
- **The answer is the same.** Same rows, same order, same cursor format (`seq:path`), so page tokens issued before the change still work. Test 21 compares the two implementations over the same store.
- **The proof** is the `list_name` bench on `large`: 402 ms before, under 200 ms after (expected around 20 ms), and a new `list_name_deep` row that reads a page 40 pages in to show a later page costs the same. Both go into `docs/benchmarks.md`'s "Symbols (R2.14)" table, whose paragraph about the cost is rewritten.

### CLI

- **`reef history [PATH]...`**, a new top-level command: "Show which changes touched files or symbols, who wrote them, and what became of them."
  - **Arguments and flags:**
    - `PATH`s become `paths`, relative to the current directory as `reef diff`'s are.
    - `--symbol S` is repeatable.
    - `--change-kind added|removed|changed|moved` is repeatable and needs `--symbol`.
    - `--by AGENT`, `--workspace WS` (resolved with `scope::workspace_arg`), `--change C`, `--outcome open|landed|abandoned|undone`: each repeatable.
    - `--since WHEN` and `--until WHEN`: an RFC 3339 time, or a humantime duration before now (`7d`, `36h`). Anything else is a usage error, exit 2.
    - `--include-empty`.
    - `--group-by agent|outcome|workspace`, repeatable.
    - `--limit N` (default 100, 0 for all; follows pages; a cut is noted on stderr, as `reef op log` notes it).
    - `--repo`.
  - **The repository** is the one the command runs in, by R2.27's scope rule.
- **Text.** One line per change, then its matched touches and paths indented. Final wording the implementer's:

  ```text
  3f2a1c9e04b7  landed     bot-1, bot-2   2026-10-29 14:02  fix the parser
      ~ method Parser#parse()  src/parser.py
  9c0d77aa1e52  abandoned  bot-3          2026-10-28 09:41  try a faster tokenizer
      - function tokenize()  src/lexer.py
  2 changes (history from 2026-10-01; 3 changes pending)
  ```

  - **Each line** shows the change id (12 characters), the outcome, the agents (up to three, then `+N`), the latest activity in local time, and the subject. `divergent`, `empty` and `stale` follow the outcome when they apply.
  - **Touch marks** are R2.15's: `+` added, `-` removed, `~` changed, `>` moved. Short symbols come from R2.15's `short_symbol`.
  - **With `--group-by`**: one line per group, the grouped values then the count.
  - **The last line** gives the count and the coverage. When `backfilling` is set it says `history is still being indexed`.
- **JSON** is `{changes, groups, groups_truncated, coverage}` with the messages' field names. Enum values are lower snake, times are RFC 3339, and empty strings and unset times are `null`, as R2.27's JSON is. Without `--group-by`, `groups` is `[]`. `next_page_token` is never printed, since the command follows pages.
- **Help.** `after_help` gives `reef history src/parser.py --since 7d` and `reef history --symbol Parser#parse --group-by agent`. Help texts stay within `help_text_is_short`. `reef guide` is unchanged: it is at its budget, and `reef history --help` is where an agent finds the command. `target/cli-shape-<os>.json` gains it.

### MCP

- **One new tool, `query_changes`**, named after its RPC as R2.13's tools are.
  - **Inputs**: `repo`, `symbols`, `paths`, `agents`, `outcomes`, `since` (RFC 3339), `page_size` and `page_token`.
  - **Not inputs**: `workspaces`, `changes`, `until`, `symbol_changes`, `include_empty` and `group_by`, which an agent asking "who touched this" does not need. The CLI has them all.
  - **The result** is the CLI's JSON plus `next_page_token`.
  - **The texts**, final wording the implementer's within the budget:
    - **Description**: "Which changes touched these files or symbols: who wrote them, when, and whether they landed. Newest first. Returns {changes, coverage, next_page_token}."
    - **`symbols`**: "Symbol, `Class#method()` suffix, or name."
    - **`outcomes`**: "`open`, `landed`, `abandoned`, `undone`."
- **The budget rises from 20,250 to 21,250 bytes.** A tool of this shape costs about 1,000 bytes: `list_operations`, with eight inputs, is 1,331.
  - **The argument.** "Who touched this" is one of the three questions R2.17 measures. Without the tool an agent answers it by paging `list_operations` and calling `get_diff` per change, thousands of tokens per answer. With it the answer is one call of a few hundred. That is R2.15's argument for its 250 bytes, and the larger number buys a whole question rather than a view.
  - **The record.** The test's constant and comment say so, the PR records the measured size, and raising it again needs the same argument in that ticket's brief. If tightening this tool's own texts brings `tools/list` under 21,000 bytes, the budget is set to the measured size rounded up to the next 50.
- **The same for every harness.** No harness is named and no behavior depends on which one connects.

## Risks

- **"Who wrote it" is whoever the operation names.** `reef-agent` is not authentication (`operations.proto`'s header), so an agent can name another. Signed provenance (R3.04) fixes that. Until then, answers are as trustworthy as the log.
- **Net-diff touches miss what a change did and undid.** That is deliberate for "what touched this", and a reviewer asking about an agent's process needs the operation log.
- **A busy repository's worker falls behind.** Changes then show `PENDING` or `STALE` and `coverage.pending` grows. The throttle bounds the cost, the answer says so, and the load test measures it.
- **The effects cap.** A rebase of more than 10,000 descendants, or a fetch of more than 10,000 commits, records only the first 10,000. Activity is lost only for rebases, which carry none, and for imports past the cap. Rebased descendants past the cap keep their old `commit_id` until their next write, and their touches, a net diff, are unchanged by a rebase anyway.
- **Activity counts can double after an unmapped rewrite** (a crash between GC's steps). Times and outcomes stay right. Only `operations` counts inflate.
- **A larger `tools/list`.** Every session pays about 1,000 bytes for the tool, used or not. R2.17 measures whether it pays back.
- **The collation is ours.** A bug in `reef_path` would misorder pages. Test 21 compares against the reference over paths built to break it (`a/b` against `a.rs`, a dot, a dash, non-ASCII).

## Choices this brief made, and why

- **Changes as the unit, and net diffs as touches**: that is what the design's question asks, and both are stable under rebases and snapshots.
- **Activity rows, not operation rows**: they grow with changes rather than with watcher snapshots, and the operations of one change are a `ListOperations` call away.
- **Outcomes from the view**: replaying effects in any order, through backfill or catch-up, gives the same answer.
- **A cache file of its own, with no `ATTACH`**: history must outlive the symbol store's evictions and must not take the metadata mutex. Losing it costs a backfill and attribution older than the log, which R3.04 makes durable.
- **The subscriptions' `Source`**: each operation is read once per repository for streams and history alike, and catch-up, frames and wake-ups are reused.
- **A typed RPC**: it gives pages, bounds and remote safety, and the store can serve it from Postgres.
- **The tree check outside SQL, in path order**: SQL does everything it can without copying trees, and the check runs only as far as the page.
- **One MCP tool and a larger budget**: "who touched this" is a question R2.17 measures, and one call replaces a page-and-diff loop.

## Open questions

1. **The worker's throttle.** 5 s of quiet or 60 s of staleness is a guess at fresh-enough answers for a cost the load test accepts. If the load test's p95 moves more than 10%, the implementer raises the 60 s and records the trade in the PR. If it does not move at all, 30 s is tried and kept if it holds.
2. **Backing up the history.** This brief keeps it out of backup. If R3.37's review finds that losing attribution older than the undo window matters before R3.04 lands, `history.sqlite3` joins the backup layout through SQLite's online backup, as `reef.sqlite3` does. That is a change to ADR 0020's layout in that ticket. Default: not backed up.
3. **Agent matching.** `agents` matches exactly, as `OperationFilter.agents` does. `ws run`'s `<user>@<host>:<pid>` owners make "all of this host's runs" a list of strings. A prefix match (`agents: ["bot-*"]`) would help, but it would differ from the subscription filter. Default: exact, and revisit with R2.17's questions.
4. **R2.17's dependencies.** Its row names R2.15 and RX.07. If its brief measures "who touched this" through this ticket, it adds R2.16 to its row then. Default: R2.17's brief decides, and this brief does not edit that row.
5. **The budget.** If the implementer fits `query_changes` with `tools/list` under 21,000 bytes, the budget is the measured size rounded up to 50, and the README's and `dev-phases.md`'s "21,250" is corrected in the same PR.
