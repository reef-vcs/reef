# R2.16 Query layer

Phase 2 · Size M · Depends on: R2.14 (`symbols`, `symbol_refs`, `symbol_files`, `commit_files`), R2.09 (the `operations` index), R1.16 (`snapshots`), R1.01 (`workspaces`, `leases`, `reclaims`), R2.01 (`Queries { List, Run }` as stubs, pagination), R2.05 (`reef query`), R2.08 (the `read` scope names `Queries.*`) · Unblocks: R3.37 (audit and explain), R5.06 (fallback telemetry), R3.20 (budgets read the same tables)

## Context

"History is a database. Agents ask structured questions such as which changes touched a given symbol in the last week and what their test outcomes were, and receive structured rows" (`docs/design.md`, Query layer). ADR 0003 chose SQLite so this would come almost for free: jj's operation log stays authoritative and the daemon indexes it. By this point in the phase the daemon has the indexes: `snapshots` (R1.16), `workspaces`, `leases` and `reclaims` (R1.01), `operations` (R2.09), and `symbols`, `symbol_refs` and `commit_files` (R2.14). This ticket exposes questions over them through the API, as named, parameterized queries: `Queries.List` says what can be asked and how, `Queries.Run` answers in rows, and `reef query` is the CLI.

The README fixes that there is no raw SQL over the API, the two RPCs, the Phase 2 query set and their parameters, the `.sql` files under `crates/reef-daemon/src/queries/`, `google.protobuf.ListValue` rows, paging, and ADR 0042. This brief writes the SQL, the parameter types and validation, the metadata, and how the CLI and a remote client reach it. Outcomes ("by outcome", in the `dev-phases.md` row) are Phase 3's: there is no landing yet; `changes_in_window` carries the columns an outcome will join on.

### What was verified while writing this ticket

The Reef tree at `d156d1e`, the Phase 2 README's schemas for R2.09 and R2.14, and rusqlite 0.40 as the workspace pins it.

- **Tables and columns this ticket reads.** `workspaces(id, repo_id, owner, purpose, change_id, commit_id, state, created_at, last_snapshot_at, ..)`, `leases(id, workspace_id, owner, issued_at, expires_at, ended_at, end_reason)`, `reclaims(id, repo_id, workspace_id, reason, final_op_id, snapshot_taken, at, detail)` (`crates/reef-daemon/src/db/migrations/0001_initial.sql:10-26`); `snapshots(op_id, repo_id, workspace_id, commit_id, change_id, kind, local, taken_at)` with `snapshots_by_change(repo_id, change_id)` and `snapshots_by_workspace(workspace_id, taken_at DESC, op_id)` (`0003_snapshots.sql`); `operations(seq, repo_id, op_id, parents, description, kind, workspace_id, username, hostname, is_snapshot, external, changes, start_at, end_at, indexed_at)` with `changes` a JSON array of `{change_id, commit_id}` objects (README, R2.09; the column layout of the JSON is this ticket's reading of "repeated ChangeRef" and R2.09's brief fixes the exact keys, so the SQL below names them through one view, `operations_changes`, that R2.09 or this ticket defines, whichever lands second); `symbol_files(repo_id, blob_id, lang, source, errors, indexed_at)`, `symbols(id, repo_id, blob_id, source, name, kind, start_line, .., parent, signature)`, `symbol_refs(..)`, `commit_files(repo_id, commit_id, path, blob_id, old_blob_id, status, indexed_at)` (R2.14's migration). Timestamps are unix milliseconds in every table (README, Identifiers and time).
- **SQLite features.** `json_each` and `->>` are built into SQLite since 3.38, and `rusqlite` 0.40 with `bundled` ships a newer SQLite (not re-checked by version; a unit test asserts `sqlite_version() >= 3.38` at startup so the assumption fails loudly). Named parameters (`:name`) bind through `rusqlite::Statement::parameter_index` / `parameter_count` / `parameter_name`, which lets a test compare a statement's parameters with the query's declared ones.
- **The database access pattern.** `Db::with(|conn| ..)` under one mutex, short statements (`crates/reef-daemon/src/db/mod.rs:370-375`); a long query holds the lock against snapshot writes, so every query here is bounded by `LIMIT` and indexed, and the PR records each one's `EXPLAIN QUERY PLAN` on the fixture.
- **Pagination.** The README fixes `Page { page_size, page_token }` with `next_page_token`, tokens that encode the cursor and the request's filter hash, and `INVALID_ARGUMENT` for a token from another request.
- **Remote reach.** R2.08's scope table puts `Queries.*` under `read`, so a `read`-scoped token runs every query; nothing here mutates.
- **Outcome columns do not exist yet.** No table records landing, decline or evidence (Phase 3); the design's "by outcome" is `changes_in_window`'s `state` column, which is `draft` for every change in Phase 2 and R3.09 widens.

## Decisions

- **A query is a Rust record plus one SQL file.** `QueryDef { name, description, params: &[ParamDef], columns: &[&str], sql: &'static str }` in `crates/reef-daemon/src/queries/mod.rs`, one `include_str!("<name>.sql")` each, in a `pub const QUERIES: &[QueryDef]`. `ParamDef { name, kind: ParamKind, required, description }` with `ParamKind { Text, Owner, ChangeId, Path, SymbolName, Timestamp, Kind }`. Every SQL statement binds `:repo` (the resolved repository id, from the request's `repo`), `:limit` and `:offset` (paging), and its declared parameters as `:name`; nothing else. A statement's parameter set must equal its declared set plus the three fixed ones, and a unit test checks every file with `parameter_count`/`parameter_name` after `prepare` on an in-memory database with the migrations applied.
- **Parameters are typed and validated before the statement runs.** `Text`: any string under 1,024 bytes. `Owner`: as `Text`. `ChangeId`: a hex or reverse-hex change id prefix of at least 4 characters, resolved to the full id through the repository head (`Repo::resolve_revision`'s change path on the blocking pool) before binding, so SQL compares full ids. `Path`: a repository-relative path, no leading `/`, no `..` component. `SymbolName`: a non-empty identifier-like string (no whitespace). `Timestamp`: RFC 3339, or a relative duration ending in `ago` or starting with `-` (`"1d ago"`, `"-30m"`, parsed with `humantime`), converted to unix milliseconds by the daemon. `Kind`: one of R2.09's operation kinds. An unknown parameter name, a missing required one, or a malformed value is `INVALID_ARGUMENT` naming the parameter; the `hint` names its kind and an example.
- **The Phase 2 set and their SQL** (the `.sql` files; `-- columns:` comment lines are stripped before `prepare` and checked against `columns`):

  `changes_touching_symbol(name: SymbolName, since?: Timestamp, until?: Timestamp, owner?: Owner)`: changes whose snapshots modified a file that defines the symbol, before or after. A filter on where the symbol lives, not a judgment that the symbol's body changed (that is R2.15's, per change).

  ```sql
  -- columns: change_id, workspace_id, owner, first_at, last_at, snapshots, files
  SELECT s.change_id, s.workspace_id, w.owner,
         MIN(s.taken_at) AS first_at, MAX(s.taken_at) AS last_at,
         COUNT(DISTINCT s.op_id) AS snapshots, COUNT(DISTINCT cf.path) AS files
  FROM snapshots s
  JOIN workspaces w ON w.id = s.workspace_id
  JOIN commit_files cf ON cf.repo_id = s.repo_id AND cf.commit_id = s.commit_id
  JOIN symbols sy ON sy.repo_id = cf.repo_id
                  AND (sy.blob_id = cf.blob_id OR sy.blob_id = cf.old_blob_id)
  WHERE s.repo_id = :repo AND sy.name = :name
    AND (:since IS NULL OR s.taken_at >= :since)
    AND (:until IS NULL OR s.taken_at < :until)
    AND (:owner IS NULL OR w.owner = :owner)
  GROUP BY s.change_id
  ORDER BY last_at DESC
  LIMIT :limit OFFSET :offset;
  ```

  `changes_touching_path(path: Path, since?, until?)`: the same shape over `cf.path = :path OR cf.path LIKE :path || '/%'`, columns `change_id, workspace_id, owner, first_at, last_at, snapshots, status` where `status` is the latest snapshot's `cf.status` for the exact path (`NULL` for a prefix match).

  `operations_by_owner(owner: Owner, since?: Timestamp, kind?: Kind)`: operations of the owner's workspaces, or written under the owner's OS user name for operations with no workspace.

  ```sql
  -- columns: seq, op_id, kind, workspace_id, description, end_at, changes
  SELECT o.seq, o.op_id, o.kind, o.workspace_id, o.description, o.end_at, o.changes
  FROM operations o
  LEFT JOIN workspaces w ON w.id = o.workspace_id
  WHERE o.repo_id = :repo
    AND (w.owner = :owner OR (o.workspace_id IS NULL AND o.username = :owner))
    AND (:since IS NULL OR o.end_at >= :since)
    AND (:kind IS NULL OR o.kind = :kind)
  ORDER BY o.seq DESC
  LIMIT :limit OFFSET :offset;
  ```

  `symbols_changed_in(change: ChangeId)`: over the change's newest snapshot commit (`snapshots` by `change_id`, newest `taken_at`), the symbols defined in files that commit changed: those present only in the `after` blob (`added`), only in the `before` blob (`removed`), and present in both (`present`; whether the body changed is R2.15's answer, which this query does not try to reproduce in SQL).

  ```sql
  -- columns: path, name, kind, parent, status
  WITH latest AS (
    SELECT commit_id FROM snapshots WHERE repo_id = :repo AND change_id = :change
    ORDER BY taken_at DESC, op_id DESC LIMIT 1),
  files AS (
    SELECT cf.path, cf.blob_id, cf.old_blob_id FROM commit_files cf, latest
    WHERE cf.repo_id = :repo AND cf.commit_id = latest.commit_id),
  after AS (
    SELECT f.path, sy.name, sy.kind, sy.parent FROM files f
    JOIN symbols sy ON sy.repo_id = :repo AND sy.blob_id = f.blob_id),
  before AS (
    SELECT f.path, sy.name, sy.kind, sy.parent FROM files f
    JOIN symbols sy ON sy.repo_id = :repo AND sy.blob_id = f.old_blob_id)
  SELECT path, name, kind, parent, 'added' AS status FROM (SELECT * FROM after EXCEPT SELECT * FROM before)
  UNION ALL
  SELECT path, name, kind, parent, 'removed' FROM (SELECT * FROM before EXCEPT SELECT * FROM after)
  UNION ALL
  SELECT path, name, kind, parent, 'present' FROM (SELECT * FROM after INTERSECT SELECT * FROM before)
  ORDER BY path, name
  LIMIT :limit OFFSET :offset;
  ```

  `changes_in_window(since: Timestamp, until?: Timestamp, owner?: Owner)`: every change with a snapshot in the window, with its owner, workspace, snapshot count, latest commit, and `state` (`'draft'` in Phase 2; R3.09 joins its lifecycle table here).

  ```sql
  -- columns: change_id, owner, workspace_id, snapshots, first_at, last_at, commit_id, state
  SELECT s.change_id, w.owner, s.workspace_id, COUNT(*) AS snapshots,
         MIN(s.taken_at) AS first_at, MAX(s.taken_at) AS last_at,
         (SELECT commit_id FROM snapshots s2 WHERE s2.repo_id = s.repo_id AND s2.change_id = s.change_id
            ORDER BY taken_at DESC, op_id DESC LIMIT 1) AS commit_id,
         'draft' AS state
  FROM snapshots s JOIN workspaces w ON w.id = s.workspace_id
  WHERE s.repo_id = :repo AND s.taken_at >= :since
    AND (:until IS NULL OR s.taken_at < :until)
    AND (:owner IS NULL OR w.owner = :owner)
  GROUP BY s.change_id
  ORDER BY last_at DESC
  LIMIT :limit OFFSET :offset;
  ```

  `workspaces_history(since?: Timestamp)`: every workspace row with its lease's end and its reclaim, newest first.

  ```sql
  -- columns: workspace_id, owner, purpose, change_id, state, created_at, ended_at, end_reason, snapshots
  SELECT w.id AS workspace_id, w.owner, w.purpose, w.change_id, w.state, w.created_at,
         r.at AS ended_at, r.reason AS end_reason,
         (SELECT COUNT(*) FROM snapshots s WHERE s.workspace_id = w.id) AS snapshots
  FROM workspaces w
  LEFT JOIN reclaims r ON r.id = (SELECT id FROM reclaims WHERE workspace_id = w.id ORDER BY at DESC LIMIT 1)
  WHERE w.repo_id = :repo AND (:since IS NULL OR w.created_at >= :since)
  ORDER BY w.created_at DESC
  LIMIT :limit OFFSET :offset;
  ```

  Where a query touches `symbols`, the `scip`-preferred rule (R2.14) is applied by joining a view `symbols_preferred` (defined in this ticket's module at connection open with `CREATE TEMP VIEW`, or as a CTE in each file; the implementation picks one and the test for every file still holds): a blob's `scip` rows when it has any, else its `tags` rows.
- **`Queries.List`** returns every `QueryDef` as `QueryInfo { name, description, params: repeated ParamInfo { name, kind, required, description }, columns }`. `Queries.Run { repo, name, params: map<string, string>, page }` returns `columns: repeated string`, `rows: repeated google.protobuf.ListValue` (one value per column: strings for ids, paths, kinds and owners; numbers for counts and sequence numbers; strings in RFC 3339 for timestamps, converted by the daemon from the millisecond columns the SQL returns, by column name suffix `_at`; `null` for NULL), and `Page`. `page_size` defaults to 100, capped at 1,000; the page token encodes `(offset, blake3 of name + sorted params)`; a token whose hash does not match the request is `INVALID_ARGUMENT`.
- **Where it runs.** Validation and `ChangeId` resolution on the blocking pool under the `[api] max_concurrent_reads` permit; the statement under `Db::with`, prepared from a per-connection statement cache (`Connection::prepare_cached`), bound with `named_params`. A query's wall time is logged at `info` with its name and row count; one over 1 s logs at `warn` with the plan, because it is holding every snapshot's row write.
- **The CLI.** `reef query list` prints each query with its parameters (`name(kind, required?)`) and description, or the `QueryInfo` array as JSON; `reef query run <name> [k=v ...] [--limit N] [--since ..] [--until ..]` (the two common parameters as flags for typing's sake, and any parameter as `k=v`) prints an aligned table of the columns, or `{ "columns": [...], "rows": [[...], ...] }` as JSON, paging for the user up to `--limit` (default 100, `0` for everything). Errors carry `hint` from the daemon's `ErrorDetail` (`since: a timestamp, RFC 3339 or "1d ago"`). `reef query run changes_touching_symbol name=area --since '7d ago'` is the guide's example line if R2.05 left the bytes; otherwise `docs/api.md` carries it.
- **ADR 0042, "Query layer"**: named queries only and why (a remote `read` client must not run SQL; the schema is the daemon's to change; a query's cost is reviewed once), one SQL file per query with a mechanical parameter check, typed parameters resolved by the daemon (change ids, relative times), rows as `ListValue` with timestamps as RFC 3339 strings, paging by offset with a request hash, the Phase 2 set as a start with Phase 3's outcome columns named, and the alternatives: a SQL endpoint with a read-only connection and an allow-list of tables (rejected: the schema becomes an API, and `LIKE` on 100k rows is a denial of service from a phone), a revset-like query language (rejected: a parser for six questions), GraphQL (rejected: a second type system beside protobuf).

## Deliverables

### `crates/reef-daemon/src/queries/{mod,params}.rs` and `src/queries/*.sql`

```rust
pub struct QueryDef { pub name: &'static str, pub description: &'static str, pub params: &'static [ParamDef], pub columns: &'static [&'static str], pub sql: &'static str }
pub struct ParamDef { pub name: &'static str, pub kind: ParamKind, pub required: bool, pub description: &'static str }
pub enum ParamKind { Text, Owner, ChangeId, Path, SymbolName, Timestamp, Kind }
pub const QUERIES: &[QueryDef];                                          // the six, alphabetical
pub fn find(name: &str) -> Option<&'static QueryDef>;
pub enum Bound { Null, Text(String), Int(i64) }
pub async fn validate(def: &QueryDef, params: &HashMap<String, String>, repo: &RepoHandle, now: Timestamp) -> Result<Vec<(&'static str, Bound)>, QueryError>;   // resolves ChangeId, parses Timestamp
pub struct Rows { pub columns: Vec<String>, pub rows: Vec<Vec<Value>>, pub next_offset: Option<u64> }   // Value: serde_json::Value, timestamps already RFC 3339
pub fn run(db: &Db, def: &QueryDef, repo: RepoId, bound: &[(&str, Bound)], offset: u64, limit: u64) -> Result<Rows, QueryError>;   // fetches limit + 1 to know whether a next page exists
pub fn strip_columns_comment(sql: &str) -> (&str, Vec<&str>);
```

`QueryError { UnknownQuery(name), UnknownParam { query, name }, MissingParam { query, name }, InvalidParam { name, kind, reason }, BadPageToken, Db(DbError), Resolve(ResolveError) }` with `Classify` (`NotFound`, `InvalidArgument` ×4, `Internal`, the resolve error's kind) and `Advise` for the parameter errors (`hint` with the kind and an example, no `next`; for `UnknownQuery` `next = ["reef", "query", "list"]`).

## Tests

Unit tests in `queries/mod.rs` and `queries/params.rs`; integration tests in `crates/reef-daemon/tests/queries.rs` through `TestDaemon` on the `small` preset; CLI tests in `crates/reef-vcs/tests/cli.rs`.

The integration fixture, built by a helper in the test file through the API only: two owners, `alice@host` and `bob@host`; alice creates workspace A on a new change, writes R2.14's python fixture (`geometry.py`, `shapes.py`, `main.py`), snapshots, then edits `geometry.py` (`area`'s body) and snapshots again; bob creates workspace B on a new change, writes `shapes.py` with a new function `volume` and a `docs/notes.md`, snapshots; alice creates workspace C on A's change, writes nothing, releases it; `Symbols.Index(scope = CHANGED)` on each snapshot commit (or `[symbols] auto` left on and the test waits for the rows). Timestamps are read back from `snapshots` so the window parameters are exact.

1. `every_sql_file_prepares_and_binds_its_declared_params` (unit): on an in-memory `Db` with every migration applied, `prepare` each `QueryDef.sql` and assert the parameter names are exactly `{repo, limit, offset} ∪ params`, and that the columns the statement returns (`column_names`) equal `columns`.
2. `params_validate_and_resolve` (unit + a `TestDaemon` for the change id): `since = "1d ago"` becomes `now - 86_400_000` within a second; `since = "2026-10-25T00:00:00Z"` parses; `since = "yesterday"` is `InvalidParam` with a hint naming `Timestamp`; `path = "../x"` and `path = "/etc"` are invalid; `change = "zz"` (too short) is invalid; a 4-character prefix of A's change id resolves to the full id; an unknown parameter and a missing required one each name the parameter.
3. `changes_touching_symbol_area`: rows for A's change (2 snapshots, `files = 1`, owner alice) and not B's; `owner = bob` yields none; `since` after A's second snapshot yields A with `snapshots = 1`.
4. `changes_touching_path_prefix_and_exact`: `path = shapes.py` lists A and B (A's first snapshot added it, B modified it) with `status` `added` for A and `modified` for B; `path = docs` lists B only with `status` NULL.
5. `operations_by_owner_joins_workspaces`: `owner = alice` lists A's create, snapshot and C's create and release operations and none of B's; `kind = snapshot` narrows to the two snapshots; the `changes` column round-trips as a JSON string the CLI pretty-prints.
6. `symbols_changed_in_b`: `change = <B's id>` yields `volume` as `added` and `Circle`, `Circle.scale` as `present`; for A's change `area`, `perimeter`, `Point`, `Point.distance`, `EPSILON` are `present` and nothing is `added` (the body change is not visible to this query by design, and the test says so in its name's doc comment).
7. `changes_in_window_and_state`: a window covering everything lists A and B with `state = "draft"`, `snapshots` 2 and 1, and `commit_id` equal to each change's latest snapshot commit; `owner = bob` lists B.
8. `workspaces_history_has_the_released_one`: three rows, C with `state = released`, `end_reason = released` and `ended_at` set, A and B with NULLs; `since` after C's creation lists none of the earlier ones.
9. `paging_is_stable_and_tokens_are_bound`: `changes_in_window` with `page_size = 1` returns A then B then an empty token; the first page's token sent with a different `owner` is `INVALID_ARGUMENT`; `page_size = 5000` is capped (the response says 1,000 in `page.page_size`).
10. `rows_are_typed`: counts and `seq` are numbers in the `ListValue`, `*_at` columns are RFC 3339 strings, NULLs are `null`, ids are strings.
11. `remote_read_scope_runs_queries` (with R2.08 merged; else `#[ignore]` with the reason): a `read` token over the web listener runs `workspaces_history`; a `presence`-only token is `PERMISSION_DENIED`.
12. `cli_query_list_and_run`: `reef query list -o json` has six entries; `reef query run changes_touching_symbol name=area --since '1d ago'` prints one row; `reef query run nope` exits 3 with `next = ["reef","query","list"]`; `reef query run changes_in_window` without `since` exits 2 with the hint.
13. `query_time_is_logged` and, printed and recorded in the PR: each query's `EXPLAIN QUERY PLAN` on the fixture (no `SCAN` of `snapshots` or `symbols` without an index), and the wall time of `changes_touching_symbol` on a database with 10,000 synthetic `snapshots` rows and 100,000 `symbols` rows inserted directly by the test.

## Implementation notes

- Strip the `-- columns:` line before `prepare`; keep every other comment (SQLite ignores them and the files stay readable).
- Bind `Bound::Null` for an absent optional parameter: the `(:x IS NULL OR ...)` form lets SQLite's planner skip the predicate; confirm with `EXPLAIN QUERY PLAN` that the `snapshots_by_change`/`commit_files_by_blob` indexes are used, and add an index in R2.14's migration file only if that ticket has not merged (a new migration otherwise).
- Fetch `limit + 1` rows to decide `next_page_token` without a `COUNT(*)`.
- Convert milliseconds to RFC 3339 in Rust by column name (`ends_with("_at")`), not in SQL: one code path, one format, the `json::rfc3339` helper the client already has.
- `prepare_cached` keeps the six statements compiled per connection; the `Db` holds one connection.
- A `ChangeId` parameter for a change that has no snapshots is valid and returns no rows; an unknown prefix is `NotFound` from the resolver, passed through with its kind.
- Keep `queries::run` synchronous and free of jj: tests 1 and 10 run on an in-memory database with hand-inserted rows and no repository.

## Out of scope

- Raw SQL over the API, user-defined queries, or queries stored in `reef.toml`.
- Outcomes, evidence, landing and provenance columns (R3.01, R3.04, R3.09 extend `changes_in_window` and add their own queries).
- Cross-repository queries: every query is scoped to one `repo`, as every table is (ADR 0003).
- Full-text search over descriptions or file contents.
- Aggregations for the fleet panel (R2.20 reads `Workspaces.List` and presence, not this layer).

## Risks

- **`changes_touching_symbol` is a filter, not a diff.** It says the symbol's file changed in that change, not that the symbol did. The description says so, test 6's name says so, and R2.15's `Diff(SYMBOLS)` per change is the precise follow-up an agent runs on the rows. Computing the precise answer in SQL would need per-symbol content hashes, which the index does not store.
- **Lock time on big tables.** `commit_files` and `symbols` grow with every indexed snapshot; the plans are checked on the fixture and the `warn` line reports a slow query in the field, but a repository with millions of symbol rows is not measured here. If it bites, a read-only second connection in WAL mode is the fix (SQLite allows concurrent readers), and a small ticket.
- **The `operations.changes` JSON shape is R2.09's.** If R2.09 lands with a different JSON layout than `[{change_id, commit_id}]`, `operations_by_owner` passes the string through unchanged (it does not parse it), so only the documentation's example changes; a query that needs `json_each` over it is Phase 3's.
- **Relative timestamps depend on the daemon's clock**, not the client's; a remote client in another time zone passing `"1d ago"` gets the daemon's day. Documented in `docs/api.md`.
