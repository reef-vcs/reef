# R2.27 Client-side store builds

Phase 2 · Size M · Depends on: R2.05 (the CLI over `reef-api`; the `embedded-daemon` split), R2.13 (`reef_store_build` becomes `Prepare`; `reef_store_seal` and `reef_store_abort`), R1.20 (the store layout, the scratch workspace, sealing), RX.01 (S-03, S-07, S-11, S-12 and ADR 0027) · Unblocks: R3.06 (the executor runs a declared command on a tree in the same shape: prepare, run outside the daemon, record)

## Context

RX.01's threat model found the one place the daemon executes repository content: `Stores.Build` runs a `reef.toml`'s declared `build` argv, as the daemon's user, with the daemon's network, outside whatever sandbox the client that asked for it is in (S-07). An agent in a harness sandbox that can reach the socket can commit its own `reef.toml` and have the daemon run anything. Phase 1 documented it, printed the command first (S-03), and added `[store] allow_builds = false` as the operator's switch, and filed [#61](https://github.com/reef-vcs/reef/issues/61) for Phase 2: run the build in the client's own process, so it stays inside the client's sandbox, and have the daemon only prepare the scratch workspace and seal what was written.

This ticket does that. The daemon keeps everything that is the store's identity and integrity: the lockfile hash from the target commit's tree, the scratch workspace on the copy backend with the other stores mounted, the `building` directory, the adoption of a replaced link, sealing with the mount lock held, the row. It stops running the command. The client (`reef store build`, the MCP server through the agent's own shell, an SDK) runs the argv the daemon hands back, in the scratch workspace, with the client's privileges and network, and tells the daemon how it ended. ADR 0022's second decision ("Only the daemon writes a store" and the build runs "as the daemon's user") is amended by ADR 0039: only the daemon *seals* a store; the build that fills it runs where the request came from.

## Decisions

- **Three new RPCs on `Stores`, and the client runs the command.**
  - `Prepare { repo, name, rev, force, owner, lease_ms } -> PrepareResponse { build_id, already_built: bool, result: BuildResult (when already_built), workspace: Workspace, lease: Lease (heartbeat_every inside), scratch_root, store_dir, argv: repeated string, env: repeated string (KEY=VALUE, as BuildStarted.env), rev, lockfile_hash, mount }`. Steps 1 to 3 of today's `run`: resolve, answer a sealed store unless `force` (no scratch is made; `already_built`), refuse a forced rebuild of a store in use, take the key's build guard, record the unsealed row, prepare the `building` directory, create the scratch workspace (copy backend, `missing_stores: Skip`, `skip_store`, the other stores mounted), pause its watcher snapshots, link the store's mount path to `<hash>.building/<leaf>/`. The scratch workspace's `owner` is the request's (the client's `<user>@<host>:<pid>`, so `ws list` shows who is building; `BUILD_OWNER` is kept for the daemon-side path), its `purpose` is `store build <name>`, and its lease is the client's to heartbeat, as any `Create`'s is. `store_dir` is the contents directory (`REEF_STORE_DIR`'s value today). A `store_builds` row is inserted in state `prepared`.
  - The client runs `argv` with the working directory `scratch_root` and the environment: its own environment (the point of the change: the build runs with what the client has, inside the client's sandbox), then `env` from the response (`[store.env]`, which the response also lists so the client can show it), then `REEF_STORE_DIR = store_dir`, `REEF_STORE_NAME`, and R1.21's `REEF_WORKSPACE`, `REEF_WORKSPACE_PATH`, `REEF_REPO`, `REEF_SOCKET` for the scratch workspace. It prints the S-03 announce line first, from the response (`started_line` unchanged), heartbeats the scratch lease while the command runs (`Heartbeater`), and forwards the command's stdout and stderr to its own (JSON mode: stderr), with no RPC in between and no dropped lines. It kills the command's process group at `--timeout` (default 30 m) as the daemon did.
  - `Seal { build_id, exit_code } -> BuildResult`: step 5 of today's `run`, in the daemon: on `exit_code == 0`, adopt a replaced link, unlink the mount, release the scratch without a final snapshot (`detail = "store build"`), seal on the blocking pool, mark the row and the `store_builds` row `sealed`; otherwise unlink, release, `fail` (`<hash>.failed-<ms>`), `store_builds.state = failed`, `BuildResult.sealed = false` with the exit code. `Seal` is refused `FAILED_PRECONDITION` for a build that is not `prepared` (sealed, failed, aborted, or unknown id: `NOT_FOUND`), and `PERMISSION_DENIED` when the request's `owner` differs from the `Prepare`'s (the same informational owner rule as `ws run --workspace`, ADR 0027: not a security boundary, a mistake catcher).
  - `Abort { build_id } -> AbortResponse { freed_bytes }`: unlink, release the scratch, discard the `building` directory (not kept as failed: nothing ran to completion), `store_builds.state = aborted`, the build guard released.
  - The build guard spans RPCs: `StoreManager` keeps `prepared: Mutex<HashMap<BuildId, PreparedBuild>>` (key, scratch workspace id, owner, client, `prepared_at`); `start_build` for a key held by a prepared build is `BuildRunning` as today; the guard is dropped by `Seal`, `Abort`, or the reclaim below.
- **A scratch lease that expires aborts the build.** The reclaim pipeline (`Manager::reclaim`) checks `store_builds` for the workspace: a `prepared` build whose scratch is being reclaimed for `Expired` is marked `aborted`, its `building` directory moved aside as `<hash>.failed-<ms>` (something may have been written; keep it for inspection as a failed build is kept), the row deleted, the guard released, and the reclaim proceeds with no final snapshot and `reclaims.detail = "store build (lease expired)"`. A `Seal` that arrives afterwards is `FAILED_PRECONDITION` with the hint `the build's workspace was reclaimed; run reef store build again`. At daemon start, `sweep_interrupted` also marks every `prepared` row `aborted` (its scratch is an `active` row the start reloads; it is released then, with the same detail).
- **`reef store build` is client-side by default and gains `--in-daemon`.** Default: `Prepare`, announce, run, heartbeat, `Seal` (or `Abort` on SIGINT/SIGTERM after killing the command's group), print the result as today. `--in-daemon`: the Phase 1 path over `Stores.Build`, which stays for an operator who wants the daemon to build (a root daemon in a container dedicated to agents, where the daemon's environment is the right one), and now requires `[store] allow_builds = true`, **whose default becomes `false`**: a daemon out of the box runs no repository-declared command. `BuildsOff`'s hint becomes `builds run in the client by default: drop --in-daemon, or set [store] allow_builds = true`. The config row, `KEYS`, `show`, and the README's config schema row change accordingly.
- **The MCP server's tool becomes two steps** (R2.13 names `reef_store_build`; this ticket defines it): `reef_store_build { repo?, name, rev?, force? }` calls `Prepare` and returns `{ build_id, cwd: scratch_root, argv, env, store_dir, heartbeat_every, next: ["reef", "store", "seal", <build_id>, "--exit-code", "<code>"] }` with a description telling the agent to run `argv` in `cwd` with `env` in its own shell and then call `reef_store_seal { build_id, exit_code }` (or `reef_store_abort`); the server heartbeats the scratch lease as it does for workspaces it created (R2.13's lifecycle) and reports `RUNNING` presence with `detail = store build <name>`. The daemon never runs the command and the MCP server process does not either: the agent's shell, under the harness's sandbox and timeouts, does, which also sidesteps the harness tool timeout a multi-minute build would hit. The CLI gets the matching leaf commands, `reef store seal <build_id> --exit-code <n>` and `reef store abort <build_id>`, so `next` is a real command and a shell-only agent can drive the three steps by hand.
- **Migration `0010_store_builds`**: `store_builds(id TEXT PRIMARY KEY, repo_id TEXT NOT NULL, name TEXT NOT NULL, lockfile_hash TEXT NOT NULL, scratch_workspace_id TEXT NOT NULL, state TEXT NOT NULL CHECK (state IN ('prepared','sealed','failed','aborted')), client TEXT NOT NULL, prepared_at INTEGER NOT NULL, ended_at INTEGER)` with an index on `(name, lockfile_hash, state)`. `client` is the owner string. Rows are kept for the undo window and deleted by R1.17's GC step 3 beside workspace rows. `BuildId` is a 64-bit hex id like the others (`reef_daemon::model::ids`).
- **Trust.** The daemon seals whatever the client left in the `building` directory; it cannot tell a build's output from anything else the same uid wrote, and under ADR 0027 it never could (the symlink-tier store is writable by the uid after sealing, S-12). What changes: the daemon no longer executes repository content on any client's say-so, so a harness sandbox that reaches the socket can no longer make the daemon run a command outside the sandbox (S-07's `Stores.Build` leg closes by default); `Create.path` and `Backup.dest` remain as S-07 and S-09 state. The threat model's findings table: S-03's status gains "and from R2.27 the daemon runs no build unless `allow_builds = true`"; S-07's status becomes "Fixed in R2.27 for store builds (client-side builds, `allow_builds` default false); `Create.path` and `Backup.dest` documented, R2.08's scopes refuse them remotely"; S-11 is reworded (the environment is now the client's, which is the sandbox's); new rows S-40 (`Prepare` creates a leased scratch workspace with a writable store directory for any client: same as `Create`, documented) and S-41 (`Seal` seals a directory the client filled: the sealed content is as trustworthy as the client, which is the uid; documented, with the bind tier as the enforced read-only). The "Harness sandboxes" section drops `Stores.Build` from the list of RPCs that act outside the sandbox and names `--in-daemon` and `allow_builds`.
- **ADR 0039, "Client-side store builds"**, amends ADR 0022's decision 2: the daemon prepares and seals, the client runs; the environment is the client's plus `[store.env]` and `REEF_*`; `allow_builds` defaults to false and gates the daemon-side path only; the lease is the client's and expiry aborts; consequences (a build survives a client disconnect only as far as the lease; the command's output no longer passes through the daemon, so nothing is dropped; a sandboxed client builds inside its sandbox and a store built there has only what the sandbox could fetch); alternatives (keep daemon-side builds with a consent step: the socket cannot tell the user from the agent, ADR 0027; run the build in the agent's own workspace and adopt the result: the agent controls that directory, ADR 0022's rejected alternative, still rejected; a build sandbox in the daemon, #62: a new execution boundary, later).
- **Documents.** The quickstart's store section shows the same `reef store build node_modules` (unchanged UX) and its limitations lose "runs the command ... as your user, with network access" in favor of "`reef store build` runs the command in your shell's process, with your environment; `--in-daemon` and `[store] allow_builds = true` make the daemon run it instead", and the harness-sandbox bullet drops "and run a store build". `CHANGELOG.md`: the default flip is a behavior change called out under a "Changed" heading. ADR 0022 is not edited (frozen); ADR 0039 names what it amends.

## Implementation notes

- Split `run` without changing its behavior for `--in-daemon`: `prepare` and `seal` are the pieces, `run` calls them around `run_command`. Then every Phase 1 build test still passes under `allow_builds = true` and proves the split is faithful; write the `Prepare`/`Seal` tests after.
- The scratch's `scheduler().pause(ws)` guard is held by the daemon from `Prepare` to `Seal`/`Abort`/reclaim, in `PreparedBuild`; today it is a local in `build_in_scratch`. Dropping it on reclaim is what lets the reclaim's (skipped) final snapshot path run normally.
- The client runs the command with `tokio::process::Command`, `process_group(0)`, `kill_on_drop`, and the same kill-the-group logic `ws run` has for its child (R1.21's `escalates_to_sigkill`); share the helper rather than copying it.
- `env` in `PrepareResponse` is `[store.env]` only; `REEF_STORE_DIR` and friends are set by the client from the other fields so a second provider cannot be given a wrong path by a stale field.
- The owner check on `Seal` compares the request's `owner` (the CLI's default owner, the MCP server's `mcp:...`) to the `Prepare`'s; `--owner` on `store seal` overrides it as `ws run --workspace --owner` does.
- Keep the announce line's function (`started_line`) and its test; it now takes the `PrepareResponse`'s fields.
- Threat model rows: coordinate the S-numbers with R2.08's PR (S-24 onward) by taking S-40 and S-41, as the README allocates ADR numbers; renumber in the PR only if R2.08 landed first with a collision.

```sh
reef store build node_modules                 # client-side: the command runs in this process
reef ws list -o json | jq '.[] | select(.purpose | startswith("store build"))'
reef store build node_modules --in-daemon     # exit 7 with the allow_builds hint on a default daemon
reef config show | grep allow_builds
cargo nextest run -p reef-daemon --test stores
cargo nextest run -p reef-vcs -E 'test(/store_build|store_seal|store_abort/)'
```

## Out of scope

- A sandbox for the build or for `ws run` ([#62](https://github.com/reef-vcs/reef/issues/62)): the build now runs in whatever sandbox the client already has.
- Verifying what a client sealed (hashing the store against a manifest, reproducible builds): under one uid there is nothing to verify against.
- Removing `Stores.Build` (kept behind `allow_builds` for daemons dedicated to agents).
- Build caches keyed by tree hash (ADR 0022's consequences).
- Restricting `[store.env]` or the build's network: both are the client's now.

## Risks

- **A client that dies mid-build.** The daemon-side build survived a disconnect; a client-side one dies with its process, and the scratch lives on until its lease expires (then: aborted, directory kept as failed). `reef store build`'s default lease is the daemon's `lease.default` (30 m) with heartbeats, so a dead client's scratch is gone within `lease.default + grace`; the `.failed-*` directory says what happened.
- **Builds that depended on the daemon's environment.** A CI job that ran `reef store build` from a shell with a minimal `PATH` now builds with that `PATH`; before, it got the daemon's. The announce line and `env` in the result show what ran; `--in-daemon` is the escape with `allow_builds = true`.
- **The default flip.** A 0.1.0 user whose daemon ran builds for sandboxed agents by design gets `PERMISSION_DENIED` on `--in-daemon` after upgrading, with a hint naming the key; the default path keeps working without a flag. The changelog says so under "Changed".
- **Two code paths for one feature.** `run` composed of `prepare`, `run_command`, `seal` keeps the daemon-side path the same functions as the client-side one; the Phase 1 tests under `allow_builds = true` hold it to that.
