# R2.08 Remote daemon access

Phase 2 · Size L (the row says M; see "Size") · Depends on: R2.01 (access levels on every method, `reef_api::access`, the error model), R1.04 (the daemon's listener and start sequence), and beyond the row R2.18 (the gate, `reef-web`, the second tonic server and its connection cap, which this ticket generalizes), R2.05 and R2.27 (the thin client and its commands, which gain a remote target), R2.04 (`EditFiles`, the write path that needs no directory on the caller's machine), R2.09 and R2.10 (the streams a remote client subscribes to) · Unblocks: R3.40 (the mobile shell connects to this listener), R3.39 (one window for local and remote), R2.06 and R2.07 (the SDKs' remote connection), and Phase 2's exit criterion "A daemon in a VM is reachable from another machine over TLS with a token, serving the same API and web UI"

## Context

The design says the daemon "exposes a typed protocol over a local socket with structured responses, and optionally over TLS with token authentication so a daemon on a remote machine can be reached by the same clients" (`docs/design.md`, API), and the mobile app reaches "the daemon's remote listener" (Interfaces). ADR 0004 recorded the same: "A daemon can optionally also listen over TLS with token authentication so remote clients, such as a phone, reach the same API."

Today nothing off the machine can reach a daemon. The Unix socket is the authorization: "one uid is one trust domain" (ADR 0027), and every RPC is open to every client that connects. R2.18 added the first listener that is not the socket, but only on loopback, only for gRPC-web, only for `ACCESS_READ` methods, and only with a per-process session minted over the socket. The threat model lists five requirements a listener that is not the socket must meet before it serves an RPC (`docs/threat-model.md`, "Requirements for a listener that is not the socket"), and says "R2.08's remote listener is next". RX.01 wrote those requirements for this ticket; ADR 0027 decision 4 and ADR 0031 decision 2 ("R2.08 binds remote callers to tokens") point here.

This ticket adds that listener. It covers:

- a TLS listener on a configurable address, off by default, enabled by `[remote] enabled = true` or `--remote` on `reef daemon start`, `reef daemon run` and `reef-daemon`, serving native gRPC (for the CLI and SDKs), gRPC-web and the embedded web UI on one port;
- TLS terminated by Reef with rustls: a self-signed certificate the daemon generates and clients pin by public key, or a certificate and key the operator supplies, reloaded when the files change;
- issued, named, scoped, expiring bearer tokens, stored as digests, created, listed, rotated and revoked through `reef remote token`;
- a gate that applies the scope to the schema's access levels, field and ownership rules on the WRITE methods that need them, and per-address backoff on the unauthenticated surface;
- the caller's token recorded on every operation it causes, and its other writes and refusals in the daemon's log;
- a remote mode in the CLI (`--remote <name>`, `REEF_REMOTE`), with client profiles that keep the token off every command line;
- threat-model rows and a self-review against the five requirements, which is what "reviewed under RX.01" means here.

R2.01's rule binds this brief: it adds one service, three fields and eight reasons, and changes nothing declared.

## Decisions

### Size

L. The row's sentence hides five deliverables, each with its own tests:

- **TLS** that a phone's browser, the CLI and the SDKs can all use: Reef's own termination (tonic's does not reload or pin), a generated certificate with public-key pinning, operator-supplied files with reload, and a client-side verifier for both.
- **Tokens**: a table, four ADMIN RPCs, rotation with overlap, revocation that ends open streams, and a CLI noun.
- **A gate with scopes**: R2.18's gate generalized to two credential kinds, field and ownership rules on the WRITE methods that need them, per-address backoff and per-token limits.
- **Identity and audit**: a token on every operation, a workspace column, the daemon log for writes that record no operation.
- **A remote CLI**: client profiles, a TLS connector in `reef-client`, a classification of every command as remote-capable or local-only, and scope resolution without a current directory.

Add the threat-model review, an ADR, a two-container end-to-end check for the exit criterion, and about forty tests. That is R2.18's breadth. It is not split: the listener without tokens cannot be tested, and tokens without a client cannot be used. Deferred to follow-ups instead (each filed by the PR): CORS for a shell's origin, response compression, built-in ACME, tokens restricted to repositories, `reef mcp` against a remote daemon, and keychain storage on the client (see "Out of scope").

### One port, three protocols

The remote listener is a third tonic server over `server::routes(state)`, sharing `AppState` with the other two, so the subscription cap, the broker, presence and the repository threads are shared. It serves, on one TCP port, behind TLS:

- **native gRPC over HTTP/2** for the CLI, the SDKs and anything else built on a gRPC library;
- **gRPC-web**, binary only, over HTTP/2 or HTTP/1.1, for the web UI;
- **the embedded assets** from `reef-web`, as R2.18 serves them, public.

One port, because `GrpcWebLayer` already sorts gRPC-web from native gRPC, browsers negotiate HTTP/2 over TLS, and one port is one firewall rule and one certificate. Native gRPC is not served by the loopback web listener (R2.18's decision stands); only this listener serves it off the socket.

The router is `Server::builder().accept_http1(true).http2_keepalive_interval(Some(30 s)).http2_keepalive_timeout(Some(20 s)).max_concurrent_streams(Some(128)).layer(WebGateLayer(gate)).layer(GrpcWebLayer::new()).layer(CompatLayer).add_routes(routes(state))`: R2.18's `WebRouter` type with keepalives, which find a phone that went away without closing its streams.

### When it runs

- **Off by default.** `[remote] enabled = false`. A daemon that is not told opens no remote port.
- **On** by `[remote] enabled = true` in the daemon's `config.toml`, or for one run by `--remote` on `reef-daemon`, `reef daemon run` (forwarded through the `exec`) and `reef daemon start` (forwarded through `autostart::command`). `--remote` sets `enabled` for that process and nothing else. Autostart from any other command never passes it.
- **Bound at start**, as step 11 of the start sequence, after the socket serves, not on demand: a remote client cannot ask for it. A failed bind (the port is taken, or the address is not up yet, such as a VPN interface at boot) does not stop the daemon: the socket serves, `GetDaemonStatus.remote` says `FAILED` with the error, and the daemon retries the bind with backoff from 1 s doubling to 60 s until it succeeds or the daemon stops. A certificate that cannot be loaded or generated is `FAILED` the same way. `reef daemon start --remote` waits up to 5 s for `LISTENING` and fails with exit 6 (`Unavailable`) and the error otherwise, so a person who asked for it learns at once.
- **A running daemon is not reconfigured.** `reef daemon start --remote` against a daemon already running without the listener is exit 5 (`Conflict`), hint "The daemon is running without the remote listener: run `reef daemon stop`, then `reef daemon start --remote`", `next` the stop. `[remote]` is read at start, like every section.
- **Restarts keep it.** `GetDaemonStatus.remote.enabled_by` says `CONFIG` or `FLAG`. The CLI's `restart` of an incompatible daemon (`cli/daemon.rs:207`) passes `--remote` to the new daemon when the old one reported `FLAG`, so an upgrade does not silently close the listener.
- **Stopped with the daemon.** A shutdown hook joins the server within `SHUTDOWN_GRACE`, as R2.18's does. Open streams end `UNAVAILABLE` with no reason, which R2.09's and R2.10's clients already resume from.

### TLS: Reef terminates it, with rustls and ring

There is no plaintext mode, on any address, loopback included. The listener's accept loop does the handshake itself with `tokio-rustls`, not tonic's `tls_config`, for three reasons: ALPN must offer `h2` and `http/1.1` (tonic offers `h2` only, and gRPC-web over HTTP/1.1 is what a client without HTTP/2 falls back to); the certificate must reload without a restart; and the crypto provider must be chosen explicitly rather than installed process-wide.

- **Library.** `rustls` 0.23 with `default-features = false` and features `ring`, `std`, `tls12`, `logging` off; `tokio-rustls` 0.26 likewise. The provider is `rustls::crypto::ring::default_provider()`, passed to `ServerConfig::builder_with_provider` and `ClientConfig::builder_with_provider`; nothing calls `install_default`. ring rather than aws-lc-rs because it builds with only a C compiler on all four release targets (aws-lc-sys needs CMake, and is a larger static archive on musl), and because nothing here needs FIPS. `crate_graph` gains a check that `aws-lc-sys` and `openssl-sys` are nowhere in the resolved graph, so a default feature cannot bring them back.
- **Versions.** TLS 1.3 and 1.2, with rustls's default cipher suites (no CBC, no RSA key exchange). No session resumption tickets beyond rustls's defaults, no 0-RTT (`max_early_data_size = 0`).
- **Handshakes off the accept loop.** Each accepted connection is handshaken in its own task, at most 64 at once (`remote::Limits::max_handshakes`), each bounded by 10 s (`handshake_timeout`), and finished connections reach `serve_with_incoming_shutdown` through a channel. A peer that opens a connection and sends nothing holds one handshake slot for 10 s and no more.

**Where the certificate comes from.** Two sources, chosen by configuration:

- **Generated (the default).** With `[remote] tls_cert` and `tls_key` unset, the daemon generates an ECDSA P-256 key with `rcgen` once, at the first start with the listener on, and keeps it in `<state>/remote/key.pem` (`0600`, in a `0700` directory created and checked as S-01 checks the state directory). The certificate (`cert.pem`, `0600`) is self-signed, with subject alternative names from `[remote] names` (default: the host name) plus the bound IP when it is not a wildcard, valid from an hour ago for 397 days. When fewer than 30 days remain, or `names` changed, the daemon issues a new certificate **for the same key**, at start and on a daily check. Clients pin the key, not the certificate, so renewal never breaks a pin.
- **Supplied.** `tls_cert` (a PEM chain, leaf first) and `tls_key` (PKCS#8, SEC1 or PKCS#1 PEM), both or neither; one alone is a configuration error. For a certificate a public CA or a private CA issued: a domain on the VM with an ACME client, a VPN's own certificate service, or a company CA. A custom `rustls::server::ResolvesServerCert` re-reads both files when either's mtime or size changed, checked at most once a minute (`cert_reload_interval`) during a handshake, so a renewal by an external tool is picked up without a restart. A pair that fails to parse or does not match is logged at `warn` and the previous pair keeps serving; `GetDaemonStatus.remote.certificate.error` says why.

The **fingerprint** of either is `sha256:` and 64 lowercase hex digits of SHA-256 over the leaf certificate's SubjectPublicKeyInfo (DER), computed with ring's digest. That is the value HPKP and `curl --pinnedpubkey` pin (curl takes it in base64; the e2e script converts). `GetDaemonStatus` and `reef remote show` print it.

The generated key is not in backups (ADR 0020's layout is unchanged). A restore, or a lost `<state>/remote/`, generates a new key; clients then fail with a pin mismatch whose hint says to compare with `reef remote show` and re-add. Copying a private key into every backup directory is a larger exposure than a re-pin after a restore.

**No HSTS, no HTTP port.** The listener speaks only TLS, so there is no plaintext URL for HSTS to upgrade, and with a generated certificate HSTS would forbid the browser's click-through for a year.

### How a client trusts the daemon

- **Pinned** (a profile or `REEF_REMOTE_FINGERPRINT` gives a fingerprint): a custom `rustls::client::danger::ServerCertVerifier` accepts exactly a leaf whose SPKI hashes to the pin, and still verifies the handshake signatures with the provider's algorithms (`verify_tls12_signature`, `verify_tls13_signature`). Name, chain and validity are not checked: the pin is stronger than all three. This is the default path for the generated certificate.
- **CA-verified** (no fingerprint): the OS's roots through `rustls-native-certs`, with webpki path validation and the URL's host as the server name. This is the path for a supplied CA-issued certificate, and for browsers.
- **Neither works**: the connection fails before any request, so the token is never sent. The error names the presented fingerprint: `reef remote add` prints "The daemon at https://vm:7470 presented sha256:9f2c…; if `reef remote show` on that machine prints the same, run this again with --fingerprint sha256:9f2c…". This is trust on first use made explicit: the person compares the value over a channel they trust (the VM's console, an SSH session) rather than the CLI accepting it silently.
- **Browsers** use the OS's roots. A generated certificate shows the browser's warning once per origin; the person compares the fingerprint in the warning's details with `reef remote show` and accepts it. For a phone, a supplied certificate is the documented path, because mobile browsers make that warning hard or impossible to pass (see "Risks").

### Tokens

- **Format.** `reef_<id>_<secret>`: `id` is 16 lowercase hex characters from the CSPRNG, unique forever; `secret` is 32 bytes from the CSPRNG as 43 base64url characters without padding. 65 characters in all. The prefix makes a leaked token recognizable to secret scanners and in logs; the id lets the daemon find the row without comparing against every token.
- **At rest on the daemon.** Only `blake3(secret)` is stored, in `reef.sqlite3`. The secret is 256 bits from the CSPRNG, so a fast hash is enough: there is nothing to brute-force that a slow hash would protect. Comparison is `blake3::Hash`'s `PartialEq`, which is constant-time; the lookup by id is a map lookup on a non-secret. Live tokens are loaded into memory at start and kept there; the table is the record.
- **Names.** `[a-z0-9][a-z0-9._-]{0,62}`, chosen by the person (`laptop`, `phone`, `ci-runner-3`), unique among live tokens. A revoked or expired token's name can be reused; its id cannot.
- **Scopes.** Two:
  - `read`: `ACCESS_READ` methods.
  - `write`: `ACCESS_READ` and `ACCESS_WRITE` methods, under the field and ownership rules below.

  No scope allows `ACCESS_ADMIN` (decided by the user). `CreateRemoteToken` without a scope is `read`, so the default scope allows none of requirement 2's dangerous calls.
- **Expiry.** `expires_in` on create, default 30 days; `--expires never` is explicit and printed with a note. An expired token is refused like a revoked one. The daemon logs at `info` once a day for each token expiring within 7 days, and `reef remote token list` shows `expires_at`.
- **Rotation.** `RotateRemoteToken { name, overlap }` gives the token a new secret, keeping its id, name, scope and expiry. The old secret stays valid for `overlap` (default 0, at most 7 days), so a client can be updated before it stops working. Only one previous secret is kept.
- **Revocation.** `RevokeRemoteToken { name }` takes effect for the next request at once. Open `SubscribeOperations` and `SubscribePresence` streams carrying it end within 1 s with `PERMISSION_DENIED`, reason `REMOTE_TOKEN_INVALID`, `state: revoked`: each remote request carries its token's revocation `CancellationToken` in its extensions, and the two streaming READ handlers select on it beside `AppState::shutdown`. The two other streaming RPCs, `Backup` and `BuildStore`, are ADMIN and never served remotely. A unary call already running finishes.
- **Last use.** Each token records `last_used_at` and `last_used_from` (the peer address), in memory at every request and written to the table at most once a minute per token and at shutdown, so a request costs no database write.
- **Limits.** At most 256 live tokens (`remote::Limits::max_tokens`; `TOO_MANY_REMOTE_TOKENS`, `Conflict`). Revoked and expired rows are kept as the audit record of which id had which name, and are listed with `--all`.
- **Where tokens come from.** Only the four ADMIN RPCs, over the socket. A token cannot mint, rotate or revoke tokens, including itself.

### The gate on the remote listener

`web/gate.rs` becomes the gate for both TCP listeners. `Gate` holds a `Policy`, one of:

- `Loopback { authority, origin, sessions }`, R2.18's rules, unchanged in behavior;
- `Remote { port, names, tokens, failures }`.

Steps, in order, with the remote listener's differences:

1. **Blocked addresses** (remote only, before TLS, in the accept loop): a connection from an address in backoff is closed at once (see "Limits").
2. **Host.** The `Host` header or `:authority` must be a name in `[remote] names` or an IP literal, with the listener's port (or no port when it is 443). Anything else is `421`. With TLS, a rebound page would already fail certificate validation for its own name; this check is the second wall and costs nothing.
3. **No upgrades, no preflight.** `Upgrade` is `400`; `OPTIONS` is `405`. No response carries an `Access-Control-*` header (CORS is out of scope).
4. **Assets.** `GET` and `HEAD` off API paths serve `reef-web`, public, with R2.18's security headers. A placeholder build serves the placeholder page; nothing refuses.
5. **API path and method.** As R2.18: `POST` on `/reef.<package>.<Service>/<Rpc>`.
6. **Origin.** An `Origin`, if sent, must be `https://` plus the request's own Host; a `Sec-Fetch-Site`, if sent, must be `same-origin`. Else `403` before the token is looked at.
7. **Content type.** Binary gRPC-web (`application/grpc-web`, `application/grpc-web+proto`), or, on the remote listener only, native gRPC (`application/grpc`, `application/grpc+proto`). Text mode and anything else is `415`.
8. **Token.** `authorization: Bearer <token>` must parse and name a live token whose secret (or previous secret, within its overlap) matches. Else `PERMISSION_DENIED`, `REMOTE_TOKEN_INVALID`, with metadata `state`: `expired` or `revoked` only when the id exists **and** the secret matches (the caller already holds that token), `unknown` otherwise, so a guess learns nothing about which ids exist. Each refusal counts against the peer address. The header is removed.
9. **Scope.** `reef_api::access(path)` must be in the token's scope. Else `PERMISSION_DENIED`, `REMOTE_ACCESS_DENIED`, metadata `method`, `access` (`write`, `admin` or `unknown`) and `scope`.
10. **Per-token limits.** In-flight requests and open streams under the token's caps, else `UNAVAILABLE`, `REMOTE_BUSY`, metadata `limit`.
11. **Pass.** The gate inserts a `RemoteCaller { token_id, token_name, scope, peer, revoked: CancellationToken }` into the request's extensions (clients cannot send extensions, so it cannot be forged), and the request goes on to `GrpcWebLayer`, `CompatLayer` and the service, holding its token's in-flight count until the response body ends.

Refusals 8 to 10 are gRPC answers: trailers-only gRPC-web for a gRPC-web request (as R2.18), and a trailers-only HTTP/2 gRPC response for native gRPC, both with the `ErrorDetail`. `Gate::refusal` picks the content type from the request.

The loopback listener keeps steps 2 to 9 as R2.18 wrote them (its step 8 is "the session", its step 9 "READ only"), and gains no remote behavior. The two policies share the step order, the security headers, the asset serving and the trailers-only builder, and nothing else.

### Field and ownership rules on WRITE methods

Requirement 2 names calls a client with ordinary write access must still not make: create a workspace at an arbitrary path, and release another client's workspace. The gate cannot see fields (it sees encoded bytes), so the rules are checked in the handlers, through one module, `remote/rules.rs`, which holds a table naming every `ACCESS_WRITE` method and its rule. A test fails when a WRITE method is missing from it, so a new WRITE RPC must be classified before it ships.

| Method | Rule for a remote caller |
| --- | --- |
| `CreateWorkspace` | `path` must be empty (the daemon's workspace root), else `REMOTE_ACCESS_DENIED` with metadata `field: path`. The new row records the caller's token id. |
| `ReleaseWorkspace`, `MoveWorkspace`, `RenewLease` | The workspace must have been created by this token, else `REMOTE_WORKSPACE_NOT_OWNED` (metadata `workspace`). `force` is allowed on its own workspaces. |
| `SnapshotWorkspace` | None: a snapshot records what is on disk, as every READ may. |
| `DescribeChange`, `AbandonChange`, `UndoOperation`, `EditFiles` | None: a write token writes changes, in every registered repository. That is what the scope means; S-38 says so. |
| `ReportPresence`, `ClearPresence` | None beyond R2.10's own (`DAEMON_PRESENCE` protects the daemon's entries). |
| `UploadScipDocuments` | None beyond R2.14's digest check. |

Callers on the socket are unaffected: they can release a remote client's workspace, as they can any other (S-08). A workspace's owner string stays informational; the token id is the remote rule's key.

### Identity and audit

- **On operations.** Every operation a remote request causes carries two new attributes beside ADR 0031's: `reef.remote-token` (the id) and `reef.remote-token-name` (the name at the time). Both are written from the request's `RemoteCaller` through `OpMeta`, never from metadata, so a remote caller cannot set or forge them. `Operation.remote` (`RemoteCaller` message) reports them typed; `Operation.attributes` already shows them verbatim. GC copies them, as it copies every attribute. Snapshots that a remote write's step 3 takes (ADR 0031) carry them too.
- **The agent.** `reef.agent` for a remote request is its `reef-agent` metadata, else the token's name, not the workspace's owner. ADR 0031 decision 2 is amended so. The token, not the agent name, is the identity; the agent name stays a label the caller chooses.
- **On workspaces.** `workspaces.remote_token_id`, set by a remote `CreateWorkspace`, reported as `Workspace.remote_token_id`.
- **In the daemon's log.** Under the target `reef_daemon::remote::audit`, at `info`: every remote request to a WRITE method (token id and name, peer, method, gRPC code and reason), including those that record no operation (`ReportPresence`, `ClearPresence`, `RenewLease`, `UploadScipDocuments`, refusals); each token create, rotate and revoke; and each address entering backoff. Token refusals (step 8) are logged at most once per address per 10 s with a count, so a scanner cannot fill the disk. READ requests are logged at `debug`. No line ever contains a secret (test 18).
- **Requirement 5 is amended.** It says "in the operation log's description"; since ADR 0031, the operation log's structured place for who caused an operation is its attributes, which the API returns typed. The amendment says "in the operation's attributes, and in the daemon's log for writes that record no operation".

### Limits and rate limiting

`remote::Limits`, on `Config::remote_limits`, not file keys, shrunk by tests through `TestDaemon::start_with`:

| Limit | Default | What happens past it |
| --- | --- | --- |
| `max_connections` | 256 | Accepted and closed at once, `warn` at most every 10 s (R2.18's `Capped`, moved to `limits.rs`) |
| `max_connections_per_address` | 32 (per IPv4 address or IPv6 /64) | The same |
| `max_handshakes` | 64 in flight | Accepts wait (the kernel's backlog holds them) |
| `handshake_timeout` | 10 s | Connection closed |
| `failures_before_backoff` | 10 token refusals in `failure_window` (60 s) from one address | The address is in backoff: its connections are closed before TLS for 60 s, doubling per repeat to 1 h, reset by an hour without failures |
| `tracked_addresses` | 4,096 | The address with the oldest last failure is forgotten |
| `max_requests_per_token` | 32 in flight | `REMOTE_BUSY` |
| `max_streams_per_token` | 16 open | `REMOTE_BUSY` |
| `cert_reload_interval` | 60 s | — |
| `max_tokens` | 256 live | `TOO_MANY_REMOTE_TOKENS` |

A guess at a 256-bit secret cannot succeed at any rate, so the backoff is for resources and log volume, not for the secret. Behind a reverse proxy or NAT, many clients share one address; the backoff counts only refusals, so working clients are unaffected unless a neighbor hammers the port with bad tokens. Open-file limits are R2.22's, and `Accepting` backs off at them as on the other listeners. Request bodies keep tonic's 4 MiB decode limit, which `EditFiles` and `UploadScipDocuments` already respect. Subscriptions share the daemon's 1,024 cap; the per-token stream cap keeps one token from taking it.

HTTP/1.1 header timeouts are not configurable through tonic's builder; a client that completes TLS and then trickles headers holds one connection slot, bounded by the caps above.

### Configuration

`[remote]` in `FileConfig`, `RemoteSection`, `deny_unknown_fields`, printed by `reef config show`:

| Key | Default | Meaning |
| --- | --- | --- |
| `enabled` | `false` | Serve the remote listener (also `--remote` for one run) |
| `listen` | `"0.0.0.0:7470"` | Any socket address with a port; port 0 is allowed (the kernel picks; tests). An IPv6 wildcard `[::]` is dual-stack where the OS makes it so |
| `names` | `[]` | DNS names (or IP literals) clients use: the Host check and the generated certificate's SANs. Empty means the machine's host name |
| `tls_cert` | `""` | A PEM certificate chain; with `tls_key`, replaces the generated certificate |
| `tls_key` | `""` | Its private key |

Validated at load: `listen` parses, `names` are valid DNS names or IP literals, `tls_cert` and `tls_key` are both set or both empty and absolute paths. `Paths::remote` is `<state>/remote`.

Unlike `[ui] listen`, `listen` is not restricted to loopback: reaching other hosts is the point. A loopback `listen` is allowed (an SSH tunnel, a reverse proxy that speaks TLS to the daemon, the tests) and still gets TLS.

### The database

Migration `0006_remote_tokens.sql`, schema version 6:

```sql
CREATE TABLE remote_tokens (
  id               TEXT PRIMARY KEY,          -- 16 hex
  name             TEXT NOT NULL,

  digest           BLOB NOT NULL,             -- blake3(secret), 32 bytes
  previous_digest  BLOB,                      -- the secret before the last rotation
  previous_until   INTEGER,                   -- unix ms; previous_digest is valid until then
  created_at       INTEGER NOT NULL,
```

Uniqueness of a live name is checked in the transaction that creates the token, since "live" depends on the clock. Backups carry the table (digests only) as part of the database; a restore brings the tokens back.

### The CLI on another machine

**Profiles.** A client keeps named remote daemons in `<state>/remotes.toml` (the client's own state directory, `0600`, in the `0700` directory S-01 checks), one table per name: `url`, `fingerprint` (optional) and `token`. The token is in the file and nowhere else: never an argument, never in shell history, never in a log.

- `reef remote add <NAME> <URL> [--fingerprint sha256:…] [--token-file PATH|-]` reads the token from the file or stdin (`-`, one line; reading an explicit `-` is not a prompt, so ADR 0025's "never interactive" holds), connects, checks the pin or the CA path, and calls `GetDaemonStatus` with the token unless `--no-check`. It refuses a URL that is not `https://` with a port or a default of 443. With no fingerprint and no CA path that validates, it fails with the presented fingerprint (see "How a client trusts the daemon").
- `reef remote list` prints each profile's name, URL and fingerprint, never the token. `reef remote remove <NAME>` deletes one.

**Choosing a remote.** A global `--remote <NAME>` (overrides `REEF_REMOTE`) points every command at a profile instead of the socket. `REEF_REMOTE` may instead be an `https://` URL, with `REEF_REMOTE_TOKEN` and optionally `REEF_REMOTE_FINGERPRINT` from the environment: for CI, containers and SDK-style use where no profile file exists. `REEF_REMOTE_TOKEN` also overrides a profile's token. `--remote` conflicts with `--socket`.

**The connection.** `reef_client::Client::connect_remote(&RemoteTarget { url, fingerprint, token })` dials TCP, handshakes with the verifier above (ALPN `h2`), and builds the same `Channel` through `connect_with_connector`, with an interceptor that adds `authorization: Bearer` beside `reef-agent`. `Client`'s `socket: PathBuf` becomes `target: Target` (`Socket(PathBuf)` or `Remote { name, url }`) for errors and the version probe. HTTP/2 keepalive every 30 s, so a stream through a NAT stays open. The connection never autostarts anything.

**What works remotely.** Every command whose arguments are ids, revisions and repository-relative paths: `status`, `log`, `show`, `diff`, `describe`, `abandon`, `undo`, `op`, `history`, `presence` (watch and report), `file read` and `list`, `symbols index`, `list` and `upload` (the SCIP file is read on the client's machine), `ws list`, `inspect`, `create`, `snapshot`, `move`, `release`, `renew`, `repo list`, `store list`, `daemon status` (it reports the remote daemon), and `remote show`.

**What is local only**, refused by the CLI before any connection with exit 9 (`Unsupported`), reason-free `CliError::RemoteLocalOnly`, hint naming why and what to do instead: `here` (it reads the current directory: "name the workspace with --workspace, or run reef here on the daemon's machine"), `ws run` (it runs a command in a directory on the daemon's machine), `ui` ("open the web URL `reef remote token create` printed"), `init`, `mcp` (a follow-up), `daemon run|start|stop`, `config`, `backup`, `restore`, `ws gc`, `store build`, `repo register|forget`, and `remote token create|list|rotate|revoke` (`backup`, `ws gc`, `store build`, `repo register|forget` and the token commands call ADMIN RPCs, which the listener would refuse anyway). Refusing early keeps a remote typo from autostarting a local daemon.

**Scope without a current directory.** In remote mode, scope resolution (ADR 0034) skips the directory steps: `--workspace` (an id or unique prefix, not a path), else `--repo` (an id, prefix, or a root path on the daemon's machine matched exactly against `ListRepositories`, never registered), else `REEF_WORKSPACE`. None is exit 2 with reason-free hint "In remote mode, name the workspace (--workspace) or repository (--repo); `reef --remote <name> ws list` lists them" and that `next`. Path arguments are repository-relative. Paths the daemon returns (workspace directories, repository roots, the state directory) are on the daemon's machine; text output prefixes them with `<name>:` (`vm:/home/u/.local/state/reef/repos/…`), and JSON keeps them as returned.

**Versions.** A remote daemon of another version is never restarted. The CLI's `Incompatible` handling becomes "the daemon at <url> is reef X (API revision N); upgrade reef on one side", exit 9.

**Errors** follow the CLI's contract. `cli/advice.rs` gains rows for the new reasons; client-side failures get their own `CliError` variants with hints: `RemoteConnect` (exit 6, "nothing answered at <url>: is the daemon running with --remote, and the port open?"), `RemoteTls` with `PinMismatch { expected, presented }`, `Untrusted { presented }` and `NameMismatch` (exit 7), and `RemoteProfile` (exit 3, "no remote named <name>; `reef remote list`").

### Commands on the daemon's machine

- `reef remote token create <NAME> [--scope read|write] [--expires DURATION|never]` prints, once, the token, the fingerprint, the listener's URL, the web URL (`https://<first name>:<port>/#session=<token>`, R2.18's bootstrap, unchanged), and the line to run on the other machine: `reef remote add <host> https://<first name>:<port> --fingerprint sha256:… --token-file -`. In JSON, `token` and `web_url` are fields of `reef_client::json::CreatedRemoteToken`. A note says when the listener is off, so tokens can be made before it is enabled.
- `reef remote token list [--all]`: id, name, scope, created, expires, last used and from where, rotated, state. Never a secret.
- `reef remote token rotate <NAME> [--overlap DURATION]` prints the new token as create does.
- `reef remote token revoke <NAME>`.
- `reef remote show`: the listener's state, address, names, certificate source, fingerprint, expiry and error, and the number of live tokens. With `--remote <name>`, it shows what that remote daemon reports, for comparing fingerprints.
- `reef daemon status` gains the same `remote` object (`reef_client::json::Status::remote`), and its text a line: `remote: listening on 0.0.0.0:7470, sha256:9f2c…, generated, expires 2027-12-02`.

`reef --help` gains the `remote` noun ("Reach a daemon on another machine, and issue tokens for it") after `ui`, and the `--remote` option: 49 lines. The agent guide does not change (34 bytes left; remote use is a person's setup step, not an agent's loop).

### The web UI over the remote listener

R2.18 designed for this: the app's `Connection` takes its base URL from `location.origin`, its bootstrap reads `#session=` into `localStorage`, and the token travels as a bearer header. Over the remote listener:

- **The URL** is the one `token create` prints: the token in the fragment, which no request line, `Referer` or server log carries, removed from the address bar by `history.replaceState`. It is a credential, and the output says so. A `read` token is the recommended one for a browser; nothing in the Phase 2 app writes.
- **HTTP/2** over TLS lifts the six-connections-per-origin limit, so the stream layer's tab sharing is no longer needed remotely (it still runs).
- **The app's changes** are small, in `web/`: `REMOTE_TOKEN_INVALID` ends the session as `WEB_SESSION_INVALID` does, with the text "This page's token is not valid for this daemon (revoked, expired or mistyped). Ask the daemon's owner for a new link." when the origin is not loopback; `REMOTE_ACCESS_DENIED` is shown like `WEB_ACCESS_DENIED`; `REMOTE_BUSY` retries with the stream backoff. The no-session page says the same when the origin is `https:`. The `web` CI job tests them.
- **No CORS.** The app is same-origin with the listener. A shell with its own origin (R3.40) is out of scope here.

### The security model, stated against the threat model

What changes is who can reach the daemon: any host that can route to the port. Against the five requirements (`docs/threat-model.md`):

1. **TLS, for a listener reachable from another host, with a pinned or CA-issued certificate.** Met: TLS 1.2 and 1.3 only, no plaintext mode on any address, the CLI and SDKs pin the key or validate against CA roots, and the token is never sent before the server is verified (S-35).
2. **A per-client token with scopes; the default scope allows none of the dangerous calls.** Met: named per-client tokens; scopes `read` and `write` as sets of access levels; no ADMIN remotely, so no store build, backup, quiesce (#64's S-10), GC, registration or web session; field rule on `CreateWorkspace.path`; ownership rule on release, move and renew; default scope `read` (S-36 to S-38).
3. **The local socket's full API is never exposed by default.** Met: the listener is off by default, serves only READ and WRITE methods under a token's scope, never the v0 beacon, never `CreateWebSession`, and never inherits the socket's "every client is the user" (S-44).
4. **Rate limits on the unauthenticated surface.** Met: handshake concurrency and timeout, connection caps per listener and address, backoff for addresses that fail tokens, refusals that cost one digest and one map lookup, bounded failure tracking (S-36, S-40).
5. **Audit of every mutation, with the client's identity.** Met as amended: the token's id and name on every operation, typed in the API; every remote WRITE request, auth event and token change in the daemon's log (S-42).

Beyond the list: a browser reaching the listener gets R2.18's protections (Host, `Origin`, fetch metadata, no CORS, CSP; S-41), and what each scope exposes is stated as findings (S-38, S-39, S-43, S-47).

**What "reviewed under RX.01" means.** RX.01 decided that a remote listener is reviewed by its own brief against the requirements it wrote, as an amendment to `docs/threat-model.md`, with no new RX ticket ("R2.08 is in scope as requirements, out as a review"). This brief is that review: the mapping above, the rows below with a test each, and the "Reviews" section recording that no external review took place. RX.02 is the first external review, and the threat model recommends, until then, serving the listener on a private network (a VPN or a cloud VPC) rather than the open internet.

A new file, `remote.proto`:

```proto
// Remote access (R2.08, ADR 0049): tokens for the daemon's remote listener.
// Every RPC here is ADMIN, so it is served only on the socket.
syntax = "proto3";

package reef.api.v1;

import "google/protobuf/duration.proto";
import "google/protobuf/timestamp.proto";
import "reef/api/v1/options.proto";

// Issuing and ending remote tokens.
service RemoteService {
  // Issues a token. Its secret is in the response and nowhere else: the
  // daemon keeps only a digest. Errors: INVALID_ARGUMENT with reason
  // INVALID_REMOTE_TOKEN_NAME; ALREADY_EXISTS with reason
  // REMOTE_TOKEN_EXISTS (a live token has the name); FAILED_PRECONDITION
  // with reason TOO_MANY_REMOTE_TOKENS (256 live).
  rpc CreateRemoteToken(CreateRemoteTokenRequest) returns (CreateRemoteTokenResponse) {
    option (reef.api.v1.access) = ACCESS_ADMIN;
  }
  // Lists tokens, newest first; live ones unless `include_ended`.
  rpc ListRemoteTokens(ListRemoteTokensRequest) returns (ListRemoteTokensResponse) {
    option (reef.api.v1.access) = ACCESS_ADMIN;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
  // Gives a live token a new secret; the old one stays valid for
  // `overlap`. Errors: NOT_FOUND with reason REMOTE_TOKEN_NOT_FOUND.
  rpc RotateRemoteToken(RotateRemoteTokenRequest) returns (RotateRemoteTokenResponse) {
    option (reef.api.v1.access) = ACCESS_ADMIN;
  }
  // Ends a live token at once, open streams included (within a second).
  // Errors: NOT_FOUND with reason REMOTE_TOKEN_NOT_FOUND.
  rpc RevokeRemoteToken(RevokeRemoteTokenRequest) returns (RevokeRemoteTokenResponse) {
    option (reef.api.v1.access) = ACCESS_ADMIN;
    option idempotency_level = IDEMPOTENT;
  }
}

// What a token allows on the remote listener.
enum RemoteScope {
  // REMOTE_SCOPE_READ on create; never reported.
  REMOTE_SCOPE_UNSPECIFIED = 0;
  // ACCESS_READ methods.
  REMOTE_SCOPE_READ = 1;
  // ACCESS_READ and ACCESS_WRITE methods, with the rules ADR 0049 lists: no
  // `path` on CreateWorkspace; release, move and renew only of workspaces
  // this token created.
  REMOTE_SCOPE_WRITE = 2;
}

// A token, without its secret.
message RemoteToken {
  // 16 hex characters, the second part of the token; never reused.
  string id = 1;
  // Unique among live tokens.
  string name = 2;
  RemoteScope scope = 3;
  google.protobuf.Timestamp created_at = 4;
  // Unset: never.
  google.protobuf.Timestamp expires_at = 5;
  // Unset until rotated.
  google.protobuf.Timestamp rotated_at = 6;
  // When the secret before the last rotation stops working; unset when it
  // already has.
  google.protobuf.Timestamp previous_valid_until = 7;
  // Unset unless revoked.
  google.protobuf.Timestamp revoked_at = 8;
  // To the minute; unset until used.
  google.protobuf.Timestamp last_used_at = 9;
  // The peer address of that use, such as `203.0.113.7:51522`.
  string last_used_from = 10;
}

message CreateRemoteTokenRequest {
  // `[a-z0-9][a-z0-9._-]{0,62}`.
  string name = 1;
  RemoteScope scope = 2;
  // Unset: 30 days. Ignored with `never_expires`.
  google.protobuf.Duration expires_in = 3;
  bool never_expires = 4;
}

message CreateRemoteTokenResponse {
  RemoteToken token = 1;
  // The bearer token, `reef_<id>_<secret>`: a credential, shown once.
  string secret = 2;
}

message ListRemoteTokensRequest {
  // Also revoked and expired tokens.
  bool include_ended = 1;
  // Tokens per page: 0 means 100, more than 1,000 means 1,000, and a
  // negative value is INVALID_ARGUMENT.
  int32 page_size = 2;
  // The previous page's `next_page_token`; empty for the first page.
  string page_token = 3;
}

message ListRemoteTokensResponse {
  repeated RemoteToken tokens = 1;
  // Empty on the last page.
  string next_page_token = 2;
}

message RotateRemoteTokenRequest {
  string name = 1;
  // How long the old secret keeps working; unset or zero: not at all. At
  // most 7 days.
  google.protobuf.Duration overlap = 2;
}

message RotateRemoteTokenResponse {
  RemoteToken token = 1;
  // The new bearer token: a credential, shown once.
  string secret = 2;
}

message RevokeRemoteTokenRequest {
  string name = 1;
}

message RevokeRemoteTokenResponse {
  RemoteToken token = 1;
}

// Who called through the remote listener.
message RemoteCaller {
  // The token's id.
  string token_id = 1;
  // Its name when the call was made.
  string token_name = 2;
}
```

### Errors and reasons

New constants in `reef_api::error`, from `RemoteError` in `reef-daemon/src/remote/mod.rs` with `Classify` and `Advise`:

| Reason | Kind (gRPC) | Metadata | Hint | `next` |
| --- | --- | --- | --- | --- |
| `REMOTE_TOKEN_INVALID` | `PermissionDenied` | `state` (`unknown`, `expired`, `revoked`) | "The daemon refused this token (`state`). Ask the daemon's owner for a new one (`reef remote token create` on that machine), then `reef remote add` it again." | none |
| `REMOTE_ACCESS_DENIED` | `PermissionDenied` | `method`, `access`, `scope`, or `field` | "This token's scope (`scope`) does not allow `method`; ADMIN calls run only on the daemon's machine." / for `field`: "Remote callers cannot set `path`; the workspace goes under the daemon's workspace root." | none |
| `REMOTE_WORKSPACE_NOT_OWNED` | `PermissionDenied` | `workspace` | "Remote callers release, move and renew only workspaces their token created." | none |
| `REMOTE_BUSY` | `Unavailable` | `limit` (`requests`, `streams`) | "This token has too many calls open; close some or retry." | none |
| `REMOTE_TOKEN_NOT_FOUND` | `NotFound` | `name` | "No live token is named `name`." | `reef remote token list` |
| `REMOTE_TOKEN_EXISTS` | `AlreadyExists` | `name` | "A live token is named `name`: rotate it, or revoke it first." | `reef remote token rotate <name>` |
| `TOO_MANY_REMOTE_TOKENS` | `Conflict` | `limit` | "Revoke tokens you no longer use." | `reef remote token list` |
| `INVALID_REMOTE_TOKEN_NAME` | `InvalidArgument` | `name` | "Use lowercase letters, digits, `.`, `_` and `-`, at most 63, starting with a letter or digit." | none |

**No tenth error kind** (decided by the user). A refused token is `PermissionDenied`, exit 7, distinguished by its reason, as R2.18's `WEB_SESSION_INVALID` is. A new `Unauthenticated` kind would add an exit code (ADR 0025) and a gRPC code mapping (ADR 0029 decision 14) for one answer, while every client already branches on `reason`. The cost is that a generic gRPC client sees `PERMISSION_DENIED` (7) where gRPC's convention is `UNAUTHENTICATED` (16) for a missing or bad credential; the SDKs (R2.06, R2.07) read the reason.

## Tests

In `crates/reef-daemon/tests/remote.rs` (new), on `TestDaemon` with the listener on `127.0.0.1:0`, through `reef_client::Client::connect_remote` for native gRPC, `tonic_web::GrpcWebClientLayer` over a hyper-util client with a rustls connector for gRPC-web, and raw TLS and HTTP through tokio-rustls and hyper:

1. `off_by_default`: a default daemon binds no remote port (`RemoteListener::is_bound()`), and `GetDaemonStatus.remote.state` is `OFF`.
2. `generated_certificate`: on first start, `<state>/remote/key.pem` and `cert.pem` are `0600` in a `0700` directory; the presented leaf's SPKI hashes to `remote.certificate.fingerprint`; the SANs hold `names` and the host name. A restart presents the same fingerprint. With a test seam making validity 40 days, the start renews: a new `not_after`, the same fingerprint. Changing `names` renews with the same key.
3. `supplied_certificate`: with `tls_cert` and `tls_key` from a test CA (rcgen), a client trusting that CA by name connects without a pin; `source` is `FILE`. Replacing both files with a new pair is presented to a handshake within `cert_reload_interval` (100 ms in the test) without a restart. A broken pair keeps the old one serving and sets `remote.error`. Unreadable files at start are `FAILED` with the error, and the socket serves.
4. `no_plaintext`: HTTP/1.1 and HTTP/2 prior knowledge in clear to the port get no HTTP response (the handshake fails and the connection closes); a TLS client offering only `http/1.1` gets gRPC-web and the assets; one offering `h2` gets native gRPC.
5. `pin_is_checked_before_the_token`: a client with a wrong pin fails with `RemoteTls::PinMismatch` naming the presented fingerprint, and the daemon's audit log shows no token refusal (the request was never sent). A client with no pin and no CA trust fails with `Untrusted` the same way.
6. `tokens_are_required`: no `authorization`, `Bearer x`, a well-formed unknown token, a known id with a wrong secret: each `PERMISSION_DENIED`, `REMOTE_TOKEN_INVALID`, `state: unknown`. The right secret after expiry (`expires_in` 200 ms) is `state: expired`, after revocation `state: revoked`. With a valid token, `GetDaemonStatus` answers.
7. `scopes_cover_every_method`: for every path in `reef_api::methods()`, with a default request: a `read` token is never `REMOTE_ACCESS_DENIED` on READ and always on WRITE and ADMIN (`access` set); a `write` token is never denied on READ or WRITE by scope and always on ADMIN; the v0 beacon and an unknown path are `access: unknown` for both. `CreateWebSession` and every `RemoteService` RPC are denied.
8. `write_rules_table_is_complete`: `rules::TABLE` names exactly the `ACCESS_WRITE` methods of `reef_api::methods()`.
9. `field_and_ownership_rules`: a write token's `CreateWorkspace` with `path` is `REMOTE_ACCESS_DENIED`, `field: path`, and creates nothing; without it, the workspace is created under the root with `remote_token_id` set. That token releases, moves and renews its own; it is `REMOTE_WORKSPACE_NOT_OWNED` for a socket-created workspace and for another token's; the socket releases the remote-created one. `SnapshotWorkspace` of a socket-created workspace succeeds.
10. `operations_name_the_token`: a remote `DescribeChange` without `reef-agent` records `reef.remote-token`, `reef.remote-token-name` and `reef.agent` = the token's name, and returns `Operation.remote`; with `reef-agent: planner`, `agent` is `planner` and `remote` is still set. A socket describe has no `remote`. A snapshot the write took first carries them too. After `CollectGarbage` rewrites the operation, its attributes are unchanged. A remote request cannot set the attributes through metadata (a `reef-remote-token` header is ignored).
11. `audit_log`: with `log.level` `info`, a remote `ReportPresence`, `RenewLease`, `UploadScipDocuments`, a refused write and a token refusal each produce one `reef_daemon::remote::audit` line with token id or peer, method and code; 100 refusals from one address in 1 s produce at most one refusal line per 10 s with a count.
12. `rotation`: rotate with no overlap: the new secret works, the old is refused at once. Rotate with `overlap` 300 ms: both work, then only the new. The id, name, scope and expiry are unchanged; `rotated_at` is set.
13. `revocation_ends_streams`: with a token, open `SubscribeOperations` (native) and `SubscribePresence` (gRPC-web); revoke over the socket; both end within 1 s with `REMOTE_TOKEN_INVALID`, `state: revoked`; a new call is refused. Another token's open stream is unaffected.
14. `token_lifecycle_rpcs`: create returns `reef_<16 hex>_<43 base64url>` and the row stores neither the secret nor anything it can be derived from but its blake3 digest (the secret's bytes appear nowhere in `reef.sqlite3`); names are validated; a live duplicate is `REMOTE_TOKEN_EXISTS`; one past `max_tokens` (shrunk to 2) is `TOO_MANY_REMOTE_TOKENS`; revoke and rotate of an unknown name are `REMOTE_TOKEN_NOT_FOUND`; list pages, hides ended tokens unless asked, and records `last_used_at` and `last_used_from` after a call (flush interval shrunk).
15. `backoff`: `failures_before_backoff` 3, backoff 300 ms: three refusals from `127.0.0.1`, then a new connection is closed before the handshake; after 300 ms a valid token works; a second round doubles the backoff. Valid calls interleaved with the failures do not reset the count.
16. `connection_limits`: `max_connections` 3 and per-address 2: a third connection from one address is closed at once; `max_handshakes` 1 with one silent connection holding it, a second handshake completes after `handshake_timeout` (200 ms) closes the first.
17. `per_token_limits`: `max_streams_per_token` 1: a second stream is `REMOTE_BUSY`, `limit: streams`; `max_requests_per_token` 1 with a slow call in flight: a second is `REMOTE_BUSY`, `limit: requests`. Another token is unaffected.
18. `secrets_never_reach_logs`: with `log.level` `debug`, after every call, refusal, rotation and stream in this file, no file under `logs/` contains a secret, and no error message or metadata does.
19. `web_ui_over_remote`: over TLS with HTTP/2 and with HTTP/1.1, `GET /` serves the assets with R2.18's headers and no `Access-Control-*` or `Strict-Transport-Security`; a `Host` of a configured name and of an IP literal with the port are served, another name is `421`; an `Origin` of `https://` plus the Host passes and any other is `403` before the token; a gRPC-web `GetDaemonStatus` with a read token answers; `SubscribeOperations` over gRPC-web delivers a describe made over the socket within R2.09's bound.

## Implementation notes

- **Order**:
  1. the schema, the revision and the reasons;
  2. the migration and `Tokens` with unit tests;
  3. `remote/tls.rs` and the client verifier, with tests 2 to 5 and 24;
  4. the incoming loop, the router and the generalized gate (tests 1, 6, 7, 15 to 17, 19 to 23);
  5. `caller_of`, the attributes, the rules table and the handlers' checks (tests 8 to 11);
  6. rotation and revocation (12 to 14, 18);
  7. the client and the CLI (25 to 32);
  8. `web/` (W9, W10);
  9. the e2e script and its CI steps;
  10. the threat model, the ADR and the quickstart.
- **Dependencies without aws-lc.** `rustls = { version = "0.23", default-features = false, features = ["ring", "std", "tls12"] }`, `tokio-rustls = { version = "0.26", default-features = false, features = ["ring", "tls12"] }`, `rcgen = { version = "0.14", default-features = false, features = ["ring", "pem", "crypto"] }`. Run `cargo tree -i aws-lc-sys` and expect nothing; the `crate_graph` check holds it. Do not enable tonic's `tls-*` features.
- **The gate inserts, handlers read.** `RemoteCaller` travels in `http::Extensions`, which tonic hands to `tonic::Request::extensions()`. Never read identity from metadata, and have the gate remove any request header whose name starts with `reef-remote` so nothing downstream is tempted.
- **`caller_of` replaces `agent_of`** in every handler at once; a grep for `agent_of(` must find none left. The `OpMeta` the write paths build takes the caller, so snapshots in a write's step 3 carry it without each call site remembering.
- **Revocation tokens.** `Tokens` keeps a `CancellationToken` per live token, cancelled on revoke and on expiry (a timer per token is unnecessary: the gate refuses expired tokens at request start, and a once-a-second sweep cancels expired tokens' streams). The streaming handlers' `select!` already watches `AppState::shutdown`; add the caller's token there.
- **The verifier must still verify signatures.** A pin verifier that returns `ServerCertVerified` without checking the handshake signature would accept a man in the middle presenting the pinned certificate without its key. Use `rustls::crypto::verify_tls13_signature` and `verify_tls12_signature` with the provider's `signature_verification_algorithms`. Test 5's wrong-pin case and a unit test with the right certificate and a wrong key cover it.
- **Fingerprints** come from `webpki::EndEntityCert::try_from(&der)` then `subject_public_key_info()`, hashed with `ring::digest::SHA256`. The same function serves the daemon's status, the client's check and the error's "presented" value, so they cannot disagree.
- **Peers.** The connection type implements `tonic::transport::server::Connected` with the peer `SocketAddr`; the gate reads it from the request extensions for backoff and audit. IPv6 peers are tracked by /64.
- **Linux.** Nothing is `cfg(target_os = "linux")`, but run `just lint` and the `remote` tests in the privileged `ubuntu:24.04` container before pushing, since `Config`, `Paths` and the database change. The e2e script needs Docker on the host.
- **Disk.** ring adds a C build; check `df` before the first build in a fresh target directory.

## Inherited scope

- **From the design and ADR 0004**: an optional TLS listener with token authentication serving the same API to remote clients, a phone among them.

## Out of scope

- CORS for a shell's origin, and push notifications from the listener (R3.40).
- Response compression for assets and messages (a follow-up issue the PR files, decided on measurements from a phone).
- ACME inside the daemon (a follow-up): an external client renewing the supplied files covers it.
- Tokens restricted to repositories or workspaces, and per-RPC custom scopes.
- `reef mcp` against a remote daemon (a follow-up: an agent on another machine working through virtual edits).
- Storing client tokens in an OS keychain (a follow-up).
- Mutual TLS, OIDC or any identity provider; daemon-user separation; peer credentials on the socket.
- An `admin` scope (decided by the user).
- A QR code for the web URL.
- Remote access to a remote store (R4).

## Risks

- **Phones and self-signed certificates.** iOS and Android browsers make the self-signed warning hard or impossible to accept for a page's background requests. The exit criterion is met with a desktop browser and the CLI; the quickstart says a phone needs a supplied certificate (a domain with ACME, or a VPN's certificate service), and the manual check records which was tested.
- **A public port on a cloud VM.** `listen` defaults to all interfaces. A person who enables the listener on a VM with an open security group exposes a TLS port that refuses everything without a token. The quickstart recommends a private network until RX.02's external review, and `reef daemon start --remote` prints the address it bound.
- **A forgotten flag.** A daemon started with `--remote` and later restarted by something other than the CLI's version restart (a reboot, a crash and an autostart) comes back without the listener. `GetDaemonStatus.remote.enabled_by` makes it visible; the quickstart recommends `[remote] enabled` for anything lasting.
- **Pins after a restore.** A restored state directory has no generated key, so clients fail with a pin mismatch until re-added. The hint says so.
- **Shared addresses.** Behind NAT or a proxy, one client that sends bad tokens puts every client from that address in backoff. Backoff counts only refusals, and its first period is a minute.
- **The token in a browser.** A remote token in `localStorage` lives until revoked or expired, unlike R2.18's per-process sessions. An injection in the app would carry it; the CSP and R2.18's rules are the mitigation, and a `read` token is recommended for browsers.
- **Build cost.** ring's C build adds to cold builds on every CI runner and target. The PR records it.
- **Revset work cannot be interrupted** inside jj-lib (R2.02's risk), so a remote reader can still occupy a repository thread with one expensive request. The per-token cap bounds how many.

## Choices this brief made, and why

- **One port for native gRPC, gRPC-web and assets**: `GrpcWebLayer` already sorts them, and one port is one firewall rule and one certificate.
- **Reef's own TLS termination**: ALPN for HTTP/1.1, certificate reload, and an explicit provider, none of which tonic's acceptor offers.
- **ring, not aws-lc-rs**: a C compiler is all it needs on the four targets, and nothing needs FIPS.
- **Key pinning with same-key renewal**: renewals never break a pin, and CA-issued certificates work without one.
- **Tokens as id plus secret, stored as blake3 digests**: lookup without scanning, and nothing at rest worth stealing.
- **Two scopes and no ADMIN**: requirement 2's dangerous calls are all ADMIN or one field away from WRITE, and SSH to the machine already covers administration.
- **A rules table checked for completeness**: a new WRITE RPC cannot ship unclassified.
- **Attributes, not descriptions**: identity in the structured place ADR 0031 created, typed in the API, unforgeable through metadata.
- **Profiles with the token in a private file, and local-only commands refused early**: no secret on a command line, and no surprise local daemon.
- **No tenth error kind**: one answer does not justify a new exit code; the reason carries it.

## Decided by the user

Decided on 2026-10-31, each as this brief recommended:

1. **The noun is `reef remote`**: `remote token …` on the daemon's machine, `remote add|list|remove|show` and `--remote` on the other. Reef's git-remote configuration can live under `reef git` when R3.17 needs it.
2. **ADMIN is never served remotely.** There are two scopes, `read` and `write`, and no `admin` scope. Administration happens on the daemon's machine.
3. **A new token defaults to scope `read` and a 30-day expiry**; `--scope write` and `--expires never` are explicit.
4. **The default certificate is generated and pinned by key**; supplied files are optional, and the quickstart's phone path uses them.
5. **`[remote] listen` defaults to `0.0.0.0:7470`**; the quickstart recommends binding a private interface until RX.02.
6. **No tenth error kind**: a refused token is `PermissionDenied` (exit 7) with its reason.
7. **Size L, not split**, with the deferrals in "Out of scope" filed as issues by the PR.
