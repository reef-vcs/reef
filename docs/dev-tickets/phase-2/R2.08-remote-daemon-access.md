# R2.08 Remote daemon access: the web and remote listeners

Phase 2 · Size M · Depends on: R2.01 (the v1 services, `Remote { IssueToken, ListTokens, RevokeToken }`, `Daemon.Status.web_url`, the full method names the scope table is checked against), R1.04 (configuration and the state directory), RX.01 (`docs/threat-model.md`'s "Requirements for a remote listener", ADR 0027) · Unblocks: R2.18 (the web UI is served from these listeners and `reef ui` issues its token here), R3.40 (the mobile shell reaches a daemon this way), the last Phase 2 exit criterion

## Context

Every RPC the daemon serves is authorized by the socket's file mode: one uid, one trust domain (ADR 0027). The design's deployment topologies need more: a daemon in a cloud VM reached from a laptop or a phone "over TLS with a token", and, before any of that, a browser on the same machine, because the web UI (R2.18) cannot open a Unix socket. A loopback HTTP listener is not the socket: every local user can connect to it, and every web page the user visits can send requests to `127.0.0.1`, so it needs the same token check as a routable one. This ticket adds one listener implementation with two bindings, the token store and scopes it checks, the TLS it speaks when routable, the CLI to issue tokens and to talk to a remote daemon, and the threat-model rows the requirements section asked for.

## Decisions

- **Three listeners, one router.** The Unix socket stays as it is and is the only listener that serves `Remote` and `tonic-reflection`. The **web listener** (`[web] enabled = true, listen = "127.0.0.1:0"`) is plaintext loopback with `accept_http1(true)` (browsers speak grpc-web over HTTP/1.1 without TLS). The **remote listener** (`[remote] enabled = false, listen = "[::]:7447", cert = "<state>/remote/cert.pem", key = "<state>/remote/key.pem", auth_rate_limit = 10, origins = []`) is TLS always: no plaintext mode exists in code, and a `[remote]` without a readable cert and key refuses to start with a hint naming `reef remote cert`. `reef daemon run --remote` (and `reef daemon start --remote`, which passes it through) enables the remote listener for that run. Both listeners serve the same `Router` minus `Remote`: every gRPC service, `tonic_web::GrpcWebLayer`, a CORS layer, the Origin/Host check, the body cap, and the auth layer; R2.18 adds the static files. Listener module: `crates/reef-daemon/src/listener/{mod,auth,scopes,tls,web,ratelimit}.rs` and `db/tokens.rs`.
- **Bearer tokens.** Every request on the web and remote listeners carries `authorization: Bearer <token>`; absent or unknown is `UNAUTHENTICATED` before any handler runs. A token is `reef_` plus 32 random bytes base64url without padding (the prefix is for secret scanners and for `reef` to tell a token from a path); the daemon stores `blake3(token)` hex, never the token, and never logs it. Migration `0007_tokens`: `tokens(id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE, hash TEXT NOT NULL UNIQUE, scopes TEXT NOT NULL, created_at INTEGER NOT NULL, expires_at INTEGER, last_used_at INTEGER, revoked_at INTEGER)`; `scopes` is a JSON array of scope names; `last_used_at` is written at most once a minute per token. `Remote.IssueToken { name, scopes, expires_in }` returns the token once; `ListTokens` returns everything but the hash; `RevokeToken { name_or_id }` sets `revoked_at` and drops the token from the in-memory cache at once. The `Remote` service is refused on the web and remote listeners with `PERMISSION_DENIED` whatever the token's scopes (it is in the never-remote list), so a token can never mint tokens. CLI: `reef remote token create --name <n> [--scope read,presence,workspaces,admin] [--expires 90d]` (default scope `read`, default expiry 90 days; `--expires never` allowed and shown in `list` as such) prints the token on stdout once (`{id, name, token, scopes, expires_at}` in JSON; text mode prints the token on its own line with a stderr note that it is not shown again), `reef remote token list`, `reef remote token revoke <name|id>`. All three are socket-only.
- **Scopes.** `read`: `Daemon.Status`, `Repositories.List`, `Workspaces.List|Inspect|Status`, `Changes.Log|Get|Diff`, `Operations.Log|Get|Subscribe|Replay`, `Trees.List|Read`, `Presence.Subscribe`, `Symbols.Lookup`, `Queries.List|Run`, `Stores.List`, `Maintenance` none. `presence`: `Presence.Report`. `workspaces`: `Workspaces.Create` (refused with `PERMISSION_DENIED` when `path` is non-empty, before the manager sees it), `Workspaces.Release|Move|Heartbeat|Snapshot`, `Changes.Describe|Abandon|Squash`, `Operations.Undo`, `Trees.Apply`, `Symbols.Index`. `admin`: `Repositories.Register|Forget`, `Maintenance.Gc|Quiesce|Resume` (S-10: quiesce is `admin`, not in the default scope), `Stores.Build|Prepare|Seal|Abort`, `Symbols.Ingest`. **Never remotely**: `Maintenance.Backup` (writes to a path on the daemon's host), `Workspaces.Create` with `path`, the whole `Remote` service, and reflection. The table is `scopes::SCOPES: &[(&str, Scope)]` keyed by full method name plus `NEVER_REMOTE: &[&str]`; a unit test walks `reef_api::DESCRIPTOR_SET` and fails if any method of any service is in neither, so a new RPC without a scope decision fails the build. A request whose token lacks the method's scope is `PERMISSION_DENIED` with the hint naming the scope and `next` empty.
- **The auth layer** (`listener::auth::AuthLayer`), a tower `Layer` applied with `Server::layer` on the web and remote routers: reads the path, resolves the method's scope (`UNIMPLEMENTED` for an unknown path, so unknown services are not probed), parses `authorization`, looks the hash up (an in-memory `RwLock<HashMap<hash, TokenRecord>>` loaded at start and updated on issue and revoke, falling back to the database on a miss so a token issued by another daemon process on the same state directory is still seen), checks `revoked_at` and `expires_at`, then inserts `ClientIdentity::Token { id, name, scopes }` into the request extensions. The socket router gets a trivial layer inserting `ClientIdentity::Socket`. Responses to failed authentication are plain gRPC statuses with no detail about why beyond `UNAUTHENTICATED` (no "unknown token" versus "expired" distinction to a remote caller; the daemon logs the reason at `info` with the token's id when it is a known token).
- **Audit.** `ClientIdentity` reaches every transaction: `CreateSpec`, `ReleaseSpec`, `MoveSpec`, the snapshot request path, and R2.03's write RPCs carry `client: ClientLabel` (`socket`, `token:<name>`, or `daemon` for the watcher's and lease loop's own operations), and the repository thread sets `tx.set_attribute("reef.client", label)` on every operation it commits. `is_reef_snapshot` is untouched. The daemon logs every remote mutating RPC at `info` with `client`, `method`, and the ids it names. The threat model's requirement 5 is reworded to "in the operation record (the `reef.client` attribute)", with the reason.
- **Browser rules.** On the web and remote listeners a layer checks `Host` against the listener's own addresses (the bound address and, for `[remote]`, each SAN of its certificate and each `[remote] origins` entry), and `Origin`, when present, against `http(s)://<those>`; mismatches are `403` before the auth layer, which defeats DNS rebinding (a page at `attacker.example` resolving to `127.0.0.1` sends `Host: attacker.example`). `CorsLayer`: `allow_origin` the same list, `allow_headers` `authorization, content-type, x-grpc-web, x-user-agent, grpc-timeout`, `expose_headers` `grpc-status, grpc-message, grpc-status-details-bin`, `allow_credentials(false)`; cookies are never read. `reef ui` (R2.18) puts the token in the URL fragment, never a query string, so it does not reach logs.
- **Limits.** Failed authentications are rate-limited per peer address with a `governor::RateLimiter` keyed by `IpAddr` from `TcpConnectInfo`/`TlsConnectInfo`: `[remote] auth_rate_limit` failures per minute (default 10), after which that address gets `RESOURCE_EXHAUSTED` with `retry-after` for the rest of the window, authenticated or not. Successful requests are not limited. `RequestBodyLimitLayer` caps bodies at 4 MiB on these listeners (the socket has no cap); `Symbols.Ingest` and `Trees.Apply` stream above that.
- **TLS.** `reef remote cert [--san <host|ip>]...` generates a self-signed certificate with `rcgen::generate_simple_self_signed` for the machine's hostname, `localhost`, its non-loopback IPs, and the given SANs, valid 2 years, into `<state>/remote/cert.pem` and `key.pem` (`0600`, directory `0700`), and prints the certificate's SHA-256 fingerprint; it refuses to overwrite without `--force`. The daemon loads `[remote] cert` and `key` with `Identity::from_pem` and serves TLS 1.2+ (rustls's default set) through tonic `tls-ring`. A CA-issued pair is configured by path. Client side: `reef_api::client::Client::connect_remote(url, token, ca: Option<PathBuf>)` uses `ClientTlsConfig` with the given CA, else the system roots (`tls-native-roots`; not `webpki-roots`, whose license is not on `deny.toml`'s list), and an interceptor adding `authorization`. The CLI reads `REEF_REMOTE` (`https://host:7447`), `REEF_TOKEN`, and `REEF_REMOTE_CA` (a PEM path); when `REEF_REMOTE` is set, `connect()` uses them instead of the socket and never autostarts. Commands that work remotely: every read command, `ws create` (without `--path`), `ws list|inspect|release|move|snapshot`, `here` (by `REEF_WORKSPACE` only), `status|log|diff|ops|describe|undo|abandon|squash|tree|watch|presence|replay|symbols|query`, `repo register|forget` and `ws gc` with `admin`. Refused client-side with a hint before any RPC: `ws run` (the workspace's path is on the other machine; the hint names `ws create` and the remote path), `daemon *`, `backup`, `restore`, `config show`, `remote token *`, `init`, `store build` (R2.27 runs builds client-side in a local scratch; remote stores are not a Phase 2 feature).
- **Status and discovery.** After binding, the daemon writes `<state>/web.json` (`0600`): `{ "url": "http://127.0.0.1:<port>", "pid": <pid> }`, removed at shutdown and replaced at start; `Daemon.Status` gains `web_url` and `remote_listen` (empty when off), and `reef daemon status` prints them. Phase 1's "a stale socket is replaced" rule applies to a stale `web.json`.
- **The port.** 7447 is the README's choice; the brief keeps it provided the IANA service-name registry shows it unassigned, which the implementer checks and records in ADR 0033 (if it is assigned, pick the nearest unassigned port above 7000 and update the README's row and this brief in the PR). It is a default, not a promise: `[remote] listen` is the knob.
- **Daemon-user separation is still out** (ADR 0027): a token is a client identity for the network listeners only; the socket stays one uid. ADR 0033 says so.
- **ADR 0033, "Remote and web listeners: TLS, tokens, scopes"**: the three listeners and why loopback needs a token; bearer tokens hashed at rest; the scope table and the never-remote list; the audit attribute instead of a description suffix; Host/Origin checks and CORS; rate limiting failures only; the body cap; the port; alternatives (mTLS, an SSH tunnel as the only remote path, a per-RPC allowlist without scopes, HTTP basic auth, daemon-user separation now); consequences for R2.18 (`reef ui`'s short-lived token) and R3.40.

## Implementation notes

- Build one `Router` per listener kind: the socket's with `Remote` and reflection, the network ones without. `Server::builder().layer(...)` applies to every service in that router; the Unix socket router gets only the identity layer.
- The auth layer must run after `GrpcWebLayer` has translated the request's content type but it reads only the path and `authorization`, which grpc-web leaves alone, so order it before grpc-web and keep the Host/Origin layer first so a rebinding page never reaches token checks.
- Tokens: generate with `rand::rng()` (the workspace's `rand`), hash with the workspace's `blake3`; compare hashes, not tokens, and look up by hash so no timing side channel on the token itself exists (the hash lookup is a `HashMap` get).
- `IpAddr` for the limiter comes from `req.extensions().get::<TcpConnectInfo>()` or the TLS wrapper; on the web listener it is always loopback, so the limiter there is effectively global, which is fine: it is a brake on a hostile local page, not a fairness mechanism.
- `web.json` is written after the bind succeeds and removed in the same place the socket file is (`supervise`'s shutdown path).
- The CLI's remote mode must not touch the local config file's socket or autostart: `connect()` branches on `REEF_REMOTE` before `Config::load`. `--no-autostart` is implied.
- The client-side refusals are `CliError::Refused` with `Advice`, so ADR 0025's `every_next_is_a_real_command` covers them.
- Linux-only test 10 runs in the `check` job on `ubuntu-24.04` (no privilege needed); gate it on an environment variable the job sets (`REEF_TEST_NON_LOOPBACK=1`) so it does not run on developer machines with odd interfaces.
- `[remote] origins`: extra allowed origins for a reverse proxy or a browser reaching the daemon by a name not in the certificate; document it, default empty.

## Out of scope

- The web UI's pages and `reef ui` (R2.18; this ticket gives it `IssueToken` with an expiry and the listener).
- Daemon-user separation, peer credentials on the socket, mTLS, OAuth or device-code flows, a token in a config file or keychain (`REEF_TOKEN` only; a `reef remote login` that stores tokens is a follow-up once R2.18 shows the shape).
- Remote `ws run`, remote stores, a reverse-proxy guide beyond `[remote] origins`.
- Streamable-HTTP MCP over this listener (R2.13 is stdio only).
- Certificate rotation and ACME.

## Risks

- **A loopback listener is a new exposure on every laptop.** The token check and Host/Origin rules are what make it acceptable, and `[web] enabled = false` turns it off at the cost of the UI. The threat model says this plainly, and the PR's review focuses on the layer order (a request must never reach a handler without passing all of them).
- **`reef.client` on every transaction touches many call sites.** A missed one is silent. Test 11 checks three paths; the implementer greps for `start_transaction` and `commit` in the daemon and adds a debug assertion in the repository thread that every committed operation has the attribute.
- **grpc-web through tonic-web with the auth layer** is new ground; test 6 is the end-to-end check, and R2.18's Playwright smoke is the second.
- **Self-signed certificates and browsers.** The quickstart has to say how to trust the certificate on a phone or a laptop; a CA-issued pair is the better path for anything beyond a trial, and the brief says so.
- **The port** may be registered; the check and fallback are decided above.

## Proposed departure from the README

*Accepted 2026-10-25: the README's crate table names `governor` 0.10 and `tls-native-roots`, and its configuration row lists `[remote] origins`.*

Two small ones. The README names `tower_governor`; its built-in key extractors read axum's `ConnectInfo`, which tonic does not insert, and a per-request layer limits requests rather than failures, so this brief uses the underlying `governor` crate (0.10, MIT) keyed by the peer `IpAddr` from tonic's `TcpConnectInfo`, limiting failed authentications only; the crate table row should say `governor` 0.10. And the CLI's remote client uses tonic's `tls-native-roots` for CA-issued certificates, not `webpki-roots`, whose CDLA-Permissive-2.0 license is not on `deny.toml`'s allow list. Also noted, not a departure: `[remote] origins` is an added key.
