# R2.11 Agent presence reporting

Phase 2 · Size M (the row says S; see "Size") · Depends on: R2.10 (the three presence RPCs, their reasons, the client's `report_presence` and `clear_presence`, the `presence` noun and `reef presence watch`) · Unblocks: R2.06 and R2.07 (the reporting contract their workspace helpers follow), R2.20 (each agent's activity per workspace in the fleet panel), R2.25 (harness hooks that report what an agent is about to do through `reef presence report`), R2.26 (a provider-created workspace kept alive with `reef ws renew`), R3.36 (declared `EDITING` entries beside the daemon's observed ones)

## Context

R2.10 built the presence channel and made the daemon report what only it knows: lease heartbeats, files snapshots change, and the progress of creates and store builds. Every entry today is a daemon entry. Nothing reports what an agent is doing: `reef ws run` heartbeats its lease but says nothing about the command it runs, `reef mcp` heartbeats the workspaces it creates but says nothing about the calls it serves, and an agent or a harness hook that wants to say "running the tests" or "about to edit `src/parser.rs`" has the RPC but no command.

This ticket adds the client side. `ws run` reports one `ACTIVITY` entry for the life of its command. `reef mcp` reports one `ACTIVITY` entry per workspace it is called for, naming the tool. `reef presence report` and `reef presence clear` let any process report an entry of its own, including one that outlives the process. `reef ws renew` renews a lease held outside `ws run`. The cadence and the rules of reporting are written down once, as a contract that the Rust reporter implements and that the Python and TypeScript SDKs (R2.06, R2.07) follow when they are written.

No daemon code changes, and the API does not change: R2.10's RPCs and the existing `RenewLease` carry everything here. The proto gains comments only.

### Daemon and API

- **No daemon code.** Everything here is a client of R2.10's RPCs and the existing `RenewLease`. The daemon's handling of a report that races a release (`PresenceError::Ended`), of ids after a restart (`PRESENCE_NOT_FOUND`) and of the caps is already what clients need.
- **No API revision.** `API_REVISION` stays 5. The only proto edit is a comment on `ReportPresence` stating the reporting contract (below), which does not move the digest.

### The reporting contract

What every client that reports for a process follows: `ws run`, `reef mcp`, and later the SDKs' workspace helpers.

1. **One entry per process and subject.** A process reports one entry for each workspace (or repository) it is active in, and keeps its id. It never reports a second entry for the same subject while it holds one.
2. **Replace by id, at most once a second.** A change of what the entry says replaces it by id; changes within a second of the last report are folded into one report of the latest state at the end of that second.
3. **Never let a live entry lapse.** While the activity lasts, the reporter replaces the entry before its TTL runs out. A long-lived reporter (`ws run`) replaces it every 10 seconds with a TTL of 30 seconds (the daemon's default), so a reporter that dies leaves an entry that ends `EXPIRED` within 30 seconds. A reporter for activity that comes in bursts (`reef mcp`) does not refresh: each burst replaces the entry with a TTL of 60 seconds, so the entry lapsing is itself the signal that the agent has gone quiet.
4. **Re-report on `PRESENCE_NOT_FOUND`.** An id the daemon no longer knows (expired while the daemon was unreachable, or from before a restart) is dropped, and the same state is reported again without an id; the new id replaces the old one.
5. **Clear at exit.** When the process ends normally, it clears each entry it holds, waiting at most 2 seconds in all; a daemon that does not answer is not waited for (the TTL ends the entry).
6. **Presence never fails the work.** A failed report or clear is logged at `debug` and retried at the next refresh; it is never printed to the agent's terminal or returned as the command's error. A report refused because its subject is gone (`FAILED_PRECONDITION` for a workspace that is not active, `ManagerError::NotActive` or `PresenceError::Ended`, both kind `Conflict`, `workspace/mod.rs:602`; or `WORKSPACE_NOT_FOUND`, `REPOSITORY_NOT_FOUND`) or as unsupported stops that reporter for good.
7. **The agent.** `agent` is the name the client sends as `reef-agent` (`--agent` or `REEF_AGENT`), else the owner of the workspace the entry names, else the client's own default (`<user>@<host>` for the CLI, `<user>@<host>:mcp` for the MCP server).

Rule 7 departs from R2.10's "else `default_owner()`": falling back to the workspace's owner makes a `ws run` without an agent name report under the same name as the daemon's `LEASE` and `EDITING` entries for its workspace, so one workspace's entries agree whenever no name was given.

The `ReportPresence` comment gains, as its second paragraph: "A client reporting for a process it runs keeps one entry per subject: it replaces it by id at most once a second and before its TTL runs out while the activity lasts, reports it again without `presence_id` on PRESENCE_NOT_FOUND, and clears it when the process ends. `agent` is the name the client sends as `reef-agent`, else the owner of the workspace the entry names."

### The reporter

`reef_client::presence` (new module), so the Rust client library carries the reference implementation of the contract, as the SDKs will:

- **`PresenceApi`**, a trait with `report_presence(ReportPresenceRequest)` and `clear_presence(&str)`, implemented for `Client`, as `WorkspacesApi` is for the heartbeater (`lib.rs:1153`), so the reporter's tests run against a fake.
- **`Reporter::start(api: Arc<dyn PresenceApi>, subject: Subject, cadence: Cadence) -> Reporter`**, where `Subject { agent, repo, workspace, kind }` holds the fixed fields (the ones `PRESENCE_MISMATCH` checks) and `Cadence` is `Refresh { every: 10 s, ttl: 30 s }` or `Burst { ttl: 60 s }`. It spawns one task; nothing is sent until the first `set`.
- **`set(state)`**, where `state` is the entry's variable part (`change`, `activity`, `paths` or `progress`; `change` may differ between replacements, so a moved workspace's next call reports its new change): stores it and wakes the task, which sends it at once if the last report was a second or more ago, else at that second's end. With `Refresh`, the task also replaces the entry every `every` with the last state.
- **`clear(self)`**: stops the task and clears the entry if one is held, within 2 seconds.
- **`is_live()`**: whether it holds an entry it has not seen lapse (last report plus TTL is in the future); the MCP map uses it to drop idle reporters.
- Errors per rules 4 and 6. A daemon that is unreachable leaves the id held; the next tick tries again, and the daemon's answer (`PRESENCE_NOT_FOUND` if the entry lapsed meanwhile) decides what happens. `TOO_MANY_PRESENCE_ENTRIES` is retried at the next refresh (`Refresh`) or dropped until the next `set` (`Burst`).

### `ws run`

- **After the command is spawned** (so a command that cannot be started reports nothing), `ws run` starts a `Refresh` reporter for kind `ACTIVITY`, `workspace` the workspace's id, and sets `activity` to `running <command line>`, the command line cut as the default purpose is (`purpose_of`, 200 characters). It sets no `change`: the agent may `reef ws move` the workspace while it runs, and the daemon's `LEASE` entry carries the workspace's current change with every heartbeat.
- **Agent**: `ctx.agent`, else the workspace's owner (`<user>@<host>:<pid>`, or `--owner`'s, or for `--workspace`, the attached workspace's).
- **When the command exits**, before `finish`: `clear`, so the entry ends `CLEARED` (the command finished) before the release ends the daemon's entries `GONE`. The same with `--keep`: the workspace stays, but nothing runs in it. A `ws run` that is killed leaves the entry to expire within 30 seconds.
- The reporter never prints to stderr, which belongs to the agent's terminal.

**Open question 1 of R2.10, answered: no, `ws run` does not pass `REEF_AGENT` as the workspace's owner.** The owner is the lease holder, a process: the attach rule reads `<user>@<host>` from it (`may_attach`), `ws list --owner` and `reef mcp`'s heartbeats (`leases.rs:36`) compare it exactly, and several processes routinely share one agent name (a harness's sub-agents, two terminals). Making it the agent name would break attaching without `--owner` and make two holders indistinguishable. The agent and the workspace meet in the `ACTIVITY` entry instead, which carries both: a view that wants every entry of one agent takes that agent's entries and then every entry of their workspaces (R2.20 renders per workspace from `ListWorkspaces` anyway). Without an agent name, rule 7 makes all of a workspace's entries name its owner.

### The MCP server

- **Every tool call that resolves a scope reports.** `Call` gains `tool: &'static str`; `Call::scope`, after resolving (`mod.rs:136` to `:145`), calls `server.presence.called(ctx, tool, &scope)`. A call that fails to resolve its scope reports nothing; `list_repositories` reports nothing.
- **One entry per subject**: `mcp/presence.rs` (new) holds a map from `(repo_id, workspace_id or none)` to a `Burst` reporter of kind `ACTIVITY`, `activity` the tool's name (`edit_files`, `wait_for_operations`), `change` the workspace's current change when there is a workspace (it is looked up for the call, so it is current). Its agent is `ctx.agent`, else the workspace's owner, else the server's owner name (`<user>@<host>:mcp`, `Leases::owner`). Reporters that are no longer `is_live` are dropped from the map when the next call arrives, so the map is bounded by the subjects of the last minute; the per-agent cap (32) bounds it on the daemon's side, and a refused report is dropped.
- **At exit**, `serve` clears every held entry, in parallel, within 2 seconds in all, after the service stops and before it returns. The map is an `Arc` shared between the server and `serve`.
- **No tool**, and `tools/list` does not change (19,983 bytes). `NOT_TOOLS`' two rows become: `ReportPresence` "the server reports its calls' activity itself", `ClearPresence` "the server clears its entries at exit". No other row changes.

### `reef presence report`

```
reef presence report [TEXT] [--path PATH]... [--phase NAME] [--done N] [--total N] [--unit UNIT]
                     [--workspace WS | --repo REPO] [--ttl DURATION] [--id ID | --id-file FILE]
```

- **About**: "Report what you are doing, for `presence watch` (prints the entry's id)". `after_help`: `Example: reef presence report --id-file .reef-presence "running the tests"`.
- **The kind follows from what is given**: `TEXT` is `activity`; `--path` (repeatable) is `editing`; `--phase` or `--done` (with `--total` and `--unit` optional) is `progress`. Exactly one of the three is required; mixing them, `--total` or `--unit` without `--phase` or `--done`, or none is a usage error (exit 2) naming the three forms. There is no `--kind` flag: `lease` cannot be reported, and the forms do not overlap.
- **Scope**: R2.27's rule (`scope::resolve`): `--workspace`, else `--repo` (no workspace), else `REEF_WORKSPACE`, else the current directory's workspace, else its repository. Outside every repository it fails as every scoped command does. `change` is the workspace's change at the time of the report when there is a workspace, else unset. `--path` values are relative to the current directory inside the scope, or absolute inside it (`scope::given_paths`), and sent repository-relative.
- **Agent**: rule 7, with `<user>@<host>` last.
- **TTL**: `--ttl` (humantime) as given, unset for the daemon's 30 seconds; the daemon clamps it to 1 second through 10 minutes, and the printed `expires_at` is what holds. `--ttl 0s` is the default, as the RPC reads zero.
- **How an entry outlives the process.** The entry lives in the daemon until its TTL runs out, it is cleared, or the daemon stops; the process that reported it may exit at once. Its id is the capability to change it: the command prints it, and a later process passes it back with `--id` to replace the entry (re-arming its TTL) or to `presence clear` to end it. To keep an entry alive across a task longer than 10 minutes, report it again with `--id` before it lapses; one that lapsed meanwhile is reported anew (below).
- **`--id ID`** replaces the entry `ID`. If the daemon answers `PRESENCE_NOT_FOUND`, the same report is sent without an id and the new entry is printed, with a note on stderr: `reef: presence entry <old> had ended; reported a new one, <new>`. Other refusals (`PRESENCE_MISMATCH`, `DAEMON_PRESENCE`, `INVALID_PRESENCE_ID`) are the command's error.
- **`--id-file FILE`** is `--id` for callers that are separate processes with nowhere to keep a variable, such as a harness's pre- and post-tool hooks: if `FILE` exists and holds an id (surrounding whitespace ignored), the report replaces that entry as `--id` would; an empty or missing file reports a new entry. After a successful report the entry's id and a newline are written to `FILE` (to a temporary file beside it, then renamed). A file the command cannot read is an I/O error (exit 8) before anything is reported, since reporting a new entry would leak the one the file names; a file it cannot write is an I/O error after the report succeeded, so the entry exists either way. The caller chooses the path, so a sandboxed agent can keep it in its workspace (it is a plain file there and would be snapshotted, so the example uses a dot-file the caller can ignore).
- **Output**: `-o json` prints the entry as stored, the same object as `presence watch`'s `presence` (`json::Presence`): `{"id", "agent", "repo_id", "workspace_id", "change_id", "kind", "activity", "paths", "progress": {"phase", "done", "total", "unit"} | null, "lease": null, "by_daemon": false, "updated_at", "expires_at"}`. Text prints the id alone and a newline, so `id=$(reef presence report -o text "running the tests")` works as `ws create -o text` prints a path.
- **Errors** are the daemon's, with two refined in `cli/advice.rs`: `TOO_MANY_PRESENCE_ENTRIES` gets "Replace your entry instead of reporting a new one: pass --id with the id a report printed, or the same --id-file each time; reef presence clear ends one." with no `next`; `PRESENCE_TOO_LARGE` keeps the daemon's hint. `INVALID_AGENT` is caught by `Global::agent` before any call. `FAILED_PRECONDITION` for a released workspace keeps the daemon's advice.

### `reef presence clear`

```
reef presence clear [ID]... [--id-file FILE]
```

- **About**: "End presence entries you reported". At least one `ID` or `--id-file`; neither is a usage error.
- Clears each id in turn (`ClearPresence`). With `--id-file`, clears the id the file holds, then removes the file; a missing or empty file clears nothing and succeeds. Clearing an id that names no live entry succeeds, as the RPC does.
- **Output**: `-o json` prints `{"cleared": ["<id>", ...]}`, every id given, in order (cleared or already gone); text prints nothing on stdout and `cleared <id>` per id on stderr (`Out::done`), or `nothing to clear`.
- **Errors**: `INVALID_PRESENCE_ID` (exit 2) and `DAEMON_PRESENCE` (exit 2) from the daemon, with its hints; the first error stops the command, after the ids before it were cleared.

### `reef ws renew`

```
reef ws renew [WS] [--lease-id ID]
```

- **About**: "Renew a workspace's lease: what `ws run` does while its command runs". `after_help`: `Example: reef ws renew   # inside the workspace`.
- **By workspace**, not by lease: `WS` is an id, unique prefix or path inside it, defaulting to the workspace you are in (`scope::implicit_workspace`, as `ws snapshot`); outside every workspace without `WS` it is `WORKSPACE_REQUIRED` with `ws snapshot`'s advice (`next` `reef ws list`). The command looks the workspace up (`GetWorkspace`, no snapshot) and renews its current lease. `--lease-id ID` renews that lease instead and fails if it is not the current one: for a holder that kept the id it was given and wants to know it still holds the lease.
- **No owner check.** Renewing does not take a workspace over (it is not `ws run --workspace`), and the daemon checks none (one uid is one trust domain, ADR 0027). Renewing someone else's workspace only keeps it from being reclaimed.
- **No `--lease`.** A renewal extends a lease by its own length, set at create (`ws create --lease`); `RenewLeaseRequest` has no length field, and adding one is an API change this ticket does not make (open question 2).
- **Output**: `-o json` prints `{"workspace_id": "<id>", "lease": <json::Lease>}`; text prints nothing on stdout and, on stderr, `renewed lease <lease id> of <workspace id>: 30m left, heartbeat every 1m` (`render::lease_text` and the heartbeat interval, as `reef here` writes them).
- **Errors** are the daemon's: `WORKSPACE_NOT_FOUND` (exit 3); a released or reclaimed workspace, or a lease past its grace, `conflict` (exit 5) with `next` `reef ws create --repo <id>`; a lease that is not the current one, `conflict` with no `next`; during a quiesce, `unavailable` (exit 6).
- **One renewal**: a holder outside `ws run` runs it again before the lease runs out (`heartbeat_every` is the cadence `ws run` uses). A long-running renewer is open question 2.

`reef here` uses it: an active workspace whose lease is `in_grace`, outside `ws run`, gets the hint "Its lease ran out; renew it to keep working here, or release it. It is reclaimed when the grace period ends." and `next` `reef ws renew <id>` (instead of `reef ws release <id>`). Every other case is unchanged.

## Implementation notes

- **Order**: the reporter and its unit tests (1 to 7); `ws run` (8); `presence report` and `clear` (9 to 12); `ws renew` and `reef here` (13, 14); the MCP server (15); the proto comment, `NOT_TOOLS`, the CLI tests (16); docs.
- **The reporter's task** selects on a `Notify` (a new `set`), a sleep until the next refresh or the end of the coalescing second, and a `CancellationToken` (`clear`). It never awaits while holding the state lock. Each request gets the heartbeater's 5-second deadline (`HEARTBEAT_DEADLINE`, `cli/heartbeat.rs:15`), moved into `reef-client` beside it or duplicated.
- **`clear` in `ws run`** runs after `supervise` returns and before `finish`, in both the spawned and the `--keep` paths; it is awaited (at most 2 s), so the `CLEARED` end is published before the release's `GONE`.
- **The MCP clear at exit** must happen after `service.waiting()` returns and on the signal paths (`mod.rs:255` to `:262`); with stdout closed by then, it logs nothing on stdout.
- **`--id-file` writes** with `tempfile::NamedTempFile::new_in(parent)` and `persist`, so a reader never sees half an id.
- **Linux**: nothing is `cfg(target_os = "linux")`; still run the clippy pass in the privileged `ubuntu:24.04` container before pushing, since `Call` changes shape under every tool.

## Known limits

- **Daemon entries still name the owner.** With an agent name set, a workspace's `LEASE` and `EDITING` entries name its owner while `ws run`'s and `reef mcp`'s entries name the agent; `presence watch --by <agent>` shows only the latter. A view joins them by `workspace_id` (above).
- **The activity is the command line**, as the default purpose already is, so arguments (a token passed on the command line) are visible to every presence subscriber on the socket. That is the same exposure the workspace's `purpose` has today; R2.08's remote listener must treat presence as it treats `ListWorkspaces`.
- **`reef mcp`'s activity is the tool's name only**, not its arguments, and lapses 60 seconds after the last call even while the model is still thinking.
- **One-shot reports default to 30 seconds.** A caller reporting a long task without `--ttl` or a refresh sees its entry lapse; the TTL is printed so it can tell.
- **A `ws run` killed with `SIGKILL`** leaves its entry for up to 30 seconds and its lease entry for up to two heartbeats.

## What later tickets inherit

- **R2.06 and R2.07** follow the reporting contract in `ReportPresence`'s comment: a workspace helper that holds a workspace for a block of code (the equivalent of `ws run`) reports one `ACTIVITY` entry for it with the `Refresh` cadence (10 s, TTL 30 s) and clears it when the block exits; the agent rule is rule 7, with `<user>@<host>` last; `reef_client::presence::Reporter` is the reference implementation, and its unit tests 1 to 6 are the behaviors to port.
- **R2.20** reads each agent's activity per workspace from client `ACTIVITY` entries and joins daemon entries to agents by `workspace_id`; an `ACTIVITY` entry ending `cleared` is a command that finished, `expired` one whose reporter died.
- **R2.25**'s hooks report declared intent with `reef presence report --id-file <file> --path <file>` before an edit and `reef presence clear --id-file <file>` after, and the current tool call as an activity the same way.
- **R2.26**'s provider contract keeps a workspace it hands out alive with `reef ws renew`, or with a `ws run`-style heartbeat if open question 2 adds one.
- **R3.36** tells declared edits (client `EDITING`, `by_daemon: false`) from observed ones.

## Open questions

1. Should the MCP server's fallback agent be the MCP client's name from `initialize` (`clientInfo.name`, such as `claude-code`) rather than `<user>@<host>:mcp`? It would name the harness without any configuration, but two sessions of one harness would share it.
2. Should `RenewLeaseRequest` gain a length, so `reef ws renew --lease 2h` extends a lease by more than its own length, and should `ws renew --follow` keep renewing until interrupted (the heartbeater, for holders that have no `ws run`)? Both are small; the first is an API change, and R2.26 is the first ticket that would need either.
3. Should `reef mcp` report `EDITING` entries for `edit_files`' paths (declared intent, which R3.36 wants), here or in R2.25? It is a second entry per workspace and a few hundred lines of tests.
4. Is the command line acceptable as `ws run`'s activity (see "Known limits"), or should it show only the program name and its first argument?
5. Should the CLI's one-shot default be longer than the daemon's 30 seconds (five minutes, say), trading a stale entry after a crash for fewer lapsed ones?
