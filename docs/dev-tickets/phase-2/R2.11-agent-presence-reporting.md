# R2.11 Agent presence reporting

Phase 2 · Size S · Depends on: R2.10 (`Presence.Report`, the table, `Workspace.presence`), R2.06 and R2.07 (the SDK workspace handles that report), R2.05 (the CLI over `reef-api`), R1.21 (`ws run`) · Unblocks: R2.20 (the fleet panel has something to show for every agent), R2.13 (the MCP server's `EDITING` reports implement the interface fixed here)

## Context

R2.10 built the channel; this ticket makes agents use it without being asked. The design wants the fleet panel to show "each agent with its workspace, current change, lease health, and presence", and the map to warn when two agents work in the same area, which only works if presence is reported by default by everything that runs an agent: `reef ws run`, the SDKs' workspace handles, and the MCP server. An agent that wants to say more than "running" gets a CLI for it.

### What was verified while writing this ticket

Reef at `d156d1e`.

- **`ws run`'s shape.** `cli/ws_run.rs:170-233` (`run`): create or attach, `prepare` (`:239-244`) builds the `Heartbeater` and installs `Signals`, `spawn` runs the child, `heartbeats(heartbeater)` is a `tokio::spawn`ed loop aborted when `supervise` returns (`:184-189`), then `finish` snapshots or releases (`:435-480`). The `Heartbeater` (`:533-646`) renews on `heartbeat_every` with backoff while the daemon is unreachable and reports a lease that cannot be renewed once. The child's environment carries `REEF_WORKSPACE`, `REEF_WORKSPACE_PATH`, `REEF_REPO`, `REEF_SOCKET` (`cli/env.rs:10`, R1.21). The owner `ws run` sends is `<user>@<host>:<pid>` (`client::default_owner`, R1.21).
- **`attach`** (`:285-316`) joins an existing workspace by id with `--workspace`, heartbeating once to prove the lease; `may_attach` (`:317`) checks the owner.
- **tonic client streaming from the client side**: `PresenceClient::report(impl IntoStreamingRequest)`; `tokio_stream::wrappers::ReceiverStream` over an `mpsc::Receiver<PresenceUpdate>` is the usual sender half, and dropping the sender half-closes the stream (how the daemon learns the client is done, R2.10's verification of `Streaming::message`).
- **R2.10's interface**: one `Report` stream per client lifetime; an update whenever activity changes and at least every `ttl / 2`; `agent` fixed per stream; `workspace_id` optional; the daemon fills `repo` and `change_id` from the workspace row.
- **The CLI contract** (ADR 0025): never interactive, `hint`/`next`, JSON on a pipe, one object or array (or, for streams, one object per line as `reef watch` prints, R2.09).

## Decisions

- **`ws run` reports presence for the child's lifetime.** Beside the heartbeater, `run` opens one `Presence.Report` stream (`Presenter`, in `cli/ws_run.rs`) with `agent` = the owner string it sent at create (`<user>@<host>:<pid>` of `ws run` itself, so the fleet panel's agent is the process a human would `kill`), `workspace_id` = the workspace, and sends: `RUNNING` with `detail = <argv[0] basename> (pid <child pid>)` once the child is spawned; a keepalive repeat of the same update every `min(ttl / 2, heartbeat_every)` (the client reads `Daemon.Status.presence_ttl`, a new field, once at start; `heartbeat_every` from the lease); `IDLE` with `detail = "exited <code>"` when the child exits and `--keep` was given (the workspace stays, idle); nothing when the workspace is released (the stream ends and the daemon clears). The stream ends when `run` returns. A `Report` failure never affects the child: it is logged once on stderr as `reef: presence unavailable: <reason>` and retried with the heartbeater's backoff; `--no-presence` turns it off.
- **Finer activity from inside the command.** `reef presence report [--workspace <id>] --activity <idle|editing|running|testing|waiting|<custom>> [--detail <text>] [--progress <done>/<total>] [--agent <str>] [--hold]`: without `--hold`, opens a stream, sends one update and exits 0 at once; the entry then lives for the TTL (the stream's end does not clear it when `--hold` is absent: see the `oneshot` flag below). With `--hold`, keeps the stream open and re-sends every `ttl / 2` until stdin closes or a signal arrives, for `cargo test & reef presence report --activity testing --hold`-style use. `--workspace` defaults to `REEF_WORKSPACE`, else the workspace containing the cwd (`reef here`'s resolution), else none (an agent with no workspace). `--agent` defaults to `REEF_AGENT` if set (so a `ws run` child's reports share the parent's agent string: `ws run` exports `REEF_AGENT=<owner>`), else `<user>@<host>:<pid>`.
- **A keepalive refreshes, never overwrites.** `PresenceUpdate` gains `keepalive: bool`. `ws run`'s repeats and the SDKs' timers send `keepalive = true`; the daemon (R2.10's `Table::report`) extends the entry's `expires` and `updated` and changes nothing else, so a finer report from inside the command (the child's `testing`) is what `(agent, workspace)` shows until it expires or the child changes it, and the parent's `running` does not flicker back every `ttl / 2`. A keepalive for a key with no entry creates it with the update's fields (the first report, or one after a TTL expiry).
- **`oneshot` in the protocol.** `PresenceUpdate` gains `oneshot: bool`: an update with `oneshot = true` is kept until its TTL even after the reporting stream ends (R2.10's `end_stream` skips entries marked oneshot). Without it `reef presence report` would clear its own entry on exit, which makes the command useless. The TTL still bounds it. R2.10's `Table::report` records the flag per entry.
- **`reef presence watch [--repo] [--workspace]... [--agent]... [--since-table]`**: `Presence.Subscribe` printed as `reef watch` prints frames (text: `<time> <agent> <workspace-short> <activity> <detail>` per update, `cleared` for a clear; JSON: one `Frame` per line); the first frame (the table) prints too. `reef presence list [--repo] [--workspace]` prints the current table once (the first frame, then exit): an `activity` table in text, an array in JSON. `presence` is a new noun with `ls` as `list`'s alias; `reef presence` alone is `list`.
- **The SDK interface** (implemented by R2.06 and R2.07, specified here so the three reporters agree): a `Client` holds at most one presence stream, opened lazily by the first report; `client.presence.report(activity, detail=None, workspace=None, progress=None)` sends one update (`oneshot = false`: the stream lives with the client); `client.presence.clear(workspace=None)` sends `IDLE`; the workspace handle (`with client.workspace(...) as ws`, `await using ws`) reports `RUNNING` with `detail = "<sdk> <program name>"` on enter, `IDLE` on exit before release, and offers `ws.presence(activity, detail)` for finer reporting; a keepalive timer repeats the last update every `ttl / 2` while the stream is open; closing the client ends the stream. The agent string is the SDK's `default_owner` (`<user>@<host>:<pid>`) unless `REEF_AGENT` is set. `client.presence.subscribe(filter)` yields frames.
- **The MCP server's reports** (implemented by R2.13): the server opens one stream with `agent = REEF_AGENT` else `mcp:<harness pid or "stdio">:<pid>`; around `reef_tree_apply` it reports `EDITING` with `detail = <path>` for the workspace or change the call names and `IDLE` after; around `reef_ws_create` it reports `RUNNING` with `detail = "mcp"` for the new workspace until `reef_ws_release`; `reef_wait` reports `WAITING` with `detail = <what it waits for>` for its duration.
- **No ADR**: the channel's ADR (0032) gets one paragraph under consequences naming the three reporters and `REEF_AGENT`; the `oneshot` and `keepalive` flags are recorded there.

2. `ws_run_keep_reports_idle`: `reef ws run --keep -- true`; after exit the entry is `idle` with `detail == "exited 0"` and stays until the TTL (`[presence] ttl = "2s"` in the daemon's config: gone after 3 s).
3. `child_inherits_the_agent`: `reef ws run -- sh -c 'reef presence report --activity testing --detail unit; reef presence list -o json; sleep 2; reef presence list -o json'` with `[presence] ttl = "1s"`: both lists printed by the child have one entry for the workspace whose `agent` is the workspace's owner (`REEF_AGENT` was exported, so the two reporters share the key); the first shows `testing` (the child's oneshot report took the entry over), the second, after the oneshot expired and a keepalive from `ws run` recreated it, `running`; a keepalive sent while `testing` was live did not change it (asserted by a list in between).
4. `oneshot_report_outlives_its_process`: `reef presence report --workspace <id> --activity waiting --detail review` exits 0 at once; `reef presence list` shows it for the TTL; `--hold` with stdin closed exits at once too (never interactive) and `--hold` with stdin open keeps re-sending (observed as `updated` advancing in `Inspect`) until SIGTERM, then the entry clears within a frame.
5. `no_presence_flag` : `reef ws run --no-presence -- sleep 2` creates no entry; the daemon's `Daemon.Status.presence_entries` stays 0 during the run.
6. `presence_unavailable_does_not_stop_the_child`: with `[presence] max_entries = 0` in the daemon (every report refused), `reef ws run -- sh -c 'echo ok'` exits 0, prints `ok`, and prints one `reef: presence unavailable` line on stderr.
7. `presence_watch_prints_frames` (`cli.rs`): `reef presence watch --once -o json` prints the table frame as one JSON object; text mode prints one line per entry; `reef presence` alone equals `reef presence list`.
8. `every_command_completes_with_stdin_closed` (existing, extended): `presence report --hold`, `presence watch --once`, `presence list` run with stdin closed and exit.
9. SDK tests (in R2.06's and R2.07's suites, specified here): entering a workspace handle creates a `running` entry whose `detail` starts with the SDK's name; `ws.presence("testing", "pytest")` updates it; leaving the handle clears it (the stream ends with the client, or `IDLE` then release); `REEF_AGENT` set in the environment is the entry's `agent`.

## Implementation notes

- The presence stream and the heartbeater are independent tasks aborted at the same point; neither waits for the other. A failed `Report` connect is retried on the heartbeater's backoff schedule (reuse `Backoff`), and a successful reconnect re-sends `last`.
- `Daemon.Status` is fetched by `ws run`'s autostart path already; read `presence_ttl` there and default to 30 s if unset, so a 0.1.x daemon still works with a 0.2 CLI during an upgrade.
- `reef presence report` without `--hold` must not wait for the daemon to process the stream's end; send the update, await the `ReportResponse` only up to `--timeout`, exit 0.
- `--progress 3/10` parses as two integers; `--activity` accepts the five names and anything else as `CUSTOM` with the text in `detail` when `--detail` is absent.
- The text table for `presence list` reuses `render.rs`'s `table` and relative times (`updated 4s ago`).

## Risks

- **Two reporters on one key.** `ws run` and its child share `(agent, workspace)` through `REEF_AGENT`, and the key holds one entry. The keepalive rule keeps the child's finer report visible, but a child that reports `testing` once and never clears it leaves `testing` showing until the TTL, with `running` returning only after that. That is the TTL doing its job; `docs/api.md` says a reporter that changes activity should also report the change back, and the SDK handles do. The alternative, a separate key per reporter (`agent` plus pid), would show two rows per `ws run` in the fleet panel, which the design's "each agent with its workspace" does not want.
- **`REEF_AGENT` leaks across nested `ws run`s.** A `ws run` inside a `ws run` gets its parent's agent string unless it sets its own; `ws run` always sets `REEF_AGENT` to its own owner for its child, which is the right scoping.
- **Keepalive traffic.** 200 `ws run`s re-sending every 15 s is 13 updates a second across the daemon, each a broker publish to presence subscribers; R2.22's presence subscribers see this load.
