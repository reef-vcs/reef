# R2.19 Smartlog view

Phase 2 · Size M · Depends on: R2.18 (the shell, the data layer, the Playwright harness, `docs/ui.md`), R2.02 (`Changes.Log` with `revset`, `Change`, `Operations.Get`), R2.09 (`Operations.Subscribe` frames with `Operation.changes`) · Unblocks: the web UI exit criterion (with R2.20 and R2.21); R2.21's replay mode renders this view at a past `seq`; R3.31 (the proposal view opens from a node here)

## Context

The smartlog is the first of the design's five live views: "stacks and changes as a graph, updating as agents snapshot, propose, and land; the shape of work in flight at a glance" (`docs/design.md`, "Live by default"). Sapling's Interactive Smartlog is the model the design names. In Phase 2 the graph shows jj changes and their parents: every visible head and its ancestors down to the nearest bookmark (the `reef_log()` default revset R2.02 defines), each node colored by its state, with the Reef workspace sitting on it and the owner behind that workspace. Agents never see this page; it exists so a human can tell in one look which agent is where and what is divergent or conflicted.

This ticket adds the `/` route to R2.18's shell: the graph layout, the node, live updates that respect "nothing reorders under your cursor", the revset input, and the click-through to an operation and a workspace. R2.21 later renders the same component in replay mode from `Operations.Replay`'s `changes`, so the component takes its rows as a prop and does not fetch for itself.

### What was verified while writing this ticket

Reef at `d156d1e`; the Phase 2 README's API decisions; jj-core 0.46.0 (vendored).

- **`Change` carries what a node needs** (README, "Change references"): `change_id`, `commit_id`, `description`, `author`, `parents: repeated ChangeRef`, `bookmarks`, `divergent`, `conflicted`, `empty`, `workspaces` (Reef workspace ids on the commit, `default` for the user's checkout), `is_working_copy`, and `edges: repeated GraphEdge { target, kind: DIRECT | INDIRECT | MISSING }` when `Changes.Log` is asked `with_graph`. The owner is not on `Change`; it comes from `Workspaces.List` (`Workspace.owner`), joined client-side by workspace id. `Changes.Log` returns a `Page`; the default revset is bounded to 200 commits (README, "Revisions").
- **Parents outside the page are the graph's edge case.** `Change.parents` names every parent; a parent not in the returned set (below the bookmark cut, or past the 200-commit limit) has no row. jj-core's own graph model (`jj-core-0.46.0/src/graph.rs:33-85`) distinguishes `GraphEdge::direct`, `indirect` (an ancestor elided by the revset) and `missing` (outside the set) for exactly this; `TopoGroupedGraph` (`:133-346`) is jj's topological grouping. R2.01's `Change.edges` carries those kinds when `with_graph` is set (accepted; see the end), so the view asks for the graph, draws a `MISSING` target as a dangling stub and an `INDIRECT` edge as an elision mark, and falls back to `parents` as stubs when `edges` is empty.
- **`Operation.changes`** (README, "Operations") lists the `ChangeRef`s whose head or working-copy commit an operation moved, so a frame says which nodes it touched without the client diffing two logs.
- **The data layer** (R2.18): `useLive(query, deps)` refetches on `stale`; `useEvents(selector)` reads the event ring; frames are applied once per animation frame; `Held` is the shared "N new" badge.
- **Rendering**: an inline SVG per graph column beside an HTML row per change keeps text selectable and accessible (rows are `<li>` elements with headings; the SVG is `aria-hidden`), which a canvas renderer would not give. No graph library: the lane algorithm below is about 80 lines and jj, Sapling and `git log --graph` all use its shape. Checked that `react-router` 8's `useSearchParams` (for `?revset=`) and `Link` are in its library mode (`react-router` package, no framework mode).

## Decisions

- **Rows, not a canvas.** `ui/src/views/Smartlog.tsx` renders `<ol class="smartlog">` with one `<li>` per change in the order `Changes.Log` returned (newest first, topologically grouped by the daemon as jj's log is; the client does not reorder). Each row is a fixed 44 px tall so the graph column's SVG, drawn once for the whole list, lines up by row index. Virtualization is not needed at 200 rows; a `--limit` beyond that is R2.02's CLI, not this page.
- **Lane assignment, client-side.** `ui/src/views/smartlog/layout.ts`: `layout(changes: Change[]): Laid[]` walks the rows top to bottom with a list of active lanes (each lane holds the commit id it is waiting for). For each row: if some lane waits for this commit, the node takes the leftmost such lane and the other lanes waiting for it merge into it (their edges curve in); otherwise the node opens a new lane at the right. Then the node's lane is reassigned to its first edge's target, and each further edge gets a new lane (a fork curves out). An `indirect` edge is drawn dashed with a small ellipsis mark at its midpoint, so the eye sees "commits elided here"; a target with no row in the set (`missing`) keeps a lane for one more row and ends in a short stub with a hollow end, so the eye sees "continues below the cut". Output per row: `{ change, column, edges: { from: column, to: column, kind: "direct" | "indirect" | "missing" }[] }`. The SVG is `columns × 16 px` wide; nodes are 10 px circles filled with the state color, with the state glyph (R2.18's `StateDot`) at 8 px inside; edges are cubic curves between row centers. Pure function, unit-tested against hand-drawn cases (linear, fork, merge, two roots, a missing parent, an elided stack).
- **Node content**, left to right after the graph column: the change id in jj's reverse-hex short form (8 characters, `title` with the full hex; R1.05's helper is mirrored in `ui/src/data/ids.ts`), the first line of the description (or `(no description)` muted), the bookmarks as small pills, then the right-hand cluster: the workspace marks (one per `Change.workspaces` entry: a chip with the workspace id's first 4 characters and the owner from `Workspaces.List`, `default` shown as `you`), a `divergent` mark (two overlapping circles) and a `conflicted` mark (a `C` in the conflicted color) when set, and `empty` rendered as a hollow node. The working-copy commits (`is_working_copy`) have a thicker ring. State comes from R2.18's `stateOf(change)`.
- **Live updates that hold position.** The view subscribes through the store and reacts to frames whose events carry `Operation.changes`. Three cases:
  1. An event touching a change already in the list (a snapshot moved its commit, a describe changed its text, a conflict appeared): the row updates in place. The state dot transitions color over 200 ms only when the state name changed (the "motion only for state change" rule); text changes do not animate.
  2. An event introducing a change not in the list (a new workspace's new change, an external `jj new`): the view refetches `Changes.Log` (debounced 250 ms, one request per burst) and diffs the result against the current rows by change id. New rows and any reordering of existing rows are **held**: the current list stays as it is, and R2.18's `Held` badge at the top of the list says `3 new changes`. Clicking it, pressing `r`, or scrolling to the top when the badge has been visible for more than two seconds applies the held result in one render. Held results replace one another; only the latest fetch is kept.
  3. An event removing a change (abandon, squash, a workspace released with an empty commit): the row is kept until the next held result is applied, marked with a muted strike so a reader following it does not lose it under the cursor; the badge then says `3 new, 1 gone`.
  The rule in `docs/ui.md` form: existing rows never move or vanish while the user has not accepted; new state is applied to rows that stay. The replay mode (R2.21) bypasses holding: a scrub is the user asking for a different list.
- **Revset input.** A text field above the list, empty by default (the daemon's `reef_log()`), bound to `?revset=` in the URL so a view is shareable; on Enter it refetches with that revset. A parse error from the daemon (`INVALID_ARGUMENT` with jj's message in `ErrorDetail.chain`) shows under the field, the previous list stays. Three preset buttons: `default`, `mine` (`author(<identity email>)`... not available in Phase 2 without R3.03, so: `workspaces` = commits with a Reef workspace on them, expressed as the revset R2.02 documents for it), `all heads` (`heads(all())`). The presets are the only revsets the UI writes; it never composes revsets from user data.
- **Click-through.** Clicking a row expands it in place (no navigation, nothing moves above it) into a details panel: the full description, author and time, the full ids, the parents as links (which scroll to and highlight the parent row), the workspaces on it as links to `/workspaces?ws=<id>` (R2.20 highlights the row), and the last operation that touched the change: `Operations.Get` of the newest indexed operation whose `changes` names it (R2.09's index; the client asks `Operations.Log { changes: [id], page_size: 1 }`), rendered as `<kind> by <username>@<hostname>, 12 s ago, op <short>` with a link to `/activity?op=<id>` (R2.21 scrolls to it). This is the "every live element links to its cause" rule. Escape or a second click collapses.
- **Keyboard.** `j`/`k` move a focus ring between rows, Enter expands, `r` accepts held changes, `/` focuses the revset field. Focus never jumps when a frame arrives.
- **Empty and error states.** No repository selected: the switcher's prompt. A repository with one change: the single node and a hint line (`reef ws run -- <cmd> starts an agent in a workspace`). A failed `Changes.Log`: the error chain and `hint` from `ErrorDetail`, with the last good list kept below.
- **Replay prop.** `<Smartlog rows={changes} live={true | false} />`: in live mode the rows come from the store's query and the holding logic applies; in replay mode (R2.21) the rows are the prop, holding is off, the revset field is disabled, and the header shows R2.21's banner. The layout and node components are shared untouched.

## Implementation notes

- Keep `layout.ts` free of React and of the proto types: it takes `{ id, edges: { target: string, kind: "direct" | "indirect" | "missing" }[] }[]` so the test cases are tiny literals and R2.21 can lay out `ReplayState.changes` with the same function. A small adapter builds that input from `Change.edges`, or, when `edges` is empty, from `parents` as `direct` edges to rows in the set and `missing` edges otherwise.
- The graph SVG is one element for the whole list, positioned beside the `<ol>` with `position: sticky` off; row height is a CSS variable the SVG reads once (`getComputedStyle`) so a density setting later changes both together.
- Debounce the refetch, not the frame application: a frame that touches existing rows applies at once (that is what "live" means); only the fetch for unknown changes waits 250 ms, so twenty agents snapshotting at once cost one `Changes.Log`.
- The "scrolled to the top for two seconds" auto-accept is the one place the list changes without a click; it exists because a reader who sits at the top is waiting for new work, and it is disabled while the pointer is over the list (the cursor rule) and while a row is expanded.
- The owner join: `Workspaces.List` for the repository is cheap and already live for R2.20's view; share the hook rather than adding owner to `Change` on the daemon side.
- Do not animate the SVG edges; redraw them. Only the node fill transitions, and only on a state name change (compare the previous state in the row's memo).
- Reverse-hex short ids can collide at 8 characters in a very old repository; the `title` has the full id, and jj's own CLI shows the same prefix length by default. Not a problem to solve here.

## Out of scope

- Collapsing linear runs (jj's `--limit`/elided nodes); Phase 2 shows every row the revset returns.

## Risks

- **Holding can hide a lot.** A reader who never accepts sees a stale graph with a growing badge. The badge is loud (it counts), the auto-accept at the top handles the common case, and replay (R2.21) is the tool for "what happened while I looked away". If dogfooding shows people missing it, the next step is a subtle column highlight, not auto-reordering.
- **Lane layout without edge kinds** (the `parents` fallback when `edges` is empty) draws a parent below the cut as a stub; if the revset elides ancestors in the middle of a stack, two rows can look adjacent when commits sit between them. With `with_graph` set, R2.02 returns `INDIRECT` edges for exactly this and the view draws the elision mark; R2.12's replay asks for the graph too, so the fallback only runs against a daemon older than R2.02's edges, and `layout.test.ts` covers both.
- **Topological order comes from the daemon.** R2.02 wraps `stream_graph` in `TopoGroupedGraph` when `with_graph` is set, with the default workspace's working-copy branch prioritized as `jj log` does, so rows arrive in that order; if that ever changes to plain reverse-chronological order, the lane algorithm still works but the graph braids more. Confirm the order against R2.02's test 5 when it lands.

## Proposed addition for R2.02 (not a README change)

*Accepted 2026-10-25: R2.01's `Change` carries `repeated GraphEdge edges = 14` with the nested `GraphEdge.Kind { DIRECT, INDIRECT, MISSING }` and `LogChangesRequest.with_graph`; R2.02 fills it from `stream_graph` wrapped in `TopoGroupedGraph` when `with_graph` is set, and R2.12's replay asks for it too. The fallback to `parents` below stays for `with_graph = false`. The proposal as written follows.*

`Changes.Log` should carry jj's edge kinds so the graph can show elision: an additive `repeated GraphEdge edges` on `Change` with `{ target: ChangeRef, kind: DIRECT | INDIRECT | MISSING }`, straight from `jj_core::graph::GraphEdge` (`graph.rs:33-85`), and rows in `TopoGroupedGraph` order. Both are additive fields and ordering guarantees, within the README's "fields and RPCs are added, never restructured" rule; this view falls back to `parents` when `edges` is empty.
