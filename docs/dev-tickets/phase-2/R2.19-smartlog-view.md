# R2.19 Smartlog view

Phase 2 · Size M · Depends on: R2.18 (the app, its router, the shared operation and presence streams, `StateBadge` and the state tokens), R2.12 (`at_operation` on `GetStatus`, so the view's two reads agree at one operation and the view can be read at a past one), R2.16 (`QueryChanges`, for who wrote a selected change), and through R2.18 R2.02 (`ListChanges`, its revsets, graph edges and pinned pages) · Unblocks: R2.21 (its scrubber renders this view at a point), R2.20 (it makes this view's workspace and agent labels links), #128 (the Playwright smoke test R2.18's decision 6 deferred until this view lands), R3.31 (actions on a selected change)

## Context

The design's smartlog shows "stacks and changes as a graph, updating as agents snapshot, propose, and land", for "the shape of work in flight at a glance" (`docs/design.md`, Live by default). Its model is Sapling's Interactive Smartlog. Four of the design's five live rules bind it: one state color per object, motion only for state change, nothing reorders under the cursor, and every live element links to its cause.

Everything the view needs is already served. `ListChanges` returns a revset's changes in `jj log`'s order with graph edges marked direct, indirect (through commits the log leaves out) or missing (outside the revset). It pages by token, pins later pages to the first page's operation, and reads at an operation (R2.02, R2.12). R2.18's app shares one operation stream and one presence stream across a browser's tabs, delivers operations per animation frame with a `reset` signal, and maps a `Change` to a state through `changeState`. The CLI's `reef log` prints the same entries and their edges as JSON and draws no graph, by decision: "The JSON carries the edges; the web UI (R2.19) draws them" (ADR 0034).

What is missing is the view: which changes it shows, how a graph is laid out in the browser, how it stays live without reading on every operation or reshuffling as agents snapshot, what selecting a change shows, and how the same view reads at a past operation for R2.21's scrubber.

This brief proposes no API change. Every RPC it calls exists and is `ACCESS_READ`, so the web listener serves it (R2.18, step 8 of the gate).

### What was verified while writing this ticket

Reef at `ce8c67c` (#131 merged); `API_REVISION` is 13 (`reef-api/src/lib.rs:49`), and R2.08's open PR #136 takes 14 and schema version 6. Paths are under `crates/` unless they start with `docs/` or `web/`.

- **The log RPC.** `ListChangesRequest { repo, workspace, revset, at_operation, skip_snapshot, page_size, page_token }` (`reef-api/proto/reef/api/v1/changes.proto:179`). `page_size` 0 means 100, and the maximum is 1,000. A page also stops before 3 MiB (`reef-daemon/src/service/page.rs:27`). Each `LogEntry` is a `Change` and its `GraphEdge`s, and each edge is a parent commit id with `DIRECT`, `INDIRECT` or `MISSING`. The response echoes `at_operation`, and later pages read the same operation as the first.
- **Pages are positional.** A page token is `<skip>:<last commit>`, and every page walks the graph again from the start and skips `skip` entries (`reef-lib/src/jj/log.rs:256`, `log_page`). Loading 1,000 entries as ten pages of 100 visits 5,500 nodes, and as one page of 1,000 visits 1,000. The view therefore asks for its whole limit in one page.
- **A read in repository scope never snapshots.** `ListChanges` treats an empty revset as using `@` (`service/changes.rs:82`), but `snapshot_first` snapshots only `Target::active()`, the named workspace (`service/reading.rs:50`). With `repo` and no `workspace`, nothing is snapshotted and no operation is recorded. The view reads in repository scope and also sends `skip_snapshot: true`, so a later change to that rule cannot make a page snapshot every agent's workspace.
- **Reef's aliases.** `trunk()` is the default start bookmark's commit, `immutable_heads()` is `trunk() | tags()`, `immutable()` is `::(immutable_heads() | root())` and `mutable()` is `~immutable()` (`reef-lib/src/jj/revset.rs:333` to `:336`). The default log set is `trunk() | working_copies() | mutable()` (`:38`). R2.18's brief and `web/src/state/states.ts:38` say `immutable_heads()` includes untracked remote bookmarks. It does not: jj's built-in alias does, Reef's does not. A branch that exists only as `name@origin` is therefore mutable, and draws as a draft stack.
- **What Reef's own log looks like.** In this repository at `ce8c67c`, `reef log --repo <id> --limit 0` lists 48 entries. 20 of them reach their parent through a `MISSING` edge, because a stack's parent is an older trunk commit, and the default set has nothing below a stack's root. About 20 stacks are branches squash-merged long ago: their commits never become ancestors of `trunk()`, so they stay mutable. Four stacks are remote-only (`dependabot/...@origin`, `tokens/...@origin`). The same log with each stack's parent added (the revset below) has 66 entries: 53 direct, 12 indirect and 1 missing edge, with `trunk()` and 18 fork points on one spine.
- **jj's order follows the newest commit.** `log_page` runs jj's `TopoGroupedGraph` over the revset's stream, which yields commits newest first. A snapshot rewrites a workspace's commit, making it the newest, so the stack it heads moves to the top of the log. With ten agents snapshotting, a view that keeps the server's order reshuffles its stacks several times a second.
- **The repository read.** `GetStatus { repo, at_operation }` returns `Repository` (its root), `RepositoryStatus { trunk, trunk_bookmark, active_workspaces (newest 100, with owner and purpose), active_workspace_count, heads, head_count, conflicted_change_ids, divergent_change_ids, last_operation }`, and echoes `at_operation` (`status.proto:101` to `:152`). It never snapshots without a workspace.
- **A change's details.** `GetDiff { repo, to_revision, format: DIFF_FORMAT_STAT, page_size, at_operation }` returns the files with kinds and line counts, and `total_files` over every page (`diff.proto`). `QueryChanges { repo, changes, include_empty }` returns a `HistoryChange` with its outcome and its activity by agent and workspace, at most 16 rows (`history.proto:98` onward). It has no `at_operation` (R2.12, "Records outside the log"), and with `[history] enabled = false` it fails with `HISTORY_DISABLED`. History is on by default (`reef-daemon/src/config.rs:633`).
- **The stream carries effects.** Every streamed `Operation` carries its `OperationEffects`: changes created, rewritten, abandoned or hidden, bookmarks and working copies moved (`operations.proto`, `SubscribeOperationsResponse.operations`). A view can tell which changes an operation touched without a read.
- **Presence names changes.** A `Presence` has `repo_id`, `workspace_id`, `change_id` (hex) and `agent` (`presence.proto:112`). The daemon's `LEASE` entries name a workspace, and `EDITING` entries name its change.
- **The app.** `web/src/api/connection.ts` builds clients for `DaemonService`, `RepositoryService`, `OperationService` and `PresenceService` only. `ui/router.tsx` matches `pathname` only, with no parameters or query string, and `navigate` compares paths only. `App.tsx` has two routes, `/` and `/states`. The daemon serves `index.html` for any path whose last segment has no `.` (`reef-daemon/src/web/assets.rs:18`), so `/repos/<id>/smartlog` reloads into the app (R2.18's test 2 uses that very path). `live/operations.ts` delivers `{ operations, live, reset }` per animation frame and turns more than 10,000 pending operations into a reset. `live/backoff.ts`'s `after` is the one sanctioned delay outside the streams, and the overview uses it to space its reloads.
- **The CLI's spelling.** `reef log` prints change ids in jj's reverse hex, 12 characters (`reef-vcs/src/cli/render_vcs.rs:20`), and `reef_client::json::reverse_hex` converts (`reef-client/src/json.rs:156`). The overview shows 8 characters of ids.
- **#128** asks for a Playwright smoke test in the `web` job "when R2.19 (smartlog) lands". It is open.
- **A stale promise.** #114's brief lists `ListWorkspacesRequest.changed_file_counts` "for the web UI (R2.19)". The smartlog does not use it: a workspace's count of changed files is the fleet panel's (R2.20), and the smartlog's labels need only `GetStatus`'s workspaces.

## Decisions

### Size

M. The ticket is web-only, apart from one daemon test. It has no daemon code, no schema change, no CLI change and no CI change. The work:

- a router that takes path parameters and a query string;
- four clients;
- a graph module (an ordering and a lane layout, with an ASCII renderer for tests);
- a view model that reads, refreshes and joins presence;
- the view and its detail pane;
- about fifteen tests.

That is R2.11's size, not R2.18's. If the stable ordering ("Order") were dropped, the ticket would be smaller, but the view would break the design's "nothing reorders under your cursor" whenever an agent snapshots. It stays in.

### What the smartlog shows

**The revset** is Reef's default log set with one generation of parents, as jj's own default log adds them:

```
trunk() | working_copies() | ancestors(mutable(), 2)
```

`ancestors(x, 2)` is `x` and its parents. Each stack therefore shows the trunk commit it was built on (its fork point). Fork points are ancestors of `trunk()`, so the graph joins them to trunk, and to each other, through indirect edges. The result is Sapling's smartlog shape: a trunk spine, each stack branching from where it started, and a dashed segment wherever the log leaves commits out. Reef's default set alone draws every stack as floating, ending in a "missing" stub (20 of 48 entries in Reef's own log). jj's default revset, `present(@) | ancestors(immutable_heads().., 2) | present(trunk())`, has the same shape, with `working_copies()` in place of `@` because the smartlog has no one current workspace.

The constant is `SMARTLOG_REVSET` in `web/src/graph/revset.ts`. Daemon test 1 reads it from that file, so the daemon behavior the view relies on is checked against the string the app sends.

**The CLI and the web agree by construction.** The page shows the revset it read and a copyable command that prints exactly its entries: `reef log --repo <id> -r '<revset>' --limit <n>`, plus `--at-op <op>` when it is read at an operation. The membership and the edges are the API's, and only the row order is the app's ("Order"). `reef log`'s own default stays Reef's default set (decision 1).

**A revset field** above the graph shows the active revset and accepts another. It is the `revset` query parameter, and empty means `SMARTLOG_REVSET`. A parse error is the daemon's `INVALID_REVSET`, shown under the field with its message and `hint`, and the last good graph stays below it.

**How each element appears.** All text is plain text. Nothing from the API is rendered as HTML (S-33).

| Element | How it shows |
| --- | --- |
| A change (one commit) | One row: the node in the graph, the state ("State"), the change id (8 characters of reverse hex, full in `title`), the commit id (8 hex characters, secondary text), bookmarks, tags, workspace and agent labels, `empty` when empty, and the description's first line or "(no description)" in secondary text. Time is the committer time as `2026-10-31 14:03`, local, with RFC 3339 in `title` (absolute, never relative: R2.18's rule). |
| A stack | A chain of rows in one lane, from its head down to its fork point, kept together by the ordering. A stack is not a separate object, so it has no header row. |
| Trunk and fork points | Rows like any other, `landed`, on the spine. `trunk()`'s row also shows the `trunk_bookmark` from `GetStatus`. |
| Bookmarks and tags | Labels after the ids. A local bookmark is `main`, and a remote one `main@origin` in secondary text. The `git` remote is never listed (the API leaves it out). Tags are prefixed `tag:`. |
| A workspace's change | One label per id in `workspace_ids`: `ws 48c61b1a`, followed by the owner from `GetStatus.active_workspaces` when it is among the newest 100. Each name in `jj_workspaces` gets a label `jj default`. |
| Agents present | Live only. Distinct agents among presence entries with this `repo_id` whose `change_id` is this change, or whose `workspace_id` is one of its workspaces. At most three are named, then `+n`. Labels use neutral tokens, never state colors (R2.18's rule). |
| A divergent change | Each of its commits is its own row, `conflicted` with the word "divergent". Selecting either selects the change, and highlights and lists both. |
| A conflicted change | `conflicted` with the word "conflicted". |
| An elided range (`INDIRECT`) | A dashed lane from child to parent. The detail pane says "through commits this view leaves out". The count is unknown: jj's graph does not count them, and neither does the view. Expanding a range is a follow-up. |
| A parent outside the revset (`MISSING`) | A short dotted stub below the node, ending in a tick: jj's `~`. The detail pane names the parent commit. |

### State

`changeState` from R2.18 is used unchanged: conflicted or divergent, then hidden, then immutable as `landed`, then `draft`. R2.18 left "whether that difference shows" (immutable against landed) to this ticket. It does not show, for these reasons:

- Reef's `immutable_heads()` is `trunk() | tags()` (see "Verified"). The only immutable commit that is not on trunk is an ancestor of a tag outside trunk's ancestry.
- In the smartlog's revset, such a commit appears only as the fork point of a stack built on such a tag.
- Telling it apart would take a second read, or reachability from `trunk()` over a graph the limit may have cut.

The comment in `states.ts` that claims untracked remote bookmarks are included is corrected.

The node glyph in the graph is the state's shape from `StateBadge`, in the state's color. The word shows for every state except `draft`, which is most rows, and is always in the row's accessible name, its `title` and the detail pane (decision 3). Phase 3's states (proposed, queued, testing, failed) have no source yet, and nothing here invents one.

### Order: stacks stay where they are

The view lays out rows in its own order, not the server's. The server's order puts the most recently rewritten stack first ("Verified"), so every snapshot would move a stack to the top. The design says "nothing reorders under your cursor".

The order is computed in `web/src/graph/order.ts` from the loaded entries and a rank per stack:

- **The graph.** A node's parents are its `DIRECT` and `INDIRECT` edges' commits that are loaded. Its children are the loaded nodes that name it. Heads are loaded nodes with no loaded children. The loaded set is a prefix of a topological order (children first), so every loaded node's children are loaded.
- **Ranks.** The view model keeps `Map<changeId, rank>` for heads, for the life of the view. A head keeps its rank across rewrites, because a rewrite keeps the change id. A new head inherits a rank when its first-parent chain, through nodes with exactly one loaded child that are not immutable, reaches a change that held a rank: the stack grew, as with `jj new` on its old head. Any other new head is ranked above every existing rank when it arrives in a live refresh (new work goes on top), and below every existing rank when it arrives in the first load or a larger limit ("Show more" adds old work, not new). The first load ranks heads in the server's order, so a fresh page looks like `jj log`.
- **Emission.** Heads are visited in rank order. A visit emits a node once all of its loaded children have been emitted, then visits its parents in edge order, with an explicit stack and no recursion, so a 1,000-commit chain cannot overflow. This is a depth-first topological order: each stack is contiguous down to the first fork point it shares with a stack not yet emitted, which follows when that stack's last child is emitted. The trunk spine therefore comes last.
- **What is guaranteed**, and tested (tests 5 and 7): children before parents; every node exactly once; a head rewritten in place keeps its position; a stack that grows keeps its position; a new stack appears at the top; and on a first load, the order equals the server's whenever the server's order is itself this ordering of its heads.

Rows only move when the graph's shape changes: a stack lands or is abandoned, a new stack arrives, or a stack is rebased onto another fork point. Scrolling is anchored as well ("Live"). The order is presentation. Membership, edges and states are the API's, so no state is shown that the API cannot show (the design's rule).

### Layout: lanes, in the browser

`web/src/graph/layout.ts` assigns each row a column, and draws the lanes passing it and the edges leaving it. It is a pure function, `layout(rows) -> GraphRow[]`, over the ordered rows, in the style of jj's and Sapling's renderer (`renderdag`), which the CLI does not use since `reef log` draws no graph.

- **State**: an array of lanes, each `null` or `{ target: commitId, kind: direct | indirect }`. A lane is a line waiting for its target row.
- **Per row**:
  1. The lanes whose target is this node are its incoming lanes. The node takes the leftmost of them, or the first free lane, or a new one on the right. The others join it from above and are freed.
  2. For each edge, in edge order: a `MISSING` edge draws a stub and reserves nothing. An edge whose parent some lane already awaits joins that lane. Otherwise, the first such edge continues in the node's own lane, and each later one takes the first free lane to the right.
  3. Every other occupied lane passes straight through.
  4. Trailing free lanes are dropped.
- **A lane keeps its kind** from the edge that opened it until its target row, so an elided range is dashed over its whole height. Two lanes awaiting the same parent with different kinds keep their kinds until they join.
- **Edges to parents beyond the cut** open lanes like any other, and lanes still open after the last row are drawn ending in a fade.
- **Output per row**: `{ column, incoming, joins: [{ from, kind }], passing: [{ column, kind }], edges: [{ to, kind }], stub, width }`. Each row knows only its own geometry.
- **Cost**: O(rows × lanes), with no allocation per lane beyond the array. Test 7 holds 1,000 rows to under 200 ms in Vitest, where it is expected to take under 20 ms. The PR records the time.

**Drawing.** Each row is one fixed-height line (28 px) with its own inline SVG, `aria-hidden`, lanes 14 px apart. Lines and stubs use `--text-secondary`, which is at least 4.5:1 on the surface in both themes, above the 3:1 WCAG asks of graphics. Direct edges are solid, indirect dashed and stubs dotted. Only the node takes a state color. Because a row draws itself, a row is one keyed DOM unit that can take focus, be selected and animate, and the layout never needs the whole graph in one SVG. When the widest row needs more than the graph column holds (24 lanes at the default width), the graph column scrolls horizontally inside its own box, never the page.

**`web/src/graph/ascii.ts`** renders a layout as text for tests, with one line per row:

- `o` is the node, `|` a direct lane, `:` an indirect lane and `~` a stub;
- `/` and `\` lines between rows show joins and edges that change lanes;
- the label follows the lanes.

For example, two stacks on trunk, a fork point below it, and a parent outside the revset:

```
o      a2  stack A head
o      a1
| o    b1  stack B head
|/
o      t4  trunk
:
o      t2  fork point
~
```

The format is documented in the file. The golden tests are written in it, inline in the test files rather than as snapshot files, so a review shows the graph.

### Limits

- **200 entries** are loaded by default, in one `ListChanges` page of `page_size: 200` ("Pages are positional"). "Show 200 more" raises the limit by 200, up to 1,000, the API's page maximum. Past that the button reads "Narrow the revset to see more" and does nothing. The limit is the `limit` query parameter. The CLI's default is 100, and 200 fits a screen of stacks with their spine on a repository like Reef's, where the whole smartlog is 66 entries.
- **The limit is the cut, not a count.** `ListChanges` returns no total, so the page says "More changes than shown" and nothing more.
- **3 MiB pages.** A page cut short by its byte limit (very long descriptions) has a `next_page_token` while entries are fewer than the limit. The view follows tokens, pinned to the first page's operation, until it has `limit` entries or none remain.
- **Rendering 1,000 rows** is about 10,000 elements. That is within React's reach for one commit, so the list is not virtualized. The PR records the time of the first render and of a refresh at 1,000 rows in Chrome. Virtualizing is a follow-up if that time is over 50 ms.

### Live: one read at a time, from the shared stream

The view adds no stream. It subscribes to R2.18's `OperationStore` and `PresenceStore`.

- **Nothing is read before the stream is live**, as the overview does, so an operation recorded after a read arrives on the stream and triggers a refresh. No operation goes unseen between the read and the stream.
- **A refresh** is `ListChanges { repo, revset, page_size: limit, skip_snapshot: true }` in repository scope, then `GetStatus { repo, at_operation }` at the operation `ListChanges` echoed. The two reads always describe one operation. The status supplies the repository's root for the header, `trunk_bookmark`, the active workspaces' owners, and the conflicted and divergent counts. If `GetStatus` fails with `OPERATION_NOT_FOUND` (GC removed the operation between the two calls), the refresh starts over once.
- **What triggers one.** A batch with `reset`, or a batch holding at least one operation with this `repo_id` whose effects are unset or list a change, a bookmark or a working copy. An operation whose effects are set and empty changes nothing the smartlog shows, and triggers nothing.
- **Coalescing.** At most one refresh is in flight. Operations that arrive during it set a dirty flag, and one refresh follows when it ends. A refresh starts no sooner than `max(250 ms, 4 × the last refresh's duration)` after the previous one started. The first after a quiet period starts at once, and later ones wait through `live/backoff.ts`'s `after`, as the overview's reload does. A burst of 1,000 operations is therefore one refresh and a trailing one, and a daemon that answers slowly is asked less often: at most a quarter of one core's time per open smartlog, whatever the operation rate. Nothing is read on a timer. A delay only spaces out a read that an operation asked for.
- **Hidden tabs** get no animation frames, so they get no batches and read nothing until they are visible again. Then one batch (or a reset, past 10,000 pending operations) gives one refresh.
- **The cause of each change.** The model keeps, per change id, the latest streamed operation whose effects created or rewrote it, since the view opened. A row that changed carries it in its `title` ("rewritten at 14:03:22 by <agent>, snapshot (watcher)"), and the detail pane shows it with the operation's id. The id is text until R2.21 gives operations a route, as the overview's are (R2.18). That is how this view meets "every live element links to its cause" in Phase 2.
- **Motion only for state change.** A row whose change id was present before with another commit id, or which first appeared in a live refresh, gets R2.18's `changed` transition once (300 ms, none under reduced motion). Rows from the first load or from "Show more", and rows that only moved, do not animate. Rows are keyed by commit id, so a rewrite is a new row.
- **Nothing reorders under the cursor.** Stacks keep their order ("Order"). Across an update, the view keeps the selected row, or else the first row in view, at the same offset from the top of the viewport. It measures the row in a layout effect and applies `scrollBy`, rather than relying on CSS `overflow-anchor`, whose support differs across the target browsers. The view never holds updates back behind a count: the smartlog is state, not a queue. The design's "new items arrive behind a visible count" is the inbox's rule (R3.34).
- **Presence** re-renders labels from `PresenceStore.version` with no read.
- **Errors.** A failed refresh shows the error with `hint` and `next` above the graph, keeps the last good graph, and says which operation it shows. The next triggering batch retries. `WEB_SESSION_INVALID` ends the session, as everywhere.

### Selecting a change

A row is selected by click, or by keyboard ("Accessibility"). The selection is the change id, so it survives rewrites. It is in the URL as `change=<reverse hex>`, set with `history.replaceState`, so selecting does not flood the back button. The detail pane shows:

- **From the loaded entry, with no read**: the state badge with its word; the full change id in reverse hex and hex; the commit id; the full description, in a `<pre>` with wrapping, as text; author and committer with times; parents, each with its edge kind in words ("direct", "through commits this view leaves out", "outside this view"); bookmarks, tags, workspaces and jj workspaces; for a divergent change, every commit of it in the graph, each selectable.
- **Its cause**, when the stream saw one ("Live").
- **Files**: `GetDiff { repo, to_revision: <commit id>, format: DIFF_FORMAT_STAT, page_size: 100, at_operation }` lists each path with its kind letter (A, M, D, R, C, as `reef diff` prints them) and `+n -m`, then "and N more files" from `total_files`, with the copyable command `reef diff --repo <id> -r <commit> --stat`. It is read again only when the selected commit id changes. Hunks and file contents are R3.38's view and are not shown.
- **Who wrote it**: `QueryChanges { repo, changes: [<change id>], include_empty: true, page_size: 1 }` gives its outcome as a state badge through `outcomeState`, and its activity rows (agent, workspace, first and last write). It is read when the selection changes and when the cause of the selected change changes, with the same spacing as a refresh. `HISTORY_DISABLED` shows the line "History is off for this daemon" instead of an error. History is current-only, so the section is absent at an operation.
- **Agents present now**: each presence entry on the change or its workspaces, with its kind, its activity text, and the number of paths it is editing.
- **Links**: none to other views yet. Workspace and agent labels become links when R2.20's routes exist, and operation ids when R2.21's do. The pane says nothing about them. The ids are selectable text.

A `change` that is not among the loaded entries (cut by the limit, or outside the revset) shows "This change is not in this view" with the revset command, and reads nothing.

### Reading at an operation: the view at a point, without the scrubber

R2.12 left "R2.19 and R2.20 read `ListChanges` and `ListWorkspaces` with the scrubber's `at_operation`, and show no presence for a past point". This ticket does the reading. R2.21 does the scrubbing.

- **In scope**: the query parameter `at=<operation id or unique prefix>`, and an `atOperation` input to the view model that R2.21 can pass when it embeds the view.
  - With it, the view reads `GetOperation { repo, operation_id }` once for the banner, then `ListChanges` and `GetStatus` with `at_operation`, and the detail pane's `GetDiff` with it too.
  - It does not subscribe to batches, refreshes nothing, shows no presence labels, no causes and no "Who wrote it", and offers no "Show more" past what one read returned.
  - The banner reads "At operation `abcd1234`, ended 14:03:22 (`<agent>`, `<kind>`). Not live; presence is not replayed." with a link back to live (the same URL without `at`).
  - Errors are the daemon's (`INVALID_OPERATION_ID`, `OPERATION_NOT_FOUND`, `OPERATION_NOT_RETAINED`, `OPERATION_LOG_REWRITTEN`), with `hint` and `next`.
- **R2.21's**: everything that picks the point. That is the operation track, time to operation (`GetOperation` with `ended_at_or_before`), stepping by effects, play to live, and any control on this page that moves `at`. Until R2.21, a point is reached by a URL alone, for example from `reef op log`'s ids. Nothing in this view links to a past point.

### Routing

- **`/repos/<repo>/smartlog`**, where `<repo>` is what `ListRepositories` gives (a full id), or any repository argument the API accepts. The query parameters are `revset`, `limit`, `change` and `at`, all optional. An unknown repository is the daemon's `REPOSITORY_NOT_FOUND`, shown with its hint.
- **The overview's repository cell links here**, as R2.18 asked of this ticket. Its operation and agent cells stay text for R2.21 and R2.20.
- **`ui/router.tsx` grows**:
  - `useLocation()` returns `{ path, query: URLSearchParams }`;
  - `match("/repos/:repo/smartlog", path)` returns decoded parameters or `null`;
  - `navigate(to, { replace })` compares the path and the query, and pushes or replaces;
  - `Link` takes a `to` with a query.

  It stays a module of about 80 lines with no dependency. `App.tsx` gains the route. R2.20 and R2.21 add theirs beside it.
- **Change ids in the URL** are reverse hex, as `reef log` prints them. Hex is also accepted, since the two alphabets (`k` to `z`, `0` to `9` and `a` to `f`) do not overlap. `ui/ids.ts` converts, matching `reef_client::json::reverse_hex`.

### Accessibility and keyboard

- **The graph is decoration.** Every SVG is `aria-hidden`. A row's accessible name says everything the graph shows, in words: state, change id, bookmarks, workspaces, agents present, `empty`, the description's first line, and, when not every edge is direct, "joins its parent through left-out commits" or "parent outside this view".
- **The list** is a `role="listbox"` with `aria-label="Changes"`, one `role="option"` per row and `aria-selected`, using a roving `tabindex`:
  - ArrowDown and ArrowUp move the selection;
  - Home and End go to the first and last row;
  - Escape clears the selection;
  - focus follows the selection, and the detail pane is an `aria-live="polite"` region that announces its heading.
  - No single-letter shortcuts, which collide with screen readers' own keys.
- **Contrast**: only R2.18's tokens are used, so W1 (`tokens.test.ts`) covers every color on the page. No new token is added.
- **Narrow screens**: at 900 px and wider the detail pane is a 360 px column beside the list, sticky to the viewport. Narrower, it renders directly after the selected row. At phone width nothing scrolls the page horizontally. The design keeps the smartlog off phones as a product, and this view only has to not break there.

### The API: no change

The view calls:

| RPC | Access | Where | At an operation |
| --- | --- | --- | --- |
| `ChangeService.ListChanges` | READ | every refresh | yes |
| `StatusService.GetStatus` | READ | every refresh, at `ListChanges`' operation | yes (R2.12) |
| `DiffService.GetDiff` | READ | the selected commit | yes |
| `HistoryService.QueryChanges` | READ | the selected change, live only | no, and not shown |
| `OperationService.GetOperation` | READ | the banner, at an operation only | not needed |
| `SubscribeOperations`, `SubscribePresence` | READ | R2.18's shared streams | not used at a point |

All six are `ACCESS_READ`, so the web listener serves them and no gate rule changes. `api/connection.ts` gains `changes`, `status`, `diff` and `history` clients. Nothing is generated by hand, since `npm run gen` builds every service.

Had a field been needed, it would have taken the revision after R2.08's 14, in a change of its own. The two candidates considered and rejected:

- **A total count on `ListChanges`**: it would cost the whole walk on every refresh to print a number. "More changes than shown" is enough.
- **A sort order on `ListChanges`**: stable stack order belongs to a view that remembers what it showed, not to a stateless read. Agents get jj's order, which is what `jj log` prints.

### The threat model

S-33's mitigation gains one sentence. The smartlog's URL parameters (`revset`, `change`, `limit`, `at`) are input a link can set:

- they reach only READ calls, bounded by the page limit;
- they are rendered as text;
- the copyable `reef log` command quotes the revset for a POSIX shell (`'` written as `'\''`), so pasting a command built from a crafted link runs nothing but `reef log`. Test 8 holds the quoting.

No new row: the page reads what any session may read (S-34), and a crafted revset can only make the page show less, which a link cannot hide from the user, since the revset is printed above the graph.

## Implementation notes

- **Order of work**:
  1. ids, router and revset with their tests (2 to 4);
  2. order and layout with ASCII and their tests (5 to 7);
  3. daemon test 1;
  4. the model (8);
  5. the view and the pane (9, 10);
  6. the manual checks.
- **`order` and `layout` are pure and synchronous.** The model calls them on every refresh with the ranks it holds and gets new ranks back. Neither touches the DOM, React or the network, so tests 5 to 7 run without jsdom.
- **Keep the server's entries as they come.** The model indexes entries by commit id and by change id (one change id may map to two commits), and never edits an entry. A row is `{ entry, state, layout row, cause, changed }`.
- **The detail pane's reads use a generation counter**, as the overview does, so an answer for a previous selection or a previous refresh is dropped.
- **Scroll anchoring** measures in `useLayoutEffect` before paint: the anchor row's `getBoundingClientRect().top` before the commit (kept from the previous layout effect) against after it, then `window.scrollBy(0, delta)`. It is skipped when the user is mid-scroll in the same frame, so the view never fights a scroll.
- **Do not reuse a state token** for lanes, labels or the selection ring. The selection uses `--focus` and a 2 px outline, and labels use `--border` and `--text-secondary`.
- **Linux**: nothing here is `cfg(target_os = "linux")`. Test 1 builds a repository through jj-lib like the rest of `reads.rs` and runs in both `check` jobs.

## Inherited scope

- **From the design**: the smartlog's purpose; one state color per object; motion only for state change; nothing reorders under the cursor; every live element links to its cause (met with operation ids as text until R2.21); never fetch on a timer.
- **From R2.18 and ADR 0047**: the app shell and its rules (no timers that fetch, frames, no HTML from the API, accessible by default); the shared streams; `changeState`, `outcomeState`, `StateBadge` and the tokens; the READ-only listener.
- **From R2.02**: the revset language with Reef's aliases, graph edges, pinned pages and their limits.
- **From R2.12**: reads at an operation, and that presence and the history index are not replayed.
- **From ADR 0034**: the CLI draws no graph; the web does.

## Out of scope

- Picking a past point: the operation track, times, stepping, play (R2.21).
- Workspaces, leases and agents as their own view, and the routes the labels will link to (R2.20).
- Any write from the UI, such as describe, abandon, rebase or new (R3.31 onward).
- Diff hunks and file contents (R3.38).
- Expanding an elided range, counting its commits, and folding stale stacks: follow-up issues.
- Agent attribution on every row, which would need `QueryChanges` for every visible change: a follow-up issue. Rows show agents present now, and the detail pane shows who wrote the change.
- Virtualized rendering past 1,000 rows, and the limit past 1,000.
- A text graph in `reef log` (ADR 0034 keeps it out; the layout is TypeScript only).
- Browser end-to-end tests in CI (#128).

## Risks

- **Squash-merged branches stay mutable forever** and fill the smartlog with old stacks (about 20 in Reef's own repository). They are real visible commits, and `jj log` shows them too, so the view shows them. Folding them needs an outcome the API does not have (R2.16's `LANDED` means "on `trunk()`"). A follow-up issue names the options: R2.16 matching by subject or patch id, or a revset that drops stacks whose bookmarks are gone.
- **Remote-only branches draw as draft stacks**, because Reef's `immutable_heads()` omits `untracked_remote_bookmarks()`, unlike jj's (decision 4).
- **The order differs from `jj log`'s after the first load.** A user comparing the page with `reef log` row by row sees the same entries in another order once stacks have been rewritten. The page says "Stacks keep their place while you watch; `reef log` lists the most recently changed first" under the revset field.
- **Two reads per refresh.** `GetStatus` at an operation is a second repository load. On the 64-entry cache from R2.12 it shares the head's index, and the PR measures it. If it dominates, the refresh reads it only when an operation's effects moved a bookmark or a working copy, or created or released a workspace.
- **A wide graph.** Many concurrent merges can open more than 24 lanes. The graph column then scrolls inside its box, and the text columns stay in place.

## Choices this brief made, and why

- **The jj-shaped revset, not Reef's default set**: stacks hang from their fork points on a spine, instead of floating with missing stubs, and the page prints the revset and the CLI command, so the two agree by construction.
- **A stable order in the browser**: the server's order follows the newest commit, and agents' snapshots would reshuffle the page several times a second.
- **Layout in TypeScript, per row**: it is pure and testable without a browser, and each row is one keyed, focusable, animatable unit.
- **One read in flight, spaced by the daemon's own speed**: bursts become one read, and a slow daemon is asked less often, with no timer reading anything.
- **Repository scope with `skip_snapshot`**: a page in the browser never snapshots an agent's workspace or records an operation.
- **No API change**: every read exists, and a count or a sort order on the server would cost more than it shows.
- **`at` in the URL, without a picker**: R2.21 gets a view it can point at any operation, and R2.19 does not build half a scrubber.

## Decisions by the user (2026-10-31)

1. **Reef's default log set stays as it is.** The web sends `trunk() | working_copies() | ancestors(mutable(), 2)` explicitly, while `ListChanges`' default and `reef log` stay `trunk() | working_copies() | mutable()`, so the output an agent gets unasked does not grow (#114, R2.17's token gate). 2. **A stable stack order**, as specified in "Order". The page says that its order differs from `reef log` once stacks are rewritten.
3. **No word on draft rows.** Every non-draft row shows its state's word. Draft rows show the shape only, with "draft" in the accessible name, `title` and detail pane. 4. **Remote-only branches show as the API classifies them** (mutable, so draft), and R2.18's comment in `states.ts` is corrected. A follow-up issue decides whether Reef's `immutable_heads()` should add `untracked_remote_bookmarks()` as jj's does; that changes every client's `immutable` and `mutable()`, so it is not a view's change.
