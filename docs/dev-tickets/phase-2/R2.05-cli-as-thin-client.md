# R2.05 CLI as thin client

Phase 2 · Size M after a split (the row says M; the row's whole scope is bigger than L, see "Size, and the split") · Depends on: R2.01 (`reef-api`, the v1 client the CLI already speaks); the row also lists R2.02 and R2.03, which only Part B needs · Unblocks: R2.13 (`reef mcp` in a thin `reef`), R2.24, R4.17 (two binaries to sign), and R2.27 (Part B of this file)

## Context

Design principle 8 is "API first, CLI second": agents talk to the daemon over a typed API, and the CLI and the MCP server are thin clients of it. ADR 0007 put the CLI in its own crate so that, one day, the dependency graph would show it. That day was deferred twice: R1.22 kept `reef_lib::jj` out of the CLI's source but left `reef-lib` and `reef-daemon` in its dependencies, and R2.01 moved every command onto `reef.api.v1` but left `reef_daemon::client` where it was and said "R2.05 decides where the thin client finally lives".

The row asks for two things. "Rewrite all CLI commands over the gRPC API" is mostly done: the survey below finds every command that talks to a daemon already speaks v1 through `reef_daemon::client::Client`. What is not done is the rest of the row and what R2.02, R2.03 and R2.04 handed to it:

- **The binary still links jj-lib.** `reef daemon run` runs the daemon in-process, `reef restore` runs the daemon library's restore, and `reef config show` loads the daemon's `Config`, which imports jj-lib's settings. The client itself lives in the daemon crate. `cargo tree -p reef-vcs -e normal` lists 398 crates; `reef-api` alone pulls 88.
- **The VCS commands do not exist.** R2.02 left `reef status`, `log` and `diff`; R2.03 left `reef describe`, `abandon` and `undo` and where the CLI's agent name comes from; R2.04 left whether the CLI gets file commands, and the `next` fields its reasons could not fill without one. The agent guide still says "Undo, status, and diff come in Phase 2: run `jj` in the repository's own root".

This brief settles all of it. It is two tickets' work, so it is written in two parts: **Part A, the thin client, is R2.05**; **Part B, the VCS commands, is a new row, R2.27**, which ships second and takes its brief from Part B of this file.

## Decisions

### Size, and the split

As one ticket the row is bigger than L. Removing jj-lib from the binary means two new crates, moving the client, the error conventions, path resolution, logging and the backup manifest out of the daemon, giving the daemon binary the two offline commands, and changing packaging and tests: about M. The commands the earlier tickets deferred are twelve leaf commands with JSON, text forms, a scope rule, and the CLI's own advice for sixteen API reasons: L on their own, as R2.02 to R2.04 each were. `dev-phases.md` says anything bigger than L is split.

The split follows the row's two sentences. **R2.05 (Part A)** removes jj-lib from the binary and leaves every command's behavior and JSON as it is, apart from three new reasons and the agent name. It needs only R2.01. **R2.27 (Part B), "VCS commands in the CLI"**, adds the commands and needs R2.02, R2.03, R2.04 and R2.05. Part A lands first, so the new commands are written once, against `reef-client`. Both parts are decided here, because the deferrals they settle are one set of decisions; when R2.27 starts, Part B is copied into its own brief with the verified-at line refreshed. The proposed edits to `dev-phases.md` and the phase README are at the end.

### Crates

Seven crates. Two are new, and the dependency direction becomes:

```
reef-vcs ──► reef-client ──► reef-api
   │              └────────► reef-error
   └─────────────────────────► reef-api
reef-daemon ──► reef-client, reef-lib, reef-api, reef-error
reef-lib ──► reef-error
reef-testing (no Reef crate; dev-dependency of any)
```

- **`reef-error`** (new, std only, no dependencies): `reef_lib::error` moved whole (`ErrorKind`, `Classify`, `classify_by_source`, `ErrorChain`), and `Advice` with `hint` and `run` moved from `reef_daemon::error`. `reef-lib`'s `error` module becomes `pub use reef_error::*;` and `reef_daemon::error` re-exports `Advice`, so no caller outside the moved files changes. `Advise` stays in the daemon: only daemon error types implement it.
- **`reef-client`** (new): everything a process needs to talk to a daemon without being one.
  - `client` (from `reef_daemon::client`, whole): `Client`, `ClientError`, `WorkspacesApi`, `default_owner`, `VERSION`, `MAX_REQUEST_BYTES`, `any_call_answered`. `parse_byte_size` is dropped (unused). `default_owner`'s user and host lookups move here too, and the daemon's `config` calls them, so both agree.
  - `error`: the client half of `reef_daemon::error`: `detail_of`, `kind_from_status` and the code table they need, and `advice_from_detail` (was `Advice::from_detail`). The daemon's `status_from` keeps the server half.
  - `json` (from `reef_daemon::client::json`): every type and helper, with the enum names written out as tables instead of borrowed from `BackendKind` and `Attention`, and RFC 3339 formatting with `time` directly. Test 13 keeps the names equal to the daemon's. `ErrorObject`, the `{"error": {...}}` object, moves here from `cli/out.rs`, so the daemon binary prints the same object (below).
  - `paths`: the path layering moved out of `reef_daemon::config` (below).
  - `logging`: `LogOptions::from_env`, `LogFormat`, the three variables, and stderr-only `init`. The daemon's `logging` builds its file appender on top and re-exports the rest.
  - `backup`: `Manifest`, `RepoManifest`, `SqliteManifest`, `ManifestError`, `MANIFEST_FILE`, `Manifest::read` (pure serde, moved from `maintenance/backup.rs`). Writing it stays in the daemon.
  - `ROOT_CHECKOUT`, the `start` text of a create with no default bookmark (from `workspace::create`; the daemon uses it from here).
  - Dependencies: `reef-api`, `reef-error`, `tonic`, `hyper-util`, `tower`, `tokio` (`net`), `prost-types`, `serde`, `serde_json`, `thiserror`, `nix` (`hostname`, `user`), `etcetera`, `toml`, `time`, `tracing`, `tracing-subscriber`. No `reef-lib`, no `reef-daemon`, no jj-lib.
- **`reef-daemon`** depends on `reef-client` and keeps `pub use reef_client as client;` in `lib.rs`, so `reef_daemon::client::Client`, `json` and the `testing` module keep working for the daemon's tests and benches unchanged.
- **`reef-vcs`** depends on `reef-client` and `reef-api` and on no other Reef crate (dev-dependencies aside: `reef-daemon` with `testing`, `reef-testing`, `jj-lib` for `ws_run.rs`). Its `lib.rs` re-exports `reef_api` and `reef_client`, so "depend on one crate" still holds for a Rust client; it no longer re-exports `reef_lib` or `reef_daemon`. Its `watchman` feature, which only forwarded to `reef-daemon`, is removed. Its `description` in `Cargo.toml` says so.

ADR 0007's direction `reef-vcs` → `reef-daemon` → `reef-lib` and its umbrella re-export are replaced; ADR 0033 records the layout and supersedes 0007.

### The daemon binary does what needs the daemon library

`reef` never runs daemon library code in its process. Three commands did:

- **`reef daemon run`** `exec`s `reef-daemon --foreground`, with `--state-dir`, `--socket` and `--config` as given, before logging or the runtime start (where it dispatches now). The process keeps its pid, stdio, environment and exit code, so a supervisor that runs `reef daemon run` sees no difference.
- **`reef config show`** runs `reef-daemon [path flags] config show [--json]` and **`reef restore`** runs `reef-daemon [path flags] restore <DIR> [--into] [--repo] [--root] [--force]`, with the path flags and variables passed as autostart passes them (absolute).

`DaemonArgs` gains an optional subcommand: none runs the daemon, exactly as today, so autostart's `reef-daemon [path flags]` and every packaging script keep working. `config show` and `restore` move from `cli/config.rs` and `cli/restore.rs` into the daemon crate (`src/offline.rs`), with `restore`'s `--repo` prefix resolution against the manifest and its `Restored` report.

**The helper protocol.** A `reef-daemon` subcommand writes exactly one document on stdout and exits:

- On success, exit 0 and the result: `config show`'s TOML, or its JSON with `--json`; `restore`'s `Restored` object as JSON.
- On failure, the kind's exit code and the `ErrorObject` on stdout, whatever the format: `{"error": {"kind", "reason"?, "message", "hint"?, "next"?}}`, with the advice from the error's `Advise`, as the CLI built it in-process before.
- Stderr is inherited; the subcommands log at `warn` unless `REEF_LOG` says otherwise.

`reef` reads the result: for `config show` it writes the bytes through (`out.raw`, as now), for `restore` it parses `Restored` (moved to `reef_client::json`) and prints it with `out.done` and the same note. On a nonzero exit it parses the error object into a new `CliError::Helper { kind, reason, message, advice }` and reports it as any error. Stdout that is not an error object (the helper crashed) is `CliError::HelperFailed { program, status }`, kind `Internal`.

**Finding `reef-daemon`.** `autostart::locate` keeps its order (beside `reef`, else the first executable on `PATH`) and loses the fallback to `reef daemon run`. One function serves autostart, `daemon run` and the two helpers. Not found is `CliError::NoDaemonBinary { searched }`, kind `NotFound` (exit 3), message `no reef-daemon beside <exe> or on PATH`, hint "Install reef-daemon beside reef: the release tarball, install.sh and Homebrew ship both; from source, `cargo install --git https://github.com/reef-vcs/reef reef-vcs reef-daemon`." No `next`: installing is not a `reef` command. A `reef-daemon` of another version is used as found: `GetDaemonStatus` reports its version, R2.01's restart rule handles a daemon that cannot serve a call, and autostart's existing check names an API mismatch.

### Paths and configuration

The CLI needs three things from the configuration: the socket, the pid file, and `[repo] auto_register`. It no longer loads the daemon's whole `Config`.

- **`reef_client::paths`** holds what `Config::load` uses to settle paths, moved, not copied: `PathOverrides`, `Source`, the platform defaults (`etcetera`, `$XDG_RUNTIME_DIR`), `STATE_DIR_ENV`, `SOCKET_ENV`, `CONFIG_ENV`, `SOCKET_PATH_MAX`, and `Layered::resolve` and `finish`, which take the file's `daemon.socket` and `daemon.pid_file` as two `Option<&Path>` instead of a `DaemonSection`.
- **`reef_client::paths::ClientConfig::load(&PathOverrides) -> Result<ClientConfig { state_dir, socket, pid, config_file, auto_register }, PathsError>`** resolves as `Config::load` does and reads the file leniently: it parses the TOML, takes `daemon.socket`, `daemon.pid_file` and `repo.auto_register` if present, and ignores every other key. A TOML syntax error or a wrong type for one of the three is `InvalidArgument`; a file named by `--config` or `REEF_CONFIG` that does not exist is `NotFound`; a socket path too long is `InvalidArgument`, each with the message `Config::load` gives now.
- **The daemon's `Config::load` calls the same `resolve` and `finish`**, so the two cannot disagree about a path (test 8). `Config::load` still validates everything, and `jj_settings` stays in the daemon.
- **What changes for a user**: a command other than `config show` no longer fails before contacting the daemon because some other key in `config.toml` is wrong. The daemon still refuses to start on it (autostart reports the exit and says to run `reef daemon run`), `reef config show` still exits 2 naming the key, and a running daemon is unaffected, as it is now. This is deliberate: the client knows the three keys it uses, and the daemon owns the rest of its configuration (ADR 0013).

### Errors and reasons

- **Three reasons**, mapped in `reason_and_metadata` and documented in the RPC comments that return them (comment changes only):

  | Reason | Kind | Metadata | Returned for |
  | --- | --- | --- | --- |
  | `REPOSITORY_NOT_REGISTERED` | `NOT_FOUND` | `path` | an absolute path in no registered repository (`ManagerError::NotRegistered`) |
  | `REPOSITORY_NOT_FOUND` | `NOT_FOUND` | `repo` | a repository id or prefix that names none (`DbError::NotFound`, what `repository`) |
  | `WORKSPACE_NOT_FOUND` | `NOT_FOUND` | `workspace` | a workspace id, prefix or path that names no workspace (`DbError::NotFound`, what `workspace` or `workspace containing`) |

  Reasons are constants, not schema: `API_REVISION` stays 3 and the digest does not change, as R2.03 added nine reasons at revision 2.
- **`is_unregistered_path` reads the reason**, not the message. No released v1 daemon lacks the reason (0.1.0 speaks v0, and R2.01's restart rule replaces an idle one), so there is no message fallback. `here` treats `WORKSPACE_NOT_FOUND` as "outside every workspace", and keeps treating any other `NOT_FOUND` as it does now.
- The advice on these errors does not change; `every_daemon_next_is_a_real_command` and `every_next_is_a_real_command` keep passing as they are.

### The agent name

- **A global `--agent <NAME>`, else `REEF_AGENT`, else none.** The CLI builds its client with `Client::with_agent`, so every call sends `reef-agent` and every operation it causes records that name as `reef.agent`. With none, the daemon records the workspace's owner, as it does now (R2.03).
- **Validated before any call**: `connect` checks the name with `with_agent`'s rule (exposed as `reef_client::check_agent`) before it tries the socket, so an invalid name is exit 2, kind `invalid_argument`, reason `INVALID_AGENT`, hint "An agent name is visible ASCII, at most 256 bytes (--agent or REEF_AGENT).", and no daemon is started. Commands that never connect (`guide`, `completions`, `config show`, `restore`, `init --print`) ignore it.
- **`ws run` exports it**: when an agent is named, its command's environment gains `REEF_AGENT` (beside the four variables it sets now), so `reef` commands the agent runs inside carry the same name without being told. A `REEF_AGENT` already in the environment is inherited anyway.
- **Not tied to the owner.** `ws create` and `ws run` keep their owner defaults (`<user>@<host>`, and `:<pid>` for `ws run`). The owner is who holds the lease; the agent is who caused an operation. A harness that wants both the same passes both.
- The flag name matches the metadata key and the variable. R2.27's `op log` filters by agent with `--by`, since a subcommand cannot reuse a global flag's name.

## Part B: the VCS commands (R2.27)

### Scope: which workspace and repository a command means

Every new command resolves a scope once, before its own call:

- `--workspace <WS>` (an id, unique prefix, or path inside one) names a workspace; else `REEF_WORKSPACE`, as `here` reads it; else the current directory. Each is looked up with `GetWorkspace` (no snapshot, no disk usage). For the current directory, `WORKSPACE_NOT_FOUND` means "not in a workspace", and the scope is the repository.
- `--repo <REPO>` names a repository and means no workspace, even inside one. Without it, the repository scope is the current directory's, looked up with `GetRepository` through `call_with_repo`, so implicit registration applies as for every other command.
- The scope gives the request's `workspace` and `repo` fields, and the directory paths are relative to: the workspace's `path`, or the repository's `root`. `op log` and `op show` use only its repository (`ListOperations` and `GetOperation` take no workspace); `op log`'s `--workspace` is a filter, not the scope.

**Paths** (`reef diff`'s paths, `reef file read|list`): when the scope came from the current directory or `REEF_WORKSPACE`, and the current directory is inside the scope's directory, a path is relative to the current directory, as `jj` takes paths, and is converted to repository-relative by joining it to the canonical current directory and stripping the scope's directory. When `--repo` or `--workspace` names the scope, or the current directory is outside the scope's directory, a path is repository-relative as given. An absolute path inside the scope's directory is converted either way. A path that leaves the directory is exit 2 before any call, message `<path> is outside <dir>`.

### The commands

| Command | RPCs | Arguments | JSON (`-o json`) |
| --- | --- | --- | --- |
| `status` | `GetStatus` | `[--workspace WS] [--repo REPO] [--no-snapshot] [--max-files N]` | `Status`: `{repository, at_operation, repository_status, workspace_status}`, `workspace_status` `null` in repository scope |
| `log` | `ListChanges`, pages to `--limit` | `[-r REVSET] [--limit N] [--at-op OP] [--no-snapshot]` and the scope flags | an array of `LogEntry`: a `Change`'s keys plus `edges` |
| `show` | `GetChange`, then `GetDiff` (`SUMMARY`, `at_operation` from the first, `skip_snapshot`) | `[REV]` (default `@`), `--at-op`, `--no-snapshot`, scope | a `Change`'s keys plus `files` (array of `FileChange`) and `total_files` |
| `diff` | `GetDiff`, every page | `[-r REV \| --from REV --to REV] [--stat \| --summary] [--context N] [--at-op OP] [--no-snapshot] [PATHS]...`, scope | `Diff`: `{from_commit_ids, to_commit_id, at_operation, total_files, files}` |
| `describe` | `DescribeChange` | `[REV]` (default `@`) `-m TEXT`... `[--expected-commit ID]`, scope | `{change, operation}`, `operation` `null` when nothing changed |
| `abandon` | `AbandonChange` | `<REV>` (required) `[--expected-commit ID]`, scope | `{abandoned_commit_id, operation}` |
| `undo` | `UndoOperation` | `<OP>` (required), scope | `{operation, snapshot, undone_operation_id}` |
| `op log` | `ListOperations`, pages to `--limit` | `[--workspace WS]... [--change C]... [--by AGENT]... [--kind KIND]... [--effects] [--limit N] [--repo REPO]` | an array of `Operation` |
| `op show` | `GetOperation` | `<OP> [--repo REPO]` | an `Operation`, with `effects` |
| `ws snapshot` | `SnapshotWorkspace` | `[WS]` (default: the scope's workspace) `[-m TEXT]` | `{changed, commit_id, scan_ms, operation}` |
| `file read` | `ReadFile`, every 1 MiB range | `<PATH> [-r REV] [--at-op OP] [--no-snapshot]`, scope | raw bytes unless `-o json`; with it `{path, type, file_id, size, commit_id, at_operation, content, content_base64}` |
| `file list` | `ListFiles`, every page | `[PATH] [-r REV] [--recursive] [--at-op OP] [--no-snapshot]`, scope | an array of `{path, type, file_id}` |

Nouns and aliases: `op` has the visible alias `operation`; `file list` has `ls`; `file read` has `cat`; `undo` takes no alias. `op log`'s `--workspace` filters (the API's `filter.workspaces`); everywhere else `--workspace` sets the scope.

Rules that apply across the table:

- **Defaults.** `-r` and `[REV]` default to `@`, which needs a workspace in scope. `log` with no `-r` sends an empty revset, Reef's default log set. `diff` with neither `-r` nor `--from`/`--to` diffs `@` against its parents; `--from` alone diffs it against `@`. `--limit` defaults to 100 for `log` and `op log`, `0` is all, and a cut (another page exists) is noted on stderr as `ws list` notes it (ADR 0025).
- **Never interactive.** `describe` without `-m` is a usage error naming `-m`; repeated `-m` values are joined by a blank line, as `jj describe` joins them; `-m ''` clears the description. Nothing reads stdin.
- **`undo` without an operation** is exit 2, kind `invalid_argument`, hint "Name the operation to undo; `reef op log` lists them, newest first.", `next` `reef op log --repo <repo id>`. There is no "undo the last operation": in a repository where watchers and other agents record operations every second, the last one is rarely the caller's (R3.26 scopes undo by agent). `abandon` without a revision is a usage error for the same reason: `@` is the change the caller is standing on.
- **`undo`** sends the scope's workspace, so it is snapshotted first and checks out the result, as `UndoOperation` specifies. **`describe` and `abandon`** send it as the scope for `@`.
- **`--expected-commit`** is `expected_commit_id`: a full commit id, as R2.03 requires.
- **`op log --kind`** takes the `reef.kind` names (`snapshot`, `create-workspace`, `release-workspace`, `move-workspace`, `describe`, `abandon`, `undo`, `edit`, `import-refs`, `external`, `other`); anything else is a usage error listing them. `--change` takes hex or reverse-hex prefixes.
- **`ws snapshot`** outside a workspace, with no `WS`, is exit 2, kind `invalid_argument`, reason `WORKSPACE_REQUIRED`, hint "Name the workspace, or run this inside one.", `next` `reef ws list`.
- **`file read` prints raw bytes even on a pipe**, as `config show` prints TOML: the bytes are the machine-readable form, and `reef file read a.rs | …` must work. `-o json` or `REEF_OUTPUT=json` asks for the object. Each range is written as it arrives, so memory stays at one range.
- **`file list`** prints a list, so its JSON is an array (ADR 0025's "one array for lists"); the commit it read is not repeated per entry. `reef show <REV>` names the commit.
- **No `reef file edit`.** `EditFiles` exists for agents without a directory, which reach it through MCP (R2.13). From a shell, the workspace is the editor.

### JSON

The new types live in `reef_client::json`, beside Phase 1's, so R2.24 derives their schemas in one place. They follow the conventions the existing ones set:

- Keys are the v1 field names. Ids are full lowercase hex. Every object with a `change_id` also has `change_id_reverse_hex`. Timestamps are RFC 3339 with milliseconds. A string field the API leaves empty to mean "none" (a previous commit id for a created change, an operation's workspace or agent, `trunk_bookmark`, `old_path`) prints as `null`; free text (`description`) stays a string.
- Enums print as lowercase names, with `-` between words: entry types `file`, `executable`, `symlink`, `directory`, `conflict`, `submodule`; file changes `added`, `modified`, `deleted`, `renamed`, `copied`; status sources `snapshot`, `index`, `walk`, `last-snapshot`; graph edges `direct`, `indirect`, `missing`; change effects `created`, `rewritten`, `abandoned`, `hidden`; operation kinds the `reef.kind` names above; snapshot kinds as `ws inspect` prints them. An unknown value prints as `unknown`, an unset one as `null`.
- **`Change`**: `change_id`, `change_id_reverse_hex`, `commit_id`, `parent_commit_ids`, `parent_change_ids`, `description`, `author` and `committer` (`{name, email, at}`), `tree_id` (`null` when conflicted), `empty`, `conflict`, `divergent`, `immutable`, `hidden`, `bookmarks`, `tags`, `workspace_ids`, `jj_workspaces`.
- **`Operation`**: `id`, `repo_id`, `parent_ids`, `description`, `started_at`, `ended_at`, `hostname`, `username`, `is_snapshot`, `kind`, `snapshot_kind`, `workspace_id`, `jj_workspace`, `agent`, `attributes`, `effects` (`null` unless filled: `{changes: [{change_id, change_id_reverse_hex, kind, commit_id, previous_commit_id}], bookmarks: [{name, remote, commit_id, previous_commit_id, conflicted}], working_copies: [{workspace_id, jj_workspace, commit_id, previous_commit_id}], change_count, bookmark_count}`).
- **`FileChange`**: `path`, `kind`, `old_path`, `old_type`, `new_type`. **`FileDiff`** is a `FileChange`'s keys plus `binary`, `conflict`, `lines_added`, `lines_removed`, `hunks` (`[{old_start, old_lines, new_start, new_lines, lines}]`), `truncated`, `old_no_final_newline`, `new_no_final_newline`, `too_large`, `invalid_utf8`.
- **`Status`**: `repository` (the existing `Repository`); `at_operation`; `repository_status` `{trunk, trunk_bookmark, active_workspaces (the existing Workspace), active_workspace_count, heads, head_count, conflicted_change_ids, divergent_change_ids, last_operation}`; `workspace_status` `{workspace, working_copy, parents, changed_files, changed_file_count, conflicted_paths, conflicted_path_count, source, snapshot}`. The name `Status` is taken by `daemon status`'s type, so the Rust type is `json::RepoStatus`.
- **`file read -o json`**: `content` is the bytes as a string when they are valid UTF-8, else `null`, with `content_base64` set instead (standard alphabet, padded); exactly one of the two is non-null.
- **The error object gains `metadata`**, the `ErrorDetail.metadata` map, when it is not empty: `{"error": {"kind", "reason", "message", "hint", "next", "metadata"}}`. An agent gets `AMBIGUOUS_REVISION`'s `commit_ids` or `EXPECTED_COMMIT_MISMATCH`'s `commit_id` as data instead of reading them out of a message. Text mode is unchanged. Additive (ADR 0025 decision 5).

### Text

Short, one record per line where there is a list, for a person or a model reading a terminal:

- `status`: the workspace line (`Workspace <id> on <change, 12 reverse hex> <first description line>`), its parents, then `Changed files (N):` and `M path`-style lines (`A`, `M`, `D`, `R old -> new`, `C old -> new`), conflicted paths; then the repository: trunk, active workspaces, heads, conflicted and divergent changes. With `--no-snapshot`, a line saying the answer is the last snapshot's.
- `log`: one line per change: an `@` when the scope's workspace is on it, the change (12 reverse hex), the commit (12 hex), bookmarks, `conflict`, `divergent`, `empty` and `immutable` markers, and the description's first line or `(no description)`. No graph: the JSON's `edges` carry it, and R2.19 draws it.
- `show`: `Change`, `Commit`, `Author`, `Committer`, `Bookmarks`, the description indented, then the summary lines.
- `diff`: unified diff, `--- a/<old>` and `+++ b/<new>` per file and the hunks' `lines` as they come; `Binary file <path> differs`, `<path>: too large to diff`, a conflict note. `--stat`: `<path> | +A -R` and a total. `--summary`: the summary lines.
- `describe`, `abandon`, `undo`, `ws snapshot`: one line on stderr through `out.done` (`described <change> (<commit>)`, `abandoned <commit>`, `undid <op> as <op>`, `snapshot <op> of <ws>: <commit>` or `nothing to snapshot in <ws>`).
- `op log`: `<op, 12> <ended_at> <kind>[/<snapshot kind>] <workspace or -> <agent or -> <description's first line>`. `op show`: the same fields as lines, then effects.
- `file list`: one path per line, directories (non-recursive) with a trailing `/`. `file read`: the bytes.

### Errors: the CLI's advice for API reasons

R2.02 to R2.04's reasons carry hints in the API's words ("Pass skip_snapshot…", "read it again and pass its commit_id as expected_commit_id") and no `next`, because the daemon cannot know which command, if any, sent the request. The CLI does know. So, in `cli/advice.rs`:

- **The daemon's `next` wins.** An error that carries one keeps its advice as sent (ADR 0025: those are already `reef` argv).
- **Otherwise, a table keyed by reason** (and by command where one reason means two things) replaces the hint with one in the CLI's words and, where the fix is a command the CLI can build from what it ran, sets `next`. Reasons not in the table keep the daemon's hint.
- **Every `next` is built from known values**: the scope and ids from the error's metadata. Never a placeholder.

| Reason | Commands | Hint | `next` |
| --- | --- | --- | --- |
| `WORKSPACE_REQUIRED` | any with `@` | "`@` is a workspace's change: run this inside a workspace, pass --workspace, or name a revision." | none |
| `REVISION_NOT_FOUND` | any with a revision | the daemon's hint (jj's "Did you mean"), else "No such revision." | `reef log` with the scope flags |
| `AMBIGUOUS_REVISION` | any with a revision | the daemon's hint (it lists the commits) | none: the caller picks one; `metadata.commit_ids` lists them |
| `EXPECTED_COMMIT_MISMATCH` | `describe`, `abandon` | "The revision now names <commit_id>; check it, then retry with --expected-commit <commit_id>." | `reef show <commit_id>` with the scope flags |
| `IMMUTABLE_REVISION` | `describe`, `abandon` | "trunk(), tags and their ancestors are immutable; describe or abandon a change of your own." | none |
| `INVALID_OPERATION_ID`, `AMBIGUOUS_OPERATION_ID`, `OPERATION_NOT_FOUND` | `undo`, `op show` | "Name an operation by id or a unique prefix; `reef op log` lists them." | `reef op log` with `--repo` |
| `OPERATION_NOT_FOUND`, `INVALID_PAGE_TOKEN` | `log`, `diff`, `op log`, `file list` (between pages) | "The log changed while the pages were read; run the command again." | the command's own argv |
| `OPERATION_SUPERSEDED` | `undo` | "Later operations changed what it did; undo them first, newest first." | `reef op log` with `--repo` |
| `SNAPSHOT_FAILED` (new, below) | reads with `@` | "The workspace could not be snapshotted; --no-snapshot reads its last snapshot." | the command's own argv plus `--no-snapshot` |
| `PATH_NOT_FOUND` | `file read`, `file list` | "No such path at <commit_id>; list its directory." | `reef file list <parent> -r <commit_id>` with the scope flags (the root when the path has no parent) |
| `NOT_A_FILE` | `file read` | "It is a directory; list it instead." | `reef file list <path> -r <commit_id>` |
| `NOT_A_DIRECTORY` | `file list` | "It is a file; read it instead." | `reef file read <path> -r <commit_id>` |
| `INVALID_PATH` | `diff`, `file read`, `file list` | "Paths are relative to the current directory inside the workspace or repository, and may not leave it." | none |
| `INVALID_AGENT` | any | Part A's hint | none |

Every `next` names its scope explicitly, `--repo <repo id>`, or `--workspace <id>` where it needs `@` (`reef log` in a workspace), so its paths are repository-relative and it runs verbatim from any directory. The two that repeat the command's own argv run from the directory it ran in. In the table, "with the scope flags" and "with `--repo`" mean exactly this.

**`SNAPSHOT_FAILED`** is the one daemon change in Part B: a reason (kind `FAILED_PRECONDITION`, as now; metadata `workspace_id`) on `ReadError::Snapshot` (`read/mod.rs:102`) and on the write path's `ManagerError::RewriteSnapshot` (`workspace/rewrite.rs:320`), so the CLI recognizes the failure without reading the hint. The write path keeps its `next` (`reef ws inspect <id>`), which wins. A reason constant and comment rewordings only; `API_REVISION` stays 3.

## Implementation notes

- **Part A order**: `reef-error` and the re-exports (everything compiles, nothing else moves); `reef-client` with the client, `json` and `error`, and `pub use reef_client as client` in the daemon; then `paths` with test 8, `logging`, `backup`; then the CLI's imports, which should leave only `daemon run`, `config show` and `restore` naming the daemon; then `offline.rs`, the helper and `exec`, with tests 3 to 7; then `Cargo.toml`s and tests 1 and 2; then the reasons and the agent; then packaging and documents.
- **Moving without copying.** A moved item leaves a `pub use` at its old path in the daemon only where daemon code or tests name it; nothing in `reef-vcs` keeps a path through the daemon. Run `cargo tree -p reef-vcs -e normal -i jj-lib` after each step: it must print nothing by the end.
- **`exec`** with `std::os::unix::process::CommandExt::exec`; it returns only on failure, which is `CliError::Io` naming the program. Keep it before `init_logging` and the runtime, where `daemon run` dispatches now.
- **The helper's error object** is built by the same `ErrorObject` the CLI prints, from the error's `Classify`, `reason_of`, `ErrorChain` and `advice_of`, so `reef restore`'s output is byte-identical to today's for a given failure.
- **Tests that need `reef-daemon`.** Integration tests of `reef-vcs` cannot name another package's binary (`CARGO_BIN_EXE_*` is per package), so `daemon_bin()` builds it once per test process with `cargo build -p reef-daemon --bin reef-daemon --message-format=json-render-diagnostics` (plus `--release` when the tests are), into the same target directory and so beside `reef`. Concurrent test processes serialize on cargo's lock. CI's `cargo nextest run --workspace` has already built it.
- **Unit tests in `reef-vcs`** may keep using `reef_daemon` through dev-dependencies (`every_daemon_next_is_a_real_command` does); test 2 checks normal and build edges only.
- **Part B**: write `scope.rs` and its path conversion first, with unit tests over a fake current directory; then the read commands (16, 18, 19), the writes (20 to 24), files (25, 26), and the advice table (29) last, since every command feeds it.
- **Paging**: `log` and `op log` ask for `min(limit, 1000)` per page and stop at the limit; `diff` and `file list` follow every page; `file read` follows `offset` until `size`. The pinned operation of the first page makes the result one view; a token error mid-way is the table's "run the command again".
- **`show`'s second call** sends `to_revision` as the commit id `GetChange` returned and `at_operation` as its `at_operation`, with `skip_snapshot`, so it reads the same view and never snapshots twice.
- Linux: nothing here is `cfg(target_os = "linux")` in `reef-vcs`; `offline.rs` calls restore code that is. Before pushing, in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux"), run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy with and without `--all-features`, and `cargo tree -p reef-vcs -e normal --target x86_64-unknown-linux-musl -i jj-lib`.

## Risks

- **`cargo install` of one crate now gives a `reef` that cannot start a daemon.** Anyone following old instructions (`cargo install … reef-vcs`) gets exit 3 on their first command, with a hint naming the fix. The tarball, `install.sh` and Homebrew are unaffected. The README and quickstart change in the same PR.
- **A stale `reef-daemon` on `PATH`** now runs where `reef daemon run` used to guarantee a matching one. ADR 0029's add-only API and R2.01's restart rule cover an older v1 daemon (an unknown method restarts it, and the restart starts the same stale binary, which autostart then names); `reef daemon status` shows the version. Packaging ships both binaries together, so this needs a hand-built mix.
- **The CLI no longer validates the whole configuration.** A typo in `[watcher]` surfaces when the daemon starts (an autostart failure naming `reef daemon run`), not on every command. `reef config show` still reports it.
- **Crate names.** `reef-error` and `reef-client` were free on crates.io on 2026-10-26 (as were `reef-vcs-error` and `reef-vcs-client`, the fallbacks), but nothing reserves them until they are published, as ADR 0007 reserved the original four at 0.0.0. Reserving them is the user's step, not this ticket's; check again before the next release.
- **Prefix breakage.** `reef st` and `reef d` stop resolving (Part B). An agent that learned them gets a usage error listing the candidates, not a wrong command. Full names in the guide and the docs are unaffected.
- **The advice table can drift from the daemon's reasons.** A reason added later without a row keeps the daemon's API-worded hint, which is correct if awkward; test 29 lists the rows, and R2.13 and later tickets that add reasons say in their brief whether the CLI needs a row.

## Choices this brief made, and why

- **Split by the row's two sentences.** Part A has no user-visible change to review beyond reasons and a flag, and Part B is reviewed as an interface. Part A needs nothing R2.02 to R2.04 built.
- **Two new crates rather than one**: `reef-lib` needs `ErrorKind` and must not depend on tonic, so the error conventions sit below it alone.
- **The daemon binary runs the offline commands**, rather than the CLI linking the code they need: that code is the daemon library (`restore` recreates jj working copies), and a `reef` that links it is not thin.
- **The client reads three keys of the configuration file**, through the same layering the daemon uses, rather than all of it: the rest belongs to the daemon, and one function for the layering means one answer for the socket.
- **The agent name is a flag and a variable, and `ws run` passes it on**: a harness sets one variable per agent, and the agent's own `reef` calls inside `ws run` inherit it.
- **The CLI owns `next` for the API's reasons**, rather than the daemon building CLI argv from request fields: only the CLI knows which command ran, and MCP and SDK callers keep hints in the API's words.
- **`undo` and `abandon` require their argument**: with watchers and several agents recording operations, "the last one" and "the one I am on" are the wrong defaults to make implicit.
- **`file read` and `file list`, not `file edit`**: reading another revision without checking it out is useful from a shell; editing from a shell is what a workspace is for.
- **Paths relative to the current directory**, as `jj` takes them, so an agent in `src/` passes the paths its own tools use.

## What later tickets inherit

- **R2.27** starts from `reef-client` (Part A) and Part B of this file.
- **R2.13** builds `reef mcp` in a `reef` with no jj-lib, on `reef_client::Client`; it sends each tool caller's name with `with_agent`, keeps the daemon's API-worded hints (the CLI's advice table is the CLI's), and reuses `reef_client::json` where a tool returns what a command prints. `reef init`'s `.mcp.json` renderer runs `reef mcp`, which needs only `reef`.
- **R2.24** reads the command tree from clap and the schema from `reef_api::FILE_DESCRIPTOR_SET`, both in `reef`; JSON Schemas for command output derive from `reef_client::json`, where every output type lives.
- **R2.06 and R2.07** mirror `reef-client`'s surface (one method per RPC, page followers, the agent metadata, the probe for a mismatched daemon).
- **R2.08** adds its remote listener flag to `reef-daemon` and forwards it from `reef daemon run|start`; its token commands are `reef-client` calls.
- **R2.17** measures tokens through R2.27's commands as well as R2.13's tools.
- **R4.17** signs and notarizes two binaries; `reef daemon run` `exec`s the daemon, so the daemon process runs under `reef-daemon`'s signature.
- A later reason that a CLI command can hit adds its row to `cli/advice.rs` in the same PR.
