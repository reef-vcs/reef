# R2.05 The `reef` binary as a thin client

Phase 2 · Size M · Depends on: R2.01 (`reef-api`, the v1 schema and its stubs), R2.02 (`Workspaces.Status`, `Changes.Log|Get|Diff`, `Operations.Log|Get`), R2.03 (`Changes.Describe|Abandon|Squash`, `Operations.Undo`) · Unblocks: R2.13 (the MCP server reuses the client-side code), R2.24 (`reef schema` reads the finished command tree), R2.17 (the Reef arm of the token benchmark), R4.17; the phase's first exit criterion

## Context

The exit criterion reads "the CLI is a thin client with no direct jj-lib access", and `dev-phases.md` adds "remove jj-lib from the binary crate". The CLI has been a client since R1.22: `crates/reef-vcs/src` never names `reef_lib::jj` (`tests/cli.rs::no_jj_lib_in_binary`, `:674`) and every command but five goes through `Client`. The binary still links jj-lib, for three reasons that each date from a Phase 1 decision: `reef daemon run` runs the daemon in-process, and `reef daemon start` falls back to `reef daemon run` when no `reef-daemon` binary is beside `reef` or on `PATH` (R1.22; `cli/autostart.rs:131-137`), which is what lets `cargo install reef-vcs` alone work (`docs/quickstart.md:24`); `reef restore` is offline by design and calls `reef_daemon::maintenance::restore` directly (ADR 0020; `cli/restore.rs`); and `reef config show` prints the daemon's effective configuration with per-key sources through `reef_daemon::config::Config::load` (`cli/config.rs`). Beyond those, the CLI reaches into the daemon crate for small things a client should own: the state-directory and socket resolution (`Config::load` → `Paths`), `logging::init`, `client::default_owner`, `workspace::ROOT_CHECKOUT`, and the backup manifest.

This ticket keeps one binary (README, Departures: "R2.05 keeps one binary") and puts the three daemon-side commands behind a default-on Cargo feature, moves what a client owns into `reef-api`, and adds the Phase 2 commands over R2.02's and R2.03's RPCs, so that the exit criterion is tested with the feature off and the shipped binary keeps every Phase 1 promise.

## Decisions

- **One binary, one feature.** `reef-vcs` gets `[features] default = ["embedded-daemon", "watchman"]`, `embedded-daemon = ["dep:reef-daemon"]`, `watchman = ["reef-daemon?/watchman"]`; `reef-daemon` becomes `optional = true` and `reef-lib` is dropped (its error types come from `reef-api`). `reef-api` is a plain dependency. Behind `#[cfg(feature = "embedded-daemon")]`: `cli/daemon.rs::run_foreground` (`reef daemon run`), `cli/restore.rs`, `cli/config.rs`, and `autostart::locate`'s `exe daemon run` fallback. Without the feature the three commands still exist (names are additive, ADR 0025) and fail with `Unavailable` (exit 6): `reef restore is not available in this build (built without the embedded-daemon feature)`, hint `Install the reef-daemon binary beside reef, or build reef with its default features.`; `autostart::locate` returns `None` when neither `reef-daemon` is found, and `CliError::Autostart` says to install it. Released binaries keep the default features; the feature-off build exists for the exit criterion and CI.
- **What moves to `reef-api`** (beyond R2.01's move): `reef_api::paths` with `PathOverrides`, `Paths { state_dir, socket, config_file, pid, ... }`, `Paths::resolve(&PathOverrides)` and the platform defaults, lifted out of `reef_daemon::config` (`Layered`, `platform_defaults`, `PlatformDefaults`, `absolute`, `SOCKET_PATH_MAX`, the three env names) so there is one implementation; `reef_daemon::config::Config::load` calls `reef_api::paths` and re-exports `Paths` and `PathOverrides` so its 30 internal uses compile unchanged. `etcetera` and `nix` (`hostname`, `user`) become `reef-api` dependencies. `reef_api::paths::ClientConfig { daemon: { socket, pid_file }, repo: { auto_register } }` reads `config.toml` leniently (`#[serde(default)]`, unknown keys ignored, a parse error reported with the file and line) for the three keys a client needs; `Paths::resolve` applies `[daemon] socket` and `pid_file` from it as `Config::load` does today, so the CLI and the daemon agree on the socket whatever the file says. `reef_api::client::default_owner` (moved by R2.01) uses `reef_api::paths::{os_username, machine_hostname}`.
- **The CLI's own logging.** `cli/log.rs` initializes `tracing-subscriber` directly: `REEF_LOG` (else `warn`, `-v` debug, `-vv` trace), `REEF_LOG_FORMAT` `text|json` (else JSON when stderr is not a terminal, R0.09's rule), stderr only, invalid values exit 2. `tests/logging.rs` passes unchanged. The daemon's `logging` module stays the daemon's (file appender, rotation).
- **`reef backup`** prints `BackupProgress.summary` (R2.01) and reads no manifest; its JSON object keeps the field names `tests/backup.rs` asserts (`repos[].{id, files, bytes}`, `sqlite.bytes`, `complete`, `manifest_path`), so the summary message carries them.
- **New commands, all real client calls.** Each is one module under `cli/`, one JSON type in `reef_api::json` (added by the ticket that implements the RPC; this ticket adds the ones R2.02 and R2.03 did not), one `TextRender` in `cli/render.rs`:
  - `reef status [--repo <repo>] [--workspace <id|path>] [--no-snapshot]`: the workspace by `reef here`'s resolution (`REEF_WORKSPACE`, else the cwd), else `--workspace`, else with `--repo` the root checkout (`Workspaces.Status` with `workspace = "default"`, which R2.02 accepts). Text: the change (reverse-hex id, description's first line, divergent/conflicted flags), then `A path`, `M path`, `D path`, `R old -> new` lines, then `dirty` paths marked `+`, then `next` when the change is divergent: `reef squash <rev> --into <other>` when the other side is in another workspace and `reef abandon <rev>` otherwise, as `hint` and `next` in the JSON too (the only command besides `here` whose success output carries `next`). `snapshot_first = true` unless `--no-snapshot`, as `ws inspect`.
  - `reef log [REVSET] [--limit N]` (`Changes.Log`; default limit 100, 0 for everything, paging through `next_page_token`): one line per change: reverse-hex id (8 chars), author, age, bookmarks, the description's first line; `-o json` the array of `Change`.
  - `reef diff [--change <rev> | --from <rev> --to <rev>] [--stat | --files | --symbols] [--context N] [PATHS...]` (`Changes.Diff`): default target is the current workspace's change; default level `LINES`, rendered as a unified diff from the hunks (the daemon returns structured hunks; the CLI renders); `--stat` and `--files` the other levels; `--symbols` sends `SYMBOLS` and relays the daemon's answer, which is R2.15's stub until it lands; `--expand <name>` reserved for R2.15.
  - `reef ops [--limit N] [--kind K]... [--workspace W] [--owner O]` and `reef ops show <op>` (`Operations.Log`, `Get`): id (12 chars), age, kind, user, description.
  - `reef describe <rev> -m <text>` (`Changes.Describe`; `-m` required: never an editor), `reef undo [<op>]` (`Operations.Undo`), `reef abandon <rev>`, `reef squash <rev> [--into <rev>] [-m <text>]` (`Changes.Abandon|Squash`): each prints the operation id and, for `squash`, the resulting change; JSON is the response's JSON type.
  - `reef tree ls <rev> [PATH] [-r]`, `reef tree cat <rev> <PATH>`, `reef tree apply <change> (--set <PATH>=<file> | --set <PATH>=- | --delete <PATH>)... [-m <text>]` (`Trees.List|Read|Apply`): `cat` writes bytes to stdout untouched (`-o` ignored, as `guide`); `apply` reads each file (or stdin for `-`) and sends one `ApplyEditsRequest`. R2.04 may land after this ticket; the daemon's stub then answers `not implemented until R2.04` and the CLI relays it, which is the Phase 2 stub rule (no CLI-side stub for an RPC that exists in the schema).
  - CLI stubs for commands whose RPC or module a later ticket adds, as R1.22 did (`not implemented until R2.xx`, exit 1, no daemon contact): `watch` (R2.09), `presence` (R2.11), `replay` (R2.12), `mcp` (R2.13), `symbols` (R2.14), `query` (R2.16), `schema` (R2.24), `remote` (R2.08), `ui` (R2.18), `telemetry` (RX.03). Each later ticket replaces its stub.
  - Revisions: every `<rev>` argument is passed as given; the daemon resolves (R2.02's rules: Phase 1's forms plus `@`, `<ws-id>@`, `<rev>-`). The CLI resolves nothing itself.
- **`--help` and `about` budgets hold.** The root gains 19 commands over the phase (41 lines after this ticket, 51 at the end, of 60). `display_order`: `ws`, `here`, `status`, `diff`, `log`, `guide`, then the rest alphabetically; `ops`, `describe`, `undo`, `abandon`, `squash`, `tree` after `log`. No new global flags. `help_lists_every_command` learns the new nouns; `help_fits_sixty_lines` is unchanged and must pass.
- **The guide is rewritten** within the same budgets. The new text (1,595 bytes, 14 short lines, measured):

  ```text
  # Reef

  Reef gives each agent its own workspace: a copy-on-write copy of a git or
  jj repository, leased to one process and snapshotted after every write.
  Work lands as a jj change; nothing is lost when a workspace is released.

  From inside the repository:

      reef ws run -- <command>   # new workspace, run there, release it
      reef here                  # where am I, and what next
      reef status                # what changed here

  The first command in a repository registers it (adding jj beside git).
  Output is JSON when piped; errors carry `hint` and `next`, a command to run.
  <!-- reef:long -->

  ## Commands

  - `reef ws create` prints a new workspace's path; `reef ws release <id>`
    ends it. `reef ws list`, `reef ws inspect <id>`. Ids take 4+ characters.
  - `reef diff [--symbols]`, `reef log`, `reef ops`: the lines (or functions)
    that changed, the changes, the operations.
  - `reef describe <rev> -m <text>`, `reef undo`, and `reef squash` or
    `reef abandon` for a divergent change.
  - `cd "$(reef ws move -o text <id> --new-on main)"` moves to the next task.
  - `--repo <path|id>` names the repository; default: the current directory's.

  ## Inside ws run

  The command runs in the workspace directory with `REEF_WORKSPACE`,
  `REEF_WORKSPACE_PATH`, `REEF_REPO`, and `REEF_SOCKET` set; its lease is
  renewed until it exits.

  ## Output

  `-o json` or `REEF_OUTPUT=json` forces JSON: one object or array, or
  `{"error": {"kind", "message", "hint", "next"}}`. Exit 0 ok, 2 usage,
  3 not found, 4 exists, 5 conflict, 6 unavailable, 7 denied, 8 I/O,
  1 other; `ws run` exits as its command did.
  ```

  The "Not yet" section is gone. The MCP server is not named: R2.13 adds its line within the budget (the README asks for it in the guide; 5 bytes of headroom is not a line, so R2.13 trims elsewhere, most likely the `ws move` bullet). `reef init --check` in CI (`just agent-files`) will fail until the committed `AGENTS.md`, `CLAUDE.md` and skill are regenerated in this PR.
- **`reef here` learns the new commands.** `advise`: divergent → `reef status --workspace <id>` (whose own `next` is the squash or abandon); `attention` set → `reef ws inspect <id>` as today; the rest unchanged. The hint for the `status` orientation guess goes with `ORIENTATION_GUESSES` losing `status`.
- **The exit criterion as a test.** `ci.yml`'s `check` job gains `cargo build -p reef-vcs --no-default-features` and `! cargo tree -p reef-vcs --no-default-features -e normal | grep -q jj-lib` (and the same for `reef-daemon` and `rusqlite`); `tests/cli.rs::no_jj_lib_in_binary` keeps its source grep and adds that `reef_daemon::` appears only in `cli/daemon.rs`, `cli/restore.rs` and `cli/config.rs` and only under `cfg(feature = "embedded-daemon")`.
- **ADR 0030, "The `reef` binary as a thin client"**: the decision (one binary; the embedded daemon and the offline restore behind a default-on feature; everything else a client of `reef-api`; the feature-off build as the test), consequences (a `reef` built without the feature cannot start a daemon by itself and cannot restore; `cargo install reef-vcs` keeps working because the default is on; a new command that needs daemon code is a smell the test catches), alternatives (two binaries with `reef` never embedding the daemon: rejected, `cargo install reef-vcs` alone would stop working and R1.22's autostart fallback is what the quickstart promises; `restore` as an RPC: rejected, ADR 0020 made it offline so it can run against a stopped daemon; leaving jj-lib in: rejected by the exit criterion).

## Implementation notes

- Do the feature gate first, with no new commands, and get test 1 green; then the moves (`paths`, `log.rs`, `backup.rs`); then the commands. Three commits.
- `#[cfg(feature = "embedded-daemon")] mod restore;` plus `#[cfg(not(feature = "embedded-daemon"))] mod restore { pub(crate) fn run(..) -> Result<(), CliError> { Err(not_in_this_build("restore")) } }` with the same `Args` struct in both (keep `Args` outside the cfg so `--help` is identical in both builds; `help_fits_sixty_lines` runs in both).
- `cargo tree -e normal` on `reef-vcs` with the feature off still lists `reef-daemon` if any normal dependency pulls it; `reef-api` must not.
- The unified-diff renderer is the one piece of presentation logic in this ticket; keep it in `diff.rs` with unit tests on hand-written hunks (one-line change, add at end, delete at start, missing trailing newline). The MCP server (R2.13) returns the structured hunks, not this text.
- `reef status` with neither a workspace nor `--repo` outside every workspace: exit 3 with hint `reef here` (which says where you are) and `next` `["reef", "status", "--repo", "."]`.
- `reef log`'s `REVSET` positional conflicts with nothing: `reef log 'bookmarks()'`. Quote in the examples.
- Regenerate the agent files last and run `just agent-files`; the skill's frontmatter version string changes with the guide.
- Shared target directory: `reef-api`'s `build.rs` changed in R2.01, not here; still `touch` the protos when switching checkouts (Phase 1 note).

## Out of scope

- The services themselves (R2.02, R2.03, R2.04) and `--symbols` (R2.15); the CLI relays their stubs.
- `watch`, `presence`, `replay`, `mcp`, `symbols`, `query`, `schema`, `remote`, `ui`, `telemetry` beyond their stubs.
- Splitting `reef` and `reef-daemon` into separately installable packages, or moving `restore` into the daemon.
- Any change to the JSON shapes of Phase 1 commands.

## Risks

- **A feature-gated binary is two binaries to test.** The CI step builds and runs the thin build's tests on every push; the risk is a `cfg` path that compiles only one way, which `cargo build --no-default-features` catches on both runners.
- **`reef st` becomes ambiguous.** `status` and `store` share a prefix; clap errors instead of guessing (ADR 0025), and the alias test asserts the error names both. `sta` and `sto` resolve. Agents that learned `reef st` in Phase 1 get a usage error with the two names in it.
- **The guide has 5 bytes of headroom.** R2.13 needs a line for `reef mcp`; it will trim the `ws move` bullet. The budget is the stopping rule, as ADR 0025 intended.
- **`Paths` lifted into `reef-api` changes a well-tested module.** The tests move with it (`config/tests.rs` keeps the ones that need `Config`), and `reef config show`'s source attribution is unchanged because `Config::load` still owns the file read.
