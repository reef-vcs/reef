# R2.03 Snapshot, describe, and undo services

Phase 2 · Size M · Depends on: R2.01 (the `v1` schema with `Changes { Describe, Abandon, Squash }` and `Operations.Undo` as stubs; `Operation` and `ChangeRef` messages), R1.13 (the snapshot pipeline and ADR 0018's divergence rule this ticket resolves), R1.06 (`Repo::move_pointer`, `check_out_tree`, the move's roll-back shape), R2.02 (revision resolution, `read::with_head`, `Operation` conversion; may be implemented in parallel against R2.01's stubs with the resolver duplicated and reconciled at merge) · Unblocks: R2.04 (`Trees.Apply` reuses the rewrite-and-check-out helper), R2.05 (`reef describe|undo|abandon|squash`), R2.13 (the tools), R3.01 (evidence attaches to commits these write), R3.09 (lifecycle transitions are operations like these), R3.26 (agent-scoped undo narrows this undo)

## Context

The write side of the API, past what Phase 1 already had. Phase 1 writes were all about workspaces: create, snapshot, move, release. An agent that wanted to name its change, throw one away, undo a mistake, or fix the divergence two workspaces on one change produce had to run `jj` at the registered root, outside its workspace, with the daemon's working copies going stale under it (ADR 0018's `Updated` and `SiblingOperation` cases exist for exactly that). This ticket gives those four operations a typed RPC each, run on the repository thread as every transaction is, with the Reef workspaces they touch updated on disk by the daemon, so `jj` at the root stops being part of an agent's day. `Snapshot` itself is R1.05's RPC and is unchanged; the row's "snapshot now" is already served.

The headline case is divergence. ADR 0018 decided that a workspace whose working-copy commit was rewritten under it keeps its edits by rewriting the commit it last snapshotted into a second visible commit of the same change, and left resolution to this ticket: squash one side into the other, or abandon one. Both land here, and the quickstart's known limitation ("resolving it is a jj operation for now") closes.

## Decisions

- **Four RPCs, one transaction each, on the repository thread.** `Changes.Describe { repo, rev, description } -> { change: ChangeRef, op: Operation }`, `Changes.Abandon { repo, revs: repeated rev } -> { abandoned: repeated ChangeRef, op }`, `Changes.Squash { repo, rev, into: rev (empty = first parent), description (empty = keep `into`'s; `+` prefix appends `rev`'s), keep_emptied: bool } -> { result: ChangeRef, abandoned: repeated ChangeRef, op }`, `Operations.Undo { repo, op (empty = the head), what: oneof { operation (default) } } -> { undone: Operation, op: Operation, workspaces_updated: repeated string }`. Each runs `RepoHandle::call_async` with: `head.refresh()`, resolve, build the transaction, `set_attribute("reef.client", client)` (`socket` until R2.08 adds token names) and the Reef workspace name when the request named one, `commit(description)`, `head.adopt(new)`, return the plain result. Descriptions: `reef: describe <change>`, `reef: abandon <change>[, <change>…]`, `reef: squash <change> into <change>`, `reef: undo operation <op>`. `OpKind` (R2.02's `kind_of`) recognizes all four.
- **Then the workspaces follow.** After the transaction, every active Reef workspace whose `wc_commit_ids` entry changed between the old and new views (the daemon's own `default` checkout excluded: it is the user's, and `jj` at the root updates it as it always has; `attention` is not set for it) is checked out on the blocking pool: `Scheduler::pause(ws)`, `workspace_head(entry, false)`, `ws.set_head(new_head)`, `check_out_tree(new_wc_commit)`, the row's `commit_id`/`change_id` updated, the guard dropped, the `snapshots` index untouched (a check-out is not a snapshot). The response lists them in `workspaces_updated`. A check-out that fails (a file in the way, an I/O error) is logged at `error`, sets `attention = checkout-failed` (new value) on that workspace, and does not fail the RPC: the operation stands, the workspace's next snapshot finds itself stale and applies ADR 0018 (adopt if its files match, else diverge), so nothing is lost. The order is fixed: operation first, files second, as `undo_last` already does.
- **Pre-condition: no unsnapshotted edits in the workspaces a write will move.** Before the transaction, every active Reef workspace whose working-copy commit is `rev` (or `into`, or whose pointer the undo would move: computed by a dry merge, below) gets a `Snapshot` through the pipeline (`Manager::snapshot(ws, SnapshotKind::Explicit, "reef: snapshot workspace <id>")`), so the rewrite starts from what is on disk and a check-out afterwards replaces nothing the agent wrote. This is `jj`'s own order ("snapshot, then operate") and `undo_last`'s. The snapshots are ordinary operations with their own `op_id`s, listed in the response as `snapshots: repeated string`. A workspace whose snapshot fails fails the RPC with that error before anything is written.
- **`Describe`** rewrites `rev`'s commit with `rewrite_commit(&commit).set_description(text).write()`, then `rebase_descendants()` (descendants keep their ids; jj's rewrite semantics). A `rev` that resolves to the root commit is `InvalidArgument`. An empty description is allowed (it clears). The change id is unchanged; the response's `ChangeRef` carries the new commit id.
- **`Abandon`** records each commit with `record_abandoned_commit` and runs `rebase_descendants()`, which moves any workspace pointer on an abandoned commit to a new empty commit on its parents (jj's rule) and rebases children onto the parents. Refuses: the root commit (`InvalidArgument`); a commit that is the `default` workspace's working-copy commit when `[api] protect_root_checkout = true` (default; the user's checkout is not an agent's to abandon; `PermissionDenied` with a hint to run `jj abandon` there); a commit a bookmark points at unless `force` (`Conflict`, hint lists the bookmarks). Abandoning one side of a divergent change is the expected use: the Reef workspace on the abandoned side is checked out to the new empty commit the rebase gave it (a new change id, jj's behaviour), and the response says so; the other side is now the change's only visible commit and both rows' `divergent` and `attention` are cleared by a `Manager::recheck_divergence(change)` pass that reads `heads()` after the transaction (new helper; the pipeline's own setting of the flag stays).
- **`Squash`** is `jj squash -r <rev> --into <into>` with full selection: `squash_commits(mut_repo, &[CommitWithSelection { commit, selected_tree: commit.tree(), parent_tree: commit.parent_tree(repo) }], &destination, keep_emptied)` then `commit_builder.set_description(desc).write()`, `rebase_descendants()`. Default `into` is `rev`'s first parent (jj's default). Description rules as jj's `--message`/append. Refuses: `rev == into` (`InvalidArgument`); `into` an ancestor of `rev`'s descendants that would make a cycle (jj refuses, surfaced as `InvalidArgument`); the root. **The divergent case:** when `rev` and `into` are two visible commits of one change, the result keeps that change id (squashing into a commit of the same change leaves `into`'s id; jj's `squash_commits` writes the destination as a rewrite of `into`), the abandoned side's Reef workspace is moved onto the result (`edit`, so both workspaces now sit on one commit and the next snapshot of either is a plain rewrite), and `recheck_divergence` clears the flags. A `Squash` whose trees conflict produces a conflicted commit (jj semantics, `Commit::has_conflict()`), which the response reports as `result_conflicted = true` with a hint to `reef diff --change`; it is never refused for that reason, since conflicts are first-class (design principle 3).
- **`Undo`** resolves `op` with `resolve_op_with_repo` (`@` and the empty string are the head), then: refuses the root operation (`InvalidArgument`), an operation with more than one parent (`Conflict`, "cannot undo a merge of operation heads", as jj does), and an operation whose undo would remove the jj workspace of an *active* Reef workspace (`Conflict`, hint: release it first with `reef ws release <id>`; the root `default` workspace is protected the same way), found by a dry run: `let base = loader.load_at(&op)`, `other = loader.load_at(&op.parents()[0])`, a scratch `MutableRepo` from `start_transaction` merged with `merge(&base, &other)` and inspected, then `leave_unpublished`/dropped; the real transaction repeats the merge and commits. Undoing an undo is allowed (it is just an operation). Unlike `jj undo`, there is no undo-stack skipping (R3.26 defines scoped semantics); the response says exactly which operation was reversed. The operation's attributes carry `reef.undo_of = <op id>` and `jj.undo = <op id>` so a future `jj undo` at the root sees it as an undo (the jj form of the description is not used because `kind_of` and `is_reef_snapshot` key on `reef:` prefixes; see Risks). Workspaces whose pointer the undo moved are checked out as above; a workspace the undo moved onto a commit that no longer exists in the view (it was abandoned by the undone op's inverse) gets the new empty commit `rebase_descendants` creates, as `Abandon` does.
- **ADR 0046 "Undo, abandon and squash in Phase 2" (amends 0018).** Records: writes are transactions on the repository thread followed by check-outs of the Reef workspaces they moved; the snapshot-first pre-condition; undo as a view merge (`merge(op, parent)`) rather than a restore, and why (a restore throws away every operation after `op`; a merge reverses only `op`); the protected `default` checkout; divergence resolution through `Squash` and `Abandon` and the `recheck_divergence` pass; what stays for R3.26 (scoping to an agent's own operations, the conflict object on dependents). Alternatives: letting agents run `jj` at the root (rejected: the daemon's working copies go stale, and the agent leaves its workspace); refusing writes while any workspace has unsnapshotted edits (rejected: snapshot-first is cheap and never loses anything); `restore_view` semantics for undo (rejected: `jj op restore`, a different operation, which R3.26 may add as `Operations.Restore`).
- **CLI.** R2.05 wires `reef describe <rev> -m`, `reef undo [<op>]`, `reef abandon <rev>...`, `reef squash <rev> [--into <rev>] [-m] [--keep-emptied]`; this ticket adds the `Client` methods, the `reef_api::json` result types (`Described`, `Abandoned`, `Squashed`, `Undone`, each with the `Operation` and `workspaces_updated`), text renderers, and the `Advise` cases: a divergent workspace's `Status` (R2.02) gets `next = ["reef","squash",<other commit>,"--into",<this commit>]` from the daemon when the request came from inside one of the two workspaces, else a hint naming both commits.

## Implementation notes

- Keep every jj-lib call inside `reef_lib::jj::write` and the check-out inside `follow.rs`; the service layer sees plain ids. `write::*` take `&Arc<ReadonlyRepo>` (the thread's `head.repo.readonly()`), not `&mut Repo`, so the same functions serve a test's bare repository.
- `follow_pointer_moves` runs after `head.adopt(new)` so `handle.head()` (R2.02) already is the new head when the check-out loads it; take `Scheduler::pause(ws)` before locking `entry.jj`, as `move_.rs` does, and release it after the row update.
- The dry run for `Undo` must not publish: use `Transaction::write` then drop, or build the `MutableRepo` and inspect `view()` without committing; verify which is cheaper (both avoid an operation file: `write` creates one unpublished operation, so prefer inspecting the mutable repo before any write).
- `recheck_divergence` reads `handle.head()`, filters `view().heads()` by change id via the store, and updates rows and `WorkspaceEntry::set_attention` for every workspace on that change; it runs after every `Abandon` and `Squash`, and after the pipeline's own divergence setting it is the only thing that clears the flag.
- `protect_root_checkout` checks `View::get_wc_commit_id("default") == Some(commit)`; the check is per commit in `Abandon`'s list.
- The attribute `jj.undo` is a convention for jj to read; jj 0.46 does not read it (unverified). It costs nothing and documents intent; drop it if R2.09's index has no use for it.

## Out of scope

- Agent-scoped undo, undo of another agent's operation needing policy, and conflict objects on dependents (R3.26); `jj op restore` semantics (`Operations.Restore`, if ever).
- Partial squash (path selection, `--interactive`), `jj split`, `jj rebase`, bookmark manipulation (`jj bookmark`), `new` as an RPC (a workspace move or create is how a new change starts).
- Editing the `default` checkout's description or tree from the API beyond `Describe` of its commit (allowed: it does not move its files).
- The CLI commands themselves (R2.05) and MCP tools (R2.13).

## Risks

- **`jj undo` at the registered root does not see Reef's undo operations as undos** because the description is `reef: undo operation <op>`, not jj's prefix, so its undo-stack skipping treats them as ordinary operations (it would undo the undo, which is correct, just not what a user pressing `jj undo` twice expects). Using jj's description would make `kind_of` and `is_reef_snapshot`'s prefix matching accept a non-Reef description shape; the attribute `jj.undo` is the compromise and the ADR records it. If jj gains attribute-based undo detection, nothing changes on Reef's side.
- **A check-out over an agent's live directory**: `Undo`/`Abandon` rewrite files the agent may be editing at that moment. The snapshot-first rule bounds the loss to edits made between the snapshot and the check-out (milliseconds to a second), and those are visible to the next snapshot as stale-with-edits, which diverges rather than discards. The response names every updated workspace so a harness can tell its agent.
- **`squash_commits` with a conflicted source or destination** was not exercised in this brief; jj handles conflicted trees in squash (it merges trees), but the result's labels and `result_conflicted` reporting need test 10 to confirm the shape.
- **`rebase_descendants` after `Abandon` gives a workspace a new change id**, which an agent holding the old id in its context will not know. The response's `new_changes` and `reef here` (which reads the row) are the mitigations; `ws run`'s environment variable `REEF_CHANGE`, if one is added by R2.05, would be stale until re-read.
- **Snapshot-first can take a second on a `large` workspace** before a trivial `Describe`; it is the price of never losing an edit, and `Status(snapshot_first)` already pays it. A workspace with a fresh snapshot (no watcher events since) is skipped: the pipeline's `changed == false` path is cheap on a seeded tree state.
