# R2.03 Snapshot, describe, and undo services

Phase 2 · Size L (the row says M; see "Size" below) · Depends on: R2.01 (the declarations, `written_operation`), R2.02 (revision resolution, `Change`, effects, the `reef.kind` vocabulary) · Unblocks: R2.04, R2.05, R3.01, R3.09, R3.26

## Context

R2.01 declared the write side of `reef.api.v1` and left three RPCs answering `NOT_IMPLEMENTED`: `DescribeChange`, `AbandonChange` and `UndoOperation`. R2.02 built what they stand on: revisions as revsets resolved to exactly one commit, `Change` built from a commit, effects on every reported operation, and a classifier that reads the attribute `reef.kind` before falling back to descriptions. This ticket implements the three RPCs, starts writing the `reef.*` attributes on every operation Reef records, and reads the caller's `reef-agent` request metadata. "Snapshot now" is `SnapshotWorkspace`, which R2.01 ported and which needs only the attributes and the metadata.

The hard part is not the jj transactions. Each write rewrites commits that live workspaces may be sitting on, while their agents keep editing files and the watcher keeps snapshotting them. Phase 1 met this once, in `MoveWorkspace` (R1.06), which locks the one workspace it moves. Describe, abandon and undo can move any number of workspaces, so this ticket generalizes that discipline, and it is what makes abandoning one commit of a divergent change (ADR 0018) a resolution rather than a new divergence.

The CLI gains nothing a user sees: `reef describe`, `abandon` and `undo` are R2.05's. `Client` gains one method per RPC and a way to send `reef-agent`.

R2.01's rule binds this brief: it implements what R2.01 declared and adds only reasons and comment rewordings. It needs no schema addition; `API_REVISION` stays 2.

## Decisions

### Size

The row is M. This brief is L, for the same reason R2.02 grew: the RPCs are small, and what they require is not.

- Each write must coordinate with every live workspace it rewrites (their scan locks, a snapshot first, adoption after), which Phase 1 did only for the one workspace a move touches.
- Undo needs its own semantics: a revert, five classes of operation it refuses, and a supersession check.
- The attributes go on every operation Reef records: seven `reef-lib` functions change signature, and the agent reaches every write path in the daemon (create, release in five forms, move and its roll-back, every snapshot kind, rematerialize, store builds, registration).
- Rows' divergent marks are reconciled after writes, and ADR 0031 records the write side as ADR 0030 records the read side.

The README's "Departures" section says so, and `dev-phases.md`'s size column reads L.

### Where the code lives, and which thread runs it

- **jj work stays in `reef_lib::jj`.** A new module `rewrite.rs` holds `Repo::describe_commit` and `Repo::abandon_commit`; `undo.rs` gains `Repo::revert_operation` and `undoable`; `oplog.rs` gains `OpMeta`. They run on the repository thread through `RepoHandle::call_async`, as `move_pointer` does: writes commit on the one thread that commits (ADR 0012), unlike R2.02's reads.
- **Coordination lives in the daemon**, in a new `workspace/rewrite.rs`: `Manager::rewrite`, described under "Writes and live workspaces". The handlers in `service/changes.rs` and `service/operations.rs` validate, call it, and build responses with `written_operation`.

### Operation attributes on every write

- **`reef_lib::jj::oplog::OpMeta { description, kind: OpKind, snapshot_kind: Option<String>, workspace: Option<String>, agent: Option<String> }`**, with `apply(&self, &mut Transaction)`, which sets `reef.kind` always and the other three when they are non-empty. Every `reef-lib` function that took a `description: &str` for a transaction takes `&OpMeta` instead: `commit_snapshot`, `create_workspace_with` (and `create_workspace`), `forget_workspace`, `move_pointer`, `restore_pointer`, `import_git_refs`, and the internal `check_out_git_head`. `Repo::snapshot(description)` and `undo_last`, the one-process API the spike and its tests use, keep their signatures and build an `OpMeta` themselves (kinds `snapshot` and `undo`, no workspace, no agent).
- **What each write records:**

  | Operation | `reef.kind` | `reef.snapshot-kind` | `reef.workspace` | `reef.agent` |
  | --- | --- | --- | --- | --- |
  | snapshot of any kind | `snapshot` | `watcher`, `explicit`, `final`, `move`, `shutdown` | the workspace | the request's agent, else the owner |
  | create | `create-workspace` | | the new workspace | the request's agent, else the request's `owner` |
  | rematerialize | `other` | | the workspace | the owner |
  | release, reclaim, create failed or interrupted, directory missing | `release-workspace` | | the workspace | the request's agent (`ReleaseWorkspace` only), else the owner |
  | move's pointer, and its roll-back | `move-workspace` | | the workspace | the request's agent, else the owner |
  | import of git refs before a create or move | `import-refs` | | the workspace being created or moved | as that create or move |
  | `import git head` on `--init` registration | `other` | | | the request's agent, if any |
  | describe, abandon, undo | `describe`, `abandon`, `undo` | | the request's workspace, if named | the request's agent, else that workspace's owner |
  | a store build's scratch create and release | as create and release | | the scratch workspace | the request's agent, else `reef-store-build` |

  "The request's agent" is the `reef-agent` metadata below. jj-lib's own `initialize repo`, `add workspace 'default'` and `reconcile divergent operations` stay unattributed and classify as `EXTERNAL`; `OPERATION_KIND_OTHER`'s "repository initialization" example is true of `import git head`. GC writes no operation of its own and keeps attributes.
- **Descriptions.** The three new writes are described `reef: describe commit <commit id>` (the commit before the rewrite), `reef: abandon commit <commit id>` and `reef: undo operation <operation id>`, full hex. `classify`'s description fallback learns the three prefixes (kinds `DESCRIBE`, `ABANDON`, `UNDO`, no workspace from the text), so an operation whose attributes some other tool stripped still classifies. The descriptions of the existing writes do not change.
- **The write path and the listed path agree.** `convert::Written` keeps the kind, snapshot kind, workspace and agent the RPC knows, which are now exactly the attributes it wrote; `convert::operation` reads `oplog::ATTR_AGENT` instead of the literal. Test 15 checks every write.
- **jj workspace names do not change.** The new writes record no jj workspace name, as creates, moves and releases do not; `reef.workspace` names the workspace. Snapshots keep `reef-<id>`.

### The `reef-agent` request metadata

- **Key `reef-agent`**, a gRPC ASCII metadata entry, the constant `reef_api::AGENT_METADATA`. Trimmed; absent or empty means none. A value that is not visible ASCII (tonic's `to_str` fails) or longer than 256 bytes is `INVALID_ARGUMENT`, reason `INVALID_AGENT`. It names who caused the write; it is not authentication. One uid is one trust domain (ADR 0027), and R2.08 binds remote agents to their tokens.
- **Read by every handler that may record an operation**: `CreateWorkspace`, `ReleaseWorkspace`, `SnapshotWorkspace`, `MoveWorkspace`, `GetWorkspace` (with `snapshot_first`), the four reads that snapshot first (`GetStatus`, `ListChanges`, `GetChange`, `GetDiff`), `DescribeChange`, `AbandonChange`, `UndoOperation`, `BuildStore` and `RegisterRepository`. One helper, `service::agent_of(&MetadataMap) -> Result<Option<String>, Status>`, runs before anything else in each. Handlers that never write ignore the entry.
- **It reaches the manager as a parameter**: `CreateSpec.agent`, and an `agent: Option<&str>` on `Manager::snapshot`, `snapshot_for_read`, the release path and `move_to`. Watcher, shutdown and reclaim snapshots, and reclaims, have no request and use the owner.
- The `operations.proto` header and `Operation.agent`'s comment name the metadata (comment only).

### Writes and live workspaces

`Manager::rewrite(repo, write)` runs every describe, abandon and undo in five steps. `write` is a `Describe`, `Abandon` or `Undo` value carrying the request's fields, its workspace and its agent.

1. **Plan** (one repository job, nothing written). Describe and abandon run `refresh_for_resolve` first (a reload, plus an import of git refs in a colocated repository, as create and move do, `create.rs:613`); undo runs `RepoHead::refresh`, since it resolves no revision. The job resolves and checks the request as step 4 will, and returns the jj workspaces whose working-copy commit the write would move: for describe and abandon, those whose working-copy commit is in `<commit>::`; for undo, those in the undone operation's working-copy effects plus those whose working-copy commit is in `A::`, where `A` is the commits it made visible (still visible at head, or the undo is refused as superseded).
2. **Lock.** Take the repository's create lock shared, so GC and a forget wait, as a move does. For the active Reef workspaces among those, plus the request's workspace for an undo, pause automatic snapshots (`scheduler.pause`) and take each scan lock, in workspace id order, as GC does. GC takes the create lock exclusively before its scan locks, so it cannot interleave with a write holding the create lock shared. Workspaces that are not active are skipped; a releasing workspace's final snapshot holds its scan lock.
3. **Snapshot** (abandon and undo only). Snapshot each locked workspace with `snapshot_locked`, kind `explicit`, the default description and the request's agent, concurrently up to the scan permits. If one fails, the write stops and writes nothing: `FAILED_PRECONDITION`, `RewriteError::Snapshot`, with the advice "Nothing was written; workspace <id> could not be snapshotted. Inspect it, then retry." and `next` `reef ws inspect <id>`. These snapshots are operations of their own in the log; only an undo's request workspace's is reported (`snapshot`). Describe takes no snapshot: it changes no tree, so a workspace's unsnapshotted edits land on the rewritten commit at its next snapshot, which is fresh.
4. **Write** (one repository job). `refresh`, resolve again, check `expected_commit_id` and every precondition on what the request now names, run the transaction with its `OpMeta`, and publish. A working copy the write moves that step 2 did not lock (a create or move landed between steps 1 and 4) is logged at `info`; it follows ADR 0018 at its next snapshot.
5. **Follow** (locks still held). For each locked workspace whose working-copy commit moved: when the new commit's tree differs from the old one's, run `snapshot_locked`, kind `explicit`. A stale working copy with no edits since step 3 adopts the new commit: its files are checked out, no operation is written, and the row follows. When the tree is the same, call `follow_view` alone, with no scan. Then reconcile the divergent marks ("Workspace rows after a write"). A failure here is logged at `warn`; the write stands, and the workspace adopts at its next snapshot. Then unlock and unpause.

Why the locks, even for describe: without them, a describe of `@` committed between a snapshot's scan and its commit makes the change divergent (the verified race above), with the description on one commit and the edits on the other. Edits that reach the disk during steps 3 to 5 make the follow-up snapshot meet a stale working copy with edits, ADR 0018's fourth arm: the change diverges and nothing is lost. The window is one transaction.

A jj workspace outside Reef (the registered root's `default`) is never written by Reef. A write that rewrites its working-copy commit leaves the root stale for the `jj` CLI, which recovers with `jj workspace update-stale`, as it does whenever another jj workspace rewrites a shared commit.

### `SnapshotWorkspace`: snapshot now

Implemented since R2.01 and unchanged in behavior. It writes the attributes (kind `snapshot`, snapshot kind `explicit`, the workspace, the agent) and reads `reef-agent`. A custom `description` is now classified by its attribute rather than by its jj workspace name.

### `DescribeChange`

- **`revision`** is required (`REVISION_REQUIRED`) and resolved with `revset::resolve_revision` in the request's workspace's scope, so `@` and every R2.02 resolution error apply.
- **`expected_commit_id`**: empty skips the check. Otherwise it must be a full commit id in lowercase hex of the store's length, else `INVALID_ARGUMENT`, reason `INVALID_COMMIT_ID`, metadata `commit_id`. Prefixes are refused: every response carries full ids, and a short prefix would weaken the check. At step 4 the revision must resolve to exactly that commit, else `FAILED_PRECONDITION`, reason `EXPECTED_COMMIT_MISMATCH`, metadata `expected_commit_id` and `commit_id` (what it names now), with the hint "The revision now names <commit>; read it again and retry with that id."
- **Refused commits.** An immutable commit (in `immutable()`, which includes `root()`) is `FAILED_PRECONDITION`, reason `IMMUTABLE_REVISION`, metadata `commit_id`. A hidden commit, named by id and not visible at head, is `FAILED_PRECONDITION`, reason `HIDDEN_REVISION`, metadata `commit_id`: rewriting it would bring it back. Both come from `ChangeInfo.immutable` and `.hidden`.
- **The description** is stored as given, with a trailing newline added when it is non-empty and lacks one, as jj's CLI stores descriptions, so `jj log` shows it as jj would. A NUL is `INVALID_ARGUMENT`, reason `INVALID_DESCRIPTION`; there is no other limit beyond the message size. The field's comment says so.
- **Unchanged text** after that normalization writes nothing: `operation` unset, `change` the current commit. The checks above still run.
- **The write**: `rewrite_commit(commit).set_description(text)`, then `rebase_descendants()`. Descendants are rebased onto it with unchanged trees, local bookmarks follow, and working copies on it or its descendants move to their rewritten commits; none becomes stale, because no tree changed. The author stays; the committer becomes the daemon's identity at the current time, as jj-lib's rewrite does.
- **One commit of a divergent change** may be described by commit id (or `<change>/<n>`); the change stays divergent.
- **The response**: `change` from `log::Describer` at the new head, in the request's workspace's scope; `operation` through `written_operation` (kind `DESCRIBE`, the request's workspace, the agent), with effects.

### `AbandonChange`, and resolving a divergent change

- **Resolution, `expected_commit_id`, and the immutable and hidden refusals** are as for describe. `revision` is required. A divergent change id alone is `AMBIGUOUS_REVISION` with both commits in `commit_ids` (R2.02), whose hint names them; the caller names the commit to abandon by commit id, a unique prefix, or `<change>/<n>`.
- **A change that is not divergent at step 4** is abandoned as `jj abandon` does: `record_abandoned_commit`, then `rebase_descendants_with_options` with `delete_abandoned_bookmarks: true`. Descendants are rebased onto its parents. Local bookmarks on it are deleted, which is what `jj abandon` does without `--retain-bookmarks`; remote bookmarks are untouched. Every working copy on it moves to one new empty commit on its parents, shared by all of them, which those workspaces adopt in step 5, so their files become the parents' tree. The content stays in the operation log, and `UndoOperation` brings it back.
- **A divergent change** (more than one visible commit of the change at step 4) is resolved instead. The abandoned commit's successor is the change's other visible commit. When there are several, it is the newest by committer time, then by commit id descending, skipping any that descends from the abandoned commit. The write calls `set_rewritten_commit(abandoned, successor)` and then `rebase_descendants`:
  - descendants are rebased onto the successor, keeping the change's content under them, where a plain abandon would drop it;
  - bookmarks on the abandoned commit move to the successor;
  - working copies on it edit the successor (`update_wc_commits` takes the new commit when the old one was rewritten, not abandoned) and adopt its tree in step 5, so the losing workspace's directory shows the winning version and stays on the change.

  The effects report the abandoned commit as `HIDDEN`, the value R2.02 added for exactly this. With no eligible successor, the commit is abandoned plainly. The usual call comes from the workspace whose version wins: `revision` and `expected_commit_id` are the other version's commit id.
- **The response**: `abandoned_commit_id` (full hex, the commit step 4 abandoned) and `operation` (kind `ABANDON`), with effects.

### `UndoOperation`

- **Meaning: revert exactly one operation onto the current head, as `jj op revert` does.** Load the repository at the undone operation X and at its parent (`RepoLoader::load_at`). In a transaction on the head, run `MutableRepo::merge(&at_x, &at_parent)`, then `rebase_descendants()`: jj-cli's transaction finish does this, and `Transaction::write` asserts it was done. Keep the head view's git refs and git heads, as jj's default portions do, and commit with `reef: undo operation <X>`. What X created is abandoned or rewritten back, what X hid comes back, and the bookmarks and working copies X moved go back. Later operations stay. This is `Repo::revert_operation`. Unlike `undo_last`, a snapshot taken first is never what gets undone.
- **`operation_id`** is required and resolved with `oplog::resolve_operation` (R2.02): a full id or a unique prefix, with `INVALID_OPERATION_ID`, `AMBIGUOUS_OPERATION_ID` and `OPERATION_NOT_FOUND` as `GetOperation` returns them. GC rewrites operation ids, so a pre-GC id is not found.
- **`workspace`**, when named, must be active (else the existing `FAILED_PRECONDITION` for a workspace that is not). It is always locked and snapshotted first, as jj snapshots before every command, and that snapshot is `snapshot` when it recorded an operation. It is checked out afterwards when the undo moved its working copy (step 5). Other workspaces the undo moves are snapshotted first and adopt too; that is R1.13's adopt rule applied at once, and the field's comment is reworded to say so.
- **Never undoable**: `INVALID_ARGUMENT`, reason `OPERATION_NOT_UNDOABLE`, metadata `operation_id`, with a message saying why. Checked in step 1, before anything is snapshotted.
  - The root operation.
  - A merge of concurrent operations (several parents), which jj refuses too.
  - An operation that adds or forgets a jj workspace: Reef's creates, releases and rematerializations, or `jj workspace add` and `forget`. A revert would leave the daemon's rows and jj's workspace store disagreeing with the view, and `merge_wc_commit` removes a workspace when either side lacks it.
  - Reef's workspace moves (kind `MOVE_WORKSPACE`, not a snapshot, roll-backs included). A move also swapped the workspace's base and stores, which a view revert cannot undo; `MoveWorkspace` back is the undo.
  - An operation that changed the view's git refs or git heads: Reef's import of git refs, `import git head`, an external `jj git` command. Reef never writes git's refs or HEAD, so a revert would leave jj and git disagreeing about bookmarks. With these refused, the merge never changes the git portion, and test 6 asserts it.
- **Not in history**: `FAILED_PRECONDITION`, reason `OPERATION_NOT_IN_HISTORY`, metadata `operation_id`, when X is not an ancestor of the head at step 4 (`closest_common_ancestors([X], [head])` is not `[X]`), such as an operation written and never published. Reverting what the head never saw has no meaning.
- **Superseded**: `FAILED_PRECONDITION`, reason `OPERATION_SUPERSEDED`, metadata `operation_id`, when something X changed has changed again since. That is: a commit X made visible is no longer visible at head, a commit X hid is visible again, or a bookmark or working copy X moved is no longer where X left it. This is computed from X's effects, uncapped, against the head's view, with index lookups only. jj would revert anyway and merge, usually leaving changes divergent; refusing keeps every undo exact. The message names the first thing that moved, with the hint "Later operations changed what it did; undo them first, newest first (ListOperations with a change filter lists them)." The check runs at step 4, after the snapshots, and that is the point: a workspace's unsnapshotted edits since X supersede X instead of being overwritten by the checkout. Their snapshot stays in the log. R3.26 replaces this refusal with conflict objects.
- **Everything else is undoable**: snapshots of any kind, describes, abandons, undos (an undo of an undo re-applies), R2.04's edits, and `EXTERNAL` or `OTHER` operations that pass the checks. That includes operations recorded for other workspaces or agents and operations older than the request's workspace. An exact revert rebases any workspace built on X's commits (`A::`), and that workspace adopts in step 5. Agent scope and policy are R3.26's.
- **Nothing to revert** (the merge leaves the view as it was): no operation, `operation` unset, `undone_operation_id` set.
- **The response**: `operation` (kind `UNDO`), `snapshot`, and `undone_operation_id`, the full id.
- `Repo::undo_last` stays for the spike and its tests; its doc comment's "(R2.03)" points to `revert_operation`, which the daemon uses.

### Workspace rows after a write

In step 5, after the follows: every locked workspace whose working copy moved gets `divergent` set to whether its change is divergent at the new head; attention `divergent` is set when it became divergent and the workspace had no other attention, and cleared when it no longer is. Every other active workspace of the repository whose row says `divergent` has the flag and attention `divergent` cleared when its change is no longer divergent. That is one `divergent()` evaluation at the new head, matched against the rows' change ids. A resolving abandon therefore clears both workspaces' marks, and undoing it marks the workspace it moved back. Rows that diverge at snapshot time keep R1.13's rule.

## Amendments made during implementation

Made in R2.03's PR; the decisions above still describe the behavior except where these say otherwise.

- **Step 3 snapshots one workspace at a time, descendants first** (`rewrite::descendants_first`), not concurrently. Test 10 caught it: when an ancestor's snapshot committed first, it rebased a descendant's commit under the descendant's scan, which then met a stale working copy with edits and diverged. Only the order of step 3 changed; workspaces are still locked in id order.
- **The daemon's write errors are `ManagerError` variants** (`Rewrite`, `Undo`, `OpLookup`, `RewriteSnapshot`), as a move's are, rather than a daemon-side `RewriteError`; reef-lib's `RewriteError` and `UndoError` carry the reasons. The reasons' `ErrorKind` is `Conflict`, which is `FAILED_PRECONDITION`.
- **`OpKind::External` writes no `reef.kind`**: it stands for another jj client. Tests that write "behind the daemon's back" use it.
- **`Repo::init_in_git_repo` and `RepoRegistry::register` take the agent** for `import git head`; a rematerialization records the owner; a create interrupted by a crash has no row left, so its forget records no agent.
- **Undo's supersession check compares views directly** (commits by visibility through the change id index, bookmarks, tags and working copies) instead of going through `effects::operation_effects`; `visible_difference` and `bookmarks_of` are shared with `effects`. Tags an operation moved count too.
- **`plan_revert` refuses non-undoable and out-of-history operations at step 1**; supersession is checked at step 4, as specified.
- **`rewrite::working_copies`** reports every working copy's commit, change, tree and divergence before and after the write; step 5's follows and the divergent marks use it.
- **Test 15 covers** a create, an explicit snapshot, a read's snapshot, `GetWorkspace` with `snapshot_first`, a move (snapshot and pointer), describe, undo and a release through the daemon. reef-lib's test 1 covers create, move, restore, forget, describe, abandon and undo with every attribute, empty values, and GC; `revert_keeps_git_refs` covers `import git head` and a ref import. Watcher snapshots, reclaims and store builds pass the agent the same way and are not exercised separately.
- **From the code review** (the PR lists each finding): the divergent marks are reconciled from a fresh read of the head after the follows, and only for workspaces that moved, so a follow-up snapshot's own divergence keeps its mark; step 3's snapshots record the request's agent, else their own workspace's owner (only the write's operation falls back to the named workspace's owner); a revision naming a commit that step 3's snapshot rewrote follows it, or with `expected_commit_id` is `EXPECTED_COMMIT_MISMATCH` naming the new commit, and `HIDDEN_REVISION` gained a hint; reads after the commit log and degrade instead of failing an RPC whose write happened; step 4 reverts the operation id step 1 resolved in full; an empty revision and a malformed `expected_commit_id` are refused before a colocated repository's ref import writes anything; `Client::with_agent("")` sends no agent.
- **Undoing an operation already undone is `OPERATION_SUPERSEDED`**, not "no operation" as tests 6 and 12 said: the commits it made visible were hidden by the first undo. "Nothing to revert" (`operation` unset) remains for an operation that changed nothing in the view.
- **The write window is longer than one transaction** for the first workspace step 3 snapshots: it lasts through the later workspaces' scans, the write, and the follows. ADR 0031 says so.
- **Test 16's raw request** goes over a plain channel, since `Client::with_agent` refuses a 257-byte value itself (`ClientError::InvalidAgent`).

## Implementation notes

- Order: `OpMeta` and the attribute plumbing first, with test 1 and test 15's existing-write half (pure plumbing, and it de-risks the rest); then `reef-agent` and test 16; then `rewrite.rs` with tests 2 to 5; then `Manager::rewrite` with `DescribeChange` and tests 8 and 9; then `AbandonChange` and tests 10 and 11; then `revert_operation`, `UndoOperation` and tests 6, 7 and 12 to 14; then the client, the bench, the comments, and the documents.
- Never await a jj-lib future on a tokio worker. Steps 1 and 4 are `RepoHandle::call_async` jobs; snapshots go through `snapshot_locked`, which already runs its blocking half on the pool. SQLite (rows, owners) stays on the async side.
- Take scan locks in workspace id order, and pause before locking, as `move_detached` and `gc_jj` do (`gc_jj`'s comment, "as nothing else takes more than one", becomes untrue; reword it); a watcher snapshot waiting on a lock then sees the pause and skips. `Manager::rewrite` runs as its own task (`tokio::spawn`), as moves and snapshots do, so a dropped RPC cannot cut it between the write and the follows.
- Step 1's working-copy set for describe and abandon is `working_copies() & <commit>::` over the view, with `reef-` names kept. For undo, take `A` and the working-copy effects from `effects::operation_effects` with the cap raised to `usize::MAX`; the same walk feeds the supersession check.
- The successor candidates are the change's visible commits (the view's change id lookup, as `ChangeInfo.divergent` is computed) minus `<abandoned>::`, ordered as described. Find them in the step 4 transaction's base repository, not at step 1.
- `revert_operation` needs the head to contain X's index entries; `merge` merges both loaded repositories' indexes first (jj-lib `repo.rs:2049`), so no extra loading is needed.
- Linux: nothing here is `cfg(target_os = "linux")`, and the unfiltered fuse-overlayfs run in CI covers `writes.rs`. ## Risks

- **The write window.** Edits that reach the disk between a write's snapshot and its follow-up make the follow-up meet a stale working copy with edits: the change diverges, visibly, and nothing is lost. The window is one transaction, and test 9 bounds it in practice.
- **Writes wait on scans.** A write holds the scan locks of every workspace it moves and snapshots each first, so abandoning an ancestor of many busy workspaces, or of one large one mid-way through a long first scan, takes as long as those scans. That is the price of not losing their edits; the response is late, not wrong.
- **Undo is stricter than jj.** The supersession check refuses what `jj op revert` would merge, so an agent must undo newest first, and an edit made after a describe blocks undoing the describe until the edit's snapshot is undone. R3.26 relaxes this with conflict objects.
- **Abandon deletes local bookmarks** on a commit that is not divergent, as `jj abandon` does; an agent that abandons a commit someone bookmarked removes the bookmark. Undo restores it. In a colocated repository git keeps the ref until the `jj` CLI next exports, since Reef never writes git's refs.
- **Successor semantics depend on jj-lib internals**: `update_wc_commits` taking the first new commit for a rewritten working copy, and `update_heads` hiding every commit in the parent mapping. Test 4 pins both, so a jj-lib bump that changes them fails there.
- **The registered root's `default` workspace** goes stale for the `jj` CLI when a write rewrites its working-copy commit's tree; jj recovers with `jj workspace update-stale`, as it does for any other workspace's rewrite.
- **jj's CLI conventions this brief copies** (the trailing newline, the abandon bookmark default, `op revert` diverging where this brief refuses) were checked against the `jj` 0.46.0 binary, not read in source, since jj-cli is not in the registry. Tests 2, 3 and 6 pin Reef's behavior, so a jj change does not silently move it.
