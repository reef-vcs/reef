# R2.02 Status, log, and change services

Phase 2 · Size M · Depends on: R2.01 (the `reef.daemon.v1` schema with `Workspaces.Status`, `Changes { Log, Get, Diff }`, `Operations { Log, Get }` as `UNIMPLEMENTED` stubs; the `reef-api` crate; `Page`), R1.13 (the snapshot pipeline `Status` runs before reading), R1.16 (the `snapshots` index) · Unblocks: R2.05 (`reef status|log|diff|ops`), R2.09 (`Operation.kind` and the `changes` an operation moved, which the index reuses), R2.14 (symbol indexing reads trees through the same head), R2.15 (`Diff` at `SYMBOLS`), R2.23 (replaces `Status`'s scan with the index), R2.09 (the op-heads watch calls the reload this ticket makes reads see)

## Context

Phase 1 answered one question about a repository: which workspaces exist and what each is on. Everything else an agent wanted to know (what did I change, what is on this change, what happened in the last hour) needed `jj` at the registered root, which the agent guide said so in its "Not yet" section. This ticket implements the read side of the schema R2.01 reviewed: the working-copy status of a workspace, the change graph (`Log`, `Get`), structured diffs at three levels, and the operation log (`Log`, `Get`). Every response is data an agent can act on without parsing text: hunks are records, not unified-diff strings; changes carry their change id, commit id, parents and bookmarks; operations carry what they moved.

It also sets how reads run from now on. ADR 0012 put every jj transaction on the repository thread and said nothing about reads, because Phase 1 had none worth the name. Reads here can be large (a `large` diff, a 200-commit log) and frequent (a UI polling `Status`), and queueing them behind snapshots on one thread would make the thread the bottleneck the design warns against. `Arc<ReadonlyRepo>` is `Send + Sync` (R1.03's static assertion), so reads take the thread's current head and run on the blocking pool. ADR 0045 records it.

## Decisions

- **Reads run off the repository thread (ADR 0045).** `RepoHandle` gains `head() -> Arc<ReadonlyRepo>`: the thread keeps an `Arc<arc_swap::ArcSwap<ReadonlyRepo>>` shared with every handle and stores into it in `RepoHead::adopt`, `RepoHead::reload` and after `Repo::reload_if_moved` returns `true` inside `refresh`, so a handle's `head()` is the thread's most recent head with no job and no lock. A read RPC loads `head()` once, runs its jj-lib calls inside `tokio::task::spawn_blocking` with `pollster::block_on` (jj-lib's futures are not `Send`), under `AppState.reads: tokio::sync::Semaphore` of `[api] max_concurrent_reads` permits (default `available_parallelism`, as `watcher.max_concurrent_scans`). A read never starts a transaction. The head a read sees may lag an operation another process wrote in the last moments (`reload_if_moved` runs on the thread's own schedule until R2.09's op-heads watch); `Daemon.Status` already says which `op_id` the daemon is at, and every read response carries `at_op` (the head it answered from) so a client can tell.
- **`Workspaces.Status`** answers for one workspace: `{ workspace, change: ChangeRef, parents: repeated ChangeRef, files: repeated StatusFile { path, kind: ADDED | MODIFIED | REMOVED (RENAMED is reserved and never produced; see Out of scope), conflicted: bool, executable_changed: bool, size_before, size_after }, conflicted: bool, divergent: bool, divergent_commits: repeated string, attention, dirty_paths: repeated string, from_index: bool, snapshot_op_id, at_op }`. With `snapshot_first = true` (the CLI default, as `Inspect`'s) the Phase 1 pipeline runs first and `snapshot_op_id` is what it recorded; `files` is the diff of the working-copy commit's tree against its parent tree (`Commit::parent_tree`, `diff_stream`, `EverythingMatcher`), `conflicted` is `Commit::has_conflict()`, `divergent` and `attention` come from the row, `divergent_commits` are the other visible commits of the change (`Repo::heads()` filtered by change id, as R1.23's test 5 reads them), `dirty_paths` is empty and `from_index` is `false` in this ticket: R2.23 fills both from the status index and skips the scan. The response shape is fixed here so R2.23 changes the source and nothing else. Without `snapshot_first` the answer reflects the last snapshot and says so (`snapshot_op_id` empty).
- **`Changes.Log`** takes `{ repo, revset, page, with_graph: bool }`. An empty `revset` means `reef_log()`, an alias the daemon defines as the README fixes it ("every visible head and its ancestors down to the nearest bookmark or 200 commits, whichever is first"): in revset terms `(bookmarks()..visible_heads()) | visible_heads() | bookmarks()`, capped at 200 commits by the page walker, with `ancestors(visible_heads(), 200)` when the repository has no bookmark. The alias is registered in the `RevsetAliasesMap` the daemon builds, so `reef_log()` can be used inside a user's revset too. Parsing: `RevsetParseContext` with `user_email` from `[identity]`, `default_ignored_remote = Some("git")` as jj does for colocated repositories, `workspace = Some(RevsetWorkspaceContext { workspace_name: "default", path_converter })` so a bare `@` is the user's checkout; `<ws-id>@` is rewritten to `reef-<ws-id>@` before parsing when `<ws-id>` is a known workspace id or unique prefix (jj's `name@` syntax then resolves it); `SymbolResolver::new(&*repo, &[] as &[Box<dyn SymbolResolverExtension>])`. A parse or resolution error is `InvalidArgument` with jj's message and, for an unknown symbol, a hint naming `reef log` with no argument. Evaluation streams `stream_graph` (`revset.rs:3529`) when `with_graph`, else `stream`; each commit becomes a `Change` (README shape) with `workspaces` from `View::workspaces_for_wc_commit_id` mapped back to Reef ids (`reef-<id>` → `<id>`, `default` stays `default`) and, when asked, `edges: repeated GraphEdge { target: ChangeRef, kind: GraphEdge.Kind }` (R2.01's message) straight from `jj_core::graph::GraphEdge` (`graph.rs:33-85`). `stream_graph` yields `GraphNode<CommitId>`, that is `(CommitId, Vec<GraphEdge<CommitId>>)`, not commits, so with `with_graph` the stream is `TopoGroupedGraph::new(revset.stream_graph(), |id| id).stream()` (`graph.rs:133-346`; `new` takes `Fn(&N) -> &ID`, and the wrapper is not itself a `Stream` until `.stream()`), with `prioritize_branch(wc_commit_id)` for the `default` workspace's working-copy commit first as `jj log` does, and each node's commit then loaded with `store().get_commit_async(&id)`; `RevsetStreamExt::commits` (`revset.rs:3559-3580`) adapts only the plain id stream, not the graph stream. Each edge's `target.change_id` is looked up the same way (a `MISSING` target outside the set still has a commit id; its change id is filled when the commit loads and left empty if it does not). Rows therefore come in `TopoGroupedGraph` order, which R2.19 lays out without braiding; without `with_graph`, rows are in the revset's own index order. Pagination walks the stream `page_size` commits and encodes the cursor as the last commit id plus a hash of `(revset, with_graph)`; the next page re-evaluates the revset at the current head and skips to the cursor, so a page token survives new operations (without `with_graph` the stream is in index order, so new descendants appear before the cursor and are simply not shown on later pages). With `with_graph`, `TopoGroupedGraph` reorders: a new child on a mid-list commit pulls that commit's branch earlier, so later pages may repeat or skip a row; the disjoint-pages guarantee (test 7) is made for `with_graph = false` only, and the graph's one client (R2.19) reads a single page. A token whose head differs is still valid; a token whose request hash differs is `InvalidArgument`.
- **`Changes.Get`** `{ repo, rev }` returns one `Change` plus `files_changed: uint32`, `insertions`, `deletions` (the `STAT` numbers against the parents) and `other_commits_of_change` (divergence). `rev` resolves as the README's revisions row: Phase 1's `resolve_revision` plus `@`, `<ws-id>@`, and a trailing `-` for the first parent, implemented by a small `reef_daemon::revision::parse` that strips the suffix and maps the `@` forms to jj workspace names before calling jj; no revset language outside `Log`.
- **`Changes.Diff`** `{ repo, oneof target { change: rev, range: { from: rev, to: rev } }, level, paths, context_lines }`. `change` diffs the commit's tree against `parent_tree` (jj's merged parent tree, so a merge commit diffs against the auto-merge as `jj diff` does). `paths` are repository-relative prefixes through `PrefixMatcher`; empty means everything. Levels: `STAT` returns per-file `{ path, kind, insertions, deletions, binary }` and totals; `FILES` returns the paths and kinds only; `LINES` returns `FileDiff { path, kind, binary, old_size, new_size, executable_before, executable_after, hunks: repeated DiffHunk { old_start, old_lines, new_start, new_lines, lines: repeated DiffLine { kind: CONTEXT | ADDED | REMOVED, text: bytes } } }` built from `ContentDiff::by_line([old, new]).hunks()` with `context_lines` (default 3) of `Matching` lines kept around each `Different` run and the rest elided, line numbers counted from newlines in the contents; `SYMBOLS` is `UNIMPLEMENTED` with hint `not implemented until R2.15`. A file is `binary` when either side contains a NUL byte in its first 8 KiB or exceeds `[api] max_diff_file_size` (default 4 MiB); binary files report sizes and no hunks. Symlinks diff their targets as one-line texts. A conflicted path reports `conflicted = true` and its materialized conflict markers as the text on that side (jj's `materialize_merge_result`), marked so the CLI can render them; that is the only place markers appear in the API. The whole response is bounded by `[api] max_diff_bytes` (default 16 MiB); past it the response sets `truncated = true` and names the first omitted path, and the client narrows with `paths`.
- **`Operations.Log`** `{ repo, page, filter: { kinds, workspace_id, owner_username, since, until } }` walks `walk_ancestors` from the head, newest first, into `Operation` messages (README shape): `kind` derived by a new `reef_lib::jj::oplog::kind_of(&OpEntry) -> OpKind` that extends `described()`'s prefix matching with `create`, `release`, `move`, `undo` (`UNDO_OP_DESC_PREFIX`), `describe`, `abandon`, `squash`, `apply` (R2.03's and R2.04's descriptions), `gc`, `import` (`import git refs`) and `external` for anything else; `workspace_id` from `reef-<id>` names; `changes` computed on request from the view diff against the first parent (`head_ids` and `wc_commit_ids` symmetric difference, deduplicated by change id, capped at 50 with `changes_truncated`); `seq` is 0 until R2.09 indexes operations, and R2.09 switches `Operations.Log` to read the index when it is complete for the range asked. The cursor is the last operation id; the walk resumes with `walk_ancestors` from that operation.
- **`Operations.Get`** `{ repo, op }` resolves `op` with `resolve_op_with_repo` (so `@`, full ids and unique prefixes work) and returns the `Operation` plus `view_summary { heads: repeated ChangeRef, workspaces: map<string, ChangeRef>, bookmarks: map<string, commit_id> }` for the UI and R2.12.
- **Resolution of `rev` through the same head.** A helper `reef_daemon::revision::resolve(head: &Arc<ReadonlyRepo>, workspaces: &dyn Fn(&str) -> Option<WorkspaceId>, text) -> Result<Resolved, ResolveError>` wraps `Repo::resolve_revision`'s logic over a plain `ReadonlyRepo` (the logic moves from `reef_lib::jj::workspace::resolve_revision_unlogged` into a free function `reef_lib::jj::resolve::revision(&ReadonlyRepo, text)` that the `Repo` method calls, so `Create` and the reads share one resolver). The `@` forms are resolved against `View::wc_commit_ids`.
- **One read module per service.** `reef_daemon::service::changes`, `service::operations`, and `Workspaces.Status` in `service::workspaces`; the jj work lives in `reef_daemon::read::{status, log, diff, oplog}` as plain functions over `Arc<ReadonlyRepo>` so R2.13's MCP server and R2.23 reuse them without the gRPC layer, and so unit tests run them against a `TestDaemon`'s repository without a socket.
- **Errors.** Unknown `rev`/`revset` symbol → `NotFound` (resolution) or `InvalidArgument` (parse), with `hint`; a `rev` that is ambiguous → `InvalidArgument` listing up to ten candidates as R1.05 did; a workspace that is not `active` → `Conflict` with `next` `reef ws create --repo <id>`; the semaphore saturated → requests wait (no error; `[api] read_timeout`, default 60 s, then `Unavailable` with a hint to retry). `Classify` and `Advise` as Phase 1.
- **CLI.** R2.05 owns `reef status`, `reef log`, `reef diff`, `reef ops`; this ticket adds the `Client` methods (`status`, `log`, `get_change`, `diff`, `op_log`, `get_op`) and the `reef_api::json` types (`Status`, `Change`, `FileDiff`, `Operation`, …) they return, and the `-o text` renderers for them in `render.rs` so R2.05 only wires clap. The unified-diff text renderer (`---`/`+++`/`@@` from `DiffHunk`) lives in `reef_api::json::diff::unified`, shared with the MCP server's text fallback.

### `docs/adr/0045-reads-off-the-repository-thread.md`, `docs/adr/README.md`

Context: ADR 0012 and what Phase 2 adds. Decision: `RepoHandle::head()` through `ArcSwap`, reads on the blocking pool under a semaphore, writes unchanged, `at_op` on read responses. Consequences: a read may lag an external operation until the next reload (R2.09 shortens this); the repository thread stays the write lock; the number of concurrent reads is bounded and configurable. Alternatives: reads as jobs (rejected: the thread becomes the bottleneck and a `large` diff blocks snapshots), a second thread per repository for reads (rejected: `Arc<ReadonlyRepo>` is `Sync`, so no thread is needed), `RwLock<Arc<ReadonlyRepo>>` (rejected: `ArcSwap` has no writer starvation and no lock to poison).

## Tests

`crates/reef-daemon/tests/reads.rs`, through `TestDaemon::with_synthetic_repo(Preset::Small)` unless stated.

1. `status_after_edit_lists_the_file`: create a workspace, write `a.txt`, modify a tracked file, delete another; `Status(snapshot_first = true)` lists `A a.txt`, `M ...`, `D ...` with sizes, `conflicted == false`, `from_index == false`, `snapshot_op_id` non-empty and equal to the `snapshots` row; a second `Status` has `snapshot_op_id` empty and the same files.

## Implementation notes

- Keep jj-lib types out of `service/`: `read::*` return plain structs, `convert.rs` maps them. The MCP server (R2.13) and R2.23 call `read::*` directly.
- `with_head` acquires the permit before `spawn_blocking`, times the wait, and logs `read waited for a permit` at `info` with `waited_ms` when it exceeded 100 ms; the timeout covers permit wait plus work.
- `ContentDiff::by_line` works on bytes; `DiffLine.text` is `bytes`, and `json` types carry it as a string with lossy UTF-8 plus a `lossy: bool` flag per file, so a Latin-1 file does not fail the whole diff.
- For the line numbers: iterate `hunks()`, count `b'\n'` in each side's content (a final line without `\n` counts as a line), keep a running `(old_line, new_line)`; emit a `Hunk` per `Different` run merged with its `context_lines` neighbours, splitting a `Matching` run longer than `2 * context_lines` as `diff -U` does.
- `changes_moved`: load the op's first parent's view (`Operation::parents().await` then `view()`), diff `head_ids` and `wc_commit_ids`, map commit ids to change ids with `store().get_commit_async`; a commit that GC has dropped is skipped with a `debug` log, never an error. Operations with no parent (the root) report none.
- The page token is `base64url(json!({ "a": after, "h": request_hash }))`; `request_hash` is `blake3` of the canonical request fields truncated to 64 bits. Tokens are opaque to clients; the CLI never shows them.
- `Status` with `snapshot_first` must take the workspace's `scan_lock` through `Manager::snapshot` exactly as `Inspect` does (`service/workspaces.rs:187`), never bypassing the scheduler's pause; the diff after it reads the head the snapshot adopted (`SnapshotOutcome.op_id`), by loading `handle.head()` after the snapshot returns.
- Register `reef_log()` in the aliases map rather than special-casing an empty string in the parser so `reef log 'reef_log() & author(x)'` works; the 200-commit cap is applied by the page walker, not the revset, so `count_estimate` is not needed.
- Verify `RevsetExtensions::default()` and `RepoPathUiConverter::Fs { cwd, base }` exist in 0.46 before relying on them; the brief did not check them (Risks).

## Out of scope

- Renames and copies in diffs (`diff_stream_with_copies`): Phase 1 trees carry no copy records; a `RENAMED` kind is reserved in the enum and never produced.
- Word-level diffs (`ContentDiff::by_word`), ignore-whitespace options, and syntax highlighting.
- `Changes.Log` over the index instead of jj (R2.09 for operations; changes stay jj's).
- The status index (R2.23), symbol diffs (R2.15), the CLI commands (R2.05), the op-heads watch (R2.09).
- Any write (R2.03, R2.04).

## Risks

- **Revset parsing needs a `RepoPathUiConverter` and extension maps the brief did not verify.** `RevsetWorkspaceContext.path_converter` is required for fileset functions (`files(...)`); if constructing it needs a cwd that makes no sense for a daemon, pass the repository root as both `cwd` and `base` and document that `files()` patterns are root-relative. A missing `Default` for `RevsetExtensions` or the alias maps is a few lines of construction either way.
- **Line numbers derived from hunk contents** can drift from `diff -U` on files without a trailing newline; test 9 and the property test in 19 pin the rule (a final partial line is a line) and `unified` prints `\ No newline at end of file` for it.
- **A read can see a head one operation old** until the thread reloads. `at_op` makes it visible, and R2.09's op-heads watch closes most of the window; a client that must see its own write reads the `op_id` the write returned and retries when `at_op` is older (the SDKs do this in their wrappers, R2.06/R2.07).
- **`large` diffs are bounded by bytes, not by time**: a `Diff` over 100,000 changed files at `FILES` level is a tree walk of changed subtrees only (O(changed)), but at `LINES` it reads every changed blob; the byte limit and `paths` are the controls, and the semaphore keeps the pool from filling with them.
- **`squash`/`abandon` (R2.03) change what `Log` shows mid-page**; the cursor-by-commit-id design tolerates a cursor commit that is now hidden: the walker skips until it sees the cursor, and when the cursor is gone from the stream it restarts from the first page and sets `page.restarted = true` so the client knows to redraw. Test 7 covers new operations; a hidden cursor is covered by a unit test on the walker.
