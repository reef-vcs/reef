# R2.26 Workspace provider contract

Phase 2 · Size M · Depends on: R2.13 (the lease rule for workspaces a tool hands out: kept alive while their holder runs, never released at its exit), R1.21 (`ws run`'s create, attach and heartbeater), and two the row does not list: R2.11 (`reef ws renew`, which grows the `--follow` its open question 2 asked about) and R2.25 (#154: the agent table's rows and the plugin trees the adapter ships in) · Unblocks: none listed (every later harness adapter is a row and a test; R3.12 can resume a session in a provider's workspace through `attach`)

## Context

Harnesses isolate parallel work in git worktrees: a session started with `--worktree`, a subagent with `isolation: worktree`, an orchestrator's task. Each worktree is a full checkout with no owner and no expiry, which is the problem Reef exists to remove (design document, "Git worktrees"). Today a harness gets Reef in one of two ways, and neither touches its own isolation. Either the whole session runs inside one workspace (`reef ws run -- <harness>`), or the agent creates workspaces itself through the CLI or `reef mcp`. A harness that makes a worktree per session or per subagent still makes a git worktree.

The row asks for three things:

1. A small documented interface with three verbs (create, attach, release) and JSON in and out.
2. A reference adapter, so a harness that creates git worktrees can ask Reef for a workspace instead.
3. The upstream conversation with the first harness.

Three earlier briefs left this ticket promises:

- **R2.13** (`R2.13-mcp-server.md` lines 320, 343) says R2.26 builds on `create_workspace`, `release_workspace` and the MCP lease rule: heartbeat while the server runs, release nothing at exit, a shared `:mcp` owner. It also names the provider contract as the fix for "a harness's file tools may not reach a workspace", because a workspace outside the project draws a permission prompt for each edit.
- **R2.11** (line 263, open question 2) says the contract keeps a workspace it hands out alive with `reef ws renew`, or with a `ws run`-style heartbeat if one is added. It also says "R2.26 is the first ticket that would need either" a lease length on renew or `ws renew --follow`.
- **R2.25** (#154, `R2.25-harness-packages.md` line 570) says the contract reaches harnesses through these packages, and a harness that adopts it gets the contract in its row.

### What was verified while writing this ticket

Paths are under `crates/reef-vcs/src/` unless they start with `crates/` or `docs/`.

- **Create.** `ws create` is `cli/ws.rs:516`, sharing `CreateTarget` (`:121`) with `ws run`. The owner defaults to `default_owner()`, which is `<user>@<host>` (`reef-client/src/lib.rs:1700`). `-o text` prints only the path (`cli/render.rs:213`). `-o json` prints `Created`: 27 keys, the workspace's fields plus `op_id`, `shared_change`, `materialize_ms`, `base_was_cached`, `timings` and `start`. This was checked against a scratch daemon (`REEF_STATE_DIR` in the session scratchpad, `REEF_SOCKET=/tmp/r226/d.sock`).
- **Attach.** `ws run --workspace` is `attach` (`cli/ws_run.rs:310`). It inspects without a snapshot and requires an active workspace with an `active` or `in_grace` lease. Its owner check is `may_attach` (`:345`): the holder must be `<user>@<host>` with or without a `:<suffix>`, unless `--owner` names it. It then renews once. On a released workspace it exits 5 with no `hint` or `next` (checked on the scratch daemon). That is a small gap, which this ticket fixes for its own attach.
- **Renew.** `ws renew` (`cli/ws.rs:374`) renews once. It runs no loop and has no `--follow`. `Heartbeater` (`cli/heartbeat.rs:66`) and `heartbeats` (`:21`) renew every `heartbeat_every`, back off 1 to 30 s while the daemon is unreachable, and stop when the lease is gone (`Conflict` or `NotFound`). `reef mcp` runs one heartbeat task per workspace it holds, with owner `<user>@<host>:mcp` (`mcp/leases.rs`).
- **Lease numbers** (ADR 0019, `reef-daemon/src/config.rs:291`):
  - `lease.default` 30 m, grace 5 m, `max` 24 h, heartbeat 60 s.
  - `heartbeat_every` is clamped to a third of the lease. A `--lease 2m` create on the scratch daemon returned `heartbeat_every_ms: 40000`.
  - A dead holder's directory therefore lives at most length + grace + tick: 35 m 10 s by default.
- **Release.**
  - Releasing a path inside an active workspace releases it with a final snapshot. On the scratch daemon this printed `{"id", "final_op_id", "snapshot_taken": true, "freed_bytes"}`.
  - Releasing the same path again exits 3 with `kind: not_found`, `reason: WORKSPACE_NOT_FOUND`, because the directory is gone.
  - Releasing the released workspace by id exits 5 (`conflict`, no `reason`), with `hint` and `next` `reef ws create --repo <id>`.
  - `ws renew` of it also exits 5.
  - A directory that is no workspace exits 3, `WORKSPACE_NOT_FOUND`.
- **Paths.**
  - `CreateWorkspaceRequest.path` must not exist.
  - A released or reclaimed workspace keeps its path until GC deletes its row (`PathRecorded`, `reef-daemon/src/workspace/mod.rs:469`), so a workspace cannot be re-created at the path it had.
  - A create with `--path` inside the repository's own checkout succeeds; the scratch daemon accepted `<repo>/.wt/one`.

## Decisions

### Size

M. The pieces are:

1. three leaf commands that read a request from flags or stdin JSON and print one result;
2. `ws renew --follow`, a detached lease holder bound to the harness's process, with a holder record;
3. `reef here` reading that record;
4. the reference adapter as a row in the agent table and a plugin tree rendered from it;
5. the contract document, its JSON Schemas through R2.24, and an ADR;
6. the upstream drafts;
7. about fifteen tests, one of them driving the adapter end to end.

No daemon change, no API revision, no new crate. If it must shrink, the `attach` hook on resume and the follower's holder record move to a follow-up, and `here` keeps telling agents to release (see "Risks").

### What create, attach and release mean

The three verbs map onto the lifecycle that exists. None needs a new RPC.

- **create**: `CreateWorkspace`, with the provider's owner and purpose, and then a holder that keeps the lease alive while the harness lives (below). The workspace is at the daemon's default path, never one the harness suggests. A directory inside the checkout would be refused by a harness's "is this inside a repository" check, and the root's jj and git would see it as untracked files.
  - **The start.** If `repo` resolves to a path inside an active Reef workspace (a subagent of a session that is itself in a provider's workspace), the new workspace starts as a new change on that workspace's change, after a snapshot (`GetWorkspace` with `snapshot_first`). The subagent then builds on its parent's files, as a worktree made from `HEAD` builds on its parent's commits. Otherwise the start is the daemon's default (R1.31), or `change` / `new_on` when given.
  - **The name.** With a `name`, create is **create or attach**:
    - **No match**: if no active workspace in that repository has the owner `<user>@<host>:<name>` (`ListWorkspaces` with `owner`), it creates one with that owner.
    - **A match**: if one does, it attaches to it and returns it with `attached: true`. This matches a harness that "opens [an existing worktree] instead of creating a new one" for a repeated name, and it makes a retried create safe.
    - **Refused names**: a `name` that is empty, all digits, `mcp`, longer than 64 characters, or contains anything but ASCII letters, digits, `.`, `_` and `-` is refused (`PROVIDER_INPUT_INVALID`). The first three would collide with `ws run`'s `:<pid>` owners and the MCP server's `:mcp`.
- **attach**: take over an existing active workspace for a new holder. This is the resumed or restarted session, whose harness kept the path. It never creates.
  - It looks the workspace up by id, prefix or a path inside it, and applies `ws run`'s rule: the workspace must be active with an `active` or `in_grace` lease, and its owner must pass `may_attach`.
  - It renews once, which gives a lease in grace its full length back. It then starts a holder, ending any previous holder of that workspace first.
  - A released or reclaimed workspace is `conflict` (exit 5), with the hint "Its directory is gone; its work is change <id>. Start a new workspace on it." and `next` `["reef", "ws", "create", "--repo", <repo>, "--change", <change id>]`.
- **release**: `ReleaseWorkspace` with a final snapshot, then the holder record is removed and its follower told to stop. There is no `keep`. A harness that keeps a worktree simply does not call release, and the workspace then lives until its holder ends plus the lease and grace (below).
  - Release is not idempotent by path: a second release of a path whose directory is gone is `not_found`, exit 3, as today.
  - By id it is idempotent: a workspace already released or reclaimed returns exit 0 with `released: false` and its `state`. A harness that retried a release with an id must not see an error.
  - A harness calling with a path ignores the failure, or, like Claude Code, only logs it.

### Who holds the lease: the holder and its follower

The workspace's lease is kept alive by a **follower**, a detached `reef ws renew --follow` process bound to a **holder**, the harness's process. This is R2.13's rule moved from the MCP server to any process. The lease is renewed while the holder runs. Nothing is released when the holder exits: the lease runs out and the daemon reclaims the directory with a final snapshot (ADR 0019), so nothing is lost.

- **`hold_while`** names the holder.
  - A pid holds the workspace while that process lives.
  - `parent` means the nearest ancestor of the `reef` process whose command name is not a shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `mksh`, `fish`). It is resolved from `pbi_ppid` and `pbi_comm` (macOS, `proc_pidinfo(PROC_PIDTBSDINFO)`) or `/proc/<pid>/stat` (Linux), walking at most 8 levels. This makes the adapter independent of how its harness spawns a hook (`sh -c`, a login shell, or an exec), which is unverified for the reference harness.
  - A resolved pid of 1, or one whose process cannot be read, is `HOLDER_NOT_RUNNING` (invalid_argument, exit 2), checked before anything is created.
  - Without `hold_while` there is no follower. The lease is then the caller's to renew (`reef ws renew`, or `attach`), for a harness that runs its own heartbeats.
- **`reef ws renew --follow [--while-pid PID] [WS]`** is R2.11's open question 2, second half. It renews the workspace's current lease (or `--lease-id`'s) on `heartbeat_every` with `Heartbeater`, and exits 0 in each of these cases:
  - the lease is gone (released, reclaimed, superseded): `heartbeats` already ends there;
  - the `--while-pid` process has exited, checked every 2 s by pid and by the start time read when the follower started, so a reused pid is not mistaken for the holder;
  - it gets SIGTERM or SIGINT.

  It writes nothing to stdout. Notes go to stderr, which the provider points at `<state>/logs/follower-<ws id>.log`, truncated at each start. Without `--while-pid` it follows until the lease is gone or it is interrupted, which is the "heartbeater for holders that have no `ws run`" R2.11 asked about. It does not change the lease's length: R2.11's other half, a length on `RenewLeaseRequest`, is an API change nobody needs yet.
- **The provider spawns the follower** with `std::process::Command`: `reef` itself (`std::env::current_exe`), `ws renew --follow --while-pid <holder> --lease-id <lease> <ws id>`, the global flags it was run with (`--socket`, `--state-dir`, `--config`, `--agent`), `process_group(0)`, stdin and stdout null, stderr to the log, as autostart spawns the daemon. It does not wait for the follower. A hook must return, and a child that kept the hook's stdout open would hold the harness until its timeout.
  - If the spawn fails, create releases the workspace it just made (with no final snapshot, since nothing has been written) and fails with kind `io`, exit 8. A harness that got an error must never have a workspace left behind.
  - For `attach`, a failed spawn is just the error: the workspace stays as it was.
- **The holder record**, `<state>/holders/<ws id>.json`, is written by the follower when it starts and removed when it exits. It holds:

  ```json
  {"workspace_id", "lease_id", "follower_pid", "holder_pid", "holder_started_at", "since"}
  ```

  - The directory is mode `0700`. The file is written to a temporary name and renamed into place.
  - A record counts only while its follower is alive (`kill(pid, 0)`) and its `lease_id` is the workspace's current lease. Anything else is stale and is removed by whoever reads it.
  - `attach` reads it to stop an older follower (SIGTERM). If the record's holder is the same pid and start time, attach keeps it and starts none.
  - `release` reads it to stop the follower at once rather than at its next heartbeat.
  - `reef here` reads it (below).
- **Why a client-side follower** rather than the daemon watching a pid:
  - no daemon or API change;
  - `Heartbeater` and its backoff already exist and are tested;
  - a daemon restart does not lose it (the follower backs off and resumes, and the daemon's restart grace covers the gap);
  - R2.11 already asked for `--follow`.
- **Why not release when the holder dies.** A harness that is restarted, or a session resumed within the lease, finds its directory and attaches. That is R2.13's reason, and a reclaim snapshots first. A dead session's directory lives at most 35 minutes by default. A harness that wants longer passes `lease`, up to `lease.max`, 24 h.

### `reef here` inside a held workspace

`here` adds a third input beside `in_run`: `held`, true when the workspace's holder record is current (above). A held, healthy workspace gets the hint "Work here; the program that created this workspace releases it." and no `next`, as inside `ws run`. `ws release` itself does not change: an explicit release still releases. A held workspace whose lease is `in_grace` keeps R2.11's renew advice, since its follower is evidently failing. `here`'s JSON gains `held: bool` beside `in_workspace`, additively. The stale record is removed by `here` only if it can be removed without error, and `here` never fails because of it.

### The surface: `reef ws provider create | attach | release`

Three leaves under `ws`, behind one line in `reef ws --help`: `provider  Create, attach and release workspaces for a harness, JSON in and out`.

- **Not a top-level noun**: `reef --help` is 509 of its 512 bytes, and the root help must name every top-level command (ADR 0051).
- **Not flags on `ws create`, `ws run` and `ws release`**:
  - Those are the commands agents read. `ws run`'s help is already 2,056 of 2,176 bytes.
  - The contract needs stdin JSON and a holder, which no agent passes.
  - The contract's output is its own stable shape, not `Created`'s 27 keys with timings.
  - Putting the plumbing on the agent-facing commands would make agents pay to read it (#122) and tie the agent contract to the harness contract.
- **Not "a documented protocol over the existing commands"**: a hook gets JSON on stdin and cannot turn it into argv without `jq`, which is not on every machine. Nothing existing holds a lease for the life of another process.

**Input.** Each field is a flag, so `next` stays an argv (ADR 0025) and R2.24's `reef schema cli ws provider create` gives the input schema with `argv`. The same fields also come as one JSON object on stdin, keyed by the same names (clap's ids). The stdin schema is therefore R2.24's `input` schema, published once.

| Command | Fields |
| --- | --- |
| `create` | `repo` (path or id; default: the current directory), `name`, `purpose` (default: `name`), `owner` (default: `<user>@<host>:<name>`, else `<user>@<host>`), `change` or `new_on`, `lease` (a duration such as `30m`), `hold_while` (a pid, or `parent`) |
| `attach` | `workspace` (id, prefix, or a path inside it; required), `owner` (the owner it must have, `ws run --workspace`'s rule), `hold_while` |
| `release` | `workspace` (required) |

- **`--stdin`** reads one JSON object from stdin, at most 1 MiB. Without it, stdin is never read (ADR 0025 rule 1).
- **`--at FIELD=POINTER`** (repeatable, implies `--stdin`) takes a field from the stdin object at an RFC 6901 pointer. This is how an adapter maps a harness's own event without code: R2.25's `--path-at`, generalized. A pointer that selects nothing leaves the field unset.
- **Precedence**: a flag, then an `--at` pointer, then the stdin object's own key, then the default. Keys the command does not know are ignored, since a harness's event carries many and a newer contract may add fields.
- **Types**: a value of the wrong JSON type (a number for `repo`; for `hold_while`, anything but an integer, a string of digits, or `parent`) fails, as does stdin that is not one JSON object, over 1 MiB, or an unknown `FIELD` in `--at`. Each is `invalid_argument`, exit 2, reason `PROVIDER_INPUT_INVALID`, with `metadata.field`.

**Output.** One value on stdout, nothing else. Autostart, registration and default-start notes go to stderr, as they already do.

```json
{"contract": 1, "workspace_id", "repo_id", "path", "change_id", "owner", "purpose",
 "lease": <Lease>, "holder": {"pid", "follower_pid"} | null, "attached": false,
 "start": "main" | null}
```

- `release` prints `{"contract": 1, "workspace_id", "released": true, "state", "snapshot_taken", "final_op_id"}`.
- `-o json`, `-o brief` and a pipe print the same compact object: it is already small, so its brief form is `Same` (R2.24).
- `-o text` prints the path alone, one line, for create and attach, which is what a harness that reads a path wants. For release it prints nothing on stdout and a `released <id>` note on stderr.
- The types are `cli.Provided` and `cli.ProviderReleased` in R2.24's document. `contract` is 1 and changes only for an incompatible change to the input or output. Fields are added without changing it (ADR 0034's additive rule).

**Errors.** These are the CLI's error document and exit codes, with no new kind. Two new reasons are CLI-side constants, as R2.24's `SCHEMA_NAME_NOT_FOUND` is: `PROVIDER_INPUT_INVALID` and `HOLDER_NOT_RUNNING`. Every daemon error passes through with its `hint` and `next`, for example a missing store, or a directory in no repository. **Deadline**: create waits up to `--timeout` or 300 s, whichever is longer. A first create in a new large repository builds its base for about 36 s, past the CLI's 30 s default, and a hook's timeout (600 s for the reference harness) is the outer bound. **Local only**: all three are refused under `--remote` (`local_only`). A harness needs a directory on its own machine, and the holder is a local process.

### The contract document

The contract document is `docs/workspace-provider.md`. It is harness-neutral and names no harness; a test checks that, as ADR 0051's test checks the help. It has these sections:

- what a provider is;
- the three commands, their fields, their output and errors, with one example each;
- the holder rule, with the 35-minute number;
- what a workspace is not: no `.git` and no `.jj`, so git-based change checks see nothing, and work lands as a jj change, not a branch;
- how to write an adapter: map the harness's event with `--at`, pass `--hold-while parent`, print with `-o text` if the harness reads a path.

`docs/quickstart.md` links it from R2.25's "Set up your agent" section, in the reference harness's row only, because that is where that harness differs.

### The reference adapter: Claude Code's worktree hooks

It is chosen by what can be verified, not by vendor:

- **Claude Code** is the only harness whose worktree creation can be replaced by a command, documented with its input, output, exit codes and timeout.
- **opencode v2**'s strategy is replaceable too, but only by in-process TypeScript published as an npm package. R2.25 decided against npm packages for now.
- **Every other harness** hard-codes `git worktree add`.

The adapter is facts in the agent table (`SIGNS`, as R2.25 extends it) and a hooks file rendered from them. It is not code. The row gains `provider: Option<&'static ProviderHooks>`:

```rust
pub(crate) struct ProviderHooks {
    /// The harness's create, release and resume events, by name.
    pub(crate) create: &'static str,               // "WorktreeCreate"
    pub(crate) release: &'static str,              // "WorktreeRemove"
    pub(crate) resume: Option<(&'static str, &'static str)>, // ("SessionStart", matcher "resume")
    /// `--at` pairs for each.
    pub(crate) create_at: &'static [(&'static str, &'static str)],  // repo=/cwd, name=/name
    pub(crate) release_at: &'static [(&'static str, &'static str)], // workspace=/worktree_path
    pub(crate) resume_at: &'static [(&'static str, &'static str)],  // workspace=/cwd
    /// Whether the harness reads a path (`-o text`) from create's stdout.
    pub(crate) reads_path: bool,
}
```

`agents::provider_hooks(&ProviderHooks) -> Json` renders:

```json
{"hooks": {
  "WorktreeCreate": [{"hooks": [{"type": "command",
    "command": "reef ws provider create --at repo=/cwd --at name=/name --hold-while parent -o text"}]}],
  "WorktreeRemove": [{"hooks": [{"type": "command",
    "command": "reef ws provider release --at workspace=/worktree_path"}]}],
  "SessionStart": [{"matcher": "resume", "hooks": [{"type": "command", "timeout": 10,
    "command": "reef ws provider attach --at workspace=/cwd --hold-while parent >/dev/null 2>&1 || true"}]}]
}}
```

- **No guard** on `WorktreeCreate`. With no `reef` the shell exits 127, the harness fails the creation and shows the error. Falling back to `git worktree add` silently would hide that Reef is not in use.
- **The resume hook** prints nothing (a `SessionStart` hook's stdout becomes session context, #122's cost) and never fails. In a session that is not in a Reef workspace it is one failed lookup. It is how a resumed session's workspace gets a holder again, since the reference harness does not run `WorktreeCreate` on a resume (as far as its documentation says).
- **No `timeout`** on create or remove: the harness's 600 s default covers a first create on a large repository.

**Where it ships**: a second plugin in R2.25's marketplace, `reef-workspaces`, at `plugins/claude-code-workspaces/` (`.claude-plugin/plugin.json`, `hooks/hooks.json`, `README.md`). It is rendered by R2.25's `packages()` from the row, pinned to the release tag like the `reef` plugin, and installed with `claude plugin install reef-workspaces --marketplace reef-vcs/reef`.

- **Why a separate plugin.** Replacing worktree creation changes what a session's isolation is: no git branch to merge, and work as a jj change. That must be a choice, not a side effect of installing Reef's skill and MCP server (open question 1).
- **A plugin's limit.** A plugin hook does not run under `--worktree --tmux`. The contract document's adapter section shows the same JSON for a settings file (`~/.claude/settings.json` or the project's `.claude/settings.local.json`) for that case. `reef init` does not write it: Reef owns no entry in those files, and a merge into a settings file is more than this ticket needs.

### What the reference harness does with a Reef workspace

Stated in the document's adapter section and checked by the live run:

- **Changes.** The harness's git-based check finds no changes in a directory that is not a git checkout. An unnamed session's workspace is therefore removed at exit without a prompt, and release takes the final snapshot first. The work is a jj change in the root checkout's log (`reef log`, `jj log`), not a branch.
- **Subagent workspaces.** Their worktrees are never removed by the harness. Their holder is the main session's process, so they are kept alive while the session runs and reclaimed, with a final snapshot, at most 35 minutes after it ends. A session with many subagents holds many copy-on-write workspaces until then.
- **Git settings.** `.worktreeinclude` (an untracked `.env`, say) is not copied. Reef's spec file and shared stores (R1.19, R1.20) are the way to give a workspace dependencies, and an untracked file stays in the root checkout.
- **Edits.** The workspace is the session's working directory, so edits in it need no per-edit permission. That is what R2.13 line 320 asked for.

## Implementation notes

- **Order**: holder resolution and records (3, 4, 5); `ws renew --follow` (12); the provider commands (1, 2, 6 to 10); `here` (11); the document and ADR; then Part 2 (13, 15) after #154.
- **The follow loop** is `heartbeats(heartbeater)` raced in a `tokio::select!` against a 2 s `interval` that checks the holder, and against SIGTERM and SIGINT (the streams `ws run` installs). Write the record after the first successful renewal, not before, so a record never names a follower that could not renew. Remove it on every exit path, in a guard.
- **Spawning**: pass the follower the same `--socket`, `--state-dir` and `--config` the provider resolved, so a provider run against a scratch daemon is followed against it. A test that leaks a follower leaks a process (see the memory note on `ws run` tests), so every test kills followers it started by the pids in their records, in a guard.
- **`parent`'s walk** reads the command name, not the path: `pbi_comm` is 16 bytes on macOS and `comm` 15 on Linux, which holds every shell name listed. Login shells show as `-zsh`, so strip a leading `-`.
- **The start time** compares as recorded (seconds and microseconds on macOS, clock ticks since boot on Linux). Never convert it, and never compare across a reboot. A reboot ends every holder anyway.
- **Create's nested start** uses `GetWorkspace { snapshot_first: true }` and then `new_on: <commit id>` of the snapshot, not the change id, so a divergent change cannot make it ambiguous.
- **No `println!`**: output through `Out` (`object`, `done`), as every command.
- **macOS and Linux** both build `holder.rs`'s two halves. macOS never compiles the Linux half, so run the unit tests in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`) before the PR.

## Performance expectations

- `ws provider create` costs `ws create` plus one process spawn: under 20 ms more than `ws create` in a release build, measured on `small` and `medium` and reported in the PR. `attach` takes under 50 ms (one inspect, one renew, one spawn). `release` costs `ws release`.
- A follower is one idle process: one renewal RPC per `heartbeat_every` (60 s by default) and one `proc_pidinfo` or `/proc` read every 2 s. The PR reports its resident memory on macOS and Linux. If it is over 15 MB, build its runtime as `current_thread`.
- `reef here` gains one file read. The `here` bench in `tests/cli.rs`, if any, is unchanged within noise.

## Risks

- **The hook's process tree is unverified.** If the harness ran hooks through a long-lived helper process rather than its own, `parent` would name the helper, and the workspace would live as long as the helper does. That is still bounded by the session if the helper is the session's. The live check records the tree. If `parent` resolves to something that outlives the session, the row gains `holder: "pid-at:/…"` once the harness passes a pid, which is the upstream draft's third ask.
- **A `$HOME` that is a git repository.** On Linux the daemon's default state directory is under `~/.local/state`. If `~` is a dotfiles checkout, the reference harness's "inside a repository" check refuses every workspace. The document says so, and `[workspace] root` (or `REEF_STATE_DIR`) outside it is the fix. Test 13 checks that the path is outside the repository, not outside every repository.
- **Git-based tools in the session.** A harness or agent that runs `git` in the workspace gets "not a git repository". This is ADR 0014's trade, already in the quickstart's limitations, now met by harnesses that never chose Reef's workflow, only its isolation. The document leads with it.
- **Many subagent workspaces in a long session** stay until the session ends. They are copy-on-write, so the cost is what each changed, plus one follower process each. The PR measures fifty workspaces held by one holder: memory and renewal RPCs.
- **A follower that outlives its usefulness**: a holder that never exits (an editor's long-lived server) keeps workspaces it no longer uses. Release, or `reef ws release`, ends it. This is the same as a harness that never removes its worktrees.
- **Resume without the hook**: if the live check finds `SessionStart` does not carry the worktree as `cwd`, a resumed session works until its lease lapses (35 minutes after the original holder died). Then the directory goes, with a final snapshot, and the harness reports the worktree missing. The `SessionStart` row field is then dropped, and the upstream draft's second ask is the fix.

## Choices this brief made, and why

- **Under `ws`, beside the agent's commands, not in them**: the agent never reads the plumbing, and the help budgets hold.
- **Flags and stdin JSON with the same names**: `next` stays an argv, R2.24 publishes one input schema, and a hook needs no `jq`.
- **`--at` pointers rather than a harness-aware command**: the CLI learns JSON Pointer, not a harness. The facts live in the row (R2.25's precedent).
- **A follower bound to a process, not a long lease**: a crashed session's directory goes in 35 minutes rather than a day, and a live one keeps it however long it runs.
- **Nothing released on the holder's death**: a resume within the lease finds its directory, and a reclaim loses nothing.
- **Idempotent create by name**: a retry or a repeated name gets the same workspace, as the harness does for git.
- **The daemon's path, never the harness's**: the harness refuses directories inside a checkout, and the root's jj would see them.
- **A separate plugin**: changing isolation is opt-in.
- **Claude Code as the reference**: it is the one harness whose replacement point is a documented command. opencode's needs npm, and the others have none.

Applied to this directory's README and the row:

> **R2.26 stays M, adds no RPC, and holds leases with a follower bound to the harness's process** (2026-11-01). The contract is three leaves under `ws`, `reef ws provider create|attach|release`, taking their fields as flags or as one JSON object on stdin with the same names, with `--at FIELD=POINTER` mapping a harness's own event, and printing one object (`contract: 1`), or the path with `-o text`. Create starts a detached `reef ws renew --follow --while-pid <holder>` (R2.11's open question 2), where the holder is a pid or `parent`, the nearest non-shell ancestor. It renews the lease while the harness lives and releases nothing at its death (R2.13's rule), so a dead session's workspace is reclaimed with a final snapshot within 35 minutes. A name makes create idempotent through the owner `<user>@<host>:<name>`. A holder record stops `reef here` from telling an agent to release a workspace its harness holds. The reference adapter is Claude Code's `WorktreeCreate`, `WorktreeRemove` and resume `SessionStart` hooks, rendered from its row into a separate `reef-workspaces` plugin in R2.25's marketplace. It is the only harness whose worktree creation a command can replace; opencode v2's strategy is in-process TypeScript, and the rest hard-code git. The upstream conversation is two drafts, an issue for Claude Code's gaps and a comment on Codex #50528, opened by the user. ADR 0053. It depends on R2.11 and R2.25 as well.

## Open questions for the user

1. **One plugin or two?** Should the worktree hooks go in a separate `reef-workspaces` plugin, or in R2.25's `reef` plugin? **Recommended: separate.** Replacing worktrees changes a session's isolation: no git branch, and a git-based change check that sees nothing. That should be a choice, not a side effect of installing Reef's skill.
2. **Which lease rule for provider workspaces?** **Recommended: the holder rule as written** (renew while the harness's process lives, nothing released at its death, reclaimed with a snapshot within 35 minutes). The alternative is a fixed long lease, say 24 h, with no follower process. It is simpler, but a crashed session's workspace would then hold disk for a day, and a session longer than the lease would lose its directory.
3. **The upstream drafts: open them, when, and from which account?**
   - **Recommended**: open the Claude Code issue after Part 2 has been used for a week and the live check has passed, from your account.
   - Post the Codex comment on #50528 at the same time, linking the contract document and the Claude Code adapter as a working example.
   - Do not file anything on Gemini CLI: its request was closed as not planned.
   - Do not file anything on Cursor: no public request to replace creation was found.
4. **The command's name.** `reef ws provider create|attach|release`, or `reef ws hook create|…` to parallel R2.25's `reef presence hook`? **Recommended: `provider`.** The contract is not only for hooks: an orchestrator or an SDK calls it from code too. `presence hook` reads a harness's event and never fails, while these must fail loudly.
5. **Should `reef here`'s JSON gain `held`, and should a held workspace's hint name no `next`?** **Recommended: yes to both.** Without it, an agent that follows `next` releases the directory its harness is running in.
6. **The live check** needs a model credential and about $1 of tokens per run. **Recommended**: once by hand before the PR merges, recorded in the PR, rather than a dispatch workflow. Add it to R2.25's `harness-packages-live` only if the hook format changes in a later harness release.

## Decided by the user (2026-11-01)

1. **A separate plugin.** The worktree hooks ship as the opt-in `reef-workspaces` plugin, not inside `reef`.
2. **The holder rule.** A follower renews the lease while the harness's process lives; nothing is released at its death.
3. **Upstream after a week.** Both drafts are opened from the user's account once Part 2 has been in use for about a week and the live check has passed; until then they stay drafts in `R2.26-upstream.md`.
4. **The live check once by hand** before merge, recorded in the PR, with no CI workflow.

Questions 4 and 5 above (the name `ws provider`; `held` in `reef here` with no `next`) were taken as recommended.
