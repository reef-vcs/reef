# R2.26 Workspace provider contract

Phase 2 · Size M · Depends on: R2.13 (an adapter may use the tools; the marketplace the adapter plugin ships in is R2.25's), R1.21 (`ws run`'s heartbeater and attach rules, which `ws attach` reuses), R1.26 (`-o json`, `hint`/`next`) · Unblocks: nothing in Phase 2; the first harness that adopts it

## Context

The design's first problem statement is git worktrees: harnesses isolate agents by creating a worktree per session or subagent, and a worktree is a full copy with no owner, no expiry and the only copy of the work. Reef replaces worktrees for agents that know Reef. Harnesses create worktrees on the agent's behalf, before the agent runs a command, so the agent never gets to choose; the harness has to. This ticket writes down the small interface a harness needs to ask Reef for a workspace instead of a worktree (create, attach, release, JSON in and out), ships a reference adapter for the first harness that has a substitution point, and opens the conversation upstream so the next harness has a contract to implement against rather than a product to study.

The first harness is Claude Code: its documentation defines `WorktreeCreate` and `WorktreeRemove` hooks that "replace the default `git worktree` logic entirely" for `claude --worktree`, `EnterWorktree`, subagents with `isolation: worktree`, workflows and background sessions. That is the substitution point this ticket plugs Reef into. Codex and opencode have no equivalent hook on their documented surface (verified below), so for them this ticket is the contract and the upstream request.

### What was verified while writing this ticket

- **Claude Code worktrees and hooks** (code.claude.com/docs/en/worktrees and /hooks, fetched 2026-10-25). `claude --worktree <name>` (`-w`) creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; `EnterWorktree` and `ExitWorktree` tools; `isolation: worktree` in a subagent's frontmatter; `worktree.baseRef` (`fresh`|`head`); `.worktreeinclude`. `WorktreeCreate` "Runs when Claude Code creates a worktree" in all of those cases, and "Configuring a WorktreeCreate hook replaces that default git behavior". Input: the common fields (`session_id`, `transcript_path`, `cwd`, `hook_event_name`) plus `name` ("a slug identifier for the new worktree, either specified by the user or auto-generated, for example `bold-oak-a3f2`"). Output: a command hook prints the path "as the last non-empty line of stdout" (ANSI stripped; other output to stderr); "If the hook fails or produces no path, worktree creation fails"; a relative path resolves against the hook's cwd; an absolute path with `.` or `..` segments, or one "that passes through a symlink below the repository root", is refused; `systemMessage` and `continue` are discarded. `.worktreeinclude` is not processed with a hook. A plugin's hook does not run for `--worktree` with `--tmux` (define it in settings for that). `WorktreeRemove` runs when the user exits an interactive worktree session and chooses removal, on an unnamed session with no changed files, on background-session delete, on `ExitWorktree` (which "refuses to remove a hook-created worktree unless the call passes `discard_changes: true`"), and on `remote-control` cleanup; input carries `worktree_path`; "Hook exits 0: the worktree counts as removed. Claude Code reads nothing else from the hook"; "Claude Code uses git to look for changed or untracked files, so it finds none in a worktree that isn't a git checkout"; "When a subagent or a workflow agent finishes, Claude Code keeps the worktree your WorktreeCreate hook made for it and doesn't run your WorktreeRemove hook. Remove those worktrees yourself." Isolation checks: a directory "with no git metadata at all" passes the adoption check "only when no git repository contains it", and from inside a worktree Claude Code blocks edits and commands whose cwd resolves to the main checkout. Hooks run in `${CLAUDE_PROJECT_DIR}` with `cwd` in the input. Claude Code's own examples parse the input with `jq`.
- **Codex** (learn.chatgpt.com, fetched 2026-10-25): the MCP page and the config keys it lists have no worktree or workspace-provider hook; Codex's sandbox and `cwd` are configuration, not a creation hook. **opencode** (opencode.ai/docs/plugins): plugins receive `{ project, directory, worktree }` in their context and hooks on tool execution, shell environment and events, but no documented hook substitutes the working directory of a session. Neither is a substitution point; both get the contract and an issue.
- **In this repository** (at `d156d1e`): `ws run --workspace <id>` attaches to an existing workspace (`crates/reef-vcs/src/cli/ws_run.rs:69-76`, `attach` at `:285-313` refusing a non-active workspace and checking the owner through `may_attach` at `:317`, then one `Heartbeat` to learn `heartbeat_every`); `Heartbeater` (`:530-620`, renews on the daemon's `heartbeat_every`, backs off while the daemon is unreachable, stops when the lease cannot be renewed); `Signals` and the SIGTERM/SIGINT rules (`:177-236`); `reef_env` (`cli/env.rs:10-17`: `REEF_WORKSPACE`, `REEF_WORKSPACE_PATH`, `REEF_REPO`, `REEF_SOCKET`); `tests/ws_run.rs` `attach_existing_workspace` and `attach_checks_the_owner` (`:445-508`). `reef ws create -o json` prints the `Created` object with `id`, `path`, `change_id`, `lease` (`reef_daemon::client::json::Created`, `client/json.rs:289`); `reef ws release <id>` prints `Released` (`:440`); `CreateRequest.path` places a workspace at a caller-chosen absolute path (`workspaces.proto:877-880`), and the default root is `<state>/repos/<repo-id>/ws/<ws-id>` (Phase 1 README, state directory), which is not inside any git repository. The owner default is `<user>@<host>` for `ws create` and `<user>@<host>:<pid>` for `ws run` (Phase 1 README, identifiers). A workspace directory has no `.git` or `.jj` (ADR 0014).
- **Not verified**: whether Claude Code's `EnterWorktree` adoption check accepts a directory under `~/Library/Application Support/reef/...` on macOS without prompting (the check is about git metadata and symlinks; the state directory has neither, but the PR records the first run); whether a `WorktreeCreate` hook may run `reef`, which may start a daemon, within whatever timeout Claude Code applies to it (the default command-hook timeout is 600 s).

## Decisions

- **The contract is three CLI invocations with JSON in and out, in `docs/workspace-provider.md`, versioned `v1`.** A provider is any program a harness can run that implements them; Reef's is the `reef` binary, and the document is written so a second provider could implement the same three. The harness never parses text: every command is run with `-o json` (or `REEF_OUTPUT=json`) and reads one object from stdout; errors are `{"error": {"kind", "message", "hint", "next"}}` with the exit codes of ADR 0025. The operations:
  1. **create**: `reef ws create -o json --repo <path> --owner <harness>:<session> --purpose <text> [--new-on <rev> | --change <id>] [--lease <duration>]` → the `Created` object; the harness reads `id` and `path` and makes `path` the agent's working directory. `--repo <path>` is the harness's project directory; the first call registers the repository (R1.25). `owner` is `<harness name>:<the harness's session or agent id>`, so `reef ws list` shows who holds what and `ws run --workspace` and `ws attach` know whom to admit.
  2. **attach**: `reef ws attach <id> -o json [--owner <owner>] [--for <duration>] [--until-pid <pid>] [--pidfile <path>]` (new, below) → prints the `Workspace` object once the first heartbeat succeeded, then keeps the lease alive until it is told to stop. A harness that cannot keep a process running for the session's lifetime may instead create with `--lease` long enough and skip attach; the document says what that costs (the directory outlives a dead session by the lease, then reclaims with a final snapshot).
  3. **release**: `reef ws release <id> -o json [--force]` → the `Released` object, after a final snapshot; the harness stops its attach process first (or `ws attach` notices the release and exits 0).
  The document also fixes: the workspace path is outside the repository and outside any git checkout, has no `.git` or `.jj`, and is a cache (the store holds every snapshot, so releasing never loses work); `REEF_WORKSPACE`, `REEF_WORKSPACE_PATH`, `REEF_REPO`, `REEF_SOCKET` are the environment a harness should give the agent (R1.21's set); `reef here` answers "where am I" from inside; the harness must not create files it needs outside the tree (dependencies go in stores, R1.20) and must not `cd` the agent back into the main checkout to run `git`, since the workspace's change is a jj change (`reef status`, `reef diff`, `reef log` from R2.02/R2.05 answer there). `v1` means these three commands, their flags and the fields named above are stable for the 0.x line (ADR 0025 rule 5, names are additive); new fields and flags are additions.
- **`reef ws attach <id>` is the new command.** It is `ws run`'s lease-keeping without a child: resolve the workspace (id, prefix, or path), refuse a non-active one with the `ws create` `next`, apply `ws run --workspace`'s owner rule (`--owner` to attach to a workspace held by another owner, same `may_attach`), heartbeat once, print the `Workspace` object (JSON) or `here`'s text form, then renew on `heartbeat_every` with `Heartbeater`'s backoff, reporting presence `RUNNING` with `detail = attach` (R2.11). It stops, exits 0 and prints nothing more when: SIGTERM or SIGINT arrives; `--for <duration>` elapses (default `lease.max` from the daemon, 24 h); `--until-pid <pid>` names a process that has exited (polled every heartbeat); stdin is a pipe or file and reaches EOF (a harness that holds a pipe to it ends the attach by closing it; stdin that is a terminal or `/dev/null` is ignored, so a detached attacher does not exit at once); or the lease can no longer be renewed (the workspace was released or reclaimed), in which case it exits 5 (`Conflict`) with the error object on stderr. `--pidfile <path>` writes its pid at start and removes it at exit, for an adapter whose remove step must find it. It never releases the workspace: that is the harness's `release`, so a crashed attacher leaves a lease that expires normally. Alias `ws keepalive`.
- **The reference adapter is a Claude Code hook pair, shipped as the opt-in plugin `reef-worktrees`** in `plugins/claude-code-worktrees/` (second entry in R2.25's marketplace, `/plugin install reef-worktrees@reef-vcs`), and as a `hooks` snippet in the contract document for `settings.json` (the `--worktree --tmux` case where a plugin's hook does not run). Two POSIX `sh` scripts, `jq` their only dependency (as Claude Code's own examples):
  - `WorktreeCreate` → `scripts/worktree-create.sh`: reads `name`, `session_id`, `cwd` from stdin; `created=$(reef ws create -o json --repo "$cwd" --owner "claude-code:$session_id" --purpose "worktree $name")`; on failure prints the error's `message` and `hint` to stderr and exits 1 (Claude Code then reports that worktree creation failed, with the hint); otherwise `setsid reef ws attach "$id" --for 24h --pidfile "$REEF_ATTACH_DIR/$id.pid" >/dev/null 2>&1 </dev/null &` and prints `path` as the last line. `REEF_ATTACH_DIR` defaults to `${XDG_RUNTIME_DIR:-$HOME/.cache}/reef/attach`. The owner names the Claude Code session, so `reef ws list` shows `claude-code:<session_id>`.
  - `WorktreeRemove` → `scripts/worktree-remove.sh`: reads `worktree_path`; `reef ws inspect -o json "$worktree_path"` resolves the workspace by path (R1.26); kills the attacher named by its pidfile if any; `reef ws release -o json "$id"` (a final snapshot first, so Claude Code's "finds no changed or untracked files in a worktree that isn't a git checkout" costs nothing: the work is in the store). Exits 0 when the directory is gone, 1 with the error on stderr otherwise.
  - The hooks file: `{"hooks": {"WorktreeCreate": [{"hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/worktree-create.sh", "timeout": 120}]}], "WorktreeRemove": [{"hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/worktree-remove.sh", "timeout": 60}]}]}}`. 120 s covers a first create on a large repository (a cold base cache materializes the tree once) and a daemon start.
  - Subagent and workflow worktrees, whose `WorktreeRemove` never runs, are covered by the lease: `--for 24h` ends the attacher and the lease expires with a final snapshot and no directory, which is the exit criterion from Phase 1 applied to a harness that forgets. The plugin's skill paragraph says so and names `reef ws list --owner claude-code:` and `reef ws release` for cleaning up sooner.
  - The plugin has a one-skill `skills/reef-worktrees/SKILL.md` that says what changed for the model: its isolated directory is a Reef workspace, `git` does not run there, `reef status`/`diff`/`log` do, and `reef here` says where it is.
- **A conformance script, `scripts/provider-conformance.sh <provider-binary>`**, exercises the contract against any provider: create (JSON with `id` and `path`, `path` exists and contains no `.git`), attach in the background (the lease's `expires_at` moves within two heartbeats), a write in the path reaches the store (`reef ws inspect` shows a snapshot; for a non-Reef provider this step is skipped with a note), release (JSON with `final_op_id`, the path gone), and the error shape for a bad id (JSON `error` object, exit 3). It runs in CI against `reef` (test 9) and is what the document tells a second implementer to run.
- **The upstream conversation** is a GitHub issue on Claude Code's repository and one each on Codex's and opencode's, drafted in the PR from the template in the document's appendix: what a workspace provider is, the three operations, what Reef provides, and the ask: for Claude Code, that `WorktreeCreate` hooks receive the base ref the session would have used (`worktree.baseRef` resolved, so a provider can start the workspace on the same commit) and that subagent worktrees get a `WorktreeRemove`; for Codex and opencode, a creation hook of the same shape as Claude Code's. The issues are filed by the user, not by the implementing agent (outward-facing), with the text in the PR; the document links them once they exist.
- **ADR 0041, "Workspace provider contract"**: the three operations as the stable interface, why the CLI with JSON rather than the gRPC API or MCP (every harness can run a process and parse JSON; few can speak gRPC from a hook, and MCP tools cannot keep a process alive), why `attach` is a separate long-running command rather than a long lease (a lease that outlives the session leaks a directory for its length; a heartbeat ends with the harness), why the adapter is opt-in (it replaces every worktree the user's Claude Code creates), and the alternatives: a `reef ws provider` subcommand speaking each harness's hook JSON (ties the CLI to vendors' schemas), an adapter inside `reef init`'s default plugin (not opt-in), git worktree emulation (a `.git` file pointing into the user's repository, so harnesses think it is a worktree: rejected, it makes git run in a Reef workspace and defeats ADR 0014).

## Tests

1. `attach_keeps_the_lease_and_prints_the_workspace` (`crates/reef-vcs/tests/ws_run.rs`, short leases `lease.default = "3s"`, `grace = "1s"`): `ws create`, then `ws attach <id> -o json` with stdin a pipe held open; its first stdout line is the `Workspace` object; after 8 s the workspace is `active` with `last_heartbeat_at` moved; closing the pipe makes it exit 0 within one heartbeat; the workspace is still `active` (attach never releases).
2. `attach_stops_on_sigterm_until_pid_and_for`: three attachers: one gets SIGTERM and exits 0; one with `--until-pid` of a `sleep 2` exits 0 within 3 s; one with `--for 2s` exits 0 at about 2 s. None released the workspace.
3. `attach_exits_conflict_when_released`: attach, then `ws release` from another process; the attacher exits 5 within one heartbeat with `error.kind == "Conflict"` on stderr.
4. `attach_refuses_wrong_owner_and_inactive`: as `attach_checks_the_owner` and `attach_existing_workspace`'s second half, for `ws attach`: exit 5 with `--owner <holder>` in the hint; a released workspace is exit 5 with `next == ["reef", "ws", "create", "--repo", <id>]`.
5. `attach_pidfile_is_written_and_removed`: `--pidfile` holds the attacher's pid while it runs and is gone after.
6. `worktree_create_hook_prints_a_reef_path` (`crates/reef-vcs/tests/provider.rs`, `jq` required, skipped without it): run `plugins/claude-code-worktrees/scripts/worktree-create.sh` with `{"session_id":"s1","cwd":"<repo>","hook_event_name":"WorktreeCreate","name":"feature-x"}` on stdin and the test's `REEF_SOCKET`, `REEF_ATTACH_DIR`: exit 0; the last stdout line is an absolute path that exists, has no `.git`, and is a workspace `ws list` shows with `owner == "claude-code:s1"` and `purpose == "worktree feature-x"`; a pidfile exists and names a live `reef ws attach`; the path contains no `.`/`..` segments and no symlink component inside the repository (it is outside the repository).
7. `worktree_remove_hook_releases_and_kills_the_attacher`: run `worktree-remove.sh` with `{"worktree_path": <that path>}`: exit 0; the workspace is `released` with `final_op_id` after a file was written in it (its final snapshot's tree has the file); the attacher is gone; the pidfile is gone; the directory is gone.
8. `worktree_create_hook_fails_loudly`: with `REEF_SOCKET` pointing at nothing and `--no-autostart` through `REEF_...`? (the hook has no flag; instead `PATH` without `reef`): exit 1 and a one-line error on stderr; stdout empty.
9. `provider_conformance_passes_for_reef`: `scripts/provider-conformance.sh target/debug/reef` exits 0 against a `TestDaemon` state directory.
10. `plugin_validates_and_matches_the_renderer` (R2.25's tests 1 and 6 extended): the `reef-worktrees` plugin is in the marketplace, renders byte-identical, and `claude plugin validate --strict plugins/claude-code-worktrees` passes.
11. By hand, recorded in the PR: `claude --worktree test-reef` in a plain git checkout with the plugin installed: the session starts in a Reef workspace path (`reef here` inside says so), an edit there is snapshotted, exiting the session and choosing remove runs the release; and `claude -p --worktree ... "run reef here"` for the non-interactive path. Also a subagent with `isolation: worktree`: its workspace appears in `reef ws list --owner claude-code:` and reclaims after the lease.

## Implementation notes

- `ws attach`'s stdin rule: use `nix::sys::stat::fstat(0)` to tell a pipe or regular file (`S_IFIFO`, `S_IFREG`) from a tty or `/dev/null` (`S_IFCHR`); read on a blocking thread and send one message on EOF. Do not read a terminal's stdin.
- The hook scripts must print nothing but the path on stdout; every `reef` call that is not the final `path` echo has its stdout captured into a variable or sent to stderr. `reef ws create` may print `reef: registered <root>` on stderr (R1.25), which is fine.
- `setsid` is in `util-linux` on Linux and absent on macOS; use `nohup ... &` with `</dev/null` and `disown` where the shell has it, or spawn through `reef ws attach --daemonize`? Do not add a flag: prefer `( reef ws attach ... & )` in a subshell, which detaches from the hook's process group on both platforms; verify Claude Code does not kill the hook's process group after the hook exits (test 6 checks the attacher is alive after the script returned; record the behavior).
- Reuse `TestDaemon`'s short-tempdir helper for the conformance run in CI: socket paths must stay under 104 bytes.
- Write the document before the scripts and have the scripts follow it literally; the conformance script is the document's test.
- Record every `reef` invocation the hooks make and its wall time in the PR for `small` and for the `same-file` clone RX.07 uses; a first create in a repository is a registration plus a base materialization, the only slow step.

## Out of scope

- Starting the workspace on the branch Claude Code's `worktree.baseRef` would have used: the hook input does not carry it (the upstream ask); the adapter uses Reef's default start (R1.31).
- `.worktreeinclude` emulation: the design puts dependencies in stores and build outputs out of the tree.
- Codex and opencode adapters: no substitution point exists; the contract and the issues are the deliverable.
- An adapter that uses the MCP tools rather than the CLI: a hook is a process, and the CLI is the process form.
- Making the adapter the default in R2.25's `reef` plugin.

## Risks

- **Claude Code's adoption check.** The path a hook returns is screened for `.`/`..` and symlinks under the repository root, and a directory with no git metadata passes "only when no git repository contains it". The state directory satisfies both on Linux (`~/.local/state/reef`) and macOS (`~/Library/Application Support/reef`); a user whose home directory is itself a git repository would fail the second rule, and the hint names `--path` on a `ws create` outside it.
- **Hook process lifetime.** If Claude Code kills the hook's process group when the hook exits, the detached attacher dies and the workspace lives on the lease alone (24 h by default, then reclaimed with a final snapshot). Test 6 catches it; the fallback is `--lease 24h` with no attacher, which the document already describes as the degraded mode.
- **A removed worktree whose work is in the store, not on disk.** Claude Code tells the user it found no changes (it looked with git); the final snapshot is where the work went, and `reef log` shows it. The skill paragraph says so; a user used to git's prompt may be surprised the first time.
- **The upstream conversation is outside this repository's control.** The contract stands on its own: the plugin works with today's hooks, and the issues ask for two improvements, not for anything the adapter needs.
