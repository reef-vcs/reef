# R2.10 Presence channel

Phase 2 · Size M · Depends on: R2.09 (the broker, `Event`, `Frame`, the subscription task and its filters), R2.01 (`Presence { Subscribe, Report }` and `PresenceUpdate` as stubs; `Workspace.presence`) · Unblocks: R2.11 (`ws run`, the SDKs and the MCP server report through `Report`), R2.20 (the fleet panel), R2.22 (100 of the 500 subscribers are presence subscribers), R3.05 (executor progress streams over this channel)

## Context

The design's API section names a second channel beside the operation log: "Presence is a second, ephemeral channel over the same connection: an agent running tests, an agent editing in a directory, a lease heartbeat, a batch's progress through its checks. Presence is never persisted, so the log stays an audit trail and liveness stays cheap." The fleet panel (R2.20) and the map (R3.36) are drawn from it, agents use it to wait on one another the way humans do, and the Phase 2 exit criterion measures it alongside the log.

R2.09 built the broker and the frame rules. This ticket adds the in-memory presence table behind it, the two RPCs, the entries the daemon itself reports, and the `presence` field on `Workspace`. What an agent reports is R2.11's.

### What was verified while writing this ticket

Reef at `d156d1e`; tonic 0.14.6 and tokio 1.52.3 as vendored.

- **Client streaming in tonic.** A client-streaming handler receives `Request<tonic::Streaming<T>>`; `Streaming::message()` (`tonic-0.14.6/src/codec/decode.rs:338-344`) returns `Ok(Some(m))` per message, `Err(status)` on a transport or decode failure, and `Ok(None)` when the client half-closes the stream, which is how the end of a client's reports is observed. `Streaming<T>` also implements `Stream` (`:398`). The daemon has no client-streaming handler yet; `Maintenance.Backup` and `Stores.Build` are server-streaming (`service/maintenance.rs:80-164`, `stores.rs:124-189`).
- **Where the daemon's own activity happens.** Lease heartbeats: `LeaseManager::heartbeat` (`lease/mod.rs:335-371`) returns the renewed `LeaseRecord` with its `expires_at`. Snapshots: `Manager::run_snapshot` (`workspace/snapshot.rs:242-351`) runs one workspace's scan and commit and ends with `scheduler.run_hooks(&outcome)`; `SnapshotOutcome` (`snapshot/mod.rs:193-236`) carries `kind`, `changed`, `op_id`, `latency_ms`, `scan_ms`. Store builds: `store::build::run` (`store/build.rs:154`) spawns the command and forwards its output lines (`:605-630`) to the `Build` stream. Backup: `backup::run(state, dest, repo, progress: mpsc::Sender<BackupProgress>)` (`maintenance/backup.rs:313-332`) sends a `BackupProgress` per step. GC: `maintenance::gc::run` (`gc.rs:182`) runs `run_repo` per repository (`:201-300`). Reclaims: `Manager::reclaim` (`reclaim.rs:85-196`).
- **`Workspace` is built in one place.** `WorkspaceView` → `v0::Workspace` (`service/convert.rs:81-120`) is the one conversion `Create`, `List`, `Inspect` and `Move` use (`service/workspaces.rs:117, 169, 197, 327` in R1.32's reading); `watch_state` was added the same way (R1.32).
- **R2.09's broker** (its brief): `Pending::Presence(..)` and `Payload::Presence(..)` are compiled but unused; the indexer assigns no `seq` to presence and writes no row; the subscription task's `Filter` and frame cutting apply to every `Payload`.
- **Memory arithmetic, not measured.** A `PresenceUpdate` with a 64-byte detail is about 300 bytes in memory; 10,000 entries are about 3 MiB. The TTL sweep is a `BTreeMap` walk.

## Decisions

The README's "Presence" and "Agent reporting" rows are binding; this ticket implements the first and the daemon-emitted part of the second.

- **The table.** `reef_daemon::presence::Table`: `HashMap<Key, Entry>` under a `std::sync::Mutex`, `Key { agent: String, workspace: Option<WorkspaceId> }`, `Entry { repo: Option<RepoId>, change_id: Option<ChangeIdHex>, activity: Activity, detail: String, progress: Option<(u64, u64)>, since: Timestamp /* first report of this activity */, updated: Timestamp, expires: Instant, source: Source }`, `Source { Client { stream_id: u64 }, Daemon }`. In memory only: never in SQLite, never in the operation log, gone on restart. `Activity { Idle, Editing, Running, Testing, Waiting, Custom }` as the README enumerates; `Custom` carries its name in `detail`.
- **`Presence.Report` is client streaming.** Each `PresenceUpdate { agent, workspace_id, change_id, activity, detail, progress { done, total } }` upserts the entry for `(agent, workspace_id)` with `expires = now + [presence] ttl` (default 30 s) and publishes `Pending::Presence(Update { key, entry, kind: Set })` through the broker. An empty `agent` is `INVALID_ARGUMENT` on the first message; the first message's `agent` is the stream's identity and later messages must repeat it (a different `agent` on the same stream is `INVALID_ARGUMENT` and closes the stream). `workspace_id` may be empty (an agent with no workspace, such as one reading through `Trees`), else it must name an active workspace (`NOT_FOUND` otherwise), and its `repo` and `change_id` are filled from the row when the update leaves them empty. When `message()` returns `Ok(None)` or `Err`, every entry with that stream's `Source::Client { stream_id }` is removed and a `Cleared` update published for each. The response is `ReportResponse { updates: uint64 }` once the stream ends. A client keeps one `Report` stream open for its lifetime and sends an update whenever its activity changes, and at least every `ttl / 2` while it stays the same (the daemon does not require that; the TTL enforces it).
- **TTL.** A sweep every `ttl / 4` (bounded between 1 s and 10 s) removes entries past `expires` and publishes `Cleared` for each. A client whose stream is alive but silent past the TTL loses its entries the same way; its next update puts them back. Daemon-sourced entries have their own lifetimes (below) and are never TTL'd except as a backstop at `4 × ttl`.
- **Memory bound.** `[presence] max_entries = 10000`. A `Report` that would create the 10,001st entry gets `RESOURCE_EXHAUSTED` with the hint "the presence table is full; raise [presence] max_entries or shorten ttl", and the daemon logs it at `warn` once a minute at most. Updates to existing keys always succeed.
- **The daemon reports itself.** Through `Table::set_daemon(key, entry, until: Until::Cleared | Until::Expires(Instant))`, with `agent = "reef-daemon"` and the workspace when there is one:
  - a lease heartbeat (`LeaseManager::heartbeat`, after the row is renewed) is not an activity and creates no entry: it is published as R2.09's `LeaseEvent { kind: heartbeat }` with `expires_at`, and the table records the time per workspace (`Table::note_heartbeat`), which `Workspace.heartbeat_at` and the fleet panel show as lease health;
  - a snapshot in flight: `Running` with `detail = "snapshot"` set when `run_snapshot` begins its scan, cleared when `run_hooks` has run (`Until::Cleared`), keyed `(reef-daemon, ws)`;
  - a store build: `Running` with `detail = "store build <name>"` and `progress` absent, for the build's scratch workspace, from `BuildStarted` to `BuildResult`;
  - a backup: `Running` with `detail = "backup <step>"` and no workspace, updated per `BackupProgress`, cleared on `done` or error;
  - GC: `Running` with `detail = "gc"` per repository (`repo` set, no workspace), cleared when `run_repo` returns;
  - a reclaim: `Running` with `detail = "reclaim (<reason>)"` for the workspace from `begin_reclaim` to `finish_workspace`.
- **`Presence.Subscribe`.** `SubscribePresenceRequest { repo, filter: EventFilter }` (the same filter message as `Operations.Subscribe`; `kinds` is ignored, `changes`, `workspaces`, `owners` apply, where `owners` matches `agent`) → `stream Frame`. The first frame is the current table as `PresenceUpdate`s with `kind = SET` (`from_seq = to_seq = 0`, `coalesced = 0`), then deltas as the broker publishes them, framed by R2.09's task (same `frame_interval`, `frame_max`). Presence events carry `seq = 0` and `Frame.from_seq`/`to_seq` cover only indexed events in the frame; a frame of presence alone has both at the last indexed `seq` the task delivered. A subscriber that lags re-sends the full table as its next frame (`lagged = true`, then a `SET` for every live entry) rather than catching up from an index it does not have; that is correct for a table whose only truth is its current state.
- **`Workspace.presence`.** `Workspace` gains `presence: repeated PresenceUpdate` (every live entry for the workspace, the daemon's included, newest `updated` first) and `heartbeat_at: Timestamp` (from the table; unset when the lease has never been heartbeated since start). `List`, `Inspect`, `Create` and `Move` fill them through `WorkspaceView.presence`. `ws list` shows the first entry's activity in a new `activity` column (`editing`, `running cargo test`, `-`); `ws inspect` lists them.
- **One event kind on the broker.** `Pending::Presence(Update { key, entry: Option<Entry> /* None = cleared */ })` and `Payload::Presence(Arc<Update>)`; the proto `PresenceUpdate` gains `kind: SET | CLEARED`, `since`, `updated`, `source: CLIENT | DAEMON`. Nothing about presence is written anywhere; `reef backup` and `reef restore` are untouched; `Daemon.Status` gains `presence_entries: uint32`.
- **ADR 0032, "Presence channel"**: why presence is in memory and not in the log or SQLite (the design's audit-versus-liveness split), the TTL as the liveness rule and the sweep, the daemon as a reporter, `heartbeat_at` as derived lease health, the lag rule (resend the table), the memory bound, and the alternatives (presence rows in SQLite with a TTL column; heartbeats as presence entries; a per-connection presence lifetime without TTL, rejected because a stalled client would look alive).

## Tests

`[presence] ttl = "2s"` and `[events] frame_interval = "20ms"` in the test config unless stated.

1. `report_sets_and_stream_end_clears` (`tests/presence.rs`): a client opens `Report`, sends `{agent: "a@h:1", workspace, activity: EDITING, detail: "src/lib.rs"}`; a `Presence.Subscribe` opened before sees a `SET` frame within 200 ms with the fields and `source = CLIENT`; `Workspaces.Inspect` shows the entry in `presence`; the client ends its stream; the subscriber sees `CLEARED` and `Inspect` shows none. `ReportResponse.updates == 1`.
2. `ttl_clears_a_silent_stream`: report once, keep the stream open and silent; after `ttl + sweep + 1 s` the subscriber sees `CLEARED`; a new update on the same stream brings the entry back as `SET`.
3. `first_frame_is_the_whole_table`: three agents report on two workspaces; a new `Subscribe` gets, as its first frame, exactly three `SET`s with `from_seq == to_seq == 0`; `coalesced == 0`.
4. `filters_by_workspace_and_agent`: `filter.workspaces = [W]` sees only W's entries (the daemon's `snapshot` entry for W included when a snapshot runs); `filter.owners = ["b@h:2"]` sees only that agent's.
5. `daemon_reports_a_snapshot_in_flight` (`hold_scans` from the scheduler's test hooks): hold scans, write a file, trigger a snapshot: a `SET` for `(reef-daemon, ws)` with `activity = RUNNING`, `detail = "snapshot"`, `source = DAEMON` arrives; release the hold; `CLEARED` follows after the hook ran, and the operation's event (R2.09) is in the same or an earlier frame than the `CLEARED`.
6. `heartbeat_shows_as_lease_health`: `Heartbeat` on a workspace; `Inspect.workspace.heartbeat_at` is within 1 s of now; a `LeaseEvent { heartbeat }` was published (R2.09's subscriber sees it); no presence entry was created for it (`Daemon.Status.presence_entries` unchanged).
7. `backup_and_gc_report_progress`: `Backup` to a temp dir: a subscriber with no workspace filter sees `SET`s with `detail` starting `backup ` for each step, then `CLEARED`; `Gc`: a `SET` with `detail = "gc"` per repository, then `CLEARED`.
8. `table_full_is_resource_exhausted` (`[presence] max_entries = 3`): the fourth distinct key's `Report` message ends the stream with `RESOURCE_EXHAUSTED` and the hint; updating an existing key still succeeds; the three entries survive; the log has one `warn`.
9. `agent_must_not_change_mid_stream`: a second message with another `agent` ends the stream with `INVALID_ARGUMENT`; the first message's entry is cleared with the stream.
10. `lagging_presence_subscriber_gets_the_table_again` (`[events] buffer = 8`): a subscriber stops reading while 100 updates happen; when it reads, one frame has `lagged = true` and is followed (or accompanied) by a `SET` for every live entry, and nothing afterwards is stale: each key's last `SET` matches `Table::snapshot()`.
11. `restart_forgets_presence`: report, restart the daemon (`TestDaemon::restart`), `Inspect` shows no presence and `Status.presence_entries == 0`.
12. `activity_column_in_ws_list` (`crates/reef-vcs/tests/cli.rs`): with an entry reported, `reef ws list -o text` has an `activity` column reading `editing src/lib.rs`; `-o json` carries `presence[0].activity == "editing"`.

## Implementation notes

- The `Report` handler must clear on every exit: wrap the stream id in a guard whose `Drop` calls `end_stream`, so a cancelled RPC (client gone, tonic drops the future) clears too. Do not rely on `Ok(None)`.
- Publish after the table update, under no lock: take the entry's clone out of the mutex, drop the guard, then `broker.publish`.
- `DaemonMark` guards for the snapshot pipeline live in `run_snapshot`'s scope; the pipeline runs on the blocking pool and the guard's `Drop` is synchronous, which is fine since `publish` never blocks.
- The sweep publishes `Cleared` for each expired key; batch them under one lock acquisition and publish after.
- The fleet panel (R2.20) needs `since` to show "editing for 4 min": keep `since` when an update repeats the same `activity` and `detail`, reset it when either changes.
- `Frame.from_seq`/`to_seq` with presence-only content: the task tracks `last_indexed_seq` and stamps presence-only frames with it on both ends, so a client's cursor never moves on presence.
- `PresenceError::Full` → `Status::resource_exhausted` is built in the service, not through `status()`; add it to ADR 0017's table in `docs/api.md` as the one code outside `ErrorKind`.

## Out of scope

- What agents report and when (R2.11: `ws run`, the SDKs, the MCP server, `reef presence report|watch`).
- Presence history or replay (there is none, by design; R2.12's `ReplayState` has no presence).
- Presence across daemons or through a store (Phase 4).
- The fleet panel's rendering of presence (R2.20) and the map's conflict warning (R3.36).
- A `Report` RPC over the remote listener without the `presence` scope (R2.08 assigns scopes).

## Risks

- **A TTL of 30 s makes a crashed agent look alive for 30 s.** Its `Report` stream's end clears it at once in the common case (the process died, the socket closed); the TTL covers a hung process. The fleet panel shows `updated` so a stale-looking entry is visible as such.
- **`agent` is a free string until R3.03.** Two clients can claim the same agent and overwrite each other's entries; under ADR 0027 (one uid, one trust domain) that is not a boundary, and the session identity replaces the string later without a schema (there is none) to migrate.
- **Presence-only frames carry no cursor movement.** A client that counts on `to_seq` advancing to detect liveness must look at the frames themselves; `docs/api.md` says so.
- **The daemon's own entries add churn.** Every snapshot is two presence events; at the load test's 1,000 operations a minute that is 2,000 presence events a minute on the channel, which is what R2.22 measures with 100 presence subscribers. `[presence] daemon_reports = true` is not added unless R2.22 shows the cost; the ADR records the option.
