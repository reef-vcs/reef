# R2.10 Presence channel

Phase 2 · Size L (the row says M; see "Size") · Depends on: R2.09 (the subscription cap, the session's channel of one, keepalives, shutdown without a reason, `Limits` in `Config`, the client's streaming method and `reef op watch`'s reconnect loop) · Unblocks: R2.11 (automatic reporting from `ws run`, the SDKs and the MCP server, and the CLI's `presence report` over this ticket's RPCs), R2.20 (the fleet panel's presence and lease health), R2.22 (500 presence subscribers beside the operation log's), R3.05 (executor progress as `PROGRESS` entries), R3.36 (the map's hot areas from `EDITING` entries)

## Context

design.md (Subscriptions) gives Reef two channels: the operation log, durable and complete, and presence, "a second, ephemeral channel over the same connection: an agent running tests, an agent editing in a directory, a lease heartbeat, a batch's progress through its checks. Presence is never persisted, so the log stays an audit trail and liveness stays cheap." R2.09 implemented the first. Nothing implements the second: the three `PresenceService` RPCs answer `NOT_IMPLEMENTED`, and nothing in the daemon records who is doing what right now. A lease renewal records no operation, so today no client can see a heartbeat at all; a create that takes ten seconds is invisible until it returns.

This ticket implements the channel: an in-memory set of presence entries with time-to-live, the RPCs that report, replace and clear entries, and `SubscribePresence`, which sends the current set and then changes to it, coalesced per entry. It also makes the daemon report what only it knows: lease heartbeats, the files a workspace's snapshots are changing, and the progress of workspace creates and store builds. It adds `reef presence watch`. Phase 2's exit criterion asks for presence events within 100 ms; this ticket delivers that for one to ten subscribers, and R2.22 measures 500.

R2.01's rule binds this brief: it implements what R2.01 declared and only adds. It adds three fields and one enum (API revision 5); nothing declared changes meaning.

## Decisions

### Size

L. The channel alone (an expiring set, three RPCs, a snapshot-then-deltas stream with per-entry coalescing, caps) is what the row's M meant. The row also names lease heartbeats, editing and progress, which only the daemon can report, and those are hooks in four places (leases, snapshots, create, store builds), plus a schema addition with six reasons, a client, a CLI command with reconnection, an ADR, and about twenty tests. That is R2.09's breadth, which was L. It is not more than L: there is no graph, no resume and no GC, and the CLI reuses `op watch`'s loop. So it is not split.

### Where the line with R2.11 is

- **R2.10 implements all three RPCs, not only `SubscribePresence`.** R2.01 assigned `ReportPresence` and `ClearPresence` to R2.11, but what they mean (ids, replacement, TTL, caps, coalescing, who may touch what) is the channel's semantics, which this ticket must decide to bound memory and test delivery; and the phase's 100 ms criterion is measured from a report. The proto comments change to say R2.10 (comment-only, no digest change), and `NOT_TOOLS` is corrected.
- **R2.10 owns every entry the daemon reports itself** (`by_daemon: true`): `LEASE` on every lease issue and renewal, `EDITING` from workspace snapshots, and `PROGRESS` of creates and store builds. Nothing a client must do.
- **R2.11 owns every entry a client reports on an agent's behalf**: `ws run` reporting `ACTIVITY` for the command it runs, the MCP server reporting for its tool calls, the SDKs' helpers, and `reef presence report` and `clear`, the "presence API for agents that want finer activity". It writes no daemon code beyond what its brief finds missing. `dev-phases.md`'s R2.11 row says so.
- **`reef ws renew` is out of R2.10 and goes to R2.11.** This ticket observes heartbeats; it does not send them. A renew command is a client-side heartbeat for a workspace held outside `ws run`, the same kind of work as `ws run`'s automatic reporting, over an RPC that already exists (`RenewLease`). R2.11's row gains it.

### The RPC shape: a second stream on the same connection

`SubscribePresence` stays its own server-streaming RPC, as declared. A client that wants both channels opens both streams on one `Client`, which is one HTTP/2 connection to the socket: that is what "over the same connection" means, and the daemon puts no limit on streams per connection (above). Multiplexing presence into `SubscribeOperations`' frames was not chosen:

- The two channels have opposite delivery contracts: the operation log drops nothing, holds a slow reader back and resumes from a cursor; presence coalesces, sends the latest state of each entry and resynchronizes from the current set. One stream would need both behaviors per frame and a cursor that means nothing for half its content.
- HTTP/2 gives each stream its own flow control, so a reader that stops reading its operation stream still receives presence on the same connection, up to the connection window (see "Risks").
- The declaration already exists, and a `oneof` in `SubscribeOperationsResponse` would change what every existing reader of that stream must handle.
- The web UI (R2.18) opens both over one gRPC-web connection the same way.

### What an entry is

- **Identity.** An entry has a daemon-assigned id (16 lowercase hex, like workspace and lease ids) and four fixed fields: `kind`, `agent`, `repo_id`, `workspace_id`. A replacement may change everything else (`change_id`, `activity`, `paths`, `progress`, the TTL) but not those four, so an entry never moves in or out of a subscriber's filter: a subscriber sees an entry appear, change, and end, never leave its view another way.
- **Kinds and what each carries.** `ACTIVITY`: free text in `activity` ("running cargo test"). `EDITING`: repository-relative files in `paths`, most recent first. `PROGRESS`: `progress` (`phase`, `done`, `total`, `unit`). `LEASE`: the lease (new field `lease`, below); daemon only. A field another kind carries is refused when set (`INVALID_ARGUMENT`, no reason: a client bug), so every entry reads one way.
- **References.** `repo` and `workspace` are references as ADR 0029 defines them, resolved once at report: `workspace` as `RenewLease` resolves it (`Manager::resolve_workspace(repo, workspace)`), and it must be `active` (a released or reclaimed one is `ManagerError::NotActive`, `FAILED_PRECONDITION`, as for a snapshot); `repo_id` is then the workspace's. An entry names no repository, a repository, or a workspace and its repository. `change` is a full change id, in hex or jj's reverse hex, stored as hex; a prefix is `INVALID_CHANGE_ID` (metadata `change`), because resolving a prefix needs a jj read and presence never reads jj; `change` without `repo` or `workspace` is `INVALID_ARGUMENT`, no reason.
- **Agent.** `agent` is required (empty or invalid is `INVALID_ARGUMENT`, reason `INVALID_AGENT`, as for `reef-agent`), visible ASCII, at most 256 bytes. It is informational, like a lease's owner: the daemon does not compare it with `reef-agent`. R2.11's reporters fill it from `--agent` or `REEF_AGENT`, else `default_owner()`.
- **Sizes.** `activity` at most 1,024 bytes; `paths` at most 64, each passing `check_paths` (`INVALID_PATH`, metadata `path`) and not empty; `progress.phase` and `unit` at most 64 bytes; the encoded `Presence` at most 4 KiB. Over a bound is `INVALID_ARGUMENT`, reason `PRESENCE_TOO_LARGE`, metadata `field` and `limit`.
- **TTL.** `ttl` unset or zero is 30 s; above 10 minutes is 10 minutes and below 1 s is 1 s, as `page_size` is clamped (ADR 0029), so the response's `expires_at` is authoritative; negative is `INVALID_ARGUMENT`, no reason. `updated_at` and `expires_at` are the daemon's clock.

### Reporting, replacing, clearing

- **`ReportPresence` without `presence_id`** creates an entry and returns it. **With `presence_id`** it replaces that live entry and returns it, keeping the id: an id that is malformed is `INVALID_ARGUMENT`, reason `INVALID_PRESENCE_ID` (metadata `presence_id`); one that names no live entry (cleared, expired, or from before a daemon restart) is `NOT_FOUND`, reason `PRESENCE_NOT_FOUND`; one whose fixed fields differ is `INVALID_ARGUMENT`, reason `PRESENCE_MISMATCH`, metadata `presence_id` and `field`. A client that reported before a restart reports again without an id; R2.11's reporters do that on `PRESENCE_NOT_FOUND`.
- **`ClearPresence`** ends a live entry now (`end_reason: CLEARED`). Clearing an id that names no live entry succeeds (it is `IDEMPOTENT`); a malformed id is `INVALID_PRESENCE_ID`.
- **The id is the capability.** Any client may replace or clear any client entry whose id it holds, as any client may renew a lease whose id it holds (ADR 0019, ADR 0027: one uid is one trust domain). No client may replace or clear a daemon entry, nor report kind `LEASE`: `INVALID_ARGUMENT`, reason `DAEMON_PRESENCE`, metadata `presence_id` or `kind`.
- **Caps.** At most 4,096 client entries per daemon (`Limits::max_entries`) and 32 per agent (`Limits::max_entries_per_agent`); one more is `UNAVAILABLE`, reason `TOO_MANY_PRESENCE_ENTRIES`, metadata `limit` and, for the per-agent cap, `agent`, hint "Clear entries you no longer need, or replace one by its presence_id instead of reporting a new one." A report never evicts another entry: a client that forgets to pass its id back finds out at once instead of silently pushing out others. Daemon entries are not counted; they are bounded by active workspaces and running creates and builds.
- **Never persisted.** Entries live in the daemon's memory only: not in SQLite, not in backups, not across a restart. Presence works during a quiesce (it writes nothing); `RenewLease` does not, so no `LEASE` entry changes then.

### Expiry and ending

- An entry lapses at `expires_at` unless replaced, and ends with `end_reason: EXPIRED`, delivered within the frame interval of that instant (one timer task wakes at the earliest deadline, not a periodic sweep).
- An entry naming a workspace ends with `end_reason: GONE` when the workspace is released or reclaimed (in `Manager::reclaim`, after `finish_workspace`); an entry naming a repository ends the same way when the repository is forgotten (`Manager::forget_repository`). A report naming a workspace that ended in the last minute is refused as not active even if it raced the end: the hub keeps the last 1,024 ended workspace ids for that check.
- Shutdown ends nothing: streams end with `UNAVAILABLE` and no reason, as R2.09's do, and entries vanish with the process.

### What a subscriber receives

- **The current set, then changes.** The first frames carry every live entry the filter matches, as events with `ended: false`, at most 1,000 events and 1 MiB per frame, in id order; the frame that completes the set has `synced: true`, and so has every later frame. An empty set is one empty frame with `synced: true`, sent at once, so every subscription's first frame arrives promptly and says where it stands. After that, each frame carries changes: an entry that appeared or changed (its current state, `ended: false`) or ended (its last state, `ended: true`, `end_reason`).
- **One state per entry per frame, in order.** A frame holds an entry at most once, at its latest state; an entry's states arrive in the order they happened and never older after newer. An entry the subscriber was never sent that ends before it is sent is not sent at all: a 30 ms progress entry is noise, not presence. An `ended` event is only ever for an id the subscriber was sent.
- **Intermediate states may be skipped; the end state never is.** Presence coalesces where the operation log holds back: a subscriber always converges on the current set, and never receives more than one frame per 50 ms (`Limits::frame_interval`, as R2.09's live frames). design.md's "coalesce, never drop" holds per entry: what is dropped is superseded states of an entry, never the fact that it exists or ended.
- **Timing.** A frame goes out as soon as there is a change, unless the previous frame with events went out less than 50 ms before; then everything changed meanwhile goes in one frame. An isolated change is never delayed. A keepalive (an empty frame, `synced` as it stands) after 15 s without a frame (`Limits::keepalive`, R2.09's).
- **A new subscription replaces what the client held.** There is no cursor and no resume: the set is small and in memory, so a reconnecting client subscribes again and treats the new set as the whole truth, dropping entries it held that are not in it. The service comment says so.

### Filters

`SubscribePresenceRequest`'s four fields, ORed within a field and ANDed across, resolved once at the start: `repos` as `repo` references (unknown is `NOT_FOUND`, `REPOSITORY_NOT_FOUND`; a path in no repository `REPOSITORY_NOT_REGISTERED`); `workspaces` as `GetWorkspace` resolves a `workspace` with an empty `repo`, any state (unknown is `NOT_FOUND`, `WORKSPACE_NOT_FOUND`); `agents` exactly; `kinds` (`UNSPECIFIED` or an unknown value is `INVALID_ARGUMENT`, no reason). An entry with no repository never matches a `repos` filter. A repository or workspace that ends mid-stream does not end the stream: its entries end (`GONE`) and the filter matches nothing new. Because an entry's filtered fields are fixed, membership is decided once per entry.

### Flow control

- **Each subscription is one task feeding a channel of one**, as R2.09's, with the same `Slot` from `Subscriptions::admit`: the cap of 1,024 counts operation and presence subscriptions together (`TOO_MANY_SUBSCRIPTIONS`), as R2.09's brief promised. The task drains the hub's changes continuously into a pending map keyed by entry id (latest state wins), whether or not the transport has taken the last frame; it builds a frame only after `Sender::reserve` gives it the slot. A slow subscriber therefore costs one built frame, what HTTP/2 lets the transport hold, and a pending map of at most one state per matching entry: memory bounded by the entry caps, not by time or by the rate of changes.
- **The hub broadcasts changes** on a `tokio::sync::broadcast` channel of `Arc<Change>` with capacity 4,096 (`Limits::backlog`). R2.09 rejected a broadcast for the operation log because a lagging receiver loses events; here a lag is repaired from state: a session told `Lagged` resynchronizes by comparing what it has sent (`HashMap<id, seq>`) with the hub's current matching set, sending the current state of every entry that is new or newer and `ended` for every sent entry no longer live, with its end reason from the hub's ring of the last 4,096 ended entries (`end_reason: UNSPECIFIED` if it has rolled out of the ring). A session lags only if its task is starved for 4,096 changes, since it drains while it waits.
- **A chatty publisher is coalesced, not refused.** The hub stores every report at once (the response returns it), but broadcasts an entry's changes at most once per 50 ms (`Limits::publish_interval`): the first change after a quiet interval goes at once, and later ones within the interval are folded into one deferred broadcast of the latest state at the interval's end. That caps fan-out work at 20 changes a second per entry whatever the client does, keeps an isolated report's latency at zero, and never fails a report for its rate. The entry caps bound the number of entries a client can churn.
- **Shutdown and disconnect** are R2.09's: the task selects on `AppState::shutdown` (ends with `UNAVAILABLE`, no reason, hint "The daemon is shutting down; subscribe again when it is back; the set you receive then replaces what you held.") and on `Sender::closed`, frees its slot on every exit, and turns a panic into `INTERNAL` with an `error` log.

### What the daemon reports

Daemon entries have `by_daemon: true` and name, as their agent, the workspace's owner (the lease holder), not the `reef-agent` of whichever call caused them, so one workspace's daemon entries agree.

- **`LEASE`, on every issue and renewal.** `LeaseManager::issue_with_workspace` (create), `issue` (restore) and `heartbeat` (every `RenewLease`, `ws run`'s and `reef mcp`'s heartbeats, store builds' scratch leases) publish or replace one entry per workspace: `repo_id`, `workspace_id`, `change_id` (the workspace's), `lease` (the `v1::Lease` as of that moment, through `convert::lease`, which becomes `pub(crate)`), `updated_at` the renewal, and `expires_at` two heartbeat intervals later (`2 × heartbeat_every`). So the entry is "the holder is heartbeating": it lapses (`EXPIRED`) when two heartbeats are missed, long before the lease itself expires, which is what the fleet panel's "what is stuck" needs; the next renewal starts a new entry. It ends `GONE` when the workspace is released or reclaimed. After a daemon restart no `LEASE` entries exist until each holder's next heartbeat (at most `heartbeat_every`): presence reports liveness seen, not leases held, and `ListWorkspaces` still lists every lease. This is observing heartbeats; heartbeats are not sent over presence. A `ReportPresence` that renewed a lease would make an ephemeral channel carry a durable capability, and `RenewLease` already travels on the same connection.
- **`EDITING`, from snapshots.** A post-snapshot hook (the first production use of `Scheduler::on_snapshot`), for `Watcher` and `Explicit` snapshots that recorded an operation in an active workspace, publishes or replaces one entry per workspace: `paths` the files the snapshot changed (a `diff_page` from the commit it rewrote to its new commit, at most 64, so ignored files never appear and only what was committed does), merged in front of the entry's previous paths, most recent first, at most 64 and 4 KiB; `change_id` the workspace's; `expires_at` 60 s after the latest such snapshot (`Limits::editing_ttl`). `SnapshotOutcome` gains `rewrote: Option<CommitIdHex>` (the plan's `rewrite_of` when an operation was recorded) for it. The diff runs on the blocking pool under the hub's own semaphore of two permits, apart from `Reads`' and subscriptions' permits; one that waits more than 1 s is skipped and the entry refreshed without new paths. A move ends the entry (`CLEARED`): its paths were on the old change. A release or reclaim ends it `GONE`. These are files changed, observed after the fact; an agent's declared intent ("about to edit src/lib.rs") is a client `EDITING` entry, R2.11's.
- **`PROGRESS`, for creates and store builds.** A guard, `presence::Progress`, is started with the entry's fields and updated with `phase(name)`, `count(done, total, unit)`; it publishes nothing until the operation has run 250 ms (`Limits::progress_after`, a timer task, so a long first phase shows), then publishes and replaces its entry as it changes (the hub's coalescing applies), refreshes `expires_at` to 10 minutes from each update, and ends the entry (`CLEARED`) when dropped, on success, failure, panic or a client that went away. Creates: phases `resolve`, `base`, `materialize`, `mount`, `jj`, `seed`, `insert`, `watch` at the existing lap points, `done` the steps finished of `total` 8, `unit` `steps`, `workspace_id` the id step 1 generated (a subscriber cannot filter by it yet, since the row is written in step 7; it filters by repository). A store build's scratch workspace's create reports this way too. Store builds: one more entry, `repo_id` the build's, no workspace, `activity` unset, phases `resolve`, `create`, `build` (`done` the output lines so far, `total` 0, `unit` `lines`), `seal`, agent the build call's `reef-agent`, else `reef-store-build` (the scratch owner). Snapshot scans, GC, backup and reclaim report no progress here (see "Out of scope").

### Limits

`presence::Limits { max_entries: 4_096, max_entries_per_agent: 32, publish_interval: 50 ms, frame_interval: 50 ms, frame_events: 1_000, frame_bytes: 1 MiB, backlog: 4_096, keepalive: 15 s, progress_after: 250 ms, editing_ttl: 60 s }`, `Default` as given. `Config` gains `presence: presence::Limits`, set like `subscribe` and not a configuration-file key, so tests shrink it through `TestDaemon::start_with`. ### Schema additions

`reef_api::API_REVISION` becomes 5 and `API_DIGESTS` gains its fifth entry. In `presence.proto`, which now imports `reef/api/v1/workspaces.proto`:

```proto
// Why a presence entry ended.
enum PresenceEndReason {
  // Not ended; on an ended event, a reason the daemon no longer knew (the
  // subscriber fell more than 4,096 changes behind and was resynchronized).
  PRESENCE_END_REASON_UNSPECIFIED = 0;
  // ClearPresence, or, for an entry the daemon reports, what it describes
  // finished.
  PRESENCE_END_REASON_CLEARED = 1;
  // Not reported again before `expires_at`. For a lease entry: two
  // heartbeats were missed; the lease itself may still be active.
  PRESENCE_END_REASON_EXPIRED = 2;
  // What it is about is gone: its workspace was released or reclaimed, or
  // its repository forgotten.
  PRESENCE_END_REASON_GONE = 3;
}

message Presence {
  // …R2.01's fields 1 to 11…
  // For PRESENCE_KIND_LEASE: the lease as of the heartbeat this entry
  // reports. Unset for other kinds.
  Lease lease = 12;
  // Reported by the daemon itself (leases, snapshots, creates, store
  // builds). ReportPresence and ClearPresence refuse such an entry.
  bool by_daemon = 13;
}

message PresenceEvent {
  // …R2.01's fields 1 and 2…
  // Why it ended; unspecified while it has not.
  PresenceEndReason end_reason = 3;
}
```

Why each is needed: `lease` because a `LEASE` entry exists to show a heartbeat, and without the lease's own `expires_at` and `heartbeat_every` a fleet panel must call `GetWorkspace` on every heartbeat; `by_daemon` because a client must know which entries it may touch, and observed edits (snapshots) differ from declared intent (an agent's report) for R3.36; `end_reason` because "cleared" (finished) and "expired" (went silent) are the fleet panel's two most different signals and `ended` alone cannot tell them apart.

Comment-only changes that do not move the digest: the three RPCs' comments lose "Declared; R2.1x implements it." and state their behavior and errors (ADR 0029 checklist 9, below); `PresenceKind.PRESENCE_KIND_EDITING` gains "Reported by the daemon from snapshots (files changed), or by a client (files it is editing)"; `ReportPresenceRequest.ttl` gains "clamped to 1 second at least"; `change` gains "a full change id"; `SubscribePresence`'s comment states the set-then-changes contract, coalescing, the 50 ms spacing, the frame bounds, that a new subscription's set replaces what the client held, and that nothing is persisted; `PresenceEvent.ended` becomes "It was cleared, expired, or what it is about is gone." (a fuller description of the same meaning, now that `end_reason` says which).

Errors, as each RPC's comment states them:

- `ReportPresence`: `INVALID_ARGUMENT` (`INVALID_AGENT`; `INVALID_PRESENCE_ID`, `PRESENCE_MISMATCH`, metadata `presence_id`, `field`; `DAEMON_PRESENCE`, metadata `kind` or `presence_id`; `PRESENCE_TOO_LARGE`, metadata `field`, `limit`; `INVALID_PATH`, metadata `path`; `INVALID_CHANGE_ID`, metadata `change`; no reason for an unspecified kind, a field another kind carries, a negative TTL, or `change` without `repo` or `workspace`); `NOT_FOUND` (`PRESENCE_NOT_FOUND`, metadata `presence_id`; `REPOSITORY_NOT_FOUND`, `REPOSITORY_NOT_REGISTERED`, `WORKSPACE_NOT_FOUND`); `FAILED_PRECONDITION` (a workspace that is not active); `UNAVAILABLE` (`TOO_MANY_PRESENCE_ENTRIES`, metadata `limit`, `agent`).
- `ClearPresence`: `INVALID_ARGUMENT` (`INVALID_PRESENCE_ID`; `DAEMON_PRESENCE`).
- `SubscribePresence`: `INVALID_ARGUMENT` (an unspecified or unknown kind); `NOT_FOUND` (`REPOSITORY_NOT_FOUND`, `REPOSITORY_NOT_REGISTERED`, `WORKSPACE_NOT_FOUND`); `UNAVAILABLE` (`TOO_MANY_SUBSCRIPTIONS`; no reason, mid-stream, when the daemon shuts down).

### Client

### `reef presence watch`

A new noun, `presence`, after `op` in `--help` ("Show what agents are doing now: activity, editing, leases, progress"), with one verb now; R2.11 adds `report` and `clear`.

- **Usage**: `reef presence watch [--repo REPO]... [--workspace WS]... [--by AGENT]... [--kind KIND]... [--count N] [--for SECONDS | --follow]`, `KIND` one of `activity`, `editing`, `lease`, `progress`. `about`: "Print presence as it changes (JSON lines on a pipe)"; `after_help`: "Example: reef presence watch --for 0". Every repository unless `--repo` names some: presence is a fleet view, as `ws list` is, so it does not take the scope rule's repository.
- **It ends by itself**, after `--for` seconds (default 30) or `--count` events printed, unless `--follow` (which still ends at `--count`). `--for 0` prints the current set and stops at the first `synced` frame: the "who is doing what now" list. It prints no note when the time runs out: there is no position to continue from.
- **Output**: each event as its frame arrives, flushed per line. `-o json` prints one `json::PresenceEvent` per line: `{"ended": bool, "end_reason": "cleared" | "expired" | "gone" | null, "presence": {"id", "agent", "repo_id", "workspace_id", "change_id", "kind", "activity", "paths", "progress": {"phase", "done", "total", "unit"} | null, "lease": <json::Lease> | null, "by_daemon", "updated_at", "expires_at"}}`, empty strings as `null` and `total: 0` as `null`. Text prints one line per event: kind, agent, the workspace's first 8 characters or `-`, then what it says (the activity; up to three paths and `(+N)`; `phase done/total unit`; the lease's expiry), or `ended (<reason>)`. JSON Lines, as `op watch` (ADR 0036, decision 12).
- **Reconnects and stays a correct delta stream**: a stream that ends with `unavailable` and no reason, or a transport error, is resubscribed with `op watch`'s backoff (100 ms doubling to 2 s, until the `--for` deadline, or for 60 s of failures with `--follow`), without starting a daemon. The command keeps the entries it has printed as live (id and `updated_at`); after resubscribing it prints only entries that are new or changed, and when the new set is synced, an `ended` event (`end_reason: null`) for every entry it held that the new set lacks. A consumer of the lines never needs to know a restart happened.
- **Ends quietly** as `op watch` does: SIGINT and SIGTERM end it with exit 0, a closed stdout (`| head -1`) exits 0, noticed within 200 ms. `op watch`'s `stdout_closed`, `reconnects`, the backoff constants and the signal setup move to `cli/stream.rs`, which both commands use.
- **Not in the agent guide** (1,596 of 1,600 bytes); `reef presence --help` and `reef guide -o json`'s command list carry it. `reef --help` grows to 44 lines.

### MCP: no tool

`tools/list` is 19,983 bytes against a 20,000-byte test budget, and a presence tool's description and schema would need several hundred. An agent does its work without watching presence: waiting for something to happen is `wait_for_operations`, and an agent's own reporting is R2.11's, which needs no tool (the server reports for its own calls). `NOT_TOOLS` changes to: `ReportPresence` "reported for the server's calls by R2.11, not as a tool", `ClearPresence` the same, `SubscribePresence` "a stream for live views; wait_for_operations waits". Revisiting the budget is R2.25's or a later ticket's.

## Implementation notes

- **Order**: the schema, revision and reasons (`buf lint`, `buf format`, `buf breaking` against main); `PresenceHub` and its unit tests; the session over a fake hub; the handler and tests 1 to 8, 12 to 16, 18; leases (9); the snapshot hook (10); progress (11, 17); the client; `cli/stream.rs` with `op watch`'s tests passing untouched, then `presence watch` (19, 20); `NOT_TOOLS` (21); docs.
- **The hub's lock is a `std::sync::Mutex`**, held only to change the map and send on the broadcast channel (`send` never blocks), so broadcast order is change order and `subscribe` can take the set and a receiver under the same lock. Never await while holding it. Every change carries a hub-wide `seq`; a session drops broadcast changes with `seq` at or below the set's.
- **The timer task** holds a `BTreeMap<(Instant, PresenceId), Due>` of expiries and deferred broadcasts, sleeps until the first, and is woken by a `Notify` when an earlier deadline is inserted. It stops with `AppState::shutdown`.
- **Daemon entries are keyed** in the hub by `DaemonKey::{Lease(WorkspaceId), Editing(WorkspaceId), Progress(u64)}`, so a publisher replaces its entry without holding its id.
- **`LeaseManager` publishes after its database write succeeds**, never before, and from whatever thread it runs on: `publish_daemon` takes the lock and returns. It needs `heartbeat_every` and the workspace's change id; read the change id from the loaded workspace entry, not a database query per heartbeat.
- **The `EDITING` hook is synchronous** (`SnapshotHook` is `Fn(&SnapshotOutcome)`): it copies what it needs and spawns the diff task. The diff reads from `OpEvents`' tip as R2.09's `blocking_read` does, under the hub's semaphore, not `Reads::run`.
- **The `Progress` guard's delay task** holds a `Weak` to the guard's state, so a guard dropped before 250 ms publishes nothing and leaves no task behind.
- **Never await a jj-lib future on a tokio worker**: the diff runs inside `spawn_blocking` under `pollster::block_on`.
- **Linux**: nothing here is `cfg(target_os = "linux")`; still run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy with and without `--all-features` in the privileged `ubuntu:24.04` container (`docs/benchmarks.md`, "Linux") before pushing, since `Manager::new`, `LeaseManager::new` and `Config` change under Linux-only test files.

## Risks

- **A connection's window is shared.** A client that stops reading one stream leaves at most that stream's window (2 MiB, hyper's client default) unread in the connection's 5 MiB, so presence keeps flowing beside one stalled operation stream (test 13); three stalled streams on one connection would stall every stream on it. The service comments tell clients to read every stream they open, or open a stalled consumer on its own connection.
- **Daemon entries name the owner, not the agent.** `ws run`'s workspaces are owned by `user@host:<pid>`, so filtering presence by `REEF_AGENT` misses their lease and editing entries until R2.11 decides whether `ws run` passes the agent as the owner (open question 1).
- **`EDITING` is after the fact.** It shows files a snapshot committed, a debounce and a scan after the write, and only in workspaces with a watcher or explicit snapshots; R3.36's warning "while avoiding the conflict is still cheap" also wants agents' declared intent, which is R2.11's and R2.25's (hooks on an agent's edit tool).
- **Lease entries vanish at a restart** until the next heartbeat (60 s by default); a fleet panel must not read "no lease entry" as "not held" without `ListWorkspaces`.
- **The hook adds work to every snapshot that changed something**: a small tree diff on the blocking pool. The load test measures it; if it moves p95, the hook computes paths only while a presence subscription is open (open question 5).
- **Clock.** `updated_at` and `expires_at` are the daemon's clock; a remote client (R2.08) with skew should use them relative to each other, not to its own clock.

## Choices this brief made, and why

- **All three RPCs here**: the channel's semantics cannot be split from the RPCs that change it, and delivery is measured from a report.
- **A second stream on one connection**: opposite delivery contracts, independent flow control, and the declaration already exists.
- **Fixed identity per entry**: filter membership never changes, so a subscriber sees appear, change, end and nothing else.
- **Set then changes, no cursor**: presence is small and in memory; a fresh set is an exact resync.
- **Broadcast with resync**: the one place a lossy channel is right, because state, not history, is the truth.
- **Coalesce publishers instead of refusing them**: bounded fan-out, zero latency for the isolated case, no error path for a cosmetic signal.
- **Refuse at the caps instead of evicting**: a leaking client finds out itself.
- **Lease entries lapse after two missed heartbeats**: liveness is the signal; the lease's own expiry rides in the entry.
- **`EDITING` from committed diffs**: no ignored files, no guessing.
- **Progress after 250 ms**: motion only for state change; a fast create is not news.
- **No MCP tool**: 17 bytes of budget, and no agent task needs it.

## Open questions

1. Should `ws run` (R2.11) pass `REEF_AGENT` as the workspace's owner, so daemon entries and the lease name the agent? Today owners are `user@host:<pid>`, and daemon entries name the owner.
2. Snapshot-scan progress for large trees: which ticket threads jj-lib's snapshot progress callback through reef-lib (R2.23, which reworks the snapshot path, is the natural home)?
3. Is a presence MCP tool wanted once the `tools/list` budget is revisited (R2.25 or later), for an agent that should notice another agent in the same area before it edits?
4. Should a daemon start publish `LEASE` entries for every active lease (as "issued, not yet heartbeated"), instead of waiting for each holder's next heartbeat?
5. If the load test shows the `EDITING` diff moving p95 write-to-snapshot latency, is computing paths only while a presence subscription is open acceptable (entries would then appear with empty paths for a later subscriber)?
6. Is refusing change id prefixes in `ReportPresenceRequest.change` an acceptable reading of ADR 0029's rule 7 (requests accept reverse hex), given presence never reads jj? Full ids in either alphabet are accepted.
7. When a store exists (R4), presence crosses daemons: ids will need a daemon prefix, and the store's broker will hold the set. Nothing here blocks that, but the 16-hex id format is per daemon.
