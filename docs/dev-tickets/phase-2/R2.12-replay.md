# R2.12 Replay

Phase 2 · Size M · Depends on: R2.09 (the `operations` and `workspace_events` index, `seq`, `Daemon.Status.seqs`), R2.02 (`Changes.Log`'s `Change` message and the function that fills it from an `Arc<ReadonlyRepo>`; `RepoHandle::head()` and reads on the blocking pool) · Unblocks: R2.21 (the activity feed's scrubber is a `Replay` call per position)

## Context

"Because the log is complete, any live view can be replayed from any point in time" (`docs/design.md`, API). The activity feed has "a scrubber to replay any period" (Human interface, the five live views). R2.09 made every operation and workspace event addressable by one `seq`; this ticket answers "what did the smartlog and the workspace list look like at `seq` N (or at operation X, or at 14:02)?" from the daemon, so the UI renders a past state through the same components it renders the present with, and a human auditing a fleet's afternoon scrubs rather than reads a log.

jj keeps every operation's view, so the changes side is exact: load the repository at that operation and ask the same questions `Changes.Log` asks of the head. The workspace side is Reef's own history: rows that are never deleted before GC (`workspaces`, `leases`, `reclaims`) plus R2.09's indexed workspace events, which together say which workspaces existed, on which change, with which lease, at any moment. Presence has no history by design and is absent from a replay.

### What was verified while writing this ticket

Reef at `d156d1e`; jj-lib 0.46.0 as vendored.

- **Loading a repository at a past operation.** `RepoLoader::load_at(&self, op: &Operation) -> Result<Arc<ReadonlyRepo>, RepoLoaderError>` (`jj-lib/src/repo.rs:828-831`) reads the operation's view and finishes the load; `RepoLoader::load_operation(&OperationId)` (`:860`) fetches an operation by id; `reef_lib::jj::Repo::wc_commit_at` (`reef-lib/src/jj/oplog.rs:220-250`) already does `load_operation` then `operation.view()` to read one workspace's commit at an operation, and `Transaction::merge_operation` (`jj-lib/src/transaction.rs:103-114`) uses `load_at` on two operations. `ReadonlyRepo::operation()`, `view()` (`repo.rs:320, 324`); `View::wc_commit_ids()`, `heads()`, `local_bookmarks()` (`view.rs:65, 87, 176`). The result is the same `Arc<ReadonlyRepo>` type R2.02's log reads from the head, so R2.02's `log(head: &Arc<ReadonlyRepo>, ctx, revset, page, with_graph) -> Result<LogPage, LogError>` serves a past operation unchanged.
- **The index at a past operation.** The default index store keeps one index segment per operation under `.jj/repo/index/operations/`; `finish_load` loads or builds the segment for the operation it is given. For an operation whose segment GC's `reinit` removed (R1.17 empties and rebuilds the index), jj rebuilds it from the commits the view reaches. Not measured here; see Risks.
- **Reef's workspace history.** `workspaces` rows carry `created_at` and are kept as `released`/`reclaimed` until R1.17's GC deletes rows older than the undo window (`db/workspaces.rs:447-466`); `reclaims` carries `at`, `reason`, `final_op_id` (`model/mod.rs:309-328`); `leases` carries `issued_at`, `expires_at`, `ended_at`, `end_reason` (`:282-305`), and `expires_at` is overwritten by each heartbeat (`db/leases.rs:268`, `renew_lease`), so a lease's past expiry is not recoverable. R2.09's `workspace_events` has `created`, `snapshotted`, `moved`, `released`, `reclaimed`, `attention`, `lease_issued`, `lease_expired`, each with a `seq` and `at`, and `operations` has `end_at` and `observed_at` per operation with the Reef workspace it ran in.
- **A workspace's change at an operation is in jj's view**, not Reef's rows: `wc_commit_ids[reef-<id>]` in the view of that operation (`wc_commit_at` reads exactly that), so the change and commit a workspace was on at `seq` N come from jj and need no Reef history.
- **tonic** unary handlers return the whole message; `ReplayState` for 200 workspaces and a 200-change log is under 200 KiB, within the 4 MiB default.

## Decisions

The README's "Replay" row is binding: `Operations.Replay { repo, at: oneof { seq, op_id, time } } -> ReplayState { op_id, seq, at, changes, workspaces }`; changes from `RepoLoader::load_at`, read on the blocking pool; presence absent.

- **Resolving `at` to one operation.** `seq`: the newest `operations` row of the repository with `seq <= N` (a `seq` that names a workspace event replays at the operation current then); `op_id`: that operation's row (a prefix is accepted as everywhere, `INVALID_ARGUMENT` if ambiguous); `time`: the newest row with `end_at <= time`. No row (a `seq` before the repository's first indexed operation, a time before it) is `NOT_FOUND` with the hint naming the oldest `seq` and `at` the index holds for the repository, read from `Daemon.Status.seqs` and `events::index::oldest_seq`. A row with `gc_rewritten = 1` (R2.09: the operation left the log and no rewrite matched) is `NOT_FOUND` with the hint "operation <op> was removed by GC; replay at seq <next surviving seq>". `repo` is required: a replay is of one repository (the smartlog is).
- **The changes side.** On the blocking pool, under R2.02's `[api] max_concurrent_reads` semaphore: `RepoHandle::head()` for the loader (`head.loader()` is shared), `load_operation(op_id)`, `load_at(&operation)`, then R2.02's `log(&repo_at, ctx, revset, &first_page, with_graph = true)` with the request's `revset` (default: R2.02's `reef_log()` evaluated on that view) and `with_graph` set, so `Change.edges` is filled and rows come in `TopoGroupedGraph` order. `ReplayState.changes` is `repeated Change` exactly as `Changes.Log` returns them with the graph, so the smartlog component renders both the same way. `ReplayState` also carries `bookmarks: repeated Bookmark { name, change: ChangeRef }` from the view's local bookmarks, because the smartlog labels them.
- **The workspaces side.** From SQLite, in one read transaction: every `workspaces` row of the repository with `created_at <= at` (the operation's `end_at`), each reconstructed to `at`:
  - `state`: `active`, unless a `reclaims` row for it has `reclaims.at <= at` (then `released` or `reclaimed` by its `reason`); `releasing` is not reconstructed (it lasts a snapshot).
  - `change_id`, `commit_id`: from the operation's view, `wc_commit_ids[reef-<id>]` through the store (the same `Arc<ReadonlyRepo>` the changes side loaded; one `get_commit` per workspace); a workspace the view lacks (its jj workspace was forgotten before `at`, or created in a later operation whose row's `created_at` precedes `at` by clock skew) is reported with its row's current ids and `reconstructed = false`.
  - `lease`: the `leases` row with `issued_at <= at` and (`ended_at IS NULL OR ended_at > at`), with `expires_at` omitted and `state = UNKNOWN` (a new `Lease.State` value) because past expiries are not recorded; `issued_at`, `owner`, `length_ms`, `grace_ms` are exact.
  - `last_snapshot_at`, `last_snapshot_op`: the newest `operations` row for the workspace with `end_at <= at` and `kind = snapshot`.
  - `attention`, `divergent`: from the newest `workspace_events` row of kind `attention` with `at <= at` (its `detail` holds the value R2.09 records as `<attention>|<divergent>`; R2.09's `Manager::set_attention` publishes both), else as the row is.
  - `presence`: empty, `heartbeat_at`: unset.
  Every reconstructed field that came from history rather than the current row is exact; `ReplayState.workspaces[].reconstructed` is false only in the view-lacks case above, and `ReplayState.partial = true` when any is.
- **Cache.** Loading a repository at an old operation can cost an index build (Risks); the daemon keeps an LRU of `[events] replay_cache` (default 32) `Arc<ReadonlyRepo>`s keyed by `(repo_id, op_id)`, and an LRU of the same size of finished `ReplayState`s keyed by `(repo_id, op_id, revset)`. A scrubber dragged across 1,000 positions asks for the same handful of operations repeatedly near each stop. Entries are dropped on GC (op ids change) and on forget. Memory: an `Arc<ReadonlyRepo>` at an old operation shares the store and holds its own index segment handle; 32 of them on `large` is on the order of tens of MiB and is measured in the PR.
- **Two cheap forms for the scrubber.** `ReplayRequest.only: enum { ALL, CHANGES, WORKSPACES }` skips the half the client did not ask for; and `Operations.Log` (R2.02) already gives the scrubber its axis (every operation with `seq` and `end_at`), so the UI never calls `Replay` to find where to scrub, only to render where it stopped.
- **`reef replay --at <seq|op-prefix|RFC 3339 time> [--repo] [--only changes|workspaces] [REVSET]`**: text prints the log as `reef log` does (R2.02's renderer over `changes`) followed by a workspace table as `reef ws list` prints, both headed by `at <time> (op <short>, seq <n>)`; JSON is one `ReplayState` object. `--at` is required (`reef log` is the present).
- **ADR 0044, "Replay"**: the operation as the unit of replay (jj's view is the truth for changes; Reef's rows and indexed events for workspaces), what is exact and what is not (`expires_at`, `releasing`, presence), the cache and why, the GC rule (`gc_rewritten` is `NOT_FOUND`; the undo window bounds how far back a replay reaches, which the ADR states as the product rule: replay reaches as far as undo), and the alternatives (a periodic snapshot of the workspace table into SQLite, rejected: the events already are that history; rebuilding from `Operations.Log` on the client, rejected: the client would need jj).

## Tests

`small` preset; `[events] frame_interval = "20ms"`.

1. `replay_at_seq_shows_the_log_then` (`tests/replay.rs`): create W1, snapshot it twice (`s1`, `s2`), create W2, snapshot it (`s3`), release W1 (`s4`); `Replay(seq = seq(s2))`: `changes` equals `Changes.Log` as it was recorded by the test right after `s2` (the test snapshots `Log`'s output at each step), `workspaces` has W1 `active` on `s2`'s commit and no W2; `Replay(seq = seq(s3))` has both active; `Replay(seq = seq(s4))` has W1 `released` with the final op and W2 active. `partial == false` throughout.
2. `replay_at_op_and_time_agree`: for each operation `o` in `Operations.Log`, `Replay(op_id = o)` and `Replay(time = o.end_at)` return the same `op_id` and `seq`; `Replay(time = o.end_at − 1 ms)` returns the previous operation; a time before the first indexed operation is `NOT_FOUND` with a hint naming the oldest `seq`.
3. `workspace_change_comes_from_the_view`: W moved from change A to B at operation `m`; `Replay(seq(m) − 1)` shows W on A, `Replay(seq(m))` on B, both with `reconstructed == true`; the current row says B throughout.
4. `lease_is_reconstructed_without_expiry`: W created, heartbeated three times, released; `Replay` between the heartbeats shows W's lease with `issued_at`, `owner`, `length_ms`, `state == UNKNOWN`, `expires_at` unset; after the release the lease is absent and the workspace `released`.
5. `attention_history`: a divergent change (two workspaces on one change, as `integration.rs`'s test 5 makes one); `Replay` before the diverging snapshot shows `divergent == false`, after it `true` with `attention == "divergent"`.
6. `revset_applies_at_the_past_view`: `Replay(seq, revset = "<change A>")` on a seq where A existed returns A alone; on a seq before A's creation returns no changes and no error (the revset resolves against that view: jj's `NoSuchRevision` is `NOT_FOUND`; test both).
7. `gc_rewritten_is_not_found` (`gc.undo_window = "0s"`, `gc.reindex_limit` low): operations, GC, a `Replay(seq)` at a `seq` whose row GC marked `gc_rewritten` is `NOT_FOUND` with `next` naming `reef replay --at <surviving seq>`; a `seq` whose row was remapped replays.
8. `cache_hits_and_invalidation`: 50 `Replay`s at one op: the second and later take under a tenth of the first's time (printed and asserted at < 1/2 to stay robust) and the daemon log has one `replay loaded` line; `Gc` then `Replay` logs a second load.
9. `replay_is_a_read` : 100 concurrent `Replay`s at distinct operations finish with no new operation written (`Operations.Log` unchanged) and `Daemon.Status.seqs` unmoved; the repository thread served no job during them except the GC-free ones (`repo_thread` job count from the log, if R2.02 logs it; else skipped with a note).
10. `reef_replay_cli` (`crates/reef-vcs/tests/cli.rs`): `reef replay --at 1 -o json` is one object with `changes` and `workspaces`; text mode prints the `at` heading, a log and a table; `--at tomorrow` is a usage error with a hint; `reef replay` without `--at` exits 2 with `next = ["reef","log"]`.

## Implementation notes

- Resolve `at` and read the workspace history in one `Db::with` so a concurrent reclaim cannot land between the two reads; then load the repository on the blocking pool; then the per-workspace `get_commit` calls on the same thread.
- `load_at` on an operation whose index segment is gone makes jj build one; do it under the reads semaphore and log `replay loaded` with `load_ms` so the cost is visible. The cache keeps the `Arc<ReadonlyRepo>`, not only the state, so a second revset at the same op is cheap.
- Keep `ReplayedWorkspace.workspace` a `v1::Workspace` built through the same `WorkspaceView` conversion `List` uses, with the reconstructed fields substituted, so the UI's workspace components render it.
- `Lease.State.UNKNOWN` must not leak into `List`/`Inspect`: only `Replay` builds it; `convert::lease` is unchanged.
- The CLI parses `--at` as an integer first, then an op prefix (hex, 4 to 64 chars), then `humantime::parse_rfc3339_weak`; say which it took in the heading.
- `invalidate` after GC runs after R2.09's reindex, so a remapped op id's cached state (keyed by the old id) is simply dropped.

## Out of scope

- The scrubber itself and the feed (R2.21).
- Presence history (none exists; the ADR says so).
- Replaying a workspace's files at a point (that is `Trees.Read` at the commit the replay names, R2.04).
- Reconstructing `expires_at` by indexing heartbeats (R2.09 chose not to; a heartbeat history table is the alternative the ADR records).
- Replay across repositories or of the daemon's configuration.

## Risks

- **Loading at an old operation may build an index.** jj's default index is per operation and GC's `reinit` discards segments; a replay at an operation from before the last GC can cost a rebuild proportional to the commits its view reaches. The cache and the semaphore bound the damage; the acceptance criterion measures it on `large`. If it is too slow, the alternative is to answer the changes side from R2.09's `operations.changes` column (what moved) without loading jj, which is approximate; the ADR records it as the fallback.
- **Reef's rows outlive jj's view only until GC.** R1.17 deletes `released`/`reclaimed` rows older than the undo window, so a replay before that window shows workspaces that jj's view names but Reef has no row for; they are reported from the view alone (`reconstructed = false`, `partial = true`). The ADR's rule "replay reaches as far as undo" sets the expectation.
- **Clock skew between `created_at` (Reef's clock) and `end_at` (jj's, the same machine).** Both are the daemon host's clock; the view check above catches the one case where it matters.
- **`Lease.State.UNKNOWN` is new API surface** for one RPC; `docs/api.md` says only `Replay` sets it.
