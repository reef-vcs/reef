# R2.12 Replay

Phase 2 · Size M · Depends on: R2.09 (`after_operation`, `live`, `head_operation_ids`: replay hands over to the live stream through them), and through it R2.02 (`at_operation`, pinned pages, effects and their cache, `ended_after` pruning) and R2.27 (`--at-op`, the CLI's scope rule) · Unblocks: R2.21 (the activity feed's scrubber), R2.19 and R2.20 (their views at a scrubbed point), R3.38 (the file browser's time axis)

## Context

The design says "because the log is complete, any live view can be replayed from any point in time" (`docs/design.md`, Subscriptions), and the activity feed is "the coalesced log with a scrubber to replay any period" (Interface). Its rule that "no state exists that the interface can show and the API cannot" makes replay an API feature, not a UI one: the UI's views at a past point must be calls an agent could make.

Most of it exists. R2.02 gave six reads an `at_operation` (`ListChanges`, `GetChange`, `GetDiff`, `ReadFile`, `ListFiles`, and through R2.14 `ListSymbols`). R2.09 replays the log forward from an operation and hands over to live frames. What is missing is narrower than the row suggests:

- **Three views have no past.** `GetStatus` (R2.02 left "`GetStatus` at an operation" to this ticket), `ListWorkspaces` and `GetWorkspace` answer only for now. `ListOperations` always walks from the op heads, so the feed ending at a past point costs a walk through everything after it.
- **There is no way to name a point by time.** A scrubber is a time axis. Today a client finds the operation at 14:00 by paging `ListOperations` with `ended_before`, 10,000 operations examined per page, through empty pages.
- **Reads at old operations are slow and write to disk.** Every GC deletes jj's index links and rebuilds the head's only. A read at any operation from before the last GC then makes jj build a full commit index for that one operation and save it, every time a new one is read (verified below). With GC daily (#95), that is most of the undo window.

This ticket adds `at_operation` to those four reads, a time lookup to `GetOperation`, makes reads at an operation share the head's commit index, and says what is not replayed and how a response shows it. R2.01's rule binds it: it adds and never changes.

### What was verified while writing this ticket

Reef at `505bfab` (R2.17 merged as #120), jj-lib 0.46.0. PR #124 (issue #114, "brief JSON by default", ADR 0045) is open. Paths are under `crates/` unless they start with `docs/`.

- **API revision and ADR numbers.** `API_REVISION` is 9 (`reef-api/src/lib.rs:49`). #124 takes revision 10, `ListWorkspacesRequest` field 6 (`changed_file_counts`), `Workspace` field 20 and ADR 0045. This ticket's revision is the next one at merge (11 after #124), and its ADR is 0046.
- **Reads at an operation today.** `at_operation` is an operation id or lowercase-hex prefix, any operation in the store (ADR 0030, decision 5). `Reads::at` resolves it with `oplog::resolve_operation` and `Reads::at_operation` loads it with `oplog::load_at`, which is jj's `RepoLoader::load_at`, cached in a FIFO of 8 (`reef-daemon/src/read/mod.rs:39`, `:343`, `:354`). A read at an operation never snapshots. `WORKING_COPY_NOT_FOUND` carries `at_operation` when the request's workspace has no working copy in that view (`reef-lib/src/jj/revset.rs:217`).
- **`GetStatus`** reads the head (`service/status.rs:116`). Its active workspaces come from `reef.sqlite3` (`manager.list(.., &[Active], ..)`, `:218`), not from the view. It refuses a workspace that is not active.
- **`ListWorkspaces` and `GetWorkspace`** read `reef.sqlite3` rows only (`service/workspaces.rs:158`, `:206`). A page token binds every request field (`service/page.rs`), so a new field is bound with no extra code. `Workspace.watch_state`, `stores`, `attention` and `Lease.state` are live state (`service/convert.rs:218`, `:93`). A lease row keeps `issued_at` and `ended_at`, but renewals overwrite `expires_at` and `last_heartbeat_at` (`db/migrations/0001_initial.sql`). The snapshot index has every snapshot operation's workspace, change, commit and `taken_at`, indexed by `(workspace_id, taken_at DESC)` (`0003_snapshots.sql`).
- **`ListOperations`** walks from the op heads through `oplog::walk_from` (`reef-lib/src/jj/oplog.rs:677`), at most 10,000 operations examined per page (`service/operations.rs:48`). `ended_before` skips newer operations without pruning (`:158`). `ended_after` stops the walk (`:183`). About 16 µs per operation (`op_page_100` 1.6 ms, `op_range_1000` 17.2 ms on `medium`, `docs/benchmarks.md`).
- **GC and jj's index.** GC rewrites every kept operation onto the root with a new id (ADR 0040). It then calls `DefaultIndexStore::reinit`, which removes every operation's index link and every segment, and reloads at head, which rebuilds the head's index alone (`reef-lib/src/jj/gc.rs:377`; jj-lib `default_index/store.rs:127`). For an operation with no link, jj's `get_index_at_op` calls `build_index_at_operation` (`store.rs:521`, `:231`). That walks back to an ancestor with a link, finds none after a GC, reads every ancestor operation's view, indexes every commit they reference, and saves a new segment and link for that operation alone. The next older operation does it all again.
- **Measured on Reef's own repository** (2,517 commits, 2,714 operations in the log, 439 index links since the last GC), through the installed CLI. `reef log --at-op` at the head or a linked operation took about 0.10 s end to end. At three operations from before the last GC it took 0.44, 0.22 and 0.16 s, and the links went from 439 to 442. On a repository the size of `large` the build is the full reindex, seconds per operation, with a full segment written each time.
- **Old ids survive one GC.** jj's op store GC keeps unreachable operation files newer than `keep_newer` (jj-lib `simple_op_store.rs:289`), and views are content-addressed and shared with the rewrites. So an operation id from before a GC still loads, with the same view, until a later GC ages it out of the undo window. R2.09 relies on this (ADR 0036, decision 9). Its ancestors older than `keep_newer` are gone, so a walk from it fails there.
- **Prior art for sharing the index.** `effects::index_holder` already computes effects with the head's index when that index holds every head of the views involved (`reef-lib/src/jj/effects.rs:177`). jj-lib's `RepoLoader::create_from(operation, view, index)` is public (`repo.rs:833`), and `DefaultReadonlyIndex` is `Clone`, reachable through `readonly_index().downcast_ref()`.
- **The CLI** has `--at-op` (alias `--at-operation`) on `log`, `show`, `diff`, `cat`, `files` and `symbols` through `scope::ReadArgs` (`reef-vcs/src/cli/scope.rs:35`). `status`, `ws list`, `ws inspect` and `op log` do not have it. The MCP server's `list_changes`, `get_change`, `get_diff`, `read_file` and `list_files` take `at_operation` (`reef-vcs/src/mcp/args.rs`). `tools/list` is at its 21,250-byte budget.

## Decisions

### Size

M. The work: one `reef-lib` loader; four request fields, three response echoes, one enum value and one lookup mode; composing a workspace at a past point from the view and the records; two reasons; four CLI flags and `--at`; an ADR; 14 tests and two benches. No new service, stream, store or background task. Each read already has its handler, and the change in each is where its repository and rows come from.

### What "any live view" means in Phase 2

A live view is replayable when everything it shows is in the operation log or derived from it. At operation X, each view answers from X's view, as jj records it:

| View (consumer) | RPC at X | What it answers |
| --- | --- | --- |
| Smartlog (R2.19) | `ListChanges`, `GetChange` (exist) | The graph and changes visible at X. |
| Diffs, files, symbols (R3.38) | `GetDiff`, `ReadFile`, `ListFiles`, `ListSymbols` (exist) | Trees as of X. |
| Repository status | `GetStatus` + `at_operation` (new) | `trunk()`, mutable heads, conflicted and divergent changes at X; the workspaces active at X; `last_operation` is X. |
| Workspace status | `GetStatus` + `at_operation` + `workspace` (new) | The workspace's working copy at X, its parents, the paths it changed and its conflicts, in any state now. |
| Fleet panel (R2.20) | `ListWorkspaces`, `GetWorkspace` + `at_operation` (new) | The workspaces active at X, each on its change and commit as of X, with its owner and lease as of X. |
| Activity feed (R2.21) | `ListOperations` + `at_operation` (new); `SubscribeOperations` with `after_operation` (exists) | X and its ancestors, newest first; and from X forward, replayed then live. |

- **A workspace is active at X** when X's view has a working copy for jj workspace `reef-<id>`. Released and reclaimed workspaces are not listed at X: the fleet panel shows who was working, not the history of who had been.
- **Counts are correct by completeness.** Every operation in a period is in `ListOperations` from the period's last operation down to its first (`at_operation` plus `ended_after`). Coalescing and counting a period is the feed's work over complete pages, as ADR 0036 left it (decision 7). This ticket adds no aggregate RPC (see "What later tickets inherit").

### What is not replayed, and how the API says so

- **Presence.** It is never persisted (design, Subscriptions; ADR 0037). `SubscribePresence` has no start, and nothing at X reports presence. A fleet panel scrubbed to the past shows no presence column. R2.10's `LEASE` liveness and `EDITING` entries are presence too.
- **Live fields of a workspace.** With `at_operation`, `Workspace.attention`, `stores` and `watch_state` are unset, and so are `GetWorkspaceResponse.disk_usage` and `snapshot`, and `WorkspaceStatus.snapshot`. These describe the daemon's state now, not the log's at X.
- **Lease liveness.** The lease at X is the workspace's lease row issued at or before X's `ended_at` and not ended by then: `id`, `owner`, `issued_at`, `length`, `grace` and `heartbeat_every`. `expires_at` and `last_heartbeat_at` are unset, because renewals overwrite them. `state` and `end_reason` are `UNSPECIFIED`. Recording every renewal would persist what R2.10 made presence.
- **Records outside the log.** Repositories, stores, daemon status, backups and the history index (`QueryChanges`, which R2.16 kept current-only) have no `at_operation`. An RPC without the field is not replayable, and its comment does not pretend otherwise.
- **How a response says it.** Every response read at an operation echoes `at_operation`, the full id read: the three new echoes below, and those that exist. `WorkspaceStatus.source` is the new `STATUS_SOURCE_OPERATION`. Each field above gains "Unset with `at_operation`." in its comment. Comment-only changes do not move the digest.

### Reads at an operation share the head's index

- **A new loader, `oplog::load_at_shared(head, operation) -> Result<Arc<ReadonlyRepo>, OpLogError>`.** It reads the operation's view. When the head's commit index holds every commit the view references (`View::all_referenced_commit_ids`, checked with `Index::has_id`), it builds the repository with `RepoLoader::create_from(operation, view, head_index.clone())`. Otherwise it falls back to `load_at`.
  - **Why it is correct.** jj's commit index is closed under ancestry, and every read at X goes through X's view. Revsets start from its heads and working copies, and `change_id_index` is built from its heads. A superset index changes no visible set. `effects::index_holder` relies on the same property, with a weaker check (heads only).
  - **The one visible difference.** A commit created after X is in the borrowed index, so a read at X that names it by commit id resolves it as `hidden: true` instead of `NOT_FOUND`. jj already resolves hidden commits by id, and "not visible at X" is what it means. ADR 0046 records it, and the `changes.proto` header's `at_operation` paragraph says so.
  - **When it falls back.** An operation off the head's history whose commits the head never indexed: a concurrent op head before the daemon reconciles it, or one `jj op abandon` dropped. Those are rare, and jj's build is correct for them.
- **`Reads::at_operation` uses it**, so every read at an operation gains it: the six that exist and the four this ticket adds. The cache grows from 8 to 64 entries (`AT_CACHE`). With a shared index an entry costs its view, not an index, so scrubbing back and forth over a few dozen operations stays in memory. `Reads::clear` still empties it at GC and forget.
- **A read at an operation the head's index covers writes nothing to the repository**: nothing goes into `index/op_links` or `index/segments`. Only the fallback still lets jj build and save an index. Test 2 checks both.

### Naming a point: operation ids, times, and GC

- **A point is an operation id**, as `at_operation` already is everywhere. A client keeps each point's `ended_at` beside its id. `Operation.ended_at` is in every response.
- **A time names a point through `GetOperation`.** A new field, `ended_at_or_before`, resolves to the newest operation that ended at or before that time:
  - **Empty `operation_id`:** the walk starts at the op heads, in `ListOperations` order (newest end first).
  - **Set `operation_id`:** the walk starts there instead. A scrubber at X jumps back an hour without walking from now.
  - **The response** is the operation found, with its effects, as `GetOperation` returns one now.
  - **A time later than the head** is the head. With concurrent op heads it is the newest end among them.
- **The walk is bounded.** It examines at most 100,000 operations (`MAX_LOCATE_EXAMINED`, about 1.7 s at 16 µs each). Past that it fails with `TOO_FAR_BACK`: at the phase's 1,000 operations a minute that is 100 minutes back from the start. Reef's own repository keeps about 2,700 operations in its week-long undo window, so there the bound never binds. Seeking further back cheaply needs a time index. That is open question 1, not this ticket.
- **Before retained history.** GC reparents the kept operations onto the root, whose time is the epoch. A time before the oldest kept operation would land on the root's empty view, which is never what a scrubber means. The lookup fails with `OPERATION_NOT_RETAINED` instead, with metadata `oldest_at`. A client that names the root operation by id still reads it, as now.
- **Across GC.**
  - **A view read at an id from before a GC keeps working**, with the same answer, until a later GC ages that operation out. The shared index makes such reads cheap instead of a full reindex each.
  - **A walk from such an id** (`ListOperations` with `at_operation`, or its page tokens) reaches the operations GC collected and fails with the existing `OPERATION_LOG_REWRITTEN` (`FAILED_PRECONDITION`, metadata `repo_id`), with a hint to locate the point again by time.
  - **An id GC aged out** is `OPERATION_NOT_FOUND`, as now. The client looks its time up again.
- **R2.09's cursors are not points.** A cursor is opaque, multi-repository and a frontier, not a view. A frame's `head_operation_ids` names a point when it holds one id. With several, the view "now" is their merge, which exists once the daemon reconciles them.
- **Operations from other jj writers** are points like any other: their views are jj's, and they classify as `EXTERNAL`. Concurrent op heads are the one oddity. An operation on one branch, before the reconciling merge, has a view without the other branch's work, so a scrubber stepping by time through two branches shows each branch's own state until the merge. ADR 0046 states it, and nothing tries to hide it.

### The fields

- **`GetStatusRequest.at_operation`.**
  - **The repository's state** is read from X's repository instead of the head: the blocking half already takes a `repo`, and nothing in it changes.
  - **Active workspaces** come from X's view (above), newest `created_at` first, 100 listed, all counted.
  - **`last_operation`** is X, with its effects.
  - **With a `workspace`**, in any state now: its working copy at X (`WORKING_COPY_NOT_FOUND` when it had none), parents, changed paths up to `max_files` and conflicts, `source` `STATUS_SOURCE_OPERATION`, and `snapshot` unset.
  - **Never snapshots**, whatever `skip_snapshot` says, and does not refuse a workspace that is no longer active.
- **`ListWorkspacesRequest.at_operation`** (and `ListWorkspacesResponse.at_operation`).
  - **The set** is the workspaces active at X. `repo` is required: an operation belongs to one repository. Without it the request is `INVALID_ARGUMENT`, no reason, hint "at_operation needs repo: an operation belongs to one repository."
  - **Filters:** `states` other than `ACTIVE` match nothing, and `owner` matches the row's owner.
  - **Order and paging** are as now, newest `created_at` first. The token binds `at_operation`, so later pages read the same X.
  - **With #124's `changed_file_counts`**, each count is of the working copy at X against its parents.
- **`GetWorkspaceRequest.at_operation`** (and `GetWorkspaceResponse.at_operation`).
  - **The workspace** as of X; `WORKING_COPY_NOT_FOUND` (metadata `workspace_id`, `at_operation`) when it was not active at X.
  - **`other_workspaces_on_change`** is computed from X's view.
  - **`snapshot_count` and `recent_snapshots`** come from the snapshot index up to X's `ended_at`.
  - **With `snapshot_first`**, the request is `INVALID_ARGUMENT`, no reason, hint "A read at an operation never snapshots; drop snapshot_first." It is an explicit request that cannot be honored, unlike the default `skip_snapshot`.
- **One rule composes a workspace at X**, for all three RPCs (`service/at_operation.rs`, `workspaces_at`):
  - **From X's view:** `change_id` and `commit_id` (the working copy), `divergent` (the change has more than one visible commit at X), and `state` `ACTIVE`.
  - **From its row:** `owner`, `purpose`, `backend`, `path`, `created_at` and `watcher`. A working copy whose row is gone is listed with the view's fields only. GC deletes rows only for workspaces released before `keep_newer`, which no retained view still holds, so this happens only after a restore or with another state directory.
  - **From the snapshot index:** `last_snapshot_at`, `last_snapshot_operation_id` and `local_snapshot_count`, counting rows with `taken_at` up to X's `ended_at`.
  - **The lease at X** as above.
  - **Everything else** unset, as listed under "What is not replayed".
- **`ListOperationsRequest.at_operation`** (and `ListOperationsResponse.at_operation`).
  - **The walk starts at X** instead of the op heads: X and its ancestors, newest first. Filters, `ended_after`, `ended_before` and effects apply as now.
  - **The page token pins `{X}`** in place of the heads; its format does not change.
  - **This is the feed ending at a past point.** It costs the operations listed, not the operations since.
- **`GetOperationRequest.ended_at_or_before`**, as above. With neither it nor `operation_id`, the request is `INVALID_OPERATION_ID`, as an empty id is now.

### Serving a scrubber

- **A stop is an operation.** The scrubber's track is `ListOperations` pages, from the newest stop shown back to the oldest, with `at_operation` and `ended_after` bounding the period. Its stops are the operations, its times their `ended_at`, and stepping back or forward is the next entry either way.
- **The delta between adjacent stops is the operation's effects.** `OperationEffects` is defined as the difference between an operation's view and its parents' (R2.02), and it is in every page with `include_effects` and in every subscription frame, cached by the daemon. A view stepping one operation applies them, or refetches only what they name: the working copies that moved, the changes created, rewritten or abandoned, and the bookmarks. Test 12 checks that applying a stop's working-copy and change effects to the previous stop's answers gives the next stop's.
- **A jump refetches the view at the new point.** With the shared index, a read at a new operation costs its view's load plus the read itself. That is about what the read costs at head (`log_default` 0.09 ms, `status_diff` 0.5 ms on `large`). Each client therefore rebuilds a view in full rather than receiving a server-computed view diff (see "Choices"). The client refetches in full whenever:
  - it jumps over more than one stop;
  - an operation's effects were capped (`change_count` larger than `changes` holds) or unset;
  - the operation is a merge of concurrent operations.
- **Play forward** from X is `SubscribeOperations` with `after_operation` X. Its replay frames (`live: false`) carry each operation and its effects at transport speed. Its first live frame says the scrubber has reached now. Further back than R2.09's 10,000 operations is `TOO_FAR_BEHIND`; the client pages `ListOperations` instead and plays from the newest page.
- **Caches.** The repository cache (64 at an operation), the effects cache (4,096 operations) and R2.22's ring for recent operations. No new cache.

### Errors and reasons

Two new reasons in `reef_api::error`, with kinds and metadata in `reef-daemon/src/error.rs`, and the CLI's hints in `reef-vcs/src/cli/advice.rs`:

| Reason | Kind | Metadata | When, and the hint |
| --- | --- | --- | --- |
| `OPERATION_NOT_RETAINED` | `FAILED_PRECONDITION` | `oldest_at` (RFC 3339) | `ended_at_or_before` is before the oldest operation the log keeps. "Operations before `<oldest_at>` were garbage-collected (`gc.undo_window`); pick a time at or after it." |
| `TOO_FAR_BACK` | `FAILED_PRECONDITION` | `repo_id`, `examined_to` (RFC 3339) | The lookup examined 100,000 operations without reaching the time. "More than 100,000 operations ended after this time; look it up from a nearer operation with `operation_id`, or page ListOperations with `at_operation`." |
| `OPERATION_LOG_REWRITTEN` (exists) | `FAILED_PRECONDITION` | `repo_id` | A walk from `at_operation` reached operations GC collected. Hint: "Garbage collection rewrote this repository's operation log since this operation was read; look the point up again by time with GetOperation's ended_at_or_before." |
| `WORKING_COPY_NOT_FOUND`, `INVALID_OPERATION_ID`, `AMBIGUOUS_OPERATION_ID`, `OPERATION_NOT_FOUND`, `INVALID_PAGE_TOKEN` (exist) | as elsewhere | as elsewhere | As for every read at an operation. |

Neither new reason has a daemon `next`: the fix needs a time or id only the caller holds (as R2.02 decided for its operation reasons). The CLI adds `next` where a command can: `reef op log --repo <repo> --at-op <id>` for `TOO_FAR_BACK` when the command had one.

### Schema

No new file. `API_REVISION` goes up by one, with the digest commented "R2.12: reads at an operation for status, workspaces and the operation log; operations by time". Every new element gets its full leading comment (ADR 0029 checklist). Field numbers are the next free ones after #124. ### CLI

Minimal, and only flags. No command is added and no JSON key changes, so this composes with #124 whichever merges first: its brief projections apply to these commands unchanged, and a read at an operation shows in the JSON through the `at_operation` keys those commands already print (`status`, `log`, `show`, `diff`, `cat`, `files`).

- **`--at-op OP`** on `reef status`, `reef ws list`, `reef ws inspect` and `reef op log`, as the other reads have it.
  - `ws list --at-op` lists one repository's: `--repo`, else the repository the command runs in by R2.27's scope rule, else exit 2. `--all` with it is a usage error (exit 2): only active workspaces exist at a point.
  - `ws inspect --at-op` never snapshots; `--no-snapshot` is accepted and changes nothing.
- **`--at WHEN`** on every command with `--at-op`, and in conflict with it: an RFC 3339 time, or a humantime duration before now (`10m`, `2h`), as `reef history --since` parses it. The CLI resolves it with one `GetOperation` (`ended_at_or_before`) and sends the id.
  - **Why not one flag.** `1d` is both a duration and a hex prefix.
  - **What it prints.** For commands whose JSON has no `at_operation` key (`ws list`, `ws inspect`, `op log`), the CLI notes the operation it resolved on stderr, `reef: at operation 1a2b3c4d5e6f (2026-10-30 14:02:11)`, unless `-q`.
- **Text output** of `reef status` at an operation starts with `at operation <short id> (<local time>)` and leaves out the snapshot line.
- `reef guide` is unchanged, and the help texts stay within `help_text_is_short`. `target/cli-shape-<os>.json` gains the flags.

### MCP

No change. Agents act on the present. Its five reads with `at_operation` keep it, and `tools/list` has no room (21,250 bytes, at its budget). Replay is the interface's and the API's. An agent that needs a past status calls the CLI.

### Documentation

- **`docs/adr/0046-replay.md`** (accepted).
  - **Decisions:**
    - Replay as `at_operation` on every read derived from the log, not a replay service.
    - What is not replayed, and that an RPC without the field is not replayable.
    - Workspaces at a point from the view, joined to rows.
    - The lease at a point without liveness.
    - The shared index, and its one visible difference.
    - Points as operation ids, with times resolved by a bounded walk.
    - Behavior across GC, and concurrent heads.
    - Effects as the step delta and full reads on a jump.
  - **Alternatives:**
    - A `ReplayService` returning a composite scene.
    - `at_time` on every read.
    - R2.09's cursor as the point.
    - A server-side view diff (`DiffOperations`).
    - A persistent operation-time index.
    - Recording lease renewals.
    - Mapping pre-GC ids through `GcOutcome.rewritten` in memory: 10 million entries at the phase's peak rate over a week.
    - Leaving jj to build an index per operation.
  - Indexed in `docs/adr/README.md`; ADR 0030 gets a "see 0046" note on `at_operation`.

## Tests

In the unit tests of `crates/reef-lib/src/jj/oplog.rs`:

1. `load_at_shared_matches_load_at`: for a fixture with workspaces, a describe, an abandon, a bookmark move and a GC, at ten operations (rewritten ones and the pre-GC copies of two):
   - The default log revset's commits, `trunk()`, `heads(mutable())`, `divergent()`, every working copy, and change-id resolution of each visible change equal `load_at`'s.
   - A commit created after the operation resolves by commit id as hidden.
2. `load_at_shared_writes_nothing`: after GC, reading 20 pre-GC operations leaves `index/op_links` and `index/segments` unchanged. An operation whose view references a commit the head's index lacks (a second op head written by a separate `jj` transaction, not yet merged) falls back to `load_at` and still answers.
3. `locate`:
   - Operations at known times: a time equal to one's `ended_at` finds it; one between two finds the older; one after the head finds the head; one from a given operation walks from there.
   - Before the oldest kept operation after a GC, the result is "only the root".
   - A budget of 10 stops with the last time examined.
   - Concurrent heads: the newest end among them wins.

In `crates/reef-daemon/tests/replay.rs` (new):

4. `status_at_operation`: two workspaces snapshot, one is described, one released; `trunk` moves.

## Implementation notes

- **Order:**
  1. The schema (bump, `buf lint`, `buf format`, `buf breaking`).
  2. `load_at_shared`, with tests 1, 2 and 11, and the `reads` benches before and after.
  3. `locate` and `GetOperation` by time, with tests 3 and 8.
  4. `ListOperations` at an operation, test 7.
  5. `workspaces_at`, `ListWorkspaces` and `GetWorkspace`, tests 5, 6 and 14.
  6. `GetStatus`, test 4.
  7. GC, other writers and deltas, tests 9, 10 and 12.
  8. The CLI, test 13.
  9. The daemon bench, the ADR and the docs.
- Check `df -h` before the first build. The disk has filled from `target/` before.
- **Read jj-lib's revset engine for anything that enumerates the index** rather than walking from the view's heads before trusting the shared index. Test 1 is the guard. Nothing in jj-lib 0.46.0's `all()`, `visible_heads()` or change-id resolution does, but any revset function added later must be checked against it.
- **The cache key stays the operation id.** A cached repository keeps the index it borrowed. A later head's index is a superset of it, so the entry stays correct until GC clears the cache.
- **Do not hold the metadata mutex across a read.** Read the rows a page needs (workspaces, leases, snapshot counts) on the async side before or after the blocking read, as `GetStatus` does now.
- **No target-specific code** is expected.
- **Run `crate_graph` outside a Reef workspace**: a shared target directory bakes stale paths into it.
- **Timing assertions belong in the benches.** The tests wait for conditions and never assert durations: timing tests flake under load.

## Performance expectations

Release build on the M2 Max. These are estimates until the first run. The first measurement becomes the baseline, and anything more than three times over gets investigated in the PR.

| Bench | What | Target |
| --- | --- | --- |
| `reads/<preset>/load_at_shared` | load an operation 500 back, uncached, after a GC | < 2 ms on `medium` and `large` |
| `reads/<preset>/load_at_rebuilt` | the same through jj's build, after `reinit`: the cost this ticket removes, recorded once | informational |
| `reads/medium/locate_2000` | `locate` to the oldest of 2,000 operations | < 50 ms (16 µs per operation) |
| `replay/medium/scrub_step` | through a daemon over its socket, 1,000 operations in four workspaces, stepping back through 200 consecutive operations: `GetStatus`, `ListChanges` (default revset) and `ListWorkspaces` at each, uncached | p95 < 50 ms per step |
| `replay/large/jump_after_gc` | the first `GetStatus` at a random kept operation after a GC, uncached | < 50 ms (seconds today) |

A scrubber at 20 steps a second needs a step within 50 ms. The PR records `scrub_step` p50 and p95, and `load_at_rebuilt` against `load_at_shared` on both presets, which is the argument for the shared index.

## Out of scope

- Presence history and lease liveness at a point (see "What is not replayed").
- An aggregate or histogram RPC for the feed's counts over long periods: R2.21, if its measurement needs one.
- A persistent operation-time index (open question 1).
- Replaying `QueryChanges`, repositories, stores, backups and daemon status.
- Released workspaces as rows of a past fleet panel; workspace lifecycle history is `ListOperations` with `kinds` create and release.
- MCP tools or inputs for replay.
- The web UI's scrubber itself (R2.21) and views (R2.19, R2.20, R3.38).
- Mapping pre-GC ids to their rewrites.

## Risks

- **The shared index is a reasoning argument about jj-lib**, not its API's promise. A jj-lib upgrade whose revsets enumerate the index directly would show later commits at X. Test 1 compares against `load_at` over every revset Reef's reads use, and the ADR names the property for each upgrade's review, as `reparent_mapped_matches_jj` does for GC.
- **Time lookups are O(operations after the time).** At the phase's peak rate the 100,000-operation bound is under two hours from the walk's start. The UI mostly steps from a known operation (`operation_id` plus a time), which is cheap. A cold jump days back on a busy repository fails with `TOO_FAR_BACK` and its hint. Open question 1 is the fix if R2.21 shows it matters.
- **Concurrent op heads make a time-ordered scrub show partial views** between a fork and its merge. Only other jj writers create them, and the merge view is complete. Documented, not hidden.
- **Old ids silently go on working after GC, then stop.** A client that never looks points up by time works for a day and then gets `OPERATION_NOT_FOUND` or `OPERATION_LOG_REWRITTEN`. Both hints say to look the point up by time, and the ADR tells client authors to keep `ended_at`.
- **The lease at a point is thinner than now's.** A fleet panel shows "held by `<owner>` since `<issued_at>`" for the past and full health for now. That is honest, and recording renewals is the alternative the ADR rejects.

## Choices this brief made, and why

- **Fields on existing reads, not a replay service**: ADR 0029 defines `at_operation` as how a read names its point, R2.01 and R2.02 planned replay on it, and each view keeps one RPC for now and the past. A composite "scene" RPC would duplicate four responses and still need them.
- **A point is an operation id, and a time is looked up once**: `at_operation` is already the convention, and one time field on `GetOperation` replaces a time field on every read.
- **Full reads on a jump, effects for steps**: with the shared index a read at a point costs what it costs at head, and effects already are the view difference per operation. A server-side view diff would add an RPC to save a client sub-millisecond reads.
- **The shared index**: it turns a full reindex and a segment write per operation into a view read, for every read at an operation, not only replay's. The cost is one documented difference (later commits resolve as hidden).
- **Presence and liveness not replayed**: the design keeps presence out of the log so that the log stays an audit trail and liveness stays cheap. Replaying it would mean persisting it.
- **No MCP surface**: agents act on the present, and the tool list is at its budget.

## What later tickets inherit

- **R2.21** builds its scrubber on `ListOperations` with `at_operation` and `ended_after` (the track), `GetOperation` by time (jumps), effects (steps), the four reads at an operation (the views), and `SubscribeOperations` with `after_operation` (play to live). It coalesces and counts over complete pages. If counting long periods costs too much, it adds an aggregate RPC on `OperationService` then, with its own measurement.
- **R2.19 and R2.20** read `ListChanges` and `ListWorkspaces` with the scrubber's `at_operation`, and show no presence for a past point.
- **R3.38** browses `ListFiles` and `ReadFile` at a point. A workspace's snapshots are `GetWorkspace`'s `recent_snapshots` and `ListOperations` filtered by workspace.
- **R2.06 and R2.07** expose the new fields through the client.
- **R4** serves the same fields from the store, where a time index is natural.

## Open questions

1. **A time index for deep lookups.** A persistent `(ended_at, operation id)` index would make a lookup O(log n) at any depth. It could be the snapshot index with a `(repo_id, taken_at)` index (migration 6) as a seed, or a table in `history.sqlite3` fed by R2.16's follower. Both cost a schema or a cache file and handling GC's rewrite. Recommendation: not now. The bounded walk covers Reef's own repository's whole undo window and the peak rate for about 100 minutes, so revisit when R2.21 measures real scrubbing.
2. **The visible difference of the shared index.** A commit created after X, named by commit id in a read at X, resolves as hidden rather than not found. Recommendation: accept and document it. The alternative is to keep jj's per-operation build, with its reindex and disk writes, for that one case.
3. **Recording lease renewals** so that a past fleet panel shows lease health. Recommendation: no. It persists what R2.10 made presence, and grows `reef.sqlite3` with every heartbeat.
4. **Field numbers against #124.** This brief assumes #124 merges first (revision 10, `ListWorkspacesRequest` 6). Recommendation: whichever merges second takes the next numbers and revision. This brief's numbers are corrected in its PR if needed.

## Departures in the implementation

- **The shared index's differences are narrower than "The one visible difference" says, and handled.** Change offsets (`<id>/<n>`) and whether a short prefix is unique, and names a commit or a change, count every commit the index holds, and the review found that a borrowed index changes them, and that the answer then depended on which head's index a cache entry borrowed. A read at an operation whose revset has a `/`, `change_id()` or `commit_id()`, or a typed symbol that could be an id prefix shorter than a change id, resolves against jj's own index for that operation (`revset::evaluate`, through `oplog::is_shared`). What remains visible: a later commit named by its full id resolves as hidden, and the shortest unique prefixes shown may be longer. ADR 0046 says so.
- **jj cannot build an index for a GC-kept pre-GC copy at all**: its load walks into the collected ancestors and fails. On `main` a read at such an id failed; the shared index answers it, and there the exact resolution above falls back to the shared answer.
- **Tests 1 to 3 are in `crates/reef-lib/tests/jj_replay.rs`**, beside `jj_gc.rs`, not unit tests in `oplog.rs`. Test 1 compares a pre-GC copy with jj's load of its rewrite, and adds offsets and one-digit prefixes at the rewritten operations.
- **`--at` notes the operation it resolved on stderr for every command**, not only the three whose JSON has no `at_operation`; `reef status`'s text output has no header of its own.
- **`replay/medium/scrub_step` and `replay/large/jump_after_gc` are not written**; `load_at_shared`, `load_at_rebuilt` (printed once) and `locate_1000` are, on `medium`. R2.21 measures real scrubbing.
- **`changed_file_counts` at an operation** (#124, merged first) counts each working copy at the operation against its parents, through the same job as at head with the repository loaded at the operation. API revision 11.
- **`locate` checks for the root before the budget**, so a log of exactly the budget's operations is `OPERATION_NOT_RETAINED`, not `TOO_FAR_BACK`.
- **An out-of-range `ended_at_or_before`** is `INVALID_ARGUMENT` with its own message, not `INVALID_OPERATION_ID`.
