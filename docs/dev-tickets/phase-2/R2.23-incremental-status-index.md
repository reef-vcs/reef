# R2.23 Incremental status index

Phase 2 · Size M · Depends on: R2.02 (`Workspaces.Status`, the walk path it replaces, `RepoHandle::head()`, reads off the repository thread), R1.13 (the scheduler's per-workspace path set and `SnapshotHook`), R1.30 (narrowed scans and `everything`), R1.02 (the seeded `tree_state`) · Unblocks: the status exit criterion ("Status on the 100k-file synthetic repository is answered from the incremental index without a tree walk"); R3.31's proposal view reads the same `Status`

## Context

The design's Storage section: "Status is answered from an incrementally maintained index fed by filesystem notifications, never from a tree walk. The index is a proper embedded database rather than a flat file, so it stays consistent across concurrent agents on the same machine. The index can be marked stale, for example after a watcher overflow, and a full walk rebuilds it; the walk is the fallback, not the path." R2.02 ships `Workspaces.Status` the only way it can before this ticket: snapshot the workspace (a walk of every tracked file's metadata), then diff the working-copy commit against its parents. On an idle M2 Max a full scan of the `large` preset is 167 ms (`docs/benchmarks.md`, R1.14); with 200 workspaces busy it was 11.4 s (`docs/load-tests.md`, R1.30), and status is the one question an agent asks before every step.

What a status answer is made of, in a continuously snapshotted workspace, is two things that cost very differently. The first is the change's content: the files that differ between the working-copy commit and its parents. That is a tree diff, O(changed subtrees), from the store, with no filesystem access at all; jj's merged-tree diff does it and `Repo::changed_paths_in_wc` already wraps it (`crates/reef-lib/src/jj/snapshot.rs:836-870`). The second is what has been written since the last snapshot and not yet recorded: the dirty paths. Today the only way to know them is the walk, which stats every tracked file to find the few whose `(file type, mtime, size)` changed. The watcher already names those few. This ticket keeps what the watcher names, with each path's last known metadata, in SQLite, so `Status` reads the tree diff plus the dirty rows and never stats the tree.

### What was verified while writing this ticket

Reef at `d156d1e` (0.1.0); jj-lib 0.46.0, the locked version.

- **jj's own notion of dirty is `(file type, mtime, size)`.** `FileState { file_type, mtime: MillisSinceEpoch, size, materialized_conflict_data }` (`jj-lib-0.46.0/src/local_working_copy.rs:295-303`); `FileType` is `Normal { exec_bit }`, `Symlink`, or `GitSubmodule` (`:283-287`); `is_clean` compares type, mtime and size and nothing else (`:308-312`). `file_state(&Metadata)` (`:936-957`) derives a file's state from `symlink_metadata`: a symlink's `size` is `metadata.len()`, the link's own length (its target's length), and the exec bit is read from the mode. A `chmod +x` changes the type, not the mtime, and jj sees it; the index must stat the mode too, not only mtime and size.
- **The seeded `tree_state` is the baseline, and Reef already decodes it.** `create.rs`'s step 6 copies the base cache entry's `tree_state` file over the new working copy's (`crates/reef-daemon/src/workspace/create.rs:766-800`), so after a create jj's recorded state matches the files on disk exactly (`materialize_tree`'s contract, `crates/reef-lib/src/jj/materialize.rs:228-233`). `tree_state_entries(state_dir)` (`materialize.rs:203-227`) decodes the protobuf into `TreeStateEntry { path, mtime_ms, size }` (`:133-140`), dropping submodules and, today, the file type. The file type is in the proto (`state.file_type()`, `:217`); the entry needs one more field.
- **The scheduler keeps the reported paths but drops them into the scan.** `Entry` holds `paths: BTreeSet<PathBuf>` relative to the canonical root and `everything` (`crates/reef-daemon/src/snapshot/mod.rs:321-326`); `record_event` adds an event's paths, turns the set into *everything* on an overflow, on the root itself, on `.reefignore`, or past `narrowed_max_paths` (`:1140-1168`); `take_reported` moves the set into the snapshot's `Trigger` once it holds a scan permit and clears the entry (`:792-801`). `WatchEvent.paths` are absolute (`crates/reef-daemon/src/watcher/mod.rs:52-63`); store mounts and literal exclude prefixes are filtered before they arrive (`skip_prefixes`, `:428-433`), glob excludes and `.gitignore` matches are not: the watcher reports a build output written under an ignored glob, and jj's walk is what ignores it.
- **A snapshot's outcome does not say which paths changed.** `SnapshotOutcome` (`snapshot/mod.rs:193-233`) carries `changed`, `op_id`, `commit_id`, `paths_count`, `narrowed`, the timings, and `updated_files` only for the adopt branch. The post-snapshot hooks (`SnapshotHook`, `:251`; `run_hooks`, `:845`, called from `workspace/snapshot.rs:351`) get that struct. The paths a snapshot recorded are recoverable: the plan has the commit it rewrote and the new tree (`SnapshotPlan { rewrite_of, tree_ids, .. }`, `crates/reef-lib/src/jj/snapshot.rs:208-229`), so a diff of the two trees names them, O(changed subtrees). A narrowed scan's prefixes are the trigger's (`Trigger::prefixes`, `snapshot/mod.rs:395-397`); a full scan covers everything.
- **Reads can run off the repository thread** once R2.02 lands `RepoHandle::head() -> Arc<ReadonlyRepo>` (Phase 2 README, "Threads and reads"; `Arc<ReadonlyRepo>: Send + Sync` per R1.03's static assertion). A tree diff needs the store and two commit ids, not the workspace's jj handle, so `Status` need not take the workspace mutex that scans hold (`WorkspaceEntry.jj`, Phase 1 README).
- **Migrations are numbered by the README and independent** (`crates/reef-daemon/src/db/mod.rs:41-56`, `MIGRATIONS`); `0003_snapshots.sql` is the style (a comment naming the ticket and the README, `CREATE TABLE`, the indexes the queries need). `0009_status_index` is this ticket's number.
- **Sizes.** `large` is 100,014 tracked files (`docs/load-tests.md`); a row of `(workspace_id 16, path ~50, kind, size, mtime_ns, blob_id NULL, dirty)` is about 100 bytes with SQLite's overhead, so 10 MB per `large` workspace on disk and 2 GB for R1.23's 200. Not verified by measurement; the brief measures it (below). The daemon already holds each loaded working copy's tree state in memory, about 18 MB per `large` workspace (`docs/load-tests.md`, Findings, "Memory grows with the tree"); the index adds disk, not memory.
- **Not verified:** whether `rusqlite` 0.40 bulk-inserts 100,000 rows in one transaction in under half a second on the runners (the M2 Max will be measured first); whether `Workspaces.Status`'s response message in R2.01's schema carries the fields named below under exactly these names (R2.01 reserves `from_index`; the rest are this ticket's additions if R2.01 did not add them).

## Decisions

- **Measure the two costs first, then build.** Before the index exists, R2.02's `Status` (snapshot, then diff) is timed on `large` on the M2 Max, idle and with 50 other `large` workspaces loaded, and the seeding cost (decoding `tree_state` and inserting 100,014 rows in one transaction) is timed in a unit benchmark. Both go into the PR. If seeding `large` takes over 2 s on the M2 Max or the index for 200 `medium` workspaces exceeds 500 MB on disk, the "Proposed departure" at the end of this brief is raised before the rest is built; otherwise the design below stands.
- **Migration `0009_status_index`**, columns as the README fixes them: `status_index(repo_id TEXT NOT NULL, workspace_id TEXT NOT NULL, path TEXT NOT NULL, kind TEXT NOT NULL CHECK (kind IN ('file','symlink','exec')), size INTEGER NOT NULL, mtime_ns INTEGER NOT NULL, blob_id TEXT, dirty INTEGER NOT NULL, PRIMARY KEY (workspace_id, path))` and `status_meta(workspace_id TEXT PRIMARY KEY, commit_id TEXT NOT NULL, stale INTEGER NOT NULL, reconciled_at INTEGER)`, plus an index `status_dirty ON status_index(workspace_id, dirty) WHERE dirty <> 0`. `dirty` is `0` when clean and otherwise the Unix millisecond at which the row became dirty: an integer, as the README's column is, and the timestamp is what reconciliation needs (below). `kind` is jj's `FileType` folded onto three values: `file` for `Normal` without the exec bit, `exec` with it, `symlink`; submodules are not indexed, as `tree_state_entries` already drops them. `mtime_ns` is from `stat` (nanoseconds, or what the filesystem gives); seeded rows carry `mtime_ms × 1,000,000` and are compared at millisecond precision until they are first re-stat'ed. `blob_id` is the git blob id (hex) when known, `NULL` for seeded rows and for dirty ones; `Status` never needs it, R2.14's symbol index does.
- **Seeding is a background step after `Create` returns, not inside it.** The create's one-second criterion holds by a few milliseconds on APFS (`docs/benchmarks.md`, R1.29), so nothing new runs inside `Create`. `Manager::create` queues a `seed_status_index(ws)` job on the blocking pool after the row is inserted; the job decodes `tree_state_entries` (with the new `file_type`), inserts the rows in one transaction, and writes `status_meta { commit_id, stale: 0 }`. Until it finishes, `status_meta` is absent and `Status` takes the fallback path with `from_index = false`. A workspace loaded at daemon start (`load_active`), restored (R1.18), or moved (R1.06; the tree is replaced) is seeded the same way from its own `tree_state`, after its row is loaded; a reseed replaces the workspace's rows in one transaction. The seed runs under the scan semaphore's sibling, a `[status]`-sized semaphore of 2 permits, so 200 creates do not run 200 seeds at once.
- **Events keep the index current.** The scheduler's `record_event` gains a second consumer: for every `WatchEvent` whose workspace has `status_meta`, an `index::note_paths(ws, paths, at)` job runs on the blocking pool (batched: the scheduler already debounces, and one job per event is fine at R1.23's 3.3 events a second). For each absolute path under the root, relative to it:
  - the path is `symlink_metadata`'d; a missing path whose row exists keeps its row with `kind` unchanged, `dirty = at`, and `mtime_ns = -1` (the deletion marker: a real stat never yields a negative mtime, and a zero-byte file keeps a real one), which `Status` reports as `DELETED`. A missing path with no row is ignored (a temporary file that came and went);
  - a present path with a row whose `(kind, size, mtime)` equals the row's is left alone (the event was spurious, or a write that changed nothing jj measures); one that differs becomes `dirty = at` with the new metadata; a present path with no row is a new file: inserted `dirty = at`, `blob_id NULL`, unless the repository's ignore rules exclude it (below);
  - a path that is a directory is expanded one level: its direct children are stat'ed as above (inotify names a new directory, not what is in it, R1.30's finding), bounded by `[watcher] narrowed_max_paths` entries per event, past which the workspace is marked stale;
  - `everything` on the event, or the root itself, or `.reefignore` among the paths, marks `status_meta.stale = 1` and touches no rows, exactly the cases that make the scan set *everything* (`record_event`, `:1158-1161`).
  Ignore rules: new paths (no row) are checked against the same `IgnoreSources` the snapshot uses (`crates/reef-lib/src/jj/ignore.rs`, the `.gitignore` chain, `.reefignore`, `[snapshot] exclude`), through a per-workspace `GitIgnoreFile` the index module caches and rebuilds when `.gitignore` or `.reefignore` is among an event's paths. Tracked paths (rows exist) are never ignored, as jj never un-tracks an ignored file that is already tracked. A path the ignore check cannot evaluate (a `.gitignore` that fails to parse) marks the workspace stale.
- **Reconciliation after every snapshot.** The pipeline's blocking half (`Pipeline::record`, `crates/reef-daemon/src/workspace/snapshot.rs:460-560`) learns, after `finish`, what the snapshot covered: `scan_started_at` (the instant the scan took its trigger), the prefixes it was narrowed to (`Trigger::prefixes`, or everything), and the paths the operation changed (a diff of `rewrite_of`'s tree against `plan.tree_ids`, computed on the blocking half with the store from `head`; empty when `changed` is false). `index::reconcile(ws, commit_id, covered, changed_paths, scan_started_at)` then, in one transaction: for each changed path, upserts the row with the new tree's `kind`, the on-disk `(size, mtime_ns)` from a fresh stat (a few paths), `blob_id` from the tree value, and `dirty = 0`; for every row with `0 < dirty <= scan_started_at` under the covered prefixes (all rows for a full scan), sets `dirty = 0`, since the scan looked at it and either recorded it (above) or found it clean; rows made dirty after the scan began stay dirty; a changed path whose new tree has no entry (deleted) deletes the row; `status_meta.commit_id = <new wc commit>`, `reconciled_at = now`, and `stale = 0` if the scan was a full one (a full scan is the rebuild the design names; a narrowed one does not clear `stale`). The adopt branch (ADR 0018: the working copy is checked out to its rewritten commit, `updated_files > 0`) reconciles as a full scan with `changed_paths` from the diff of the old tree against the adopted commit's tree. The recover and divergent branches reconcile as ordinary commits (the new commit's tree is the scanned tree either way).
- **`Workspaces.Status` reads the index unless it is stale or missing.** The handler (R2.02's) gains a first branch: look up `status_meta`; if present and `stale = 0`, answer from the head (`RepoHandle::head()`) on the blocking pool with `changed_paths_between(store, parents_of(commit_id), commit_id)` (a new `reef_lib::jj` function taking `&ReadonlyRepo` and two commit ids, the generalization of `changed_paths_in_wc`) plus the dirty rows, and set `from_index = true`; else the R2.02 path (snapshot through the workspace handle, then the same diff) with `from_index = false` and `stale_reason` (`seeding`, `overflow`, `reefignore`, `too_many_paths`, `ignore_error`, `root_checkout`). The user's own `default` workspace (`reef status --repo`) has no watch and no index; it is always the walk path with `stale_reason = root_checkout`. The response's dirty section lists each dirty row as `DirtyPath { path, kind: ADDED | MODIFIED | DELETED | TYPE_CHANGED, since }`: `ADDED` for a row with no `blob_id` and no entry in the commit's tree, `DELETED` for a row carrying the deletion marker (`mtime_ns = -1`), `TYPE_CHANGED` when the row's `kind` differs from the tree's, `MODIFIED` otherwise. `Status.index_reconciled_at` carries `status_meta.reconciled_at`.
- **`Status` never snapshots.** It reports the dirty paths; it does not record them. `reef status --snapshot` (and `Status { snapshot_first: true }`) opts in, exactly as `reef here` does (ADR 0025: "`here` must be cheap enough to call before every step, and it must have no side effects. A snapshot records an operation"). An agent calling `status` in a loop must not write 1,000 operations; and the watcher will record the dirty paths within `debounce + min_interval` anyway, so the answer and the store converge without the reader's help. The text renderer marks dirty paths with `(unsnapshotted, 3 s)` so a human knows the store is behind the disk.
- **`[status] index = true`** (new key, in `reef config show`, the daemon's `KEYS` list, and the README's configuration row). `false` seeds nothing, records nothing, and makes every `Status` the walk path with `stale_reason = disabled`: the kill switch, and the control for the benchmark.
- **The benchmark, `crates/reef-daemon/benches/status.rs`**, in the shape of `workspace_create.rs`'s `create_api` group: an in-process daemon on the `REEF_BENCH_PRESET` preset, one workspace, the index seeded and reconciled (the bench waits for `from_index = true`). Groups `status/<preset>/index` and `status/<preset>/walk`: before each iteration (outside the timer) the bench rewrites 10 tracked files and waits until `Status` lists 10 dirty paths (the watcher's latency, not the RPC's); the timed body is one `Status` call, `snapshot_first = false` for `index` and `snapshot_first = true` for `walk` (R2.02's path; the snapshot it takes clears the dirty set, which is why the dirtying is per iteration). A `LogCapture` layer in the bench process counts `snapshot taken` and `watcher snapshot taken` lines during the `index` group and prints `status/<preset>/index scans: N` after it; the criterion is `N == 0` for the timed calls (the watcher's own snapshots between iterations are excluded by holding scans with `Scheduler::hold_scans` during the timed body and releasing it after). The row and a `target:` line go to stderr and `target/bench-ws.json` as the workspace bench's do. `bench.yml` runs it through `cargo bench --workspace --bench '*'` with no change; `docs/benchmarks.md` gains a section with the M2 Max and both runners' numbers for `medium` and `large`.
- **ADR 0036, "Incremental status index"**, records: what status is made of (tree diff plus dirty paths) and why only the second needs an index; `(kind, size, mtime)` as the dirty rule, borrowed from jj so the index and the scan never disagree about what counts as changed; the full table seeded from `tree_state` (against dirty-only rows with the baseline read from the loaded working copy, the departure below); seeding off the create path; the stale rule and that only a full scan clears it; `Status` reporting and never recording; the measured costs; and the alternatives (walk on every status, a tree_state diff per status, an in-memory index per workspace, jj's own `fsmonitor` state).

## Tests

Notify, `small` preset, `fallback_interval` and `watched_fallback_interval` at 10 minutes so no fallback snapshot stands in for the index, in `crates/reef-daemon/tests/status_index.rs` unless stated. Each waits for `from_index = true` after the create before acting.

1. `seed_matches_tree_state`: after a create and the seed, the row count equals the tracked file count, every row's `(kind, size, mtime_ms)` equals `tree_state_entries`'s, no row is dirty, and `Status.from_index` is true with an empty dirty list and `changes` equal to the walk path's answer on the same workspace.
2. `write_is_dirty_then_clean`: write a tracked file; within `debounce + 1 s`, `Status` lists it `MODIFIED` with `from_index = true` and the daemon log has no `snapshot taken` between the write and the answer (scans held with `hold_scans`); release the hold; after the watcher snapshot, `Status` lists no dirty paths and `changes` names the file.
3. `added_deleted_and_chmod`: a new file is `ADDED` (and absent from `changes` until snapshotted), a removed tracked file `DELETED`, `chmod +x` on a tracked file `TYPE_CHANGED`; after the snapshot each appears in `changes` with the right kind and the dirty list is empty.
4. `ignored_new_file_is_not_dirty`: a file under a `.gitignore`d glob and one under `[snapshot] exclude` are written; neither is dirty; a tracked file that `.gitignore` later matches stays indexed and reports `MODIFIED` when written.
5. `new_directory_children_are_indexed`: `mkdir` and 20 files written into it at once; all 20 are `ADDED` before the snapshot and in `changes` after.
6. `overflow_marks_stale_and_full_scan_clears_it`: `inject_event(ws, [], everything = true)`; `Status` is `from_index = false, stale_reason = overflow` and still correct (the walk path); after the next full snapshot `from_index` is true again. A narrowed snapshot in between (write one file, let the watcher snapshot it) does not clear `stale`.
7. `events_during_a_scan_stay_dirty`: `hold_scans`, write A, release, and while the scan runs (hold the pipeline with the test hook `hold_snapshot_record` added here, or write B within the scan's window on `large`), write B; after reconciliation A is clean and in `changes`, B is dirty; the next snapshot clears B.
8. `status_never_snapshots`: 100 `Status` calls in a loop with a dirty file and scans held; the operation log's length is unchanged and the dirty path is still listed; `Status { snapshot_first: true }` writes one operation and clears it.
9. `restart_reseeds_and_stays_correct`: write a file, SIGKILL the daemon (`SpawnedDaemon`), respawn; `Status` is `from_index = false` until the reseed, then `from_index = true` and the file is either dirty (no snapshot caught it) or in `changes` (the start-time snapshot did), never absent from both.
10. `move_reseeds`: `Move` to another change; `Status` after the reseed shows the new change's `changes` and no stale dirty rows from the old tree.
11. `index_off_is_the_walk`: with `[status] index = false`, no rows are written, `Status` is `from_index = false, stale_reason = disabled`, and correct.
12. `release_forgets_rows`: after `Release`, `status_index` and `status_meta` have no rows for the workspace.
13. `root_checkout_is_the_walk`: `Status` for the `default` workspace is `from_index = false, stale_reason = root_checkout`.
14. `seed_cost_and_size` (`#[ignore]`, `--nocapture`, run by hand on `large` and recorded in `docs/benchmarks.md`): the seed's wall time and the two tables' bytes for one `large` workspace, and for 20 `medium`.
15. `changed_paths_between_matches_jj` (`crates/reef-lib/tests/jj_diff.rs`): for a fixture with an added, a modified, a deleted, a type-changed and a renamed file, the function returns the expected kinds, blob ids and `kind_after`, and agrees with `changed_paths_in_wc` on the working-copy commit.

## Implementation notes

- Measure first, as R1.30 did: run R2.02's `Status` on `large` with `hyperfine`-style repetition through the CLI and through the API, idle and with 50 loaded `large` workspaces, and the seed benchmark (test 14), before writing the index. Put both numbers at the top of the PR.
- The dirty rule must be jj's or the index and the scan disagree: an index that marks a file dirty on a `utimes` call that changed only the mtime will show a `MODIFIED` that the next snapshot clears with no `changes` entry. That is correct (jj rehashes it and finds it equal) and the text renderer's `(unsnapshotted)` marker says so; do not try to be cleverer than jj by hashing in the index.
- `note_paths` runs on the blocking pool with the database mutex for short transactions; never on the scheduler's event loop and never on the repository thread. A workspace with hundreds of events a second (a build writing under an unignored path) is bounded by `narrowed_max_paths` per event and by the scheduler's debounce; past the bound the workspace goes stale, which is the walk path, which is correct.
- Reconcile after `finish`, not before: `finish` saves the tree state at the new operation, and a crash between the commit and the reconcile leaves rows dirty that the next snapshot clears; the reverse order could clear rows for a snapshot whose working-copy state was never saved.
- `scan_started_at` is when `take_reported` ran (the scan holds its permit then), not when the trigger was first taken: paths reported between the two joined the scan's set (R1.30) and are covered.
- `changed_paths_between` on a conflicted tree (a `Merge<TreeId>` with several terms): diff the merged tree as `diff_stream` does; a path that is conflicted reports `kind_after = None` and `blob_id = None`, and the CLI prints `(conflicted)`.
- The bench needs the watcher's latency excluded from the timed body; dirtying and waiting outside `b.iter` with `iter_batched` and `BatchSize::PerIteration`, as the workspace bench's disk pass structures its untimed work.
- Keep the Linux build honest: nothing here is `cfg(target_os)`, but the inotify "new directory" case (test 5) behaves differently from FSEvents; run the suite in the privileged container before pushing, as the Phase 2 README's process says.

## Out of scope

- Status for the user's `default` workspace from an index: it has no watch (Phase 1 README, "jj workspace name"); it stays the walk path.
- Content hashes in the index beyond what reconciliation records from the tree (`blob_id`); hashing dirty files on event is R2.14's concern if the symbol index wants it, and would slow events for no status benefit.
- Using the index to narrow the scan itself (the scheduler's path set already does that, R1.30) or to replace jj's `tree_state`.
- Rename detection in `changes` (jj's copy tracking, `copies.rs`); `changes` reports added and deleted.
- Unloading idle working copies to bound memory (the Phase 2 Scale question R1.23 raised); the index adds disk, not memory, and does not change it.

## Risks

- **Disk per workspace.** 100,000 rows per `large` workspace is about 10 MB; 200 of them 2 GB in `reef.sqlite3`, beside the 3 GB of `wc/` state directories R1.23 counted. The database is one file, so backups (R1.18) copy it whole, and `PRAGMA page_count` growth after releases needs `VACUUM` or `auto_vacuum = INCREMENTAL` (not set today; measure after test 12 on `large` and set it if the file does not shrink). The measurement gate at the top of Decisions decides whether this stands.
- **The index can lie in one direction.** A write the watcher never reported (a lost event with no overflow, a write before the Linux watch attached, R1.32) is dirty on disk and clean in the index until the next full scan: the watched fallback (10 minutes) is the backstop, the same one narrowed scans rely on (ADR 0026). `Status` says `index_reconciled_at`, and the renderer prints `index as of <relative time>` so a reader can judge. The other direction cannot happen: a dirty row is cleared only by a scan that covered it.
- **Seeding 200 workspaces at once after a daemon restart.** `load_active` loads every active workspace; 200 seeds of `medium` are 2 million rows, bounded to 2 at a time, perhaps a minute during which `Status` is the walk path and says `seeding`. Acceptable and reported; if the measurement shows seeding dominates restart, the rows survive restarts instead (they do today: nothing deletes them on shutdown) and only workspaces whose `status_meta.commit_id` differs from the loaded working copy's commit reseed. Decide from the measurement, record in the ADR.
- **Ignore evaluation on the event path.** A `.gitignore` chain for a deep path costs microseconds, but a repository with thousands of `.gitignore` files makes the cached `GitIgnoreFile` large; `narrowed_max_paths` bounds the paths per event, and a workspace that exceeds it goes stale rather than slow. Measured in test 14's run with a synthetic repository that has a `.gitignore` per directory (`reef_testing::synth` writes some; check how many).
- **`Status` semantics drift from `jj status`.** jj's status snapshots first, so it never shows "dirty". An agent that knows jj may expect `reef status` to have recorded what it lists. The text output's `(unsnapshotted)` marker, the `--snapshot` flag, and the guide line are the mitigation; RX.07's scenario D (oriented) is where a misunderstanding would show, and R2.17's benchmark asks the state question with this command.

## Proposed departure from the README

*2026-10-25: held, as written; R2.01's `StatusResponse` carries `from_index`, `stale_reason`, `index_reconciled_at` and `dirty: repeated DirtyPath` under those names.*

None is proposed now; one is held ready. If the measurement gate fails (seeding `large` over 2 s on the M2 Max, or 200 `medium` workspaces over 500 MB), the index should hold **only dirty rows**, with the baseline `(kind, size, mtime)` read from the loaded working copy's in-memory file states (`LocalWorkingCopy::file_states()`, `jj-lib-0.46.0/src/local_working_copy.rs:2882`, through a `reef_lib::jj` accessor on the workspace handle) instead of a seeded copy in SQLite. That removes the seed step and the disk cost and keeps the dirty rule identical, at the price of taking the workspace's jj mutex on the event path, which a running scan holds for its length (up to 11 s loaded, R1.30); events would then be queued per workspace and applied when the mutex frees, and `Status` during a scan would answer from the rows already present with `index_reconciled_at` saying so. The README's "Seeded from the workspace's `tree_state` at create" would change to "baseline from the loaded working copy"; the columns, the stale rule, `from_index` and the bench would not.
