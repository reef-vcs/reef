# R2.23 Incremental status index

Phase 2 · Size L (the row said M; see "Size") · Depends on: R2.02 (`GetStatus`, `snapshot_for_read` and the reads that snapshot first, the `StatusSource` values R2.01 declared), R1.13 (the scheduler, scan locks, the snapshot pipeline), R1.30 (narrowed scans and the path set this ticket moves ahead of the debouncer), and through them R1.14 (Watchman narrowing) and R1.32 (attaches, the inotify turn) · Unblocks: none listed (Phase 2's exit criterion "Status on the 100k-file synthetic repository is answered from the incremental index without a tree walk")

## Context

The design says "status is answered from an incrementally maintained index fed by filesystem notifications, never from a tree walk", that the index "can be marked stale, for example after a watcher overflow, and a full walk rebuilds it; the walk is the fallback, not the path" (`docs/design.md`, Storage). Today the walk is the path. `GetStatus` on a workspace snapshots first, and that snapshot is explicit, so it scans every tracked file (ADR 0026, decision 7). On `large` the walk is 165 ms of a 182 ms status (measured below); the read after it is a tree diff of 0.5 ms. Under load it is worse: a full scan of `large` took 11.3 s with 200 workspaces (R1.30), and on Linux a full scan of a notify workspace waits its inotify turn behind every full scan and attach queued before it (ADR 0028, decision 9). Every read that snapshots first pays the same: `ListChanges`, `GetChange`, `GetDiff`, `ReadFile`, `ListFiles`, `ListSymbols`, and `GetWorkspace` with `snapshot_first`.

Most of the index exists, in two pieces nothing joins:

- **The per-file record is jj's working-copy state.** Each tracked path has a `FileState` (type with the executable bit, mtime, size, materialized-conflict data) and the tree holds its content hash. jj already rehashes only files whose state differs. What a walk costs is reading every directory and `lstat`ing every path to find them.
- **The dirty set is R1.30's.** The scheduler keeps, per workspace, the paths reported since its last scan and three marks (`everything`, `behind`, `watched`) that say when they cannot be trusted. Watcher snapshots narrow to it.

What is missing is what lets a read trust that set. It is fed 500 ms late, after the debouncer. Nothing proves a read has seen the events of writes finished before it. On macOS every workspace create and release silently drops other workspaces' events. Reads never use it.

This ticket moves the path set ahead of the debouncer as a per-workspace journal, adds a sync point and per-workspace FSEvents streams, answers every read's snapshot from it, and falls back to jj-lib's walk with a stated reason. R2.01's rule binds it: it implements the two values R2.01 declared and adds one enum and one field.

### What was verified while writing this ticket

Reef at `29da6dbc` (R2.18 merged as #127), jj-lib 0.46.0, notify 8.2.0, notify-debouncer-full 0.7.0. `API_REVISION` is 12 (`reef-api/src/lib.rs:49`), the highest ADR is 0047, and `reef.sqlite3` is at schema version 5. Paths are under `crates/` unless they start with `docs/`.

- **How `GetStatus` snapshots.** `service/status.rs:126` calls `snapshot_first` (`service/reading.rs:96`), which calls `Manager::snapshot_for_read` (`workspace/snapshot.rs:178`). That runs `snapshot_locked` with `take_trigger`, whose `from_events` is false, so `Trigger::prefixes` (`snapshot/mod.rs:415`) is `None` and the scan is full. The response's `source` is `SNAPSHOT`, or `LAST_SNAPSHOT` with `skip_snapshot`. A read is `Covered` when a full scan that began after it arrived has succeeded (`WorkspaceEntry::scan_started`, `workspace/mod.rs:102`, set at `workspace/snapshot.rs:466`). Narrowed scans never set it.
- **What R2.01 declared.** `StatusSource.STATUS_SOURCE_INDEX = 2` ("The incremental index (R2.23)") and `STATUS_SOURCE_WALK = 3` ("A walk of the tree, the index's fallback (R2.23)") exist in `status.proto` and are never set. The RPC's comment says "R2.23 changes how it is answered, not its shape." The client's JSON already names them `index` and `walk` (`reef-client/src/json.rs:881`). The brief view keeps `source` (`reef-client/src/brief.rs:328`). Text output prints a note only for `last-snapshot` (`reef-vcs/src/cli/render_vcs.rs:152`).
- **The read after the snapshot walks nothing.** `diff_page` with `DiffBase::Parents` is a tree diff that skips equal subtrees; `reads/large/status_diff` is 0.50 ms (`docs/benchmarks.md`, Reads).
- **R1.16's snapshot index is not this index.** `snapshots` (`snapshot/index.rs`, `0003_snapshots.sql`) has one row per snapshot operation (workspace, commit, change, kind, `local`, `taken_at`) and no file state. It sits beside this ticket, unchanged.
- **jj's state.** It lives in `repos/<id>/wc/<ws>/`, outside the workspace root, which has no `.jj`. `FileState { file_type, mtime, size, materialized_conflict_data }` (jj-lib `local_working_copy.rs:295`) is compared by `is_clean` on type, mtime and size. A file whose mtime is not older than the state's own save time is rehashed anyway (`:1952`). `TreeState::load` decodes the whole state: 7 ms on `large` idle (below).
- **The path set.** The scheduler's `Entry` (`snapshot/mod.rs:334`) has `paths`, `everything`, `watched` and `behind`, fed by `record_event` (`:1235`) from debounced `WatchEvent`s:
  - `everything` is set on an inotify overflow or an FSEvents rescan (`watcher/notify.rs:672`), on a workspace's next event after one was dropped from the full scheduler queue (`lost`), past `narrowed_max_paths`, and when the root or `.reefignore` is reported.
  - `behind` is set when a workspace is tracked again (`:1075`) and on `Attach::Pending` (`:1107`). Only a successful *scheduled* snapshot clears it (`:1322`); an explicit full scan does not.
- **A busy workspace is never fully scanned on a timer.** `start_due` (`snapshot/mod.rs:1266`) fires the fallback only when `dirty_since` is `None` and `last_completed` is older than the interval, and `Manager::snapshot_locked` calls `completed` after every snapshot, narrowed or not (`workspace/snapshot.rs:265`), while a dirty workspace always gets a narrowed watcher snapshot (`from_events = !fallback`, `:284`). So a workspace written at least once every 10 minutes is fully scanned only by a read (today, every read) or its release. The module doc and ADR 0026, decision 7, call the watched fallback "the backstop for any change a narrowed scan missed"; it is that only for idle workspaces.
- **`IN_CLOSE_WRITE` is dropped.** `DropReads` (`watcher/notify.rs:555`) drops every `Access` event, which includes notify's `Access(Close(Write))`, the only event a writer through a memory mapping produces on Linux (ADR 0028, decision 9). The drop was for the debouncer's map cost.
- **The debounce.** `watcher.debounce` is 500 ms (`config.rs:383`), and notify-debouncer-full emits a path once it has been quiet that long. So the set lags every write by at least half a second. Reads are already dropped on notify's own thread before the debouncer (`DropReads`, `notify.rs:552`). An undebounced tap can go there.
- **No sync point exists** for notify: no cookie, no flush. jj's Watchman query syncs through Watchman's own cookie (`watchman_client`'s `QueryRequestCommon::sync_timeout` defaults to the server's sync).
- **macOS drops events at every create and release.** notify 8.2.0's `FsEventWatcher` watches every root in one stream. `watch` and `unwatch` stop it and start a new one (`fsevent.rs:308`) with `since_when = kFSEventStreamEventIdSinceNow` (`:299`). Writes to any other workspace between the stop and the start are never delivered, and no rescan flag says so. Each create and release opens that window (9 ms, R1.29). Today it can make a narrowed watcher snapshot miss a write until the 10-minute watched fallback. notify-debouncer-full 0.7's `watcher()` accessor is deprecated and does nothing (`lib.rs:572`), so Reef reaches its watcher only through the `notify::Watcher` calls the debouncer makes on `ChangesOnly`.
- **Linux.** One inotify instance and one kernel queue serve every notify workspace (ADR 0028). An overflow is a rescan for every workspace. Full scans of watched notify workspaces, explicit ones included, wait for the inotify turn (`snapshot/mod.rs:844`). Narrowed scans do not.
- **Layout.** Workspace roots are `repos/<id>/ws/<ws>`, with released roots renamed to `*.trash-*` siblings and swept at start (`daemon.rs:503`).
- **Measured.** Apple M2 Max, the installed 0.2.0 at `29da6dbc`, a scratch daemon, `large` (seed 42, 100,014 tracked files, 8,336 directories) on APFS, through `reef status -o json` (process start included), 10 runs each:

  | Workspace | Clean tree | One file appended first | `--no-snapshot` |
  | --- | ---: | ---: | ---: |
  | notify | 182 ms (walk 165, load 7) | 224 ms (scan 172 to 175, walk 165 to 168) | 6 ms |
  | Watchman | 33 ms | 81 ms | |

  A notify *watcher* snapshot of one appended file on the same workspace, narrowed: 63 to 69 ms in the daemon. Its scan is 17 to 18 ms (two state loads 13 to 14 ms, walk 3 to 4 ms). The rest is writing the commit and the operation, saving the working-copy state, and the rows. That is the cost of an index answer with one change. With nothing changed, the answer is about what `--no-snapshot` costs.
- **Open issues that touch this.**
  - **#91** (an ancestor's snapshot rebases a busy descendant): the descendant's working copy is stale until it is adopted, and its reads walk (`STALE_WORKING_COPY`) until then.
  - **#92** (a failed `finish` after a conflicted check-out): any failed snapshot marks the index stale, so the index never answers from a state that was not saved.
  - **#101** (a macOS crash and respawn flake): a respawn makes every index stale, so that test's reads walk. Nothing changes for it.
  - **#126** (brief `status` and `at_operation`): this ticket changes `source`'s value from `snapshot` to `index` (3 bytes shorter) and keeps `walk_reason` out of the brief view.

## Decisions

The user's decisions on this brief (2026-10-31): the index stays out of SQLite (open question 1, resolved by a review against the code); the sync cookie lives outside the workspace root; reads never walk on a timer, and instead every watched workspace is fully scanned at least every `watched_fallback_interval`, busy or idle (open question 2, resolved the same way); writes' pre-snapshots stay full scans; Watchman's clean fast path is a follow-up issue.

### Size

L. The row's M assumed the index could be filled from the events Reef already had. Three watcher changes it did not foresee are each needed for the index to be correct:

- a journal fed before the debouncer;
- a sync point, so a read sees the events of every write finished before it;
- on macOS, one FSEvents stream per workspace, so attaching one never drops another's events.

On top of those come:

- answering every read's snapshot from the journal;
- staleness with reasons, and reconciliation that detects misses;
- one enum, one field and a configuration section;
- a bench through the daemon on `large`;
- about twenty tests on both platforms and in the overlay job;
- an ADR.

Two smaller versions were considered. Narrowing reads to the debounced set without a sync point is wrong for an agent that writes a file and then asks for status, which is the common case. Marking every macOS workspace stale at each stream restart is correct, but the index then answers nothing while workspaces come and go. Splitting the watcher changes into their own ticket was rejected: alone they change nothing a client sees, and the read path is incorrect without them. There is no SQLite schema, no new service, no MCP change and no new crate.

### What the index is

The row's fields, and where each one lives:

| The row's field | Where it is | Who keeps it |
| --- | --- | --- |
| path, size, mtime | the path's `FileState` in jj's working-copy state | jj, at every snapshot |
| type, executable bit, symlink, conflict | `FileState.file_type`, `materialized_conflict_data` | jj |
| content hash, when known | the working-copy tree's blob id at the path | jj, at every snapshot |
| dirty flag | the path, or a directory above it, is in the workspace's journal | the watcher, from events |
| stale mark | the journal's stale reason | the watchers and the scheduler |

- **A path is dirty** when it, or a directory above it, is in the journal: something may have changed it since the last scan took the journal. Every other path is as jj's state records it, unless the index is stale.
- **Status from the index** is jj's snapshot narrowed to the dirty paths, or no snapshot when none are dirty, followed by R2.02's read. The narrowed scan is jj's own code with a narrower matcher (ADR 0026). So deletions, renames, new directories, ignore rules, conflicts, the executable bit, symlinks and the new-file size limit behave as in a walk, for every path the journal names.

### Where it lives: memory and jj's state, not SQLite

The row put the index in SQLite. It is not (a departure, decided by the user):

- **The per-file record is jj's, and only jj's decides what a snapshot records**: racy mtimes, ignore rules, conflicts and the new-file size limit. A copy in SQLite would have to equal it after every snapshot. Seeding it is 100,014 rows inside each `large` create, which has a one-second budget (R1.12). At the phase target, 200 workspaces of `large`, it is 20 million rows. Status would still hand jj the paths to look at.
- **The journal is worthless after a restart.** Writes made while the daemon was down were never reported. A persisted journal would only let a restarted daemon trust it wrongly. Every index starts stale at daemon start.
- **"Consistent across concurrent agents"** (design.md) holds without a database. One daemon is the only writer. The journal has its own lock, and jj's state is under jj's working-copy lock and the workspace's scan lock. Two agents never share a workspace (ADR 0019).
- **Nothing a persisted dirty set would let a restarted daemon trust.** inotify has no replay, and notify hard-codes `since_when = now` for FSEvents (`fsevent.rs:299`), so replaying events across a restart needs Reef's own FSEvents binding (the daemon-owned watcher under "Out of scope"). Watchman workspaces already survive a restart without a crawl: jj keeps the Watchman clock in its tree state.
- **Nothing is backed up**, and a restore starts stale, as a restart does. `reef.sqlite3` stays at schema version 5. ADR 0003's context names the status index as one reason for the database; ADR 0048 amends it (added to its "Amended by", as ADRs 0042 and 0044 were). The design's Storage paragraph says the index is jj's working-copy state plus an in-memory journal.

### The journal

- **One journal per tracked workspace**, in a new module, `snapshot/journal.rs`. `Journals` maps each workspace to a `Journal`: `paths` (a `BTreeSet` relative to the canonical root), `stale: Option<StaleReason>` and `seen_sync: u64`. It sits behind its own mutex in an `Arc` shared by the watchers and the scheduler. The lock is never held across I/O or an `.await`.
- **It is fed on the watcher's thread, before the debouncer.**
  - **notify:** `DropReads` routes each change event's paths through `Demux` (the same routing and skipped prefixes as `route_batch`) and records them.
  - **Watchman:** each subscription result's files are recorded, where they become events now.
  - **The debounced `WatchEvent`s still drive scheduling** (`dirty_since`, `min_interval`, the fallbacks). Their paths no longer feed a set. R1.30's `Entry.paths` and `everything` move into the journal, and `record_event`'s rules move to `Journal::record`.
- **Recording rules.**
  - **A path** relative to the root is inserted. A path outside every root is dropped.
  - **On Linux, `Access(Close(Write))` is a change**: the tap journals its path, and forwards it to the debouncer as a modify, so a write through a mapping that is then closed is seen. Scans open files read-only (`IN_CLOSE_NOWRITE`), so this adds no events from Reef's own reads. Every other `Access` kind is still dropped.
  - **A metadata-only change of the root itself** (inotify `IN_ATTRIB` on the root, FSEvents `ItemInodeMetaMod` on the root) is dropped: jj records nothing about the root directory.
  - **The root itself created, removed or renamed**, or `.reefignore` reported, makes the journal stale with `TOO_BROAD`. So do more than `watcher.narrowed_max_paths` distinct paths. These are R1.30's rules.
  - **A rescan** (inotify `IN_Q_OVERFLOW`, or FSEvents `MustScanSubDirs`, `UserDropped` or `KernelDropped`) makes the journal stale with `EVENTS_LOST`.
    - **On Linux** that is every notify workspace's journal: one queue serves them all.
    - **On macOS** it is the workspace whose root contains the rescan's path, since each stream is one workspace's (below). If the path is under no root, it is every workspace's.
    - The tap sees every rescan. ADR 0026's reason for ignoring the path, that the debouncer keeps only the latest, no longer applies.
  - **The scheduler's `lost` rule is removed.** A full scheduler queue drops a debounced event, but the journal never went through that queue. The dropped-event counter and its log line stay.
- **Taking.**
  - **Every snapshot takes the journal**, whatever its kind, at the point where `take_reported` runs now: under the scan lock, once it holds its scan permit. Its paths and its stale reason move out together, and the snapshot remembers `taken_sync = seen_sync`. Events after the take go to the next snapshot.
  - **A snapshot that fails** puts nothing back. It marks the journal stale with `SNAPSHOT_FAILED`, since the paths it took are gone.
  - **A full scan that succeeds clears every stale reason**, except `NOT_WATCHED` while the watch is still down. This is the rebuild: "the walk is the fallback".
  - **A watcher snapshot that takes an empty, fresh journal skips the scan.** A read's snapshot already covered its events, which arrived ahead of their debounced event. It counts as completed, not failed.
- **Full scans on a timer.** The scheduler's `Entry` keeps `last_full_completed`, set by `completed` when a successful snapshot's scan was full, whatever its kind: a read's walk, the `Snapshot` RPC, a fallback, a move's. In `start_due`, a dirty watched workspace whose `last_full_completed` is older than `watched_fallback_interval` runs its scheduled snapshot full (`from_events = false`, so `Trigger::prefixes` is `None`), taking the journal as any snapshot does. The idle rule stays as it is. This is what bounds a change no event names (below). No new key: `watched_fallback_interval`'s doc comment (`config.rs`) and `reef config`'s text say it is now "the longest a watched workspace goes without a full scan".

### The sync point

- **A read syncs before it trusts the journal.**
  - **Each notify workspace has a sync directory outside its root**, `repos/<id>/sync/<ws>/` beside `wc/`, created `0700` when the workspace is tracked and removed at release; a crash's leftovers are swept at start with `ws/` and `wc/` (`workspace/abandoned.rs`). It is on the same volume as the root, which lives under `repos/<id>/ws/`.
  - It is watched as part of the workspace's watch: on Linux a non-recursive inotify watch in the daemon's one instance; on macOS a second path in that workspace's own FSEvents stream (below). `Demux` routes it to its workspace as a sync directory, not as a root.
  - `Journals::sync(ws, deadline)` writes a cookie file, `<sync dir>/<pid>-<n>`, with `O_CREAT | O_EXCL`, empty and `0600`.
  - It waits until the tap has seen that file's creation (`seen_sync >= n`), then removes the file off notify's thread.
  - The tap recognises a cookie by its path under a routed sync directory. It records `seen_sync` and journals nothing for it, on create or remove. Cookie events never reach the debouncer.
- **Why this suffices.**
  - inotify has one queue per instance, and the daemon has one, holding the root's watches and the sync directory's.
  - FSEvents delivers one stream's events in event-id order, across all of the stream's paths, and each notify workspace has its own stream over its root and its sync directory (below).
  - A cookie seen after a write's event therefore means every write that finished before the cookie was created has been seen. A client's write finished before it sent the request, and the cookie is created after the request arrived.
- **Never in the agent's tree.** No cookie appears in the root, so watch-mode tools an agent runs there (cargo-watch, watchexec, `jest --watch`, nodemon) never see one, and jj, `ListFiles` and the base ignores need no rule for it.
- **Reads share cookies.** At most one is in flight per workspace. A read that arrives while one is in flight waits for the next, which is written as soon as the first is seen. Concurrent reads therefore cost at most two round trips each.
- **It is bounded.** It waits at most `[status_index] sync_timeout` (default 1 s). A cookie not seen in time, or one that cannot be written (a full disk, a removed sync directory), makes the read walk with `NOT_SYNCED`, and the cookie is removed.
- **Cookies a crash left behind** are removed when the workspace is tracked (its sync directory is emptied).
- **Watchman workspaces need no Reef cookie and no sync directory.** jj's Watchman query syncs through Watchman's.

### macOS: one FSEvents stream per workspace

- **`ChangesOnly` on macOS holds one `FsEventWatcher` per watched root**, each with a clone of the one handler: `DropReads<F>` behind an `Arc<Mutex<_>>`, wrapped to implement `notify::EventHandler`.
  - Watching a workspace starts one stream over its root and its sync directory, both paths given before the stream starts (`notify::Watcher::paths_mut`, so the stream starts once), and unwatching it stops that one.
  - No stream ever restarts for another workspace's attach or release, so nothing is dropped.
  - Linux keeps its one `INotifyWatcher`.
- **What it costs.** An attach is one stream start, as now (9 ms, R1.29), rather than a restart of a stream over every root. Each notify workspace on macOS costs one CFRunLoop thread: 200 at the phase target. The load test's `peak_threads` records them.
- **It closes the same gap for R1.30.** Narrowed watcher snapshots can no longer miss a write made while another workspace was created or released.
- **ADR 0028, decision 6, is amended:** a macOS attach is a new stream for that workspace, not a restart of the shared one.

### What marks the index stale

`StaleReason` in the daemon, `StatusWalkReason` in the API. The first five are journal states, which the next successful full scan clears. The last four are found by one read.

| Reason | Set when |
| --- | --- |
| `NOT_WATCHED` | The workspace's watch is not up: it failed or was refused, the watcher could not start (`NoWatcher`), a Linux attach is pending until its post-attach scan, the watch limit was hit for a new directory (health down), or a Watchman subscription is down. Cleared only by a full scan once the watch is up. |
| `WATCH_RESTARTED` | A notify workspace tracked again after a time unwatched: daemon start (every notify workspace), restore, an aborted release, a move's rewatch. This replaces `behind`, and so does a pending attach. Never set for Watchman workspaces: jj keeps their Watchman clock in its tree state, so their first snapshot after a restart is narrowed by jj, not a crawl. |
| `EVENTS_LOST` | A rescan (above), a Watchman fresh instance, or a subscription's first result. |
| `TOO_BROAD` | More than `watcher.narrowed_max_paths` paths, the root itself, or `.reefignore` (R1.30's rules). |
| `SNAPSHOT_FAILED` | A snapshot that took the journal failed: the scan, the commit or `finish` (#92). |
| `NOT_SYNCED` | The read's cookie was not seen within `sync_timeout`, or could not be written. |
| `STALE_WORKING_COPY` | The working copy is stale against the view, or the view has no working-copy commit for it: ADR 0018's adopt, divergent and recover arms, which stay full scans (ADR 0026, decision 7; #91). |
| `PATH_NOT_NARROWABLE` | A journal path jj cannot be narrowed to: `..`, not UTF-8, or on macOS a spelling that cannot be resolved (ADR 0026, decisions 6 and 7). |
| `COVERED_BY_FULL_SCAN` | A full scan that was not a read's (the `Snapshot` RPC, a fallback snapshot, a move) took the journal after this read synced, and answered it. |

The scheduler's fallback interval reads the journal: a fresh journal waits `watched_fallback_interval` (10 minutes), and a stale one `fallback_interval` (60 s), as `watched && !behind` chose before. Independently, a dirty watched workspace whose last full scan is older than `watched_fallback_interval` gets its next scheduled snapshot full ("Full scans on a timer").

A Watchman workspace's walk reasons come only from its subscription state (`NOT_WATCHED` while it is down, `EVENTS_LOST` on a fresh instance or a first result) and from the snapshot itself (`SNAPSHOT_FAILED`, `STALE_WORKING_COPY`). `NOT_SYNCED` and `WATCH_RESTARTED` never apply to it.

### Answering a read

`Manager::snapshot_for_read`, with the index on, for a workspace read at head without `skip_snapshot` (anything else is unchanged):

1. **A Watchman workspace** snapshots as now, under the scan lock: jj narrows the scan through its own synced Watchman query (R1.14). Its source is `INDEX` if the journal was fresh when the snapshot took it, else `WALK` with the journal's reason. It has no clean fast path (open question 4).
2. **A notify workspace syncs first**, outside the scan lock, and gets a sync number `s`, or `NOT_SYNCED`.
3. **It takes the scan lock.** If a scan that succeeded took the journal at `taken_sync >= s` (or, for a read that walks, began after the read arrived, as R2.02's rule), the read is covered. It answers with that scan's source and reason: `INDEX` for a narrowed scan; `WALK` with its reason, or `COVERED_BY_FULL_SCAN`, for a full one. `WorkspaceEntry::scan_started` becomes `last_scan: Mutex<Option<ScanMark { began, taken_sync, full, reason }>>`.
4. **It checks the workspace is active**, as now.
5. **It peeks at the journal** (no take yet). If the journal is stale, or the read is `NOT_SYNCED`, it takes a full scan, and the source is `WALK` with that reason. On Linux the full scan waits for its inotify turn, as now.
6. **Clean.** If the journal is fresh and empty, and the row's commit is the view's working-copy commit at head (no adoption pending), nothing is snapshotted and nothing is recorded. The source is `INDEX`, `snapshot` is unset, and the read runs at head. It does not touch the scheduler's `last_completed` or `last_full_completed`, so a workspace that is only read still gets its timer's scans.
7. **Dirty.** Otherwise it takes a snapshot of kind `explicit` through the existing pipeline, with the taken journal's paths as its prefixes. The source is `INDEX` if jj narrowed the scan. If jj did not, the source is `WALK`, with `STALE_WORKING_COPY` or `PATH_NOT_NARROWABLE` from a new `PendingSnapshot::full_reason()`. The narrowed scan takes no inotify turn.
8. **Every scan that succeeds** records its `ScanMark`, so the reads behind it are covered.

A row whose commit differs from the view's (step 6's second condition) goes to step 7, where `begin_snapshot` finds the working copy stale and runs the adopt arm in full: `STALE_WORKING_COPY`. Narrowing the stale arms when the journal vouches for the files is left out (see "Out of scope").

### What a status from the index equals

- **The guarantee.** For every change the watcher reports, an index answer equals the walk's: the same working-copy commit, tree, changed paths, conflicted paths and untracked files. Test 3 compares them over seeded random edits. The cases that need care, each in that test:
  - **Deletions** are found because the journal names the path and jj finds it gone.
  - **Renames.** Both halves are journaled: inotify's `MOVED_FROM` and `MOVED_TO`, and FSEvents' two events. Each raw event carries its own path, and the tap records both.
  - **New directories.** The directory's own event becomes a prefix, and jj walks under it (ADR 0026, decision 3).
  - **Ignore rules.** An ignored path in the journal is checked and stays ignored. A `.gitignore` edit makes jj rescan its directory, and `.reefignore` is `TOO_BROAD`.
  - **The executable bit.** `IN_ATTRIB` and `ItemInodeMetaMod` arrive as `Modify(Metadata)` events, which `DropReads` keeps.
  - **Symlinks.** The link's own path is reported, and links are never followed.
  - **Conflicts** come from the commit tree. Editing a materialized conflict file names that file.
- **What it does not see until the next full scan**: a change no event names.
  - **Both platforms:** a write through a hard link from outside the root (the kernel reports the path used), and a write into an overlay's upper directory directly (only by bypassing the mount as root).
  - **Linux:** a write through a shared mapping whose file is never closed. inotify reports no `IN_MODIFY` for `mmap` writes, but `IN_CLOSE_WRITE` at close, which the tap now journals.
  - **macOS:** a write through a shared mapping, until a test shows FSEvents reports it (the implementation adds a ten-line check to test 20's macOS arm and states the result in ADR 0048); an APFS deletion through another spelling (ADR 0026, decision 6).
  - **No agent tool writes tracked files this way.** Editors, formatters, compilers and `git` write with `write()`, and package managers hard-link only into ignored directories (`node_modules/`, `target/`). The sync covers the write-then-ask path completely.
  - **This is the set R1.30's watcher snapshots already accept.** Reads now accept it too.
  - **The bound is `watched_fallback_interval` (10 minutes):** every watched workspace is fully scanned at least that often, idle or busy ("Full scans on a timer"), and sooner by any walk, a release, or the `Snapshot` RPC (`reef ws snapshot`, the MCP `snapshot_workspace`), which stays a full scan and is the escape hatch. Reads never walk on a timer: under load a full scan of `large` takes up to 11.3 s (R1.30), and on Linux it waits for the inotify turn, so it belongs off the read path.
  - **Reconciliation reports each miss** (below).

### Reconciliation on snapshot

- **Every snapshot takes the journal, and every full scan that succeeds clears its stale reason** (see "The journal"). A full scan of any kind counts: the fallbacks, a read that walked, the `Snapshot` RPC, a move. `behind`'s old rule, cleared by scheduled snapshots only, goes away.
- **Misses are detected.** When a full scan of a notify workspace takes a fresh journal, Reef keeps the paths it took. After the commit it diffs the old tree against the new one (`diff_stream`, proportional to what changed). A changed path is a miss when no taken path covers it (the path or a directory above it) and no path reported during the scan covers it either: Reef peeks at the journal when the scan ends.
  - Reef logs one warning, "status index missed changes", with `workspace_id`, `missed_count` and up to 10 paths.
  - It adds `index_misses` to the watcher summary line, and a `testing` accessor exposes the count.
  - Nothing else changes, since the walk already recorded the change.
  - Watchman workspaces are not checked, because jj narrows their scans.
  - The timer's full scans are where misses on a busy workspace are found, so the warning and `index_misses` are a live alarm during a session, not only at release.

### Which snapshots use the index

- **Every read's incidental snapshot**: `snapshot_for_read`, used by `GetStatus`, `ListChanges`, `GetChange`, `GetDiff`, `ReadFile`, `ListFiles` and `ListSymbols`. `GetWorkspace` with `snapshot_first` (`workspace/manager.rs:499`) moves onto `snapshot_for_read`, so `reef ws inspect` reads from the index too.
- **Stay full scans**:
  - the `Snapshot` RPC (`reef ws snapshot`, the MCP `snapshot_workspace`): a request for a snapshot, and the escape hatch;
  - a release's final snapshot, moves, shutdown snapshots and GC's;
  - writes' pre-snapshots (R2.03, R2.04: `workspace/rewrite.rs:311`, `:425`). A write that misses an edit has more at stake than a read; decided by the user, to revisit after a release whose load runs report 0 misses.
- **Watcher snapshots** keep R1.30's narrowing, now over the journal.

### Linux and macOS

| | Linux | macOS |
| --- | --- | --- |
| Watcher | one inotify instance and one queue for every notify workspace | one FSEvents stream per notify workspace (new) |
| Sync ordering | the queue | the workspace's stream |
| Lost events | `IN_Q_OVERFLOW`: every notify workspace `EVENTS_LOST` | a stream's rescan flags: that workspace, or every one when the path is under no root |
| Not watched | watch limit for a new directory; a background attach until its post-attach scan (ADR 0028) | a stream that cannot start |
| After a create | `NOT_WATCHED` until the attach and its full scan, so the first reads walk | fresh at once: the stream is up before `Create` returns |
| Full scans | wait for the inotify turn; narrowed reads do not | no turn |
| Backends | reflink and copy as files; kernel overlayfs and `fuse-overlayfs` through the merged mount, which reports writes made through it. A FUSE process that dies fails `check_materialized`, so `SNAPSHOT_FAILED` | APFS clones and copy |

`cfg(target_os = "linux")` code is checked in the privileged Linux container, as `docs/benchmarks.md` describes, since macOS never compiles it.

### The response

- **`WorkspaceStatus.source`** is `INDEX` or `WALK` for a read at head that snapshots first. With `[status_index] enabled = false` it is `SNAPSHOT`, as before. It stays `LAST_SNAPSHOT` with `skip_snapshot` and `OPERATION` with `at_operation`, and those two never sync.
- **`WorkspaceStatus.walk_reason`** (new) is set only with `WALK`.
- **`snapshot`** is the operation the read recorded, as now. It is unset on a clean index answer, which records nothing.
- **Other reads** report no source: they have no field for it, and adding one to each is out of scope. Their snapshots follow the same path, and the daemon logs each one's source.

### Schema

API revision 13, with the digest commented "R2.23: `StatusWalkReason`, `WorkspaceStatus.walk_reason`". Every new element gets its full leading comment (ADR 0029 checklist). Comment changes on existing elements do not move the digest.

```proto
// status.proto
service StatusService {
  // ... (replaces "R2.23 changes how it is answered, not its shape.")
  // Since R2.23 the workspace's files are read from the incremental index:
  // the watcher's journal of paths changed since the last scan, synced to
  // the request's arrival. Nothing changed means no snapshot; otherwise a
  // snapshot of those paths alone. When the index cannot answer, the
  // snapshot walks the tree, and `walk_reason` says why.
  rpc GetStatus(GetStatusRequest) returns (GetStatusResponse) { ... }
}

enum StatusSource {
  // ...
  // A snapshot this request took, or found nothing new to record. Since
  // R2.23 only with `[status_index] enabled = false`.
  STATUS_SOURCE_SNAPSHOT = 1;
  // The incremental index (R2.23): no snapshot when nothing changed since
  // the last scan, else a snapshot of the changed paths alone, in
  // `snapshot`.
  STATUS_SOURCE_INDEX = 2;
  // A snapshot that walked every tracked file because the index could not
  // answer; `walk_reason` says why (R2.23).
  STATUS_SOURCE_WALK = 3;
  // ...
}

// Why a status walked the tree instead of reading the index (R2.23).
enum StatusWalkReason {
  // Not set: the source is not STATUS_SOURCE_WALK.
  STATUS_WALK_REASON_UNSPECIFIED = 0;
  // The workspace's watch is not up: it failed, is still attaching, hit
  // the watch limit, or its Watchman subscription is down.
  STATUS_WALK_REASON_NOT_WATCHED = 1;
  // It was watched again after a time unwatched (a daemon start, a
  // restore, a move): writes in between were never reported.
  STATUS_WALK_REASON_WATCH_RESTARTED = 2;
  // The watcher lost events: an inotify overflow, an FSEvents rescan, or a
  // Watchman fresh instance.
  STATUS_WALK_REASON_EVENTS_LOST = 3;
  // More paths changed than `watcher.narrowed_max_paths`, or the root or
  // `.reefignore` changed.
  STATUS_WALK_REASON_TOO_BROAD = 4;
  // The workspace's last snapshot failed after taking the changed paths.
  STATUS_WALK_REASON_SNAPSHOT_FAILED = 5;
  // The watcher did not confirm within `[status_index] sync_timeout` that
  // it had seen every write made before the request.
  STATUS_WALK_REASON_NOT_SYNCED = 6;
  // The working copy is stale against the view, or has no working-copy
  // commit in it: the snapshot adopts, diverges or recovers (ADR 0018).
  STATUS_WALK_REASON_STALE_WORKING_COPY = 7;
  // A changed path cannot be scanned alone (not UTF-8, `..`, or a macOS
  // spelling that cannot be resolved).
  STATUS_WALK_REASON_PATH_NOT_NARROWABLE = 8;
  // A full scan that another request or the daemon started after this one
  // arrived answered it.
  STATUS_WALK_REASON_COVERED_BY_FULL_SCAN = 9;
}

message WorkspaceStatus {
  // ...
  // Why the tree was walked; set only when `source` is STATUS_SOURCE_WALK.
  StatusWalkReason walk_reason = 10;
}
```

No new reason in `reef_api::error`: a walk is not an error. CHANGELOG lists the additions (checklist 11).

### Documentation

- **`docs/adr/0048-status-from-the-watchers-journal.md`** (accepted).
  - **Decisions:**
    - The index as jj's working-copy state plus an in-memory journal, not SQLite.
    - The journal fed before the debouncer, taken by every snapshot.
    - The sync cookie in a per-workspace directory outside the root, and why it orders.
    - One FSEvents stream per workspace on macOS, over its root and its sync directory.
    - The stale reasons and what clears them.
    - The read path: clean, narrowed, or walk.
    - Which snapshots stay full.
    - A watched workspace is fully scanned at least every `watched_fallback_interval`, busy or idle; reads never walk on a timer.
    - Misses detected at full scans.
    - The guarantee and its stated gaps, including whether FSEvents reports mapped writes (measured).
  - **Alternatives:**
    - A SQLite table of file states per workspace.
    - Narrowing to the debounced set with no sync point.
    - Stale on every macOS stream restart.
    - A cookie in the workspace root (Watchman's choice without a VCS directory): watch-mode tools in the agent's tree would see one per read.
    - A daemon-owned watcher without notify-debouncer-full.
    - `FSEventStreamFlushSync` through Reef's own FSEvents binding.
    - Writes' pre-snapshots from the index.
    - A periodic walk for reads (11.3 s per full scan of `large` under load, R1.30).
  - **Amends:** ADR 0003 (the status index is not in the database); ADR 0026, decision 7 (explicit snapshots are full: reads' are not any more; the watched fallback was a backstop only for idle workspaces) and its consequence on rescans; ADR 0028, decisions 6 (the macOS attach) and 9 (`IN_CLOSE_WRITE` is journaled).
  - Indexed in `docs/adr/README.md`.
- **`docs/design.md`**, Storage, replacing the status index's place in the database: "The index is jj's working-copy state, a file per workspace under the daemon's state directory that records each file's size, mtime, type and content hash, plus an in-memory journal of the paths the watcher reported since the last scan, synced to each read. It is marked stale after a watcher overflow, a restart or a failed snapshot, and a full walk rebuilds it; the walk is the fallback, not the path."
- **`docs/benchmarks.md`**: a "Status index (R2.23)" section with the bench, both presets, both platforms, and the before numbers in "What was verified".
- **`docs/load-tests.md`**: `REEF_LOAD_STATUS` and the run's results.
- **`CHANGELOG.md`**:
  - **Added:** `StatusWalkReason` and `WorkspaceStatus.walk_reason`; `[status_index]`.
  - **Changed:** reads that snapshot a workspace first answer from the incremental index, with no snapshot when nothing changed and a snapshot of the changed paths otherwise; `source` reports `index` or `walk`.
  - **Fixed:** on macOS, creating or releasing a workspace no longer drops other workspaces' filesystem events.
- **`docs/dev-phases.md`**: the exit criterion's line, once measured, reads: "Status on the 100k-file synthetic repository is answered from the incremental index without a tree walk: no snapshot when nothing changed, a snapshot of the changed paths alone otherwise, checked by `status/large/index_*`, which fails if any iteration walks. ## Tests

In `crates/reef-daemon/tests/status_index.rs` (new), on both platforms, with the watcher on and the default debounce. Tests wait for conditions and never assert durations.

1. `clean_status_takes_no_snapshot`: after a write's watcher snapshot settles, `GetStatus` answers `INDEX` with `snapshot` unset. The op heads are unchanged and the scan counter did not move. `ListChanges`, `GetDiff` and `GetWorkspace` with `snapshot_first` take no scan either.
2. `status_right_after_a_write`: 200 rounds, each one edit then `GetStatus` at once, with no wait. The edits cycle through create, append, truncate, delete, rename, `chmod +x` and `-x`, a symlink, and a file in a new directory. Each answer lists the edit, with source `INDEX` and a narrowed snapshot.
3. `index_status_matches_walk`: the differential test. Eight seeds of 100 random steps each. A step is one or more of:
   - a new file, or a new nested directory with files;
   - a modify keeping the size, or changing it;
   - a delete, a file rename, or a directory rename;
   - a directory moved in from outside the root, or out of it;
   - `chmod`;
   - a symlink created, retargeted, or replaced by a file;
   - an ignored file, or a `.gitignore` edit;
   - a file over `snapshot.max-new-file-size`;
   - an edit to a materialized conflict;
   - an empty directory;
   - on macOS, a case-only rename.

   After each step: `GetStatus` (`INDEX`), then the `Snapshot` RPC (a full scan) must record nothing, and `GetStatus` with `skip_snapshot` must equal the index answer in working copy, changed files and conflicted paths. The miss counter stays 0.
4. `overflow_walks_then_recovers`: an injected rescan makes the next status `WALK` with `EVENTS_LOST`, and the one after it `INDEX`. On macOS a rescan naming one workspace's root leaves another's index fresh.
5. `restart_walks_once`: after a daemon restart the first status is `WALK` with `WATCH_RESTARTED`, and the second is `INDEX`.
6. `unwatched_workspace_walks`: with `refuse_watches`, `WALK` with `NOT_WATCHED`; on Linux, also a create's first status before its attach is up.
7. `sync_timeout_walks`: with cookies swallowed and `sync_timeout = "100ms"`: `WALK` with `NOT_SYNCED`, and no cookie left in the sync directory.
8. `too_broad_walks`: `narrowed_max_paths = 5` and six files written, then `.reefignore` edited, each `WALK` with `TOO_BROAD`.
9. `stale_working_copy_walks`: #91's setup (a parent workspace's snapshot rebases a child's change). The child's status is `WALK` with `STALE_WORKING_COPY`, its files are adopted, and the next status is `INDEX`.
10. `failed_snapshot_marks_the_index_stale`: with `fail_scans`, a read fails. After it, `WALK` with `SNAPSHOT_FAILED`, and nothing the failed scan took is lost.
11. `covered_reads`: 20 concurrent statuses after one write: at most two snapshots and two cookies, every answer lists the write, and the sources are `INDEX`. With a `Snapshot` RPC started after they synced, a covered read reports `WALK` with `COVERED_BY_FULL_SCAN`.
12. `index_disabled_is_r2_02`: with `[status_index] enabled = false`, source `SNAPSHOT`, a full scan, and no cookie written.
13. `skip_snapshot_and_at_operation_do_not_sync`: `LAST_SNAPSHOT` and `OPERATION` as before, with no cookie and no scan.
14. `missed_change_is_reported`: raw events under one path dropped through a `testing` hook, then a write there. Status does not list it (the stated gap). The `Snapshot` RPC records it, and the miss counter and the warning name the path.
15. `no_events_lost_across_creates`: a workspace written every 2 ms (a new file each time) while 20 other workspaces are created and released. Every written path is in its journal, its status lists every file, and the miss counter is 0. This fails on macOS before the per-workspace streams.
16. `cookies_order_after_writes`: 1,000 rounds of a write in workspace A then a sync of A, with B and C written meanwhile. A's journal holds the path whenever the sync returns.
17. `watcher_snapshot_skips_an_empty_journal`: a write, a status at once (which takes the journal), then the debounced event. No second scan runs.
18. `cookies_never_enter_the_root`: a recursive watcher of the test's own on the workspace root, 100 statuses, and no event under the root; the sync directory is gone after release, and a leftover one is swept at start.
19. `busy_workspace_is_fully_scanned_on_the_timer`: a short `watched_fallback_interval`, writes every few seconds, and one change whose raw events are dropped through test 14's hook. A full scan runs within the interval, records the change, and the miss counter names it. An idle workspace that is only read still gets its timer scan.

21. `watchman_restart_is_not_a_walk` (feature `watchman`): after a daemon restart, a Watchman workspace's first status is `INDEX`, not `WATCH_RESTARTED`.

## Implementation notes

- **Order:**
  1. The schema (bump, `buf lint`, `buf format`, `buf breaking`).
  2. The journal behind the existing debounced feed, with `narrowed.rs` green.
  3. The tap on notify's thread, the journal fed there, and `lost` removed.
  4. Cookies and `sync`, with test 16.
  5. macOS streams, with test 15 (run it before the change to see it fail).
  6. The read path and the reasons, tests 1 to 13 and 17.
  7. Miss detection, test 14.
  8. Watchman and overlay, tests 21, 22 and 23; the timer and `Close(Write)`, tests 19 and 20; the root check, test 18.
  9. The bench, the load run, the ADR and the docs.
- Check `df -h` before the first build. The disk has filled from `target/` and Docker's volumes before.
- **Never block notify's thread.** The tap takes `Demux`'s lock and the journal's lock, each for a lookup and an insert. Cookie removal, logging and wake-ups go elsewhere: a `tokio::sync::Notify`, or a `watch` channel per workspace, for `seen_sync`. R1.32 found the overflow loop in exactly this thread falling behind.
- **The lock order is fixed:** `Demux`, then `Journals`. Never take the scheduler's `entries` while holding `Journals`.
- **Lint and test `cfg(target_os = "linux")` code in the privileged `ubuntu:24.04` container** before pushing. macOS never compiles it.
- **Run `crate_graph` outside a Reef workspace**: a shared target directory bakes stale paths into it.
- **Timing tests flake under load.** Assertions on time belong in the bench. When a timing test fails, compare with `main` before blaming the change.
- **Do not hold the metadata mutex across the sync or the scan.** Read the row first, as `GetStatus` does now.

## Acceptance criteria

- [ ] Reads that snapshot a workspace first answer from the index: no snapshot when nothing changed, a narrowed one otherwise, and a walk only for the stated reasons, each reported (tests 1, 2, 4 to 13, 17).
- [ ] An index answer equals the walk's over the differential test, with no misses (test 3), and misses outside events are detected and logged (test 14).
- [ ] No events are lost across creates and releases on either platform, and a sync orders after every earlier write (tests 15, 16).

## Out of scope

- A SQLite table of file states (decided by the user).
- Writes' pre-snapshots from the index (decided by the user).
- A clean fast path for Watchman workspaces, which needs Reef's own synced Watchman clock (a follow-up issue the PR files, decided by the user).
- Narrowing ADR 0018's stale arms when the journal vouches for the files.
- A daemon-owned watcher without notify-debouncer-full, and an inotify mask without `IN_OPEN` (ADR 0028's note).
- jj-lib's upstream contribution 2 (ADR 0008), which would remove one of the two state loads per narrowed scan.
- A `source` field on reads other than `GetStatus`, and index health on `Workspace`. R2.20 adds one if its panel needs it.
- Persisting the journal across restarts.
- Detecting writes through hard links from outside the root, and through mappings never closed.

## Risks

- **FSEvents ordering within a stream** is what the macOS sync relies on: events in event-id order, a cookie after a write meaning the write was delivered. Test 16 is the guard. If it fails on a runner, the fallback is FSEvents' own flush (`FSEventStreamFlushSync`), which needs Reef to own the stream (an alternative ADR 0048 records). Until then, macOS reads would have to walk.
- **The sync directory's ordering on macOS** rests on FSEvents ordering events by id across a stream's two paths, not only within one. Test 16 is the guard; if it fails, the fallback is a cookie in the root (the alternative ADR 0048 records) or `FSEventStreamFlushSync`.
- **One CFRunLoop thread per macOS workspace.** 200 at the phase target. FSEvents has no documented per-process stream limit at that count; the load run is the check.
- **The tap runs on notify's only thread.** A slow tap fills the kernel queue and starts R1.32's overflow loop. It does two map operations under two short locks and nothing else (see "Implementation notes"), and the load run's overflow count is the check.
- **A change no event names is missing from status** until the next full scan, which every watched workspace gets at least every `watched_fallback_interval` (10 minutes), busy or idle. Before this ticket a read would have found it. It is stated, detected and counted at those scans (tests 14, 19), and has an escape hatch.
- **The timer's full scans cost** one full scan per busy workspace per 10 minutes, the rate R1.23 already accepts for idle ones (200 `large` workspaces: 20 a minute), on the inotify turn on Linux. A read or watcher snapshot that lands during one waits for it once. The load run records them by trigger.
- **A Linux workspace's first reads after create walk** until its background attach is up: seconds during a burst (R1.32). The source says so.
- **Watchman's staleness is approximated by Reef's subscription.** jj's own query can see a fresh instance the subscription has not reported yet. Then a read reports `INDEX` for what was a crawl. The answer is still correct; only the label is wrong.

## Choices this brief made, and why

- **jj's state plus a journal in memory, not SQLite**: the file record already exists and is the one that decides what a snapshot records, and a dirty set is invalid after any restart. A database would add a copy to keep equal and nothing to trust.
- **Before the debouncer**: a read cannot wait half a second for a path, and the tap's place already exists (`DropReads`).
- **A cookie, outside the root**: the standard sync for event-based indexes (Watchman's), and the only one notify allows without forking it; outside the root so tools watching the agent's tree never see it (decided by the user).
- **Full scans on a timer, not walks on reads**: the scan that bounds a missed change costs the same either way, and off the read path it never slows the agent's write-then-ask loop.
- **One FSEvents stream per workspace**: the only way, with notify 8.2.0, to stop one workspace's attach from dropping another's events.
- **Clean means no snapshot**: the common case after a watcher snapshot has settled. It costs a sync and the read.
- **Reads only**: a read that misses an edit shows stale state until the next scan; a write that misses one acts on it.
- **A walk reason, not only a source**: "why was this slow" is state the daemon has. The rule that the interface shows nothing the API cannot means the API carries it.

## What later tickets inherit

- **R2.20** can show each workspace's index state if its panel needs it: a `Workspace` field over the journal's stale reason.
- **R3's file browser and editors** read through the same snapshot path, so their reads of a live workspace cost what changed.
- **R4's store** keeps no working-copy index. Workspaces stay local.
- **A daemon-owned watcher** (ADR 0028's note) would replace notify-debouncer-full and own the FSEvents streams. It could flush instead of using cookies, and drop `IN_OPEN` from the inotify mask.

## Departures in the implementation

Found while implementing it or in its review; ADR 0048 records the decisions.

- **New directories stay dirty on Linux.** notify adds a new directory's inotify watch only once it has read the rest of its buffer, so a write under a directory just created can go unreported. The journal keeps a directory created or moved in dirty across takes until an event from under it shows its watch is up, or 10 s have passed.
- **A new macOS stream is confirmed with a cookie** before the workspace counts as attached: notify drops a stream's start error, so a stream that never started would otherwise answer every read as clean. The brief's "a stream that cannot start → `NOT_WATCHED`" is this.
- **Cookie numbers come from one counter for the daemon's life**, not one per journal, so a journal tracked again (an aborted release) never reuses a number a scan's mark still holds.
- **A watch-limit error marks every notify journal `events-lost`**: notify stops adding the batch's new watches at the first one, whichever workspaces they were in.
- **A macOS rescan is routed by root, skipped prefixes included**, so a rescan in one workspace's excluded build directory is that workspace's alone.
- **A pending attach marks the journal without touching whether the watch is up**, since the attach can report up before `watch` returns.
- **A waiting read stops when its journal goes stale**, instead of sitting out `sync_timeout`.
- **`ScanMark` keeps the last full scan beside the last scan**, so a read that did not sync is still covered by a full scan a narrowed one followed (R2.02's rule).
- **A failed snapshot marks the journal only if it took it.**
- **Misses are not checked after a read that could not sync**, and not counted when the check's own sync fails or the journal went stale meanwhile.
- **Sync directories are swept at start** by removing `repos/<id>/sync/` whole in `sweep_abandoned_creates`; each active workspace makes its own again when tracked.
- **Watchman paths are journaled by the scheduler** from its debounced events (`record_event`), not in `watchman.rs`: jj narrows Watchman scans, so the paths only count.
- **The bench's `walk` rows** walk through the index path with an injected `events-lost`, not with the index off: one daemon per preset.
- **Tests.** Test 3 runs 3 seeds of 40 steps by default and the brief's 8 × 100 with `REEF_INDEX_SEEDS=8`; conflict edits are not among its steps. Test 2 runs 108 rounds (`REEF_INDEX_ROUNDS`). Test 16 checks ordering through `GetStatus` with two other workspaces written meanwhile, without a tap-delay hook. Test 11 has no `COVERED_BY_FULL_SCAN` half, and test 19 no idle half. Test 23 is the `status_index` and `overlay_restart` suites run as root in the privileged container, where workspaces are kernel overlayfs mounts. Unit tests cover the sticky directories and the tap.
