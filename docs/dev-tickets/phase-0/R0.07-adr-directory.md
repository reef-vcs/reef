# R0.07 ADR directory and template

Phase 0 · Size S · Depends on: nothing · Unblocks: the ADRs written by R0.01 (0007), R0.04 (0008), R0.09 (0009), R0.08 (0010)

## Context

`docs/design.md` already makes most of the foundational technology decisions in its "Technology choices" table, with a one-line reason each. Those reasons will get lost or relitigated unless they are recorded as decisions with context and consequences. Several Phase 0 tickets must write an ADR and need a template and a numbering scheme first. Numbers are pre-assigned in `docs/dev-tickets/phase-0/README.md` so tickets running in parallel do not collide.

## Decisions

- **Location:** `docs/adr/`. One file per decision, `NNNN-kebab-title.md`, four-digit zero-padded, never reused or renumbered.
- **Format:** a trimmed MADR. Sections: Status, Date, Context, Decision, Consequences, Alternatives considered. No "Decision drivers" section; fold drivers into Context.
- **Statuses:** `proposed`, `accepted`, `superseded by NNNN`, `deprecated`. An ADR is edited after acceptance only to change its status or add a "Superseded" note; new information goes in a new ADR.
- **Index:** `docs/adr/README.md` holds a table of all ADRs. Every ADR PR updates the table.
- **Backfill scope is exactly six technology ADRs** plus the meta ADR: jj-lib, SQLite, gRPC with tonic, Tauri 2, CEL, and the hash function and object backend by phase. Other rows of the technology table (BLAKE3, gitoxide, tree-sitter/Mergiraf, SCIP, rmcp, in-toto, notify/Watchman, React) are not backfilled now; they get ADRs when the ticket that first depends on them lands.
- **Content comes from design.md.** The ADRs restate the design document's reasoning in ADR form and may add detail, but must not contradict it. Where this ticket adds a nuance the design does not state, say so in the ADR.

## Deliverables

### `docs/adr/0000-template.md`

```markdown
# NNNN. Title in sentence case

- Status: proposed | accepted | superseded by NNNN | deprecated
- Date: YYYY-MM-DD
- Ticket: R0.XX (or "none")

## Context

What situation forces a decision. Facts, constraints, and the forces in tension. Link to design.md sections and to prior ADRs.

## Decision

The decision, in one or two paragraphs, in the active voice ("We will ..."). State the scope: what this decision covers and what it does not.

## Consequences

What becomes easier, what becomes harder, what we commit to maintaining, and what would make us revisit this.

## Alternatives considered

One short paragraph per alternative: what it is, why it lost. Include "do nothing" where it was an option.
```

### `docs/adr/0002-build-on-jj-lib.md`

Context: the data model section of design.md needs working-copy-as-snapshot, stable change IDs, an operation log with undo, and stored conflicts; Jujutsu implements all four in an embeddable Apache 2.0 Rust library; the roadmap's open question "contribution to Jujutsu or a separate project" is decided as separate project depending on jj-lib (design.md, Roadmap, last paragraph). Decision: depend on `jj-lib` as a library, exact-pinned per release; never fork `jj-cli`; upstream generic improvements (gitoxide migration, Watchman) and keep workspaces, leases, evidence, and the daemon in Reef. Consequences: jj-lib is 0.x and breaks between minor versions, so each bump is a deliberate ticket (Dependabot ignores it); jj-lib's MSRV becomes Reef's MSRV floor; compile times include gix; Reef inherits jj's on-disk repo format and must open repos created by the `jj` CLI; some needed hooks may not exist in the public API and must be upstreamed or worked around (R0.04 records which). Alternatives: fork jj-cli (carries human-oriented UX decisions, diverges fast); build a new store on gitoxide directly (rewrites change IDs, op log, conflicts; years of work jj already did); use git plumbing via libgit2 (no change identity, no op log, C dependency).

### `docs/adr/0003-sqlite-for-daemon-metadata.md`

Context: the daemon needs a durable, queryable local store for workspace inventory, leases, the status index, and later the query layer; design.md "Technology choices" and the "SQLite over RocksDB" paragraph. Decision: SQLite via a Rust binding (binding choice deferred to R1.01; `rusqlite` with bundled SQLite is the default expectation), one database per machine in the daemon state directory with every table keyed by repository id, since one daemon serves many repositories (R1.01), WAL mode, migrations tracked in-crate. jj-lib's own operation log stays in jj's format; SQLite holds Reef's metadata and its indexes over the op log and symbols, not a second copy of jj's op store. Consequences: SQL for the query layer for free; readable from any language for debugging; single-writer semantics mean the daemon is the only writer and clients go through the API; a future swap of the hot path to RocksDB is allowed only on profiling evidence. Alternatives: RocksDB (what EdenFS uses; opaque binary, no SQL); sled/redb (less mature, no SQL); flat files (not consistent across concurrent agents).

### `docs/adr/0004-grpc-over-unix-socket.md`

Context: agents written in Python and TypeScript need typed, streaming access; the CLI and MCP server are thin clients; subscriptions require server streaming. Decision: protobuf schemas in `crates/reef-daemon/proto/` (from R1.05) compiled with `tonic`/`prost`; the daemon listens on a Unix domain socket with filesystem permissions as the first access control; SDKs generated from the same schema; the web UI reaches the same services over gRPC-web or a WebSocket bridge. Schema is versioned and reviewed as an API. Consequences: codegen keeps SDKs in sync; no text parsing anywhere; the schema review process is a real cost; Windows named-pipe transport is an open item tied to RX.05. Alternatives: JSON-RPC over HTTP (no streaming, hand-written clients); Cap'n Proto (smaller ecosystem for Python/TS); a bespoke binary protocol (no tooling).

### `docs/adr/0005-tauri-desktop-shell.md`

Context: design.md "Human interface" wants one web application rendered locally and from a store, plus a thin desktop shell for notifications, menu bar state, a bundled daemon, deep links, and auto-update; the shell ships after the triage inbox exists (R3.39). Decision: Tauri 2; Rust backend supervises or links the daemon; native webview; Electron is the documented fallback if webview inconsistencies bite, and the shell is kept thin enough to swap. Consequences: small binaries; three platforms of signing and packaging cost (R3.41); webview differences are a known risk; the UI must stay a plain web app with no Tauri-specific code outside the shell. Alternatives: Electron (consistent webview, 150 MB, second runtime); native per-platform apps (three codebases); no desktop app (loses OS notifications and bundled daemon, which the triage inbox needs).

### `docs/adr/0006-cel-for-policy.md`

Context: landing policy (trusted attestors, required evidence kinds, size limits, forbidden paths, sign-off areas, conflict tiers, attempt caps, compute budgets) must be auditable, fast to evaluate at landing, and not Turing-complete. Decision: CEL via `cel-rust`, one policy file per repository (name settled in R3.07), evaluated in the landing service and in policy simulation; Rego is the named fallback if policies outgrow CEL. Consequences: policies are expressions over a documented input object, which the evidence/policy spec (R6.03) must define; CEL has no loops, so aggregate rules need host-provided functions; the `cel-rust` crate's maturity is a risk to re-check at R3.07. Alternatives: Rego/OPA (more powerful, heavier runtime, separate language ecosystem); Starlark (Turing-complete); TOML/YAML rule tables (not expressive enough for path-conditional rules).

### `docs/adr/0011-hash-and-object-backend-by-phase.md`

Context: the data model says objects are content-addressed and the technology table names BLAKE3, but building on jj-lib means the git backend and SHA-1 identities for trees, blobs, and snapshots until Reef has its own backend; the design's data model section now states this explicitly. Decision: phases one through three use jj-lib's git backend unchanged, so a Reef repository is a jj repository and opens with the `jj` CLI; phase four delivers a jj-lib `Backend` over Reef's own object format (BLAKE3 identities, FastCDC-chunked blobs, packfile-style local cache indexed in SQLite, the store protocol as remote), per R4.03; change IDs are random and survive the switch; migration rewrites commit identities once and records the mapping. Consequences: nothing in phases one through three may depend on the hash algorithm or on blob chunking; evidence objects (R3.01) bind to whatever snapshot identity the backend produces, so an evidence object references a backend-qualified hash; the git backend's SHA-1 is a known weakness the store backend removes; `jj` CLI compatibility is lost for repositories that migrate to the Reef backend. Alternatives: a Reef backend from phase one (delays every phase one deliverable behind a storage engine); staying on the git backend forever (no chunking, SHA-1, store protocol would have to speak git objects); SHA-256 git objects (git's own transition is incomplete and jj's support is partial).
