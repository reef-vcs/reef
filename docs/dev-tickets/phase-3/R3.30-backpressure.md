# R3.30 Backpressure

Phase 3 · Size S · Depends on: R3.28 (the `[conflicts]` table applied from `trunk()`, its fail-closed rule), and builds on R3.25 (conflict objects, `introduced` and `inherited`, `conflict::list`), R3.27 (assignments, which this ticket reads nothing from), R3.07 (`reef-policy.toml`, `[conflicts]`), #259 (`RebaseChange`, its plan, the `CHANGE_QUEUED` pre-check), R1.06 and R2.04 (`MoveWorkspace`, `EditFiles` with `new_on`) · Unblocks: none listed

## Context

The design names the job in Data model, Conflicts: "Conflicts also carry backpressure: landing refuses a conflicted change, a conflict whose owner's session has ended moves to a resolver queue with a priority, and a change cannot acquire a second unresolved conflict ancestor without policy approval." The first two parts exist (`builtin:conflicts` at the gate, R3.27's queue). This ticket builds the third. The row is one line: "Refuse a second unresolved conflict ancestor without policy approval."

Why it matters: a conflicted commit is a legal parent, so agents can keep starting work on top of conflicts nobody has resolved. Every resolution below then rewrites the work above it, and a pile of two or more unresolved conflicts under one change means that work rests on content that will change twice. Backpressure stops new work from piling on, the way a full queue slows its producers: one unresolved conflict below a change is allowed (often it is the agent's own), a second needs the policy to allow it.

So this ticket builds:

1. **A count**: the unresolved conflicts a change would rest on after an operation, read from jj on the head the operation starts from.
2. **A limit in policy**: `[conflicts] ancestors` in the `reef-policy.toml` at `trunk()`, from 0 to 32, default 1.
3. **The refusal**: at the four RPCs where a caller asks Reef to put a change on a base (`CreateWorkspace`, `MoveWorkspace` and `EditFiles` with `new_on`, and `RebaseChange`), with reason `CONFLICT_ANCESTORS` and a `next` that lists the conflicts in the way.
4. **The documents**: `docs/conflicts.md`, `docs/policy.md`, `docs/rebasing.md`, ADR 0099, threat rows S-305 to S-308.

No migration, no new RPC, no new message field. The refusal is a new reason on four existing RPCs, documented in proto comments, which the API digest leaves out.

### The rule

An operation that puts a change on a **base** is refused when, after it, the change would rest on more unresolved conflicts than the limit, and at least one of them comes from the base:

```text
from_base = unresolved conflicts in  ::base & mutable()          (the base itself included)
total     = from_base, plus, for a branch-mode rebase only,
            those in the change's own stack below it             ((base..change) & mutable(), the change itself excluded)
refused   = from_base > 0 && total > limit
```

An **unresolved conflict** is a commit that introduces a conflict jj stores (decision 3). The change the operation names is never counted: its own conflict is its own work, not an ancestor.

| Operation | Base | Counted revset (`total`) |
| --- | --- | --- |
| `CreateWorkspace` with `new_on` | the `new_on` commit | `::<base> & mutable()` |
| `MoveWorkspace` with `new_on` | the `new_on` commit | `::<base> & mutable()` |
| `EditFiles` with `new_on` | the `new_on` commit | `::<base> & mutable()` |
| `RebaseChange`, plan `Move`, branch mode | the destination | `(::<dest> \| (<dest>..<rev>)) & mutable() ~ <rev>` |
| `RebaseChange`, plan `Move`, source mode | the destination | `::<dest> & mutable()` |
| `RebaseChange`, plan `StartOn` (a landed revision starts a new change on the destination) | the destination | `::<dest> & mutable()` |
| `RebaseChange`, plan `UpToDate` | none: nothing is checked | none |

`<base>`, `<dest>` and `<rev>` are full commit ids. For a new change `from_base` equals `total`, so the test is `total > limit`. For a rebase onto a clean destination (the usual case: `trunk()`, which is immutable) `from_base` is 0 and nothing is refused, whatever the stack carries: those conflicts are the change's own, assigned to its owner by R3.27. In branch mode the moved members are judged as they are before the rebase (introduced against their old parents); a conflict the rebase itself makes in them is counted by the next operation that builds on them.

Worked examples with the default limit of 1, using the spike's commits (A and B each introduce a conflict, B on A; C clean on `main`):

| Request | from_base | total | Result |
| --- | --- | --- | --- |
| `reef ws create --new-on A` | 1 | 1 | allowed |
| `reef ws create --new-on B` | 2 | 2 | `CONFLICT_ANCESTORS` |
| `reef ws create --change B` (edit B, to resolve it) | not checked | | allowed |
| `reef rebase C --onto A` | 1 | 1 | allowed |
| `reef rebase C --onto B` | 2 | 2 | `CONFLICT_ANCESTORS` |
| `reef rebase B` (onto `trunk()`, branch mode, moves A and B) | 0 | | allowed |
| `reef rebase R --onto A`, R a clean child of another conflicted change Q, branch mode (moves Q and R) | 1 | 2 | `CONFLICT_ANCESTORS` |
| the same with `--source` (moves R only) | 1 | 1 | allowed |

### Where it is checked

In the service layer, before the handler calls the manager or `write_change`, on a read of the current head. This is the `CHANGE_QUEUED` pattern: a pre-check from what Reef reads, not a lock. A conflict that appears between the check and the write is not seen (S-306). Nothing in `workspace/`, `reef-lib` or jj's transaction changes.

- **`CreateWorkspace`** (`service/workspaces.rs:403`): after `start` is mapped (`:423` to `:427`), when it is `Start::NewOn(revision)`, before `manager.create` (`:428`).
- **`MoveWorkspace`** (`service/workspaces.rs:831`): after `start` is mapped (`:847` to `:851`), when it is `Start::NewOn(revision)`, before `manager.move_to` (`:852`). The revision may be `@` (the workspace's own change), so the check snapshots the workspace first when the revision uses the working copy, as `ListConflicts` does (`service/conflicts.rs:643` to `:646`, with `reading::uses_working_copy`, `:274`, and `reading::snapshot_first`, `:128`).
- **`EditFiles`** (`service/files.rs:225`): after `edit_target` is mapped (`:233` to `:239`), when it is `EditTarget::NewOn(revision)`, before `write_change` (`:246`); the same snapshot-first rule.
- **`RebaseChange`** (`service/rebase.rs:36`): after the `CHANGE_QUEUED` loop (`:61` to `:71`), from the plan `moving_changes` already computes (`:216`), which now returns it.

Not checked, on purpose:

- **Snapshots, and the rebases jj does on them.** Amending a change rebases its dependents (R3.11), which may give a dependent more conflict ancestors. The design says an amend never blocks ("a dependent that no longer applies cleanly carries a conflict object rather than blocking the amend"), and Reef never refuses a snapshot.
- **Editing an existing change** (`change` starts, `EditFiles` without `new_on`, `reef conflict claim`): this is how a resolver reaches a conflict. Refusing it would block the way out.
- **The default start**, which is a bookmark on `trunk()` except in a repository with none (S-305).
- **R3.11's supersede** (`RebaseMode::Children`, the daemon's own move of dependents onto the superseding change) and every internal create (`store/build.rs:396`).
- **Proposing and landing**: landing already refuses a conflicted change (`builtin:conflicts`) and one whose parents have not landed (R3.13), so a change resting on conflicts cannot land anyway.
- **The jj CLI**: Reef cannot refuse `jj new` or `jj rebase` (S-305).

### The limit: `[conflicts] ancestors`

```toml
[conflicts]
tier = "approve"
attempts = 3
ancestors = 1      # 0 to 32; default 1: how many unresolved conflicts a change may rest on through Reef (R3.30)
```

- **Range** 0 to 32 (32 is R3.10's stack bound). 0 refuses building on any unresolved conflict. Out of range is a load diagnostic at `conflicts.ancestors`: `33 is not from 0 to 32`.
- **Only in `[conflicts]`**, not in `[[conflicts.rule]]`: a rule is per conflict, and the limit is per change. `deny_unknown_fields` already refuses it there.
- **Which policy.** The `reef-policy.toml` at `trunk()`, as R3.28 reads it. It is read only when `from_base > 0`, so an operation on a clean base costs one revset walk and no policy read.

| What `trunk()` has | Limit | Metadata `policy` |
| --- | --- | --- |
| A policy that loads | its `ancestors`, else 1 | `file` |
| No `reef-policy.toml` | 1 | `default` |
| `trunk()` does not resolve (no bookmark) | 1, with a `tracing::warn!` | `default` |
| A file whose bytes cannot be read, or that does not load | 0, the strictest (R3.07's fail-closed rule, as R3.28's `ask`) | `invalid` |

### The refusal

`FAILED_PRECONDITION`, kind `Conflict` (CLI exit 5), reason **`CONFLICT_ANCESTORS`**.

- **Message**: `a change on 1a2b3c4d5e6f would rest on 2 unresolved conflicts, more than the 1 the policy at trunk() allows ([conflicts] ancestors)`. With `policy` `invalid`: `… more than the 0 allowed while the policy at trunk() does not load: <first diagnostic or read error>`. With 33 found: `at least 33`.
- **Metadata**: `operation` (`create`, `move`, `edit` or `rebase`), `commit_id` (the base, full), `count` (unresolved conflicts found, at most 33), `limit`, `oldest_change_id` (the last one found, which is the lowest in log order; reverse hex), `change_ids` (the first 5 found, reverse hex, comma-separated, newest first), `policy` (`file`, `default` or `invalid`), `policy_commit` (`trunk()`'s commit; empty when `trunk()` did not resolve).
- **Hint**: `Resolve the conflicts under it first, the oldest first: reef ws create --change <oldest, 12 letters> edits that change. Or start on a revision with fewer unresolved conflicts below it, such as main. The owners of reef-policy.toml at trunk() set how many a change may rest on, with [conflicts] ancestors.` (For `invalid`, the last sentence is `The policy at trunk() does not load; fix it to allow any.`)
- **`next`**: `["reef", "conflict", "list", "--introduced", "-r", "<the counted revset>"]`, the same text the check evaluated, so what the agent reads is exactly what was counted.

## Performance expectations

- An operation on a clean base (a new change on `main`, a rebase onto `trunk()`) costs one revset evaluation that finds nothing (`::<base> & mutable()` is empty when the base is immutable) and no policy read.
- Otherwise, one walk of the base's mutable ancestors: a commit load per commit looked at, a conflict read per conflicted one, at most 10,000 looked at and 33 conflicts kept; a second walk for a branch-mode rebase; then one policy read and one cached load.
- No new work on snapshots, reads, the follower or the gate.

## Acceptance criteria

- [ ] A new change on a base with two unresolved conflicts below it is refused with `CONFLICT_ANCESTORS`, from create, move and edit; one with one below is allowed (tests 8 to 10).
- [ ] Editing a conflicted change is never refused (test 11).
- [ ] A rebase onto a destination that brings unresolved conflicts is refused past the limit, counting a branch rebase's own stack; a rebase onto a clean destination never is (tests 16 to 18).
- [ ] `[conflicts] ancestors` sets the limit; no policy is 1; a policy that does not load is 0 (tests 2, 12 to 14).
- [ ] Every refusal carries the metadata, a hint naming the oldest conflict, and a `next` that lists exactly what was counted (tests 3, 8).
- [ ] No migration, no API revision; `tools/list` and `reef schema` unchanged.
- [ ] `just preflight`, `just doc` and the full suite pass.

## Out of scope

- **A person's go-ahead, per conflict or per request**: decisions 4 and 5's alternatives.
- **A CEL rule over the operation and its conflicts**: decision 4's alternative; R3.24 is adding a `stack` input to the same crate.
- **Counting after the rebase, in jj's transaction**: decision 2's alternative.
- **Telling an agent that already rests on too many conflicts** (made outside Reef, or by a dependent rebase): a `reef here` step or a `reef status` line is a follow-up if agents need it; the next Reef operation that builds on it says so.
- **`missing_dependency` conflicts** (R3.11): they live on proposals, not in trees, and the dependent already cannot land.
- **The default start's fallback** to the root checkout's working-copy commit (S-305).

## Risks

- **Existing tests that build on two conflicts.** The daemon suite may have some; step 3 runs it whole and gives those fixtures a policy, never a weaker rule.
- **A stale count for the workspace's own change.** `new_on @` is snapshotted first; a change named by id with unrecorded edits in some other workspace is read as recorded, at most the watcher's delay behind.
- **Repositories that never opted in.** With no policy file the limit is 1, so building on two unresolved conflicts is refused everywhere Reef runs, the Reef repository included (it has no `reef-policy.toml`). This is decision 4's default; its alternative makes the rule opt-in.
- **Parallel tickets.** R3.21 and R3.24 also edit `reef-policy` and `docs/policy.md` (see "Files shared with R3.21 and R3.24").

## Choices this brief made, and why

- **A pre-check in the service layer, not a check in jj's transaction.** It is where `CHANGE_QUEUED` already refuses, it needs no change to `reef-lib` or the manager, and it leaves internal creates and supersede alone. The cost is a race (S-306) that only lets a little more work through.
- **Count from jj, with `conflict::list` as it is.** R3.27's brief already said backpressure counts from jj, not from assignment rows; the rows lag the follower and a commit nobody recorded has none.
- **Fail closed to 0 on an invalid policy**, as R3.28 fails to `ask`. An invalid policy at `trunk()` lands nothing anyway, so the extra refusal costs little and says why.
- **Fail open past the scan bound.** Refusing every create on a 10,000-commit branch would be worse than missing a pile that deep; it is logged.
- **No `reef here` step.** The refusal is the moment an agent needs to know, and it carries `next`; a step for a change already resting on too many conflicts is a follow-up if agents miss it.

## Decisions for the user

Answered 2026-11-27: the user took the recommendation on every decision. The rest of this brief already follows them.

1. **Which operations refuse.** *Recommended:* the four RPCs that put a change on a base a caller names: `CreateWorkspace`, `MoveWorkspace` and `EditFiles` with `new_on`, and `RebaseChange` (onto a destination that brings unresolved conflicts). Never snapshots or the dependent rebases they cause, editing a conflicted change, the default start, supersede, proposing or landing. *Alternatives:* (a) only the three that start a new change, not rebases (an agent could still move its work onto a pile); (b) also refuse proposing such a change (it cannot land anyway, so this only adds a second refusal); (c) also refuse a snapshot that would rebase a dependent onto a second conflict (the design says an amend never blocks).
2. **How ancestors are counted.** *Recommended:* commits in the base's mutable ancestry, the base included, that introduce a conflict (R3.25's `introduced`), so a stack inheriting one conflict counts once; the change itself never counts; a branch rebase also counts its own stack below the change, as it is before the rebase; a rebase is refused only when the destination brings at least one. *Alternatives:* (a) count every conflicted commit, inherited ones too (one conflict under a stack of five counts five: far too strict); (b) count after the rebase, inside jj's transaction in `reef_lib::jj::rebase::Repo::rebase` (exact for conflicts the rebase makes, but it touches the write path supersede shares and refuses rebasing a two-conflict stack onto a clean `trunk()`, which leaves an agent no Reef way to update its stack).
3. **What "unresolved" means.** *Recommended:* jj's stored conflict on the head the operation reads, whatever R3.27's assignment says (`unowned`, `assigned`, `queued`, `blocked`, `taken` all count; a resolved commit stops counting before the follower closes its row); `missing_dependency` conflicts do not count. *Alternatives:* (a) count open assignments of kind `tree` (lags the follower; a change Reef never recorded has none until the follower looks); (b) leave out conflicts a person has `taken` (the base still changes under the new work when the person resolves it).
4. **What "policy approval" is.** *Recommended:* a number in the policy at `trunk()`, `[conflicts] ancestors` (0 to 32), default 1 even with no policy file, 0 when the policy does not load. *Alternatives:* (a) the same number, but no limit without a policy file (opt-in; most repositories would never get backpressure); (b) also a person's go-ahead per conflict, like `reef conflict allow`: `reef conflict allow <asg> --build-on` marks a conflict so it is not counted (a column on `conflict_assignments`: schema 35, `0037_*.sql`; a field on `AssignConflictRequest`: API revision 55; about M); (c) a CEL `when` in `[conflicts]` over the operation, the caller and the conflicts below (paths, tier, owner), built on R3.24's `stack` input rather than a parallel one (expressive, but it adds a check scope in the files R3.24 changes, and whichever of the two merges second builds on the other).
5. **Agents and people.** *Recommended:* the same rule for every caller, through every listener. The actor is declared, and a harness that sets no `REEF_AGENT` reads as a person (`service/assignments.rs:61`), so an agents-only rule would miss many agents; a person who means it uses the jj CLI or raises the limit. *Alternatives:* (a) agents only, as R3.28 refuses blocked conflicts to agents only (a person's call is never refused); (b) every caller, plus an override on the four requests that only a person may set, refused through the remote listener (a field on four requests: API revision 55).
