# R3.21 Landing queue priority

Phase 3 · Size S, at its top end (decisions 2 and 6 keep it there) · Depends on: R3.14 (`batch::drive`, `form`, `stack_groups`, the batch's `request` and `BATCH_PRIORITY`), and builds on R3.13 (the gate, `Requester`, landing rows), R3.45 (the automatic pass, `PROPOSAL_PRIORITY`, `wait_for_evidence`), R3.10 (stack groups), R3.07 (the policy file, `Scope::Change` conditions, sign-off kinds), R3.09 (each transition's actor), R3.44 (`Ambient`, the harness table) and R3.05 (job priority and claim order) · Unblocks: R3.34 (draws each landing's priority and who waits)

## Context

The design names the job in its CI load section: "Policy sets compute budgets per proposal, per agent, and per repository ... Proposals a human is waiting on are scheduled before proposals an agent is waiting on." The roadmap row adds: "Policy can add priority rules."

Three tickets left this one a seam:

- **R3.14**: "Candidates: the open landings for the destination of the oldest queued one, oldest enqueue first (R3.21 replaces the order)", and each batch job is submitted "with priority `BATCH_PRIORITY` (1,000; R3.21 replaces it)". Its "What later tickets inherit": "R3.21 orders the candidates and sets the jobs' priority."
- **R3.45**: proposal jobs at "`PROPOSAL_PRIORITY` 500 (below `BATCH_PRIORITY` 1,000, so landing batches run first; R3.21 replaces both)", and "R3.21 orders proposals within a pass".
- **R3.10** (ADR 0078): "R3.21 orders groups, not changes."

Today every queue in the landing path is first come, first served. A person who runs `reef land` and waits at the terminal waits behind every agent change queued before theirs, and behind every agent proposal's executor jobs. On a laptop running five agents, that is most of the wait.

So this ticket builds:

1. **Who waits**: a rule for when a person waits on a change (decision 1), and a fix so the rule can tell an agent from a person (decision 2).
2. **A priority**: a number per landing and per proposal, `human` (100) when a person waits plus what the policy's `[[priority.rule]]` entries add, aged one point a minute (decisions 3 and 4).
3. **Where it applies**: the landing queue's order, which destination is served next, the order inside a batch, the executor priority of batch and proposal jobs, and the automatic service's pass order (decision 6).
4. **The surface**: two fields on `Landing` and `AutomaticStatus`, a line in `reef landing show` and `reef proposal show`, and the documents (decision 7).

### Who waits on a change (decision 1)

A person **waits on** a landing or a proposal when any of these hold. Each is a **reason**, recorded by name:

| Reason | When | Read from |
| --- | --- | --- |
| `request` | A person asked to land it: the landing's requester declared `human` on the socket (not through the remote listener), or it came through the web UI (`web_session` set). Also, for a proposal, a person's `reef land` that is waiting right now for the evidence its jobs will produce. | `Requester`; the automatic service's person mark (below) |
| `proposal` | A person proposed it: the change's latest transition with a cause other than `landing` is to `proposed` with actor `human`. | `Db::last_transition(repo, change, "landing")` |
| `signoff` | A person signed it off: the judgment's input has a `pass` evidence object of one of the policy's sign-off kinds from a `bound` key whose actor is `human` and identity kind `person` (on its tree, or on a stack member's above it, as R3.10 counts sign-offs). | `PriorityDecision.signed_off` |

No reason means only an agent waits. The daemon's own requests (the automatic service, actor `daemon`) are never a `request`.

Why these three: a person at a terminal running `reef land` is the plain case; a person who proposes their own change under `[landing] automatic = true` never runs `reef land`; and a reviewer who accepts an agent's proposal (a sign-off, R3.09) is waiting for it to land, often with no request of their own, since automatic landing queues it.

### The declared actor under a harness (decision 2)

The spike shows the first two reasons are wrong by default: an agent running in a harness that sets no `REEF_AGENT` is recorded as `human`. So:

- **The CLI** (`reef land`, and the transitions of `reef propose` and `reef proposal`) declares `agent` when `--actor` is not given, no agent name is set, and `Ambient::current().harness` is `Some`: the same harness table R3.44 reads, so no harness is named in code. `--actor human` still declares a person. One helper, `declared_actor(flag: Option<ActorArg>, named: bool) -> v1::TransitionActor`, in `reef-vcs/src/cli/proposal.rs` next to `ActorArg` (`:50`), used at `land.rs:596` and `proposal.rs:281` (each `actor:` field of the request).
- **MCP** declares `agent` on `propose_change` and `land_change` (`actor: v1::TransitionActor::Agent.into()` in both requests): MCP is the agent interface.
- **Comments** (`comment.rs:1047`, `:1166`) keep today's default; their actor decides R3.12's and R3.33's routing, and changing it is a follow-up issue the PR files.
- `docs/proposals.md` (`:50`) says the new default: "`agent` when an agent name is set or the environment names a coding agent (R3.44's harness table, `AI_AGENT`), and `human` otherwise".

### The number (decision 3)

A **priority** is an integer. For one landing or proposal:

- **base** = `add` + (`human` if a person waits, else 0), clamped to −1,000 to 1,000;
- `human` is the policy's `[priority] human` (100 by default, 0 to 1,000);
- `add` is the sum of the `add` of every `[[priority.rule]]` that matches, clamped to −1,000 to 1,000.
- **effective** = base + the whole minutes since it was queued (a landing's `created_at`; a proposal's lifecycle row `updated_at`), at most 1,000 (decision 4).

The queue orders by effective priority, highest first, then `created_at`, then id. With no `[priority]` table and every change an agent's, effective priority is the age in minutes, so the order is exactly today's.

### The policy table (decision 3)

`[priority]` in `reef-policy.toml` at the destination's head, additive to format 1:

```toml
[priority]
human = 100                     # added when a person waits on the change; 0 to 1000; default 100

[[priority.rule]]
paths = ["hotfix/**"]           # optional; with except, as [[conflicts.rule]]
when = '!change.description.startsWith("wip")'   # optional; a change condition
add = 50                        # -1000 to 1000; required
```

- **Every matching rule adds.** A rule matches when its path filter applies to the change's paths (or it names none) and its `when` holds. Summing keeps "a person first" while a rule says "hotfixes first, docs last".
- **The `when` is a change condition** (`Scope::Change`): `change`, `evidence`, `provenance`, `landing`, `batch` (always empty for a priority rule) and `groups`, as `[[rule]]` sees them, checked by the static check at load. R3.24's `stack` input reaches it the same way. A rule that reads `landing` makes the policy read the destination (`reads_destination`), which R3.45's evaluation key already follows. Who waits is not a CEL variable: a rule cannot read `request`, so a person's later request needs no new evaluation.
- **A rule that errors adds nothing.** Priority never admits or blocks anything, so it does not fail closed: the error is in `PriorityDecision.errors` and the daemon logs it at `warn` with the rule's index. The cost bound is the evaluation's (`Evaluator::run`).
- Each `[[priority.rule]]` counts toward `MAX_ENTRIES` (256), and the message at `format.rs:1006` names the table.
- `[[priority.rule]]` changes nothing on a repository without the table; `reef policy init`'s starter is unchanged.

### Starvation and preemption (decision 4)

- **Aging.** One point per whole minute queued, up to 1,000. An agent's change queued behind a steady stream of a person's changes waits at most `human` minutes (100 by default), and behind the strongest rule at most 1,000 minutes.
- **No preemption.** A batch that is testing is never cancelled for a higher priority. One batch is in flight per repository (R3.14), so a person's change waits at most one batch's checks, and cancelling would throw away executor work and could starve agents altogether.
- **No waiting to fill.** When the first candidate has a person waiting, `batch_wait` does not apply: the batch forms at once.

### Where priority is computed and stored (decision 5)

- **With each judgment.** `judge_with` already builds the input. After `evaluate_file`, on the same blocking thread, it calls `Policy::priority(&input)` when the policy loaded, and puts a `Priority { add, human, rules, waiting }` on `Judged`. `waiting.request` comes from a new `JudgeContext.person_waits`; `waiting.proposal` from one `last_transition` query; `waiting.signoff` from the decision. No policy, or an invalid one: `Priority::default()` (add 0, human 100, no rules), and the gate blocks such a change anyway.
- **Recorded on the landing row.** The gate writes the priority on each row it queues (`judge_slots`, beside `:1721`); formation writes it again on each member's row (`batch.rs:815`), from its fresh judgment, so a sign-off added while queued counts from the next formation.
- **Raised at once by a person's request.** A person's `reef land` of a change already queued (`Gate::Queued`, and each `Decided::Open` member of a stack) adds `request` to that landing's `waiting` with one update, no judgment.
- **The queue reads the rows.** Ordering happens before formation judges anything, so it reads the stored columns (`Priority::of_row`) and the age.
- **The automatic status carries it.** Each status gets the base priority and waiting of its last judgment.

### What priority reaches (decision 6)

1. **The candidate order.** `drive` sorts `open_landings` with `priority::order` before anything else. Groups then follow their best member, and the chain puts the highest first.
2. **The destination served next**: the first row after sorting.
3. **The batch's jobs.** `request` submits at `job_priority(max effective priority of members 1..=k, Stage::Batch)`.
4. **The proposal's jobs.** `lacks` submits at `job_priority(effective priority, Stage::Proposal)` and raises the jobs already open for those pairs to it.
5. **The automatic pass.** `pass` sorts stack heads by the highest effective priority of their members' previous statuses, then by today's position, so the person's proposals take the 16 judgments and the 32 job slots first.
6. **The person mark.** A person's `reef land` that waits for evidence (`wait_for_evidence`, a non-zero wait) marks the change in the automatic service until the wait's deadline. The next pass judges that stack with `person_waits`, so its status reads `request` and its open jobs are raised.

**Job priority** = 4,000 + 2 × effective + stage, where stage is 1 for a batch and 0 for a proposal. At equal priority a batch's job is claimed first (R3.45's rule), one point of priority outranks the stage, and every landing job (2,000 to 8,001) stays above a `reef job submit` at its default 0, as today. `BATCH_PRIORITY` and `PROPOSAL_PRIORITY` are deleted.

### The surface (decision 7)

No new RPC, no new MCP tool, brief JSON unchanged. Fields only, read by `reef landing show`, `reef proposal show`, R3.34 and the SDKs.

## Risks

## Decisions for the user

Answered 2026-11-27: the user took the recommendation on every decision. The rest of this brief already follows them.

1. **Who waits on a change.** *Recommended*: a person waits when a person asked to land it (socket actor `human`, or the web UI, or a `reef land` waiting now for its evidence), proposed it, or signed it off (a passing sign-off from a bound person key). Alternatives: only the verified signals (a person-key sign-off and the web UI), which an agent cannot get by declaring, but which miss a person at a terminal; or only the landing's requester, the row's literal reading, which misses a person's own proposal under automatic landing and a reviewer's accept.
2. **The declared actor under a harness.** *Recommended*: `reef land`, `reef propose` and `reef proposal` declare `agent` when the environment names a harness (R3.44's table) and no `--actor` or agent name is given, and MCP's `propose_change` and `land_change` always declare `agent`; comments keep their default (a follow-up). Alternatives: no change, so every harness agent without `REEF_AGENT` ranks as a person (the spike); every CLI command, comments included, which changes R3.12's and R3.33's routing in this ticket; or require `REEF_AGENT` in each harness package, which names harnesses one by one.
3. **The number and the rule syntax.** *Recommended*: `[priority] human = 100` and `[[priority.rule]]` with `paths`, `except`, a change condition `when` and `add`, every matching rule adding, clamped to ±1,000; an erroring rule adds nothing; who waits is not a CEL variable. Alternatives: the first matching rule sets the priority, as `[[conflicts.rule]]` does (simpler to read, but a "docs last" rule would also put a person's docs change last); or named classes (`urgent`, `normal`, `low`) with no numbers.
4. **Starvation and preemption.** *Recommended*: a point a minute of age, up to 1,000; a testing batch is never cancelled; a batch led by a person's change skips `batch_wait`. Alternatives: strict priority with no aging (agents can wait for ever behind a busy person or a strong rule); a fairness slot (every fourth batch led by the oldest landing); or cancelling and re-forming a testing batch when a person's change arrives (faster for the person, wasted executor work for everyone).
5. **Where it is computed.** *Recommended*: with each judgment the change already gets (the gate, formation, the automatic dry run), stored on the landing row and the status; the queue orders by the stored value plus age; a person's later request raises a queued change at once. Alternative: judge every queued change again at each formation for an exact priority (one more judgment per queued change per batch).
6. **What priority reaches.** *Recommended*: the candidate order and the destination served next, the chain order, batch and proposal job priorities (4,000 + 2 × effective + stage, replacing 1,000 and 500), the automatic pass order, and raising a proposal's open jobs while a person waits. Alternative: the landing queue only, leaving R3.45's two constants: a clean S, but a person's checks still wait behind every agent's jobs.
7. **The surface.** *Recommended*: `priority`, `waiting` and `priority_rules` on `Landing`, `priority` and `waiting` on `AutomaticStatus`, a `WaitingReason` enum, a line in `reef landing show` and `reef proposal show`; no RPC, MCP tool or brief JSON change. Alternatives: no API change (the order is visible only in which change lands first); or also a queue order on `ListLandings`, as `ListJobs` has, for R3.34 now.
