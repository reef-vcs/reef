# R3.43 Verified human presence for sign-off keys

Phase 3 · Size L, at its top end (the row said M; #252, the `localhost` origin, the web listener's first WRITE path, pinning in policy and the CLI's verified sign-off are folded in) · Depends on: R3.03 (session keys, the certificate, `presence`), R2.18 (the web UI and its loopback listener), and builds on R3.07 (`presence` in attestor sets, `[[signoff]]` and `[owners]`), R3.42 (a second issuer kind beside the daemon's, the precedent for evidence carried in a certificate) · Unblocks: R3.31 (the proposal view signs with these keys and adds its decline, comment and land rows to this ticket's allowlist), R3.33 and R3.40 (sign-offs from the inbox and the phone), #222 (a verifier can tell a person from an agent holding the key) · Closes #252

## Context

#222 asks: "How do we know a human signed, and not an agent holding the key?" R3.03 answered that on one uid Reef cannot know it from a key alone, since anything the user can do on the socket, an agent running as the user can do, and it left two seams: a `presence` field in every session-key certificate (only `none` is issued), and this row. R3.03's brief: "How a key gets bound to a human: by the person identity it is certified for, and, after R3.43, by a user-verified passkey assertion. The passkey is registered to that identity, and it signs over the session key's id at issuance. The assertion is kept in the certificate so that any verifier, a store included, can check it again. R3.43 makes a browser tab ... hold a non-extractable key for a few minutes, certified only after such an assertion, and gives the web listener its first WRITE path for that one purpose."

A passkey (WebAuthn with the user-verified flag) needs the person: a touch and a fingerprint, a face or a PIN for every assertion, on an authenticator the agent cannot drive. That is the one thing on this machine an agent running as the user cannot do on its own. Policy already asks for it (`presence = "user_verified"` parses in attestor sets, `[[signoff]]` and `[owners]`; `docs/policy.md:130`: "matches nothing until R3.43").

On 2026-11-19 the user chose this ticket before R3.31's proposal view: the view's Accept must sign with a key a person was present for, never a `presence: none` key, so the web listener's write path is built here, once, around presence. The user also moved #252 (the bundle budget) here as the first commit, because this ticket ships the first new web page.

**The certificate and issuance.**

- `Presence` (`reef-evidence/src/session.rs:118`) has one value, `none`; an unknown value makes a certificate `INVALID` for its reader (`binding_of`, `:845`), and a test asserts `Presence::parse("user_verified") == None` (`:998`). Unknown predicate fields are ignored (`SessionKeyPredicate.unknown`, `:273`). So a certificate that says `user_verified` fails closed on a pre-R3.43 reader, and evidence for it must sit beside `presence`, never replace it.
- `certify` (`:447`) builds the payload (compact serde JSON in field order, not RFC 8785), parses it back so the authority never signs what a reader refuses, and signs it whole: the authority signs every predicate field. Certificates are at most 64 KiB and 32 levels deep.
- The proof of possession (`:652`) is `PAE("application/vnd.reef-vcs.session-key-proof", "reef-session-key-proof/v1\n{authority}\n{key id}\n{identity}\n{actor}\n{session}\n")`. A key id is the SHA-256 of the key's DER SPKI; keys are ed25519 only (ADR 0055).
- `Identities::issue` (`reef-daemon/src/identity/issue.rs:315`) checks the proof, the channel's rules (`check_rules`, `:159`: `human_over_remote`, `human_for_ci`), the session, freshness (a key already certified or used is `SESSION_KEY_EXISTS`), then certifies and inserts in one transaction under a per-identity limit. `presence` is the constant `Presence::None` at `:455` and `:501`.
- `channel_of` (`service/identity.rs:160`) returns `Channel::Socket` for any request without the remote gate's caller, so a web request looks like the socket to every handler. Only the web gate's READ-only step 8 (`web/gate.rs:222`) keeps a browser from getting `human` keys with `presence: none` today.
- Reads verify every certificate again (`identity/read.rs:152`); `presence_message` (`:333`) and the client's `session_presence_name` (`reef-client/src/json.rs:5063`) are exhaustive matches. The CLI prints "(not verified)" whatever the presence (`cli/identity.rs:889`, `cli/evidence.rs:1227`).

### The data shape

- **A passkey** belongs to one person identity: `pk_<16 hex>`, the credential id, its public key as DER SPKI with its COSE algorithm (`-7`, `-8` or `-257`; others refused at registration), its **fingerprint** (SHA-256 of the DER SPKI, lowercase hex, as Reef's key ids are), the RP ID (`localhost`), a label the person types, the authenticator's AAGUID when it gives one, the last sign count, when and through which web session it was added, when it was last used, and when and why it was removed. Table `passkeys` (schema 26), machine-wide like `identities`.
- **An approval** is a person's verified approval of **one sign-off**: `apr_<16 hex>`, the requester (the CLI over the socket, or a web session), the identity, the session key's public key and its proof of possession, the in-toto statement it will sign (its bytes, parsed by the daemon: kind, result, target, tree), the revision's commit and change (the daemon checks that the statement's subject is that commit's tree), the requester's agent and workspace when given, created and expiry (2 minutes), and its state: `pending`, `approved` (with the issued certificate), `declined`, `expired`. In memory only: an approval lives two minutes, and a restart drops pending ones (the CLI then says so). The certificate it produces is a `session_keys` row like any other.
- **Presence evidence** in a certificate: when `presence` is `user_verified`, the predicate carries `presenceEvidence`:

  ```json
  "presence": "user_verified",
  "presenceEvidence": {
    "type": "webauthn",
    "passkey": "<fingerprint>",
    "credentialId": "<base64url>",
    "publicKey": "<base64 DER SPKI>",
    "algorithm": -7,
    "rpId": "localhost",
    "approves": { "statement": "<SHA-256 of the statement payload, hex>", "change": "<change id>" },
    "authenticatorData": "<base64>",
    "clientDataJSON": "<base64>",
    "signature": "<base64>"
  }
  ```

  Required exactly when `presence` is `user_verified`, refused otherwise. The authority's signature over the predicate is its statement that the passkey belongs to the certificate's identity; the fingerprint is what a policy pins.
- **The binding (decision 2).** The WebAuthn challenge is derived, so any verifier recomputes it from the certificate alone and the daemon stores none:

  `challenge = SHA-256(PAE("application/vnd.reef-vcs.presence-approval", "reef-presence-approval/v1\n{authority}\n{key id}\n{identity}\nhuman\n{session}\n{statement sha256}\n{change}\n"))`

  So the touch approves this key, this statement (which names the kind, the result, the target and the tree) and this change, and nothing else. It is checked three times:
  1. **At approval** (the daemon): the assertion verifies over the derived challenge for the approval's key, statement and change.
  2. **In the certificate** (any verifier, `check_certificate`): the same derivation from the predicate's fields.
  3. **At `AddEvidence` and on every read**: a `user_verified` key counts only for the evidence object whose payload's SHA-256 is `approves.statement`, linked to the change `approves.change`. `AddEvidence` refuses any other envelope signed by such a key (`PRESENCE_STATEMENT_MISMATCH`) and a second evidence object from it (`SESSION_KEY_SPENT`: one key, one sign-off). A read that finds a mismatch anyway (a database edited behind the daemon) reports the object's presence as `none`.
  The key's certificate lives 2 minutes; the key is generated for the one sign-off and dropped after it.
- **Verification** (`reef_evidence::webauthn`, pure, in `check_certificate` after the authority's signature and in `certify` before it): `clientDataJSON` parses with `type` `webauthn.get`, the derived `challenge`, and an `origin` whose host is `rpId`; `authenticatorData` starts with SHA-256(`rpId`) and has user presence and **user verification** set; the signature verifies over `authenticatorData ‖ SHA-256(clientDataJSON)` with `publicKey` (ring, by `algorithm`); `passkey` is the SHA-256 of `publicKey`. The daemon also checks, at approval only, what a stateless reader cannot: the passkey is registered to the identity and not removed, the origin's port is the listener's, and the sign count went up (or both are zero, as synced passkeys report).

### Passkeys count only when the policy pins them (decision 1)

**Registration**, as briefed before the answer:

- An identity's **first** passkey is added from the Passkeys page of any `reef ui` session (WebAuthn registration with `userVerification: "required"`, attestation `none`); the daemon issues the registration challenge (32 random bytes, single use, 5 minutes, tied to the web session).
- **Every later add, and every removal from the page, needs a user-verified assertion by one of that identity's existing passkeys** over the change (`SHA-256(PAE("application/vnd.reef-vcs.passkey-change", "add\n{registration challenge}\n" | "remove\n{pk id}\n"))`).
- **Reset** (`reef identity passkey reset IDENTITY`, socket only, ADMIN) removes all of an identity's passkeys and revokes every unexpired key they certified; recorded and printed loudly.
- Registration and removal are refused over the remote listener (R3.40) and over the socket except reset: a ceremony needs a browser.
- Every add, removal and reset is a row with its time and web session, shown on the Passkeys page and by `reef identity passkey list`, and logged.

**Pinning** (the answer): a `user_verified` key satisfies policy only when its passkey is one **the destination's policy names** for that key's identity. The policy file (R3.07's `reef-policy.toml`, read from the destination's tree like every other table) gains:

```toml
[passkeys]                                   # pinned passkeys, by identity name or id
alice = ["3c9e0d…64 hex…"]                   # fingerprints: SHA-256 of each passkey's public key
```

- Wherever policy asks for `presence = "user_verified"` (attestor sets, `[[signoff]]`, `[owners]`, and `builtin:resolution`'s sign-off), a key meets it only if its certificate's presence is `user_verified` **and** its `presenceEvidence.passkey` is listed under its identity (by name or id) in `[passkeys]`. Otherwise its presence counts as `none`. One function computes that effective presence; both comparisons in `eval.rs` (`declared_match`, `is_signoff`) call it.
- An identity with no `[passkeys]` entry has no verified presence in that repository, whatever it registered. A policy that asks for `user_verified` with no pins is reported by `reef policy check` ("no passkey pinned for alice: no sign-off of hers will meet presence user_verified").
- The policy input's key gains `passkey` (the fingerprint, empty for none), so CEL can read it too.
- Changing `[passkeys]` is a change to the policy file, which `[owners]` must sign off: an agent cannot pin its own passkey without the owners.
- **One step to pin**: the Passkeys page shows each passkey's fingerprint with **Copy policy snippet** (`[passkeys]` and the identity's line with every live passkey of hers), and `reef identity passkey list` prints the same line.

**Why trust on first use alone was rejected** (ADR 0085 records it): an agent running as the user can mint a `reef ui` session and drive a headless browser with a virtual authenticator, exactly as this ticket's e2e does, and register its own software "passkey" before the person ever does; every later guard then protects the agent's passkey. Pinning moves the trust from the daemon's database, which a same-uid process can write, to the destination's reviewed policy. And because the certificate carries the assertion and the passkey's public key, a forged `user_verified` certificate (signed with a stolen `authority.pem`, S-58) cannot name a pinned fingerprint without the matching private key, which lives on the person's authenticator: for policy, the authority key alone is no longer enough.

### One touch per sign-off (decision 2)

Every sign-off is its own approval: a fresh key, one assertion whose challenge binds the key, the statement and the change (above), a 2-minute certificate, used once. Reviewing ten changes is ten touches; each touch approves exactly what the approval page or the Sign off button showed.

### Sign off on the change detail panel (decision 3)

The smartlog's selected change gains **Sign off**: kind `signoff`, result `pass`, on the change's tree as the page shows it. The page builds the statement and a WebCrypto Ed25519 key (non-extractable private half), requests an approval for it (`RequestApproval`, through the web), resolves it with the passkey assertion (`ResolveApproval`), signs the statement with the issued certificate and adds it (`AddEvidence`). The panel then lists the sign-off with `user_verified` and whether the repository's policy pins the passkey. It is disabled, with the reason, when the identity has no passkey (a link to the Passkeys page). R3.31's Accept is this action plus its landing request.

### The CLI's verified sign-off (decision 4)

`reef evidence add --kind signoff --result pass --actor human --verified [-r REV]` (`--verified` needs `--actor human`; any kind, result and target the command already takes):

1. The CLI builds the statement over the revision's tree and a fresh key in process, and calls `RequestApproval` over the socket with the statement, the revision, the key and its proof.
2. It opens the web UI's approval page for that approval, `/approve/apr_…`, through a new web session, the way `reef ui` opens the app (the launch file; `--print-url` prints the URL instead of opening, for SSH). It prints, on stderr, "Waiting for your approval in the browser: sign off <change> (<description>) as arsood, expires in 2 minutes".
3. It waits with `GetApproval { wait }` (a long poll, up to the expiry), bounded by `--timeout` (default 2 minutes). Approved: it signs with the certificate and adds the evidence, which carries `presence user_verified`. Declined, expired or timed out: exit 5 (`Conflict`) with the reason, a `hint` and no `next` that approves (there is none).

ADR 0025 holds: the CLI asks nothing on its terminal and runs no login; the approval happens in the browser, outside the command, like `reef land` waiting for evidence. The agent guide does not mention `--verified` (its byte budget is untouched): it is a person's command.

**The approval page** shows, before the button: the identity it signs as; the kind, result and target; the change with its description and author, and the tree; who asked (the CLI's `reef-agent` name and workspace, or "this browser"); the time left. **Approve** runs the assertion over the derived challenge; **Decline** ends it. The page approves nothing on load, has no "remember" option, and has no other path to the approval than the touch.

**What stops an agent approving its own request.** An agent can run `--verified`, and it can open the approval page in its own headless browser. It cannot produce a user-verified assertion from the person's passkey (that takes the person's finger, face or PIN on the authenticator); an assertion from a software authenticator it registered does verify, but that passkey is not pinned, so the sign-off it yields never meets the policy. **The residual risk** is the person: an agent can start an approval at a moment the person expects one and hope for a touch without reading. Mitigated by the page naming the exact sign-off and who asked, by one touch approving one sign-off on one tree (never a key that signs more), by the 2-minute expiry, and by every approval being listed with its requester. The platform's own passkey prompt shows only "localhost", so the page is where the person reads what they approve.

### The web listener as `localhost` (decided here)

- **The printed URL, the Host check and the gate's origin use `localhost:<port>`** (and only it: a `Host` of `127.0.0.1:<port>` is now 421 too, so the app has one origin and one localStorage scope). DNS rebinding is unaffected: a rebinding page's `Host` is its own name, and browsers resolve `localhost` to loopback themselves.
- **The listener binds both loopback families on one port**, `127.0.0.1:<p>` and `[::1]:<p>`: with port 0, it takes the IPv4 port and binds IPv6 on it, retrying a new port on `EADDRINUSE`; with a fixed port, either taken is a start error; IPv6 is skipped only where the host has no IPv6 loopback (nobody can bind it then). Without this, another local user, or an agent, holding `[::1]:<p>` serves a page whose origin is exactly `http://localhost:<p>` to a browser that tries `::1` first, and gets genuine assertions for Reef's RP ID (S-251).
- `[ui] listen` stays an IP literal; it must be `127.0.0.1:<p>` or `[::1]:<p>` (either means both). Another loopback address (`127.0.0.2`), which `localhost` does not reach, is refused at load with the reason.
- The registration's `user.name` and `displayName` say "Reef: <identity>", since a passkey picker lists every `localhost` app's credentials together.
- The daemon checks the exact origin (`http://localhost:<the listener's port>`) at registration and issuance, because the RP ID `localhost` is shared by every local web server: a dev server on another port can ask for an assertion, never one the daemon accepts.
- **The Vite dev server cannot run a ceremony** (its origin is another port, signed into `clientDataJSON`). The passkey flows are previewed on a scratch daemon serving `just web-build`'s assets; every other part of the UI previews through Vite as before. No extra-origin setting is added.
- ADR 0047 decisions 2, 4, 5 and 6 and S-30, S-31 are amended. localStorage at the old origin (`reef.devMode`) resets once.


### The web listener's WRITE allowlist (decided here)

Step 8 of the gate passes READ methods and the rows of a table, `web/rules.rs`, in `remote/rules.rs`'s shape; every other WRITE and every ADMIN method is refused as today (`WEB_ACCESS_DENIED`, its hint naming the allowlist). A test walks every v1 method.

| Method | Rule |
| --- | --- |
| `IdentityService.StartPasskeyRegistration` | a person identity; empty is the default person |
| `IdentityService.RegisterPasskey` | the challenge this web session started; an existing passkey's assertion when the identity has one |
| `IdentityService.RemovePasskey` | an assertion by one of the identity's passkeys |
| `IdentityService.RequestApproval` | a person identity; the statement's subject is the revision's tree |
| `IdentityService.ResolveApproval` | any pending approval (the CLI's or this browser's); approve needs a valid assertion by a passkey of the approval's identity |
| `EvidenceService.AddEvidence` | signed by a `user_verified` key, for its approved statement and change |

`IssueSessionKey` stays off the web listener: a browser gets keys only through an approval. On the socket, `IssueSessionKey` is unchanged (`presence: none`), and `RequestApproval` and `GetApproval` serve the CLI; `ResolveApproval` with approve is refused there (`APPROVAL_NEEDS_WEB`), so no socket client approves anything. Over the remote listener the approval and passkey writes are refused (`PASSKEY_OVER_REMOTE`; R3.40).

**The web caller.** The gate inserts `web::Caller { session }` (the first 16 hex digits of the session token's digest, never the token), as the remote gate inserts its caller. `channel_of` returns `Channel::Web`, stored as `sessions.channel` `web`. Approvals issue through it: actor `human`, a person identity, `presence: user_verified`, never renewed.

**Audit (threat-model requirement 5).** `web_session` on `session_keys`, `passkeys` and `evidence` rows, typed in the API (`WebCaller`); the session key row also names its passkey and approval; a daemon log line per web write and per approval (requested, approved, declined, expired). None of these writes records a jj operation.

### Threat model rows

- **S-250 An agent's own passkey.** A same-uid agent can register a software authenticator (trust on first use) through a `reef ui` session and a headless browser. Fixed for policy: only passkeys the destination's policy pins under the identity give `user_verified`, and the policy file needs the owners' sign-off to change. Recorded: every add is listed with its time and web session.
- **S-251 `::1` squatting at `localhost`.** A process on the other loopback family at the listener's port would serve the daemon's exact origin. Fixed: both families bound on one port, or the start fails.
- **S-252 A shared RP ID.** Every local web server can ask for `localhost` assertions. Fixed: the daemon checks the exact origin, the type and the derived challenge; a dev server's assertion is refused.
- **S-253 The web listener's first writes, and a leaked session URL.** Fixed: an allowlist table and its per-method rules; socket-only paths (publish with git credentials, fetch, `PushLanded`, workspace creation) stay refused, walked by a test over every method. A leaked URL can add a first passkey to an identity with none and approve pending approvals with it, never one a policy pins without the owners.
- **S-254 An agent-started approval.** `--verified` or `RequestApproval` puts a page in front of the person. Bounded: the page names the identity, the change, the tree, the kind, the result and who asked; one touch approves one sign-off on one tree; 2-minute expiry; no approval without an assertion; listed and logged. Residual, documented: a person who touches without reading.
- **S-255 Forging `user_verified` with the authority key** (S-58). Fixed for policy: a pinned fingerprint names the passkey's public key, and the certificate's assertion must verify with it, so forging needs the person's authenticator, not only `authority.pem`. A reader that does not pin (`reef evidence show` without a policy) still trusts the authority, and says "not pinned".
- **S-256 Replay and reuse.** A presence key is fresh, certified for 2 minutes, bound by its challenge to one statement and one change, and spent by its first evidence object; replaying an assertion yields at most the same certificate for the same key.
- S-59, S-92, S-107, S-159 and S-239 lose their "after R3.43" and say what a pinned `user_verified` now proves.

## Choices this brief made, and why

- **A derived challenge**, so a store or any verifier checks the assertion with nothing but the certificate.
- **The passkey's public key and fingerprint inside the certificate**, so pinning in policy checks the person's authenticator, not the daemon's word.
- **Approvals as the only way a browser gets a key**, so the web listener never issues a key that is not bound to one sign-off.
- **DER SPKI from the browser, not CBOR**, so no new parser and no new dependency: `getPublicKey()` gives it, and attestation `none` carries nothing else to check.
- **`localhost` only, both families**, because a second accepted origin is a second localStorage scope where passkeys do not work, and one family leaves the other to a squatter.
