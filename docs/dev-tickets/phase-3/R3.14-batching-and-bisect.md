# R3.14 Batching and bisect

Phase 3 · Size L · Depends on: R3.13 (the gate, the queue and its worker, `land_batch`, `judge`, `Repo::land`, landing records and pins), R3.06 (an executor that runs jobs by revision), and builds on R3.05 (`Executor::submit`, the job table, dedupe by spec, `cancel`), R3.07 (`[[require]]`, `RuleKind::Require`, `missing` and `failed` needs, the policy read from the destination) and R3.09 (lifecycle rows, the lifecycle lock, `dequeue`) · Unblocks: R3.15, R3.18, R3.20, R3.21, R3.34, R4.11

## Context

The design's Landing section: "A rebase produces a new tree hash, so evidence computed on the submitted tree proves nothing about the rebased one, and disjoint hunks are no guarantee of semantic compatibility: one agent can change a signature while another adds a caller. The landing service is therefore a merge queue. It batches rebased changes, asks the trusted executor to run the required checks on the batch head, lands the batch if the checks pass, and bisects the batch to find the culprit if they fail. A stack lands as a prefix: if a later change fails, the earlier ones still land." And CI load: "The landing queue tests a batch head rather than each proposal. Evidence is keyed by tree hash, so an identical tree is never tested twice." Scaling: "Landing is serialized per repository. One head, one queue. Throughput is batch size times batch rate."

R3.13 built the queue with a batch of one and judges only the submitted tree: a clean rebase lands untested (S-120, "documented and partly fixed ... R3.14 tests the batch head"). Every earlier ticket left something here:

- **R3.05**: "R3.13 and R3.14 call `Executor::submit` in process and read coverage."
- **R3.06**: "R3.14 ... treats `FAILED` as infrastructure"; jobs are submitted by revision so every job has a commit an executor can read through `FileService`.
- **R3.07**: the `batch` input is reserved for R3.14 (`docs/policy.md`, "What later tickets add").
- **R3.13**: "R3.14 widens `land_batch` to a batch with an executor run on the head (the `batch` input), lands a prefix and bisects, and treats `FAILED` jobs as infrastructure." `docs/landing.md` and the `fast-forward-only` recipe say "until R3.14".

So this ticket builds:

1. **Batches**: the worker takes several queued changes for one destination, rebases them as a chain onto its head, and records the batch.
2. **The tested tree**: when a member's required evidence is not already on the chain's head tree, a trial commit carrying that tree is written and executor jobs are submitted for exactly the missing pairs.
3. **Landing on pass**: every member whose `[[require]]` rules pass on the tested tree lands, in one operation that moves the destination.
4. **Bisect on failure**: binary search over the chain's prefixes finds the first change whose inclusion fails; the prefix before it lands, the culprit returns to its owner, the rest wait for the next batch.
5. **Lifecycle of a batch**: cancellation when the destination moves or a member leaves, infrastructure failures, restart.
6. **The surface**: the policy's `[landing]` table and `batch` input, `LandingBatch`, `GetBatch`, `ListBatches`, `reef landing batches|batch`, records, and the documents.

### What a batch is

A **batch** is one attempt to land several queued changes for one destination together: `bat_` and 16 hex digits. Its **members** are queued landings (R3.13's rows, one per change), in queue order. Its **base** is the destination's head `D` when it formed. Its **chain** is the members rebased one on another onto `D`: member 1 onto `D`, member *k* onto member *k − 1*'s result, giving trees `T1 … Tn`, where `Tk` is `D` with members 1 to *k* applied. `Tn` is the **head tree**. A landing with one member is a batch of one: there is no other path.

A batch tests **prefixes**: prefix *k* is `Tk`. A **trial** is one tested prefix: its tree, the commit that carries it (below), the jobs requested for it, and its result: `passed`, `failed`, `unavailable` or `cancelled`.

| Batch state | Means |
| --- | --- |
| `testing` | The head tree's checks are requested or running. |
| `bisecting` | The head failed; a smaller prefix is being tested. |
| `finished` | Ended; `outcome` says how. |

| Outcome | Means |
| --- | --- |
| `landed` | Every member landed. |
| `split` | A prefix landed (possibly empty), the culprit was dequeued with reason `checks`, the members after it were requeued. |
| `unavailable` | No verdict could be had; the tested members were dequeued with reason `unavailable`. |
| `reformed` | The destination moved or a member left; the members still queued form the next batch. |
| `interrupted` | The daemon stopped; the next batch re-forms from the queue. |
| `busy` | The destination moved under three re-formations in a row; the members were dequeued with reason `busy`. |

Lifecycle states do not change: every member stays `QUEUED` throughout (R3.09), and `landed`, `dequeued` or requeued is each member's own. `batched`, `testing` and `bisecting` are the batch's, for R3.34.

### Where required evidence must hold (decisions 2 and 3)

The policy's new `[landing]` table says where a member's `[[require]]` evidence must hold:

- **`checks = "batch"`** (the default): the gate (R3.13) is unchanged, judging the submitted tree with every rule. At landing, each member is judged twice: the **submitted evaluation** (R3.13's re-judgment of the queued commit at the destination's head, every rule) must be `ALLOW`, and the **tested evaluation** (the same policy over the same change, with `evidence` read from the tested tree instead of the submitted one, and `batch` filled) must satisfy or not apply every `[[require]]` rule; its other rules are not consulted, since sign-offs and the rest are about the submitted tree.
- **`checks = "proposal"`**: only the submitted evaluation, as R3.13 lands today; the chain still lands in one operation, and nothing is requested from an executor. For repositories whose trusted evidence does not come through executor jobs (a CI system that adds evidence with its own `ci` key).

In the tested evaluation, member *k* is judged with the evidence on the tree of the trial that lands it: `Tn` when the head passes, `Tp` when bisection lands prefix *p* ≥ *k*. **The tested tree's evidence counts for every member at or below it** (decision 3). That is the merge queue's assumption: `Tk` for *k* < *p* was not itself tested, and the record says which tree was (`tested_tree_id` on each landed change). A repository that wants every landed tree to be exactly a tested one sets `batch_max = 1`. Evidence stays bound to the tree it attests: nothing is copied or re-signed, and an object on `Tn` names `Tn`.

A member whose required evidence is already on the tested tree needs no job: a fast-forward batch of one has `T1` equal to the submitted tree, which passed the gate, and lands at once, as in R3.13. Evidence is keyed by tree, so a tree tested before (a re-formed batch, a restart, two batches converging on one tree) is never tested twice.

### Forming a batch (decision 4)

`[landing]` in `reef-policy.toml` at the destination's head (additive to format 1; the static check learns it):

```toml
[landing]
checks = "batch"          # batch | proposal; default batch
batch_max = 8             # 1 to 32; default 8
batch_wait = "0s"         # 0s to 10m; default 0s
alone = ["migrations/**"] # path patterns whose changes land in a batch of one; default none
```

R3.45 adds `automatic` to the same table; R3.20's budgets and R3.21's priority rules are tables of their own.

The worker forms a batch when it has no open one:

1. **Candidates**: the open landings for the destination of the oldest queued one, oldest enqueue first (R3.21 replaces the order), at most `batch_max`. A change that touches a policy file (`reef-policy.toml`, `reef-checks.toml`) or an `alone` path is a batch of its own: as the first candidate it is the whole batch, and elsewhere it ends the candidate list before it. A policy-file change must be judged before anything after it is (later members are judged by the policy it lands), and a `reef-checks.toml` change changes what the executor runs for every member below the head (S-146).
2. **Waiting for more**: when fewer than `batch_max` candidates are queued and the oldest was queued less than `batch_wait` ago, the worker waits until then, or until the batch fills.
3. **Judging**: under the create lock shared, each candidate is judged as R3.13 judges (the preview onto `D`, the submitted evaluation at `D`). A blocked candidate is dequeued with R3.13's reason, as today. The policy and `[landing]` are read once, at `D`.
4. **The chain**: on the repository thread, the passing candidates are rebased in memory one on another onto `D` (`preview_chain`). A candidate that conflicts with `D` alone was already dequeued `conflicted` in step 3; one that conflicts only with an earlier member is **left out** (it stays queued and leads the next batch, judged then against what landed). Each member's `landing` input is from the chain: `destination_commit` is `D`, `rebased` is true unless it is the first member and a fast-forward, and `overlap` is the paths it and the destination (since its parents) or an earlier member both changed.
5. **The record**: the batch row (`testing`) with its members, base and planned trees, and each member landing's `batch_id`. The lock is released: **no lock is held while checks run**.

One batch is in flight per repository; the worker stays one per repository, and destinations in one repository take turns. A member's parents must be on `D`, as in R3.13 (`unlanded_parents`); R3.10 lets a member's parents be earlier members.

### Testing a prefix: trials and jobs

To test prefix *k* (the head first, then bisect probes):

1. **Evaluate first.** The tested evaluation of members 1 to *k* over the evidence already on `Tk`. All satisfied: the trial passed, with no job. A `failed` need (the newest trusted verdict is `fail`): the trial failed, with no job.
2. **The trial commit.** Otherwise the missing pairs need an executor, which reads a commit (R3.06). A **trial commit** is a new change on `D` whose tree is `Tk`, author and committer the daemon, description `reef: batch bat_… prefix k of n onto main` with the members' change ids in the body, written in an operation of new kind `batch` (`reef: test batch bat_… on main`, attribute `reef.batch`) under the create lock shared. A visible trial commit with the same parent and tree from an open or interrupted batch is reused. Trial commits are visible in the log while their batch is open (decision 7); jobs read them by commit id, which still resolves after they are abandoned.
3. **Jobs.** The union, over members 1 to *k*, of their `[[require]]` rules' `missing` pairs on `Tk`, grouped into one job per kind with that kind's targets (a whole-check pair and targeted pairs of one kind are two jobs), since an executor claims only a job whose kinds are all its own. Each is `Executor::submit` by revision (`Tk`'s trial commit and change) with priority `BATCH_PRIORITY` (1,000; R3.21 replaces it), the executor's default wall time, a queue timeout of 15 minutes (`BATCH_QUEUE_TIMEOUT`), no requirements, and the batch's agent (`reef-landing`). An identical open job is reused by the executor's dedupe. At most 16 jobs per trial (the kinds a job may name), and the trial records their ids.
4. **Waiting.** The worker waits on a new `Executor::changed` notify (each `UpdateJob` that adds evidence, each completion, expiry and cancellation), on lifecycle transitions of the repository, and on a 5-second tick. On each wake, at most once a second, it re-checks the batch (below) and re-evaluates. **Fail fast**: the first `failed` need fails the trial, and the trial's other open jobs are cancelled ("the batch's tree failed").
5. **The result.** Every needed pair satisfied: `passed`. A `failed` need: `failed`, with the needs. Every job ended and a pair still missing (a job `FAILED`, `BUDGET_EXHAUSTED`, expired, or done with `error` or untrusted evidence only): infrastructure (decision 6).

### Landing on pass

When the head passes (or bisection ends):

1. Under the create lock shared: refresh, check the destination is still at `D` and each landing member still `QUEUED` at its queued commit (else re-form, below); judge each landing member's submitted evaluation again, since evidence may have been added to its tree (a block dequeues it with `policy` and re-forms).
2. Under the lifecycle lock, through `Manager::rewrite_held` with `Write::Land` widened to a list: pause, scan-lock and snapshot the workspaces on the members and their descendants (an amendment re-forms the batch, as R3.13's `amended`); then on the repository thread, rebase members 1 to *p* as a chain onto `D` (none for a fast-forward first member), **refuse unless each landed tree equals the planned `Tk`** (a merge is deterministic, so this fails only on a bug or a tampered plan: `failed`, nothing written), give every jj workspace whose working-copy commit is any landed commit a new empty change on it (R3.13 did this for the head only; a snapshot on a landed ancestor would rebase the destination's head past the gate), set the bookmark to member *p*'s landed commit, abandon the batch's trial commits, and commit one operation: kind `land`, `reef: land change <id> on main` for one member or `reef: land 3 changes on main (batch bat_…)` for several, `reef.lifecycle` with every member's `QUEUED → LANDED`, `reef.landing` (the landing id when one member) and `reef.batch`.
3. Commit the rows in one transaction: each member's transition, its landing `LANDED` with its landed and tested commits and trees, both evaluations, the pins (the submitted evaluation's, as R3.13, and the tested evaluation's satisfied `[[require]]` evidence), the batch `finished` with its outcome and operation.

### Bisect on failure (decision 5)

When the head fails, the batch is `bisecting`: a binary search over prefixes for the smallest failing one, with `lo = 0` (the base, assumed good) and `hi = n` (failed). While `hi − lo > 1`: test `mid = ⌊(lo + hi) / 2⌋`; passed sets `lo = mid`, failed sets `hi = mid`. At the end, member `hi` is the **culprit**: prefix `hi − 1` passed and adding it failed. At most `⌈log2 n⌉` probes, five for 32 members, each one trial.

Then, in order: land prefix `hi − 1` as above (nothing when `hi` is 1), each with the evidence of the trial that passed at `hi − 1` (`Thi−1`; when `hi − 1` is 0 nothing lands); dequeue the culprit with reason **`checks`** (R3.09's dequeue, its own operation), its landing finished `DEQUEUED` with the failing trial's tested evaluation (the failed needs and their evidence ids, so `reef land` prints which check failed on which tree); and leave members `hi + 1` to `n` queued (their landings' `batch_id` cleared, member result `requeued`), so they lead the next batch, rebased onto the new head without the culprit.

Prefix *k* is judged by the requirements of members 1 to *k* only: a check that only a later member requires does not run on an earlier prefix. The culprit is the change whose inclusion first fails some included member's requirements, which is what policy asks of each landing. A flaky failure can blame a change wrongly (S-144); the newest verdict wins on a tree (R3.07), so a re-landed change on the same tree with a passing rerun lands.

### Infrastructure (decision 6)

A trial with no failure and a pair still missing after its jobs ended is infrastructure, never the change's fault. A job that an executor ran and that ended `FAILED`, `BUDGET_EXHAUSTED`, expired with `ATTEMPTS` or `DEADLINE`, or completed with only `error` or untrusted objects for a pair, is submitted once more (`duplicate` false; the finished one does not dedupe). A job nobody claimed in `BATCH_QUEUE_TIMEOUT` (`QUEUE_TIMEOUT`), or a second infrastructure end, makes the trial `unavailable`: the members it tested are dequeued with reason **`unavailable`** ("no verdict on the batch's tree: job_… expired unclaimed after 15m"), each landing carrying the tested evaluation with its missing needs and rejected objects, and the batch finishes `unavailable`. Members not in that trial (above a bisect probe) are requeued. `reef land` again retries. The landing's message, and `reef land`'s error (`LANDING_DEQUEUED` with metadata `reason` `unavailable`), carry a `hint` that names the way out for a repository with no executor serving the required kinds: "No executor answered for kinds test, lint. Run one (`reef executor run`), or, if this repository's trusted evidence does not come through executor jobs, set `[landing] checks = \"proposal\"` in reef-policy.toml (a policy change, which needs the owners' sign-off)." Its `next` is `reef executor run` when no executor has claimed any job of the repository's in the last day (the job table says so), and `reef landing batch <id>` otherwise, to see which jobs ended how. `reef landing show` and `reef landing batch` print the same hint for such a landing or batch.

### Cancellation and re-forming (decision 8)

On every wake, and before each lock-holding step, the worker checks cheaply: the destination's head (a refresh on the repository thread) and the members' lifecycle rows. When the destination moved (a jj writer, an observed landing, a `git fetch` import), or a member is no longer `QUEUED` at its queued commit (withdrawn, declined, superseded, landed by hand), or its visible commit moved (amended): the batch's open jobs are cancelled ("the batch re-formed"), its trial commits are abandoned in an operation of kind `batch` (`reef: end batch bat_…`), the batch finishes `reformed`, an amended member is dequeued `amended` as R3.13 does, and the worker forms the next batch at once. Trees and evidence carry over by hash: a prefix unchanged by the move is the same tree, its evidence still counts, and an identical open job is reused by dedupe. A batch re-formed three times in a row because the destination moved finishes `busy` and dequeues its members with reason `busy` (R3.13's `MAX_ATTEMPTS`).

### Restart

At start (`landing::start`), every batch not `finished` finishes `interrupted`; the worker re-forms from the queue as above, reusing trial commits by parent and tree, open jobs by dedupe, and verdicts by evidence on the trees. A bisect replays from evidence without new jobs for the trees it already tested. A crash inside the land operation is R3.13's case, widened: the pending transitions are resolved at start by their ids, and an open landing whose change a `landing` transition landed is finished `LANDED` from it; its batch's row is finished from its members. Trial commits no open batch uses are abandoned by the next `batch` or `land` operation.

### What a policy sees: `batch`

The `batch` input (reserved by R3.07, learned by the static check): `{id, size, position, tree, commit}`: the batch, how many members, this member's position from 1, and the tested tree and trial commit (empty when none was needed). It is set in both of a member's evaluations at landing and empty at the gate and in `EvaluatePolicy` and `SimulatePolicy`. A free rule over it is judged at landing only; a rule that blocks there dequeues the member with `policy`. Use `[landing] alone` for "land by itself", not a rule over `batch.size`, so the batch is formed right instead of failing.

### The record

Migration `0015_batches.sql` (schema 15, renumbered at rebase):

```sql
CREATE TABLE landing_batches(repo_id TEXT NOT NULL, id TEXT NOT NULL,             -- bat_<16 hex>
             destination TEXT NOT NULL, base_commit TEXT NOT NULL,
             state TEXT NOT NULL,                        -- testing | bisecting | finished
             outcome TEXT,                               -- landed | split | unavailable | reformed | interrupted | busy
             size INTEGER NOT NULL, culprit_position INTEGER, landed_count INTEGER NOT NULL DEFAULT 0,
             checks TEXT NOT NULL,                       -- batch | proposal
             policy_commit TEXT, policy_sha256 TEXT,
             operation_id TEXT, operation_collected INTEGER NOT NULL DEFAULT 0,   -- the land
             message TEXT, created_at INTEGER NOT NULL, finished_at INTEGER,
             PRIMARY KEY (repo_id, id)) WITHOUT ROWID;
CREATE TABLE landing_batch_members(repo_id TEXT NOT NULL, batch_id TEXT NOT NULL, position INTEGER NOT NULL,
             landing_id TEXT NOT NULL, change_id TEXT NOT NULL, queued_commit TEXT NOT NULL,
             planned_tree TEXT NOT NULL,
             result TEXT,                                -- landed | culprit | requeued | dequeued | left | unavailable
             PRIMARY KEY (repo_id, batch_id, position)) WITHOUT ROWID;
CREATE TABLE landing_batch_trials(repo_id TEXT NOT NULL, batch_id TEXT NOT NULL, prefix INTEGER NOT NULL,
             tree TEXT NOT NULL, commit_id TEXT, operation_id TEXT, operation_collected INTEGER NOT NULL DEFAULT 0,
             result TEXT,                                -- passed | failed | unavailable | cancelled; NULL while open
             job_ids TEXT NOT NULL DEFAULT '[]',         -- JSON
             failed TEXT,                                -- JSON needs, at most 20, and the total
             attempts INTEGER NOT NULL DEFAULT 1,
             created_at INTEGER NOT NULL, finished_at INTEGER,
             PRIMARY KEY (repo_id, batch_id, prefix)) WITHOUT ROWID;
ALTER TABLE landings ADD COLUMN batch_id TEXT;
ALTER TABLE landing_changes ADD COLUMN tested_tree TEXT;
ALTER TABLE landing_changes ADD COLUMN tested_commit TEXT;
ALTER TABLE landing_changes ADD COLUMN tested_evaluation TEXT;   -- reef_policy::Evaluation as JSON
-- indexes: landing_batches by (repo_id, created_at DESC), (state) WHERE state != 'finished';
-- landing_batch_members by (repo_id, landing_id)
```

- Batches are written as they move (formation, each trial, each result, the end), never pending: the lifecycle rows and R3.13's landing rows stay the source of truth for what landed, and a batch row is reconciled from them at start.
- `repo forget` deletes the three tables; backups copy them; GC's id map covers `landing_batches.operation_id` and `landing_batch_trials.operation_id` and marks collected ones; GC never deletes batch rows.
- Pins: the tested evaluation's satisfied `[[require]]` evidence of a landed member joins R3.13's `landing_evidence` (and its evidence link to the change), so the head tree's evidence is kept with the submitted tree's.

## Implementation notes

- **Order**: reef-policy's table and input (2); reef-lib's chain, trials and widened land (1); the migration and store; the worker restructured around a batch with `checks = "proposal"` and no jobs (10, and R3.13's tests green); trials, jobs and waiting (3, 4, 6); bisect (5); infrastructure (7); re-forming and restart (8, 11); `alone` and windows (9); the API surface and GC (12); the CLI, schema and MCP (13); the web UI; the documents.
- **Locks**: the create lock shared for each step that reads for a judgment or writes (formation, a trial commit, the end of a batch, the landing), never across waiting; the lifecycle lock only around the land write and dequeues, as in R3.13.
- **Threads**: previews, trials and the land on the repository thread; evaluations on the blocking pool with a turn each (a batch of 32 takes up to 32 turns in sequence per evaluation round, so rounds are rate-limited to one a second); SQLite on the async side's blocking pool.
- **The in-test executor** claims through the same API an executor uses, with a `ci` identity's key, so the evidence is trusted by the test policy exactly as R3.06's would be.
- **Linux**: nothing is `cfg(target_os = "linux")`; CI covers it.
- **No new daemon configuration.** `BATCH_PRIORITY`, `BATCH_QUEUE_TIMEOUT`, the retry count, the probe bound and the tick are constants; the repository's settings are in its policy.

## Out of scope

- **Evidence transfer** from the submitted tree for cheap checks when hunks commute (R3.15): a per-kind exception to `checks = "batch"`, recorded per need.
- **The minimal check set** (R3.18): `request_pairs` asks for every missing pair.
- **Budgets** (R3.20): the batch's jobs report `usage`; nothing is capped.
- **Priority** (R3.21): queue order and `BATCH_PRIORITY` are constants.
- **The pipeline view** (R3.34): `ListBatches` and the `JOB` presence entries are its data.
- **Automatic landing and requesting evidence for proposals** (R3.45): it reuses `request_pairs`.
- **Stacks in a batch** (R3.10): a member whose parent is an earlier member.
- **Speculative batches**: testing the next batch on top of the one in flight, or several batches at once.
- **Pushing** (R3.17) and the store (R4.11).

## Risks

- **No executor, default `checks = "batch"`**: a rebased landing waits up to 15 minutes, then is `unavailable`. Mitigated by the hint, `reef policy init`'s explicit `[landing]`, the CHANGELOG's Upgrading note, and decision 2's alternative.
- **Trial commits in the log** may confuse agents reading `reef log` during a batch. Mitigated by their descriptions and their short life; decision 7 has the alternative.
- **Restructuring the worker** touches R3.13's landing path; its tests are the guard, run with `checks = "proposal"` where they rebase.
- **Field numbers** in `landing.proto` and `operations.proto` may collide with R3.27's or R3.12's at rebase; renumbered then.
- **tools/list** is at its budget; the `batch` kind costs a few bytes that must be found in descriptions.

## Choices this brief made, and why

- **Every landing is a batch**, so there is one path; a batch of one with nothing missing is R3.13's landing.
- **The gate is unchanged**, so a proposal must still pass with its own evidence before it costs a batch anything, and R3.13's structured refusals stand.
- **Only `[[require]]` rules are judged on the tested tree**, because sign-offs, limits, forbidden paths and free rules are about the change and its submitted tree, and carrying sign-offs across trees is R3.15's.
- **Jobs per kind**, because an executor claims only a job whose kinds are all its own.
- **Visible trial commits**, because GC rebuilds jj's index from operations' views and jobs need a commit an executor can read.
- **Re-forming rather than resuming**, because evidence by tree and job dedupe make a re-formed batch cost nothing for trees already tested, and there is then one path for moves, departures and restarts.
- **Policy-file changes alone**, because a later member must be judged, and checked, by what is in force.

## Departures from dev-phases.md

`dev-phases.md` and this directory's README were edited to match with this brief:

- **"Run the executor on the batch head"** requests only the `[[require]]` pairs missing on the tested tree, one job per kind, by revision on a visible trial commit; `[landing] checks = "proposal"` turns it off for repositories whose evidence does not come through jobs.
- **"Land on pass"** lands every member whose `[[require]]` rules pass on the tested tree, judged also on its submitted tree as R3.13 does; the tested tree's evidence counts for every member at or below it.
- **"Bisect on failure"** is a binary search over the chain's prefixes; the passing prefix lands, the culprit returns to its owner (`checks`), the rest are requeued; infrastructure failures are `unavailable`, not the change's fault.
- The row also gains the policy's `[landing]` table and `batch` input, re-forming on moves and restarts, `GetBatch`, `ListBatches` and `reef landing batches|batch`.

## Departures in the implementation

Found while building it (2026-11-09):

1. **`batch_wait` does not apply to a change that was in a batch before** (requeued behind a culprit, re-formed, or interrupted): it has waited already, and a requeued tail would otherwise wait again for a batch that will not fill.
2. **A waiting batch wakes on `Executor::changed` and a five-second tick**, not on lifecycle transitions: a withdrawal or an amend is seen at the next tick, when the members' rows are read again.
3. **Trials are keyed by the order tested** (`seq`) as well as their prefix, and a trial's `needs` (`BatchTrial.needs`, `needs_total`) holds the failed needs of a failed trial or the missing ones of an unavailable trial, rather than a `failed` list only.
4. **Formation judges each candidate with its own preview onto the destination**; the chain's `landing` input (overlap with earlier members) is what the landing's re-judgment and the tested evaluation see. A rule over `landing.overlap` that the chain fails dequeues that change with `policy` at landing, and the rest re-form.
5. **A `[[require]]` rule that errors with nothing missing counts as failed** on the tested tree, so it is bisected like a failure rather than treated as infrastructure.
6. **Restart reuse is by key, not by record**: the next batch finds a visible trial commit with the same parent and tree (`trial_commit_for`) and an open job by the executor's dedupe; interrupted batches' trial commits are abandoned by the next batch's end or landing.
7. **Every landing of a batch records the batch's new head as `destination_after`**, not its own landed commit (`LandedChange.landed_commit_id` has that).
8. **`reef land`'s advice** for `unavailable`: the hint names `[landing] checks = "proposal"` in `reef-policy.toml` and the owners' sign-off it needs, and `next` is `reef executor run` when the landing's message says no executor claimed a job of the repository in the last day, else `reef landing batch <id>`; for `checks`, `next` is `reef landing batch <id>` and the hint names the failed checks. A pending landing's message names its batch.
9. **Under `checks = "proposal"` a batch records no trials**, and its landings no tested tree.
10. **A batch's job names the trial commit's change** as its `change_id`; the members are in the trial commit's description.
11. **Formation that keeps finding the destination moving** (judgments against different heads, or a head other than the one whose `[landing]` table was read) retries up to twelve times, then waits for the next wake-up; it counts apart from the three re-formed batches that make `busy`, which a `Left` re-form resets.
13. **A landing refused before its operation is written** (review finding 1) dequeues the change the error names (amended, unlanded parents, conflicted, already on the destination, a tree other than the planned one) and re-forms; a batch of one is dequeued with R3.13's reason; otherwise every member lands in a batch of its own next (the worker's `solo` set), which finds the one that fails, rather than forming the same batch again.
14. **One queued change that cannot be judged** has the error noted on its landing and is skipped, so the rest of the queue still lands (as R3.13 went on to the next landing).
15. **An unavailable probe during bisect** lands the prefix that passed first, then returns only the members the probe added.
16. **Batch rows keep GC's work**: `write_batch` keeps an operation id GC mapped, or collected, since the batch read it, and writes nothing for a repository forgotten meanwhile; landing rows are read again before every write a batch makes after waiting.
17. **Interrupted batches' trial commits are swept for a week** after their interruption, by every batch end or landing; older ones stay until someone abandons them.
12. **Tests**: the daemon's cases are seven in `tests/batch.rs` (`batch_lands_on_pass` with the undo refusal and the operation's `batch_id`; `fast_forward_needs_no_job`; `bisect_finds_the_culprit`; `infrastructure`; `reforms_and_restart`; `withdrawn_member_reforms`; `alone_and_proposal_checks` with the RPCs' filters and `BATCH_NOT_FOUND`); fail-fast cancelling a second kind's job, `busy`, a crash inside the land operation, `batch_wait` and two destinations have no test of their own; GC's id map for batches runs in GC's existing step and has no test of its own; policy-file changes landing alone are tested in reef-policy (`the_landing_table`), since a policy change needs an owner's sign-off. ## Decisions for the user

Asked on 2026-11-09; the user accepted every recommendation below, and the brief's body follows them. To decision 2 the user added: the default stays `checks = "batch"`, and an `unavailable` dequeue's `hint` names setting `[landing] checks = "proposal"` in `reef-policy.toml` as the way out for a repository with no executor serving the required kinds, with a `next` where one makes sense.

**Group 1: scope**

1. **Size.** L, with everything above and nothing split off. *Recommended*: as stated. Alternatives: split bisect into a new row (R3.47, S): R3.14 tests the head and, on failure, dequeues the whole batch; or split the policy's `[landing]` table out and use constants until it lands.

**Group 2: what is tested, and what it proves**

2. **Where required evidence must hold.** `[landing] checks = "batch"` by default: the gate unchanged (the submitted tree, every rule), and at landing each member's `[[require]]` rules judged again on the tested tree's evidence; `checks = "proposal"` keeps R3.13's landing for repositories with no executor. *Recommended*: as stated (the design's merge queue; S-120 fixed by default). Alternatives: default `proposal`, with testing opt-in (no surprise for repositories without an executor, but a clean rebase lands untested unless asked); a third value, `"batch-only"`, where the gate does not require `[[require]]` evidence on the submitted tree (the design's "tests a batch head rather than each proposal", halving executor load, but a broken proposal then costs a bisect), here or in R3.15; or no knob, always testing.
3. **What a batch's evidence proves for each member.** The tested tree's evidence counts for every member at or below it (the merge queue's assumption); intermediate trees are untested and the record says which tree was; `batch_max = 1` for exactly-tested landings. *Recommended*: as stated. Alternative: test every prefix's tree in parallel (n trials per batch, every landed tree tested, n times the executor load).
4. **Forming batches.** Settings in the destination's policy (`[landing] batch_max` 8 by default, 1 to 32; `batch_wait` 0 s by default, up to 10 minutes; `alone` paths); changes to `reef-policy.toml` or `reef-checks.toml` always alone; one destination per batch, oldest first; a member conflicting only with an earlier member waits for the next batch; one batch in flight per repository. *Recommended*: as stated. Alternatives: the settings in the daemon's `reef.toml` (per machine, not reviewed with the policy); a smaller default (4) for cheaper bisects; speculative next batches (more throughput, much more state).

**Group 3: failure**

5. **Bisect.** Binary search over prefixes, at most ⌈log2 n⌉ probes, failing fast on the first trusted `fail`; the passing prefix lands in one operation at the end; the culprit is dequeued with reason `checks` and its failing evidence; the members after it are requeued at the front. *Recommended*: as stated. Alternatives: test each member alone on the destination in parallel (one round, n trials, blames only changes that fail alone, missing interactions); land each passing probe's prefix at once (earlier landings, more operations); re-test the culprit once before blaming it (one more probe, fewer flaky blames).
6. **Infrastructure.** A job that ran and gave no verdict is submitted once more; one nobody claims in 15 minutes, or a second failure, dequeues the tested members with reason `unavailable` (not the change's fault; `reef land` retries). *Recommended*: as stated. Alternatives: keep the members queued and pause the repository's queue, retrying with backoff until an executor answers (no owner action, but the queue stalls silently); the executor's one-hour queue timeout instead of 15 minutes.

**Group 4: mechanics**

7. **Trial commits.** One visible commit per tested tree, a new change on the destination's head, written by an operation of a new kind `batch` and abandoned when the batch ends; jobs run on it by revision. *Recommended*: as stated (GC rebuilds jj's index from operations' views, and an executor reads a commit). Alternatives: hidden commits (no log clutter, but GC must learn to keep them, and a rebuilt index loses them); a `FileService` read by tree so a job needs no commit (an API and executor change, and CI adapters that fetch still need a commit).
8. **Cancellation and recovery.** No lock while checks run; a moved destination or a departing member cancels the batch's open jobs and re-forms it (three destination moves in a row: `busy`); a restart finishes open batches `interrupted` and re-forms, reusing trial commits, open jobs (dedupe) and verdicts (evidence by tree). *Recommended*: as stated. Alternative: persist the bisect position and resume it exactly (more state and recovery code for a replay that evidence already makes cheap).

**Group 5: the surface**

9. **API, CLI, MCP.** `LandingBatch` with members and trials; `GetBatch` and `ListBatches` (READ) on `LandingService`, in `NOT_TOOLS`; reasons `CHECKS` and `UNAVAILABLE`; `Landing.batch_id`; the tested tree, commit and evaluation on `LandedChange`; `OPERATION_KIND_BATCH` and `Operation.batch_id`; the policy's `[landing]` table and `batch` input; `reef landing batches|batch` in `--help-all`; API revision 26, schema 15. *Recommended*: as stated. Alternatives: batches only as fields on landings, with no batch RPCs (R3.34 groups them itself); MCP tools for the two reads (about 900 bytes over `tools/list`'s budget).
