# R3.03 Session keys and operator identity

Phase 3 · Size L · Depends on: R3.01 (the format crate, `evidence_keys`, `Evidence.key_id`), R3.02 (GC's seventh step, schema 8, API revision 16) · Unblocks: R3.04, R3.06, R4.09, R4.10, and the two follow-up rows this brief adds, R3.42 (Sigstore keyless) and R3.43 (verified human presence)

## Context

R3.01 made the attestor a key: "The attestor is the key that signed the envelope, reported as `key_id`; R3.03 binds key ids to operator and CI identities" (R3.01, "No attestor field"). R3.01 left this ticket four jobs. It issues session keys that `reef-evidence` signs with unchanged. It adds verification material beside `public_key`, and identity storage beside `evidence_keys`. It answers "who is key K" in `Evidence`. And it keeps the ring-only rule, or changes it by ADR (R3.01, "What later tickets inherit"). R3.02 added nothing for this ticket. Its GC step is where expired session keys are swept.

The design states the model in one paragraph (Provenance): "The daemon, or the store for a human acting from a device with no daemon, issues session keys bound to a longer-lived operator or CI identity in the keyless Sigstore pattern, so provenance chains to a person or pipeline without long-lived agent secrets, and a session key can be revoked without touching anything else." Its durability table adds: "Session keys are short-lived and never backed up". And under Open ecosystem: "each repository's policy names the attestor identities it accepts. A solo developer trusts their own machine. A large project trusts its CI identity and nothing else."

This ticket builds four things, all local:

1. **Operator identities**: named, machine-wide records of a person or a CI pipeline, which the daemon's user creates and revokes.
2. **An issuing authority and a certificate format**: an ed25519 key held by the daemon signs a certificate. The certificate binds a session key to an identity, a declared actor (`human`, `agent` or `executor`), a session and a validity window. The format and its check live in `reef-evidence`, so R4.10's store issues and verifies the same thing.
3. **Session keys**: issued through the API. Each private key is generated in the process that will sign with it and never leaves it. Issuance needs a proof of possession. Keys are short-lived, renewed by issuing a new key in the same session, and revocable one at a time, by session, by identity, or by authority.
4. **Identity in every evidence read**: `Evidence` gains `identity`, which carries the bound identity, the actor, and whether the key was valid and unrevoked when the daemon first saw the evidence. As in R3.01, nothing in it says "trusted": R3.07 decides that.

Sigstore keyless becomes a follow-up row, R3.42. This ticket defines its seam: an issuer kind, and a verification path that takes another issuer's material. Verified human presence (passkeys) becomes another follow-up row, R3.43. Issue #222 asks how a verifier can know that a human, and not an agent holding the key, signed something. "Human sign-off" below gives this ticket's answer to that.

### What an operator identity is

An **operator identity** is the person or pipeline that a key ultimately answers to. There are two kinds:

| Kind | Who | Keys issued for it carry the actor | Issued through |
| --- | --- | --- | --- |
| `person` | A human operator: the user of this daemon, or someone who reaches it with a token | `human`, `agent` or `executor` | the socket, or the remote listener with a token linked to the identity |
| `ci` | A pipeline: a CI job that reaches the daemon through the remote listener | `executor` or `agent`, never `human` | **only** the remote listener, with a token linked to the identity |

- **Agents are not identities.** The design wants "provenance chains to a person or pipeline without long-lived agent secrets". An agent acts *for* an operator, in a session, and its label is recorded as a claim. An agent fleet needs no identity records, and revoking a person ends every agent session under that person.
- **The actor is declared, not proven.** The requester says what the key is for: `human` (the person signs directly, for example a sign-off), `agent` (an agent acting for the operator), or `executor` (an automated check runner, such as R3.06's). The authority records the declaration and enforces only the rules in the table above. In R3.03, the one property of a certificate that a verifier can rely on beyond the uid boundary is which **identity** it binds. That property is meaningful only when the key was issued through a linked remote token ("Who can get a key for what"). `presence` (below) is where a later ticket adds proof that a human was there.
- **Naming.** `[a-z0-9][a-z0-9._-]{0,62}`, the remote tokens' pattern. A name is unique among all identities, revoked ones included, and is **never reused**. A policy that names `alice` therefore cannot be satisfied by a new `alice` after the first is revoked. Each identity also has an id, `idn_<16 hex>`, random and never reused, which certificates carry beside the name. `display_name` (up to 128 bytes, no control characters) and `email` (a syntactic check only) are optional and for display. Reef verifies neither.
- **Machine-wide**, as `remote_tokens` and `evidence_keys` are: an operator works across repositories, and R3.07's per-repository policy chooses which identities count. `repo forget` does not touch identities.
- **Who creates one**: the daemon's user, through ADMIN RPCs, which are served only on the socket and never as MCP tools. A remote caller cannot create, link or revoke an identity.
- **The default identity.** At start, after migrations, a daemon whose `identities` table is empty creates one `person` identity. Its name is the OS login name, lowercased, with characters outside the pattern replaced by `-` and truncated to 63; it falls back to `operator` when that is empty or does not match. Its id is recorded in `meta` as `default_identity_id`, and the creation is logged. `[session_keys] default_identity` (a name) overrides it. Socket requests that name no identity use the default. So a solo developer gets keys bound to themselves with no setup: "A solo developer trusts their own machine." Question 6 asks whether to create it implicitly.

### The authority: the daemon's issuing key

- **One current authority key per daemon**: ed25519, generated at the first start after this ticket. Its private key is PKCS#8 at `<state>/identity/authority.pem`, `0600` in a `0700` directory, **not backed up**, exactly as the remote listener's key is (S-45). Its public key and key id (the SHA-256 of the SPKI, as for every Reef key) go in `identity_authorities`, which *is* backed up.
- **Why a stable key and not one per start.** Other parties will need to pin this machine's authority: R4.09's store, a teammate, or R3.07's policy ("A solo developer trusts their own machine"). A key that changed on every restart would make that impossible. `reef identity authority show` prints its key id and PEM public key.
- **At every start** the daemon loads the file and checks that its public key is the current row's. If the file is missing (a restore, or a new machine), unreadable, or does not match, the daemon marks the current row `retired_at = now`, generates a new key and row, and logs a warning that names both key ids. Certificates the old authority issued still verify, since its public key is kept. Only new issuance moves to the new authority. A bad mode on the file (group or others may read it) is fixed to `0600` with a warning, as the state directory's mode is.
- **Rotation and compromise.** `RotateAuthority` (ADMIN) retires the current key and makes a new one. With `revoke`, it also sets `invalid_from` on the old key (default: its `created_at`, meaning everything it ever issued), so every certificate it issued reads `REVOKED` from then on.
- **The one-uid limit, stated.** A same-uid agent can read `authority.pem`, and it can call `IssueSessionKey` on the socket anyway. Against the daemon's own uid, a certificate therefore proves only that this daemon's user, or something running as that user, asked for it. This is ADR 0027, not a new weakness. What an identity does distinguish is other local users (modes), remote callers (the linked token decides the identity), and, through R3.43, a present human (S-58, S-59). An OS keystore or a hardware-backed authority key is a follow-up issue. The format names the authority's algorithm so that a P-256 Secure Enclave key can be added later, since the Secure Enclave has no ed25519.

### The certificate: a second predicate type in the same envelope

A session key's certificate is an in-toto Statement v1 in a DSSE envelope, signed once by the authority key. It uses the same envelope, PAE, canonical form, duplicate-key and depth checks, and key rules as evidence (ADR 0055). The only differences are its subject and its predicate:

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{"name": "session-key", "digest": {"sha256": "9c41…<the session key's key id>"}}],
  "predicateType": "urn:reef-vcs:session-key:v1",
  "predicate": {
    "publicKey": "MCowBQYDK2VwAyEA…",
    "identity": {"id": "idn_8f3a0c2d91e4b675", "name": "alice", "kind": "person"},
    "actor": "agent",
    "agent": "builder-3",
    "session": "ses_41c9e07ab2d35f18",
    "presence": "none",
    "custody": "client",
    "notBefore": "2026-11-06T10:00:00.000Z",
    "notAfter": "2026-11-06T11:00:00.000Z",
    "issuer": {"kind": "reef-daemon", "keyId": "3fa9…<the authority's key id>", "host": "mbp.local"}
  }
}
```

| Field | Required | Meaning | Checked |
| --- | --- | --- | --- |
| `subject` | yes | Exactly one, `name` `"session-key"`, `digest` `{"sha256": <key id>}` | 64 lowercase hex, equal to `KeyId::of(publicKey)` |
| `publicKey` | yes | The session key's DER SPKI, in standard base64 | `PublicKey::from_spki` (ed25519, not small-order, canonical) |
| `identity` | yes | `id`, `name`, `kind` (`person` or `ci`) | id `^idn_[0-9a-f]{16}$`, the name pattern, a known kind |
| `actor` | yes | `human`, `agent` or `executor`, as declared | one of three; `human` only with `kind` `person` |
| `agent` | no | The issuing request's `reef-agent`: a declared label | visible ASCII, at most `AGENT_MAX_BYTES` |
| `session` | yes | The session it belongs to, `ses_<16 hex>`; successive keys of one session share it | pattern |
| `presence` | yes | How a human's presence was established: `none` in this ticket; R3.43 adds `user_verified` with its own evidence | one of the values this reader knows; an unknown value makes the certificate `INVALID` for this reader |
| `custody` | yes | Where the private key lives: `client` (the requesting process) here; `daemon` is R3.04's | one of two |
| `notBefore`, `notAfter` | yes | The validity window, as R3.01's times | `notAfter > notBefore`; at most `[session_keys] max_lifetime` apart when this daemon issues it |
| `issuer` | yes | `kind`: `reef-daemon` here (`reef-store` is R4.10's, `sigstore` R3.42's); `keyId`: the authority's key id; `host`: the issuing daemon's hostname, for display | `keyId` equals the envelope's `keyid` |

- **The certificate's id** is the SHA-256 of its canonical envelope bytes, as an evidence id is. It is reported but never used as a key: one session key has one certificate, so the key id names it.
- **Format rules.** ADR 0055's stability rules apply to `urn:reef-vcs:session-key:v1`: fields are only added, a change of meaning is a new predicate type, and a reader never rewrites a stored certificate.
- **Why not X.509.** Question 3 asks this. Reef's own envelope reuses every check `reef-evidence` already has, adds no ASN.1 parser to the daemon's input surface, and is what R4.10's store can issue with the same crate. Sigstore's certificates are X.509 because Fulcio's are, and R3.42 reads them through its own issuer kind. A Reef certificate is *not* readable by `cosign`. Only the evidence envelope is, as before.

### The verification path, shared with R4.10

`reef-evidence` gains a `session` module. Every function in it is pure: no clock, no database, no I/O.

```rust
/// Issues a certificate (R3.03, ADR 0057): the authority signs a binding.
pub fn certify(authority: &SigningKey, binding: &Binding) -> Result<Envelope, Invalid>;

/// Checks a certificate in ADR 0055's order: size, envelope, the authority
/// found by `keyid` through `authorities`, the signature over the PAE, and
/// only then the statement and the predicate.
pub fn check_certificate(
    envelope: &[u8],
    authorities: &dyn Fn(&KeyId) -> Option<Authority>,
) -> Result<Certified, Invalid>;

/// What a verifier reports for evidence signed by a certified key, from
/// the time the evidence was first witnessed and the revocations that apply.
pub fn status_at(certified: &Certified, witnessed_at: Timestamp, revocations: &Revocations) -> IdentityStatus;

/// The proof of possession a requester signs with the session key.
pub fn proof_payload(key_id: &KeyId, identity: &str, actor: Actor, session: &str) -> Vec<u8>;
```

- `Authority { key: PublicKey, kind: IssuerKind, invalid_from: Option<Timestamp> }`. `Revocations` holds the key's, its session's and its identity's `invalid_from`. `Certified` is the parsed `Binding` plus the certificate's id and canonical bytes.
- `Verified::check`'s first half, the envelope through the signature, becomes a shared internal function, and evidence and certificates each add their own statement checks. Evidence behaviour is unchanged, and R3.01's tests 1 to 7 pass untouched.
- **Witness time, not claimed time.** A signature's own times (`startedOn`, `finishedOn`) are the attestor's claim. The daemon's `added_at` is when a trusted clock first saw the object, as Rekor's integrated time is for Sigstore. `witnessed_at` is the evidence row's `added_at`, the first add's, which R3.01 keeps on re-adds.

**`IdentityStatus`**, which `status_at` and the API report:

| Status | Meaning |
| --- | --- |
| `UNBOUND` | No certificate for the key on this daemon: a bare key (R3.01's `--key`, `--envelope`) |
| `BOUND` | The certificate verifies against a known authority; `witnessed_at` is within `[notBefore, notAfter]`; and it is before every applicable `invalid_from` (key, session, identity, authority). A revocation made *later* is still reported, as `revoked_at`, beside `BOUND` |
| `EXPIRED` | The certificate verifies, but the evidence was first witnessed outside the window |
| `REVOKED` | The certificate verifies, but the evidence was witnessed at or after an applicable `invalid_from` |
| `INVALID` | The certificate does not verify (a row changed behind the daemon, an unknown authority, a `presence` this reader does not know) |

A later issuer kind (R3.42, R4.10) adds statuses only if it needs to, and additively.

**Revocation means "invalid from a time".** Every revocation records `revoked_at` (when it was made) and `invalid_from` (from when signatures stop counting). By default `invalid_from = revoked_at`: evidence the daemon saw earlier keeps its identity, and the reader sees that the key was revoked afterwards. A compromise backdates it. `--since <time>` sets an earlier time, and `--since-issued` (for a key or session) or `--since-created` (for an identity or authority) sets it to the start, so everything it signed reads `REVOKED`. Revoking again may move `invalid_from` earlier, never later. A time in the future is refused. This one rule serves both a routine end ("this agent session is over") and a compromise ("this key leaked on Tuesday"), and it is what policy reads.

### Session keys

**Issuance.** `IssueSessionKey` (ACCESS_WRITE) takes four things:

- `public_key`: the SPKI of an ed25519 key the caller just generated;
- `identity`: a name, or empty for the default (socket) or the token's identity (remote);
- `actor`, plus an optional `lifetime` and an optional `session` to continue;
- `proof`: the session key's signature over `PAE("application/vnd.reef-vcs.session-key-proof", proof_payload(key_id, identity as sent, actor, session as sent))`.

The daemon then does the following, in order:

1. It checks the key (`PublicKey::from_spki`) and the proof.
2. It applies the rules below.
3. It refuses a key that already has a certificate, or that already signed evidence as a bare key (`SESSION_KEY_EXISTS`, `state` `certified` or `used`), so a session key is always fresh.
4. It refuses the request when the identity already has 10,000 unexpired keys (`TOO_MANY_SESSION_KEYS`).
5. It signs the certificate, with `notBefore` set to now.
6. It inserts the session (if new) and the key in one transaction.
7. It returns the record and the certificate.

The proof of possession is Fulcio's rule too. Without it, a caller could bind someone else's public key to an identity of its choosing and claim their future signatures.

**Who can get a key for what** (refusals are `SESSION_KEY_REFUSED` with a `rule` metadata value):

| Caller | `person` identity | `ci` identity | Actor `human` |
| --- | --- | --- | --- |
| The socket (every client is the user) | any live one; empty means the default | refused (`ci_over_socket`) | allowed, with `presence: none` |
| The remote listener, token linked to identity X | X only (`token_identity_mismatch` otherwise); empty means X | X only | refused (`human_over_remote`) |
| The remote listener, token with no identity | refused (`token_not_linked`) | refused (`token_not_linked`) | refused |
| The web listener | not served (READ only, ADR 0047) | not served | not served |

- `human` for a `ci` identity is refused (`human_for_ci`).
- A `ci` identity is never issued over the socket. If the socket could do it, a local agent could mint "CI" evidence with one RPC, which would empty "A large project trusts its CI identity and nothing else". The bar is then stealing a file (S-58) rather than one call.
- A remote `read` token is refused by scope, since the method is WRITE.

**Lifetime.** The default is `[session_keys] lifetime` (1 hour). A request may ask for 1 minute up to `[session_keys] max_lifetime` (24 hours by default; at most 7 days). Out of range is `INVALID_SESSION_KEY_REQUEST` (`field` `lifetime`). Short keys are what make witnessed-time validity useful: a leaked key stops working within the hour even if nobody revokes it.

**Where the private key lives.** Only in the process that generated it. The daemon never sees it and stores no private session key anywhere. The CLI keeps it in memory for the length of one command and zeroizes it on drop (`zeroize`, already in the lockfile). No session key is ever written to disk by Reef, in a workspace or anywhere else. `reef identity session issue` prints one to stdout for a script in another language, as a credential, as `remote token create` prints a secret. A daemon-held key (`custody: daemon`), which signs on the daemon's behalf for a workspace's session, is R3.04's: it is the only way to sign snapshots the watcher takes. The format and the tables already carry it.

**How an agent or executor gets one.** In-process, through `reef_client::Client::issue_session_key(identity, actor, lifetime, session) -> SessionKey { signing_key, certificate, record }`. This generates the key, signs the proof, calls the RPC, and returns a `SigningKey` that `Claim::sign` uses unchanged. Where each caller gets its key:

| Caller | How |
| --- | --- |
| The CLI's `reef evidence add` | Without `--key` or `--envelope`, it issues a key with a 5-minute lifetime for the one envelope it signs (below) |
| R3.06's executor, locally | Issues one key per run, `actor: executor`, bound to the default person identity |
| R3.06's executor, in CI | Does the same over the remote listener, with a token linked to the `ci` identity |
| A script in another language | `reef identity session issue -o json` |

An agent never needs a key file.

**Renewal.** There is no extension of a certificate. A client renews by issuing a new key with `session` set to its current session id. The daemon requires the same identity and actor as the session's first key and an unrevoked session (otherwise `SESSION_KEY_REFUSED`, `session_mismatch` or `session_revoked`), and it does not require the previous key to be unexpired. Keys of one session share `session`, so provenance (R3.04) and audit (R3.37) can group them.

**No operation.** Issuing a key changes no jj view, so `IssueSessionKeyResponse` has no `operation`, as for `AddEvidence`. ADR 0029 decision 12's exceptions gain `IssueSessionKey`. Every issuance and every revocation is logged under a new target, `reef_daemon::identity::audit` (identity, actor, key id, session, agent, token, never a private key). Remote issuance is also in `remote::audit`.

### Storage: migration `0009_identity.sql`, schema 9

```sql
-- R3.03: operator identities, the daemon's issuing authorities, sessions, and the session keys
-- issued for them, with the certificate (a canonical DSSE envelope) each key was issued.
-- Machine-wide, as remote_tokens and evidence_keys are. No private key is stored here or
-- anywhere in the database. Enumerations are checked in Rust, not by CHECK, so that later
-- values (presence, issuer kinds) need no table rebuild. Released migrations are never edited.
CREATE TABLE identity_authorities(id TEXT PRIMARY KEY,         -- key id: sha256 of public_key
             algorithm TEXT NOT NULL, public_key BLOB NOT NULL, -- DER SPKI
             host TEXT NOT NULL, created_at INTEGER NOT NULL,
             retired_at INTEGER,                              -- stopped issuing
             revoked_at INTEGER, invalid_from INTEGER, revoke_reason TEXT);
CREATE TABLE identities(id TEXT PRIMARY KEY,                   -- idn_<16 hex>, never reused
             name TEXT NOT NULL UNIQUE,                       -- never reused, even once revoked
             kind TEXT NOT NULL, display_name TEXT, email TEXT,
             created_at INTEGER NOT NULL,
             revoked_at INTEGER, invalid_from INTEGER, revoke_reason TEXT);
CREATE TABLE sessions(id TEXT PRIMARY KEY,                     -- ses_<16 hex>
             identity_id TEXT NOT NULL REFERENCES identities(id),
             actor TEXT NOT NULL, agent TEXT, created_at INTEGER NOT NULL,
             revoked_at INTEGER, invalid_from INTEGER, revoke_reason TEXT);
CREATE TABLE session_keys(key_id TEXT PRIMARY KEY,             -- the evidence key id
             session_id TEXT NOT NULL REFERENCES sessions(id),
             identity_id TEXT NOT NULL REFERENCES identities(id),
             authority_id TEXT NOT NULL REFERENCES identity_authorities(id),
             actor TEXT NOT NULL, presence TEXT NOT NULL, custody TEXT NOT NULL,
             certificate BLOB NOT NULL,                       -- canonical envelope
             not_before INTEGER NOT NULL, not_after INTEGER NOT NULL,
             issued_at INTEGER NOT NULL, issued_by_agent TEXT, remote_token_id TEXT,
             revoked_at INTEGER, invalid_from INTEGER, revoke_reason TEXT);
CREATE INDEX session_keys_by_identity ON session_keys(identity_id, not_after);
CREATE INDEX session_keys_by_session ON session_keys(session_id);
CREATE INDEX session_keys_by_expiry ON session_keys(not_after);
ALTER TABLE remote_tokens ADD COLUMN identity_id TEXT REFERENCES identities(id);
```

- **The certificate is authoritative; the columns index it.** Every read re-verifies it with `check_certificate`, and a read takes every reported field from the verified payload, never from the columns, as R3.01 does for evidence. A row changed behind the daemon reads `INVALID`. Revocation columns are not in the certificate. They are the daemon's own records, and the same uid can edit them (ADR 0027), as it can edit anything in `reef.sqlite3`.
- **Times** are unix milliseconds. `invalid_from` is never after `revoked_at`.
- **Backups** copy all four tables with the database. Restore keeps them. The authority's private key is not in the backup, so the restored daemon retires the restored authority and makes a new one at its first start, as described above. A restore therefore stops new issuance by the old authority while every old certificate still verifies. No private session key existed anywhere to back up. That is the design's "never backed up". Its "a restore invalidates them" holds for R3.04's daemon-held keys, which live in memory. A client-held key keeps its certificate until it expires within the hour ("Departures").
- **Forget** touches none of these tables.
- **GC.** In the first report of a run, as the stores step does for machine-wide stores, GC deletes `session_keys` rows whose `not_after` is before `min(now − 7 days, keep_newer)` and whose key no `evidence` row in any repository names. Sessions with no remaining keys go too. Identities and authorities are never deleted. `GcReport` gains `uint32 session_keys_removed = 21`. R3.04 extends the pin to keys that provenance names (`identity::retention::pinned`, one function).

- **`Evidence` gains `KeyIdentity identity = 18`**, filled at every read. `ListEvidence` does it in one query per page, joining the page's key ids to `session_keys` and their revocations, and re-verifies each certificate in the blocking job that already re-verifies the envelopes. `signature` keeps its meaning. ### Human sign-off: what R3.03 provides for #222

#222 asks: "How do we know a human signed, and not an agent holding the key?" **On one uid, Reef cannot know it from a key alone.** Anything the user can do on the socket, an agent running as the user can do, and any key file or daemon the user can reach, the agent can reach (ADR 0027). Only an authenticator that requires the person's presence for each use can tell them apart, and only if a verifier can check its proof. A passkey or security key (WebAuthn, with the user-verified flag), or a platform biometric key, is such an authenticator. This ticket provides the vocabulary and the plumbing, and states the gap:

- **An identity kind for humans** (`person`), distinct from `ci`. A verifier sees the kind in every `KeyIdentity`.
- **An actor for a human acting directly** (`human`), distinct from `agent` and `executor`. A verifier sees the actor and that it was *declared*.
- **A `presence` field in the certificate**, which every verifier reads. R3.03 issues only `none`, meaning "the daemon's user, or anything running as that user, asked for a key declared human". `human` keys are issued over the socket only. They are never issued over the remote listener (where a token, not a person, is what authenticated) or the web listener.
- **A CLI path that works now**: `reef evidence add --kind manual --result pass --actor human` signs manual evidence with a fresh key bound to the default person identity. The CLI text prints `presence: none (not verified)` beside it.
- **How a key gets bound to a human**: by the person identity it is certified for, and, after R3.43, by a user-verified passkey assertion. The passkey is registered to that identity, and it signs over the session key's id at issuance. The assertion is kept in the certificate so that any verifier, a store included, can check it again. R3.43 makes a browser tab, the desktop shell or the phone hold a non-extractable key for a few minutes, certified only after such an assertion, and gives the web listener its first WRITE path for that one purpose. `presence` becomes `user_verified`.

The rest of #222 is deferred, each to its ticket:

| #222's question | Ticket |
| --- | --- |
| Policy: "this path needs manual evidence from someone in this group", and requiring `presence` | R3.07 (identity groups, `identity.actor`, `identity.presence` in CEL) |
| Approval versus evidence: whether accepting a proposal also records a `manual` attestation | R3.09 (the lifecycle's accept transition) |
| What the human records: a note field, screenshots as artifacts | R3.31 (an additive predicate field under ADR 0055's rules; artifacts through R3.02) |
| Where it is given: the inbox, the proposal view, the phone | R3.31, R3.33, R3.40, with keys from R3.43 |
| Lifetime of a sign-off across edits | R3.15 (transfer rules) |
| Verified presence itself | R3.43 |

### Sigstore keyless: the seam, and R3.42

Full keyless needs three things:

- **Signing**: an OIDC token (a person's browser login, or a CI job's ambient token), Fulcio to certify an ephemeral key against it, and Rekor to log the signature.
- **Verification**: a TUF-distributed trusted root, X.509 chain and SCT checks, and Rekor inclusion proofs.
- **Configuration**: what maps an OIDC issuer and subject to a Reef identity.

That is a ticket by itself (M), so it becomes R3.42. This ticket leaves it four things:

1. **`IssuerKind`** in the format and the API. R3.42 adds `sigstore`, and a `KeyIdentity` whose key was certified by Fulcio reports it with the OIDC issuer and subject.
2. **`check_certificate`'s authority lookup** is where another issuer's material plugs in. R3.42 adds a sibling, `check_sigstore_bundle`, that yields the same `Certified` binding. `status_at` is unchanged: Rekor's integrated time becomes `witnessed_at` when it is earlier than `added_at`.
3. **Identities gain OIDC matches** in R3.42: a `ci` identity names the issuer and subject it accepts (for example a workflow's `job_workflow_ref`), in a new table. Nothing in this ticket's tables changes for it.
4. **Crates.** Verification can use `sigstore-verify` 0.15.1 with `default-features = false, features = ["rustls-no-provider"]` and a ring `CryptoProvider`. That passed `cargo deny` with no aws-lc in the graph ("What was verified"). Signing needs `reqwest` and an OIDC flow. Whether Reef signs keylessly at all, or only verifies what CI signed with `cosign`, is R3.42's first decision.

The evidence envelope stays ed25519. R3.42's session keys are ed25519 keys that Fulcio certifies. If Fulcio refuses ed25519, R3.42 asks to extend `PublicKey` to P-256 by ADR.

### The CLI

```
reef identity create <name> --kind person|ci [--display-name <text>] [--email <addr>]
reef identity list [--all]
reef identity show [<name>]
reef identity revoke <name> [--since <time> | --since-created] [--reason <text>]

reef remote token create <name> [--scope read|write] [--identity <name>] …
```

- **`evidence add` signs with a session key by default.** Without `--key` or `--envelope` (which R3.01 made a usage error), the CLI issues a key in-process. The identity is `--identity` or the default (in remote mode, the token's), the actor is `--actor` (default `agent`), and the lifetime is 5 minutes. It signs the claim, adds it, and drops the key. `--key` keeps R3.01's behaviour for scripts and trials, and its evidence reads `UNBOUND`. Its help now says to prefer the default. `--identity` and `--actor` conflict with `--key` and `--envelope`.
- **`evidence show`** prints, under the signature line:
  - bound: `identity: alice (person) as agent "builder-3", session ses_41c9…, presence none, certified by 3fa9… (this daemon)`;
  - not bound: `identity: unbound key 9c41…`, `expired (added 2026-11-06 12:03, key valid until 11:00)`, `revoked from <time> (<reason>)`, or `invalid certificate`.

  A `revoked_at` later than the witness time prints as `(key revoked later, <time>)`. The line ends with "policy decides whom to trust" once per output, as R3.01's `signature: valid` text does. `evidence list` prints `alice:agent` (or `unbound`) in place of the key id when bound.
- **`identity session issue`** prints `key <id 12> for alice as executor, session ses_…, valid until <time>`, and the private key and certificate when `-o json` (which is the default on a pipe): `SessionKeyIssued { key, private_key (PKCS#8 PEM), certificate (the envelope as a JSON object) }`. On a terminal, the text form omits the private key, and stderr says to use `-o json` to receive it. It is a credential, and the help says so.
- **`identity authority show`** prints the current authority's key id, the PEM public key and the host, then the retired ones.
- **`identity revoke` and `session revoke`** print what they covered, `invalid_from`, and, for an identity, its linked tokens with `reef remote token revoke <name>` lines.
- **Help budget.** `identity` joins the root help's "Also:" line. To stay within 512 bytes, `completions` leaves that line (it stays in `--help-all`, and `reef completions --help` is unchanged). `help_lists_every_command` gains `identity`.
- **JSON** (`reef_client::json`): `Identity`, `SessionKey`, `SessionKeyIssued`, `Authority`, `KeyIdentity` (on `json::Evidence` as `identity`), and lists as JSON arrays, with `JsonSchema` and `names` for the enum strings (R2.24's rules). `brief.Evidence` gains `identity` (`"alice:agent"`) when the status is `BOUND`, and `identity_status` only when it is `EXPIRED`, `REVOKED` or `INVALID`, so `UNBOUND` costs no tokens (#114). `brief.Identity` and `brief.SessionKey` keep the name, kind, actor and validity.
- **Advice** rows in `cli/advice.rs` for each new reason a command can hit.

### Documentation

- **`docs/adr/0057-operator-identities-and-session-keys.md`** (accepted), indexed in `docs/adr/README.md`.
  - **Decisions**:
    1. identities are `person` or `ci`, machine-wide, named once and forever; agents are actors, not identities;
    2. a per-daemon ed25519 authority key, on disk and not backed up, whose public keys are kept for good;
    3. certificates as a second predicate type in ADR 0055's envelope, with the fields above;
    4. client-held session keys, issued with a proof of possession, with a default life of 1 hour and a maximum of 24 hours, renewed by session;
    5. the issuance rules (no `ci` over the socket, no `human` remotely, remote identity from the linked token);
    6. validity at witness time (`added_at`) and revocation as `invalid_from`;
    7. `KeyIdentity` beside `signature`, with no trust decision;
    8. `presence` and `IssuerKind` as the seams for R3.43, R3.42 and R4.10.
  - **Alternatives**:
    - X.509 certificates through `rcgen` and `x509-parser` (an ASN.1 parser on the input path, and still not Fulcio's chain);
    - an authority key per daemon start, in memory only (nobody could pin a machine);
    - the authority key in the OS keychain (no Linux equivalent without D-Bus, and unsigned binaries prompt on every upgrade on macOS; a follow-up);
    - the authority key in `reef.sqlite3` (it would be in every backup);
    - daemon-generated session keys returned to the client (the daemon would see every private key);
    - a signing RPC with daemon-held keys for evidence (a signing oracle any socket client can call, and the attestor would be the daemon);
    - agents as identities (long-lived agent records, against the design);
    - remote tokens as identities (a token is a transport credential that rotates, and its holder is not necessarily a person or pipeline);
    - claimed time (`finishedOn`) for validity (the attestor's claim);
    - revocation that invalidates everything always (it would punish routine ends of sessions) or nothing (a leaked key's past signatures would keep counting);
    - full Sigstore keyless here (an M ticket on its own: R3.42);
    - CRL or OCSP distribution (the daemon is its own only verifier until R4.10).

## Implementation notes

- **Order**:
  1. `reef-evidence`'s `session` module, with tests 1 to 3. This is the format R4.10 inherits, and question 3 fixes its shape.
  2. The migration, `db/identity.rs` and the start sequence (test 4).
  3. The service and the rules (tests 5 to 8).
  4. Evidence reads (tests 9 to 11).
  5. GC, backup and config (12, 13).
  6. The client and the CLI (14, 15).
  7. Schema, MCP, help and SDKs (16), then the documents.
- **The authority at start** runs on the blocking pool before the socket serves. Generation uses `SigningKey::generate`, and the file is written with `create_new` and mode `0600` into a temporary name in `<state>/identity/`, then renamed and the directory fsynced, so a crash never leaves a half-written key. The private key stays in `AppState` as a `SigningKey`, zeroized on drop. Rotation swaps it under a `std::sync::RwLock` that issuance holds only for the signature.
- **The proof's payload** is exactly `"reef-session-key-proof/v1\n" + key_id + "\n" + identity + "\n" + actor + "\n" + session + "\n"`, with `actor` lowercase and the empty string for an empty field, inside the PAE with the payload type above. Test 6 pins it, and `docs/identity.md` gives it for other languages.
- **Ids**: `idn_` and `ses_` plus 16 lowercase hex characters from the thread's CSPRNG (`rand`, as token ids are), retried on the vanishingly rare collision.
- **The evidence join** is one `SELECT … FROM session_keys LEFT JOIN sessions … LEFT JOIN identities … LEFT JOIN identity_authorities … WHERE key_id IN (…)` per page, passed to the same blocking job that re-verifies envelopes. Certificates are re-verified at every read. At about 50 µs each, a page of 50 costs about 2.5 ms (see the benchmark).
- **The witness time** for status is the evidence row's `added_at`, which R3.01 keeps from the first add. The same envelope added to a second repository after its key expired reads `EXPIRED` there, since each repository row has its own `added_at`. `docs/identity.md` states this.
- **Linux**: no `cfg(target_os)`. Build and lint in the privileged `ubuntu:24.04` container anyway, since `server.rs`, `maintenance/` and the start sequence change and the Linux-only daemon tests construct `TestDaemon`.

## Risks

- **Identity on one uid is weaker than its name suggests.** Any same-uid process can get a person's keys, any actor included, and the authority key is a readable file (S-58, S-59). A reader who takes `BOUND` with `actor: human` for "a person signed" is wrong until R3.43. Mitigations: `presence: none` on every key; "not verified" in the CLI text; the threat model rows; `docs/identity.md`; and R3.07's docs. What identity does buy now is that remote callers can sign only as their token's identity, `ci` keys come only from CI's token, and revocation and expiry work.
- **The format is the part R4.10 inherits.** Its predicate type, fields, proof payload and status rules are the promise. Question 3 must be answered before implementation, and tests 1 to 3 pin the bytes and the boundaries.
- **Witness time is the daemon's clock.** A daemon with a wrong clock judges validity wrongly (S-63). Lifetimes of an hour make small skews harmless.
- **`evidence add` changes default behaviour.** The command used to need `--key`, and now it issues a key and signs. Scripts that passed `--key` are unaffected. The CHANGELOG says so.
- **The default identity is created implicitly.** It is named from the login name, which may not be the name a team wants in policy. The rename path is to create another identity and set `default_identity`, since names are never reused. Question 6.
- **The root help loses `completions`** from its first screen to make room.

## Choices this brief made, and why

- **Person and CI identities, with agents as actors**, because the design chains provenance "to a person or pipeline without long-lived agent secrets".
- **A daemon authority key that is stable but not backed up**, because others must be able to pin a machine, while a lost key costs only new issuance: old certificates verify by their recorded public keys.
- **Reef's own envelope for certificates**, because it reuses every check the evidence format has, adds no ASN.1 parser, and is what a store issues with the same crate.
- **Client-held keys with a proof of possession**, because the daemon should never see a private key, and an unproven binding would let a caller claim another's key.
- **No `ci` over the socket and no `human` remotely**, because those are the two cases where the authenticated channel (the uid, or the token) does not match the identity kind.
- **Witness-time validity and `invalid_from` revocation**, because evidence outlives keys, and a routine end must not erase history while a compromise must.
- **Identity beside the signature, never "trusted"**, because R3.07 decides trust, as R3.01 established.
- **Keyless and presence as their own rows**, because each is an M ticket with its own dependencies, and the seams here make them additive.

## What later tickets inherit

## Decided by the user (2026-11-06)

The brief's twelve questions, answered in one round of four grouped questions. Every recommendation was accepted:

1. **Identity kinds: `person` and `ci`**, with agents as declared actors under an operator.
2. **The issuing root: a stable per-daemon authority key** in `<state>/identity/authority.pem`, `0600`, not backed up, with its public keys kept in the database for good.
3. **The certificate is a Reef in-toto statement** (`urn:reef-vcs:session-key:v1`) in the same DSSE envelope, not X.509.
4. **Witness-time validity and `invalid_from` revocation**, with `--since` and `--since-issued` to backdate a compromise.
5. **Lifetimes: 1 hour by default, 24 hours at most** (configurable up to 7 days), and 5 minutes for the CLI's per-command key.
6. **A default `person` identity is created at first start**, named after the login user.
7. **Human keys are issued now**, with `presence: none`, reported on every key and printed as "not verified".
8. **R3.42 (Sigstore keyless) and R3.43 (verified human presence) are added as plan rows.**
9. **A `ci` identity on the landing daemon**, with keys issued only to a remote token linked to it.
