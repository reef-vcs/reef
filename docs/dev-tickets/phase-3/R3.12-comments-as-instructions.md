# R3.12 Comments as instructions

Phase 3 · Size M, at its top end, with the webhook split to R3.46 (decision 1) · Depends on: R3.09 (lifecycle rows, the transition's `session_id`, `record`'s row-pending, operation, row-committed order, `Operation.transitions`, `Rule::Lifecycle`), R2.13 (`reef mcp`, `NOT_TOOLS`, `wait_for_operations`, the `tools/list` budget), and builds on R2.03 (`OpMeta`, undo's refusals), R2.08 (remote tokens, `remote/rules.rs`), R2.09 (the operation stream), R2.16 (GC's operation-id map), R2.25 (the harness packages and their hooks), R3.03 (identities and token links), R3.04 (provenance sessions and their declared `client_session` and `harness`), R3.05 (jobs and their usage) and R3.44 (the hook input rules, the env-signal table's harness facts, the client-session fan-out) · Unblocks: R3.32 (help requests, resolved by an instruction that replies to them), R3.46 (instruction webhooks); through R3.32, R3.33 and the exit criterion "the human's reply resumes the agent's session"

## Context

The design asks for this in three places. Human interface, *Review stacks, not commits*: "Comments are addressed to the originating agent and resume its session, so a review comment is an instruction rather than a note for a human to act on later." *What stays headless*: agents respond to review comments through the API. And the warning that closes that section: "The review comment that becomes an instruction is the most powerful feature here and the easiest to abuse, since a casual note now spawns work and consumes compute. Comments are explicitly marked as instructions or as notes, and an instruction shows its estimated cost before it runs." The Subscriptions paragraph adds that agents wait "for a reviewer's instruction instead of polling". The design also says what Reef is not: "The app shows and acts on repository state. It is not an agent runner."

Those two statements bound the ticket. Reef never starts an agent. It records a comment, routes an instruction to the session that produced the change, and hands the instruction to whoever is running that session: a hook in the harness, `reef mcp`, the CLI, an SDK, or (R3.46) a runner that a webhook wakes. "Resumes the session" means the session's own process receives the instruction and continues, or a runner that the operator controls restarts it.

Earlier tickets left seams here:

- **R3.09**: "R3.12 attaches comments by change id and round, and resumes the session the proposing transition recorded." A `PROPOSED → PROPOSED` transition is "the agent's way of saying 'ready again' after review (R3.12)". Reasons on transitions are data, and "R3.12's instructions are a separate, marked object" (S-111).
- **R3.04 and R3.44**: a workspace's provenance session carries the declared `harness` and `client_session` (the harness's own session id), and the hook fans a declaration out "to every active workspace of the same client session". The instruction hash in provenance is how a commit says which instruction produced it.
- **R3.32** (help requests) is "resolved by a human reply that resumes the agent's session the way an instruction does", so the routing and delivery built here must not assume a proposal or a reviewer.

So this ticket builds:

1. **The comment**: an immutable object on a change, a note or an instruction, anchored to the change, its round and the commit the author saw, optionally to a path and lines, optionally replying to another comment.
2. **The instruction's lifecycle**: awaiting confirmation, pending, delivered, running, done or failed, or cancelled, with the estimate shown and stored before confirmation.
3. **Routing**: the session an instruction is for, resolved from the proposal's transition or the change's provenance, and the rules for who may take it.
4. **Delivery that pulls**: `ClaimInstruction`, used by `reef comment next` (which can wait), by a harness hook at the turn's end or the next prompt, and by `reef mcp` inside `wait_for_operations`.
5. **The record and the surface**: a row and an operation per write, `CommentService`, `reef comment`, the web UI's feed sentences, and the documents.

The webhook (push delivery to a runner, with signing, retries and the SSRF rules) is designed in "What R3.46 inherits" and built there.

## Decisions

### Size, and the split (decision 1)

M at its top end, without the webhook. The work divides like this:

| Part | Size |
| --- | --- |
| The model: kinds, states, the instruction table, limits, as one module with unit tests | about 300 lines |
| The record: migration, store, the write path (row pending, operation, row committed), start-up resolution, GC's id map, expiry | about 600 |
| Routing, the estimate, claim | about 400 |
| `CommentService` (five RPCs), `Operation.comments`, remote rules, undo's refusal, the lifecycle hooks (re-propose, final states) | about 650 |
| `reef comment`, JSON and brief types, `reef schema` | about 450 |
| The hook mode, the hook facts and packages; `reef mcp`'s inline claim and the kind | about 300 |
| The web UI's sentences and counts | about 50 |
| `docs/comments.md`, ADR 0069, the threat model | prose, about 350 lines |

The webhook is new network egress from the daemon, the first outside a git fetch, and needs its own client, secret handling, retry queue, address checks and threat rows: another M. It becomes R3.46, **Instruction webhooks** (M, after R3.12), whose design is fixed below so that this ticket's states and messages already fit it.

### What a comment is

| Field | Meaning |
| --- | --- |
| `id` | `cmt_<16 hex>` |
| `change_id` | required; the change it is about |
| `round` | the change's lifecycle round when written (R3.09); 0 for a change never proposed |
| `commit_id` | the commit the author saw: the change's visible commit, or `expected_commit_id` when given, which must be that change's visible commit (R2.03's `EXPECTED_COMMIT_MISMATCH`) |
| `path`, `side`, `start_line`, `end_line` | optional anchor: a path in `commit_id`'s tree (`side: NEW`) or its first parent's (`OLD`, for removed lines), and a 1-based inclusive line range within that file's text |
| `reply_to` | optional; another comment on the same change |
| `kind` | `NOTE` or `INSTRUCTION`, fixed at creation |
| `text`, `text_sha256` | the body, UTF-8, 1 byte to 16 KiB, no control characters but newline and tab; its SHA-256 |
| `author` | agent, actor (`HUMAN`, `AGENT`), identity, provenance session, remote token: R3.09's attribution rules, unchanged |
| `instruction` | for an instruction only: state, estimate, target, delivery, outcome (below) |

- **On any change, not only proposals** (decision 2). A comment needs a change with a visible commit or a lifecycle row. Agents are often instructed while drafting, and R3.32's help requests come from drafts; R3.31 shows the comments of proposals. A change abandoned after the comment keeps its comments, read with `visible: false` as R3.09 reports.
- **Comments are immutable.** No edit and no delete, except `reef repo forget`. A note is corrected by another note that replies to it. An instruction can be cancelled until it runs. A comment never moves with an amended change: `outdated` is computed on read when `path` is set and the visible commit's blob at `path` differs from the anchor's, so R3.31 can mark it.
- **A note is data, and stays data.** Notes are never claimed, delivered, inlined by `reef mcp` or printed by a hook. To act on a note, write an instruction that replies to it.
- **Limits** (constants, `RESOURCE_EXHAUSTED`, reason `TOO_MANY_COMMENTS` or `TOO_MANY_INSTRUCTIONS`): 1,000 comments per change, 16 unfinished instructions per change, 64 unfinished instructions per target session.

### The instruction lifecycle (decision 4)

| State | Means | Entered by |
| --- | --- | --- |
| `AWAITING_CONFIRMATION` | Written, estimate stored, nothing delivered | `CreateComment` |
| `PENDING` | Confirmed; waiting for its session to take it | `confirm`, or `CreateComment` with `confirm` within ceilings |
| `DELIVERED` | A client took it for the session | `ClaimInstruction` |
| `RUNNING` | The session said it started | `start`, or a claim with `start: true` (hooks, `reef mcp`) |
| `DONE` | The session said it finished, or the change was proposed again after delivery | `done`, or the daemon (cause `reproposed`) |
| `FAILED` | The session said it could not, or it ran past its time | `fail`, or the daemon (cause `expired`) |
| `CANCELLED` | Withdrawn before it ran, or made moot | `cancel`, or the daemon (causes `change_final`, `expired`) |

- **Transitions**: `AWAITING_CONFIRMATION → PENDING | CANCELLED`; `PENDING → DELIVERED | RUNNING | CANCELLED`; `DELIVERED → RUNNING | DONE | FAILED | CANCELLED | PENDING` (a release: the claimer hands it back); `RUNNING → DONE | FAILED`. `DONE`, `FAILED` and `CANCELLED` are final. A cancellation after delivery is recorded and reported to the next claim and to `reef comment show`, but it stops nothing a session already has.
- **Done by re-proposal.** When a change is proposed again (R3.09's `PROPOSED → PROPOSED` update, or a new round), its instructions in `DELIVERED` or `RUNNING` that were delivered before that transition become `DONE` with cause `reproposed`, naming the transition. That is the loop the design describes: instruction, amendment, proposal.
- **Final changes.** When a change reaches `LANDED` or `SUPERSEDED` (any cause, R3.13's landing included), its instructions in `AWAITING_CONFIRMATION` or `PENDING` become `CANCELLED`, cause `change_final`. Delivered and running ones are left for their session to finish.
- **Expiry.** An unfinished instruction untouched for 7 days ends: `CANCELLED` before it runs, `FAILED` while `RUNNING`, cause `expired`, swept by the timer that expires jobs. A constant, as R3.09 kept its limits.
- **Not undoable.** `UndoOperation` of an operation carrying comment events is `OPERATION_NOT_UNDOABLE`, hint "a comment is a record of what someone said; cancel an instruction with `reef comment cancel`". A delivered instruction cannot be unsent, and a note cannot be unsaid.
- **Every outcome names who.** Each state change records agent, actor, identity, remote token and a summary of up to 4 KiB (`done -m`, `fail -m`), under the same rules as `text`.

### Who may write and act (decision 5)

- **On the socket**, one uid is one trust domain (ADR 0027): any caller writes notes and instructions, confirms, cancels and claims. Actor, identity and session are recorded as declared, by R3.09's defaults (`AGENT` with an agent name, else `HUMAN`). `docs/comments.md` says plainly that an agent on the same uid can instruct another agent, and that the record says it was an agent.
- **Through the remote listener**, one new rule, `Rule::Comment`, decided per call in the handler:
  - a note: any `write` token;
  - an instruction: a `write` token linked to an operator identity (R3.03), so the instruction is attributed to someone; otherwise `REMOTE_IDENTITY_REQUIRED`. The remote actor is always `AGENT` until R3.43 makes a remote human verifiable, as for R3.09's decline;
  - confirm and cancel: the token that wrote it (`REMOTE_COMMENT_NOT_OWNED`);
  - claim: the token that proposed the change (R3.09's `proposed_by_token`), or with `take` any token linked to an identity; start, done, fail and release: the token that claimed it.
- **Not signed** (decision 5). A comment is recorded with the identity as declared, like a transition. The daemon could sign it with a key it holds, but that proves only that this daemon wrote the row, which the row already says; a person's signature means something after R3.43 (verified presence) and travels after R4.07 (the store). The link that matters is kept instead: `text_sha256` is the instruction hash that the resumed session declares into its provenance (below), so R3.37 can answer "which instruction produced this line" with a comment and its author.

### Routing: which session an instruction is for (decision 6)

The target is resolved when the instruction is written, stored, and reported as `target`:

1. The latest committed `propose` transition of the change (R3.09) with a `session_id`: that provenance session's `client_session`, `harness`, `agent` and workspace. `source: PROPOSAL`.
2. Else the change's latest provenance record (R3.04, `provenance_by_change`): its session, as above. `source: PROVENANCE`.
3. Else none: `source: NONE`, and any session working on the change may take it.

A Reef session ends with its workspace, but the harness session it declared is what resumes, so routing is by the declared **client session**. When the session declared none, the target is the Reef session and its workspace, and only a claim naming that workspace matches.

- **Claims match the target** when the request's `client_session` equals the target's, or the request names a workspace whose session declared it (or, without a client session, is the target workspace).
- **Take.** `take: true` lets a caller claim an instruction meant for another session on a change it names (its workspace's change, or `change`). The instruction records `taken: true` and both sessions, and `reef comment show` says so. This is the fallback when the original session has gone.
- **Liveness is not known.** Reef cannot tell whether a harness session is still running. `target.last_seen_at` is the latest of the client session's declarations, records and claims, which is the honest signal; `docs/comments.md` says what it is and is not.
- **The instruction reaches provenance.** A Reef client that claims an instruction declares its `text_sha256` as the instruction of every active workspace of the claiming client session (R3.44's fan-out, `declare_hook.rs`), so the records the work produces name it. An SDK or other client does the same with `DeclareProvenance`, which `docs/comments.md` shows.

### The estimate, and confirmation (decision 8)

"Shows estimated cost before running" needs a definition Reef can stand behind. Reef never sees model tokens, prices or a harness's internal effort. It does see two costs it recorded itself, and the declared facts of the target session. The estimate is those, labelled as what they are:

| Part | From | Unknown when |
| --- | --- | --- |
| `checks`, `check_wall_ms`, `check_cpu_ms` | the change's jobs (R3.05) on the tree of its recorded proposal commit, else its visible commit: what re-running its checks after a fix costs, as last time | no finished job for that tree |
| `agent_wall_ms`, `agent_samples`, `agent_basis` | the median of delivery-to-done wall time of earlier instructions that finished `DONE`: on this change, else to this client session, else the repository's last 50 | no finished instruction in any of the three |
| `model`, `harness` | the target session's declaration (R3.04), unverified | not declared |
| `reported` | a cost a runner reports for this instruction (R3.46's quote): tokens and an amount in a currency, with its source | always, until R3.46 |
| `unknown` | a sentence per part that is unknown, and always "model tokens and price are not visible to Reef" while `reported` is unset | |

- **Computed once, at creation, and stored** with a `digest` (SHA-256 of its canonical JSON) and `computed_at`. It is what the author was shown, so it is what the record keeps; `reef comment show` prints it with its age.
- **Confirmation is a second call.** An instruction is written `AWAITING_CONFIRMATION`, with the estimate in the response. `UpdateInstruction` with `to: PENDING` confirms it. A web UI, the CLI and an SDK each show the estimate between the two calls; that is the design's gate.
- **One call, with ceilings.** `CreateComment` with `confirm: true` confirms in the same operation only when it carries `ceilings` (`max_check_wall_ms`, `max_agent_wall_ms`) that the known parts meet, and an unknown part meets a ceiling only with `allow_unknown`. Otherwise the instruction stays `AWAITING_CONFIRMATION` and the response says which ceiling stopped it (`confirm_refused`), not an error. Scripts and agents replying to agents (R3.32) use this. `confirm: true` with no ceilings is `CEILINGS_REQUIRED`.
- **It is not a budget.** Nothing stops a session from spending more than its estimate. Compute budgets in policy are R3.20's, which may read the stored estimate.

### The record: a row and an operation (decision 3)

Every comment write (a creation, and each state change of an instruction) is recorded the way R3.09 records a transition: a pending row, an empty jj operation that carries it, then the row committed with the operation's id. The operation puts comments in `ListOperations`, the subscription stream, `reef op log`, the activity feed and replay, and wakes an agent waiting with `wait_for_operations`. The rows keep the text and the state through GC.

- **The operation**: kind `comment` (`OpKind::Comment`, `OPERATION_KIND_COMMENT = 14`), the request's workspace and agent, description `reef: <event> comment <id> on change <change hex>` (`comment`, `instruct`, `confirm`, `claim`, `start`, `finish`, `cancel`, `release`), and an attribute **`reef.comment`**, format 1, which never holds the text:

  ```json
  {"v":1,"comments":[{"id":"cmt_8f3a0c2d91e4b675","change":"<hex>","round":2,"kind":"instruction",
    "event":"confirm","from":"awaiting_confirmation","to":"pending","cause":"request","event_id":"cev_…"}]}
  ```

  A list, so the daemon's `reproposed`, `change_final` and `expired` sweeps record several in one operation. `classify` learns the prefixes.
- **The rows**, migration `0015_comments.sql` (schema 15, renumbered at rebase):

  ```sql
  CREATE TABLE comments(repo_id TEXT NOT NULL, id TEXT NOT NULL,          -- cmt_<16 hex>
               status TEXT NOT NULL,                                     -- pending | committed
               change_id TEXT NOT NULL, round INTEGER NOT NULL, commit_id TEXT NOT NULL,
               path TEXT, side TEXT, start_line INTEGER, end_line INTEGER, reply_to TEXT,
               kind TEXT NOT NULL, text TEXT NOT NULL, text_sha256 TEXT NOT NULL,
               agent TEXT, actor TEXT NOT NULL, identity_id TEXT, identity_name TEXT, session_id TEXT,
               remote_token TEXT, remote_token_name TEXT, created_at INTEGER NOT NULL,
               PRIMARY KEY (repo_id, id)) WITHOUT ROWID;
  CREATE TABLE instructions(repo_id TEXT NOT NULL, comment_id TEXT NOT NULL,
               state TEXT NOT NULL, estimate TEXT NOT NULL, estimate_digest TEXT NOT NULL,   -- JSON
               target_source TEXT NOT NULL, target_session_id TEXT, target_client_session TEXT,
               target_harness TEXT, target_agent TEXT, target_workspace_id TEXT,
               claimed_client_session TEXT, claimed_workspace_id TEXT, claimed_agent TEXT,
               claimed_token TEXT, channel TEXT, taken INTEGER NOT NULL DEFAULT 0,
               confirmed_at INTEGER, delivered_at INTEGER, started_at INTEGER, finished_at INTEGER,
               summary TEXT, cause TEXT, updated_at INTEGER NOT NULL,
               PRIMARY KEY (repo_id, comment_id)) WITHOUT ROWID;
  CREATE TABLE comment_events(repo_id TEXT NOT NULL, id TEXT NOT NULL,   -- cev_<16 hex>
               seq INTEGER, status TEXT NOT NULL, comment_id TEXT NOT NULL, change_id TEXT NOT NULL,
               event TEXT NOT NULL, from_state TEXT, to_state TEXT, cause TEXT NOT NULL,
               transition_id TEXT,                                       -- reproposed: R3.09's transition
               agent TEXT, actor TEXT NOT NULL, identity_id TEXT, remote_token TEXT, summary TEXT,
               operation_id TEXT, operation_collected INTEGER NOT NULL DEFAULT 0,
               created_at INTEGER NOT NULL, recorded_at INTEGER,
               PRIMARY KEY (repo_id, id)) WITHOUT ROWID;
  -- indexes: comments by (repo_id, change_id, created_at); instructions by (state, updated_at)
  -- WHERE state not final, by (target_client_session, state), by (repo_id, state, updated_at DESC);
  -- events by (repo_id, comment_id, seq) and (status) WHERE status = 'pending'
  ```

  A comment row is visible once its creation event is committed. `instructions` is the current state, updated in the transaction that commits an event. `reef repo forget` deletes all three by repository; backups copy them whole.
- **The write path** (`reef-daemon/src/comments/`) follows R3.09's steps: validate; snapshot a named workspace first when the revision uses `@`; take the create lock shared, then the repository's **comment lock** (a per-repository `tokio::sync::Mutex`, never held across a snapshot, and never taken while holding the lifecycle lock); resolve the revision, anchor and target on the repository thread; check the state table and the remote rule; insert pending rows; commit the operation; commit the rows with `seq`; respond. The write runs in a task of its own, as R3.09's review required, so a dropped call cannot leave an operation without its row. Start-up resolution reuses R3.09's: a pending event whose operation is found is committed, otherwise it and a pending comment row are deleted.
- **The lifecycle hooks** run after R3.09's `record` commits a transition, outside the lifecycle lock: one call into `comments::on_transition(repo, &[TransitionRow])`, which takes the comment lock and records the `reproposed` or `change_final` events in one operation of its own. The landing worker (R3.13, R3.14) reaches it through `record`, so no landing code changes.
- **GC** maps `comment_events.operation_id` through `GcOutcome.rewritten`, as for transitions, and never deletes rows.

### Delivery that pulls (decisions 7 and 10)

One RPC hands an instruction to a session: `ClaimInstruction`. It never blocks. It picks the oldest `PENDING` instruction that matches (or the one `comment_id` names), moves it to `DELIVERED`, or straight to `RUNNING` with `start: true`, records the claimer and the `channel`, and returns the comment with its text. Nothing matches: an empty response, not an error. Four clients call it:

- **`reef comment next`** (any harness with a shell, scripts): `--change REV`, `--workspace`, `--client-session ID` (default: the harness's session variable from the env-signal table, else `REEF_CLIENT_SESSION`), `--take`, `--start`, and `--wait DURATION`, which subscribes to the operation stream filtered to kind `comment` and the change (or the repository), and claims on each confirm event until one matches or time runs out (exit 0 with nothing, `next` repeats the command). Text output is the framed instruction (below); JSON is the claim response.
- **The harness hook** (R2.25's packages, facts in the env-signal table): `reef comment next --hook --at client_session=POINTER --at workspace=POINTER --emit FORM`. It claims with `start: true` and channel `HOOK`, declares the instruction's hash (R3.44's fan-out), and prints the framed instruction in `FORM`, else nothing. It never fails, never starts a daemon, and stops after two seconds, as every hook does. Two placements, each a fact per harness:
  - **at the turn's end**, `FORM` is the harness's documented "keep going" output, so an agent that finished its turn continues with the instruction instead of stopping. This is how a running headless or interactive session is resumed. A harness with no such output gets no turn-end hook;
  - **at the next prompt and at session start**, `FORM` is `context`, plain stdout added to the model's context: the instruction arrives with the next thing the person types, or when the session is resumed by any means.

  `HookFacts` gains `instruct: &'static [(HookEvent, Emit)]`; `Emit` names generic output forms (`Context`, and the decision-object form the implementation verifies), never a harness. The packages render the hooks with `just packages`, and `packages_are_current` checks them.
- **`reef mcp`** (no new tool): `wait_for_operations` and `list_operations` accept the kind `comment`. When `wait_for_operations` returns an operation whose comment events confirm an instruction for the server's client session (from its environment, R3.44), the server claims it (`comment_id`, `start: true`, channel `MCP`), declares its hash, and adds `instruction: {id, text, author, change_id, round, path, lines}` to that operation in the tool's result. An agent that waits on its change after proposing therefore gets the instruction in the result it is already waiting for. The server instructions gain one sentence (under 120 bytes): "After proposing, wait_for_operations with kind comment on your change delivers a reviewer's instruction; do it, then propose again."
- **SDKs**: the generated `claimInstruction`; no helper.

**The framed instruction.** Every client that hands text to a model prints it inside the same frame, so the model can tell whose words they are: `Reef instruction cmt_… from <identity or agent> (<actor>) on change <short id>, round <n>[, at <path>:<lines>]:`, then the text, then `When done, propose the change again (reef propose), or run reef comment fail cmt_… -m WHY.` Control characters are refused at creation, so the frame cannot be broken out of on a terminal.

**When the session has ended** (decision 9). An instruction stays `PENDING` until a claim, a take, a cancel or expiry. It is listed by `reef comment list --state pending` (R3.33's inbox later), `show` reports `target.last_seen_at`, and its `next` is `reef comment next --take --change <id>`, for any agent asked to pick it up. Starting a session that has ended is a runner's job, which R3.46's webhook wakes.

### The API: `CommentService`, API revision 26 (decision 11)

A new `comments.proto`:

```proto
// Comments on changes, and instructions to the session that made them (R3.12, ADR 0069).
service CommentService {
```

## Implementation notes

- **Order**: the model; the migration and store; reef-lib's attribute (test 1); the write path and `CreateComment`, reads (3); the instruction table, `UpdateInstruction` (4); estimate and ceilings (5, 6); routing and claim (7, 13); the lifecycle hook and sweep (8, 9); recovery, undo, GC (10, 11); remote (12); CLI (14); hooks (15); MCP (16); web; documents.
- **Locks**: create lock shared, then the comment lock. `on_transition` runs after the lifecycle lock is released, so the two locks are never held together.
- **The estimate's queries** run on the async side's blocking pool and are bounded: jobs by `(repo_id, change_id)` with a tree filter, at most 500 rows; instructions by change, session, then repository, at most 50 each.
- **Hook facts are verified, not assumed.** Before writing a harness's turn-end `Emit`, check its pinned release's documented hook output (as R3.44 did for its facts), and record the source in the table's comment. A harness whose turn-end continuation is not documented gets the prompt and session-start hooks only.
- **`reef mcp`'s claim** is made only for operations returned by `wait_for_operations`, never by `list_operations`, so reading the log never consumes an instruction.
- **Linux**: nothing is `cfg(target_os = "linux")`; CI covers it.
- **No new configuration.** Limits, the expiry and the sample counts are constants.

## Out of scope

- **The webhook** (R3.46), with push delivery, signing, retries, address checks and a runner's cost quote.
- **Help requests** (R3.32): a comment kind authored by an agent, answered by an instruction that replies to it. `CommentKind` and `reply_to` are its seams.
- **The proposal view** (R3.31): rendering comments, anchors and `outdated`, and the confirm step with its estimate; **the inbox** (R3.33): pending instructions and unanswered help requests in its buckets.
- **Budgets** (R3.20), and any policy over comments.
- **Signed comments** (after R3.43 and R4.07), and comments travelling with a change to a store (R4.07).
- **Starting or resuming a harness process.** Reef starts no agent; a runner does, woken by R3.46.
- **Editing or deleting comments.**

## Risks

- **Delivery depends on the session asking.** A session with no hook installed, not using `reef mcp`'s wait, and never running `reef comment next` never sees its instruction. Mitigated by the hooks in the packages, the MCP sentence, the take fallback and R3.46; `docs/comments.md` lists what each harness integration does.
- **Turn-end continuation differs per harness**, and a harness can change it. Mitigated by keeping it a verified fact in the table, checked against pinned releases, with context delivery as the floor.
- **The estimate is thin at first**: few finished instructions and, until R3.45 submits jobs, few checks per change. It says so part by part rather than guessing.
- **Operations per instruction**: up to five empty operations per instruction, a few hundred bytes each, collected by GC like any other.

## Choices this brief made, and why

- **Reef routes and records; it does not run agents**, because the design says the app is not an agent runner, and a harness or a runner owns its process and its credentials.
- **Pull delivery first**, because every harness can run a command or call a tool, while a push needs a listener someone runs (R3.46).
- **An estimate of what Reef recorded**, because a token or price figure Reef cannot see would be invented, and a labelled partial estimate is still something a reviewer can weigh.
- **Two steps or ceilings**, because the design's worry is a casual note spawning work.
- **Re-proposal finishes an instruction**, because R3.09 already made it the agent's "ready again", and it needs no new habit from agents.
- **Not undoable**, because an instruction that reached a session cannot be unsent.

## What later tickets inherit

- **R3.46 (instruction webhooks)** builds the push path on this ticket's states:
  - **Configuration** in the daemon's config file only (`[[webhooks]]`: `url`, `secret_file`, `repos`, `events`), never through the API, so only the daemon's user points the daemon at a URL. `https` required except to loopback; redirects not followed; 5-second connect and 10-second total timeouts.
  - **Address checks** (SSRF): the resolved address is refused when loopback, private, link-local, unique-local or a cloud metadata address, unless the entry says `allow_private = true`; the check is on the address actually connected to, so DNS rebinding cannot pass it.
  - **Payload**: event `instruction.pending` with the comment (text and `text_sha256`), the change, round, anchor, author, target (`client_session`, `harness`, `agent`, workspace) and the estimate; R3.46 decides whether text is included or fetched back with a token. Signed by the Standard Webhooks scheme (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256 of id.timestamp.body>`), a secret per endpoint, rotation by a second secret; receivers reject stale timestamps.
  - **Delivery**: a 2xx is `DELIVERED` with channel `WEBHOOK`; retries with backoff for about an hour, in a table that survives restarts; then the instruction stays `PENDING` for a pull. The runner reports `start`, `done` and `fail` through the API with a token.
  - **Quote**: an optional `instruction.quote` request before confirmation, whose answer fills `estimate.reported`.
  - Its own threat rows: egress and SSRF, the secret, replay, payload disclosure, a slow receiver.
- **R3.32** adds `COMMENT_KIND_HELP_REQUEST`, written by an agent through a WRITE RPC or this one, and resolved by an instruction with `reply_to` naming it; the reply resumes the session through the same claim.
- **R3.31** lists comments with `ListComments`, renders anchors and `outdated`, and shows the estimate between `CreateComment` and the confirm.
- **R3.33** builds "needs you now" from unanswered help requests and the "watching" bucket from instructions in flight, live from `OPERATION_KIND_COMMENT`.
- **R3.20** may cap confirmation by the stored estimate.
- **R3.37** answers "which instruction" through `instruction_sha256` in provenance and the comment with that `text_sha256`.
- **R4.07** carries comments with their change to a store, and decides signing with R3.43.

## Departures from dev-phases.md

- **"Through a webhook or the MCP server"**: this ticket delivers by pull (the CLI, harness hooks and `reef mcp` inside `wait_for_operations`, with no new MCP tool), and the webhook is a new row, R3.46. Reef never starts an agent: a session receives its instruction, or a runner the webhook wakes restarts it.
- **"Estimated cost"** is what Reef recorded (the change's check time and earlier instructions' agent time) plus the session's declared model, with tokens and price stated as unknown until a runner reports them (R3.46).
- **"On proposals"**: comments attach to any change with a visible commit or a lifecycle row; the proposal view shows a proposal's.

## Departures in the implementation

Found while building it (2026-11-09):

1. **Two tables, not three.** `comments` holds an instruction's state, estimate, target and claim as nullable columns beside the comment, and `comment_events` holds every write with what its move set; committing an event updates the comment's columns in the same transaction, only while the comment is still in the event's `from` state. A separate `instructions` table would have been one row per comment joined on every read.
2. **The comment types live in `comment_event.proto`** (`CommentKind`, `InstructionState`, `InstructionCause`, `CommentEvent`), imported by `operations.proto` and `comments.proto`: `Operation.comments` needs `CommentEvent`, and `comments.proto` imports `operations.proto`. R3.09 did the same with `lifecycle.proto`.
3. **`UpdateInstructionRequest` has no `client_session`.** The remote rule decides by token (the writer's for confirm and cancel, the claimer's after), and the socket records what the caller declares.
4. **`TOO_MANY_COMMENTS` and `TOO_MANY_INSTRUCTIONS` are `UNAVAILABLE`**, as R3.13's `QUEUE_FULL` is: Reef's error kinds have no resource-exhausted kind.
5. **`reef mcp` returns taken instructions as a top-level `instructions` list** of the wait's result (`id`, `change_id`, `frame`), not inside each operation, so `Operation` keeps one shape everywhere. To stay under 21,250 bytes with the `comment` kind and `instructions` named in its description, `wait_for_operations` says "(another agent's write)" and its `after_operation` text drops the sentence the description already gives. The server instructions are 976 of 1,000 bytes.
6. **Results.** `reef comment add` prints `{comment, confirm_refused}`, `show` prints `{comment, replies}`, and `next` prints `{comment, frame}`, both null when there was none to take. Moves print the comment.
7. **The hook's forms are `--emit context` and `--emit block`**, named by what they print, not by harness. With no workspace in its event, the hook tries each registered repository for the client session.
8. **Re-proposals and final states reach the instructions through a queue.** R3.09's `record` (and R3.13's land, through `commit_written_transition`) hands committed transitions to the comment sweep's task, which takes the create lock shared and the comment lock afterwards, so the two locks are never held together; the same task expires instructions every ten minutes.
9. **`confirm` on a note is `CEILINGS_REQUIRED`**, the same refusal as `confirm` without ceilings, and so are ceilings that bound nothing (both 0).
10. **From the code review** (the PR's table lists every finding):
    - A release must name `expected_state: DELIVERED`; a bare move to PENDING is a confirmation only, so a confirmation sent again never hands a taken instruction out twice. A move to the state the instruction is already in does nothing, whatever it expected.
    - Hooks and `reef mcp` take instructions as `DELIVERED`, not `RUNNING`, and the hook prints the instruction before it declares the hash (without a snapshot), so one the deadline or a cancelled call cuts off can still be released. The hook tries every repository even when one errors.
    - The sweep also reconciles from the database, at start and every ten minutes, so a re-proposal or a final state whose notice a restart lost still moves its instructions.
    - The estimate's checks are the latest finished run of each check (by spec) on the tree, at most the 500 newest jobs; `jobs` gains an index on its tree.
    - An instruction on a landed or superseded change is refused (`CHANGE_FINAL`, a new reason); notes are still taken.
    - Bidirectional overrides and isolates are refused in text, as control characters are.
    - Through the remote listener, cancel needs the writing token at every state.
    - `reef op log` and `reef op watch` take `--kind comment`; reef-lib's undo planner refuses comment operations too.
    - Not done: `NOT_CLAIMER` on the socket (one uid is one trust domain; through the remote listener only the claiming token moves a taken instruction), `reef op log` words for comment events (it prints the operation's description, which names the event), and the `outdated` check for an old-side anchor compares the path on the new side.
11. **Renumbered at the rebase onto R3.14** (#255, 2026-11-09), which took API revision 26, schema 15 (`0015_batches`), `OPERATION_KIND_BATCH = 14` and `Operation.batch_id = 20`: this ticket is API revision 27, schema 16 (`0016_comments.sql`), `OPERATION_KIND_COMMENT = 15` and `Operation.comments = 21`.

## Decisions for the user

Asked on 2026-11-09; the user accepted every recommendation below, and the brief's body follows them.

**Group 1: scope**

1. **Split the webhook into R3.46 (M, after R3.12).** R3.12 delivers by pull (CLI, harness hooks, `reef mcp`); R3.46 builds the daemon's first outbound HTTP (config-file-only endpoints, SSRF address checks, Standard Webhooks HMAC signing, persistent retries, a runner's cost quote) to the design fixed in "What R3.46 inherits". *Recommended*: split. Alternatives: keep the webhook here (L, and the daemon's first egress reviewed inside a large ticket); or no webhook in Phase 3 at all (an ended session is resumed only by a person or an agent that takes the instruction).

**Group 2: the object and its record**

2. **What a comment attaches to.** Any change with a visible commit or a lifecycle row, anchored to change, round and the commit the author saw, optionally a path, side and line range, optionally replying to another comment; immutable, with `outdated` computed on read. *Recommended*: as stated (agents are instructed while drafting, and R3.32's help requests come from drafts). Alternatives: proposals only (a `PROPOSED` or `QUEUED` change); anchoring to the commit alone, so comments disappear from view on every amend; editable comments.
3. **Storage.** Rows in `reef.sqlite3` (migration 15: `comments`, `instructions`, `comment_events`) plus an empty jj operation per write (kind `comment`, attribute `reef.comment` with ids and states, never text), in R3.09's row-pending, operation, row-committed order. *Recommended*: as stated, so comments are in the feed, replay and `wait_for_operations`. Alternatives: rows only, announced on presence (no feed or replay, and an agent cannot wait through the operation stream); text in the operation attribute.
4. **The instruction lifecycle.** Awaiting confirmation, pending, delivered, running, then done, failed or cancelled; a re-proposal of the change marks delivered and running instructions done; landing or superseding the change cancels unconfirmed and pending ones; 7 days untouched expires; comment operations are not undoable. *Recommended*: as stated. Alternatives: no automatic done (the agent must always run `reef comment done`); no expiry; undo of a comment operation as a cancel.

**Group 3: who, and to whom**

5. **Permissions and signing.** On the socket anyone may write, confirm, cancel and claim, recorded with a declared actor (R3.09's rules). Remotely: any `write` token writes notes; instructions need a token linked to an operator identity and are recorded `AGENT`; confirm and cancel need the writing token; claim needs the proposing token, or `take` with a linked token. Comments are not signed; `text_sha256` becomes the resumed session's declared instruction hash. *Recommended*: as stated. Alternatives: instructions only from `HUMAN` actors (unverifiable on the socket until R3.43, so only a label); sign each comment with a daemon-held key for the author's identity (proves only that this daemon wrote it); refuse remote instructions entirely, as R3.09 refuses remote decline.
6. **Routing.** The target is the declared client session of the provenance session that recorded the latest `propose`, else of the change's latest provenance record, else none (any session on the change may take it). Another session may claim with `take`, recorded and shown. Reef reports `last_seen_at`, not liveness, which it cannot know. *Recommended*: as stated. Alternatives: route to the Reef workspace session only (it ends with its workspace, while the harness session usually outlives it); route to whoever next writes to the change.

**Group 4: delivery and cost**

7. **The MCP path.** No new tool: `wait_for_operations` and `list_operations` gain the kind `comment` (about 20 bytes, paid for by shortening descriptions), and `reef mcp` claims an instruction for its own client session when `wait_for_operations` returns its confirm operation and inlines the text in that result; one sentence in the server instructions (844 → about 960 of 1,000 bytes). *Recommended*: as stated. Alternatives: a combined `instruction` tool (list, claim, finish; about 450 bytes, which means raising the budget or trimming more); an MCP resource with `resources/updated` notifications (no budget, but most clients do not show server notifications to the model); adding pending instructions to every tool result (changes every result's shape).
8. **The estimate and the gate.** The estimate is what Reef recorded: the change's last check run (job count, wall and CPU time) and the median agent time of earlier finished instructions (on the change, else the session, else the repository), with the session's declared model and harness, and tokens and price stated as unknown until a runner reports them (R3.46). Stored at creation. Confirmation is a second call; one call confirms only with ceilings the known parts meet (`allow_unknown` for the rest). *Recommended*: as stated. Alternatives: no estimate, only the confirmation step (the design asks for an estimate); a token guess from text length and a price table (Reef would be inventing numbers); confirming in one call without ceilings.
9. **When the session has ended.** The instruction stays pending until claimed, taken by any agent on the change (`reef comment next --take`), cancelled or expired; R3.46's webhook is how a runner restarts a session. *Recommended*: as stated. Alternatives: fail the instruction at once when no live workspace session declared its client session (Reef cannot tell, so this would fail instructions to live sessions working from the root checkout); have the CLI print a harness-specific resume command from the env-signal table now (a fact per harness to verify; better done with R3.46's runner).
10. **Harness hooks.** The packages gain an instruction hook at the turn's end (the harness's documented "keep going" output, where one is verified) and at prompt submit and session start (plain context), rendered from the env-signal table; `reef comment next --hook` claims with `start` and declares the instruction hash. *Recommended*: as stated (it is how a running session is resumed without a runner). Alternative: no hooks in this ticket, delivery only through `reef comment next` and MCP (an agent must remember to wait).

**Group 5: the surface**

11. **API.** A new `CommentService`: `CreateComment`, `UpdateInstruction`, `ClaimInstruction` (WRITE), `GetComment`, `ListComments` (READ); `Operation.comments`, `OPERATION_KIND_COMMENT`; API revision 26; all five in `NOT_TOOLS`. *Recommended*: as stated. Alternatives: the methods in `ChangeService` (comments are objects of their own, with R3.32 adding kinds); one RPC per instruction verb (five methods with one shape).
12. **CLI and web.** `reef comment add|list|show|confirm|cancel|next|start|done|fail|release` in `--help-all` only, root help and guide unchanged; the web UI gains only feed sentences and counts, and R3.31 renders comments. *Recommended*: as stated. Alternatives: a separate `reef instruction` noun for the instruction verbs; a guide line now ("after proposing, `reef comment next --wait`"), dropping another line to stay under 1,600 bytes.
