# R3.06 Trusted executor reference implementation

Phase 3 · Size L, with the scope moves below · Depends on: R3.05 (the executor protocol, `docs/executor-protocol.md`, `ExecutorService`, `reef job`), R3.03 (session keys with actor `executor`, `Client::issue_session_key`, tokens linked to a `ci` identity); builds on R3.01 (`reef-evidence`, `Claim::sign`), R3.02 (`Client::upload_artifact_file_as`), R2.02 (`FileService.ListFiles` and `ReadFile` at a revision) and R2.08 (the remote listener) · Unblocks: R3.14, R3.22; through them R3.15, R3.18, R3.20, R3.21, R3.34 and R4.11

## Context

The design gives the executor two sentences of its own. In CI load: "Running the jobs stays outside Reef. Sandboxing, hermetic builds, remote execution, and runner fleets are an established domain, and Reef sits on top of it through the evidence format and the executor protocol." In its open problems: "Evidence can be forged by the agent that produced it. Only attestations from executors the repository trusts carry weight. The executor must run in an environment the submitting agent cannot tamper with, which pushes toward hermetic builds and keyless signing." Its trust paragraph adds: "A solo developer trusts their own machine. A large project trusts its CI identity and nothing else."

So Reef ships one executor, as a reference and as the thing a solo developer and a small CI setup actually run, and keeps every other executor possible: the protocol (R3.05) is the contract, and this ticket is its first real client. The earlier tickets left it these pieces:

- **R3.05** built the queue and wrote the spec. Its handoff: "R3.06 builds `reef executor run` against `docs/executor-protocol.md`: claim with a wait and its kinds and labels; `Client::issue_session_key(…, Actor::Executor, …)` once per job; materialize `tree_id` (checking it); map kinds and targets to what runs; upload with `upload_artifact_file`; sign with `Claim::sign`; send evidence and progress in `UpdateJob`; complete `DONE` with a summary per pair, or `BUDGET_EXHAUSTED` or `FAILED`. Locally over the socket, in CI over the remote listener with a token linked to a `ci` identity. Any gap it finds is fixed in the spec, with the protocol version unchanged unless an executor would have done the wrong thing." Its out-of-scope list gave this ticket "getting the tree's content, mapping kinds and targets to what runs (in the executor's configuration or a declaration in the repository at that tree, R3.06's choice), the sandbox, issuing a session key per job, uploading, signing, and an executor command line (`reef executor run`) usable locally and in CI".
- **R3.03** fixed the signer: "R3.06's executor, locally: issues one key per run, `actor: executor`, bound to the default person identity. In CI: does the same over the remote listener, with a token linked to the `ci` identity." It also fixed where the key lives: "Only in the process that generated it… No session key is ever written to disk by Reef."
- **R3.01 and R3.02**: "R3.06 signs with `reef-evidence` and an R3.03 key, and adds by tree with no `revision`"; "R3.06 uploads with `reef_client::Client::upload_artifact_file`, then adds by tree."
- **The spec's section 8**, "What a trusted executor must do": run where the submitting agent cannot reach; never run a command or a shell built from request strings; one session key per job, in memory, actor `executor`; report `error`, not `pass`, when unsure; check that what it ran on is exactly `tree_id`.
- **RX.01's threat model** left a sandbox for this ticket to build and for #62 to share: "Sandboxing `reef ws run` or a store build (user namespaces, seccomp, a build container)… Scheduled when a harness asks for it, or when R3.06's executor sandbox exists to share: #62."

This ticket therefore builds:

1. **`reef executor`**: `run` (the claim loop of the spec's section 3) and `check` (configuration, sandbox probe, and what a revision declares), in a new crate, `reef-executor`, that links no jj-lib and no daemon.
2. **Declarations**: what runs for a kind and a target, from the executor's configuration (`executor.toml`) or from a file in the repository at the job's tree (`reef-checks.toml`), with the executor's configuration deciding what a repository may declare.
3. **Materialization**: the job's tree, read through `FileService` at the job's commit into a private directory, with every blob and the tree itself checked against their git object ids before anything runs.
4. **The sandbox**: Seatbelt (`sandbox-exec`) on macOS and bubblewrap on Linux, denying the network, writes outside the job's directory, the user's home, Reef's state and configuration, the daemon's socket, and the executor's own process. Without one, the executor refuses to start unless configured with `kind = "none"`.
5. **Results**: an exit status becomes a signed summary per requested pair, logs become uploaded artifacts, and the job completes as the spec says.

What stays out is listed under "Out of scope". The largest moves: parsing test reports into per-test objects goes to R3.22, which needs them; a workspace-backed materializer for very large trees, containers, and seccomp and landlock hardening become follow-up issues.

### What was verified while writing this ticket

Reef at `2600ca08` (R3.05 merged; API revision 19, `reef-api/src/lib.rs:49`; `EXECUTOR_PROTOCOL` 1, `:135`; database schema 11, migrations up to `0011_jobs.sql`; ADR 0059 the latest, so the next is 0060; the threat model's last row is S-81). Paths are under `crates/` unless they start with `docs/`, `sdk/`, `scripts/` or `.github/`.

- **The client already has every call this needs.** `claim_job`, `update_job`, `complete_job` (`reef-client/src/lib.rs:1823` on), `issue_session_key(identity, actor, lifetime, session)` (`:2000`), which generates the key in-process and returns a `SessionKey` whose PKCS#8 PEM is `Zeroizing` (`:2175`), `upload_artifact_file_as(repo, path, sha256)` (`:1631`), and `get_repository` (`:790`). `reef_evidence::Claim` (`reef-evidence/src/statement.rs:208`) carries `kind`, `result`, `target`, `started_on`, `finished_on`, `artifacts` and free `annotations`, and `Claim::sign` (`:345`) signs it over a `TreeDigest`. `docs/evidence.md` says of annotations: "Reef never reads it and never defines a field in it", so the executor's own fields go there.
- **The fake executor** in `reef-daemon/tests/executor.rs:1760` (`FakeExecutor::run_one`) runs the spec's loop against `reef-client` and `reef-evidence` only: one key per job with `Actor::Executor`, a log uploaded by digest first, summaries and finer objects over several `UpdateJob` calls, then `DONE`. The reference executor is that loop with real work in the middle.
- **The `reef` binary links no jj-lib.** `reef-testing/tests/crate_graph.rs` checks that `reef-vcs` reaches only `reef-client`, `reef-api` and `reef-error` among Reef crates and nothing of jj (lines 3 to 12, 41 to 52). So the executor cannot check out a tree with jj-lib or reach the daemon's materialization backends (`reef-daemon/src/backend`); it gets a tree through the API, or through a workspace the daemon makes.
- **`FileService` reads any revision without a workspace.** `ListFiles` (`reef-api/proto/reef/api/v1/files.proto:45`) is paged, and recursive lists every non-directory entry. `FileEntry` (`:117`) has `path`, `type` and `file_id`, "the content's id in the store", which with jj's git backend is the git blob id (ADR 0011: trees and commits are git object ids until Phase 4). `EntryType` (`:83`) is `FILE`, `EXECUTABLE`, `SYMLINK`, `DIRECTORY`, `CONFLICT` or `SUBMODULE`. `ReadFile` (`:142`) returns at most 1 MiB from an `offset`, the file's `size`, and the `commit_id` it read. Both are `READ`, so a remote `write` token linked to an identity (which a claim needs) can call them (S-80).
- **A workspace is a heavier route.** `CreateWorkspaceRequest` (`workspaces.proto:377`) starts from `change` or `new_on`, takes a `path` and a `ProvenanceDeclaration` (actor included), and the daemon materializes it from its base cache (ADR 0015) with a copy-on-write backend, which is fast. But every workspace has a watcher (`WatcherKind` is `NOTIFY` or `WATCHMAN`, fixed at create; there is no unwatched kind), so a check's writes to tracked files are snapshotted into the repository; it records operations; it starts a provenance session; and agents see it in `ws list`. `ReleaseWorkspace` "takes a final snapshot, forgets the jj workspace, and removes the directory".
- **A job may have no commit.** `JobSpec.commit_id` is set only when the job was submitted by revision (R3.05, "The request"); `reef job submit --tree` and `SubmitJob(tree_id)` leave it empty. `FileService` and `CreateWorkspace` take revisions, not trees.
- **Hashes.** `ring` (already in `reef-client`) has SHA-1 only as `SHA1_FOR_LEGACY_USE_ONLY`, with no collision detection. `sha1dc`, the collision-detecting SHA-1 that git uses, is already in `Cargo.lock` (0.1.5, through jj-lib's gix), so `cargo deny` has already passed it.
- **Session keys.** `[session_keys] lifetime` defaults to 1 hour and `max_lifetime` to 24 hours; a request may ask for 5 minutes up to the maximum (`reef-daemon/src/config.rs:743`). Renewal is a new key in the same `session` (R3.03, "Renewal"). A job's `wall_time` may be up to 6 hours (`[executor] max_wall_time`).
- **Remote connection** is configured by `REEF_REMOTE`, `REEF_REMOTE_TOKEN` and `REEF_REMOTE_FINGERPRINT` (`reef-client`). The token is a bearer secret for the identity it is linked to: a process holding it can issue `ci` session keys.
- **Configuration files.** The client reads three keys of `<state>/config.toml` (`reef-client/src/paths.rs:22`), the file the daemon parses strictly, and the daemon already has an `[executor]` section (R3.05, the queue's limits). The repository's own file is `reef.toml` (ADR 0021), parsed strictly by the daemon at every create: unknown keys are errors (decision 3), so a new table in it would break workspace creation on every daemon that predates it.
- **The CLI.** The root help is exactly 512 bytes against its budget (`reef-vcs/src/cli/help.txt`); `job` is in `--help-all` only. Every command has an `OUTPUTS` row (`reef-vcs/src/cli/schema/outputs.rs:182`). Exit codes are by `ErrorKind`, 1 to 9 (`reef-error/src/lib.rs:64`).
- **CI.** `ci.yml`'s Linux legs run on GitHub-hosted `ubuntu-24.04`. Its macOS legs run on the self-hosted runner `reef-mac` when `MACOS_RUNNER` is `self-hosted` (`ci.yml:171`), and that runner runs everything it starts under `sandbox-exec -f runner.sb` (`scripts/mac-runner.sh:163`). A process already in a Seatbelt sandbox is expected to be refused a second `sandbox_apply`; this has to be confirmed on `reef-mac` first ("Implementation notes"). Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor (`kernel.apparmor_restrict_unprivileged_userns`), which makes `bwrap` fail with "setting up uid map: Permission denied" unless bwrap has an AppArmor profile allowing `userns` or the restriction is lifted. Whether the hosted runner image lifts it is also confirmed first.
- **Issues.** #61 (open, phase-3): run store builds in the client's process, not the daemon. #62 (open): "An optional sandbox for `reef ws run` and for store builds… Scheduled when a harness asks for it, or when R3.06's executor sandbox exists to share an implementation."

## Decisions

### Size

L. The work divides like this:

| Part | Size |
| --- | --- |
| `executor.toml` and `reef-checks.toml`: parsing, validation, precedence, target matching | about 600 lines |
| Materialization: listing, fetching, the blob cache, the job directory, the tree and blob checks | about 600 |
| The sandbox: the policy type, Seatbelt profiles, bubblewrap arguments, `none`, the probe | about 700 |
| Running a check: environment, process tree, timeouts, CPU accounting, logs, kills | about 450 |
| Results: claims, summaries per pair, annotations, artifact uploads, batching into `UpdateJob` | about 350 |
| The loop: claims, keys and renewal, heartbeats, cancellation, release, signals, concurrency | about 500 |
| `reef executor run` and `check`, JSON types, `reef schema` rows | about 400 |
| `docs/executor.md`, ADR 0060, the threat model, the spec's edits | prose, about 450 lines |

What stays out to keep it L, each with its ticket or issue under "Out of scope":

- Parsing test reports (JUnit XML) into per-test evidence objects: R3.22, whose behavioral diff needs per-test outcomes and is the first consumer. This ticket uploads declared reports as artifacts unparsed.
- A materializer backed by a Reef workspace, for trees too large to read file by file: a follow-up issue.
- Seccomp filters and landlock on Linux, beyond bubblewrap's namespaces: a follow-up issue.
- Containers or images per check: an adapter executor's business, not the reference's.
- Sandboxing `reef ws run` and store builds (#62): this ticket builds the sandbox so #62 can reuse it, and does not wire it in.

### Where it lives: a new crate, `reef-executor`

`crates/reef-executor` is a library with no jj-lib, no daemon, and no SQLite, depending on `reef-client`, `reef-api`, `reef-evidence` and `reef-error` (and `tokio`, `serde`, `toml`, `nix`, `libc`, `sha1dc`, `globset`, `etcetera`, `zeroize`, `tracing`, all in the lockfile). `reef-vcs` depends on it for `reef executor`, the way it uses `reef-client`; `crate_graph` gains it with the same no-jj rule as `reef-vcs`. A crate of its own keeps the executor's tests, its platform code and its sandbox apart from the CLI, and gives #62 a sandbox to depend on without the CLI.

Modules: `config` (both files), `declare` (matching pairs to checks), `materialize` (listing, blob cache, checks), `sandbox` (`Policy`, `macos`, `linux`, `none`, `probe`), `run` (one check as a process), `result` (claims and summaries), `job` (one job end to end), `serve` (the loop), and `probe` (the escape probes, also run by `reef executor check`).

The sandbox module takes a `Policy` (readable, writable and hidden paths, network level, environment) and an argv, and returns a `std::process::Command` to spawn. It knows nothing about jobs, so #62 can call it from `reef ws run --sandbox` later.

### What runs: declarations

A **check** is one declared command. A job's pairs (R3.05: `kinds × targets`, or each kind with no target) are matched to checks, and each matched check runs as one sandboxed process.

```toml
[[check]]
name = "crate"                        # unique in its file; [a-z0-9][a-z0-9_-]{0,63}
kind = "test"                         # R3.01's kind pattern
targets = ["crates/*"]                # globs over target names this check accepts; absent: none
run = ["cargo", "test", "--workspace", "--offline"]                        # for the pair (test, no target)
run_target = ["cargo", "test", "--offline", "--manifest-path", "{target}/Cargo.toml"]  # per target
timeout = "20m"                       # at most the job's remaining wall time; default: that
network = "none"                      # none | loopback | full; capped by the executor
env = { RUST_BACKTRACE = "1" }        # literal values only
artifacts = ["target/nextest/default/junit.xml"]   # files to upload after the run, tree-relative
error_exit = [75]                     # exit codes that mean "no verdict"; default none
```

- **Two sources.** The executor's configuration (`executor.toml`, its `[[check]]` tables) and the repository at the job's tree (`reef-checks.toml` at the tree's root, read from the materialized and checked tree). The file is new and separate from `reef.toml` because the daemon parses `reef.toml` strictly at every workspace create (ADR 0021 decision 3): a `[[check]]` table there would make every earlier daemon refuse to create workspaces on that commit. The name follows `reef.toml` and R3.07's `reef-policy.*` at the root.
- **Precedence.** For each pair, the executor's own checks of that kind match first: with a target, those whose `targets` match it and that have `run_target`; with no target, those that have `run`. Only when none of the executor's checks match, and `[repository] checks = "allow"`, are the tree's checks tried the same way. A pair nothing matches gets `error` evidence ("Results").
- **What a repository may declare.** The argv, the targets it accepts, a timeout, literal environment variables, artifacts, `error_exit`, and a network level up to `[sandbox] max_repository_network` (default `none`; a higher declaration is lowered to the cap and noted in the evidence). It may **not** name host environment variables to pass through, readable or writable host paths, caches, or the sandbox kind. Those are the executor's (`executor.toml` only), because they are what separates one run from the host and from other trees.
- **Why a repository may declare at all.** Whatever runs on a tree is the tree's code: `cargo test` runs the tree's build scripts and tests, and `just test` runs the tree's `justfile`. A declaration in the tree changes which entry point runs, not whose code runs, so it gives a tree no power over its own verdict that it did not already have. What a tree must not control is the environment around the run, which no repository declaration can reach. A change to `reef-checks.toml` is still a change to how a tree is judged, so it is visible in the proposal's diff, recorded by digest in every object it produced ("Annotations"), and R3.07 and R3.24 should treat the file as policy-sensitive ("What later tickets inherit").
- **Strict executors.** `[repository] checks = "deny"` runs only the executor's own checks, for a CI identity whose operator wants every command reviewed outside the tree.
- **Kinds advertised** in `ClaimJob` are the kinds of the executor's own checks plus `[repository] kinds` (default `["build", "lint", "test"]` when repository checks are allowed). The executor cannot see a tree's declarations before it claims a job on it, so a claimed kind that the tree turns out not to declare gets `error` evidence.
- **The file at a tree** is parsed strictly (unknown keys are errors) with the same schema as the executor's `[[check]]` tables minus the executor-only keys. A file that does not parse, or has more than 64 checks, makes every pair that would have matched it `error` evidence naming the parse error, rather than failing the job: the tree is at fault, not the executor.

### Targets are data

The spec says targets are "matched against what you know how to run and passed as arguments; never build a shell command from them" (S-75). The executor enforces that mechanically:

- **Matching.** A requested target is matched against a check's `targets` globs (`globset`, with `*` not crossing `/` and `**` crossing it). A target that also fails the executor's target pattern, `^[A-Za-z0-9._/:@+=-]{1,512}$` by default (`[declarations] target_pattern`), matches nothing, so no target with spaces, quotes, `$`, `;`, backticks or newlines ever reaches an argv. `..` as a path component is refused by the same rule.
- **Substitution.** `{target}` may appear in `run_target` elements, as a whole element or inside one (`--package={target}`). Each element stays one argv element: there is never a shell between the executor and the program. `{{` and `}}` escape braces; any other `{…}` is a declaration error.
- **Shells are refused as substitution sites.** A declaration whose program's base name is `sh`, `bash`, `dash`, `zsh`, `ksh` or `fish` and that puts `{target}` in the element after `-c` is refused at parse time: that is building a shell command from a request string, with extra steps. `["sh", "-c", "cargo test -p \"$1\"", "sh", "{target}"]` passes the target as data and is allowed.

### Getting the tree: `FileService`, a blob cache, and three checks

The executor reads the job's tree through the API, the same way over the socket and over the remote listener:

1. **List.** `ListFiles(revision: commit_id, recursive: true)`, every page (1,000 entries per page). Each entry has a path, a type and a blob id.
2. **Check the listing.** The executor builds the git tree objects from the entries (mode `100644`, `100755`, `120000` or `160000` by type; directories `40000`; entries sorted as git sorts them, a directory's name compared with a trailing `/`) and hashes them as git does. The root's id must equal `spec.tree_id`. This proves, without trusting anyone's word, that the listing is exactly that tree. A `CONFLICT` entry, a path with an empty, `.` or `..` component, or a path that is both a file and a directory fails the job.
3. **Fetch.** Each blob not already in the cache is read with `ReadFile(revision: commit_id, path)`, 1 MiB at a time, 8 calls at once (a remote token has 32 request slots, and its claims and heartbeats need some). Each blob's bytes must hash, as a git blob (`blob <size>\0<bytes>`, with `sha1dc`), to its listed id. A blob is written to the cache (`<work>/blobs/<2 hex>/<38 hex>`) through a temporary file and a rename, only after its hash matched. `ReadFile`'s `commit_id` must be the job's.
4. **Lay out.** The executor creates `<work>/jobs/<job_id>/tree/` (mode `0700` above it) and, for each entry in path order, makes its parents as directories, copies the blob from the cache (`std::fs::copy`, which clones on APFS and uses `copy_file_range`, so reflinks on btrfs and XFS), and sets mode `0644` or `0755`; a symlink is created with `symlinkat` from its blob's bytes and never followed; a submodule is an empty directory, as jj's working copy leaves it. Every file is created with `O_CREAT | O_EXCL | O_NOFOLLOW`, under directories the executor itself created in this walk, so no entry can write through a link.
5. **Check the disk** (`[materialize] verify = "disk"`, the default). Before the first check runs, the executor hashes the laid-out tree back into a tree id, from the disk and with no reference to the listing, and requires `spec.tree_id` again. This catches a cache file changed after it was verified, and a copy that went wrong. `verify = "listing"` skips this pass for trees where it costs too much; the evidence records which ran.

**Jobs with no commit** (submitted by tree alone) cannot be read through `FileService`, which takes revisions. The executor completes them `FAILED` with "this job names a tree with no commit; submit it with a revision (`reef job submit -r`)". R3.13 and R3.14 submit by revision, so in practice every job they make has a commit. The spec's section 4 gains a sentence saying so.

**The cache** is content-addressed and shared by every job and repository of one executor, bounded by `[materialize] cache_size` (default 4 GiB), evicted least recently used at the end of each job (a hit touches the file's mtime). A blob in the cache was verified when it was written, and the disk check verifies it again in every job that uses it. The cache is never visible inside a sandbox.

**Cost.** One `ReadFile` per new blob. For a tree like Reef's (about 1,100 files) the first job reads everything and later jobs read only what changed; for the synthetic `medium` preset the targets are in "Performance expectations". A tree of 100,000 files (`large`) costs tens of seconds cold, which is why a workspace-backed materializer is a follow-up issue, not a non-goal.

**Why not a Reef workspace.** It would be faster on large trees, since the daemon's base cache and copy-on-write backend already exist (ADR 0015). But every workspace has a watcher, so a check that writes to a tracked file would be snapshotted into the repository's history; each job would record operations and a provenance session in the repository; the job's directory would be listed to every agent by `ws list` and writable by any `EditFiles` naming it; and it works only on the daemon's machine, so CI would need the `FileService` path anyway. One path that works everywhere is checked twice and costs the repository nothing. The follow-up would add `[materialize] source = "workspace"` for local executors on large trees, behind the same three checks.

**Why not a git checkout.** The tree being checked is usually a proposal that exists only in the daemon's store, not on any git remote. An executor on a CI runner may still have its own clone (`actions/checkout`); the follow-up issue can add `source = "git"` for trees already present there, behind the same checks.

### The job's directory

```
<work>/                          [work] dir; default <platform cache dir>/reef/executor, mode 0700
  blobs/                         the verified blob cache
  caches/<repo_id>/<check>/      persistent caches, only for checks with cache = true in executor.toml
  jobs/<job_id>/                 mode 0700, removed when the job ends
    tree/                        the checked tree; the check's working directory; writable
    home/                        the check's HOME, empty at start; writable
    tmp/                         the check's TMPDIR; writable
    out/                         logs, never visible inside the sandbox
```

The platform cache directory is `~/Library/Caches` on macOS and `$XDG_CACHE_HOME` (`~/.cache`) on Linux (`etcetera`, as `reef-client/src/paths.rs` uses). A job's directory is removed when the job ends, whatever its outcome, unless `reef executor run --keep-work`. At start the executor removes every `jobs/` directory left by a crashed run, after taking an exclusive lock on `<work>/lock` so that two executors never share one work directory (a second one gets "another executor uses <work>; give this one its own [work] dir").

### The sandbox

Each check runs in a sandbox built from a `Policy`:

| What | Inside the sandbox |
| --- | --- |
| The job's `tree/`, `home/`, `tmp/` | read and write |
| The check's cache, when `cache = true` | read and write |
| The user's home directory | hidden, except the job's directory and the paths in `[sandbox] read` (toolchains: `~/.rustup`, `~/.cargo`, `~/.nvm`) |
| Reef's state directory (the daemon's socket, database, TLS keys, workspaces), Reef's configuration, `REEF_SOCKET`'s path, `$XDG_RUNTIME_DIR` | hidden, even when under a `read` path |
| `<work>` except this job's directory (other jobs, the blob cache, `out/`) | hidden |
| The rest of the filesystem | read only |
| Network | `none` by default; `loopback` or `full` when the check asks and the executor allows |
| Other processes, the executor's included | not visible or not inspectable |
| Setuid programs | not elevated |
| Environment | built from nothing ("Environment") |

- **Network levels.** `none`: on Linux, a network namespace of its own with only its own loopback, so a test can still bind `127.0.0.1` and reach nothing outside; on macOS, no network at all, Unix-domain sockets included. `loopback`: on Linux the same as `none`; on macOS, the host's loopback, which reaches whatever listens on it (the daemon's web listener among them, which still needs a session token), so it is opt-in. `full`: the host's network, DNS included. The executor's own `[[check]]` tables may ask for any level; a repository's are capped by `[sandbox] max_repository_network`.
- **Hidden, not denied, where the platform allows.** On Linux, hidden paths are replaced by empty `tmpfs` mounts, so the tree's code cannot even see what was there. On macOS, Seatbelt refuses reads, so a hidden path's metadata may be visible (the ancestors of allowed paths must stay statable for `getcwd`).

**macOS: Seatbelt through `sandbox-exec`.** `/usr/bin/sandbox-exec -p <profile> -- <argv>`, with a profile generated per check. `sandbox-exec` is deprecated in its man page but ships with every macOS release; Seatbelt is what Bazel's darwin sandbox and Nix's macOS sandbox use, and it is the only unprivileged sandbox macOS offers a command-line program. The profile, in order, since a later Seatbelt rule overrides an earlier one:

```scheme
(version 1)
(allow default)
(deny network*)                                            ; none; loopback adds the next line
;(allow network* (remote ip "localhost:*") (local ip "localhost:*"))
(deny file-write*)
(allow file-write* (subpath "<job>/tree") (subpath "<job>/home") (subpath "<job>/tmp")
                   (literal "/dev/null") (literal "/dev/zero") (regex #"^/dev/fd/") (regex #"^/dev/tty"))
(deny file-read* (subpath "<home>"))
(allow file-read* (subpath "<job>/tree") (subpath "<job>/home") (subpath "<job>/tmp")
                  (subpath "<each [sandbox] read path>") (literal "<the reef binary, for the probe>"))
(allow file-read-metadata (literal "<each ancestor of an allowed path>"))
(deny file-read* file-write* (subpath "<state dir>") (subpath "<config dir>") (literal "<REEF_SOCKET>")
                             (subpath "<work>/blobs") (subpath "<job>/out"))
(deny process-info* (target others))                       ; no environment or task port of other processes
(deny mach-lookup (global-name "com.apple.SecurityServer") (global-name "com.apple.securityd"))   ; keychain
```

The exact operation names for reading another process's arguments and environment (`sysctl kern.procargs2`) and for task ports are confirmed by the escape probes ("Tests"); if `process-info*` does not cover them, the profile adds the narrower rules the probe shows are needed. The child is started in a new session (`setsid`), and Seatbelt refuses to exec setuid programs, so `sudo` and `/bin/ps` fail inside.

**Linux: bubblewrap.** `bwrap` 0.8 or later, found on `PATH` or at `[sandbox] bwrap`, with an argv generated per check:

```
bwrap --die-with-parent --new-session --unshare-user --unshare-pid --unshare-ipc --unshare-uts
      --unshare-cgroup-try [--unshare-net unless network = full]
      --ro-bind / /  --dev /dev  --proc /proc  --tmpfs /tmp  --tmpfs /run  --tmpfs /var/tmp
      --tmpfs <home>  [--ro-bind <each read path> <same>]...
      [--tmpfs <state dir> and <config dir> when outside home]
      [--ro-bind /run/systemd/resolve /run/systemd/resolve when network = full and it exists]
      --bind <job>/tree <job>/tree  --bind <job>/home <job>/home  --bind <job>/tmp <job>/tmp
      [--bind <cache> <cache>]
      --chdir <job>/tree  --clearenv  --setenv K V ...  --  <argv>
```

The new user, PID and IPC namespaces mean the child cannot see or signal the executor, and bubblewrap sets `PR_SET_NO_NEW_PRIVS`, so setuid programs do not elevate. `--tmpfs /run` hides `$XDG_RUNTIME_DIR` (where the daemon's socket may live, with the session bus and SSH and GPG agents). Killing `bwrap` kills the namespace's init through `--die-with-parent`, and with it every process in the namespace. Bubblewrap needs unprivileged user namespaces: on Ubuntu 24.04 that means an AppArmor profile for `bwrap` granting `userns` (preferred) or `kernel.apparmor_restrict_unprivileged_userns=0`, and in Docker a container allowed to create them (`--privileged`, or a seccomp profile that allows `unshare`). The probe names which.

Why bubblewrap and not namespaces written in Rust: bubblewrap is small, audited, packaged everywhere, and gets the user-namespace, mount and `pivot_root` sequence right, which is exactly the delicate part; reimplementing it is a security bug surface for no gain. Why not landlock alone: it is unprivileged and works in more containers, but as of the kernels in CI it does not govern `connect` to a path-named Unix socket, so it cannot keep the tree's code from the daemon's socket. Landlock and a seccomp filter on top of bubblewrap are the hardening follow-up.

**No sandbox.** `[sandbox] kind` is `auto` (Seatbelt on macOS, bubblewrap on Linux), `seatbelt`, `bubblewrap`, or `none`. With `auto` or a named kind, the executor runs the probe at start; if the sandbox cannot be applied, it refuses to start (exit 6, `Unavailable`), naming why (`bwrap` not found; user namespaces restricted, with the AppArmor fix; already inside a sandbox; `sandbox-exec` missing) and `kind = "none"` as the explicit alternative. With `none`, checks run as plain child processes in the job's directory with the same environment rules, and the executor says so on every start. Whatever the kind, the executor adds the label `sandbox=<kind>` to its claims, so a requester can require `sandbox=bubblewrap` (R3.13's policy can), and records the kind in every evidence object's annotations. `none` exists for executors that are already isolated (a fresh container or VM per run) and for platforms with neither tool.

**Environment.** The child's environment is built from nothing: `PATH` (the executor's, so toolchains are found, and only useful where `read` exposes them), `LANG`, `LC_ALL`, `TZ`, `TERM=dumb`; `HOME=<job>/home`, `TMPDIR=<job>/tmp`; `REEF_CHECK_JOB`, `REEF_CHECK_KIND`, `REEF_CHECK_TARGET` (empty for the whole check), `REEF_CHECK_TREE`, `REEF_CHECK_NAME`; the names in the executor's `[sandbox] pass_env` (such as `RUSTUP_HOME`, `CARGO_HOME`), copied from the executor's environment, never from a repository's declaration; and the check's literal `env`. Nothing else crosses: no `REEF_REMOTE_TOKEN`, no `REEF_SOCKET`, no `GITHUB_TOKEN`, no `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, no `SSH_AUTH_SOCK`. `pass_env` refuses names starting with `REEF_` at parse time.

**Caches.** A check in `executor.toml` with `cache = true` gets a persistent directory, `<work>/caches/<repo_id>/<check>/`, writable inside the sandbox and named by `REEF_CHECK_CACHE` (a check points `CARGO_TARGET_DIR` at it in its `env` with `{cache}`, the one placeholder `env` accepts). Without caches every build starts cold, which for a Rust workspace is minutes. With them, one tree's run can leave files that change another tree's result (a poisoned build output), so caches are off by default, available only to the executor's own checks, never to a repository's, and recorded in the evidence (`cache: true`). An operator whose CI identity must be strict leaves them off (S-85).

**#62.** The `Policy` and the two backends are the sandbox #62 asks for: a workspace and its stores as the only writable paths, the home and state hidden, the network optional. Wiring it into `reef ws run --sandbox` is #62's (a flag, a policy built from the workspace, and its interaction with harness sandboxes), and store builds wait for #61, which moves them out of the daemon. The threat model's "Not boundaries" bullet is updated to say the implementation exists. #62 gets a comment linking this brief when it merges.

### Running a check

- **Process tree.** The child is spawned in a new session (`setsid`), inside the sandbox. A timeout, a budget, a cancellation or a shutdown sends `SIGTERM` to the whole group (on Linux, to `bwrap`, whose namespace then dies), then `SIGKILL` after `[run] kill_grace` (10 seconds). After every check, on macOS, any process still running with its working directory inside the job's directory (`proc_listpids` and `proc_pidinfo`, as the self-hosted runner's hook and the tests already do) is killed; on Linux the PID namespace has already taken them. A check never outlives its job.
- **Timeouts.** A check runs for at most its `timeout` and at most the job's remaining wall time (from the claim, `budget.wall_time`, less a 30-second reserve for uploads and the completion). When the job's wall time runs out mid-check, the check is killed, its pair gets `error` evidence (annotation `stopped: budget`), no further check starts, and the job completes `BUDGET_EXHAUSTED` with what it has.
- **CPU time.** `budget.cpu_time` is checked between checks, against the sum of each check's CPU time as `wait4` reports it (the check's process and the descendants it waited for). Past it, the executor stops and completes `BUDGET_EXHAUSTED`. A check is not stopped mid-run for CPU time: that would need cgroups, which an unprivileged executor does not have everywhere. `usage` in `CompleteJob` reports both totals.
- **Logs.** The check's stdout and stderr go, interleaved, to `<job>/out/<n>-<check>.log`, outside the sandbox's view, capped at `[run] max_log` (16 MiB): past the cap, the rest is counted and dropped, and the log ends with a line saying how many bytes were dropped. The executor's own stderr prints one line per check (`test crates/reef-lib  pass  1m12s`), never the log.
- **Order.** Pairs run one at a time, in the job's spec order (kinds sorted, then targets sorted), and checks within a pair in declaration order, executor's first. `--jobs N` runs N jobs at once, each sequentially. Parallel pairs within one job are left out: they need resource accounting that no ticket asks for yet.

### Results

| How the check ended | Its result |
| --- | --- |
| Exit 0 | `pass` |
| An exit code in `error_exit` | `error` |
| Any other exit code, or a signal the executor did not send (the tree's code crashed) | `fail` |
| Killed by the executor: its timeout, the job's budget, a cancellation, a shutdown | `error` |
| Could not start: the program was not found inside the sandbox, the sandbox refused it, the tree's declaration did not parse | `error` |
| No check matched the pair | `error` |

R3.01 defines `error` as "the check reached no verdict: the runner crashed, timed out, or ran out of budget. Not a failure of the tree", and the table follows it: what the tree's code did is `pass` or `fail`, what happened to the run is `error`.

- **A summary per pair.** Each requested pair gets exactly one object with that kind and target (absent for the whole check), as R3.05's completeness rule requires for `DONE`. With one matched check, its result is the summary's. With several (two `lint` checks for the whole lint), the summary is `fail` if any failed, else `error` if any errored, else `pass`, and each check also gets a finer object whose target is `<target>#<check>` (`#<check>` for the whole check). R3.19 decides how finer objects compose and may name them otherwise; the summary per pair stays.
- **Annotations** (the executor's own fields, which Reef never reads): `executor` (name and version), `job` and `attempt`, `sandbox` (kind and network level), `checks` (for each check that ran: `name`, `source` (`executor` or `repository`), `declaration` (the SHA-256 of the check's canonical TOML, so a reader can tell which declaration produced the object), `exit` or `signal`, `stopped` when the executor stopped it, `wall_ms`, `cpu_ms`), `verify` (`disk` or `listing`), `cache` when a cache was used, and `note` (why a pair is `error`, at most 512 bytes). The envelope stays under R3.01's 64 KiB; the argv is not recorded, since the declaration digest identifies it.
- **Artifacts first.** After each check, its log and its declared `artifacts` (tree-relative regular files, never through a symlink, at most `[run] max_artifact` 64 MiB each and 16 per check, within R3.01's 64 per object) are uploaded with `upload_artifact_file_as`, naming the SHA-256 the executor computed, before the object that names them is sent. An upload that still fails after three tries does not stop the job: the object is sent naming the artifact, which then reads `absent` (R3.02), and its `note` says so.
- **Sending.** Objects are signed as each pair finishes and sent in the next `UpdateJob`, at once if a heartbeat is not due, at most 50 per call. The completing call carries what is left. A refusal of an object (`JOB_EVIDENCE_MISMATCH`, `INVALID_EVIDENCE`) is an executor bug: the executor logs it with the object's id, releases the job, and exits nonzero, since every later job would repeat it.
- **Outcomes.** `DONE` once every pair has its summary, whatever the results. `BUDGET_EXHAUSTED` when the wall time or CPU time ran out. `FAILED` when the job could not be run at all: no commit, the listing or a blob did not match, the materialization failed, the disk check failed. `FAILED`'s `message` names the step.

### Keys

- **One session per job.** After a claim, before any work, the executor issues a key with `issue_session_key(identity, Actor::Executor, None, "")`: the identity is `[executor] identity` (default empty: the default person identity on the socket, the token's linked identity remotely, R3.03's table), the lifetime the daemon's default. When less than 10 minutes of the key's validity remain and the job is still running, it issues the next key in the same session (`session` set to the first key's), so a six-hour job is one session of several keys, and every object is signed by a key valid when the daemon witnesses it (R3.03's witnessed time). Keys and sessions are never shared between jobs.
- **In memory only.** The `SessionKey` lives in the job's task and is dropped when the job ends, which wipes its PEM; ring's key schedule is not wiped (R3.03 says the same). Nothing writes it: not the work directory, not logs, not the child's environment. The claim token is held the same way.
- **The executor's process.** At start it sets `RLIMIT_CORE` to 0, and on Linux `PR_SET_DUMPABLE` to 0, so a same-uid process can neither read `/proc/<pid>/mem` and `/proc/<pid>/environ` nor attach to it, and a crash leaves no core with a key in it. The sandbox already keeps the tree's code from the executor's process; this also covers anything else of the same uid outside it.
- **Issuance failure** (no linked identity, a revoked identity, a refused actor) releases the job and stops the executor with the daemon's error: it is a configuration problem, and every later job would hit it.
- **The remote token.** Read from `REEF_REMOTE_TOKEN` as every client reads it, or from `--token-file`. The child never inherits it ("Environment"); on Linux the PID namespace and `PR_SET_DUMPABLE` keep it from `/proc`, and on macOS the profile's `process-info` rule keeps it from `sysctl kern.procargs2`, which the probes test. `docs/executor.md` recommends `--token-file` on macOS CI runners, where other processes of the runner's uid (the step's shell) also hold the variable.

### The loop

- **Claiming.** `ClaimJob` with `wait` 60 seconds, the configured `lease` (default 60 seconds), `protocol_version` 1, `repos` from `[executor] repos` and `--repo`, and `ExecutorInfo { name, version, kinds, labels }`: `name` from `[executor] name` (default `reef-executor@<host>`), `version` Reef's, kinds as in "Declarations", labels `os=<std::env::consts::OS>`, `arch=<ARCH>`, `sandbox=<kind>`, and `[executor] labels`. A claim response's `protocol_version` above 1 is logged once; one below 1 cannot happen.
- **Heartbeats.** A task per job sends `UpdateJob` every third of the lease, with `JobProgress { phase, done, total, unit: "checks" }` (`phase` is `materialize`, then each check's `<kind> <target>`), and whatever evidence is ready. A lost connection is retried with backoff until the lease would have lapsed, then the job is abandoned (its directory removed, its checks killed): the daemon requeues it.
- **Cancellation and loss.** `JOB_NOT_CLAIMED` from any call (`cancelled`, `lapsed`, `expired`, `wrong_token`, `completed`) kills the running check within `kill_grace`, stops the job, removes its directory, and sends nothing more for it, as the spec says. `JOB_NOT_FOUND` (a forgotten repository) is handled the same way.
- **Shutdown.** The first `SIGINT` or `SIGTERM` stops claiming, kills running checks, sends each running job's ready evidence with `release: true`, and exits 0. A second within 5 seconds exits at once (exit 130 or 143), leaving the leases to lapse.
- **Concurrency.** `--jobs N` (default 1, at most 16) runs N claim loops. Each holds at most one job. Claims of one remote token beyond 16 waiting are answered at once by the daemon (R3.05), which `--jobs 16` stays within.
- **Restart.** The daemon keeps jobs across its own restarts, and extends running leases (R3.05); the executor's calls fail during the restart, are retried, and go on. An executor that restarts has lost its claim tokens, so its jobs lapse and requeue; the stale job directories are removed at its next start.

### Configuration: `executor.toml`

At `<state>/executor.toml` (beside `config.toml`, in a directory every sandbox hides), or `--config <file>`, or `REEF_EXECUTOR_CONFIG`. Parsed strictly; unknown keys are errors with their line. Absent: the defaults, which run only repository-declared checks in the default sandbox.

```toml
[executor]
name = "laptop"                     # default reef-executor@<host>
labels = ["gpu=none"]               # added to os=, arch=, sandbox=
repos = []                          # only these repositories; empty for all
identity = ""                       # the session keys' identity; empty for the default
lease = "60s"                       # 15s to 10m

[repository]
checks = "allow"                    # allow | deny: read reef-checks.toml at the job's tree
kinds = ["build", "lint", "test"]   # kinds to claim for repository-declared checks

[declarations]
target_pattern = '^[A-Za-z0-9._/:@+=-]{1,512}$'

[materialize]
verify = "disk"                     # disk | listing
cache_size = "4GiB"

[work]
dir = ""                            # default <cache dir>/reef/executor

[sandbox]
kind = "auto"                       # auto | seatbelt | bubblewrap | none
bwrap = ""                          # default: bwrap on PATH
read = ["~/.rustup", "~/.cargo"]    # readable inside the hidden home
pass_env = ["RUSTUP_HOME", "CARGO_HOME"]
max_repository_network = "none"     # none | loopback | full

[run]
max_log = "16MiB"
max_artifact = "64MiB"
kill_grace = "10s"

[[check]]                           # the executor's own checks; may also set cache = true
name = "clippy"
kind = "lint"
run = ["cargo", "clippy", "--workspace", "--all-targets", "--offline", "--", "-D", "warnings"]
cache = true
env = { CARGO_TARGET_DIR = "{cache}/target" }
```

`reef config show` is the daemon's and does not print this file; `reef executor check` does.

### The CLI: `reef executor`

```
reef executor run [--config <file>] [--repo <repo>]... [--jobs <n>] [--once [--wait <dur>]]
                  [--exit-when-idle <dur>] [--keep-work] [--token-file <file>]
reef executor check [--config <file>] [-r <rev> [--kind <k>]... [--target <t>]...]
```

- **`run`** serves until stopped. `--once` claims one job, waiting up to `--wait` (default 60 seconds, the claim's maximum, repeated until the wait is spent), runs it, and exits: 0 when it ran a job to any completion or when no job came (`--require-job` turns no job into exit 3, `NotFound`, "no job matched within …"). `--exit-when-idle 5m` exits 0 after five minutes with no job, for a CI step that drains the queue. The CI recipe in `docs/executor.md` is `reef executor run --exit-when-idle 2m` with `REEF_REMOTE`, `REEF_REMOTE_FINGERPRINT` and a token file from a secret. Output: one line per job on stderr (`job job_8f3a… test×2 lint: done  pass 2 fail 1  3m12s`), and with `-o json` (or piped, as brief JSON) one object per finished job on stdout, a JSON line each, as `op watch` prints its stream.
- **`check`** prints the configuration as parsed (sources, kinds, labels, sandbox kind, network caps), runs the sandbox probe ("Tests", test 9) and prints each probe's result, and exits 0 only if the sandbox holds (6, `Unavailable`, when the configured sandbox cannot be applied; 2 for a configuration error). With `-r <rev>`, it also reads `reef-checks.toml` at that revision (through `ReadFile`) and prints, for the given or the advertised kinds and targets, which check each pair would run, from which source, with which argv and network level, without running anything. It is how a repository author checks a declaration and an operator checks a machine.
- **Exit codes** use the existing kinds: a configuration error is 2; a sandbox that cannot be applied is 6 (`Unavailable`), with the probe's reason as `hint` and `reef executor check` as `next`; a daemon error is the daemon error's code.
- **Not in the root help.** Like `job`, `executor` is in `--help-all`, and `help_lists_every_command` gains it. The root help stays byte for byte as it is.
- **JSON** (`reef_client::json`, with `JsonSchema`): `ExecutorJobReport` (job id, repository, outcome or the reason it stopped, counts by result, pairs, elapsed and CPU time, sandbox kind) and `ExecutorCheckReport` (configuration, probes, and the plan for `-r`). Brief views keep the job id, outcome and counts. `reef schema`'s `OUTPUTS` gains rows for both commands.
- **No MCP tool.** `reef executor` calls no new RPC, so `NOT_TOOLS` and `tools/list` are unchanged. Agents do not run executors; an operator does.

### No daemon, API, schema or protocol change

Everything above uses RPCs that exist: `ClaimJob`, `UpdateJob`, `CompleteJob`, `IssueSessionKey` (through `issue_session_key`), `ListAuthorities`, `UploadArtifact`, `ListFiles`, `ReadFile`. API revision stays 19, schema 11, protocol 1, and the SDKs are untouched. The gaps found while writing this brief go into the spec, as R3.05 asked, without changing the protocol:

- Section 4 gains: a job submitted by tree alone has no `commit_id`, so an executor that reads through `FileService` cannot materialize it and completes it `FAILED`; requesters that want any executor to run a job submit it by revision. And: the listing's tree id can be computed from `ListFiles`' entries, and each blob checked against its `file_id`, so a remote executor checks the tree without trusting the daemon's word.
- Section 8 gains a pointer to `docs/executor.md` as one way to meet each requirement.

Whether `SubmitJob` should refuse tree-only jobs, or `FileService` should read by tree, is left to R3.13 and R4.11, which own requesting and remote trees.

  - **Decisions**:
    1. the reference executor is a client in its own crate, `reef-executor`, run as `reef executor`; it links no jj-lib and calls only existing RPCs;
    2. checks are declared in `executor.toml` and, when the executor allows, in `reef-checks.toml` at the job's tree; the executor's own checks take precedence; a repository declares argv, targets, timeout, literal environment, artifacts and exit codes, never the environment around the run;
    3. targets are matched against declared globs and a pattern, substituted as argv elements, and never into a shell script;
    4. the tree is read through `FileService` at the job's commit into a private directory, through a verified blob cache, and checked three times: the listing's tree id, each blob's id, and the laid-out disk; a job with no commit fails;
    5. every check runs in a sandbox (Seatbelt on macOS, bubblewrap on Linux) that hides the home, Reef's state and configuration, the socket and the executor, denies the network by default, and allows writes only in the job's directory; without one the executor refuses to start unless `kind = "none"`, and the kind is a claim label and in every object;
    6. one session per job, keys in memory, renewed within the session, never inherited by a check; the executor's process is non-dumpable with no core files;
    7. exit statuses map to `pass` and `fail`, and anything the run did to the check to `error`; one summary per pair, finer objects per check;
    8. the sandbox is a reusable module for #62.
  - **Alternatives**:
    - declarations only in the executor's configuration (strict, but every repository's checks must be copied to every executor);
    - declarations only in the repository (the environment around the run would be the tree's);
    - a table in `reef.toml` (every earlier daemon would refuse to create workspaces on the commit);
    - materializing through a Reef workspace (fast on large trees; watcher snapshots, operations, provenance, visibility to agents, local only);
    - a git checkout of `commit_id` (the tree is usually only in the daemon's store);
    - trusting the daemon's listing without hashing (the check the spec asks for would be someone else's word);
    - `ring`'s SHA-1 (no collision detection);
    - namespaces written in Rust, or landlock alone, on Linux;
    - containers per check;
    - running unsandboxed with a warning by default;
    - one key per check, or one key for the executor's lifetime;
    - parsing test reports in this ticket.

## Tests

In `crates/reef-executor/` (unit tests per module, and `tests/` with `TestDaemon`, `testing::no_automatic_snapshots` in new fixtures, and no sleeping for a lease: jobs use short wall times and the queue's `Executor::advance` where a lapse is needed):

1. `config`: both files parse with every key; unknown keys, `pass_env = ["REEF_X"]`, `cache` in a repository file, a duplicate check name, `{foo}` in an argv, `{target}` in `run`, a `lease` out of range, and 65 repository checks are refused with their line.
2. `declare`:
   - Precedence: an executor check shadows the repository's for the same pair; a repository check fills a pair the executor lacks; `checks = "deny"` ignores the repository file.
   - A pair nothing matches, a kind the tree does not declare, and a repository file that does not parse each yield an `error` plan with a `note`.
   - A repository's `network = "full"` is lowered to `max_repository_network` and noted.
   - The kinds advertised are the executor's plus `[repository] kinds`.
3. `targets` (S-88): `crates/reef-lib` matches `crates/*` and not `crates/**/tests`; `a b`, `$(id)`, `;rm`, `x\ny`, `../etc`, and 513 bytes match nothing; `--package={target}` substitutes inside one element; `["sh", "-c", "test {target}"]` and `["/bin/bash", "-c", "{target}"]` are refused at parse time; `["sh", "-c", "… \"$1\"", "sh", "{target}"]` is accepted; `{{` is a literal brace.
4. `materialize` (S-86), against a `TestDaemon` repository holding regular, executable, symlinked, nested, empty and 3 MiB files and a submodule entry:
   - The listing's computed tree id equals the commit's tree (compared with jj-lib's, a dev-dependency), and the laid-out disk hashes to it with `verify = "disk"`.
   - A listing altered in a test double (one id changed) fails with the listing step named; a blob whose bytes are altered fails the blob step and never enters the cache; a cache file changed after it was written fails the disk step on the next job.
   - A symlink is created, not followed; an entry `a/b` under a symlink `a` and a path with `..` fail the job before anything is written.
   - A second job on a tree with one changed file reads exactly one blob (counted).
   - A job with no `commit_id` completes `FAILED` with the message above.
   - The cache stays under `cache_size`, evicting the least recently used.
5. `run_job` over the socket, with a repository whose `reef-checks.toml` declares `test` per target (`sh -c 'exit "$1"' sh {target}`, with targets `0`, `1` and `75` and `error_exit = [75]`) and a whole `lint` with two checks:
   - `reef job submit -r @ --kind test --kind lint --target …` then `reef executor run --once` completes `DONE`; coverage has `pass`, `fail` and `error` for the three test targets and `fail` for lint (one of its two checks fails), with finer `#<check>` objects for lint.
   - Every object is signed by a key with actor `executor`, bound to the default identity, one session for the job; `ListEvidence(job_id)` lists them, and each names its uploaded log, which reads `stored`.
   - The annotations carry the sandbox kind, the source and declaration digest of each check, and `verify`.
   - Progress phases are seen by a presence subscriber (`materialize`, then each pair).
   - The work directory holds nothing of the job afterwards.
6. `remote`: the same over the remote listener with a token linked to a `ci` identity (`--token-file`); the evidence reads `BOUND` to `ci-main`. With `[repository] checks = "deny"` and an executor-declared `test`, the tree's file is not read, and the objects' `source` is `executor`. With `cache = true`, the second job sees the first's cache file, and the objects record `cache`.
7. `budgets_and_kills` (S-89):
   - A check that sleeps past the job's wall time is killed, its pair is `error` with `stopped: budget`, later pairs do not run, and the job completes `BUDGET_EXHAUSTED`. A check past its own `timeout` is `error` with `stopped: timeout`, and the job goes on.
   - A check that forks a background child that ignores `SIGTERM` and calls `setsid`: after the job, no process of the check is alive (the child writes its pid; `kill(pid, 0)` fails), on both platforms.
   - `cpu_time` exhausted after the first check stops before the second.
   - A log over `max_log` is truncated with the dropped count.
8. `cancel_release_and_signals`: a job cancelled mid-check stops within a third of the lease, its check killed, nothing more sent; `SIGTERM` to `reef executor run` releases the running job (it returns to `QUEUED`) after sending finished pairs, and exits 0; a second signal exits at once.
9. `sandbox_probe` (S-82, S-83, S-87): `reef executor check` runs each probe as `reef executor __probe <name>` inside the configured sandbox and reports pass or fail as JSON. Each must be refused inside the sandbox and allowed in a control run without it:
   - connect to a Unix socket in a fake state directory, and to `REEF_SOCKET`'s path (a listener the test opens);
   - TCP connect to a listener on the host's loopback (`none`), and succeed with `loopback` on macOS; on Linux, binding the private loopback succeeds;
   - read a file in the (fake) home outside `read`, in the state and configuration directories, in the blob cache, and in another job's directory;
   - write outside the job's directory (home, `/tmp` on the host, the work directory);
   - read the executor's environment (Linux: `/proc/<ppid>/environ`; macOS: `sysctl kern.procargs2` on the executor's pid) and see or signal its pid;
   - exec a setuid program (`sudo -n true`) and gain privileges;
   - see a variable the executor had (a canary `REEF_REMOTE_TOKEN`) in the child's environment.

   The sandbox's paths (home, state, configuration, socket) are parameters of `Policy`, so the tests point them at temporary directories and never touch the real ones. With `kind = "none"`, the probe reports every escape as possible and `check` exits 0, saying so.
10. `sandbox_build`: a small Rust crate (a dev fixture with a build script and a test) builds and tests with `cargo test --offline` inside the sandbox with the toolchain in `read`, so the profile does not break a real toolchain on either platform (the macOS keychain rule included).
11. `secrets`: after a full job, no session key PEM, signing seed, claim token or remote token appears in the work directory, the executor's stderr, the `-o json` output, the logs uploaded, or any file the check could write (a scan for each secret's text).
12. `concurrency`: `--jobs 3` with three queued jobs runs them at once, each in its own directory, with separate sessions.

In `crates/reef-vcs/` (`tests/cli.rs`, `tests/schema.rs`):

13. `executor_cli`: `reef executor check` without a sandbox available (a `bwrap` path that does not exist) exits 6 with the probe's reason as `hint` and `next`; with a bad config exits 2 naming the line; `check -r @` prints the plan for each pair; `run --once --wait 1s` with no job exits 0, and with `--require-job` exits 3; every command's `-o json`, `-o brief` and piped output validates against `reef schema`; `--help-all` lists `executor`, and the root help is unchanged.

In `crates/reef-testing/`: `crate_graph` with the new crate and its rule.

## Implementation notes

- **Order**:
  1. Confirm the two CI facts first: nested `sandbox-exec` on `reef-mac`, and `bwrap` on the hosted `ubuntu-24.04` image (with and without the AppArmor fix). Record both in the PR; they decide test 9's CI wiring.
  2. `config` and `declare` (tests 1 to 3).
  3. `materialize` (test 4): the git tree hash first, checked against jj-lib's ids in tests.
  4. `sandbox` and the probes (tests 9, 10), macOS and Linux side by side; write the Seatbelt profile from the probes' failures, not from memory.
  5. `run` and `result` (test 7), then `job` and `serve` (tests 5, 6, 8, 11, 12), then the CLI (13), then the documents.
- **The git tree hash.** Entries sorted by git's rule: compare names as bytes with a directory's name followed by `/`. Mode text without leading zeros (`40000`). The tree object is `tree <len>\0` then `<mode> <name>\0<20-byte id>` per entry. Build bottom up from the sorted path list. A unit test checks a few trees against `git mktree`/`git write-tree` fixtures embedded as ids, so the hash does not need git at test time.
- **Linux**: `PR_SET_DUMPABLE`, the bwrap backend and the `/proc` probes are `cfg(target_os = "linux")`; build and lint them in the privileged container, since macOS never compiles them.
- **macOS**: `proc_listpids`/`proc_pidinfo` through `libc`; the Seatbelt profile is generated text with every path escaped for SBPL string literals (a path with `"` or `\` in it is escaped, and a control character refuses the configuration).
- **Paths in profiles** are canonicalized (`/var` is `/private/var` on macOS; Seatbelt matches real paths), and `~` in `read` expands to the executor's home.
- **No new crate.** `sha1dc`, `globset`, `etcetera`, `nix`, `libc`, `toml`, `zeroize` are in the lockfile. `cargo deny check` must pass unchanged.

## Risks

- **A sandbox gives a false sense of safety.** Seatbelt is deprecated, under-documented, and permissive by default (`allow default`); bubblewrap is only as strong as the kernel's namespaces. Mitigations: the probes test each property this brief claims, on each platform, in CI; the threat model lists what stays reachable; the docs say a trusted CI identity should run on a fresh VM or container anyway; RX.02 reviews the profiles.
- **Seatbelt may disappear.** Apple has deprecated `sandbox-exec` for years without removing it. If a macOS release removes it, the probe says so and `kind = "none"` (or a VM) is what remains; Bazel, Nix and others would be in the same place.
- **CI may not be able to run the sandbox.** Ubuntu 24.04's AppArmor restriction and the self-hosted Mac's own sandbox are both possible blockers. Mitigation: confirm both first; the AppArmor profile or sysctl for Linux, and the hosted macOS job if nesting fails.
- **Real toolchains may break inside the profile.** Cargo writes a lock under `CARGO_HOME`, Xcode tools talk to mach services, and Node toolchains look in the home. Mitigations: test 10 builds a real crate; `read`, `pass_env` and caches are the operator's knobs; `docs/executor.md` carries worked examples, starting with Reef's own (what cargo needs offline is settled by the dogfood run and written down).
- **Reading trees file by file is slow for large repositories.** Mitigations: the blob cache makes later jobs cheap; the benchmarks measure it; the workspace-backed materializer is a filed follow-up.
- **Trust is easy to misread, again.** A `pass` from the reference executor means the tree's own tests exited 0 in a sandbox, not that the tests are good. Mitigations: the docs' wording; R3.22 and R3.24 are the answer to circular evidence; the annotations say exactly which declaration ran.
- **Process cleanup on macOS** relies on finding stray processes by working directory; one that changes its directory out of the job's escapes. Mitigation: documented in S-89; Linux has the PID namespace; a VM is the complete answer.

## Choices this brief made, and why

- **Both declaration sources, the executor's first**, because the tree's code runs either way, so a repository declaring its entry point costs nothing in trust, while the environment around the run stays the executor's.
- **A separate `reef-checks.toml`**, because a table in `reef.toml` would break workspace creation on every earlier daemon.
- **`FileService` with a verified cache, not a workspace**, because it works the same locally and in CI, leaves the repository untouched, and checks the tree without trusting anyone's word.
- **Three hash checks**, because "materializes the tree hash and checks it" should be a check the executor makes itself.
- **Seatbelt and bubblewrap**, because they are the unprivileged sandboxes each platform offers and others already depend on, and the delicate parts are theirs.
- **Refusing to run unsandboxed by default**, because a trusted executor that silently runs a tree's code with the user's privileges is the failure this ticket exists to prevent.
- **Caches opt-in and executor-only**, because speed matters, but one tree must not be able to change another's verdict without the operator choosing it.
- **One session per job, renewed**, because R3.03's keys are short and R3.05's jobs can be long, and a key must not outlive or be shared beyond its job.
- **No protocol change**, because R3.05 got the messages right for this executor, and the gaps found are wording in the spec.
- **Report parsing in R3.22**, because its first consumer is there and this ticket is already L.

## Decisions for the user

The user accepted all twelve recommendations on 2026-11-07.

1. **Where checks are declared.** Both: the executor's `executor.toml` and, unless the executor sets `[repository] checks = "deny"`, a new `reef-checks.toml` at the job's tree; the executor's checks take precedence; a repository declares argv, targets, timeout, literal environment, artifacts and exit codes, but never environment pass-through, host paths, caches, the sandbox kind, or more network than `max_repository_network` (default `none`). *Recommended*: as stated, with `allow` as the default. The alternatives are executor configuration only, or a `[[check]]` table in `reef.toml` (which breaks earlier daemons).
2. **Targets.** Matched against each check's `targets` globs and the executor's pattern (`^[A-Za-z0-9._/:@+=-]{1,512}$`), substituted as argv elements, refused after a shell's `-c`; an unmatched pair gets `error` evidence. *Recommended*: yes.
3. **Results.** Exit 0 `pass`, `error_exit` codes `error`, other exits and the tree's own crashes `fail`, and anything the executor did to the run (timeout, budget, cancel, start failure, no matching check) `error`; one summary per pair (fail over error over pass), finer `#<check>` objects when several checks ran; logs and declared files uploaded first. *Recommended*: yes, with report parsing moved to R3.22.
4. **Materialization.** `FileService` at the job's commit into a private job directory, through a content-addressed blob cache (4 GiB), with three checks (listing, blobs with `sha1dc`, disk), and `FAILED` for jobs with no commit. *Recommended*: yes. The alternative is a Reef workspace on the commit (faster on huge trees, but snapshots, operations, provenance and visibility to agents, local only), which becomes a follow-up issue.
5. **The sandbox.** Seatbelt (`sandbox-exec`) on macOS and bubblewrap (an external `bwrap` 0.8+) on Linux; the home, Reef's state and configuration, the socket, `$XDG_RUNTIME_DIR`, other jobs and the cache hidden; writes only in the job's directory; network `none` by default; processes isolated; environment built from nothing. *Recommended*: yes. The alternatives are namespaces in Rust, landlock alone (cannot block the socket), or containers.
6. **No sandbox available.** Refuse to start unless `kind = "none"` is configured; label claims `sandbox=<kind>` and record it in every object. *Recommended*: refuse. The alternative is to run unsandboxed with a warning.
7. **Caches.** Opt-in per check in `executor.toml` only (`cache = true`), never from a repository, recorded in the evidence. *Recommended*: yes. The alternatives are no caches (every build cold) or caches a repository can ask for.
8. **Keys.** One session per job, the first key issued after the claim with the daemon's default lifetime and renewed within the session when under 10 minutes remain; in memory only; the executor non-dumpable with no core files; a key issuance failure releases the job and stops the executor. *Recommended*: yes.
9. **The CLI.** `reef executor run` (`--once`, `--exit-when-idle`, `--jobs`, `--token-file`, `--keep-work`) and `reef executor check` (configuration, sandbox probes, and the plan at a revision), both in `--help-all` only; configuration at `<state>/executor.toml`; one JSON line per finished job. *Recommended*: yes.
10. **Packaging.** A new crate, `reef-executor`, under `crate_graph`'s no-jj rule, with the sandbox a public module for #62; no daemon, API, schema, protocol or MCP change; ADR 0060. *Recommended*: yes.
11. **CI for the sandbox.** Linux: install bubblewrap and apply an AppArmor profile (or the sysctl) in the hosted job. macOS: if a nested `sandbox-exec` fails on `reef-mac`, add an `executor sandbox (macos-15, hosted)` job on `main` and `macos`-labelled PRs, and skip the Seatbelt tests with the reason on `reef-mac`. *Recommended*: yes. The alternative is to verify Seatbelt by hand only.
12. **Dogfooding.** Add `reef-checks.toml` to Reef's own root (`lint`: rustfmt; `test`: per crate), used for the manual verification and the docs' example, not run by CI. *Recommended*: yes.
