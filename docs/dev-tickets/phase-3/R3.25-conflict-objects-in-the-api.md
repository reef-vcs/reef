# R3.25 Conflict objects in the API

Phase 3 · Size M, with the scope lines below · Depends on: R3.04 (provenance records found by change, `ListProvenance`, `GetProvenance(commit_id)`), and builds on R2.02 (revisions, `Change`, the diff and its binary rule), R2.12 (reads at an operation), R3.07 (`reef_policy::input::ConflictInput`, `conflict_tier`) and R3.09 (`Change.lifecycle`) · Unblocks: R3.26, R3.27, R3.35, R5.01; through them R3.28, R3.29, R3.30 and R5.03

## Context

The design calls conflicts first-class in three places. Principles: "A merge that conflicts still produces a valid snapshot containing the conflict. It can be stored, pushed, handed to a resolver agent, or fixed later. Nothing blocks." Data model, Conflicts: "A conflicted snapshot stores each hunk as a structured record: the base, each side, and the sides' snapshot hashes. The working copy renders this as markers for tools that need text, but the API exposes it as data." Human interface: a conflict object "is assigned automatically to a resolver, by default the originating agent of the later change, which sees base, both sides, and the task and instruction behind each … marked as a resolution so the reviewer sees both sides' provenance."

jj-lib already stores the conflict. Reef today reports only that one exists: `Change.conflict` (a bool), `GetStatus`'s conflicted change ids and paths, `ReadFile`'s materialized markers, and the diff's `conflict` flag. Nothing says which sides there are, where each came from, or who wrote them.

Five later tickets read what this ticket builds:

- **R3.26** (agent-scoped undo) "attaches a conflict object naming the undone operation to the dependent".
- **R3.27** (resolver assignment) assigns "to the originating agent of the later change" and queues conflicts "whose owner's session has ended".
- **R3.28** (tiers and caps) "builds the conflict input from R3.25's objects" for R3.07's `conflict_tier`, and caps attempts "per conflict".
- **R3.35** (conflict view) shows "base and both sides with provenance, resolver status, tier, attempts".
- **R5.01** (merge engine) returns "either a merged tree or a conflict object", and R5.03 maps Mergiraf's output "into Reef's conflict objects".

R3.07 left a seam: `ConflictInput { change_id, paths, sides: [{change_id, identity, agent}] }`, "R3.25 to R3.28 fill it from conflict objects and may add fields". R3.04 left another: "R3.25 reports each side's provenance as `ListProvenance(change_ids: [the side's change])`, plus the record of the exact side commit when one exists (`GetProvenance(commit_id)`)."

So this ticket builds a read, and nothing that acts on it:

1. **The object**: one record per conflicted commit, built from jj's stored conflict: every term (sides and bases) with jj's label and the commit it came from, every conflicted file with each term's value, and, on request, the file's hunks.
2. **Attribution**: which commit each term came from, read from jj's conflict labels and checked against the content, so a label cannot pin a side on someone else.
3. **Provenance per side**: R3.04's records of the side's change, summarized, plus the exact commit's record.
4. **The surface**: `ConflictService.ListConflicts` and `GetConflict` (READ, the next API revision), `reef conflict list|show`, and `--policy-input` for R3.28's seam.

Nothing is stored. Assigning, tiering, resolving and the view are later tickets ("Out of scope").

### What was verified while writing this ticket

Reef at `e127a19d` (R3.08 merged; API revision 22, `reef-api/src/lib.rs:49`; `SERVED` has 21 services, `reef-daemon/src/server.rs:76`; database schema 12, migrations up to `0012_lifecycle.sql`; ADR 0063 the latest on main). Three tickets run in parallel: R3.13 takes ADR 0064 and S-119 to S-126, this ticket ADR 0065 and S-127 to S-134, R3.42 ADR 0066 and S-135 to S-142. Whichever merges later renumbers its API revision. Paths are under `crates/` unless they start with `docs/` or `web/`. jj-lib 0.47.0 re-exports most of its model from a new crate, `jj-core` 0.47.0 (`jj_lib::merged_tree` is `jj_core::merged_tree`); the line numbers below are `jj-core`'s.

- **A conflict is a tree-level `Merge` with labels.** A commit stores `root_tree: Merge<TreeId>` and `conflict_labels: Merge<String>` (`backend.rs:200`); `Commit::tree()` is a `MergedTree` of both (`commit.rs:128`). A `Merge` of arity *n* has *n* adds (sides) and *n − 1* removes (bases), interleaved side, base, side, … (`merge.rs:261`, `:266`, `:316`). Two-sided conflicts are the common case; jj makes wider ones (an octopus merge, a rebase of a conflicted commit).
- **Per path, the terms keep their alignment.** `MergedTree::conflicts()` (`merged_tree.rs:199`) walks into subtrees only where every term is a tree and yields `(path, MergedTreeValue)`, where `MergedTreeValue` is `Merge<Option<TreeValue>>` with the root's arity, unsimplified (`ConflictsVisitor`, `:533`). So term *i* at a path is term *i* of the tree, and its label is label *i*. A file/directory conflict is one entry, not one per path below it.
- **Term trees are not the source commits' trees.** `merge_trees` (`tree_merge.rs:54`) writes every entry it can resolve into every term, and keeps per-term values only where it cannot. A term's root tree id therefore names no commit after a real rebase; a conflicted path's per-term value is the source commit's value at that path.
- **Labels are free text in a known shape.** jj-lib writes `Commit::conflict_label()` (`commit.rs:229`): `"{change:.8} {commit:.8} \"{subject}\""`, the change id in reverse hex (`k`–`z`) and the commit id in hex, control characters stripped from the subject; several commits are joined with `", "` in their short form (`conflict_label_for_commits`, `:264`). Rebase appends ` (rebase destination)`, ` (parents of rebased revision)` and ` (rebased revision)` (`jj-lib rewrite.rs:271`–`:283`); restore and squash append ` (original revision)`, ` (squash destination)` and others (`:383`–`:398`, `:1332`). Conflicts written before labels existed, and by other clients, may have none (`ConflictLabels::unlabeled`, `conflict_labels.rs`), and any client can write any label.
- **Hunks are computed, not stored.** `jj_core::files::merge_hunks(&Merge<T>, &MergeOptions) -> MergeResult` (`files.rs:311`) returns `Resolved(bytes)` or `Conflict(Vec<Merge<BString>>)`, each hunk resolved or one text per term. `try_materialize_file_conflict_value` (`conflicts.rs:265`) gives a file conflict's simplified ids, labels and contents; `resolve_file_executable` (`:291`) the merged executable bit.
- **Predecessors and prefixes are reachable.** `jj_lib::evolution::walk_predecessors` (`evolution.rs:84`) walks a change's earlier commits through the operation log; `Index::resolve_commit_id_prefix` (`index.rs:69`) resolves a short commit id, hidden commits included while they are indexed.
- **What Reef reports about conflicts today.** `ChangeInfo::conflict` from `commit.has_conflict()` (`reef-lib/src/jj/log.rs:66`, `:211`) becomes `Change.conflict` (`changes.proto:194`); `reef_lib::jj::diff::conflicted_paths` (`diff.rs:830`) lists a commit's conflicted paths, used by `GetStatus` with `mutable() & conflicts()` for change ids (at most 100) and up to 1,000 paths for a workspace (`service/status.rs:40`, `:179`, `:214`); `ReadFile` returns jj's materialized markers for a conflict (`reef-lib/src/jj/files.rs:201`–`:225`), and the diff writes them in jj's `Diff` marker style (`diff.rs:369`). Conflicted changes are refused by R3.09's `PROPOSED` (`CHANGE_CONFLICTED`, `changes.proto:113`, `:133`), evidence (`CONFLICTED_REVISION`, `evidence.proto:57`), jobs (`executor.proto:41`) and R3.07's `builtin:conflicts`. Provenance records of a conflicted commit have no tree (`provenance.proto:167`).
- **R3.07's seam.** `reef_policy::input::ConflictInput` and `ConflictSide` (`reef-policy/src/input.rs:257`–`:283`), `Policy::conflict_tier` (`reef-policy/src/conflict.rs`), and `reef policy check --input` accepting `{"conflict": {...}}` (`input.rs:285`).

### What a conflict object is: one per conflicted commit (decisions 1 to 4)

A **conflict** is one conflicted commit's stored conflict: the commit's `Merge<TreeId>`, its labels, and the paths where its terms disagree. It is the unit R3.07's `ConflictInput` already describes (one change, its paths, its sides), the unit a resolver resolves (one new snapshot of the change), and the unit `Change.conflict` flags.

```text
Conflict
  id              cfl_ + 32 hex: SHA-256 over the change id and each conflicted file's id, in path order
  kind            TREE (jj's stored conflict); later tickets add others (below)
  change          the conflicted commit as a `Change` (id, commit, description, workspaces, lifecycle)
  arity           its number of sides
  terms           every term, in jj's order: side 0, base 0, side 1, …, side n-1
    index, role: SIDE | BASE, label (jj's, verbatim), origin (the label's parenthesized suffix)
    source        the commit it came from: {commit_id, change_id, attribution, description, author, committed_at}
    provenance    sides only: R3.04's records of the source's change, summarized (below)
  files           conflicted paths, in path order, a page at a time
    path, id (sha256 of the path and its simplified terms), kind, inherited
    terms         per term of the commit: {index, type: FILE|SYMLINK|TREE|SUBMODULE|ABSENT, id, executable}
    hunks         on request: the file as resolved and conflicted hunks (below)
  files_total, introduced (files not inherited)
  at_operation
```

- **Every term, not "base and both sides".** jj's model has *n* sides and *n − 1* bases; a two-sided conflict is the case the design describes. Each term is reported once, with its role and index, so a three-sided conflict reads correctly and R5.01 can produce any arity.
- **The file's `kind`** summarizes its terms: `CONTENT` (files on every present term, text or binary, and the bits agree), `EXECUTABLE` (only the executable bit differs), `ADD_ADD` (no base has it, several sides add it), `MODIFY_DELETE` (some side deletes it), `TYPE` (a file against a symlink, directory or submodule), `OTHER`. The per-term values carry the detail.
- **`inherited`** is true when the commit's merged parents carry the same conflict at that path (the same file `id`): a child of a conflicted commit inherits its conflict, as jj shows. `introduced` counts the rest. R3.27 assigns the introduced conflicts, and R3.30's "second unresolved conflict ancestor" counts the commits that introduced one.
- **Derived on every read, never stored.** jj's stored conflict is the source of truth; a table copying it would go stale with every rewrite, undo and GC. Reads at an operation (R2.12) work as for every other read.
- **Identity.** A file's `id` is SHA-256 over its path and its simplified per-term values (jj's `simplify`: duplicate side/base pairs dropped, order kept), so it survives a describe, an edit elsewhere in the change, and the widening of another path's conflict, and changes when that path's sides change. The conflict's `id` hashes the change id and its files' ids, so a child that inherits the same conflict has its own conflict id but the same file ids. Labels are not hashed: a rebase rewrites them without changing the conflict. R3.28 counts attempts per conflict or per file id, its choice; R3.27 and R3.28 compare ids to tell that a conflict changed under them.
- **Kinds jj does not store.** R3.26's "conflict object naming the undone operation" and R3.11's "naming the missing dependency" are facts about the operation log and the stack, not about a tree. `kind` is an enum with `TREE` only; those tickets add `UNDONE_OPERATION` and `MISSING_DEPENDENCY` with their own storage and fields, and `ListConflicts` gains them. A client that meets an unknown kind shows the change and the kind's name.

The Rust type is built from a `MergedTree` and an optional commit, not from a commit alone (`reef_lib::jj::conflict::read(tree, context)`), so R5.01's merge engine can return the same object for a merge it has not written yet.

### Which commit each term came from (decision 5)

jj stores no source for a term, only its label. A label is free text that any client can write, so the label proposes a source and the content decides.

1. **Candidates**, at most 32 per conflict, in this order:
   - the commits a term's label names: each `"{change:.8} {commit:.8}"` group in it, resolved by the commit id prefix through the index (hidden commits included while indexed), kept only when the resolved commit's change id starts with the label's change prefix;
   - the conflicted commit's parents;
   - its change's predecessors (`walk_predecessors`), at most 16: after a rebase, the "rebased revision" term is the change's own earlier commit.
2. **The check.** A candidate is a term's source when, at every conflicted path of the conflict (the first 200 in path order, when there are more), the candidate's tree has exactly the term's value. A term whose label named a candidate is checked against that candidate first, then against the rest in order; the first match wins.
3. **`attribution`**: `VERIFIED` (a candidate matched; `source` is that commit), `LABEL` (the label named a commit that resolved but did not match, or matched on fewer than every checked path; `source` is that commit, as declared), `NONE` (nothing resolved or matched; `source` is empty). A label naming several commits (a merge's parents) is `VERIFIED` when one of them matches, otherwise `LABEL` with the first.

`VERIFIED` means "this commit holds exactly this side's content at every conflicted path". It does not say the commit was the one merged: a cherry-pick with the same content also matches (S-128). Candidates named by the label come first so the label wins among equals. `origin` is the label's last parenthesized suffix (`rebase destination`, `rebased revision`), shown as written and never trusted.

### Each side's provenance (decision 6)

For each side whose `source` is set, from R3.04's store, re-verified at this read as every provenance read is:

```text
ConflictSideProvenance
  change_id            the source's change
  commit_record        the record of the source commit itself, when one exists (full `ProvenanceRecord`, no envelope)
  latest_record        the change's newest record recorded at or before the source commit's committer time,
                       else its newest (task, model, instruction hash, identity, signature)
  sessions             the sessions with records of that change, newest first, at most 10 (`ProvenanceSession`:
                       identity, actor, agent, context, started_at, ended_at, problem)
  sessions_total, records, invalid_records
```

- **By change, as R3.04 said.** Most source commits have no record of their own (a rebase or a describe writes none), so who produced a side is every record of its change. `commit_record` is the exact one when the daemon recorded that commit.
- **Sides only.** A base is where the sides diverged, usually landed history; its `source` is attributed the same way, and its provenance is one `ListProvenance` away.
- **The conflicted change itself** has the same summary as `change_provenance`, since its owner is not always a side (a merge commit's owner wrote neither parent). R3.27's "owner's session has ended" reads `ended_at` here.
- **No records** reads as an empty summary, not an error: a person's git commit, a change written by the jj CLI, or a change whose records expired.
- **One query per page.** The daemon collects every source change of a response and reads their records with one `list_provenance` call over at most 100 change ids, as `ListProvenance` does, and the sessions they name with one lookup.

The design's "the task and instruction behind each" is `latest_record.context`: the declared task reference and the instruction's SHA-256; the instruction's text never reaches Reef (R3.04).

### Hunks: on request, bounded (decision 7)

`GetConflict` with `hunks: true` fills each `CONTENT` and `ADD_ADD` file's hunks from `merge_hunks` with jj's options (line-level, `same_change: accept`), the same split jj's markers show:

```text
ConflictHunk
  resolved          true: every term agrees here
  text              the agreed text (resolved hunks only)
  terms             conflicted hunks only, one per term of the file's simplified merge:
                    {index (the commit's term index), text, start_line (from 1), line_count}
```

- **The whole file, in order**, resolved and conflicted hunks alike, so a client can rebuild any side or write a resolution without reading the file again.
- **Bounds.** A file is not split, and `hunks` stays empty with `binary: true`, when a term has a NUL in its first 8,000 bytes (the diff's rule), or with `too_large: true`, when a term is over `max_file_bytes` (default 1 MiB, at most 16 MiB) or its hunks' text would pass 4 MiB. A response stops before it passes 3 MiB and returns a `next_page_token`, as `ListChanges` does.
- **Text** is UTF-8 with invalid sequences replaced, as the diff's hunks are; `binary` files are the way to get exact bytes (`ReadFile` at the source commit).
- **Not in `ListConflicts`**, which carries no files beyond the first paths.

### Limits

| What | Limit |
| --- | --- |
| Terms reported per conflict | 64; a wider conflict has `too_wide: true`, its terms' sources unattributed, and its files with paths only |
| Files per `GetConflict` page | `page_size`, 0 for 200, at most 1,000 |
| Paths per `ListConflicts` entry | 20, with `files_total` |
| Conflicts per `ListConflicts` page | `page_size`, 0 for 50, at most 200 |
| Paths checked per attribution | 200 |
| Candidates per conflict | 32 (predecessors 16) |
| Response | 3 MiB |

### The API: `ConflictService`, the next API revision

A new file, `reef/api/v1/conflicts.proto`. Every field and enum value gets a comment, `_UNSPECIFIED` included.

```proto
// Conflicts (R3.25, ADR 0065): jj's stored conflicts as structured records.
// Reads only; nothing here assigns or resolves a conflict.
service ConflictService {
  rpc ListConflicts(ListConflictsRequest) returns (ListConflictsResponse) { option (reef.api.v1.access) = ACCESS_READ; option idempotency_level = IDEMPOTENT; }
  rpc GetConflict(GetConflictRequest) returns (GetConflictResponse) { option (reef.api.v1.access) = ACCESS_READ; option idempotency_level = IDEMPOTENT; }
}
enum ConflictKind { CONFLICT_KIND_UNSPECIFIED = 0; CONFLICT_KIND_TREE = 1; }
enum ConflictTermRole { CONFLICT_TERM_ROLE_UNSPECIFIED = 0; CONFLICT_TERM_ROLE_SIDE = 1; CONFLICT_TERM_ROLE_BASE = 2; }
enum ConflictAttribution { CONFLICT_ATTRIBUTION_UNSPECIFIED = 0; CONFLICT_ATTRIBUTION_VERIFIED = 1;
                           CONFLICT_ATTRIBUTION_LABEL = 2; CONFLICT_ATTRIBUTION_NONE = 3; }
enum ConflictFileKind { CONFLICT_FILE_KIND_UNSPECIFIED = 0; CONFLICT_FILE_KIND_CONTENT = 1; CONFLICT_FILE_KIND_EXECUTABLE = 2;
                        CONFLICT_FILE_KIND_ADD_ADD = 3; CONFLICT_FILE_KIND_MODIFY_DELETE = 4; CONFLICT_FILE_KIND_TYPE = 5;
                        CONFLICT_FILE_KIND_OTHER = 6; }
enum ConflictValueType { CONFLICT_VALUE_TYPE_UNSPECIFIED = 0; CONFLICT_VALUE_TYPE_ABSENT = 1; CONFLICT_VALUE_TYPE_FILE = 2;
                         CONFLICT_VALUE_TYPE_SYMLINK = 3; CONFLICT_VALUE_TYPE_TREE = 4; CONFLICT_VALUE_TYPE_SUBMODULE = 5; }
message ConflictSource { string commit_id = 1; string change_id = 2; ConflictAttribution attribution = 3;
                         string description = 4; Signature author = 5; google.protobuf.Timestamp committed_at = 6; }
message ConflictSideProvenance { string change_id = 1; ProvenanceRecord commit_record = 2; ProvenanceRecord latest_record = 3;
                                 repeated ProvenanceSession sessions = 4; uint32 sessions_total = 5; uint64 records = 6;
                                 uint64 invalid_records = 7; }
message ConflictTerm { uint32 index = 1; ConflictTermRole role = 2; string label = 3; string origin = 4;
                       ConflictSource source = 5; ConflictSideProvenance provenance = 6; }
message ConflictValue { uint32 index = 1; ConflictValueType type = 2; string id = 3; bool executable = 4; }
message ConflictHunkTerm { uint32 index = 1; string text = 2; uint32 start_line = 3; uint32 line_count = 4; }
message ConflictHunk { bool resolved = 1; string text = 2; repeated ConflictHunkTerm terms = 3; }
message ConflictFile { string path = 1; string id = 2; ConflictFileKind kind = 3; bool inherited = 4;
                       repeated ConflictValue terms = 5; repeated ConflictHunk hunks = 6; bool binary = 7; bool too_large = 8; }
message Conflict { string id = 1; ConflictKind kind = 2; Change change = 3; uint32 arity = 4; repeated ConflictTerm terms = 5;
                   ConflictSideProvenance change_provenance = 6; repeated ConflictFile files = 7; uint32 files_total = 8;
                   uint32 introduced = 9; bool too_wide = 10; }
message ListConflictsRequest {
  string repo = 1; string workspace = 2;
  string revset = 3;             // empty for `mutable() & conflicts()`
  string at_operation = 4; bool skip_snapshot = 5;
  int32 page_size = 6; string page_token = 7;
  bool introduced_only = 8;      // leave out commits whose every conflicted file is inherited
}
message ListConflictsResponse { repeated Conflict conflicts = 1; string next_page_token = 2; string at_operation = 3; }
message GetConflictRequest {
  string repo = 1; string workspace = 2;
  string revision = 3;           // one commit; `@` with `workspace`
  repeated string paths = 4;     // only these files, as the diff's `paths` filter
  bool hunks = 5; uint64 max_file_bytes = 6;
  string at_operation = 7; bool skip_snapshot = 8;
  int32 page_size = 9; string page_token = 10;
}
message GetConflictResponse { Conflict conflict = 1; string next_page_token = 2; string at_operation = 3; }
```

- **`ListConflicts`** returns each conflict with its terms, sources, provenance summaries and its first 20 files (paths, ids, kinds, `inherited`; no per-term values, no hunks), in the revset's log order. Later pages read the same operation as the first.
- **`GetConflict`** returns one conflict with its files a page at a time, each with its per-term values, and hunks when asked. Later pages repeat `terms` and `change` (they are small) so each page stands alone.
- **Errors**: the revision errors of `changes.proto`; `NOT_FOUND` with reason `NOT_CONFLICTED` (metadata `commit_id`) when the revision's tree has no conflict, whose hint says so and whose `next` is `reef show -r <rev>`; `INVALID_ARGUMENT` with `INVALID_PAGE_TOKEN`, and with `MAX_FILE_BYTES_TOO_LARGE` over 16 MiB. Each reason is documented on its RPC, as ADR 0029 requires.
- **Who may call them**: every caller of a READ RPC, on the socket, the web listener and the remote listener. Sources may be hidden commits (a rebased change's earlier commit); their ids, content and provenance are what `ReadFile` and `GetProvenance(commit_id)` already give a READ caller (S-133). No WRITE RPC, so `remote/rules.rs` is unchanged.
- **Review checklist**: ADR 0029's, item by item in the PR. `SERVED` gains `ConflictService`; `API_REVISION` the next free number with its digest; no migration. `GetConflict` is paged with more than one repeated field (`terms`, `files`), so `sdk/fixtures/page-items.json` names `files` as its items.

### The CLI: `reef conflict`

```
reef conflict list [-r <revset>] [--introduced]
reef conflict show [-r <rev>] [--path <path>…] [--hunks] [--policy-input]
```

- **`list`** prints one block per conflict: the change (short id, description's first line, workspaces), its id, each side's source with its attribution and newest agent (`side 1: rebased revision  kmnopqrs 1a2b3c4d  verified  agent claude-x (ended)`), and its paths (up to 20, then a count). Text output escapes control characters in labels, descriptions and paths (S-130).
- **`show`** prints one conflict: terms with sources and provenance (agent, identity, task, instruction hash, model, session state), then each file with its kind and per-term values, then, with `--hunks`, each file's conflicted hunks labeled by term (`side 0 (rebase destination, lines 12–14)`). It follows every page.
- **`--policy-input`** prints `{"conflict": ConflictInput}` for R3.07's `reef policy check --input`: `change_id`, every conflicted path, and per side the source's `change_id` and the `identity` and `agent` of `latest_record`. A side without a source contributes empty strings. The mapping lives in `reef-vcs` over `reef-policy`'s type, so R3.28 extends one function.
- **Exit codes**: 0; `NOT_CONFLICTED` exits 4 (`NotFound`) with its `hint` and `next`.
- **JSON** (`reef_client::json`, `JsonSchema`): `ConflictList`, `Conflict`; brief view: `id`, `change_id`, `arity`, `files_total`, `introduced`, and per side `{origin, change_id, attribution, agent}`. `reef schema`'s `OUTPUTS` gains rows for both commands.
- **Not in the root help**, which is at its budget: `conflict` is in `--help-all`, and `help_lists_every_command` gains it. Discovery comes from where an agent meets a conflict: `reef status`'s conflicted-paths line, and the refusals `CHANGE_CONFLICTED` (R3.09) and `CONFLICTED_REVISION` (evidence, jobs), gain `next: reef conflict show -r <change>`. The agent guide is near its byte budget and is unchanged unless a bullet fits.

### `reef schema`, MCP, SDKs, web UI

## Implementation notes

- **Order**:
  1. Feasibility first, in a reef-lib test: rebase with jj-lib so a real conflict with real labels exists, read its `Merge<TreeId>` and labels, walk `conflicts()`, check that per-path arity equals the root's, parse the labels, resolve a hidden predecessor by prefix, and run `merge_hunks`. If any of it is not public in jj-lib 0.47.0 or behaves otherwise, stop and report before building on it.
  2. `read`, ids, kinds and `inherited` (tests 1, 2, 5).
  3. Attribution (tests 3, 4), then hunks (test 6).
  4. The proto, `ConflictService` and the provenance join (tests 7 to 10), then the CLI (11), then the documents.
- **Building.** Every local build sets `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=line-tables-only` with a target directory of its own, and checks for 50 GiB free first. No `cfg(target_os)` code, so the hosted Linux leg covers Linux; the privileged container is for reproducing a Linux-only failure.
- **Reads** run on the repository thread through the reading layer (`Target`, `snapshot_first` unless `skip_snapshot`), as `GetChange` does; jj-lib's async calls are driven as the diff drives them.
- **Content checks read values, not blobs.** Attribution compares `TreeValue`s at paths (`MergedTree::path_value` on each candidate), which reads trees, never file contents. Hunks read blobs only for the files of the page.
- **The provenance summary** reuses `read_records` and the session reader; nothing is re-implemented, and every record is re-verified.
- **No new configuration.** Limits are constants, documented in `docs/conflicts.md`.

## Risks

- **Labels are jj's formatting, not an API.** A jj release could change `conflict_label()`. Mitigations: the parser accepts what 0.47.0 writes and falls back to parents and predecessors; an unparseable label is `NONE`, never an error; the feasibility test and test 3 pin the format so a jj upgrade fails loudly.
- **Attribution cost on wide conflicts.** Checking candidates reads trees at every conflicted path. Mitigations: 200 paths, 32 candidates, tree reads only.
- **Predecessors after GC.** Operation GC drops old operations, and with them the evolution walk past its window; a rebased side whose predecessor is gone falls back to its label (`LABEL`) or `NONE`. Documented.
- **"Base" means something else to a reader of the design.** jj has *n − 1* bases; the API says so in `docs/conflicts.md`, and two-sided conflicts read as the design describes.

## Choices this brief made, and why

- **One object per conflicted commit**, because R3.07's input, a resolver and `Change.conflict` all work per change, with per-file ids for what needs a finer key.
- **Derived, not stored**, because jj's conflict is the source of truth, and later tickets store only what Reef alone knows.
- **Labels propose, content decides**, because a label is free text and attribution steers R3.27's routing.
- **Provenance by the source's change**, as R3.04 said, because most source commits have no record of their own.
- **Hunks on request**, because routing and policy need sides and paths, and only a resolver or the view needs text.
- **A read-only service with a `kind` seam**, so R3.26 and R3.11 add their conflicts without reshaping this one.

## What later tickets inherit

- **R3.26** adds `CONFLICT_KIND_UNDONE_OPERATION` with its row and fields, and `ListConflicts` returns it beside tree conflicts.
- **R3.11** adds `CONFLICT_KIND_MISSING_DEPENDENCY` the same way.
- **R3.27** assigns introduced conflicts to the newest session of the `VERIFIED` side whose change is the later one (by `committed_at` or, for a rebase, the `rebased revision` side), and queues those whose `change_provenance` sessions have all ended; it keys its rows by conflict id or file id and re-reads before acting.

- **RX.02** reviews S-127 to S-133.

## Departures from dev-phases.md

- **"Structured records with base, sides"** is one object per conflicted commit with every term of jj's merge (*n* sides, *n − 1* bases), per-file values and ids, and hunks on request, derived from jj on every read and never stored.
- **"Each side's provenance"** is each side's source commit, attributed from jj's labels and verified by content, and R3.04's records of that commit's change, summarized, with the exact commit's record.
- **The ticket adds an API and a CLI** (`ConflictService.ListConflicts` and `GetConflict`, `reef conflict list|show`, `--policy-input`) that the row did not name.
- **Conflict kinds jj does not store** (an undone operation, a missing dependency) belong to R3.26 and R3.11, which own their storage; this ticket gives them the `kind` seam.

## Decisions for the user

Grouped for asking; the brief's body follows every recommendation. Answered 2026-11-08: every recommendation accepted (1a to 10a); the `next` hint on R3.09's `CHANGE_CONFLICTED` stays, and whichever of R3.13 and R3.25 merges second resolves the overlap.

**Group 1: what a conflict object is**

1. **Granularity.** One object per conflicted commit, with per-file entries. *Recommended*: as stated, matching R3.07's `ConflictInput` and how a resolver works. Alternatives: one object per conflicted path; or per commit with no file detail beyond paths.
2. **Stored or derived.** Derived from jj on every read, with no table and no migration; R3.27 adds rows for what only Reef knows. *Recommended*: derived. Alternative: a `conflicts` table filled when a conflict is first seen (first-seen time, a stable row id), at the cost of following every rewrite, undo and GC.
3. **Identity.** File id = SHA-256 of path and simplified terms; conflict id = change id plus file ids; labels excluded. Stable across describes and edits elsewhere; changes when a side changes. *Recommended*: as stated. Alternatives: the conflicted commit id (changes on every describe), or the root `Merge<TreeId>` (changes on any edit in the change).
4. **Inherited vs introduced, and the `kind` seam.** Each file says whether it is inherited from the parents; `kind` is `TREE` now, and R3.26/R3.11 add their own. *Recommended*: include both. Alternative: leave both to R3.27/R3.30 and R3.26.

**Group 2: sides and provenance**

5. **Attribution.** Labels propose a source; content equality at the conflicted paths decides (`VERIFIED`/`LABEL`/`NONE`), with parents and predecessors as fallback candidates. *Recommended*: as stated (S-127). Alternatives: trust labels as written; or parents only (misses rebases, the common case).
6. **Provenance shape.** Per side: a summary (up to 10 sessions, counts), the change's newest record, and the exact commit's record; the conflicted change gets the same; bases get a source but no provenance. *Recommended*: as stated. Alternatives: only the side's change id, leaving clients to call `ListProvenance`; or every record embedded (unbounded).

**Group 3: content**

7. **Hunks.** Computed with jj's merge options only when `GetConflict` asks (`hunks: true`), whole file in order, bounded (1 MiB a term by default, 16 MiB at most; binary and large files flagged). *Recommended*: on request. Alternatives: always; or never (clients read markers through `ReadFile`).

**Group 4: surface**

8. **API.** A new `ConflictService` with `ListConflicts` and `GetConflict`, READ, the next API revision, no migration. *Recommended*: a new service, which R3.27 extends with its writes. Alternative: two RPCs on `ChangeService`.
9. **CLI.** `reef conflict list|show` in `--help-all` only (root help at budget), `--hunks`, `--policy-input` printing R3.07's `ConflictInput` for `reef policy check --input`, and `next: reef conflict show` on `reef status` and the existing conflicted refusals. *Recommended*: as stated. Alternatives: drop `--policy-input` (R3.28 builds it), or put `conflict` in the root help by trimming another line.
10. **MCP.** `NOT_TOOLS` now, revisited by R3.27 when agents are handed conflicts. *Recommended*: `NOT_TOOLS`. Alternative: a `get_conflict` tool now, raising `tools/list`'s 21,250-byte budget by about 1 KiB.
