# Phase 3 tickets

Source of truth for scope: [`docs/dev-phases.md`](../../dev-phases.md) (Phase 3 tables) and [`docs/design.md`](../../design.md) (Data model, Landing, What evidence proves, CI load, Provenance, Durability and backup, Human interface). These files expand each Phase 3 row into an implementation brief. They are written for an implementing agent, not for humans: every decision that could be made in advance has been made here, and the brief says so. If a brief and `dev-phases.md` disagree on scope, the brief wins for the implementation and the disagreement is fixed in `dev-phases.md` in the same PR. Where a brief departs from `dev-phases.md`, the departure is listed under "Departures from dev-phases.md" below, and `dev-phases.md` was edited to match when the brief was written. Briefs are added as each ticket starts, so the table below fills in with them.

Phase 2 is complete and released as 0.2.0 to 0.4.0 (0.4.2 on jj-lib 0.47.0, 2026-11-05). What it left behind, and what every Phase 3 brief builds on:

- **The v1 API** (`reef.api.v1`, ADR 0029): every RPC classified `READ`, `WRITE` or `ADMIN`; `API_REVISION` and `API_DIGESTS` bumped on every schema change; the review checklist; `buf` lint and breaking checks. Writes coordinate with live workspaces (ADR 0031) and record `reef.*` attributes and the caller's `reef-agent` on every operation. Errors carry `ErrorDetail { kind, chain, hint, next }` and a reason constant documented on each RPC.
- **The thin clients**: `reef-client` (one method per RPC, page followers, `json` and `brief` types), the `reef` CLI under ADR 0025 (never interactive, `hint` and `next`, brief JSON on a pipe by ADR 0045), `reef mcp` (ADR 0035; every v1 method is a tool or in `NOT_TOOLS`, with `tools/list` under a byte budget, #116), `reef schema` (ADR 0050; every command has an `OUTPUTS` row), and the Python and TypeScript SDKs generated from the descriptor set (ADR 0054).
- **Live state**: the operation log subscription and broker (ADR 0036, 0038), presence (ADR 0037), replay (ADR 0046), the history and symbol indexes (ADR 0042, 0044), the status index (ADR 0048).
- **Listeners**: the loopback web listener (ADR 0047) and the remote listener with scoped tokens (ADR 0049). A new WRITE RPC gets a row in `remote/rules.rs`, and the threat model's listener requirements hold for every RPC.
- **The daemon's database**: `reef.sqlite3`, schema 6 at 0.4.2, numbered migrations that are never edited, every row keyed by repository (ADR 0003), copied whole by backups (ADR 0020).
- **The trust model** (`docs/threat-model.md`, ADR 0027): one uid is one trust domain; RX.02 is the first external review, and Phase 3 is where identity and signatures enter it.
- **Objects** are jj's git objects with SHA-1 identities until Phase 4 (ADR 0011), so trees and commits are git object ids.

## Departures from dev-phases.md

These were decided while writing the briefs. `dev-phases.md` was edited to match in the same change.

- **R3.01's "attestor" is the signing key and its "snapshot hash" is the snapshot's tree hash** (2026-11-05). A field in which the producer names itself proves nothing, so the attestor is the key that signed the envelope, and R3.03 binds keys to identities. Evidence binds to the tree, as the design's Landing and CI load sections say, not to the commit, which the data model row's wording suggested. The design's data model row is reworded in R3.01's PR.
- **R3.02 also owns the retention of evidence objects** (2026-11-05). R3.01 stores evidence with no deletion except `repo forget`, and a retention rule needs a walk over reachable trees that would push R3.01 past M.
- **R3.03 leaves Sigstore keyless and verified human presence to two new rows, R3.42 and R3.43** (2026-11-06). Keyless (OIDC, Fulcio, Rekor, the trusted root) and passkey presence are each an M ticket; R3.03 defines their seams (`IssuerKind`, `presence`) in its certificate format. R3.43 answers #222's question of how a verifier knows a human signed. R1.01's row no longer says R3.03 replaces the workspace owner: R3.04's provenance ties a workspace's work to a session.
- **R3.04 signs provenance with a daemon-held session key, one record per commit the daemon records for a workspace, and leaves harness, MCP and SDK declarations to a new row, R3.44** (2026-11-06). "Signed with the session key" is the key the daemon holds for the workspace's session (`custody: daemon`, as R3.03 reserved), since the watcher records commits with no client present. "Attached to snapshots" is a record per commit the daemon records for a workspace (each snapshot that commits, and `EditFiles` naming the workspace), kept in `reef.sqlite3`, found by change, and compacted and expired by GC, which the row did not mention. The instruction is a SHA-256 the client computes; its text never reaches Reef. Prompt hooks, `reef mcp`'s declaration and the SDK blocks would push R3.04 to L, so they become R3.44 (S).
- **R3.05 has executors pull jobs from a queue the daemon keeps, ships both sides of the protocol, and moves the executor conformance suite to R6.03** (2026-11-07). The row did not say who connects: executors dial the socket or the remote listener and claim jobs under a lease, and the daemon never connects to an executor (the design's diagram arrow shows the flow of work, and is left as is). Nobody requests checks before R3.13 and R3.14, so R3.05 also builds the durable job table, `SubmitJob` and `CancelJob`, `reef job`, and GC retention for jobs, and stays M. Artifacts are uploaded through R3.02 by digest before the evidence that names them, so a response carries signed evidence, not bytes. "Progress streams over the presence channel" is a daemon-reported presence kind, `JOB`, built from executors' `UpdateJob` calls. R3.06's row now says a request carries no command (what runs for a kind and target is the executor's configuration or the repository's declaration, R3.06's choice) and that R3.06 owns getting the tree and the executor's command line. R6.03's row gains the conformance suite, built from R3.05's checklist.
- **R3.06 reads trees through `FileService` with three hash checks, takes checks from `executor.toml` or a new `reef-checks.toml` at the tree, refuses to run without Seatbelt or bubblewrap unless configured `kind = "none"`, and moves per-test report parsing to R3.22** (2026-11-07). "Materializes the tree hash and checks it" is a listing, every blob and the laid-out disk checked against git object ids, in a private job directory rather than a Reef workspace, so it works the same over the socket and the remote listener and leaves the repository untouched; a job submitted by tree alone, with no commit, fails. "Declared in the executor's configuration or in the repository at that tree" is both, the executor's checks first, and a repository declares only the entry point, never the environment around the run; `reef-checks.toml` is a new file because the daemon parses `reef.toml` strictly. No daemon, API or protocol change; the spec gains wording in sections 4 and 8. R3.22's row gains parsing a declared JUnit report into per-test outcomes, which its behavioral diff needs first.
- **R3.07's policy is `reef-policy.toml`, read from the destination's tree, and the ticket adds `EvaluatePolicy` and `reef policy`; R3.28 applies the conflict tiers it parses** (2026-11-08). "`reef-policy.cel` or similar" is a strict TOML file whose tables (trusted attestor sets, required evidence, limits, forbidden paths, sign-off areas, conflict tiers and attempt caps) carry CEL conditions, plus free CEL rules, because the landing service needs data (which evidence is missing, who must sign) that a boolean expression cannot give. The policy in force is the one on the destination (`trunk()` by default), never the change's own, and changes to `reef-policy.toml` and `reef-checks.toml` need the owners' sign-off, built in; a missing or invalid policy lands nothing, which R3.13's row now says. Sign-offs are `signoff` evidence from person identities, which exists today. Evaluation is a READ RPC and a CLI so a decision can be asked for before R3.13 enforces it, and R3.08 builds on its policy-text field. Conflict tiers and caps are parsed and looked up here and applied by R3.28; R3.20's budgets and R3.24's stack rules are later tables and inputs in the same file.
- **R3.08's recent landings are the destination's non-merge ancestors until R3.13 records landings, and each is compared with a baseline** (2026-11-08). Nothing records a landing before R3.13, so a landing is a commit that reached `trunk()`, other than a merge, judged as its own change, newest first, with any revset accepted; R3.13's landing records, with the evidence they pinned, replace that default. The report compares each landing's decision under the proposed policy with the destination's current policy, and counts apart the landings blocked only for missing evidence, which history usually lacks (squash merges make new trees, and retention expires old evidence). The row now says so.
- **R3.44's prompt hook also reaches the workspaces its harness session creates or holds elsewhere, and the model comes from hook events** (2026-11-08). An agent following the guide works from the root checkout, so a hook that declared only for its `cwd` would leave most records without an instruction: the hook also declares for every active workspace whose session declared the same client session, and leaves a session note (hashes only) that the session's next workspaces declare from for 24 hours. The reference harness documents its model only in hook events (`SessionStart`, `PostModelSwitch`), not in its environment, so "where a harness documents one" covers both.
- **R3.09 records each transition as an operation and a row, records only the client transitions and observed landings itself, and makes accept a sign-off rather than a state** (2026-11-08). "Recorded as operations" is an operation per transition carrying a `reef.lifecycle` attribute, plus a row in `reef.sqlite3`, because GC drops operations older than its window and the inbox needs every open proposal in one query. Clients propose, withdraw, decline and supersede; enqueue, dequeue and land are defined here and recorded by R3.13, whose row now says so, except that the daemon records a recorded change as landed when it reaches `trunk()`, since until R3.13 every landing happens outside Reef. Accept is R3.07's `signoff` evidence, which R3.31's row now says. The ticket adds `reef propose` and `reef proposal`, which the row did not mention.
- **R3.13 lands on request, judges the submitted tree, and leaves automatic landing and evidence requests to a new row, R3.45** (2026-11-08). Landing what policy allows without anyone asking needs a second trigger system (evidence, provenance and policy changes) and per-proposal evaluation keys, and requesting missing evidence needs job dedupe and retries; together they push R3.13 well past L, so R3.45 (M, after R3.13 and R3.05) takes both. "Checks commutation" is a rebase onto the destination that merges with no conflict; the paths both sides touched are recorded and given to policy as `landing`, so a repository can require fast-forward or disjoint paths until R3.14 tests the batch head. A change whose parents have not landed is refused (R3.10 lands stacks). "Pins the evidence and the policy blob" also links the evidence to the change, copies the policy bytes into `reef.sqlite3`, and keeps the change's provenance whole; artifacts keep their own retention. The row now says so, and R3.45's row is new.
- **R3.25 derives one conflict object per conflicted commit from jj on every read, attributes each term by its label checked against content, and adds `ConflictService` and `reef conflict`** (2026-11-08). "Base, sides" is every term of jj's merge (*n* sides, *n − 1* bases) with per-file values and ids, and hunks on request; nothing is stored, so later tickets store only what Reef alone knows (assignment, attempts). "Each side's provenance" is each side's source commit, proposed by jj's conflict label and `VERIFIED` only when that commit holds the side's content at the conflicted paths, with R3.04's records of its change and the exact commit's record. Conflicts jj does not store (an undone operation, a missing dependency) are R3.26's and R3.11's, through a `kind` field. The row now says so.
- **R3.42 logs a keyless session key's binding statement in Rekor, not each evidence object, takes a person's OIDC token rather than running a login, and lets policy require keyless keys** (2026-11-08). Fulcio certifies an ed25519 session key against an OIDC token; the key signs a Reef binding statement (actor, agent, session) that Rekor logs, and the bundle is registered with the daemon, which verifies it offline against a vendored trusted root through `sigstore-verify` and a ring provider. Evidence stays R3.01's, and a Sigstore bundle per evidence object is a follow-up. ADR 0025 keeps the CLI non-interactive, so a person's token comes from a file or `SIGSTORE_ID_TOKEN`, and a browser login is a follow-up in the web UI and desktop shell. R3.07's input and attestor sets gain the issuer fields and `issuer_kinds`. The row now says so.
- **R3.14 runs the executor only for the `[[require]]` pairs missing on the batch's tested tree, counts that tree's evidence for every member at or below it, bisects over prefixes, and puts its settings in the destination's policy** (2026-11-09). "Run the executor on the batch head" requests, one job per kind, by revision on a visible trial commit, only the pairs each member's `[[require]]` rules lack on the tested tree, so a tree tested before (a fast-forward, a re-formed batch, a restart) is never tested again; the gate still judges the submitted tree with every rule, and `[landing] checks = "proposal"` keeps R3.13's landing for repositories whose evidence does not come through jobs. "Land on pass" lands every member whose required evidence passes on the tested tree, the merge queue's assumption for the untested trees below the head, which the record names. "Bisect on failure" is a binary search over the chain's prefixes: the passing prefix lands, the culprit returns to its owner with reason `checks`, the rest are requeued; infrastructure failures are `unavailable`, never the change's fault. Batch size, window and `alone` paths are a `[landing]` table in the policy (R3.45 adds `automatic` to it), changes to the policy files land alone, and the row gains re-forming on moves and restarts, the `batch` input, `GetBatch`, `ListBatches` and `reef landing batches|batch`. The row now says so.
- **R3.12 delivers instructions by pull and leaves the webhook to a new row, R3.46; its estimate is what Reef recorded** (2026-11-09). Reef starts no agent (the design's "not an agent runner"): an instruction is routed to the client session declared by the session that proposed the change (else the change's latest provenance), and the session takes it through one claim RPC, used by `reef comment next`, harness hooks at the turn's end and the next prompt, and `reef mcp` inside `wait_for_operations` (no new MCP tool). The webhook is the daemon's first outbound HTTP and needs its own address checks, signing, retries and threat rows, which push R3.12 past M, so R3.46 (M, after R3.12) builds it to the design R3.12's brief fixes. "Estimated cost" is the change's recorded check time and earlier instructions' agent time with the session's declared model, and tokens and price are stated as unknown until a runner reports them (R3.46). Comments attach to any change, not only proposals. The rows now say so, and R3.46's row is new.
- **R3.27 keys an assignment by the conflicted change, takes its owner from that change's provenance, defines a session's end as its workspace's, and adds reassignment, takeover and an API** (2026-11-09). "The later change" is the conflicted change, the one moved onto the other, and "its originating agent" the newest live session that recorded it; a change Reef never recorded is unowned and is queued only by a person, so no resolver rewrites a person's change uninvited. "Whose owner's session has ended" is the owner's workspace having no live provenance session (released or reclaimed), not presence, which is never persisted; an assignment follows the same identity's declared client session, waits a 5-minute grace, and returns to a resumed owner while unclaimed. "With priority" is a person-set priority, then the time queued. Claims are held by the claiming workspace's session rather than a lease of their own. The row did not name the state (schema 15), the operation per change, reassignment and the design's takeover by a person, five RPCs, or the CLI; it now does.
- **#258 adds `reef publish` before R3.17, and R3.17 pushes through it** (2026-11-09). A team whose work reaches `main` as pull requests needs a push long before the landing service pushes landed history (#194, question 2). `GitService.PublishChange` and `reef publish` push a change and every ancestor the remote's branches lack to a review branch named from its change id (`reef/<id>`), through jj-lib's `push_refs` in the daemon with the user's git credentials, lease-protected, never onto trunk, socket only, and print the host's pull-request command in `next`; publishing clears R1.16's `local` flag on what it pushed. R3.17 lands its push through the same plan, lease and record, fast-forward only onto the destination's branch, and R4.14 replaces the git subprocess under both. The R3.17 and R4.14 rows now say so.
