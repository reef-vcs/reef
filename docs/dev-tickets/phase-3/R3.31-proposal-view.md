## Context

The design's human interface: "**Approve, not read.** The review surface opens on intent, then evidence, then diff, in that order. ... The diff defaults to a symbol-level summary with affected call sites and expands to lines on demand. Most approvals never reach the line view." And: "The reviewer accepts the proposal or a prefix of its stack. Comments are addressed to the originating agent and resume its session." Its rule for the interface: "no action exists in the interface that is not one API call", and its five live rules (one state color per object, motion only for state change, nothing reorders under the cursor, every live element links to its cause, coalesce, never drop).

Reef's users are mostly agents. The person on this page is the one reviewing what agents propose, and the page exists so they can judge a proposal and act on it fast: read what the agent meant, see whether the evidence holds, look at what changed by symbol, and accept, decline or comment without leaving the page.

**Reads: everything the view shows is a READ RPC the web listener already serves.**

- `ChangeService.ListProposals` with `changes: [id]` is the one-proposal read (there is no `GetProposal`). `ProposalEntry` (`changes.proto:475`) carries the lifecycle (state, round, recorded commit, `amended`, destination, last transition), the `Change` (description, author, tree, conflict, empty), `proposed_by`, `automatic` (`AutomaticStatus`: state, message, `missing` needs including sign-offs, job ids, landing id, `next`), and `resolutions`.
- `ListTransitions` is the history; `EvaluatePolicy` (with `stack: true`, field 9) gives rule results, `missing`/`failed` needs and a `PolicySignoff` per sign-off rule (`have`, `signed_by`, `presence`); `ListEvidence` by `change_id` marks each object `current`, with its `KeyIdentity` (name, kind, actor, presence, status); `ListComments`/`GetComment`; `ListProvenance`.
- The stack had no RPC at `7254fa4e`: `reef proposal show` reads it with `ListChanges` and the revset `(::<commit> ~ ::(<destination>)) ~ <commit>` (`reef-vcs/src/cli/proposal.rs:432`). Since R3.11, `ProposalEntry.dependencies` is that list, bottom first (see below).

**The symbol diff: `GetDiff` with `symbols: true`, computed per request, never stored.** Measured on this Mac with the installed 0.4.2 release daemon, `reef diff -o json` process wall time, 7 warm runs each, median, against R3.28's commit `7254fa4e` (82 files, +5,561/−540):

| Request | Time | JSON size |
| --- | ---: | ---: |
| `--stat` | 66 ms | 37 KB |
| line hunks, every file | 80 ms | 487 KB |
| `--symbols --call-sites 0` | 129 ms | 362 KB |
| `--symbols` (10 call sites per change) | 292 ms | 601 KB |
| `--expand of_workspace` (one definition's lines and call sites) | 165 ms | 22 KB |

A cold commit (entries not yet extracted, tree not indexed) costs 0.2 to 0.4 s more once; R2.16's history worker usually extracts a change's entries within seconds of it going quiet, so a proposal is mostly warm by the time a person opens it (all 98 file sides of `7254fa4e` were cached before the runs). Warm cost is the whole diff's definition matching plus the call-site row queries; call sites are about half the time and 40 % of the bytes. Expanding one definition re-runs the matching for the whole diff. 32 of the 82 files were outside the tags languages (`.md`, `.proto`, `.json`, `.sql`): the view shows those by lines. A diff over 1,000 files is `DIFF_TOO_LARGE` and computes nothing. Nothing in `web/` asks for symbols today (`ChangeDetail.tsx` asks for `STAT`).

**Writes: every action is a WRITE RPC, and the web listener refuses them all.**

- **Accept** is `signoff` evidence. The CLI (`reef evidence add --kind signoff --result pass --actor human -r <change>`, `reef-vcs/src/cli/evidence.rs:902`) generates an ed25519 key in process, calls `IssueSessionKey` (WRITE) with a proof of possession (PAE over a fixed text naming the authority, key id, identity, actor and session, `reef-evidence/src/session.rs:671`), gets a five-minute certificate for the default person with actor `human` and `presence: none`, signs an in-toto statement over the change's tree, and calls `AddEvidence` (WRITE). The daemon never signs for a person: its own keys (`issue_held`) serve provenance only, through no RPC.
- **Decline** is `TransitionChange { to: DECLINED, reason, stack, actor, expected_state, expected_commit_id }`; refused through the remote listener (`REMOTE_HUMAN_REQUIRED`, `lifecycle/mod.rs:790`).
- **Comment** is `CreateComment` (note, instruction, or an answer to a help request through `reply_to`), and `UpdateInstruction` to confirm or cancel an instruction after its estimate.
- The web gate's step 8 (`web/gate.rs:222`) passes `ACCESS_READ` only and answers anything else `WEB_ACCESS_DENIED`. It inserts no caller into the request, so a write it let through would look like a socket call to every handler: actor `human`, decline allowed, and every `remote_of(...).is_none()` check passed, including `PublishChange` with the user's git credentials (`service/git.rs:47`), `PushLanded` and fetch. Opening the gate is therefore not "loosen step 8": it is an allowlist plus a caller of its own.
- CSRF is already sufficient for writes: the token travels in a header, Origin and `Sec-Fetch-Site` are checked, the gRPC-web content type forces a preflight the gate refuses, and the CSP has `form-action 'none'` (S-29, S-30, S-33).

### The write path (decision 1: R3.43 first)

R3.43 builds the web listener's first WRITE path: the allowlist table `web/rules.rs` (passing only listed WRITE methods, each with a rule), the web caller the gate inserts, `Channel::Web` in key issuance, the audit of web writes, the listener served as `localhost`, passkeys, `human` keys issued to the browser only after a user-verified assertion (`presence: user_verified`), and the browser signer (`web/src/sign/`).   | Method | Rule |
  | --- | --- |
  | `ChangeService.TransitionChange` | `to` must be `DECLINED`; `expected_commit_id` must be set |
  | `CommentService.CreateComment` | any kind the socket allows |
  | `CommentService.UpdateInstruction` | as the socket (confirm or cancel) |
  | `LandingService.LandChange` | as the socket (decision 2) |

- **Audit for them**: `WebCaller` (R3.43's message) on `ChangeTransition`, `CommentAuthor` and `Operation`, stored as `web_session` on `lifecycle` and `comments`. The decline guard treats the web caller as local.
- **Accept signs through an R3.43 approval**, never with a `presence: none` key: one passkey touch per Accept, whose challenge binds a fresh key, the `signoff` statement over the reviewed tree and the change (R3.43's "Sign off" flow, reused), and the key signs that one statement once. "Accept up to here" is one touch for that member. A sign-off counts for policy only when the destination's policy pins the person's passkey (R3.43's `[passkeys]`); the evidence section says when it is not pinned. A person with no passkey registered sees Accept explain that and link to the passkeys page; Decline and Comment need no passkey (they are not evidence).

### What Accept does (decision 2)

**Accept signs a `signoff` on the tree of the member it is pressed on, then asks to land it when the destination does not land automatically.** With `[landing] automatic = true` the R3.45 service lands it when the gate allows; otherwise the page calls `LandChange` for that member (which lands the stack's prefix below it, R3.10), and the page shows the landing's state, or the gate's reason when it blocks (a missing test is `waiting` under R3.45, not a failure). "Accept up to here" on a stack member signs that member (a sign-off counts for the members below it). The sign-off is over **the tree the person reviewed** (the tree id from the read the page rendered, not a fresh one). Accept is disabled, with the reason, when the proposal is not `PROPOSED` or was amended since the page loaded (the person reviewed another tree). Sign-offs carry no self-exclusion (`policy.md:153`), and the page does not invent one.

### The page (decided here)

Route `/repos/:repo/proposals/:change`, a lazy chunk with its own `proposal-route.ts` helpers, `?at=` honored for reads (actions hidden when frozen). Top to bottom, at desktop and at 375 px:

1. **Header and actions.** The description's first line, the state badge (the one state color), the automatic status as a sentence ("Waiting for test on this tree", "Needs a sign-off from release", "Ready to land", "Landing"), who proposed it and when. Accept, Decline and Comment stay in reach (sticky bar on a phone).
2. **Intent.** The full description (as text, never Markdown or HTML, S-33); the declared provenance: task, model, harness, the instruction's hash marked "declared"; for a stack, the members bottom to top with their states, each a link, the current one marked, "Accept up to here" on each. R3.11's `ProposalEntry.dependencies` gives the members below, with their states; a declined or withdrawn one holds the proposal, and the page says which and why (#350).
3. **Evidence.** The policy's verdict from `EvaluatePolicy` (`stack: true` when the change heads a stack): each rule passed, missing or failed, in words; sign-offs needed and given (who, presence); each current evidence object: kind, result, target, who attested (identity name and kind, actor, presence, revoked later), when, signature status. Non-current objects (another tree) folded under a count. Developer mode adds key ids, digests and the `reef evidence show` line.
4. **Diff.** `GetDiff { symbols: true, max_call_sites: 0 }` against the change's parents (what the agent wrote; a stack member against the member below). Files ordered by the most changed symbols; each covered file lists its definitions nested by `enclosing_symbol`, with kind (added, removed, changed, moved), name and line counts. A definition expands in place: `GetDiff { format: HUNKS, paths: [file], expand_symbols: [symbol] }` with call sites (the default ten), cached for the page's commit. Files outside the tags languages, skipped files and `DIFF_TOO_LARGE` show line counts and expand to the file's hunks. Never clipped by the client (ADR 0043). One diff read in flight.
5. **Comments.** The thread (`ListComments`), anchored ones beside their lines when expanded, `outdated` marked; help requests on the change shown with their state and an Answer box (`CreateComment` with `reply_to`). A new comment is a note by default; "Send as an instruction" shows the estimate (`AWAITING_CONFIRMATION`) and a Confirm/Cancel step. A selected line range in an expanded hunk can be commented on (anchor path, side, lines).
6. **History.** `ListTransitions`, folded.

**Decline** opens a reason box (required: an agent cannot act on "declined" alone), declines this member or the stack (`stack: true`), with `expected_commit_id` and `expected_state` from the rendered read, so a decline never applies to a tree the person did not see.

**Data shape.** One `ProposalModel` per page (the `*-model.ts` pattern): the proposal read (entry, stack, policy, evidence, comments, transitions) refreshed as a unit on the operation stream, paced by `live/paced.ts`, plus a per-commit diff cache. Each action is a small state machine, `idle → editing → working → done | failed(error)`, rendered from one reducer, so a button never shows two states. Errors render the daemon's `hint`; a refusal over the remote listener (`human_over_remote`, `REMOTE_HUMAN_REQUIRED`) shows "Accept and decline happen on the daemon's machine for now" rather than a raw code.

### Threat model rows (S-257 to S-263)

- **Self-approval through the page.** A proposing agent controls text the page renders (description, diff, comments, paths); a script injected through it could decline, comment or request a landing. Bounded by S-33 (React escaping, no HTML rendering, the strict CSP, the lint and the asset test), extended to every new component. It cannot sign: a sign-off needs a user-verified passkey assertion (R3.43).
- **A leaked session URL declines and comments.** Extends R3.43's row: it can decline, comment and request landings until the daemon restarts, never sign.
- **Acting on a stale view.** Accept signs the tree the person reviewed, and a decline carries the rendered commit and state; an amended proposal disables Accept and refuses a decline (`expected_commit_id`).
- **Instructions spending compute from a click.** The estimate and its confirm, as on the CLI; a note is the default.

## Choices this brief made, and why

- **The tree the person saw**, because a sign-off is bound to one tree (R3.15), and accepting a tree nobody looked at is the failure the view exists to prevent.
- **No `GetProposal`, no stack RPC**: the reads exist; the CLI already assembles them the same way.
- **Call sites on expand, not on load**: half the load time and 40 % of the bytes, for detail a person wants only for the definition they open.
- **Decline requires a reason**, because the proposing agent reads it as its next instruction.
