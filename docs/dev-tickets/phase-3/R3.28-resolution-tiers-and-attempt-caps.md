# R3.28 Resolution tiers and attempt caps

Phase 3 · Size M, at its top end, with the scope lines below · Depends on: R3.27 (the assignment row, its follower, `assign::may_claim`, `moved`, `claims`, `resolved_session_id`, the reopen window), R3.07 (`[conflicts]`, `Policy::conflict_tier`, `ConflictInput`, the built-in rules, sign-offs), and builds on R3.25 (conflict objects, `VERIFIED` sides, reads of hidden conflicted commits), R3.09 (proposals, `ListProposals`), R3.13 and R3.45 (the gate, its dry run, the automatic status), R3.10 (sign-offs counting downward in a stack), #262 (`ChangeStep`, `reef here`), R2.08 (remote tokens) · Unblocks: R3.29 (escalates to `ask`), R3.30 (backpressure's "policy approval"), the tier and attempts in R3.33 and R3.35; R3.32's help request names a blocked conflict

## Context

The design names the job in Human interface, "Approve resolutions, not perform them": "The resolution is a new snapshot that enters the normal proposal flow with its evidence, marked as a resolution so the reviewer sees both sides' provenance. Policy sets the tier per area: resolve and land, resolve and require approval, or ask before attempting. … Policy caps attempts per conflict so a hard one cannot loop."

Two tickets left this one its parts. R3.07 parses the `[conflicts]` table (`tier = "land" | "approve" | "ask"`, `attempts` from 1 to 20, `[[conflicts.rule]]` by paths and a CEL `when` over `conflict`) and looks it up with `Policy::conflict_tier(&ConflictInput) -> ConflictDecision { tier, attempts, rule }`, with `approve` and 3 when the table is absent, and an error that "R3.28 treats as the strictest tier, `ask`". Nothing in the daemon calls it; only `reef policy check --input` does. R3.27 assigns each conflict to its change's owner, queues it when the owner's session ends, and lets resolvers claim it, with one function, `assign::may_claim`, that "allows everything here; R3.28 refuses an agent's claim of an `ask` tier conflict or one over its attempt cap there", a `claims` count, and a closed `RESOLVED` row with `closed_commit_id` and `resolved_session_id` from which "R3.28 marks resolutions in the proposal flow".

Since R3.45, landing happens without anyone asking. A conflict is now the main thing that stops an agent working alone, and nothing tells the agent that owns one whether it may resolve and land, must get approval, or must ask first, and nothing stops a hard one bouncing between resolvers for ever.

So this ticket builds:

1. **The tier of each assignment**: the conflict input built in the daemon from R3.25's object, looked up against `trunk()`'s policy, kept on the row, and refreshed when the conflict or the policy changes.
2. **Attempts and the go-ahead**: what an attempt is, a new `BLOCKED` state for a conflict that needs a person first (an `ask` tier without a go-ahead, or attempts used up), enforced where a conflict is handed to a resolver, and `reef conflict allow` for a person to unblock it.
3. **Resolutions in the proposal flow**: a resolution's record (tier, attempts, whether it needs approval), shown on proposals, given to policy as `change.resolutions`, and enforced at the gate by a new built-in rule, `builtin:resolution`, that asks a person's sign-off for a resolution that needs one.
4. **The surface**: fields on `ConflictAssignment`, `ProposalEntry`, `GetConflict` and `AssignConflict`, a `CHANGE_STEP_ASK` step for `reef here`, `reef conflict allow`, and the documents.

R3.32 (help requests) runs beside this ticket. R3.28 does not build a way for an agent to ask a person: it blocks the attempt, records why, and shows it where an agent already looks. Decision 6 names how the two connect.

### Attempts (decision 1)

An **attempt** is one resolver's turn at a conflict. It starts when a resolver is handed the conflict: the default owner when the assignment opens or reopens (`DEFAULT`, `REOPENED`), a claim (`CLAIMED`), or an assignment to a workspace (`ASSIGNED`). The same agent continuing is the same attempt: a follow to its other session (`FOLLOWED`) or its return to an unclaimed conflict (`RETURNED`). A person who takes the conflict over (`TAKEN`) is not making an attempt.

- **Counted at the start, checked before it.** `attempts` on the row counts attempts started. A hand-off that would start attempt *n* + 1 when `attempts` is already the row's **limit** does not happen: the conflict goes to `BLOCKED` instead (below), or the claim is refused.
- **The limit** is the policy's `attempts` for the conflict plus what people have granted (`granted`, below).
- **An undone resolution uses an attempt.** A resolution undone within 24 hours reopens the same row with its counts (R3.27's reopen window, which exists for this), and the reopen starts a new attempt. After 24 hours the same conflict is a new assignment with a fresh count (S-233).
- **What is not an attempt.** A resolution that later fails its checks or is declined is not a conflict attempt: by then the change has no conflict, and it is ordinary work under R3.45's give-up rules and R3.09's decline. A partial resolution (the conflict id moves, `CHANGED`) is progress within the attempt.

Most conflicts use one attempt: the owner resolves its own change. The cap matters when a conflict moves between resolvers: an owner gives up (`ws release`, `reef conflict release`), the queue hands it to another, who gives up too. With the default cap of 3, the third resolver to give up leaves it for a person.

### The tier of a conflict (the input and the lookup)

The tier and the cap come from `Policy::conflict_tier` over a `ConflictInput` built by the daemon.

- **One mapping, in the daemon.** The CLI's `policy_input` (`reef-vcs/src/cli/conflict.rs:795`) moves to `reef-daemon/src/service/conflicts.rs`, from the `v1::Conflict` the daemon already builds, so the input matches what clients read. `GetConflictRequest.policy_input` asks for it in the response, and `reef conflict show --policy-input` prints the daemon's (the CLI's copy is deleted).
- **One field added**: `sides[].actor` (`human`, `agent`, or empty when the side is not `VERIFIED` or has no record), from the side's latest verified record's session. A policy can then ask before an agent rewrites a person's work: `when = 'conflict.sides.exists(s, s.actor == "human")'`, `tier = "ask"`. Unverified sides stay empty (S-127): a label cannot steer a tier.
- **Which policy.** `reef-policy.toml` at `trunk()`'s head, as R3.07 decides for every evaluation before a destination is known. No file: the `[conflicts]` defaults (`approve`, 3), since a repository with no policy lands nothing through Reef anyway. An invalid policy, a lookup error or a cost over the bound: `ask`, with the error on the row (R3.07's rule, S-235).
- **When it is looked up.** When a row opens or reopens, when its conflict id changes, and when `trunk()`'s policy blob changes (compared once per look, at most 64 rows refreshed a pass, the rest on the next). The row keeps the decision with the conflict id and policy commit and SHA-256 it came from. A refresh changes what the next hand-off and the close do; it never takes a conflict from a resolver mid-attempt.
- **A close uses the tier as last looked up**, refreshed first when stale (the conflicted commit is still readable, above).

### States: `BLOCKED`

R3.27's states gain one:

```text
                     tier ask, no go-ahead; or attempts used up
  open / reopen ──────────────────────────────────────▶ BLOCKED ──allow (a person)──▶ ASSIGNED or QUEUED
  ASSIGNED ──owner ended + grace, release──▶ (limit reached?) ──yes──▶ BLOCKED
                                                          └──no───▶ QUEUED
```

| State | Owner | In the queue | Who can move it |
| --- | --- | --- | --- |
| `BLOCKED` | the owner it would have gone to, kept for `allow` | no | a person: `allow`, `assign`, `take` |

Reasons: `ASK` (an `ask` tier with no go-ahead), `ATTEMPTS` (the limit is reached), `ALLOWED` (a person's go-ahead moved it on).

- **Opening an `ask` conflict** whose owner is live makes it `BLOCKED` (`ASK`) with that owner kept, so it shows in the owner's `reef status` and `reef here` and nobody resolves it before a person says so.
- **The last attempt ending** (release, or the owner ended past its grace with no follow) makes it `BLOCKED` (`ATTEMPTS`) instead of `QUEUED`, so the queue only holds what a resolver may claim, and `claim --next` never trips on a blocked conflict.
- **A blocked conflict still closes** when its change stops carrying the conflict; that resolution needs approval (decision 3).
- **`UNOWNED`** stays as R3.27 made it (a person's change, waiting for a person); its tier is looked up and shown.

### Where tiers and caps are enforced

At four places, each a call to one pure function in `reef-daemon/src/assign/tier.rs`:

1. **Hand-offs** (`hand_off(row, wanted, reason, by) -> Handoff`), called from `moved`'s callers before they write: a wanted `ASSIGNED` that starts an attempt is allowed when the tier is not `ask` or the row has a go-ahead, and `attempts` is under the limit; otherwise the follower writes `BLOCKED` and `claim` and an agent's `assign` return `ASSIGNMENT_BLOCKED`. A wanted `QUEUED` becomes `BLOCKED` on the same test. `may_claim` becomes this function's claim case (R3.27's seam, kept by name).
2. **A person's assignment is a go-ahead.** `assign --workspace` or `--queue` by a person (actor `human`, not over the remote listener, as `take` is) records the go-ahead and, at the limit, grants one attempt, so it is never refused. An agent's `assign` (an orchestrator) is held to a claim's rules, as R3.27 already does.
3. **The close** (`approval(row, resolver) -> bool`): whether landing the resolution needs a person's sign-off (decision 3).
4. **The gate**: `builtin:resolution` reads that flag (below).

Reef cannot stop an agent writing files in its own workspace, and does not try: snapshots of a blocked conflict's change are recorded as always. The block is advice where the agent looks plus a refusal of claims and hand-offs, and the gate is the hard stop (S-230).

### A person's go-ahead: `reef conflict allow`

`AssignConflict` gains a target, `allow`, and a field, `attempts`:

- **`allow`** moves a `BLOCKED` conflict on: to its kept owner if that workspace's session is live (or a follow of it), as a new attempt with reason `ALLOWED`; else to the queue (`ALLOWED`). It records the go-ahead (`go_ahead_identity_id`, `go_ahead_at`) and, when the row is at its limit, grants attempts.
- **`attempts`** (1 to 20, default 1) is how many attempts a grant adds when the limit is reached. With `allow` on a conflict under its limit, it adds nothing unless given.
- **Person only.** Refused when the caller's actor is `agent` (`ALLOW_NEEDS_PERSON`, `next: reef conflict assignment <id>`) and over the remote listener (`REMOTE_HUMAN`), as `take` is.
- **Once per conflict** (decision 4): the go-ahead covers every attempt up to the limit. A repository that wants a person asked before each attempt writes `attempts = 1` on its `ask` rule.
- `allow` on a conflict that is not blocked records the go-ahead (useful before it opens an `ask` hand-off) and grants nothing unless `attempts` is given.

### Resolutions in the proposal flow (decisions 2, 3, 5)

A **resolution** is an assignment closed `RESOLVED`: the change no longer carries the conflict. R3.27 already keeps its conflicted commit, its resolved commit and the session that wrote it. This ticket adds, at the close:

- **`approval`**: whether landing the change needs a person's sign-off. True when the resolver is not a person and either the tier is not `land` (an `approve` or `ask` conflict) or the row was `BLOCKED` when it closed (resolved without a go-ahead, or past its attempts). The resolver is a person when the row was `TAKEN` or the resolving session's actor is `human` (decision 5). A resolution written outside Reef (the jj CLI, `resolved_session_id` empty) is judged by its tier: an unknown resolver of an `approve` conflict needs approval.
- **The marking.** `ProposalEntry.resolutions` lists the change's resolutions with their tier, attempts, `approval`, the resolving session and agent, and the conflicted commit, which `reef conflict show -r <commit>` reads for both sides and their provenance. `reef proposal show` prints one line per resolution and that command as a hint. This is the design's "marked as a resolution so the reviewer sees both sides' provenance", without copying the sides.
- **For policy.** `change.resolutions` in the policy input: `[{assignment, tier, attempts, limit, approval, resolver_actor, conflicted_commit}]`, so a policy can say more (`[[signoff]] when = 'change.resolutions.exists(r, r.tier == "approve")'` with its own approvers).
- **Which resolutions count.** Every `RESOLVED` row of the change: a change lands once, and after it lands the rows no longer matter. Pre-migration resolutions have `approval` false.

### The gate: `builtin:resolution`

A built-in rule, after `builtin:owners`:

- **Not applicable** when no resolution of the change has `approval`.
- **Satisfied** by one `signoff` evidence on the change's tree from a person identity (`is_signoff`'s test: `pass`, bound key, actor `human`, identity kind `person`), any person (decision 2), counted through `Policy::signoff` with a built-in spec so the message, `signoff` need and evidence ids are the same as `[owners]`'. In a stack, a sign-off on a member above counts, as R3.10 made sign-offs count.
- **Unsatisfied** otherwise: "resolves conflict asg_… (tier approve): needs a sign-off from a person (0 so far)". R3.45 reports it as `needs signoff` and writes no instruction (the reviewer's to do), so the agent's `reef here` says to wait.
- **A pending close counts.** The three input sites read the change's resolutions, and when the judged commit carries no conflict while the change's assignment is still open (the follower has not looked since the resolving snapshot), they count that assignment as the resolution its close will record, so a gate that runs a moment after the resolving snapshot never judges a resolution as ordinary work (S-234).

### Storage: schema 24

`0026_resolution_tiers.sql` (planned as `0024`; numbered after R3.32's `0025`):

```sql
-- R3.28: resolution tiers and attempt caps (ADR 0082). The tier is looked up from trunk()'s
-- reef-policy.toml for the conflict as last read; attempts count resolver turns; a person's
-- go-ahead and grants unblock. Times are milliseconds since the Unix epoch. Released
-- migrations are never edited.
ALTER TABLE conflict_assignments ADD COLUMN tier TEXT;                 -- land approve ask; NULL until looked up
ALTER TABLE conflict_assignments ADD COLUMN attempt_cap INTEGER;       -- the policy's attempts
ALTER TABLE conflict_assignments ADD COLUMN tier_rule INTEGER;         -- the [[conflicts.rule]] index; NULL for the defaults
ALTER TABLE conflict_assignments ADD COLUMN tier_conflict_id TEXT;     -- the conflict id it was looked up for
ALTER TABLE conflict_assignments ADD COLUMN tier_policy_commit TEXT;   -- trunk()'s commit read
ALTER TABLE conflict_assignments ADD COLUMN tier_policy_sha256 TEXT;   -- NULL: no policy, the defaults
ALTER TABLE conflict_assignments ADD COLUMN tier_error TEXT;           -- why the tier is ask by failure
ALTER TABLE conflict_assignments ADD COLUMN tier_at INTEGER;
ALTER TABLE conflict_assignments ADD COLUMN attempts INTEGER NOT NULL DEFAULT 0;
ALTER TABLE conflict_assignments ADD COLUMN granted INTEGER NOT NULL DEFAULT 0;
ALTER TABLE conflict_assignments ADD COLUMN go_ahead_identity_id TEXT;
ALTER TABLE conflict_assignments ADD COLUMN go_ahead_at INTEGER;
ALTER TABLE conflict_assignments ADD COLUMN approval INTEGER NOT NULL DEFAULT 0;  -- closed resolved: landing needs a person's sign-off
UPDATE conflict_assignments SET attempts = claims + (CASE WHEN EXISTS (
         SELECT 1 FROM conflict_assignment_events e WHERE e.repo_id = conflict_assignments.repo_id
           AND e.assignment_id = conflict_assignments.id AND e.reason = 'default') THEN 1 ELSE 0 END);
CREATE INDEX conflict_assignments_resolved ON conflict_assignments(repo_id, change_id)
             WHERE close_reason = 'resolved';
```

- Rows opened before the migration have no tier; the follower looks each up on its first pass. An `ASSIGNED` row is not moved to `BLOCKED` by the upgrade; the tier applies from its next hand-off.
- **Retention.** GC's tenth step keeps a `RESOLVED` row with `approval` while its change has a visible, mutable commit, so 30 days of waiting for review never drops the requirement (S-234). The rest is R3.27's 30 days.
- Events carry the new reasons; `note` records a grant (`granted 2 attempts`). No new event columns.

### The API: revision 40

No new RPC. In `conflicts.proto` and `assignments.proto`:

### The help-request seam (decision 6)

R3.28 blocks and records why; R3.32 builds the help request. They connect at `reef here`'s `ask` step: its `next` becomes R3.32's command with the assignment named (R3.32's row already says a help request names "the change or conflict it concerns"), so an agent that hits a block asks in one step, and the request shows in the person's inbox with the tier and attempts. A person unblocks with `reef conflict allow` (or `take`); R3.32's reply resumes the agent, which reads `reef here` again. R3.32 names the command `reef ask --reason conflict` (its brief, "The seam with R3.28"), which records the conflict and assignment ids, and adds its own step, `CHANGE_STEP_AWAIT_HELP`, ranked above this ticket's `ask` while the help request is open. The user decided that the agent raises the help request, not the daemon, and that an answer resumes the agent without unblocking the conflict. Whichever of the two merges second wires the `next` (a few lines in `here.rs` and a test), or names it as a follow-up in its PR.

## Implementation notes

- Build `tier.rs` and its two tables first: everything else calls it.
- `hand_off` takes the caller (`Caller` already has actor and remote) and returns the state, reason, whether an attempt starts, and grants; `moved` stays the writer of the row.
- The follower's conflict reads for the input use R3.25's `conflict::read` with files and attribution, only for rows whose conflict id or policy changed; `found` from the existing scan is unchanged.
- The lookup runs on the policy thread through `state.policy.load` (the compiled cache) and holds a `turns` permit, as evaluations do.
- `resolutions_of` is one indexed query; the three input sites share one helper that looks first and then reads.

## Performance expectations

- **Follower**: one policy blob id read per look per repository; tier lookups only for opened, changed or stale rows, each one conflict read and one `conflict_tier` evaluation (at most R3.07's cost bound), at most 64 a pass. The load test (`load.rs`) is run with a policy carrying three `[[conflicts.rule]]` entries and must stay within its gate.
- **Gate**: one indexed query per change judged, plus a look that costs nothing when the head has not moved.
- `GetStatus` reads the rows as they are; no lookup on the hot path.

## Risks

- **Agents ignore advice.** An agent can resolve a blocked conflict anyway. Mitigation: the gate requires a person's sign-off for such a resolution (S-230), so the cost of ignoring a block is review, not a bad landing.
- **Tier drift.** A policy change while a conflict is open changes the tier at the next look, not mid-attempt. Documented; the row shows the policy commit it used.
- **Cap too low for flaky resolvers.** A resolver that crashes three times uses the cap. Mitigation: follow and return do not count, so a resumed agent keeps its attempt; a person grants more with one command.
- **Seam with R3.32 renumbering.** Both tickets add a `ChangeStep` value and touch `here.rs`; the second to merge reconciles (the runbook's rule).

## Choices this brief made, and why

- **`BLOCKED` as a state, not a flag.** A blocked conflict must leave the queue, keep its intended owner and refuse claims; a state does all three in R3.27's existing machinery, and the inbox and view read one field.
- **Enforce at hand-offs and the gate, not at snapshots.** Reef cannot stop an agent writing in its own workspace without breaking the snapshot model; the gate is where a landing is decided, and the hand-off is where a resolver is chosen.
- **The tier as last looked up, refreshed lazily.** A refresh needs a conflict read; 64 rows a pass keeps a policy change from stalling the follower.
- **One input mapping in the daemon.** Two copies (CLI and daemon) would drift, and the daemon is the one that decides.
- **No copy of the sides on the resolution.** The conflicted commit is readable while indexed, and R3.25 reads it with provenance; a copy would be a second, stale source.
- **Any person approves.** A new approvers key per rule duplicates `[[signoff]]`, which a policy can already aim at resolutions through `change.resolutions`.

## Decisions for the user

1. **What an attempt is.** *User: as recommended (2026-11-18).* One resolver's turn, counted when a resolver is handed the conflict (its default owner, a claim, an assignment, a reopen after an undone resolution); the same agent continuing (followed, returned) does not count. Alternatives: only a claim that ends without a resolution (R3.27's reading; the owner's own first turn is free and unbounded); or also each resolution that later fails its checks or is declined (bounds the land-tier retry loop too, but needs resolutions tracked past their close).
2. **Who approves a resolution.** *User: as recommended (2026-11-18).* Any person's `signoff` on the resolved tree, through a built-in rule; a repository that wants particular approvers adds a `[[signoff]]` whose `when` reads `change.resolutions`. Alternatives: the `[owners]` only; or a new `approvers` key on `[conflicts]` and each `[[conflicts.rule]]`.
3. **What `ask` means after the go-ahead, and what ignoring a block costs.** *User: as recommended (2026-11-18).* An `ask` resolution still needs approval (ask is approve plus asking first), and a resolution of a blocked conflict lands only with a person's sign-off. Alternatives: after the go-ahead, `ask` behaves like `land`; or a blocked resolution is refused outright until a person both allows and signs off.
4. **How far a go-ahead reaches.** *User: as recommended (2026-11-18).* Once per conflict, covering its attempts up to the cap, and a person's `assign` counts as a go-ahead; per-attempt asking is `attempts = 1` on the rule. Alternative: a go-ahead covers one attempt only.
5. **A person's own resolution.** *User: as recommended (2026-11-18).* Needs no approval (a `TAKEN` conflict, or a resolving session whose actor is human). Alternative: the tier applies to people too, so a person's resolution of an `approve` conflict needs a second person's sign-off.
6. **Asking a person (the seam with R3.32).** *User: as recommended (2026-11-18).* The agent asks through R3.32's help request: whichever ticket merges second makes `reef here`'s `ask` step point at R3.32's command with the assignment named, and a person unblocks with `reef conflict allow` (the reply resumes the agent; it does not unblock). Alternatives: the daemon raises the help request itself when a conflict becomes blocked, so a person hears even from an agent that stopped; or a reply to a help request about a conflict also counts as the go-ahead.

## Departures in the implementation

- **The gate does not look first; it counts a pending close.** The gate's `judge_with` runs with a plain `&AppState`, and the follower's look needs the shared handle. Reading an open assignment of a change whose judged commit has no conflict as the resolution its close will record gives the same answer with no look and no wait (S-234). `ListProposals` does look first, as the assignment RPCs do.
- **A refresh that unblocks moves the conflict on.** A blocked conflict whose tier is looked up again and now allows an attempt (a policy changed from `ask` to `land`) goes to its kept owner when that session is live, as a new attempt, else to the queue; a queued one that now may not start an attempt is blocked.
- **A person handing a taken conflict back is a go-ahead**, as their assignment to the queue is, so it never lands straight in `blocked`.
- **Numbers.** `CHANGE_STEP_ASK = 11` (R3.32 holds 10 for `CHANGE_STEP_AWAIT_HELP`), `GetConflictRequest.policy_input = 11` (9 and 10 are the page fields). No new index: `conflict_assignments_by_change` serves `resolutions_of`.
- **Landed history** names a resolution's approver as a reviewer, as it names `[owners]` and `[[signoff]]` signers.
- **The CLI's `CLAIMS` column** became `TIER` and `ATTEMPTS`; `claims` stays in the JSON and in `reef conflict assignment`.
- **Review fixes that refine the design.** Under the same policy a narrowing conflict keeps its strictest tier and smallest cap, and only a person or a new policy unblocks a blocked conflict (review findings 1 and 2: a resolver fixing a strict rule's files first lifted the requirement). A `trunk()` that cannot be read, and a conflict wider than 10,000 paths, are failed lookups (`ask`), and a failed lookup is tried again after a minute. A taken conflict that an agent's session resolved needs approval, since an agent wrote it. Only a person's release of a take is a go-ahead.
- **A close uses the tier as last looked up, without refreshing it first.** A policy change the follower has not reached yet leaves the old tier for a close in the same second; rows opened before the migration close on the default `approve`, which fails closed.
- **GC keeps a resolution awaiting approval while its change is visible and not landed** (by Reef's lifecycle), not "mutable": a change made immutable outside Reef is kept until it is hidden, which only keeps a row longer.
- **The seam, wired when merging R3.32's main** (decision 6). `ask`'s `next` is `reef ask --reason conflict --conflict <asg_…> --while-blocked --tried <why it waits> -m`, with the assignment in the new `Workspace.conflict_assignment_id = 31` and the reason in `Workspace.conflict_block_reason = 32`, set where `step` is `ASK` (without them, an older daemon, `reef ask` takes the change's conflict and `--tried` says only that it waits for a person). R3.32 accepts any assignment of the change, blocked included. The rule between the two steps: a help request the workspace's session asked and still waits on (`AWAIT_HELP`) outranks `ASK`, so an agent that asked sees `await_help`; once it takes the answer, a conflict still blocked is `ask` again, since only a person's go-ahead or takeover unblocks it, and `step` takes the two as `Waits { conflict, help }`. The merge's reviews closed holes in that rule. An assignment that leaves `BLOCKED` withdraws the open help requests naming it (cause `INSTRUCTION_CAUSE_CONFLICT_UNBLOCKED`, in `record_and_announce`), so a person's allow without an answer does not leave the agent on `await_help`. The comment sweep's reconcile withdraws the same from the rows when a restart or a failed write skipped that. `HelpInput.while_blocked` (`reef ask --while-blocked`, which `next` passes) refuses a question asked after a person already unblocked the conflict (`CONFLICT_NOT_BLOCKED`). And `ask` with an answered help request of the session's, asked since the assignment last entered `BLOCKED` and its conflict last changed, names it in `Workspace.help_request_id`, and `reef here`'s next becomes `reef op watch --kind conflict-assignment --change <c> --count 1 --for 120` instead of the same question again.
