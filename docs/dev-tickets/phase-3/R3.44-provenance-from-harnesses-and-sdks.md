# R3.44 Provenance from harnesses and SDKs

Phase 3 · Size S, at its top end · Depends on: R3.04 (`DeclareProvenance`, `CreateWorkspaceRequest.provenance`, `reef provenance declare`, `REEF_MODEL` and `REEF_TASK`, API revision 18), R2.25 (the harness packages, `SIGNS`, `packages.rs`, `scripts/test-harness-packages.sh`), R2.26 (the provider contract's `--stdin --at FIELD=POINTER`, ADR 0053; the re-hold on `UserPromptSubmit`) · Unblocks: nothing listed; it feeds R3.31's intent section and R3.37's audit with records that carry a model, a harness, a client session and an instruction without anyone typing them

## Context

R3.04 gave provenance a format, a signer and a way to declare: `CreateWorkspaceRequest.provenance`, `DeclareProvenance` (which snapshots first), `reef provenance declare`, hidden `--model/--task/--instruction-file/--identity/--actor` flags on `ws create` and `ws run`, and `REEF_MODEL`/`REEF_TASK` as environment defaults. It left the clients that declare *without a person typing anything* to this row ("Departures" of R3.04: "Prompt hooks, `reef mcp`'s declaration and the SDK blocks would push R3.04 to L"). Its "What later tickets inherit" fixed the shape:

> R3.44 calls `DeclareProvenance` from a prompt hook through `reef provenance declare --stdin --at instruction=/<pointer> --at client_session=/<pointer> --at workspace=/<pointer>`, with the provider contract's pointer rules (ADR 0053). The hook hashes the instruction in process, never fails the prompt, prints nothing and starts no daemon. It adds `harness` and model facts to the env-signal table, `CreateWorkspaceRequest.provenance` from `reef mcp`, and the SDK block's `provenance=` argument and `declare()`.

So this ticket builds five clients of an API that already exists, and no API:

1. **`reef provenance declare --stdin --at FIELD=POINTER --hook`**: the provider contract's input rules on `declare`, an `instruction` field that is text hashed in the process, and a hook mode that never fails, never prints, never starts a daemon and gives up after two seconds.
2. **Harness facts in the env-signal table** (`SIGNS`, `reef-vcs/src/agents/mod.rs`): the harness's provenance name, the variable that carries its session id, and its prompt hook's event and pointers; plus the cross-tool `AI_AGENT` convention, read the same way for every harness. `ws create`, `ws run`, `ws provider create` and `reef mcp` declare what the environment tells.
3. **The harness packages install the prompt hook**: Claude Code's `reef` plugin (and, by decision 2, Codex's tree), rendered from the table.
4. **`reef mcp` declares** from its environment and the client's `initialize` (`clientInfo.name/version`) on the workspaces it creates and on its launch workspace.
5. **The SDKs** (Python and TypeScript): a `provenance` argument on the workspace block and `declare()` on its handle, hashing an instruction locally.

And one paragraph of the agent guide.

**No API change, no database change.** API revision stays 20 (or whatever main has when this merges), schema stays 11. Everything here is a client of R3.04's RPCs.

### 1. `reef provenance declare --stdin --at FIELD=POINTER`

`declare` takes R2.26's input rules, unchanged, through a module both commands share (`cli/input.rs`: `Input`, `Fields`, `parse_stdin`; the provider keeps its reason `PROVIDER_INPUT_INVALID`, `declare` reports `INVALID_PROVENANCE` with `field`, as R3.04's errors do):

| Field | From a pointer or key | Meaning |
| --- | --- | --- |
| `workspace` | a string: id, prefix, or a path inside one (`/cwd`) | the workspace to declare for; the scope's default (`--workspace`, `REEF_WORKSPACE`, the current directory) when absent |
| `instruction` | a string, **hashed in the process** | the instruction's text; SHA-256 of its UTF-8 bytes exactly as the JSON string decodes, nothing trimmed; the text is never sent, logged or written |
| `instruction_sha256` | a string | an already computed hash |
| `model`, `harness`, `task`, `client_session` | strings | as the flags |

- A flag wins over a pointer, a pointer over the object's key (ADR 0053). `--instruction-file -` and `--stdin` both want stdin, so they conflict (usage error). `instruction` and `instruction_sha256` from the same input: `instruction` wins.
- **The instruction's bytes.** JSON gives the hook the text as a string; its UTF-8 encoding is what is hashed, so `printf %s "$prompt" | shasum -a 256` of the same text matches. What the harness puts in that string (Claude Code's expanded pastes and `<pasted_content>` markers) is part of "exactly as delivered", and `docs/provenance.md` says so.
- **`--stdin` alone** (no `--hook`) is an ordinary command: it fails, prints and autostarts like any other `declare`. It exists for scripts and other harnesses' adapters.

### 2. `--hook`: never fails, never prints, never slows the prompt

`reef provenance declare --hook` is the mode a harness's hook runs. It follows `reef presence hook` exactly:

- **Never fails**: exit 0 whatever happens; a refused field is dropped (an oversize or control-character `model` from the event declares the rest), not fatal. Usage errors are the one exception and exit 2, since they are the plugin's bug, caught by `packages_agree` before a release.
- **Prints nothing**: stdout and stderr stay empty, since `UserPromptSubmit`'s stdout is context the model sees. Failures go to the debug log (`-v`, `REEF_LOG`) by field name and reason, **never with the event or the instruction**. The plugin still adds `>/dev/null 2>&1 || true`.
- **Starts no daemon** (`--hook` implies `--no-autostart`): no daemon means nothing to record onto.
- **Gives up after 2 seconds** over everything (connect, read, declare, fan-out), with stdin read on its own thread, as `presence hook` does. `DeclareProvenance` snapshots first (R3.04 decision 10), which is what makes edits before the prompt keep the old instruction; the deadline bounds it. A declaration the client abandoned may still complete in the daemon: the snapshot is a blocking task that is not cancelled, and the swap after it either happens or does not. Test 6 checks the daemon is left consistent either way.
- **What it reads from the environment** (unlike plain `declare`, which reads only flags): the harness facts below, when the event does not give them. A hook runs as the harness's child, so its environment is the harness's.
- **Nothing to declare is success**: no workspace at `workspace`, no daemon, an ended workspace.
- **Latency**, measured in the implementation and recorded in the PR: the median and p99 of 200 runs of the plugin's exact command with a 2 KiB prompt event, (a) with no daemon (no socket), (b) with a daemon and a workspace with nothing to snapshot, (c) with a daemon and the cwd outside every workspace. Gates: (a) median under 20 ms, (b) and (c) under 60 ms, every run under the 2 s deadline plus process exit.

### 3. Which workspaces a prompt declares for (decision 1)

The common flow in Reef's own guide is an agent in the repository's root that runs `reef ws run -- …`, `reef ws create`, or MCP `create_workspace`: the harness's `cwd` is not a workspace, and the workspace often does not exist yet when the prompt is submitted. Declaring only for `/cwd` covers a harness started inside a workspace (`reef ws run -- <harness>`, the `reef-workspaces` plugin, `cd` into one) and nothing else.

**Recommended (option A): the cwd's workspace, every live workspace of the same client session, and a session note for the ones still to be made.**

- The hook declares for the workspace at `workspace` (if any), and for every `active` workspace whose session's declared `client_session` equals the event's (one `ListWorkspaces` over every repository, `states: [ACTIVE]`, filtered here), concurrently, within the deadline.
- It also writes a **session note**: `<state>/provenance/sessions/<name>.json` (`name` as `presence hook`'s id files: the session id if plain, else its hash), mode 0600 in a 0700 directory, holding `{instruction_sha256, model, harness, declared_at}`: hashes and labels only, never text. It replaces the previous note. Notes older than 24 hours are deleted by the next hook that writes one.
- `ws create`, `ws run`, `ws provider create` and `reef mcp`'s `create_workspace`, when the environment names a client session (below) that has a note younger than 24 hours, declare the note's instruction and model unless a flag gives them. So the workspace an agent creates in answer to a prompt is created under it.
- The note is the client's, on the harness's machine: no daemon state, no API. A remote daemon (`REEF_REMOTE`) works the same, since the hook and the creation run beside the harness.

Option B: the cwd's workspace only, as the row reads. Simpler (no note, no fan-out), but most records of agents following the guide would carry no instruction.

### 4. The env-signal table gains the harness's facts (decision 3 for the table's shape)

`SIGNS` is the one place a harness is named. Each row gains:

```rust
/// What provenance takes from this harness (R3.44); None when nothing is verified.
provenance: Option<Provenance>,

struct Provenance {
    /// The harness's name in `context.harness`, as its MCP clientInfo and AI_AGENT give it.
    name: &'static str,                      // "claude-code"
    /// A variable holding the harness's session id, in its tools', hooks' and MCP servers' processes.
    session_env: Option<&'static str>,       // Some("CLAUDE_CODE_SESSION_ID")
    /// A variable holding the running model, where the harness documents one.
    model_env: Option<&'static str>,         // None: "There is no $CLAUDE_MODEL"
    /// The hooks that declare: (event, pointers), rendered into the package.
    hooks: &'static [(&'static str, &'static [(&'static str, &'static str)])],
}
```

| Harness | `name` | `session_env` | `model_env` | `hooks` |
| --- | --- | --- | --- | --- |
| Claude Code | `claude-code` | `CLAUDE_CODE_SESSION_ID` (documented) | none (documented as none) | `UserPromptSubmit`: `instruction=/prompt`, `client_session=/session_id`, `workspace=/cwd`; `SessionStart`: `model=/model`, `client_session=/session_id`, `workspace=/cwd`; `PostModelSwitch`: `model=/to_model`, same two |
| Codex | `codex` | none until verified (`CODEX_THREAD_ID` is source-only) | none | decision 2 |
| Cursor | none | | | follow-up |
| opencode | none | | | not possible without npm |

**The harness's name and version, read the same for every harness:**

1. `--harness` or the event's pointer;
2. in `reef mcp`, the client's `initialize`: `clientInfo.name/clientInfo.version` (the protocol's own self-description);
3. `AI_AGENT`, the cross-tool convention: `name[_/]version[_/]rest` becomes `name/version`, with a version of digits and dashes read as dots (`claude-code_2-1-318_agent` → `claude-code/2.1.318`), and any other value that passes R3.04's label check kept as it is;
4. the row whose `env` signal is set: its `name`, with no version.

So the same Claude Code session reads `claude-code/2.1.318` from its hooks (`AI_AGENT`, `_agent`), its MCP server (`clientInfo`), and its shells, and a harness Reef has never heard of that sets `AI_AGENT` is named without a row. A value that fails the label check is ignored, never fatal (R3.04 F4).

**The client session**: the row's `session_env` when its `env` signal is set (Claude Code: `CLAUDECODE=1` and `CLAUDE_CODE_SESSION_ID`). **The model**: `REEF_MODEL` (R3.04), else the row's `model_env`, else the session note's (from `SessionStart`/`PostModelSwitch`).

**Where the environment declares**: `ws create`, `ws run`, `ws provider create` (so a subagent's worktree workspace carries its harness and session), and `reef mcp`. As R3.04 decided, only commands that create a workspace read the environment; plain `declare` reads only its flags, and `declare --hook` reads it for what the event lacks. `ws run` passes nothing new to its command: the command inherits the harness's environment anyway.

**Existing constants** in `packages.rs` (the edit tools' names and pointers, the worktree events) move into the same row as `presence` and `provider` facts, so a harness's facts are in one place (decision 3).

### 5. The harness packages install the hooks (decision 2)

Rendered by `packages.rs` from the row's `hooks`, in the `reef` plugin (not `reef-workspaces`), since a session in any workspace, or creating them, wants them:

```json
"UserPromptSubmit": [{"hooks": [{"type": "command", "timeout": 5,
  "command": "command -v reef >/dev/null 2>&1 && reef provenance declare --hook --at instruction=/prompt --at client_session=/session_id --at workspace=/cwd >/dev/null 2>&1 || true"}]}],
"SessionStart":     [... "--hook --at model=/model --at client_session=/session_id --at workspace=/cwd" ...],
"PostModelSwitch":  [... "--hook --at model=/to_model --at client_session=/session_id --at workspace=/cwd" ...]
```

- It runs beside `reef-workspaces`' re-hold on the same event; harnesses run an event's hooks in parallel, and neither depends on the other.
- `packages_agree` gains: every `provenance declare` hook parses with this binary, carries `--hook`, and names only fields `declare` takes; the pointers come from the row.
- **Codex (decision 2)**: the same three facts exist in Codex's documented hook input (`prompt`, `session_id`, `cwd`, and `model` on every event), so its row could render `plugins/agent-plugins/hooks/hooks.json` with one `UserPromptSubmit` hook that also takes `model=/model`. Two things are unverified: that the Agent Plugins 1.0.0 tree may carry `hooks/hooks.json` (Codex's own `.codex-plugin` format may), and Codex's trust flow (a plugin's hook is skipped until the user trusts it in `/hooks`). `test-harness-packages.sh` can check the first with the pinned Codex, no sign-in needed.
- `scripts/test-harness-packages.sh` gains, for Claude Code: the installed plugin's `UserPromptSubmit` command, run as Claude Code runs it (`sh -c`, event on stdin, the plugin's environment with `CLAUDECODE`, `AI_AGENT`, `CLAUDE_CODE_SESSION_ID`), declares the event's instruction hash, client session and harness for a scratch daemon's workspace, prints nothing, and exits 0 with no daemon.
- One **live check** by hand with the pinned Claude Code (a scratch daemon, a `--plugin-dir` session, `claude -p` twice in a workspace): both prompts' hashes appear on records, the harness reads `claude-code/2.1.316`, the session's `model` comes from `SessionStart`, and the prompt's text is nowhere in the daemon's state directory. Recorded in the PR, with cost.

### 6. `reef mcp`

- **`initialize`**: the server keeps the client's `clientInfo` (`RequestContext::peer().peer_info()`) and makes `harness` from it as in section 4, step 2.
- **`create_workspace`** sends `CreateWorkspaceRequest.provenance`: `harness`, `client_session` (the row's `session_env`), `model` (`REEF_MODEL`, the row's `model_env`, the session note), `task` (`REEF_TASK`), and the note's instruction (decision 1). The tool gains **no parameter**, so `tools/list` stays byte for byte the same. A daemon older than API revision 18 is not a concern for the CLI-shaped server, which already refuses an incompatible daemon.
- **The launch workspace** (`REEF_WORKSPACE`, or started in a workspace): at the first tool call that resolves it, the server declares `harness` and `client_session` once, only the fields that differ from the session's current context, with its snapshot. A server that serves several agents (ADR 0035) declares only for its launch workspace, never for one a call names.
- `NOT_TOOLS`' reason for `DeclareProvenance` stays true and is reworded to drop "(R3.44)".
- MCP note: Claude Code's MCP server "retains the ID it was spawned with" across `/clear`, so `client_session` from `reef mcp` is the session at spawn. Documented, not worked around.

### 7. The SDKs (decision 4)

Python (`reef`, sync and `reef.aio`):

```python
with client.workspace("/repo", provenance=reef.Provenance(model="m", task="T-1", instruction=prompt_text)) as ws:
    ...
    ws.declare(instruction=next_prompt)            # snapshots first; snapshot=False to skip
    ws.declare(task="", instruction=None)          # "" clears a field; None leaves it
```

- `reef.Provenance` (a frozen dataclass): `model`, `harness`, `task`, `instruction` (`str` or `bytes`, hashed with `hashlib.sha256` in the process and never kept on the object: the constructor stores only `instruction_sha256`), `instruction_sha256`, `client_session`, `identity`, `actor` (`"agent" | "executor" | "human"`, creation only). A `dict` with the same keys is accepted.
- `handle.declare(**fields, snapshot=True) -> DeclareProvenanceResponse`, through `DeclareProvenance`; `identity`/`actor` there are a `TypeError`. `client.attach(...)` handles have `declare()` too.
- Defaults: `REEF_MODEL` and `REEF_TASK`, as the CLI's, when `provenance` does not set them; nothing else from the environment (decision 4). `client.require_revision(18)` before sending a declaration, so an older daemon is an `IncompatibleError` rather than silently ignored.

TypeScript (`reef-vcs`): `client.workspace({ ..., provenance: { model, task, instruction } })`, `handle.declare({ ... }, { snapshot })`, hashing with `node:crypto` (`createHash("sha256")`), the same defaults and revision check. Both READMEs gain a short example.

### 8. The agent guide

One line in "Inside ws run", within a raised budget (decision 5):

```
Set `REEF_MODEL` and `REEF_TASK` to name your model and task on what you record;
harness hooks declare each prompt's hash (`reef provenance show`).
```

`docs/provenance.md` replaces "Harness hooks, `reef mcp` and the SDKs' workspace blocks declaring on their own are R3.44" with a **Declared for you** section: what each client declares, from where, the `AI_AGENT` rule, the session note, the `--hook` contract, and how another harness's adapter declares (`reef provenance declare --hook --at …`, three lines). The threat model gains rows in S-114 to S-121 (below). An ADR is not needed if decisions 1 to 3 go as recommended (they apply ADR 0052, 0053 and 0058); if the user wants the `AI_AGENT` reading or the session note recorded as decisions, ADR 0064.

## Threat rows (S-114 to S-121)

| Row | Asset | Who | Severity | Threat | Mitigation |
| --- | --- | --- | --- | --- | --- |
| S-114 | The instruction's text | A local reader of logs or files | Medium | The hook handles the prompt; a log line, a note, or a crash report could keep it. | The text is hashed on read and dropped; logs name fields only; the note holds hashes; a test greps the state directory, logs and the daemon database for the prompt. |

## Tests

Unit (`reef-vcs`):

1. `input`: the shared `Fields` keep R2.26's tests and precedence; `declare`'s field list; `--instruction-file -` with `--stdin` is a usage error.

## Out of scope

- **A subagent's own instruction.** A subagent's prompt arrives as the parent's tool call (Claude Code's `Agent` tool input), not as a `UserPromptSubmit`; its worktree workspace gets the harness and session here, and the parent's latest instruction through the note. Declaring the subagent's task message as its instruction is a follow-up issue.
- **Cursor's and opencode's prompt hooks**: follow-up issues (Cursor: `beforeSubmitPrompt` in `.cursor/hooks.json` from `reef init`; opencode: an npm plugin, R2.25's deferral).
- **Verifying a declaration.** Everything here is declared (S-67); R3.42 and R3.43 are where identity gets stronger.
- **A tool to declare from MCP.** `DeclareProvenance` stays out of `tools/list` (budget, and a model should not choose its own instruction).
- **Filtering by harness or model**: R3.37.

## Risks

- **A hook on every prompt adds latency.** Bounded by the 2 s deadline and gated in section 2; a snapshot of a big pending edit is the slow case, and it is work the watcher would do anyway.
- **Undocumented signals change.** `AI_AGENT`'s Claude Code format is source-only; a change in it degrades to the row's name with no version, never to an error. `CLAUDE_CODE_SESSION_ID` and the hook fields are documented.
- **The fan-out is only as good as the declared client session.** A workspace created outside the harness, or by an MCP server after `/clear`, has another or no session, so a prompt does not reach it. Documented.
- **Codex's trust prompt** (if decision 2 takes B): users see an untrusted-hook review the first time. Documented in the plugin's README.

## Choices this brief made, and why

- **`--hook` on `declare`** rather than a `reef provenance hook` subcommand: the row and R3.04 name `declare --stdin --at`; the hook mode is that command's never-failing form.
- **The text hashed in the `reef` process**, never in the hook's shell, so no harness's shell quoting or `printf` subtleties are involved and the text stays out of `argv`.
- **`AI_AGENT` read generically** rather than one variable per harness: it is the cross-tool convention, and it names harnesses Reef has no row for. The table still holds what is harness-specific (the session variable, the hook pointers).
- **No API change**: everything rides on R3.04's fields.

## Departures from dev-phases.md

- **The prompt hook also reaches workspaces the harness's session creates or holds elsewhere**, through the session's client session and a session note, so the guide's root-checkout flow records instructions (decision 1). If the user picks option B, there is no departure.
- **`SessionStart` and `PostModelSwitch` hooks declare the model**, since the reference harness documents its model only in hook events, not in its environment ("where a harness documents one" is read as "in its environment or its hook events").

## Departures found while implementing

- **Codex gets no hook in this ticket.** With the pinned Codex 0.166.0 under a scratch `CODEX_HOME`, a `hooks/hooks.json` added to the Agent Plugins tree (`plugins/agent-plugins/`) is installed into the plugin cache, but the app server's `hooks/list` shows no hook from it, with or without a `hooks` key in `plugin.json` and with `[features] plugin_hooks` (which 0.166.0 lists as `removed`); the same file as the user's `~/.codex/hooks.json` is listed (untrusted until reviewed). Codex reads plugin hooks from its own `.codex-plugin` format only. Per decision 2, Codex is a follow-up issue, #237; Cursor and opencode are #238, and a subagent's own instruction #239.
- **The pinned Claude Code (2.1.316) was checked**, from the npm package's binary: it sets `AI_AGENT` the same way as 2.1.318 (`claude-code_<version, dots as dashes>_…`), names itself `claude-code` with its version in MCP `clientInfo`, exports `CLAUDE_CODE_SESSION_ID` to tool shells and hooks, and has `SessionStart`'s `model` and `PostModelSwitch`. `claude plugin validate --strict` accepts the new hooks, and `scripts/test-harness-packages.sh` runs the installed plugin's prompt hook as Claude Code does.
- **The guide's budgets.** `long()` is the whole guide without its marker line, not the part after it, so "the long part under 1,600" bounds nearly the whole guide. The line went in at 1,597 bytes by trimming three phrases (`each one's`, `(default: here)`, `in the workspace`); the whole-guide budget is 1,750 as decided. `o200k`: 434 to 446 tokens (the short part unchanged at 125); no Anthropic key was available locally to count the other.
- **`--hook` swallows every failure, usage errors from `--at` included.** Clap's own parse errors still exit 2; a field name the command does not take is logged, since `packages_agree` checks every rendered hook's fields.
- **`reef mcp` declares the launch workspace without a snapshot.** Its harness and client session name who runs there, not what an edit was for, and a snapshot would have slowed the server's first call.
- **`declare --stdin` refuses a bad field as `INVALID_PROVENANCE`** (with `field`), R3.04's reason, rather than the provider's `PROVIDER_INPUT_INVALID`. The shared input module (`cli/input.rs`) takes each command's error.
- **`reef schema`**: `provenance declare`'s row gains `bytes_with: ["hook"]`: with `--hook` it prints nothing.
- **Live check** (2026-11-08, the installed Claude Code 2.1.319 with `--plugin-dir plugins/claude-code`, a scratch daemon, `claude -p` in a workspace, $0.35): the session's workspace got the prompt's SHA-256 (equal to `printf %s "$prompt" | shasum -a 256`), the session id, and `harness: claude-code/2.1.319` from `AI_AGENT`; the watcher's record of the file it wrote carries them; the prompt's text is nowhere in the state directory. A second run with a probe plugin ($0.31) showed that `SessionStart` in `-p` mode carries no `model`, so no model was declared: whether an interactive session's does is unverified here.
- **The guide line is shorter than section 8's**: "`REEF_MODEL` and `REEF_TASK` name your model and task in provenance." The clause about harness hooks went, to fit the 1,600 bytes, and because it gives an agent nothing to do.
- **Review fixes** (the PR lists every finding): in `--hook`, a field that is not a string is left out and the rest declared, every step is best effort (the note, each lookup, the session's workspaces), `--workspace` wins over the event's pointer as ADR 0053 says, paths are not looked up on a remote daemon, and the note is written on a thread of its own; the note ages each field from its own declaration (the brief's `declared_at`, per field); the agent table's session is taken only when exactly one harness's signal is set and `AI_AGENT`, if set, names the same harness; `reef mcp` declares the launch workspace's harness and session only where it has none, never over a newer one a hook declared; an empty `--model` or `--task` counts as not given for the `PROVENANCE_DISABLED` retry; the SDKs ignore a `REEF_MODEL` or `REEF_TASK` the daemon would refuse, and an empty instruction clears it; a hook whose logging cannot start (a bad `REEF_LOG`) runs without it instead of failing.
- **Not built: test 6's forced deadline during a large snapshot.** The silent-socket case covers the deadline at connect; what the daemon does with a `DeclareProvenance` whose client left mid-snapshot is untested here, and is part of #239.

## Decisions for the user

1. **Which workspaces a prompt's instruction reaches.**
   - **A (recommended)**: the cwd's workspace, every active workspace with the same client session, and a 24-hour session note (hashes only) that `ws create`, `ws run`, `ws provider create` and `reef mcp` read, so workspaces an agent creates in the root checkout carry the prompt.
   - B: only the workspace at the hook's `cwd` (or `REEF_WORKSPACE`), as the row reads; agents that create workspaces from the root get model, harness and session but no instruction.
2. **Which harnesses get a prompt hook in this ticket.**
   - **A (recommended)**: Claude Code only (verified fields, live check), with Codex's row filled once `test-harness-packages.sh` shows its pinned release installs `hooks/hooks.json` from the Agent Plugins tree; if it does not, a follow-up issue.
   - B: Claude Code and Codex now, from Codex's docs, accepting the unverified plugin-tree path and the first-run trust review.
   - C: Claude Code only, Codex a follow-up regardless.
3. **The table's shape.**
   - **A (recommended)**: the harness's provenance facts (name, session variable, model variable, hook pointers) in its `SIGNS` row, and the existing presence and provider constants in `packages.rs` moved into the same row, so all of a harness's facts are in one table.
   - B: the new facts in the row, existing constants left where they are (smaller diff).
4. **What the SDKs read from the environment.**
   - **A (recommended)**: only `REEF_MODEL` and `REEF_TASK`, as the CLI; harness and session are the program's to pass. No second copy of the env-signal table in Python and TypeScript.
   - B: also `AI_AGENT` (generic) for `harness`.
   - C: nothing; every field explicit.
5. **The agent guide's budget.** The line in section 8 is about 130 bytes; the guide is at 1,585 of 1,600.
   - **A (recommended)**: raise `guide_fits_its_budget` to 1,750 bytes (the long part stays under 1,600), and rerun the token count for #122 in the PR.
