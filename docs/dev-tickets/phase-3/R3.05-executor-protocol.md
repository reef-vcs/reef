# R3.05 Executor protocol

Phase 3 · Size M, at its top end, with the scope moves below · Depends on: R3.01 (the evidence format, `Verified::check`, `AddEvidence`'s insert path, migration 0007), R2.01 (the v1 schema and its review checklist, ADR 0029); builds on R3.02 (`UploadArtifact`, GC's seventh step), R3.03 (session keys with actor `executor`, `Rule::LinkedIdentity`, `KeyIdentity`) and R3.04 (API revision 18, schema 10, GC's eighth step) · Unblocks: R3.06, R6.03; through them R3.13, R3.14, R3.18 to R3.22, R3.34 and R4.11

## Context

The design gives this ticket one paragraph (CI load): "Running the jobs stays outside Reef. Sandboxing, hermetic builds, remote execution, and runner fleets are an established domain, and Reef sits on top of it through the evidence format and the executor protocol. Scheduling is Reef's, execution is the executor's, and the protocol between them is what Reef must get right: a request names a tree hash, the targets to check, the evidence kinds expected, and a budget; a response is signed evidence plus artifacts; progress streams over the presence channel. The protocol is written down before the reference executor is built, so other executors can be built against it." Its non-goals add: "Running builds or tests. The system defines the attestation format and the executor is external." Its open problems add: "Evidence can be forged by the agent that produced it. Only attestations from executors the repository trusts carry weight."

Four earlier tickets left this one its pieces:

- **R3.01** fixed the response's contents: "R3.05 puts envelopes as bytes in the executor response, and reuses `Evidence` and `EvidenceResult` in its messages. The request's 'tree hash' is the `gitTree` value. Evidence kinds expected are the `kind` vocabulary. An executor's `error` result is `EVIDENCE_RESULT_ERROR`." It also said an executor "adds by tree alone, and creates no link", and that "R3.05's progress travels over presence".
- **R3.02** fixed the artifacts: "an executor uploads them through `ArtifactService` (resumable, deduplicating, over the remote listener) before returning its envelopes, or R3.05 defines an inline form". This brief takes the first option.
- **R3.03** fixed the signer: an executor "issues one key per run, `actor: executor`", bound to the default person identity locally, and to a `ci` identity through a remote token linked to it in CI.
- **R2.10 and R2.11** (ADR 0037) built the presence channel, which already has a daemon-reported progress kind and the rule that a client may not report a kind the daemon owns.

Nobody requests checks yet. The landing service (R3.13) and the batching queue (R3.14) will. Until they exist, a protocol with only an executor side could not be exercised, and R3.06 would have nothing to run against. This ticket therefore builds a small, complete job queue in the daemon, with both sides:

1. **The protocol**: protobuf messages and an `ExecutorService` in `reef.api.v1`, with a job's lifecycle. A requester submits and cancels jobs. An executor claims a job under a lease, reports progress and partial evidence, and completes it with signed evidence. A job can also lapse, run out of budget, or expire.
2. **The daemon's side**: a durable job table, the claim matching and the leases, the checks that bind returned evidence to the requested tree and kinds, and progress published as daemon-reported presence.
3. **A requester for now**: `SubmitJob` and `reef job submit|show|list|cancel`, for tests, scripts and R3.06, and an in-process function that R3.13 and R3.14 will call.
4. **The written protocol**: `docs/executor-protocol.md`, which an outside author can build an executor against without reading Reef's source, and a conformance test with a fake executor.

What stays out is the executing: materializing a tree, running a command, sandboxing and signing are R3.06's ("Out of scope").

### Who connects to whom: executors pull

**The daemon never connects to an executor.** An executor is a client of the daemon, like an agent or a CI job. It dials the daemon's socket, or its remote listener with a token, claims a job, and reports back on the same connection. The daemon keeps a queue and leases its jobs out, as it leases workspaces.

Why pull, and not the daemon calling an executor endpoint:

- **Reef starts nothing.** The design keeps execution outside Reef, and the threat model already wants the one place where the daemon runs repository code (store builds) gone (#61). A daemon that dials executors needs endpoints, credentials for them, and outbound network access. Those are a configuration surface and an attack surface (it would make requests on behalf of whoever can submit a job), and no ticket needs them.
- **It fits what exists.** The socket, the remote listener's TLS, scoped tokens, per-token limits, audit logging and R3.03's linked identities already authenticate and bound a remote client. A CI runner behind NAT can dial out to a daemon. A daemon cannot dial in to it. Runner fleets such as Buildkite agents and self-hosted GitHub runners work the same way, for the same reason.
- **An adapter is an executor.** A process that claims Reef jobs and forwards them to a remote execution service, a CI system or a runner fleet is an executor, and needs nothing more from this protocol. That is how Reef "sits on top of" that domain.

**Alternatives** (ADR 0059): (b) the daemon calls a configured executor endpoint (rejected for the reasons above); (c) a transport-neutral message set with several bindings. This brief takes the useful half of (c): the spec defines the messages and the state machine independently of gRPC, so R4.11 and R6.03 can restate them, but only one binding ships: `reef.api.v1.ExecutorService` over gRPC.

**The claim is a long poll, not a stream.** `ClaimJob` is unary with a `wait` of up to 60 seconds. It returns a job as soon as one matches, or nothing when `wait` runs out. A stream of offers would still need a claim call to take one, would hold one of a token's 16 streams per idle executor, and would need idle-timeout handling at every proxy in between. A unary call works from any gRPC client and both SDKs.

**What R4.11 inherits.** The store serves the same `ExecutorService` (ADR 0029 decision 1: the package is `api`, not `daemon`, because the store serves the same services), with the same messages and the same rules, to executors that dial it with a token linked to a `ci` identity. Only where the tree's content comes from changes.

### What a job is

A **job** is one request for checks on one tree, from one requester, run by one executor at a time:

```
            SubmitJob
               │
               ▼        ClaimJob                    CompleteJob
           ┌────────┐ ─────────────▶ ┌─────────┐ ──────────────▶ COMPLETED (outcome: done,
  ┌──────▶ │ QUEUED │                │ RUNNING │                    budget_exhausted, failed)
  │        └────────┘ ◀───────────── └─────────┘
  │          │   │    lease lapsed,       │  │
  │          │   │    or UpdateJob        │  └── deadline passed ─────▶ EXPIRED (deadline)
  │          │   │    release, with       │
  │          │   │    attempts left       └── lapsed, no attempts left ▶ EXPIRED (attempts)
  │          │   └── queue_timeout passed ─────────────────────────────▶ EXPIRED (queue_timeout)
  │          └────── CancelJob (also from RUNNING) ────────────────────▶ CANCELLED
  └─ requeued: attempt + 1
```

- **Ids** are `job_<16 hex>`, random, unique across the daemon (an index, not only per repository), as R3.03's `idn_` and `ses_` ids are. Every row is still keyed by repository (ADR 0003). Reads accept the full id, or `job_` and a unique prefix of 4 or more hex digits. `UpdateJob` and `CompleteJob` take only the full id.
- **States**: `QUEUED`, `RUNNING`, and three terminal ones. `COMPLETED` means the executor finished, and its `outcome` says how much it ran. `CANCELLED` means a requester cancelled it. `EXPIRED` means the daemon ended it, and its `end_reason` says why. No terminal state says anything about pass or fail. The evidence does.
- **Outcomes** (`CompleteJob`):
  - `DONE`: everything requested ran, and the evidence covers every requested pair ("Completeness").
  - `BUDGET_EXHAUSTED`: the executor stopped at its budget, with whatever evidence it had.
  - `FAILED`: the executor could not run the checks (it could not get the tree, its runner broke), with a `message`.

  A check that ran and could not reach a verdict is not `FAILED`: it is evidence with `result: error`, which R3.01 defined so that R3.14's bisect does not blame a change for an executor's failure.
- **End reasons** (`EXPIRED`): `QUEUE_TIMEOUT` (nobody claimed it in time), `ATTEMPTS` (its last attempt's claim lapsed or was released), `DEADLINE` (its wall time and the grace passed while it was running).
- **No operation.** A job is daemon metadata, not jj state, like evidence. Nothing in the job's life records an operation, and undo has nothing to revert. The five WRITE RPCs join ADR 0029 decision 12's exceptions. Every transition is logged under `reef_daemon::executor::audit`: the job, repository, requester's agent, remote token, executor and outcome. Remote WRITE calls are also logged in `remote::audit`.

### The request: `JobSpec`

| Field | Required | Meaning | Checked (`INVALID_JOB_SPEC`, `field`) |
| --- | --- | --- | --- |
| `tree_id` | yes | The tree to check: the `gitTree` value of R3.01's subject. `SubmitJob` takes it directly or resolves it from a `revision` | Lowercase hex of the store's length, and present in the repository (`TREE_NOT_FOUND`); a conflicted revision is `CONFLICTED_REVISION` |
| `kinds` | yes | The evidence kinds expected, 1 to 16, from R3.01's open vocabulary (`test`, `build`, `lint`, `policy`, later `behavioral-diff`) | R3.01's pattern, `^[a-z][a-z0-9-]{0,62}$`; duplicates removed; stored sorted |
| `targets` | no | The targets to check, 0 to 1,000, in the executor's own naming (`crates/reef-lib`, `//foo:bar_test`). Empty means the whole check of each kind | R3.01's target rule: 1 to 512 bytes, no control characters; duplicates removed; stored sorted; `kinds × max(1, targets)` at most 1,000 |
| `budget.wall_time` | no | How long one attempt may run, from its claim. Default `[executor] default_wall_time` (30 minutes) | 1 second to `[executor] max_wall_time` (6 hours by default) |
| `budget.cpu_time` | no | CPU time one attempt may use; enforced only by the executor, which reports its use | 1 second to 7 days |
| `requirements` | no | Labels an executor must have to claim it, 0 to 16, `key=value`, such as `os=linux` | key `[a-z0-9][a-z0-9._-]{0,62}`, value 1 to 128 bytes of visible ASCII |
| `priority` | no | Higher is claimed first; equal priorities go in submission order. Default 0 | any `int32` |
| `commit_id` | no | A commit with this tree, for executors whose tools check out commits. Set when the job was submitted with a `revision` | must have `tree_id` as its tree |
| `change_id` | no | The change the job is for. Set when submitted with a `revision`. Reef's record, and the presence entry's `change`; the executor may ignore it | full hex |

What the request does **not** carry, deliberately:

- **No command, script, image or environment.** What runs for a kind and a target is the executor's: its own configuration, or a declaration in the repository at that tree, which R3.06 decides. If a request could carry a command, then every caller who can submit a job (every `write` token, every same-uid process) could run code on every executor. The spec states the corollary for executor authors: targets are data, matched against what the executor knows how to run and passed as arguments, never through a shell (S-75).
- **No repository location.** The job names `repo_id`. A local executor reads the root with `GetRepository`. A remote one has its own clone or reads files through `FileService` at `commit_id` (below).
- **No change in the claim.** As R3.01 says, an executor sees a tree. `change_id` is context, not part of what is checked.
- **No base tree.** R3.22's behavioral diff runs on a base tree and the proposal, and adds a `base_tree_id` field then. Fields are only added (Versioning).

**Dedupe.** Two open jobs (queued or running) in one repository with the same tree, kinds, targets and requirements are the same work. `SubmitJob` returns the open one with `created: false`, raising its priority to the higher of the two, unless the request sets `duplicate`. The spec's digest is the SHA-256 of the canonical JSON of those four fields, sorted. Evidence that already exists on the tree is not consulted: deciding what still needs running is the requester's (R3.18's minimal check set reads `ListEvidence` first). The protocol's job is to run what it is asked.

**The open-job cap.** At most `[executor] max_open_jobs` (1,000) jobs are queued or running across the daemon. Past it, `SubmitJob` is `TOO_MANY_JOBS` (`UNAVAILABLE`, metadata `limit`). The cap refuses and never evicts, as presence's caps do (ADR 0037 decision 6). It also bounds the presence entries jobs add.

### Claiming: matching, leases and the claim token

`ClaimJob` names the executor and what it can do:

| Field | Meaning | Checked (`INVALID_EXECUTOR`, `field`) |
| --- | --- | --- |
| `executor.name` | What the executor calls itself, such as `ci-runner-7`. Declared, never verified | R3.03's agent label rule: 1 to 256 bytes, visible ASCII and spaces |
| `executor.version` | Its version | 0 to 64 bytes, visible ASCII |
| `executor.kinds` | The kinds it can produce, 1 to 64 | R3.01's kind pattern |
| `executor.labels` | Its labels, 0 to 32, `key=value`: by convention `os` (`linux`, `macos`, `windows`) and `arch` (`x86_64`, `aarch64`), Rust's `std::env::consts` names | as `requirements` |
| `protocol_version` | The highest protocol version it speaks | at least 1 |
| `repos` | Only these repositories (`repo` references); empty for all | as every `repo` |
| `wait` | How long to wait for a job | 0 to 60 seconds; 0 returns at once |
| `lease` | How long the claim lasts without an `UpdateJob`. Default 60 seconds | 15 seconds to 10 minutes |

- **Matching.** A job matches when each of its kinds is among the executor's, each of its requirements is among the executor's labels, its repository is in `repos` (when given), and its protocol version is at most the executor's. Among matching queued jobs, the highest `priority` wins, then the oldest `submitted_at`, then the id. The selection and the update to `RUNNING` are one `IMMEDIATE` transaction, so two executors never claim one job. A queue is at most 1,000 open jobs, so matching scans the queue's rows in order in Rust, with no index over labels.
- **The long poll.** With nothing matching, the call waits on a daemon-wide `Notify` that every submit and every requeue signals, re-runs the selection when woken, and returns `job` unset when `wait` runs out. `protocol_version` in the response is the daemon's highest, set whether or not a job came back, so an executor learns what it is talking to from its first call.
- **The claim token** is 32 random bytes, base64url, returned only in `ClaimJobResponse`. The daemon keeps its blake3 digest (`jobs.claim_digest`), as it keeps remote token secrets, and compares in constant time. It is the capability for that one attempt, as a lease id is for a workspace (ADR 0037 decision 5 says the same of presence ids): `UpdateJob` and `CompleteJob` require it. It never appears in `GetJob`, `ListJobs`, presence, the database in plain text, or any log. A requeue makes it worthless: the next attempt gets a new one.
- **The lease.** A claim lasts `lease` from the claim and from every `UpdateJob`. An executor sends `UpdateJob` at least every third of its lease, and at most once a second. When the lease lapses, the job goes back to `QUEUED` with `attempt` + 1, unless that was attempt `max_attempts` (`[executor] max_attempts`, 3), in which case it is `EXPIRED` with `ATTEMPTS`. `UpdateJob` with `release: true` ends the claim at once, as a lapse does, for an executor that is shutting down. A lost `ClaimJob` response costs one attempt, after one lease. The spec says so.
- **The deadline.** A running attempt's `deadline_at` is its claim time plus `wall_time` plus a fixed 60-second grace for the last `CompleteJob`. The executor enforces its budget itself and completes with `BUDGET_EXHAUSTED`. The deadline is the daemon's backstop: past it, the job is `EXPIRED` with `DEADLINE`, and further calls with its claim token are refused. Each attempt gets the whole `wall_time`. Caps across attempts, proposals and agents are R3.20's.
- **The queue timeout.** A job unclaimed by `submitted_at + queue_timeout` (the request's, else `[executor] queue_timeout`, 1 hour; 1 minute to 7 days) is `EXPIRED` with `QUEUE_TIMEOUT`, so a requester with no executor running finds out instead of waiting for ever. A requeue keeps the original queue expiry, extended to at least one lease from the requeue.
- **One timer.** The executor module keeps the next lease expiry, deadline and queue expiry of every open job in memory, and one task sleeps until the earliest, as presence's timer does. Every transition is a database transaction first and an in-memory change after.
- **Restarts.** Jobs are rows, so they survive a restart and a restore. At start, the module loads the open jobs, extends every running claim's lease to at least one lease from now (an executor that kept running across the restart reconnects and goes on), and republishes the jobs' presence entries. A restore behaves the same: running jobs whose executors never come back lapse and requeue.

### The response: signed evidence, by value; artifacts, by digest

- **Evidence travels in the protocol.** `UpdateJob` and `CompleteJob` carry `repeated SignedEvidence { bytes envelope; bytes public_key; }`, exactly `AddEvidence`'s pair, at most 50 per call (50 × 64 KiB is within the 4 MiB request bound). An executor with more sends several `UpdateJob` calls before it completes. Partial results therefore arrive as they finish, which is what R3.19's composition and R3.14's early bisect want.
- **One verification path.** The daemon runs each envelope through R3.01's `Verified::check`, then the job's binding, and only then stores the call's evidence in one transaction. That transaction goes through the same insert `AddEvidence` uses: the key row, the evidence row (or the re-add rules), the artifact digests, and one `job_evidence` row per object. `AddEvidence`'s body is split so that both callers share it, `executor::accept` and the service handler. If any object in a call is refused, nothing from that call is stored, and the reason names it (`index`, its position in the call). An executor that wants an object outside a job can still call `AddEvidence`.
- **The binding** (`JOB_EVIDENCE_MISMATCH`, `FAILED_PRECONDITION`, metadata `index`, `field` and `evidence_id`): the statement's tree must be the job's `tree_id` (`field` `tree`), and its kind must be one of the job's kinds (`field` `kind`). Its target may be any target, or none. An executor may split a requested target into finer ones, and R3.19 decides how they compose. No store read is needed, since the job's tree was checked at submission.
- **No link to the change.** As R3.01 said for executors, the evidence is added by tree, with no `evidence_links` row. The job records `change_id`, and R3.13 links what it lands.
- **Artifacts go first, by digest.** An executor uploads each artifact with R3.02's `UploadArtifact` (resumable, deduplicating, over the remote listener) before it sends the evidence that names it. The protocol carries no bytes. `ListEvidence` and `GetEvidence` report each artifact's `ArtifactState` as R3.02 does. A missing artifact is not refused, since R3.01 never requires the bytes. R3.07 can require a stored log.
- **Freshness.** Each `job_evidence` row records `created` (whether this call stored the object for the first time) and `fresh` (created, and its claimed `startedOn` is no earlier than five minutes before the claim of the attempt that sent it). A re-sent old envelope is still valid evidence about the tree, and is accepted, but reads as not fresh. That is the replay case (S-78). R3.07 or R3.13 may require fresh evidence for what a job reports; this ticket reports it.
- **What the daemon checks on receipt, and what it leaves.** It checks the envelope, the key, the signature, the statement (R3.01), the tree and kind binding, the call's bounds, and, for `DONE`, completeness. It records the key, freshness and the attempt. It does **not** check whether the key is certified, its actor, or its identity's status. Those are reported on every evidence read (`KeyIdentity`, R3.03), and whether they count is policy's (R3.07). "Evidence from an untrusted attestor is stored but carries no weight at landing."

### Completeness: what `DONE` promises

A job's **pairs** are `kinds × targets`, or `kinds × {""}` (the whole check) when no targets were requested. `CompleteJob` with `DONE` is accepted only when, for every pair, the job holds an accepted evidence object with exactly that kind and target (absent for `""`), from any attempt or call, including the completing call. Otherwise it is `JOB_INCOMPLETE` (`FAILED_PRECONDITION`, metadata `missing`, up to ten `kind:target` pairs, and `missing_count`), and the job stays running.

- So `DONE` gives a requester a firm guarantee: one summary object per requested pair, with a `pass`, `fail` or `error` result. An executor that could not check a target sends `error` evidence for it, or completes with `BUDGET_EXHAUSTED` or `FAILED`.
- Finer objects beyond the pairs are accepted and kept. A summary for a target is the executor's verdict on the whole target, so R3.13 reads pairs and R3.19 reads the finer ones.
- **Coverage** is reported on `Job.coverage`: one entry per pair, in the spec's order, with the latest accepted summary's evidence id, result, freshness and signature check. Results are read from the verified payload, as every evidence read is.

### Progress over the presence channel: a daemon-reported `JOB` kind

The design says progress "streams over the presence channel". In the code, that channel is `SubscribePresence` (ADR 0037). Executors do not report presence entries of their own for jobs. They send progress in `UpdateJob`, and the daemon publishes it.

- **A new kind, `PRESENCE_KIND_JOB`**, reported only by the daemon. `ReportPresence` refuses it with `DAEMON_PRESENCE`, as it refuses `LEASE`. `Presence` gains `JobPresence job = 14`: the job's id, state, outcome, end reason, attempt, executor name, kinds, tree, and its last `JobProgress`. An entry reads one way, so `activity` and `progress` stay unset on it.
- **One entry per open job**, keyed `DaemonKey::Job`. It appears at submission (state `queued`) and changes at the claim (the executor's name, the attempt), at each progress report, and at a requeue. At a terminal transition, the module publishes the terminal state and then ends the entry (`CLEARED`), so the ended event carries the final state. A repository's forget ends its entries as `GONE`, which the hub already does. The entry's fixed fields are the requester's agent (`requested_by_agent`, else `reef`), the job's repository, no workspace, and the job's `change_id` as its `change`, so "every live element links to its cause". Its `expires_at` is the job's own next deadline plus 30 seconds, refreshed with each transition, so the module's transitions always come first.
- **Why a new kind, not `PROGRESS` with a job id.** `PROGRESS` is a daemon or client operation's phase and count. A job also has a state, an executor and an outcome, which a pipeline view (R3.34) shows, and the end of a job is an event a subscriber must tell apart from "went silent". A kind of its own reads one way (ADR 0037 decision 3), lets a subscriber filter for it, and leaves `PROGRESS`'s meaning alone.
- **The bound.** Job entries are daemon entries and not counted against the client caps. `max_open_jobs` bounds them.
- **Rate.** The hub already broadcasts an entry's changes at most once per 50 ms. `UpdateJob`'s progress is stored with the heartbeat (one `UPDATE`), and published each time.
- **Consumers.** `reef_client::json` names the kind `job`. `reef presence watch` prints the entries like any other, and its `--kind` takes `job` (`KindArg` gains `Job`; `reef presence report` infers its kind from its arguments and can never send `JOB`). The fleet panel skips `JOB` entries (`fleet-rows.ts`), since they belong to the pipeline view (R3.34), not to an agent's row.

### Security: who may do what

| RPC | Access | Socket | Remote listener (`write` token) | Remote rule |
| --- | --- | --- | --- | --- |
| `SubmitJob` | WRITE | any client | in every registered repository | `Rule::None`, as `AddEvidence` |
| `CancelJob` | WRITE | any client | only jobs its token submitted | new `Rule::OwnJob` |
| `ClaimJob` | WRITE | any client | only a token linked to an operator identity (R3.03), which the claim records | new `Rule::LinkedToken` |
| `UpdateJob`, `CompleteJob` | WRITE | the claim token's holder | the claim token's holder, and only through the token that claimed | new `Rule::OwnClaim` |
| `GetJob`, `ListJobs` | READ | any client | `read` and `write` tokens; web sessions by classification | none |

- **Why remote claims need a linked token.** An unlinked token cannot get session keys (R3.03), so any evidence it returned would read `UNBOUND` and weigh nothing. What it could still do is sit on jobs or complete them with `error` evidence. Requiring a link narrows that to pipelines and people the user named, and records who it was on the job (`executor.identity`). A refusal is `EXECUTOR_REFUSED` (`PERMISSION_DENIED`, metadata `rule` `token_not_linked`).
- **`OwnJob` and `OwnClaim`** follow `OwnWorkspace`: the job's `requested_by_token`, or its executor's `remote_token_id`, must be the caller's token, else `JOB_NOT_OWNED` (`PERMISSION_DENIED`, metadata `job_id`). `OwnClaim` holds even for a caller that has the claim token, so a token leaked from one CI token's runner cannot be played through another token.
- **On the socket**, every client is the user (ADR 0027): a same-uid process can claim any job, complete it with evidence signed by any key it can get a certificate for, or cancel any job. The binding still holds, and so does weight by identity: a socket client cannot get a `ci` key (R3.03), so "A large project trusts its CI identity and nothing else" survives a local agent that claims jobs.
- **Executor-forged evidence** (the design's open problem) is not something the daemon can detect. An executor signs whatever it likes about the tree. The daemon guarantees that what a job reports is bound to the job's tree and kinds, signed, and attributed to a key whose identity every read reports. Weight is R3.07's trust in that identity. The spec tells executor authors what a trusted executor must do: run in an environment the submitting agent cannot touch, and use one session key per job (S-74).
- **Replay** is reported, not refused ("Freshness", S-78).
- **Tree disclosure.** A job's tree is readable by whoever claims it. A remote claimant needs a `write` token, which can already read every tree through `FileService` (S-80).

### Versioning: protocol version 1

- **An integer, separate from the API revision.** `reef_api::EXECUTOR_PROTOCOL` is `1`. The API revision moves with every schema change anywhere in v1, and most of those mean nothing to an executor. The protocol version moves only when an executor that speaks the old version would do the wrong thing with a new job.
- **What moves it, and what does not.** An added optional field that an old executor can ignore and still produce correct evidence does not (R3.22's `base_tree_id` will not, because a behavioral-diff job also names the new kind, and only an executor declaring that kind claims it). A change of meaning to an existing field, or a job that an old executor would run wrongly if it ignored a new field, does. Such a job records the version it needs (`jobs.protocol`), and `ClaimJob` gives it only to executors declaring at least that version. Old executors keep getting the jobs they can run.
- **v1 only grows**, as ADR 0029 decision 17 says for the schema: no field of the protocol is removed, renumbered or reinterpreted. R6.03 specifies protocol 1 from `docs/executor-protocol.md`, and the spec carries its version in its title.

### Storage: migration `0011_jobs.sql`, schema 11

```sql

-- evidence each job accepted. A claim token is kept only as its blake3 digest. JSON arrays are
-- sorted and deduplicated. kind and target in job_evidence are index columns read from the
-- verified payload at acceptance, for the completeness check. Released migrations are never edited.

             tree_id TEXT NOT NULL, commit_id TEXT, change_id TEXT,
             kinds TEXT NOT NULL, targets TEXT NOT NULL, requirements TEXT NOT NULL,   -- JSON arrays
             spec_digest TEXT NOT NULL,                             -- sha256 of the canonical spec
             wall_time_ms INTEGER NOT NULL, cpu_time_ms INTEGER, priority INTEGER NOT NULL,
             state TEXT NOT NULL,                                   -- queued running completed cancelled expired
             outcome TEXT, end_reason TEXT, message TEXT,
             attempt INTEGER NOT NULL DEFAULT 0, max_attempts INTEGER NOT NULL,
             submitted_at INTEGER NOT NULL, queue_expires_at INTEGER NOT NULL,
             requested_by_agent TEXT, requested_by_token TEXT,
             claim_digest BLOB, claimed_at INTEGER, lease_ms INTEGER, lease_expires_at INTEGER,
             deadline_at INTEGER,
             executor_name TEXT, executor_version TEXT, executor_labels TEXT, executor_kinds TEXT,
             executor_protocol INTEGER, executor_agent TEXT, executor_token TEXT,
             executor_identity_id TEXT,
             progress TEXT,                                         -- JSON: phase, done, total, unit
             usage_wall_ms INTEGER, usage_cpu_ms INTEGER, elapsed_ms INTEGER NOT NULL DEFAULT 0,
             finished_at INTEGER, cancelled_by_agent TEXT, cancel_reason TEXT,
             PRIMARY KEY (repo_id, id)) WITHOUT ROWID;
CREATE UNIQUE INDEX jobs_by_id ON jobs(id);
CREATE INDEX jobs_open ON jobs(state, priority DESC, submitted_at, id) WHERE state IN ('queued','running');
CREATE INDEX jobs_open_by_spec ON jobs(repo_id, spec_digest) WHERE state IN ('queued','running');
CREATE INDEX jobs_by_submitted ON jobs(repo_id, submitted_at DESC, id);
CREATE INDEX jobs_by_finished ON jobs(finished_at) WHERE finished_at IS NOT NULL;
CREATE TABLE job_evidence(repo_id TEXT NOT NULL, job_id TEXT NOT NULL, evidence_id TEXT NOT NULL,
             attempt INTEGER NOT NULL, kind TEXT NOT NULL, target TEXT,
             created INTEGER NOT NULL, fresh INTEGER NOT NULL, accepted_at INTEGER NOT NULL,
             PRIMARY KEY (repo_id, job_id, evidence_id)) WITHOUT ROWID;
CREATE INDEX job_evidence_by_evidence ON job_evidence(repo_id, evidence_id);
CREATE INDEX job_evidence_by_pair ON job_evidence(repo_id, job_id, kind, target, accepted_at);
```

- **No foreign key from `job_evidence` to `evidence`.** R3.02's retention deletes evidence on its own schedule. A `job_evidence` row whose evidence is gone reads as a coverage entry with the id and no result (`signature` unspecified), and `ListEvidence(job_id)` leaves it out. Jobs never pin evidence: R3.13 pins what a landing uses.
- **`elapsed_ms`** is observed by the daemon: the sum, over attempts, of each attempt's time from claim to its end. `usage_*` is what the executor reports. R3.20 can read either.
- **Times** are unix milliseconds. **Backups** copy both tables with the database. ADR 0020's layout is unchanged.

### Retention: GC's ninth step, and forget

- **GC's ninth step, jobs**, after provenance and before the reindex: terminal jobs that finished before `min(now − [executor] job_retention, keep_newer)` are deleted with their `job_evidence` rows, 1,000 per transaction. Their evidence stays, under R3.02's rules. `dry_run` counts and deletes nothing. `GcReport` gains `uint32 jobs_removed = 25` and `string jobs_error = 26`. A failure is logged and the run goes on, and a requested run reports it (`reef ws gc` exits 8, as for `evidence_error`), because jobs are authoritative records. `reef ws gc`'s text line gains `jobs <n> removed`. The module docs' step count is corrected to nine.
- **`reef repo forget`** deletes the repository's jobs and `job_evidence` rows in `Db::delete_repository`'s transaction, after the module has dropped them from memory. Their presence entries end `GONE`. An executor holding a claim gets `JOB_NOT_FOUND` on its next call.

Each element gets the full leading comment ADR 0029's checklist requires. The sketch abbreviates. The rules:

- **`SubmitJob`** resolves `revision` through the reading layer (`Target`, `snapshot_first`), filling `tree_id`, `commit_id` and `change_id`. With `tree_id`, it checks the tree's presence and leaves the other two empty. Then it validates the spec, applies the dedupe and the cap, inserts the row, publishes the entry, and signals waiting claims. It returns `created: false` for a dedupe hit.
- **`ClaimJob`** with no job returns an empty `job`, an empty `claim_token`, and `protocol_version`. It is not idempotent: a retried claim may claim a second job, and the first lapses.
- **`UpdateJob`** checks the claim (below), then the evidence, extends the lease, stores the progress, and publishes. With `release`, it requeues or expires the job after storing the call's evidence.
- **`CompleteJob`** checks the claim, then the evidence, then completeness for `DONE`, and then completes the job in the transaction that stores its evidence. A `CompleteJob` repeated with the same claim token after it succeeded, whose envelopes are all already accepted by the job, returns the completed job: a lost response is safe to retry. With other evidence it is `JOB_NOT_CLAIMED` (`state` `completed`). `outcome` unspecified is `INVALID_ARGUMENT`.
- **The claim check** (`UpdateJob`, `CompleteJob`): `JOB_NOT_FOUND` for an unknown full id, then the token's digest and state. Any failure is `JOB_NOT_CLAIMED` (`FAILED_PRECONDITION`, metadata `job_id` and `state`: `wrong_token`, `lapsed` (a later attempt or a requeue holds it), `cancelled`, `completed` or `expired`). The spec tells executors: on `JOB_NOT_CLAIMED`, stop work on that job, and do not retry.
- **`CancelJob`** ends a queued or running job as `CANCELLED` at once, recording the caller's agent and the reason (at most 256 bytes). Cancelling a cancelled job returns it. Cancelling a completed or expired job is `JOB_FINISHED` (`FAILED_PRECONDITION`, metadata `state`). A running executor learns of it on its next `UpdateJob` (`JOB_NOT_CLAIMED`, `cancelled`), within a third of its lease. Evidence it already returned stays stored and listed by the job.
- **`ListJobs`** returns jobs newest submitted first, or, with `queue_order`, only open jobs in claim order. `page_size` works as ADR 0029 decision 10 says (0 means 100, at most 1,000). `coverage` is left empty: it is the heavy part, opt-in through `GetJob` (decision 11).
- **No exception to the remote rules table's completeness**: `TABLE` gains the five WRITE methods with the rules above. `remote/rules.rs` gains `check_own_job`, `check_own_claim` and `check_linked_token`, beside `check_owned`.
- **ADR 0029 decision 12** gains five exceptions: `SubmitJob`, `CancelJob`, `ClaimJob`, `UpdateJob` and `CompleteJob` record no operation, since a job is not jj state.
- `API_REVISION` becomes 19 with its digest. `SERVED` gains `reef.api.v1.ExecutorService` (20 entries). `reef_api::EXECUTOR_PROTOCOL` is `1`.

- **`submit`** defaults to `-r @` inside a workspace, which snapshots first; outside one, `-r` or `--tree` is required (a usage error otherwise). ### The written protocol: `docs/executor-protocol.md`

The document an executor author builds against, titled "Executor protocol 1". It restates what this brief decides, in the order an author needs it, and never assumes the reader has Reef's source:

1. **Roles.** Requester, daemon, executor; what each owns. Reef schedules, the executor executes; the daemon never calls the executor and never sends a command.
2. **Connecting.** The socket (`REEF_SOCKET`, the default paths), or the remote listener with TLS and a `write` token linked to an identity (`reef remote token create --scope write --identity <ci>`), the `reef-agent` metadata, and the error model (`ErrorDetail`, reasons, `hint`).
3. **The loop**, as pseudo-code: claim with a wait; on a job, issue a session key (`IssueSessionKey`, actor `executor`, one per job); get the tree (below); run each pair; upload artifacts; send evidence and progress in `UpdateJob` at least every third of the lease; complete. On `JOB_NOT_CLAIMED`, stop. On a lost connection, retry `UpdateJob` until the lease would have lapsed.
4. **Getting the tree.** The executor's business, by any means that yields exactly `tree_id`: a git checkout of `commit_id` (and a check that `git rev-parse <commit>^{tree}` equals `tree_id`), the repository's own store for a local executor, or `FileService.ListFiles` and `ReadFile` at `commit_id` as a slow fallback that works over the remote listener. Evidence must be about `tree_id`, and nothing else.
5. **Messages**, field by field, with every bound, and the state machine, with every transition and who causes it.
6. **Evidence**: R3.01's format (`docs/evidence.md`), the binding, the 50-per-call bound, all-or-nothing calls, artifacts first, completeness and the summary-per-pair rule, `error` versus `FAILED`, freshness.
7. **Budget, cancellation, release, deadlines.** What the executor enforces, and what the daemon enforces as a backstop.
8. **What a trusted executor must do**, which no protocol can check: run where the submitting agent cannot reach, never run a command or a shell built from request strings, one session key per job, keys never written to disk, and report `error` rather than guess. Policy decides whom to trust; this is how to deserve it.
9. **Versioning**: protocol 1, what moves it, how to read the daemon's version (`ClaimJobResponse.protocol_version`, `reef schema`).
10. **A conformance checklist**, one line per rule, each naming the test in `reef-daemon/tests/executor.rs` that exercises it. R6.03 turns it into a suite.

### Documentation

- **`docs/adr/0059-executor-protocol.md`** (accepted), indexed in `docs/adr/README.md`.
  - **Decisions**:
    1. executors pull: the daemon keeps a durable queue and leases jobs; it never connects to an executor;
    2. a request names a tree, kinds, targets, a budget, requirements and a priority, and never a command;
    3. a claim is a long poll with a lease and a per-attempt claim token kept as a digest; lapses requeue up to `max_attempts`; the daemon enforces a deadline and a queue timeout;
    4. evidence travels by value in `UpdateJob` and `CompleteJob`, through R3.01's verification and `AddEvidence`'s insert, bound to the job's tree and kinds, all or nothing per call; artifacts by digest through R3.02 first;
    5. `DONE` promises a summary object per requested pair; freshness is reported, not enforced;
    6. progress is a daemon-reported presence kind, `JOB`;
    7. remote claims need a token linked to an identity; updates and completions only through the claiming token; cancellation only by the submitting one;
    8. protocol version 1, separate from the API revision, moved only by changes an old executor would get wrong;
    9. jobs are kept `job_retention` after they finish, in GC's ninth step.
  - **Alternatives**:
    - the daemon calls an executor endpoint (push);
    - a stream of job offers instead of a long poll;
    - the executor adds evidence with `AddEvidence` and `CompleteJob` names the ids (two paths to keep consistent, and a gap in which evidence is stored but not yet bound);
    - evidence by digest only, as artifacts are;
    - commands or images in the request;
    - executors reporting `PROGRESS` entries themselves (an executor could report anything about any job, and the entry's end would not say how the job ended);
    - `PROGRESS` with a job id instead of a new kind;
    - the API revision as the protocol version;
    - the daemon judging completeness by kind only, or not at all;
    - refusing evidence that is not fresh;
    - any `write` token claiming jobs.
  - ADR 0029 gains "Amended by: 0059" (decision 12's five exceptions). ADR 0037 gains "Amended by: 0059" (a daemon-only kind, `JOB`, bounded by `max_open_jobs`).

## Implementation notes

- **Order**:
  1. The protos, then `docs/executor-protocol.md` in draft: the spec is the deliverable executors depend on, and writing it first finds gaps in the messages.
  2. The migration and `db/jobs.rs` (test 1).
  3. Submit, claim and the lease timer (tests 2 to 5).
  4. The shared evidence path, acceptance and completeness (6, 7).
  5. Cancel, presence and the remote rules (8, 9, 10, 16).
  6. GC, forget and config (11, 13).
  7. The fake executor (12), then the client and the CLI (14), then schema, MCP and SDKs (15, 17), then the documents.
- **Splitting `AddEvidence`.** Move everything after `Verified::check` and the tree check into a function that takes verified objects, the repository, the adder's agent and token, and an optional closure that writes extra rows in the same transaction. `AddEvidence` passes none, and `executor::accept` passes the `job_evidence` rows and the job's update. R3.01's and R3.02's evidence tests must pass unchanged.
- **Locks.** One `IMMEDIATE` transaction per transition, with the job's row re-read inside it, is the serialization: no per-job mutex. A claim's selection runs inside its transaction. Verification of a call's envelopes runs before the transaction, on the blocking pool; the transaction re-checks the claim, so a lapse that raced the verification refuses the call.
- **The timer and the database agree.** The timer acts only through the same transactions the RPCs use, and a transition that finds the row already moved (a heartbeat that arrived first) does nothing. The in-memory deadlines are rebuilt from the rows at start.
- **Coverage on read.** `GetJob` reads the latest `job_evidence` row per pair through `job_evidence_by_pair`, then verifies those objects through `service/evidence.rs`' `messages` (at most 1,000), on the blocking pool.
- **Linux**: no `cfg(target_os)`. Build and lint in the privileged `ubuntu:24.04` container anyway, since `server.rs`, GC and the presence hub change and the Linux-only daemon tests construct `TestDaemon`.

- **Executor registration, health and fleet views** beyond what a job records: no ticket asks for them; presence shows who holds a job.

## Risks

- **The protocol is the part that cannot be cheaply changed.** Every executor written against it depends on its states, rules and bounds. Mitigations: the spec is written first and reviewed with the protos; the fake executor exercises every rule; a protocol version that only moves for changes old executors would get wrong; R3.06 is built against the spec, not against the daemon's internals, and any gap it finds is fixed in the spec before R3.06 merges.
- **The completeness rule may not fit every executor.** An executor whose runner cannot produce a summary per requested target must synthesize one. Mitigation: the rule is simple to meet (a summary is pass when all its finer objects pass), stated with an example in the spec, and R3.06 meets it first.
- **Leases and timers are where races live.** A heartbeat, a lapse and a completion can meet. Mitigations: every transition is one transaction that re-reads the row; the timer acts only through those transactions; tests use a controlled clock; the "Timing tests flake under load" history says to never sleep for a lease in a test.
- **Trust is easy to misread.** A `COMPLETED`/`DONE` job with passing coverage says that some key signed passing claims about the tree, not that the checks passed. Mitigations: the signer and identity on every coverage entry and evidence read, the CLI's wording, the spec's section on trust, and R3.07.
- **Queue flooding costs real compute.** Mitigations: the cap, dedupe, per-job budgets; R3.20 adds caps per requester.

## Choices this brief made, and why

- **Pull, not push**, because Reef starts nothing, executors behind NAT can dial out, and the socket and remote listener already authenticate, bound and audit clients.
- **A real queue in this ticket**, because nobody requests jobs until R3.13 and R3.14, and an executor protocol with no requester and no daemon side cannot be tested or built against.
- **Evidence by value through the existing verification**, because one path means one set of checks, and binding at receipt leaves no window where a job's evidence is stored but unbound.
- **No command in a request**, because a command channel would let every submitter run code on every executor.
- **A summary per pair for `DONE`**, because it gives requesters a firm, checkable promise and still lets executors report finer results.
- **Freshness reported, not refused**, because old evidence on the same tree is still true, and whether a job's result must be new is a policy question.
- **A daemon-reported `JOB` kind**, because executors cannot then misreport jobs, and the end of a job carries its outcome.
- **Remote claims through linked tokens only**, because an unlinked claimant can only waste jobs, and a linked one is named on each job.
- **A protocol version apart from the API revision**, because executors care about far fewer changes than the schema has.
- **The conformance suite in R6.03**, because the suite is part of publishing the specification, and this ticket's test already exercises every rule.

## What later tickets inherit

- **R3.06** builds `reef executor run` against `docs/executor-protocol.md`: claim with a wait and its kinds and labels; `Client::issue_session_key(…, Actor::Executor, …)` once per job; materialize `tree_id` (checking it); map kinds and targets to what runs; upload with `upload_artifact_file`; sign with `Claim::sign`; send evidence and progress in `UpdateJob`; complete `DONE` with a summary per pair, or `BUDGET_EXHAUSTED` or `FAILED`. Locally over the socket, in CI over the remote listener with a token linked to a `ci` identity. Any gap it finds is fixed in the spec, with the protocol version unchanged unless an executor would have done the wrong thing.
- **R3.07** reads, for a job's evidence, the signer's `KeyIdentity` (identity, actor `executor`, session) and `fresh`. Its "excludes the submitting agent signing its own test run" compares the evidence key's session with the change's provenance sessions (R3.04).
- **R3.13** calls `executor::submit` in process with the kinds policy requires that the proposal's tree lacks, waits on the job (an in-process watch, not the API), reads `coverage`, and pins the evidence it lands on. It links landed evidence to the change.

## Departures from dev-phases.md

- **Executors pull, and the daemon never connects to one.** The row does not say who connects. The design's architecture diagram draws an arrow from the daemon to the executor ("materialize, run"), which shows which way the work flows, not who dials; it is left as is. R3.05's row now says executors claim jobs over the socket or the remote listener.
- **The ticket ships a working queue with both sides**, not only messages: a durable job table, `ExecutorService` with requester and executor RPCs, leases, deadlines, presence, GC retention for jobs, and `reef job` for requesting. Nobody requests jobs before R3.13 and R3.14, and R3.06 needs something to run against. The row is reworded to list them, and it stays M.
- **Artifacts travel by digest, uploaded through R3.02 before the evidence that names them.** The row's "a set of signed evidence objects plus artifacts" becomes "signed evidence objects, with artifacts uploaded beforehand by digest".
- **"Progress streams over the presence channel" means a daemon-reported presence kind, `JOB`**, built from executors' `UpdateJob` calls, not entries executors report themselves.
- **R3.06's row now says the request carries no command**: what runs for a kind and target is declared in the executor's configuration or in the repository at that tree, R3.06's choice; and that R3.06 owns getting the tree and the executor's command line.
- **R6.03's row gains the executor conformance suite**, built from this brief's checklist. The design asks for "a conformance suite so alternative stores and clients can exist", and no row owned the executor half.

## Decisions for the user

1. **Executors pull.** The daemon keeps the queue and leases jobs, and executors dial the socket or the remote listener and claim with a long poll. *Recommended*: pull. The alternatives are the daemon calling configured executor endpoints, or both.
2. **A working queue in R3.05**, with `SubmitJob`, `CancelJob`, `reef job submit|show|list|cancel`, and GC retention for jobs, so the protocol is exercised before R3.13 and R3.14. *Recommended*: yes. The alternative is messages and the spec only, with the daemon's side in R3.06 (which would then be larger than L) or R3.13.
3. **Evidence by value in `UpdateJob` and `CompleteJob`**, through `AddEvidence`'s verification and insert, all or nothing per call, 50 per call. *Recommended*: by value. The alternative is that the executor calls `AddEvidence` and `CompleteJob` names the ids.
4. **Requests never carry a command**: kinds and targets only, and the executor (R3.06) decides what runs. *Recommended*: yes.
5. **`DONE` requires one summary object per requested (kind, target) pair**, with finer objects allowed. *Recommended*: yes. The alternatives are one object per kind, or no completeness check.
6. **Freshness is reported, not enforced.** A re-sent old envelope on the same tree is accepted and marked not fresh. *Recommended*: report. The alternative is to refuse evidence older than the claim.
7. **Remote claims need a `write` token linked to an operator identity**; updates and completions go only through the claiming token, and cancellation only through the submitting one. *Recommended*: yes. The alternative is any `write` token.
8. **Progress as a new daemon-only presence kind, `JOB`.** *Recommended*: a new kind. The alternatives are `PROGRESS` with a job id, or executors reporting entries themselves.
9. **Defaults.** Lease 60 seconds (15 seconds to 10 minutes), 3 attempts, wall time 30 minutes by default and 6 hours at most, queue timeout 1 hour, 1,000 open jobs, finished jobs kept 30 days. *Recommended*: as stated.
10. **Protocol version 1, an integer apart from the API revision**, moved only by changes an old executor would get wrong. *Recommended*: yes.
11. **`reef job` for requesters only, not in the root help**; no executor subcommands until R3.06; no MCP tools. *Recommended*: yes.
12. **The executor conformance suite goes to R6.03**, and a new ADR 0059. *Recommended*: yes.
