# R3.42 Sigstore keyless identity

Phase 3 · Size M, at its top end, with the scope lines below · Depends on: R3.03 (operator identities, `session_keys`, `IssuerKind`, `check_certificate`, `status_at`, `KeyIdentity` on every evidence read), and builds on R3.06 (the reference executor in CI, which strips the CI's OIDC request variables from every check), R3.07 (attestor sets and the policy input's `key`), R3.04 (sessions in provenance, R3.07's `self`) and R2.08 (remote tokens, `remote/rules.rs`) · Unblocks: none listed; R4.09 and R4.10 inherit the verification path

## Context

R3.03 bound keys to operator identities through one issuer, the daemon's own authority key, and left Sigstore keyless to this row with four seams (R3.03, "Sigstore keyless: the seam, and R3.42"):

1. `IssuerKind` in the format and the API, to which this ticket adds `sigstore`, with a `KeyIdentity` that reports the OIDC issuer and subject.
2. A sibling of `check_certificate`, `check_sigstore_bundle`, yielding a binding that `status_at` judges unchanged.
3. OIDC matches on identities: "a `ci` identity names the issuer and subject it accepts (for example a workflow's `job_workflow_ref`), in a new table".
4. The crates: `sigstore-verify` with a ring `CryptoProvider`, and the question of whether Reef signs keylessly at all or only verifies.

The main use is CI evidence. Today a CI job's evidence is bound to a `ci` identity because the executor dials the remote listener with a token linked to that identity (`docs/executor.md`, "Running it in CI"; R3.03 S-60, S-61). That token is a long-lived secret stored in the CI system, and whoever holds it can mint keys for `ci-main`, which a policy that "trusts its CI identity and nothing else" (design, Open ecosystem) accepts. Keyless moves the CI identity from "who holds Reef's token" to "what the CI provider's OIDC issuer says about this job, certified by Fulcio and logged in public": a stolen Reef token can then still add evidence, but not evidence that a keyless-only policy counts. It also makes the binding verifiable by any Sigstore client, and the identity portable to another daemon or R4's store, since no Reef authority vouches for it.

So this ticket builds:

1. **Keyless session keys**: a session key generated in the signing process, certified by Fulcio against an OIDC token, which signs a Reef *binding statement* that Rekor logs. The resulting Sigstore bundle is registered with the daemon. Evidence signed by the key is ordinary R3.01 evidence.
2. **Offline verification** in the daemon: the bundle against Sigstore's trusted root, embedded in the binary or supplied as a file, through `sigstore-verify` with a ring crypto provider. No network call, ever, at verification.
3. **OIDC matches**: a `ci` or `person` identity names the exact OIDC issuer and subject it accepts. A registered key is bound to the identity whose match accepts its certificate.
4. **Reads**: `KeyIdentity` reports `issuer_kind: sigstore` with the OIDC issuer, subject and transparency log entry, through R3.03's path, and the policy input carries them.
5. **The signing client**: ambient CI tokens (GitHub Actions, and any CI that puts a token in `SIGSTORE_ID_TOKEN`) and a token file, in `reef-client`, used by `reef identity session issue --keyless`, `reef evidence add --keyless` and the executor (`[executor] keyless = true`).

### What is certified and logged: the session key, once

A **keyless session key** is a session key whose certificate comes from Fulcio instead of a Reef authority:

1. The signing process generates an ed25519 key (question 3 asks what happens if Fulcio refuses it).
2. It gets an OIDC token for audience `sigstore` (below) and asks Fulcio for a certificate for the key, signing the token's subject as Fulcio's proof of possession.
3. It signs a **binding statement** with the key, as a DSSE envelope:

   ```json
   {"_type": "https://in-toto.io/Statement/v1",
    "subject": [{"name": "session-key", "digest": {"sha256": "9c41…<the key's id>"}}],
    "predicateType": "urn:reef-vcs:sigstore-session-key:v1",
    "predicate": {"actor": "executor", "agent": "reef-executor@ci-7",
                  "session": "ses_41c9e07ab2d35f18", "presence": "none", "custody": "client"}}
   ```

4. It logs the envelope in Rekor (v1, `dsse` 0.0.1) and assembles a Sigstore bundle v0.3: the Fulcio leaf certificate, the transparency log entry with its inclusion proof, checkpoint and SET, and the envelope.
5. It registers the bundle with the daemon (`RegisterSigstoreKey`). The daemon verifies it offline and records the key.
6. It signs evidence with the key, as R3.01 evidence, unchanged (`AddEvidence` with the envelope and the SPKI).

| Field | Required | Meaning | Checked |
| --- | --- | --- | --- |
| `subject` | yes | Exactly one, `name` `"session-key"`, `digest.sha256` the key id | equals `KeyId::of` the Fulcio leaf's SPKI |
| `actor` | yes | `human`, `agent` or `executor`, as declared | one of three; `human` only for a `person` identity (at registration, once the identity is known) |
| `agent` | no | A declared label | R3.03's rule |
| `session` | yes | `ses_<16 hex>`, chosen by the client for its first key and repeated by its renewals | pattern; see "Sessions" |
| `presence` | yes | `none`: an OIDC login is not a user verification of each use | a value this reader knows |
| `custody` | yes | `client` | `client` only |

- **Why the key and not each evidence object.** One Fulcio certificate and one Rekor entry per session key, not per object (a job signs one object per kind and target); the evidence format, `AddEvidence` and every R3.01 to R3.07 read stay as they are; and the key-to-certificate seam R3.03 left is used as designed. The bundle is a standard Sigstore bundle of a DSSE in-toto statement, so any Sigstore verifier checks the binding with the exact identity and issuer. The alternative, a Sigstore bundle per evidence object (as `cosign attest-blob` makes), is question 1's option B and a follow-up.
- **The window is Fulcio's.** `not_before` and `not_after` are the leaf certificate's (10 minutes on the public-good instance), and the bundle's integrated time must fall inside them (Sigstore's own rule, which `sigstore-verify` enforces). Evidence the daemon first witnesses outside the window reads `EXPIRED`, as R3.03 defines. So a keyless key is obtained when it is needed and lives minutes: the executor gets one when it first signs a job's result, not at the job's start, and renews when less than 3 minutes remain.
- **Witness time stays `added_at`.** R3.03 said Rekor's integrated time "becomes `witnessed_at` when it is earlier than `added_at`". Here Rekor logs the binding, not the evidence, so its time witnesses only that the certificate was used in its window; evidence is still judged at the daemon's `added_at` ("Departures").
- **A separate predicate type, not R3.03's.** `urn:reef-vcs:session-key:v1` is an authority's statement about a key; the binding statement is the key's own statement about itself, with its identity in the certificate and its window in X.509. ADR 0055's stability rules apply to the new type.

### Sessions

A keyless key's session is named in its signed statement, so session grouping cannot be forged by whoever registers the bundle (it is public in Rekor, so anyone can):

- A session id the daemon has not seen creates a session row with the identity, actor and agent of the registration, `channel` `sigstore`.
- A known session must have the same identity and actor (`SESSION_KEY_REFUSED`, `session_mismatch`) and be unrevoked (`session_revoked`). A keyless session never mixes with a daemon-issued one: a known session whose channel is not `sigstore` is `session_channel_mismatch`.
- No channel check otherwise: the proof is Fulcio's, not the connection's.

### Registration: who may register what

`RegisterSigstoreKey` (ACCESS_WRITE) takes the bundle (at most 64 KiB). In order, the daemon:

1. checks the size, then verifies the bundle with `check_sigstore_bundle` against its trusted root, off the async runtime;
2. finds the live OIDC match whose issuer and subject equal the certificate's (none: `SIGSTORE_IDENTITY_UNMATCHED`, whose hint gives the exact `reef identity oidc add <identity> --issuer … --subject …` line, so setup starts from the first refusal);
3. applies the rules below and the session rules above;
4. records the key: the same bundle again returns the existing record with `created: false`; the same key with another bundle is `SESSION_KEY_EXISTS` (`certified`); a key that already signed evidence as a bare key is `SESSION_KEY_EXISTS` (`used`), as R3.03 does;
5. returns the record.

| | `person` identity | `ci` identity | Actor `human` |
| --- | --- | --- | --- |
| The socket | yes | **yes**, unlike R3.03's `ci_over_socket` | person only, `presence: none` |
| A `write` token, linked or not | yes | yes | person only |
| A `read` token | refused by scope | | |
| The web listener | not served | | |

- **Why the channel does not matter.** The identity comes from the OIDC issuer's token, which Fulcio checked and Rekor logged, not from who calls. A local agent can register a `ci` keyless key only with a key Fulcio certified for CI's subject, which it can get only with CI's OIDC token. A registrant who copies someone else's bundle from Rekor gains nothing: every field it binds was signed by the key, and it cannot sign with the key. So `remote/rules.rs` gives `RegisterSigstoreKey` `Rule::None`.
- **`human` for `ci`** is refused (`human_for_ci`), and the 10,000 live keys per identity limit applies, as in R3.03.
- Registration records no operation (ADR 0029 decision 12's exceptions gain it), and logs to `identity::audit` with the issuer, subject, log index and key id.

### OIDC matches

A match is a record that an identity accepts certificates for one exact (issuer, subject):

- **Exact strings.** The issuer is compared with the certificate's OIDC issuer extension (`.1.8`, else `.1.1`), the subject with its SAN (an email or a URI), byte for byte. No patterns (question 2): `sigstore-verify`'s own matcher is exact, and a pattern that also matches a branch or a pull request's workflow lets that branch's code mint CI keys (S-136). A second workflow is a second match.
- **The issuer** is an `https://` URL of at most 256 bytes, the subject at most 1,024 bytes of visible ASCII. A `ci` identity's subjects are usually workflow URIs (`https://github.com/reef-vcs/reef/.github/workflows/checks.yml@refs/heads/main`); a `person`'s are emails at their login issuer (`https://github.com/login/oauth`, `https://accounts.google.com`). Reef checks the form, not the meaning; `docs/identity.md` gives the recipes.
- **Unique among live matches**: one (issuer, subject) names at most one identity, so a certificate binds to one identity or none.
- **Added and revoked by the daemon's user** through ADMIN RPCs (`AddOidcMatch`, `RevokeOidcMatch`), never remotely, never as MCP tools. `CreateIdentity` takes initial matches. A revoked identity takes no new match.
- **Revoking a match is a revocation.** It records `revoked_at` and `invalid_from` with R3.03's rules (`--since`, `--since-created`, earlier only, never in the future), and applies to every key bound through it: `Revocations` gains a fourth member, the binding's, beside the key's, session's and identity's.
- **A key's match is fixed at registration** and recorded in the row. Adding a match later never rebinds an existing key; a read checks that the recorded match's issuer and subject still equal the bundle's (else `INVALID`).

### Verification: `check_sigstore_bundle`, offline

`reef-evidence` gains a `sigstore` module behind a `sigstore` feature, which the daemon enables and the client and executor do not, so the `reef` binary does not link the X.509 stack (question 4 weighs a separate crate). Like `session`, it is pure: no clock, no I/O.

```rust
/// The trusted root a verifier uses: the embedded public-good root, or one
/// parsed from a `trusted_root.json`.
pub struct TrustedRoot { /* sigstore_trust_root::TrustedRoot, its SHA-256, its source */ }

/// Checks a bundle in this order: size; the bundle's JSON and media type;
/// the certificate chain to a Fulcio CA of `root` valid at the integrated
/// time; the SCT; the transparency log entry (inclusion proof, checkpoint,
/// SET) against a log of `root`; the integrated time within the leaf's
/// validity; the envelope's one signature by the leaf key over the PAE;
/// and only then the binding statement.
pub fn check_sigstore_bundle(bundle: &[u8], root: &TrustedRoot) -> Result<SigstoreCertified, Invalid>;

pub struct SigstoreCertified {
    pub public_key: PublicKey,          // the leaf's, ed25519
    pub actor: Actor, pub agent: Option<String>, pub session: String,
    pub presence: Presence, pub custody: Custody,
    pub oidc_issuer: String, pub oidc_subject: String,
    pub ci_claims: BTreeMap<String, String>,   // `.1.9`–`.1.24`, for display
    pub not_before_ms: i64, pub not_after_ms: i64,
    pub integrated_time_ms: i64, pub log_id: String, pub log_index: u64,
    pub ca_key_id: KeyId,               // the issuing Fulcio CA's SPKI SHA-256
    pub id: String,                     // SHA-256 of the bundle bytes
}

impl SigstoreCertified {
    /// The R3.03 binding for the identity the daemon matched, so `status_at`
    /// judges it unchanged.
    pub fn bind(&self, identity: IdentityRef) -> Certified;
}
```

- **The ring provider.** `reef-evidence` implements `sigstore_crypto::CryptoProvider` over ring (SHA-256/384/512, ECDSA P-256 and P-384 ASN.1, ed25519, RSA PKCS#1 and PSS), installed once with `install_default_provider` by the first `TrustedRoot` constructed; `verify_prehashed` returns unsupported. `sigstore-verify`, `-trust-root` and `-crypto` are pinned `=0.15.1` with `default-features = false`. A test runs a bundle per algorithm through it, and `crate_graph`'s `tls_is_ring_only` and `NOT_IN_EVIDENCE` stay as they are.
- **The identity policy passed to `sigstore-verify`** is `any_identity()`: the bundle is verified for any identity, and the match is the daemon's step 2, so one verification serves every identity.
- **The leaf key must be ed25519** (`Invalid::Statement` otherwise), because evidence verification is ed25519 (ADR 0055). Question 3.
- **`Certified` is the seam.** `bind` gives `status_at` an R3.03 `Certified` whose `Binding` has the matched identity, `issuer.kind` `sigstore`, `issuer.key_id` the CA's key id, and Fulcio's window, and whose `Authority` is the CA's row with its revocation (below). R3.03 said the sibling "yields the same `Certified` binding"; it does once the daemon supplies the identity, which the certificate does not name ("Departures").

### The trusted root

- **Embedded**: the public-good `trusted_root.json`, vendored at `crates/reef-evidence/sigstore/trusted_root.json` from Sigstore's TUF repository (not from the crate, so Reef's release updates it without waiting for a sigstore-rust release), with its SHA-256 and source date in a comment file beside it. `scripts/sigstore-root.sh` fetches the current one through TUF and a CI job warns when the vendored one is older than the published one.
- **Overridden** by `[sigstore] trusted_root = "<path>"` in the daemon's `config.toml`, for a private Sigstore deployment or a root newer than the build. Read at start; a file that does not parse is logged and registration is refused (`SIGSTORE_UNAVAILABLE`) until fixed; the daemon still starts.
- **`[sigstore] enabled = true`** by default; `false` refuses registration and reads every keyless key `INVALID`, for an operator who wants none.
- **No TUF in the daemon.** The daemon never fetches anything. A TUF refresh command is a follow-up issue (S-137).
- **Every read re-verifies** the stored bundle against the current root, as R3.03 re-verifies certificates. A root that no longer contains a key's CA or log makes that key read `INVALID`: distrusting a CA by root override takes effect at once. Verification is cached per bundle id and root digest within one read.
- **Fulcio CAs as authorities.** The first registration from a Fulcio CA records it in `identity_authorities` (`kind` `sigstore`, `algorithm` the CA key's, `public_key` its SPKI, `host` its subject's common name, `retired_at` = `created_at`, so it never issues). `ListAuthorities` shows it, R3.07's `authorities` can pin it, and `reef identity authority revoke <ca key id>` revokes it locally with R3.03's rules.

### Storage: migration `0013_sigstore.sql`, schema 13

```sql
-- R3.42: OIDC matches on operator identities, Sigstore keyless session keys, and Fulcio CAs as
-- authorities. A keyless key's certificate column holds its Sigstore bundle (v0.3 JSON, as
-- registered). Released migrations are never edited.
CREATE TABLE identity_oidc(id TEXT PRIMARY KEY,                -- oidc_<16 hex>, never reused
             identity_id TEXT NOT NULL REFERENCES identities(id),
             issuer TEXT NOT NULL, subject TEXT NOT NULL,
             created_at INTEGER NOT NULL,
             revoked_at INTEGER, invalid_from INTEGER, revoke_reason TEXT);
CREATE UNIQUE INDEX identity_oidc_live ON identity_oidc(issuer, subject) WHERE revoked_at IS NULL;
CREATE INDEX identity_oidc_by_identity ON identity_oidc(identity_id);
ALTER TABLE identity_authorities ADD COLUMN kind TEXT NOT NULL DEFAULT 'reef-daemon';
ALTER TABLE session_keys ADD COLUMN issuer_kind TEXT NOT NULL DEFAULT 'reef-daemon';
ALTER TABLE session_keys ADD COLUMN oidc_id TEXT REFERENCES identity_oidc(id);
```

- `session_keys` rows for keyless keys: `authority_id` the CA's row, `certificate` the bundle, `not_before`/`not_after` Fulcio's, `presence` `none`, `custody` `client`, `issued_at` the registration time, `issued_by_agent` and `remote_token_id` the registrant's.
- The daemon's own issuance and "current authority" queries gain `kind = 'reef-daemon'`, so a CA row is never current and `RotateAuthority` never touches one.
- **GC, backup, forget**: R3.03's rules unchanged: keyless keys are swept like any key no evidence names; matches are never deleted; backups copy the new table; forget touches none of it.
- The number is the next free one when the PR opens (R3.13 and R3.25 run in parallel and may take 13).

### The API: API revision 23

`identity.proto`:

}

enum IssuerKind { …; ISSUER_KIND_SIGSTORE = 2; }   // Fulcio, against an OIDC identity (R3.42)

message OidcMatch { string id = 1; string identity_id = 2; string issuer = 3; string subject = 4;
                    google.protobuf.Timestamp created_at = 5; Revocation revocation = 6; }

}

// SessionKey gains:   SigstoreCertificate sigstore = 21;
// Identity gains:     repeated OidcMatch oidc_matches = 11;
// Authority gains:    IssuerKind kind = 9;
// CreateIdentityRequest gains: repeated OidcMatchSpec oidc = 5;
message OidcMatchSpec { string issuer = 1; string subject = 2; }

message RegisterSigstoreKeyResponse { SessionKey key = 1; bool created = 2; }   // with the bundle as `certificate`

- `SessionKey.authority_key_id` is the CA's key id for a keyless key; `GetSessionKey` returns the bundle as `certificate`. `KeyIdentity` is unchanged: its `key` carries `sigstore`. The brief view keeps `sigstore.oidc_issuer` and `oidc_subject` only.
- `ListSessionKeysRequest` gains `IssuerKind issuer_kind = 6` (unset for any).
- `API_REVISION` 23 (or the next free one) with its digest; `SERVED` is unchanged (same service). `remote/rules.rs`: `RegisterSigstoreKey` gets `Rule::None`; the ADMIN methods are never served remotely.
- **MCP**: the three methods go in `NOT_TOOLS` (keys are registered by the process that signs; ADMIN is never a tool); `tools/list` is unchanged byte for byte.

| Reason | Kind | Metadata | RPCs |
| --- | --- | --- | --- |
| `INVALID_SIGSTORE_BUNDLE` | `INVALID_ARGUMENT` | `step` (`size`, `json`, `chain`, `sct`, `tlog`, `time`, `signature`, `statement`, `key`), `problem` | `RegisterSigstoreKey` |

### The signing client

`reef_client::keyless` (no new crate, no `reqwest`, no `sigstore-sign`): HTTPS through the `hyper-util` and `tokio-rustls` on ring that the client already links, with the OS's roots.

- **Getting an OIDC token**, through one provider table (the agent-agnostic rule: one table, no special cases), first match wins:

  | Provider | Signal | How |
  | --- | --- | --- |
  | A file | `--oidc-token-file PATH` | read it; mode `0600` or tighter, else refused |
  | Environment | `SIGSTORE_ID_TOKEN` | the token itself (GitLab's `id_tokens:`, or any CI or script that sets it; cosign's and sigstore-python's convention) |
  | GitHub Actions | `ACTIONS_ID_TOKEN_REQUEST_URL` and `_TOKEN` | `GET $URL&audience=sigstore` with the bearer token (the workflow needs `permissions: id-token: write`) |

  None: `KeylessError::NoToken`, whose CLI hint names the three. The token is held in a `Zeroizing<String>`, never logged, and checked only for its form and `aud` (Fulcio verifies it).
- **Fulcio**: `POST {fulcio}/api/v2/signingCert` with the token, the ed25519 public key in PEM and the proof (the key's signature over the token's `sub`). The chain comes back with an embedded SCT.
- **Rekor**: `POST {rekor}/api/v1/log/entries` with a `dsse` 0.0.1 entry (the envelope and the leaf as verifier). The response's log index, integrated time, SET and inclusion proof go into the bundle.
- **The bundle** is built with small serde types for the v0.3 JSON (the client does not link `sigstore-types`), and the client checks it no further: the daemon verifies.
- **Endpoints**: public-good by default (`https://fulcio.sigstore.dev`, `https://rekor.sigstore.dev`), overridden by the client's `config.toml` `[sigstore] fulcio_url`, `rekor_url`, or `REEF_SIGSTORE_FULCIO_URL` / `_REKOR_URL` (tests and private deployments). Only `https://` unless the host is loopback.
- **API**: `Client::issue_keyless_session_key(actor, session, &KeylessOptions) -> SessionKey`, the same `SessionKey { signing_key, certificate, record }` R3.03's issuance returns, so `Claim::sign` and every caller are unchanged. Timeouts: 30 seconds per request.

### A person's login and ADR 0025

A person's keyless key needs an OIDC token from an interactive login (a browser redirect to Sigstore's OAuth provider). ADR 0025 decision 1 says the CLI is never interactive: "every command completes with stdin closed". So (question 7):

- **The CLI never opens a browser or waits for a person.** A person's token reaches Reef the same way a CI's does: `--oidc-token-file` or `SIGSTORE_ID_TOKEN`, from a tool the person runs (for a Google account, `gcloud auth print-identity-token --audiences=sigstore`; any OIDC client registered with Fulcio's issuers).
- **Verification of a person's keyless key is complete in this ticket**: `person` identities take email matches, and their keys read `BOUND` with the issuer and email.
- **The browser login belongs in the web UI and the desktop shell**, where a person is present by definition, beside R3.43's passkey flow: a follow-up issue.
- `presence` stays `none` for every keyless key: an OIDC login proves who logged in recently, not who is at the keyboard for this key's use.

### The executor

`[executor] keyless = false` by default. With `true`:

- Each job's key comes from `issue_keyless_session_key(Actor::Executor, …)`, obtained when the job first signs, not at claim, and renewed in the same session when less than 3 minutes remain (`RENEW_BEFORE` becomes per issuer kind).
- `identity` must be empty (the OIDC match decides; a non-empty one is a configuration error naming the conflict).
- The claim still goes through a token linked to an identity (`Rule::LinkedToken`, R3.05) or the socket; only the evidence identity is keyless. A keyless claim with an unlinked token is a follow-up.
- The OIDC request variables stay hidden from checks (R3.06), and the executor requests the token in its own process. `docs/executor.md` gets a keyless GitHub Actions example with `id-token: write`.

### Policy

R3.07's input `key` gains `issuer_kind` (`reef-daemon` or `sigstore`), `oidc_issuer` and `oidc_subject` (empty for a daemon-issued key), and attestor sets gain `issuer_kinds` (default any), so "trust `ci-main`, keyless only" is `identities = ["ci-main"]`, `issuer_kinds = ["sigstore"]`. Additive to format 1: an older daemon refuses the new key (`INVALID_POLICY`) and fails closed. `docs/policy.md` gains the recipe (question 6).

## Out of scope

- **An interactive login in the CLI** (browser redirect or device code): the web UI and desktop shell, a follow-up beside R3.43.
- **TUF refresh** of the trusted root, in the daemon or a command: follow-up.
- **Signing to Rekor v2** (`hashedrekord` 0.0.2 with a TSA timestamp). Verification accepts v2 bundles already; the client signs to v1 until public-good stops taking v1 writes: follow-up.
- **A Sigstore bundle per evidence object** (evidence made by `cosign attest-blob` or another client, accepted by `AddEvidence`): follow-up.
- **Keyless claims** without a token linked to an identity (R3.05's `Rule::LinkedToken`): follow-up.
- **More ambient providers** (Buildkite, CircleCI, Google Cloud metadata): additive rows in the table.
- **Pattern matches** and matches over Fulcio's CI claims (repository id, ref) beyond the SAN: follow-up if exact matches prove too rigid.
- **Verified presence** (R3.43), store verification (R4.09, R4.10).

## Risks

- **Fulcio or Rekor refuses ed25519 in production.** The default Fulcio configuration allows it, but the public-good deployment and Rekor's `dsse` type are unverified. Mitigation: the first implementation step is the staging check; the fallback (question 3) is P-256 session keys by ADR, which touches ADR 0055's key rule.
- **sigstore-rust churn.** Pre-1.0 with breaking minors every few weeks. Pinned `=0.15.1`; Reef owns the ring provider and its review (RX.02).
- **A stale embedded root fails closed.** A new Rekor shard's bundles do not verify on an old Reef until it updates or the operator overrides the root. The CI freshness check and the override bound it.
- **The public log reveals CI identities** of private repositories (S-140).
- **Ten-minute keys.** A clock-skewed daemon or a slow upload reads fresh keyless evidence `EXPIRED`; the executor obtains keys at signing time and renews early.
- **Overlap with the parallel tickets.** `reef-policy`'s input and attestor sets change (R3.07's crate, which R3.13 calls but should not change); `identity/` and `service/evidence.rs`'s identity path are this ticket's. The migration and API revision numbers will need renumbering if R3.13 or R3.25 merge first.

## Choices this brief made, and why

- **The session key is certified and logged once, evidence unchanged**, because it reuses R3.03's seam and every read, and costs one Fulcio and Rekor round trip per key.
- **Verification only in the daemon, offline, against a vendored root**, because the daemon must never depend on the network to judge evidence, and the ring-only rule holds.
- **A feature on `reef-evidence`**, because R3.03 put `check_sigstore_bundle` in the format crate for R4.10, and the `reef` binary should not link the X.509 stack for a check it never runs.
- **Our own small Fulcio and Rekor client over the client's existing HTTPS stack**, because `sigstore-sign` signs P-256 only, through digests ring cannot sign, over reqwest whose provider is aws-lc.
- **Exact matches on identities**, because a pattern that admits a branch admits that branch's code, and policies already name identities.
- **No browser in the CLI**, because ADR 0025's contract is what agents rely on, and a person's interactive flow belongs where a person is.

## What later tickets inherit

- **R3.13** refuses on a keyless key's status as on any other; a policy can require `issuer_kinds = ["sigstore"]`.
- **R3.31** shows the issuer and subject beside a keyless signer.
- **R3.43** may host the browser login beside the passkey flow, and keeps `presence: none` for keyless keys.
- **R4.09, R4.10** verify keyless keys with `check_sigstore_bundle` and the same root: a keyless key needs no daemon authority.
- **RX.02** reviews the ring provider, the registration rules and S-135 to S-142.

## Departures from dev-phases.md

- **"Logged in Rekor" logs the key's binding statement, not each evidence object.** Evidence stays R3.01's, and a bundle per object is a follow-up.
- **"A person's login" is a token supplied to the CLI, not a login the CLI runs**, under ADR 0025; the browser login is a follow-up in the web UI and desktop shell. Verification of person keyless keys is complete.
- **The policy input and attestor sets gain the issuer fields**, which the row did not name, so a policy can require keyless keys.
- **R3.03's "Rekor's integrated time becomes `witnessed_at`"** does not apply: Rekor witnesses the binding, not the evidence, and evidence is judged at `added_at`. R3.03's "yields the same `Certified` binding" holds once the daemon supplies the matched identity (`SigstoreCertified::bind`).

## Decisions for the user

Grouped for asking; the brief's body follows every recommendation.

**Group 1: the shape of keyless**

1. **What Fulcio certifies and Rekor logs.** *Recommended (A)*: the session key, once: the key signs a Reef binding statement (actor, agent, session) that Rekor logs, the bundle is registered with the daemon, and evidence stays R3.01's. (B) A Sigstore bundle per evidence object, accepted by `AddEvidence` (cosign-compatible per object, but a Rekor entry per object and a new evidence path). (C) Both, which pushes the ticket to L.
2. **How an identity names what it accepts.** *Recommended*: exact (issuer, subject) matches on identities, unique across identities, added and revoked by ADMIN RPCs, revocation applying to keys bound through it. Alternatives: patterns or regexes on the subject (rigid setups get easier, branch code gets in); or matches written in each repository's policy instead of on identities (no identity record, but policy then trusts raw OIDC strings).
3. **Key algorithm.** *Recommended*: ed25519, as every Reef key is, with the staging check as the first implementation step; if Fulcio or Rekor refuses ed25519, stop and return to ask. Alternatives: decide now to fall back to P-256 session keys by ADR (ring signs and verifies P-256; touches ADR 0055's key rule and `AddEvidence`); or P-256 from the start.

**Group 2: dependencies and trust root**

4. **Crates.** *Recommended*: `sigstore-verify`, `-trust-root` and `-crypto` `=0.15.1`, no default features, a ring `CryptoProvider` in Reef, behind a `sigstore` feature of `reef-evidence` that only the daemon enables; signing by Reef's own Fulcio and Rekor client over the client's hyper and rustls. Alternatives: a new `reef-sigstore` crate for both (a fourteenth workspace member); or `sigstore-sign` with aws-lc for signing only (breaks `tls_is_ring_only` for the `reef` binary).
5. **The trusted root.** *Recommended*: the public-good root vendored in Reef's repository with a CI freshness check, overridable by `[sigstore] trusted_root`, never fetched by the daemon, re-verified at every read. Alternatives: the root embedded in `sigstore-verify` (updates only with its releases); or TUF refresh in the daemon (network from the daemon, tokio and reqwest in the verifier).

**Group 3: who signs, and how**

6. **Registration rules and the executor.** *Recommended*: any `write` channel, the socket included, may register a bundle, since the OIDC identity decides (so a `ci` keyless key is allowed over the socket, unlike R3.03's daemon-issued `ci` keys); `[executor] keyless = true` signs evidence keyless while claims keep R3.05's linked token; policy gains `issuer_kinds` and the input's issuer fields. Alternatives: registration only through a token linked to the matched identity (no gain in proof, and it keeps the long-lived secret this ticket removes); or no policy change (keyless keys count wherever their identity does, with no way to require keyless).
7. **A person's login under ADR 0025.** *Recommended*: the CLI never runs a login; a person supplies a token by `--oidc-token-file` or `SIGSTORE_ID_TOKEN`, verification of person keyless keys is complete, and the browser login is a follow-up in the web UI and desktop shell. Alternatives: an opt-in `reef identity login` that opens a browser only on a terminal, amending ADR 0025 with a second exception; or a device-code flow that prints a URL and polls (no stdin, but it still waits on a person, and Sigstore's issuer support for it is unverified).
8. **Scope lines.** *Recommended*: Rekor v1 for signing (v2 verified, signing v2 a follow-up), GitHub Actions and `SIGSTORE_ID_TOKEN` as the providers, no TUF, no per-evidence bundles, no keyless claims; the ticket stays M at its top end. Alternative: also sign to Rekor v2 with a TSA timestamp now (L).
