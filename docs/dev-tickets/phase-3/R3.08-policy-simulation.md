# R3.08 Policy simulation

Phase 3 · Size S, at its top end, with the scope lines below · Depends on: R3.07 (`reef-policy`, `PolicyService.EvaluatePolicy` and its `policy` text field, the daemon's policy cache and evaluation turns), and builds on R2.02 (revsets, `trunk()`, positional paging pinned to an operation) · Unblocks: none listed; the design's policy editor (R3.31, R3.33) renders it, and R3.13's landing records later replace its default window

## Context

The design, Human interface: "Policy has an editor with simulation that shows which recent landings a proposed rule would have blocked." ADR 0006: "The landing service evaluates it at landing, and policy simulation evaluates it against recent landings." The row: "Evaluate a proposed policy (R3.07's `EvaluatePolicy` with the policy's text) against recent landings and report what it would have blocked. API and CLI."

R3.07 left the means: `EvaluatePolicyRequest.policy` evaluates a policy's bytes instead of the destination's, `include_input` returns the input, and its brief says "R3.08 sends a proposed policy as `EvaluatePolicyRequest.policy` for each recent landing and compares decisions". `docs/policy.md` says `--policy-file` is "for trying a policy out (R3.08's simulation builds on that)".

What this ticket has to settle, because main has no landing service yet (R3.13) and no lifecycle states (R3.09, in flight beside this ticket):

1. **What a recent landing is**, in terms of what exists today.
2. **What it is compared with**, so the report says what the proposed policy changes and not only what it decides.
3. **How a simulation over many commits stays bounded**: one evaluation is bounded by R3.07 (a 50,000,000 cost bound, 100,000 paths, 20,000 evidence rows); N of them must be too, for a remote `read` token as much as for the socket.
4. **The surface**: one READ RPC and `reef policy simulate`.

### What was verified while writing this ticket

Reef at `31421cfc` (R3.07 merged; API revision 20, `reef-api/src/lib.rs:49`; database schema 11; ADR 0061 the latest, this ticket's slot is 0062; the threat model's last row is S-97, this ticket's slot is S-98 to S-105). Paths are under `crates/` unless they start with `docs/`.

- **`EvaluatePolicy` is one function** (`reef-daemon/src/service/policy.rs:587`, 290 lines): it resolves the change, reads its diff against the merged parents in one `diff_page` call with `sizes` (up to `reef_policy::MAX_PATHS + 1` = 100,001 files), reads `reef-policy.toml` from the change's tree when the change touches it (`proposed_policy`) and from `policy_revision`'s tree, all inside one `state.reads.run` closure; then reads evidence on the tree (`evidence`, `:272`, newest 20,000 rows in pages of 1,000) and provenance of the change (`provenance`, `:382`, 10,000 records), and evaluates in `spawn_blocking` through `state.policy.load` (the cache of 16 compiled policies keyed by SHA-256, `reef-daemon/src/policy.rs`). It holds one of `CONCURRENT_EVALUATIONS` (4) `turns` for the whole call. `reef_policy::Policy::evaluate` runs on its own 64 MiB `reef-policy` thread.
- **An evaluation's cost is reported**: `Evaluation.cost` (`reef-policy/src/eval.rs:241`), the sum of the per-expression bounds computed before each runs; `cost::MAX_EVALUATION_COST` is 50,000,000 and `MAX_EXPRESSION_COST` 10,000,000. R3.07 measured about 0.14 µs per AST node, so one evaluation at its bound is about 7 s of one core; real policies cost a few times the number of paths.
- **Revset paging exists.** `ListChanges` pages any revset with `log::log_page(&repo, &parsed, skip, limit, &stop)` (`reef-lib/src/jj/log.rs:256`, topological, children first) and a positional cursor `skip:last_commit_id` (`service/reading.rs:331`), in a token that pins the first page's operation (`service/page.rs`; ADR 0029: page tokens bound to the request's other fields, reason `INVALID_PAGE_TOKEN`). `state.reads.stop()` stops a read when the caller goes away.
- **jj 0.47's revset language** has `first_ancestors(x, depth)`, `first_parent(x)`, `merges()`, `committer_date(after:"…")`, so any window a user wants is a revset.
- **What "landed" means today.** Nothing records a landing: there is no landing service (R3.13), no `landed` state (R3.09), and Reef's own `main` moves by `jj git fetch` of GitHub squash merges. What exists is the destination's ancestry: `trunk()` (`reef_lib::jj::revset::trunk`, `revset.rs:94`) and the commits reachable from it.
- **Evidence on old trunk trees expires.** `docs/evidence.md:150`: "Evidence on an old trunk commit that no bookmark or live change keeps expires after `[evidence] retention`" (90 days by default), and commits squash-merged by a forge carry no evidence at all, since evidence binds to a tree (R3.01) and a squash makes a new one. A simulation over history therefore sees `missing` evidence for most landings, which the report must separate from the other reasons a landing would be blocked.
- **Surfaces.** `reef policy` is in `--help-all` only (the root help is at its 512-byte budget); `EvaluatePolicy` is in MCP's `NOT_TOOLS` (`reef-vcs/src/mcp/tools.rs:504`, `tools/list` at its byte budget); every command has an `OUTPUTS` row in `reef schema`; the SDKs are generated from the descriptor set. The CLI's `reef policy eval` (`reef-vcs/src/cli/policy.rs:599`) already converts an evaluation message to `reef_policy::Evaluation` (`evaluation_of`, `:517`) and renders unmet rules (`render_rules`, `:251`).

### What a recent landing is (user decision 1)

**A landing is a commit that reached the destination**: a non-merge ancestor of `trunk()`, judged as its own change, exactly as `reef policy eval -r <commit>` judges it today. The window is a revset, `revisions`, and its default is:

```text
::trunk() ~ root() ~ merges()
```

read children first (jj's topological order, newest landings first), and **the newest 20** by default (`reef policy simulate --limit`, at most 1,000 through the CLI; the API pages, below).

- **Why every ancestor and not the first-parent line**: a branch merged into the destination landed each of its commits, and R3.13 will judge each change it lands, so each is a landing. A merge commit is left out because its diff against its merged parents (what R3.07 judges) is only its conflict resolution; its content is its parents', which are in the window. On a squash or rebase history (Reef's own), every ancestor is on the first-parent line anyway.
- **Any revset works**: `-r 'first_ancestors(trunk(), 50)'`, `-r 'trunk()~30..trunk()'`, `-r 'ancestors(trunk()) & committer_date(after:"2 weeks ago")'`, `-r 'ancestors(main) & author("ci")'`. A revset that names `@` snapshots first, as every read does.
- **The seam with R3.09 and R3.13.** Once R3.13 records landings (with the evidence and the policy blob it pinned) and R3.09 records `landed` as an operation, the default window becomes "the destination's newest landing records", judged with the evidence pinned at landing. `SimulatePolicyRequest.revisions` stays; a later field selects landing records. This ticket builds no landing record and reads no lifecycle state.

### What a landing is compared with: the baseline (user decision 2)

Each landing is evaluated twice, from one input: under the **proposed** policy and under a **baseline**, the policy at `baseline_revision`, **`trunk()` by default**, the same for every landing. The input (diff, evidence, provenance) is read once; the second evaluation is a cache hit plus the rules' cost.

- **Why the destination's current policy**: the question a policy edit raises is "what does this edit change", holding history fixed. The current policy is what the edit replaces. The policy in force at each landing (the policy at its first parent) answers a different question, "would history have gone otherwise", and before R3.13 nothing enforced it, so it would mostly be `NO_POLICY`.
- **Each landing reports** `decision` (proposed) and `baseline_decision`, and an `outcome`:

  | Outcome | Proposed | Baseline |
  | --- | --- | --- |
  | `NEWLY_BLOCKED` | not `ALLOW` | `ALLOW` |
  | `STILL_BLOCKED` | not `ALLOW` | not `ALLOW` (`BLOCK` or `INVALID_POLICY`) |
  | `NEWLY_ALLOWED` | `ALLOW` | not `ALLOW` (`BLOCK` or `INVALID_POLICY`) |
  | `STILL_ALLOWED` | `ALLOW` | `ALLOW` |
  | `BLOCKED` | not `ALLOW` | `NO_POLICY`, or no baseline asked for |
  | `ALLOWED` | `ALLOW` | `NO_POLICY`, or no baseline asked for |

  A baseline of `NO_POLICY` is "nothing to compare with", not "blocked": the landings in the window did land, and under no policy nothing judged them. Most repositories today have no policy on `trunk()`, so their first simulation reports `BLOCKED` and `ALLOWED` only.
- **`no_baseline`** skips the second evaluation; `baseline_revision` names another (a release branch's policy, or `@-`).
- **"Would have blocked" means "not `ALLOW`"**: `BLOCK`, and `INVALID_POLICY` for the baseline. A proposed policy that does not load is not simulated at all (below).

### Why a landing is blocked: missing evidence apart

A landing the proposed policy does not allow carries its **unmet rules**: each rule `UNSATISFIED` or `ERROR`, with R3.07's `PolicyRuleResult` (name, kind, status, message, paths, `missing`, `failed`, `signoff`). And one flag:

- **`missing_evidence_only`**: every unmet rule is a `[[require]]` whose only unmet pairs are `missing` (no trusted object, rather than a trusted `fail`). That is what a squash-merged or expired tree looks like, so the summary counts it apart: "12 would be blocked, 9 only for evidence their trees do not have". `docs/policy.md` says why history usually lacks evidence and that the other reasons (limits, forbidden paths, sign-offs, rules, failed evidence) are the ones a simulation is for.

No option rewrites the policy to pretend the evidence was there: the simulation runs the policy's bytes as they are, so its decisions are the ones `reef policy eval` would give.

### The proposed policy

Either `policy` (the file's bytes, at most 256 KiB, as in `EvaluatePolicy`) or `policy_revision` (the `reef-policy.toml` at a revision, for example a change that edits the policy); exactly one is required (`POLICY_SOURCE_CONFLICT` for both, `POLICY_SOURCE_MISSING`, new, for neither).

- **It must load.** A proposed policy that does not load is answered at once with `proposed_decision: INVALID_POLICY` and its diagnostics, and no landing is evaluated: every landing would be `INVALID_POLICY`, and the call would spend its budget saying so. A revision with no `reef-policy.toml` is `proposed_decision: NO_POLICY` the same way. Neither is an RPC error, as in R3.07.
- **The proposed policy judges every landing, including one that edits the policy.** `builtin:owners` and `builtin:policy-file` apply as R3.07 defines them, with the landing's own file as `proposed_policy` in the input.

### Bounds: every call is bounded, and the CLI walks pages

A simulation is one page per call; a page evaluates landings in the window's order and stops at the first of:

1. **`page_size` landings**: 0 means 20, more than 100 is 100, negative is `INVALID_ARGUMENT` (ADR 0029's reason). Not ADR 0029's 100 and 1,000: each item here is up to two evaluations, not a row.
2. **A page cost of 100,000,000**: the page ends after the landing whose evaluations (proposed plus baseline) take the page's summed `cost` past it. One landing costs at most 2 × 50,000,000, so a page's evaluations are at most 200,000,000 (about 28 s of one core at R3.07's measured rate, and a few milliseconds for a real policy).
3. **200,000 touched paths**: the page ends after the landing that takes the page's total past it, since reading diffs, not evaluating, is what large commits cost.
4. **3 MiB of encoded response** (`page::MAX_PAGE_BYTES`, under tonic's 4 MiB limit), checked before a landing is added; a page holds at least one landing.
5. **The caller going away** (`state.reads.stop()`): the call ends with `CANCELLED`.

Every page returns `next_page_token` (empty on the last), a positional cursor pinned to the first page's operation, as `ListChanges`'s is. The boundaries depend only on the window and the inputs, not on a clock.

- **One evaluation turn per page.** The page holds one of the daemon's four `turns` while it runs and evaluates its landings one after another, so a simulation never takes more than one core from other evaluations and never more than one of the four slots. Diffs are read on the repository thread one landing per `reads.run` call, so other reads interleave.
- **The CLI walks pages** up to `--limit` landings (default 20, at most 1,000), summing the pages' summaries. `--limit 1000` is ten pages at most and a few seconds for a real policy.

### The API: `PolicyService.SimulatePolicy`, API revision 22

Added to `reef/api/v1/policy.proto`:

```proto
service PolicyService {
  rpc EvaluatePolicy(...) ...
  // Evaluates a proposed policy over recent landings: each commit of `revisions` (the destination's
  // non-merge ancestors by default), newest first, one page at a time, beside a baseline policy, and
  // reports which landings it would have blocked and why. Reads only. Errors: the revision reasons
  // for `revisions`, `policy_revision` and `baseline_revision`; INVALID_ARGUMENT with POLICY_SOURCE_CONFLICT
  // (both `policy` and `policy_revision`), POLICY_SOURCE_MISSING (neither), POLICY_TOO_LARGE, and
  // INVALID_PAGE_TOKEN; SNAPSHOT_FAILED.
  rpc SimulatePolicy(SimulatePolicyRequest) returns (SimulatePolicyResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
}

// How a landing's proposed decision compares with its baseline decision.
enum PolicySimulationOutcome {
  POLICY_SIMULATION_OUTCOME_UNSPECIFIED = 0;
  POLICY_SIMULATION_OUTCOME_NEWLY_BLOCKED = 1;
  POLICY_SIMULATION_OUTCOME_STILL_BLOCKED = 2;
  POLICY_SIMULATION_OUTCOME_NEWLY_ALLOWED = 3;
  POLICY_SIMULATION_OUTCOME_STILL_ALLOWED = 4;
  POLICY_SIMULATION_OUTCOME_BLOCKED = 5;   // no baseline to compare with
  POLICY_SIMULATION_OUTCOME_ALLOWED = 6;   // no baseline to compare with
}

message SimulatePolicyRequest {
  string repo = 1; string workspace = 2;
  string revisions = 3;          // the window, a revset; empty for `::trunk() ~ root() ~ merges()`
  bytes policy = 4;              // the proposed policy's bytes, at most 256 KiB
  string policy_revision = 5;    // or the reef-policy.toml at this revision; exactly one of the two
  string baseline_revision = 6;  // the baseline's revision; empty for trunk()
  bool no_baseline = 7;          // evaluate the proposed policy only
  string at_operation = 8; bool skip_snapshot = 9;
  int32 page_size = 10;          // landings: 0 means 20, over 100 means 100
  string page_token = 11;
  bool include_evaluations = 12; // each landing's full evaluations, not only its unmet rules
}

message PolicySimulatedLanding {
  string change_id = 1; string commit_id = 2; string tree_id = 3;
  string subject = 4;                       // the description's first line
  string author = 5;                        // name <email>
  google.protobuf.Timestamp committed_at = 6;
  PolicyDecision decision = 7;              // proposed
  PolicyDecision baseline_decision = 8;     // UNSPECIFIED with no_baseline
  PolicySimulationOutcome outcome = 9;
  repeated PolicyRuleResult unmet = 10;     // the proposed policy's rules UNSATISFIED or ERROR
  repeated string baseline_unmet = 11;      // the baseline's, by name
  bool missing_evidence_only = 12;
  uint64 cost = 13;                         // both evaluations
  PolicyEvaluation evaluation = 14;         // with include_evaluations
  PolicyEvaluation baseline_evaluation = 15;// with include_evaluations
}

message PolicySimulationRuleCount { string name = 1; PolicyRuleKind kind = 2; uint32 landings = 3; }

message PolicySimulationSummary {           // over this page's landings
  uint32 landings = 1; uint32 blocked = 2; uint32 missing_evidence_only = 3;
  uint32 newly_blocked = 4; uint32 still_blocked = 5; uint32 newly_allowed = 6; uint32 still_allowed = 7;
  repeated PolicySimulationRuleCount rules = 8;  // each proposed rule that blocked some landing, in file order
}

message SimulatePolicyResponse {
  PolicyDecision proposed_decision = 1;     // ALLOW here means "it loads"; NO_POLICY or INVALID_POLICY end the call
  PolicySource proposed = 2;
  repeated PolicyDiagnostic diagnostics = 3;
  PolicySource baseline = 4;                // empty with no_baseline
  PolicyDecision baseline_state = 5;        // NO_POLICY or INVALID_POLICY when the baseline has none or does not load
  repeated PolicySimulatedLanding landings = 6;
  PolicySimulationSummary summary = 7;
  uint64 cost = 8;
  string at_operation = 9;
  string next_page_token = 10;
}
```

(Field names may be tightened during implementation; every enum value and field gets a comment for `buf lint`, and the RPC's doc lists every reason, as ADR 0029 requires.)

- `proposed_decision` is reused from `PolicyDecision` so a client tells "did not load" from "loaded" without a second enum; the brief's text output never prints "ALLOW" for it.
- **Who may call it**: every READ caller, on the socket, the web listener and the remote listener. No WRITE RPC, so `remote/rules.rs` is unchanged. No database migration. `SERVED` is unchanged (same service). `API_REVISION` 22 with its digest (R3.09 took 21 first).
- **New reason**: `POLICY_SOURCE_MISSING` in `reef_api::error`.

### The daemon

- **The refactor first, no behaviour change**: `service/policy.rs` gains `read_change(state, target, repo, commit) -> ChangeRead` (the diff, the change's own policy file, evidence and provenance: today's `Read` plus the evidence and provenance calls) and `evaluate_over(state, bytes, &Input) -> Evaluation` (today's `evaluate` plus the invalid-file handling). `EvaluatePolicy` calls them; its tests stay green unchanged.
- **`SimulatePolicy`**: validate the sources and the page; take one turn; snapshot first when a revset uses `@` (first page at head only, as `ListChanges`); resolve the window, the proposed policy (bytes or revision) and the baseline at the pinned operation; load both through the cache (load errors end the call as above); then for each commit of `log_page(skip, page_size + 1)`, read its input, evaluate both on the `reef-policy` thread inside `spawn_blocking`, convert, add to the page, and check the budgets.
- `service/policy.rs` stays one module; the simulation goes in `service/policy/simulate.rs` if the file passes about 1,200 lines.

### The CLI: `reef policy simulate`

```
reef policy simulate [--policy-file FILE | --policy-revision REV] [-r REVSET] [--limit N]
                     [--baseline-revision REV | --no-baseline] [--all] [--evaluations]
```

- **The proposed policy** is `./reef-policy.toml` by default, read by the CLI and sent as text, as `reef policy check`'s default file; `--policy-file` names another, `--policy-revision` reads one at a revision (for a change that edits the policy: `--policy-revision @`). With no file and no flag: exit 2, `hint` naming both flags.
- **Text output**: the proposed and baseline sources (path or revision, short SHA-256), then one line per landing that is not allowed (`--all`: every landing): outcome, short commit, subject, and each unmet rule's name with its short reason (`tests: missing test from [ci]`, `limits: 5,321 lines over 4,000`, `forbid secrets: 2 paths`), then the summary: "20 landings: 7 would have been blocked (3 newly, 4 also by the baseline; 5 only for missing evidence); 13 allowed", and the rules that blocked, with counts. A proposed policy that does not load prints its diagnostics as `reef policy check` does and exits 2 (`INVALID_POLICY`, the client reason R3.07 added). Otherwise it exits 0 whatever it reports.
- **JSON** (`reef_client::json`, `JsonSchema`): `PolicySimulation` (sources, landings with the response's fields, the summary summed over pages, `at_operation`, `truncated` when `--limit` stopped before the window's end). **Brief**: the summary, and per blocked landing `commit`, `outcome` and the unmet rules' names. `reef schema`'s `OUTPUTS` gains its row.
- `--evaluations` sets `include_evaluations` and prints, in JSON only, each landing's full evaluations.
- **Not in the root help**: `policy` is in `--help-all` already; `help_lists_every_command` gains `simulate` if it lists subcommands.

### MCP, SDKs, web UI

- **MCP**: `SimulatePolicy` joins `EvaluatePolicy` in `NOT_TOOLS` ("`reef policy simulate`; the policy editor renders it; tools/list is at its budget (#116)"). `tools/list` is unchanged.
- **SDKs**: regenerated from the descriptor set (`simulate_policy` / `simulatePolicy`), no hand-written code; their generation checks must pass. (R3.44 is changing the SDKs at the same time; the generated files are rebased, not hand-merged.)
- **Web UI**: nothing. The design's "editor with simulation" is R3.31/R3.33's to render; `SimulatePolicy` is what it calls.

## Threat model rows

- **S-98, Simulation cost amplification**, any READ caller (a remote `read` token sending `policy` text), Medium: one call evaluates attacker-chosen CEL over many commits. Fixed: a page of at most 100 landings, a page cost bound of 100,000,000 on top of each evaluation's 50,000,000, a 200,000-path bound, one evaluation turn per page, `reads.stop()` on disconnect (tests 4, 5, 9).
- **S-99, Misleading history**, repository state, Low: evidence expired by retention, never produced for a squash-merged tree, or a signer's key revoked since, makes a simulation report blocks the landing service would not have made, or allows the reader to dismiss real ones. Documented: decisions are as of this read (S-96); `missing_evidence_only` separates absent evidence; `docs/policy.md` says what a simulation over history can and cannot tell (test 3).
- **S-100, Baseline confusion**, a reader, Low: comparing with `trunk()`'s policy hides that the policy in force at an old landing differed, and a `NO_POLICY` baseline could read as "everything was blocked". Fixed by the outcome table (`BLOCKED`/`ALLOWED` with no baseline) and documented (test 2).
- **S-101, Reading another revision's policy**, a READ caller, Low: `policy_revision` and `baseline_revision` read `reef-policy.toml` at any revision the caller names; a READ caller can already read any file with `FileService.ReadFile`, so this exposes nothing new. Documented.

S-102 to S-105 stay unused.

## Tests

In `crates/reef-daemon/tests/policy.rs` (`TestDaemon`, `testing::no_automatic_snapshots`), over a fixture repository whose `main` has six commits: one touching `crates/a.rs` with 10 lines, one adding `secrets/key.pem`, one of 5,000 lines, one editing `reef-policy.toml`, one with `test` evidence from a `ci` session key on its tree, and a merge of a two-commit branch:

1. `window`: the default window is the non-merge ancestors of `main`, newest first, the merge left out and its branch's commits in; `revisions` narrows it; a revset naming `@` snapshots; `at_operation` is honoured and pinned across pages.
2. `baseline` (S-100): with `main`'s policy as baseline and a proposed policy that adds `[[forbid]] secrets` and `[limits] max_lines = 4000`: the secrets commit and the large commit are `NEWLY_BLOCKED` with the rule names, the rest keep their outcome; with no policy on `main`, outcomes are `BLOCKED`/`ALLOWED`; `no_baseline` evaluates once and `baseline_decision` is unspecified; `baseline_revision` reads another; an invalid baseline is `baseline_state: INVALID_POLICY` and its landings `STILL_BLOCKED` or `NEWLY_ALLOWED`.
3. `missing evidence` (S-99): a proposed `[[require]] tests` from `ci` blocks every landing but the one with evidence; those blocked only for it have `missing_evidence_only`, and a landing with a trusted `fail` does not.
4. `paging` (S-98): `page_size` 2 walks the window in three pages with the same `at_operation`; a token with other fields is `INVALID_PAGE_TOKEN`; 0 is 20 and 500 is 100; negative is `INVALID_ARGUMENT`.
5. `budgets` (S-98): a proposed rule whose cost per landing is about 40,000,000 ends a page after its third landing (proposed plus baseline past 100,000,000) with a token; a window whose commits touch 150,000 paths each ends after the second; each is deterministic over two runs.
6. `sources`: `policy` text and `policy_revision` (a change editing `reef-policy.toml`) give the same results for the same bytes; both is `POLICY_SOURCE_CONFLICT`; neither is `POLICY_SOURCE_MISSING`; 257 KiB is `POLICY_TOO_LARGE`; an invalid proposed policy returns `INVALID_POLICY` with diagnostics and no landings, and a revision without the file `NO_POLICY`; the cache compiles each policy once per call (the counter).
7. `parity`: for every landing, `evaluation` (with `include_evaluations`) equals `EvaluatePolicy` for that commit with the same `policy` text, field for field but `at_operation`.

## Risks

- **Most history lacks evidence**, so a policy with `[[require]]` blocks most of it. Mitigation: `missing_evidence_only`, the summary's split, and the docs.
- **The default window is not "landings" in a forge's sense** on a merge-heavy history: each branch commit is judged alone, as R3.13 will judge each change. Mitigation: any revset, documented examples (`first_ancestors`).
- **A page can take tens of seconds at the bound.** Mitigation: the bounds above, one turn, cancellation; real policies cost milliseconds per landing.
- **API revision collisions** with R3.09 and R3.44 in flight: renumber at rebase, as the runbook says.

## Departures in the implementation

Found while building it (2026-11-08):

1. **The page's cost and path bounds are fields of the daemon's policy state** (`Policies::page_cost` and `page_paths`, defaulting to the constants `MAX_PAGE_COST` and `MAX_PAGE_PATHS`), not configuration: test 5 lowers them, since a rule costing 40,000,000 per landing would take seconds per landing in a debug build.
2. **`summary.rules` lists every rule of the proposed policy**, with the landings each blocked (0 for none), not only those that blocked: the CLI sums pages by name in the policy's order, and an editor sees which rules never fire. Text prints only those that blocked.
3. **The CLI's two refusals** reuse the reasons that exist: no `./reef-policy.toml` and no flag is `POLICY_SOURCE_MISSING` (exit 2, as the daemon names it), and `--policy-revision` naming a revision with no policy is `INVALID_POLICY` (exit 2), like a policy that does not load.
4. **Test 9 holds the daemon's evaluation turns itself**: with three held a simulation runs, with all four held it waits until they are released, and every turn is back afterwards. That shows each evaluation takes exactly one turn without racing calls against each other.
5. **The CLI tests use `-r '::@ ~ root()'`**: the synthetic fixture has no `main`, so `trunk()` is the root and the default window is empty.
6. **Performance is measured through the daemon test in a debug build** (eight landings in 16 ms, about 2 ms each), not on Reef's own `main` in release: this ticket may not restart the installed daemon, and no SDK or binary is regenerated for it. The SDKs generate their code at build time, so nothing is committed for them.
7. **The review's findings changed the bounds** (the PR's table has them all): a page no longer holds one evaluation turn for its whole length; a daemon reads at most two pages at once (`CONCURRENT_SIMULATIONS`), and each evaluation takes a turn that is moved into the task running it, so a caller that disconnects cannot free a turn while its evaluation runs (`EvaluatePolicy` now does the same, and its diff read stops with its caller); a page also ends after the landing that takes the evidence and provenance rows read past 50,000; a landing too large for a page alone is `trimmed` (a new field); full evaluations carry their `source` and `at_operation`; an invalid baseline reports its SHA-256 and version as `EvaluatePolicy` does; an empty `--policy-file` is `INVALID_POLICY` in the CLI (for `eval` too).

## Decisions for the user

Asked on 2026-11-08; the user accepted every recommendation, and the brief's body follows them.

1. **The window**: every non-merge ancestor of `trunk()`, newest first (`::trunk() ~ root() ~ merges()`), the newest 20 by default, any revset accepted; R3.13's landing records replace the default later. (Not the first-parent line, not the operation log's bookmark moves.)
2. **The baseline**: the policy at `trunk()`, the same for every landing, with `--baseline-revision` and `--no-baseline`; a `NO_POLICY` baseline gives `BLOCKED`/`ALLOWED`. (Not the policy in force at each landing, not no baseline.)
3. **Missing evidence on history**: the policy runs as written; `missing_evidence_only` is flagged per landing and counted apart. (No option that treats missing requirements as satisfied.)
4. **Bounds**: a paged unary RPC; a page stops at 20 landings by default (100 at most), a summed cost of 100,000,000, 200,000 touched paths, or 3 MiB, holding one evaluation turn; the CLI walks pages up to `--limit` (20 by default, 1,000 at most). (Not one unpaged call, not a server stream.)
5. **The surface**: `PolicyService.SimulatePolicy` (READ) and `reef policy simulate`, the proposed policy from `./reef-policy.toml` by default, exit 0 whatever it reports, no `--require-no-new-blocks`. (Not a client-side loop over `EvaluatePolicy`.)
