# R3.01 Evidence object format

Phase 3 · Size M · Depends on: R2.03 (the commits writes report, `reef-agent`, the reasons and their documentation rule) · Unblocks: R3.02, R3.03, R3.05, R3.07, R3.19 (and, through them, R3.04, R3.06, R3.13, R3.15, R3.22, RX.02)

## Context

The design's fifth object is evidence: "a signed attestation: the snapshot hash it was computed on, the attestor identity, the kind (test, build, lint, policy), result, and an optional artifact hash" (data model table), "content-addressed objects linked to the snapshot they were computed against" (principle 7). The landing gate's proof is a chain of five links ("What evidence proves"). This ticket builds the first two: a claim bound to an exact tree hash, and an attestation that signs the claim in a standard envelope. The other three are later tickets: a trusted attestor (R3.03 session keys, R3.07 policy), policy satisfaction (R3.07, R3.13) and coverage (R3.19, R3.18).

Executors are built against this format: R3.05 writes the protocol, R3.06 the reference executor, and later anyone else's. The format is therefore the part of the ticket that cannot be cheaply changed, and most of this brief is about it. The rest is the smallest surface that stores evidence, finds it again and checks it: one service with three RPCs, three CLI commands, one database migration and a format crate.

This ticket makes no trust decision. A stored evidence object whose signature verifies says that the holder of key K signed the claim. It does not say that K belongs to anyone, that anyone should believe K, or that the claim is true. "Evidence from an untrusted attestor is stored but carries no weight at landing" (design, Open ecosystem). R3.01 stores it and does not weigh it.

### What was verified while writing this ticket

- **The database.** `reef-daemon/src/db/mod.rs` has six numbered migrations; `SCHEMA_VERSION` is their count, 6, and a test asserts it (`:634`). Released migrations are never edited (`0001_initial.sql` header). `Db::delete_repository` deletes the repository's leases, workspaces, base cache rows and the repository row, and refuses while a workspace is active (`db/repositories.rs:183`–`:204`). It does not delete `snapshots` rows. Backups copy the whole of `reef.sqlite3` through SQLite's online backup API (ADR 0020). Every remote WRITE call is logged under `reef_daemon::remote::audit` (`remote/audit.rs`), which is how requirement 5 of the threat model is met for a write that records no operation.

- **Crypto already in the lockfile.** `ring` 0.17.14 (rustls on ring; `reef-client` and `reef-daemon` depend on it), `sha2` 0.11.1, `base64` 0.23.1, `serde_json` 1.0.154. `ed25519-dalek` is not in the lockfile. `crate_graph`'s `tls_is_ring_only` keeps aws-lc and openssl out.
- **ring's ed25519** (`ring-0.17.14/src/ec/curve25519/ed25519/`): `Ed25519KeyPair::generate_pkcs8` (PKCS#8 v2), `from_pkcs8` (v2 only), `from_pkcs8_maybe_unchecked` (v1 or v2), `sign`; `UnparsedPublicKey::new(&ED25519, pk).verify(msg, sig)` (`src/signature.rs:385`). Verification rejects a non-canonical S (`scalar.rs:30`) and a non-canonical R, but accepts small-order and non-canonical public keys (`verification.rs`; `curve25519.c:166`). ed25519-dalek's `verify_strict` also rejects small-order R and A. `openssl genpkey -algorithm ed25519` (OpenSSL 3.6.3, checked on the baseline Mac) writes a 48-byte PKCS#8 v1 key with no public key, which only `from_pkcs8_maybe_unchecked` reads; its SubjectPublicKeyInfo DER is 44 bytes. macOS's own `/usr/bin/openssl` is LibreSSL 3.3.6, and `genpkey -algorithm ed25519` there prints `Algorithm ed25519 not found` (checked on the baseline Mac; the self-hosted runner has it first on `PATH`, #216). So a stock Mac cannot make a key with `openssl`, and tests must not shell out to it for ed25519.
- **DSSE v1.0.2** (`secure-systems-lab/dsse`, `protocol.md`, `envelope.md`): `PAE(type, body) = "DSSEv1" SP LEN(type) SP type SP LEN(body) SP body`, LEN the decimal byte length with no leading zeros. The envelope is `{"payload", "payloadType", "signatures": [{"keyid", "sig"}]}`. Verifiers must accept both standard and URL-safe base64. `keyid` is an unauthenticated hint that "MUST NOT be used for security decisions". The payload need not be canonical, and an implementation must not re-parse the envelope after verification to get the payload. Consumers ignore unknown fields.
- **in-toto Statement v1** (attestation spec v1.2.0, 2026-03-18): `_type` `https://in-toto.io/Statement/v1`, `subject` (ResourceDescriptors, each with a `digest`), `predicateType` (a URI), `predicate`. The DSSE `payloadType` is `application/vnd.in-toto+json`. Consumers ignore unknown fields. The DigestSet lists `gitTree`, `gitCommit`, `gitBlob` and `gitTag` as "the lowercase hex SHA-1 (40 character) or SHA-256 (64 character)" git object id, and says `gitTree` "can be used for arbitrary trees … even outside git". `blake3` is not listed; custom keys are allowed if their encoding is documented.
- **Existing predicates do not fit alone.** in-toto's `test-result/v0.1` (`result` `PASSED`/`WARNED`/`FAILED`, `configuration`, test-name lists) covers tests only. SLSA provenance v1 describes builds of artifacts, not checks of a source tree. SVR v0.2 requires `verifier.policies`. None has a kind, a target or an `error` result.
- **Sigstore bundle v0.3** carries one DSSE envelope as `dsseEnvelope`, with `verificationMaterial` as a `publicKey.hint`, a certificate, or a chain. "DSSE envelopes in a bundle MUST have exactly one signature", and the key hint must equal the envelope's `keyid`. Sigstore's recommended hint is the SHA-256 of the key's DER SubjectPublicKeyInfo (RFC 6962, section 3.2).
- **The Rust crates.** `in-toto` 0.4.0 (2024-12) implements Statement v0.1 only, and its DSSE module is private and not conformant (it hex-encodes signatures, and its open PR #123 fixes that). `in_toto_attestation` 0.1.0 (2025-08, one release) is rust-protobuf with proto-JSON, not serde. `dsse` 0.1.6 is seven weeks old, has one maintainer, and its repository was archived on 2026-10-31. `sigstore` 0.15.0 (released today) is marked experimental, requires openssl or aws-lc-rs (there is no ring option), and cannot sign DSSE. The newer `sigstore-types` 0.15.1 (sigstore-rust) has crypto-free `DsseEnvelope` and `Statement` types and a keyless `sign_raw_statement` in `sigstore-sign`, which defaults to aws-lc-rs and signs with ECDSA P-256. All licences are allowed by `deny.toml`. None is needed for this ticket.

## Decisions

### Size

M, as the row says, at its top end. The format and its checks are about 600 lines with their unit tests. The service, the migration and three CLI commands are each small and follow existing patterns. What stays out to keep it M: trust, keys bound to identities, artifacts, evidence in `Change`, MCP tools, the web UI, deletion and retention ("Out of scope", each with its ticket).

### What the evidence binds to: the tree

- **The subject is the tree, never the commit.** The design keys evidence by tree hash in two places ("Evidence is keyed by tree hash, so an identical tree is never tested twice", CI load; "verifies that each evidence object's snapshot hash matches the submitted tree", Landing), and R3.05's request "names a tree hash". A commit id changes on every describe and rebase, while a describe or a rebase onto an unchanged base keeps the tree, and evidence about the tree stays true. Two changes with the same tree share their evidence.
- **The data model table's "snapshot hash" means the snapshot's tree hash.** A snapshot in that table is a commit ("a tree hash, parent snapshot hashes, author, timestamp"), so read literally the row binds evidence to the commit, which contradicts the two passages above. This brief follows the passages, and the design's row is reworded (Deliverables).
- **A conflicted tree has no evidence.** It has no single tree id (`tree_id` is empty), and landing refuses a conflicted change anyway. Adding evidence through a revision that is conflicted is refused with `CONFLICTED_REVISION`.
- **The link to a change is Reef's record, not part of the claim** (see "Linked from the change").

### The statement

One in-toto Statement v1, serialized as JSON, in the DSSE payload:

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{"name": "tree", "digest": {"gitTree": "4b825dc642cb6eb9a060e54bf8d69288fbee4904"}}],
  "predicateType": "urn:reef-vcs:evidence:v1",
  "predicate": {
    "kind": "test",
    "result": "pass",
    "target": "crates/reef-lib:jj_writes",
    "startedOn": "2026-11-05T10:00:00Z",
    "finishedOn": "2026-11-05T10:01:12Z",
    "artifacts": [{"name": "test.log", "digest": {"sha256": "9f86d0…"}, "mediaType": "text/plain"}],
    "annotations": {"runner": "ci-7"}
  }
}
```

- **`subject`**: exactly one ResourceDescriptor with `name` `"tree"` and `digest` `{"gitTree": <lowercase hex>}`, of the repository's object id length (40 with SHA-1 git, 64 with SHA-256 git). `name` must be exactly `"tree"` (a missing or other name is refused, check `subject`), so that two producers write the same bytes; `uri` and `mediaType`, if present, are strings and `annotations` an object, also checked as `subject`. Other digest keys in the same subject are refused in v1. ADR 0011's consequence, "an evidence object references a hash qualified by its backend", is met by the DigestSet key. Phase 4's Reef backend (R4.03) will use a documented custom key, such as `reefTree`, in the same position.
- **`predicateType`**: Reef's v1 predicate. The user chose `urn:reef-vcs:evidence:v1` ("Decided by the user"), consistent with R2.24's `urn:reef-vcs:schema:<version>`. Any other predicate type is refused in this ticket (`INVALID_EVIDENCE`, check `predicate_type`).
- **The predicate's fields**, all names lowerCamelCase as in in-toto and SLSA:

  | Field | Required | Meaning | Checked |
  | --- | --- | --- | --- |
  | `kind` | yes | What was checked. An open vocabulary: `^[a-z][a-z0-9-]{0,62}$`. `test`, `build`, `lint` and `policy` are the design's and are reserved with those meanings; R3.22 adds `behavioral-diff`. Policy names the kinds it requires. | pattern |
  | `result` | yes | `pass`, `fail`, or `error`: the check could not reach a verdict (a crash of the runner, a timeout, an exhausted budget). `error` is not `fail`, so R3.14's bisect does not blame a change for an executor's failure. | one of three |
  | `target` | no | The test or build target the evidence covers, in the executor's own naming. Absent means the whole check of that kind on the tree. R3.19 defines how per-target results compose; this ticket stores and filters it. | 1 to 512 bytes, no control characters |
  | `startedOn`, `finishedOn` | yes | When the check ran, as the attestor claims: RFC 3339 in UTC with `Z`. | `YYYY-MM-DDTHH:MM:SS[.fraction]Z` exactly (one to nine fraction digits, UTC with `Z`, from 1970 to 9999; a leap second, `:60`, is refused); `finishedOn` ≥ `startedOn` |
  | `artifacts` | no | ResourceDescriptors of what the check produced (logs, binaries, reports): `name` required, `digest` with `sha256` required, `uri`, `mediaType` and `annotations` optional. R3.02 stores the bytes by `sha256`; this ticket records the digests and never requires the bytes to exist. | at most 64; `sha256` is 64 lowercase hex |
  | `annotations` | no | A JSON object for the producer's own data. Reef never reads it, and never defines a field inside it. | an object |

- **No attestor field.** A field in which the producer names itself proves nothing, since anyone can write any name. The attestor is the key that signed the envelope, reported as `key_id`; R3.03 binds key ids to operator and CI identities. The row's "attestor" is that key. The proposal view and policy must never present or read a self-declared name as the attestor.
- **No change or commit id in the claim.** An executor sees a tree, not a change (R3.05). Which change the evidence was added for is Reef's record.

### The envelope and its serialization

- **DSSE v1**, `payloadType` `application/vnd.in-toto+json`, **exactly one signature**. One attestor per object is the data model's, and a sigstore bundle v0.3 accepts only one, so R3.03's keyless option can wrap an envelope unchanged. A second signature is refused in v1 (`INVALID_EVIDENCE`, check `signatures`). A countersignature, such as a store's at landing, is a separate evidence object.
- **The payload is not canonicalized.** DSSE signs bytes, so a producer may write any JSON encoding. The daemon parses the verified payload bytes and stores them exactly as received. Reef's own producer (`reef-evidence`) writes compact JSON with keys in the order of the example and no trailing newline, so it produces the same bytes for the same claim. The rules: the payload is UTF-8 JSON, and it must contain no duplicate key at any depth. Two parsers that keep different copies of a duplicated key can disagree about what was signed, which is a known attestation attack.
- **The stored envelope is canonical.** The daemon writes the envelope again as compact JSON with exactly `payload`, `payloadType` and `signatures` (`keyid`, `sig`), in that order, with standard base64 and padding, and no trailing newline. It drops unknown envelope fields, which DSSE says consumers ignore. The signature covers the PAE of the payload, not the envelope's encoding, so this rewrite keeps it valid. A producer that used URL-safe base64 or extra whitespace gets the same object as one that did not.
- **The evidence id is the SHA-256 of the canonical envelope bytes**, in lowercase hex (64 characters). `reef evidence show <id> --envelope | shasum -a 256` reproduces it. ed25519 is deterministic, so the same key signing the same payload gives the same envelope, the same id, and an idempotent add. SHA-256, not BLAKE3: these ids leave Reef (R4.07, federation in R4.12, sigstore tooling, a log entry), and the attestation ecosystem identifies envelopes by SHA-256. ADR 0011 is about object identities, which evidence ids are not; they do not change when the object backend does.
- **Size**: the envelope as received is at most 64 KiB, and the JSON nests at most 32 levels deep. Logs belong in artifacts.

### Signing in this ticket: a caller's ed25519 key

- **The attestor signs, and the daemon verifies.** A private key never reaches the daemon. The CLI signs with a key file the caller names (`reef evidence add --key`). R3.06's executor will sign with an R3.03 session key the same way. The daemon holds no evidence-signing key in this ticket.
- **ed25519 through `ring`**, already in the lockfile and the tree's only crypto provider. No new dependency.
- **Keys.** `AddEvidenceRequest.public_key` is the signer's DER SubjectPublicKeyInfo (44 bytes for ed25519), so the key carries its algorithm. The **key id** is the lowercase hex SHA-256 of that DER: what `openssl pkey -pubin -outform DER | shasum -a 256` prints, and the hint sigstore recommends. The envelope's `keyid` must equal it (`INVALID_EVIDENCE`, check `key_id`). That is a consistency check, not a security decision: verification uses `public_key`, never the hint. Small-order and non-canonical public keys are refused (`INVALID_EVIDENCE`, check `public_key`), using a fixed list of the eight small-order encodings plus a canonical-y check, which closes the gap between ring and `verify_strict`. Keys are recorded once per machine in `evidence_keys`.
- **What "verified" means before policy.** An evidence object's `signature` is `SIGNATURE_VALID` when all of these hold: its id is the SHA-256 of its canonical bytes; its one signature verifies over `PAE(payloadType, payload)` with the recorded public key; the envelope's `keyid` is that key's id; and every index column of the row (`tree_id`, `kind`, `result`, `target`, `started_at`, `finished_at`, `format`) equals what the verified payload says. The daemon checks this at add and again at every read, and a read takes every field of `Evidence` from the payload, never from the columns, so a row edited in the database, its envelope or its columns, shows `SIGNATURE_INVALID` with the payload's own values. A row whose `key_id` names no stored key, or whose columns hold values of the wrong type, still reads, as invalid (the same uid can edit the database; ADR 0027). Nothing in the API says "trusted": R3.07 evaluates trust, and R3.13 refuses on it.
- **Verification order**, following DSSE: decode the envelope, check the key, verify the signature over the PAE, and only then parse the payload as a Statement. Junk that is unsigned, or signed by a malformed key, never reaches the statement parser.

### Storage: rows in `reef.sqlite3`

The envelopes are small (about 1 to 2 KiB), authoritative, and not rebuildable. ADR 0003 and the design's storage table put the evidence index in the daemon's SQLite; this brief puts the envelopes there too, beside their index columns (the user's decision). Backups then include evidence with no change to ADR 0020, and an add is one transaction.

Migration `0007_evidence.sql`, which makes `SCHEMA_VERSION` 7:

```sql
-- R3.01: evidence objects (signed in-toto statements in DSSE envelopes), the keys that signed
-- them, and which changes they were added for. `envelope` is the canonical envelope; `id` is its
-- sha256. Every other evidence column is read from the envelope's payload at insert, an index
-- over it. Released migrations are never edited.
CREATE TABLE evidence_keys(id TEXT PRIMARY KEY,            -- sha256 of public_key, lowercase hex
             algorithm TEXT NOT NULL CHECK (algorithm IN ('ed25519')),
             public_key BLOB NOT NULL,                     -- DER SubjectPublicKeyInfo
             first_seen_at INTEGER NOT NULL);
CREATE TABLE evidence(repo_id TEXT NOT NULL, id TEXT NOT NULL,
             envelope BLOB NOT NULL, format INTEGER NOT NULL,   -- 1: urn:reef-vcs:evidence:v1
             tree_id TEXT NOT NULL, kind TEXT NOT NULL,
             result TEXT NOT NULL CHECK (result IN ('pass','fail','error')),
             target TEXT, key_id TEXT NOT NULL REFERENCES evidence_keys(id),
             started_at INTEGER NOT NULL, finished_at INTEGER NOT NULL,
             added_at INTEGER NOT NULL, added_by_agent TEXT, remote_token_id TEXT,
             PRIMARY KEY (repo_id, id)) WITHOUT ROWID;
CREATE INDEX evidence_by_tree ON evidence(repo_id, tree_id, kind, target);
CREATE INDEX evidence_by_added ON evidence(repo_id, added_at DESC, id);
CREATE TABLE evidence_links(repo_id TEXT NOT NULL, change_id TEXT NOT NULL,
             evidence_id TEXT NOT NULL, commit_id TEXT NOT NULL, linked_at INTEGER NOT NULL,
             PRIMARY KEY (repo_id, change_id, evidence_id),
             FOREIGN KEY (repo_id, evidence_id) REFERENCES evidence(repo_id, id)) WITHOUT ROWID;
CREATE INDEX evidence_links_by_evidence ON evidence_links(repo_id, evidence_id);
```

- **Rows are keyed by repository** (ADR 0003). The same envelope added in two registered repositories is two rows with one id. Keys are machine-wide, as remote tokens are.
- **Times** are unix milliseconds, as every other table's. `started_at` and `finished_at` are the claim's, truncated to milliseconds. The payload keeps the original text.
- **`added_by_agent`** is the request's `reef-agent` (R2.03). **`remote_token_id`** is the token of a remote caller (R2.08), as `workspaces.remote_token_id` records it. Both say who uploaded the evidence, not who attested it.

### Linked from the change

A jj change has no field Reef can write, and writing evidence ids into descriptions or trailers would rewrite commits. Two links, neither in jj:

- **By tree, always.** The evidence that applies to a revision now is the evidence on that revision's tree: `ListEvidence` with a `revision` resolves it to a commit, takes its tree, and reads `evidence_by_tree`. This is what landing uses (R3.13), and it needs nothing stored per change.
- **By change, when the adder names one.** `AddEvidenceRequest.revision` (optional) names the change the evidence was produced for. The daemon resolves it, refuses it when its tree is not the subject's (`EVIDENCE_TREE_MISMATCH`) or is conflicted (`CONFLICTED_REVISION`), and writes an `evidence_links` row with the change id and the commit id it resolved. A link outlives the commit it names. After the change's tree moves on, `ListEvidence` with `change_id` still lists the evidence, each object marked `current: false`, meaning it is not on the change's tree now. That is the history the proposal view (R3.31) and evidence transfer (R3.15: "accept evidence from the submitted tree") need. An executor adds by tree alone, and creates no link.

`Change` and `reef show` gain nothing in this ticket. Showing a change's evidence is the proposal view's first section after intent (R3.31). Summaries in `ListChanges` would cost a lookup per change, and tokens per line of brief output (#114).

### What survives what

| Event | Evidence objects | Links |
| --- | --- | --- |
| Describe, or a rebase that keeps the tree | Unchanged; still on the change's tree | Unchanged; `current` stays true |
| An edit, snapshot, or rebase that changes the tree | Unchanged; no longer on the change's tree | Unchanged; `current` becomes false |
| Abandon, undo (R2.03) | Unchanged. Evidence records no operation, so undo neither adds nor removes it | Unchanged; a link to a hidden change still lists |
| `reef ws gc` (jj and git GC) | Unchanged. The tree may leave the object store; `GetEvidence` still works, and `ListEvidence` by that tree id still answers | Unchanged |
| `reef backup` and `restore` | Copied and restored with the database | Same |
| `reef repo forget` | **Deleted** with the repository's other rows, in the same transaction (the user's decision). Keys stay | Deleted |
| A daemon upgrade | Kept; `format` says which reader to use | Kept |

Evidence is never deleted otherwise. A retention rule for evidence objects goes to R3.02 with the artifacts' ("Departures").

### No operation in the log

Adding evidence writes no jj operation. Evidence is an immutable object, not a change to the view: there is nothing for undo to revert, and an operation per evidence object would put more evidence than code into the log the design wants legible, since "evidence volume outgrows code volume at agent scale". `AddEvidenceResponse` has no `operation`, like `UploadScipDocuments`. ADR 0029 decision 12's list of exceptions gains `AddEvidence` and the `UploadScipDocuments` it had missed. Live notice of new evidence is not in this ticket: R3.05's progress travels over presence, and R3.09's lifecycle operations are where a proposal's evidence becomes an event.

### The API: `EvidenceService`, API revision 15

A new file `reef/api/v1/evidence.proto`:

```proto
// Evidence (R3.01, ADR 0055): signed in-toto statements in DSSE envelopes about a tree, stored
// content-addressed by the daemon. A signature that verifies says who signed, not that the
// claim is true or the signer trusted; policy decides that (R3.07).
service EvidenceService {
  rpc AddEvidence(AddEvidenceRequest) returns (AddEvidenceResponse) {
    option (reef.api.v1.access) = ACCESS_WRITE;
    option idempotency_level = IDEMPOTENT;
  }
  rpc GetEvidence(GetEvidenceRequest) returns (GetEvidenceResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
  rpc ListEvidence(ListEvidenceRequest) returns (ListEvidenceResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
}

enum EvidenceResult { EVIDENCE_RESULT_UNSPECIFIED = 0; EVIDENCE_RESULT_PASS = 1;
                      EVIDENCE_RESULT_FAIL = 2; EVIDENCE_RESULT_ERROR = 3; }
enum SignatureCheck { SIGNATURE_CHECK_UNSPECIFIED = 0; SIGNATURE_CHECK_VALID = 1;
                      SIGNATURE_CHECK_INVALID = 2; }

message EvidenceArtifact { string name = 1; string sha256 = 2; string uri = 3; string media_type = 4; }

message Evidence {
  string evidence_id = 1;            // full hex sha256 of `envelope`
  string tree_id = 2;
  string kind = 3;
  EvidenceResult result = 4;
  string target = 5;                 // empty: the whole check
  string key_id = 6;
  google.protobuf.Timestamp started_at = 7;
  google.protobuf.Timestamp finished_at = 8;
  google.protobuf.Timestamp added_at = 9;
  string added_by_agent = 10;
  repeated EvidenceArtifact artifacts = 11;
  repeated string change_ids = 12;   // changes it was added for, from links
  SignatureCheck signature = 13;     // checked at this read
  string predicate_type = 14;
  bytes envelope = 15;               // the canonical envelope; GetEvidence only
  bool current = 16;                 // ListEvidence with change_id: on that change's tree now
  string remote_token_id = 17;
}

message AddEvidenceRequest {
  string repo = 1; string workspace = 2;
  bytes envelope = 3;                // a DSSE envelope as JSON, at most 64 KiB
  bytes public_key = 4;              // the signer's DER SubjectPublicKeyInfo
  string revision = 5;               // optional: the change it is for; not snapshotted
}
message AddEvidenceResponse { Evidence evidence = 1; bool created = 2; }

message GetEvidenceRequest { string repo = 1; string evidence_id = 2; }  // full or a unique prefix of 4+
message GetEvidenceResponse { Evidence evidence = 1; }

message ListEvidenceRequest {
  string repo = 1; string workspace = 2;
  string revision = 3;               // its tree; `@` snapshots first unless skip_snapshot
  string tree_id = 4;                // or a tree directly; not both
  string change_id = 5;              // evidence linked to this change, on any tree
  repeated string kinds = 6; repeated EvidenceResult results = 7; string target = 8;
  repeated string key_ids = 9;
  string at_operation = 10; bool skip_snapshot = 11;
  int32 page_size = 12; string page_token = 13;   // int32, as every List RPC (lists_are_paginated)
}
message ListEvidenceResponse { repeated Evidence evidence = 1; string next_page_token = 2; }
```

Each element gets the full leading comment ADR 0029's checklist requires (meaning, unit, what empty means); the sketch above abbreviates. The rules:

- **`AddEvidence`**: checks in the order of "Verification order", then the tree (`Store::get_tree` on the read pool; `TREE_NOT_FOUND` when the repository does not hold it), then `revision` when set. The insert is one transaction: the key (insert, or repair a stored key row that differs: its id is the hash of its public key), the evidence (insert, or, when already stored, rewrite its envelope and index columns from the verified input where they differ, keeping the first add's `added_at`, adder and token), the link (insert or ignore). `created` is false when the object was already stored, repaired or not, and the response is otherwise the same: idempotent, as declared. So re-adding the genuine envelope repairs a row changed behind the daemon. `revision` resolves at head without a snapshot (`@` is the workspace's commit as last snapshotted): the CLI sends the commit id it just read, so no race with the watcher can make the link name a different tree from the one it signed.
- **`GetEvidence`**: by full id or a unique prefix of at least 4 hex characters (`db::MIN_PREFIX_LEN`), within `repo`, looked up as a range of the primary key (`id GLOB '<prefix>*'`, as the other tables' prefixes are), never a scan. Returns `envelope`.
- **`ListEvidence`**: at most one of `revision` and `tree_id`; neither means the whole repository. `change_id` is a full change id, in hex or reverse hex; anything else is `INVALID_CHANGE_ID` (metadata `change`), R2.02's reason. The CLI's `--change` takes any revision naming the change and sends its full id. The filters AND across fields and OR within one, as `ListSymbols`' do. Results are newest added first; the page token pins `(added_at, id)` (opaque base64url, as R2.01's tokens are). `page_size` is `int32` like every List RPC's (`reef-api`'s `lists_are_paginated` test requires it; negative is `INVALID_ARGUMENT`); it defaults to 50, capped at 200. `envelope` is left empty. A revision with a conflicted tree returns an empty page, not an error: no evidence can be on it. `key_ids` are full key ids (64 lowercase hex); anything else is `INVALID_ARGUMENT`, with a hint, since the CLI's text shows 12 digits and a prefix would match nothing. The filters run in SQL on the index columns, and each listed object is checked again against them on its verified payload: a row whose columns were changed so that SQL matches it, but whose payload does not, is left out of the page and logged.
- **The `Evidence` message is read from the stored envelope**, not from client input or the index columns: every field comes from the verified payload (from the payload as stored when it no longer verifies, from the columns only when it does not decode).

**Reasons** (new constants in `reef_api::error`, each documented on its RPCs, and each mapped in `error.rs`):

| Reason | Kind | Metadata | RPCs |
| --- | --- | --- | --- |
| `INVALID_EVIDENCE` | `INVALID_ARGUMENT` | `check`: one of `size`, `envelope`, `payload_type`, `signatures`, `public_key`, `key_id`, `statement`, `subject`, `predicate_type`, `predicate`; and `field` for a predicate field | `AddEvidence` |

`ListEvidence` also returns R2.02's revision reasons, `INVALID_PAGE_TOKEN`, and a failed snapshot's `SNAPSHOT_FAILED`; `AddEvidence` returns the revision reasons for `revision`. `SIGNATURE_INVALID` is its own reason, since a forged or corrupted signature is the case RX.02 and Phase 3's second exit criterion care about, and a caller may want to tell it from a malformed envelope. The hints say which check failed and what the format wants ("the envelope has 2 signatures; Reef evidence has exactly one"), and none has a `next` except `EVIDENCE_NOT_FOUND` (`reef evidence list`).

### The format crate: `reef-evidence`

A new crate with no jj-lib, gRPC, tokio or SQLite, like `reef-symbols` and `reef-broker`: the daemon, the client, R3.06's executor and the Phase 4 store all need the format, and the executor and the store should not have to link `reef-client` to get it. Contents:

- `Statement`, `Predicate`, `ResourceDescriptor`, `Envelope`, `Signature`: serde types for exactly the JSON above, deriving `schemars::JsonSchema` (for `reef schema`, below). `Predicate` keeps unknown fields in a `#[serde(flatten)] BTreeMap<String, Value>`, so a reader that is older than the producer still parses what it knows.
- `pae(payload_type, payload) -> Vec<u8>`.
- `KeyId::of(spki_der)`, `PublicKey::from_spki(der)` (algorithm check, small-order and canonical checks), `SigningKey::generate() -> (pkcs8_pem, spki_pem)`, `SigningKey::from_pkcs8_pem(text)` (v1 or v2, through `from_pkcs8_maybe_unchecked`, then a check that the derived public key signs and verifies once).
- `Claim` (the predicate fields as Rust values) with `fn statement(&self, tree: &TreeDigest) -> Result<Statement, Invalid>` and `fn sign(&self, tree: &TreeDigest, key: &SigningKey) -> Result<Envelope, Invalid>`, which writes the compact payload in fixed key order. Both refuse what the checker would (a time before 1970 or after 9999, a bad kind or target) and never panic: an executor calls them.
- `Verified::check(envelope_bytes, public_key) -> Result<Verified, Invalid>`: the whole checking order above, returning the canonical bytes, the id, the parsed statement and the index fields. `Invalid` has one variant per `check` value, so the daemon's reason metadata comes from the variant. One function, so the daemon at add, the daemon at read, the CLI and later executors check the same way.
- `const FORMAT: u32 = 1`, `PREDICATE_TYPE`, `PAYLOAD_TYPE`, `MAX_ENVELOPE_BYTES`.

`crate_graph` gains it: eleven members; `reef-evidence` depends on no Reef crate except `reef-error`, and reaches none of jj-lib, tonic, tokio or rusqlite. `reef-daemon` and `reef-client` depend on it.

### The CLI: `reef evidence add`, `list`, `show`, `key generate`

```
reef evidence key generate <path>
reef evidence add --kind <kind> --result pass|fail|error --key <pem> [-r <rev>] [--target <t>]
                  [--started <time>] [--finished <time>] [--artifact <path>]... [--annotation k=v]...
reef evidence add --envelope <file> --public-key <pem> [-r <rev>]
reef evidence list [-r <rev> | --tree <id>] [--change <id>] [--kind <k>]... [--result <r>]...
                   [--target <t>] [--key <key id>]... [--limit <n>]
reef evidence show <id> [--envelope]
```

- **`add` signs locally.** `--kind`, `--result` and `--key` are checked by the command, not marked required for clap (`reef schema`'s constraint model has no "required unless"); without them, or `--envelope` and `--public-key`, it is a usage error. It resolves `-r` (default `@`, which needs a workspace as every `@` does) with `GetChange`, which snapshots first. A conflicted tree is refused with the daemon's own reason (`CONFLICTED_REVISION`), sent before anything is signed. It builds the claim, signs it with the key, and sends `AddEvidence` with `revision` set to the full commit id it read. `--started` and `--finished` take RFC 3339 or `history`'s "a duration ago" form (`history::when`); both default to now. `--artifact` hashes a local file (SHA-256, streamed) into an artifact named by the file's base name, with no `uri`; the file is not uploaded (R3.02). `--annotation` sets string values under `annotations`.
- **`--key`** is an ed25519 private key in PKCS#8 PEM (v1 or v2), as `reef evidence key generate` or OpenSSL 3's `openssl genpkey -algorithm ed25519` writes. The CLI refuses a key file that its group or others can read (mode `& 0o077`), as ssh does, with the hint `chmod 600 <file>`.
- **`key generate <path>`** (the user's decision, 2026-11-05: macOS's LibreSSL cannot make ed25519 keys) makes a key with ring's `Ed25519KeyPair::generate_pkcs8`, writes it as PKCS#8 v2 PEM (`-----BEGIN PRIVATE KEY-----`) created with mode `0600` (`OpenOptions::mode`, `create_new`, so an existing file is refused, never overwritten), and writes the public key beside it as `<path>.pub` (SPKI PEM, the form `add --envelope --public-key` takes). It prints the key id; `-o json` is `EvidenceKey { key_id, path, public_key_path }`. It talks to no daemon and records nothing: a key is recorded in `evidence_keys` when it first signs evidence. It is a local key for scripts and trials until R3.03's session keys, and its help says so.
- **`add --envelope`** sends an envelope made elsewhere, with the signer's public key as PEM (`-----BEGIN PUBLIC KEY-----`). It is how a script or another tool attests before R3.06 exists.
- **`list`** prints one line per object in text: `<id 12> <kind> <result> [<target>] key <key id 12> <duration> <added, relative>`, and `(not current)` for a link whose tree moved on. Without `-r`, `--tree` or `--change`, it lists the repository's evidence, newest first. Inside a workspace, `-r @` is not implied: `reef evidence list` is the repository's list, and `-r @` is the current change's.
- **`show`** prints the fields, the statement exactly as signed (the payload's bytes, keys in their order), and `signature: valid` or `invalid`. It exits 0 either way: `invalid` is data about a stored object, not a failure of the command. `--envelope` writes the canonical envelope bytes and nothing else, so `| shasum -a 256` gives the id and the file feeds `cosign verify-blob-attestation` or any DSSE verifier.
- **JSON**: `reef_client::json::Evidence` (every field of the message, `evidence_id` as `id`, plus `duration_ms`, the statement as a JSON object, and `envelope` as a JSON object rather than base64 in `show -o json`), `EvidenceAdded { evidence, created }`, and the list as a JSON array of `Evidence`, as every list command prints; `--limit` (default 100, 0 for all) cuts it, with the cut noted on stderr as `reef log` notes its own. The brief view `brief.Evidence` keeps `id`, `kind`, `result`, `target` and `key_id`, leaving `target` out when empty (ADR 0045), and `signature` only when it is not `valid`, so a tampered row still shows on a pipe. The piped default is brief for `list` and the full JSON, compact, for `add` and `show`.
- **`--help`**: `evidence` joins the "Also:" line, one word. The root help was 509 bytes against `root_help_fits_its_budget`'s 512, so the line's closing sentence becomes "`--help-all` has more." (from "describes each.") to fit. The agent guide gets nothing until evidence decides something for an agent (R3.13).
- **Advice**: rows in `cli/advice.rs` for each new reason a command can hit.

### `reef schema`, MCP, SDKs, web UI

### Stability and versioning

This is the promise executors are built against, and ADR 0055 states it:

1. **Format 1 is fixed**: Statement v1, `payloadType` `application/vnd.in-toto+json`, one signature, the subject rule, Reef's v1 predicate type and its fields as above, SHA-256 ids over the canonical envelope, and the SPKI key ids.
2. **Fields are only added.** A later Reef may add optional predicate fields to v1. An added field never changes what an existing field means, and a v1 reader that ignores it reaches the same decision it would without it. Readers ignore fields they do not know, as in-toto requires. Producer data goes in `annotations`, where Reef will never add a field.
3. **A change of meaning is a new predicate type** (`…:v2`), accepted beside v1. A daemon never rewrites a stored payload, and never drops support for reading a format it once accepted.
4. **Ids never change.** An evidence id is SHA-256 of the canonical envelope for as long as Reef exists. A new canonical form would be a new `format`, with its own id rule and its own column value.
5. **Until 1.0** (Reef is pre-1.0), a breaking change to format 1 still needs an ADR that supersedes 0055 and a migration of stored rows. This brief does not plan one.

## Implementation notes

- **Order**: `reef-evidence` with tests 1 to 7 first. That is the format; the user's decisions below fix its open choices. Then the migration and `db/evidence.rs` with test 8; then the service with tests 9 to 15; then the client and the CLI with test 16; then the schema, MCP and help (17 to 19), and the documents.
- **Duplicate keys**: serde's derived `Deserialize` refuses a duplicate field of a struct but not of a map or a `Value`, and `Predicate`'s flatten map and `annotations` are maps. Run one pass over the bytes before any typed parse with a `serde::de::Visitor` that walks objects with a `HashSet` of keys per level, and counts depth. It costs one extra parse of at most 64 KiB.
- **Base64**: decode with `base64`'s `STANDARD` and `URL_SAFE`, each with padding indifferent, trying standard first; encode canonical output with `STANDARD`. Refuse trailing garbage and non-canonical trailing bits, so one string has one decoding.
- **Small-order keys**: the eight encodings are well known (the identity, the point of order 2, and the order-4 and order-8 points with both signs). Write them as constants with a comment citing their origin, and test each one. The canonical-y check compares the decoded y against p = 2^255 − 19.
- **The tree check** is `Store::get_tree(RepoPathBuf::root(), &id)` in a read job, behind `reef_lib::jj::files::tree_presence` (the daemon reaches jj-lib only through `reef-lib`, which also gains `tree_id_hex_len`, `commit_tree_id` and `change_tree_ids`). `NotFound` is `TREE_NOT_FOUND`. A blob id passed as a tree fails `try_into_tree` and is reported as `TREE_NOT_FOUND` too, with the message saying the object is not a tree: a `ReadObject` error with no I/O error in its chain.
- **Times**: parse with the same RFC 3339 code the history query uses (`humantime::parse_rfc3339`), accept only `Z` (humantime also takes `+00:00`, which is refused), and keep the original text in the payload. Reef's own producer writes times to the millisecond (`2026-11-05T10:00:00.000Z`).
- **Never await jj-lib on a tokio worker** (R2.03's rule); SQLite stays on the async side as elsewhere. `AddEvidence` does verification and the tree check before taking the database lock, and holds the lock only for the insert transaction.
- **Linux**: no `cfg(target_os)` in this ticket. Run `CARGO_BUILD_WARNINGS=deny cargo build --workspace --all-targets` and clippy in the privileged `ubuntu:24.04` container anyway, since `db/repositories.rs` and `server.rs` are touched and the Linux-only daemon tests construct `TestDaemon`.

## Out of scope

- **Trust**: which keys or identities a repository trusts, and refusing on it (R3.07, R3.13). Session keys, keys bound to operator or CI identities, revocation, and sigstore keyless signing (R3.03). A daemon-held signing key.
- **Artifacts**: storing logs and outputs, fetching them by digest, and retention for artifacts and for evidence objects (R3.02).
- **The executor**: the protocol (R3.05), the reference executor and its sandbox (R3.06), and `reef evidence run -- <command>`, which would be a small executor without a sandbox.
- **Per-target composition** (R3.19) and the behavioral diff kind (R3.22): this ticket stores `target` and an open kind.
- **Provenance** (R3.04). It may reuse this envelope, these key ids, and the `evidence_keys` table, with its own predicate type and a `gitCommit` subject; R3.04 decides that.
- **Evidence in `Change`, `reef show`, `reef log`, the proposal view** (R3.31) and the web UI. MCP tools for evidence. Live events when evidence is added (R3.05's presence and R3.09's operations).
- **Deleting evidence**, multi-signature envelopes, predicate types other than Reef's v1, other key algorithms, OpenSSH-format keys, and key storage beyond a file (keychains and agents are R3.03's).
- **SDK helpers** to build and sign evidence.
- **Sharing evidence across registered repositories** that hold the same tree; R3.18's cache may look across them later.

## Risks

- **The format is the irreversible part.** Every executor written against it, and every row stored, depends on the predicate type URI, the field names, and the id and key id rules. Questions 1 and 4 must be answered before implementation starts, and test 5's documented bytes pin the canonical form.
- **Self-signed evidence will exist before any policy.** Anyone can add evidence that shows `signature: valid`. Until R3.07, a reader who takes `valid` for "trusted" is wrong, and the CLI's text must not invite it: it prints the key id, never a name, and the docs say what `valid` means. RX.02 reviews it.
- **ring is less strict than `verify_strict`**, and the gap is closed by Reef's own key checks. Test 2 pins the list. A future ring that changes its checks does not loosen Reef's.
- **SHA-1 trees.** The subject is a SHA-1 git tree id while the repository is on jj's git backend (ADR 0011's known weakness). A chosen-prefix collision on a tree would let one claim cover two trees. The `gitTree` key states the algorithm, and Phase 4's backend changes the key.
- **Growth.** About 1 to 2 KiB per object, never deleted until R3.02. At 10,000 objects a day that is 10 to 20 MiB a day in `reef.sqlite3` and in every backup. R3.02's retention is the answer; until then it is S-52.
- **Forget deletes evidence.** It is ADMIN, refused while a workspace is active, and rare, but nothing undoes it except a backup.
- **`schemars` and flatten**: the `Predicate`'s flatten map may make schemars emit `additionalProperties`, which is correct here. Test 7 checks what it emits against real payloads.

## Choices this brief made, and why

- **Tree, not commit**, because the design keys evidence by tree hash, landing compares trees, and rebases change commits.
- **One predicate with a kind**, rather than in-toto's `test-result` plus others, because policy reads one shape, and `target` and `error` have nowhere to go in `test-result`.
- **One signature per envelope**, because one attestor per object is the data model's and a sigstore bundle requires it.
- **The payload as signed and the envelope canonical**, because DSSE avoids canonicalization and a stable id still needs a fixed form.
- **SHA-256 for ids and key ids**, because these leave Reef and the attestation ecosystem uses them, and because `shasum` reproduces them.
- **ring, no new crate**: it is already the tree's only crypto provider, and the in-toto and DSSE crates are unmaintained, not conformant, or need aws-lc or openssl.
- **The caller signs**, because the attestor is whoever ran the check, and the daemon did not.
- **Envelopes in `reef.sqlite3`**, because they are small and authoritative, and backups then cover them.
- **Links stored by change, binding by tree**, because landing needs the tree and the proposal view and evidence transfer need the change's history.
- **No operation, no MCP tools, nothing in `Change`**, to keep the log legible, `tools/list` within its budget, and the ticket M. Each has a named later ticket.
- **A format crate**, because the executor and the store need the format without the client.

## What later tickets inherit

- **R3.02** stores artifact bytes under the `sha256` digests the predicate records, and gives evidence objects a retention rule (likely: keep while the tree is reachable or a link's change is open, plus a window). It deletes rows only with the repository's write lock held, since evidence is in `reef.sqlite3`.
- **R3.03** issues session keys that `reef-evidence` signs with unchanged. It adds verification material beside `public_key` (a certificate that binds a session key to an identity, or a sigstore bundle), adds identity columns or a table beside `evidence_keys`, and answers "who is key K" in `Evidence`. It may adopt `sigstore-types` for the bundle once keyless is added, and must keep the ring-only rule or change it by ADR.
- **R3.04** decides whether provenance reuses this envelope and key table with its own predicate type and a `gitCommit` subject.
- **R3.05** puts envelopes as bytes in the executor response, and reuses `Evidence` and `EvidenceResult` in its messages. The request's "tree hash" is the `gitTree` value. Evidence kinds expected are the `kind` vocabulary. An executor's `error` result is `EVIDENCE_RESULT_ERROR`.
- **R3.06** signs with `reef-evidence` and an R3.03 key, and adds by tree with no `revision`.
- **R3.07** evaluates CEL over `Evidence`: `kind`, `result`, `target`, `key_id` (and R3.03's identity), `tree_id`, `finished_at`, and `signature`, which must be `VALID`. The submitting agent's own key is excluded by policy, not by the format.
- **R3.13** verifies that each evidence object's `tree_id` is the submitted tree, and refuses an `INVALID` signature with a structured reason (Phase 3's second exit criterion). **R3.15** finds the submitted tree's evidence through the change's links. **R3.14** treats `error` as "no verdict", never as a culprit.
- **R3.19** defines how `target` values compose and which kinds take them. **R3.22** registers `behavioral-diff`, with additive predicate fields or artifacts for the outcome changes.
- **R3.31** renders a change's evidence from `ListEvidence` with `change_id`, current first, and shows the key, never a self-declared name. **R2.16 or R3.37** can join evidence to changes through `evidence_links` or by tree.
- **R4.07 and R4.12** move evidence between stores as canonical envelope bytes with their ids, which never change. **R6.03** starts from ADR 0055 and `docs/evidence.md`.
- **RX.02** reviews S-48 to S-53, the parser, and the key checks.
- **Every later change to the predicate** follows the stability rules: optional fields only, or a new predicate type.

## Departures from dev-phases.md

- **The row's "attestor" is the signing key**, not a field of the claim; R3.03 binds keys to identities. The row's "snapshot hash" is the snapshot's tree hash. `dev-phases.md`'s R3.01 row is reworded to say both.
- **R3.02 also owns the retention of evidence objects**, since R3.01 stores them with no deletion. Its row gains that.
