# R3.33 Triage inbox

Phase 3 · Size a small L (decision 5) · API revision 44, schema 28 (`0030_inbox_marks.sql`), ADR 0088, threat rows S-261 to S-265 · Folds in #145 (workspace attention publishes no event) and #362 (automatic status and evidence publish no event) · Depends on: R3.31 (the proposal page the inbox opens, its Answer box, the Proposals tab it replaces), R3.32 (help requests), R2.09 (the operation stream), and builds on R3.09 (lifecycle rows and transition `seq`), R3.12 (instructions and their states), R3.27 and R3.28 (conflict assignments, `UNOWNED` and `BLOCKED`), R3.45 (`AutomaticStatus`), R2.11 and R3.05 (daemon presence entries), R2.20 (workspace attention words) and R2.21 (held rows behind a count, `coalesce.ts`) · Unblocks: R3.39 (desktop notifications for the needs-you-now bucket), R3.40 (the phone's inbox and Web Push), R4.13 (the hosted inbox)

## Context

The design's human interface: "**Handle exceptions.** A triage inbox is the home page, not a feed. It has three buckets: needs you now (policy requires sign-off, a conflict nobody owns, an agent asking for help through an explicit help request that records what it tried and what it needs, a batch that failed bisect), watching (proposals you asked for, in flight), and landed since you last looked (a digest, not a list). Attention is the scarce resource and routing it is the interface's main job." Its live rules: nothing reorders under the cursor, new items arrive behind a visible count, every live element links to its cause, coalesce, never drop.

Reef's users are mostly agents. The person on this page runs a fleet of them, and the page exists so they can open one place and see what is waiting on them, across every repository, without reading a feed. Since R3.45 agents propose, collect evidence and land alone; since R3.32 they can stop and ask. Nothing yet tells the person that an agent is asking, that a proposal waits on their sign-off, or that a conflict is blocked for them. Three Phase 3 exit criteria wait on this ticket: the needs-you-now bucket live (and notified by the desktop app, R3.39), a help request appearing there and the person's reply resuming the agent's session, and the phone approval (R3.40).

Every earlier ticket left this one a seam:

- **R3.32**: "R3.33 lists open help requests (`ListComments` with `help_states: [OPEN]`, any change) as needs-you-now, live from `OPERATION_KIND_COMMENT` events whose `help_to` is `OPEN`, and answers with `CreateComment` replying to one."
- **R3.12**: "R3.33 builds 'needs you now' from unanswered help requests and the 'watching' bucket from instructions in flight."
- **R3.27 and R3.28**: R3.33 lists `UNOWNED` assignments ("a conflict nobody owns") and `BLOCKED` conflicts under needs-you-now.
- **R3.45 and R3.07**: R3.33 shows `AutomaticStatus`; "`needs` with sign-offs is the reviewer's queue".
- **R3.09**: R3.33 builds its buckets from `ListProposals`, `ListTransitions` (`recorded_after`) and the operation stream; `ListTransitions` is "R3.33's 'landed since you last looked'".
- **R3.11**: the inbox reads `ProposalEntry.dependencies` and `missing_dependency` conflicts.
- **R3.31 and ADR 0086**: "R3.33's inbox replaces the tab's list; the proposal page stays." The tab already uses the inbox icon.
- **R2.21**: "Since you last looked" was left to R3.33 with the user (its decision 5); the inbox "reuses the held-count rule and `coalesce.ts`".
- **ADR 0005**: the desktop shell exists so the triage inbox reaches a person promptly, and ships only once the inbox has real items.

- **`ListProposals` costs more than it looks.** It brings conflict assignments up to date first (`assign::look`, which can record CONFLICT_ASSIGNMENT operations), waits for pending lifecycle rows, reads every row's change at head from jj, and runs two queries per row (`service/changes.rs:407-514`). It never evaluates policy: `automatic` is an in-memory lookup.
- **`AutomaticState.OFF` hides sign-off needs.** A destination with no valid policy, or `checks = "change"` without `automatic`, has no status (`automatic/mod.rs:450-460`). The default is `checks = "batch"` (`reef-policy/src/format.rs:490`), which judges every proposal.
- **The status already has a change detector.** The automatic task computes which proposals changed key or state just before `set` (`automatic/mod.rs:770-779`), to instruct their agents. The key covers the evidence on the proposal's trees (R3.45), so new evidence changes it.
- **Daemon presence entries are the precedent for in-memory state.** `PresenceHub::publish_daemon` and `end_daemon` under a `DaemonKey` (`presence/hub.rs:33-42, 331-360`) serve leases, editing, progress and executor jobs (`PRESENCE_KIND_JOB`, R3.05). The web UI keeps one operation stream and one presence stream per browser, shared across tabs by a leader (`web/src/live/share.ts`); a third stream would compete for HTTP/1.1's six connections.
- **The attention writer is one SQL function** with nine callers. One of them is in the snapshot commit path (`workspace/snapshot.rs:1236`), which #357 owns. A notifier inside `Db::set_workspace_attention` covers every caller without touching that file.
- **The web session is not a person.** `web::Caller` is a session digest (`web/mod.rs:204-210`); sessions live in memory, end at restart or after 24 h idle, and every `reef ui` mints a new one. Every web write already records the **default person identity** through `identity_for` (`lifecycle/mod.rs:936-965`), and agents act for that identity too (their provenance sessions take it, `provenance/session.rs:206-218`). On a one-person daemon, "you" can only mean the default person.
- **Browser storage does not survive a daemon restart.** The UI's origin is `http://localhost:<port>` and `[ui] listen` defaults to port 0, a new port at every start (`config.rs:1300-1311`; ADR 0085 says so). A "last looked" in `localStorage` would reset at every restart, and the desktop shell's webview and the phone have their own storage.
- **Nothing records "a person asked for this proposal".** `lifecycle.proposed_by_agent` names the agent; transitions and comments name the identity, which is the default person for agents and people alike.
- **The bundle**, from the build on disk (raw bytes, the budget test's measure): `/` 249,262; proposals 324,953; proposal 371,361; smartlog 356,704; all assets 520,359 of 614,400. The total is the tighter limit: about 94 KB of headroom.

### Spikes run for this brief

The automatic task already holds `before` and the new `statuses` at the publish point, and `AppState` holds the hub.

### Where the inbox lives (decision 1)

**The inbox is the home page.** `/` shows the inbox across every registered repository, with the repository list it shows today kept below it. Inside a repository, an **Inbox** tab takes the Proposals tab's place and shows the same page for that repository. `/repos/:repo/proposals` redirects to the tab; `/repos/:repo/proposals/:change` (the proposal page) stays. `Proposals.tsx` and `ProposalsModel` are deleted (the list's hold-in-place logic moves into the inbox model).

### The buckets (decision 4)

One rule table in the daemon (`inbox::rules`), each row a source, a test that admits an item, its bucket, a reason and the words. Items are keyed `kind:repo:object` (for example `help:<repo>:<comment id>`), stable across reads, so a client can tell a new item from one it has shown. That key is the seam R3.39's notifications diff on.

| Item | Bucket | Reason | Opens |
| --- | --- | --- | --- |
| An open help request | needs you now | `HELP` | inline Answer box; the proposal page or change detail |
| A proposal whose automatic status is `NEEDS` with a `signoff` need | needs you now | `SIGNOFF` (which rule, which attestors) | the proposal page |
| A conflict assignment `UNOWNED` | needs you now | `CONFLICT_UNOWNED` | the change; `reef conflict assign --queue` or `take` as text |
| A conflict assignment `BLOCKED` (tier `ask`, or attempts spent) | needs you now | `CONFLICT_BLOCKED` | the change; `reef conflict allow` as text |
| A proposal whose last transition came back from landing (cause `LANDING`, to `PROPOSED`) and that has not changed since | needs you now | `RETURNED` (the landing's reason: checks, bisect culprit, conflict) | the proposal page |
| A proposal whose status is `NO_EXECUTOR` | needs you now | `NO_EXECUTOR` | `reef executor run` as text |
| An active workspace with `attention` | needs you now | `ATTENTION` (R2.20's words) | the workspace pane |
| An instruction by a person `AWAITING_CONFIRMATION` | needs you now | `CONFIRM` | the proposal page's Confirm |
| Any other open proposal (`PROPOSED`, `QUEUED`), with its automatic sentence | watching | its state | the proposal page |
| An instruction `PENDING`, `DELIVERED` or `RUNNING` | watching | its state, and "nobody has picked it up" when its target session was last seen over an hour ago | the change |
| Changes landed since the mark | landed since you last looked | | the digest |

A proposal that is in needs-you-now is not also in watching. A `NEEDS` status for a reason the agent fixes (a failed check, a rule, a conflict of its own change) stays in watching with its sentence: on a destination that lands automatically, the daemon already instructs the agent (`docs/comments.md`, "The daemon's own instructions").

"Watching" is every open proposal and instruction in scope, not only "proposals you asked for": nothing records that a person asked for one, and on a one-person daemon every agent acts for the same identity. A filter by asker is R4's, when a store serves several people.

### The read: `InboxService.GetInbox` (decision 5)

`GetInbox { repo }` (READ; empty `repo` is every registered repository) returns `needs_you_now` and `watching` as `InboxItem`s, newest first, each bucket capped at 200 with a `total`, and `landed` as one `LandedDigest` per repository: the count since the caller's mark, counts by agent, the newest 10 landings (change id, first line, agent, when), `through_seq` (the newest transition counted) and `since` (the mark's time; with no mark, the last 24 hours). Each `InboxItem` carries its `key`, `repo_id`, `reason`, `since` and one of the records the existing reads return (`ProposalEntry`, `Comment`, `ConflictAssignment`, `Workspace`), so a client renders it with no second read.

It is built from the same functions the per-source reads use: `list_proposals`'s entry assembly moves into a function both call; the assignment, comment, workspace and transition reads are the existing `Db` queries. A repository that fails to read is reported in `errors` (repo id, reason) and the others still return.

`reef inbox` prints the three buckets (text, or the brief JSON when piped), with `--repo`; it reads and never moves the mark. Not an MCP tool: `tools/list` is at its budget, so `GetInbox` and `MarkInboxSeen` are `NOT_TOOLS` rows, and an agent supervising others runs `reef inbox`.

### Live (folds in #362 and #145; not #330)

The page re-reads `GetInbox`, paced (`live/paced.ts`, one read in flight), when the shared operation stream reports an operation of kind COMMENT, TRANSITION, LAND, BATCH, CONFLICT_ASSIGNMENT, CREATE_WORKSPACE, RELEASE_WORKSPACE or UNDO in a repository in scope, and when the shared presence stream reports a change to an entry of the two new kinds. Snapshots alone do not trigger a read. Two daemon presence kinds close the gaps:

- **`PRESENCE_KIND_AUTOMATIC`** (#362): one entry per open proposal the automatic service judges, keyed `DaemonKey::Automatic(repo, change)`, carrying its `AutomaticStatus` and the change id; replaced when its key or state changes (new evidence on its tree changes the key), ended when it leaves review. Published beside the existing change detector in the automatic task. The proposal page reads again on its entry and drops its 10 s poll for any proposal whose status is not `OFF`; an `OFF` proposal (no policy judges it) keeps the poll, because nothing evaluates it to notice evidence. A harness can wait on its proposal's status the same way.
- **`PRESENCE_KIND_ATTENTION`** (#145): one entry per active workspace that needs attention, keyed `DaemonKey::Attention(workspace)`, carrying the `Attention` value; published or ended by a task woken from a notifier inside `Db::set_workspace_attention` (and the create path), which reconciles the attention rows against the live entries. No call site in the snapshot path changes. The fleet panel refreshes on it too, which is #145's own complaint. `watch_state` stays without an event: it is a transient "waiting" or "attaching" computed when a response is built, and a watch that fails becomes `ATTENTION_WATCH_FAILED`, which this covers.

Presence, not operations, because both are in-memory or derived state that the reads rebuild: an operation per status change would bloat the log and replay nothing (ADR 0037). A subscriber that reconnects re-reads, as every page does.

**#330 (overlap start) stays out.** Overlaps are not an inbox bucket, and its hook runs after every snapshot, next to #357's code.

### Held in place, with a count

Each bucket holds its rows: the first read fills it; later reads put new keys behind a count in the bucket's header ("2 new · Show"), and an item that left (answered, signed off, landed) keeps its row, dimmed with what happened, until the person shows the new ones or reloads. Nothing reorders under the cursor; `useScrollAnchor` keeps the row under the pointer or focus fixed when "Show" inserts rows above it. The page title carries the needs-you-now count ("(3) Inbox · Reef"), which is also the first piece of R3.39's seam: `inbox/needs.ts` exposes the set of needs-you-now keys and the keys new since the last read, which the shell turns into notifications.

### Since you last looked (decisions 2 and 3)

**The mark is the daemon's, one per person and repository**: a table `inbox_marks (identity_id, repo_id, seq, seen_at)` in `0030_inbox_marks.sql`, where `seq` is the newest `lifecycle_transitions.seq` the person has seen. A local web session and the socket mark for the default person (as every web write already records it); a remote token marks for the person identity it links, and one that links none is refused.

`MarkInboxSeen { marks: [{ repo, seq }] }` (WRITE) only moves a mark forward, never past the repository's newest committed transition, and records no operation (ADR 0029 decision 12's exceptions, as R3.43's writes). It joins the web allowlist as row `seen` (no other field to abuse) and `remote/rules.rs`.

**The mark moves when the person has looked.** When a repository's digest has been on screen for 3 seconds in a visible tab, the page marks it seen up to the newest landing it showed. The digest stays on screen as it was for the rest of the visit, and landings during the visit join it live; the next visit starts from the new mark. `reef inbox` never moves it.

### Actions

- **Answer** a help request inline: R3.31's Answer box, moved into a shared component, through the existing `comment` row. This is the exit criterion's path: the answer is an instruction replying to the request, routed to the asking session (R3.32).
- **Open** everything else: a sign-off opens the proposal page, where Accept is (one passkey touch; no Accept in the list, since the page shows the evidence and diff the person signs). Conflict and executor items show the `reef` command that acts, since those writes are not on the web allowlist.
- No new web write besides `seen`.

### Threat model rows (S-261 to S-265)

- **S-261 A leaked session moves the mark.** It can mark every repository seen, hiding the digest until more lands. It cannot hide a needs-you-now item (they come from state, not the mark) or a landing (the activity feed and `reef land` history keep them), and the mark only moves forward to a seq that exists.
- **S-262 Agent text in the inbox.** Help requests, descriptions, workspace purposes and agent names are agent-written and rendered as text, never HTML (S-33), in every new component.
- **S-263 An agent floods needs-you-now.** Bounded by R3.32's limits (one open request per change and session, 256 per repository), the caps with totals, and R3.39's notifications coalescing by key.
- **S-264 The new presence kinds.** They carry the same facts `ListProposals` and `ListWorkspaces` return, to the same subscribers (socket, web session, remote token with read scope), and no client can report them.
- **S-265 The read across repositories.** A remote read token sees every repository's inbox, as it already sees each source; `GetInbox` is bounded by the caps and reads each repository once.

## Risks

- **#357 runs beside this ticket** in the snapshot and adopt code. This ticket touches neither; the attention notifier is in `db/workspaces.rs`, and no snapshot call site changes.
- **The read's cost on a large fleet.** `GetInbox` runs each repository's `ListProposals` assembly, including its jj read; paced to one read in flight and triggered only by the listed kinds. Measured in the implementation on this repository's own daemon, and bounded in the brief JSON.
- **A web write.** `seen` is security-sensitive by the R3.31 lesson; each review round attacks it as a leaked session would.

## Choices this brief made, and why

- **One definition in the daemon**, because the web page, `reef inbox`, the desktop shell (R3.39) and the phone's push from the daemon (R3.40) must agree on what needs a person; a definition in TypeScript would be written again in Rust for push.
- **Presence for the gaps**, because the state is in memory or derived, the web already holds one presence stream, and the reads rebuild it after a reconnect.
- **Keys, not positions**, so held rows, notifications and the title count all diff the same thing.
- **Answer inline, everything else opens**, because answering is short and is the exit criterion, and a sign-off needs the page that shows what it signs.

## Decisions for the user

**Answered 2026-11-20**, each as recommended.

1. **Where the inbox lives.** *Recommended*: the home page `/`, across every repository, with the repository list below it, plus a repository Inbox tab in place of Proposals. Alternative: only the repository tab in place of Proposals, with `/` unchanged.
2. **Where "since you last looked" is kept.** *Recommended*: in the daemon, one mark per person and repository (a local web session marks for the default person), set by a new web write that only moves it forward. Alternative: the browser's local storage, which needs no web write but resets at every daemon restart (the UI's port changes) and differs between the browser, the desktop app and the phone.
3. **When the mark moves.** *Recommended*: automatically, once a repository's digest has been on screen for 3 seconds; it stays shown for the rest of the visit. Alternative: only when the person presses "Mark seen".
4. **What counts as needs-you-now.** *Recommended*: help requests, sign-offs needed, conflicts unowned or blocked, proposals a landing returned, proposals with no executor, workspaces needing attention, and the person's unconfirmed instructions; a failed check or rule the agent fixes stays in watching. Alternative: every proposal the automatic service says `NEEDS` something, whatever the reason.
5. **How much this ticket builds.** *Recommended*: the daemon's `GetInbox` and `reef inbox`, and the two presence events that fold in #362 and #145 (a small L). Alternative: the web page assembles the inbox from the existing per-repository reads and polls for sign-off and attention changes (M, no new read, but R3.39 and R3.40 must define the buckets again).
