# R3.32 Help requests from agents

Phase 3 · Size M, at its low end (decisions 3 to 6 take the row's S there) · Depends on: R3.12 (comments, instructions, `reply_to`, routing by client session, `ClaimInstruction` and its three clients, the comment write path and sweep), R2.13 (`reef mcp`, `NOT_TOOLS`, the `tools/list` budget), and builds on R3.03 (identities and token links), R3.04 and R3.44 (provenance sessions and their declared `client_session`), R3.09 (lifecycle rows), R3.25 (conflict objects and their ids), R3.27 (resolver assignments), R3.45 (the automatic status and `mark`) and #262 (`ChangeStep`) · Unblocks: R3.33 (the "agent asking for help" entries of needs-you-now), R3.28 (its "ask before attempting" tier and a spent attempt cap point at a help request), R3.40 (help requests and replies at phone width)

## Context

The design's Human interface section puts "an agent asking for help" in the first bucket of the triage inbox, the one that "needs you now". The row says what the agent sends: "a reason, the change or conflict it concerns, what it tried, and an optional question", and how it ends: "resolved by a human reply that resumes the agent's session the way an instruction does".

Since R3.45, landing runs with nobody asking. An agent can propose, collect evidence and land alone. What it still cannot do is stop and ask a person. Today an agent that hits a product decision, a conflict it should not resolve, a missing credential or an ambiguous task either guesses, or ends its turn with a question printed into a transcript that nobody running a fleet reads. Reef already knows which session made which change (R3.04, R3.44) and already delivers a person's words to that session (R3.12). The missing piece is the other direction.

R3.12 left the seam on purpose. Its brief: "R3.32 adds `COMMENT_KIND_HELP_REQUEST`, written by an agent through a WRITE RPC or this one, and resolved by an instruction with `reply_to` naming it; the reply resumes the session through the same claim." Its proto comment says the same (`CommentKind`, "R3.32 adds COMMENT_KIND_HELP_REQUEST"). `docs/comments.md` lists it under "What later tickets add".

So this ticket builds:

1. **The help request**: a third comment kind, written by the agent on a change (and, for a conflict, on the conflicted change with the conflict's ids), with a reason, the text of what is wrong, what it tried, an optional question, and the asking session.
2. **Its lifecycle**: open, answered, withdrawn, recorded as comment events in the operation log.
3. **The answer**: an R3.12 instruction whose `reply_to` names the help request, routed to the asking session rather than the change's proposer, and confirmed as written (decision 1). It reaches the agent through R3.12's claim, unchanged: `reef comment next`, the harness hooks, and `reef mcp`'s `wait_for_operations`.
4. **What waits on it**: `reef here` says to wait for the answer (decision 4), and automatic landing holds a proposal whose author asked for help (decision 3).
5. **The surface**: `CreateComment` with the new kind, one new RPC (`WithdrawHelpRequest`), `reef ask` and `reef comment answer|withdraw`, an MCP tool `ask_for_help`, feed sentences in the web UI, and the documents.

### What a help request is (decision 2)

A comment of kind `HELP_REQUEST` on a change. Every R3.12 field keeps its meaning: `change_id`, `round`, `commit_id` (what the agent saw), an optional anchor (a path and lines it is asking about), `author`, `text`. It adds:

| Field | Meaning |
| --- | --- |
| `reason` | `DECISION` (a choice that is a person's: product, design, scope), `CONFLICT` (the change's conflict: not allowed, not clear how, or out of attempts), `BLOCKED` (something outside its reach: access, a credential, a broken environment, a check it cannot fix), `UNCLEAR` (the task or an instruction is ambiguous or contradicts itself), `OTHER`. Default `OTHER`. |
| `text` | What is wrong, in the agent's words. Required, R3.12's rules (1 byte to 16 KiB, no control characters but newline and tab, no bidirectional overrides). |
| `tried` | What it tried. Required, same rules. An agent that asks before trying (R3.28's tier) says so. |
| `question` | The question for the person, optional, up to 4 KiB, same rules. |
| `client_session` | The asking harness session: the request's `client_session`, else the declared one of the workspace's live provenance session. Empty when neither. |
| `conflict_id`, `assignment_id` | With reason `CONFLICT` only: the change's conflict id when asked (R3.25) and its open assignment (R3.27), if any. |
| `state`, `cause`, `answer_id`, `answered_at`, `closed_at` | The lifecycle below. |
| `conflict_moved` | Computed on read: the change's conflict id now differs from `conflict_id`, or it has none. |

- **A conflict is named through its change.** Reason `CONFLICT` requires the revision's commit to be conflicted (`NOT_CONFLICTED` otherwise); the daemon reads the conflict without files and records both ids. The assignment id is what R3.28 and R3.35 look up, since it survives the conflict id moving.
- **On any change the caller can resolve**, draft or proposed, as R3.12's comments are. Not on a landed or superseded change (`CHANGE_FINAL`).
- **Never claimed, never delivered, never inlined.** A help request is addressed to people. Hooks and `reef mcp` ignore it as they ignore notes.
- **Limits** (constants): one open help request per change and asking session (`HELP_ALREADY_OPEN`, naming it, hint: wait for it, or withdraw it and ask again); 16 open per change and 256 per repository (`TOO_MANY_HELP_REQUESTS`, `UNAVAILABLE` as R3.12's limits are). They count toward R3.12's 1,000 comments per change.

### The lifecycle

| State | Means | Entered by |
| --- | --- | --- |
| `OPEN` | Asked; nobody has answered | `CreateComment`; the daemon (cause `answer_cancelled`) |
| `ANSWERED` | An instruction replying to it was written | the daemon, in the answer's own operation |
| `WITHDRAWN` | The asker no longer needs it, or it became moot | `WithdrawHelpRequest`; the daemon (causes `change_final`, `expired`, and since R3.28 `conflict_unblocked`) |

- **Moves**: `OPEN → ANSWERED | WITHDRAWN`; `ANSWERED → OPEN` only when every answer is cancelled before any was delivered (cause `answer_cancelled`, event `reopen`). `WITHDRAWN` is final, and so is `ANSWERED` once an answer has been delivered.
- **Answered in one operation.** The answer's `instruct` event and the help request's `answer` event go in one operation's `reef.comment` list, so a reader never sees an answer without the help request answered.
- **Final changes.** When the change lands or is superseded, its open help requests are withdrawn (`change_final`) in the sweep R3.12 already runs on transitions.
- **Expiry.** Open for 7 days untouched: withdrawn, cause `expired`, by R3.12's expiry timer.
- **A conflict that stops waiting** (added by R3.28's merge). When the conflict assignment an open `conflict` help request names leaves `BLOCKED` (a person allows or takes it, a policy change lets an agent attempt it, or it closes), the help request is withdrawn, cause `conflict_unblocked`, in an operation of its own, and automatic landing judges the change again. The sweep's reconcile does the same from the rows for one a restart or a failed write missed. It orders the two by commit, not by clock: a help request keeps the seq of its assignment's last event when asked (`help_assignment_seq`, added by R3.28's migration 0026), and an event leaving `BLOCKED` with a later seq withdraws it. So reconcile also withdraws a help request whose missed unblock was followed by a new block: that question was about the earlier block, and the agent, back on `ask`, asks once more. A help request asked with `while_blocked` is refused (`CONFLICT_NOT_BLOCKED`) once its assignment is not blocked. `reef here`'s `ask` passes it, and so does `ask_for_help` after `get_workspace` returned `ask`. The daemon's inline withdrawal uses reconcile's rule too: it leaves a help request asked after the unblock's event.
- **Not undoable**, like every comment operation.

### The answer (decision 1)

An instruction (R3.12) whose `reply_to` names a help request that is not withdrawn is an answer:

- **Routed to the asker**: target source `HELP_REQUEST`, and the target's client session, Reef session, harness, agent and workspace are the help request's. With no client session and no Reef session, the source is `NONE` (any session on the change may take it), as R3.12's routing does.
- **Confirmed as written**: it is written `PENDING` with its estimate stored and returned, the same exception R3.45's daemon instructions take. The agent is already stopped and waiting; the design's worry, a casual note spawning work, is about work nobody asked for.
- **Not from the asker.** An answer whose writer's client session or Reef session is the help request's is refused (`SELF_ANSWER`), so an agent cannot answer itself to lift the landing hold.
- **Later answers** to an answered help request are routed and confirmed the same way (a correction, a second thought). A reply to a withdrawn help request is an ordinary instruction. A note replying to a help request is a note: it answers nothing and is never delivered.
- **The frame** for an answer: `Reef answer cmt_… from <identity or agent> (<actor>) to your help request cmt_… on change <short id>:`, the text, then `When finished, run reef comment done cmt_… (proposing the change again also does), or reef comment fail cmt_… -m WHY.` The CLI, the hook and `reef mcp` print it from `instruction.target.source` and `reply_to`; no field is added for it.

### Who may ask, answer and withdraw (decision 7)

- **On the socket**, one uid is one trust domain (ADR 0027): any caller asks, answers and withdraws; the actor is recorded as declared by R3.09's defaults. An agent's answer counts, recorded `AGENT`, so a supervising agent can unblock its workers; R3.33's inbox shows who answered.
- **Through the remote listener**, `Rule::Comment`: a help request needs a `write` token, like a note; an answer is an instruction, so it needs a token linked to an operator identity (R3.12); withdraw needs the token that asked.

### Waiting for the answer

The answer is an instruction for the asking session, so it arrives by R3.12's paths, which need no change:

- **`reef ask --wait DURATION`** asks, then claims as `reef comment next --wait` does, scoped to the change and the asking session, and prints the framed answer. Without `--wait`, its `next` is `reef comment next --wait 10m --change <id>`.
- **`reef mcp`**: `ask_for_help`'s result says to call `wait_for_operations` with kind `comment` on the change, which returns the answer inline (R3.12's `deliver`).
- **Hooks**: an answer that arrives while the agent works is printed at its turn's end or its next prompt, as any instruction is.
- **An ended session**: the answer waits `PENDING` for the same session, or is taken (`--take`) by another agent on the change. R3.46's runner restarts a session; this ticket does not.

### What waits on a help request (decisions 3 and 4)

- **`reef here`.** A new step, `CHANGE_STEP_AWAIT_HELP = 10`, ranked above every row but `DONE`: the change has an open help request, or an answer that is still `PENDING`. Its line names the help request and its first line of text; its `next` is `reef comment next --wait 10m` (which takes the answer). `Workspace.help_request_id = 30` carries the id, set where `step` is.
- **Automatic landing.** A proposal whose change has an open help request is `AUTOMATIC_STATE_NEEDS`, reason `help`, message "its author asked for help (cmt_…)", `next` `reef comment show cmt_…`. Asking, answering, withdrawing and reopening call `Automatic::mark` for the change. `reef land` by a caller is not held: an explicit landing is a decision someone made.

### The CLI (decision 5)

```
reef ask [REV] -m TEXT | -F FILE --tried TEXT [--question TEXT]
         [--reason decision|conflict|blocked|unclear|other] [--path PATH [--lines N[-M]]]
         [--client-session ID] [--wait DURATION]
reef comment answer ID -m TEXT | -F FILE
reef comment withdraw ID [-m TEXT]
reef comment list [REV] --kind help [--help-state open|answered|withdrawn]... [--all]
```

- `reef ask` is top-level so an agent finds it in the guide; it is in `--help-all`, not the root help (511 of 512 bytes). `--client-session` defaults as `reef comment next`'s does (the env-signal table's variable, else `REEF_CLIENT_SESSION`). `--reason conflict` checks the conflict. Text output: the id, `next: reef comment next --wait 10m --change <id>`; with `--wait`, the framed answer.
- `reef comment answer` is `reef comment add --reply-to ID --instruction` for a help request, confirmed as written; it refuses `NOT_A_HELP_REQUEST` and prints the answer's id and its target.
- `reef comment show` prints a help request's reason, text, what it tried, the question, the conflict ids (with "moved" when they did), its state and its answers. `list` prints the reason and first line, escaped as R3.12 escapes text.
- **The agent guide** gains one line under Changes: "Stuck on what only a person can settle? `reef ask -m why --tried what --wait 10m`." Another line is shortened to keep the guide under 1,900 bytes.
- **JSON and brief**: `HelpRequest`, `HelpState`, `HelpReason`; the brief `Comment` adds `help.state`, `help.reason` and the question's first 200 bytes.
- `reef op log` and `reef op watch --kind comment` already show the events.

### MCP (decision 6)

A new tool, `ask_for_help`: `repo`, `workspace`, `revision` (default `@`), `reason`, `text`, `tried`, `question`; it calls `CreateComment` with the server's client session (from its environment, R3.44), and, on the workspace's own change while its step is `ask`, or is `resolve` after `get_workspace` last returned `ask` (R3.28), with reason `conflict` and `while_blocked`, unless the agent named a decision or something unclear. It returns the brief comment and `next`, "call wait_for_operations with kinds [\"comment\"] and changes [<id>]; the answer comes back in `instructions`". `WithdrawHelpRequest` goes in `NOT_TOOLS` ("rare; an agent runs `reef comment withdraw`").

The argument for raising the `tools/list` bound, as the test asks: without the tool an MCP agent that cannot settle something has no way to reach a person at all. It ends its turn with a question in a transcript that a fleet's operator does not read, or it guesses. The server instructions have no room (992 of 1,000 bytes), so the tool's description carries how to wait. The bound rises to what the tool measures, at most 25,900 bytes; descriptions are trimmed first if the measurement is over.

### Web UI (decision 8)

`words.ts` gains sentences from `operation.comments[0]` (`asked for help`, `answered a help request`, `withdrew a help request`, `reopened a help request`), and `log/counts.ts` counts them. No view: R3.33's inbox lists open help requests, and R3.31 renders a change's comments.

### The seam with R3.28

R3.28 blocks an attempt when its tier says "ask before attempting" or its attempt cap is spent, and reports it where the agent looks. This ticket lets the agent ask about exactly that conflict: `reef ask --reason conflict` records the conflict id and the assignment id. The agent raises it, not the daemon, because only the agent knows what it tried (decision 9). R3.28's blocked report names `reef ask --reason conflict` in its `next`. How an answer lets the agent attempt (for example, an answered help request on the assignment allowing one more attempt) is R3.28's to apply, reading `Comment.help.assignment_id` and `state`. Whichever ticket merges second wires the `next` if it is a line; otherwise it is a follow-up named in that PR. R3.28 merged second and wired it: `ask`'s `next` is `reef ask --reason conflict --conflict <asg_…>`, and `AWAIT_HELP` outranks `ASK` while the session waits on its help request.

## Out of scope

- **The inbox** (R3.33): needs-you-now from open help requests, with live counts. **Notifications** (R3.39, R3.40).
- **Restarting an ended session** to deliver an answer: R3.46's runner.
- **What an answer means for a conflict's tier** (R3.28), and intent conflicts escalating to a help request (R3.29).
- **A structured verdict** (approve, stop) on answers.
- **The daemon raising help requests** on an agent's behalf.

## Risks

- **An agent that asks and stops waiting** gets its answer only at its next turn or prompt. Mitigated by `--wait`, the MCP result's `next`, the step in `reef here`, and the hooks; an ended session needs R3.46.
- **Agents asking too often.** The guide line invites it. Mitigated by `tried` being required, the limits, and the reasons R3.33 can rank; the risk is watched in dogfooding.
- **The answer's estimate is shown but not gated.** A person answering commits the agent's time without a confirm step. That is the point of decision 1, and the estimate is still recorded.

## Choices this brief made, and why

- **A comment kind, not a new object**, because R3.12 built the record, the routing and the delivery for exactly this, and its brief and proto reserved the kind.
- **The asking session, not the change's proposer, is answered**, because a helper agent can ask about a change it did not make, and the answer must reach the one that asked.
- **The agent raises a conflict's help request**, because the daemon cannot say what was tried.
- **No wait inside `ask_for_help`**, because `wait_for_operations` already delivers the answer inline and the MCP budget is tight.

## What later tickets inherit

- **R3.33** lists open help requests (`ListComments` with `help_states: [OPEN]`, any change) as needs-you-now, live from `OPERATION_KIND_COMMENT` events whose `help_to` is `OPEN`, and answers with `CreateComment` replying to one.
- **R3.28** points its blocked tiers at `reef ask --reason conflict`, and reads `help.assignment_id` and `state` to decide what an answer allows.
- **R3.35** shows a conflict's help requests by assignment id.
- **R3.40** lays out help requests and answers at phone width.
- **R3.46** pushes answers like any instruction; an `instruction.pending` event whose target source is `HELP_REQUEST` is how a runner knows to resume a waiting session.

## Departures in the implementation

Found while building it (2026-11-19):

1. **Numbers on this base.** Built on `main` at API revision 38 and schema 22 beside R3.28, so the code serves API revision 39 and schema 23 (`0025_help_requests.sql` keeps the slot's file name); whichever of R3.28 and R3.32 merges second renumbers to 40 and 24. The documents say 39 and 23 to match the code.
2. **`ask_for_help` acts on the server's own repository and workspace** and takes only `revision`, `text`, `tried`, `question` and `reason`: with `repo`, `workspace` and `conflict` it measured 26,413 bytes, past the user's 25,900. A conflict is the change's own with reason `conflict`; `reef ask --conflict` names one by id. Three other tools' `revision` texts were shortened to the form `propose_change` and `land_change` use, which brought `tools/list` to 25,898.
3. **Existing reasons where they fit.** A stale conflict id is R3.27's `CONFLICT_CHANGED` (not a new `CONFLICT_MOVED`), and an unknown assignment id `ASSIGNMENT_NOT_FOUND`. `HelpRequest.summary` keeps the withdrawer's reason.
4. **`reef here`'s hint names only the help request's id**, not its first line: #262's rule (S-216) keeps every comment's text out of `hint` and `next`.
5. **The hold covers the whole stack**, with each member's message naming the asking change, since a stack is judged and landed as one.
6. **Through the remote listener the asking token claims the answer** without `take`, as the proposing token claims an instruction.
7. **The agent guide** fit its line by shortening two others: the Commands bullet on `ws list` and `ws inspect`, and the Output line, which no longer names `REEF_OUTPUT=json` or the error's `metadata` (both still work). The long form is 1,847 of 1,850 bytes.
8. **The web UI's workspace page** names the new step, since its step labels are an exhaustive table. `log/counts.ts` needs no change: it counts by operation kind, and help requests are `comment` operations.
9. **From the code review** (the PR's table lists every finding):
   - The step is the asking workspace's only: a help request a helper agent asks about another agent's change leaves that agent's `reef here` alone, since it could never take the answer.
   - The automatic hold does not touch a stack with a queued member: its landing goes on and its status says so; withdrawing the proposal stops it.
   - Through the remote listener a help request's `client_session` is ignored and its answers go to the asking token (folded into S-240), and the remote claim of a reply to a withdrawn help request is the proposer's, as for any instruction.
   - `SELF_ANSWER` compares the asking token, else the asking client session, else (when the asker declared none) the Reef session, so a person answering from the asker's workspace shell is not refused.
   - An answer that expires before anyone takes it reopens its help request, as a cancelled one does.
   - `reef comment answer` refuses a withdrawn help request rather than send an ordinary instruction to the change's session.
   - Answer lookups are scoped to the change, so they use `comments_by_change`.

## Decisions for the user

Asked on 2026-11-18; the user accepted every recommendation below, and the brief's body follows them.

**Group 1: the answer**

1. **Answers skip the estimate's confirmation.** A reply instruction to an open help request is written `PENDING`, its estimate stored and shown, as R3.45's daemon instructions are. *Recommended*: as stated (the agent is stopped and waiting; the design's worry is work nobody asked for). Alternative: answers are ordinary instructions, written `AWAITING_CONFIRMATION` and confirmed in a second call or with ceilings.
2. **What the agent sends.** A reason from a fixed set (decision, conflict, blocked, unclear, other; default other), the text of what is wrong, what it tried (required), and an optional question. *Recommended*: as stated (R3.33 can rank and group by reason; a required `tried` makes the agent show its work before a person spends time). Alternatives: free text only, with no reason; `tried` optional.

**Group 2: what waits on a help request**

3. **Automatic landing holds** a proposal whose change has an open help request (`NEEDS`, reason `help`); an explicit `reef land` is not held. *Recommended*: as stated (an agent asking "is this approach right?" after proposing should not see its change land before the answer). Alternative: no effect on landing; an agent that wants to hold withdraws its proposal itself.
4. **`reef here` says to wait.** A new step, `AWAIT_HELP`, ranked above every row but done, while the help request is open or its answer is untaken; `next` is `reef comment next --wait 10m`. *Recommended*: as stated. Alternative: `here` prints the open help request on a line and keeps the table's step, so an agent following `here` keeps working while it waits.

**Group 3: the surface, and who may answer**

5. **The CLI.** `reef ask` top-level, with a line in the agent guide (another line shortened to stay under 1,900 bytes) and not in the root help; a person answers with `reef comment answer ID -m TEXT` and anyone withdraws with `reef comment withdraw`. *Recommended*: as stated (agents find commands in the guide). Alternative: `reef comment ask` in `--help-all` only, with no guide line.
6. **An MCP tool, `ask_for_help`**, raising the `tools/list` bound from 25,286 to what it measures, at most 25,900 bytes. *Recommended*: as stated (the row names an MCP tool, and without one an MCP agent cannot reach a person). Alternative: `NOT_TOOLS`, and an MCP agent runs `reef ask` in a shell.
7. **Who may answer.** Any caller on the socket, recorded with its actor, except the asking session itself; remotely, an identity-linked token. *Recommended*: as stated (a supervising agent can unblock its workers, and the inbox shows who answered). Alternative: only an answer recorded `HUMAN` resolves it, and an agent's reply leaves it open (a label only, since the socket cannot verify a person until R3.43).
8. **How a person notices before R3.33.** Feed sentences in the web UI, `reef comment list --all --kind help --help-state open`, and the hold's message in `reef proposal show`. *Recommended*: as stated (R3.33 builds the inbox next). Alternative: a small "asking for help" list in the web UI's fleet panel now (about S more, and replaced by R3.33).

**Group 4: the seam with R3.28**

9. **The agent raises a conflict's help request**, and R3.28's blocked report names `reef ask --reason conflict` in its `next`; R3.28 decides what an answer allows. *Recommended*: as stated (only the agent knows what it tried). Alternative: the daemon raises a help request for the agent when a tier blocks or a cap runs out, with `tried` filled from the attempt count.
