# R3.16 Landed history projection

Phase 3 · Size M · Depends on: R3.13 (`Write::Land`, `Repo::land_chain`, landing rows, pins, the policy read at the destination's head), R3.14 (`land_batch` over a chain, `[landing]`, the planned and tested trees, `PlanMismatch`), and builds on R2.03 (`Manager::rewrite`, `OpMeta`), R2.12 (reads `--at-operation`), R2.16 (the history index, GC's operation-id map), R3.04 (provenance and its retention), R3.07 (the policy file, built-in rules, the static check) and #258 (`with_signoff`, trailers kept byte for byte) · Unblocks: R3.17 (pushes the projection), R4.16 (exports it); R3.37 reads its records

## Context

The design, "Published versus working history": "The operation log keeps every agent step. Landed history is a curated projection that policy produces at landing time, so squashing is a rule rather than a chore and humans read a legible history without agents losing their undo trail." Its open problems: "Agents produce enormous working histories. The landing projection must squash and summarize by policy without destroying the operation log that agents need for undo and audit." And the human interface: "Commit messages become agent summaries plus structured provenance."

Every earlier ticket left something here:

- **R3.13**: "R3.16 replaces the rebase in `Write::Land` with the projection, keeping the record." R3.13 and R3.16 "pin the changes a landing consumed so their provenance never expires".
- **R3.14**: landings are batches (`land_batch`, `land_prefix_part`), one operation per landed prefix, each landed tree checked against the planned one; `[landing] checks` says where required evidence must hold.
- **R3.04** and `docs/provenance.md`: "A projection records the source change ids it squashed, so R3.37 can map a landed commit back to them"; "a change squashed into another has no visible commit, so its records expire too, until the landed projection pins the changes it consumed (R3.16)". And: "Nothing is written into the commit … A git push (R3.17) therefore carries no provenance."
- **R3.07**: "Landed-history projection rules: R3.16", a later table in the policy file if it needs one.
- **R3.17** pushes "the landed projection" fast-forward through #258's push path and refuses conflicted changes; **R4.16** exports "the landed projection, not the operation log". The direction since 2026-11-09 is agents first and fully git compatible, with no further git machinery inside workspaces.

So this ticket builds:

1. **The projection**: a pure step inside the land operation that decides what each landed change looks like on the destination: its description rewritten as a summary with trailers, or kept as written, by the destination's policy. The tree never changes.
2. **The policy's `[history]` table**, the built-in rule `builtin:description` that keeps undescribed changes off a summarized branch, and the starter policy.
3. **Empty landings**: a change that the chain leaves with no diff is returned rather than landed as an empty commit.
4. **The record**: what each landing wrote, so R3.37 and R3.17 read it; the pins R3.04 asked for, verified.
5. **The surface**: two fields, one reason, `reef landing show`, and the documents.

What stays out, each under "Out of scope": squashing a batch into one commit (decision 3's alternative), squashing a stack (R3.10), message templates, setting the author, signing commits, pushing (R3.17), exporting (R4.16).

### The destination is the projection (decision 2)

There is one landed history: the destination bookmark. The projection is applied inside the land operation, so the bookmark only ever points at projected commits, R3.17 pushes it as it is, and R4.16 exports it. The working history is the operation log: every snapshot of every change, and the queued commit each landed commit replaced, as its predecessor.

A second, "published" bookmark beside an unprojected local one is not built: agents would build on one and git users on the other, and every fetch would conflict them.

### What is squashed (decision 3)

**One commit per change.** A change is already the squash of its working history: every snapshot an agent's workspace took is an operation that rewrote the same change, and the change lands as its last commit. The projection keeps that unit: each landed change is one commit on the destination, with its change id, so `reef show <change>`, the lifecycle, workspaces and the history index all keep working, and `git bisect` and `git revert` on the destination work per change. A batch lands as one commit per member, in chain order, as R3.14 lands it.

A stack (R3.10) is where several changes become one commit; R3.10 adds `squash = "stack"` to `[history]`. Squashing a whole batch into one commit is not built (the alternative): it hides every member's change id, which the history index would read as abandoned, mixes unrelated agents' work in one commit, and makes per-change bisect and revert impossible.

### The summary (decision 4)

Under `[history] message = "summary"`, each landed change's description is rewritten, and nothing else is: the tree, the change id, the author and the parents R3.14 chose stay.

1. **The text is the change's own description**, the agent's summary in the design's words. Reef writes no prose. Normalized: `\r\n` to `\n`, control characters other than newline and tab removed, trailing whitespace on each line removed, leading and trailing blank lines removed, one final newline.
2. **Owned trailers are removed** from the description's trailer block (its last paragraph, as `parse_description_trailers` reads it): every `Reef-*` key, and `Reviewed-by` when the projection writes it. Other trailers, `Signed-off-by` and `Co-Authored-By` among them, stay byte for byte.
3. **The projection's trailers are appended** to that block (or after a blank line when there is none), in a fixed order, each value with no control characters and at most 200 bytes (decision 5).

A summarized change needs a description. `builtin:description` applies when the destination's policy says `message = "summary"`: a change whose description is empty after normalization is `unsatisfied` at the gate, with the message "a change landing on main needs a description: `reef describe <id> -m \"<summary>\"`". The landing judges the same rule again, so a description emptied after proposing is caught.

Under `message = "keep"` the change lands as written, as before this ticket: a fast-forward keeps its commit id, a rebase only rebases.

### Trailers (decision 5)

`[history] trailers` picks from four sets, written in this order:

| Set | Writes |
| --- | --- |
| `change` | `Reef-Change: <change id, hex>` |
| `landing` | `Reef-Landing: lnd_…`, and `Reef-Batch: bat_…` when the batch landed more than one change |
| `agents` | `Reef-Agent: <name>` for each distinct agent in the change's provenance records, oldest first, at most 5 |
| `signoffs` | `Reviewed-by: <display name> <<email>>` for each person identity whose `signoff` evidence satisfied a `[[signoff]]` rule or `builtin:owners` in the landing's evaluation (the name alone when the identity has no email), sorted, at most 10 |

**The default is `["change", "landing"]`**: ids only. Agent names and reviewers' emails are opt-in, because R3.17 pushes these commits to a git host and the design keeps provenance local. A trailer is a reference into Reef's records, not proof: evidence, sign-offs and provenance stay in `reef.sqlite3` (S-191).

`Reef-Change` repeats jj's `change-id` header where git hosts and git-only tools can see it, so R3.17 and R4.16 can map a pushed commit back, and a forge that squash-merges keeps it in the message.

### Opt-in, and the starter (decision 6)

A policy with no `[history]` table lands as before: `message = "keep"`, no trailers, no `builtin:description`. Existing repositories see no change in their commits, and a fast-forward still lands the very commit that was reviewed, which a published review branch (`reef publish`) shares, so the host can show it merged.

`reef policy init` writes the table with the recommended settings:

```toml
# How landed changes are written on this branch (docs/landing.md). "summary"
# keeps each change's description, removes Reef-* trailers from it, and adds
# the trailers below; "keep" lands the commit as written.
[history]
message = "summary"
trailers = ["change", "landing"]       # change | landing | agents | signoffs
```

`[history]` is strict like every table: an unknown key or set is an error with its line and column, and `trailers` is valid only with `message = "summary"`. Changing it is a policy-file change: the owners sign it off and it lands alone (S-146); the change that adds it is projected by the policy before it.

### Authorship and the DCO (decision 7)

- **Author**: kept. Reef-written work is authored by the daemon's `[identity]`, which a person sets to themselves (`docs/publishing.md`); setting the author from the proposer is a follow-up for daemons serving several people.
- **Committer**: the daemon's `[identity]` at landing time, as a rebase sets it today. A summarized fast-forward therefore gets a new committer time and commit id.
- **`Signed-off-by`**: never added. A sign-off certifies the Developer Certificate of Origin in a person's name, so only that person adds it (`reef describe --signoff`, #258's rule); the summary keeps it. A repository that requires it says so in a free rule, documented as a recipe:

```toml
[[rule]]
name = "dco"
expr = 'change.description.matches("(?m)^Signed-off-by: .+ <.+>$")'
message = "sign off the change: reef describe --signoff"
```

### Empty landings (decision 8)

A member whose tree on the chain equals the tree before it (its edits are already on the destination, or in an earlier member) would land as an empty commit. `preview_chain` reports it `empty`, and the batch dequeues it at formation with a new reason, **`empty`**: "its changes are already on main", hint "withdraw it (`reef proposal withdraw <id>`) or abandon it", `next` the withdraw. Under any `[history]`, since an empty commit on the destination helps nobody. `land_chain` refuses an empty member too (`LandError::Empty`), which the batch treats as R3.14's refusals.

### The operation log, undo and GC (decision 9)

- **One operation.** The projection is part of the `land` operation R3.13 writes: no new operation kind, and the land stays not undoable.
- **The queued commit stays reachable through the log.** Each summarized commit's predecessor is the queued commit (or, for a rebased member, the queued commit through the same rewrite), recorded in the land operation. `reef op show` lists the rewrite; `reef show <change> --at-operation <the operation before the land>` and `reef diff --from <queued commit> --to <landed commit>` read the original, for as long as GC keeps the operation (`gc.undo_window`, 7 days by default, or the backup retention).
- **After that, records.** GC collects the queued commit like any rewritten commit. What survives is the landing row: the queued commit and tree, the landed commit and tree, `summarized`, and the settings it landed under; and the change id, which the landed commit keeps. No extra ref keeps queued commits (the alternative): `refs/reef/…` refs would keep every landed change's original for good, and `git log --all` in a colocated repository would show them.
- **Provenance and evidence are pinned already**: every landed change has its own `landing_changes` row, whose change id provenance retention skips (R3.04's inherited pin), and its evidence is in `landing_evidence`. Since nothing is hidden, no change becomes invisible; a test holds the pin through a GC that collects the queued commit.
- **R3.37's map** from a landed commit to its source is the change id (the same) and the landing row (`landed_commit_id`).

### Batches, bisect and conflicts

- The projection runs on the prefix R3.14 lands, after the planned-tree check, and checks that every projected tree equals the planned tree (`PlanMismatch`, S-193). Trial commits are never projected: they are abandoned in the same operation.
- Bisect is unchanged: it tests trees, and the projection does not change one.
- The projection never writes a conflicted commit: a conflicted change is refused at the gate and a conflicting rebase before the projection, as now. R3.17 still refuses to push a conflicted change.
- `[history]` is read from the policy at the batch's base, with `[landing]`, so every member of one land operation is projected by one policy.

### Rewrites that follow

Under `summary`, every landing rewrites its member, even a fast-forward, so descendants of a landed commit (a change proposed on top of it, a workspace on it) are rebased onto the projected commit in the same operation, as a rebased landing does today; their trees do not change, so their evidence still applies. A proposal on such a descendant reads `amended` and is proposed again (R3.11 carries proposals across a dependency's rewrite). `land_chain` calls `rebase_descendants` whenever a member was rewritten, not only rebased.

### The record: schema 18 (decision 10)

Migration `0018_history.sql`:

```sql
ALTER TABLE landings ADD COLUMN history TEXT;            -- JSON {"message": "summary", "trailers": [...]}; NULL before R3.16
ALTER TABLE landing_changes ADD COLUMN summarized INTEGER NOT NULL DEFAULT 0;
```

Written with the landing's other rows when it lands; `repo forget` and backups need nothing new.

### The API: revision 32 (decision 10)

In `landing.proto`:

```proto
// How a landing wrote its changes on the destination (R3.16): the
// `[history]` table of the policy it was judged by.
message LandingHistory {
  string message = 1;              // "summary" or "keep"
  repeated string trailers = 2;    // the sets written, in order
}
message Landing { ...; LandingHistory history = 21; }      // unset until it lands, and before R3.16
message LandedChange { ...; bool summarized = 17; }        // its description was rewritten as a summary
enum LandingReason { ...; LANDING_REASON_EMPTY = 10; }
```

- No new RPC, operation kind or error: `GetLanding` and `ListLandings` carry the fields; `ListLandings` carries `history` too (it is small).
- **Remote rules**: nothing new. **ADR 0029's checklist** in the PR; `API_REVISION` 32 with its digest; both SDKs regenerate; the web UI's generated code regenerates and nothing else changes.

### The CLI, MCP, web

- JSON gains `history` and `summarized`; brief output is unchanged; `reef schema`'s rows follow.

## Implementation notes

- **Order**: reef-policy (3); `summarize` (1); `land_chain` and `preview_chain` (2); the migration and rows; the daemon's settings, facts and dequeue (4 to 9); the API and CLI (10); the documents.
- **The projection is computed in the daemon, applied in reef-lib.** The daemon knows the landing and batch ids, the provenance and the identities; reef-lib takes a finished description per member and only checks that trees did not change, so the projection cannot change content.
- **One commit per member.** `CommitRewriter::new(mut_repo, commit, vec![tip]).rebase().await?.set_description(d).write()`, or `rewrite_commit(&commit).set_description(d)` for a fast-forward; never a rebase and then a second rewrite.
- **Facts are read under the create lock**, with the landing's re-judgment (`land_prefix_part`), so the sign-offs written are the ones the evaluation counted.
- **Linux**: nothing is `cfg(target_os = "linux")`; CI covers it.
- **No new daemon configuration.** The limits (5 agents, 10 reviewers, 200 bytes) are constants.

## Performance and laptop cost

No new process, job or watcher. Per landed change under `summary`: one more commit object (a few hundred bytes) for a fast-forward that would have kept its commit, one provenance query for `agents`, one identity lookup per sign-off; the summary itself is microseconds. A landing of 8 changes stays within R3.14's "< 600 ms" (trend, M2 Max, release). Migration 18 adds two columns. Disk: unchanged after GC, since the queued commits it replaced are collected with the operations.

## Out of scope

- **Squashing a batch** into one commit (decision 3's alternative).
- **Squashing a stack** (R3.10 adds `squash = "stack"`).
- **Message templates** or a CEL expression for the message; a title length rule is a free rule over `change.description`.
- **Setting the author** from the proposer, and **signing commits** (gpg or ssh) for hosts that require signed commits: follow-ups.
- **Pushing** the destination (R3.17) and **exporting** it (R4.16).
- **Carrying proposals of descendants** across a landing's rewrite (R3.11).
- **Following a forge's squash merge** by its `Reef-Change` trailer (R3.17).

## Risks

- **Summarized fast-forwards get new commit ids**, so a review branch published with `reef publish` no longer shares its commit with the destination and a host will not show it merged. Mitigated: `keep` is the default with no table, and R3.17 pushes the destination itself.
- **Descendant proposals read `amended`** after every summarized landing below them, not only rebased ones. Mitigated: their trees are unchanged, so their evidence holds and proposing again is one command; R3.11 removes the step.
- **Trailer formats are public once pushed**: their keys are part of the contract R3.17 and R4.16 inherit. Mitigated by the ADR.

## Choices this brief made, and why

- **The projection is the destination**, so there is one history to push, export and build on.
- **A change is the unit**, because a change already is the squash of its working history and keeps every Reef reference working.
- **The description is the summary**, because the design asks for agent summaries and Reef has no business writing prose; normalization and trailers are what policy adds.
- **Ids by default**, because the projection is what leaves the machine.
- **Opt-in by table**, so no existing landing changes its commits without a reviewed policy change.

## What later tickets inherit

- **R3.10** adds `squash = "stack"`: a stack's changes as one commit, its members' change ids recorded on the landing rows and pinned there, and the history index taught to read them as landed.
- **R3.11** carries descendant proposals across a landing's rewrite.
- **R3.17** pushes the destination as the projection wrote it, fast-forward, and may follow forge merges by `Reef-Change`.
- **R3.37** maps a landed commit to its change by the change id and the landing row, and reads `summarized` and `history`.
- **R4.16** exports the destination; the trailers are the provenance git can carry.

## Departures from dev-phases.md

`dev-phases.md` and this directory's README were edited to match with this brief:

- **"Squash"** is one commit per change: a change is already the squash of its working history, which stays in the operation log; squashing a stack is R3.10's, and a batch is not squashed.
- **"Summarize by policy"** is the change's own description, normalized, with the trailers the destination's `[history]` table picks (ids by default), and `builtin:description` on a summarized branch; without the table, landings are unchanged.
- The row also gains empty landings returned with reason `empty`.

## Departures in the implementation

Found while building it (2026-11-13):

1. **reef-lib applies the summary.** `PlannedMember.summary` carries a `Summary` (the keys to strip besides `Reef-*`, and the trailers to append), and `land_chain` applies it to the queued commit's own description in the rewrite that lands it, instead of the daemon passing a finished description: the daemon never reads the description, and what is summarized is exactly the commit that lands. The pure function is `reef_lib::jj::projection::summarize` (the brief's `history.rs` name was taken by the history index); the daemon's side is `landing/history.rs`.
2. **A `[history]` table names `message` optionally**: without it the table means `summary`, with the default trailers; `trailers = []` is a summary with none.
3. **`empty` at the gate, and later in a batch.** A change already empty against the destination is blocked at the gate with reason `empty` (its preview says so), or dequeued with it when a batch judges it. One that only an earlier member of its batch makes empty is not dequeued at formation (review finding 2: that member may still fail to land, and the message would be false): it is left out and stays queued, as a member conflicting with an earlier one is, and the next batch returns it `empty` once those edits have landed.
4. **Owned trailers are stripped as git reads them** (review finding 1): from the last paragraph after the title whether or not jj reads it as a trailer block, with whitespace before the colon and tab continuations; normalization also removes invisible formatting characters (bidirectional controls, zero-width characters), and `builtin:description` counts neither those nor control characters as a description (review findings 3 and 8). Other trailers stay, normalized like the rest of the text, not byte for byte.
5. **`reef landing show`** marks a summarized change `(summarized)` on its line and prints a `history` line, rather than each landed commit's title, which would cost a read per change.
6. **`Reef-Agent`** comes from the change's provenance rows (`Db::provenance_agents`), oldest first, without re-verifying their signatures: a trailer is a reference, not proof (S-191).
7. **The daemon's tests** are in `tests/landed_history.rs` (`tests/history.rs` is the history index's): `summarized_landing` (tests 4 and 7), `batch_projection` (5), `keep_and_no_table` (6 and 7), `empty_member` (8), `history_after_gc` (9). Test 9 checks the record, the pins and the provenance after GC drops the land operation; it does not check that git collected the queued commit's objects.

## Decisions for the user

Asked on 2026-11-13; the user accepted every recommendation below, and the brief's body follows them.

**Group 1: scope**

1. **Size.** M, with everything above. *Recommended*: as stated. Alternatives: leave empty landings (decision 8) to a follow-up; or add batch squash (decision 3's alternative), which takes it to L with the history index and lifecycle work.

**Group 2: what the projection is**

2. **Where it lives.** The destination bookmark is the projection, written inside the land operation. *Recommended*: as stated (one history to build on, push and export). Alternative: an unprojected local bookmark plus a published one, which agents and git users would see diverge.
3. **What is squashed.** One commit per change, with its change id; a batch lands one commit per member; stacks are R3.10's. *Recommended*: as stated (a change is already its working history squashed; bisect, revert, `reef show` and the lifecycle keep working). Alternative: `squash = "batch"`, one commit per land operation (fewer commits, but members' change ids hidden and work mixed).
4. **The summary.** The change's own description, normalized, owned trailers removed, the projection's appended; `builtin:description` blocks an undescribed change on a summarized branch. *Recommended*: as stated. Alternatives: a CEL or template message in the policy; a generated title ("Change <id>") instead of blocking.
5. **Trailers.** Sets `change`, `landing` (with `Reef-Batch`), `agents`, `signoffs`; default `["change", "landing"]`, ids only. *Recommended*: as stated (they leave the machine with R3.17). Alternatives: default to all four (more legible history on the host, names and emails public); no trailers by default.
6. **Opt-in.** No `[history]` table keeps commits as written; `reef policy init` writes `message = "summary"`. *Recommended*: as stated (no existing landing changes; a fast-forward keeps the reviewed commit). Alternative: summary for every policy by default.
7. **Authorship and the DCO.** Author kept (`[identity]`), committer the daemon at landing, no `Signed-off-by` added, a DCO free-rule recipe. *Recommended*: as stated. Alternatives: `author = "proposer"`; add the operator's `Signed-off-by` when `[identity]` is set.

**Group 3: history and records**

8. **Empty landings.** A member the chain leaves empty is dequeued with new reason `empty`, under any `[history]`. *Recommended*: as stated. Alternatives: land it as an empty commit (today); drop it silently and record it landed.
9. **Reachability, undo, GC.** The land stays one non-undoable operation; queued commits stay readable through the operation log for the undo window, then only the records remain; provenance and evidence are pinned by the landing rows already. *Recommended*: as stated. Alternative: keep every queued commit for good with `refs/reef/…` refs (more disk, visible to `git log --all`).
10. **Surface and numbers.** Schema 18 (`landings.history`, `landing_changes.summarized`); API revision 32 (`LandingHistory`, `LandedChange.summarized`, `LANDING_REASON_EMPTY`); no RPC, kind or MCP tool; ADR 0075; S-191 to S-195. *Recommended*: as stated. Alternative: no migration, recomputing the settings from the policy bytes each landing keeps.
