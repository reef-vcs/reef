# R3.39 Desktop shell

Phase 3 · Size L · API revision 46, schema 29 (`0031_inbox_raises.sql`), ADR 0093, threat rows S-267 to S-273 · Folds in #389 (a `WatchInbox` client cannot tell a repository's starting state from an item that arrived while another repository was busy) · Leaves out #346 (decision 4) · Depends on: R3.33 (the inbox, its keys and words), #372 (`WatchInbox`, ADR 0091), R2.18 (the web listener and its sessions, ADR 0047), R3.43 (passkey sign-offs), R1.28 (releases) · Unblocks: R3.40 (the phone: the same shell, a remote daemon, and push from the daemon's own ledger), R3.41 (Linux and Windows ports)

## Context

Phase 3's last open desktop criterion reads: "The triage inbox shows the needs-you-now bucket live, and the desktop app notifies on it." The inbox is live since #372. Nothing yet tells a person, outside an open browser tab, that an agent is asking or that a proposal waits on their sign-off. ADR 0005 chose Tauri 2 for the shell: the web UI in the platform's webview, a Rust side that supervises the daemon, and "no Tauri-specific code outside the shell", so the web UI stays a plain web app.

Agents are Reef's main users. The shell is for the person who runs a fleet of them. It must not hold anything an agent needs: an agent that supervises others reads the same "what is new" rule from `reef inbox watch`.

Earlier tickets left this one seams:

- **R3.33** keyed every inbox item (`proposal:<repo>:<change>`, `help:<repo>:<comment>`, ...) "for R3.39's notifications", and wrote the daemon's own words for each item (`inbox/words.rs`), never agent text (S-262).
- **ADR 0091** made the inbox a stream the daemon keeps while someone watches, so a notifier subscribes instead of copying the trigger table. Its Consequences named the web page's store (`live/inbox.ts`, `inbox/needs.ts`) as the shell's source; this brief takes the stream from the shell's Rust side instead (choices, below).
- **R2.18** left `web/src/api/connection.ts`'s `Connection` seam for "a shell (R3.39, R3.40)", and `CreateWebSession` takes the page to open (`path`).
- **R3.43** said the desktop shell and the phone use the same approvals.

### What was verified while writing this ticket

Reef at `e3586955` (API revision 45, schema 28, last migration `0030_inbox_marks.sql`, ADR 0092 the latest, threat rows to S-266). Paths are under `crates/` unless they start with `docs/`, `web/` or `shell/`.

- **The window must be the daemon's own page.** The web listener (`reef-daemon/src/web/gate.rs`) accepts only Host `localhost:<port>`, refuses `OPTIONS` and any foreign `Origin`, and sends `connect-src 'self'` and `frame-ancestors 'none'`. A page served from `tauri://localhost` cannot call it. Sessions come only from `CreateWebSession` (ADMIN, the socket); the page reads `#session=` and strips it (`web/src/session.ts`). Every daemon restart ends every session, and `[ui] listen` defaults to a new port each start.
- **The daemon cannot run inside the app.** `reef-daemon`'s `run_main` calls `set_var(WATCHMAN_SOCK)`, sound only while the process has one thread, and raises `RLIMIT_NOFILE` for the process. A child process dies with the app and with it every agent's workspace. The CLI already starts the daemon detached (`reef-vcs/src/cli/autostart.rs`): its own process group, `reef-daemon` beside the CLI first, then `PATH`. One daemon runs per state directory (`daemon.lock`). A newer schema refuses an older daemon (`DbError::TooNew`), so no daemon is ever downgraded.
- **`WatchInbox` gives state, not news (#389).** `service/inbox/session.rs` sends each repository's first section as soon as the board reads it and sets `synced` once every repository is on the board. Three cases break a client that treats everything before `synced` as its starting inbox: an item that arrives in B while A's thread is busy (the #389 probe: 28 ms, `synced=false`); a repository registered after the board was ready, whose whole first section comes after `synced` (`Board.ready` is sticky, `watch.rs:53`); and a repository whose first read fails, which is sent as an error with no items, so its items later arrive as changes (`RepoBoard::failed(None, ..)`). A daemon restart re-judges every proposal: until the automatic service's first pass a proposal has no status and reads from its lifecycle (a sign-off reads in review under watching, a returned landing as returned), then by its judgment (`inbox/rules.rs`'s `PROPOSAL` table ends in a catch-all `InReview` row, so the proposal stays on the board throughout). The page waits for `synced` before showing anything (`InboxStore.applyFrame`, `InboxModel.project()`), so first load waits for the slowest repository.
- **`NeedsWatcher`** (`web/src/inbox/needs.ts`) has no consumer. It reports nothing on its first call and never forgets a key.
- **Routes.** `web/src/App.tsx` has pages for a proposal, the fleet (`?workspace=`) and the smartlog (`?change=`); a help request is answered in place in the inbox; `Inbox.tsx::targetOf` maps an item to its page. `CreateWebSession.path` accepts `/[A-Za-z0-9/._-]*`, 256 bytes, no query (`web/mod.rs::is_app_path`).
- **Passkeys.** Sign-off runs `navigator.credentials.get` on the proposal page (`web/src/views/SignOff.tsx`, `web/src/sign/passkey.ts`), approvals at `/approve/:id`, registration at `/passkeys`. RP ID `localhost`; the daemon compares the exact origin of its listener.

### Spikes run for this brief

A Tauri 2.12.7 app (scratch, not in the tree), built as an ad-hoc signed debug `.app` on macOS 27.2, M-series:

1. **The web UI loads in the webview.** `WebviewUrl::External(session_url)`, the URL minted in process and never printed, loads the real page at `http://localhost:65442`. Every call returns 200 through the gate (fetch instrumented by an initialization script): `GetDaemonStatus`, `SubscribeOperations`, `SubscribePresence`, `WatchInbox`. Playwright's Chromium and WebKit render the full inbox from the same URL.
2. **`tauri-plugin-notification` is not usable on macOS.** Version 2.8.1 posts through the deprecated `NSUserNotification` (notify-rust), and its `permission_state()` returns `Granted` unconditionally (`desktop.rs:196-206`), so the app could never tell the person notifications are off.
3. **`UNUserNotificationCenter` works with ad-hoc signing.** Through `objc2-user-notifications` 0.3: a bundle whose code-signing identifier is the linker's (`reef_shell_spike-<hash>`, not the bundle id) is refused (`UNErrorDomain` 1, "Notifications are not allowed for this application"), and the refusal sticks to the bundle id. A fresh bundle id signed `codesign --force --deep -s -` before its first launch is granted provisional authorization, and `getDeliveredNotificationsWithCompletionHandler` lists the request by the identifier we gave it (`help:spike:1`). The request identifier is the item key, so posting again replaces and `removeDeliveredNotificationsWithIdentifiers` takes one back. A visible banner needs a person at an unlocked screen (the screen was locked during the spike); that is the manual evidence row in Tests.
4. **WebAuthn in the webview.** `PublicKeyCredential` exists; `get` failed "The document is not focused" with the screen locked. Apple's guidance: WKWebView runs passkey ceremonies only for an app's associated domains or with the browser entitlement, and `localhost` cannot have associated domains. The shell sends ceremonies to the default browser (decision below); the implementation checks the webview once at an unlocked screen and records what it saw.
5. Size: the debug `.app` is 29 MB without Reef's binaries.

Design runners (two models, independently) both put "what is new" in the daemon as a persisted ledger, for the same three reasons: #389, the restart re-judge, and R3.40's push, which runs in the daemon and must not push twice across a daemon restart.

## Decisions

Numbered decisions are the user's (Decisions for the user, at the end). The rest are this brief's, with reasons in "Choices".

### Size

L. Four parts: the daemon's raise ledger and stream fields (#389), the web's item route, embedded flag and per-repository first load, the `reef-shell` core crate, and the `shell/` Tauri app with its CI and release jobs.

### The raise ledger: one definition of "new" (#389)

The daemon gives every needs-you-now **episode** a number, a **raise**, and keeps it across restarts. An episode is an item key, its reason, and a cause that changes when the person would want telling again:

| Object | Cause | So |
| --- | --- | --- |
| proposal | its commit id | a new revision raises again, since a sign-off binds the tree; a restart's re-judge of the same commit does not |
| conflict | the assignment's commit id | a new conflicting commit raises again |
| help request, instruction | none | once per request and reason |
| workspace | none | once per workspace and reason |

- **Table** `inbox_raises (seq INTEGER PRIMARY KEY AUTOINCREMENT, repo_id, key, reason, cause, UNIQUE (key))`, a key's latest episode; `AUTOINCREMENT` never reuses a number. The **raise epoch** is the database's instance id, with its restore time once restored, so a client can tell a new or restored database from the one it knew.
- **Only the board task writes it**, in `service/inbox/watch.rs` after a good read and before the board is published (one writer, no lock). For each listed needs-you-now item: a row with the same reason and cause keeps its number (a provisional reading, a proposal not judged since the daemon started, keeps it whatever its reason); none, or another reason or cause, takes the next number. Rows whose key is in neither bucket are deleted, so an answered help request asked again raises again; `classify` sees every item before `BUCKET_CAP` cuts the buckets, so the read prunes with every key it placed and keeps the rows of keys past the cap (main-session review F3). A failed read writes nothing. Running it twice on the same read changes nothing. A forgotten repository's rows go with it.
- **`InboxItem.raised`** (field 15): the item's number, above 0 exactly when its bucket is needs-you-now and a board has settled it. `GetInbox` reads the rows and never writes (an item no board has settled yet reads 0), so news is told from a stream. `reef inbox` and `reef inbox watch` print it.
- **`InboxSectionChange.listing`** (field 9, `InboxListing`): `PART` on every part of this stream's first listing of the repository from a good read, `END` on its last part, `UNSPECIFIED` on every later difference. A repository not yet read, or whose first read failed with nothing to show, sends `UNSPECIFIED` with its error, and its first good read is the listing. A repository registered late lists after `synced`, and that is fine.
- **`InboxSectionChange.raised_through`** (field 10), on the last part of a listing or difference only: every listed needs-you-now item of this repository with `0 < raised <= raised_through` has been sent on this stream. Per repository on purpose: one mark for the whole stream would be wrong whenever a busy repository lists after another moved on, which is #389 again.
- **`WatchInboxResponse.raise_epoch`** (field 3, every frame).
- `synced` keeps its meaning (every followed repository has listed). `docs/inbox.md` and ADR 0091 drop "everything up to `synced` is the whole inbox".

A client keeps one number per repository. Items with `raised` above it are new. A repository it has no number for takes `raised_through` at its listing's `END` and announces nothing it listed.

### The web page

- **First load shows each repository as it lists** (#389's second half): `InboxStore` folds sections straight in until the first `synced`, and keeps replace-at-`synced` for reconnects; `InboxModel.project()` shows listed repositories and "Reading N more" for the rest.
- **`/repos/:repo/items/:key`**: finds the key in the live store and replaces the URL with `targetOf(item)`. A help request or instruction, which has no page, opens its repository's inbox. A key that is gone opens the inbox with "That no longer needs you." Banners, deep links and R3.40's pushes link here, so the item-to-page mapping stays in one place (TypeScript). `CreateWebSession.path` accepts `:`, since keys sit in paths.
- **`embedded`**: the shell adds `&embedded=1` to the session fragment it navigates to. `session.ts` strips it with the token and keeps it in `sessionStorage`. With it set, `SignOff.tsx`, `/approve/:id` and `/passkeys` show "Continue in your browser", a same-origin link that opens a new window. In a browser it opens a tab; in the shell, the new-window request goes to the default browser through a fresh launch-file session at that path. The ceremony runs in Safari or Chrome against the same `http://localhost:<port>` origin the daemon checks today, and the app's window updates from its streams when the sign-off lands. The flag names no host, so an Electron fallback sets it the same way.
- **`NeedsWatcher` is deleted**; `inboxTitle` stays.

### `crates/reef-shell`: the core, tested on Linux

A workspace crate with no Tauri or Objective-C dependency, so `cargo test --workspace` on Ubuntu runs all of the shell's policy:

```
crates/reef-shell/src/
  lib.rs      Shell::start, ShellHandle, Command, Platform, ShellConfig    the public surface
  inbox.rs    parse WatchInboxResponse into Frame; Held (needs per repo)   the only reef_api::v1 user
  notice.rs   Notifier::observe -> Vec<Effect>; Cursor (saved)             the notification rule
  link.rs     Conn state machine, step(); the start policy                  pure transitions
  path.rs     WebPath, DeepLink
  menu.rs     MenuSpec, menu(&View)
```

One task owns every piece of state (connection, window page, held inbox, notifier), so nothing is shared and nothing locks. The Tauri app sends `Command`s (open a page, a deep link, a notification click, a menu action, the window closed) and implements `Platform` (show a page, post, retract, render the menu, open a launch file in the browser).

**The notification rule** (`Notifier`, pure):

- `Cursor { epoch, through: repo -> raise }`, saved as `notices.json` in the app's data directory (temporary file, then rename) after a change, once the banners it moved past are posted (main-session review F1). Another epoch starts it over, silently.
- Per section: removed, drop the repository's number and retract its banners. No number yet, post nothing, and take `raised_through` at `END`. Number `t`, post every needs-you-now item with `raised > t` not already posted this run, then raise `t` to `raised_through`.
- One to three new items in a frame post one banner each; more post one summary ("5 things need you"). The banner's identifier is the item key; its title is the daemon's headline and its body the repository's name (S-262: never agent text). A crash between posting and saving posts again under the same identifier, which replaces: duplicates are possible, losses are not.
- A posted item that leaves needs-you-now is retracted after 30 s unless it is back, so a restart's re-judge never empties Notification Center.
- Permission off posts nothing and still moves the cursor: the menu bar count is the fallback, and a backlog is never replayed.

**The connection** (`Conn`, one enum, `step(conn, event) -> (conn, effects)` pure): `Connecting`, `Starting`, `Up`, `TooOld { api_revision, active_workspaces }`, `Down { error, retry_at }`.

- At launch, the shell connects to the socket (`reef_client::paths`, so `REEF_SOCKET` and `REEF_STATE_DIR` apply). When nothing answers, it runs `reef daemon start -o json`, the CLI's own idempotent, lock-guarded, detached start, never a sidecar child: from a `reef` on `PATH` or in `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `~/.cargo/bin` first, else the bundled one (decision 1). A newer bundled daemon must never migrate a state directory that an installed CLI starts its own daemon on, or that CLI's daemon would refuse to start afterwards (`DbError::TooNew`).
- A daemon that answers is used as it is, whoever started it, if its API revision is at least 46. Below that the menu says so; once `active_workspace_count` reads 0 it offers "Restart the daemon" (stop, then start, as above). It never stops a busy daemon.
- A lost connection reconnects with backoff (1 s doubling to 30 s) and never starts a daemon by itself: a person who ran `reef daemon stop` to upgrade must not see the app start the old one again. The menu offers "Start the daemon".
- A new `instance_id` means every web session ended: with the window open, the shell mints one at the page the window was on and navigates; otherwise it waits until the window opens.
- `GetDaemonStatus` is read on connect and on the stream's 15 s keepalive frame, for the menu's counts. No other timer.

**Paths and links.** `WebPath` is the one Rust grammar of a web UI path, moved from `is_app_path` into `reef-client` so the daemon and the shell share it. Deep links are `reef://local/<web path>` (`reef://local/repos/<repo>/items/<key>`, `reef://local/`): scheme `reef`, authority exactly `local` (R3.40 may name a remote daemon there), no user, port, query or fragment, no percent escapes. A link only navigates the person's own window to a path on the daemon's origin; every route stays side-effect free on load (a sign-off or approval needs a click and a passkey), which is what makes a link from any page harmless.

**The menu bar** (`menu(&View) -> MenuSpec`, pure; the tray is redrawn only when the spec changes):

```
[icon] 3                                       the needs-you-now total; no number at 0
  3 need you now
    Needs a sign-off: fix lease renewal · reef   newest five, each opens its item
    and 1 more                                    opens the inbox
  ─
  5 workspaces active in 2 repositories           GetDaemonStatus
  1 push to a git remote needs you                when pushes_attention > 0
  Daemon 0.4.3                                    | starting | too old (Restart the daemon) | stopped (Start the daemon)
  Notifications are off                           when not authorized: opens System Settings
  ─
  Open Reef
  Open at login ✓
  Quit Reef (agents keep running)
```

### `shell/`: the Tauri app

`shell/` holds the Tauri 2 crate `reef-app` with its own `[workspace]` and `Cargo.lock`, outside `members = ["crates/*"]`, so no `--workspace` recipe and no Linux job sees Tauri or webkit. It holds only adapters:

- **Window.** `WebviewUrl::External`, one window, its data store not persisted. `on_navigation` allows exactly the current daemon origin; another `http(s)` URL opens in the default browser; anything else is refused. A same-origin new-window request is the browser hand-off above. The page gets no Tauri IPC (no capability for its origin), so it can call nothing in the app. Closing the window destroys the webview and hides the Dock icon (accessory); opening it shows both. A bundled `offline.html` shows while the daemon is down or too old.
- **Notifications.** `UNUserNotificationCenter` through `objc2-user-notifications` (spike 3), with a delegate: a click opens the item; a banner shows while the app is frontmost too. Full authorization (alert, sound, badge) is asked once at first launch.
- **Deep links** (`tauri-plugin-deep-link`, scheme `reef`) and **open at login** (`tauri-plugin-autostart`, on by default: a notifier that is not running notifies nothing). The person's choice is kept in the data directory; while on, a launch from a lasting path writes the launch agent again when it opens another path (not from `/Volumes`, App Translocation or a debug build, which show no toggle), off removes it from any copy, and the menu's checkmark means the launch agent opens this copy (`reef_shell::login`, main-session review F2).
- **Bundle.** Identifier `io.github.reef-vcs.reef`, name Reef. A release bundles `reef` and `reef-daemon` (`externalBin`, decision 1). Signing as above.
- `just shell-build`, `just shell-check` (clippy, `tauri build --debug`) and `just shell-run` set `CARGO_TARGET_DIR=target/shell`, so the cache-cleaning rule removes it with the rest.

### Signing and updates (decisions 2 and 2b)

A developer's build (`just shell-build`) signs with `APPLE_SIGNING_IDENTITY`, else the keychain's first Apple Development identity, else ad hoc. A release build (`scripts/shell-build.sh release`, from `release.yml`'s macOS legs) carries that target's `reef` and `reef-daemon` and is signed ad hoc, as `Reef-<version>-<target>.dmg` beside the tarballs. There is no auto-update in R3.39: macOS pins an ad-hoc app's notification permission to its exact code (measured, decision 2b), so an update re-signed ad hoc would silently turn banners off. Auto-update arrives with Developer ID in R4.17.

### Laptop budget

Targets, measured for the PR with `ps` over 10 minutes: window closed, one process under 60 MB RSS and under 0.1 % of one core, waking once per 15 s keepalive; window open adds WebKit's processes, freed on close. On disk: the app plus the two binaries under 100 MB, `notices.json` under 1 KB, no webview data. The daemon pays one more `WatchInbox` stream on the shared board (no extra reads) and one small transaction per good read whose needs-you-now pairs changed.

### Threat model rows (S-267 to S-273)

- **S-267** A page or app opens `reef://local/<path>`: only a same-origin navigation of the person's window; the path grammar admits no scheme, host, query or escape; every route is side-effect free on load.
- **S-268** A banner's words: the daemon's headline and the repository's name only, never an agent's text (extends S-262).
- **S-269** The daemon's page calling into the app: no IPC capability is granted to its origin; navigation is pinned to it, and other origins open in the browser.
- **S-270** The session token: minted over the socket, given to the webview in process, never logged or put on a command line; a browser hand-off goes through a 0600 launch file as `reef ui` does.
- **S-271** The app starts a daemon from where an installed `reef` lives, then its bundle; never again after launch unless asked, never stopping a busy one.
- **S-272** The ad-hoc signed app: same-user code can replace it or its bundled binaries, as it can any binary on `PATH` today; no auto-update downloads code into it; Developer ID signing and notarization are R4.17's.
- **S-273** The raise ledger: numbers and keys of items already readable through `GetInbox`; no new disclosure.

## Out of scope

- **#346** (a fixed web port and the origin pinned beside each passkey): decision 4. The shell mints per daemon instance and stores no port; ceremonies go through the browser and the same origin check as today.
- Developer ID signing and notarization (R4.17, decision 2); Linux and Windows (R3.41); the phone (R3.40).
- Running a passkey ceremony inside the app (`ASWebAuthenticationSession` or the browser entitlement): a follow-up if the hand-off proves clumsy.
- Notifications for watching or landed items, per-repository mutes, quiet hours (the OS's Focus modes cover them).

## Risks

- A proposal whose commit an automatic rebase rewrites while it waits for a sign-off raises again. That is correct for a sign-off, which binds the tree; if rebases prove noisy, the cause becomes the lifecycle transition.
- Ad-hoc signing: a downloaded app is quarantined and Gatekeeper asks the person to allow it in System Settings once, and its notification permission does not survive a rebuild (decision 2b).
- Tauri's new-window hook for a remote page on macOS carries the passkey hand-off; if it does not fire, the link becomes a same-window navigation to `/handoff` that `on_navigation` catches.
- The self-hosted runner is this laptop, so the `shell` job's build competes with local work; it runs only on `main` and the `macos` label.

## Choices this brief made, and why

- **The daemon numbers what is new**, because the desktop shell, an agent on `reef inbox watch` and R3.40's push from the daemon need the same answer, and a key set kept per client either drops a revised proposal or announces again after every restart's re-judge.
- **The notifier is the shell's Rust side over the socket, not the web page**, because it must work with no window open, needs no IPC into the page, and keeps Tauri out of `web/` (ADR 0005). ADR 0091's Consequences line is amended.
- **One task in `reef-shell` owns all state**, with pure `observe`, `step` and `menu`, so the Tauri crate is adapters only and R3.40 reuses the core with a remote connection.
- **A `PATH` daemon before the bundled one**, because a newer bundled daemon that migrates the schema strands the installed CLI's daemon.
- **Ceremonies in the browser**, because WKWebView runs passkeys only for associated domains, and the browser already passes the daemon's origin check.
- **`UNUserNotificationCenter` directly**, because the Tauri plugin's macOS path cannot report permission or route clicks (spike 2).

## What later tickets inherit

- **R3.40** builds `shell/` for iOS and Android with a remote connection in `reef-shell`, drops the bundled binaries and the notifier, and pushes from the daemon's ledger: one cursor per push endpoint, items with `raised` above it, linking `/repos/:repo/items/:key`.
- **R3.41** adds Linux and Windows `Platform` notifications and the tray; `reef-shell` is unchanged.

## Departures in the implementation

Found while building it (2026-11-22):

- **No auto-update** (decision 2b): measured that macOS answers "Notifications are not allowed for this application" without asking once an ad-hoc app's code changes, even with an explicit designated requirement naming only the bundle id; a fresh ad-hoc app asks and waits. Copies under `/private/tmp` are refused at once too. `tauri-plugin-updater` and its menu rows are gone.
- **The news rule is in `reef-client`** (`reef_client::inbox::News`), not only in the shell, so `reef inbox watch` prints `new` with the same rule an agent can block on.
- **`raise_epoch` is the database's instance id**, with its restore time when restored: no new meta key, and a restored ledger, which can hand numbers out again, starts clients over.
- **The re-judge after a restart** is covered by the raise rule's tests (provisional readings) rather than an integration test with a sign-off policy, which is a follow-up.
- **A daemon restart is a new pid**, not a new `instance_id` (the database's id, which survives restarts and restores): the shell mints a session when the pid changes.
- **`raised_through` never falls on a board** below the last one's, since the newest row goes when its item is answered.
- **One ledger row per key, and provisional readings** (review rounds 1 to 4, R1.F4, R2.F4, R3.F1, R4.F1): a row per key and reason brought back an old reason's lower number when a proposal went from a sign-off to a returned landing and back. One row per key, replaced on a new reason, then announced a returned proposal twice after every daemon restart: until the automatic service's first pass it has no status and reads as returned from its lifecycle, then as needing a sign-off once judged (round 2's fix watched a `Pending` status, which is absent then and also means waiting for a job slot, so it was reverted; round 3's fix dropped the reason, which silenced a new ask on the same commit). Now a reading with no automatic status, or a `Pending` one (round 5, R5.F1: the first pass judges 16 stacks per repository and leaves the rest pending), is provisional and keeps the number its key and commit hold; with no number for its commit it numbers nothing until judged (rounds 5 to 7, R5.F2, R6.F1, R7.F1, R7.F2: rows a provisional reading wrote either took a second number at the judgment or absorbed a later ask, and announced a busy re-queue at a restart); a judged new ask is news, and the same ask again on the same commit (a second return) is not (R5.F3). Round 8 found no correctness bug; its fixes (docs, a test predicate, the limit above in ADR 0093) needed no further round.
- **`GetInbox` carries no `raised_through` or `raise_epoch`** (review round 1, R1.F1 and R1.F2): only the board task numbers items, and it runs while a stream is open, so a poller could never trust the numbers to be current, and reading the newest raise after the items could cover an item the read did not list. News is told from a stream; `reef inbox watch` is the agent's way.
- **No `Reconcile` of delivered banners after an app restart**: a banner left from an earlier run for an item handled while the app was closed stays until clicked, which opens "That no longer needs you".

## Decisions for the user

1. **Does the app bundle `reef` and `reef-daemon`?** **Answered 2026-11-22 in chat (`cmt_6458ee2351b7f6cb`): bundle.** The question offered the app's own daemon whenever none answers; the brief starts one through an installed `reef` first, when there is one, so a newer bundled daemon never migrates the schema under an older installed CLI (`DbError::TooNew`), and the app's own otherwise. *Recommended*: bundle them (about 50 MB on disk); the app uses a daemon that answers, else starts one detached through an installed `reef`, else through its own. Alternative: no bundled daemon; the app needs `reef` installed first and shows install steps when it finds none.
2. **Signing.** **Answered 2026-11-22 in chat (`cmt_66e57b49535974f0`): ad-hoc now.** *Recommended*: ad-hoc signing in this ticket (spike 3: notifications work), with Developer ID and notarization staying in R4.17. Alternative: pull Developer ID forward (an Apple Developer Program membership, a Developer ID Application certificate, notary credentials as release secrets).
3. **The update key.** Withdrawn (`cmt_615dd0e1e3942819`) once decision 2b showed an ad-hoc update loses notification permission; superseded by 2b. *Recommended*: you generate a minisign key pair (`npx @tauri-apps/cli signer generate`), the public key is committed, and the private key and its password are release secrets; until they exist the release builds the app without update artifacts. Alternative: no auto-update until R4.17.

Alternative: Developer ID signing and notarization in R3.39, and auto-update with it.
