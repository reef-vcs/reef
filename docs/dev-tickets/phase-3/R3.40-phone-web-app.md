## Context

**The goal.** A person away from their desk gets a needs-you-now notification on their phone from their own self-hosted Reef daemon, opens the exact proposal, and approves it with a passkey.

The exit criterion reads: "A human on a phone receives a needs-you-now notification, opens the proposal, and approves it" (`docs/dev-phases.md:196`). Three things stand between today and it:

1. The phone cannot hold a connection. A Home Screen app has its own storage, so it opens on "Not connected", and nothing in it can get a token.
2. The phone cannot decide. The remote listener refuses passkeys, approvals and declines, and the daemon knows one RP ID, which is the Mac's.
3. Nothing tells the phone. The daemon numbers news (R3.39), and sends it to nobody who is not connected.

**The smallest change that meets the goal.** Let a phone pair by a typed code and be a *page* of the daemon, with the same rules as the local web UI's page. Let its passkey be registered under the remote address, approved on the Mac. Send each raised item to the phone's push endpoint.

### Scope

In: pairing, a device token, the manifest, icons and service worker, the phone layout of the inbox, the proposal, the help answer and the sign-off, remote passkeys, Web Push from the raise ledger, the outbound guard, documentation of hosts and certificates.

Out: a Tauri mobile shell, App Store and Play Store distribution, a push relay, APNs (R4.13, R4.17). The store (R4.13). Laying out the smartlog, the workspaces and the activity pages for a phone beyond not breaking. Notifications for watching or landed items. Per-repository mutes and quiet hours (the phone's Focus modes cover them). Taking a conflict over from a phone. Offline reading. More than one daemon in one Home Screen app (each daemon's address is its own app).

## Design

### The shape: a paired device is a page

A **device** is a phone (or tablet) that a person paired. It holds a remote token of a third kind. A call with that token is a *page's* call. It passes the web UI's allowlist with the web UI's rules, and not the `write` scope's. Its record is the token's name, which every row and operation already has room for.

```rust
// service/mod.rs: the one question every page rule asks.
pub(crate) enum Page<'a> {
    Local(&'a web::Caller),      // a reef ui session
    Device(&'a remote::Device),  // a paired device's token
}
pub(crate) fn page_of<T>(request: &Request<T>) -> Option<Page<'_>>;

// remote/mod.rs
pub struct Device {
    pub identity_id: String,     // the person it was paired for
    pub origin: Origin,          // the address it was paired at
    pub verified: bool,          // a passkey touch within the last 10 minutes
}
pub struct Caller { /* as today */ pub device: Option<Device> }

// identity/issue.rs
enum Channel { Socket, Web { .. }, Remote { .. }, Device { token_id, token_name, identity_id, origin } }
```

The five `web_of(..).is_some()` flags become `page_of(..).is_some()`. A row a device writes records the remote token as today and no web session. `caller_of` marks the operation with the token and no agent name, as a web call names none.

### 1. Pairing

**On the Mac** (proposed, decision 7):

```
$ reef remote pair iphone
Open   https://mac.example.ts.net:7470/
Code   K7QX-9M2D          good for 10 minutes, once

On the phone: open the address in Safari, Share, Add to Home Screen, open Reef
from the Home Screen, and type the code.
```

It prints the address as a QR code on a terminal too. The QR code holds the address only, never the code. A camera opens Safari, and Safari's storage is not the app's, so a code inside the QR would pair the wrong place. JSON output when piped, as every command (ADR 0025).

- `RemoteService.StartPairing` (ADMIN, so the socket only) takes a name, an identity (empty: the default person; a person only) and a life (90 days by default). It needs `[remote] origin`, else `REMOTE_ORIGIN_REQUIRED` with the line to write.
- The code is 8 characters of Crockford base32, 40 bits, drawn by the daemon. Memory holds its blake3 digest, at most 4 at once, 10 minutes each. A restart drops them. 100 wrong codes end every pending one.
- **The phone** sends it as `authorization: Bearer reef_pair_<code>` to `RemoteService.RedeemPairing`. The gate admits a pairing code for that one method and no other, so there is still no RPC without a credential. The header is removed before the handler, and logs never hold it. A wrong code counts against the address, as a wrong token does (10 a minute, then backoff, `remote/mod.rs:109`).
- The code is taken, then the token is made, in that order, so a replay finds nothing. The answer holds the token once. The page stores it under `reef.session` in `localStorage`, where the remote page keeps its token today (`web/src/session.ts`).
- A live device token of the same name is revoked by the redeem, not by the start, so pairing again never locks a working phone out.

**The token** is a `remote_tokens` row with `scope = 'read'` and a new column `device_origin`. Code that does not know the column reads it as a `read` token, the safer reading. `TokenScope::Device` is what the pair decodes to, and `('write', device_origin)` is a load error. A device token works only at its `device_origin`. When `[remote] origin` changes, the device is told `REMOTE_ORIGIN_CHANGED` and shows the pairing form. Rotation is refused for a device (`DEVICE_TOKEN_ROTATE`), since nobody could put the new secret on the phone.

**What a device may call** (`remote/rules.rs`, a second table, checked complete against the web allowlist by a test):

| Method | Needs |
| --- | --- |
| every `ACCESS_READ` method | the token |
| `StartPasskeyRegistration`, `RegisterPasskey` | the token; the passkey then waits for the Mac |
| `RemovePasskey` | the token, and an assertion in the call |
| `RequestApproval`, `ResolveApproval` (approve) | the token, and an assertion in the approve |
| `AddEvidence` | the token, and a `user_verified` key for its approved statement |
| `MarkInboxSeen`, `SubscribePush`, `UnsubscribePush`, `StartDeviceVerification`, `VerifyDevice` | the token |
| `TransitionChange` (decline only), `CreateComment` (a note, an instruction, an answer), `UpdateInstruction` (confirm, cancel), `LandChange`, `ResolveApproval` (decline) | a person verified within 10 minutes, and the web row's rule |
| everything else | refused, `REMOTE_ACCESS_DENIED` |

**Verified within 10 minutes** (proposed, decision 1). `StartDeviceVerification` gives a challenge, single use, 2 minutes, bound to the token. It is `SHA-256(PAE("application/vnd.reef-vcs.device-verification", "verify\n<nonce>\n<token id>\n"))`, so an assertion over it approves nothing else. `VerifyDevice` checks the assertion and holds `verified_until = now + 10 min` in memory, per token. An approved sign-off sets it too, so Accept is one touch, not two. A refused write is `DEVICE_VERIFICATION_REQUIRED`. The page then runs Face ID once and sends the write again.

**What a stolen phone can do.**

| It has | It can | It cannot |
| --- | --- | --- |
| a locked phone | nothing, except read banners if previews show when locked | |
| an unlocked phone, or the token alone | read every repository, its diffs and its inbox until the token is revoked; ask for an approval page; receive pushes | answer an agent, instruct one, decline, land, sign off, add a passkey that counts |
| an unlocked phone and its passcode | pass Face ID's passcode fallback, so all a person can | change the policy without a pinned passkey, edit files, run jobs, push |

`reef remote token revoke iphone` ends the token, its streams, its verification and its push subscription within a second. The passkey is ended on the Mac, with the Mac's own passkey, or by `reef identity passkey reset`.

### 2. Passkeys on the remote origin

**The address.** A new key, `[remote] origin`, names the one address the phone opens, for example `https://mac.example.ts.net:7470`. It parses as a policy origin (`Origin::parse`, `crates/reef-policy/src/origin.rs:25`), must be `https`, and its host must be in `[remote] names`. Its host is the RP ID.

- *Which of several names?* Exactly this one. `names` stays a list of what the `Host` check accepts. A device's calls must come to this authority. Picking `names[0]` was rejected: order in a list would decide where passkeys work, and a port forward makes the port unknowable to the daemon.
- *What when the name changes?* The old passkeys stay listed, as "for https://old". They cannot be asserted at the new address, and old pins do not cover it. The phone pairs again, adds a passkey and the policy pins the new line. A change of port alone keeps the RP ID and the passkey, and moves the pin, as on the Mac (ADR 0094).

**A page's origin and RP ID travel together.** `struct PageOrigin { origin: String, rp_id: String }` comes from the channel: the run's origin and `reef.localhost` for a local page, `[remote] origin` and its host for a device. It replaces the bare `origin: &str` parameters (`identity/passkeys.rs:303`, `:389`, `:475`, `identity/approvals.rs:463`). `verify_assertion` refuses a passkey whose row names another RP ID (check `rp`) before it looks at the signature. `credential_ids`, `Approval.rp_id` and `StartPasskeyRegistration.rp_id` are the calling page's. A CLI approval opened on the phone asks for the phone's passkey.

**Adding the phone's passkey** (proposed, decision 3). The phone starts, and the Mac approves:

1. The phone calls `StartPasskeyRegistration` and `RegisterPasskey`. The daemon checks the registration under the remote RP ID and the exact origin, and stores nothing. It answers with a pending request: `pkr_<16 hex>`, expiry 10 minutes, and a 6-digit code taken from a digest of the new key and the request id.
2. The Mac's Passkeys page shows "iPhone wants to add a passkey · 481 205 · `https://mac.example.ts.net:7470`". The phone shows the same digits. The person compares and presses Approve.
3. The Mac's page asserts with an existing passkey, at `reef.localhost`, over `PasskeyChange::AddFor { registration_challenge, fingerprint }`, whose payload is `add-for\n<challenge>\n<fingerprint>\n`. The touch covers the key, not only the registration.
4. The daemon stores the passkey with its RP ID, its origin and the device's token, under the lock that every change takes (`identity/passkeys.rs:338`).

An identity with no live passkey has nothing to assert with. Then the local page's Approve needs no touch, as its first passkey needs none today, and `reef identity passkey approve pkr_…` does it on the socket for a daemon with no browser. A remote first passkey is **never** trusted on first use: a stolen device token could otherwise register its own, get `human` keys (which no remote caller can have today, `identity/issue.rs:185`), and satisfy a policy that asks for no presence.

At most 4 requests wait. `ResolvePasskeyRequest` is on the local web allowlist and, with no live passkey, the socket. It is refused to every remote caller, devices too (`PASSKEY_OVER_REMOTE`).

**Pins.** `reef identity passkey list` prints each passkey's line with its own origin. The Passkeys page shows a snippet for the passkeys of *its* RP ID, and says where to confirm the others. The phone's page confirms its own and offers Copy. A policy then holds two pins for one person:

```toml
[passkeys]
alice = [
  { fingerprint = "3c9e…", origin = "http://reef.localhost:17333" },
  { fingerprint = "a41f…", origin = "https://mac.example.ts.net:7470" },
]
```

Adding the second pin is a change to the policy file, so it needs the owners' sign-off (`builtin:owners`), which the Mac's pinned passkey gives.

**Who may do what from a phone.**

| Act | From a device | `presence` |
| --- | --- | --- |
| Accept | a touch per sign-off at the remote origin, then `LandChange`, which needs a pinned touch on the tree as through the local web (`landing/touch.rs:234`) | `user_verified` when the policy pins the phone's passkey at the remote origin |
| Decline, note, instruct, answer, confirm | a person verified within 10 minutes; recorded as actor `human`, the device's identity, and the token | not evidence, so none |
| Take a conflict over, allow a conflict | refused (`REMOTE_HUMAN_REQUIRED`), as the local web page has no such act either; the phone opens the conflict and can instruct its agent | |
| Sign off from a `read` or `write` token | refused, unchanged | |

The guards in `lifecycle/mod.rs:914`, `:1341`, `comments/mod.rs:1183`, `:1345`, `:1678`, `:1690` ask "remote, and not a verified device". `REMOTE_HUMAN_REQUIRED`'s hint drops "once R3.43 verifies them" (`lifecycle/mod.rs:430`) and names `reef remote pair`.

### 3. The web app

**Manifest and icons.** `web/public/app.webmanifest` (`name` Reef, `id` `/`, `start_url` `/`, `scope` `/`, `display` `standalone`), `apple-touch-icon.png` (180 px, no transparency) and two icons (192 and 512 px), and `viewport-fit=cover`. `crates/reef-web/build.rs` learns `webmanifest`. The remote listener serves the manifest, the icons and `sw.js`. The local listener answers 404 for them: an app installed at a run's name would be dead at the next start.

**Pairing form.** `NoSession` over `https` (`web/src/views/NoSession.tsx`) shows the code field. In a Safari tab it first shows the three Home Screen steps, and a smaller "Pair this browser instead". A pasted or typed code is upper-cased and stripped.

**The service worker** (`web/src/sw.ts`, built to `/sw.js`, under 80 lines):

- Scope `/`. It caches nothing and opens no `CacheStorage`. It never touches an API call or an asset.
- `fetch`: a navigation only. It passes it to the network. When that fails it answers a page it builds itself: "Cannot reach Reef", the address, what to check (VPN, the Mac asleep), Retry. The page holds no script from anywhere else.
- `push`: parses the message and shows it, for browsers without declarative push and for iOS before 18.4. `notificationclick`: focuses or opens the URL, which must be same-origin, else `/`.
- `install` skips waiting and `activate` claims, so a new worker is the only worker after one load. The page registers it with `updateViaCache: "none"`, only when it is `https`, paired and standalone.
- To kill it: a daemon that ships a `sw.js` which unregisters itself, or the app, which unregisters every worker when `[remote] push = false`. The person can also delete the Home Screen app.

`SECURITY_HEADERS` splits: both listeners get an explicit `worker-src`, `'none'` locally and `'self'` remotely. Locally that closes a door that is open today.

**Deep links.** Pushes and shared links use `/repos/<repo>/items/<key>` (ADR 0093 decision 9). The item route stays the one mapping. For a help request it opens `/repos/<repo>/inbox?item=<key>`, which scrolls to the request and opens its answer. A key that is gone says "That no longer needs you." (`web/src/views/ItemLink.tsx`). A cold open loads `/` for half a second first. `App` starts no stream on `/` until the next frame, so it costs one page, not two sets of streams.

**When the daemon cannot be reached at the tap**, the offline page shows with the item's address kept, and Retry opens it. Nothing is readable offline, on purpose: a phone holds no copy of the code.

### 4. Phone width

At 375 px, in the order the person meets it. Each has a Playwright check at 375 by 812.

1. **Inputs and text areas** are 16 px under 900 px (no zoom on focus). `base.css:689`, `:1927`.
2. **Disabled buttons** look disabled, everywhere (`button:disabled`: muted text, no brand fill, `cursor: not-allowed`), and the reason for Accept and Decline is under the buttons, as text, where a phone has no hover.
3. **The proposal page** shows no scrubber at any width, since a proposal is read live. `RepoFrame` passes it only to pages that read at an operation.

5. **Headings** get a top margin so that they do not touch the card above.

### 5. Push

**Subscribing** is the person's tap on "Turn on notifications", on the phone, after pairing. Nothing is asked before. `PushService.SubscribePush` takes the endpoint, `p256dh` (65 bytes, uncompressed point) and `auth` (16 bytes). It is refused unless the caller is a device. The answer says what the welcome message's delivery gave ("Notifications are on."), so the person learns at once if the path does not work.

```sql
-- 0034_push.sql, schema 32
CREATE TABLE push_subscriptions(
  id TEXT PRIMARY KEY,                       -- psh_<16 hex>
  token_id TEXT NOT NULL UNIQUE REFERENCES remote_tokens(id),
  endpoint TEXT NOT NULL UNIQUE,             -- at most 1,024 bytes, allowlisted host
  p256dh BLOB NOT NULL, auth BLOB NOT NULL,
  vapid_key TEXT NOT NULL,                   -- fingerprint of the key it was made for
  raise_epoch TEXT, raised_through INTEGER,  -- NULL until the first ready board
  created_at INTEGER NOT NULL,
  last_sent_at INTEGER, last_status INTEGER, last_error TEXT, failing_since INTEGER);
```

One per device. Subscribing again replaces it. A revoked or expired token's row is deleted by the revoke and by the expiry sweep (`remote/mod.rs:126`).

**The sender** (`push/`), one task while at least one subscription exists:

- It holds `InboxWatch::watch`, so the board runs while a phone is subscribed.
- `plan(items, through) -> Plan` is pure: the needs-you-now items with `raised > through`, in order. One to three are one message each. More is one summary that opens `/`. That is the desktop app's rule (`docs/desktop.md:34`).
- It waits 1 s for a burst to settle, sends in raise order, and moves `raised_through` after each accepted message, in the database. There is no outbox: a failed send leaves the number, and the next try works out the news again from the board. What was answered meanwhile is never sent. A crash between the send and the write sends once more, with the same `Topic`. Duplicates are possible, losses are not.
- The first ready board sets `raised_through` to the largest raise and sends nothing. Another raise epoch (a restored database) does the same.
- A phone that has the app in the foreground still gets the push. iOS decides what to show.

**The message.** One JSON for declarative and worker-shown notifications:

```json
{"web_push": 8030,
 "notification": {"title": "Needs a sign-off from owners", "body": "reef",
   "navigate": "https://mac.example.ts.net:7470/repos/a3dda866c7e8f343/items/proposal%3Aa3dd…",
   "lang": "en", "silent": false}}
```

The words are the daemon's headline and the repository's name, as the desktop's banner (S-268), never an agent's text (proposed, decision 4). The plaintext is padded to 1,024 bytes, so a push service learns nothing from its length. It is encrypted to the phone's keys (RFC 8291). Apple sees the endpoint, the time, the `Topic` and the Mac's network address. `Topic` is 32 base64url characters of an HMAC of the item key under a per-subscription secret derived from `auth`, so it names nothing. `Urgency: high`. `TTL: 43200`: an undelivered need from yesterday is noise.

**VAPID.** An ECDSA P-256 key, made once on the first subscription, `<state>/remote/push.pem`, `0600`, not in backups, as `key.pem` is not (S-45). The JWT's `sub` is the project's URL, so no personal address is sent. `aud` is the endpoint's origin. `exp` is 12 hours ahead. It is held in memory and reused for 6 hours. After a restore there is another key: the sender skips rows with another fingerprint, and the app, which compares its subscription's `applicationServerKey` at each open, subscribes again.

**Answers.** 201 and any 2xx: done. 404 and 410: the subscription is deleted, and the app says "Notifications stopped" at its next open. 429: wait `Retry-After`, at most an hour. 5xx, a timeout, no route: 30 s doubling to an hour. 400, 403, 405, 413 and 3xx: `failing`, the reason kept, tried hourly, deleted after 7 days. Nothing of an answer but its status and Apple's one-word `reason` (32 ASCII letters at most) is kept, and neither goes to the phone's page as more than words the daemon wrote.

### 6. Outbound HTTP and SSRF

A subscription's endpoint is a URL that a token holder chose, and the daemon posts to it. `outbound/` is the one way out of the daemon, shared with R3.46:

```rust
pub struct Policy { hosts: Hosts, allow_private: bool }   // push: the four vendors, never private
pub fn parse(url: &str, policy: &Policy) -> Result<Target, Refused>;   // at subscribe, and again at send
pub async fn post(target: &Target, headers, body, limits) -> Result<Answer, SendError>;
```

- **URL**: `https`, port 443, no user, no fragment, at most 1,024 bytes, a DNS name, never an IP literal. The host is exactly `fcm.googleapis.com` or `updates.push.services.mozilla.com`, or under `push.apple.com` or `notify.windows.com` (a label boundary, so `evilpush.apple.com.example` and `xpush.apple.com` fail).
- **Address**: resolved once, 5 s. If any answer is not a public unicast address the request is refused, whatever the others are: loopback, private, carrier-grade NAT (which Tailscale uses), link-local (which the cloud metadata services use), unique-local, multicast, documentation, benchmarking, mapped and NAT64 forms by their inner address. The connection goes to the checked address, so a second lookup cannot change it.
- **Connection**: TLS 1.2 or 1.3 with the operating system's roots and the URL's name. No proxy variable is read. No redirect is followed: a 3xx is a failure.
- **Limits**: 10 s in all, 4 KiB of answer read and dropped, 4 sends at once, 1 per subscription, 256 subscriptions (the token limit, `remote/mod.rs:121`), 60 messages an hour per subscription, then one summary.
- **Nothing returned**: no RPC carries an answer's body or headers.

The HTTP exchange itself is `reef-client`'s (`crates/reef-client/src/keyless.rs:347` to `:475`), moved to `reef_client::http` with the connection passed in and `Retry-After` read.

**What changes in trust.** Today the daemon opens no connection of its own: only the user's git does, when asked or when a policy pushes. With one phone subscribed the daemon calls that phone's push service by itself, with a time, a size and its network address, and an encrypted body. Off until then. `[remote] push = false` refuses subscriptions, deletes the rows and stops the sender (proposed, decision 5: available by default once `[remote] origin` is set, since a person must still opt in on a paired phone).

### 7. Certificates and host names

`docs/phone.md` gives three ways, each with exact commands and how it renews (proposed, decision 6: Tailscale first).

| Way | Trusted by the phone | Renewal | Costs |
| --- | --- | --- | --- |
| Tailscale: `tailscale cert <name>`, files in `[remote] tls_cert` and `tls_key`, `listen` on the tailnet address | yes, Let's Encrypt | 90 days, and Tailscale says that renewing files is yours: a weekly job runs `tailscale cert` again. The daemon reloads within a minute | an account, the app on the phone, the machine's name in public certificate logs |
| Your own domain with DNS-01 (any ACME client) | yes | the client's timer; the daemon reloads | a domain, an API key for its DNS, a route from the phone |

The generated certificate does not work in a Home Screen app: an exception made in Safari does not carry over. `reef remote pair` says so when the certificate is generated. `reef remote show` prints the days left, and `reef daemon status` warns under 14. `ts.net` is on the public suffix list, so the RP ID is the machine's full name and another machine of the tailnet cannot claim it. `tailscale serve` as a TLS proxy is not documented: every client would share one peer address and one backoff.

### 8. What the remote origin does not close

ADR 0094 says that an `https` origin "served outside that uid" closes S-274. On a person's own Mac it is not outside. The TLS key is a file that the same user reads, and an agent running as the user can stop the daemon and serve the pinned origin to the phone. Worse than on the Mac, the address cannot change at every start, so a service worker that such a page registers stays until the Home Screen app is deleted. The brief does not claim otherwise (S-280, S-281). A daemon on another machine, or under another uid, closes both. `docs/phone.md` says it in one paragraph, and the policy recipe shows how to pin the Mac's passkey only for `[owners]`.

## Alternatives

- **A Tauri mobile shell** (the row today). Measured: a WKWebView has neither the Push API nor passkeys, so the shell would be native push plus native passkeys around a web view, an Apple account and a store review. Decided against.
- **A `write` token on the phone.** Works today for answering. It also edits files and runs jobs from anywhere, and it still cannot sign, decline or be told of news.
- **A fifth scope string in the `scope` column.** The `CHECK` would need the table rebuilt, and an unknown scope read by old code is an error instead of a `read` token.
- **Passkey sign-in instead of a device token.** Discoverable passkeys would give short sessions with no stored secret. The passkey must be registered first, which needs pairing anyway, and a push subscription needs something lasting to hang on. Renewing a device with its passkey is a follow-up.
- **A pairing code in the QR, carried by a dynamic `start_url`.** Nothing to type. It puts a secret in a URL that Safari keeps, and depends on when iOS reads the manifest.
- **First remote passkey trusted on first use.** One step fewer. A stolen token becomes a person wherever a policy asks for no presence.
- **The raise numbers kept per repository and endpoint** (`News`). The stream needs that. The board does not, and one number is one column. The one difference is that a repository registered later, with items already waiting, is told once on the phone and not on the desktop.
- **An outbox table of messages to send.** It keeps what was answered meanwhile and needs its own pruning. Working out the news from the board each time needs one number.
- **`web-push` or `web-push-native`.** More dependencies than the 47 lines they replace.
- **`hyper` as a dependency.** `reef-client` already holds the 120 lines needed.
- **Caching the app shell in the worker.** Faster cold opens, and a second place where an old page, or an attacker's, lives.
- **No service worker at all.** On iOS 18.4 a declarative push needs none. Then an unreachable daemon shows the system's error page, and Android shows no notification.
- **Deriving the RP ID from `names[0]`.** See section 2.

## Manual verification

**The exit criterion, once, with the user, after pull request 3.** Recorded in the pull request's table with the iOS version, and in `docs/phone.md`'s tested line. If #222's manual evidence exists by then, it is added to the change as well.

## Risks

- **The real iPhone check fails** at a step the Simulator could not show. It runs before pull request 3 for that reason, and nothing in 1 or 2 depends on push.
- **iOS changes what a Home Screen app may do**, as in the EU in 2024. The app then still works in a Safari tab, without push.
- **A MacBook asleep** sends nothing and answers nothing. The raise is sent when it wakes. `docs/phone.md` says so, and a daemon on a machine that stays up is the answer.
- **The 10-minute window is a nuisance** for someone who answers all day. The number is one constant.
- **Pull request 2 touches the guards of five services.** `page_of` is one function, the device table is checked against the web table, and test 28 lists the refusals.
- **Corporate networks** that only allow a proxy get no push, since no proxy variable is read.
- **Android** is expected to work (the worker shows the message) and is not tested by hand.

## Decisions for the user (each recommendation accepted, 2026-11-23)

In priority order, with the alternatives as asked.

1. **What may a paired phone do without a fresh touch?** *Recommended*: read only. Answering an agent, instructing, declining and asking to land need Face ID within the last 10 minutes, and each Accept has its own touch. An answer steers an agent that runs commands on your machine, so a stolen token must not give one. Alternatives: the token alone decides, as a browser session on the Mac does (no prompts; a leaked token steers agents from anywhere); a touch for every act (safest; a prompt per comment).
2. **One pull request or three?** *Recommended*: three, read then (decide and push, in parallel), so that each is reviewable and you use the phone after the first. Alternatives: one (one review of about 6,900 lines, all or nothing); push before passkeys (you are told sooner and walk to the Mac to act).
3. **How does the phone's passkey get in?** *Recommended*: the phone asks, and your Mac approves with its own passkey after you compare six digits. Alternatives: the pairing code is enough (one step fewer; whoever sees the code adds a passkey); first use on the phone (none; a stolen token becomes a person where a policy asks for no presence).
4. **What does the lock screen say?** *Recommended*: what the desktop banner says: "Needs a sign-off from owners", and the repository's name. Alternatives: only "Needs you now" (nothing leaks, every banner looks the same); the proposal's title as well (useful, and agents write it).
5. **Push available by default, or off until a setting?** *Recommended*: available once `[remote] origin` is set, to Apple, Google, Mozilla and Microsoft. Nothing is contacted until you turn it on, on the phone. Alternatives: `push = false` by default (one more step); Apple only (smaller; Android gets nothing).
6. **Does the documentation recommend Tailscale?** *Recommended*: yes, first of three. It needs no open port and no domain, and it is the one you will have tested. The other two follow with their costs. Alternatives: three equal ways (neutral; a reader must choose without knowing); your own domain first (no third party in the path; hardest to set up).
7. **How long does a phone stay paired, and how does it pair?** *Recommended*: an 8-character code typed once, and 90 days. Alternatives: 30 days, as other tokens (pair monthly); until revoked (never again; a forgotten phone reads forever); a code in a QR (nothing typed; the secret sits in a URL that Safari keeps, and depends on iOS details we have not tested).
