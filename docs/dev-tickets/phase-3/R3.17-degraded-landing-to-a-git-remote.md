# R3.17 Degraded landing to a git remote

Phase 3 · Size M, at its top end (decision 1) · Depends on: R3.16 (the destination is the projection, `[history]`, `builtin:description`), #258 (`reef_lib::jj::push`: `plan_push`, `push`, `record_push`, the environment, the classification; the daemon's `publish` module: the branch lock, the timeout, R1.16's marking), and builds on R3.13 (`LandChange`, the gate, landing rows, `settled`), R3.14 (batches, the base read, "the destination moved"), #259 (`reef_lib::jj::fetch`, the daemon's `fetch` module, the observer that follows trunk), R2.08 (remote rules), R2.16 (GC's operation-id map) · Unblocks: R4.14 (makes this push native), R4.16 (exports the same history)

## Context

The design's roadmap promises phase three "a degraded form against a git remote": the landing service lands locally, and a team on GitHub sees landed history, while evidence, provenance and conflicts stay on the machine. Federation: "Humans review on GitHub and will for the foreseeable future … one person on a team can use the new system against a repository nobody else has heard of."

Every earlier ticket left something here:

- **#258** built the one push path for this ticket to reuse: "R3.17 calls `plan_push`, `push` and `record_push` with a landing mode: the destination's branch, fast-forward only, no hint; conflicted changes are already refused" (ADR 0070 decision 9). `reef publish` refuses trunk's branch on purpose: "Landing on `main` is `reef land` and R3.17."
- **#259**: "R3.17 fetches the destination before pushing landed history through `reef_lib::jj::fetch`." Its fetch fast-forwards (or merges) a tracked local bookmark.
- **R3.13** and `docs/landing.md`: "A local `main` that also follows a git host diverges from it after a landing, and a later `jj git fetch` that moved `main@origin` can leave it conflicted: … wait for R3.17." "R3.17 pushes after a landing and refuses conflicted changes."
- **R3.16** and ADR 0075: "R3.17 pushes the destination as the projection wrote it"; "Trailer keys are a public format from R3.17 on"; S-192 (names and emails leave through trailers) is "fixed by default" because only ids are written. "Following a forge's squash merge by its `Reef-Change` trailer (R3.17)" and R3.09's "R3.17 is where Reef learns to follow such landings" are both promises this brief decides on (decision 11).
- **R3.04**: "A git push (R3.17) … carries no provenance": nothing of provenance is in a commit.
- Open follow-ups of R3.16: #295 (author from the proposer), #296 (signed projected commits: a host that requires signatures refuses this ticket's push), #297 (a landing settled at start records no history; folded into this ticket by decision 11).

The direction since 2026-11-09: agents are the users; full compatibility with git remotes and workflows, without hooking Reef further into git inside workspaces. Landing stays local-first: a push failure never undoes or blocks a local landing. Laptop resources are an acceptance criterion.

So this ticket builds:

1. **A landing mode of the push path**: plan the destination's head against its remote branch, fast-forward only, conflicts refused; record without touching the local bookmark.
2. **The push worker**: one per (repository, destination) that pushes, after each landing operation, the destination's head; it retries an unreachable remote with backoff, and when the remote moved it fetches and either finds nothing to do, follows the remote fast-forward, or stops as `diverged`.
3. **Fetching before a batch** for a pushing destination, and a fetch that never conflicts a pushing destination.
4. **The configuration**: `[landing] push = "<remote>"` in the destination's policy, and the operator's `[publish] landings` switch.
5. **The record and the surface**: schema 20, API revision 34, `reef landing push|pushes`, the push state in `reef land`, `reef landing show`, `reef here` and `reef daemon status`.

### What was verified while writing this ticket

Reef at `f392192c` (API revision 32, `reef-api/src/lib.rs:49`; schema 18, migrations up to `0018_history.sql`; ADR 0075 the latest; the threat model's last row S-195). PR #300 (#272) is open and takes API revision 33, schema 19 (`0019_workspace_disk.sql`), ADR 0076 and S-196 to S-199, and edits `daemon.proto`; this ticket plans **API revision 34**, **schema 20** (`0020_landing_pushes.sql`), **ADR 0077** and **S-200 to S-206**, renumbered at rebase. Paths are under `crates/` unless they start with `docs/` or `web/`.

- **The push path** (`reef-lib/src/jj/push.rs`). `plan_push` (`:558`) starts from `rewrite::writable`, which refuses an immutable revision, so a landed commit cannot be planned as it stands. `check_publishable` (`:829`) refuses trunk's branch, the remote's HEAD branch, an immutable branch and git's checked-out branch: everything a landing destination is. `range` (`:730`) is `::C ~ ::(remote's bookmark targets | root())` with the 1,000 cap; `check_range` (`:763`) checks description, conflict, divergence, identity, default author and other workspaces' working copies. `push` (`:934`) runs `push_refs` on a dropped transaction with the lease `previous` and maps a lease failure to `PushError::Moved`. `record_push` (`:1252`) sets the remote bookmark **Tracked** and the local bookmark of the branch's name. The daemon's `publish/mod.rs` holds a per-(repository, remote, branch) lock from plan to record, runs the push in a task that owns it, waits at most `[publish] timeout` and marks the lock `stuck` past it, then marks R1.16's rows.
- **The fetch path** (`reef-lib/src/jj/fetch.rs`). `record_fetch` (`:337`) replays jj's import: for a tracked remote bookmark it calls `merge_local_bookmark(name, base, new)` (`:416`) with `merge_base` (`:448`), except git's checked-out branch (S-183). The daemon's `fetch.rs` has the same lock, task and timeout shape per (repository, remote). Fetches run only on request (`reef fetch`, `reef rebase`); nothing in the daemon fetches by itself.
- **Spike 1, crash between push and record** (git 2.50.1, jj 0.47.1, a bare repository as the remote, scratch only). With the remote already at the commit being pushed and a stale lease, `git push --porcelain --force-with-lease=refs/heads/main:<old>` reports `=` (`[up to date]`) and exits 0: git checks the lease only for a ref it would update. `jj git push -b main` after `jj op restore` to before its push does the same and records `main@origin`. So a push whose record was lost is repaired by pushing again, with no fetch.
- **Spike 2, a foreign push.** A commit pushed to the remote's `main` by another clone, while the local `main` has an unpushed landed commit: the push with the stale lease is rejected (`stale info`), which jj-lib reports as rejected (`PushError::Moved`). Then `jj git fetch` with `main@origin` **tracked** leaves the local `main` **conflicted** (landed commit and foreign commit as adds, the old remote target as the removal), which R3.13 refuses as `DestinationConflicted`. Reef's `record_fetch` replays the same merge, so `reef rebase` or `reef fetch` after a foreign push would stop every landing onto `main`. With `main@origin` untracked, the fetch leaves the local bookmark alone.
- **Tracking state varies.** In a scratch clone, `jj git init --colocate` left `main@origin` untracked; in Reef's own repository it is tracked. Both occur in practice.
- **Spike 3, cost.** A one-commit push to a local bare repository: 0.23 s wall, 0.08 s CPU; a no-op push 0.04 s. An unreachable SSH host with `ConnectTimeout` costs the timeout in wall time and almost no CPU; git's stderr `Operation timed out` is classified `GIT_UNREACHABLE` by #258's table.
- **Where a landing finishes.** `land_prefix_part` (`reef-daemon/src/landing/batch.rs:1395`) writes one `land` operation per landed prefix, then finishes each member's landing row (`finish_landing`) and calls `state.landings.notify_finished()`. A landing cut short by a stop is finished at start by `settled` (`landing/worker.rs:192`). The batch reads the destination's policy once at its base (`batch.rs:329`, `policy.landing()` and `policy.history()`).
- **Policy.** `[landing]` is `LandingSettings` (`reef-policy/src/format.rs:425`: `checks`, `batch_max`, `batch_wait`, `alone`), strict. `builtin:description` (`reef-policy/src/eval.rs:472`) applies only when `[history]` summarizes. `reef.toml` is repository content any change may edit without the owners; `reef-policy.toml` changes need the owners' sign-off and land alone (S-146).
- **Trunk.** Reef's `trunk()` is the local `main` first (`reef-lib/src/jj/revset.rs:94`), so a landed commit is in `trunk()` and `immutable()` as soon as it lands; pushing changes neither.
- **The proto.** `Landing` ends at field 21 (`history`), `LandingReason` at 10 (`EMPTY`), `LandingService` has five RPCs (`landing.proto`). Remote rules: `LandChange` is `Rule::None`; `PublishChange` and `FetchGitRemote` are `Rule::SocketOnly` (`remote/rules.rs:113`, `:140`).
- **Surfaces.** MCP has no landing tool; `wait_for_operations` and `list_operations` already take kind `publish`. The web UI shows no landings; it names operation kinds in `web/src/ui/words.ts`.

### What a pushing destination is (decision 2)

A destination **pushes** when the policy at its head says so:

```toml
[landing]                 # in reef-policy.toml, at the destination's head
push = "origin"           # after each landing, push this branch to that git remote
```

- `push` names a remote configured in the repository's git config, never a URL: `[A-Za-z0-9][A-Za-z0-9._-]{0,99}`, not `git` (the same rule as #258's `check_remote`, repeated in reef-policy, which does not depend on reef-lib). An invalid name is a policy error with its line and column, so nothing lands until it is fixed.
- **The branch is the destination's own name**: local `main` pushes to `origin/main`. No override: "fast-forward only onto the destination's own branch", and one less way to aim landed history at a branch someone else owns.
- **The policy, not daemon configuration or `reef.toml`**: where landed code goes is a governance decision, so it changes only through a policy change the owners sign off and that lands alone (S-146); it is per destination because the policy is; it travels with the repository. Every clone's daemon that lands onto the branch pushes it; the lease keeps two of them honest.
- **The policy read is at the head being pushed**, so the landing that adds `push` is itself pushed, and the landing that removes it is the last one pushed (the row is then deleted).
- **The operator** keeps #258's switches, which govern every push of the one path: `[publish] enabled = false` and `[publish] remotes` apply here too, and a new `[publish] landings` (default `true`) turns off only landing pushes. A destination whose push is switched off still lands; its push state reads `disabled`.

`reef policy init` writes the key commented out (`# push = "origin"`), since the starter cannot know the remote.

### When the push happens (decision 3)

**After the land operation, in the background.** Each landed prefix wakes the push worker of (repository, destination) after its rows are written (`land_prefix_part`, next to `notify_finished`). The worker:

1. reads the destination's head `H` and the policy there; no `push` → deletes the row and stops;
2. takes #258's branch lock for (repository, remote, branch) and pushes `H` through the shared push-and-record (below);
3. updates the row, sets `pushed_at` on every landing the push carried, and stops when `H` has not moved meanwhile, else loops.

Pushes **coalesce**: whatever landed while a push ran goes in the next one, so a batch of eight is one push, and ten landings during an outage are one push when the remote comes back. A landing never waits for the push, and a push never holds the create lock or the repository thread across the network (#258's rule).

**`reef land` reports it.** After the change lands, `reef land` keeps waiting, within its own wait (2 minutes by default), for the first push that covers the landing, and prints its state. The exit code is the landing's: 0 when landed, whatever the push did. JSON has `landing.push`.

Not built (alternatives): pushing **inside** the landing before moving the bookmark (a merge queue's semantics, where the remote is the truth): a push failure would block the local landing, which the direction rules out. A **synchronous** push in `LandChange`: an offline laptop would hang every `reef land` for the timeout.

### What is pushed (decision 4)

`plan_landed_push(repo, destination, remote, allowed, max)` in `reef_lib::jj::push`, beside `plan_push`, sharing `choose_remote`, `check_branch`, `range` and the lease:

| Case (`H` the local destination, `T` the view's `<branch>@<remote>`) | Update | Network |
| --- | --- | --- |
| `H` absent or conflicted | refused, `DESTINATION_NOT_FOUND` or `DESTINATION_CONFLICTED` (R3.13's reasons) | none |
| `T` conflicted | refused, `BRANCH_CONFLICTED` | none |
| `T` is `H` | `UP_TO_DATE`: nothing is pushed | none |
| `T` absent | `CREATED`, lease "must not exist" | push |
| `T` an ancestor of `H` | `FAST_FORWARD`, lease `T` | push |
| `H` an ancestor of `T` | `REMOTE_AHEAD`: follow (decision 5) | none |
| otherwise | `DIVERGED` (decision 5) | none |

- **The range** is #258's `::H ~ ::(the remote's bookmark targets | root())`, newest first, at most 1,000 commits (`RANGE_TOO_LARGE`, refused; the hint says to push the branch's history once with git: `git push <remote> <H>:refs/heads/<branch>`). Each commit of it is checked for **conflicts** (`CHANGE_CONFLICTED`, refused): a landing never writes one, but a person's `jj bookmark set` could put one there.
- **Not checked at push time**: immutability, trunk, the remote's HEAD branch and git's checked-out branch (it is the destination, by definition); other workspaces' working copies (a landing moves workspaces off what it lands); descriptions and authors (below). A check that fails on a landed commit could never be fixed without rewriting the published history, so the checks that matter run **at the gate**, where the change can still be fixed:
  - **`builtin:description`** applies when the destination summarizes (R3.16) **or pushes**: an undescribed change is blocked before it can reach the host as `(no commit message)`.
  - **`IDENTITY_UNSET`**: `LandChange` onto a pushing destination is refused (`FAILED_PRECONDITION`, no landing row) while the daemon's `[identity]` is the default, with #258's hint; the push refuses the same (`refused`), for changes queued before a restart unset it.
  - **Authors are not checked per commit** (decision 4's alternative): a change written before `[identity]` was set carries `reef <reef@host>` to the host. `docs/landing.md` says to `reef describe --reset-author` before proposing; a free rule over `change.author` can require it.
- **No tags**, no other branches, no pull-request hint, and never `force`.
- **What reaches the host** is exactly the projection: commits, trees, descriptions with R3.16's trailers, jj's `change-id` header. Evidence, provenance, conflicts, the operation log and the queued commits stay local.

### When the remote moved (decision 5)

The lease is the view's `T`, Reef's last-known position, as in #258. A rejected lease (`PushError::Moved`) means someone else wrote the branch. The worker then **fetches the branch** through `crate::fetch` (the destination listed as followed, below), plans again on the new view, and:

| After the fetch | What happens |
| --- | --- |
| the remote is at `H` | `UP_TO_DATE`: recorded, nothing pushed |
| the remote is an ancestor of `H` (it was rewound) | pushed once more with the new lease |
| `H` is an ancestor of the remote (someone pushed on top of what Reef pushed, or a pull request merged on the host) | **followed**: the fetch's record fast-forwarded the local destination; nothing to push. Refused instead, `REMOTE_POLICY_CHANGED`, when the policy files' blobs (`reef-policy.toml`, `reef-checks.toml`) differ between `H` and the remote's head (S-201) |
| neither | **`diverged`**: pushing paused for this destination |

**Diverged** is reported, not repaired. The row records the remote's head (id, author, title, sanitized as #258's `foreign`), and the count of landed changes not on the remote. Landings onto the destination **continue locally** (the direction: a push failure never blocks a landing); each new landing tries the push once more (after the batch's fetch, decision 6), so the state clears by itself if someone resets the remote. The hint says what happened and the two ways out, both a person's: make the remote include the local landings (rebase the unpushed landed commits onto the remote's head with jj, `jj rebase -b <destination> -d <destination>@<remote> --ignore-immutable`, then `reef landing push`), or make the local destination the remote's (`jj bookmark set <destination> -r <destination>@<remote>`, then land the unpushed changes again). `next` is `reef landing pushes`.

Not built (alternatives): **re-landing** the unpushed changes onto the remote's head automatically or by a command (`reef landing reland`): their rebased trees were never judged, so it needs R3.14's batch machinery against a new base, about 400 lines, a follow-up issue. **Blocking landings** while diverged: the person's fix is the same, and agents would stop on a problem they cannot fix. **`--force`**: would erase what someone else pushed.

### Fetching before a batch (decision 6)

When the destination pushes, the batch fetches its branch from the push remote **before it forms** (before the base read at `batch.rs:329`), so a pull request merged on the host since the last landing is followed and the batch lands on top of it instead of diverging:

- through `crate::fetch::fetch` with the destination followed; bounded by 30 s (or `[fetch] timeout` if lower);
- skipped when `[fetch] enabled` is false, when the push state is `retrying` for an unreachable remote or failed authentication and its next attempt is in the future (the laptop is known to be offline), and when the destination was fetched or pushed less than 30 s ago;
- **a failed fetch is a note on the batch, never a refusal**: the batch lands on the local head.

Following moves the destination in the fetch's operation; R3.14 already treats a destination that moved as a new base, and #259's observer then moves workspaces on landed commits and R3.09's records proposals whose commits arrived (a merge-commit or fast-forward merge on the host).

### Following, and a fetch that never conflicts the destination (decision 7)

- **`record_fetch` takes a list of followed bookmarks** (`follow: &[String]`): for each, the local bookmark is fast-forwarded when it is an ancestor of the fetched commit and the policy files are unchanged, and otherwise left exactly as it is, never merged into a conflict, tracked or not. `RecordedBranch` gains `left: Option<Left>` (`diverged`, `policy`). Every Reef fetch (`reef fetch`, `reef rebase`'s, the worker's, the batch's) passes the repository's pushing destinations (the rows of `destination_pushes`), so spike 2's conflict cannot come from Reef. Other bookmarks keep #259's behaviour, and `record_matches_jj` still holds for them.
- **The landing-mode record keeps the remote bookmark's tracking state**: it sets `<branch>@<remote>` to the pushed commit as `Tracked` if it was tracked, otherwise as not tracked (`New`), and never touches the local bookmark (it is `H`). #258's record tracks, which makes jj's own `jj git fetch` merge the local bookmark; an untracked one leaves a jj user's fetch harmless too. A jj user's `jj git fetch` on an already tracked `main@origin` can still conflict it, as today; `docs/landing.md` says to untrack it (`jj bookmark untrack main@origin`).
- Following moves the destination even when it is git's checked-out branch in a colocated root: a landing already moves it there (R3.13), and leaving it would turn every followed merge into `diverged`. `docs/landing.md` keeps R3.13's advice not to keep the destination checked out at the root.

**No loop.** Pushes start from landings, the start sweep and `reef landing push`; fetches from batches, rejected pushes (once per attempt) and requests. A push writes only `<branch>@<remote>`, which neither moves `trunk()` nor wakes anything that fetches; a follow moves the destination, which wakes the observer (workspaces, observed landings) and the batch's "destination moved", never the push worker, whose head then equals the remote. A test asserts it (test 13).

### Retries, offline and failures (decision 8)

| Failure | State | Next attempt |
| --- | --- | --- |
| `GIT_UNREACHABLE`, `GIT_PUSH_FAILED`, `PUBLISH_TIMEOUT`, `PUBLISH_IN_PROGRESS` (`UNAVAILABLE`) | `retrying` | 30 s, doubling to 15 min; a new landing tries at once if the last attempt is 30 s old |
| `GIT_AUTH_FAILED`, `GIT_NOT_FOUND` | `retrying` | 15 min (the fix is outside Reef); `reef landing push` at once |
| `REMOTE_REJECTED` (a protected branch, a host requiring signed commits, #296), `CHANGE_CONFLICTED`, `RANGE_TOO_LARGE`, `IDENTITY_UNSET`, `GIT_REMOTE_NOT_FOUND`, `GIT_REMOTE_NOT_ALLOWED`, `BRANCH_CONFLICTED`, `DESTINATION_CONFLICTED`, `REMOTE_POLICY_CHANGED`, `GIT_TOO_OLD` | `refused` | the next landing, `reef landing push`, or a start |
| a moved remote that diverged | `diverged` | the same |
| `[publish] enabled`, `landings` or `remotes` | `disabled` | when the configuration allows it (a restart) |

Each failure keeps #258's reason, its redacted stderr (last 2,048 bytes), `hint` and `next`, in the row. Nothing polls: there is no timer without a failure, and a destination that is `pushed` costs nothing until its next landing. Backoff state is the row's `attempts` and `next_attempt_at`, so a restart resumes it rather than hammering an unreachable host.

**Crashes.** At start, every row whose destination's head differs from its remote bookmark (or whose state is not `pushed`) wakes its worker; `settled` (a landing finished at start) upserts the row as a landing does. A crash between the land and the push is therefore pushed at the next start; a crash between the push and its record is pushed again and reads `UP_TO_DATE` at git (spike 1), then recorded. The timeout's `stuck` lock is #258's.

### The record: schema 20 (decision 9)

Migration `0020_landing_pushes.sql`:

```sql
-- R3.17: pushing landed history (ADR 0077). destination_pushes is one row per (repository,
-- destination) whose policy pushes it: where it pushes, its state (pushed pending retrying
-- diverged refused disabled), the local and remote commits as last seen, the last failure
-- (reason, message, git's redacted stderr), the retry schedule, and the last successful push.
-- landings gains when a push first carried the landed commit, and that push's operation.
CREATE TABLE destination_pushes(repo_id TEXT NOT NULL, destination TEXT NOT NULL,
             git_remote TEXT NOT NULL, branch TEXT NOT NULL,
             state TEXT NOT NULL,
             local_commit TEXT, remote_commit TEXT, unpushed_count INTEGER NOT NULL DEFAULT 0,
             reason TEXT, message TEXT, git_stderr TEXT, remote_head TEXT,  -- JSON, when diverged
             attempts INTEGER NOT NULL DEFAULT 0, next_attempt_at INTEGER,
             pushed_at INTEGER, operation_id TEXT, operation_collected INTEGER NOT NULL DEFAULT 0,
             updated_at INTEGER NOT NULL,
             PRIMARY KEY (repo_id, destination)) WITHOUT ROWID;
ALTER TABLE landings ADD COLUMN pushed_at INTEGER;
ALTER TABLE landings ADD COLUMN push_operation_id TEXT;
CREATE INDEX landings_unpushed ON landings(repo_id, destination)
             WHERE outcome = 'landed' AND pushed_at IS NULL;
```

- One row per destination, not per attempt: an outage of a day is one row, not a hundred. The history of pushes is the operation log (each a `publish` operation with its bookmark effect), bounded by GC like every other write's; a landing's own `pushed_at` and `push_operation_id` last as long as the landing row.
- After a push (or an `UP_TO_DATE` record), the landings of that destination with `pushed_at` null whose `destination_after` is in `::H` get the push's time and operation, in chunks of 500 (one revset each). The first push of a destination that landed before this ticket marks its older landings too, which is true.
- GC maps `operation_id` and `push_operation_id` through its rewrite and sets `operation_collected`, as for landings. `repo forget` deletes the rows; backups copy them.

**The operation** is #258's kind `publish`, not undoable, described `reef: push landed main to origin/main (3 commits)` (a new prefix `PUSH_LANDED_PREFIX`, classified as `Publish`), with no workspace and actor `DAEMON`. R1.16: `mark_published` and `published_commits` run on the pushed range as for a publish. No new operation kind.

### Credentials, and who may cause a push (decision 12)

- Credentials and environment are #258's, unchanged: the daemon's environment and the user's git configuration, every prompt off, `--no-verify` (no hooks).
- **A landing requested through the remote listener pushes**, since the destination's signed policy, not the caller, decides that it pushes, where, and only fast-forward (S-200). `LandChange` stays `Rule::None`.
- `PushLanded` (push now) is `Rule::SocketOnly`, as `PublishChange` and `FetchGitRemote` are: it is a person's or local agent's lever. `ListPushes` is `READ`.

### The API: revision 34 (decision 10)

In `landing.proto`:

```proto
// Whether a destination's landed history is on its git remote (R3.17).
enum PushState {
  PUSH_STATE_UNSPECIFIED = 0;  // the destination does not push
  PUSH_STATE_PUSHED = 1;       // the remote branch is at the destination's head
  PUSH_STATE_PENDING = 2;      // a push is due or running
  PUSH_STATE_RETRYING = 3;     // the last attempt failed for a reason that may pass; next_attempt_at
  PUSH_STATE_DIVERGED = 4;     // the remote has commits the destination lacks, and lacks some it has
  PUSH_STATE_REFUSED = 5;      // a person must act: reason, hint, next
  PUSH_STATE_DISABLED = 6;     // the daemon's [publish] configuration turns it off
}
message DestinationPush {
  string repo = 1; string destination = 2; string git_remote = 3; string branch = 4;
  PushState state = 5;
  string local_commit_id = 6;          // the destination's head
  string remote_commit_id = 7;         // the remote branch as Reef last saw it; empty when absent
  uint32 unpushed_count = 8;           // landings not yet on the remote, at most 1000
  string reason = 9;                   // the failure's reason constant (#258's, or REMOTE_POLICY_CHANGED)
  string message = 10; string git_stderr = 11;  // redacted, at most 2048 bytes
  string hint = 12; repeated string next = 13;  // argv, quoted by the client
  string remote_head = 14;             // diverged: "<id> <author>: <title>", sanitized
  uint32 attempts = 15;
  google.protobuf.Timestamp next_attempt_at = 16;
  google.protobuf.Timestamp pushed_at = 17;    // the last successful push
  string operation_id = 18;            // its operation
  google.protobuf.Timestamp updated_at = 19;
}
message LandingPush {                  // on a landed landing
  PushState state = 1;                 // PUSHED once a push carried it, else the destination's
  string git_remote = 2; string branch = 3;
```

## Implementation notes

- **Order**: reef-policy (4); `plan_landed_push` and the record (1, 2); `record_fetch`'s follow (3); the migration and rows; the extracted push-and-record; the worker (5, 6, 10 to 13); the batch's fetch and following (7 to 9); the gate and switches (14); the API and CLI (15); the documents.
- **The worker is not the landing worker.** It never holds the landing worker's claim or the lifecycle lock; it takes the create lock shared only inside #258's plan and record jobs, and the branch lock across the push. A landing that runs meanwhile moves `H`, and the worker loops.
- **The fetch on a moved remote** goes through `crate::fetch::fetch` (the per-remote lock, the timeout, the replayed import), never a second fetch path.
- **Lock order**: the fetch lock (repository, remote) is never taken while holding the branch lock; on `Moved`, the worker releases the branch lock, fetches, and plans again under it.
- **Linux**: nothing is `cfg(target_os = "linux")`; tests run on both CI runners.

## Performance and laptop cost

- **No new process at rest, no polling, no watcher.** A pushing destination costs one git process per push (spike 3: about 0.25 s wall and 0.08 s CPU against a local remote; the network dominates against a host), coalesced across a batch and across landings during a push.
- **One fetch per batch** on a pushing destination (skipped within 30 s of the last fetch or push, and while offline), plus one per rejected push.
- **Offline**: one attempt at 30 s, 1, 2, 4, 8, then every 15 minutes: at most four short-lived git processes an hour per destination, each failing in milliseconds (DNS) or idle for ssh's 30 s `ConnectTimeout`; no thread is held between attempts.
- **Memory**: one tokio task per destination with work, which ends when the destination is pushed.
- **Disk**: one row per pushing destination, two columns per landing; no new objects (the pushed commits exist already). A landing of 8 changes stays within R3.14's "< 600 ms" (the push is after it).

## Out of scope

- **Deleting a published review branch** after its change lands: a follow-up issue.

## Risks

- **Divergence needs a person.** A team that merges on the host and lands with Reef diverges whenever a merge lands between a batch's fetch and its push. Mitigated by the fetch before each batch, the loud state and both recipes; the re-land follow-up removes the step.
- **Following brings in commits nobody judged.** Mitigated by the policy-file check and S-201's documentation; the host's branch protection is the real control.
- **A jj user's own `jj git fetch`** on a tracked `main@origin` can still conflict the destination. Mitigated: Reef records it untracked when it was, and `docs/landing.md` says to untrack it.
- **Background failures are easy to miss.** Mitigated by `reef land`'s line, `reef here`, `reef daemon status` and `reef landing pushes`.
- **Numbers** collide with #300's at rebase (API 33, schema 19, ADR 0076, S-196 to S-199, `daemon.proto`); renumbered then.

## Choices this brief made, and why

- **The policy names the remote**, because where landed code goes is the owners' decision and the policy is already per destination.
- **Push after, in the background, coalesced**, because landing is local-first and an offline laptop must keep landing.
- **Checks at the gate, conflicts at the push**, because a landed commit cannot be fixed without rewriting the published history.
- **Lease, fetch, classify; never force**, because the host's history is other people's too.
- **Fast-forward-only following, and no merge into a pushing destination**, because a conflicted destination stops every landing.
- **One row per destination**, because status is what agents and people read, and the operation log already has the history.

6. **Fetch before a batch.** A pushing destination's batch fetches its branch first (30 s bound, skipped while offline or within 30 s), a failure only a note. *Recommended*: as stated (a host merge is followed instead of diverging). Alternative: fetch only after a rejected push.
