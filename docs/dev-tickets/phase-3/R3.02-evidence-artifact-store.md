# R3.02 Evidence artifact store

Phase 3 · Size M · Depends on: R3.01 (the evidence format, `EvidenceService`, migration 0007) · Unblocks: none listed in `dev-phases.md`; R3.05, R3.06, R3.13 and R3.31 build on it

## Context

R3.01 records what a check produced only as digests: each predicate lists at most 64 `artifacts`, each with a `name` and a `sha256`, and "R3.02 stores the bytes by `sha256`; this ticket records the digests and never requires the bytes to exist". It also stores evidence with no deletion except `repo forget`, and gives the retention of evidence objects to this ticket (README, "Departures"; R3.01, "What survives what": "A retention rule for evidence objects goes to R3.02 with the artifacts'"). The threat model's S-52 ("nothing bounds how many evidence objects a writer adds") points here too.

The design names both halves. Its data model row: "Artifacts live in a separate store with its own retention policy, since evidence volume outgrows code volume at agent scale". Its durability table: artifacts are authoritative "within retention", rebuilt by "re-running the executor". The executor protocol's response is "a set of signed evidence objects plus artifacts" (R3.05), and the proposal view shows a check's log beside its result (R3.31). So this ticket does three things, all local:

1. **An artifact store**: logs, reports and build outputs, addressed by the SHA-256 the evidence already records. Uploads go in resumable chunks and downloads stream; bytes are stored once per repository.
2. **Retention for evidence and artifacts**: a seventh GC step that keeps whatever live work needs, and deletes the rest once it is older than a configured age. Artifacts get a shorter age and a size cap. A reader sees which artifacts were collected.
3. **A seam**: the bytes sit behind a trait, so a later remote store can replace where they live while the database index stays where it is. No remote store is built here.

### What was verified while writing this ticket

Reef at `77503ab` (R3.01 merged as `e3483cd`; API revision 15, database schema 7, ADR 0055 the latest). Paths are under `crates/` unless they start with `docs/` or `sdk/`.

- **The format already addresses artifacts by SHA-256.** `EvidenceArtifact { name, sha256, uri, media_type }` (`reef-api/proto/reef/api/v1/evidence.proto`, fields 1 to 4), and its comment says "Reef does not store its bytes in this revision". `reef evidence add --artifact <path>` hashes the file with `reef_evidence::sha256_hex_of` (`reef-evidence/src/lib.rs:217`, 64 KiB reads through ring) and uploads nothing (`reef-vcs/src/cli/evidence.rs:421`). `--artifact` conflicts with `--envelope` (`:110`). The daemon parses an envelope's artifacts only when it reads one, and no table indexes them (`db/migrations/0007_evidence.sql`).
- **No client streaming, by rule and by tooling.** ADR 0029 decision 13: "Streaming is server-side only … The web UI reaches the API over gRPC-web, which carries no client streaming." Both SDK generators refuse a client-streaming RPC: `sdk/python/codegen/clientgen.py:239` raises `GenerateError`, and `sdk/typescript/codegen/protoc-gen-reef.mjs:181` throws for anything but `unary` and `server_streaming`. The largest unary request in the schema is `UploadScipDocuments`, "at most 4 MiB (larger is OUT_OF_RANGE, from gRPC)" (`symbols.proto:41`), which is tonic's default decoding limit. Server-streaming RPCs exist (`Backup`, `BuildStore`, the subscriptions), and the SDKs wrap them (ADR 0054 decision 1).
- **GC is six steps under the repository's create lock** (`reef-daemon/src/maintenance/gc.rs`, module docs and `run_repo`): jj, base cache, workspace rows, stores, symbols, history. `keep_newer = now − max(gc.undo_window, backup.retention while the last backup is within it)` is the floor every step honours (ADR 0020 decision 6: "Nothing a recent backup references is pruned"). `CollectGarbageRequest.dry_run` exists, and `GcReport` has fields 1 to 15 (`maintenance.proto:69`). The timer runs it every `gc.interval`, 1 day by default (ADR 0041). The symbols step (`symbols/gc.rs`) has the shape this ticket reuses: mark the live set, sweep what is older than `keep_newer` and not live, then cap at `max_size` without ever evicting what is live.
- **The live set has a name already.** `reef_lib::jj::revset::DEFAULT_LOG` is `trunk() | working_copies() | mutable()` (`reef-lib/src/jj/revset.rs:38`), with Reef's own aliases `immutable_heads()` = `trunk() | tags()` and `mutable()` = `~immutable()` (`:333`–`:336`), so it does not depend on the user's jj configuration. `files::working_copy_commits` (`jj/files.rs:1392`) and `files::change_tree_ids` (`:1437`) are R3.01's helpers.
- **Per-repository state is `<state>/repos/<id>/`**: `bases/`, `wc/`, `history.sqlite3`, `symbols.sqlite3` (`Paths::repo_dir`, `config.rs:1151`). `Manager::forget_repository` removes that whole directory after `Db::delete_repository` (`workspace/manager.rs:429`–`:450`), which already deletes `evidence_links` and `evidence` (`db/repositories.rs:206`–`:207`). Stores are machine-wide, under `<state>/stores/`.
- **Backups copy none of `repos/<id>/`.** The layout is `manifest.json`, `reef.sqlite3`, and per repository `repo/`, `git/` and `heads.json` (`maintenance/backup.rs`, module docs). The caches under `repos/<id>/` stay out by design (ADR 0042 decision 6, ADR 0044 decision 4). `copy_tree_with(…, Existing::Keep)` already exists for content-addressed files. `RepoManifest` has no `deny_unknown_fields` (`reef-client/src/backup.rs:45`), so it can gain fields with `#[serde(default)]` and stay at `MANIFEST_VERSION` 1. Backup holds the maintenance lock, so GC cannot run during a backup (ADR 0020 decision 2).
- **Migrations are SQL only** (`db/mod.rs:483`, `migrate`), and released ones are never edited. An index that has to be read out of stored envelopes (base64 inside JSON) cannot be backfilled by SQL alone.
- **Config.** Every section has its own `KEYS` row (`config.rs:72`), a `Default` impl, and checks in `validate` (`:1717`). Retention and size keys follow `[history]` (`retention` `"90d"`, from 1 day to 10 years; `max_size` `"512MiB"`) and `[symbols]` (`max_size`, `max_file_size`). `gc.interval`'s `0s` turns it off (`:1764`).
- **Surfaces a new service touches**, as R3.01 found them: `server.rs` `SERVED` (16 entries, `:71`) and `routes`; `remote/rules.rs` `TABLE` (`AddEvidence` and `UploadScipDocuments` are `Rule::None`), with a completeness test; `reef-vcs/src/mcp/tools.rs` `NOT_TOOLS`, with `tools/list` bounded at 21,250 bytes (`reef-vcs/tests/mcp.rs:203`); `reef schema`'s `OUTPUTS` (`cli/schema/outputs.rs`), where `file read` is the model for a command whose stdout is bytes ("the file's bytes unless -o json or -o brief"); the web listener serves every `ACCESS_READ` method by the schema's classification (ADR 0047 decision 2).

## Decisions

### Size

M, at its top end, like R3.01. The store (a trait and a local implementation) is about 300 lines; the service, about 500; the GC step, about 400; the migration, config, backup, restore and CLI are each small and follow existing patterns. What stays out to keep it M: listing artifacts, a remote store, quotas that refuse uploads, an API to pin evidence, MCP tools, the web UI and SDK helpers ("Out of scope", each with its ticket).

### Where the bytes live: files under the repository's state directory

```
<state>/repos/<id>/artifacts/sha256/<first 2 hex>/<remaining 62 hex>   stored, mode 0444
<state>/repos/<id>/artifacts/incoming/<sha256>.<size>                   a partial upload
```

- **Files, not SQLite blobs.** Artifacts are build outputs and logs, from bytes to gigabytes. Blobs in `reef.sqlite3` would put them in the WAL, the database lock and every backup's online copy, which walks pages and restarts a step when a page changes. Files stream, cost nothing to read in ranges, and on APFS are cloned by `std::fs::copy`. The **index** stays in `reef.sqlite3` (below): small, authoritative, and in the same transaction as the evidence that references it.
- **Per repository**, keyed as every row is (ADR 0003). Two repositories that store the same bytes hold two copies. `repo forget` then deletes the files with the directory it already removes, and a remote token's rule is the same as `AddEvidence`'s. Dedup across repositories is a follow-up with R3.18's cross-repository cache, if ever.
- **Content-addressed by SHA-256 in lowercase hex**, the digest R3.01's predicate requires. A path is built only from a digest that has already been checked as 64 lowercase hex, so no request text ever reaches the filesystem.
- **Dedup is free**: storing bytes already stored changes nothing but the row's `used_at`.
- **Size**: one artifact is at most `[artifacts] max_object_size` (default 1 GiB). Nothing in this ticket refuses an upload because the store as a whole is large; `max_size` is GC's target ("Retention").

### The index: migration `0008_artifacts.sql`, schema 8

```sql
-- R3.02: the artifact store's index. Bytes are files under repos/<id>/artifacts/ (one per
-- sha256); a row with collected_at set is a tombstone: retention removed the bytes while some
-- evidence still names them. evidence_artifacts records which digests each evidence object's
-- payload lists, read from the payload at add. evidence_by_added (0007) already orders evidence
-- by age for retention. Released migrations are never edited.
CREATE TABLE artifacts(repo_id TEXT NOT NULL, sha256 TEXT NOT NULL,
             size INTEGER NOT NULL,
             stored_at INTEGER NOT NULL,       -- when its bytes were last stored
             used_at INTEGER NOT NULL,         -- stored, uploaded again, or named by evidence added
             collected_at INTEGER,             -- NULL while stored
             added_by_agent TEXT, remote_token_id TEXT,
             PRIMARY KEY (repo_id, sha256)) WITHOUT ROWID;
CREATE INDEX artifacts_by_use ON artifacts(repo_id, collected_at, used_at);
CREATE TABLE evidence_artifacts(repo_id TEXT NOT NULL, evidence_id TEXT NOT NULL,
             sha256 TEXT NOT NULL,
             PRIMARY KEY (repo_id, evidence_id, sha256),
             FOREIGN KEY (repo_id, evidence_id) REFERENCES evidence(repo_id, id)) WITHOUT ROWID;
CREATE INDEX evidence_artifacts_by_sha256 ON evidence_artifacts(repo_id, sha256);
```

- **`evidence_artifacts` has no foreign key to `artifacts`**: evidence may name bytes that were never uploaded (R3.01's rule stands).
- **`AddEvidence` fills it** in its insert transaction, from the verified payload, and sets `used_at = now` on each named artifact row that exists. A repair (R3.01's re-add of a changed row) rewrites the evidence's `evidence_artifacts` rows too.
- **The backfill.** Evidence stored under schema 7 has no `evidence_artifacts` rows, and SQL cannot read base64 payloads. `Db::open` therefore runs a one-time Rust step after the migrations: while the `meta` key `evidence_artifacts_indexed_at` is unset, it reads every `evidence` row's payload with `reef_evidence`'s statement parser, inserts its digests, and sets the key, all in one `IMMEDIATE` transaction. The parse skips the signature check: the index only steers retention, and a row that does not parse indexes nothing and is logged. This is the first post-migration step in `db/mod.rs`; it is written as a named function called from `open`, not as a general mechanism.
- **`repo forget`**: `delete_repository` deletes the repository's `evidence_artifacts` and `artifacts` rows in its transaction, before `evidence`. The files go with `repos/<id>/`, which forget already removes.

### The seam: `ArtifactBytes`

`reef-daemon/src/artifacts/` (new) holds the store, behind one trait:

```rust
/// Where an artifact's bytes live (R3.02, ADR 0056). Content-addressed by SHA-256.
/// The index (the `artifacts` rows, and which evidence names what) stays in
/// `reef.sqlite3` whichever store holds the bytes. Blocking: called on the
/// blocking pool, as every filesystem step is.
pub trait ArtifactBytes: Send + Sync {
    /// Bytes of a partial upload of (`digest`, `size`) received so far; 0 for none.
    fn received(&self, digest: &Digest, size: u64) -> io::Result<u64>;
    /// Appends `data` to that partial upload at `offset`, which must equal `received`.
    fn append(&self, digest: &Digest, size: u64, offset: u64, data: &[u8]) -> Result<u64, AppendError>;
    /// Hashes the complete partial upload, without the lock; deletes it on a mismatch.
    fn check(&self, digest: &Digest, size: u64) -> Result<(), CommitError>;
    /// Stores the checked partial upload; quick, under the lock.
    fn commit(&self, digest: &Digest, size: u64) -> Result<(), CommitError>;
    /// Reads stored bytes from `offset`.
    fn open(&self, digest: &Digest, offset: u64) -> io::Result<Box<dyn Read + Send>>;
    /// Whether stored bytes exist, and their length.
    fn stat(&self, digest: &Digest) -> io::Result<Option<u64>>;
    /// Deletes stored bytes; the bytes it had allocated.
    fn remove(&self, digest: &Digest) -> io::Result<u64>;
    /// Every stored digest with its length and mtime, for GC's orphan sweep.
    fn stored(&self) -> io::Result<Vec<(Digest, u64, SystemTime)>>;
    /// Deletes partial uploads last written before `before`.
    fn sweep_incoming(&self, before: SystemTime) -> io::Result<(u32, u64)>;
}
```

- `Digest` is a checked 64-lowercase-hex newtype; building one is the only way to name a path.
- `LocalArtifacts` implements it over the layout above. `append` writes with `O_APPEND` after checking the file's length; `commit` fsyncs, hashes the file (ring, 64 KiB reads), and on a match renames it into `sha256/` (`create_dir_all` for the fan-out directory), sets mode `0444`, and fsyncs the directory.
- **What the seam promises**: a remote implementation (R4.02's S3-compatible blob storage, or a team's own) replaces `LocalArtifacts`, and nothing above the trait changes: the service, the index, retention and the CLI only call the trait. The methods are blocking; a remote implementation may make them async in its own ticket, since that changes signatures but not the seam. No remote store, no config to choose one, and no second implementation besides a test double are in this ticket.

### Upload: chunked unary calls, keyed by the digest

Client streaming is ruled out (ADR 0029 decision 13, and both SDK generators refuse it). One unary RPC is called repeatedly:

```
UploadArtifact { repo, sha256, size, offset, data }  →  { received, artifact, created }
```

- **The digest and size come first.** The client hashes the file, then sends chunks. A partial upload is the file `incoming/<sha256>.<size>`: the size is in the name, so an upload declaring a different size never appends to it.
- **Each call**: if the digest is stored (its row stored and its file present at the row's size), the call returns at once with `received = size`, the stored `Artifact` and `created: false`, whatever `data` holds, and sets `used_at`. That is dedup, and an empty probe (`offset 0`, no `data`) is how a client asks. Otherwise `offset` must equal the bytes received so far (`ARTIFACT_OFFSET_MISMATCH`, metadata `received`, otherwise), and `data` is appended. When `received` reaches `size`, the daemon hashes it without the lock (`ARTIFACT_DIGEST_MISMATCH` deletes the partial upload), then under the lock checks that the repository is still registered, commits it, and inserts or updates the row (a tombstone becomes stored again), and returns the `Artifact` with `created: true`.
- **Retries and resumption**: a lost response is retried and answered with the mismatch's `received`, from which the client goes on. A retried last chunk finds the digest stored, so it is answered as a probe of stored bytes is: `received = size`, the record, `created: false`. A partial upload survives a daemon restart, so a client that comes back resumes from the probe's `received`. Two clients uploading the same digest cooperate: the bytes are the same, and each resumes from whatever the other appended.
- **Bounds**: `data` at most 1 MiB (`MAX_CHUNK`; the request stays well under gRPC's 4 MiB), `offset + len(data) ≤ size`, and `size ≤ max_object_size` (`ARTIFACT_TOO_LARGE`, checked on every call after the dedup check, so a large upload is refused before any byte is written, and a stored artifact is still found once the limit is lowered). A zero-byte artifact is one call with no `data`.
- **Concurrency with GC**: a per-repository `tokio::sync::Mutex` (`ArtifactLock`) is held by GC while it collects, by `ForgetRepository` while it forgets, by an upload's commit (the repository checked again, the rename and the row, after the hash), by an upload's stored-digest answer when a stored row matches (a read decides whether to take it), and by a damaged read's quarantine while it deletes. No upload commits a row and a file that outlive the repository, and a client never hears "stored" for bytes GC is deleting. Appends and hashing do not take it.
- **No operation** is recorded, as for `AddEvidence`: ADR 0029 decision 12's exceptions gain `UploadArtifact`. Remote uploads are traced by the remote listener's audit log.

### Download: one server-streaming RPC

`ReadArtifact { repo, sha256, offset, length }` streams `ReadArtifactResponse { artifact, offset, data }` messages of at most 1 MiB, read on the blocking pool. The first message carries `artifact` (its size and state), and later messages carry only data. `length` 0 means "to the end". When the read covers the whole artifact, the daemon hashes what it sent and, if the bytes no longer match the digest, ends the stream with `ARTIFACT_DAMAGED` (metadata `sha256`, `damage` `digest`, `actual_sha256`) after the data. The client has then received bytes it must discard: the CLI exits non-zero and says so. Before it sends that error, the daemon hashes the file again without the lock and, if it is still wrong, takes the `ArtifactLock` and, unless an upload repaired it meanwhile (the row's `stored_at` changed), makes the row a tombstone and deletes the file, so the artifact then reads as collected and the next upload of the genuine bytes stores them again. A stored row whose file is gone is `ARTIFACT_DAMAGED` with `damage` `missing`, and one whose file's length is not the row's size is `damage` `size` (`actual_size`), both before any data; an upload's stored check treats both as not stored. When the file is gone because GC collected it after the row was read, the read is `ARTIFACT_COLLECTED`. This mirrors R3.01's re-verification on every read: a file changed behind the daemon is reported, never served as genuine.

### Retention

GC gains a seventh step, **evidence and artifacts**, after history and before the reindex. It runs under the create lock `run_repo` already holds, reads the head after step 1, and honours `dry_run`. It follows the symbols step's mark, sweep and cap.

**Mark: the live set.** Evaluate `trunk() | bookmarks() | working_copies() | mutable()` on the repository's head (on the read pool), and collect the resolved tree ids and the change ids of those commits. That revset is `reef log`'s default set (`DEFAULT_LOG`) plus every local bookmark's target: the work that may still be proposed, and every published head. It is computed once per run in a new `reef_lib::jj::files::live_set(repo) -> LiveSet { trees, changes }`.

**An evidence object is pinned** when its `tree_id` is in `LiveSet.trees`, or an `evidence_links` row links it to a change in `LiveSet.changes` (an open change's evidence on its earlier trees, which R3.15's transfer rules read). Pinned evidence is never deleted.

**Evidence sweep.** Delete evidence that is not pinned and was added before `min(now − [evidence] retention, keep_newer)`. Its `evidence_links` and `evidence_artifacts` rows go in the same transaction, 1,000 objects per transaction, so the database is never held for long. `evidence_keys` stay (machine-wide, as at forget). `added_at` is the first add's (R3.01 keeps it on a re-add), so re-adding old evidence does not renew it.

**Artifact sweep.** This runs after the evidence sweep, with `ArtifactLock` held. The sweep never touches an artifact whose `used_at` is at or after `keep_newer`. An upload waiting for its evidence is kept by a grace of its own, `UPLOAD_GRACE` (1 day): an artifact no evidence names goes only once used before `min(keep_newer, now − 1 day)`, since `[gc] undo_window = "0s"` makes `keep_newer` now. Older ones:

| The artifact is | It goes when | What remains |
| --- | --- | --- |
| Named by no evidence | used before `min(keep_newer, now − 1 day)` | nothing: file and row deleted |
| Named only by evidence that is not pinned | `used_at` before `now − [artifacts] retention` | a tombstone: `collected_at` set, the file deleted |
| Named by pinned evidence | never, by age | stored |

**Cap.** While the stored bytes exceed `[artifacts] max_size`, collect what may be collected, least recently used first: not named by pinned evidence and `used_at` before `min(keep_newer, now − 1 day)`. What is pinned or newer is never collected. A repository whose pinned artifacts alone pass the cap keeps them, logs a warning, and reports `artifact_bytes` above the cap, as the symbols index does.

**Tidy.** Delete tombstones named by no remaining evidence, partial uploads last written more than 1 day ago (a constant, `INCOMING_MAX_AGE`; they are not in backups, so the backup floor does not apply), and stored files with no stored row whose mtime is more than 1 hour old (a crash between commit and insert). A stored row whose file is missing becomes a tombstone, logged: readers see it collected, and an upload of the genuine bytes stores it again.

**Order of deletion**: a row change commits before its file is removed. A crash in between leaves a file with no stored row, which the next run's tidy removes. The database never names stored bytes that are gone because of GC.

**`GcReport` gains** (fields 16 to 19): `uint32 evidence_removed`, `uint32 artifacts_collected` (files deleted, tombstoned or not), `uint64 artifact_bytes_freed` (what the removed files had allocated; in a dry run, their sizes), `uint64 artifact_bytes` (what the store holds after the step, or would hold in a dry run). `reef ws gc`'s text line gains `evidence <n> removed, artifacts <n> collected (<size>), <size> kept`. A failure in this step is logged and the run goes on, as steps 5 and 6 do, but it is reported as an error for a requested run, because these are authoritative data and not a cache: `GcReport` gains `string evidence_error = 20`, set when the step stopped short, and `reef ws gc` exits 8 (`io`) for it, as for `jj_error`.

**What a reader sees afterwards:**

- `GetEvidence` for a deleted object: `EVIDENCE_NOT_FOUND`. Its hint now adds "evidence that is not on live work is deleted after `[evidence] retention` (`reef config show`)". No tombstone is kept for evidence: an id refers to a 1 to 2 KiB object, and R3.13's landing pin (below) is what keeps the evidence anyone will refer to later.
- `Evidence.artifacts[]` carries each artifact's state from the index: `ARTIFACT_STATE_STORED` with its `size`, `ARTIFACT_STATE_COLLECTED` with `collected_at`, or `ARTIFACT_STATE_ABSENT` (never uploaded, or deleted with no evidence naming it at the time). `reef evidence show` prints it.
- `ReadArtifact` on a tombstone: `ARTIFACT_COLLECTED` (`NOT_FOUND`, metadata `sha256`, `collected_at`); hint: run the check again, or upload the same bytes, which makes it stored again.

**Config**, two new sections:

| Key | Default | Range | Meaning |
| --- | --- | --- | --- |
| `[evidence] retention` | `"90d"` | `0s`, or 1 day to 10 years | Evidence not on live work is deleted this long after it was added. `0s` keeps all evidence. |
| `[artifacts] retention` | `"30d"` | `0s`, or 1 day to 10 years | Artifacts named only by evidence that is not pinned are collected this long after they were last used. `0s`: never by age. |
| `[artifacts] max_size` | `"10GiB"` | at least 64 MiB | The store's size per repository that GC collects down to, never collecting what pinned evidence names or what was used within the undo window or the last day. |
| `[artifacts] max_object_size` | `"1GiB"` | 1 KiB to 64 GiB | The largest artifact an upload accepts. |

Every cutoff is floored at GC's `keep_newer`, so nothing younger than the undo window, or than the last backup's retention, is deleted, whatever the keys say. Both sections join `KEYS` and `validate`, and `reef config show` prints them.

### The API: `ArtifactService`, API revision 16

A new file `reef/api/v1/artifacts.proto`, a service of its own, because a later store may serve artifacts without evidence:

```proto
// Artifacts (R3.02, ADR 0056): the bytes evidence names by SHA-256 (logs, reports, build
// outputs), stored once per repository and kept by retention. Records no operation.
service ArtifactService {
  rpc UploadArtifact(UploadArtifactRequest) returns (UploadArtifactResponse) {
    option (reef.api.v1.access) = ACCESS_WRITE;
    option idempotency_level = IDEMPOTENT;
  }
  rpc GetArtifact(GetArtifactRequest) returns (GetArtifactResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
  rpc ReadArtifact(ReadArtifactRequest) returns (stream ReadArtifactResponse) {
    option (reef.api.v1.access) = ACCESS_READ;
    option idempotency_level = NO_SIDE_EFFECTS;
  }
}

enum ArtifactState { ARTIFACT_STATE_UNSPECIFIED = 0; ARTIFACT_STATE_STORED = 1;
                     ARTIFACT_STATE_COLLECTED = 2; ARTIFACT_STATE_ABSENT = 3; }

message Artifact {
  string sha256 = 1;
  ArtifactState state = 2;
  uint64 size = 3;                          // 0 when absent
  google.protobuf.Timestamp stored_at = 4;  // unset when absent
  google.protobuf.Timestamp used_at = 5;
  google.protobuf.Timestamp collected_at = 6;   // set when collected
  string added_by_agent = 7;
  string remote_token_id = 8;
  uint32 evidence_count = 9;                // evidence objects naming it
  repeated string evidence_ids = 10;        // the newest 20 of them
}

message UploadArtifactRequest {
  string repo = 1;
  string sha256 = 2;                        // 64 lowercase hex
  uint64 size = 3;                          // the whole artifact's
  uint64 offset = 4;                        // where `data` starts; must equal `received`
  bytes data = 5;                           // at most 1 MiB; empty to probe
}
message UploadArtifactResponse {
  uint64 received = 1;                      // bytes held: `size` once stored
  Artifact artifact = 2;                    // set once stored
  bool created = 3;                         // this call stored it
}

message GetArtifactRequest { string repo = 1; string sha256 = 2; }  // full, or a unique prefix of 4+
message GetArtifactResponse { Artifact artifact = 1; }

message ReadArtifactRequest {
  string repo = 1; string sha256 = 2;       // full, or a unique prefix of 4+
  uint64 offset = 3; uint64 length = 4;     // length 0: to the end
}
message ReadArtifactResponse {
  Artifact artifact = 1;                    // first message only
  uint64 offset = 2;                        // of `data` in the artifact
  bytes data = 3;                           // at most 1 MiB
}
```

`evidence.proto` gains, additively: `EvidenceArtifact.state = 5` (`ArtifactState`, imported), `size = 6`, `collected_at = 7`, filled from the index at every read (one `IN` query per page), and comments saying so. The comment "Reef does not store its bytes in this revision" is replaced. `AddEvidence`'s comment says it indexes the artifacts the payload names.

Each element gets the full leading comment ADR 0029's checklist requires; the sketch abbreviates. The rules:

- **`GetArtifact`** answers for a digest that is stored or collected (an `artifacts` row) or only named by evidence (`ABSENT`, from `evidence_artifacts`). A prefix is looked up as a range of the primary key over `artifacts` rows only, as R3.01's prefixes are; an absent artifact needs its full digest. A digest neither stored nor named is `ARTIFACT_NOT_FOUND`.
- **`ReadArtifact`**: `offset` beyond `size` is `INVALID_ARTIFACT_RANGE` (metadata `offset`, `size`); an `ABSENT` artifact is `ARTIFACT_NOT_FOUND`; a collected one, `ARTIFACT_COLLECTED`.
- **The web listener** serves `GetArtifact` and `ReadArtifact` by their classification, which is what R3.31 needs to show a log. The bytes travel as protobuf `bytes` inside gRPC-web, never as an HTTP resource with a content type, so the browser never renders an artifact as a page.
- **Remote**: `remote/rules.rs` gains `UploadArtifact` with `Rule::None`, as `AddEvidence`.

**Reasons** (new constants in `reef_api::error`, documented on their RPCs and mapped in `error.rs`):

| Reason | Kind | Metadata | RPCs |
| --- | --- | --- | --- |
| `INVALID_ARTIFACT_DIGEST` | `INVALID_ARGUMENT` | `sha256` | all three (upload: not 64 lowercase hex; get and read: not 4 to 64 hex) |
| `AMBIGUOUS_ARTIFACT_DIGEST` | `INVALID_ARGUMENT` | `sha256`, `sha256s` (up to 10) | `GetArtifact`, `ReadArtifact` |
| `INVALID_ARTIFACT_UPLOAD` | `INVALID_ARGUMENT` | `field`: `data` (over 1 MiB) or `size` (`offset + len(data)` beyond it) | `UploadArtifact` |
| `ARTIFACT_TOO_LARGE` | `INVALID_ARGUMENT` | `size`, `max_object_size` | `UploadArtifact` |
| `ARTIFACT_OFFSET_MISMATCH` | `FAILED_PRECONDITION` | `received` | `UploadArtifact` |
| `ARTIFACT_DIGEST_MISMATCH` | `INVALID_ARGUMENT` | `sha256`, `actual_sha256` | `UploadArtifact` |
| `ARTIFACT_NOT_FOUND` | `NOT_FOUND` | `sha256` | `GetArtifact`, `ReadArtifact` |
| `ARTIFACT_COLLECTED` | `NOT_FOUND` | `sha256`, `collected_at` | `ReadArtifact` |
| `INVALID_ARTIFACT_RANGE` | `INVALID_ARGUMENT` | `offset`, `size` | `ReadArtifact` |
| `ARTIFACT_DAMAGED` | `INTERNAL` | `sha256`, `damage` (`missing`, `size` or `digest`), `actual_size` for `size`, `actual_sha256` for `digest` | `ReadArtifact` |

`ARTIFACT_OFFSET_MISMATCH` is the one a client acts on in a loop. Its hint is "resume from byte `<received>`", and it has no `next`. An I/O failure (a full disk) is the ordinary `Io` kind with its chain. `ARTIFACT_COLLECTED`, `ARTIFACT_NOT_FOUND` and `ARTIFACT_DAMAGED` name `reef evidence artifact upload <file>` in their hint and have no `next`: a `next` is an argv to run verbatim, never one with a placeholder.

`API_REVISION` becomes 16 with the digest; `SERVED` gains `reef.api.v1.ArtifactService` (17); `BackupStep` gains `BACKUP_STEP_ARTIFACTS = 6`; `GcReport` gains fields 16 to 20.

### Backup and restore

Artifacts are authoritative within retention (the design's durability table), and a test log from a flaky run cannot be produced again. So backups include them:

- **Backup**: after the SQLite copy (step 2) and before each repository's jj files, each repository's `repos/<id>/artifacts/sha256/` is copied to `<dest>/repos/<id>/artifacts/sha256/` with `copy_tree_with(…, Existing::Keep)`. `incoming/` is skipped. A `BACKUP_STEP_ARTIFACTS` progress message is sent per repository. Consistency follows from the lock: GC, the only thing that deletes genuine artifacts, cannot run while the backup holds the maintenance lock, so every stored row in the database copy has its file in the backup. The other deletions are a damaged read's quarantine, which removes only bytes that already fail their digest (the restored daemon's tidy makes such a row a tombstone), and `ForgetRepository`, which deletes a repository whole. Files uploaded after the SQLite copy are harmless extras, which the restored daemon's tidy removes. `RepoManifest` gains `artifact_files` and `artifact_bytes` (`#[serde(default)]`; `MANIFEST_VERSION` stays 1).
- **Restore**: each repository's `artifacts/` is staged beside `<state>/repos/<id>/artifacts/` and renamed into place with the repository's other copies (step 4). What was there before is kept as `.replaced-<nanos>`, and so is what `--force` replaces. A backup without `artifacts/` (from before R3.02) restores none, and its evidence reads `ABSENT`. With `--into`, the path is relative to the repository's directory, so nothing moves.

### The CLI

```
reef evidence add … [--artifact <path>]... [--no-upload]          (--no-upload conflicts with --envelope)
reef evidence add --envelope <file> --public-key <pem> [--artifact <path>]... [-r <rev>]
reef evidence artifact upload <path>...
reef evidence artifact show <sha256>
reef evidence artifact read <sha256> [--offset <n>] [--length <n>]
```

- **`add --artifact` now uploads.** For each file the CLI hashes it (once, for the claim, then names the upload by that digest with `reef_client::Client::upload_artifact_file_as`), sends a probe, uploads in 1 MiB chunks from the probe's `received` (following `ARTIFACT_OFFSET_MISMATCH`'s `received`), and only then sends `AddEvidence`. So evidence made by Reef's own producer never names bytes the store lacks. `--no-upload` keeps R3.01's behaviour of recording the digest only. A file that changes between the hash and the upload ends in `ARTIFACT_DIGEST_MISMATCH`, and nothing is added.
- **`add --envelope … --artifact <path>`** uploads the files, and refuses before sending anything a file whose digest is not among the envelope's artifacts (a usage error naming the file and its digest). `--artifact` stops conflicting with `--envelope`.
- **`artifact upload`** uploads files without evidence, for a script that signs elsewhere: one line per file, `<sha256 12> <size> stored|already stored`. Its JSON is a list of `ArtifactUploaded { artifact, created, path }`.
- **`artifact show`** prints the `Artifact`: state, size, times, adder, and the evidence naming it. `-o json` is `json::Artifact`.
- **`artifact read`** writes the bytes to stdout, on a pipe too, unless `-o json` or `-o brief`, which print `json::Artifact` and `brief::Artifact` (as `reef file read` does). It never decodes or pages them. A damaged stream exits with the error after the bytes, and stderr says that the output is not the artifact.
- **`evidence show`** prints each artifact as `artifact <name> sha256:<12> stored <size>`, `collected <date>` or `absent`. `json::EvidenceArtifact` gains `state`, `size` and `collected_at`, and `brief.Evidence` stays as it is.
- **Help and budget**: `artifact` is a subcommand of `evidence`, so the root help does not change (R3.01 left it at its 512-byte budget). Advice rows go in `cli/advice.rs` for each reason a command can hit. `OUTPUTS` gains the three rows, with `artifact read` as a bytes row in `file read`'s pattern.

## Implementation notes

- **Order**: the migration, `db/artifacts.rs` and the backfill (test 1); `artifacts/` (test 2); the service (tests 3 to 7, 15); `live_set` and the GC step (tests 8 to 13); backup and restore (14); config (16); the client and the CLI (17); schema, MCP, help, SDKs and the documents (18).
- **`live_set`**: parse the revset with Reef's aliases (`revset::parse`, as `status.rs` does for `heads(mutable())`), evaluate it once, and read each commit's resolved tree id and change id, skipping conflicted trees (they carry no evidence). Run it as a read job on the repository's thread pool, never on a tokio worker (R2.03's rule). Pass the sets to SQLite as a temporary table on the GC connection, so that the pin test is a join and not a per-row lookup.
- **Hashing** at commit and at full reads uses `reef_evidence::sha256_hex_of`; no new dependency. `ARTIFACT_DAMAGED` after the data is a tonic stream `Err` item, which the SDKs surface as the stream's error.
- **Appends** open with `O_APPEND` and check the length under a per-file `std::sync::Mutex` held for the write, so two writers to one partial upload never interleave inside a chunk.
- **Disk-full**: a failed append leaves the partial upload at the length it reached; `received` reports it, and the client resumes after space is freed.
- **Linux**: no `cfg(target_os)` in this ticket. Build and lint in the privileged `ubuntu:24.04` container anyway, since `maintenance/` and `server.rs` change and the Linux-only daemon tests construct `TestDaemon`.

## Out of scope

- **A remote artifact store**: the S3-compatible implementation of `ArtifactBytes` is R4.02's blob storage, and moving artifacts with evidence between stores is R4.07's. Fetching an artifact's `uri` (Reef never reads it).
- **Listing artifacts** (`ListArtifacts`, `reef evidence artifact list`): follow-up issue "list a repository's artifacts with sizes". The dry-run GC report gives the store's size until then.
- **A quota** that refuses uploads over a repository's budget (S-54): follow-up issue.
- **Pinning by request** (`reef evidence pin`, a landing pin): R3.13 records which evidence a landing used and pins it; a manual pin can come with it.
- **Retention policy per repository** in the policy file (R3.07), and per kind or per key: follow-up if wanted.
- **Dedup across repositories**, compression, chunked or delta storage of artifacts.
- **MCP tools**, the web UI (R3.31), and SDK upload helpers.
- **A tombstone for deleted evidence.**

## Risks

- **Deleting authoritative data.** This is the first ticket that deletes evidence other than at forget. The pins are a revset, and a mistake in it deletes evidence someone needed. Mitigations: the floor at `keep_newer`; a default of 90 days; `0s` to turn it off; the dry run; test 8's fixture covering each pin; and the CHANGELOG's upgrade note. Evidence on old trunk commits expires until R3.13 adds the landing pin, which is stated in the docs.
- **`mutable()` can be large.** When `trunk()` resolves to the root (no `main` bookmark), `mutable()` is every visible commit, and `live_set` reads every commit. The bench's 2,000 commits is the expected case; a repository without trunk pays one commit read per commit per day, and the step logs its duration.
- **Disk use is soft-capped.** `max_size` never collects pinned or recent bytes, and uploads are never refused for the store's size (S-54). A busy executor can pass the cap within the undo window. Reported in `artifact_bytes`, and the follow-up quota addresses it.
- **Backups grow** by the artifact store, up to `max_size` per repository, on every backup, since each backup is a full copy into a new directory. APFS clones within a volume, and other destinations pay the copy. This is the price of "authoritative within retention" (question 3).
- **A post-migration step** is new in `db/mod.rs`; if it fails, `Db::open` fails. It runs once over evidence that exists only since R3.01, inside one transaction, and test 1 covers a row that does not parse.

## Choices this brief made, and why

- **Files for bytes, rows for the index**, because artifacts are large and streamed while their index must be in the evidence's transaction.
- **Per repository**, because every other row and directory is, and forget and remote rules follow.
- **Chunked unary upload keyed by digest and size**, because client streaming is excluded, the digest already names the upload, and dedup and resumption then need no session state.
- **A seam at the bytes, not the index**, because a remote store replaces where bytes live while the daemon still decides what evidence names and what retention keeps.
- **Pins from the live set**, because live work and open changes are what landing (R3.13) and transfer (R3.15) read, and `reef log`'s default set already defines live.
- **Artifacts expire before evidence**, because the design gives artifacts "their own retention" and they are rebuildable by re-running the executor, while an evidence object is small and is the record.
- **Tombstones for artifacts only**, because "collected" and "never uploaded" mean different things to a reader of evidence that still exists.
- **GC's seventh step**, not a timer of its own, because GC already holds the right locks, honours the backup floor, reports, and dry-runs.
- **Backups include artifacts**, because the durability table calls them authoritative within retention.

## Departures found while implementing

Each is fixed in the text above.

- **No `evidence_by_age` index.** 0007's `evidence_by_added (repo_id, added_at DESC, id)` already orders evidence by age, so migration 0008 does not add a second one.
- **A repeated last chunk answers "stored", not a mismatch.** The commit happens in the call that completes the bytes, so a retried last chunk finds the digest stored and gets the stored answer (`received = size`, `created: false`); a repeated earlier chunk is the mismatch (test 3).
- **No `next` on `ARTIFACT_COLLECTED` and `ARTIFACT_NOT_FOUND`.** reef-error's `Advice` makes `next` an argv run verbatim, never a placeholder, so `reef evidence artifact upload <file>` is in the hint.
- **A damaged file is deleted, and a missing file is not stored.** Without both, test 6's "uploading the genuine bytes again repairs both" cannot hold: an upload of a stored digest answers "stored" at once. A whole read that finds the bytes damaged hashes the file again and deletes it if it is still wrong; an upload's stored check treats a stored row whose file is missing as not stored.
- **`upload_artifact_file_as`.** `add` hashes each file once, for the claim, and names its upload by that digest, so a file changed in between ends in `ARTIFACT_DIGEST_MISMATCH` and nothing is added. The helpers return `ArtifactUpload { artifact, created, sent }` and fail with `UploadError { Io, Changed, Client }`.
- **`reef ws gc` exits 8 on `evidence_error`**, as on `jj_error`.
- **CLI details.** `--no-upload` conflicts with `--envelope` and `--public-key`. `artifact read`'s stdout is the bytes on a pipe too, as `file read`'s is; `-o json` prints `json::Artifact`, `-o brief` `brief::Artifact`.
- **`ForgetRepository` holds the `ArtifactLock`** while it forgets (`Holder::Forget`), taken after the repository's create lock as GC takes them, so no upload commits a row and a file that outlive the repository.
- **Test 14's restores** each use `--into` with `--root`: without `--root`, a restore replaces the live test repository's `.jj/repo`.
- **`artifact_bytes_freed`** is what the removed files had allocated in a run, and their sizes in a dry run, as `GcReport` documents.
- **Test 8's fixture sets its own bookmarks**: synthetic repositories have no trunk bookmark.
- **The backup path** is `<dest>/repos/<id>/artifacts/sha256/`, the store's own layout.
- **Review (2026-11-06): an upload grace independent of `keep_newer`.** The design let `keep_newer` alone keep an upload waiting for its `AddEvidence`, and `[gc] undo_window = "0s"` is legal, so GC could delete a fresh unnamed upload, or cap-collect a fresh one. The unnamed sweep and the cap now leave alone what was used after `min(keep_newer, now − UPLOAD_GRACE)`, `UPLOAD_GRACE` being a day, as long as a partial upload is kept (`artifacts::retention::tests::the_upload_grace_holds_whatever_the_floor`, `artifacts::upload_grace`).
- **Review: a size that disagrees with the file is damage.** An upload's stored check treats a stored row whose file's length is not the row's size as not stored, so an upload repairs it, and `ReadArtifact` reports it before any data as `ARTIFACT_DAMAGED` with a new `damage` value, `size` (metadata `actual_size`) (`artifacts::size_damage`).
- **Review: bytes Reef drops read as collected.** The quarantine of a damaged whole read, and the tidy finding a stored row with no file, make the row a tombstone (`collected_at` now), so readers see `ARTIFACT_STATE_COLLECTED` rather than a stored artifact with no bytes; an upload of the genuine bytes stores them again. "Collected" now also covers bytes Reef found damaged or missing and dropped (tests 6 and 11).
- **Review: the lock is held for less.** An upload's chunk checks for a stored digest with a read and takes the lock and writes (`used_at`) only when a stored row matches; the complete partial upload is hashed (`ArtifactBytes::check`, new) before the lock is taken, and the commit holds it only to check the repository and the stored digest again, rename (`ArtifactBytes::commit`) and insert the row; a quarantine hashes outside the lock and, under it, deletes only while the row's `stored_at` is still the one the read saw. Test 13's guarantee holds because the answer "stored" is still only given under the lock, after a re-read of the row and a stat: a probe that saw GC's victim stored waits for GC and then finds it gone.
- **Review: a forget racing an upload stores nothing.** The commit checks under the lock that the repository is still registered (`REPOSITORY_NOT_FOUND`), `store_artifact` inserts only while the repository's row exists, and no store method creates a directory above `artifacts/`, so an append after a forget fails rather than recreate `repos/<id>/` (`artifacts::forget_racing_an_upload`, `artifacts::local::tests::a_forgotten_repository_is_not_recreated`).
- **Review: dedup before the size limit**, so a probe of a stored artifact still succeeds after `max_object_size` is lowered; **`artifact read -o json`/`-o brief` reads the record with `GetArtifact`**; and the schema 7 backfill streams the stored envelopes instead of loading them all.
- **The GC step's benchmark is 4.62 s, not under 3 s** (1.5 times; `live_set` 60 ms). About 1.6 s is the 65 commits of 1,000 objects and the WAL checkpoints they trigger; the 1,000 stays, to keep the write lock short. Preparing the deletes once per transaction took it from 5.02 s. `docs/benchmarks.md` has the profile.
