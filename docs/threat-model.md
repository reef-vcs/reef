# Threat model

What Reef protects, from whom, and where it does not. RX.01 wrote this for the 0.1.0 release; [ADR 0027](adr/0027-trust-boundaries-in-phase-1.md) is the decision it rests on. It is a living document: a ticket that changes a trust boundary (a new RPC, a new file the daemon writes or runs, a new place it reads repository content) adds its rows to the [findings table](#findings), and [`SECURITY.md`](../SECURITY.md) points reporters here.

## The boundary in one paragraph

In Phase 1, one user id is one trust domain. The daemon runs as the user, and anything running as that user can reach its socket. An agent in a workspace can therefore do everything the user can: read and write every workspace, the user's checkout, the shared stores, and the state directory, and call every RPC. Workspaces isolate *accidents* (a separate directory, a separate working-copy commit, build outputs out of the tree, a lease that cleans up) and *repository content* (a tree, a `reef.toml`, a symlink), not a hostile agent. Containing a hostile agent needs a sandbox outside Reef: the harness's own, a user namespace, or a microVM. The boundaries Reef does enforce are the kernel's, against other local users, and the ones around repository content, which Reef acts on before the user runs anything from it.

## Assets

| Asset | Where | Why it matters |
| --- | --- | --- |
| The agents' work | jj changes and operations in `.jj/repo`, workspace directories | Losing it is what Reef exists to prevent |
| The user's checkout | The registered root, its `.git` and `.jj` | Reef writes `.jj` and one `info/exclude` line there (ADR 0024) |
| The state directory | `<state>`: `reef.sqlite3`, `logs/`, `repos/*/bases`, `repos/*/ws`, `stores/` | Holds every workspace's lease id, paths, and the base cache; the stores are mounted into every workspace |
| The socket | `<state>/daemon.sock`, or `$XDG_RUNTIME_DIR/reef/daemon.sock` | Every RPC is authorized by reaching it |
| Backups | Any directory `reef backup` names | A full copy of the database and the jj repositories |
| The binaries | Release tarballs, the Homebrew formula, `install.sh` | 0.1.0 is the first thing anyone installs |
| The web listener (R2.18) | A TCP port on loopback, `[ui] listen` (`127.0.0.1:0` by default), bound by the first `reef ui` until the daemon stops | The first listener that is not the socket: with a session's token it reads every registered repository |
| Web UI sessions and launch files | Session tokens in the daemon's memory (as blake3 digests) and in the browser's `localStorage`; `<state>/ui/open-*.html` for at most 60 s | A token is a credential for every `ACCESS_READ` RPC until the daemon stops |
| The remote listener (R2.08) | A TLS port, `[remote] listen` (`0.0.0.0:7470` by default), off unless `[remote] enabled` or `--remote` | Any host that routes to it can attempt it; with a token it serves the API and the web UI |
| Remote tokens | blake3 digests in `reef.sqlite3`'s `remote_tokens`; secrets in clients' `remotes.toml` (`0600`), their environment, and browsers' `localStorage` | A `write` token describes, abandons, undoes and edits changes in every registered repository until it expires or is revoked |
| The remote listener's generated key | `<state>/remote/key.pem` (`0600`, in a `0700` directory), not in backups | Whoever holds it can impersonate the daemon to a client that pinned it |

## Actors

| Actor | In scope for 0.1.0 | Why |
| --- | --- | --- |
| A same-uid agent in a workspace, running arbitrary code | Only as the subject of claims: no document promises protection against it that the code does not enforce | Not a boundary (ADR 0027) |
| Another local user on the same host | Yes | The one boundary the kernel gives us: modes and ownership |
| Repository content: a repository the user cloned, or a commit an agent made (`reef.toml`, tree entries, symlinks, `.git/config`) | Yes | Reef acts on it with the user's privileges before the user runs anything from it |
| A compromised package fetched by a store build | Documented only | The same as running the install yourself; Reef cannot vet it |
| A network attacker against the installer, and the release pipeline | Yes | 0.1.0 is the first thing anyone installs |
| A page in the user's browser, from any origin (R2.18) | Yes | It can send requests to the web listener's port, and any site can send the user's browser there |
| A remote client with a token (R2.08) | Yes | It calls the scopes its token allows through the remote listener |
| Any host that can route to the remote port (R2.08) | Yes | It reaches the TLS handshake and the token check without a token |
| A network attacker between a remote client and the daemon (R2.08) | Yes | It sees or alters traffic, or impersonates the daemon to collect a token |
| Forged evidence, keys, executors | No | RX.02, Phase 3 |

## Boundaries and what each component trusts

- **The socket** is `0600` in a `0700` directory the daemon's user owns, so only that uid connects. The daemon reads no peer credentials: every client is the user, and every RPC is open to every client. A root daemon (the kernel overlay tier) serves only root clients, so its agents are root too.
- **The state directory** is `0700` and owned by the daemon's euid, checked at every start; the database is `0600`. A state directory another uid owns is refused, root included (S-01).
- **Repository registration** walks up from the given path to the nearest `.jj` or `.git` and accepts it only if that directory is owned by the daemon's euid, or under `sudo` by `SUDO_UID`, git's `safe.directory` rule (S-02).
- **Repository content** is trusted to be data. Materialization goes through jj-lib's checkout, which refuses `.`, `..`, `.git`, and `.jj`; Reef refuses a commit with a tree entry jj-lib cannot read before a create, a move, a store build, GC, or registration reads it, and a read RPC that meets one fails without taking the repository down (S-18); every walk Reef does itself refuses to follow symlinks; store mounts check every ancestor of the mount path; ignore files are patterns, never paths the daemon opens. The tests are `crates/reef-daemon/tests/hostile_repo.rs`.
- **`reef.toml`'s `build`** is the one piece of repository content the daemon executes, as the repository's declared build command, and only when `Stores.Build` asks for it. The CLI shows the argv and `[store.env]` before the output; `[store] allow_builds = false` refuses every build (S-03).
- **The lease id** authorizes heartbeats, and the owner string is informational. Any client can list every lease id, and `Release` needs none: the socket is the authorization (S-08).
- **`git gc`** runs `[gc] git_executable` in a registered repository, from `reef ws gc` and from the daemon's daily GC timer (#95), which reads that repository's `.git/config`. For a repository the user owns, that is git's behavior, outside this model (S-13).
- **The web listener** (R2.18, [ADR 0047](adr/0047-web-ui-transport-and-local-listener.md)) is bound only by `CreateWebSession`, an ADMIN RPC on the socket, and only on a loopback IP literal. Its gate trusts nothing a browser or another local user sends: the `Host` must be the bound authority, an `Origin` or `Sec-Fetch-Site` must be its own, the body must be binary gRPC-web, and the bearer token must name a live session, before an `ACCESS_READ` method runs. The embedded assets are public. See [Loopback listener (R2.18)](#loopback-listener-r218).
- **The remote listener** (R2.08, [ADR 0049](adr/0049-remote-listener.md)) is bound at start only when `[remote] enabled` or `--remote` asks, and speaks only TLS. Its gate trusts nothing a client sends: the `Host` must be a configured name or an IP literal, an `Origin` or `Sec-Fetch-Site` must be its own, the body must be binary gRPC-web or native gRPC, and the bearer token must name a live token whose scope allows the method; ADMIN methods are never served. Handlers apply the WRITE rules (no `path` on a create; release, move and renew only of the token's own workspaces). The caller's token is recorded on every operation it causes. See [Remote listener (R2.08)](#remote-listener-r208).
- **The installer** fetches over HTTPS only, checks each tarball against the release's `SHA256SUMS`, and installs without `sudo`. The checksums come from the same release, so they prove the download is what GitHub serves, not who built it; the provenance attestation does that (S-06).

## Harness sandboxes

Harness sandboxes (Claude Code's, Codex's) confine an agent's writes and network access. None of them knows about Reef's socket. If the sandbox lets the agent connect to it, `Create.path`, `Backup.dest`, and `Stores.Build` act outside the sandbox with the user's full privileges: a store build runs the argv of the agent's choosing (it can commit its own `reef.toml`), and a workspace created at a path of the agent's choosing writes a tree of the agent's choosing there. This is the one-uid decision seen from inside a sandbox: Reef is not the sandbox's enforcement point and cannot tell the sandboxed agent from the user (S-07).

What an operator can do:

- Deny the sandboxed agent the socket: `<state>/daemon.sock` (`~/Library/Application Support/reef/daemon.sock` on macOS, `~/.local/state/reef/daemon.sock` on Linux), `$XDG_RUNTIME_DIR/reef/daemon.sock` on Linux, and whatever `REEF_SOCKET` names. The agent then cannot use Reef at all.
- Or let it use workspaces but never trigger a build: `[store] allow_builds = false` in the daemon's `config.toml`, and build stores outside the sandbox. `Create.path` and `Backup.dest` stay open; give the sandbox no daemon whose user can write where it must not.

The MCP server, `reef mcp` ([ADR 0035](adr/0035-mcp-server.md)), runs where the harness starts it, outside the sandbox the harness gives the agent's shell, so a rule denying the socket does not stop an agent from reaching the daemon through it. What it reaches there is the server's tools: no ADMIN RPC, no `path` on a create, no backup, no store build, no forced release, and no implicit registration of a repository a call names (only the checkout the harness started the server in is registered implicitly). Through it an agent writes only inside Reef's workspaces, at the daemon's root, and the jj stores of registered repositories, and reads any registered repository's committed files. An operator who denies the socket must also leave `reef mcp` out of the harness's MCP configuration (for Claude Code, the `.mcp.json` that `reef init` writes). Its tools' annotations are hints for the client's confirmation policy, not authorization.

The follow-up that would remove daemon-side execution altogether ([#61](https://github.com/reef-vcs/reef/issues/61)) is to run the build in the client's process, inside its sandbox, with the daemon only sealing the result. It changes ADR 0022's second decision for `reef store build` and is a Phase 2 question; the MCP server exposes no build.

## Findings

Severity is the rubric's:

| Severity | Meaning |
| --- | --- |
| Critical | Repository content gets code execution, or a write or delete outside the workspace and state directory, from an operation that does not ask for that repository's code to run (create, snapshot, release, reclaim, gc, backup, registration); or another local user reaches the socket, state, or workspaces |
| High | Another local user reads Reef state or a workspace, or plants something Reef then acts on; repository content makes one of those same operations act outside the workspace and state directory; a tampered binary installs over HTTPS without a checksum failure |
| Medium | A documented promise the code does not keep; repository content crashes or wedges the daemon; an operation that does ask for the repository's code to run (`reef store build`) does so without showing the command or without an operator's switch; a same-uid process doing something the documents imply it cannot |
| Low | Hardening with no concrete actor behind it |

What blocks a release: every Critical and High is fixed or unreachable by default; every Medium is fixed, or listed in [the quickstart's limitations](quickstart.md#known-limitations-in-phase-1) and here; Low is filed.

Status is *fixed in RX.01* with the tests, *verified* (the test shows Reef already does the safe thing), *documented* with where, or *follow-up*.

## Not boundaries in Phase 1

- **Sandboxing `reef ws run` or a store build** (user namespaces, seccomp, a build container): ADR 0016's alternative and ADR 0022's consequence. Scheduled when a harness asks for it, or when R3.06's executor sandbox exists to share: [#62](https://github.com/reef-vcs/reef/issues/62).
- **Daemon-user separation**: a `reef` system user owning the daemon and the stores, clients told apart by peer credentials. This is the step that would make the daemon a boundary against its own clients and make `workspace.overlay_nosuid` mean something; a later decision. R2.08 tells remote callers apart by token and leaves local callers one trust domain.
- **Peer-credential checks on the socket**: the mode already limits clients to one uid, and the daemon has no second uid to tell apart.
- **Denial of service on the local socket**: rate limits and request size limits.
- **A shared state directory**: two uids sharing one never works (a root-owned database, socket, and lock refuse the other's daemon), and S-01 refuses it outright.

## Requirements for a listener that is not the socket

Every RPC on the socket is authorized by the socket's mode, so a listener that is not the socket must satisfy these before it serves any of them, and its brief reviews its implementation against this list and adds its rows to the findings table. R2.18's loopback listener is the first; R2.08's remote listener is the second.

1. **TLS, for a listener reachable from another host**, with a pinned or CA-issued certificate. No plaintext mode. A loopback listener carries no traffic between hosts and is exempt; its rules are [below](#loopback-listener-r218).
2. **A per-client token with scopes.** A phone that approves proposals is not a client that can `Create` a workspace at an arbitrary path, run a store build, back up to a path, quiesce the daemon, or release another client's workspace. Each scope names the RPCs it allows; the default scope allows none of those. The schema classifies every RPC for this: `(reef.api.v1.access)` is `READ`, `WRITE` or `ADMIN` on each method ([ADR 0029](adr/0029-daemon-api-v1.md)), and scopes are sets of those levels plus field rules.
3. **The local socket's full API is never exposed by default.** What a client of the listener can call is an explicit list.
4. **Rate limits on the unauthenticated surface**: the handshake and token checks.
5. **Audit**: every mutation through the listener is recorded with the client's identity: in the operation's attributes, which the API returns typed, and in the daemon's log for a write that records no operation. (Amended by R2.08 from "in the operation log's description": since [ADR 0031](adr/0031-writes-over-jj-state.md) the attributes are where the operation log records who caused an operation.)

### Loopback listener (R2.18)

The web UI's listener ([ADR 0047](adr/0047-web-ui-transport-and-local-listener.md)) meets the list as follows:

1. **TLS**: not required. It binds only a loopback IP literal (`[ui] listen`, validated at load), so no other host reaches it. Packet capture on loopback needs root on Linux (`CAP_NET_RAW`) and on macOS (the BPF devices), and root is outside the model.
2. **Tokens with scopes**: one 256-bit token per `reef ui`, with one fixed scope, `ACCESS_READ`. `CreateWebSession`, which mints them, is ADMIN and served only on the socket. Tokens are never persisted and end at every daemon restart (S-31, S-32, S-34).
3. **Not the full API by default**: READ methods only, by the schema's classification, over gRPC-web only. The listener exists only after the first `reef ui`, and `[ui] enabled = false` keeps it from ever binding.
4. **Rate limits**: a guess at a 256-bit token cannot succeed at any rate, so the limits are on resources: 64 open connections, tonic's 4 MiB decode limit, and a refusal that costs one hash and one lookup (S-28). Denial of service by a local user is not a boundary (above).
5. **Audit**: nothing to audit; the listener serves no mutation. R3.31's first write from the UI brings audit with it.

A listener that browsers reach must also refuse other origins and DNS rebinding (S-29, S-30), and keep repository content from running as script in its page (S-33).

### Remote listener (R2.08)

The remote listener ([ADR 0049](adr/0049-remote-listener.md)) meets the list as follows:

1. **TLS**: always, on any address, loopback included; TLS 1.2 and 1.3 through rustls on ring. The certificate is generated and pinned by its key's digest, or supplied and validated against CA roots; a client verifies one or the other before it sends anything (S-35, S-45).
2. **Tokens with scopes**: named per-client tokens, `read` (ACCESS_READ) or `write` (also ACCESS_WRITE), `read` by default, 30 days by default, stored as digests, rotated and revoked through ADMIN RPCs on the socket. No scope allows ADMIN, so no store build, backup, quiesce, GC, registration or web session. The WRITE rules refuse a create at a path and a release, move or renewal of a workspace the token did not create (S-36 to S-39).
3. **Not the full API by default**: the listener is off unless asked for; it serves only what a token's scope allows, never the v0 beacon or `CreateWebSession`, and never inherits the socket's "every client is the user" (S-44).
4. **Rate limits**: handshake concurrency and timeout, connection caps per listener and per address, backoff for addresses that fail tokens, refusals that cost one digest and one lookup, bounded tracking (S-36, S-40).
5. **Audit**: the token's id and name on every operation a remote call causes, typed in the API, and every remote WRITE call, refusal and token change in the daemon's log under `reef_daemon::remote::audit` (S-42).

A browser reaching it gets R2.18's protections from a non-loopback origin (S-41). What each scope exposes is stated as findings (S-39, S-43, S-46, S-47). Until an external review, run the listener on a private network (a VPN, a cloud VPC) rather than the open internet.
