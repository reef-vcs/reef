# Changelog

All notable changes to Reef. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/) once a release exists.

## [Unreleased]

### Upgrading

- The daemon's database becomes schema 7 (`0007_evidence`, R3.01) the first time this daemon opens it. An older daemon then refuses the database, as with every migration: restore a backup taken before the upgrade to go back.
- The daemon's database becomes schema 8 (`0008_artifacts`, R3.02) the first time this daemon opens it, and the same start indexes, once, the artifact digests of the evidence already stored.
- The daemon's database becomes schema 9 (`0009_identity`, R3.03) the first time this daemon opens it. The same start creates a `person` operator identity named after the login user (lowercased; `operator` when the name has nothing usable), which socket requests use when they name none, and the daemon's identity authority key at `<state>/identity/authority.pem` (`0600`). The key is never in a backup: a restore retires the restored authority and the next start makes a new one, while certificates already issued still verify.
- `reef evidence add` now signs with a session key by default: without `--key` or `--envelope`, it no longer refuses, but has the daemon certify a five-minute key for the default identity (or `--identity`) and signs with it. Scripts that pass `--key` are unaffected; their evidence reads `unbound`.
- The root help's "Also:" line lists `identity` and no longer `completions`, which `--help-all` still lists.
- The daemon's database becomes schema 10 (`0010_provenance`, R3.04) the first time this daemon opens it. From then on every committing snapshot and every `EditFiles` naming a workspace records a signed provenance record; `[provenance] enabled = false` turns that off.
- The root help's "Also:" line lists `provenance` and no longer `restore`, which `--help-all` and `reef backup --help` still name.
- Garbage collection now deletes evidence that is not on live work and was added more than 90 days ago, at the first run after upgrading (the daemon runs GC every `[gc] interval`, a day by default). Set `[evidence] retention = "0s"` in the daemon's `config.toml` before upgrading to keep all evidence; `reef ws gc --dry-run` reports what would go.

### Added

- Evidence objects (R3.01, [ADR 0055](docs/adr/0055-evidence-object-format.md), [docs/evidence.md](docs/evidence.md)): a signed claim that a check (test, build, lint, policy, or another kind) passed, failed, or reached no verdict on one git tree. The claim is an in-toto Statement v1 with the predicate `urn:reef-vcs:evidence:v1`, signed once with ed25519 in a DSSE envelope; its id is the SHA-256 of the envelope in canonical form, and the signer is its key, named by the SHA-256 of the key's DER SubjectPublicKeyInfo. Evidence binds to the tree, so it stays on a change across a describe or a rebase that keeps the tree, and survives garbage collection; `reef repo forget` deletes a repository's evidence. A valid signature says which key signed, not that the key is trusted; policy decides that in a later release (R3.07).
- `EvidenceService` (API revision 15): `AddEvidence` checks an envelope (the envelope, the key, the signature, then the payload) and stores it with its key and, optionally, a link to the change it was produced for; `GetEvidence` and `ListEvidence` read it back, checking each signature again, by id, by revision or tree, or by change. Adding evidence records no operation.
- `reef evidence add`, `list`, `show` and `key generate`: sign a claim about a revision's tree with an ed25519 key file and store it, or send an envelope signed elsewhere (`--envelope`); list a revision's, a tree's or a change's evidence; show one object, its statement and whether its signature verifies, or its canonical envelope's bytes (`--envelope`); and make a key pair. A key file that others can read is refused.
- `reef schema evidence`: the evidence format as JSON Schema (`evidence.Statement`, `evidence.Predicate`, `evidence.Envelope`), from the binary, for executors in any language.
- `reef-evidence`, the format crate: building, signing and checking evidence, with no jj-lib, gRPC, tokio or SQLite dependency.
- An artifact store for evidence (R3.02, [ADR 0056](docs/adr/0056-evidence-artifact-store-and-retention.md), [docs/evidence.md](docs/evidence.md#artifacts)): the logs, reports and build outputs evidence names by SHA-256, stored once per repository under the daemon's state directory, with their index in `reef.sqlite3`. Evidence reads now report each artifact as `stored` (with its size), `collected` (with its date) or `absent`.
- `ArtifactService` (API revision 16): `UploadArtifact` stores an artifact in chunks of at most 1 MiB, keyed by its digest and size, so an upload resumes after a lost response or a daemon restart and bytes already stored are never sent again; `GetArtifact` reads an artifact's record and the evidence naming it; `ReadArtifact` streams the bytes, and a read of a whole artifact whose stored bytes no longer match the digest ends in `ARTIFACT_DAMAGED`. Uploads record no operation.
- `reef evidence artifact upload`, `show` and `read`: upload files without evidence, show an artifact's state, size and evidence, and write its bytes to stdout (`--offset`, `--length`; the record with `-o json`). `reef evidence add --artifact` now uploads each file before adding the evidence; `--no-upload` records the digest only, and with `--envelope`, `--artifact` uploads the files the envelope names.
- Evidence and artifact retention, as garbage collection's seventh step: evidence that is not on live work (`trunk() | bookmarks() | working_copies() | mutable()`, or a change it was added for that is still live) is deleted after `[evidence] retention`; artifacts no evidence names are deleted, those named only by such evidence are collected after `[artifacts] retention`, and the least recently used go while the store passes `[artifacts] max_size`. Nothing newer than the undo window, or the last backup's retention, is deleted. `GcReport` gains `evidence_removed`, `artifacts_collected`, `artifact_bytes_freed`, `artifact_bytes` and `evidence_error`; `reef ws gc` prints `evidence <n> removed, artifacts <n> collected (<size>), <size> kept`, and exits 8 when the step stopped short.
- `[evidence] retention` (`"90d"`), and `[artifacts] retention` (`"30d"`), `max_size` (`"10GiB"`) and `max_object_size` (`"1GiB"`) in the daemon's configuration; `0s` turns a retention off.
- Operator identities and session keys (R3.03, [ADR 0057](docs/adr/0057-operator-identities-and-session-keys.md), [docs/identity.md](docs/identity.md)): an identity is the person or CI pipeline a key answers to (`person` or `ci`, named once and never reused); agents are the declared actor of a key, not identities. The daemon's authority key certifies short-lived ed25519 session keys, generated by the process that signs and never seen by the daemon, with a proof of possession. A certificate is an in-toto statement (`urn:reef-vcs:session-key:v1`) in the same DSSE envelope as evidence. On the socket any live `person` identity gets keys, and a `ci` identity never; through the remote listener a token gets keys only for the identity it is linked to, and never declared `human`. Keys live an hour by default (`[session_keys] lifetime`, at most `max_lifetime`, 24 hours by default), renew within a session, and are revoked one at a time, by session, by identity or by authority, from an `invalid_from` that `--since` can backdate.
- `IdentityService` (API revision 17): `CreateIdentity`, `GetIdentity`, `ListIdentities`, `RevokeIdentity`, `IssueSessionKey`, `GetSessionKey`, `ListSessionKeys`, `RevokeSessionKeys`, `ListAuthorities`, `RotateAuthority` and `RevokeAuthority`. Issuing a key records no operation.
- `Evidence.identity`: every evidence read reports which identity the signing key is bound to, its actor and session, and its status when the daemon first saw the object: `unbound` (a bare key), `bound`, `expired`, `revoked` or `invalid`. It sits beside `signature` and is not a trust decision. `ListEvidenceRequest.identities` and `reef evidence list --identity` filter by it; `reef evidence show` prints an `identity:` line, and `--actor human` keys print `presence none (not verified)`.
- `reef identity create`, `list`, `show`, `revoke`, `session issue|list|show|revoke`, and `authority show|rotate|revoke`. `session issue -o json` prints a session key's private key, a credential, for a script in another language; the text form refuses before issuing. `RevokeAuthority` revokes an authority already retired (by a restore, a replaced key file, or a rotation without `--revoke`).
- `reef remote token create --identity <name>` (`CreateRemoteTokenRequest.identity`, `RemoteToken.identity`) links a token to an identity: the only one it gets session keys for, and a `ci` identity's only way to get any.
- `[session_keys]` in the daemon's configuration: `lifetime` (`"1h"`), `max_lifetime` (`"24h"`), each at least 5 minutes, and `default_identity`. One that names no live person identity is logged and leaves the daemon without a default, which cannot be revoked while it is one.
- Garbage collection sweeps session keys that ended over a week ago, and before the undo window, that no evidence names (`GcReport.session_keys_removed`).
- `reef schema evidence` includes `evidence.SessionKeyStatement` and `evidence.SessionKeyPredicate`, so a verifier in another language can parse a certificate.
- Provenance records (R3.04, [ADR 0058](docs/adr/0058-provenance-records.md), [docs/provenance.md](docs/provenance.md)): every commit the daemon records for a workspace (each snapshot that commits, and each `EditFiles` naming the workspace) gets one record, an in-toto statement (`urn:reef-vcs:provenance:v1`, subject `gitCommit`) in the evidence envelope, signed by a key the daemon holds in memory for the workspace's session and certifies with `custody: daemon`. A record carries the commit, change, tree, workspace, session and time the daemon observed, and the model, harness, task, instruction hash and client session a client declared, which Reef never verifies. Recording never fails a snapshot. Records are found by change, read back checked at every read with the key's identity, and kept in `reef.sqlite3`; nothing is written into commits.
- `ProvenanceService` (API revision 18): `DeclareProvenance` (snapshots the workspace first, then replaces fields of its declared context), `GetProvenance` (by revision, commit id or record id) and `ListProvenance` (by changes, workspace, session and time). `CreateWorkspaceRequest.provenance` declares at creation and names the session's identity and actor; `Workspace.provenance` reports the live session.
- `reef provenance show`, `list` and `declare`; `--model`, `--task`, `--instruction-file`, `--identity` and `--actor` on `reef ws create` and `reef ws run`. `--model` and `--task` default to `REEF_MODEL` and `REEF_TASK`, which `ws run` passes on to its command. An instruction is sent as the SHA-256 of a file's exact bytes; its text never leaves the CLI. `reef ws inspect` prints the session.
- `[provenance]` in the daemon's configuration: `enabled` (`true`), `compact_after` (`"7d"`) and `retention` (`"90d"`). Garbage collection's eighth step keeps the first and last record of each run under one context once records are older than `compact_after`, and deletes records of changes with no visible commit after `retention` (`GcReport.provenance_compacted`, `provenance_removed`, `provenance_error`).
- `reef schema evidence` includes `evidence.ProvenanceStatement` and `evidence.ProvenancePredicate`.
- Backups include each repository's stored artifacts (`repos/<id>/artifacts/`, a `BACKUP_STEP_ARTIFACTS` progress message, and `artifact_files` and `artifact_bytes` in the manifest), and restore puts them back. A backup from before this release restores without artifacts.

### Fixed

- The web UI's workspaces page shows a released workspace as `released`. When the release's last operation reached the page before the workspace's final state, the row kept reading `releasing` until the next operation in the repository. The page now reads a releasing workspace again until it ends, and also shows a release that failed as active again ([#212](https://github.com/reef-vcs/reef/issues/212)).

## [0.4.2] - 2026-11-05

Reef on jj-lib 0.47.0. With jj-lib 0.46, a revset nested deeply enough overflowed the parser's stack and aborted the daemon, so one request that takes a revset or revision (`reef log -r` and `ListChanges`, `GetChange`, `GetDiff`, the file reads, the MCP tools), from a local agent or a remote reader, could take it down; 0.47 refuses one nested more than 256 levels. It also carries this project's two upstream fixes for git trees jj cannot represent.

### Upgrading from 0.4.1

Nothing to migrate: the API revision (14) and the database schema (6) are those of 0.4.1, and a `jj` 0.46 or 0.47 CLI works in a repository Reef uses. **Restart the daemon** once `reef ws list` shows no active workspaces (`reef daemon stop`; the next command starts 0.4.2's): the fix is in the daemon, and a 0.4.1 daemon keeps running after the binaries are replaced.

### Changed

- Reef is built on jj-lib 0.47.0 (from 0.46.0). Nothing to migrate: jj 0.47 keeps 0.46's on-disk formats, so a `jj` 0.46 CLI keeps working in a repository Reef uses, and the API revision (14) and database schema (6) are unchanged. Date patterns in revsets that name a time on a day with a daylight-saving change (`after:"2024-03-10 03:30"`) use that time's UTC offset, not the one at the start of the day, which put times after the change an hour off.

### Fixed

- A revset nested more than 256 levels deep is refused as an invalid argument; before, one could overflow the parser's stack and crash the daemon. A diff whose rename detection meets a git tree entry name jj cannot represent fails with an error instead of panicking the read, which reopened the repository ([jj-vcs/jj#10501](https://github.com/jj-vcs/jj/pull/10501)); so does a read of a tree with such an entry, which also panicked inside jj-lib, while holding its git backend's lock, before the repository was reopened ([jj-vcs/jj#10467](https://github.com/jj-vcs/jj/pull/10467)). Both now fail with `INTERNAL` and the path jj could not read.

## [0.4.1] - 2026-11-04

The TypeScript SDK on npm, which 0.4.0's release did not publish, and a Claude Code plugin install that works without a GitHub SSH key. Nothing else changes: the API revision (14) and the database schema (6) are those of 0.4 and 0.3, and a 0.4.0 daemon serves the 0.4.1 CLI.

### Fixed

- The TypeScript SDK reaches npm. 0.4.0's release published everything but `reef-vcs` 0.4.0 to npm: its `npm` job passed the tarball as `dist/reef-vcs-0.4.0.tgz`, which npm reads as a GitHub repository (`user/repo`), and the job only warns when it fails, so the run stayed green. Its dry run had used a path npm reads as a file. Both now run `scripts/npm-publish.sh`, which passes npm an absolute path, so every dry run checks the npm command line a tag runs, and lets a dry run through once the version is already on npm. Install the TypeScript SDK at 0.4.1 or later; the rest of 0.4.0 (the binaries, Homebrew, the MCP registry, the Python SDK on PyPI) was published.
- `claude plugin install reef --marketplace reef-vcs/reef` (and `reef-workspaces`) installs without a GitHub SSH key. The Claude Code marketplace named its plugins' source as `reef-vcs/reef`, which Claude Code clones over SSH, so since 0.3.0 the install failed with `Permission denied (publickey)` in a container, on CI, or on any machine without a key; it now names `https://github.com/reef-vcs/reef.git`, as the Codex marketplace already did. Claude Code reads the marketplace from `main`, so this reached 0.4.0's plugins when it merged. If the install failed for you before, run `claude plugin marketplace update reef` first: an added marketplace keeps its old copy. The release runs' check of the published install lines only warned, and now checks `reef-workspaces` too.

## [0.4.0] - 2026-11-03

Phase 2's last rows: the Python and TypeScript SDKs, both named `reef-vcs` and published to PyPI and npm by this release's workflow. Brief `reef status` and `reef diff` read at an operation now say which operation they read, `reef history -o text` names the authors of changes no Reef agent wrote, and the remote listener answers errors in a form every gRPC client reads. Two fixes come from trying 0.3 on a large monorepo: a workspace create waits up to 5 minutes instead of failing at 30 s, and `reef init` adds Reef's MCP entry without reformatting `.mcp.json`. Phase 2 is complete.

### Upgrading from 0.3

Nothing to migrate. The API revision (14) and the database schema (6) are those of 0.3, so a 0.3 daemon serves the 0.4 CLI. Restart it anyway, once `reef ws list` shows no active workspaces (`reef daemon stop`; the next command starts 0.4's), for the remote listener's fix below, which the SDKs need when they reach a daemon remotely.

### Added

- The Python SDK ([ADR 0054](docs/adr/0054-sdks.md), [`docs/python-sdk.md`](docs/python-sdk.md)): `pip install reef-vcs`, then `import reef`. Every API call is a typed method on `reef.connect()`'s client and on `reef.aio`'s, generated from the schema, with page iterators and streams. The daemon's errors arrive as exceptions by kind, with `reason`, `hint` and `next`. The SDK finds the daemon as the CLI does and reaches a remote one with its key pinned before the token is sent. `client.workspace(...)` holds a workspace for a block of code as `reef ws run` does for a command: lease heartbeats, a presence entry, and a release with a final snapshot. Published to PyPI by each release.
- The TypeScript SDK ([ADR 0054](docs/adr/0054-sdks.md), [`docs/typescript-sdk.md`](docs/typescript-sdk.md)): `npm install reef-vcs`, then `import { connect } from "reef-vcs"`. ESM for Node 22.15 and later, loadable by `require()`. Every API call is a typed async method, generated from the schema, with page iterators and streams; messages are in `reef-vcs/api/v1`. The same error classes, discovery, remote pinning (checked in every TLS handshake) and workspace block as the Python SDK, the block both as `await using` and as `withWorkspace(...)`. Published to npm with provenance by each release.

### Fixed

- `reef ws create`, `reef ws run` and the MCP `create_workspace` tool wait up to 5 minutes for a workspace create, not 30 s, so a create in a large repository that checks the whole tree out into the base cache (the first, and on the overlay or copy backend each new tree) no longer fails partway. `--timeout` still sets the deadline. A create that runs past 5 s says why on stderr, and one that reaches its deadline says that the checkout goes on and that running the command again waits for it ([#188](https://github.com/reef-vcs/reef/issues/188)).
- `reef init` adds Reef's MCP server to an existing `.mcp.json` or `opencode.json` without reformatting it: the rest of the file keeps its indentation (tabs or spaces), line endings, one-line arrays, number and string spellings and final newline, and only Reef's lines are added ([#190](https://github.com/reef-vcs/reef/issues/190)).
- `reef init` skips a `.mcp.json` or `opencode.json` with comments or trailing commas with a reason that quotes the entry to add by hand, as it does for `opencode.jsonc`, instead of calling it "not a JSON object"; a file that already has Reef's entry is skipped with a reason that asks to check that Claude Code (or opencode) reads a file with comments ([#190](https://github.com/reef-vcs/reef/issues/190)).
- Piped `reef status` and `reef diff` read at an operation (`--at-op`, `--at`) keep `at_operation`, the full id of the operation read, so brief JSON says when its answer is not about now; so does the MCP `get_diff` tool when called with `at_operation`. Their text read at an operation starts with `At operation <id>`, with the operation's time for `status`. Reads at head print what they did ([#126](https://github.com/reef-vcs/reef/issues/126)).
- `reef history -o text` names a change's author, as `<email>`, when no Reef agent wrote it (committed or fetched outside Reef, or written by another jj client), and no longer lists `-` beside the agents of a change that has some ([#115](https://github.com/reef-vcs/reef/issues/115)).
- The remote listener sends a service's error as a trailers-only answer, its HEADERS frame ending the stream. It used to send the headers and then an empty DATA frame, which tonic accepted and other gRPC clients (grpcio) refused as "Stream removed".

## [0.3.0] - 2026-11-02

The rest of Phase 2's agent surface and its live views. Agents get brief JSON by default, a task-first `reef --help`, symbol-level diffs and a queryable history (`reef history`, the MCP `query_changes` tool), `reef schema` for generating tool definitions, and one-line installs for Claude Code, Codex and opencode, with the MCP server published to the MCP registry and as an MCPB bundle per target. Humans get a web UI (`reef ui`) with a live smartlog, a workspaces and fleet page, and an activity feed with a replay scrubber. Status answers from an incremental index instead of a tree walk, a daemon can be reached remotely over TLS with a token, and harnesses that isolate sessions in git worktrees can ask Reef for workspaces instead (the workspace provider contract). Every Phase 2 exit criterion is met; the Python and TypeScript SDKs (R2.06, R2.07) follow in a later release.

### Upgrading from 0.2

Piped output is now brief JSON: compact, one list element per line, and for `ws list`, `status` and `diff` only the keys an agent acts on, with zero values (`false`, `0`, `""`, `[]`) left out, so a check such as `.divergent == false` no longer matches. A script that reads piped `reef` output and needs the full objects passes `-o json`, or sets `REEF_OUTPUT=json` once. The MCP server's `list_workspaces`, `get_status` and `get_diff` return the brief objects too.

**Restart the daemon after upgrading:** `reef daemon stop` once `reef ws list` shows no active workspaces, and the next command starts 0.3's. A 0.2 daemon keeps running after the binaries are replaced, and it answers commands that use new options of calls it already has as if the option were absent: `--at-op` and `--at` read the current state, `diff --symbols` returns no symbols, and `ws list` shows no file counts. A command whose first call the 0.2 daemon lacks restarts it when it has no active workspaces (not under `--no-autostart` or `--remote`); otherwise it fails with exit code 9 and `next` set to `reef daemon stop`.

The new daemon migrates its database (schema 6, for remote tokens) when it starts, and a 0.2 daemon then refuses that database: there is no going back to 0.2 on the same state directory. Its first start also backfills each repository's history index (`repos/<id>/history.sqlite3`, up to 100,000 operations and 512 MiB, `[history]`) in the background, and the state directory gains `ui/` and `remote/`.

`reef init --user` now writes the user-level files only of the agents it detects by their home directories, so a machine without `~/.claude` (or `CLAUDE_CONFIG_DIR`) no longer gets the Claude Code skill; `--agents` names them instead.

### Added

- Harness packages ([ADR 0052](docs/adr/0052-harness-packages.md)): one line sets up an agent for every repository. Claude Code: `claude plugin install reef --marketplace reef-vcs/reef` (the skill, Reef's MCP server, and hooks that declare the files it edits). Codex: `codex plugin marketplace add reef-vcs/reef && codex plugin add reef@reef` (the skill and the server, from a plugin in the vendor-neutral Agent Plugins format). opencode: `reef init --agents opencode --user`. This repository is both marketplaces, pinned to each release's tag.
- `reef init --agents codex` and `--agents opencode`, also detected by `.codex/` and by `opencode.json`, `opencode.jsonc` or `.opencode/` (and opencode by `OPENCODE=1`): the skill in `.agents/skills/reef/SKILL.md`, which both read, and Reef's server in `.codex/config.toml` (merged keeping the file's comments) or `opencode.json`; with `--user`, in the home directory.
- `reef presence hook edit` and `end`: a harness's hook reports the files the agent is about to edit as an editing entry, from the hook event on stdin and JSON Pointers into it. One entry per session, replaced by its next edit, lasting 5 minutes; it always exits 0, prints nothing, and never starts a daemon.
- An MCPB bundle per target on each release, `reef-<version>-<target>.mcpb`, holding `reef` and `reef-daemon`, and the server listed on the MCP registry as `io.github.reef-vcs/reef`. Releases also carry `reef schema`'s document and descriptor set, attested with the rest.
- The onboarding benchmark's scenario E: after the Claude Code plugin.
- The workspace provider contract ([ADR 0053](docs/adr/0053-workspace-provider-contract.md), [`docs/workspace-provider.md`](docs/workspace-provider.md)): `reef ws provider create | attach | release`, for a program that isolates its sessions in directories and asks Reef for them instead of making git worktrees. Fields come as flags, or as one JSON object on stdin with `--at FIELD=POINTER` mapping the program's own event; each command prints one object (`contract: 1`), or the path alone with `-o text`. A name makes `create` return the same workspace while it lives, and a create from inside a workspace starts on its change. `--hold-while PID|parent` keeps the lease alive while that process runs, through a detached `reef ws renew --follow`; nothing is released when it exits, so the daemon reclaims the workspace with a final snapshot once the lease runs out. Two reasons: `PROVIDER_INPUT_INVALID`, `HOLDER_NOT_RUNNING`.
- `reef ws renew --follow [--while-pid PID]` renews a lease until it ends, the process exits, or a signal.
- `reef here` reports `held` and no longer tells an agent to release a workspace that a provider's holder holds.
- The `reef-workspaces` Claude Code plugin, opt-in beside `reef` in the same marketplace: `claude plugin install reef-workspaces --marketplace reef-vcs/reef` makes Claude Code's worktrees (`--worktree`, subagents with `isolation: worktree`) Reef workspaces, through its `WorktreeCreate` and `WorktreeRemove` hooks; a resumed session's first prompt holds its workspace again (`UserPromptSubmit`).

- Symbol-level diffs ([ADR 0043](docs/adr/0043-symbol-level-diff.md), API revision 8). `GetDiff` with `symbols` reports each file's added, removed, changed and moved definitions, matched across the whole diff (renamed files and moves included), with each file's coverage, and the call sites in the new tree of the changed, removed and moved ones: exact through uploaded SCIP, by name through tags, with how many definitions share the name. `expand_symbols` returns only the named symbols' lines. `max_call_sites` and `symbol_source` tune it. Symbols are computed when at most 1,000 files differ.
- `reef diff --symbols` lists each file's symbol changes under it, nested, with up to three call sites each and the totals; `--stat` adds the line counts, `--call-sites N` sets how many are listed, and `--source` picks tags or SCIP. `reef diff --expand SYMBOL` shows only that symbol's lines. JSON gains `symbol_summary` and each file's `symbols` only with these flags.
- The MCP server's `get_diff` takes `format: "symbols"` and `expand`. `tools/list` is held to 20,250 bytes.

- A history index and `HistoryService.QueryChanges` ([ADR 0044](docs/adr/0044-history-index-and-query-layer.md), API revision 9): which changes touched files or symbols, who wrote them (activity per agent and workspace), when, and what became of them (open, landed on `trunk()`, abandoned, undone), filtered by symbol, path, agent, workspace, change, outcome and time window, paged or counted by agent, outcome or workspace, with the history each answer covers. The daemon follows the operation log into `repos/<id>/history.sqlite3`, backfills it, and keeps it through GC. `[history]` configures it. Two reasons: `HISTORY_DISABLED`, `INVALID_HISTORY_QUERY`.
- `reef history [PATH]...` with `--symbol`, `--change-kind`, `--by`, `--workspace`, `--change`, `--outcome`, `--since`/`--until` (RFC 3339 or a duration ago), `--include-empty`, `--group-by` and `--limit`.
- The MCP server's `query_changes` tool. `tools/list` is held to 21,250 bytes.
- Replay ([ADR 0046](docs/adr/0046-replay.md), API revision 11): `GetStatus`, `ListWorkspaces`, `GetWorkspace` and `ListOperations` take `at_operation` and answer as of that operation: the workspaces whose working copy its view holds, each on its change then, with what the log does not record (presence, attention, stores, the watch, lease liveness) left unset. `GetOperation` finds an operation by time with `ended_at_or_before`. Two reasons: `OPERATION_NOT_RETAINED`, `TOO_FAR_BACK`; `STATUS_SOURCE_OPERATION`.
- `--at-op` on `reef status`, `ws list`, `ws inspect` and `op log`, and `--at WHEN` (an RFC 3339 time or a duration ago) on every command that takes `--at-op`.

Every command's `--help` is about half as long.
- The R2.17 token benchmark's live gate adds the `mcp` arm's fixed cost, as its scripted half always did.

Each read first syncs with the watcher through a cookie in a directory outside the workspace root, so a write made just before it is seen.
- A watched workspace is now fully scanned at least every `watcher.watched_fallback_interval` (10 minutes), busy or idle; before, a workspace with events was never fully scanned until its release. A full scan that finds a change no event named logs "status index missed changes".

A commit created after the operation, named by its full id in a read at it, now resolves (hidden) instead of not found; change offsets and short prefixes still resolve as of the operation.
- `ListSymbols` by name or symbol reads only the matching rows of the index, not each matching file's whole entry, and (R2.16) reads them in path order with its filters and cursor in SQL, stopping at the end of the page.

### Fixed

- A command run while the daemon was shutting down, or still starting, started a second daemon, which lost the instance lock and exited, and the command reported "reef-daemon exited … before … answered". Since tonic 0.14.7 a daemon refuses connections while it drains. A command now waits, up to 15 s, while the daemon's lock is held and its socket refuses, and starts one only once the lock is free (#162).
- A panic on the daemon's filesystem-watcher threads no longer ends a workspace's watch silently. Since notify 8.2.1 such a panic unwound out of the macOS `FSEvents` thread, and a later unwatch could then spin forever. A panic in Reef's tap is logged and marks every notify workspace's journal `events-lost`, so the next reads walk; any other panic on notify's or the debouncer's threads aborts the daemon, as notify did before 8.2.1 on macOS, and the next command starts one that rescans (#161).
- `reef init` says when the `.mcp.json` it writes duplicates the MCP server of Reef's Claude Code plugin, installed on this machine, for this user or this repository, and how to turn the project's `reef` server off on this machine; it still writes the file, which is for everyone working in the repository (#153). Claude Code's user directory follows `CLAUDE_CONFIG_DIR`, for the user-level skill too.
- `reef mcp --help`'s example no longer names one harness's command (#118).
- On macOS, creating or releasing a workspace no longer drops other workspaces' filesystem events: each notify workspace has its own `FSEvents` stream.
- A read at a GC-kept copy of an operation from before the last GC failed: jj could not build an index for it once GC had removed its ancestors. It answers through the head's index now (R2.12).
- The MCP server reads path arguments as the CLI does under `--workspace`: `./`, `..` and a trailing `/` resolve, and `.` is the root where a tool takes one (`get_diff`, `list_files`). `get_diff`, `read_file` and `list_files` had refused `src/` with `INVALID_PATH`, and `query_changes` matched nothing for `./src`. An `edit_files` target with a trailing `/` is still refused (#117).
- The MCP server's `get_diff` described `max_lines_per_file` as "[default: no cut]"; the default is 1,000.
- Timestamps print with exactly three fraction digits (`2026-10-30T17:04:34.000Z`, `…34.100Z`), in the CLI's JSON and text, MCP results and backup manifests, so they sort as strings. `time`'s RFC 3339 formatting had trimmed trailing zeros and dropped a zero fraction, so a time on a whole second sorted after a later one in the same second.

## [0.2.0] - 2026-10-28

The first release of Phase 2: a typed API, `reef.api.v1`, with the CLI as a thin client of it, so `reef` now needs `reef-daemon` beside it or on `PATH`; commands that look at and revert what agents did without jj; an MCP server; live operation and presence streams; a symbol index; and garbage collection on a timer. Coming from 0.1, read [Upgrading from 0.1](#upgrading-from-01) first.

### Added

- The symbol index ([ADR 0042](docs/adr/0042-symbol-index.md)): `SymbolService` with `IndexSymbols`, `UploadScipDocuments` and `ListSymbols` (API revision 7). The daemon extracts tree-sitter tags for Python, TypeScript, TSX, JavaScript, Go and Rust itself, in the background for new snapshots and edits and on demand, and stores definitions and references with their ranges and enclosing definitions in a per-repository cache (`repos/<id>/symbols.sqlite3`), keyed by path and file content so unchanged files share entries across revisions. SCIP documents an indexer wrote are uploaded and checked against the file they describe. Four error reasons: `SYMBOLS_DISABLED`, `SYMBOLS_NOT_INDEXED`, `INVALID_SYMBOL_QUERY` and `INVALID_UPLOAD`. GC collects the index as its fifth step.
- `reef symbols index`, `upload` and `list` (alias `sym`): index a revision, upload a SCIP index, and list a file's or directory's symbols or a name's occurrences, with JSON when piped.
- `[symbols]` in `config.toml`: `enabled`, `background`, `workers`, `max_file_size` and `max_size`.
- `reef-symbols`, the extraction crate: Reef's tag queries, SCIP's symbol grammar and SCIP normalization, with no jj-lib, gRPC or SQLite dependency.
- The daemon runs garbage collection by itself every `[gc] interval` (default a day; `0s` turns it off), over every repository, 10 minutes after it starts at the earliest and a full interval after the last full run, timed or `reef ws gc` (#95, [ADR 0041](docs/adr/0041-gc-on-a-timer.md)). Its reports go to the daemon's log.
- API revision 6: `GcReport.base_bytes_unshared`, what removing the base cache entries freed on disk, counting blocks shared between incremental bases once (measured on APFS). `reef ws gc` prints it beside the allocated size.
- `reef-broker`, the subscription broker ([ADR 0038](docs/adr/0038-subscription-broker.md)): bounded in-memory rings between a log and the streams that follow it, generic over topic, position and item, with no jj-lib or gRPC dependency.
- A subscription load test (`crates/reef-daemon/tests/subscription_load.rs`, [docs/load-tests.md](docs/load-tests.md)): 500 operation-log and 500 presence subscribers at 1,000 operations a minute, every delivery checked, gated on p99 within 100 ms. `subscription-load.yml` runs it on both runners.
- `reef ws run` reports the command it runs as a presence entry (`running <command line>`), refreshed every 10 seconds and cleared when the command exits, before the release. `reef mcp` reports, per repository or workspace its calls name, the last tool called there, for a minute after the call, and clears its entries when it exits. Both name the agent from `--agent` or `REEF_AGENT`, else the workspace's owner.
- `reef presence report` reports what you are doing: `TEXT` for an activity, `--path` for files you are editing, `--phase` and `--done` for progress, in the current workspace or repository; it prints the entry's id (`-o text`) or the entry. `--id` replaces an entry, and `--id-file` keeps the id in a file for callers that are separate processes, such as a harness's hooks; an entry that had ended is reported anew. `reef presence clear` ends entries by id or `--id-file`.
- `reef ws renew` renews a workspace's lease, the one you are in by default: what `ws run` does for its command, for a workspace held outside `ws run`. `reef here` suggests it for a lease in its grace period.
- `reef_client::presence`: the `Reporter` that `ws run` and `reef mcp` use, the reporting contract that `ReportPresence`'s comment now states, and `PresenceApi`.
- Presence ([ADR 0037](docs/adr/0037-presence-channel.md)): `ReportPresence`, `ClearPresence` and `SubscribePresence`. Entries say what an agent is doing (activity), the paths it is editing, a lease heartbeat, or a long operation's progress; each has a TTL (30 seconds by default, 1 second to 10 minutes) and lives in the daemon's memory only. A subscription receives the current set, then changes, the latest state of each entry, at least 50 ms apart. At most 4,096 client entries, 32 per agent. Six error reasons: `PRESENCE_NOT_FOUND`, `INVALID_PRESENCE_ID`, `PRESENCE_MISMATCH`, `DAEMON_PRESENCE`, `PRESENCE_TOO_LARGE` and `TOO_MANY_PRESENCE_ENTRIES`. `Client::report_presence`, `clear_presence` and `subscribe_presence`.
- The daemon reports presence itself: a lease entry per workspace on every heartbeat, lapsing after two missed ones; the paths each snapshot changes; and the progress of workspace creates and store builds that run longer than 250 ms.
- `reef presence watch` prints presence as it changes, one JSON line per event when piped, filtered by `--repo`, `--workspace`, `--by` and `--kind`; `--for 0` prints who is doing what now. It stops after 30 seconds unless `--follow`, and stays a correct stream of changes across a daemon restart.
- API revision 5: `Presence.lease`, `Presence.by_daemon`, `PresenceEvent.end_reason` and `PresenceEndReason`.
- `SubscribeOperations` streams the operation log ([ADR 0036](docs/adr/0036-operation-log-subscriptions.md)): frames of operations as they are recorded, filtered like `ListOperations`, from now, after an operation, or from a frame's cursor, with nothing dropped. Operations Reef records arrive within 100 ms, other `jj` processes' within about 200 ms. Four error reasons: `INVALID_CURSOR`, `TOO_FAR_BEHIND`, `OPERATION_LOG_REWRITTEN` and `TOO_MANY_SUBSCRIPTIONS`. `Client::subscribe_operations` returns the stream.
- `reef op watch` prints operations as they are recorded, one JSON line each when piped, with `op log`'s filters, `--after` to start from an operation, and `--count`; it stops after 30 seconds (`--for`) unless `--follow`, and says on stderr how to continue.
- API revision 4: `SubscribeOperationsResponse.head_operation_ids`.
- `reef mcp`, an MCP server over stdio ([ADR 0035](docs/adr/0035-mcp-server.md)): twenty tools named after the API's RPCs (`get_status`, `list_changes`, `get_diff`, `read_file`, `edit_files`, `describe_change`, `undo_operation`, `create_workspace`, `wait_for_operations` and the rest), returning the JSON `reef -o json` prints, with errors as tool results carrying the daemon's `hint`, `next` and `metadata`. No ADMIN RPC is a tool. Workspaces the server creates are heartbeated while it runs. `wait_for_operations` waits for operations matching a filter, reading `SubscribeOperations`.
- `reef init` writes Reef's entry in `.mcp.json` with Claude Code's files, and with `--agents mcp`; it owns only `mcpServers.reef` and leaves the rest of the file as it was.
- `json::Edited`, `edit_files`' result, in `reef-client`.
- Commands over the VCS services ([ADR 0034](docs/adr/0034-cli-over-the-vcs-services.md)): `reef status`, `log`, `show`, `diff`, `describe`, `abandon`, `undo`, `op log`, `op show`, `ws snapshot`, `file read` and `file list`, from a workspace or a checkout, or with `--workspace` or `--repo`. Paths given are relative to the current directory; paths printed are repository-relative. Each prints JSON when piped (`file read` prints the file's bytes unless `-o json`), and errors from the API carry the CLI's own `hint` and a `next` built from the command and the error. Writes in a workspace return it afterwards and note on stderr when it is divergent, naming how to resolve it.
- The JSON error object carries the daemon's `metadata` when there is any, such as `AMBIGUOUS_REVISION`'s `commit_ids`.
- An error reason, `SNAPSHOT_FAILED` (metadata `workspace_id`), on a snapshot that fails before a read or a write; its kind is the snapshot error's.
- The read side of the API ([ADR 0030](docs/adr/0030-reads-over-jj-state.md)): `GetStatus` (the repository's trunk, active workspaces, mutable heads, conflicted and divergent changes, and a workspace's changed and conflicted files), `ListChanges` (the log, with graph edges, over jj's revset language), `GetChange`, `GetDiff` (summary, line counts, or unified hunks, with renames and copies), `ListOperations` and `GetOperation`. Revisions are jj revsets with Reef's `trunk()`, `immutable_heads()`, `immutable()` and `mutable()`; reads can be made at any operation, and reads of a workspace's `@` snapshot it first.
- Every operation a response reports carries its effects: changes created, rewritten, hidden or abandoned, bookmarks moved, working copies moved. Operations Reef did not just write are classified by kind.
- The write side of the API ([ADR 0031](docs/adr/0031-writes-over-jj-state.md)): `DescribeChange` sets a commit's description; `AbandonChange` abandons a commit, and on one commit of a divergent change resolves the divergence, handing its descendants, bookmarks and working copies to the surviving commit; `UndoOperation` reverts exactly one operation, refusing what it cannot revert exactly (workspace creation, release and moves, git ref imports, operations later ones changed again). Each takes an optional `expected_commit_id` (describe, abandon) and returns the operation it recorded, with effects. Workspaces a write moves are held still and, for abandon and undo, snapshotted first, so a write never overwrites unsnapshotted edits; they take the result afterwards.
- Every operation Reef records carries `reef.kind`, `reef.workspace`, `reef.agent` and, for snapshots, `reef.snapshot-kind` attributes.
- The `reef-agent` gRPC request metadata names the agent behind a write; operations record it as their agent instead of the workspace's owner. `Client::with_agent` sends it.
- Files without a workspace ([ADR 0032](docs/adr/0032-files-without-a-workspace.md)): `ReadFile` reads a file at a revision, 1 MiB at a time; `ListFiles` lists a directory, or everything below it, a page at a time; `EditFiles` applies edits (whole content, text replacement, delete, copy or rename, the executable bit) in order, all or none, to a change or as a new change on one, and records the result as one commit and one operation of kind `EDIT`, undoable with `UndoOperation`. No directory is materialized; workspaces on an edited commit are snapshotted first and take the result. Edits never write through a symlink, into `.git` or `.jj`, or under a shared store's mount. `Client` gains `read_file`, `read_file_to_end`, `list_files_page`, `list_files` and `edit_files`.
- `reef --agent <name>` and `REEF_AGENT` name the agent on every operation a command causes; `ws run` passes it on to its command as `REEF_AGENT`. An invalid name is exit 2, reason `INVALID_AGENT`.
- Three error reasons: `REPOSITORY_NOT_REGISTERED` (a path in no registered repository), `REPOSITORY_NOT_FOUND` and `WORKSPACE_NOT_FOUND`, with the path, repository or workspace as metadata.
- Two crates: `reef-client`, the thin client of the API, and `reef-error`, the error conventions ([ADR 0033](docs/adr/0033-thin-client.md)).
- `reef-daemon config show [--json]` and `reef-daemon restore`, which `reef config show` and `reef restore` run.
- API revision 3: `FileEdit.copy_from`.
- API revision 2: `OperationEffects.change_count` and `bookmark_count`, `CHANGE_EFFECT_KIND_HIDDEN`, `BookmarkEffect.conflicted`, `WorkspaceStatus.conflicted_path_count`, and `FileDiff`'s `old_no_final_newline`, `new_no_final_newline`, `too_large` and `invalid_utf8`.

### Fixed

- `reef ws gc` no longer leaves `jj` unusable in the repository's own checkout ("Could not read working copy's operation", with `jj workspace update-stale` failing too). GC now moves the operation your checkout, and any workspace you added with `jj workspace add`, last recorded onto the rewritten log, under jj's working-copy lock. While a `jj` command holds that lock, GC abandons no operations and says so (#94, [ADR 0040](docs/adr/0040-gc-and-the-users-jj-workspaces.md)).
- A write that rewrites the commit a busy workspace sits on (`EditFiles`, `AbandonChange`, `UndoOperation`) no longer makes that workspace's change divergent: edits made during the write are carried onto the new commit in the same change, and an overlap with the write is left as a conflict there (#80, [ADR 0039](docs/adr/0039-carrying-edits-through-a-write.md)).

### Changed

- `reef init --agents auto` also writes the files of the agent running it, when that agent sets a documented variable in the processes it starts, though the repository has none of them yet, so an agent told only to run `reef init` gets the files it reads. So far that is Claude Code (`CLAUDECODE=1`: its shells, hooks, stdio MCP servers, and the terminals of its IDE extensions, so also scripts started from them), which gets `CLAUDE.md`, the skill and `.mcp.json`. An `--agents` list is unaffected, and `--check` goes by the repository's files alone, so it can pass where `reef init` run by an agent would still add that agent's files. Unsetting the variable (`env -u CLAUDECODE reef init`) writes as before.
- A GC, backup or quiesce refused because maintenance is running now names what is running, such as a timed GC.
- `reef status` is a command, no longer a usage error pointing at `reef here`. Prefixes that named one command now name several and are usage errors listing them: `reef s` and `reef st` (formerly `store`), `reef d` (formerly `daemon`), `reef a` (formerly `guide`). `reef sto`, `reef da` and `reef gu` still work.
- `reef here` points a divergent workspace at `reef log --workspace <id> -r 'change_id(<id>)'`, which lists its commits, instead of `reef ws inspect`.
- An operation's `kind`, `snapshot_kind`, workspace and `agent` come from its `reef.*` attributes when it has them; `import git head` at registration is now `OTHER` rather than `EXTERNAL`.
- The daemon's API is `reef.api.v1`, in the new `reef-api` crate: typed enums instead of strings, every list paginated, every write returning the jj operation it recorded, errors as `google.rpc.Status` with a `reef.api.v1.ErrorDetail` that stock gRPC tooling decodes, and every RPC Phase 2 implements declared up front ([ADR 0029](docs/adr/0029-daemon-api-v1.md)). `reef.daemon.v0` is gone except `Daemon/Status`, which a 0.1 `reef daemon status` and `stop` still use.
- A daemon that cannot serve a request as asked says so: exit code 9, kind `unsupported`. The CLI's JSON error object carries the daemon's `reason` when there is one, such as `API_VERSION_MISMATCH`.
- `reef ws list` asks the daemon for workspaces newest first, a page at a time.
- `reef` contains no daemon and links no jj-lib ([ADR 0033](docs/adr/0033-thin-client.md)): `reef daemon run` runs `reef-daemon`, and `reef config show` and `reef restore` run `reef-daemon config show` and `reef-daemon restore`. Autostart no longer falls back to `reef daemon run`. `reef-daemon` must be beside `reef` or on `PATH`; without it, a command that needs it fails with exit 3 and the install line. The release tarballs, `install.sh` and Homebrew ship both binaries; from source, install both crates (`cargo install --git https://github.com/reef-vcs/reef reef-vcs reef-daemon`, and the same for `cargo binstall`).
- Commands other than `reef config show` read only `daemon.socket`, `daemon.pid_file` and `repo.auto_register` from `config.toml`, so an unrelated bad key no longer stops them; the daemon still refuses to start on it, and `reef config show` names it.
- `reef-vcs` re-exports `reef-api` and `reef-client` instead of `reef-lib` and `reef-daemon`, and its `watchman` feature is gone.
- `ws create --change`/`--new-on`, `ws move`, and `store build --rev` take a jj revset naming one commit, resolved in jj's order: tags, bookmarks, commit id prefixes, then change id prefixes. A bookmark whose name is also an id prefix (`cafe`) now names the bookmark, and hex text that prefixes both a commit id and a change id names the commit. A divergent change id or a conflicted bookmark is now `invalid_argument` (exit 2, reason `AMBIGUOUS_REVISION`, with the commits in the hint) instead of `conflict` (exit 5).
- Operation subscriptions are served from an in-memory broker ([ADR 0038](docs/adr/0038-subscription-broker.md)): the daemon reads each new operation once per followed repository, however many subscribe, and reads the log for a subscriber only behind the ring. Frames are unchanged.
- `reef-daemon` raises its open-file limit at start (to 10,240 on macOS, 65,536 elsewhere, within the hard limit) and logs it, so hundreds of clients can connect to a daemon started from a shell whose limit is 256. At the limit it backs off accepting for 100 ms and warns, instead of spinning a core in the accept loop.

### Upgrading from 0.1

`reef` no longer contains the daemon: install `reef-daemon` with it (`cargo install` and `cargo binstall` take both crate names; the tarballs and the Homebrew formula carry both).

A 0.1 daemon keeps running after the binaries are replaced. The first `reef` command restarts it when it has no active workspaces. Otherwise the command fails with exit code 9 and `next` set to `reef daemon stop`: stop it once its `ws run` sessions end, and the next command starts the new one. A 0.1 `reef` against the new daemon is told to upgrade (exit 5); its `daemon status` and `daemon stop` keep working.

A checkout where `jj` fails after a 0.1 `reef ws gc` is repaired by the next `reef ws gc` when its files match its commit. Otherwise that GC removes the stranded operation, and `jj workspace update-stale` there recovers it with a recovery commit.

The daemon now collects garbage by itself, first 10 minutes after the new daemon starts; set `[gc] interval = "0s"` to keep it manual. That first run also repairs a checkout a 0.1 `reef ws gc` broke, as described above.

## [0.1.0] - 2026-10-25

Phase 1: leased copy-on-write workspaces. Start with the [quickstart](docs/quickstart.md).

### Added

- `reef-daemon`, a per-user service over a Unix socket (gRPC, `reef.daemon.v0`), with a SQLite state database, structured logs, and a graceful restart that keeps leases and mounts. Any `reef` command starts it.
- Workspaces on existing git and jj repositories: `reef ws create|list|inspect|release|move|gc`, each a jj workspace materialized copy-on-write (APFS clones, kernel overlayfs or fuse-overlayfs, reflinks on btrfs and XFS, or a plain copy).
- No setup step: the first `reef` command in a git checkout registers it and initializes jj alongside git (`.jj/` and one line in `.git/info/exclude`).
- Continuous snapshots driven by a filesystem watcher (notify; Watchman for large repositories when installed), with staleness and divergence handling that never discards an agent's edits.
- Leases with heartbeats, expiry, and reclaim with a final snapshot; `reef ws run` as the agent entry point.
- `reef init`, `reef guide`, and `reef here`: `AGENTS.md`, `CLAUDE.md`, and a Claude Code skill that start agents in a workspace on their own, and errors that carry a `hint` and the `next` command to run. `reef status` and similar guesses at "where am I" point at `reef here`.
- `reef.toml` workspace spec: lease default, snapshot excludes, and shared dependency stores built once per lockfile and mounted read-only (`reef store build|list`).
- `reef backup` and `reef restore`, and a quiesce RPC for filesystem snapshots.
- Prebuilt binaries for macOS and Linux on arm64 and x86_64, a one-line installer, a Homebrew tap, and `cargo binstall` metadata.
- Benchmarks for workspace creation and a load test at 200 workspaces ([docs/benchmarks.md](docs/benchmarks.md), [docs/load-tests.md](docs/load-tests.md)).
- An agent onboarding benchmark: what a Claude Code agent new to Reef spends to reach a working `reef ws run`, in four scenarios, run in CI on demand ([docs/onboarding-benchmark.md](docs/onboarding-benchmark.md)).
- A threat model ([docs/threat-model.md](docs/threat-model.md)) and the fixes from its review: the daemon refuses a state directory another user owns and keeps its state `0700` and its database `0600`; registration refuses a repository another user owns (`[repo] allow_foreign_owner`); `reef store build` prints the command it runs, and `[store] allow_builds = false` turns builds off; a root daemon warns at start; a commit with a tree entry jj cannot read is refused instead of crashing the repository; the release workflow attests each tarball's build provenance (`gh attestation verify`), first exercised by 0.1.0's release.

### Known limitations

- Watcher snapshots are local: they stay in the repository on this machine and are never pushed or exported to git.
- Two workspaces editing one change make it divergent. Nothing is lost; resolving it is a jj operation for now.
- New workspaces start on `main`, `origin/HEAD`'s branch, `master` or `trunk`. In a repository with none of these they start on the checkout's own working-copy change, and a `jj` command in the checkout rebases them; pass `--new-on <branch>`.
- In a git checkout, Reef imports branches but does not export: an agent's change is a jj change, not a git branch, until you make it one.
- A workspace directory has neither `.git` nor `.jj`, so `git` and `jj` commands inside it fail: agents work on files, and you run `git` and `jj` in your checkout.
- `reef.toml` is read from the commit a workspace starts on, not from disk: commit it before it takes effect.
- On Linux a new workspace's watch attaches in the background after `reef ws create` returns, and `reef ws inspect` shows `notify (attaching)` meanwhile; writes made before it is up reach the store with its first snapshot.
- A shared store is read-only, so a tool that writes a cache into it fails (Vitest's `node_modules/.vitest-cache`; Vite's `cacheDir` setting moves it).
- On macOS, and on Linux without `CAP_SYS_ADMIN`, a store is protected by file permissions only: a process running as the same user could make it writable again.
- A workspace is not a sandbox: an agent runs as you and can do anything you can, including through the daemon's socket, and a harness sandbox that lets it reach the socket does not confine what the daemon does for it.
- `reef store build` runs the repository's declared command as you, with network access.
- The daemon's state directory and socket directory must be your own: a `REEF_SOCKET` directly in `/tmp`, or a state directory another user created, is refused at start.
- Reef is built on jj-lib 0.46. A newer `jj` may upgrade the repository's on-disk formats when you run it there.
- Tools that do not read `.git/info/exclude` see the `.jj/` directory.
- The binaries are not signed or notarized. Windows is not supported.
