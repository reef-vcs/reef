# Reef

[![CI](https://github.com/reef-vcs/reef/actions/workflows/ci.yml/badge.svg)](https://github.com/reef-vcs/reef/actions/workflows/ci.yml)

**Version control for fleets of coding agents.**

Reef keeps git's content-addressed storage and replaces git's working model with one suited to many concurrent, speculative, token-constrained authors. The name is the metaphor: a durable structure built by countless small organisms.

> Status: Phase 1 (leased copy-on-write workspaces) is complete and was released as 0.1.0 (2026-10-25). Phase 2 (typed API, MCP server, and live state) is complete and was released as 0.4.0 (2026-11-03); the latest release is [0.4.2](https://github.com/reef-vcs/reef/releases/tag/v0.4.2), with prebuilt binaries for macOS and Linux and Python and TypeScript SDKs. Phase 3 (evidence, proposals, and landing) is under way: signed evidence, its artifact store, operator identities with session keys, and provenance records are on `main`, not yet in a release. Start with the [quickstart](docs/quickstart.md). The CLI is not stable yet. The work is tracked in [docs/dev-tickets](docs/dev-tickets/phase-3/README.md); see [What runs today](#what-runs-today) and the roadmap below.

## Why

Git was designed for a few dozen humans making a few commits a day. Agents break every assumption behind that design.

- **Commit volume rises by orders of magnitude.** Thousands of small changes a day from dozens of concurrent writers. Anything that costs O(repository size) becomes the bottleneck.
- **Most work is speculative.** An agent tries several approaches and keeps one. Branching, snapshotting, and discarding must be nearly free.
- **The consumer of history is also an agent.** Tokens are a performance metric. A diff that costs 40k tokens to read is slow no matter how fast it computed.
- **Conflicts are routine.** Two agents editing the same file at once is the normal case. A conflict that halts an agent in a modal state halts the fleet.
- **Trust shifts from author to evidence.** No human can review every line. A change must carry verifiable evidence of which tests ran on exactly this tree.
- **Git ceremony is waste.** Staging areas, detached HEADs, and parsing porcelain output burn tokens and cause errors. Agents want a typed API.

Git worktrees, the current answer to agent isolation, make the problem concrete: every worktree is a full copy, its dependency directories dwarf the source, it has no owner and no expiry, and it holds the only copy of uncommitted work, so nobody dares delete one.

## What Reef does differently

1. **Snapshots, not commits.** The working copy is always a snapshot. No staging area, no uncommitted state.
2. **Stable identity, mutable content.** A change has a permanent ID that survives rebase and amendment.
3. **Conflicts are first-class objects.** A conflicted merge still produces a valid snapshot. It can be stored, delegated to a resolver, or fixed later. Nothing blocks.
4. **Everything is undoable.** A global operation log records every mutation, so any agent action reverts in one call (`reef undo <op>`).
5. **Workspaces are caches, not truth.** Working directories are leased, copy-on-write, and reclaim themselves when the agent goes away. Deleting one loses nothing.
6. **Hub and ephemeral workspaces.** One authoritative store per repository with lazy-fetching clients. Full clones are the exception.
7. **Evidence rides with the change.** Test results and build hashes are signed, content-addressed objects linked to the snapshot they were computed on. Landing is gated on evidence, not on who pushed.
8. **API first, CLI second.** A local daemon speaks a typed protocol. The CLI and an MCP server are thin clients. No agent should ever regex a log.

A **proposal** is the unit of review: a change or stack of changes, with its evidence, put forward for main. It is the change itself in its proposed state, identified by its change ID. There are no pull requests.

## What runs today

Reef works on existing git and [Jujutsu](https://github.com/jj-vcs/jj) repositories. Release 0.1.0 was Phase 1, which replaces git worktrees for agents, and 0.2.0 to 0.4.0 add Phase 2. Phase 3's first tickets are on `main` and in no release yet. Coming from 0.3, read [Upgrading from 0.3](CHANGELOG.md#upgrading-from-03); from 0.2, [Upgrading from 0.2](CHANGELOG.md#upgrading-from-02) as well, and from 0.1, [Upgrading from 0.1](CHANGELOG.md#upgrading-from-01) too.

### Phase 1 (0.1.0)

- **A local daemon** (`reef daemon run|start|stop|status`) serving gRPC over a Unix socket, with its state, configuration, and logs under a per-user state directory. It serves many repositories; the first `reef` command in a checkout registers it, and in a plain git checkout first creates jj's side of a colocated repository (`.jj/` plus one line in `.git/info/exclude`).
- **Leased workspaces.** `reef ws create` materializes a workspace on a change in a second or two on a 100k-file repository (under half a second on overlayfs), `reef ws run` runs a command inside a fresh workspace with the lease heartbeated for the life of the process and the workspace released on exit, `reef ws move` puts another change in a workspace's directory without giving up its lease, and `reef ws list|inspect|release` manage them. When an agent dies, its lease expires, a final snapshot lands in the store, and the directory is reclaimed. Nothing is lost.
- **Copy-on-write backends.** APFS clones on macOS, kernel overlayfs or fuse-overlayfs on Linux, reflink clones on btrfs and XFS, and a plain copy fallback everywhere, all behind one `Backend` trait and one conformance suite. A workspace costs disk proportional to what the agent changed.
- **Continuous snapshots.** A filesystem watcher (`notify`, or Watchman on large repositories) snapshots each workspace through jj-lib after every debounced write. Watcher snapshots are marked local-only and never leave the machine until a change is published.
- **Garbage collection.** `reef ws gc` reclaims operations past the undo window, base cache entries no workspace uses, and stale workspace records, and reports what it freed.
- **Backup and restore.** `reef backup <dir>` copies the daemon's database and every repository's jj state while agents keep writing, pausing each repository only while its operation files are copied; `reef restore` brings it back offline, and the next start rebuilds every workspace's directory from its last snapshot without reclaiming any ([ADR 0020](docs/adr/0020-local-backup-format.md)). A quiesce RPC holds the daemon still for a filesystem snapshot instead.
- **Shared dependency stores.** A `reef.toml` in the repository declares stores such as `node_modules` or `target`; `reef store build` builds one in a scratch workspace and seals it, and the daemon mounts it read-only into every workspace after verifying it against the lockfile hash.
- **A CLI an agent can learn from.** `reef` alone prints a one-screen guide, `reef here` says which workspace you are in and what to run next, every error with a known fix carries it as a `hint` and a `next` command, and no command ever waits on input ([ADR 0025](docs/adr/0025-agent-facing-cli-contract.md)).
- **Benchmarks** for snapshot cost and workspace creation on synthetic repositories of 1k to 100k files, published from CI on both platforms. See [docs/benchmarks.md](docs/benchmarks.md) for the numbers against the Phase 1 exit criteria.
- **An onboarding benchmark.** A real Claude Code agent that has never seen Reef, given only `reef` on `PATH`, after `reef init`, with Reef not yet installed, and inside `reef ws run`: tool calls, failed `reef` calls, tokens, and cost to a working workspace, three trials each, run in CI on demand. See [docs/onboarding-benchmark.md](docs/onboarding-benchmark.md).

### Phase 2 (0.2.0 to 0.4.0)

- **A typed API and a thin CLI.** The daemon serves `reef.api.v1`, a versioned protobuf schema checked by `buf` lint and breaking-change checks in CI ([ADR 0029](docs/adr/0029-daemon-api-v1.md)). The `reef` binary is a client of it with no jj-lib of its own ([ADR 0033](docs/adr/0033-thin-client.md)).
- **Changes without jj.** `reef status`, `log`, `show`, `diff`, `describe`, `abandon`, `undo`, `op log`, `op show`, `ws snapshot`, `file read` and `file list` look at and revert what agents did, from a workspace or the checkout, with JSON for each and a `next` command on every error with a known fix ([ADR 0034](docs/adr/0034-cli-over-the-vcs-services.md)). The API also reads files, lists directories, and applies edits at any revision without a workspace directory ([ADR 0032](docs/adr/0032-files-without-a-workspace.md)).
- **An MCP server.** `reef mcp` serves the API to an agent harness over stdio as twenty-one tools named after its RPCs: workspaces, status, the log, changes, diff, files (read, list and edit, without a directory), describe, abandon, the operation log, undo, which changes touched a file or symbol, and a tool that waits for other agents' operations. `reef init` writes its entry for Claude Code, Codex and opencode ([ADR 0035](docs/adr/0035-mcp-server.md)).
- **Live operations.** `SubscribeOperations` streams the operation log as operations are recorded, filtered by repository, change, workspace, or agent, and resumes from a cursor; `reef op watch` prints it ([ADR 0036](docs/adr/0036-operation-log-subscriptions.md)). A broker reads each operation once and fans it out ([ADR 0038](docs/adr/0038-subscription-broker.md)): with 500 subscribers at 1,000 operations a minute, p99 delivery is 53 ms for operations and 57 ms for presence on a 12-core Mac ([docs/load-tests.md](docs/load-tests.md)).
- **Presence.** What each agent is doing now: its activity, the files it is editing, lease heartbeats, and the progress of workspace creates and store builds, never persisted ([ADR 0037](docs/adr/0037-presence-channel.md)). `reef ws run` and `reef mcp` report it on their own, `reef presence report` and `clear` report finer activity, `reef presence watch` shows it, and `reef ws renew` renews a lease held outside `ws run`.
- **A symbol index.** The daemon extracts definitions and references with tree-sitter for Python, TypeScript and JavaScript, Go, and Rust, in the background for new snapshots and edits, and accepts uploaded SCIP indexes; `reef symbols index`, `upload` and `list` drive it ([ADR 0042](docs/adr/0042-symbol-index.md)).
- **Symbol-level diffs and history.** `reef diff --symbols` says which definitions a change added, removed, changed or moved, and which call sites they affect ([ADR 0043](docs/adr/0043-symbol-level-diff.md)). `reef history` and the MCP `query_changes` tool answer which changes touched a file or a symbol, by whom, and how each ended: open, landed, abandoned or undone ([ADR 0044](docs/adr/0044-history-index-and-query-layer.md)).
- **Output sized for agents.** Piped output is brief JSON with only the keys an agent acts on ([ADR 0045](docs/adr/0045-brief-json-by-default.md)), and `reef --help` is a 509-byte task-first help ([ADR 0051](docs/adr/0051-task-first-help.md)): in live Claude Code runs on the CLI, answering "what is the state of this repo" took a seventh of the tokens git did ([docs/token-benchmark.md](docs/token-benchmark.md)). `reef schema` prints the commands, MCP tools and API as JSON Schema, for generating tool definitions.
- **One-line installs for agents.** A Claude Code plugin and a Codex plugin from this repository, `reef init --agents opencode --user`, and the MCP server on the MCP registry ([ADR 0052](docs/adr/0052-harness-packages.md)). A harness that isolates sessions in git worktrees can ask Reef for workspaces instead, through the workspace provider contract; Claude Code's comes as the opt-in `reef-workspaces` plugin ([ADR 0053](docs/adr/0053-workspace-provider-contract.md)).
- **Status without a tree walk.** The watcher keeps an index of what changed, so status on a 100,000-file workspace takes 12 ms when nothing changed, against 161 ms for a walk ([ADR 0048](docs/adr/0048-status-from-the-watchers-journal.md)).
- **Remote access.** A daemon in a VM serves the same API and web UI to another machine over TLS with a scoped, revocable token ([ADR 0049](docs/adr/0049-remote-listener.md)).
- **A local web UI.** `reef ui` opens a read-only page in your browser, live from the operation and presence streams: every repository with its latest operation, each repository's smartlog, its workspaces and agents, with who is on which change, each lease's health, and disk use, and its activity feed, with a scrubber that replays any page at a past operation ([ADR 0047](docs/adr/0047-web-ui-transport-and-local-listener.md)).
- **Garbage collection on a timer.** The daemon runs `reef ws gc` by itself every `[gc] interval` (a day by default), and GC leaves the user's own jj workspaces loadable ([ADR 0040](docs/adr/0040-gc-and-the-users-jj-workspaces.md), [ADR 0041](docs/adr/0041-gc-on-a-timer.md)).

- **Python and TypeScript SDKs.** `pip install reef-vcs` (`import reef`) and `npm install reef-vcs`: every API call as a typed method, generated from the schema, with page iterators, streams, the daemon's errors by kind with `hint` and `next`, remote access with the daemon's key pinned, and a workspace block that holds a lease and reports presence as `reef ws run` does ([ADR 0054](docs/adr/0054-sdks.md), [Python](docs/python-sdk.md), [TypeScript](docs/typescript-sdk.md)).

### Phase 3 so far (on `main`, unreleased)

The groundwork for the landing gate: what a check claims, who signed it, where each commit came from, and what a repository requires. A build from `main` has it. Its daemon migrates the database to schema 17, which an older daemon then refuses, and serves API revision 29; [Unreleased](CHANGELOG.md#unreleased) has the upgrade notes.

- **Evidence objects.** A signed claim that a check (test, build, lint, policy, or another kind) passed, failed, or reached no verdict on one git tree: an in-toto statement in a DSSE envelope, signed with ed25519 and addressed by the hash of its envelope. Evidence binds to the tree, so it stays on a change across a describe or a rebase that keeps the tree, and every read checks the signature again. `reef evidence add`, `list` and `show` add and read it (`key generate` makes a key pair), and `reef schema evidence` prints the format for executors in other languages ([ADR 0055](docs/adr/0055-evidence-object-format.md), [docs/evidence.md](docs/evidence.md)). The format is its own crate, `reef-evidence`, with no jj-lib. Which keys a repository trusts is its policy's.
- **An artifact store.** The logs, reports and build outputs evidence names by digest, uploaded in resumable chunks and stored once per repository. Garbage collection deletes evidence off live work after `[evidence] retention` (90 days), and artifacts no evidence names; it collects artifacts named only by such evidence after `[artifacts] retention` (30 days), and the least recently used while the store passes `[artifacts] max_size` ([ADR 0056](docs/adr/0056-evidence-artifact-store-and-retention.md), [docs/evidence.md](docs/evidence.md#artifacts)). `reef evidence add --artifact` and `reef evidence artifact upload` upload them; backups include them.
- **Operator identities and session keys.** An identity is the person or CI pipeline a key answers to. The daemon's authority certifies short-lived ed25519 session keys that the signing process generates, and every evidence read reports the identity beside the signature (`bound`, `expired`, `revoked`, `invalid`, or `unbound` for a bare key, as of when the daemon first saw it). `reef evidence add` signs with a session key by default, and `reef identity` creates and revokes identities, issues and revokes session keys, and rotates the daemon's authority; a remote token can be linked to one identity ([ADR 0057](docs/adr/0057-operator-identities-and-session-keys.md), [docs/identity.md](docs/identity.md)).
- **Sigstore keyless keys.** A CI job, or a person with an OIDC token, can sign with a session key that Sigstore's Fulcio certified for its OIDC identity, logged in Rekor and verified offline by the daemon against a trusted root: an identity names the exact workflow or email it accepts, so a CI's evidence is bound by its workflow rather than by a long-lived token. `reef identity session issue --keyless`, `reef evidence add --keyless` and `[executor] keyless = true` sign that way, and policy can require it (`issuer_kinds = ["sigstore"]`) ([ADR 0066](docs/adr/0066-sigstore-keyless-session-keys.md), [docs/identity.md](docs/identity.md#keyless-sigstore)).
- **Provenance records.** Every commit the daemon records for a workspace gets a signed record (unless `[provenance] enabled = false`) of its change, tree, workspace and session, and of the model, harness, task and instruction hash a client declared, which Reef reports but never verifies. A client declares that context with `--model`, `--task` and `--instruction-file` on `reef ws create` and `reef ws run`, or with `reef provenance declare`, and `reef provenance show` and `list` read the records. Records live in the daemon's database, never in the commit; GC compacts them after a week and deletes those of changes with no visible commit after 90 days ([ADR 0058](docs/adr/0058-provenance-records.md), [docs/provenance.md](docs/provenance.md)).
- **Provenance from harnesses and SDKs.** Claude Code's `reef` plugin declares each prompt's SHA-256 (never its text), the session and the model through a hook that never fails or prints (`reef provenance declare --hook`); `reef ws create`, `ws run`, `ws provider create` and `reef mcp` declare the harness and its session from the environment (the cross-tool `AI_AGENT`, the agent table's session variable, the MCP client's `initialize`), and the Python and TypeScript workspace blocks take `provenance` and `declare()` ([docs/provenance.md](docs/provenance.md#declared-for-you)).
- **The executor protocol.** The contract between Reef and the processes that run checks: a job asks for evidence kinds and targets on a tree; an executor dials the daemon, claims the job under a lease, and returns signed evidence, which must be about that tree and cover every requested pair. Executors pull, so the daemon never connects to one and never sends a command; progress streams as presence. `reef job submit`, `show`, `list` and `cancel` are the requester's side ([ADR 0059](docs/adr/0059-executor-protocol.md), [docs/executor-protocol.md](docs/executor-protocol.md)).
- **The reference executor.** `reef executor run` claims jobs, reads each job's tree and checks it against the tree id, runs the commands declared for the requested kinds and targets (in its own `executor.toml`, or in the tree's `reef-checks.toml`) in a sandbox (Seatbelt on macOS, bubblewrap on Linux) with no network, no home and nothing of Reef's in view, and returns signed evidence under a session key per job. It runs on a laptop over the socket, or in CI over the remote listener with a token linked to a `ci` identity; `reef executor check` tests the sandbox with escape probes ([ADR 0060](docs/adr/0060-reference-executor.md), [docs/executor.md](docs/executor.md)).
- **Repository policy.** `reef-policy.toml` at a tree's root says whose evidence counts (named sets of identities, actors and authorities, never the change's own session), which evidence kinds a change needs for which paths, size limits, forbidden paths, which areas need a person's sign-off, and conflict tiers, with CEL conditions and free CEL rules. The policy in force is the destination's (`trunk()`), never the change's, and a change to the policy needs its owners' sign-off. `reef policy eval` evaluates it over a change through `PolicyService.EvaluatePolicy` and reports every rule, with the evidence still missing and the sign-offs still needed; `reef policy check` checks a file offline and `reef policy init` writes a starter. The landing service enforces it ([ADR 0061](docs/adr/0061-repository-policy-file.md), [docs/policy.md](docs/policy.md)).
- **Policy simulation.** `reef policy simulate` evaluates a proposed policy (a file, or the one a change proposes) over recent landings, the destination's commits newest first, beside the policy in force, and reports which it would have newly blocked or allowed and why, with blocks caused only by evidence history lacks counted apart. Each call through `PolicyService.SimulatePolicy` is a bounded page ([ADR 0062](docs/adr/0062-policy-simulation.md), [docs/policy.md](docs/policy.md#simulating-a-policy)).
- **Change lifecycle.** A change is a draft until `reef propose` puts it forward for main; its proposer can withdraw it, a reviewer decline it, or another change supersede it, and a withdrawn or declined change can be proposed again. Every transition is an operation in the log and a record that outlives GC, and every change the API returns carries its state, which the web UI colors. `reef proposal list` and `show` read them, and `reef op watch --kind transition` follows a proposal. `reef land` lands a proposal, and the daemon also records one as landed when it reaches `trunk()` another way ([ADR 0063](docs/adr/0063-change-lifecycle.md), [docs/proposals.md](docs/proposals.md)).
- **The landing service, local.** `reef land` asks to land a proposed change onto its bookmark: the policy at the bookmark's head judges the commit that was proposed, and anything but `allow` is refused with the evaluation, which names every evidence object that did not count and why. A change it allows is queued and landed: a fast-forward, or a rebase onto the bookmark's head that must merge cleanly (the paths both sides touched are recorded and in the policy's input, so a policy can ask for fast-forward only), in one operation that moves the bookmark. Every attempt is a record (`reef landing list`, `show`) keeping its evaluation, and the evidence a landing used is kept for good. Landing what policy allows without a request, and asking executors for missing evidence, come next (R3.45) ([ADR 0064](docs/adr/0064-landing-service-local.md), [docs/landing.md](docs/landing.md)).
- **Batching and bisect.** Queued changes land in batches: rebased one on another onto the destination, judged again there, and, under the default `[landing] checks = "batch"`, checked again on the tree they land as, with an executor asked only for the evidence that tree lacks. A passing batch lands in one operation; a failing one is bisected, its passing prefix lands, and the change that broke it returns to its owner with the failing check. `reef landing batches` and `batch` show where each batch is ([ADR 0067](docs/adr/0067-batching-and-bisect.md), [docs/landing.md](docs/landing.md#batches)).
- **Conflict objects.** A conflicted commit reads as data: every term of jj's merge (its sides and bases), the commit each came from, who wrote each side (the provenance records of its change), and every conflicted file with each term's value and, on request, its hunks. jj's conflict label proposes a side's commit and the content decides: a side is `verified` only when a commit related to the conflicted one holds its content at the conflicted paths, so a label cannot pin a side on an unrelated commit. `reef conflict list` and `show` read them through `ConflictService`; nothing is stored, and nothing resolves a conflict yet ([ADR 0065](docs/adr/0065-conflict-objects.md), [docs/conflicts.md](docs/conflicts.md)).
- **Comments and instructions.** `reef comment add` writes a note, or with `--instruction` work for the session that made the change: it is routed to the client session that proposed it, shows an estimate of what Reef recorded (the change's last check run, earlier instructions' agent time, and what Reef cannot see, such as tokens and price), and waits for `reef comment confirm`. The session takes it through a harness hook at the turn's end or the next prompt, `reef mcp`'s `wait_for_operations`, or `reef comment next --wait`, and finishes it by proposing the change again. Reef starts no agent; webhooks that wake a runner come next (R3.46) ([ADR 0069](docs/adr/0069-comments-and-instructions.md), [docs/comments.md](docs/comments.md)).
- **Resolver assignment and queue.** Every conflict a change introduces is assigned to whoever should resolve it: by default the newest live session that recorded the conflicted change, followed to the same agent's next workspace when its harness declares a session. When that agent's session ends, the conflict waits five minutes and joins the repository's resolver queue, ordered by priority then age, from which another agent claims it (`reef conflict claim --next` makes the workspace too); a change Reef never recorded waits for a person, who can also reassign, reprioritize or take any conflict over. `reef status` and MCP's `get_status` name a workspace's assigned conflicts, and each change of an assignment is an operation subscribers see ([docs/conflicts.md](docs/conflicts.md#who-resolves-a-conflict), [ADR 0068](docs/adr/0068-resolver-assignment.md)).
- **Publishing for review.** `reef publish -m <summary>` pushes a change, and the ancestors the remote lacks, to a branch named from its change id (`reef/<id>`) on the repository's git remote, through the daemon with your git credentials and no prompts, and prints the `gh` or `glab` command that opens the pull request as `next`. Publishing again updates the branch; it never pushes to trunk, always leases on where it last saw the branch, and replaces someone else's commit only with `--force`. `--signoff` adds a DCO trailer; MCP's `publish_change` does the same ([ADR 0070](docs/adr/0070-publishing-to-a-git-remote.md), [docs/publishing.md](docs/publishing.md)).

## Install

**Ask your agent.** In the repository you want to use Reef in, give your coding agent (Claude Code, Codex, Cursor, or any agent with a shell) this prompt:

```text
Install Reef from https://github.com/reef-vcs/reef, then run `reef init` in this repository and walk me through anything I still need to do.
```

The agent finds the installer below and runs it. `reef init` then registers the repository, which adds `.jj/` beside git and starts Reef's daemon, and writes Reef's instructions to `AGENTS.md`, plus the files of each agent that reads its own instead: those the repository already has files for, and the agent running `reef init` when Reef recognizes it. Later agent sessions then start in a workspace without being told. In the [onboarding benchmark](docs/onboarding-benchmark.md), Claude Code agents that had never seen Reef, given only that link, installed it and finished a task in a workspace in a median of five or six tool calls (measured before 0.1.0, against a local copy of the installer).

**Or install it yourself.** Prebuilt binaries of the latest release, 0.4.2, are available for macOS and Linux on arm64 and x86_64. The Linux binaries are static, so they run in any container.

```sh
curl -fsSL https://raw.githubusercontent.com/reef-vcs/reef/main/install.sh | sh   # ~/.local/bin, no sudo
brew install reef-vcs/tap/reef
cargo binstall --git https://github.com/reef-vcs/reef reef-vcs reef-daemon
```

The installer checks the tarball against the release's `SHA256SUMS` and never prompts. The binaries are not signed or notarized yet (R4.17). The [quickstart](docs/quickstart.md#install) has the installer's options, the system requirements, and how to verify a tarball's provenance.

To build from source, with Rust 1.97.1 or later: `cargo install --locked --git https://github.com/reef-vcs/reef reef-vcs reef-daemon` installs `reef` and `reef-daemon`, the daemon it runs. It builds `main`, which can be ahead of the release; `reef --version` names the commit. `main` now carries Phase 3's unreleased migrations: read [Unreleased](CHANGELOG.md#unreleased) before running its daemon on an existing state directory. From a checkout, `cargo build --release` builds both into `target/release`. A build from source has no web UI unless you run `just web-build` (Node 24) first; `reef ui` says so. Coming from 0.3, read [Upgrading from 0.3](CHANGELOG.md#upgrading-from-03) first; from 0.2, [Upgrading from 0.2](CHANGELOG.md#upgrading-from-02) as well, and from 0.1, [Upgrading from 0.1](CHANGELOG.md#upgrading-from-01) too.

Once installed, in a git or jj repository, `reef ws run -- <your agent command>` runs an agent in a fresh workspace. `reef` alone prints the [agent guide](docs/agent-guide.md), `reef here` says which workspace you are in and what to do next, and `reef --help` lists the rest. `reef init --check` in CI keeps the files `reef init` wrote current. Output is brief JSON when stdout is not a terminal (`-o json` for every field), and an error with a known fix carries it as `hint` and `next`, a command to run.

## Roadmap

Reef builds on Jujutsu's data model and Rust crates rather than starting clean. Each phase ships something independently useful.

1. **Leased copy-on-write workspaces** (complete, released as 0.1.0). A daemon that creates workspaces via overlayfs or APFS clones, snapshots on a filesystem watcher, heartbeats leases, and reclaims expired workspaces with a final snapshot. Shared dependency store mounting. Ships as a standalone tool against existing git and jj repositories. This alone removes the worktree problem.
2. **Typed API, MCP server, and live state** (complete, released as 0.4.0). Structured status, snapshot, diff, log, and undo over a local socket, with the CLI as a client. Live operation and presence streams. Symbol-level diffs for the first supported languages. A local web UI showing the fleet live.
3. **Evidence objects and landing gate** (in progress: evidence, artifacts, identities and provenance are on `main`). The attestation format, trusted attestor policy, and a landing service that batches rebased proposals, runs checks on the batch head, and bisects on failure. The triage inbox ships here as a web UI, then as a desktop app and as iOS and Android apps, so a human can steer and approve agents from anywhere.
4. **Shared lazy object store.** A store server speaking the native protocol, with lazy fetch into the local cache and federation between stores.
5. **Structural merge.** Tree-sitter based merge, starting from [Mergiraf](https://mergiraf.org), for Python, TypeScript, Go, and Rust.
6. **Protocol specification and conformance suite.** Published once the first four phases have stabilized, so alternative implementations can exist.

## Scope

Reef targets the open ecosystem, not one organization's monorepo. The hub is a protocol anyone can host, trust is declared per repository, and git interop is the adoption path: one person on a team should be able to use Reef against an ordinary GitHub repository nobody else has heard of.

Non-goals: replacing GitHub or any review platform, running builds or tests, or being a hosted service.

## Repository layout

- `crates/reef-error`: the error conventions every crate shares: error kinds, classification, and advice.
- `crates/reef-lib`: core library. Data model, jj-lib embedding, snapshots, operation log, undo.
- `crates/reef-api`: the API schema, `reef.api.v1` (`proto/reef/api/v1`), and its generated Rust clients and servers ([ADR 0029](docs/adr/0029-daemon-api-v1.md)).
- `crates/reef-client`: the thin client of the API, its stable JSON, and how to find the daemon, with no jj-lib ([ADR 0033](docs/adr/0033-thin-client.md)).
- `crates/reef-broker`: bounded in-memory rings that read a log once and fan it out to the streams that follow it, with no jj-lib ([ADR 0038](docs/adr/0038-subscription-broker.md)).
- `crates/reef-symbols`: tree-sitter tag extraction and SCIP normalization for the symbol index ([ADR 0042](docs/adr/0042-symbol-index.md)).
- `crates/reef-evidence`: the evidence format: signed in-toto statements in DSSE envelopes (evidence about a tree, session-key certificates, provenance records), with signing and checking, and no jj-lib ([ADR 0055](docs/adr/0055-evidence-object-format.md)).
- `crates/reef-executor`: the reference executor behind `reef executor`: declarations, tree checks, the sandbox and the claim loop, a client of the daemon with no jj-lib ([ADR 0060](docs/adr/0060-reference-executor.md)).
- `crates/reef-policy`: repository policy: `reef-policy.toml`'s format, Reef's static check and cost bound over its CEL, and the evaluator, with no jj-lib ([ADR 0061](docs/adr/0061-repository-policy-file.md)).
- `crates/reef-web`: the web UI's built assets, embedded in the daemon, or a placeholder page when the UI was not built ([ADR 0047](docs/adr/0047-web-ui-transport-and-local-listener.md)).
- `crates/reef-daemon`: the local service and the `reef-daemon` binary. Workspaces, materialization backends, watchers, leases, garbage collection, shared stores, evidence and artifacts, identities and session keys, provenance records, and the gRPC services.
- `crates/reef-vcs`: the `reef` binary, built on `reef-client` alone, and an umbrella library re-exporting the API and the client.
- `crates/reef-testing`: unpublished test fixtures and the synthetic repository generator.
- `web/`: the web UI app, built into `crates/reef-web` ([ADR 0047](docs/adr/0047-web-ui-transport-and-local-listener.md)).
- `sdk/python` and `sdk/typescript`: the Python and TypeScript SDKs, generated from the API schema ([ADR 0054](docs/adr/0054-sdks.md)).
